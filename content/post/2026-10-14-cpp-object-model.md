对象的创建与销毁，以及 C 与 C++ 在这一层的差异，一并放在这篇里。核心是把两件事分开：标准规定对象如何存在与如何被解释，编译器等实现规定字节怎么摆。绝大多数说法把这两层混在一起，本节先立这条界线。

## 1. 标准在语义层定义对象，不定义布局

标准里对象就是一块存储区域（region of storage），由类型决定如何解释这段字节。标准只保证：

- 同一类型对象的大小不小于其成员之和，并满足对齐要求；
- 同一 access specifier 内的非位域成员，地址按声明顺序递增（`[class.mem]`）；
- 标准布局类型有更严格的保证，包括 pointer-interconvertible、common initial sequence 等。

除此之外，vptr 在哪、基类子对象偏移多少、vtable 长什么样，标准一概不规定。所以「vptr 一定在对象开头」「多继承一定按声明顺序排基类」都是实现行为，不是语言保证。凡是把这两层混着说的结论，都要拆开重述。

---

## 2. 非多态对象的布局

成员按声明顺序放置，中间和末尾可能插入 padding 以满足对齐。空基类优化（EBO）允许空基类子对象占 0 字节，这是实现选择，主流编译器都做。空类对象本身大小至少 1：完整对象必须有非零大小，否则无法区分两个不同对象的地址。

C++20 起 `[[no_unique_address]]` 让空成员子对象也可能不占独立存储，这是标准层面的布局提示，不是不可移植的宏。

---

## 3. 多态对象：vptr 与 vtable

有虚函数的类，典型实现会给对象埋一个隐藏指针（vptr）指向 vtable；vtable 里放虚函数地址、RTTI 指针，以及供 `dynamic_cast`、虚基类使用的偏移。但标准里没有 vptr 这个词，`sizeof` 的结果是实现定义的。

版本变化在这里很关键：C++11 起，对非 trivially copyable 的类型做 `memcpy`，或用 `malloc` 得到的存储直接当对象访问而不开始其生命期，是明确的 UB（`[basic.types]`）。C++11 之前这类代码在实践中「能跑」，但从来不是语言保证。

---

## 4. 虚继承与虚基类

虚基类只保留一份子对象。典型实现用虚基类偏移表（vbtable）描述从当前子对象到虚基类的偏移。初始化规则是重点：虚基类的初始化由最派生类负责，中间类写的初始化器会被忽略（`[class.base.init]`）。这是菱形继承里「最派生类必须直接初始化虚基类」这条规定的来源。

---

## 5. 多继承中的指针调整

把派生类指针转成基类指针时，编译器可能需要给地址加/减一个偏移；虚继承下这个偏移编译期未知，于是通过 vtable 里的偏移项在运行期查。这解释了一个经典现象：同一个对象转成不同基类指针，打印出来的地址可能不一样。而转成 `void*` 不会做这种调整（`[expr.static.cast]` 规定用对象地址）。这是标准行为，不是实现细节。

---

## 6. `dynamic_cast` 与 RTTI

`dynamic_cast` 对多态类型在运行期沿继承图查找，失败时指针返回空指针、引用抛 `std::bad_cast`。RTTI 只有在类有虚函数时才可用：`typeid` 对非多态类型是编译期结果，对多态类型是运行期结果。`-fno-rtti` 关掉 RTTI 后，对多态类型的 `dynamic_cast`／`typeid` 不可用，这是编译器选项而非标准语义。

---

## 7. 平凡性与标准布局

对象模型的另一半是 trivial、standard-layout、POD 这组概念，它们决定能不能安全 `memcpy`、能不能当 C 结构体用。

- trivially copyable 是可 `memcpy` 的前提。C++11 起用它取代 POD 的部分用途。
- POD 在 C++20 起被弃用（`std::is_pod` 已弃用），拆成 trivial 与 standard-layout 两个正交概念。C++11 引入 standard-layout 措辞，C++20 重写了判断规则。
- standard-layout 保证指针往返转换能还原、可以按 common initial sequence 访问，是 C++ 与 C 互操作的受控接口。

## 8. 生命期、创建与销毁

「对象模型」有两层用法：狭义指布局与多态，广义指标准 `[basic]` 下的一整套——对象、子对象、存储、生命期、对齐、类型。`[basic.life]` 就在其中，讲一个对象的生命何时开始、何时结束。所以创建与销毁不是外挂在对象模型旁边的机制，它就是分内事。

几条硬规则：

存储、对象、生命期不是一回事。存储由分配得到，对象的生命期是在这块存储上「开始」的。完全可能存在「有存储、没活对象」的状态：这块存储可以按 `unsigned char` 数组读写，但不能当成一个 `T` 访问。这正是 placement new、`union` 成员切换、`std::launder` 存在的理由。

生命期的开始。对类类型通常由构造函数调用完成。`[class.cdtor]` 规定构造函数体执行期间对象已存在，但基类与成员的初始化可能尚未结束，所以构造函数里调用虚函数只会派发到当前构造层的版本，不会到最派生类。

生命期的结束。析构函数调用是结束信号。析构开始后、结束前对象处于特殊状态，只能做有限操作；析构完成后，自动／静态存储期的存储随之消失，分配来的存储还在，但需要显式结束生命期或重新开始。

存储期与生命期要对齐着看。`[basic.stc]` 定义 automatic、static、thread、dynamic 四种存储期，管存储何时来去；`[basic.life]` 管对象何时在。两者一致是常态，但可以错开。

这一层有公开可观察的后果，也常被考：复用存储后需要 `std::launder` 才能拿到指向新对象的指针；`union` 里非平凡成员的赋值与析构规则在 C++11 起有明确规定，C++20 起放宽了「改变活跃成员时隐式开始生命期」的范围；`memcpy` 非 trivially copyable 的对象是 UB，因为拷出的字节不构成活对象。

### 8.1 隐式创建对象（C++20）

C++20 起，`[intro.object]` 正式引入「隐式创建对象」：某些操作被描述为在一块指定存储区域内隐式创建对象。这类操作会隐式创建并开始零个或多个隐式生命期类型（implicit-lifetime type）对象的生命期，前提是这样做能让程序有定义行为。这是 P0593R6 引入的，并作为缺陷报告追溯适用到 C++98，也就是说它更像「本来就该如此」的澄清而非全新语义。

隐式生命期类型大致包括标量类型、隐式生命期的类类型（聚合体，或有至少一个平凡 eligible 构造且析构平凡的类），以及它们的数组。

关键限定是只创建隐式生命期类型的对象，不会顺带开始那些本身不是隐式生命期类型的子对象的生命期（`[intro.object]` 注 4）。所以往 `unsigned char` 缓冲区里 `memcpy` 一个带非平凡构造的类型，编译器不会代为创建那个对象。

#### 8.1.1 触发隐式创建的操作

- 非常量求值中，开始一个 `unsigned char` 或 `std::byte` 数组的生命期的操作，会在该数组占据的存储区域内隐式创建对象（`std::byte` 自 C++17 起）。
- 分配函数：`operator new`、`operator new[]`，以及 `std::malloc`、`std::calloc`、`std::realloc`、`std::aligned_alloc`（C++17 起）。任何对名为 `operator new`／`operator new[]` 的函数的隐式或显式调用，都会在返回的存储区域隐式创建对象，并返回指向合适创建对象的指针。
- 按对象表示复制的函数：`std::memcpy`、`std::memmove`（C++20 起 `std::bit_cast` 的结果亦然），在目标区域或结果中隐式创建对象。`memcpy` 的适用条件仍是源对象 trivially copyable、目标区域对齐与大小足够。
- C++23 起还有 `std::start_lifetime_as` 与 `std::start_lifetime_as_array`，这两个是显式索取，不是隐式触发。
- 库侧的其他来源：`std::allocator<T>::allocate`、union 类型隐式定义的复制／移动特殊成员函数（见 `[obj.lifetime]`、`[mem.res.public]`、`[bit.cast]`、`[cstring.syn]` 的注）。

另外两类「创建」不属于隐式创建那一节，但常被一起问：隐式改变 `union` 活跃成员时开始该成员的生命期（`[class.union]`），以及从纯右值创建临时对象（`[conv.rval]`/1 所称的 temporary materialization conversion）。`[intro.object]`/1 把对象来源统一列为：定义、new 表达式、隐式创建对象的操作、隐式改变 union 活跃成员、创建临时对象。

#### 8.1.2 两个容易记错的点

读到旧字节不会创建对象。隐式创建只在「某操作被标准描述为隐式创建对象」时发生。`memset` 没有这类条款，读一块 `char` 缓冲区也不会。所以「`memset` 一个 `malloc` 来的对象」这类代码的合法性要落到具体条款，不能想当然。

创建与产出指针是两件事。`[intro.object]`/13 讲隐式创建，/14 讲产出指向合适创建对象（suitable created object）的指针：操作从隐式创建出的对象中选一个，其地址等于存储区域起始地址，并返回指向它的指针。若不存在这样的指针值能让程序有定义行为，行为未定义；若有多个，具体是哪个未指定。

#### 8.1.3 版本差异

- C++20 之前没有这套规则。`malloc` 得到的存储上要使用非平凡类型，必须 placement new；`memcpy` 只能用于 trivially copyable 类型；往 `unsigned char` 缓冲里搬字节再当对象读，严格说是 UB。实践中「能用」，但不是语言保证。
- C++20 起，`malloc` 加写入、`memcpy` 到缓冲区、`operator new` 后直接使用，对隐式生命期类型都被正式覆盖。
- C++23 起 `std::start_lifetime_as` 把这种需求做成了显式 API。
- 常量求值例外：隐式创建被限制在非常量求值中。P0593R6 起初允许常量求值里发生，但会造成不可接受的不确定性，P2747R2 取消了它，并按缺陷报告处理。

## 9. 与 C 的区别

两者都有对象概念，但对生命期的规定程度差一个数量级。

### 9.1 C 的对象模型是扁平的

C 里对象是执行环境中一块数据存储的区域。类型分 object type／function type／incomplete type，对象必须有完整类型。没有子对象、没有基类、没有 vtable、没有 RTTI。对象的同一性由左值承担：左值就是指定一个对象的表达式。

C 有存储期（automatic／static／allocated／thread），但管的是存储，不是生命。C 标准通篇没有「对象生命期从哪开始到哪结束」这种规定。`malloc` 只给出一块存储，往里面写什么由调用者决定；`free` 之后只是不能再访问，没有「生命期已结束」这个正式状态。

C 里最接近「类型与存储关系」的是 effective type 规则：对没有声明类型的对象（典型是 `malloc` 来的），通过左值访问时以用于存储的最后一个左值类型为准。这是 C 独有的，C++ 没有对应物，C++ 用的是 `std::launder` 与对象生命期那套。

### 9.2 C++ 加上的东西

1. 生命期作为一等概念（`[basic.life]`）：对象有开始和结束，存储与对象可分离。
2. 构造与析构：C 里没有「创建对象」这个动作，只有初始化；C++ 的类类型对象靠构造函数开始生命期、析构函数结束生命期，RAII 的一切推论由此而来。
3. 子对象层级：成员子对象与基类子对象的构造／析构顺序有明确规定，虚基类由最派生类初始化。
4. 多态与运行期类型：vtable、`dynamic_cast`、`typeid`。
5. 对齐的形式化：C++11 起有 `alignof`／`alignas`；C 要到 C11 才引入 `_Alignof`／`_Alignas`，之前靠实现约定。
6. 标准布局与 C 互操作：standard-layout 是 C++ 用「与 C 兼容」的直觉反向定义出来的概念，保证二进制布局一致。

### 9.3 实践中最容易踩的差异

- union type punning：C99 起明确允许读非活跃成员时重新解释字节；C++ 里 `union` 长期以来只允许读活跃成员，C++20 起才通过隐式开始生命期的规则放宽一部分。同一段代码在 C 里是标准行为，在 C++ 里要看版本。
- 非平凡类型的内存操作：`memcpy` 一个非 trivially copyable 的 C++ 对象是 UB；C 里没有这层概念，字节就是字节。
- `malloc` 之后：C 里 `malloc` 加写入就是合法使用；C++ 里对非隐式生命期类型，`malloc` 只给了存储，严格说要 placement new 或等隐式生命期规则覆盖（C++20 明确了 `malloc` 隐含创建 implicit-lifetime 类型）。
- 严格别名：两边都有，但判据不同。C 看 effective type，C++ 看对象的实际类型与生命期状态。

### 9.4 一句话

C 的对象模型是「存储 + 类型 + 左值」，不讲生命；C++ 在这之上加了「生命期 + 构造／析构 + 子对象层级 + 多态」，并把与 C 的兼容收缩成 standard-layout 这一个受控接口。本质区别是：C++ 规定了对象什么时候存在，C 只规定了存储和怎么按类型解释它。

## 10. C 的常用行为在 C++ 里的处境

结论先说：C++ 不是 C 的超集，也从不以「把 C 的常用写法都覆盖一遍」为目标。C++ 只承诺一个受控的兼容层——C 兼容头文件（`<cxxx>` 那批）、语言链接（`extern "C"`）、以及布局上与 C 互操作的 standard-layout 类型。除此之外的 C 惯用法，要么在 C++ 里有语义不同的对应物，要么压根没有、只能靠编译器扩展。

### 10.1 语义不同但都有标准的

- 聚合初始化：C89 起就允许「第一个成员之后跳过」的初始化器；C++ 直到 C++20 才引入 designated initializers，且限制更严——只能是直接非静态数据成员、必须按声明顺序、不能嵌套、没有数组设计器（`[dcl.init.list]`）。所以 `struct S s = {.b = 1, .a = 2};` 在 C 里合法，在 C++ 里（即便 C++20）非法。
- `static`：C 里文件作用域 `static` 是内部链接、块作用域 `static` 是持久存储；C++ 里块作用域还有 `static` 局部变量的线程安全初始化（C++11 起），语义已经不同。
- `union`：C99 起明确允许读非活跃成员重新解释字节；C++ 长期只允许读活跃成员，C++20 才通过隐式开始生命期放宽一部分（见 8.1）。
- `malloc` 与字节复制：C 里 `malloc` 加写入、`memcpy` 任意字节都是「字节就是字节」；C++20 才用隐式创建对象和隐式生命期类型把这些惯用法正式覆盖，之前严格说是 UB。
- `thread_local`：C11 用 `_Thread_local`，C++11 用 `thread_local`；类类型的 C++ 版本多了构造／析构，语义不完全对应。

### 10.2 C 有标准、C++ 没有对应物的

- 变长数组（VLA）：C99 是标准；C++ 标准自始至终没有 VLA，GCC／Clang 的 `-std=c++` 下能用只是扩展，`-pedantic` 会警告。要长度运行期决定的数组，C++ 用 `std::vector` 或 `alloca`（后者是非标准扩展）。
- `restrict`：C99 的别名限定符，C++ 标委会多次讨论但未纳入。C++ 编译器只在各自的扩展（`__restrict`／`__restrict__`）里给。
- 复合字面量（compound literals）：C99 的 `(T){...}`，C++ 没有，C++ 用临时对象或具名对象替代，生命周期规则也不同。
- `_Generic`：C11 的类型选择，C++ 用重载／模板／`if constexpr` 等一套完全不同的机制。
- `_Atomic`：C11 的关键字；C++ 用 `std::atomic` 模板，模型也不一样（顺序一致性的默认、`atomic_ref` 等）。

### 10.3 与对象有关的实践：逐条对照

上面两节是语言特性的有无，真正会被问到的是「这些对象相关的惯用法在 C++ 里算不算数」。按结果分三类。

#### 10.3.1 第一类：C++ 有规定，但晚于 C 或与 C 判据不同

| 惯用法 | C 的处境 | C++ 的处境 |
| --- | --- | --- |
| 通过 `unsigned char*`（或 `std::byte*`）读写任意对象的字节 | 标准明确允许用字符类型检查对象表示 | 同样允许；C++17 起 `std::byte` 是更合适的选择 |
| `malloc` 之后直接写入并强制转换使用 | `malloc` 提供可存放任意类型对象的存储 | 仅隐式生命期类型成立（C++20 隐式创建），其余仍需 placement new |
| `memcpy` 复制整个对象 | 对对象逐字节复制，类型不匹配时限制宽松 | 源必须是 trivially copyable；目标区域由 memcpy 隐式创建对象 |
| `union` 类型双关 | C99 起明确允许读非活跃成员 | C++20 才通过隐式开始生命期覆盖一部分 |
| 按 common initial sequence 访问 | 标准有规定 | C++ 有对应规定，但要求 standard-layout |

#### 10.3.2 第二类：C++ 有对应属性，但接口不同

`offsetof` 两边都有，C++ 里对非 standard-layout 类型是条件支持（C++17 起对某些非标准布局类型给了条件定义，其余是实现定义）。聚合初始化两边的设计器规则不同，见 10.1。这些不是「不成立」，是「写法要改」。

#### 10.3.3 第三类：两边都没有明确标准保证的

最典型的是 `container_of` 这类「指针往返 + 成员访问」：从成员指针减回外层对象指针，再访问其他成员。C 里严格说也不是标准保证的行为，各编译器实际支持；C++ 里要配合 `std::launder`（C++17 起）才能拿到指向新对象的可用指针，否则对含 const／引用成员的类这类场景是 UB。

#### 10.3.4 判据的分野

把这些放一起看，结论是 C 与 C++ 在对象实践上的分歧不是逐条规则，而是出发点不同：

- C 从字节与 effective type 出发：存储就是字节，类型通过访问它的左值来判定。
- C++ 从对象、生命期与 provenance 出发：必须存在一个活对象及其类型，指针的来历决定它指向谁；存储复用后是否还需要 `std::launder` 也由这套规则决定。

所以同一段 C 惯用法在 C++ 里的判断路径永远是三问：这里有没有活对象、它有隐式生命期吗、指针的 provenance 对不对得上。三问都能答「是」，写法才成立。

### 10.4 一句话

C++ 与 C 的兼容是受控且单向的：通过 `<cxxx>`、`extern "C"` 和 standard-layout 保证接口能对上，但不去覆盖 C 的全部惯用法。判断一段 C 写法在 C++ 里是否成立，不能靠「看起来一样」，要落到具体条款——见 10.1 和 10.2 的分界，以及与对象有关的实践在 10.3 的三类结果。
