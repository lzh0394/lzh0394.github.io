## 1. 单元测试与测试设计

### 1.1 测试金字塔为何把单元测试放在底层？

- 单元测试只依赖被测代码与少量替身，单次执行通常在毫秒量级，失败时能定位到函数。
- 服务级测试要启动进程与网络栈，端到端测试再叠加前端与外部系统，单次代价依次上升。
- 金字塔的约束在数量比例，常见经验是单元测试占多数，集成测试次之，端到端测试保持少量。
- 倒金字塔的代价在反馈时间与稳定性，端到端测试受网络、时钟与第三方服务影响，容易产生 flaky。
- 金字塔并非通用规则，编译器、内核与图形栈的单元边界难以切分，比例需要按模块调整。
- 判定标准是失败定位成本与修复成本，而非测试层级的名称。
- Google 的测试分类按规模约束资源使用，small 测试禁止网络访问，medium 测试允许本机回环，large 测试可访问外部系统。

### 1.2 一个测试用例的结构应满足哪些约束？

- 常见结构为准备、执行、断言与清理四段，GoogleTest 用 `TEST` 或 `TEST_F` 承载。
- 每个用例验证一个行为，断言失败信息应包含期望值与实际值。
- 用例名应描述行为与条件，例如 `ParseRejectsEmptyInput`，避免 `Test1` 与 `TestParse2`。
- 准备阶段只构造该用例需要的状态，共享夹具中的多余状态会掩盖依赖。
- `ASSERT_*` 失败后立即返回，`EXPECT_*` 继续执行，选择取决于后续语句是否依赖该值。
- 用例之间不得有顺序依赖，`--gtest_shuffle` 可暴露隐式依赖。
- 清理阶段的失败同样需要报告，析构中抛出的异常会导致进程终止。

### 1.3 边界值分析如何选取测试数据？

- 对区间 `[lo, hi]` 取 `lo`、`hi`、`lo - 1` 与 `hi + 1`，再取区间内部的代表值。
- 整数类型要覆盖最小值与最大值，`INT_MIN` 与 `INT_MAX` 附近的运算容易溢出。
- 浮点数要覆盖 0、-0、次正规数、最大有限值、`inf` 与 `nan`，比较语义与整数不同。
- 容器与字符串要覆盖空、单元素、容量边界与扩容点。
- 指针与可选值要覆盖空值与有值两种情况，`std::optional` 的空状态是常用分支。
- 时间与长度参数要覆盖 0、1、最大合法值与超限值，超限路径应返回明确错误。
- 边界组合的数量增长很快，先按等价类压缩，再对关键参数做两两组合。

### 1.4 等价类划分如何处理无效输入？

- 有效等价类中的任一值可代表该类，无效等价类需要单独设计用例。
- 一次只引入一个无效值，多个无效值同时出现时，实现可能只报告第一个错误。
- 无效输入的处理路径包括返回错误码、抛异常、断言终止与未定义行为，测试应明确期望哪一种。
- 参数校验的位置影响划分，前置条件由调用方保证时，测试应验证调试构建下的断言。
- 字符串输入按长度、字符集、编码与终止符划分等价类。
- 数值输入按符号、量级与精度划分，`-0.0` 与 `0.0` 在比较中相等，在序列化输出中可能不同。
- 划分结论应写成表或注释，便于评审时检查遗漏。

### 1.5 （场景）一个函数有多个输入参数时如何设计用例？

- 全组合的数量是各参数取值数的乘积，三个参数各取 5 个值即为 125 条用例。
- 两两组合覆盖所有参数对的取值组合，可用 `PICT` 一类工具生成。
- 参数之间存在约束时需要声明禁止组合，否则生成的用例无法执行。
- 关键参数单独做边界值分析，其余参数取等价类代表值。
- 状态机的输入序列需要覆盖迁移路径，可用 N 切换覆盖或全路径覆盖。
- 用例数量应与缺陷分布匹配，历史缺陷集中的参数组合优先覆盖。
- 组合测试不能替代针对具体缺陷的回归用例。

### 1.6 判定表适合表达哪类测试设计？

- 判定表把条件与动作列成矩阵，每列是一条规则，适合条件之间存在逻辑组合的规格。
- 条件数为 n 时完整判定表有 2 的 n 次方列，可用无关项合并规则。
- 合并时用 `-` 表示该条件不影响结果，合并后仍需至少一条用例覆盖该规则。
- 判定表可直接转换为参数化测试，每行规则对应一组输入与期望输出。
- 规格中的「否则」分支容易被遗漏，判定表要求每条规则都有明确动作。
- 判定表与代码中的条件嵌套结构对应，便于发现不可达规则。

### 1.7 测试替身分为哪几类？

- dummy 只用于填充参数，测试过程中不被调用。
- stub 返回预设值，让被测代码继续执行。
- spy 记录调用信息，断言在动作之后检查。
- mock 预设期望并在调用时验证，违规立即失败。
- fake 提供可工作的简化实现，例如内存仓库或内存文件系统。
- 分类来自 Meszaros 的《xUnit Test Patterns》，术语在不同框架中并不统一。
- GoogleMock 中的 mock 同时承担 stub 与 spy 的职责，分类应按使用方式而非对象类型判断。

### 1.8 （辨析）stub 与 mock 的验证方式有何区别？

- stub 只关心返回值，测试在动作之后断言被测对象的状态或输出。
- mock 关心交互，测试在动作之前声明调用次数、参数匹配器与顺序。
- 交互断言把测试与实现细节绑定，调整调用顺序后测试会失败。
- 状态断言更稳定，但对「是否调用了外部服务」这类副作用无能为力。
- 对写操作与外部请求，交互断言能捕获缺失的调用；对纯函数，状态断言足够。
- 同一测试混用两种断言时，失败信息应能区分返回值错误与调用缺失。
- 用 mock 验证查询类接口通常属于过度约束。

### 1.9 （场景）fake 与 mock 分别在什么情况下更合适？

- 依赖有复杂行为且被多次调用时，fake 更接近真实语义，例如内存数据库。
- fake 需要自己的测试，否则它的缺陷会伪装成被测代码的缺陷。
- mock 适合验证协议层面的交互，例如重试次数、请求顺序与超时处理。
- fake 适合验证业务逻辑，尤其是分页、事务与并发语义。
- fake 的实现应尽量简单，用 `std::map` 或 `std::vector` 承载状态即可。
- 依赖接口频繁变化时，fake 与 mock 都需要同步修改，维护成本应计入设计决策。

### 1.10 单元测试为何不应依赖真实时钟？

- 真实时钟使结果依赖执行速度与机器负载，超时类断言在不同环境下的结论不同。
- 依赖 `std::chrono::system_clock::now()` 的代码无法稳定测试跨天、跨时区与夏令时行为。
- 注入时钟接口可把时间变成可控输入，常见做法是传入返回 `time_point` 的可调用对象。
- 超时逻辑可用条件变量配合模拟时钟验证，避免测试真的等待数秒。
- 时间相关断言应留出余量，或改为断言调用次数与顺序。
- 日志与指标的时间戳同样应可注入，否则输出无法做基准比对。

### 1.11 如何为在构造函数中直接申请资源的类建立可测试性？

- 构造函数中直接 `new` 或打开文件，使对象无法在测试中构造出失败路径。
- 把资源获取移出构造函数，改为接受抽象接口或工厂函数。
- 必须保留构造函数语义时，可用两阶段初始化并提供返回错误的工厂函数。
- 内存分配失败路径可用注入分配器测试，替身可模拟 `std::bad_alloc`。
- 资源释放由 RAII 负责，析构中的失败无法用异常报告，需要记录或终止。
- 改造的代价是增加一层间接，应评估调用点数量与热路径影响。

### 1.12 可测试性设计有哪些可操作的手段？

- 依赖以参数或构造函数传入，避免在实现内部构造具体类型。
- 纯函数优先，把 I/O 与状态变更推到边界。
- 全局状态改为显式上下文对象，减少测试之间的相互影响。
- 时间、随机数、文件系统与环境变量通过接口注入。
- 模块提供细粒度入口，避免只能通过 `main` 触发整条链路。
- 错误路径用返回值或异常明确表达，避免静默失败。
- 构建系统允许单独链接模块的测试目标，避免测试依赖整个可执行文件。

### 1.13 测试中的随机数据如何保证可复现？

- 使用固定种子初始化伪随机数引擎，失败时输出种子。
- `std::mt19937` 的输出序列由标准规定，跨标准库实现一致；`std::random_device` 的结果不可复现。
- 属性测试框架通常支持保存失败用例，并在下次运行中按种子重放；C++ 中可用 `RapidCheck` 一类库实现。
- 随机数据应配合收缩，把失败输入化简为最小样例。
- 随机测试应记录生成参数，包括区间、分布与迭代次数。
- 时间与并发相关的随机性无法靠种子固定，需要额外注入调度点。

### 1.14 一个测试应当断言几件事？

- 一个测试对应一个行为，断言数量可以多于一个，但应围绕同一行为。
- 多个断言失败时框架通常只报告第一个，定位成本随之上升。
- 参数化测试可把同一行为的多组数据拆成独立用例，失败时按参数命名。
- 断言之间若有依赖，应使用 `ASSERT_*` 提前返回，避免后续断言读到无效状态。
- 对输出集合的断言应比较完整结构，避免只检查首元素。
- 断言消息应包含输入，失败时无需重新构造数据。

### 1.15 （场景）flaky 测试的根因如何分类与处理？

- 时序类：依赖 `sleep` 等待异步结果，负载高时超时；应改为等待条件或事件。
- 顺序类：用例共享全局状态或文件，执行顺序变化导致失败；应让每个用例使用独立夹具。
- 并发类：数据竞争导致偶发失败，可用 ThreadSanitizer 复现。
- 环境类：依赖端口、临时目录、网络与外部服务，应固定资源或使用替身。
- 随机类：未固定种子或依赖哈希顺序，应固定种子并避免依赖容器遍历顺序。
- 资源类：文件句柄、内存与线程未释放，长时间运行后失败。
- 处理策略是先隔离再修复，长期保留的 flaky 测试会使真实失败被忽略，通常应标记并限期修复。

### 1.16 单元测试的执行时间应控制在什么范围？

- 单个用例通常在毫秒量级，整个单元测试集在数十秒内完成，才能支持频繁运行。
- 超过阈值的用例应检查是否做了真实 I/O、启动子进程或等待网络。
- 测试集按标签分层，快速集在提交前运行，慢速集在合并队列运行。
- 测试并行执行可缩短墙钟时间，共享资源的用例需要隔离。
- 构建时间常被忽略，测试目标的链接依赖应尽量少。
- 时间指标应记录趋势，逐步变慢通常意味着依赖范围扩大。

### 1.17 测试夹具的生命周期如何管理？

- `SetUp` 在每个用例前执行，`TearDown` 在用例后执行，二者与构造、析构并不同步。
- 构造函数适合做不会失败的准备，`SetUp` 可调用 `ASSERT_*` 并在失败时跳过用例。
- 夹具析构在 `TearDown` 之后执行，清理顺序与构造顺序相反。
- 共享的昂贵资源可用 `SetUpTestSuite` 创建，但会引入用例间依赖。
- 夹具成员在每个用例中应处于确定状态，避免上一用例的残留。
- 夹具继承层次过深会降低可读性，组合优于继承。

### 1.18 golden 文件适合什么场景？

- 输出结构复杂且人工编写期望值成本高时，可保存一份经过评审的基准输出。
- 基准文件应纳入版本控制，变更时在评审中可见。
- 失败时框架输出差异，更新基准必须人工确认并纳入评审。
- 基准输出包含时间戳、路径与随机标识时，需要先归一化。
- 跨平台换行与浮点格式化差异会导致基准不一致，比较前应统一格式。
- 基准文件容易演变为看到差异就更新，需要配合来源说明与抽查。

### 1.19 参数化测试如何设计命名与失败定位？

- `INSTANTIATE_TEST_SUITE_P` 为每组参数生成独立用例，名称由参数生成器决定。
- 参数生成器应提供可读名称，例如输出 `input=3, expect=9`。
- 参数数量过大时报告会冗长，可按类别拆成多个参数化套件。
- 参数化测试适合同一逻辑的多组数据，不适合流程不同的场景。
- 失败信息应包含参数索引与参数值，便于复现。
- 生成器可用 `Values`、`Combine` 与 `Range` 组合，夹具与普通测试相同。

### 1.20 测试代码的重复是否应当消除？

- 测试代码同样需要维护，重复的准备逻辑在接口变化时会成倍修改。
- 提取夹具与辅助函数可减少重复，过度抽象会隐藏用例的实际输入。
- 辅助函数应保持直白，避免在断言外再包一层断言。
- 测试中的魔法值应命名，便于说明其来源。
- 复用生产代码的辅助函数要谨慎，共享缺陷会让测试与实现一起出错。
- 三个以上用例重复同一段准备逻辑时再提取，过早抽象的成本高于重复。

## 2. mock 与依赖注入

### 2.1 为什么接口抽象是可替换依赖的前提？

- 依赖以具体类型出现时，测试无法在不修改生产代码的情况下替换实现。
- 抽象基类与纯虚函数提供运行期替换点，模板参数与 `std::function` 提供编译期替换点。
- 抽象应围绕行为划分，接口方法对应调用方的需求。
- 抽象基类需要虚析构函数，否则通过基类指针删除派生对象是未定义行为。
- 接口应尽量窄，宽接口迫使替身实现大量无关方法。
- 抽象会阻止部分内联优化，热路径上需要评估间接调用的代价。

### 2.2 虚接口、模板参数与 `std::function` 三种注入方式如何取舍？

- 虚接口适合运行期选择实现、跨模块边界与插件场景，代价是虚调用与对象生命周期管理。
- 模板参数适合编译期确定实现，可 inline 展开，代价是头文件暴露实现细节与编译时间上升。
- `std::function` 适合单一回调，灵活但可能有堆分配与间接调用开销。
- 模板与 `std::function` 使实现在头文件中可见，ABI 稳定性较差。
- 虚接口配合 `final` 可由编译器去虚拟化，在实现可见的范围内消除虚调用。
- 测试中三种方式都可替换，模板方式需要不同实例化，虚接口方式用派生替身。

### 2.3 mock 的边界在哪里？

- mock 适合验证跨进程、跨网络与跨模块的交互要求，例如请求次数、参数与顺序。
- 被测代码内部的数据结构不应 mock，替身只会重复实现缺陷。
- 标准库类型不应 mock，`std::vector` 与 `std::string` 的行为由标准规定，替身会引入偏差。
- 第三方库的稳定接口可用薄封装隔离后再替换，直接 mock 其头文件中的类型容易随版本失效。
- 交互断言越具体，测试与实现耦合越紧，重构时失败率越高。
- 边界的选择标准是变化频率与该依赖是否属于被测职责。

### 2.4 （辨析）构造函数注入与 setter 注入有何差异？

- 构造函数注入保证对象创建后依赖已就绪，成员可声明为引用或 `const` 成员。
- setter 注入允许后续替换，代价是对象存在依赖未设置的中间状态。
- 构造函数注入使依赖关系显式，构造参数超过四五个时说明职责过多。
- setter 注入适合可选依赖与测试专用替换点，需要在文档中说明默认值。
- 构造函数注入与继承配合时，基类构造需要转发依赖，层次深时参数列表会膨胀。
- 成员按声明顺序初始化，构造函数注入要注意成员的声明次序。

### 2.5 （场景）全局单例如何改造成可注入的对象？

- 单例的问题在于调用点隐式获取依赖，测试无法替换，也无法并行创建多个实例。
- 第一步把单例的获取点收敛到少数函数，统计调用点数量。
- 第二步把单例的接口抽成抽象基类，原实现派生自该接口。
- 第三步在构造链上传递接口引用，从进程入口传到使用点。
- 过渡期可保留默认实现的访问器，仅在 `main` 中初始化，测试中替换。
- 全局状态改为显式上下文后，初始化顺序问题随之消失。
- 改造代价与调用点数量成正比，可用适配器先包一层再逐步迁移。

### 2.6 （陷阱）`EXPECT_CALL` 的匹配与顺序如何影响结果？

- 同一方法的多个 `EXPECT_CALL` 按后声明先匹配的顺序尝试，先匹配到的规则生效。
- 未声明 `Times` 时，既无 `WillOnce` 也无 `WillRepeatedly` 的期望默认按一次处理，多次调用需要显式声明次数。
- `InSequence` 与 `Sequence` 约束跨 mock 的调用顺序，未声明的调用在验证时报错。
- `ON_CALL` 设置默认行为，`EXPECT_CALL` 设置期望，两者冲突时期望优先。
- `StrictMock` 把未声明的调用变成失败，测试对实现变化过于敏感。
- `NiceMock` 抑制未预期调用的告警，适合只关心部分交互的场景。
- 验证发生在 mock 析构或 `VerifyAndClearExpectations` 调用时，提前清理可分段验证。

### 2.7 过度 mock 会带来哪些维护代价？

- 每个 mock 都复制一份接口签名，接口变化时全部需要修改。
- 交互断言把调用顺序写进测试，重构内部实现时测试大面积失败。
- mock 返回值由测试手工构造，容易与真实实现的语义偏离。
- 大量 mock 使准备代码超过被测逻辑，阅读成本上升。
- 测试通过而集成失败，说明 mock 掩盖了协议或时序差异。
- 减少 mock 的手段包括收窄接口、改用 fake、把交互测试上移到集成层。

### 2.8 如何为 mock 配置返回值与副作用？

- `ON_CALL` 设置默认动作，`WillOnce` 与 `WillRepeatedly` 设置调用序列。
- `Return`、`ReturnRef`、`Throw` 与 `Invoke` 是常用动作，`Invoke` 可调用 lambda 模拟副作用。
- 返回引用时要注意生命周期，`ReturnRef` 绑定的对象必须比调用活得久。
- 多次调用返回不同值时用 `WillOnce` 链，次数用尽后的调用属于超预期调用，需要 `WillRepeatedly` 提供兜底。
- 需要修改传入参数时用 `SetArgReferee` 或 `Invoke`，避免在 mock 中写复杂逻辑。
- 动作中抛出的异常沿调用栈传播，可用于测试异常安全路径。

### 2.9 依赖注入容器在 C++ 中是否必要？

- C++ 缺少反射，容器通常依赖显式注册与类型擦除，配置在启动阶段完成。
- 小型项目用工厂函数与构造参数即可，容器会增加间接层与启动期错误。
- 容器适合对象图较大、生命周期分层的场景，例如按请求创建的作用域对象。
- 注册顺序与解析顺序不一致时，错误要到运行期才暴露，需要启动自检。
- 常用库有 `Boost.DI` 与 `Fruit`，绑定可以落在编译期模板或运行期注册，选型时要确认错误检查发生在哪个阶段。
- 容器的代价是调试困难，构造失败时的调用栈不直观。

### 2.10 如何测试调用了非虚成员函数的代码？

- 非虚成员函数无法通过派生类替换，需要改动设计或使用链接期替换。
- 把该函数的行为抽成可注入的接口是最直接的做法。
- 若函数属于第三方库，可用薄封装层隔离，在测试中替换封装对象。
- `#define private public` 一类技巧破坏封装，在不同标准库实现下不可靠。
- 链接期替换用同名符号覆盖，依赖链接顺序，在静态链接与 LTO 下容易失效。
- 生产代码无法修改时，只能在集成测试层覆盖该路径。

### 2.11 如何 mock 第三方 C 库？

- C 库以自由函数暴露，替换方式包括链接期替换、函数指针表与封装层。
- 封装层把库函数包装成类方法，测试替换封装对象，生产代码不直接调用库函数。
- 链接期替换要求测试提供同名符号，链接器按顺序解析。
- `--wrap=symbol` 让链接器把对 `symbol` 的引用重定向到 `__wrap_symbol`，原函数通过 `__real_symbol` 访问。
- 函数指针表适合库本身提供回调注册的接口。
- 封装层的代价是一次间接调用与额外的头文件依赖。

### 2.12 时间与时区的注入如何设计？

- 定义时钟接口，返回 `std::chrono::time_point`，生产实现包装 `system_clock` 或 `steady_clock`。
- 测试实现返回固定时间或按调用递增，便于验证超时与过期逻辑。
- 时区处理可用 `std::chrono::zoned_time` 与 `locate_zone`（C++20），避免依赖进程全局时区。
- 依赖 `TZ` 环境变量的代码在测试中需要设置与恢复，进程级状态会影响并行用例。
- 日期边界测试要覆盖月末、闰年与夏令时切换点。
- 时钟精度与单调性需要区分，超时逻辑应使用单调时钟。

```cpp
struct Clock {
    virtual ~Clock() = default;
    virtual std::chrono::system_clock::time_point now() const = 0;
};

class TokenCache {
public:
    explicit TokenCache(const Clock& clock) : clock_(clock) {}
    bool expired(const Token& token) const {
        return clock_.now() > token.deadline;
    }
private:
    const Clock& clock_;
};
```

### 2.13 如何验证某个依赖没有被调用？

- GoogleMock 用 `EXPECT_CALL(mock, foo()).Times(0)` 声明零次调用，任何调用都失败。
- `StrictMock` 下未声明的调用直接失败，但会影响同一对象上的其他期望。
- 用 spy 记录调用计数，在动作后断言计数为零，失败信息更直接。
- 负向断言只能说明已覆盖的路径未调用，覆盖面有限。
- 对资源释放类接口，未调用通常意味着泄漏，应配合析构检查。
- 负向断言容易在重构后失效，需要与正向用例成对维护。

### 2.14 mock 对象的所有权与生命周期如何安排？

- mock 通常是栈对象，测试结束时析构并验证期望。
- 被测对象若持有依赖的引用，mock 必须比被测对象活得久。
- 用 `std::unique_ptr` 持有 mock 时，析构顺序由声明顺序决定，需要显式控制。
- 依赖以 `shared_ptr` 传递时，mock 的销毁时机不确定，验证点应显式调用。
- 循环引用会导致泄漏，mock 与生产对象都可能参与循环。
- 夹具中把 mock 声明在被测对象之前，可保证后者先析构。

### 2.15 如何用替身测试异常传播路径？

- 替身的动作抛出自定义异常，验证被测代码是否正确转换或回滚。
- 异常安全测试要检查资源是否释放，可配合计数型分配器。
- 构造函数抛异常时，已构造的成员按逆序析构，测试可验证析构次数。
- `noexcept` 函数中抛出异常会调用 `std::terminate`，这类路径只能用死亡测试验证。
- 死亡测试在子进程中执行，`EXPECT_DEATH` 匹配标准错误输出，代价较高。
- 异常类型应使用专门的错误类型，避免捕获 `...` 掩盖问题。

### 2.16 接口抽象过细会带来哪些代价？

- 每个方法一个接口会导致实现类数量膨胀，测试替身同步增加。
- 细接口使调用链变长，调试时需要跨多个对象追踪。
- 抽象边界与模块边界不一致时，依赖图容易出现环。
- 接口应按调用方的使用方式划分，而非按实现类的成员划分。
- 过细的抽象还会阻碍优化，间接调用难以 inline 展开。
- 发现多个接口总是一起使用时，就是合并的时机。

### 2.17 （实现）链接期替换有哪些风险？

- 链接期替换依赖符号解析顺序，静态库与目标文件的顺序变化会改变结果。
- inline 展开后的函数没有符号可供替换，`-O2` 下替换可能静默失效。
- LTO 会跨翻译单元优化，替换点可能被消除。
- 替换符号的签名必须完全一致，C++ 的名称修饰使签名不匹配时链接失败。
- 同一符号在多个库中出现时，替换会影响所有调用方。
- 动态链接场景可用 `LD_PRELOAD` 替换，只影响动态符号，且平台相关。

### 2.18 测试耦合有哪些表现？

- 修改生产代码的内部结构导致大量测试失败，说明测试依赖实现细节。
- 测试之间通过全局状态、文件或数据库相互影响。
- 测试依赖执行顺序或真实时间。
- 测试直接访问私有成员，重构时同步失效。
- 测试断言日志文本或异常消息的全部内容，文案调整即失败。
- 降低耦合的手段是断言可观察行为、用接口隔离依赖、避免共享可变状态。

### 2.19 mock 测试与集成测试的边界如何划分？

- mock 测试验证单元内部的逻辑分支与交互要求。
- 集成测试验证真实依赖下的协议、序列化与事务语义。
- 两者的重叠部分通常是错误处理路径，mock 覆盖罕见错误，集成测试覆盖常见路径。
- 只做 mock 测试会漏掉 ABI、序列化格式与超时配置问题。
- 只做集成测试会拖慢反馈，并难以覆盖错误分支。
- 划分标准是缺陷类型：逻辑缺陷用 mock，接口缺陷用集成。

### 2.20 依赖注入如何与性能敏感代码共存？

- 热路径上的虚调用与间接调用会阻止 inline 展开，影响指令缓存与分支预测。
- 可在模块边界注入，内部循环使用具体类型。
- 模板参数可在编译期绑定实现，保留 inline 展开的机会。
- 运行期多态可用 CRTP 或 `std::variant` 加 `std::visit` 替代虚函数。
- 注入带来的对象体积增大会影响缓存局部性，需要评估。
- 测试专用注入点用条件编译排除时，构建配置数量会上升。

## 3. 模糊测试与属性测试

### 3.1 模糊测试与属性测试各解决什么问题？

- 模糊测试通过变异输入寻找崩溃与超时，侧重内存安全与健壮性。
- 属性测试通过随机生成输入验证不变式，侧重逻辑正确性。
- 模糊测试的判定标准是进程异常终止，需要 sanitizer 配合捕获未定义行为。
- 属性测试的判定标准是属性是否成立，失败时给出反例。
- 二者都依赖输入生成与失败复现，工程上可共用语料与最小化流程。
- 模糊测试适合解析器、编解码器与协议栈，属性测试适合数据结构与算法。

### 3.2 libFuzzer 的入口函数如何编写？

- 入口签名为 `extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size)`。
- 函数内根据 `data` 与 `size` 构造输入，调用被测接口并返回 0。
- 函数不得保留跨调用的状态，全局缓存会使后续输入的行为依赖历史。
- 输入过短时直接返回，避免空输入消耗执行预算。
- 目标以 `-fsanitize=fuzzer,address` 编译，运行时自动完成变异与覆盖收集。
- 长时间运行应设置 `-max_total_time` 与 `-rss_limit_mb`，避免占满资源。
- 崩溃输入自动写入当前目录，文件名以 `crash-` 开头。

```cpp
#include <cstddef>
#include <cstdint>

extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size) {
    if (size < 4 || size > 4096) return 0;
    Decoder decoder;
    decoder.decode(reinterpret_cast<const char*>(data), size);
    return 0;
}
```

### 3.3 （实现）AFL++ 的插桩与运行方式有何特点？

- AFL 在编译期插桩并记录边覆盖，`afl-clang-fast` 使用 LLVM pass，`afl-gcc` 使用汇编级插桩。
- 输入可来自文件或共享内存，命令行中的 `@@` 表示输入文件路径。
- 首次运行使用 `afl-fuzz -i corpus -o out -- ./target @@`，语料目录中的样本作为种子。
- AFL++ 支持持久模式 `__AFL_LOOP`，避免每次 fork，提高执行速度。
- 并行模糊测试用 `-M` 与 `-S` 指定主从角色，共享输出目录。
- 崩溃默认按执行路径去重，接入符号化工具后可再按调用栈归并。
- QEMU 模式用于无源码场景，速度明显低于插桩模式。

### 3.4 语料库如何构建与裁剪？

- 种子应覆盖主要格式分支，来源包括单元测试、文档示例与真实样本。
- 语料过大拖慢启动与变异调度，需要按覆盖率裁剪。
- `-merge=1` 把多个语料目录合并，只保留带来新覆盖的样本。
- 样本体积影响变异效率，大文件应精简到最小可解析长度。
- 语料需要版本控制与来源记录，避免引入含敏感数据的样本。
- 定期回放语料可发现回归，语料本身就是回归测试集。

### 3.5 字典与自定义变异器在什么情况下有用？

- 字典提供关键字与魔数，帮助模糊器穿过格式校验，用 `-dict=file.dict` 加载。
- 字典条目格式为 `"value"` 或 `name="value"`，适用于协议字段与文件头。
- 自定义变异器适合结构化输入，`LLVMFuzzerCustomMutator` 可保持格式合法。
- 结构感知变异器能提高深层路径的命中率，代价是实现复杂。
- 对压缩或加密输入，先解压再模糊测试，或在变异后重新编码。
- 字典与变异器都需要随格式演进而维护。

### 3.6 覆盖率引导如何决定变异方向？

- 模糊器记录边覆盖，新的覆盖特征会进入队列作为后续变异的种子。
- 覆盖特征包括边、边执行次数的分桶与值剖面（value profile）。
- 值剖面记录比较指令的操作数，帮助通过魔数比较。
- 队列调度策略影响探索效率，AFL 按执行速度与稀有度分配能量。
- 覆盖饱和后需要更换策略或增加字典，否则执行次数增加而覆盖停滞。
- 插桩粒度会改变覆盖统计，粗粒度插桩低估新路径。

### 3.7 崩溃如何去重与分级？

- 去重键可用崩溃地址、调用栈哈希或 sanitizer 报告中的类型与位置。
- 同一缺陷在不同输入下可能产生不同栈，符号化后按顶层帧归并。
- 分级依据包括可利用性、影响范围与能否在发布构建复现。
- ASan 报告中的 `SEGV` 与 `heap-buffer-overflow` 应分别归类。
- 超时与内存耗尽同样属于缺陷信号，需要单独的判定策略。
- 去重结果进入缺陷跟踪系统，并保留最小复现输入。

### 3.8 如何为模糊测试目标设置资源限制？

- libFuzzer 用 `-timeout` 设置单次执行秒数，`-rss_limit_mb` 限制常驻内存，`-max_len` 限制输入长度。
- 超时判定依赖看门狗线程，阻塞在系统调用中的目标可能无法被及时终止。
- AFL 用 `-t` 设置超时，`-m` 设置内存上限，`-m none` 关闭限制。
- 容器中运行需要预留内存，否则 OOM killer 会终止进程而非报告缺陷。
- 长时间运行用 `-max_total_time` 限制，由定时任务承载。
- 限制过松会掩盖泄漏，过紧会把正常输入判为超时。

### 3.9 模糊测试目标应做多少输入校验？

- 目标先拒绝明显不合法的输入，避免准备阶段消耗执行预算。
- 校验不应掩盖被测代码的缺陷，例如把解析失败一律当作正常返回。
- 长度检查应放在构造容器之前，防止分配超大内存。
- 对递归结构要限制深度，避免栈溢出被误判为目标缺陷。
- 目标中不应捕获所有异常后静默返回，否则缺陷被吞掉。
- 目标不应调用 `exit` 或终止进程，框架依赖函数返回来继续执行。

### 3.10 结构感知模糊测试如何处理复杂格式？

- 一种做法是先生成语法树再序列化，变异在语法树上进行。
- `libprotobuf-mutator` 用 protobuf 描述输入结构，自动生成变异器。
- 另一种做法是提供校验与修复函数，把变异后的输入修正为合法格式。
- 也可分阶段模糊测试，先测词法层再测语法层。
- 结构感知降低无效输入比例，但会缩小探索空间，需要保留一部分原始字节变异。
- 复杂格式的种子构造成本高，通常从规范与真实样本中提取。

### 3.11 属性测试如何选取不变式？

- 不变式应来自规格而非实现，例如排序后相邻元素有序。
- 常见属性包括往返、幂等、交换律、结合律与单调性。
- 往返属性适合序列化与编解码，`decode(encode(x)) == x` 在合法输入域内成立。
- 参照实现属性用简单实现作为判定基准，适合优化前后的等价性验证。
- 元性质描述输入变换与输出变换的关系，例如缩放输入后结果按比例变化。
- 属性过弱时测试通过而缺陷仍在，过强时会频繁误报。

### 3.12 收缩如何工作？

- 收缩在失败后对输入做系统化简化，直到找不到更小的失败输入。
- 简化操作包括删除元素、缩小数值、缩短字符串与合并分支。
- 收缩要求属性可判定，且失败原因保持一致，否则会收缩到无关缺陷。
- 收缩的代价是重复执行被测代码，复杂属性上耗时明显。
- 收缩结果写入失败报告，并作为回归用例保存。
- 部分框架支持按结构收缩，例如对容器与树逐层简化。

### 3.13 如何测试解析与序列化的往返属性？

- 对合法输入，`parse(serialize(x))` 应等于 `x`，比较需要定义等价关系。
- 浮点数与哈希容器需要特殊处理，逐位相等往往过强。
- 对非法输入，解析应返回错误并保持进程存活，可用模糊测试补充。
- 序列化格式的稳定性应单独测试，用固定字节序列作为基准。
- 往返测试要覆盖空值、极值与嵌套结构。
- 旧版本需要解析新版本输出时，往返属性要加入版本参数。

### 3.14 如何为比较函数测试排序属性？

- 排序结果的属性包括有序性、元素多重集不变与长度不变。
- 比较器必须满足严格弱序，违反时 `std::sort` 可能越界访问，属于未定义行为。
- 可用随机数据断言 `comp(a, a)` 为假、`comp(a, b)` 与 `comp(b, a)` 不同时为真。
- 传递性检查的复杂度是三次方，样本规模需要控制。
- 属性测试适合发现比较器在相等元素上的不一致。
- 稳定性需要单独验证，`std::stable_sort` 与 `std::sort` 的语义不同。

### 3.15 属性测试的随机源与可复现性如何保证？

- 固定种子可复现，失败时应输出种子与迭代序号。
- 生成器应覆盖边界值，均匀分布难以命中极端输入。
- 可用偏置生成器提高零值、最小值与最大值的出现频率。
- 收缩后的反例比原始随机输入更稳定，应优先保存。
- 依赖系统随机源的生成器无法复现，测试中应禁用。
- 迭代次数与时间预算需要配置，持续集成中通常限制迭代数。

### 3.16 模糊测试如何接入持续集成？

- 短时运行放在每次合并请求，长时运行放在定时任务。
- OSS-Fuzz 提供持续模糊测试服务，项目需要提供 `build.sh` 与目标入口。
- 持续集成中应保存语料与崩溃样本，作为缓存跨运行复用。
- 回归用例包括历史崩溃输入，确保修复后不再复现。
- 覆盖率报告可上传到代码托管平台，跟踪覆盖趋势。
- 资源开销需要限额，模糊测试任务通常使用独立执行器。

### 3.17 模糊测试如何发现内存泄漏？

- AddressSanitizer 中的 LeakSanitizer 在进程退出时检查未释放内存。
- libFuzzer 在同一进程内多次调用，泄漏会累积并触发 `-rss_limit_mb`。
- 单次少量泄漏在长期运行中表现为内存增长，需要按输入定位。
- 可在目标中重置全局状态，避免状态累积掩盖泄漏。
- 检测泄漏时应减少框架自身缓存，防止分配噪声干扰判定。
- 修复后应把触发输入加入回归语料。

### 3.18 如何区分输入非法与实现缺陷？

- 规格应明确哪些输入属于前置条件违反，哪些属于必须处理的错误。
- 目标在输入非法时应正常返回，在实现缺陷时应崩溃或被 sanitizer 捕获。
- 断言用于检查内部不变式，前置条件检查用于拒绝外部输入，二者位置不同。
- 模糊测试中把断言失败视为缺陷，把返回错误视为正常。
- 输入校验缺失时，非法输入会走到底层并触发未定义行为，这类崩溃属于实现缺陷。
- 报告需要记录判定依据，避免把设计约束当成缺陷上报。

### 3.19 差分测试适用于哪些场景，有哪些陷阱？

- 差分测试比较两个实现的输出，适合编译器、序列化库与算法重写。
- 参照实现可以是旧版本、另一语言实现或规范模型。
- 两者都允许的行为差异需要显式排除，否则误报率高。
- 未定义行为上的差异不构成缺陷，测试应限制在定义良好的输入域。
- 浮点结果需要容差比较，否则舍入差异被判为失败。
- 差分测试无法发现两个实现一致的错误。

### 3.20 模糊测试的收益如何度量？

- 指标包括执行速度、边覆盖率、新发现缺陷数与缺陷去重率。
- 覆盖率增长曲线趋于平坦，说明需要新种子或新策略。
- 缺陷密度按代码行或按接口统计，便于比较模块。
- 回归语料的数量与命中率反映长期价值。
- 单次执行代价与可并行度决定总吞吐。
- 收益评估应结合缺陷严重性，低危崩溃的数量不能代表质量提升。

## 4. 覆盖率与变异测试

### 4.1 行覆盖率的局限是什么？

- 行覆盖只记录某行是否执行，不区分分支与条件组合。
- 一行中的短路求值可能只执行部分子表达式，行覆盖仍计为已覆盖。
- 异常路径与 `catch` 块容易被遗漏，行覆盖无法体现异常传播。
- 模板实例化与头文件中的代码会重复计算，统计口径需要统一。
- 行覆盖达到 100% 仍可能遗漏边界值与错误处理。
- 行覆盖率适合作为下限指标，不适合作为质量结论。

### 4.2 分支覆盖率与行覆盖率有何差异？

- 分支覆盖要求每个判定取真与取假都执行过，行覆盖只要求语句执行。
- 对 `if (a && b)`，分支覆盖要求整个判定的两种结果，不要求 `a`、`b` 的每种组合。
- 循环的零次与多次执行都计入分支覆盖。
- `switch` 的每个 `case` 与 `default` 属于分支。
- 分支覆盖通常低于行覆盖，差距反映未测试的条件方向。
- 具体统计方式由实现定义，`gcov`、`llvm-cov` 与商业工具的口径并不完全一致。

### 4.3 （辨析）条件覆盖与分支覆盖有何区别？

- 条件覆盖要求每个原子条件取真与取假，分支覆盖只要求判定结果。
- 对 `if (a && b)`，条件覆盖需要 `a` 为真、`a` 为假、`b` 为真、`b` 为假四种情况。
- 分支覆盖可用 `a=false` 与 `b=false`、`a=true` 与 `b=true` 两组满足，条件覆盖则不足。
- 条件覆盖不保证判定结果被覆盖，可能出现条件都取过而判定只取一种结果的情况。
- 条件/判定覆盖同时要求两者。
- 航空与汽车领域的标准对覆盖等级有明确规定，DO-178C 与 ISO 26262 的要求不同。

### 4.4 MC/DC 的定义与适用标准是什么？

- 修正条件/判定覆盖要求每个原子条件都能独立影响判定结果。
- 对 n 个条件的判定，MC/DC 至少需要 n+1 组测试用例。
- 独立性要求固定其他条件，改变目标条件时判定结果随之改变。
- MC/DC 比条件/判定覆盖更强，能发现条件之间的耦合缺陷。
- DO-178C 的 Level A 要求 MC/DC，Level B 要求判定覆盖。
- 手工构造 MC/DC 用例容易遗漏，可借助工具生成。

### 4.5 覆盖率数据如何采集？

- GCC 用 `-fprofile-arcs -ftest-coverage` 生成 `.gcno` 与 `.gcda`，由 `gcov` 或 `lcov` 汇总。
- Clang 用 `-fprofile-instr-generate -fcoverage-mapping` 生成 `.profraw`，`llvm-profdata merge` 后由 `llvm-cov report` 读取。
- 插桩会改变代码布局与执行速度，覆盖率构建不应与发布构建混用。
- 多进程测试需要为每个进程指定独立的 profile 输出路径，否则数据互相覆盖。
- 合并多次运行的 profile 数据才能得到完整覆盖。
- 覆盖率数据应与源码版本绑定，否则行号错位。

### 4.6 覆盖率数据为什么会失真？

- 优化级别影响插桩，`-O2` 下部分代码被合并或消除，行号映射不准确。
- 模板与头文件中的代码在每个实例化处计为独立区域，汇总方式影响百分比。
- inline 函数的覆盖归属取决于调试信息，可能被计入调用方。
- 未链接的目标文件不进入报告，未构建的模块显示为未覆盖。
- 异步与多线程路径的执行顺序影响计数器合并。
- 覆盖率工具版本与编译器版本不匹配时，映射可能完全错误。

### 4.7 覆盖率门槛如何设置才不诱导造假？

- 门槛按模块设置，核心模块高，生成代码与胶水层低。
- 新代码覆盖率比整体覆盖率更有效，避免历史债务稀释。
- 门槛应配合豁免机制，明确哪些代码不计入，例如平台适配层。
- 只考核行覆盖会诱导写无断言的执行型测试，应同时考核分支覆盖与变异得分。
- 门槛值参考历史趋势，不宜凭经验直接设定。
- 门槛过高的直接后果是测试中堆砌无意义断言。

### 4.8 （陷阱）覆盖率造假有哪些常见手法？

- 写只调用不检查的测试，让行覆盖上升而缺陷不变。
- 用条件编译把难测代码排除出覆盖率构建。
- 在测试中直接构造内部状态，绕过真实入口。
- 用提前返回让不可达分支消失，或把断言改成日志输出。
- 用 `LCOV_EXCL_LINE` 一类注释批量排除代码。
- 造假难以从覆盖率报告发现，需要结合变异测试与代码评审。

### 4.9 变异测试的基本流程是什么？

- 工具对源码施加小改动生成变异体，每个变异体运行测试集。
- 测试失败称为「杀死」变异体，测试通过称为「存活」。
- 存活变异体要么说明测试不足，要么是等价变异体。
- 流程包括选择变异算子、生成变异体、执行测试与汇总得分。
- 执行成本等于变异体数量乘以测试集时间，需要采样与增量策略。
- 结果用于指导补充测试，不宜直接作为准入门槛。

### 4.10 变异算子有哪些类别？

- 算术算子替换运算符，例如 `+` 改为 `-`。
- 关系算子替换比较符，例如 `<` 改为 `<=`。
- 逻辑算子替换 `&&` 与 `||`，以及删除取反。
- 常量替换为 0、1 或边界值。
- 语句删除，用于检测缺失的副作用。
- 返回值替换，用于检测忽略返回值的调用。
- 不同工具的默认算子集不同，跨项目比较得分需要固定配置。

### 4.11 变异得分如何计算与解读？

- 变异得分等于被杀死的变异体数除以非等价变异体总数。
- 分母的处理是关键，等价变异体会拉低得分，需要人工或工具识别。
- 得分与测试集强度相关，也与算子集和代码结构相关。
- 得分不宜跨项目直接比较，同一项目的趋势更有意义。
- 高覆盖低得分说明测试只执行不检查。
- 得分应结合存活变异体的位置分析，集中在核心逻辑的存活更有价值。

### 4.12 等价变异体如何处理？

- 等价变异体与原始程序语义相同，任何测试都无法杀死。
- 识别方法包括人工评审、约束求解与变异体检测工具。
- 常见来源是冗余条件、不可达分支与整数运算的恒等变换。
- 处理方式是从分母中排除并记录理由。
- 排除过多会削弱得分可信度，需要评审。
- 部分工具支持标注等价变异体，配置应纳入版本控制。

### 4.13 变异测试的运行代价如何控制？

- 只对变更代码生成变异体，减少总量。
- 用测试选择技术只运行覆盖该变异体的测试。
- 按算子与位置分层抽样。
- 并行执行，按变异体分片到多台机器。
- 降低测试集时间，变异测试对测试速度高度敏感。
- 定期全量运行，日常只做增量。

### 4.14 如何用变异测试评估测试有效性？

- 先确定关键模块与算子集，建立基线得分。
- 对存活变异体分类，区分测试缺失、断言不足与等价变异体。
- 补充测试后重跑，观察得分变化。
- 得分提升应与缺陷发现率结合评估。
- 变异测试适合评估测试集，不适合评价个人产出。
- 评估周期以季度或版本为单位，避免短期波动。

### 4.15 变异测试与覆盖率如何互补？

- 覆盖率衡量代码是否被执行，变异测试衡量断言能否发现问题。
- 覆盖率高而变异得分低，说明测试缺少有效断言。
- 覆盖率低时变异得分通常也低，先补覆盖再评估变异。
- 变异测试的成本高于覆盖率统计，适合关键模块。
- 两者结合可发现执行但未验证的代码区域。
- 报告中并列展示两项指标，便于定位薄弱点。

| 指标 | 回答的问题 | 主要成本 | 适用场合 |
| --- | --- | --- | --- |
| 行覆盖 | 语句是否执行 | 插桩与报告汇总 | 下限约束 |
| 分支覆盖 | 判定两个方向是否都执行 | 略高于行覆盖 | 合并请求门禁 |
| MC/DC | 每个条件是否独立影响判定 | 用例设计与工具支持 | 高完整性领域 |
| 变异得分 | 断言能否发现改动 | 变异体数量乘测试时间 | 关键模块评估 |

### 4.16 增量覆盖率与全量覆盖率有何取舍？

- 全量覆盖率反映整体状态，受历史代码影响大，改进缓慢。
- 增量覆盖率只统计变更行，反馈直接，适合合并请求门禁。
- 增量统计需要准确的差异映射，重命名与移动会干扰。
- 生成代码与第三方代码应排除在增量统计之外。
- 全量覆盖率适合版本发布评审，增量适合日常开发。
- 两者口径需要一致，否则数字无法对照。

### 4.17 覆盖率报告如何与代码评审结合？

- 报告应标注未覆盖行与新增未覆盖行，评审时逐条确认原因。
- 未覆盖行分为可测、不可测与环境相关三类。
- 评审关注关键分支是否被覆盖，而非百分比本身。
- 覆盖率变化作为评审信息而非阻断条件，除非低于门槛。
- 报告需要与提交关联，避免评审时看到过期数据。
- 工具链应支持在差异视图中直接显示覆盖标记。

### 4.18 未覆盖代码如何分类与处置？

- 防御性分支：参数校验与不可能状态，可用断言或注入测试覆盖。
- 平台相关代码：条件编译分支，需在对应平台的持续集成中运行。
- 错误处理：I/O 失败与内存不足，可用故障注入覆盖。
- 模板未实例化：缺少使用点，可增加显式实例化测试。
- 死代码：确认无调用后删除，而非排除。
- 生成代码：由生成器保证正确性，通常排除统计。

### 4.19 覆盖率门槛遇到遗留代码怎么办？

- 先统计基线，按模块设定不降低现有水平的门槛。
- 新代码使用更高门槛，存量代码逐步偿还。
- 重构与补测分开提交，避免一次改动过大。
- 优先补测高风险模块，按缺陷历史排序。
- 门槛提高的节奏应与团队产出匹配。
- 用增量覆盖率避免存量债务阻塞合并。

### 4.20 如何发现「测试通过但断言无效」？

- 变异测试是最直接的手段，存活变异体指向无效断言。
- 检查测试是否只调用不断言，可用静态规则扫描。
- 断言恒真也是常见问题，例如比较同一变量。
- 断言异常类型过宽，例如捕获 `std::exception` 后不做检查。
- 只断言返回值的一部分，遗漏关键字段。
- 定期做测试评审，抽查断言的判别能力。

## 5. 集成测试与端到端

### 5.1 集成测试与单元测试的边界在哪里？

- 单元测试隔离外部依赖，集成测试使用真实依赖验证协作。
- 边界通常落在进程内模块之间、进程与数据库之间、服务与服务之间。
- 集成测试覆盖序列化、协议、事务与配置，这些在单元测试中被替身跳过。
- 集成测试的失败定位成本高于单元测试，需要日志与追踪支撑。
- 集成测试数量按接口数量而非代码行数决定。
- 边界划分影响测试运行时间与缺陷发现阶段。

### 5.2 测试环境如何与生产环境对齐？

- 操作系统版本、运行时版本、库版本与配置项应记录并对齐。
- 差异项应显式列出，例如测试环境使用单节点而生产使用集群。
- 配置通过环境变量或配置文件注入，镜像中不写死。
- 依赖服务可用容器或模拟服务替代，替代品的版本需要固定。
- 环境对齐的成本随保真度上升，按缺陷历史选择关键项。
- 环境清单应纳入版本控制，变更时同步更新。

### 5.3 用容器编排测试环境有哪些代价？

- 启动时间从秒级到分钟级，影响反馈速度，可用预热与镜像缓存缓解。
- 端口、卷与网络命名空间需要隔离，并行运行时冲突概率上升。
- 容器内的时钟、主机名与资源限制与生产不同，可能掩盖问题。
- 编排文件的维护成本随服务数量增长。
- 本地开发与持续集成的环境差异会导致本地通过而流水线失败。
- 容器镜像的构建与拉取是主要耗时，应尽量复用层。

### 5.4 数据库测试的数据隔离方案有哪些？

- 每个测试使用独立 schema 或独立数据库，隔离彻底但创建成本高。
- 事务回滚：测试开始开启事务，结束回滚，速度快但无法测试提交语义。
- 每个测试使用唯一的数据前缀，共享库但逻辑隔离，清理需要可靠。
- 容器化数据库按测试类启动，兼顾隔离与速度。
- 内存数据库与生产数据库的 SQL 方言差异会掩盖问题。
- 隔离方案的选择取决于测试是否涉及事务、锁与并发。

### 5.5 测试数据如何生成与清理？

- 固定数据集适合稳定断言，随机数据适合发现边界问题。
- 数据生成应保证唯一性，例如在名称中加入进程号与计数器。
- 清理应在测试开始与结束都执行，避免上次失败留下的数据。
- 清理失败会导致后续测试连锁失败，需要显式报告。
- 敏感数据使用脱敏样本，不直接复制生产数据。
- 数据量应与断言需求匹配，过大拖慢执行。

### 5.6 （陷阱）事务回滚式隔离有哪些陷阱？

- 被测代码若自行提交或开启新事务，回滚失效。
- 测试框架与被测代码使用不同连接时，事务不在同一会话。
- 自增序列与缓存不会随回滚恢复，跨测试的标识可能不连续。
- 部分数据库的 DDL 会隐式提交，建表操作无法回滚，具体行为由实现定义。
- 连接池复用连接时，未清理的会话状态会影响后续测试。
- 回滚后仍需验证数据确实未写入，可加一条查询断言。

### 5.7 契约测试解决什么问题？

- 服务提供方与消费方对接口的假设不一致时，集成测试才暴露问题。
- 契约测试把接口期望固化为契约，双方独立验证。
- 契约包括请求格式、响应字段、状态码与错误语义。
- 契约测试不验证业务逻辑，只验证接口兼容性。
- 契约变更需要双方同步，版本管理是关键。
- 契约测试能缩短联调周期，减少对共享环境的依赖。

### 5.8 消费者驱动契约的流程是什么？

- 消费方编写测试，声明期望的请求与响应，生成契约文件。
- 契约文件发布到 broker，例如 Pact Broker。
- 提供方拉取契约并回放请求，验证实际响应是否匹配。
- 验证结果回传 broker，消费方据此判断能否部署。
- 流程需要版本标记与部署环境标记，避免用错契约。
- 契约文件的兼容性规则包括字段新增、类型变更与删除。

### 5.9 契约测试与端到端测试如何取舍？

- 契约测试覆盖接口兼容性，端到端测试覆盖业务流程。
- 端到端测试数量应控制在关键路径，其余用契约与集成测试替代。
- 契约测试运行快、定位准，但无法发现业务流程缺陷。
- 端到端测试受环境影响大，失败归因困难。
- 两者结合可减少端到端测试数量而不降低覆盖。
- 契约测试依赖双方遵守流程，缺少治理时会退化。

### 5.10 端到端测试的数量如何控制？

- 按关键用户路径选取，通常控制在数十条以内。
- 同一路径的变体用参数化覆盖，避免重复实现。
- 边界与错误路径优先由集成测试覆盖。
- 每条用例的维护成本应记录，长期失败的用例需要下线。
- 用例数量增长应与缺陷发现率对照，边际收益递减时停止扩张。
- 分层测试策略下，端到端测试承担跨系统验证职责。

### 5.11 端到端测试中的等待与重试如何编写？

- 固定 `sleep` 是主要的不稳定来源，应改为轮询条件直到超时。
- 轮询间隔可以固定，也可以逐步加长，总超时按业务指标设置。
- 重试只用于可恢复的瞬时故障，断言失败不应重试。
- 重试次数与间隔需要记录，频繁重试说明系统或测试有问题。
- 异步操作的完成信号应使用事件或状态查询，避免等待固定时间。
- 超时失败时应输出当前状态与最近日志，便于定位。

```cpp
template <class Pred>
bool wait_until(Pred pred, std::chrono::milliseconds timeout) {
    const auto deadline = std::chrono::steady_clock::now() + timeout;
    while (std::chrono::steady_clock::now() < deadline) {
        if (pred()) return true;
        std::this_thread::sleep_for(std::chrono::milliseconds(50));
    }
    return false;
}
```

### 5.12 如何定位端到端测试失败的责任方？

- 先确认失败是否可复现，再判断是环境、数据还是代码问题。
- 日志与追踪标识应贯穿各服务，请求 ID 是主要线索。
- 环境问题包括依赖服务未启动、配置错误与资源不足。
- 数据问题包括前置数据缺失与上次运行的残留。
- 代码问题按变更范围定位，结合提交历史与部署记录。
- 归因结论应记录在缺陷单中，避免同类问题重复排查。

### 5.13 回归测试集如何选择？

- 按变更影响范围选择，模块依赖图与覆盖数据可作为依据。
- 高风险模块的用例始终运行，低风险模块按变更触发。
- 历史缺陷对应的用例必须保留，属于长期资产。
- 测试集过大时按执行时间分层，快速集每次运行，慢速集定时运行。
- 选择结果需要可解释，否则遗漏时无法追溯。
- 定期评估用例有效性，删除长期未失败的冗余用例。

### 5.14 冒烟测试应覆盖什么？

- 服务能否启动、健康检查是否通过、关键依赖是否可达。
- 核心接口的最小可用路径，例如登录、下单与查询。
- 配置加载与数据库迁移是否成功。
- 冒烟测试应在一分钟内完成，失败即阻断后续测试。
- 冒烟测试不追求覆盖，追求快速判断环境是否可用。
- 失败信息应直接指向环境或部署问题。

### 5.15 灰度发布与线上验证如何衔接测试？

- 灰度阶段用真实流量验证，测试环境无法完全复现。
- 关键指标包括错误率、延迟分位数与业务转化率。
- 灰度放量应分级，每级设置观察窗口与回滚条件。
- 线上验证的断言来自监控与告警，而非测试框架。
- 灰度发现的问题应回流为回归用例。
- 回滚路径需要演练，否则故障时不可用。

### 5.16 环境漂移如何检测？

- 基础设施即代码把环境定义纳入版本控制，减少手工变更。
- 定期对比实际配置与期望配置，输出差异报告。
- 依赖版本使用锁定文件，避免自动升级引入差异。
- 容器镜像使用固定摘要而非浮动标签。
- 环境漂移会导致测试通过而生产失败，需要纳入发布检查。
- 漂移检测的成本主要在维护期望状态。

### 5.17 测试数据中的敏感信息如何处理？

- 生产数据不得直接进入测试环境，需脱敏或合成。
- 脱敏要覆盖自由文本字段，正则替换容易遗漏。
- 合成数据应保持统计特征与关联关系，否则测试失去意义。
- 测试账号与密钥使用独立凭据，不共享生产凭证。
- 日志中不得输出敏感字段，测试断言也要避免打印。
- 数据访问需要审计，测试环境的权限应与生产隔离。

### 5.18 并行执行集成测试的资源竞争如何处理？

- 端口、数据库、临时目录与消息队列是主要竞争点。
- 为每个测试进程分配独立端口段与独立 schema。
- 使用随机后缀命名资源，避免冲突。
- 共享的外部服务需要支持并发，否则串行执行。
- 资源池可复用昂贵资源，但需要重置状态。
- 竞争导致的失败通常表现为偶发超时或连接拒绝，需要用唯一标识定位。

### 5.19 （场景）持续集成中的集成测试超时与卡顿如何设置与定位？

- 超时应包含环境启动、测试执行与清理三个阶段。
- 单条用例的超时按历史 P99 设置，整体作业超时留出余量。
- 超时过短会把慢机器判为失败，过长会浪费执行资源。
- 超时后应输出进度与堆栈，便于判断卡在何处。
- 重试策略要有限度，避免掩盖死锁。
- 超时阈值随测试集增长定期复核。

### 5.20 如何度量测试结果的可信度？

- 指标包括 flaky 率、失败复现率与失败归因准确率。
- flaky 率按用例统计，持续高于阈值的用例进入隔离区。
- 失败复现率反映日志与追踪信息的充分程度。
- 归因准确率反映团队对失败原因的判断质量。
- 测试通过率不能单独作为可信度指标，测试可能被跳过。
- 长期趋势比单次结果更有参考价值。

## 6. CI/CD 与构建矩阵

### 6.1 一条 C++ CI 流水线的最小阶段如何划分？

- 预检阶段完成格式检查、提交信息校验与轻量静态检查，单次控制在 1 分钟内，失败时不再占用编译资源。
- 编译阶段生成目标文件与链接产物，同时导出 `compile_commands.json`，供后续静态分析与调试使用。
- 单元测试与组件测试在编译产物上运行，报告用 JUnit XML 汇总，失败用例保留日志与复现命令。
- 集成阶段启动依赖服务，执行端到端用例与接口兼容性测试，资源消耗大，通常只在合并请求的最终版本运行。
- 制品阶段收集二进制、调试符号、头文件、SBOM 与校验和，写入不可变仓库，并记录构建元数据。
- 发布阶段只提升已经通过验证的同一份制品，不在发布时重新编译，避免引入未验证的差异。

### 6.2 （场景）构建时间从 8 分钟涨到 40 分钟，如何定位？

- 先看流水线各阶段耗时曲线，区分排队时间与执行时间，排队占比高说明执行机容量不足。
- 编译阶段用 `ninja -d explain` 或 `-d stats` 查看目标被重建的原因，常见原因是头文件变更、命令行变化与时间戳。
- 用 `-ftime-trace` 生成 Clang 的编译耗时报告，按文件与模板实例化排序，确认是个别翻译单元还是普遍变慢。
- 检查缓存命中率与缓存键，编译器升级、宏定义变化与构建目录搬迁都会让缓存整体失效。
- 对比依赖数量与头文件包含图，模板与重量级头文件的传递包含会放大每个翻译单元的解析成本。
- 查看磁盘与网络指标，共享存储的随机读延迟、安全软件扫描与容器层复制都会拉长链接与写盘时间。
- 修复顺序通常是先恢复缓存，再削减依赖，最后才考虑增加并行度或升级机器。

### 6.3 编译缓存的命中条件由什么决定？

- 缓存键通常由预处理后的源码、编译器二进制与版本、完整命令行、目标架构与语言标准共同决定。
- 头文件内容通过预处理结果进入键，包含路径的顺序与宏定义会影响预处理输出，进而影响命中。
- 编译器自身路径、包装脚本与环境变量可能被计入键，工具链安装位置变化会导致整库缓存失效。
- 时间宏 `__DATE__`、`__TIME__` 与绝对路径会降低可复用性，可用 `-ffile-prefix-map` 与固定时间戳缓解。
- 预编译头需要额外的校验信息，命中条件比普通目标文件更严格，缓存工具对此有专门开关。
- 远程缓存还要考虑权限、网络往返与对象存储一致性，跨区域访问的延迟可能抵消命中收益。

### 6.4 （辨析）ccache 与 sccache 的适用边界？

- `ccache` 面向本地单机，键与存储都在本地磁盘，配置项成熟，对 GCC 与 Clang 的支持稳定。
- `sccache` 支持本地与远端后端，常见后端包括 S3、GCS 与 Redis，适合多台执行机共享缓存。
- `ccache` 的直接模式依赖 manifest 记录头文件依赖，预处理模式更保守，命中率略低但更可靠。
- `sccache` 对 MSVC 的支持较好，跨平台流水线可以统一到一套缓存服务。
- 远端缓存要处理密钥、租户隔离与投毒风险，缓存内容应按信任边界分区，不能接受不可信写入。
- 选择依据是执行机数量、编译器种类与合规要求，单机开发用 `ccache` 的运维成本最低。

### 6.5 （陷阱）缓存命中率很高但构建仍然慢？

- 命中率按编译动作统计，链接、归档、代码生成与测试准备不在缓存范围内，可能才是主要耗时。
- 命中的动作仍要读取缓存对象并写回工作目录，大量小文件与慢速磁盘会让这部分开销显著。
- 缓存键包含命令行，`-D` 中嵌入的随机值或构建编号会让键不断变化，统计结果却仍显示高命中。
- 并行度不足时，缓存命中只是缩短单个动作，关键路径上的串行步骤没有变化。
- 增量构建的依赖图若被误判为全部过期，缓存只能省下编译，重新扫描与重新链接仍会发生。
- 应同时观察动作数、命中数、关键路径长度与总 CPU 时间，单独看命中率容易得出错误结论。

### 6.6 分布式编译如何切分翻译单元？

- 最小单位是翻译单元，预处理可以在本地完成再把结果发给远端，也可以在远端完成，两者对头文件一致性要求不同。
- 远端主机需要相同编译器版本、相同目标架构、相同系统头文件与相同宏环境，否则产物不可比。
- 链接仍在发起机构执行，分布式编译只覆盖编译动作，链接与 LTO 往往成为新的瓶颈。
- 任务粒度受翻译单元大小影响，过大的单元会导致负载不均，过小则网络与调度开销占比上升。
- 预处理后传输可以避免远端头文件漂移，代价是传输体积增大，包含大量模板时尤其明显。
- 失败重试要区分编译器错误与网络错误，前者重试没有意义，后者需要幂等与超时控制。

### 6.7 （场景）构建矩阵组合爆炸如何裁剪？

- 先列出维度：编译器、编译器版本、语言标准、构建类型、目标平台、特性开关，计算全组合的数量。
- 把组合分为合并门禁与定时任务，门禁只保留高风险组合，例如最新标准加最低支持编译器。
- 用 `include` 与 `exclude` 精确添加例外，避免用大范围排除掩盖真实的组合缺失。
- 语言标准与编译器版本存在支持边界，超出边界的组合应在配置阶段直接拒绝，避免在编译阶段报错。
- 依赖外部服务的组合可以只做编译不做运行，运行验证放到夜间任务。
- 记录每个组合的最近成功时间，长期未运行的组合视为失效，防止矩阵名义存在而实际无人维护。

### 6.8 交叉编译的矩阵如何组织？

- 工具链文件描述编译器、系统根目录、目标架构与浮点 ABI，矩阵维度应绑定工具链文件，避免散落的命令行参数。
- 主机与目标的组合需要分别验证，主机侧工具与目标侧库不能混用同一套编译选项。
- 模拟器或目标板资源有限，运行测试要按可用设备排队，避免并行任务互相抢占串口与网络。
- 交叉编译的产物要在目标环境验证，主机上的单元测试只能覆盖与平台无关的逻辑。
- 系统根目录中的库版本要固定，滚动升级的发行版会导致同一提交在不同时间产出不同结果。
- 工具链升级应作为独立变更，先执行完整矩阵再合并，避免与业务改动混在一起排查。

### 6.9 制品应该包含哪些内容？

- 可执行文件与共享库是主体，需记录构建 ID、提交号、编译器版本与完整编译选项。
- 调试符号单独存放，按构建 ID 索引，发布包中剥离符号以减小体积，分析时再按需取回。
- 头文件、导出符号表与 ABI 描述供下游编译与兼容性检查使用。
- SBOM 列出直接与传递依赖及版本，便于漏洞公开时快速定位受影响制品。
- 校验和与签名用于验证完整性，签名密钥应与构建系统分离，避免构建机被攻破后伪造制品。
- 测试报告、覆盖率与静态分析结果作为质量证据一并归档，便于回溯某次发布依据了哪些结论。

### 6.10 （辨析）构建产物与制品库的职责如何划分？

- 构建产物是流水线工作目录中的临时文件，生命周期以一次任务为界，可被清理与重建。
- 制品库保存通过验证的不可变对象，用版本或摘要寻址，发布与回滚都从制品库取件。
- 制品库负责保留策略、权限、审计与复制，构建系统负责生成与上传，两者不应互相承担对方职责。
- 用可变标签指向制品会破坏可追溯性，标签应解析为摘要，部署时按摘要拉取。
- 制品库的可用性直接影响发布，跨区域复制与离线镜像属于容灾设计的一部分。
- 清理策略要区分正式版本与临时快照，误删正式制品会导致无法回滚。

### 6.11 制品如何做到可复现？

- 固定工具链、依赖版本与构建镜像，引用镜像时使用摘要，标签不参与寻址，避免基础层漂移。
- 消除时间与路径依赖，使用 `SOURCE_DATE_EPOCH`、`-ffile-prefix-map` 与稳定的归档顺序。
- 编译器的随机种子要固定，`-frandom-seed` 可减少符号名一类的随机差异。
- 并行构建的输出顺序可能影响归档内容，打包前对文件排序并固定元数据。
- 用两次独立构建比较摘要，差异用 `diffoscope` 定位到具体节或文件。
- 完全可复现难以覆盖所有工具，至少应保证同一构建环境下重新运行得到相同结果。

```cpp
const char* build_time() {
    return __DATE__;  // 每次编译都不同，会破坏可复现性
}
```

### 6.12 （场景）CI 中偶发失败如何归类与处置？

- 先按失败阶段与错误文本聚类，区分环境问题、资源竞争、超时与真实缺陷。
- 复现时记录随机种子、并行度、机器负载与依赖服务版本，缺少这些信息无法判断是否同一问题。
- 测试框架提供重复与随机顺序选项，`--gtest_repeat` 与 `--gtest_shuffle` 可提高复现概率。
- 确认是测试自身缺陷后，应修复或隔离，长期重试会掩盖真实回归并消耗执行时间。
- 与时间、端口、临时目录、共享缓存的冲突通常有固定模式，可在测试夹具中统一分配资源。
- 记录每个偶发用例的失败率与最近失败时间，超过阈值进入隔离区并设定修复期限。

### 6.13 测试分片与并行执行的常见错误？

- 按用例数量平均分片会忽略耗时差异，应按历史耗时做负载均衡，并允许动态领取任务。
- 分片之间共享端口、数据库与临时目录会造成偶发冲突，资源名称要带分片编号。
- 全局状态与单例在进程内复用会破坏隔离，并行执行应以进程为边界。
- 用例顺序依赖在打乱后暴露，修复方式是显式建立前置条件，固定顺序只能掩盖问题。
- 收集阶段与执行阶段的过滤条件不一致，会导致部分用例从未运行而报告显示通过。
- 分片数超过可用核数时，上下文切换与内存压力会抵消并行收益。

### 6.14 流水线中的资源隔离如何做？

- 每个任务使用独立容器或工作目录，挂载点只读，临时目录使用任务级路径。
- CPU 与内存用 cgroup 限额，编译任务的内存峰值差异大，限额过低会触发 OOM 而不会给出编译错误。
- 端口由系统分配或从任务编号推导，避免固定端口在并行时冲突。
- 缓存目录要加锁或按任务分片，多个任务同时写同一缓存对象可能产生损坏。
- 网络访问按需开放，依赖下载走内部镜像，减少外部服务抖动对流水线的影响。
- 执行机上的残留进程要在任务结束后清理，否则会占用端口与文件句柄，影响后续任务。

### 6.15 （场景）缓存污染导致产物异常如何排查？

- 现象通常是本地可复现而 CI 失败，或同一提交在不同执行机得到不同结果。
- 先禁用缓存重新运行，确认问题是否消失，再逐步恢复缓存范围以定位污染对象。
- 检查缓存键是否遗漏了编译器版本、宏定义、依赖提交或环境变量。
- 预编译头与生成代码对头文件变化敏感，键中未包含生成器版本时容易命中过期对象。
- 缓存对象的写入应是原子的，先写临时文件再改名，避免中断留下半成品。
- 缓存服务应支持按前缀清理与版本隔离，工具链升级时整体失效旧命名空间。

### 6.16 构建环境的镜像如何版本化？

- 镜像用内容摘要固定，流水线配置中不出现浮动标签。
- 每次工具链或依赖变更生成新镜像，旧镜像保留一段时间以支持历史提交重新运行。
- 镜像内记录编译器、构建工具与系统包版本，构建日志同时输出这些信息。
- 基础镜像的安全更新要定期重建，重建后执行完整矩阵，确认没有行为变化。
- 镜像构建本身也应可复现，包管理器缓存与时间戳会影响层摘要。
- 镜像仓库的保留策略与制品库分开管理，避免同时清理导致历史版本无法重建。

### 6.17 发布回滚的触发条件与粒度？

- 触发条件应基于可观测指标，例如错误率、延迟分位数、崩溃率与业务成功率，并设置观察窗口。
- 粒度可以是实例、批次、服务或整个版本，粒度越细回滚越快，但状态一致性越难保证。
- 回滚必须使用与发布相同的制品与配置，重新构建会引入新的变量。
- 数据库变更要向前兼容，采用扩展与收缩两步，避免回滚时旧代码读到新结构。
- 回滚脚本要定期演练，未演练的回滚路径在故障时往往不可用。
- 自动回滚需要防止抖动，设置最小观察时间与连续失败次数，避免瞬时波动触发反复切换。

### 6.18 （辨析）蓝绿发布与金丝雀发布的区别？

- 蓝绿发布保留两套完整环境，切换流量在负载均衡层完成，回滚是切回旧环境。
- 金丝雀发布把少量流量引到新版本，按指标逐步扩大比例，失败时停止扩大并回退。
- 蓝绿需要双倍资源与状态同步，金丝雀需要按维度分流与稳定的对比指标。
- 蓝绿切换快，但新旧版本同时存在的时间短，难以发现长尾问题。
- 金丝雀观察期长，能覆盖更多真实流量，但分流不均可导致结论偏差。
- 有状态服务还要考虑会话粘滞、缓存预热与消息重复消费，单纯切换流量不足以保证正确性。

### 6.19 （场景）回滚后问题仍在，如何继续定位？

- 先确认回滚是否真正生效，检查运行中的制品摘要、配置版本与实例数量。
- 区分代码缺陷与数据副作用，写入错误数据后回滚代码不会修复已有数据。
- 检查缓存与消息队列中的残留，旧版本可能继续消费新版本产生的消息。
- 外部依赖与客户端版本不受回滚控制，需要确认对端是否同时变更。
- 回滚本身可能触发新的问题，例如连接重建、证书切换与限流阈值变化。
- 保留故障时间窗内的日志与指标，回滚后继续观察，确认指标回到基线，避免被暂时掩盖。

### 6.20 CI 指标如何设计才不被滥用？

- 常用指标包括变更前置时间、流水线时长分位数、失败率、偶发失败率与缓存命中率。
- 指标按团队与项目维度聚合，避免用单次构建的极值评价个人。
- 时长应区分排队与执行，否则增加机器就能改善指标而不改变实际效率。
- 失败率要与失败原因分类结合，编译错误与基础设施故障的处理方式不同。
- 指标用于发现趋势与瓶颈，不宜直接作为考核目标，否则会出现拆分任务与规避检查的行为。
- 定期复核指标定义，工具链与流程变化后旧定义可能失真。

## 7. 调试方法与工具

### 7.1 （辨析）gdb 与 lldb 的命令差异如何迁移？

- 断点：gdb 用 `break`、`tbreak`、`rbreak`，lldb 用 `breakpoint set -n`、`-f`、`-l`。
- 运行：gdb 用 `run`、`continue`、`next`、`step`，lldb 用同名命令，程序参数放在 `--` 之后。
- 栈：gdb 用 `bt`、`frame`、`up`、`down`，lldb 用 `bt`、`frame select`、`frame variable`。
- 数据：gdb 用 `print` 与 `x`，lldb 用 `expression` 与 `memory read`，表达式语法更接近 C++。
- 线程：gdb 用 `info threads` 与 `thread apply all bt`，lldb 用 `thread list` 与 `thread backtrace all`。
- 自动化：gdb 用命令文件与 Python，lldb 用 Python 脚本与 `command script import`，两者 API 不通用。
- 迁移时先统一脚本输出格式，再替换命令，调试习惯的差异比命令名差异更难迁移。

### 7.2 调试符号缺失时如何仍能工作？

- 确认二进制是否带 `.debug_info`，`file` 与 `readelf -S` 可以给出初步结论。
- 按构建 ID 查找分离的调试文件，`debuginfod` 或内部符号服务器可以自动取回。
- 仅有符号表时仍可看到函数名，`nm` 与 `objdump -d` 能定位到函数边界。
- 无符号时用反汇编与寄存器推断参数，x86-64 的系统调用号与调用约定提供线索。
- 崩溃地址需要换算为文件偏移，PIE 与共享库要先减去加载基址。
- 保留一份未剥离的构建产物是最直接的手段，发布流程应把符号归档作为必选项。

### 7.3 （场景）断点命中次数与预期不符，如何排查？

- `info breakpoints` 查看断点是否解析到多个位置，inline 与模板实例化会产生多个地址。
- 优化构建中同一行可能对应多条指令，行断点会落在其中一条，命中次数与源码直觉不同。
- 断点可能因共享库尚未加载而处于 pending 状态，程序运行到库加载后才生效。
- 条件断点中的表达式有副作用时，每次命中都会改变程序状态。
- 多线程下其他线程可能已经越过断点，`set scheduler-locking` 会改变命中顺序。
- 用 `dprintf` 或断点命令打印计数，避免频繁中断改变时序。

### 7.4 条件断点与断点命令如何减少停顿？

- 条件断点把判断放在调试器侧，命中不满足条件时仍要陷入调试器，开销高于代码中的判断。
- 断点命令配合 `silent` 与 `printf` 可以只记录信息后继续，适合观察高频路径。
- `commands` 中可访问 `$bpnum` 与命中计数，按次数打印能减少输出量。
- 条件表达式依赖的变量被优化掉时，条件断点会失效或报错。
- 高频断点会放大调试器开销，必要时改用日志或硬件跟踪。
- 脚本化采集比人工中断更稳定，输出写入文件便于后续处理。

### 7.5 （实现）watchpoint 的硬件与软件实现差别？

- 硬件 watchpoint 使用 x86 调试寄存器，数量通常为 4 个，监视长度限制为 1、2、4 或 8 字节。
- 软件 watchpoint 由调试器单步执行并在每一步比较值，速度慢几个数量级。
- gdb 优先使用硬件 watchpoint，数量不足时回退到软件方式，可用 `set can-use-hw-watchpoints` 控制。
- 硬件 watchpoint 监视的是地址，变量超出作用域后地址可能被复用，命中原因会误导。
- 监视大对象需要多个寄存器，通常只能覆盖开头一段，完整监视要改用其他手段。
- watchpoint 在只读内存或未映射地址上设置会失败，需先确认地址有效。

```cpp
int main() {
    int value = 0;
    int* p = &value;
    *p = 1;          // 在 p 指向的地址上设置 watchpoint
    return value;
}
```

### 7.6 （陷阱）watchpoint 监视的地址为何失效？

- 局部变量位于栈上，函数返回后栈帧被复用，原地址的内容变化不再对应该变量。
- 优化构建中变量可能被放入寄存器，内存地址不存在或只在部分路径有效。
- 容器扩容后元素地址变化，监视旧地址无法发现新分配区域的问题。
- 共享库卸载后地址空间被回收，watchpoint 仍指向已释放的映射。
- 多线程栈各自独立，跨线程监视同一地址需要确认对象生命周期。
- 监视表达式而非地址可以缓解部分问题，但调试器仍需在每次停顿时重新求值。

### 7.7 （场景）多线程程序断点导致其他线程超时，如何处理？

- 默认 all-stop 模式下所有线程同时停止，持有锁的线程被暂停会让其他线程无法推进。
- `set scheduler-locking on` 只让当前线程运行，适合单线程步进，但会改变并发行为。
- `set scheduler-locking step` 在步进时锁定，继续运行时恢复其他线程。
- 非停止模式允许其他线程继续，调试器需要支持 `non-stop`，命令与事件处理更复杂。
- 超时可能来自看门狗或服务端心跳，调试时应延长超时或使用离线复现。
- 生产环境优先抓取现场后离线分析，长时间暂停进程会触发健康检查与流量摘除。

### 7.8 如何调试 fork 与 exec 之后的子进程？

- `set follow-fork-mode child` 让调试器跟随子进程，父进程继续运行或被分离。
- `set detach-on-fork off` 保留两个进程，用 `inferior` 列表切换。
- `catch fork` 与 `catch exec` 在事件发生前暂停，适合检查环境与参数。
- exec 之后符号与地址空间被替换，原断点失效，需要在新程序中重新设置。
- 子进程继承调试器附加状态，exec 会保留 PID，调试器需要重新读取可执行文件。
- 守护进程双重 fork 后与终端脱离，用 `set follow-fork-mode` 配合 `detach-on-fork` 跟踪目标。

### 7.9 （辨析）attach 与在启动时调试的差别？

- 启动时调试可以停在 `main` 之前的初始化代码，适合分析静态初始化与加载阶段问题。
- attach 到运行中的进程会暂停全部线程，可能错过已经发生的事件与早期的调用栈。
- attach 受权限限制，需要相同用户或 `CAP_SYS_PTRACE`，`ptrace_scope` 会影响非父子进程。
- attach 不改变程序的启动参数与环境，适合线上进程的只读检查。
- 启动时调试可以设置环境变量、重定向输入与使用包装脚本。
- 容器中 attach 需要进入正确的 PID 命名空间，并具备相应的能力位。

### 7.10 反向调试需要什么支持，代价是什么？

- gdb 的 `record full` 在软件层记录执行历史，速度慢且缓冲区有限，遇到不支持的系统调用会停止记录。
- `record btrace` 使用处理器分支跟踪，开销低但只支持部分平台，无法回退内存内容。
- `rr` 基于 `perf` 事件做记录与重放，重放时单核执行，支持 `reverse-continue` 与条件断点。
- 记录阶段需要可复现的输入与稳定的环境，多线程竞争在单核重放时被确定性调度。
- 记录文件体积大，长时间运行的程序需要限制记录范围。
- 反向调试适合定位一次性破坏，例如内存在某次写之后才异常，正向断点难以捕捉。

### 7.11 （场景）线上进程不能停，如何取一份可用现场？

- 先确认暂停时间是否可接受，抓取 core 或附加调试器都会让进程停止，健康检查可能触发摘除。
- `gcore` 在进程停止期间写入 core 文件，文件大小与内存映射相关，可能达到数 GB。
- 只读采集可以先取 `/proc/PID/maps`、`status`、`stack` 与线程列表，开销小且不需要暂停。
- 需要堆内容时，可用分配器自带的统计接口或 eBPF 采集，避免全量转储。
- 抓取时间点要记录，后续分析需要与日志、指标对齐。
- 多实例部署时先摘除一个实例再采集，避免影响整体容量。

### 7.12 core 与 live 进程的调试差异？

- core 是某一时刻的内存快照，不能继续执行，也不能观察系统调用的返回。
- live 进程可以单步、修改变量、调用函数，但会改变运行时状态。
- core 中的共享库需要与当时版本一致，路径缺失会导致栈帧显示为问号。
- live 调试可以直接读取 `/proc` 信息，core 只能依赖转储中记录的映射。
- core 适合事后分析，live 适合验证假设与追踪执行路径。
- 两者都需要匹配的符号与源码，版本不一致时结论不可靠。

### 7.13 日志级别如何设计才不至于拖慢热路径？

- 级别在编译期裁剪可以减少分支与字符串常量，但会失去运行时调整能力。
- 运行期判断应先检查级别再构造消息，避免参数求值与字符串拼接。
- 格式化库的编译期检查能发现占位符错误，运行时开销取决于实现。
- 热路径日志要限制频率，采用令牌桶或首次触发后静默。
- 异步日志把格式化与写盘移到后台线程，队列满时的丢弃策略需要明确。
- 日志内容应包含稳定字段，避免把高频变化的值拼进消息导致聚合困难。

### 7.14 （场景）日志时间戳乱序如何判断因果？

- 多线程各自缓冲后统一写盘，写盘顺序不等于事件发生顺序。
- 墙钟受校时影响，跨机比较需要时钟同步并记录时钟源，单机内的先后顺序用单调时钟。
- 每条日志附带线程 ID 与序号，可以在单线程内恢复顺序。
- 跨线程因果关系需要显式传递请求 ID 或 span ID，时间戳只能作参考。
- 日志采集端的缓冲与批处理会进一步打乱顺序，必要时记录采集时间。
- 判断因果时应以事件之间的同步点为准，例如锁、消息投递与系统调用返回。

### 7.15 结构化日志与采样日志的取舍？

- 结构化日志以字段承载信息，便于过滤与聚合，代价是序列化与存储体积。
- 文本日志可读性好，解析依赖正则，字段变化容易破坏既有查询。
- 采样降低开销，但会丢失低频异常路径，错误与慢请求通常应全量记录。
- 采样率要随流量调整，固定比例在低流量时样本过少。
- 结构化字段应有稳定命名与类型，避免同一语义出现多种写法。
- 日志与追踪可以共享上下文，通过 trace ID 关联，减少重复记录。

### 7.16 （陷阱）调试器改变时序后缺陷消失，如何继续定位？

- 断点与单步会放大线程切换间隔，竞争窗口被破坏，缺陷不再触发。
- 启用 sanitizer 或压力工具可以在不改变源码的情况下放大竞争。
- `rr` 记录一次失败执行后可以反复重放，避免依赖现场复现。
- 在代码中加入可控延迟或屏障可以验证时序假设，但延迟不能作为修复。
- 检查未初始化内存与越界写，这类缺陷的表现常随时序变化。
- 记录原始失败时的线程状态与锁持有情况，调试器下的行为不能代表线上。

```cpp
std::atomic_int ready = 0;

void worker() {
    while (ready == 0) { }  // 调试器暂停会改变循环观察到的时序
}
```

### 7.17 （实现）如何用 gdb 脚本自动化采集现场？

- `gdb -batch -ex` 可以执行固定命令序列，适合在崩溃收集脚本中调用。
- 命令文件按顺序输出 `thread apply all bt full`、`info registers`、`info proc mappings` 与局部变量。
- Python API 可以遍历线程、帧与符号，把结果写入结构化文件。
- 采集脚本要设置超时与输出上限，避免大对象打印耗尽磁盘。
- `set pagination off`、`set confirm off` 与 `set print elements` 影响非交互行为。
- 脚本应在受控环境测试，调试器版本差异会导致命令不可用。

### 7.18 （场景）死锁现场如何用调试器确认锁的持有者？

- 先抓取全部线程栈，找到等待锁的线程与持有锁后未释放的线程。
- `pthread_mutex_t` 的内部字段由实现定义，直接读取 `__owner` 只在特定 glibc 版本有效。
- 等待 futex 的线程栈会显示 `__lll_lock_wait` 一类帧，可据此确认阻塞点。
- 自定义自旋锁没有调试器可识别的类型信息，需要结合代码与原子变量值判断。
- TSan 与锁顺序检查工具能在运行时发现部分循环等待，事后分析只能确认现象。
- 修复要针对锁顺序或持有时间，增加超时只会把死锁变成偶发失败。

### 7.19 （辨析）print 调试与调试器、日志的分工？

- 插入打印语句需要重新编译，适合快速验证局部假设，频繁使用会污染代码。
- 调试器可以检查任意状态，但会暂停进程，不适合高频事件与生产环境。
- 日志在部署后仍然有效，适合记录长时间跨度的行为与低频异常。
- 三者对时序的影响不同，打印与断点都会改变执行速度，日志的影响取决于实现。
- 复杂问题通常先用日志缩小范围，再用调试器确认细节。
- 任何手段都要保留可复现的输入与环境，否则结论无法验证。

### 7.20 如何建立可复现的调试环境？

- 固定二进制与符号版本，用构建 ID 关联源码、调试文件与 core。
- 容器镜像记录编译器、系统库与依赖版本，避免宿主环境差异。
- 记录输入数据、随机种子、环境变量与并发度，这些因素决定执行路径。
- 用 `rr` 或确定性调度工具保存失败执行，便于反复分析。
- 调试环境与生产环境的优化级别、分配器与内核参数应尽量一致。
- 建立最小复现用例，剥离无关服务与配置，缩短验证周期。

## 8. 崩溃分析与 core dump

### 8.1 崩溃报告从产生到入库经过哪些环节？

- 信号或异常处理器捕获崩溃，收集线程栈、寄存器、模块列表与异常码。
- 本进程内生成 minidump 或 core，或交给独立进程写入，避免依赖崩溃进程自身的内存状态。
- 上传前压缩与限流，弱网与离线场景先落盘，下次启动补传。
- 服务端做符号化，把地址映射为函数与行号，符号文件按构建 ID 匹配。
- 按签名聚合为问题，记录首次出现时间、影响版本与设备分布。
- 分派给责任人，修复后用同一输入或同一签名验证关闭。

### 8.2 core 文件缺失如何排查？

- 检查 `ulimit -c` 的软限制与硬限制，非交互 shell 与 systemd 单元可能设置了不同的值。
- 查看 `/proc/sys/kernel/core_pattern`，以管道符开头表示交给用户态程序处理，不在当前目录生成文件。
- 确认进程是否可转储，`fs.suid_dumpable` 与 `PR_SET_DUMPABLE` 会影响设置了用户 ID 的进程。
- 容器内的限制来自容器运行时，`--ulimit core=0` 会禁止生成，写入路径位于容器文件系统。
- 磁盘空间不足、目标目录不可写或被安全模块拦截都会导致写入失败，内核日志中可能有记录。
- 用 `coredumpctl list` 或 `systemd-coredump` 的存储位置确认是否由 systemd 接管。

### 8.3 （场景）容器内 core 文件写到哪里？

- `core_pattern` 是宿主机内核参数，容器共享同一内核，路径按容器挂载命名空间解释。
- 相对路径写入进程的当前工作目录，容器重启后该目录随可写层丢失。
- 绝对路径需要宿主机目录挂载进容器，否则写入失败或落在容器内部。
- 使用 `systemd-coredump` 时转储由宿主机服务接收，容器内看不到文件。
- 编排系统可能限制 core 大小，部署清单中的 `ulimits` 需要显式设置。
- 建议把 core 写到挂载卷，并在采集后及时转移，避免占满节点磁盘。

### 8.4 （辨析）core pattern 中的管道与文件两种模式？

- 文件模式由内核直接写入路径，受 `RLIMIT_CORE` 限制，适合本地保留。
- 管道模式把 core 交给用户态程序，程序可以压缩、上传或丢弃，内核不等待处理完成。
- 管道程序的命令行可以使用 `%p`、`%e`、`%t` 等占位符，参数由内核展开。
- 管道模式不受 `RLIMIT_CORE` 限制，写入量由处理程序控制，配置不当会占满磁盘。
- 文件模式的核心转储可能很大，需要配合 `coredump_filter` 减少映射。
- 处理程序运行环境与崩溃进程的命名空间关系由内核版本决定，容器场景需要验证。

### 8.5 崩溃转储的大小由什么决定？

- 虚拟地址空间中的映射不一定全部写入，`coredump_filter` 决定匿名页、文件页与共享页的取舍。
- 堆与栈通常被转储，文件映射的只读代码段可能只保留头部。
- 大页与设备映射会增加体积，`MADV_DONTDUMP` 可排除指定区域。
- 转储格式本身有压缩选项，ELF core 默认不压缩。
- 线程数量多的进程会为每个线程保存寄存器与栈，体积随之增长。
- 采集前应评估磁盘与传输带宽，必要时只保留关键映射。

### 8.6 （场景）core 与二进制版本不匹配如何确认？

- `readelf -n` 读取 core 中的 NT_FILE 映射，记录文件路径、起始地址与偏移，用于定位对应的二进制。
- 二进制的构建 ID 用 `readelf -n` 读取，与制品库记录比对，文件名不能作为版本依据。
- gdb 加载时会提示可执行文件与 core 不匹配，警告不应忽略。
- 共享库版本同样需要匹配，`info sharedlibrary` 显示实际加载路径与地址。
- 构建 ID 一致但源码不同，可能是符号文件与二进制错配，行号会偏移。
- 版本不匹配时栈帧可能仍然可读，但局部变量与行号不可信。
- 制品库按构建 ID 保存二进制与调试文件，可以避免人工比对。

### 8.7 符号服务器如何组织才能支持多版本？

- 以构建 ID 或调试标识为键，避免以文件名或版本号为键。
- 目录结构可按构建 ID 的前两位分片，避免单目录文件过多。
- 同时保存未剥离二进制、调试文件与源码索引，权限按需开放。
- 符号文件不可变，同名覆盖会破坏历史分析。
- 提供 HTTP 接口供调试器按需拉取，`debuginfod` 与符号服务器都遵循类似模式。
- 保留策略要覆盖产品的支持周期，过期删除会导致旧版本无法分析。

### 8.8 （陷阱）backtrace 只显示地址，如何补救？

- 先确认二进制是否被剥离，调试文件是否可获取。
- 用 `addr2line` 或 `llvm-symbolizer` 把地址转换为函数与行号，PIE 需要先减去加载基址。
- 栈展开失败可能缺少帧指针或 CFI，`-fno-omit-frame-pointer` 能改善但增加开销。
- 优化后的栈可能缺少帧，回溯到错误函数，需结合寄存器和反汇编验证。
- 第三方库没有符号时只能看到模块名与偏移，需单独获取对应版本符号。
- 记录崩溃时的模块列表与加载地址，事后才能正确换算。

### 8.9 （实现）信号处理器中写崩溃文件的安全做法？

- 只调用异步信号安全的函数，`write`、`open` 与 `sigaction` 可用，`malloc`、`printf` 与锁不可用。
- 预先打开文件描述符，处理器中直接写入固定格式的原始数据。
- 使用 `sigaltstack` 为栈溢出准备独立栈，注册时带上 `SA_ONSTACK`。
- 用 `SA_SIGINFO` 获取 `siginfo_t` 与 `ucontext_t`，保存故障地址与寄存器。
- 处理器只做最小采集，符号化与上传交给独立进程或下次启动完成。
- 处理器本身可能再次崩溃，需设置递归保护与超时。

```cpp
static int fd = -1;

void on_fault(int sig, siginfo_t* info, void* ctx) {
    (void)info;
    (void)ctx;
    unsigned char code = (unsigned char)(sig & 0xff);
    write(fd, &code, 1);  // 只调用异步信号安全的 write
}
```

### 8.10 （陷阱）崩溃处理中再次崩溃如何避免？

- 处理器中调用非异步信号安全函数可能死锁，尤其在崩溃时锁已被持有。
- 用原子标志防止重入，第二次信号直接终止进程。
- 备用栈要足够大，栈溢出时主栈已不可用。
- 不要在处理器中分配内存或格式化字符串，缓冲区应静态分配。
- 多线程同时崩溃时只允许一个线程执行采集，其他线程等待或退出。
- 复杂采集交给独立进程，父进程只传递文件描述符与必要信息。

### 8.11 （场景）栈溢出导致的崩溃如何识别？

- 故障地址接近栈边界或保护页，`si_addr` 与 `info proc mappings` 可以确认。
- 回溯通常只剩少量帧或完全失败，因为栈指针已越界。
- 递归调用、超大局部数组与变长数组是常见原因。
- `sigaltstack` 配合 `SA_ONSTACK` 才能在栈溢出时执行处理器。
- 编译器栈保护能发现部分溢出，但不能替代栈大小与递归深度检查。
- 复现时限制栈大小可以稳定触发，便于确认边界条件。

```cpp
int depth(int n) {
    volatile char buf[4096];
    buf[0] = (char)n;
    return depth(n + 1) + buf[0];  // 无终止条件，栈最终溢出
}
```

### 8.12 （辨析）SIGSEGV 与 SIGABRT 的报告差异？

- `SIGSEGV` 由非法内存访问触发，`si_code` 区分地址未映射与权限错误。
- `SIGABRT` 由 `abort` 触发，常见来源是断言失败、未捕获异常与堆一致性检查。
- `SIGABRT` 的栈顶通常在 `abort` 与 `raise`，真正原因在更下层或之前的日志中。
- `SIGSEGV` 的故障地址与访问类型是定位关键，`SIGABRT` 更依赖断言消息与堆状态。
- 两者都可能被信号处理器捕获，但恢复执行通常不可行。
- 报告聚合时应把信号编号与顶层业务帧一起作为签名的一部分。

### 8.13 （场景）minidump 相比 core 缺少什么？

- minidump 只保存选定内存区域，通常包含线程栈、模块列表与异常信息，不含完整堆。
- 缺少完整堆时无法检查被破坏对象的全局引用，只能依赖栈上的局部信息。
- Linux 上的 Breakpad minidump 与 Windows 的格式相近，但采集能力受实现限制。
- 需要更多内存时可在崩溃时按地址范围追加，或改用完整 core。
- minidump 体积小，适合大规模上报，代价是分析深度受限。
- 采集策略应根据问题类型选择，内存破坏类问题通常需要更完整的转储。

### 8.14 Windows 上如何生成与分析 minidump？

- 进程内调用 `MiniDumpWriteDump`，由异常过滤器触发，转储类型决定包含的信息。
- 系统级可用 WER 的 `LocalDumps` 注册表配置，或 `procdump` 在异常时抓取。
- 分析用 WinDbg，设置符号路径后执行 `!analyze -v` 获取异常与栈。
- PDB 必须与二进制匹配，匹配依据是 GUID 与年龄，文件名不能作为依据。
- 私有符号服务器可以按需加载 PDB，避免把符号分发到每台机器。
- 完整转储体积大，通常只在受控环境开启，线上使用小型转储加按需内存。

### 8.15 （场景）崩溃只发生在发布版本，如何定位？

- 发布版本通常开启优化并定义 `NDEBUG`，断言被移除，未定义行为的表现随之改变。
- 优化会改变对象布局、栈复用与变量生命周期，依赖调试版本的观察可能失效。
- 分配器、库版本与编译选项差异也会影响行为，需逐项对齐。
- 用相同优化级别加调试信息构建复现版本，保持代码生成一致。
- 检查只在发布版本启用的特性开关与安全加固选项。
- 若仍无法复现，比较两次运行的输入、环境与并发度，缩小差异。

```cpp
int checked(int i) {
    assert(i != 0);  // NDEBUG 下被移除
    return 10 / i;
}
```

### 8.16 崩溃去重与聚合的键如何选择？

- 签名通常由异常类型、顶层业务帧与若干层调用栈组成，需去掉地址与偏移。
- 构建 ID 应参与签名，否则不同版本的同一位置会被错误合并。
- 模板参数与 inline 展开会让函数名变化，归一化时可按规则裁剪。
- 过度聚合会掩盖不同根因，聚合不足会产生大量重复问题。
- 分配点与释放点可作为辅助键，用于区分同一崩溃点的不同来源。
- 定期抽样复核聚合结果，确认签名规则没有随编译器升级失效。

### 8.17 （场景）崩溃率上升但栈相同，如何判断根因？

- 先确认发布范围与时间相关性，比较新旧版本的崩溃率与影响面。
- 栈相同不代表原因相同，输入分布、并发度与依赖版本都可能变化。
- 查看崩溃时的寄存器、故障地址与对象大小，寻找分布上的差异。
- 对比同时段的延迟、内存与错误日志，排除资源耗尽导致的次级崩溃。
- 用灰度批次做对照，确认问题是否只出现在特定环境或设备。
- 若无法从聚合数据分辨，增加临时字段采集，避免以直接回滚代替分析。

### 8.18 （实现）如何在崩溃报告中附带线程与寄存器？

- 遍历 `/proc/self/task` 获取线程列表，但崩溃时文件系统操作可能不可用，需预先采集或由外部进程完成。
- `ucontext_t` 提供崩溃线程的寄存器，其他线程的寄存器需要暂停后读取。
- 保存线程 ID、名称与栈指针，便于判断死锁与竞争。
- 模块列表包含加载地址与构建 ID，符号化时用于换算地址。
- 数据量要控制，线程数多时只保留栈顶若干帧。
- 采集格式应稳定，服务端解析器与客户端版本需要兼容。

### 8.19 （辨析）崩溃与未定义行为的对应关系？

- 未定义行为不必然崩溃，可能表现为错误结果、静默继续或看似正常的执行。
- 崩溃也可能来自完全定义的行为，例如资源耗尽、外部输入与硬件故障。
- 越界写破坏相邻对象后，崩溃点可能远离真正的错误位置。
- 信号处理器、栈溢出与分配失败属于运行时环境问题，与语言层面的未定义行为不同。
- 用 sanitizer 与静态分析缩小未定义行为的范围，用崩溃转储确认现场。
- 不能因为程序没有崩溃就认定不存在未定义行为。

### 8.20 崩溃分析平台如何做回归验证？

- 把触发崩溃的输入、环境与构建信息保存为回归用例，修复后重新运行。
- 验证标准是同一签名不再出现，崩溃总数下降不能作为依据。
- 在 CI 中加入针对已知崩溃的测试，防止修复被回退。
- 平台应能对比修复前后的版本，确认没有引入新的崩溃类型。
- 对无法复现的问题，记录采样与观察窗口，持续监控签名变化。
- 关闭问题前保留证据链接，便于后续同类问题参考。

## 9. sanitizer 与动态分析

### 9.1 （场景）ASan 报错但本地无法复现，如何缩小范围？

- 先确认本地与 CI 的编译选项一致，优化级别、`-fsanitize` 组合与标准库版本都会改变行为。
- 使用同一二进制与同一组 `ASAN_OPTIONS` 运行，环境变量差异会影响隔离区与泄漏检测。
- 把测试输入、随机种子与并发度固定，避免执行路径漂移。
- 在 CI 日志中查找 `AddressSanitizer` 前后的进程状态，确认并非 OOM 导致的退出。
- 用 `log_path` 把报告写入文件，避免多进程输出交错。
- 仍无法复现时，用 `-fsanitize-recover=address` 收集多个报告，再按栈聚合。

### 9.2 （陷阱）ASan 报告中的分配栈与访问栈为何矛盾？

- 分配栈描述对象创建位置，访问栈描述越界访问位置，两者本来不同。
- 地址可能已被释放并重新分配，分配栈对应新的使用者，释放栈才是关键。
- `fast_unwind_on_malloc=0` 让分配栈基于帧指针展开，默认的快速展开在缺少帧指针时可能不准确。
- inline 与尾调用会让栈帧折叠，`llvm-symbolizer --inlines` 可以展开。
- 多线程下报告可能来自另一个线程的访问，线程编号需要与日志对照。
- 报告矛盾通常说明对象生命周期复杂，应结合隔离区大小与释放点分析。

### 9.3 ASan 与 Valgrind 的定位差别？

- ASan 在编译期插桩，运行开销约 2 倍，只能检查被插桩的代码。
- Valgrind 在二进制层动态翻译，不需要重新编译，能检查未插桩的第三方库。
- Valgrind 的 Memcheck 能发现未初始化读，ASan 不提供该检查。
- Valgrind 运行开销通常在 20 倍以上，不适合长时间运行与性能测试。
- ASan 支持多平台与多架构，Valgrind 对新指令集与平台的支持滞后。
- 选择取决于是否能重编译、是否需要检查未初始化内存以及可接受的时间成本。

### 9.4 （场景）TSan 报告的数据竞争如何判定真假？

- 先看两侧访问栈是否真的并发，线程创建与 join 关系能否解释顺序。
- 检查是否存在 TSan 不识别的同步，例如自定义自旋锁、信号量与直接 futex 调用。
- 原子操作与内存序会影响判定，宽松序下的竞争需要按内存模型分析。
- 信号处理器与 `volatile` 轮询常被误报，需用注解或抑制说明。
- 第三方库未插桩时，库内部的同步不可见，可能产生误报。
- 确认是真竞争后，修复应建立 happens-before 边，简单加锁只能掩盖问题。

```cpp
int counter = 0;

void bump() {
    for (int i = 0; i != 100; ++i) {
        ++counter;  // 缺少同步，TSan 会报告数据竞争
    }
}
```

### 9.5 TSan 在 CI 中的时间预算如何控制？

- TSan 的 slowdown 通常在 5 到 10 倍，内存占用也显著增加，长测试需要分片。
- 只对并发相关的测试集启用，其余测试用普通构建。
- 使用 `-O1` 或 `-O2` 降低插桩开销，过低优化会放大运行时成本。
- 设置单用例超时，避免竞争导致的挂起占满执行机。
- `TSAN_OPTIONS=halt_on_error=0` 可以在一次运行中收集多个报告，但要防止后续状态被污染。
- 把 TSan 放到夜间或合并后任务，门禁只保留高风险模块。

### 9.6 （场景）UBSan 报告在发布构建中消失如何解释？

- 高优化级别可能删除未执行分支或合并访问，原本触发检查的路径不再存在。
- 发布构建可能使用 `-fwrapv` 或 `-fno-strict-overflow`，有符号溢出的语义被改为回绕，检查不再报告。
- 检查只覆盖实际执行的代码，输入与并发度变化会改变覆盖范围。
- `-fsanitize-trap` 把报告替换为陷阱，日志中没有诊断文本，容易被误判为未触发。
- 构建系统可能只在调试配置中追加 `-fsanitize=undefined`，发布配置没有该选项。
- 对比不同优化级别与完整编译命令，确认检查是否被启用以及路径是否可达。
- 保留 UBSan 构建的符号与日志，避免因优化后的行号变化误读位置。

### 9.7 （陷阱）UBSan 报告的行号为何指向调用方？

- 优化与 inline 会把检查点归并到调用者，行号对应编译器认为的出错位置。
- 宏展开会让位置指向宏定义或使用点，`-g` 的宏信息可以改善。
- 模板实例化的位置可能显示为实例化点，而非模板内的语句。
- `print_stacktrace=1` 输出完整调用栈，比单行位置更有用。
- 低优化级别下行号通常更接近源码，但覆盖的路径不同。
- 不能只根据行号修改代码，应结合报告中的检查类型与表达式。

### 9.8 MSan 需要全程序插桩，工程上如何满足？

- 所有参与链接的代码都要用 MSan 编译，包括 C 与 C++ 标准库。
- 预编译的第三方库必须重新构建，或使用带 MSan 的发行版库。
- 系统调用与汇编需要拦截器或手动标记，否则影子状态会丢失。
- 与 ASan、TSan 互斥，CI 中需要独立任务与独立构建目录。
- `-fsanitize-memory-track-origins=2` 提供来源链，开销更高。
- 无法全量插桩时，MSan 的结论只对已插桩部分有效。

### 9.9 （场景）sanitizer 只在第三方库中报错，如何处理？

- 先确认报告是否由库的合法行为触发，例如自定义分配或访问内部缓冲区。
- 能升级或替换库时优先修复依赖，避免在本地累积抑制。
- 无法修改时，用抑制文件按栈帧过滤，并记录库版本与原因。
- 抑制范围要尽量窄，按函数名过滤，避免整个库失效。
- 在库的边界加注解或包装层，把不透明的内存操作标记为已初始化或可访问。
- 定期复核抑制条目，库升级后重新评估。

### 9.10 插桩开销如何度量？

- 准备同一份代码的普通构建与插桩构建，使用相同输入与机器。
- 记录墙钟时间、CPU 时间、峰值 RSS 与系统调用次数，`/usr/bin/time -v` 可以给出基础数据。
- 分别测量冷启动与热路径，插桩对启动阶段的影响通常更大。
- 用固定迭代次数与预热消除缓存差异，避免单次测量波动。
- 性能测试不应在插桩构建上做结论，插桩会改变内存布局与分支行为。
- 把开销数据写入 CI 报告，工具链升级后可以对比变化。

### 9.11 如何在发布前做 sanitizer 分级门禁？

- 第一级在每个合并请求运行 ASan 与 UBSan 的单元测试，覆盖新增代码。
- 第二级在夜间运行 TSan 与完整集成测试，覆盖并发路径。
- 第三级在发布候选上运行 MSan 与长时间模糊测试，覆盖未初始化读与边界输入。
- 门禁按新增报告判断，存量问题单独跟踪，避免总数量掩盖回归。
- 每级设置超时与资源上限，失败时保留完整日志与复现命令。
- 分级依据是风险与成本，全部检查常开会拖慢合并。

### 9.12 （场景）ASan 与自定义内存分配器冲突如何排查？

- 自定义池从系统申请大块内存后自行切分，ASan 只能看到大块，无法检测池内越界。
- 池内释放的内存不会进入 ASan 隔离区，use-after-free 可能漏报。
- 用 `__asan_poison_memory_region` 标记空闲区域，分配时解除标记。
- 分配器的元数据与用户块位于同一大块时，ASan 无法区分越界访问与合法元数据访问，报告可能指向分配器内部。
- 检查分配器是否绕过 `malloc` 直接使用 `mmap`，这会改变泄漏检测的结果。
- 在 sanitizer 构建中切换到系统分配器，可以判断问题是否来自分配器交互。

```cpp
char* pool = new char[4096];

char* take(int offset) {
    return pool + offset;  // ASan 只看到整块，无法发现池内越界
}
```

### 9.13 （辨析）sanitizer 抑制与代码注解的取舍？

- 抑制按栈帧或函数名过滤，作用范围大，容易掩盖同函数的其他问题。
- 注解在代码中声明语义，范围精确，但需要修改源码并维护空实现。
- 第三方库适合抑制，自有代码适合注解。
- 抑制文件应随工具链版本管理，升级后重新验证。
- 注解要有注释说明前置条件，否则会被误用为关闭检查的手段。
- 两者都需要复核周期，长期积累会降低检测的有效性。

### 9.14 （实现）如何为自定义容器补充 sanitizer 注解？

- 连续存储容器可以用 `__sanitizer_annotate_contiguous_container` 标记已构造区间。
- 扩容与销毁时更新注解，确保未构造区域被标记为不可访问。
- 非连续结构用 `__asan_poison_memory_region` 标记空闲槽位。
- 注解接口在非 sanitizer 构建中应提供空实现，避免条件编译散落。
- 注解错误会产生误报，需用单元测试覆盖容量变化与异常路径。
- 标准库容器已由实现处理，自定义容器才需要手动维护。

```cpp
void shrink(char* begin, char* end, char* new_end) {
    __sanitizer_annotate_contiguous_container(begin, end, new_end);
}
```

### 9.15 （场景）多进程程序如何收集 sanitizer 报告？

- 每个子进程独立设置 `log_path`，文件名包含 PID，避免多个进程写同一文件。
- fork 之后选项继续生效，exec 之后依赖环境变量，包装脚本要显式传递。
- 父进程回收子进程时读取退出码，`exitcode` 选项可让 sanitizer 失败与普通失败区分。
- 守护进程可能关闭标准错误，报告必须落盘，采集端定期扫描目录。
- 父进程重启崩溃子进程会掩盖问题，需要在聚合层统计同一签名的出现次数。
- 容器内多进程共享卷，报告目录要可写并设置容量上限，避免占满。

### 9.16 （陷阱）sanitizer 未覆盖的路径为何仍可能崩溃？

- 插桩只检查实际执行的代码，未运行的路径不会被验证。
- 未插桩的第三方库、汇编与 JIT 代码不在检查范围内。
- 信号处理器、`longjmp` 与自定义栈切换会破坏运行时假设。
- 数据竞争可能只在特定调度下出现，TSan 也需要对应执行。
- sanitizer 不能替代输入验证与资源限制，资源耗尽不属于其检查范围。
- 覆盖率高不代表路径全覆盖，需结合覆盖率与静态分析评估。

### 9.17 动态分析还有哪些非 sanitizer 手段？

- Valgrind 的 Memcheck、Helgrind 与 DRD 覆盖内存与并发问题，不需要重新编译。
- Dr. Memory 在 Windows 上提供类似能力，适合无法使用 ASan 的场景。
- 分配器自带的检查，例如 glibc 的 `MALLOC_CHECK_` 与 `MALLOC_PERTURB_`，可以发现部分堆破坏。
- 堆剖析工具可以记录分配栈与生命周期，用于分析泄漏与碎片。
- 系统调用跟踪与 eBPF 可以观察资源使用，但不检查内存安全。
- 这些工具的开销与覆盖不同，通常与 sanitizer 组合使用。

### 9.18 （场景）预编译第三方库如何参与 sanitizer 构建？

- ASan 构建可以与未插桩的库链接，分配与释放仍会被拦截，但库内代码没有插桩，检测范围只覆盖本项目。
- TSan 与 MSan 要求库也插桩，否则同步与初始化状态不可见。
- 预编译库的 ABI 与编译器版本不匹配时，可能出现符号冲突或运行时崩溃。
- 优先获取源码重新构建，或使用发行方提供的插桩版本。
- 无法重建时，把库调用隔离到独立进程，用进程边界限制影响。
- 在报告中标注未插桩模块，避免把漏报误认为没有问题。

### 9.19 sanitizer 报告的归档与去重如何做？

- 签名由错误类型、顶层业务帧与分配点组成，去掉地址与线程编号。
- 保存完整日志、构建 ID、运行选项与复现输入，便于后续分析。
- 同一签名在不同版本重复出现时，应关联到同一问题，避免重复建单。
- 编译器升级会改变帧名与 inline 展开，归一化规则需要更新。
- 报告数量用于趋势分析，修复优先级应结合严重程度与影响面。
- 定期清理已修复的签名，避免历史数据干扰判断。

### 9.20 如何评估引入 sanitizer 的工程收益？

- 统计引入前后在测试与灰度阶段发现的缺陷数量与类型。
- 关注逃逸到生产的缺陷，尤其是内存安全与并发问题。
- 计算 CI 时间与机器成本，比较新增发现与新增开销。
- 记录误报率与处理误报的人力，误报过高会降低团队信任。
- 以试点项目的数据为依据，再决定推广范围与门禁级别。
- 收益评估应持续进行，工具链与代码结构变化会改变结论。

## 10. 静态分析与代码规范

### 10.1 静态分析在流水线中的位置如何选择？

- 提交前在本地运行格式与快速检查，减少往返。
- 合并请求阶段对改动文件运行增量分析，反馈时间控制在分钟级。
- 合并后运行全量分析，覆盖跨文件与跨翻译单元的问题。
- 发布前对高风险模块运行深度分析，例如 Coverity 或路径敏感检查。
- 位置越靠前修复成本越低，但工具能力与耗时也越受限。
- 同一规则不应在多个阶段重复报告，结果需要去重与合并。

### 10.2 clang-tidy 的检查项如何选型？

- 从高信号类别开始，例如 `bugprone-*`、`cert-*` 与 `cppcoreguidelines-*` 中的确定性规则。
- 风格类检查交给格式化工具，避免与分析告警混在一起。
- 逐项评估误报率与修复成本，低价值检查会增加噪音。
- 用 `-*` 清空默认集合，再显式启用，避免版本升级引入未评估的检查。
- 项目专属约定可以通过 `CheckOptions` 配置，避免修改检查源码。
- 选型结果写入版本控制，评审时说明新增或移除的理由。

### 10.3 （场景）clang-tidy 在 CI 上耗时过长如何优化？

- 只分析改动文件及其直接依赖，全量分析放到夜间任务。
- 用 `run-clang-tidy` 的并行选项按核数拆分，注意内存占用。
- `-header-filter` 限制头文件告警范围，避免每个翻译单元重复分析同一头文件。
- 关闭开销大且收益低的检查，按项目度量数据调整。
- 复用已有的编译数据库，避免每个任务重复生成配置。
- 在流水线层按文件与检查配置缓存结果，未变化的文件直接跳过。

### 10.4 （陷阱）`compile_commands.json` 不完整会导致什么？

- 生成文件、自定义命令与外部构建的翻译单元可能不在数据库中，分析时被静默跳过。
- 缺少宏定义与包含路径会导致解析失败，产生大量虚假告警。
- 交叉编译的目标架构与系统头文件不一致，检查结果可能不适用。
- 数据库中的命令若包含相对路径，工作目录错误会让头文件解析失败。
- 构建系统变更后数据库需要重新生成，旧文件不会自动更新。
- CI 中应校验数据库覆盖的源文件比例，低于阈值时告警。

### 10.5 Coverity 的构建捕获为何容易失败？

- 捕获依赖编译器包装器，直接调用 `ld` 或自定义编译脚本会绕过捕获。
- 并行构建可能产生竞争，捕获工具对临时文件与工作目录有假设。
- 不支持的编译器版本或新语言特性会导致前端解析失败。
- 构建未清理时，增量捕获可能遗漏未重新编译的文件。
- 交叉编译需要正确配置编译器类型与系统头文件路径。
- 捕获日志中的错误要逐条处理，忽略后分析结果不完整。

### 10.6 （辨析）Coverity 与 clang-tidy 的能力边界？

- clang-tidy 基于 AST 与局部规则，速度快，适合风格、易错模式与部分语义检查。
- Coverity 做过程间、路径敏感分析，能发现资源泄漏、空指针与并发问题。
- clang-tidy 可以给出自动修复，Coverity 以缺陷报告为主。
- Coverity 需要完整构建捕获，配置与授权成本高。
- clang-tidy 的跨翻译单元能力有限，链接期问题通常无法发现。
- 两者结果需要统一去重与分级，避免同一缺陷重复派单。

### 10.7 误报如何分类与处理？

- 分类至少包括真实缺陷、误报、有意为之、工具限制与暂不修复。
- 每条结论要有证据，例如代码路径、标准条款或运行时验证。
- 误报应反馈给工具配置或规则维护者，本地抑制只是临时手段。
- 暂不修复要记录原因与复核条件，避免长期堆积。
- 统计各类比例与处理时长，识别规则质量与流程瓶颈。
- 关闭前确认修复已被测试覆盖，防止同一问题再次出现。

### 10.8 抑制注释如何写才可审计？

- 注明规则名、原因、负责人与失效条件，必要时附问题编号。
- 抑制范围尽量小，优先单行，避免整个文件失效。
- 使用工具支持的语法，例如 `NOLINT` 与 `coverity[...]`，避免自定义标记。
- 定期扫描抑制注释，检查对应代码是否仍然存在。
- 规则升级后重新评估旧抑制，避免沿用已失效的理由。
- 抑制数量作为技术债务指标，纳入趋势观察。

```cpp
int read(char* buf, int size) {
    return ::read(0, buf, size);  // NOLINT(bugprone-easily-swappable-parameters)
}
```

### 10.9 （场景）规则集升级后告警激增如何处理？

- 先在旁路任务运行新规则集，保留旧结果作为对照。
- 按规则与文件统计新增告警，区分真实缺陷、规则误报与风格差异。
- 新规则默认不阻断合并，设置观察期与修复配额。
- 对存量代码建立基线，只要求新增代码满足新规则。
- 与规则维护者确认变更原因，必要时调整检查参数。
- 升级与业务变更分开提交，便于回滚与对比。

### 10.10 自定义 clang-tidy 检查如何实现与维护？

- 以 Clang 插件形式实现 `ClangTidyCheck`，注册匹配器与诊断。
- 插件与 LLVM 版本强绑定，升级工具链时需要重新编译与测试。
- 检查逻辑要有单元测试，覆盖正例、反例与边界语法。
- 诊断信息应给出修复建议，降低使用成本。
- 分发方式可以是内部构建的二进制或预编译插件，需考虑跨平台。
- 自定义检查的维护成本高，优先使用现有检查与配置组合。

### 10.11 （辨析）编码规范与静态分析规则的关系？

- 编码规范描述团队约定，包含命名、接口设计与错误处理等难以自动检查的内容。
- 静态分析规则是规范中可机械判定的子集，工具只覆盖一部分。
- 规范中的每条规则应说明理由与例外，否则难以在评审中执行。
- 工具规则与规范条目需要建立映射，避免出现两套互不一致的要求。
- 规范更新时同步评估工具配置，防止检查与文档脱节。
- 不能因为工具通过就认为符合规范，人工评审仍不可替代。

### 10.12 告警门禁应设置在哪个级别？

- 阻断合并的应是高置信度的错误，例如未定义行为、安全漏洞与资源泄漏。
- 风格与性能建议可以作为警告，不阻断合并但进入待办。
- 新增代码与存量代码采用不同标准，存量通过基线管理。
- 门禁规则要可解释，开发者能理解为何被阻断以及如何修复。
- 过于严格的门禁会促使开发者拆分提交或添加抑制，反而降低质量。
- 定期复核阻断规则的有效性，移除长期无真实发现的检查。

### 10.13 （场景）增量分析为何漏掉跨文件问题？

- 只分析改动文件时，其他翻译单元没有重新分析，跨文件的重复定义与不一致无法发现。
- 头文件改动会影响包含它的所有文件，增量范围需要按依赖图扩展。
- ODR 违规、ABI 不匹配与链接错误通常只在完整构建中暴露。
- 过程间分析需要全程序视图，增量运行会退化为局部结论。
- 用夜间全量分析与链接期检查补足，增量结果只作为快速反馈。
- 记录增量与全量结果的差异，评估漏报风险。

### 10.14 （场景）宏与模板导致的分析误报如何处理？

- 宏展开后源码位置指向宏定义，告警难以对应到调用点，需要借助调试信息中的宏映射或工具的位置还原。
- 模板实例化的诊断可能落在实例化点，同一模板的多个实例会重复报告，应按模板与参数聚合。
- 条件编译会隐藏部分分支，分析配置需要与目标构建的宏定义一致，否则结论不适用于实际产物。
- 宏生成的声明可能缺少完整类型信息，工具按保守规则推断，容易产生误报。
- 用 `constexpr`、inline 函数与类型别名替代复杂宏，可以从源头减少分析歧义。
- 对无法避免的宏，缩小抑制范围并在宏定义处说明约束条件。
- 把宏与模板相关告警纳入规则评估，确认工具版本升级后行为变化。

### 10.15 （实现）如何度量静态分析的有效性？

- 统计真实缺陷占报告总数的比例，以及修复所需时间。
- 跟踪逃逸到测试或生产的缺陷，分析静态分析为何没有发现。
- 记录每条规则的命中与误报，按规则评估价值。
- 对比引入前后的缺陷密度与评审工作量。
- 指标按项目与时间窗口聚合，避免单次扫描的波动。
- 定期抽样人工复核，确认分类标准没有漂移。

### 10.16 （陷阱）修复告警引入行为变化如何防范？

- 自动修复可能改变求值顺序、生命周期与异常行为，必须逐条审查。
- 修复提交应与功能变更分开，便于回滚与定位。
- 用测试与 sanitizer 验证修复，覆盖原本触发告警的路径。
- 涉及接口与布局的修改要检查 ABI 兼容性。
- 对无法确认语义的告警，选择抑制并记录原因，强行修改会引入风险。
- 批量修复后运行完整回归，避免局部正确而整体失效。

```cpp
int value = 0;
if (value = 1) {  // 赋值作为条件，工具可能建议改为比较
}
```

### 10.17 （场景）安全规则（CERT、MISRA）如何裁剪？

- 先明确适用标准与合规要求，安全关键项目与通用业务的规则集不同。
- 逐条评估规则与项目实践的匹配度，记录偏离理由与补偿措施。
- 工具对规则的支持程度不一，部分规则只能人工检查。
- 裁剪结果形成项目规则集，随标准版本更新。
- 偏离项要有审批与复核周期，不能一次性永久豁免。
- 规则数量不等于安全性，重点是高风险类别的覆盖。

### 10.18 静态分析结果如何与代码评审结合？

- 把告警以评论形式附在改动行上，减少评审者切换工具的成本。
- 阻断项与建议项使用不同标记，避免被大量提示掩盖。
- 评审者关注设计、接口与测试，工具负责机械规则，两者分工明确。
- 对反复出现的告警，补充规范条目或检查配置，逐次评论无法阻止复发。
- 评审记录中保留告警处理结论，便于后续追溯。
- 工具结果延迟过高会脱离评审上下文，尽量在提交后几分钟内反馈。

### 10.19 （辨析）静态分析与模糊测试的互补？

- 静态分析覆盖所有代码路径的近似，能发现未被执行的分支问题。
- 模糊测试基于真实执行，能发现静态分析难以建模的输入相关缺陷。
- 静态分析的误报需要人工判断，模糊测试的崩溃可直接复现。
- 模糊测试依赖语料与覆盖率，长期未覆盖的路径仍是盲区。
- 两者共用 sanitizer 与符号化设施，结果可以关联到同一缺陷。
- 组合使用比单独依赖一种手段更能覆盖内存安全与逻辑错误。

### 10.20 静态分析平台的长期维护成本？

- 工具许可、执行机容量与存储是固定成本，随代码规模增长。
- 规则升级、插件编译与结果去重需要专人维护。
- 误报处理消耗开发者时间，抑制积累会降低工具价值。
- 平台与构建系统、代码托管、缺陷跟踪的集成需要持续适配。
- 指标与报告要定期清理，避免历史数据干扰判断。
- 维护预算应与覆盖范围匹配，盲目扩大规则集会增加负担。

## 11. 内存安全与加固

### 11.1 （辨析）越界读与越界写的影响有何不同？

- 越界读通常不立即改变程序状态，后果是信息泄露或后续分支判断错误。
- 越界写可破坏相邻对象、返回地址或堆元数据，后果是崩溃或控制流被劫持。
- 两者在 C++ 中都属于未定义行为，标准不为任一者规定结果，`[expr.add]` 只允许指针在数组范围内移动。
- 检测手段相同：消毒器的 redzone、编译期长度检查、页保护与分配器校验。
- 越界读更隐蔽，把内存内容写入日志或哈希输出的路径会把泄露扩散到外部。
- 修复手段不同：读越界可用受限视图收敛范围，写越界还需追查长度来源。
- 可利用性取决于越界距离与写入内容，连续小范围写入比大范围破坏更难被发现。

### 11.2 （场景）栈缓冲区溢出如何被检测？

- 栈保护在函数序言写入 canary，函数返回前比对，值不匹配时调用 `__stack_chk_fail`。
- canary 的取值与存放位置由实现定义，常见实现从线程本地存储读取。
- `-fstack-protector` 只覆盖含数组或取地址局部变量的函数，`-fstack-protector-strong` 覆盖范围更大，`-fstack-protector-all` 覆盖全部函数。
- 该机制只能发现返回地址被改写，不能阻止溢出本身，也不能发现未触达 canary 的越界。
- `_FORTIFY_SOURCE` 在编译期已知目标大小时把 `memcpy` 一类调用替换为带检查的版本，需要开启优化。
- 消毒器用 redzone 直接检出越界写，代价是内存与时间开销，通常不进入生产构建。
- 硬件层面的影子栈与内存标签可覆盖编译器插桩无法触及的路径。

### 11.3 （陷阱）use-after-free 为什么在生产环境中难以复现？

- 释放后的内存通常仍在进程地址空间内，读取往往返回旧值而不触发错误。
- 是否崩溃取决于分配器是否复用该块、复用者写入的内容以及访问时序。
- 调试构建的填充模式与生产分配器不同，调试环境能暴露的问题在发布版本中消失。
- 常见的分配器优先复用同尺寸的空闲块，释放后写入会污染新分配的对象。
- 消毒器的隔离区延迟复用，把偶发问题变成稳定失败，是定位该类缺陷的主要手段。
- 生产环境可用的手段是分配器加固与崩溃聚合，检出能力弱于消毒器。
- 根因多为所有权不清，修复应明确唯一所有者，而非依赖分配器的行为。

### 11.4 （辨析）ASan、MSan、TSan 与 UBSan 分别覆盖什么？

- ASan 检测堆、栈与全局对象的越界访问以及释放后使用，依赖影子内存与 redzone。
- MSan 跟踪未初始化内存的传播，要求全部代码与标准库都插桩，否则漏报。
- TSan 检测数据竞争与锁序问题，基于 happens-before 关系，时间与内存开销显著。
- UBSan 在运行时检查有符号溢出、移位越界与空指针解引用，默认只报告不终止。
- ASan 与 TSan 不能同时启用，二者对内存布局的要求冲突。
- 各工具的结论只覆盖被执行到的路径，未覆盖分支的问题不会被发现。
- 常见组合是单元测试跑 ASan 与 UBSan，并发测试跑 TSan，模糊测试跑 ASan。

### 11.5 （实现）栈保护的 canary 如何在栈帧中布局？

- 序言读取 guard 值写入栈帧，尾声再次读取并比对。
- guard 的初值由运行时在进程启动时设置，具体来源由实现定义。
- canary 位于局部缓冲区与保存的返回地址之间，溢出必须先覆盖它才能改写返回地址。
- 局部变量的排列顺序由实现定义，编译器可重排以把缓冲区放在高地址侧。
- 比对失败进入 `__stack_chk_fail`，该函数通常打印信息后终止进程。
- 覆盖 canary 的溢出在函数返回时被发现，未覆盖 canary 的溢出不被发现。
- 该机制的性能影响集中在函数序言与尾声，`-fstack-protector-strong` 是常见折中。

### 11.6 （条款）标准中哪些操作属于未定义行为且常被利用？

- 数组下标越界与指针算术超出同一数组范围，见 `[expr.add]`。
- 解引用生命周期已结束的对象，见 `[basic.life]`。
- 有符号整数溢出，见 `[expr.pre]` 对结果可表示性的要求。
- 移位位数为负或不小于类型宽度，见 `[expr.shift]`。
- 通过错误类型的指针访问对象，违反严格别名规则。
- 读取未初始化的自动变量，其值不确定。
- 编译器可假定上述情况不发生，依赖它们的检查可能被优化删除。

### 11.7 CFI 在哪些位置插入检查？

- 间接调用、虚函数调用与函数指针赋值是主要检查点。
- 检查内容是比较目标地址的类型签名与调用点期望的签名是否一致。
- Clang 的实现依赖链接期优化，签名信息需要跨翻译单元可见。
- 开启方式为 `-fsanitize=cfi` 配合 `-flto`，可按需选择 `-fsanitize=cfi-icall` 与 `-fsanitize=cfi-vcall`。
- 微软的 Control Flow Guard 维护合法目标位图，粒度比类型签名粗，但不需要链接期优化。
- CFI 只约束控制流转移的目标集合，不阻止数据面攻击。
- 隐藏符号可见性可缩小需要生成签名的函数集合，降低开销。

### 11.8 （场景）CET 的影子栈与 IBT 分别防什么？

- 影子栈保存返回地址的副本，执行 `ret` 时比对，拦截返回地址被改写。
- IBT 要求间接跳转目标以 `endbr64` 开头，拦截跳转到任意 gadget。
- 两者互补，影子栈约束返回，IBT 约束间接调用与跳转。
- `-fcf-protection=branch` 只插入 IBT 标记，`-fcf-protection=full` 同时处理返回地址。
- 影子栈能否生效取决于操作系统与硬件支持，缺少支持时该部分不生效。
- CET 不检验参数与数据，无法阻止数据面攻击。
- 收益依赖进程镜像整体按该选项编译，混用会降低覆盖范围。

### 11.9 （辨析）ASLR 与 PIE 的关系是什么？

- ASLR 是内核特性，随机化栈、堆、共享库与可执行文件的加载基址。
- PIE 让可执行文件按位置无关方式链接，使其加载基址可被随机化。
- 未使用 PIE 时主程序代码段地址固定，ASLR 只能随机化库与栈。
- 编译用 `-fPIE`，链接用 `-pie`，可用 `readelf -h` 确认文件类型为 `DYN`。
- ASLR 只提高利用门槛，信息泄露可绕过，需要与其他缓解手段组合。
- 容器与部分嵌入式环境可能关闭 ASLR，部署配置需要确认。

### 11.10 沙箱的层次如何划分？

- 系统调用过滤：以 seccomp 一类机制限制进程可用的调用集合。
- 路径与资源约束：限制可访问的文件路径与网络命名空间。
- 权限约束：以非特权用户运行，设置 `PR_SET_NO_NEW_PRIVS`，裁剪能力集。
- 命名空间隔离：把挂载、网络与进程视图分开，限制可见对象。
- 虚拟机与轻量虚拟机提供更强的边界，代价是启动时间与内存开销。
- 语言级运行时（如 WebAssembly）限制内存访问与宿主调用，边界依赖运行时实现。
- 逃逸路径多来自共享的内核接口、文件描述符传递与信号处理。

### 11.11 智能指针为什么不能消除全部 use-after-free？

- `std::shared_ptr` 在最后一个持有者释放后销毁对象，循环引用会让对象永不销毁。
- 从 `std::shared_ptr` 取出的裸指针或引用在所有权结束后悬垂。
- `std::weak_ptr::lock` 返回的 `std::shared_ptr` 只在存活期间有效，访问期间仍需保持持有。
- 先检查 `expired` 再 `lock` 存在竞态，应直接 `lock` 并判断结果。
- `std::unique_ptr::release` 转移所有权，调用方负责删除，遗漏即泄漏。
- 返回容器元素引用的接口在容器扩容后失效，所有权并未因此改变。
- 生命周期信息应在签名中表达，`T&` 与 `T*` 不携带该信息。

### 11.12 （填空）这段复制函数缺少哪一项前置条件？

```cpp
void copyInto(char* dst, const char* src) {
    std::memcpy(dst, src, std::strlen(src) + 1);
}
```

- 函数没有目标容量参数，无法判断 `dst` 是否足以容纳源串与终止符。
- 调用方与被调用方对容量的假设不一致时发生越界写，属于未定义行为。
- `std::strlen` 与 `+ 1` 只保证长度覆盖终止符，与目标空间无关。
- 修复方式是增加目标容量参数并在复制前比较，或改用 `std::span<char>`。
- `std::span` 同时携带指针与长度，长度不再由调用方单独维护。
- `std::span` 不延长底层对象生命周期，从临时容器构造会立即悬垂。
- `std::span` 的 `operator[]` 不检查越界，其布局也不由标准规定，不适合作为跨编译器 ABI 的边界类型。

### 11.13 容器扩容为什么会使迭代器与引用失效？

- `std::vector` 扩容时重新分配缓冲区，原有指针、引用与迭代器全部指向旧缓冲区。
- 未触发扩容的 `push_back` 也会使尾后迭代器失效。
- `std::deque` 在首尾插入可能使迭代器失效，已存在的引用通常保持有效。
- `std::map` 的插入不使引用失效，`std::unordered_map` 的 rehash 使迭代器失效而引用保持有效。
- 预先 `reserve` 可按已知上界避免扩容，代价是提前占用内存。
- 在范围 `for` 中修改容器是常见错误，扩容后循环持有的引用悬垂。
- 以索引代替引用可规避该问题，但删除元素会改变索引与元素的对应关系。

### 11.14 加固选项如何组合并验证生效？

- 典型组合为 `-O2`、`-D_FORTIFY_SOURCE=2`、`-fstack-protector-strong`、`-fPIE`、`-pie`、`-fcf-protection=full`。
- 链接选项 `-Wl,-z,relro,-z,now,-z,noexecstack` 启用只读重定位与不可执行栈。
- `readelf -l` 可确认 `GNU_RELRO` 与 `GNU_STACK` 段的属性。
- `readelf -s` 或 `nm` 中出现 `__stack_chk_fail` 引用，说明栈保护进入产物。
- `checksec` 一类工具可汇总 PIE、RELRO、canary 与 NX 的状态。
- 生产与调试构建的选项应一致，否则缺陷在发布版本中表现不同。
- 加固只降低利用成功率，不修复缺陷本身。

### 11.15 （场景）内存标签与能力指针分别解决什么问题？

- 内存标签在指针高位携带少量标签位，分配时给内存打标签，访问时比对，不匹配触发故障。
- 标签位只有 4 位时取值空间为 16，重复分配可能让错误标签碰巧匹配，检测是概率性的。
- 同步模式在每次访问检查，异步模式延迟报告，后者开销更低但定位更难。
- 能力指针在指针中携带基址、长度与权限，越界访问在硬件层被拦截。
- 能力指针需要重新编译全部代码并调整 ABI，迁移成本远高于内存标签。
- 两者都属于体系结构层面的缓解，不改变语言层面的未定义行为规则。
- 采用前需要评估工具链、内核与库的完整支持程度。

### 11.16 模糊测试如何与消毒器配合发现内存缺陷？

- 模糊测试以覆盖率为反馈持续变异输入，把输入交给固定的测试入口。
- 与 ASan 或 UBSan 共同编译，越界与释放后使用在触发瞬间终止并给出调用栈。
- 语料库保存已覆盖路径的输入，崩溃用例应固化为回归测试。
- 长时间运行需要并行与限时参数，失败用例的复现依赖固定种子。
- 同一根因会产生大量重复报告，需要按调用栈去重。
- 输入解析层是优先目标，反序列化、协议解析与格式化最易触发缺陷。
- 模糊测试的覆盖依赖入口设计，接口过粗时有效路径难以到达。

### 11.17 标准容器为什么不做下标越界检查？

- `operator[]` 的复杂度要求为常数，检查会引入分支，标准未要求检查。
- 越界访问属于未定义行为，编译器可据此优化，检查也可能被删除。
- `at()` 提供检查并抛出 `std::out_of_range`，代价是异常路径与代码体积。
- 接口设计把检查责任交给调用方，以换取常规路径的零开销。
- libstdc++ 的 `_GLIBCXX_ASSERTIONS` 可在 `operator[]` 中插入检查，属于实现扩展。
- 在边界处把范围收敛为受限视图，可把检查集中到一处。
- 调试构建开启检查、发布构建关闭，是常见的折中方式。

### 11.18 双重释放为什么危险，如何检测？

- 第二次释放会让分配器把同一块插入空闲结构两次，后续两次分配可能返回同一地址。
- 部分分配器在空闲块中保存校验值，可检出部分双重释放，覆盖不完整。
- 消毒器在释放后把块放入隔离区并标记，第二次释放立即报告。
- 根因多为所有权重复，例如两个对象持有同一裸指针，或异常路径重复清理。
- 修复方式是让 `std::unique_ptr` 表达唯一所有权，并在转移后把源指针置空。
- 析构函数中重复释放会破坏堆元数据，崩溃位置常与根因相距很远。
- 崩溃聚合中的调用栈可用于定位首次与再次释放的位置。

### 11.19 分配器层面有哪些加固手段？

- 分离元数据与用户数据，降低溢出改写块头的收益。
- 在空闲块中保存校验值，检测块头被改写。
- 随机化分配地址与隔离区大小，降低地址的可预测性。
- 限制单次分配上限，避免长度计算溢出导致的过小分配。
- 明确处理分配失败，`new` 抛 `std::bad_alloc`，`nothrow` 版本返回空指针。
- 分配器加固与消毒器的目标不同，前者提高利用门槛，后者用于检出缺陷。
- 加固会带来内存与性能开销，需要按进程角色分别配置。

### 11.20 内存安全的改进应按什么顺序推进？

- 先建立可观测性：崩溃聚合、消毒器的持续集成任务与符号化调用栈。
- 再收敛高频缺陷：修复崩溃集中的越界与释放后使用，补齐入口处的长度校验。
- 引入类型约束：用 `std::span`、`std::string_view` 与受限视图替代裸指针与长度对。
- 加固编译与运行环境：栈保护、CFI、CET、ASLR 与沙箱。
- 长期方向是缩小不安全子集的使用范围，把新代码限制在受检查的接口内。
- 每一步都应有度量：崩溃率、消毒器任务失败数与缺陷修复周期。
- 改造优先级按模块划分，热路径与第三方代码的代价不同。

## 12. 安全编码与密码学

### 12.1 （辨析）比较认证标签为什么需要常量时间？

- 逐字节比较在首个不同字节处返回，耗时与匹配前缀的长度相关。
- 攻击者通过大量请求测量耗时分布，可逐字节恢复标签内容。
- 网络抖动通常大于单次比较的差异，但统计足够多的样本仍可恢复信号。
- 常量时间比较固定遍历全部字节，用按位或累积差异，只在最后产生分支。
- 该要求适用于 MAC、口令哈希与令牌校验，不适用于公开数据的比较。
- 编译器可能把累积循环改回提前退出，需要阻止此类优化。

### 12.2 （实现）如何实现常量时间比较？

```cpp
bool equalCT(const unsigned char* a, const unsigned char* b, std::size_t n) {
    unsigned char diff = 0;
    for (std::size_t i = 0; i < n; ++i) {
        diff = static_cast<unsigned char>(diff | (a[i] ^ b[i]));
    }
    return diff == 0;
}
```

- 迭代次数只依赖 `n`，与两个输入的内容无关。
- 累积使用按位或，避免提前返回与短路求值。
- 循环内不出现依赖数据的下标，避免缓存访问模式泄露信息。
- 编译器可能向量化或展开循环，可用 `volatile` 限定累积变量或插入编译器屏障，是否需要由实现与优化级别决定。
- 长度不同时直接返回会泄露长度，调用方应使用固定长度或先对输入做哈希。
- 返回值的比较位于循环之外，分支不再依赖秘密数据。
- 标准库未提供该功能，可依赖 `CRYPTO_memcmp` 或 `sodium_memcmp` 一类接口。

### 12.3 密码学随机数应从哪些来源获取？

- 操作系统提供内核熵源，Linux 上是 `getrandom`，Windows 上是 `BCryptGenRandom`。
- C++ 标准库的 `std::random_device` 是否使用密码学安全的来源由实现定义。
- 系统调用失败时应视为致命错误，不应回退到可预测的源。
- 伪随机数引擎的状态可从输出恢复，`std::mt19937` 在输出足够多之后即可重建状态。
- 令牌、盐、初始化向量与会话标识都必须来自密码学随机源。
- 大量随机数据应一次批量获取，逐次调用的系统开销较高。

### 12.4 （陷阱）`std::random_device` 能直接用于生成密钥吗？

- 标准只要求它产生非确定性随机数，实现可以是硬件指令、系统调用或伪随机算法。
- 部分实现以固定序列实现，输出完全可预测。
- `entropy()` 的返回值是估计值，返回 0 不代表不可用，也不代表可用。
- 每次取少量数据时性能可以接受，大量取用时系统调用开销明显。
- 即使播种安全，`std::mt19937` 的输出也不能用于密钥，其状态可从输出恢复。
- 密钥与令牌应使用平台提供的密码学接口或专用库。

### 12.5 密钥管理的基本要求有哪些？

- 密钥不进入源码、镜像与日志，配置中只保存引用或密钥标识。
- 运行时从密钥管理服务或硬件安全模块获取，优先使用短期凭证。
- 静态加密的密钥与密文分开存放，访问受最小权限与审计约束。
- 每把密钥绑定用途与算法，避免同一密钥承担加密与认证两种职责。
- 泄露响应需要轮换流程，包括吊销旧密钥与重加密受影响数据。
- 备份与恢复同样要保护密钥，避免备份成为薄弱环节。
- 本地开发环境使用独立密钥，不共享生产密钥。

### 12.6 密钥轮换如何设计？

- 密文携带密钥版本，解密时按版本选择密钥。
- 轮换期间新旧密钥并存，写入使用新密钥，读取兼容旧密钥。
- 加密密钥与认证密钥分别轮换，避免同一批次同时失效。
- 轮换周期由数据敏感度与合规要求决定，不能只按固定天数设定。
- 重加密历史数据需要限速与断点续跑，避免压垮存储。
- 轮换失败要能回退，回退窗口覆盖发布与回滚的完整周期。

### 12.7 （场景）口令存储为什么选择 Argon2 或 bcrypt？

- 通用哈希计算太快，离线爆破的代价低，不适合直接存储口令。
- 口令哈希需要可调的计算与内存代价，Argon2id 提供时间、内存与并行度参数。
- 每个口令使用独立盐，盐与哈希一起存储，防止相同口令产生相同结果。
- bcrypt 的输入上限为 72 字节，超出部分被截断，需要先做预哈希并注意编码。
- 校验失败与账号不存在应返回同一错误并保持相近耗时，避免枚举账号。
- 参数需要随硬件演进上调，旧哈希在下次登录时按新参数重算。

### 12.8 （陷阱）初始化向量或 nonce 重复使用会怎样？

- CBC 模式下重复 IV 会让相同明文产生相同密文，泄露明文之间的相等关系。
- 计数器模式下重复 nonce 会复用密钥流，两份密文异或即得两份明文的异或。
- GCM 的 nonce 重复会泄露认证密钥，属于严重缺陷。
- 随机生成 nonce 时，长度决定碰撞概率，96 位是常见取值。
- 使用计数器时状态需要持久化，进程重启后不能回到旧值。
- 根本约束是密钥与 nonce 的组合唯一，单看 nonce 唯一并不充分。

### 12.9 AEAD 的正确使用顺序是什么？

- 加密时先处理附加数据，再加密明文，输出密文与认证标签。
- 解密时必须先验证标签，再使用明文，不得先解析后校验。
- 认证失败应丢弃全部明文，不返回部分结果。
- 附加数据用于绑定上下文，例如版本号、消息序号与接收方标识。
- 密文与标签一起传输，标签长度不应截断。
- 标准库未提供 AEAD，通常依赖 OpenSSL 或 libsodium 的接口。

### 12.10 （辨析）哈希、MAC 与签名分别解决什么问题？

- 哈希提供完整性校验但没有密钥，攻击者可同时替换数据与哈希。
- MAC 用共享密钥提供完整性与来源认证，双方持有同一密钥。
- 签名用私钥生成、公钥验证，提供不可否认性，验证方不需要私钥。
- HMAC 是常用的 MAC 构造，避免把密钥与消息直接拼接后哈希。
- 签名依赖可信的公钥分发，证书链或预置公钥是前提。
- 三者都不提供机密性，机密性需要加密。

### 12.11 整数溢出如何转化为安全漏洞？

- 长度计算溢出后得到小值，分配过小的缓冲区，随后越界写。
- 有符号溢出属于未定义行为，编译器可假定不发生并删除相关检查。
- 无符号回绕由标准规定，但同样会让长度校验失效。
- 校验应在运算之前完成，用除法或上界比较代替事后检查。

```cpp
bool fits(std::size_t n, std::size_t elem) {
    return elem != 0 && n <= SIZE_MAX / elem;
}
```

- 编译器内建函数（如 `__builtin_mul_overflow`）可在不溢出的前提下完成运算并报告结果。
- 类型转换发生在校验之后仍会截断，例如先转 `int` 再比较。

### 12.12 格式化字符串漏洞的成因与防护？

- 把外部输入直接作为格式串传给 `printf`，`%x` 与 `%s` 会读取栈上或任意地址的数据。
- `%n` 可写入内存，配合可控参数可改写返回地址。
- 防护方式是把用户数据作为参数传入，格式串使用字面量。
- 编译期可用 `-Wformat` 与 `-Wformat-security` 检查。
- `printf` 的属性标注可把格式检查扩展到自定义函数。
- `std::format` 在格式串为常量表达式时于编译期检查，运行时错误抛出 `std::format_error`。
- 日志接口应把模板与参数分离，避免拼接后再次格式化。

### 12.13 路径穿越如何防御？

- 拼接用户提供的文件名之前先规范化，去掉 `..` 段与绝对路径前缀。
- 规范化后校验结果仍位于允许的根目录下。
- 符号链接可绕过字符串层面的检查，应使用 `openat` 配合 `O_NOFOLLOW` 或等价机制。
- 文件名采用白名单校验，限制字符集与长度。
- 临时文件使用 `mkstemp` 一类接口，避免可预测的文件名。
- 以最小权限运行进程，限制越界写入的影响范围。

### 12.14 命令注入的边界在哪里？

- 把外部输入拼接进命令行后，shell 会解释其中的元字符。
- 使用 `system` 与 `popen` 必然经过 shell，转义规则因 shell 而异。
- 优先使用 `execve` 一类直接传参数的接口，避免 shell 解析。
- 参数校验采用白名单，不允许的字符直接拒绝。
- 环境变量与 `PATH` 可被篡改，调用外部程序时使用绝对路径。
- 降低权限与限制可执行文件集合属于纵深防御，不能替代输入校验。

### 12.15 （陷阱）`strncpy` 与 `snprintf` 的终止符有哪些陷阱？

- `strncpy` 在源长度不小于 `n` 时不写终止符，后续按字符串处理会越界读。
- `strncpy` 会用 0 填充剩余空间，大缓冲区上的代价高。
- `snprintf` 返回本应写入的长度，截断时该值大于缓冲区大小。
- 把 `snprintf` 的返回值直接当作实际长度会越界读。
- `snprintf` 在 `n` 为 0 时不写入任何字节，但仍返回所需长度。
- 返回值转为 `int` 时可能为负，判断长度前需要检查符号。
- C++ 代码优先使用 `std::string`，避免手动管理终止符。

### 12.16 如何安全清除内存中的敏感数据？

- `std::memset` 在缓冲区随后不被读取时可能被优化删除。
- 需要 `explicit_bzero`、`SecureZeroMemory` 或带编译器屏障的填充函数。
- C++23 及之前的库没有提供该功能，需依赖平台或第三方接口。
- `std::string` 的短字符串优化把小串放在对象内部，扩容后旧缓冲区仍保留内容。
- 释放内存不会清零，分配器可能把旧内容交给下一个请求者。
- 密钥缓冲区可用 `mlock` 锁定，避免换页写入磁盘。
- 清除后应把指针与长度一并失效，避免清理完成后再被读取。

### 12.17 侧信道除了时间还包括哪些？

- 缓存侧信道通过访问时间推断被访问的内存地址。
- 推测执行让指令在分支结果确定前运行，可留下可观测的缓存痕迹。
- 分支预测与执行单元争用可泄露控制流信息。
- 功耗与电磁辐射属于物理侧信道，需要硬件层面的对策。
- 对策包括常量时间实现、避免以秘密作为下标、编译器屏障与推测执行屏障。
- 大整数运算的窗口法与表查找可能依赖秘密，需要固定的访问模式。
- 侧信道防护的代价较高，强度按威胁模型选择。

### 12.18 （辨析）`std::string` 适合存放密钥吗？

- 扩容时内容被复制到新缓冲区，旧缓冲区释放但内容未清零。
- 复制与移动语义使副本数量难以追踪，按值传参即产生副本。
- 短字符串优化让内容位于对象内部，对象被复制时内容随之复制。
- `operator==` 的耗时与公共前缀长度相关，不能用于比较秘密。
- 密钥应使用固定大小的缓冲区类型，例如 `std::array<std::byte, 32>`，并显式清零。
- 接口层面可删除复制构造，只保留移动与显式清零。

### 12.19 证书校验容易遗漏哪些步骤？

- 只检查证书是否过期不够，还要校验主机名与证书中的标识一致。
- 需要校验用途扩展与吊销状态。
- 自签名证书的信任锚必须显式配置，不能默认接受任意证书。
- 校验回调中返回接受会关闭校验，常见于调试代码遗留。
- 证书固定提高门槛，但需要配套的更新流程，否则轮换会导致中断。
- TLS 版本与密码套件应限制在安全集合，禁用已知弱的算法。
- 校验失败的错误应终止连接，不应降级重试。

### 12.20 安全编码评审应包含哪些检查项？

- 输入边界：长度、编码、空值与超限值是否在入口处校验。
- 内存与所有权：缓冲区大小的来源、释放路径与异常路径的清理。
- 整数运算：乘加是否可能溢出，类型转换是否发生在校验之前。
- 密码学使用：算法与模式、随机源、nonce 的唯一性、密钥来源。
- 错误处理：失败是否被静默忽略，错误信息是否泄露内部细节。
- 并发：共享状态的同步方式、锁的持有范围与原子操作的内存序。
- 依赖与构建：加固选项、告警级别与第三方库版本。

## 13. 供应链与依赖安全

### 13.1 SBOM 的作用与格式是什么？

- SBOM 是制品所含组件的清单，记录名称、版本、来源与依赖关系。
- 常见格式为 SPDX 与 CycloneDX，前者偏许可证合规，后者偏安全与漏洞管理。
- 用途包括漏洞响应、许可证审计与制品溯源。
- 生成时机在构建阶段，与制品一起签名并归档。
- C++ 项目的难点在静态链接与头文件依赖，最终产物中的组件需要从构建图推导。
- SBOM 必须随版本更新，否则与实际制品脱节。
- 清单中记录组件哈希，可在事后核对内容。

### 13.2 （场景）如何为 CMake 项目生成 SBOM？

- 从构建系统导出依赖图，记录每个目标的来源、版本与许可证。
- 包管理器（Conan、vcpkg）可导出依赖清单，作为 SBOM 的输入。
- 静态链接的第三方代码需在构建脚本中显式登记，不能只依赖包管理器清单。
- 生成脚本读取锁文件，保证清单与实际构建一致。
- 产物与 SBOM 用同一构建编号关联，便于回溯。
- 生成过程纳入持续集成，避免人工维护导致的遗漏。
- 首次生成的清单需要与二进制成分分析结果比对，确认覆盖范围。

### 13.3 依赖审计的流程如何组织？

- 先建立依赖清单，包括直接依赖、传递依赖与构建期依赖。
- 把组件版本映射到漏洞数据库，注意同一组件在不同生态中的命名差异。
- 按可达性排序，被调用路径上的代码优先处理。
- 修复选项包括升级、打补丁、禁用功能与替换实现。
- 审计结果要有责任人与期限，否则清单会长期积压。
- 定期重跑审计，漏洞数据库持续更新。
- 审计范围包括构建工具与镜像中的组件。

### 13.4 构建可复现的要求是什么？

- 相同源码、相同工具链与相同环境下重复构建，得到逐字节相同的制品。
- 需要固定编译器版本、标准库、构建脚本与依赖的精确版本。
- 时间戳、绝对路径、用户名与随机种子必须可控或消除。
- 归档格式中的成员顺序与权限需要规范化。
- 可复现性是验证构建未被篡改的前提，独立方可用相同输入重建并比对哈希。
- 完整可复现难以一步达成，可先在相同环境内做到可复现。

### 13.5 （实现）构建结果不确定的常见来源有哪些？

- `__DATE__` 与 `__TIME__` 把构建时间写入二进制。
- `__FILE__` 展开为路径，绝对路径随构建目录变化。
- 链接顺序与哈希表遍历顺序影响符号与段的布局。
- 并行编译使目标文件的处理顺序不同，归档成员顺序随之变化。
- 临时文件名与随机种子可能进入调试信息。
- 对策是固定路径、固定链接顺序与统一的构建时间戳。
- `-ffile-prefix-map` 可同时归一化 `__FILE__` 与调试信息中的路径。

### 13.6 制品签名解决什么问题？

- 签名证明制品由持有私钥的一方发布，且内容未被修改。
- 验证方需要可信的公钥来源，签名本身不建立信任。
- Sigstore 一类方案使用短期证书与透明日志，把签名与身份绑定。
- 签名应覆盖制品与 SBOM，任一被替换都可被发现。
- 私钥的保护等级决定整体安全性，泄露后可伪造任意制品。
- 签名不检查制品是否含漏洞，只保证来源与完整性。

### 13.7 （辨析）校验和与签名有何区别？

- 校验和只能发现传输错误，攻击者可同时替换文件与校验和。
- 签名使用私钥，验证方只需公钥，能抵抗有意的篡改。
- 校验和的计算不需要密钥，任何人都能生成。
- 哈希值可作为签名的输入，签名保护的是哈希而非全文。
- 从同一站点下载文件与校验和时，安全性依赖传输层。
- 供应链场景应使用签名，或至少从独立渠道获取校验和。

### 13.8 供应链攻击的常见入口有哪些？

- 依赖安装阶段执行脚本，例如包管理器的安装钩子。
- 依赖混淆：内部包名在公共仓库被抢注。
- 维护者账号被盗后发布恶意版本，包名与签名都可能有效。
- 构建环境被入侵，源码未改而产物被替换。
- 镜像与代理被劫持，下载内容与上游不一致。
- 对策包括锁定版本与哈希、使用私有仓库、最小权限的构建账号与产物签名。

### 13.9 依赖版本应如何固定？

- 锁定到精确版本与内容哈希，而非语义化版本范围。
- 锁文件纳入版本控制，并在构建中强制使用。
- 传递依赖同样需要固定，否则上游变更会改变构建结果。
- 升级通过显式提交完成，评审中可见依赖变化。
- 固定版本会延迟安全更新，需要配套的定期升级流程。
- 从源码构建时固定 commit 哈希，而非分支名。

### 13.10 vendoring 与 fork 的维护代价是什么？

- 代码复制进仓库后与上游脱节，上游修复需要手动移植。
- 需要记录来源版本与本地改动，否则无法判断合并时的语义。
- 补丁应尽量提交上游，减少长期分叉。
- vendoring 的好处是构建不依赖外部网络，供应链面收敛。
- 定期同步应纳入计划，长期不动的副本会成为漏洞来源。
- 许可证义务在复制代码时同样适用。

### 13.11 CVE 与 CVSS 的使用限度在哪里？

- CVE 标识漏洞，CVSS 给出严重性评分，二者都不描述特定项目是否受影响。
- 评分基于假设场景，与实际可达性和缓解措施无关。
- 受影响版本范围由厂商公告给出，需要逐条核对。
- 未被分配 CVE 的缺陷同样存在，审计不能只看数据库。
- 修复优先级应结合可达性、暴露面与利用条件。
- 评分可作为沟通工具，不宜作为唯一决策依据。

### 13.12 （陷阱）`FetchContent` 直接拉取分支有什么风险？

- 分支内容可变，同一配置在不同时间得到不同代码。
- 缺少完整性校验，中间人可替换下载内容。
- 构建依赖网络，离线环境与审计环境难以复现。
- 拉取的代码在配置阶段执行构建脚本，具有构建机权限。
- 应固定到 commit 哈希，或改用带锁文件的依赖管理。
- 缓存目录的复用可能掩盖内容变化，变更后需要清理再验证。

### 13.13 工具链本身如何纳入信任边界？

- 编译器、链接器与代码生成工具都可能被替换，产物随之改变。
- 使用发行版或厂商签名的工具链，并校验下载包的签名。
- 容器镜像固定摘要，而非标签。
- 构建机的访问权限最小化，构建日志需要留存。
- 引导信任问题无法完全消除，只能缩小范围。
- 独立重建或双构建可提高发现篡改的概率。

### 13.14 二进制成分分析补充了什么？

- 源码清单无法覆盖预编译库、静态库与复制进仓库的代码。
- 二进制分析从符号、字符串与特征码推断组件与版本。
- 推断结果存在误报，版本号可能被裁剪或改写。
- 适合审计历史制品与来历不明的依赖。
- 与 SBOM 互补：清单声明应当是什么，二进制分析验证实际是什么。
- 结果需人工确认，不能直接作为合规结论。

### 13.15 私有依赖与镜像如何管理？

- 私有包仓库限制可发布者，降低依赖混淆的风险。
- 镜像同步上游需校验签名或哈希，避免缓存被污染。
- 代理应记录拉取来源，便于事后追溯。
- 内部包使用命名空间前缀，避免与公共仓库重名。
- 镜像的保留策略影响可复现构建，旧版本不能随意删除。
- 认证凭证不应写入构建脚本，使用短期令牌。

### 13.16 构建环境如何隔离？

- 每次构建使用干净容器，基础镜像固定摘要。
- 构建过程禁止访问公网，依赖预先下载并校验。
- 构建账号只有读取源码与写入产物的权限。
- 环境变量与挂载点最小化，避免泄露凭证。
- 产物在隔离环境中签名，私钥不进入构建容器。
- 日志保留完整命令与环境信息，便于复现。

### 13.17 依赖图中的菱形依赖如何处理？

- 同一库的多个版本被不同上游要求，包管理器通常选择其中一个。
- 版本选择规则因生态而异，可能导致 ABI 不兼容。
- C++ 缺少统一的 ABI 标准，混用不同版本的同名库会出现符号冲突。
- 对策是统一版本、使用 `inline namespace` 隔离，或把依赖隐藏在实现文件之后。
- 静态链接时重复符号会导致链接错误，动态链接时先加载者生效。
- 依赖收敛需要构建系统提供版本对齐机制，并在评审中检查。

### 13.18 SBOM 与实际制品的漂移如何发现？

- 漂移指清单声明的组件与制品实际内容不一致。
- 用二进制成分分析对制品做独立核对。
- 构建时记录每个目标的输入哈希，作为清单的补充。
- 制品发布后无法重建时，漂移难以通过重建发现。
- 定期对线上制品抽检，比对符号与字符串特征。
- 漂移的责任在流程：清单应由构建系统生成，而非人工维护。

### 13.19 （场景）发现依赖存在严重漏洞后如何处置？

- 先确认受影响版本范围与调用路径，判断是否真的可达。
- 评估暴露面：相关代码是否处理外部输入，是否在特权进程中运行。
- 可临时缓解：关闭相关功能、增加输入过滤、在网络层阻断。
- 升级到修复版本，验证 ABI 兼容与行为变化。
- 无法升级时评估打补丁的维护成本与提交上游的路径。
- 处置结果回写到清单与漏洞跟踪系统，形成闭环。
- 同类依赖应一并排查，漏洞往往成批出现。

### 13.20 许可证合规与安全审计如何协同？

- 依赖清单同时服务许可证与漏洞管理，可复用同一份 SBOM。
- 许可证类型影响分发方式，静态链接会把库代码并入产物。
- 需要区分开发期依赖与分发产物中的依赖。
- 许可证变更可能随版本发生，升级时要重新核对。
- 合规检查应自动化，在合并请求阶段拦截不允许的许可证。
- 安全修复与许可证审查的优先级可能冲突，需要明确的决策流程。

## 14. 代码评审与遗留系统

### 14.1 代码评审应优先关注什么？

- 正确性：边界条件、错误路径、并发与资源生命周期。
- 接口与语义：命名是否表达意图，前置条件是否明确。
- 可测试性：新增分支是否有对应的测试。
- 安全性：输入校验、权限检查与敏感数据处理。
- 可维护性：重复、耦合与隐含假设。
- 风格问题交给格式化工具与静态检查，不占用评审注意力。
- 意见应指向具体行，并说明理由与可选方案。

### 14.2 评审的规模如何控制？

- 单次评审的改动量在数百行以内时缺陷发现率较高，超过之后明显下降。
- 大改动拆分为可独立理解与回滚的提交。
- 机械改动（重命名、格式化）与语义改动分开提交。
- 评审等待时间过长会导致上下文丢失，应设定响应时限。
- 评审者数量以两人左右为宜，过多会分散责任。
- 并发、密码学与序列化等高风险改动需要具备相应背景的评审者。

### 14.3 （场景）如何评审一段并发代码？

- 明确共享状态的范围，确认每个共享变量的同步方式。
- 检查加锁顺序，是否存在交叉加锁的可能。
- 检查锁的保护范围是否覆盖读改写全过程。
- 条件变量的等待放在循环中，处理虚假唤醒。
- 原子操作的内存序与需求匹配，`memory_order_relaxed` 是否足够。
- 对象析构与线程退出的顺序，是否存在线程访问已销毁对象。
- 用 TSan 运行相关测试，作为评审的补充证据。

### 14.4 评审中的风格分歧如何处理？

- 有自动化工具覆盖的规则不进入人工讨论。
- 项目内已有约定时按约定执行，不在单个改动中引入新风格。
- 无约定时以可读性与一致性为准。
- 争议较大时记录决策与理由，形成可查的约定。
- 意见区分必须修改与建议，避免无谓阻塞。
- 风格讨论的成本应计入评审时间预算。

### 14.5 （辨析）重构与重写的边界在哪里？

- 重构在不改变外部行为的前提下调整结构，可逐步验证。
- 重写替换实现，行为可能变化，验证依赖测试与对比。
- 遗留系统缺少测试时，重写的风险主要来自未文档化的行为。
- 重构的每一步应保持可构建、可发布。
- 重写适合边界清晰、行为可枚举的模块。
- 混合策略是先在外围补测试与埋点，再替换核心。

### 14.6 如何理解没有文档的遗留代码？

- 从入口点反向追踪调用链，记录实际路径。
- 用日志与埋点在运行环境中观察真实行为。
- 用版本控制历史定位每次修改的原因与关联缺陷。
- 把观察到的行为写成特征测试，固定现状。
- 识别隐式依赖：全局变量、环境变量、文件路径与时间。
- 与业务方确认哪些行为是需求，哪些是历史偶然。

### 14.7 特征开关如何支持渐进替换？

- 开关把新旧实现的选择放在运行时，便于小流量验证。
- 开关应有明确的生命周期，替换完成后删除。
- 开关组合会导致测试矩阵膨胀，需要限制同时生效的开关数量。
- 开关状态需要可观测，指标按开关分组。
- 默认值指向稳定实现，异常时回退。
- 开关的读取路径要缓存，避免每次请求都访问配置中心。

### 14.8 渐进替换如何用路由层落地？

- 在新旧系统之间加入路由层，按请求特征逐步切换流量。
- 先替换边缘功能，验证数据通路与监控，再替换核心。
- 新旧系统并存期间需要数据同步或双读。
- 路由规则可回退，切换粒度从百分比到单用户。
- 旧系统在没有流量后仍需保留一段时间，用于对比与回退。
- 下线旧系统需要明确的所有权与时间点。

### 14.9 双写与对账如何设计？

- 双写指同时写入新旧存储，失败时的处理顺序决定一致性。
- 先写新再写旧与先写旧再写新，故障语义不同，需要明确以哪边为准。
- 双写不能保证原子性，需要补偿或对账修正。
- 对账任务按主键比对，记录差异并分类：缺失、内容不同与时间偏移。
- 差异修复要幂等，重复执行不产生副作用。
- 对账指标包含差异率与修复延迟，作为切换门槛。

### 14.10 技术债如何记录与量化？

- 条目包含影响范围、触发条件、修复代价与不修复的风险。
- 用可观测指标表达影响：故障次数、变更失败率与构建时长。
- 与业务目标关联，避免清单变成无人处理的愿望列表。
- 定期评审清单，合并重复项并删除已失效项。
- 修复排期占用固定比例的时间，而非等到空闲。
- 量化不必精确，粗略排序已足够支持决策。

### 14.11 （陷阱）缺少测试时直接重构有什么风险？

- 无法区分行为变化与结构调整，缺陷在发布后才暴露。
- 遗留代码的行为可能被外部系统依赖，包括错误码与日志格式。
- 先补特征测试，用现有实现生成期望值，再开始改动。
- 测试覆盖对外接口与关键数据流即可，不必追求行覆盖率。
- 重构过程保持小步提交，每步都能回退。
- 在关键路径加埋点，用生产流量验证新旧行为一致。

### 14.12 如何为遗留代码建立接缝？

- 接缝是可以在不修改调用方的前提下替换行为的位置。
- 把静态函数调用改为通过接口或函数指针间接调用。
- 把全局状态收敛到显式传入的上下文对象。
- 用链接期替换同名符号隔离外部依赖，适合测试替身。
- 提取接缝不改变行为，可作为独立提交评审。
- 接缝增加一层间接，热路径上需评估开销。

### 14.13 遗留系统中的全局状态如何处理？

- 先枚举全局变量与单例，记录读写位置与初始化顺序。
- 静态初始化顺序问题跨翻译单元时尤为隐蔽。
- 把全局状态改为显式依赖，通过构造函数传入。
- 无法立即移除时，提供重置接口供测试使用。
- 全局状态影响并发安全，多线程访问需要同步或改为线程局部。
- 迁移按模块推进，避免一次性改动引发大范围回归。

### 14.14 接口版本如何演进而不破坏调用方？

- 新增可选参数与新增虚函数都会影响二进制兼容，需要按 ABI 规则评估。
- 通过新增函数而非修改签名来扩展能力。
- 结构体尾部追加字段可保持旧调用方可用，但改变大小会影响按值传递。
- `inline namespace` 可用于并行维护多个版本。
- 弃用先标记再移除，给出迁移窗口与替代方案。
- 兼容性测试应覆盖用旧版本编译的调用方。

### 14.15 （实现）如何在不改调用方的前提下替换实现？

- 保持头文件中的声明不变，替换实现文件或所链接的库。
- 用抽象接口加工厂函数隐藏具体类型，调用方只依赖接口。
- 动态库替换需要 ABI 一致，包括类布局、虚表顺序与异常规格。
- 符号可见性设为隐藏，避免内部符号被外部绑定。
- 通过适配层把旧接口映射到新实现，逐步迁移调用方。
- 替换后要做行为对比测试，接口不变不代表语义不变。

### 14.16 代码度量指标的限度在哪里？

- 圈复杂度反映分支数量，不反映分支之间的耦合。
- 行数与函数长度是粗略指标，长函数也可能结构清晰。
- 重复率工具受限于语法匹配，语义重复难以发现。
- 覆盖率反映执行到的代码，不反映断言质量。
- 指标适合发现异常点，作为考核目标会被针对性优化。
- 结合缺陷历史与变更频率，能更准确定位高风险模块。

### 14.17 评审意见应该怎样写？

- 指出问题所在的行与具体条件。
- 说明影响：在什么输入或并发时序下出错。
- 给出可选方案，并说明各自的代价。
- 区分阻塞性问题与改进建议，便于作者安排。
- 对不确定的判断标明不确定性，邀请作者补充上下文。
- 避免评价性措辞，聚焦代码与行为。

### 14.18 大规模机械改动如何评审？

- 机械改动由工具生成，提交说明写明生成命令与参数。
- 拆分为纯机械改动与后续语义改动两个提交。
- 用脚本核对一致性，例如统计替换次数与残留匹配。
- 评审重点放在工具配置与例外清单，而非逐行核对。
- 保留生成脚本，便于复现与增量执行。
- 构建与测试必须全部通过，机械改动也可能引入编译错误。

### 14.19 （场景）如何设计可回滚的发布？

- 制品不可变，回滚即切换到上一个版本的制品，而非重新构建。
- 数据库变更需要向前兼容：先新增列与双写，再切换读取，最后删除旧列。
- 回滚窗口内新旧版本必须能同时运行，接口与数据格式保持兼容。
- 配置与特性开关独立于制品，可单独回退。
- 回滚演练定期执行，验证备份与流量切换的实际耗时。
- 监控指标能区分版本，回滚决策依赖明确的阈值。

### 14.20 遗留系统如何安全下线？

- 先确认没有调用方：分析访问日志、依赖扫描与人工确认。
- 把下线拆成停止写入、只读与停止服务三个阶段。
- 只读阶段保留足够长时间，覆盖季度性业务与批处理任务。
- 数据按合规要求归档，保留恢复路径。
- 通知相关方并记录确认，避免遗漏内部脚本与定时任务。
- 下线后移除凭据与网络入口，减少遗留攻击面。

## 15. 系统设计题与代码阅读

### 15.1 （场景）设计限流器时先澄清哪些问题？

- 限流对象：按用户、按来源地址、按接口还是按全局。
- 限流粒度：每秒请求数、并发数还是带宽。
- 超限行为：拒绝、排队还是返回降级结果。
- 一致性要求：单机精确即可，还是多节点共享配额。
- 时间窗口语义：固定窗口、滑动窗口还是令牌桶。
- 可观测性：限流命中率、拒绝原因与配额使用情况。
- 失败策略：限流组件不可用时放行还是拒绝。

### 15.2 （辨析）令牌桶与漏桶分别适合什么流量形态？

- 令牌桶按固定速率补充令牌，桶容量决定允许的突发量。
- 漏桶以固定速率输出，平滑突发，队列满时丢弃。
- 需要允许短时突发时用令牌桶，需要严格平滑时用漏桶。
- 令牌桶只需保存令牌数与上次补充时间，状态很小。
- 并发更新令牌数需要原子操作或锁，时间来源应使用单调时钟。
- 桶容量与补充速率按下游容量设定，而非按请求方的期望设定。

### 15.3 分布式限流的精度与一致性如何权衡？

- 集中式计数精度高，但每次请求都要远程调用，延迟与可用性受影响。
- 本地预取配额减少远程调用，代价是节点之间的配额分配不均。
- 滑动窗口可用分桶计数近似，内存与精度需要折中。
- 节点时钟不同步会让窗口边界漂移，本地间隔应使用单调时钟计算。
- 限流组件故障时的策略必须明确，放行会压垮下游，拒绝会影响可用性。
- 最终一致模型下短时超额可接受，为下游留出余量即可。

### 15.4 限流器的接口应如何设计？

- 返回结果包含是否允许、剩余配额与建议的重试间隔。
- 接口支持批量检查，减少远程调用次数。
- 配额维度用键表达，键的构造规则需要版本化。
- 失败语义明确，错误类型区分超限与组件不可用。
- 提供只读的查询接口，用于监控与调试。
- 接口不暴露内部算法，便于后续替换实现。

### 15.5 （场景）设计日志库时先确定哪些约束？

- 同步还是异步：同步在调用线程写入，异步经队列由后台线程落盘。
- 吞吐与延迟目标：每秒日志条数与单条写入的尾延迟。
- 丢失容忍度：进程崩溃时允许丢失多少条尚未落盘的记录。
- 格式化开销：热路径上是否允许分配内存。
- 输出目标：文件、标准错误、网络或多种组合。
- 线程模型：多生产者单消费者，还是每线程独立缓冲。
- 轮转与保留策略由日志库还是外部工具负责。

### 15.6 日志库如何在热路径上减少开销？

- 使用编译期格式串与结构化字段，避免运行时拼接。
- 日志级别尽早过滤，避免构造参数字符串。
- 参数以二进制形式入队，由后台线程完成格式化。
- 缓冲区按线程预分配，用环形队列减少锁竞争。
- 时间戳在入队时取一次，避免多次系统调用。
- 大对象采用截断或惰性求值，避免在热路径上序列化。

### 15.7 日志落盘与轮转如何保证不丢数据？

- 写入使用带缓冲的接口，按需同步到磁盘，在吞吐与持久性之间取舍。
- 同步只保证文件数据，目录项更新需要额外处理。
- 轮转时先重命名再创建新文件，避免并发写入交错。
- 多进程写同一文件应使用追加模式，跨进程交错仍可能发生。
- 保留策略按大小与时间双重触发，删除前确认已归档。
- 磁盘写满属于必须处理的失败路径，日志库不能因此阻塞业务。

### 15.8 异步日志的队列如何选择？

- 有界队列提供背压，队列满时阻塞生产者或丢弃日志，策略需显式配置。
- 无界队列把内存风险转移给进程，突发流量可能导致内存耗尽。
- 多生产者单消费者用互斥量与条件变量实现，简单且通常足够快。
- 高吞吐场景可用无锁环形队列，代价是实现复杂度与内存序的正确性。
- 消费者批量取出，减少唤醒次数。
- 关闭时需要排空队列，否则最后一批日志丢失。

### 15.9 （场景）设计任务调度器需要哪些组件？

- 任务表示：可调用对象、执行时间、优先级与取消令牌。
- 时间结构：最小堆或时间轮，决定插入与取出的复杂度。
- 执行器：线程池大小、任务窃取与优先级反转的处理。
- 持久化：进程重启后是否需要恢复未执行任务。
- 去重与幂等：同一任务重复投递时的处理方式。
- 可观测性：排队时长、执行时长、失败率与积压量。
- 关停语义：等待运行中任务完成还是立即中断。

### 15.10 时间轮与最小堆如何取舍？

- 最小堆的插入与删除为对数复杂度，适合任务数量不大且时间分散的场景。
- 时间轮把时间分桶，常见实现中插入为常数复杂度，适合大量定时任务。
- 分层时间轮用多个精度层级覆盖长时间范围，减少空转。
- 时间轮的取消需要从桶中移除，常用惰性删除加标记。
- 两者都依赖单调时钟，系统时间跳变不应影响调度。
- 执行时间的抖动由执行器吸收，而非调整调度结构。

### 15.11 调度任务的取消与生命周期如何管理？

- 取消是协作式的，任务需要周期检查取消信号。
- `std::stop_token` 提供标准的取消信号传递方式，C++20 引入。
- 取消后仍要等待任务退出，避免访问已销毁的捕获对象。
- 在析构函数中等待可能导致死锁，需要明确关停顺序。
- 延后执行的任务持有捕获对象的引用时，生命周期需由调度器保证。
- 取消语义要区分不再开始与中断执行中两种情况。

### 15.12 这段代码中的引用为什么悬垂？

```cpp
void appendAll(std::vector<std::string>& out, const std::string& prefix) {
    const std::string& first = out.front();
    out.push_back(prefix + first);
    std::cout << first.size();
}
```

- `first` 绑定到 `out.front()`，`push_back` 触发重新分配后该引用悬垂。
- `push_back` 的参数 `prefix + first` 在调用之前求值，此时 `first` 仍然有效。
- 悬垂发生在之后的 `first.size()` 调用，属于释放后使用。
- `out` 为空时 `front()` 属于未定义行为，函数对空输入没有防护。
- 未触发扩容时引用保持有效，缺陷只在容量不足时出现，难以稳定复现。
- 修复方式是先复制 `first`，或在函数起始处预留足够容量。

### 15.13 这个计数器存在什么并发缺陷？

```cpp
class Counter {
public:
    void add(int n) { value_ += n; }
    int value() const { return value_; }

private:
    int value_ = 0;
};
```

- `value_` 是非原子对象，多线程同时读写构成数据竞争，属于未定义行为。
- `add` 的读改写不是原子操作，两个线程的增量可能相互覆盖。
- `value()` 的读取同样参与竞争，标准不保证读到某个确定值。
- ASan 不检测数据竞争，需要 TSan 才能在测试中暴露。
- 修复方式是改用 `std::atomic<int>` 并声明为 `mutable`，或加锁保护两个操作。
- 只要求最终计数时 `memory_order_relaxed` 足够，与其他状态配合时需要更强的顺序。
- 成员改为原子类型后类不可复制，需要显式定义复制语义或删除复制。

### 15.14 这段求平均值的代码有哪些边界缺陷？

```cpp
int average(const std::vector<int>& v) {
    int sum = 0;
    for (int x : v) sum += x;
    return sum / static_cast<int>(v.size());
}
```

- 容器为空时 `v.size()` 为 0，除以 0 属于未定义行为。
- `sum` 为 `int`，元素较多或数值较大时有符号溢出，属于未定义行为。
- 元素数量超出 `int` 可表示范围时，`static_cast<int>(v.size())` 的结果不能用于除法。
- 整数除法向零取整，负数结果与算术平均的期望不同。
- 签名没有表达空输入的处理方式，调用方无法判断前置条件。
- 修复方式是返回 `std::optional<double>`，或要求非空并用更宽的类型累加。
- 若约定空输入返回 0，需要在函数内显式判断并写入接口文档。

### 15.15 这段更新函数违反了什么保证？

```cpp
struct Widget {
    std::string name;
    int index = 0;
};

void update(Widget& w, const std::string& name) {
    w.name = name;
    w.index = rebuildIndex(w);   // 可能抛出
    logUpdate(w);
}
```

- `rebuildIndex` 抛出时 `w.name` 已修改，对象处于部分更新状态。
- 这违反强异常保证，调用方捕获异常后看到的是不一致的 `Widget`。
- `logUpdate` 抛出时字段已更新而记录缺失，审计信息与状态不一致。
- 实现强异常保证的方式是先构造临时对象，全部成功后再交换。
- 让 `rebuildIndex` 接受新名称并返回索引，也可把赋值集中到末尾。
- `logUpdate` 的失败是否应影响更新结果，需要在接口中明确。
- `Widget` 没有自定义析构，交换不会抛出，可作为提交点。

### 15.16 这段资源管理代码漏掉了什么？

```cpp
void load(const char* path) {
    FILE* f = std::fopen(path, "rb");
    char* buf = new char[4096];
    if (std::fread(buf, 1, 4096, f) == 0) return;
    process(buf, 4096);
    std::fclose(f);
    delete[] buf;
}
```

- `fopen` 失败时 `f` 为空指针，`fread` 解引用空指针属于未定义行为。
- `fread` 返回 0 时提前返回，`buf` 与 `f` 都泄漏。
- `process` 抛出异常时，`fclose` 与 `delete[]` 都不会执行。
- 修复方式是用 `std::unique_ptr<FILE, decltype(&std::fclose)>` 管理文件，用 `std::vector<char>` 管理缓冲区。
- 缓冲区长度写死为 4096，实际读取字节数应以 `fread` 的返回值为准。
- 短读时 `process` 仍收到 4096，读取超出已读取内容的部分。
- 资源由对象析构释放后，异常路径与提前返回路径都会自动覆盖。

### 15.17 设计题中如何表达取舍？

- 先给出约束与假设，再给方案，最后说明方案在该约束下的代价。
- 明确容量估算的输入：请求量、增长率与单条数据大小。
- 对每个关键选择给出替代方案与不选的理由。
- 指出方案的失效点：在哪一级流量或哪种故障下失效。
- 说明演进路径：当前阶段的最小实现与后续扩展点。
- 承认未覆盖的部分，比声称方案完备更可信。

### 15.18 容量估算应包含哪些量？

- 请求速率与峰值系数，峰值通常是均值的数倍。
- 单请求的资源消耗：CPU 时间、内存与网络字节。
- 存储增长：单条记录大小乘以写入速率再乘以保留期。
- 连接数与文件描述符上限，常成为实际瓶颈。
- 余量系数：为故障切换与突发预留的容量。
- 估算结果用于选择分片数与副本数，而非精确预测。

### 15.19 （陷阱）系统设计中的过度设计有哪些表现？

- 在请求量很低的场景引入分布式协调与多级缓存。
- 为尚未出现的多租户需求增加隔离层。
- 用消息队列解耦同步调用，引入最终一致性与运维负担。
- 抽象层次过多，简单查询要穿过五层接口。
- 缺少度量支撑就提前优化热点。
- 判断标准是复杂度是否换来了可验证的收益。

### 15.20 从设计到落地需要补充哪些工程要素？

- 可观测性：指标、日志与追踪覆盖关键路径。
- 失败处理：超时、重试、熔断与降级的默认值。
- 容量与压测：明确单机上限与扩容方式。
- 变更管理：灰度、回退与配置版本化。
- 运维接口：健康检查、就绪检查与优雅关停。
- 文档：接口语义、状态机与故障处理手册。
