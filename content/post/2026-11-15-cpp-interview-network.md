## 1. 网络分层与封装

### 1.1（辨析）OSI 参考模型与 TCP/IP 模型如何对应？

- OSI 分为七层：物理层、数据链路层、网络层、传输层、会话层、表示层、应用层。
- TCP/IP 四层模型为链路层、网络层、传输层、应用层，会话层与表示层的职责并入应用层。
- 对应关系为物理层与数据链路层合并为链路层，网络层对应 IP 层，传输层对应 TCP 与 UDP。
- 五层模型在四层基础上拆出物理层，便于描述比特传输、编码与介质访问。
- 分层的依据是各层只依赖下层提供的服务，层间接口称为服务访问点（SAP），层间数据单元称为协议数据单元（PDU）。
- 实际协议栈并不严格对齐，TLS 位于应用层与传输层之间，ARP 与 ICMP 横跨网络层与链路层。
- OSI 的会话层与表示层缺少独立协议实现，相关功能由应用库承担。

### 1.2 数据从应用进程发出到网卡要经过哪些封装步骤？

- 应用调用 `send` 把数据写入套接字发送缓冲区，内核按 MSS 切分并加上 TCP 首部，形成 TCP 段。
- TCP 段交给 IP 层，加上通常 20 字节的 IPv4 首部，填写源地址、目的地址、协议号 6、TTL 与标识字段。
- IP 包交给链路层，加上 14 字节以太网首部，包含目的 MAC、源 MAC 与类型字段，尾部追加 4 字节 FCS。
- 网卡通过 DMA 读取帧，完成 CRC 计算与线路编码后发送；开启校验和卸载时，TCP 与 IP 校验和由硬件填写。
- 每层只处理本层首部，负载保持不变，封装的代价主要是首部开销与缓冲区复制。
- 发送路径上的切分受 MSS 约束，接收路径上的重组只发生在 IP 层（分片）与 TCP 层（乱序段）。
- 中间设备按层处理：交换机解析到以太网首部，路由器解析到 IP 首部并改写 TTL 与首部校验和。

### 1.3 接收路径上的解封装在哪些位置完成？

- 网卡校验 FCS 后通过 DMA 写入环形缓冲区，触发中断，或在 NAPI 模式下由轮询收包。
- 驱动剥离以太网首部，按类型字段分发：`0x0800` 交 IPv4，`0x86DD` 交 IPv6，`0x0806` 交 ARP。
- IP 层检查版本与首部校验和，按目的地址判断本机接收或转发，分片在此缓存等待重组。
- 传输层按协议号分发，TCP 用四元组查找控制块，UDP 用本地端口查找套接字。
- TCP 校验序列号与校验和，把按序数据放入接收队列并唤醒等待的进程。
- 未匹配到套接字的报文被丢弃，UDP 回送 ICMP 端口不可达，TCP 回送 RST。
- 校验和卸载开启时，网卡在描述符中标记校验通过，内核跳过软件校验。

### 1.4（辨析）MTU 与 MSS 有什么区别？

- MTU 是链路层一次能承载的最大帧负载，以太网为 1500 字节，由接口配置与链路协商决定。
- MSS 是 TCP 段中数据部分的最大长度，由双方在 SYN 中用 MSS 选项通告，不含 TCP 首部与 IP 首部。
- 以太网上 IPv4 的典型 MSS 为 1460 字节，IPv6 下为 1440 字节。
- MTU 约束 IP 包，超长时由 IP 层分片或丢弃；MSS 约束 TCP 载荷，超长时由 TCP 自行切分。
- MSS 只在握手时协商一次，路径 MTU 变化不会自动更新；MTU 可以按接口与路由逐跳变化。
- 隧道会额外占用首部，GRE 或 IPsec 下的有效 MTU 小于 1500，需要同步调整 MSS。

### 1.5 IP 分片与 TCP 分段有什么区别？

- 分段由 TCP 完成，发生在传输层，每段有独立首部与序列号，可以单独重传。
- 分片由 IP 完成，发生在网络层，只有首个分片携带传输层首部，其余分片共享同一标识字段。
- 分片偏移以 8 字节为单位，标志位 `MF` 表示后续还有分片，`DF` 禁止分片。
- 任一分片丢失都会导致整个数据报无法重组，传输层看到的是整段丢失。
- 分片增加重组开销与攻击面，重叠分片可用于绕过无状态防火墙，多数网络禁止分片。
- TCP 分段对中间路由器透明，IP 分片对中间设备可见，需要防火墙与 NAT 逐片处理。

### 1.6（场景）路径 MTU 发现如何工作，PMTUD 黑洞是什么现象？

- 发送端在 IP 首部置 `DF` 位，按本地 MTU 发送，不允许中途分片。
- 路由器发现包长超过出接口 MTU 时丢弃，并回送 ICMPv4 类型 3 代码 4，消息中携带下一跳 MTU。
- 发送端据此下调路径 MTU 缓存与 MSS，然后重传。
- 若 ICMP 被防火墙过滤，发送端会持续重传相同大小的包，形成 PMTUD 黑洞。
- 线上现象是握手与短请求正常，大响应卡住，`curl` 取小文件成功、取大文件挂起。
- 缓解手段包括在隧道接口上配置 `mtu`、放行 ICMP 类型 3 代码 4、在应用侧调小 MSS。

### 1.7 IPv4 首部校验和覆盖哪些字段，TCP 为什么还需要校验和？

- IPv4 首部校验和只覆盖首部，通常为 20 字节（含选项时更长），采用 16 位反码求和。
- 每经过一个路由器，TTL 减一，首部校验和必须重新计算，逐跳都有计算开销。
- 首部校验和只能发现首部错误，无法发现数据损坏，也无法发现地址被错误改写。
- TCP 校验和覆盖伪首部、TCP 首部与全部数据，提供端到端检测。
- 伪首部包含源地址、目的地址、协议号与 TCP 长度，使错误投递的段无法通过校验。
- IPv6 取消了首部校验和，把差错检测交给链路层 CRC 与传输层校验和，减少逐跳开销。

### 1.8 TCP 与 UDP 校验和中的伪首部包含什么？

- 伪首部包含源 IP 地址、目的 IP 地址、一个零字节、协议号与传输层长度。
- 伪首部不随报文传输，只参与计算，作用是把地址信息纳入校验范围。
- IPv4 下 TCP 的协议号为 6，UDP 为 17；IPv6 下改用 32 位长度与下一个首部字段。
- UDP 在 IPv4 中校验和可选，字段为 0 表示未计算；IPv6 中必须计算。
- TCP 校验和必须计算，接收端校验失败时静默丢弃，不回送差错报文。
- 校验和卸载开启后，抓包看到的校验和可能尚未由网卡填写，Wireshark 会标注为不正确。

### 1.9（陷阱）网卡校验和卸载对抓包有什么影响？

- 发送方向上，`tcpdump` 在网卡填写校验和之前抓包，TCP 与 UDP 校验和常显示为错误值。
- 接收方向上，网卡校验通过后内核不再重复校验，抓包看到的是线路上收到的原始值。
- Wireshark 按抓到的字节重新计算校验和，因此可能显示 `checksum: incorrect`，并不表示报文损坏。
- 虚拟网卡的卸载行为由驱动实现，`veth` 与 `virtio` 的处理并不一致，容器内抓包尤其容易误判。
- 判断校验和问题的可靠方式是在对端抓包，或临时执行 `ethtool -K eth0 tx off` 关闭卸载后复现。
- 关闭卸载会增加 CPU 开销，生产环境只在定位阶段短时启用。

### 1.10 以太网帧的最小与最大长度由什么决定？

- 以太网帧最小 64 字节（含 4 字节 FCS），负载不足 46 字节时由填充字段补齐。
- 最小长度源于共享介质上的冲突检测，帧必须持续足够长的时间才能被所有站点感知。
- 最大长度为 1518 字节，即 1500 字节 MTU 加 14 字节首部与 4 字节 FCS；带 VLAN 标签时为 1522 字节。
- 超过上限的帧称为巨型帧，常见配置为 9000 字节，需要链路两端与中间设备一致开启。
- 巨型帧降低首部开销与中断次数，同时增加单帧传输时延与丢包代价。
- 长度不符的帧被网卡丢弃，计入 `rx_length_errors` 与 `rx_over_errors`。

### 1.11 ARP 的解析过程是什么？

- 请求方广播 ARP 请求帧，目的 MAC 为 `ff:ff:ff:ff:ff:ff`，内容为询问某个 IP 对应的 MAC。
- 目标主机以单播回应，携带自身 MAC，请求方把映射写入 ARP 缓存。
- 缓存项有状态，Linux 下分为 `REACHABLE`、`STALE`、`DELAY`、`PROBE`，可用 `ip neigh` 查看。
- 条目老化后先置为 `STALE`，再次使用时直接发送并进入 `DELAY`，等待上层确认后回到 `REACHABLE`。
- 目的地址不在同一子网时，ARP 只解析默认网关的 MAC，不会解析最终目的地址。
- 缓存有容量与时间限制，表满时新条目可能被拒绝，表现为间歇性丢包。

### 1.12（场景）ARP 欺骗如何生效，有哪些观测与防护手段？

- 攻击者发送伪造的 ARP 应答，把网关地址映射到自身 MAC，流量随后经过攻击者转发或丢弃。
- 主机不校验未经请求的 ARP 应答，缓存被覆盖后不会主动恢复，直到条目老化或收到正确应答。
- 观测手段包括比对 `ip neigh` 中网关 MAC 与交换机记录的端口，以及监控同一 MAC 对应多个 IP 的现象。
- 接入交换机可开启动态 ARP 检测，依据 DHCP snooping 绑定表丢弃非法 ARP 报文。
- 主机侧可配置静态 ARP 条目，或用 `arp_ignore` 与 `arp_announce` 限制应答与通告范围。
- 根本手段是启用 802.1X 与端口安全，避免未授权设备接入同一广播域。

### 1.13 免费 ARP 有什么用途？

- 免费 ARP 是发送方 IP 与目标 IP 相同的 ARP 请求或应答，目的 MAC 通常为广播地址。
- 主机启动或网卡上线时发送，用于宣告地址并促使其他主机更新缓存。
- 配置 IP 前发送免费 ARP，若收到应答则说明地址已被占用，可用于冲突检测。
- 虚地址漂移（VRRP、Keepalived）切换后发送免费 ARP，使交换机与网关更新 MAC 表。
- 免费 ARP 不被所有系统接受，部分实现只对请求形式更新缓存。
- 大量免费 ARP 会形成广播风暴，需要在接入层做广播抑制。

### 1.14（辨析）交换机、路由器与网关在分层中各自处理什么？

- 交换机工作在数据链路层，按目的 MAC 查表转发，不修改帧内容，对未知单播在广播域内泛洪。
- 路由器工作在网络层，按目的 IP 查路由表转发，逐跳改写 TTL 与首部校验和，隔离广播域。
- 三层交换机兼具路由能力，转发由硬件完成，时延低于通用路由器。
- 网关是逻辑概念，指通往其他网段的下一跳，可以是路由器，也可以是主机上的虚拟接口。
- NAT 设备改写地址与端口，破坏端到端语义，需要额外处理校验和与 ICMP 载荷。
- 负载均衡器可能工作在四层或七层，七层设备会终结并重建连接。

### 1.15 VLAN 标签插在什么位置，对 MTU 有什么影响？

- 802.1Q 标签为 4 字节，插入在源 MAC 之后、类型字段之前，包含 12 位 VLAN ID 与 3 位优先级。
- 标签使帧的最大长度从 1518 变为 1522 字节，链路上的所有设备都需要支持该长度。
- 标签对上层透明，IP 层看到的 MTU 仍是 1500，但可承载的负载减少 4 字节。
- 双标签（QinQ）再增加 4 字节，常见于运营商接入，需要相应调整 MTU 或 MSS。
- 交换机按标签隔离广播域，跨 VLAN 通信必须经过三层转发。
- 标签在接入端口剥离、在干道端口保留，两端配置不一致会导致帧被丢弃。

### 1.16 环回接口的 MTU 与数据路径有什么特殊之处？

- Linux 的 `lo` 接口 MTU 为 65536，不做分片，适合本机大报文传输。
- 环回流量不经过网卡，数据在协议栈内部完成回环，仍会经过 IP 与 TCP 处理。
- 环回接口使用 `127.0.0.0/8` 与 `::1`，不依赖 ARP 解析。
- 在 `lo` 上抓包能看到进出两个方向的完整报文，序号与真实链路一致。
- 环回时延极低，基于环回的压测结果不能代表跨机性能。
- 本机连接仍受端口、全连接队列与 `somaxconn` 约束。

### 1.17（实现）TTL 字段的作用是什么，traceroute 如何利用它？

- TTL 是 IPv4 首部的 8 位字段，每经过一个路由器减一，减到 0 时丢弃并回送 ICMP 时间超过。
- 初值由发送端设定，常见为 64、128、255，可用于粗略判断路径长度。
- `traceroute` 依次发送 TTL 为 1、2、3 的探测包，收集每跳返回的 ICMP 消息与源地址。
- UDP 版本使用高位端口，收到 ICMP 端口不可达即认为到达目标；ICMP 版本使用 Echo 请求。
- 部分路由器不回复 ICMP 或对回复限速，路径中会出现 `*`，连续无响应即形成黑洞。
- IPv6 使用 Hop Limit 字段，语义相同；`tracepath` 还会利用路径 MTU 信息。

### 1.18 为什么分片会带来性能与安全问题？

- 分片把一次传输拆成多个 IP 包，接收端需要缓存与重组，占用内存并增加时延。
- 任一分片丢失都会导致整个数据报重传，在丢包链路上放大无效流量。
- 只有首个分片含传输层首部，后续分片没有端口信息，无状态防火墙难以过滤。
- 重叠分片可以让不同系统重组出不同内容，用于绕过检测。
- 分片泛洪会耗尽重组缓冲区，Linux 用 `ipfrag_high_thresh` 限制占用。
- 现代网络倾向在源端按路径 MTU 分段，并对分片流量限速或丢弃。

### 1.19 IP 地址与 MAC 地址的分工是什么，为什么两者都需要？

- IP 地址是逻辑地址，具有层次结构，可聚合路由，跨网段转发依赖它。
- MAC 地址是链路层地址，平面结构，只在同一广播域内有效，用于最后一跳交付。
- 以太网帧只能承载 MAC 地址，IP 包必须封装进帧才能发送，因此需要地址映射。
- ARP 负责在 IPv4 中完成映射，IPv6 用邻居发现协议完成同样功能。
- 每经过一个路由器，帧首部的源与目的 MAC 被重写，IP 地址保持不变，NAT 例外。
- 分离两者使上层地址可以独立于硬件变更，更换网卡不影响 IP 规划。

### 1.20（场景）跨网段访问时，源与目的 MAC 在各跳如何变化？

- 源主机发现目的地址不在同一子网，于是 ARP 解析默认网关，帧的目的 MAC 为网关接口。
- 网关收到帧后剥离以太网首部，查路由表确定出接口与下一跳，重新封装新的源 MAC 与目的 MAC。
- 每经过一个路由器，TTL 减一，首部校验和重算，源与目的 IP 保持不变。
- 目的主机所在网段的最后一跳路由器用 ARP 解析目的主机 MAC，完成最终交付。
- 抓包时在同一链路上看到的是本跳的 MAC，无法从帧首部推断原始发送方。
- 存在 NAT 时源或目的 IP 与端口会被改写，端到端地址不再保持。

## 2. TCP 连接管理

### 2.1 三次握手为什么需要三次？

- 两次握手只能确认一个方向的收发能力，被动方无法确认自己的 SYN 已被对方收到。
- 第三次 ACK 让服务端确认客户端具备接收能力，同时确认客户端已收到服务端的初始序列号。
- 网络中滞留的旧 SYN 若在两次握手模型下到达，服务端会直接建立连接并占用资源，直到超时。
- 三次是双方各自完成发送与接收确认所需的最小报文数。
- 握手期间协商 MSS、窗口缩放、SACK、时间戳等选项，这些选项只在 SYN 段中携带。
- 连接建立的判定并不同步：客户端收到 SYN-ACK 即返回，服务端要等第三次 ACK 才进入 `ESTABLISHED`。

### 2.2 初始序列号如何选择？

- ISN 不是固定值，也不能简单递增，需要随时间变化且难以预测。
- RFC 6528 规定 ISN 由计时器值与四元组、密钥的散列结果相加得到，计时器每 4 微秒递增。
- 引入密钥后，相同四元组在不同时间得到不同 ISN，降低序列号猜测与注入攻击的成功率。
- 序列号回绕由时间戳与 PAWS 机制处理，长时间连接不会把旧段误认为新数据。
- ISN 选择不当会让旧连接的重复段落入新连接的窗口，破坏数据完整性。
- Linux 使用 `secure_tcp_seq` 基于 SipHash 生成 ISN，密钥在启动时随机化。

### 2.3 TIME_WAIT 为什么存在？

- 主动关闭方发出最后一个 ACK 后进入 `TIME_WAIT`，持续 2 倍最大段生存期（2 MSL）。
- 若最后 ACK 丢失，被动方会重传 FIN，`TIME_WAIT` 状态使连接仍能回应 ACK 而不回送 RST。
- 让旧连接的重复段在网络中消亡，避免相同四元组的新连接收到历史数据。
- Linux 固定为 60 秒（`TCP_TIMEWAIT_LEN`），不随 `tcp_fin_timeout` 改变。
- 期间套接字仍占用四元组与内核内存，同一端口不能立即重新建立相同四元组的连接。
- 处于 `TIME_WAIT` 的连接不占用文件描述符，`close` 已经返回。

### 2.4（场景）TIME_WAIT 过多会带来什么现象，如何处理？

- 客户端侧表现为临时端口耗尽，`connect` 返回 `EADDRNOTAVAIL`，新连接无法建立。
- 服务端侧表现为重启时 `bind` 失败，报 `Address already in use`，即使没有进程在监听。
- 大量 `TIME_WAIT` 同时占用 conntrack 表项与内核内存，极端情况下触发丢包。
- 优先手段是使用连接池减少短连接，或改由对端主动关闭，把状态转移出去。
- `net.ipv4.tcp_tw_reuse=1` 允许带时间戳的出向连接复用 `TIME_WAIT` 套接字，仅对本机发起的连接有效。
- `SO_LINGER` 置 0 可在 `close` 时发送 RST 跳过 `TIME_WAIT`，但会丢弃未发送数据并可能让对端报错。
- 调小 `tcp_fin_timeout` 不影响 `TIME_WAIT`，该参数只作用于孤儿连接的 `FIN_WAIT_2`。

### 2.5 四次挥手为什么通常是四次？

- TCP 是全双工协议，两个方向独立关闭，收到 FIN 只表示对方不再发送数据。
- 被动方先回 ACK，连接进入半关闭，仍可继续发送剩余数据。
- 应用处理完剩余数据后再发 FIN，因此 FIN 与 ACK 通常分开发送。
- 若被动方没有待发数据，ACK 与 FIN 可以合并，实际只观察到三次报文。
- 半关闭由 `shutdown(SHUT_WR)` 触发，接收方向仍可继续读取。
- 关闭过程中任何一方继续发送数据都会延长状态停留时间。

### 2.6（陷阱）CLOSE_WAIT 大量堆积说明什么？

- `CLOSE_WAIT` 表示本端已收到对端 FIN 并回了 ACK，但应用尚未调用 `close`。
- 堆积的直接原因是代码路径遗漏关闭，常见于异常分支、线程阻塞与引用计数未归零。
- 与 `TIME_WAIT` 不同，它不受内核参数控制，调整 `tcp_fin_timeout` 无效。
- 现象是文件描述符持续增长，最终 `accept` 返回 `EMFILE`，新连接被拒绝。
- 用 `ss -tan state close-wait` 与 `lsof -p` 可定位到具体进程与套接字。
- 对端使用短连接而本端使用长连接池时也会出现该状态，需要检查协议是否匹配。

### 2.7（辨析）半连接队列与全连接队列有什么区别？

- 半连接队列保存已收到 SYN、已回 SYN-ACK、尚未收到 ACK 的连接，状态为 `SYN_RCVD`。
- 全连接队列保存已完成三次握手、等待 `accept` 取走的连接，状态为 `ESTABLISHED`。
- 半连接队列上限受 `listen` 的 `backlog` 与 `net.ipv4.tcp_max_syn_backlog` 共同限制。
- 全连接队列上限为 `backlog` 与 `net.core.somaxconn` 的较小值。
- `ss -lnt` 中 `Send-Q` 为全连接队列上限，`Recv-Q` 为已排队但尚未被 `accept` 的连接数。
- 队列满时新连接可能被丢弃或回 RST，客户端表现为握手超时与 SYN 重传。

### 2.8 SYN flood 的攻击原理与防御手段是什么？

- 攻击者伪造源地址发送大量 SYN，服务端为每个 SYN 分配请求块并回 SYN-ACK，队列被占满。
- 由于源地址伪造，第三次 ACK 不会到达，条目只能等待重传超时后释放。
- 直接症状是新连接建立缓慢或失败，`ss -s` 中 `SYN_RECV` 数量异常升高。
- SYN cookie 是无状态防御，把四元组与时间编码进 ISN，收到 ACK 后再重建连接。
- cookie 模式会丢失 SYN 中的窗口缩放、SACK 等选项，吞吐受到影响。
- `net.ipv4.tcp_syncookies=1` 仅在队列溢出时启用，`2` 为始终启用。
- 其他手段包括缩短 `tcp_synack_retries`、增大队列、在边界设备做源地址校验与限速。

### 2.9（陷阱）全连接队列满时服务端会怎么处理？

- 默认 `net.ipv4.tcp_abort_on_overflow=0` 时，服务端丢弃第三次 ACK，连接停留在 `SYN_RCVD`。
- 客户端此时认为连接已建立并可以发送数据，但数据不会交付给应用。
- 服务端按 `tcp_synack_retries` 重传 SYN-ACK，客户端重复回 ACK，直到客户端超时。
- 置 `tcp_abort_on_overflow=1` 时改为回 RST，客户端立刻收到 `ECONNRESET`。
- 两种行为都表现为端口可连通但首个请求超时，或连接被重置。
- 根因通常是 `accept` 循环被阻塞、工作线程不足或 `backlog` 设置过小。

### 2.10 RST 在哪些情况下会被发送？

- 目的端口没有监听，收到 SYN 后回 `RST+ACK`，客户端得到 `ECONNREFUSED`。
- 连接已关闭，仍收到数据或 ACK，回 RST 告知对端连接不存在。
- 套接字设置 `SO_LINGER` 且超时为 0，`close` 直接发送 RST。
- 连接处于半开状态，本端已无对应控制块，收到对端数据时回 RST。
- 收到无法接受的 ACK 或不在窗口内的段时，回送 RST 或 challenge ACK，具体行为由实现决定。
- 防火墙配置 `REJECT` 时也会代发 RST，表现为连接被立即拒绝。

### 2.11 收到 RST 后连接状态如何变化？

- `ESTABLISHED` 收到 RST 直接转入 `CLOSED`，未读数据被丢弃，`read` 返回 `ECONNRESET`。
- `SYN_SENT` 收到 RST 表示端口不可达，`connect` 失败并返回 `ECONNREFUSED`。
- `FIN_WAIT_1`、`FIN_WAIT_2` 与 `CLOSE_WAIT` 收到 RST 都会直接关闭，跳过正常挥手流程。
- 处于 `TIME_WAIT` 的套接字收到 RST 会被提前销毁，2 MSL 保护随之失效。
- RST 不保证送达，对端可能仍认为连接存在，直到重传失败或探活超时。
- 应用层看到的是读错误，或在写入时触发 `SIGPIPE`（未忽略时）。

### 2.12 同时打开与同时关闭的过程是什么？

- 双方几乎同时发送 SYN，各自从 `SYN_SENT` 进入 `SYN_RCVD`，并回送 SYN-ACK。
- 各自收到对方的 SYN-ACK 后回 ACK，连接建立，不区分客户端与服务端角色。
- 同时关闭时双方都发送 FIN 并进入 `FIN_WAIT_1`，收到对方 FIN 后转入 `CLOSING`。
- 各自收到自己 FIN 的 ACK 后进入 `TIME_WAIT`，全过程共四条报文。
- 这两条路径在实际网络中很少出现，但状态机必须支持。
- 服务端在 `SYN_RCVD` 收到 RST 时释放半连接并回到 `LISTEN`。

### 2.13 FIN_WAIT_2 长期停留有什么隐患？

- 主动关闭方发出 FIN 并收到 ACK 后进入 `FIN_WAIT_2`，等待对端 FIN。
- 若对端应用不关闭，连接会一直停留，占用内核控制块与文件描述符。
- Linux 对已无应用引用的孤儿连接用 `net.ipv4.tcp_fin_timeout` 限制停留时长，默认 60 秒；应用仍持有套接字时不会强制回收。
- 对端主机崩溃或断电时本端无法感知，只能依赖超时或 keepalive。
- 大量 `FIN_WAIT_2` 通常说明对端存在连接未关闭的缺陷，或本端 `shutdown` 后不再读取。
- 该状态不占用端口，但占用内存，容器中表现为不可回收的内核内存。

### 2.14 服务端主动关闭与客户端主动关闭有什么差异？

- 主动关闭方承担 `TIME_WAIT`，被动关闭方承担 `CLOSE_WAIT`。
- 服务端主动关闭时，`TIME_WAIT` 集中在服务端，可能与固定端口、重启流程冲突。
- 客户端主动关闭时，`TIME_WAIT` 分散在大量客户端，通常不构成问题。
- 由谁关闭取决于协议设计，短连接多由客户端关闭，长连接多由服务端按空闲超时关闭。
- 高并发短连接服务中，让客户端先关闭可减轻服务端的端口与内存压力。
- `TIME_WAIT` 只影响相同四元组，不影响其他客户端建立新连接。

### 2.15（辨析）TCP keepalive 与 HTTP keep-alive 有什么区别？

- TCP keepalive 是内核探活机制，默认空闲 7200 秒后发送探测包，连续失败 9 次后关闭连接。
- 探测包为不含数据的 ACK，对端正常时回 ACK，连接中断时可能收到 RST 或超时。
- HTTP keep-alive 是应用层复用同一条 TCP 连接处理多个请求，与内核探活无关。
- TCP keepalive 的参数为 `tcp_keepalive_time`、`tcp_keepalive_intvl` 与 `tcp_keepalive_probes`。
- 通过 `SO_KEEPALIVE` 按连接开启，时间粒度较粗，难以满足秒级检测。
- 应用层心跳更灵活，可携带业务状态，并能穿过中间设备的空闲超时。

### 2.16 四元组如何唯一标识一条连接？

- 四元组为源地址、源端口、目的地址与目的端口，协议类型由套接字类型隐含。
- 服务端监听套接字只绑定本地地址与端口，不构成完整连接。
- `accept` 返回的新套接字与客户端四元组一一对应，内核用哈希表查找。
- 同一客户端端口不能同时连接同一服务端的同一端口两次，内核会拒绝复用。
- NAT 设备改写地址与端口后需要维护映射表，表项耗尽会导致新连接失败。
- 连接关闭后四元组进入 `TIME_WAIT`，期间不能建立相同四元组的新连接。

### 2.17（陷阱）`connect` 返回成功是否代表服务可用？

- `connect` 成功只说明三次握手完成，即收到 SYN-ACK 并回了 ACK。
- 服务端可能尚未 `accept`，连接停在全连接队列中，业务逻辑没有执行。
- 服务端线程池可能已满，请求排队或被拒绝，握手仍然可以成功。
- 中间设备可能代理了握手，真实后端不可用，表现为连接成功而请求失败。
- 反向路径可能不通，握手包很小而响应包较大，PMTUD 黑洞时连接成功、传输失败。
- 健康检查应包含应用层请求，不能只依赖端口连通性。

### 2.18 `tcp_tw_reuse` 的语义与限制是什么？

- 该选项允许新的出向连接复用处于 `TIME_WAIT` 的本地端口。
- 仅在开启 TCP 时间戳时生效，且新连接的 TS 值必须大于旧连接的最后 TS 值。
- 只影响本机主动发起的连接，对 `bind` 到 `TIME_WAIT` 端口的监听套接字无效。
- 复用的前提是旧连接已无未确认数据，时间戳保证旧重复段被拒绝。
- `tcp_tw_recycle` 依赖每主机时间戳，在 NAT 环境下会错误丢弃连接，已在 Linux 4.12 移除。
- 更稳妥的做法是减少短连接，或让对端主动关闭。

### 2.19（场景）抓包看到 SYN 重传多次后连接超时，如何定位？

- 先在服务端抓包：若没有看到 SYN，问题在路径、安全组或防火墙。
- 若服务端看到 SYN 但未回 SYN-ACK，检查监听状态、半连接队列与 `tcp_syncookies`。
- 若回了 SYN-ACK 而客户端未收到，检查反向路径、会话表与中间设备。
- SYN 重传间隔按指数退避，`tcp_syn_retries` 为 6 时总时长约 127 秒。
- 客户端可用 `ss -tan state syn-sent` 观察重传中的连接数量。
- 大量 `SYN_SENT` 堆积且目标单一，通常指向目标端口不可达或被限速。

### 2.20（实现）如何用 `ss` 与 `/proc/net/tcp` 判断连接卡在哪一步？

- `ss -tan` 的 State 列给出当前状态，非监听套接字上的 `Recv-Q` 与 `Send-Q` 为待读与待发字节数。
- `ss -lnt` 在监听套接字上 `Send-Q` 为队列上限，`Recv-Q` 为已排队连接数。
- `ss -s` 汇总各状态数量，`ss -tan state syn-recv` 可单独过滤。
- `/proc/net/tcp` 用十六进制表示地址与端口，状态为两位十六进制码，`0A` 对应 `LISTEN`。
- `ss -tie` 额外给出 RTT、重传次数与拥塞窗口，可判断是否处于重传。
- 卡在 `SYN_SENT` 指向对端无响应，卡在 `SYN_RCVD` 指向握手未完成，卡在 `CLOSE_WAIT` 指向应用未关闭。

## 3. TCP 可靠传输与拥塞控制

### 3.1 滑动窗口如何同时实现可靠传输与流量控制？

- 发送方为每个字节编号，窗口内的数据可以连续发送，不必逐段等待确认。
- 接收方通过 ACK 的确认号与窗口字段通告可接收范围，窗口之外的字节不能发送。
- 发送窗口左边界随 ACK 前移，右边界由通告窗口决定，形成滑动效果。
- 未确认数据保留在发送缓冲区，超时或收到足够重复 ACK 时重传。
- 窗口字段为 16 位，最大 65535 字节，窗口缩放选项可把有效窗口扩大到 2 的 30 次方字节。
- 流量控制只解决接收方处理能力，拥塞控制另行限制网络中的在途数据量。

### 3.2 发送窗口由哪些量共同决定？

- 发送窗口取拥塞窗口 `cwnd` 与接收方通告窗口 `rwnd` 的较小值。
- `cwnd` 由拥塞控制算法维护，反映网络可承受的在途数据量。
- `rwnd` 由接收缓冲区的空闲空间决定，反映接收端处理能力。
- 实际可发送量为窗口减去已发送但未确认的字节数。
- 窗口缩放因子在握手时协商，双方各自通告，只影响自己的接收窗口。
- 接收窗口过小会限制吞吐，即使链路带宽充足也无法填满。

### 3.3 零窗口与窗口探测如何处理？

- 接收缓冲区满时，接收方通告窗口为 0，发送方停止发送新数据。
- 发送方启动持续计时器，超时后发送 1 字节的窗口探测。
- 探测包携带已发送数据的下一字节，接收方回 ACK 并附带当前窗口。
- 探测间隔按指数退避增长，避免在零窗口期间反复打扰对端。
- 若窗口更新报文丢失，探测可以恢复传输，避免双方永久等待。
- 窗口更新属于不携带数据的 ACK，本身不保证送达，不能只依赖它。

### 3.4 RTO 如何计算？

- RTO 取 SRTT 加上 G 与 4 倍 RTTVAR 中的较大值，其中 G 为计时器粒度。
- 首次测量前 RTO 取 1 秒；每次采样后 SRTT 按 1/8 的权重更新，RTTVAR 按 1/4 的权重更新。
- 重传过的段不参与采样，即 Karn 算法，避免把重传时间当作真实 RTT。
- 时间戳选项可为每个 ACK 提供精确 RTT，缓解 Karn 算法造成的采样缺失。
- RTO 有上下界，Linux 下限为 200 毫秒，上限为 120 秒。
- 连续重传时 RTO 指数翻倍，直到达到上限，避免在拥塞时加剧负担。

### 3.5 快速重传在什么条件下触发？

- 接收方收到失序段时立即重复发送最后一个按序字节的 ACK，即重复 ACK。
- 发送方收到 3 个重复 ACK 即认为对应段丢失，不等待 RTO 直接重传。
- 阈值 3 用于容忍一定程度的乱序，避免把乱序误判为丢包。
- 快速重传后进入快速恢复，`cwnd` 减半，不回到 1。
- Linux 还结合重复 ACK 的数量与 SACK 信息判断，减少不必要的重传。
- 窗口过小时重复 ACK 数量不足，快速重传无法触发，只能等待 RTO。

### 3.6 SACK 解决了什么问题？

- 标准 ACK 只能累计确认，丢失一个段会让其后所有已到达的数据被重复传输。
- SACK 选项在 ACK 中报告不连续的已接收区间，发送方只重传真正缺失的部分。
- 每个 SACK 块用 32 位左边界与右边界描述，一个选项通常携带 3 到 4 个块。
- D-SACK 用于报告重复收到的段，帮助发送方识别伪重传与 ACK 丢失。
- SACK 需要在握手时协商，双方都支持才启用。
- 选项空间受 TCP 首部 40 字节选项区限制，块数量不能任意增加。

### 3.7 慢启动与拥塞避免如何衔接？

- 连接初始 `cwnd` 为 10 个 MSS（RFC 6928），每收到一个 ACK 增加一个 MSS，呈指数增长。
- 增长到慢启动阈值 `ssthresh` 后进入拥塞避免，每个 RTT 增加约一个 MSS，呈线性增长。
- 超时重传时 `ssthresh` 设为当前在途数据量的一半，`cwnd` 回到 1 个 MSS。
- 快速重传时 `ssthresh` 同样减半，但 `cwnd` 从 `ssthresh` 继续，避免完全重来。
- 慢启动用于快速探测可用带宽，拥塞避免在接近上限时谨慎增长。
- 短连接往往在慢启动阶段结束，实际吞吐低于链路带宽。

### 3.8 快速恢复的状态如何变化？

- 收到 3 个重复 ACK 后，`ssthresh` 设为 `cwnd` 的一半，`cwnd` 设为 `ssthresh` 加 3 个 MSS。
- 每收到一个额外重复 ACK，`cwnd` 加 1，允许继续发送新数据。
- 收到覆盖恢复点的累计 ACK 后，`cwnd` 回落到 `ssthresh`，进入拥塞避免。
- 快速恢复避免了超时导致的窗口归零，适合单个丢包的场景。
- 多个包丢失时标准快速恢复可能反复减窗，NewReno 用部分确认改进。
- SACK 与 PRR 按实际在途量调整窗口，减少恢复期间的发送停顿。

### 3.9（辨析）CUBIC 与 BBR 的拥塞控制思路有何差异？

- CUBIC 以丢包为拥塞信号，窗口按三次函数增长，与 RTT 弱相关，适合高带宽长时延链路。
- BBR 以带宽时延积为模型，测量瓶颈带宽与最小 RTT，按速率与窗口两个维度控制。
- CUBIC 在缓冲区较大的链路上会填满队列，增加排队时延。
- BBR 试图维持恰好填满瓶颈链路的在途量，降低排队，但与基于丢包的流共存时可能占用更高带宽份额。
- 算法按套接字选择，`net.ipv4.tcp_congestion_control` 设置默认值，`TCP_CONGESTION` 可按连接覆盖。
- 更换算法只影响发送端，接收端不参与。

### 3.10（陷阱）Nagle 算法与延迟确认叠加会出现什么现象？

- Nagle 算法在有未确认小数据时，把小段缓存到收到 ACK 或凑满 MSS 再发送。
- 延迟确认让接收方等待一段时间再回 ACK，Linux 上限为 200 毫秒，通常为 40 毫秒。
- 两者叠加形成等待环：发送方等 ACK，接收方等更多数据或等待超时。
- 典型现象是请求响应式的小包交互出现约 40 毫秒的固定延迟，吞吐正常而时延抖动。
- 关闭 Nagle 用 `TCP_NODELAY`，减少延迟确认用 `TCP_QUICKACK`，后者一次生效。
- 批量发送场景保留 Nagle 可以减少小包数量，降低首部开销。

```cpp
int flag = 1;
if (setsockopt(fd, IPPROTO_TCP, TCP_NODELAY,
               &flag, sizeof flag) < 0) {
    perror("setsockopt");
}
```

### 3.11 什么时候应该设置 `TCP_NODELAY`？

- 交互式协议、RPC、游戏与终端类应用对时延敏感，应关闭 Nagle。
- 请求响应模式中，客户端发送小请求后等待响应，Nagle 会引入额外等待。
- 已经自行合并写操作、按 MSS 组包的应用，关闭 Nagle 不会增加小包数量。
- 大块连续传输、吞吐优先的场景可以保留 Nagle，减少报文数量。
- `TCP_CORK` 提供更明确的聚合控制，适合在确定的边界内拼接首部与载荷。
- 关闭 Nagle 后小包增多，需要评估每秒报文数与中断开销。

### 3.12 糊涂窗口综合征如何避免？

- 接收方在缓冲区只空出少量空间时不立即通告，而是等到可用空间达到一定比例再更新窗口。
- 常见策略是可用窗口小于 MSS 与缓冲区一半中的较小值时通告 0，避免发送方发出大量小段。
- 发送方使用 Nagle 与延迟发送，避免逐字节发送。
- 窗口更新报文本身也可能被延迟，需要与零窗口探测配合。
- 糊涂窗口综合征与 Nagle 解决的是不同侧的问题，前者在接收方，后者在发送方。
- 现代实现默认启用窗口避免，应用通常无需干预。

### 3.13 如何区分乱序与丢包？

- 乱序时后续段仍会到达，接收方用 SACK 报告已收区间，重复 ACK 的数量有限。
- 丢包时缺口之后的数据持续到达，重复 ACK 持续增加，SACK 块稳定缺失同一区间。
- 仅凭重复 ACK 无法完全区分，阈值 3 是一种折中，多路径链路上乱序更常见。
- 时间戳与序列号结合可判断段的新旧，D-SACK 可确认重复段。
- 把乱序误判为丢包会导致不必要的重传与窗口缩减，吞吐下降。
- 在抓包中观察同一段是否出现两次、ACK 是否重复，可以还原判定过程。

### 3.14 什么情况下会出现伪重传？

- RTO 过小、ACK 路径延迟突增或接收方延迟确认，都会让计时器在数据已到达时超时。
- 链路层重传、链路聚合切换或路由抖动会造成突发时延，触发超时重传。
- 发送方重传后收到原数据的 ACK，无法判断确认来自原包还是重传包。
- F-RTO 通过观察重传后的 ACK 序列判断是否为伪超时，避免不必要的减窗。
- DSACK 可让发送方确认重传是多余的，并据此恢复拥塞窗口。
- 伪重传增加链路负载，在高抖动链路上影响明显。

### 3.15（场景）抓包发现吞吐只有带宽的一成，如何排查？

- 先计算带宽时延积，确认窗口是否足够：1 Gbps 链路在 100 毫秒 RTT 下需要约 12.5 MB 在途数据。
- 检查窗口缩放是否生效，抓包看 SYN 中是否携带缩放因子，`ss -ti` 看实际窗口。
- 检查是否长期处于慢启动，短连接或频繁重连会让 `cwnd` 反复归零。
- 观察重传率与重复 ACK，丢包会触发减窗，吞吐按比例下降。
- 检查 `SO_RCVBUF` 是否过小，接收窗口受缓冲区限制，自动调优也有上限。
- 检查中间设备是否限速、整形，或代理拆分了连接。

### 3.16 接收缓冲区与接收窗口是什么关系？

- 接收窗口上限由套接字接收缓冲区大小决定，内核为其保留部分空间用于重组。
- `SO_RCVBUF` 设置缓冲区大小，实际值会被内核翻倍并受 `net.core.rmem_max` 限制。
- 自动调优依据读取速度扩大缓冲区，`net.ipv4.tcp_moderate_rcvbuf` 控制开关。
- 应用读取过慢会让窗口缩小，最终通告零窗口。
- 增大缓冲区可提升高时延链路的吞吐，同时增加内存占用。
- 窗口缩放因子在握手时确定，连接建立后无法更改。

### 3.17 什么是缓冲区膨胀？

- 路由器或中间设备使用过大的队列吸收突发，导致排队时延显著增加。
- 表现为吞吐正常但 RTT 从几毫秒升到数百毫秒，交互类业务体验变差。
- 根因是队列长度超过带宽时延积所需，丢包信号被延迟。
- 缓解手段包括主动队列管理（CoDel、FQ-CoDel）与更小的缓冲区。
- BBR 通过测量最小 RTT 与带宽避免填满队列，对缓冲区膨胀不敏感。
- 端到端无法控制中间队列，只能在协议与算法层面适应。

### 3.18 ECN 的作用是什么？

- ECN 使用 IP 首部的两位字段，路由器在拥塞时标记报文，不直接丢弃。
- 接收方通过 TCP 首部的 ECE 标志回传拥塞信号，发送方以 CWR 响应并减小窗口。
- 优点是避免丢包与重传，适合对时延敏感的业务。
- 需要端到端与中间设备都支持，任一路径不支持则协商失败。
- 协商在 SYN 中完成，双方都置 ECE 与 CWR 才启用。
- 观测手段为 `netstat -s` 中的 ECN 统计与抓包中的 ECE、CWR 标志。

### 3.19（实现）如何用 `ss -ti` 读取拥塞控制状态？

- `ss -ti` 在连接详情中给出 `cwnd`、`ssthresh`、`rtt`、`rttvar`、`retrans` 与 `bytes_acked`。
- `cwnd` 以 MSS 为单位，乘以 MSS 可估算在途数据上限。
- `retrans` 给出重传段数，持续增长说明链路丢包或超时。
- `rtt` 为平滑后的往返时间，`rttvar` 反映抖动程度。
- `bytes_retrans` 与发送字节数可估算重传率。
- 结合 `nstat -az TcpRetransSegs` 观察全局重传计数。

### 3.20 时间戳选项解决了哪些问题？

- 时间戳选项在每个段中携带发送时刻与回显时刻，用于精确测量 RTT。
- 配合 PAWS 防止序列号回绕后的旧段被接受，提升长连接的正确性。
- 使 RTT 采样不再完全依赖 Karn 算法，重传段也能获得有效采样。
- 时间戳增加 12 字节开销（10 字节选项加 2 字节填充），降低有效载荷比例。
- `net.ipv4.tcp_timestamps` 可关闭，但会同时失去 `tcp_tw_reuse` 的前提。
- 时间戳不加密，可被用于推断对端时钟频率，隐私敏感场景需要评估。

## 4. UDP 与可靠 UDP

### 4.1 UDP 提供什么，不提供什么？

- UDP 只提供端口复用与可选的校验和，不保证送达、顺序与不重复。
- 每个数据报独立处理，不建立连接，不维护序列号与确认。
- 首部仅 8 字节，开销小，适合短报文与高频查询。
- 没有拥塞控制与流量控制，发送速率完全由应用决定。
- 保留报文边界，一次 `sendto` 对应一次 `recvfrom`，不会被合并或拆分。
- 重传、超时、乱序与分片处理都需要应用自行实现。

### 4.2 UDP 首部包含哪些字段，长度上限是多少？

- 首部 8 字节，依次为源端口、目的端口、长度与校验和，各占 16 位。
- 长度字段包含首部与数据，最小值为 8，最大值为 65535。
- IPv4 下最大载荷为 65535 减去 20 字节 IP 首部与 8 字节 UDP 首部，即 65507 字节。
- IPv6 下没有 IP 首部校验和，最大载荷为 65527 字节，巨帧场景另行协商。
- 校验和覆盖伪首部与整个数据报，IPv4 中字段为 0 表示未计算。
- 端口 0 保留，源端口为 0 表示不需要回复。

### 4.3（辨析）UDP 的「无连接」具体指什么？

- 内核不为 UDP 维护连接状态机，不发送握手报文，也不区分建立与关闭。
- `sendto` 每次携带目的地址，`recvfrom` 返回源地址，一个套接字可以向多个对端发送。
- 调用 `connect` 只记录默认对端并过滤其他来源，不产生任何网络报文。
- 没有重传与超时，报文丢失后内核不会通知应用。
- 端口绑定仍然存在，未绑定的套接字在首次发送时由内核分配临时端口。
- 服务端不需要 `listen` 与 `accept`，单个套接字即可处理全部客户端。

### 4.4 UDP 报文何时被分片？

- 报文长度超过出接口 MTU 时由 IP 层分片，UDP 首部只出现在第一个分片中。
- 分片发生在发送主机或中间路由器，重组只在目的主机进行。
- 一个分片丢失会导致整个数据报被丢弃，接收方无法感知丢失位置。
- 把 `IP_MTU_DISCOVER` 设为 `IP_PMTUDISC_DO` 可让内核在超长时返回 `EMSGSIZE`，避免分片。
- 常见做法是把应用层报文控制在 1200 字节以内，兼容隧道与 IPv6 的最小 MTU。
- 分片会放大丢包影响，1% 的分片丢失率会让大报文的丢失率显著上升。

### 4.5 为什么 UDP 应用要自己控制报文大小？

- 单个数据报越大，分片越多，任一分片丢失都会导致整体丢弃。
- 大报文占用更多缓冲区，接收端队列更容易溢出。
- 路径 MTU 可能小于本地 MTU，经过 VPN 与隧道时尤其明显。
- 应用层分片可以按序号重传单个片段，避免整体重传。
- 1200 字节是 IPv6 保证可通行的保守上限，常作为设计值。
- 控制在 MTU 以内还能减少中间设备的处理开销与分片攻击面。

### 4.6（陷阱）UDP 丢包为什么在应用层表现为超时？

- UDP 没有确认与重传，内核不会因丢包产生错误，`sendto` 通常仍返回成功。
- 接收端未收到报文时没有任何事件，只能由应用层计时器发现。
- ICMP 端口不可达可能异步返回，但多数实现只在已 `connect` 的套接字上报告。
- 发送缓冲区满且为非阻塞时返回 `EAGAIN`，设备队列满时可能返回 `ENOBUFS`。
- 接收缓冲区满时内核直接丢弃，`/proc/net/snmp` 中的 `InErrors` 会计数。
- 超时阈值与重试次数需要按业务时延要求设计，不能照搬 TCP 的经验值。

### 4.7 可靠 UDP 需要哪些机制？

- 序列号与确认，用于检测丢失、重复与乱序。
- 重传计时器与 RTT 估计，按网络状况调整超时。
- 接收端的乱序缓存与按序交付。
- 滑动窗口与流量控制，避免接收端被压垮。
- 拥塞控制，按丢包或时延调整发送速率。
- 连接标识与握手，用于协商参数并确认对端可达。
- 加密与认证，防止伪造与篡改。

### 4.8（辨析）KCP 与 TCP 的设计取舍是什么？

- KCP 是应用层的自动重传请求协议，运行在 UDP 之上，连接管理与加密由应用负责。
- 以牺牲带宽为代价换取更低延迟，允许配置更激进的重传策略。
- 不依赖内核协议栈，升级与调参不需要重启系统或修改内核。
- 默认不启用拥塞控制，可用 `nocwnd` 关闭或启用简化实现。
- 没有 TCP 的跨流队头阻塞，但单连接内仍按序交付。
- 流量大时重传比例高，可能挤占同链路的其他流量。

### 4.9 KCP 的重传与 RTO 策略有哪些特点？

- RTO 由 SRTT 与 RTTVAR 计算，下限可配置，`nodelay` 模式下可降至 30 毫秒。
- 快速重传依据 `fastresend` 阈值，收到足够多的后续 ACK 即重传缺失段。
- 关闭 `nodelay` 时行为接近 TCP，延迟更高但带宽利用率更好。
- `interval` 控制内部刷新周期，影响延迟与 CPU 占用。
- 每个段可配置重传次数上限，超过后放弃并通知上层。
- 参数需要按链路 RTT 与丢包率调整，固定配置在跨区域链路上效果差异明显。

### 4.10 QUIC 在 UDP 之上解决了哪些问题？

- 在用户态实现可靠传输、拥塞控制与加密，摆脱内核协议栈的升级周期。
- 多路复用独立流，单个流丢包不阻塞其他流，消除 TCP 的跨流队头阻塞。
- 握手与 TLS 1.3 合并，首次连接为 1 个 RTT，会话恢复可以做到 0-RTT。
- 使用连接 ID 而非四元组标识连接，支持网络切换后的连接迁移。
- 默认加密传输层元数据，中间设备无法读取或篡改首部。
- 支持可插拔拥塞控制，便于灰度新算法。

### 4.11 QUIC 的连接迁移与 0-RTT 各有什么代价？

- 连接迁移依赖连接 ID，客户端更换地址或端口后仍可继续，服务端需要验证新路径。
- 路径验证通过 `PATH_CHALLENGE` 与 `PATH_RESPONSE` 完成，防止地址伪造与放大攻击。
- 迁移后拥塞控制与 RTT 估计需要重置，避免沿用旧路径的参数。
- 0-RTT 数据在握手完成前发送，存在重放风险，只适合幂等请求。
- 服务端可以拒绝 0-RTT，客户端需要准备重发。
- 0-RTT 不提供前向保密，密钥派生自上一次会话的恢复密钥。

### 4.12（辨析）广播与组播有什么区别？

- 广播发往同一广播域内的所有主机，目的地址为 `255.255.255.255` 或子网定向广播地址。
- 组播发往加入特定组的主机，IPv4 使用 `224.0.0.0/4`，需要 IGMP 加入。
- 广播默认不跨路由器，组播可以跨路由器，依赖组播路由协议。
- 广播消耗全部主机的处理能力，组播只复制到有成员的链路。
- 广播用于 ARP、DHCP 等本地发现，组播用于媒体分发与服务发现。
- 交换机对广播泛洪，对组播可启用 IGMP snooping 按需转发。

### 4.13 组播地址与 IGMP 的作用是什么？

- IPv4 组播地址范围为 `224.0.0.0/4`，`224.0.0.1` 为所有主机，`224.0.0.2` 为所有路由器。
- 组播 MAC 地址由组播 IP 的低 23 位映射到 `01:00:5e` 前缀，存在地址重叠。
- 主机通过 IGMP 报文向路由器声明加入或离开某个组。
- 交换机通过 IGMP snooping 学习成员端口，避免向所有端口泛洪。
- 组播路由使用 PIM 等协议构建分发树，跨域时需要额外机制。
- TTL 或作用域字段限制组播传播范围，避免泄露到管理域之外。

### 4.14（场景）UDP 打洞为什么会失败？

- 双方位于对称 NAT 之后时，每个目的地址分配不同的映射端口，预先获得的端口无法用于对方。
- 端口受限型 NAT 只允许已通信过的对端地址进入。
- 映射表项有超时，打洞前交换的地址可能在连接建立前失效。
- 多层 NAT 或运营商级 NAT 使映射与控制都不可预测。
- 防火墙可能只放行特定方向的 UDP，或对未知会话直接丢弃。
- 失败后需要中继服务器转发，STUN 与 TURN 分别负责地址发现与兜底。

### 4.15（陷阱）UDP 套接字调用 `connect` 有什么作用？

- 不发送任何报文，只在本地记录默认对端地址。
- 之后可以用 `send` 与 `write`，不必每次指定地址。
- 内核只把来自该对端的报文交给套接字，其他来源被丢弃。
- 可以接收 ICMP 差错，未连接的套接字通常收不到端口不可达。
- 可以多次调用 `connect` 切换对端，也可用 `AF_UNSPEC` 解除。
- 它不建立连接状态，对端不会感知，也没有握手与超时。

```cpp
struct sockaddr_in peer = {};
peer.sin_family = AF_INET;
peer.sin_port = htons(9000);
inet_pton(AF_INET, "192.0.2.10", &peer.sin_addr);
connect(fd, (struct sockaddr *)&peer, sizeof peer);
```

### 4.16 UDP 接收缓冲区与丢包如何观测？

- 接收缓冲区满时新报文被丢弃，`recvfrom` 不会返回错误。
- `/proc/net/snmp` 中的 `InDatagrams`、`NoPorts` 与 `InErrors` 分别统计接收、无端口与错误。
- `InErrors` 包含校验和错误与缓冲区溢出，需要结合 `/proc/net/udp` 的队列长度判断。
- `SO_RCVBUF` 可增大缓冲区，但受 `net.core.rmem_max` 限制。
- `SO_RXQ_OVFL` 允许在辅助数据中返回累计丢包数，便于精确定位。
- 多线程读取同一套接字会竞争，`SO_REUSEPORT` 可把流量分散到多个套接字。

### 4.17 为什么可靠 UDP 也必须实现拥塞控制？

- 没有拥塞控制的持续重传会在瓶颈处形成排队，严重时导致拥塞崩溃。
- 与 TCP 共享链路时会挤占带宽，引发不公平竞争。
- RFC 8085 要求 UDP 应用遵循拥塞控制原则，否则不应大规模部署。
- 实现方式可以是类 TCP 的加性增乘性减、基于带宽估计的模型，或直接采用 QUIC 的算法。
- 丢包率与 RTT 是主要信号，需要区分随机丢包与拥塞丢包。
- 拥塞控制同时约束重传策略，避免在拥塞时加倍重传。

### 4.18 DNS 为什么以 UDP 为主，何时回退到 TCP？

- 查询报文小，UDP 一次往返即可完成，无需握手，服务端也不保存连接状态。
- 传统 DNS 响应上限为 512 字节，超出时置 TC 位，客户端改用 TCP 重试。
- EDNS0 允许协商更大的 UDP 载荷，常见取值为 1232 字节，减少回退。
- 区域传送、DNSSEC 大响应与长记录必须使用 TCP。
- UDP 易受伪造源地址的放大攻击，服务端需要限制响应比例。
- 现代方案包括 DNS over TLS 与 DNS over HTTPS，均基于 TCP。

### 4.19（实现）如何设计 UDP 心跳与超时判定？

- 心跳间隔应小于中间设备的会话超时，常见为 15 到 30 秒。
- 每个心跳携带序号与时间戳，接收方回显，用于计算 RTT 与丢包率。
- 连续丢失 N 个心跳判定断开，N 的取值需要容忍短暂抖动。
- 超时判定使用单调时钟，避免系统时间跳变影响。
- 心跳报文应尽量小，避免分片，并设置独立的发送队列优先级。
- 断开后需要重连与重新协商，避免直接复用旧的会话标识。

### 4.20 用 UDP 传输大文件需要哪些分片与重组设计？

- 应用层按固定大小切块，块大小不超过路径 MTU 减去首部，常用 1200 字节。
- 每块携带文件标识、块序号与总块数，接收端按序号写入位图。
- 接收端维护重排窗口，窗口外的块可以暂存或丢弃。
- 发送端按位图重传缺失块，配合拥塞窗口控制并发块数。
- 完成判定基于位图全满，收到最后一块不代表传输完成。
- 需要校验整体完整性，通常用分块哈希加整体哈希。

## 5. Socket 编程基础

### 5.1 `socket` 调用做了什么，参数如何选择？

- `socket(domain, type, protocol)` 返回文件描述符，内核分配套接字结构并关联协议操作表。
- `AF_INET` 与 `AF_INET6` 分别对应 IPv4 与 IPv6，`AF_UNIX` 用于本机通信。
- `SOCK_STREAM` 对应 TCP，`SOCK_DGRAM` 对应 UDP，`SOCK_RAW` 需要特权。
- `protocol` 通常填 0，由类型推导；原始套接字需要显式指定，如 `IPPROTO_ICMP`。
- Linux 允许在类型参数中按位或上 `SOCK_NONBLOCK` 与 `SOCK_CLOEXEC`，避免额外的 `fcntl` 调用。
- 失败返回 -1 并设置 `errno`，常见值为 `EMFILE`、`ENFILE`、`EAFNOSUPPORT`。

### 5.2 `bind` 的地址与端口语义是什么？

- `bind` 把本地地址与端口关联到套接字，服务端必须绑定，客户端通常由内核分配临时端口。
- `INADDR_ANY` 表示接受任意本地地址，绑定后仍可接收发往具体地址的连接。
- 端口填 0 表示由内核选择，之后可用 `getsockname` 获取实际值。
- 绑定已占用的地址与端口返回 `EADDRINUSE`，除非设置 `SO_REUSEADDR` 或 `SO_REUSEPORT`。
- 非特权进程只能绑定 1024 以下的端口，需要 `CAP_NET_BIND_SERVICE` 能力。
- 绑定本机不存在的地址返回 `EADDRNOTAVAIL`。

### 5.3 `listen` 的 backlog 含义是什么？

- `listen` 把套接字转为被动模式，内核开始接受 SYN 并维护半连接与全连接两个队列。
- `backlog` 指定已完成握手、等待 `accept` 取走的连接队列上限。
- Linux 把 `backlog` 截断为 `min(backlog, net.core.somaxconn)`。
- 半连接队列的上限另由 `net.ipv4.tcp_max_syn_backlog` 控制。
- 队列满时新连接可能被丢弃或回 RST，取决于 `tcp_abort_on_overflow`。
- `backlog` 不是并发连接总数，已 `accept` 的连接不再占用队列。

### 5.4 `accept` 返回什么，有哪些注意事项？

- 返回新的文件描述符，代表一条已建立的连接，与原监听套接字相互独立。
- 新套接字继承监听套接字的套接字选项，但不继承 `O_NONBLOCK` 状态。
- 对端地址通过第二个参数返回，长度参数是值-结果参数，调用前需填入缓冲区大小。
- `accept4` 可直接设置 `SOCK_NONBLOCK` 与 `SOCK_CLOEXEC`，避免先接受再设置的竞态。
- 监听套接字耗尽文件描述符时返回 `EMFILE`，已完成的连接仍留在队列中。
- 阻塞模式下 `accept` 会睡眠，非阻塞模式下无连接时返回 `EAGAIN`。

### 5.5 `connect` 在 TCP 中执行了哪些步骤？

- 分配本地端口，构造 SYN，进入 `SYN_SENT`，启动重传计时器。
- 收到 SYN-ACK 后回 ACK，连接进入 `ESTABLISHED`，`connect` 返回 0。
- 收到 RST 返回 `ECONNREFUSED`，重传耗尽返回 `ETIMEDOUT`。
- 非阻塞模式下立即返回 `EINPROGRESS`，需要等待可写事件后检查 `SO_ERROR`。
- `connect` 失败后套接字状态未定义，通常应关闭并重建。
- 对 UDP 调用 `connect` 只记录对端，不产生报文。

### 5.6 非阻塞 Socket 中 EAGAIN 与 EINTR 如何分别处理？

- `EAGAIN` 与 `EWOULDBLOCK` 表示当前操作未就绪，不是错误，应等待可读或可写事件后重试。
- `EINTR` 表示调用被信号打断，通常直接重试；设置 `SA_RESTART` 可让部分调用自动重启。
- 水平触发下读到 `EAGAIN` 说明缓冲区已排空，应停止本轮读写；边缘触发下必须循环读到 `EAGAIN`。
- 部分写需要维护用户态发送缓冲区与偏移，不能假设一次 `write` 写完。
- `accept` 在非阻塞模式下无新连接时返回 `EAGAIN`，应等待监听套接字的可读事件。
- 连接被对端重置时返回 `ECONNRESET`，与 `EAGAIN` 不同，不能重试。

### 5.7（辨析）`select`、`poll` 与 `epoll` 的接口差异是什么？

- `select` 使用位图，描述符上限受 `FD_SETSIZE` 限制，每次调用都要复制集合并线性扫描。
- `poll` 使用数组，没有固定上限，仍需每次遍历全部描述符。
- `epoll` 由内核维护兴趣列表，`epoll_wait` 只返回就绪项，开销与就绪数量相关。
- `epoll` 支持水平触发与边缘触发，边缘触发必须配合非阻塞套接字并读到 `EAGAIN`。
- `epoll` 用 `EPOLLRDHUP` 直接报告对端半关闭，`select` 需要读到 0 才能判断。
- 连接数少且都很活跃时三者差异不大，大量空闲连接时 `epoll` 优势明显。

### 5.8 `SO_REUSEADDR` 解决了什么问题？

- 允许绑定处于 `TIME_WAIT` 的本地地址与端口，服务端重启时不必等待。
- 在监听场景下，允许通配地址与具体地址绑定同一端口，前提是相关套接字都设置了该选项。
- Linux 下多个监听套接字绑定完全相同的地址与端口仍需要 `SO_REUSEPORT`。
- 必须在 `bind` 之前设置，`accept` 返回的套接字会继承该选项。
- 它不解决端口被其他进程占用的问题，`EADDRINUSE` 仍会出现。
- UDP 下可用于多播接收，以及同一端口的多个绑定。

### 5.9 `SO_REUSEPORT` 的语义与风险是什么？

- 允许多个套接字绑定完全相同的地址与端口，由内核按四元组哈希分发。
- 所有参与绑定的套接字都必须设置该选项，且属于同一用户。
- 常用于多进程或多线程服务器，每个进程独立 `accept`，减少锁竞争。
- 内核在连接建立时选择套接字，同一连接始终落到同一进程。
- 进程重启会触发哈希重分布，已有连接不受影响，新连接可能分布不均。
- 与 `SO_REUSEADDR` 不同，它允许真正的同时监听。

### 5.10 `SO_LINGER` 的语义是什么？

- 默认关闭，`close` 立即返回，内核在后台发送剩余数据并正常挥手。
- 开启且超时为 0 时，`close` 发送 RST，丢弃发送缓冲区中的数据，跳过 `TIME_WAIT`。
- 开启且超时大于 0 时，`close` 阻塞直到数据发送完毕或超时。
- 超时后仍未发送完的数据被丢弃，连接随之关闭。
- 发送 RST 会让对端读到 `ECONNRESET`，可能丢失已提交的业务数据。
- 该选项常用于需要快速释放端口，或明确拒绝连接的场景。

### 5.11（陷阱）文件描述符继承会带来什么问题？

- `fork` 后子进程继承全部描述符，引用计数加一，父进程关闭不影响子进程。
- `exec` 保留未设置 `FD_CLOEXEC` 的描述符，可能把监听套接字泄漏给外部程序。
- 泄漏的监听套接字使端口无法释放，重启时出现 `EADDRINUSE`。
- 泄漏的管道读端会让对端永远等不到 EOF。
- 解决方式是在创建时使用 `SOCK_CLOEXEC`、`O_CLOEXEC`，或改用 `accept4`。
- 多线程程序中先创建再用 `fcntl` 设置存在竞态，应在创建时原子设置。

### 5.12 `close` 与 `shutdown` 有什么区别？

- `close` 减少文件描述引用计数，归零时才释放套接字并发送 FIN。
- `shutdown` 直接作用于连接，可以只关闭读方向、写方向或两者。
- `shutdown(SHUT_WR)` 发送 FIN，进入半关闭，仍可继续读取对端数据。
- `shutdown(SHUT_RD)` 丢弃接收方向的数据，对端不会收到通知。
- 多个描述符指向同一套接字时，`close` 一个不影响其他，`shutdown` 影响全部。
- 需要向对端明确表示请求结束而不立即释放资源时，使用 `shutdown`。

### 5.13 `EINTR` 与 `EAGAIN` 应如何处理？

- `EINTR` 表示调用被信号中断，通常应重新发起相同调用。
- 使用 `SA_RESTART` 可以让部分调用自动重启，但 `poll`、`epoll_wait` 与 `select` 不在其列。
- `EAGAIN` 表示非阻塞调用暂时无法完成，应等待事件后重试。
- `accept`、`read`、`write` 都需要区分这两种错误，不能一律视为失败。
- `write` 返回部分写入时需循环发送剩余数据。
- 把 `EAGAIN` 当成连接错误并关闭套接字是常见缺陷。

### 5.14（实现）非阻塞 `connect` 如何判断完成？

- 调用后返回 -1 且 `errno` 为 `EINPROGRESS`，表示握手正在进行。
- 用 `poll` 或 `epoll` 等待 `POLLOUT`，再通过 `getsockopt(SOL_SOCKET, SO_ERROR)` 读取结果。
- `SO_ERROR` 为 0 表示连接建立，其他值对应具体错误，如 `ECONNREFUSED`。
- 仅判断可写不够，连接失败时同样可能触发可写事件。
- 超时需要应用层计时器控制，内核的 SYN 重传可能持续很久。
- 连接失败后应关闭套接字，不能对同一描述符重试 `connect`。

```cpp
int r = connect(fd, addr, addrlen);
if (r < 0 && errno == EINPROGRESS) {
    struct pollfd p = { fd, POLLOUT, 0 };
    poll(&p, 1, timeout_ms);
    int err = 0;
    socklen_t len = sizeof err;
    getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len);
}
```

### 5.15 `getaddrinfo` 相比 `inet_addr` 有什么优势？

- `getaddrinfo` 同时支持 IPv4 与 IPv6，返回可直接用于 `socket` 与 `connect` 的结构。
- 它统一处理主机名解析、服务名到端口的转换以及地址排序。
- `inet_addr` 已废弃，无法表示 `255.255.255.255`，也不支持 IPv6。
- `AI_PASSIVE` 用于服务端生成通配地址，`AI_NUMERICSERV` 禁止服务名解析。
- 返回的链表需要 `freeaddrinfo` 释放，逐个尝试直到连接成功。
- `getaddrinfo` 可能阻塞，事件驱动程序中应放到独立线程或使用异步解析。

### 5.16 `inet_pton` 与 `inet_ntop` 的使用要点是什么？

- `inet_pton` 把点分十进制或 IPv6 文本转换为二进制，返回 1 表示成功，0 表示格式错误，-1 表示地址族无效。
- `inet_ntop` 把二进制地址转换为文本，需要提供足够大的缓冲区。
- IPv4 使用 `INET_ADDRSTRLEN`，IPv6 使用 `INET6_ADDRSTRLEN` 作为缓冲区长度。
- 两者都不做 DNS 解析，只处理数字地址。
- 转换结果与主机字节序无关，地址结构中的字段保持网络字节序。
- 端口转换使用 `htons` 与 `ntohs`，不要与地址转换混淆。

### 5.17 文件描述符耗尽时会出现什么现象？

- `accept` 返回 `EMFILE`，新连接留在队列中，队列满后开始丢弃。
- `socket` 返回 `EMFILE`，无法创建新连接。
- `open` 与 `pipe` 同样失败，日志与监控可能一并失效。
- 单进程上限由 `RLIMIT_NOFILE` 控制，系统级上限由 `fs.file-max` 控制，`fs.nr_open` 限制 `RLIMIT_NOFILE` 可设置的最大值。
- 应急手段是预留一个空闲描述符，耗尽时关闭它，接受连接后立即关闭该连接。
- 根治方式是修复泄漏，并用监控观察描述符的增长趋势。

### 5.18 如何判断对端已关闭连接？

- `read` 返回 0 表示收到 FIN，连接进入半关闭，仍可发送数据。
- `read` 返回 -1 且 `errno` 为 `ECONNRESET` 表示收到 RST。
- 向已关闭的连接写入会触发 `SIGPIPE`，忽略信号后返回 `EPIPE`。
- `poll` 的 `POLLRDHUP` 与 `epoll` 的 `EPOLLRDHUP` 可在事件中直接感知半关闭。
- `recv` 的 `MSG_PEEK` 可以预读而不消费数据，用于判断是否有数据可读。
- 不能仅凭 `write` 成功判断连接存活，写入成功只表示数据进入发送缓冲区。

### 5.19（实现）一个 TCP 回显服务端的调用序列是什么？

- 创建监听套接字，设置 `SO_REUSEADDR`，绑定地址与端口。
- 调用 `listen` 进入监听，把监听套接字注册到 `epoll` 的可读事件。
- 事件触发后循环调用 `accept4` 直到 `EAGAIN`，把新套接字设为非阻塞并注册。
- 读事件到达后循环 `read` 直到 `EAGAIN`，把数据写入待发缓冲区。
- 写事件按需注册，发送缓冲区满时挂起剩余数据，可写时继续发送。
- 读到 0 字节或遇到错误时注销并关闭套接字，释放连接状态。

### 5.20（实现）如何用 `TCP_INFO` 获取连接的内核统计？

- `getsockopt(fd, IPPROTO_TCP, TCP_INFO, &info, &len)` 返回 `struct tcp_info`。
- 常用字段包括 `tcpi_state`、`tcpi_rtt`、`tcpi_snd_cwnd`、`tcpi_retransmits` 与 `tcpi_unacked`。
- 结构体随内核版本扩展，调用时需要传入实际长度并检查返回的长度。
- 可在应用内按连接埋点，上报 RTT 与重传次数，便于定位尾延迟。
- 字段语义由内核定义，跨平台不可移植。
- 与 `ss -ti` 的数据来源一致，便于互相对照。

```cpp
struct tcp_info info = {};
socklen_t len = sizeof info;
if (getsockopt(fd, IPPROTO_TCP, TCP_INFO, &info, &len) == 0) {
    printf("state=%u rtt=%u cwnd=%u\n",
           info.tcpi_state, info.tcpi_rtt, info.tcpi_snd_cwnd);
}
```

## 6. I/O 多路复用

### 6.1（辨析）网络服务器选择 select、poll 还是 epoll，依据是什么？

- 连接数在几十以内时，`select` 与 `poll` 的封装与调试成本最低，跨平台支持也最完整。
- `select` 的关注集合容量由 `FD_SETSIZE` 固定，Linux 上为 1024，描述符编号超过该值无法加入。
- 描述符达到数千以上时，每次等待都要提交整个关注集合，逐项检查的开销随连接总数增长。
- `epoll` 把关注集合保存在内核对象中，等待开销与就绪连接数相关，适合长连接为主的服务器。
- 只在 Linux 部署时可以直接使用 `epoll`；需要覆盖 Windows 与 BSD 时通常选择跨平台库，或按平台条件编译多个后端。
- 事件语义也影响选型：边缘触发与一次性关注在其他接口上没有等价物，`poll` 虽支持 `POLLRDHUP`，但没有边缘触发语义。
- 连接生命周期很短、每秒新建量很大的服务，`accept` 与注册开销占比上升，机制差异被摊薄。

### 6.2 io_uring 与传统就绪通知模型在服务器中的差别？

- 就绪通知模型在事件到达后由应用发起读写，是否阻塞、读到多少字节都由应用处理。
- `io_uring` 是完成模型：应用提交 `recv`、`send`、`accept` 请求，内核完成后在完成队列报告结果与字节数。
- 提交与收割可以批量化，一次进入内核处理多个请求，系统调用次数不再与连接数成正比。
- `accept` 与 `recv` 支持一次提交、多次完成（multishot），持续产生完成事件，适合连接数大而活跃比例低的服务器。
- 代价是请求上下文与缓冲区的生命周期必须覆盖到完成事件，状态机比就绪回调复杂。
- 不同内核版本支持的操作码与标志存在差异，部署环境需要统一版本。

### 6.3 可读事件、对端关闭与套接字错误分别如何识别？

- `EPOLLIN` 在接收缓冲区有数据、对端发送 FIN、监听套接字上有待取连接三种情形下都会置位。
- 数据可读时 `recv` 返回大于 0 的字节数，可能小于请求长度，不能据此判断消息结束。
- 对端关闭写方向后 `recv` 返回 0，表示该方向不会再有数据，本端仍可继续发送。
- 注册 `EPOLLRDHUP` 后可以在不调用 `recv` 的情况下提前得知对端关闭了写方向。
- `EPOLLHUP` 与 `EPOLLERR` 不受事件掩码控制，出现时先用 `getsockopt(SO_ERROR)` 取错误码再决定关闭方式。
- 关闭前应把接收缓冲区中的剩余数据读完，否则 `close` 会使未读数据触发 RST。
- 监听套接字上的可读事件不携带数据，必须调用 `accept` 才能得到新连接。

### 6.4 水平触发与边缘触发在服务器实现中的差异？

- 水平触发在条件成立期间反复报告，处理函数可以只读一部分，剩余数据在下一次等待中再次出现。
- 边缘触发只在状态变化时报告一次，处理函数必须在同一次回调中把数据读到 `EAGAIN`。
- 边缘触发减少重复通知，连接数多而单次数据量小时收益明显。
- 水平触发容错更高，漏读只产生一次多余唤醒；边缘触发漏读会让连接停到下一次数据到达。
- 边缘触发必须配合非阻塞套接字，否则读空的调用会睡眠在事件循环线程上。
- 同一进程内可以混用：监听套接字用水平触发简化 `accept`，数据连接用边缘触发减少唤醒。
- 两种模式对 `EPOLLERR` 与 `EPOLLHUP` 的处理相同，都要在读写前检查。

### 6.5（陷阱）边缘触发下读循环为什么必须读到 EAGAIN？

- 边缘触发只在状态变化时通知，循环提前退出后剩余数据不会再触发事件。
- 读到 `EAGAIN` 说明接收缓冲区已空，此时退出循环是安全的。
- 循环内若使用阻塞套接字，读空后进入睡眠，事件循环停止，其他连接的处理全部延迟。
- 用 `recv` 返回 0 作为退出条件会漏掉后续数据，0 只表示对端关闭写方向。
- 单次读到的字节数小于请求长度不代表读完，TCP 字节流没有固定边界。
- 读循环应设置单次处理上限，避免单个连接长期占用事件循环。

### 6.6（场景）边缘触发下发送大响应为什么会停滞？

- `write` 可能只发出一部分，剩余数据留在用户空间，未注册可写事件时不会自动重试。
- 发送缓冲区受 `SO_SNDBUF` 与对端通告窗口约束，接收方读取慢时很快写满。
- 处理方式是为连接维护输出缓冲区，关注可写事件，在回调中继续发送。
- 输出缓冲区清空后要立即取消关注可写事件，否则会持续触发并形成忙循环。
- 抓包表现为接收方通告零窗口，发送方周期性发送窗口探测报文。
- 增大 `SO_SNDBUF` 只是推迟写满的时刻，内核缓冲区占用随连接数上升。

### 6.7 可写事件应该在什么时候关注与取消？

- 刚建立的套接字通常处于可写状态，关注可写事件会立刻产生一次通知。
- 应按需关注：输出缓冲区非空时才加入，清空后立即移除。
- 边缘触发下可以先尝试发送再决定是否关注，避免窗口变化被漏掉。
- 频繁修改事件掩码有系统调用成本，可在用户态缓存掩码，仅在变化时提交。
- 关闭连接时输出缓冲区中未发送的数据是否丢弃取决于业务语义，需要与关闭流程配合。
- 只关注可读事件却期望可写通知，是长连接代理中常见的错误。

### 6.8（场景）accept 返回 EMFILE 之后如何处理？

- `EMFILE` 表示进程描述符数达到 `RLIMIT_NOFILE`，`ENFILE` 表示系统级上限耗尽。
- 水平触发下未被取走的连接让监听套接字持续可读，等待调用忙循环并占满一个核。
- 预留描述符方案：启动时打开 `/dev/null` 保存，出现 `EMFILE` 后关闭它，取出连接并立即关闭，再重新打开预留描述符。
- 也可以把监听套接字暂时移出等待集合，等资源回收后再加入。
- 长期方案是提高限制、限制单机连接数，或在接入层设置配额。
- 抓包可见客户端完成三次握手后长时间无响应，服务端日志中 `accept` 持续失败。

### 6.9 惊群是怎么产生的，EPOLLEXCLUSIVE 如何缓解？

- 多个进程或线程等待同一监听套接字时，新连接到达会唤醒全部等待者，只有一个 `accept` 成功。
- 无效唤醒的代价是上下文切换与调度开销，连接速率高时 CPU 使用率出现系统性上升。
- `EPOLLEXCLUSIVE` 让同一文件上的多个等待实例只唤醒其中一个，从而减少无效唤醒。
- 该标志只能与 `EPOLLIN`、`EPOLLOUT`、`EPOLLWAKEUP`、`EPOLLET` 组合，其他位会使注册失败。
- `SO_REUSEPORT` 从另一层面解决：每个工作进程持有独立监听套接字，由内核按四元组分流。
- 基于哈希的分流可能不均，扩缩容只影响新连接，已有连接保持原归属。

### 6.10（辨析）共享一个等待实例与 SO_REUSEPORT 多实例如何选择？

- 共享实例实现简单，连接由最先被调度的线程取走，负载容易出现倾斜。
- 共享实例便于统一超时扫描与全局统计，代价是跨线程同步。
- `SO_REUSEPORT` 在连接进入时确定归属，减少跨线程队列与缓存失效。
- `SO_REUSEPORT` 需要内核支持，同一端口上的套接字需要有效用户一致。
- 独立实例下单个线程退出会带走其监听套接字，滚动重启需要逐个摘除。
- 需要全局连接数限制时，独立实例必须额外汇总计数。

### 6.11 多线程服务器如何确定连接归属与负载均衡？

- 连接在 `accept` 之后立即绑定到某个事件循环，此后所有读写都在该循环线程执行。
- 归属方式有轮询、按活跃连接数、按四元组哈希，轮询实现简单但忽略处理成本差异。
- 连接迁移需要暂停该连接的事件处理并转移描述符与缓冲区，代价高，通常只在扩缩容时执行。
- 每个循环的线程数与 CPU 核数匹配，绑定处理器可以减少迁移与缓存失效。
- 统计信息按循环汇总，避免全局原子计数成为热点。
- 循环之间的连接数差异是延迟抖动的主要来源，需要暴露每循环的队列长度。

### 6.12 边缘触发下 accept 为什么只取到一个连接？

- 监听套接字为阻塞模式时，处理完第一个连接后再次 `accept` 会睡眠，事件循环随之停住。
- 边缘触发下，一次事件只对应一次状态变化，队列中等待的连接需要在同一次回调中循环取出。
- 正确写法是循环调用 `accept4` 直到返回 `EAGAIN`，并为新连接设置 `SOCK_NONBLOCK`。
- 单次回调可以设置处理上限，避免高连接速率下回调长期不返回。
- `backlog` 只是提示值，实际长度受 `somaxconn` 限制，队列满后新到的 SYN 被丢弃。
- `ss -lnt` 中监听套接字的 `Recv-Q` 持续等于 `Send-Q` 显示的值，说明 `accept` 速度落后于连接到达速度。

### 6.13 空闲连接如何检测与回收？

- TCP keepalive 需要先用 `SO_KEEPALIVE` 开启，空闲两小时后才开始探测，只反映链路可达性，不反映业务处理能力。
- 应用层心跳可以携带序号与时间戳，用于测量往返时延与处理延迟。
- 心跳间隔需要小于中间设备的空闲回收时间，NAT 与负载均衡通常在数分钟后丢弃空闲连接。
- 连接数很大时不宜为每个连接创建定时器，固定周期扫描加时间戳比较更省资源。
- 超时判定需要容忍抖动，通常连续多次无响应才关闭。
- 关闭空闲连接前应通知对端，直接 `close` 可能让对方在写数据时收到 RST。

### 6.14（场景）对端半关闭之后连接还能继续发送吗？

- 对端调用 `shutdown(SHUT_WR)` 后本端读到 0，本端的发送方向仍然可用。
- 收到 0 后立即 `close` 会丢弃尚未发送的数据，对端可能收不到完整响应。
- 正确流程是先停止读取，把响应写完后调用 `shutdown(SHUT_WR)`，等对端关闭再释放。
- 边缘触发下读到 0 后读方向不再有事件，写方向仍需关注可写事件。
- 关闭流程需要设置超时，避免对端不关闭导致连接长期占用资源。
- 请求响应式协议通常由客户端先关闭写方向，服务端在响应结束后关闭连接。

### 6.15（场景）为什么 close 之后对端收到的是 RST 而不是 FIN？

- 接收缓冲区仍有未读数据时调用 `close`，内核发送 RST 而不是 FIN。
- 设置 `SO_LINGER` 且超时为 0 时，`close` 立即发送 RST 并丢弃发送缓冲区中的数据。
- 优雅关闭应先 `shutdown(SHUT_WR)` 发送 FIN，等发送缓冲区排空，再等待对端关闭。
- 重启服务时先停止 `accept`，再逐个关闭连接，可以避免新请求落到即将退出的进程。
- RST 会让对端立即收到 `ECONNRESET`，进行中的响应全部丢失。
- 抓包中 FIN 与 RST 的位置可以区分正常关闭与异常关闭。

### 6.16（陷阱）描述符关闭后被复用会带来什么风险？

- `close` 之后描述符号会被系统复用，新连接可能得到同一编号。
- 旧连接的事件处理尚未完成时，按编号查找连接对象可能命中新连接，造成数据错发。
- 用连接对象指针作为事件数据可以避免按编号误认，但必须保证对象在注销之后才释放。
- 多线程环境下关闭与事件处理需要串行化到同一线程，避免注销与回调交叠。
- 引用计数或延迟释放可以让处理中的事件先完成，再回收连接对象。
- 日志同时记录描述符与连接编号，便于定位复用引起的错乱。

### 6.17 单机连接数受哪些参数限制？

- `backlog` 与 `/proc/sys/net/core/somaxconn` 取较小值决定已完成三次握手的队列长度。
- `/proc/sys/net/ipv4/tcp_max_syn_backlog` 影响半连接队列，SYN 洪泛时先于已完成队列溢出。
- `RLIMIT_NOFILE` 限制单进程描述符数，`/proc/sys/fs/file-max` 限制系统总量。
- 每个连接的内核内存随连接数线性增长，收发缓冲区与协议控制块都要计入。
- `net.ipv4.ip_local_port_range` 在客户端侧限制可用的临时端口数量。
- 两类耗尽的表现不同：端口耗尽使 `connect` 返回 `EADDRNOTAVAIL`，描述符耗尽使 `accept` 返回 `EMFILE`。

### 6.18 io_uring 服务器如何管理请求缓冲区？

- 每个未完成的读请求都需要一块在完成之前不可复用的缓冲区。
- 常见做法是每连接一个固定读缓冲区，同一时刻只保留一个未完成的读请求。
- 预注册缓冲区后内核以索引引用，请求完成前用户态不能改写该区域。
- 零复制发送期间缓冲区由网卡读取，完成事件才表示可以复用。
- 取消请求不保证立即生效，完成事件仍会到达，缓冲区要等完成后再回收。
- 批量提交需要限制在途请求数，避免内存随并发请求膨胀。

### 6.19（实现）用 epoll 编写单线程回显服务器的关键步骤？

```cpp
int lfd = socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK, 0);
int one = 1;
setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &one, sizeof one);
sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_port = htons(port);
addr.sin_addr.s_addr = htonl(INADDR_ANY);
bind(lfd, reinterpret_cast<sockaddr*>(&addr), sizeof addr);
listen(lfd, 128);
int ep = epoll_create1(EPOLL_CLOEXEC);
epoll_event ev{};
ev.events = EPOLLIN | EPOLLET;
ev.data.fd = lfd;
epoll_ctl(ep, EPOLL_CTL_ADD, lfd, &ev);
```

- 监听套接字以非阻塞方式创建并设置 `SO_REUSEADDR`，`listen` 的 `backlog` 与 `somaxconn` 取较小值生效。
- 事件循环等待后就绪事件分派，监听套接字可读时循环 `accept4` 到 `EAGAIN`。
- 新连接以非阻塞方式接受，关联连接对象后加入等待集合。
- 读回调循环 `recv` 到 `EAGAIN` 或 0，返回 0 表示对端关闭写方向。
- 写回显数据时处理部分写，未发送部分挂入输出缓冲区并关注可写事件。
- 关闭连接时先注销事件再释放对象，避免后续回调访问已释放内存。

### 6.20（场景）连接数达到十万后事件等待变慢如何排查？

- 先区分等待耗时与处理耗时：统计单次返回的事件数与每个事件的处理时间。
- 水平触发下慢连接反复就绪，唤醒次数随活跃连接增长。
- 单次返回事件数设置过小会使就绪队列分批返回，调用次数上升；过大则单次复制与遍历成本上升。
- 每连接的内核内存随连接数增长，内存压力引起的页回收与缺页会间接拖慢事件循环。
- 用户态数据结构的选择同样关键：按描述符索引的数组优于哈希表，回调中应避免动态分配。
- 定时器若每轮遍历全部连接，会成为主要开销，应改为最小堆或时间轮。
- 观测手段包括 `perf top` 查看内核符号、`ss -s` 与 `/proc/net/sockstat` 查看套接字与内存统计。

## 7. Reactor 与 Proactor

### 7.1 Reactor 模式由哪些角色组成？

- 事件分离器等待多个描述符上的事件，把就绪事件分派给注册的处理函数。
- 事件处理器负责非阻塞的读写与业务逻辑，通常以回调、虚函数或协程恢复点的形式存在。
- 资源对象持有套接字、缓冲区与连接状态，处理函数通过它访问连接。
- 事件循环只做等待与分派，任何耗时操作都要移到工作线程，否则整个循环停止推进。
- 处理函数在循环线程内依次执行，默认不存在并发，跨线程访问需要显式投递。
- 与 Proactor 的差别在于通知内容：Reactor 通知可以读写，由应用发起系统调用；Proactor 通知读写已完成。
- libevent、libuv、muduo 与 Asio 的 `epoll` 后端都属于 Reactor 模型。

### 7.2（辨析）Reactor 与 Proactor 的核心差别是什么？

- Reactor 关注就绪：应用收到可读事件后调用 `recv`，返回值与错误码由应用处理。
- Proactor 关注完成：应用提交读请求并登记缓冲区，操作完成后回调，结果码与字节数随完成事件返回。
- Proactor 把数据复制纳入异步操作，应用不必在事件回调中立即读取，逻辑更接近顺序代码。
- Reactor 的读写经常部分完成，需要应用层缓冲区；Proactor 的一次完成对应一次请求，仍可能短读。
- Windows 的 IOCP 提供完成通知，Linux 的 `io_uring` 提供完成队列，`epoll` 本身只提供就绪通知。
- Proactor 的代价是请求生命周期管理：提交时分配的缓冲区与上下文必须存活到完成回调执行。
- 两者可以组合：就绪通知加线程池执行阻塞操作，再把结果作为完成事件投递回事件循环。

### 7.3 单线程 Reactor 与多线程 Reactor 如何取舍？

- 单线程模型没有锁竞争，逻辑简单，适合连接数多而单连接计算量小的网关与推送服务。
- 单线程受限于一个核，任何阻塞调用或长计算都会抬高全部连接的延迟。
- 多线程模型可以是多个独立事件循环，也可以是共享一个循环加工作线程。
- 每循环一线程的模型把连接固定在某个循环上，循环内部无需加锁，跨循环通信代价较小。
- 线程数通常取 CPU 核数，超过核数后上下文切换与缓存失效会抵消并行收益。
- 共享循环加工作线程适合处理逻辑耗时差异大的场景，但共享状态需要保护。
- 选择依据是业务的计算占比、连接数与延迟目标，不能只看吞吐。

### 7.4 主从 Reactor 中 accept 线程与工作线程如何分工？

- 主线程只负责监听与接受连接，取到连接后按策略选择一个从线程，把描述符与初始状态移交。
- 移交之后描述符的注册、读写与关闭都由从线程负责，主线程不再持有。
- 移交通过线程安全队列加唤醒，或直接在从线程的执行上下文上投递任务。
- 从线程的负载需要反馈给主线程，否则连接数少的线程空闲而热点线程先饱和。
- 关闭时先停止接受新连接，再通知各从线程排空，最后等待线程结束。
- 主线程不做业务处理，可以避免 `accept` 被长请求阻塞而丢连接。

### 7.5 注册回调时如何管理对象生命周期？

- 回调捕获裸指针时，对象在事件触发前被销毁会导致悬垂访问。
- 常用做法是捕获 `std::weak_ptr`，执行时提升为 `std::shared_ptr`，提升失败则丢弃回调。
- `std::enable_shared_from_this` 便于在成员函数内取得当前对象的持有者，把生命周期延长到回调结束。
- 连接关闭时应先从事件循环注销关注，再释放对象；注销与回调需要串行化到同一线程。
- 尚未执行的任务同样应持有弱引用，避免关闭之后仍访问成员。
- 连接持有回调、回调持有连接会形成循环引用，需要用弱引用打破。

### 7.6（陷阱）在回调中销毁当前对象会出什么问题？

- 回调执行期间对象被释放，回调返回后继续访问成员即为释放后使用。
- 典型场景是收到错误后在回调里关闭并释放会话，随后代码仍记录日志或更新统计。
- 安全做法是把释放推迟到当前事件处理结束之后，或让最后一个持有者在回调返回后自然析构。
- 在 Asio 中可让会话由 `shared_ptr` 管理并在回调结束时不触碰成员，由引用计数决定释放时机。
- 同一对象的多个回调可能并发执行，释放时机需要由 `strand` 串行化保证。
- 调试时可借助地址检查工具观察释放后使用，线上表现为随机崩溃或数据错乱。

### 7.7 post 与 dispatch 有什么区别？

- `asio::post` 总是把处理函数排队，稍后在该执行器上运行，不关心当前所在线程。
- `asio::dispatch` 在当前已处于该执行器上下文时立即调用，否则与 `post` 相同。
- 从事件循环线程调用 `dispatch` 可能造成递归调用，深层递归会耗尽栈空间。
- 跨线程修改连接状态应投递到该连接所属的执行器，避免数据竞争。
- `io_context::run` 在没有待处理任务时返回，需要 `executor_work_guard` 阻止提前退出。
- 停止时先调用 `stop` 再 `join` 线程，未执行的任务被丢弃，其中的资源需要自行回收。

### 7.8 strand 保证什么，不保证什么？

- `strand` 保证投递到同一 `strand` 的处理函数不会并发执行。
- `strand` 不绑定固定线程，处理函数可以在不同线程上运行，同一时刻只有一个在执行。
- 连接的所有异步操作绑定同一 `strand` 后，会话状态不需要额外加锁。
- `strand` 只约束通过它投递的调用，直接调用成员函数不受保护。
- 完成处理器必须显式绑定执行器，否则按 I/O 对象的默认执行器运行，可能落到其他线程。
- `asio::make_strand` 从上下文创建 `strand`，`bind_executor` 把处理函数绑定到指定执行器。
- 多个 `strand` 之间没有顺序关系，跨连接共享的状态仍需单独保护。

### 7.9 io_context、executor 与 strand 是什么关系？

- `io_context` 是执行上下文，持有事件循环、任务队列与定时器队列，`run` 驱动分派。
- executor 是提交任务的句柄，决定任务在哪个上下文、以何种方式执行。
- 每个 I/O 对象都有默认执行器，`get_executor` 可以取出，异步操作的完成处理器默认沿用该执行器。
- `strand` 是一种 executor 适配器，把并发保证叠加在底层执行器之上。
- 同一个 `io_context` 可以被多个线程同时 `run`，任务由这些线程分担。
- 上下文销毁前必须停止并 `join` 所有线程，否则任务可能访问已销毁的对象。

### 7.10 Asio 的完成令牌有哪几种，如何选择？

- 回调形式最直接，完成处理器接收错误码与结果，需要手动管理捕获对象的生命周期。
- `use_future` 返回 `std::future`，便于与同步代码衔接，但会占用线程等待且取消支持有限。
- `use_awaitable` 在协程中把操作变成 `co_await` 表达式，错误码可按需转换为异常。
- `asio::deferred` 延迟启动操作，可组合成操作链，适合把异步操作当作值传递。
- `as_tuple` 让完成处理器接收结果元组，`redirect_error` 在错误码与异常之间转换。
- 自定义令牌需要提供 `async_result` 特化，把完成签名映射到返回值类型。
- 同一项目中混用多种令牌会增加阅读成本，通常按模块统一约定。

### 7.11（实现）async_write 为什么需要额外的输出缓冲区？

- `async_write` 保证整个缓冲区写完才调用完成处理器，内部可能分成多次单次写。
- 缓冲区必须在完成之前保持有效，栈上的临时缓冲区在函数返回后即失效。
- 常见做法是给每个会话维护输出队列，把待发数据放入队列，再以队首元素发起写。
- 多个写请求不能并发：上一个 `async_write` 未完成时再次发起会导致数据交错。
- 写完一项后从队列头部移除，若队列非空继续下一项，避免为每个响应单独分配。
- 队列元素被移除会使指向它的缓冲区失效，必须在完成回调之后才修改容器。

### 7.12（场景）异步关闭连接时如何处理未完成的异步操作？

- 关闭流程应先停止读，再排空输出队列，最后关闭套接字。
- 未完成的读操作在关闭后以 `asio::error::operation_aborted` 完成，回调中不应访问已释放的缓冲区。
- 主动取消可以用 `socket::cancel`，它让挂起的操作以取消错误完成，但不关闭描述符。
- `socket::close` 会取消挂起操作并释放描述符，之前排队的写数据被丢弃。
- 关闭动作应投递到连接所属的 `strand`，与正在执行的回调串行。
- 会话对象由引用计数管理时，最后一个未完成回调结束后才真正析构。
- 服务端主动关闭前可先调用 `shutdown(send)` 发送 FIN，让对端读到 0 再关闭。

### 7.13 事件循环中的定时器如何与 I/O 事件统一调度？

- 定时器按到期时间组织成最小堆，等待调用的超时取最近到期时间与固定上限中的较小值。
- 定时器数量很大时用时间轮，插入为常数时间，精度由槽宽决定。
- Asio 的 `steady_timer` 使用单调时钟，`expires_after` 会重置到期时间并取消挂起的等待。
- 定时器回调与 I/O 回调在同一线程执行，回调耗时过长会推迟其他定时器。
- 大量连接的空闲检测不适合每连接一个定时器，固定周期扫描加时间戳比较更省资源。
- 取消定时器时挂起的等待以 `operation_aborted` 完成，需要区分主动取消与真实超时。
- 单次处理时间超过定时器精度时，应把长任务拆分成多段并让出事件循环。

### 7.14（场景）线程数增加后吞吐不升反降的原因有哪些？

- 共享状态上的锁竞争加剧，线程大部分时间在等待，实际并行度没有提升。
- 缓存行在多个核之间来回失效，计数器与队列头尾指针是常见的竞争点。
- 上下文切换与调度开销随线程数增长，超过核数后收益转为负值。
- 内存分配器在多线程下的竞争同样明显，每线程缓存可以缓解。
- 任务粒度太细时，投递与唤醒的成本超过任务本身的执行时间。
- `strand` 或任务队列的串行化点过多，使并行执行的代码段被压缩。
- 定位手段是比较不同线程数下的 CPU 使用率、上下文切换次数与锁等待时间。

### 7.15（陷阱）在事件回调中调用阻塞操作会怎样？

- 当前线程停止处理其他事件，若该线程是唯一的事件循环，全部连接延迟上升。
- 阻塞时间超过心跳周期时，对端可能判定连接失效并断开。
- 阻塞调用不响应取消，退出时停止上下文无法中断它，进程只能被强制结束。
- 异步接口误用也会造成阻塞：同步域名解析会查询 DNS，`async_resolve` 才把查询交给后台。
- 把阻塞操作移入线程池，完成后投递回事件循环，是常见的隔离方式。
- 日志、指标上报与配置读取都可能隐含磁盘或网络操作，需要在回调路径上审计。

### 7.16 Proactor 模型下缓冲区生命周期如何管理？

- 提交读请求时缓冲区地址交给内核，完成之前不能被移动、释放或复用。
- 常见做法是每连接维护固定大小的读缓冲区，同一时刻只有一个未完成的读请求。
- 需要并发多个请求时，用缓冲区池按请求分配，完成后归还。
- 预注册缓冲区后内核以索引引用，用户态不能同时改写该区域。
- 取消操作不保证立即生效，完成事件仍可能到达，缓冲区必须等到完成事件再回收。
- 零复制发送期间缓冲区由网卡直接读取，提前复用会破坏已发出的报文。

### 7.17 协程如何接入事件循环？

- 有栈协程保存独立栈，挂起与恢复的成本较高，但可以在任意调用深度挂起。
- 无栈协程由编译器生成状态机，`co_await` 挂起时把恢复句柄交给异步操作。
- Asio 的 `co_spawn` 启动协程，`use_awaitable` 把回调式接口转换为可等待对象。
- 协程帧保存局部变量，帧的分配可能被编译器优化掉，也可能落在堆上。
- 协程恢复仍在事件循环线程执行，长时间计算同样会阻塞循环。
- 挂起期间不能持有指向栈上对象的引用，恢复后栈帧已经不同。
- 同一连接上的协程需要串行化时，绑定同一 `strand` 即可，不必额外加锁。

### 7.18 协程的取消与异常如何传播？

- 协程内抛出的异常交给 `co_spawn` 的完成处理器，处理器的签名需要接收 `std::exception_ptr`。
- 使用 detached 令牌时异常被丢弃，未捕获的失败不会出现在任何地方。
- 取消通过取消槽传播，`bind_cancellation_slot` 把槽与异步操作关联，操作以取消错误完成。
- 协作式取消要求每个 `co_await` 点检查状态或依赖操作自身的取消语义。
- 协程帧在取消后仍需等待挂起操作完成才能释放，提前销毁会导致恢复时访问已释放内存。
- 结构化并发要求父协程等待子协程结束，否则退出时子协程的结果无人接收。

### 7.19（实现）用 Asio 编写异步回显会话的关键点？

```cpp
void session::read() {
  auto self = shared_from_this();
  sock_.async_read_some(asio::buffer(buf_),
    [this, self](std::error_code ec, std::size_t n) {
      if (ec) return;
      out_.append(buf_.data(), n);
      asio::async_write(sock_, asio::buffer(out_),
        [this, self](std::error_code ec, std::size_t) {
          out_.clear();
          if (!ec) read();
        });
    });
}
```

- 会话由 `std::shared_ptr` 管理，回调捕获 `shared_from_this` 把生命周期延长到回调结束。
- 读缓冲与输出缓冲都是成员，回调执行期间地址保持有效。
- 同一时刻只保留一个未完成的读与一个未完成的写，避免数据交错。
- 完成处理器中的错误码需要区分 `eof`、`operation_aborted` 与真实错误。
- 会话析构时套接字自动关闭，关闭前取消挂起操作可以加快回收。
- 若把完成处理器绑定到 `strand`，回显逻辑不需要额外的互斥保护。

### 7.20 事件循环退出时需要按什么顺序清理？

- 先停止接受新连接，关闭监听套接字并从等待集合中移除。
- 向所有会话发起优雅关闭，等待输出队列排空或到达超时后强制关闭。
- 取消定时器与信号等待，挂起的操作以 `operation_aborted` 完成。
- 停止执行上下文，`run` 返回后 `join` 所有线程，再释放会话对象。
- 停止时未执行的处理函数被丢弃，其中捕获的资源需要在析构路径上释放。
- 最后刷新日志与指标，异步日志组件本身也需要停止并排空队列。
- 退出顺序错误会在关闭阶段产生释放后使用，表现为进程退出时的崩溃。

## 8. 粘包与协议设计

### 8.1 TCP 为什么会出现粘包与拆包？

- TCP 提供字节流，`send` 的调用边界与 `recv` 的返回边界之间没有对应关系，内核只保证字节顺序。
- 连续两次 `send` 的数据可能被合并进同一个报文段，接收方一次 `recv` 就读到多条消息。
- 接收缓冲区中的数据可以分批返回，一次 `recv` 也可能只取到一条消息的一部分。
- 路径 MTU 决定单个报文段的上限，消息超过上限时被分段，接收端需要多次读取才能拼齐。
- 因此消息边界必须由应用层协议定义，长度前缀、分隔符与固定长度是三种基本手段。
- `TCP_NODELAY` 只影响发送延迟，不能消除合包，边界问题仍然存在。

### 8.2 长度前缀协议如何设计？

- 固定长度的头部包含魔数、版本、消息类型、负载长度与请求编号，长度字段描述负载的字节数。
- 接收端先读满头部，再按长度读满负载，解析状态机分为头部与负载两个阶段。
- 长度字段需要上限校验，超过阈值直接断开，避免畸形长度导致巨量内存分配。
- 头部自身也要校验，魔数不符说明字节流已经错位，无法重新同步时只能关闭连接。
- 长度字段的字节序必须固定，通常使用网络字节序。
- 单条消息过大时应拆分为多条或改为分块传输，避免一次性分配大块内存。
- 抓包时可以按长度字段核对负载是否完整，快速判断是发送截断还是接收解析错误。

### 8.3 分隔符协议有哪些边界问题？

- 分隔符不能出现在负载中，否则解析提前结束，需要在负载中转义。
- 转义方案必须定义转义字符自身的编码，否则出现二义性。
- 单字节分隔符实现简单，逐字节扫描在长消息上开销明显，可用 `memchr` 加速。
- 分隔符跨越两次 `recv` 时扫描状态需要保留，不能每次都从缓冲区头部重新开始。
- 仍然需要最大消息长度限制，否则对端始终不发送分隔符时缓冲区无限增长。
- HTTP/1.1 的头部用 CRLF 分隔，正文用 `Content-Length` 或分块编码，是两种方案的组合。

### 8.4（辨析）固定长度、长度前缀与分隔符三种方案如何取舍？

- 固定长度实现最简单，解析不需要状态机，负载长度变化时浪费带宽或需要填充。
- 长度前缀适合二进制协议，一次定位负载边界，解析复杂度与消息长度无关，需要处理字节序与上限。
- 分隔符适合文本协议，可读性好，负载需要转义，扫描成本随消息长度增长。
- 三种方案都要求接收端具备缓冲区管理，能处理半包与多包共存。
- 定长方案在协议演进时难以扩展，新增字段只能占用预留位置。
- 长度前缀与定长头部可以组合：头部用固定长度，头部内部再给出负载长度。

### 8.5 protobuf 的线格式如何界定消息边界？

- protobuf 编码本身不带总长度，解析接口依赖调用方给出的字节范围。
- 字段以 `tag` 开头，低 3 位是线类型：0 变长整数、1 固定 64 位、2 长度前缀、5 固定 32 位。
- 长度前缀线类型的字段自带长度，但整条消息的边界仍需外层协议提供。
- 常用做法是在外层加长度前缀，或使用 delimited 格式：先写消息长度再写消息体。
- 缺少边界时连续写入多条消息，解析器会把后一条字节当作前一条的未知字段。
- 未知字段会被保留并在重新序列化时写出，跨版本转发不会丢失，但字段顺序可能改变。

### 8.6（场景）delimited 格式在流式解析中有什么限制？

- 长度前缀使用 varint 编码，读取时要逐字节判断最高位，不能按固定宽度读。
- 读取方必须使用相同的 delimited 解析接口，混用普通解析会导致字节流错位。
- 长度前缀为 0 表示空消息，读取方应产生一个空消息，而不是判定流结束。
- 该格式与文本协议的分隔符逻辑不兼容，同一连接上不能混用两种边界规则。
- 单条消息过大时前缀仍然很小，内存分配仍按消息体大小进行，需要单独限流。
- C++ 的实现位于 `google/protobuf/util/delimited_message_util.h`，Java 的 `writeDelimitedTo` 使用相同格式。

### 8.7 protobuf 的版本兼容规则有哪些？

- 字段编号一旦发布不能复用，删除字段应把编号与名称加入 `reserved`。
- 新增字段使用新编号，旧版本解析时作为未知字段保留，不影响已有字段。
- 修改字段类型会破坏兼容，线类型改变时解析直接失败。
- 重复字段的打包编码与非打包编码互不兼容，修改该选项会使新旧版本无法互读。
- 枚举新增值对旧版本是未知值，proto3 保留数值，proto2 放入未知字段。
- 默认值不参与序列化，无法区分未设置与设置为零，需要显式存在性时用 `optional`。
- 字段编号 1 到 15 的 `tag` 占一个字节，热字段应优先使用这些编号。

### 8.8（陷阱）修改 protobuf 字段类型后线上为什么解析错位？

- 线类型改变时解析器按旧类型读取新字节，长度判断与边界推进全部失效。
- `int32` 与 `sint32` 线类型相同，负数编码方式不同，互换后数值错误但不报错。
- `string` 与 `bytes` 线类型相同，互换后不报解析错误，但字符串校验可能失败。
- `int32` 改为 `int64` 线类型相同，旧版本读取大值时被截断，表现为数值溢出。
- 修改 `repeated` 字段的打包选项，会使新旧版本互相无法解析。
- 上线前应做兼容性检查，或在消费端保留旧 schema 做灰度对照。

### 8.9 心跳报文应放在协议哪一层，间隔如何确定？

- 心跳作为独立的消息类型，与业务请求共用同一帧格式，解析路径一致。
- 心跳可以携带序号与时间戳，用于测量往返时延并发现处理线程阻塞。
- 间隔需要小于中间设备的空闲回收时间，NAT 与负载均衡通常在数分钟后丢弃空闲连接。
- 间隔过短会带来额外流量与唤醒，连接数大时成本明显，可与低频业务消息合并。
- 超时判定要容忍抖动，通常连续多次无响应才判定连接失效。
- 服务端也可以主动探测，用于回收半开的连接，两端的心跳参数需要协调。
- 心跳失败与业务错误要分开统计，前者反映链路与对端存活，后者反映处理逻辑。

### 8.10（场景）半包处理不当会造成什么后果？

- 读取长度字段时缓冲区不足 4 字节，按固定偏移解析会读到未初始化内存或越界。
- 长度字段解析错误后按错误长度分配缓冲区，可能触发巨量分配或直接崩溃。
- 只处理一条消息而忽略缓冲区中的剩余数据，剩余消息被丢弃，表现为间歇性丢请求。
- 一次读到多条消息时解析循环没有推进读指针，导致重复处理同一条消息。
- 缓冲区扩容策略不当会频繁搬移数据，长连接上表现为 CPU 占用升高。
- 正确做法是维护读指针与可读长度，循环解析到不足一条完整消息，再整理缓冲区。

### 8.11 校验与压缩应放在协议的哪一层？

- 校验和通常覆盖头部与负载，接收方在解析之前验证，失败即丢弃或断开。
- CRC32 计算成本低，适合高吞吐场景，更强的校验会带来额外的 CPU 开销。
- 压缩应在加密之前，否则压缩率下降并可能泄露信息。
- 压缩算法与级别需要协商，接收方不支持时回退到不压缩。
- 逐条压缩对小消息收益很低，可以把多条消息合并后整体压缩。
- 校验字段本身要参与长度计算，避免校验范围与长度定义不一致。

### 8.12 帧格式如何支持版本演进与扩展？

- 头部保留版本字段，接收方按版本选择解析逻辑，未知高版本直接拒绝或按基础字段解析。
- 头部长度字段让旧版本能够跳过新增字段，实现向前兼容。
- 扩展字段以 TLV 形式追加在负载之后，旧版本解析时忽略未识别的类型。
- 连接建立时交换支持的版本与特性位图，后续按协商结果处理。
- 升级需要过渡期，服务端同时支持新旧版本，按连接分别处理。
- 拒绝策略要明确：返回错误码并关闭，还是降级处理，取决于协议语义。

### 8.13（场景）UDP 为什么不存在粘包？

- UDP 保留消息边界，一次 `sendto` 对应一个数据报，一次 `recvfrom` 取出完整数据报。
- 超过 MTU 的数据报会被 IP 分片，任一分片丢失都会导致整个数据报被丢弃。
- 接收缓冲区不足时数据报被截断，多余部分丢弃，`recvfrom` 返回实际复制的长度。
- 应用层仍需处理乱序、重复与丢失，可靠传输要在 UDP 之上自行实现。
- 数据报大小应控制在路径 MTU 以内，避免分片带来的丢包放大。
- 需要消息边界又要求可靠时，可用 `SOCK_SEQPACKET` 或基于 UDP 的可靠协议。

### 8.14（场景）如何用抓包定位粘包问题？

- 在服务端与客户端分别抓包，对比同一请求的字节流是否完整到达。
- 按 TCP 流跟踪查看字节顺序与分段位置，核对长度字段与实际负载长度。
- 观察是否存在重传、乱序与零窗口，网络层问题会放大解析错误的概率。
- 应用日志应打印收到的字节数与解析出的消息长度，与抓包结果逐条对照。
- 复现时可用随机长度的消息做压测，覆盖跨两次读取边界的组合。
- 若只有一侧抓包，可以按时间戳对齐请求与响应，判断是发送截断还是接收偏移。

### 8.15 接收缓冲区如何组织以减少复制？

- 环形缓冲区让写入与读取各自推进指针，避免每次搬移数据。
- 消息跨缓冲区尾部时先读到临时区，或用两段 `readv` 写入。
- 解析出完整消息后只移动读指针，空间不足时再整理。
- 大消息可预分配与长度匹配的缓冲区，避免多次扩容。
- `recvmsg` 配合 `MSG_PEEK` 可以先查看头部再决定读取量，代价是多一次系统调用。
- 缓冲区上限要可配置，超过上限说明对端违反协议，应断开连接。

### 8.16（实现）如何编写长度前缀的解码循环？

```cpp
bool decode(Buffer& in, std::vector<std::string>& out) {
  while (in.readable() >= 4) {
    uint32_t len = 0;
    std::memcpy(&len, in.peek(), sizeof len);
    len = ntohl(len);
    if (len > kMaxFrame) return false;
    if (in.readable() < 4 + len) return true;
    in.retrieve(4);
    out.emplace_back(in.peek(), len);
    in.retrieve(len);
  }
  return true;
}
```

- 循环条件是缓冲区中至少有 4 字节，长度字段本身也可能分两次到达。
- 先校验长度上限再判断是否完整，避免畸形长度导致大块分配。
- 不足一条完整消息时直接返回，保留缓冲区内容，等下一次读取补齐。
- 取出消息后推进读指针，剩余数据继续参与下一轮解析。
- 返回错误表示协议违规，调用方应关闭连接而不是继续解析。
- `in.peek()` 与 `in.retrieve()` 的语义需要与缓冲区实现一致，避免野指针。

### 8.17 请求编号与多路复用如何设计？

- 每条请求带单调递增的 64 位编号，响应回填同一编号，调用方据此匹配。
- 编号回绕时需要保证在途请求数小于编号空间，否则会与旧请求混淆。
- 服务端可以并发处理同一连接上的多个请求，响应顺序可以与请求不同。
- 需要保序的协议可规定同一编号空间内按序返回，或引入流标识区分逻辑通道。
- 取消请求时发送带编号的取消帧，服务端丢弃对应任务并返回确认。
- 编号与连接绑定，重连后重新开始，避免与旧连接的在途响应混淆。

### 8.18（陷阱）直接把结构体写到套接字有什么风险？

- 结构体存在填充字节，不同编译器与编译选项下布局不同，跨平台解析错位。
- 多字节整数按主机字节序存放，对端字节序不同时数值错误。
- 指针与容器类型不能跨进程传输，序列化内容必须限定为可平凡复制的定长类型。
- 对齐要求可能使 `sizeof` 大于字段之和，长度字段与实际负载不一致。
- 打包属性可以消除填充，但会造成非对齐访问，在部分架构上性能下降或触发异常。
- 结构体的填充内容不确定，可能把栈或堆中的残留数据发送出去。
- 正确做法是按字段序列化，逐字段写入固定字节序的缓冲区。

### 8.19（场景）代理转发时修改帧内容要注意什么？

- 只做透传时不改动任何字段，长度与校验和保持不变。
- 修改负载后必须同步更新长度字段与校验和，否则下游解析越界。
- 在头部追加字段会改变负载偏移，后续所有字段的位置都需要调整。
- 分块转发不能简单拼接两个帧，需要在应用层重新组帧。
- 压缩或加密会改变负载长度，长度字段应按变换后的字节数填写。
- 转发前校验长度上限，避免把畸形帧继续传给下游。
- 对比入口与出口的帧结构，可以判断是代理改写错误还是下游解析错误。

### 8.20 协议升级时如何保持消息边界兼容？

- 新版本只在尾部追加字段，旧版本按头部长度跳过未知部分。
- 变更分隔符或长度字段宽度会使旧版本无法解析，需要版本协商后再切换。
- 握手阶段交换版本号与能力位图，服务端按连接选择解析器。
- 灰度期间同一端口可能同时存在新旧客户端，服务端需要并行支持两套解析。
- 升级失败要有回退路径，协议版本单调递增，降级后旧解析器仍能处理基础字段。
- 解析器应区分无法识别的版本与数据错误，前者返回明确的错误码，后者直接断开。

## 9. 字节序与序列化

### 9.1 如何判断主机字节序？

- 把一个 32 位整数 `0x01020304` 写入内存，再按字节读取，首字节为 `0x04` 说明是小端。
- 小端把最低有效字节放在低地址，大端把最高有效字节放在低地址。
- 运行时判断可以用 `memcpy` 到字节数组，避免用指针别名读取造成的未定义行为。
- C++20 起可用 `std::endian::native` 在编译期判断，不需要运行时探测。
- 判断结果只影响是否交换，协议本身必须固定为网络字节序，不能依赖主机结果。
- 双端处理器可以在启动时选择字节序，代码不应假定只存在纯小端与纯大端两种情况。

### 9.2 网络字节序为什么采用大端，转换函数如何使用？

- 大端与数值书写顺序一致，手工解析报文时高位在前，便于阅读与调试。
- 早期协议实现与当时的处理器多采用大端，RFC 1700 规定网络字节序为大端。
- `htons`、`htonl`、`ntohs`、`ntohl` 声明在 `arpa/inet.h`，Windows 下在 `winsock2.h`。
- 这些函数只处理 16 位与 32 位整数，浮点数与结构体没有对应的标准函数。
- 主机字节序与大端一致时，实现通常把转换函数做成空操作，代码不应依赖这一点。
- 转换位置要成对出现：写入报文字段前转换，读出字段后转换，遗漏一次就会得到错误数值。
- 同一条报文中混用已转换与未转换字段，是排查字节序问题时最常见的现象。

### 9.3 64 位整数与浮点数如何转换字节序？

- 64 位整数可用 `htobe64` 与 `be64toh`，声明在 `endian.h`，需要定义 `_DEFAULT_SOURCE`。
- Windows 没有对应函数，需要按字节重排或使用编译器内建函数。
- 浮点数先按位复制到同宽度的无符号整数，转换后再复制回浮点类型。
- `std::bit_cast` 提供标准的按位复制途径，要求两个类型大小相同且可平凡复制。
- 直接对浮点变量取地址并按字节交换会破坏其表示，必须经过整数中转。
- IEEE 754 规定的是位布局，字节顺序仍由主机决定，跨平台传输时按整数方式转换即可。
- NaN 的载荷位在不同实现间可能被改写，协议不应依赖具体的位模式。

### 9.4（辨析）对齐与填充如何影响协议布局？

- 编译器按成员的自然对齐要求插入填充，使每个成员的偏移是其对齐值的整数倍。
- `sizeof` 包含尾部填充，`offsetof` 才能给出真实偏移，协议文档应使用偏移描述字段。
- 成员顺序影响结构体大小，把 8 字节成员放在前面通常能减少填充。
- 跨平台协议应显式规定每个字段的宽度与偏移，避免依赖编译器的布局规则。
- `alignas` 可以提高对齐要求，但不能降低已有类型的自然对齐。
- 用 `static_assert` 校验 `sizeof` 与 `offsetof`，可以在编译期发现布局变化。
- 对齐规则属于实现定义的行为，不同 ABI 的默认对齐可能不同。

### 9.5（实现）打包结构体有哪些代价？

- `#pragma pack(1)` 或 `__attribute__((packed))` 消除填充，`sizeof` 等于字段宽度之和。
- 非对齐访问在 x86 上通常可用但有性能损失，在部分 ARM 配置上会触发异常或由内核模拟。
- 取打包成员的地址可能产生未对齐指针，传给要求对齐的函数会出错。
- 编译器对打包成员的访问可能生成逐字节读取的代码，吞吐下降。
- 打包只解决布局，不解决字节序与 ABI 演进问题。
- 打包属性属于编译器扩展，行为由实现定义，跨编译器移植需要验证。
- 需要稳定布局时，显式序列化比打包结构体更可靠。

### 9.6 varint 编码的原理是什么？

- 每个字节的低 7 位存放数据，最高位表示后面是否还有字节。
- 数值越小占用字节越少，32 位无符号整数最多 5 字节，64 位最多 10 字节。
- 编码按低位在前排列，解码时按 7 位一组左移拼接。
- 变长编码无法随机访问，定位第 n 个字段必须从头扫描。
- 连续的小整数在 varint 下压缩效果明显，适合编号、长度与计数类字段。
- 固定宽度的哈希值与浮点数不适合 varint，编码后反而变长。
- 编码长度依赖数值大小，同一字段在不同消息中占用不同字节数，解析必须逐字节判断。

### 9.7 zigzag 编码解决什么问题？

- 负数用补码直接做 varint 编码会占满 10 字节，浪费空间。
- zigzag 把有符号整数映射为无符号整数，绝对值小的负数也只需 1 字节。
- 32 位映射为 `(n << 1) ^ (n >> 31)`，64 位把移位量改为 63。
- 实现时先把整数转换为无符号类型再移位，避免对有符号负数左移带来的未定义行为。
- 解码为 `(v >> 1) ^ -(v & 1)`，与编码互逆。
- 映射依赖算术右移，C++20 起有符号数的右移定义为算术移位。
- protobuf 用 `sint32` 与 `sint64` 表示 zigzag 编码，`int32` 与 `int64` 仍是补码 varint。
- 字段值以正数为主时 zigzag 没有收益，选择类型应按取值分布决定。

### 9.8（陷阱）varint 解码为什么会溢出或越界？

- 连续 10 个字节的最高位都为 1 表示编码非法，继续读取会越过缓冲区。
- 对 32 位类型，第 5 字节中超出 32 位的部分应判为错误，否则数值被静默截断。
- 左移位数达到或超过类型宽度属于未定义行为（`[expr.shift]/1`），解码循环必须限制次数。
- 解码前应确认缓冲区剩余长度，逐字节读取并检查边界。
- 畸形输入应作为协议错误返回，而不是继续解析后续字节。
- 长度字段本身用 varint 编码时，同样需要上限校验，避免按错误长度分配内存。

### 9.9 位域与位序在协议中如何处理？

- 位域的分配顺序由实现定义，同一份声明在不同编译器上可能得到不同的位布局。
- 网络协议中的位字段需要按位操作显式组装，例如把类型与标志位拼成一个 16 位整数。
- 用移位与掩码读写位字段，可以保证结果与主机字节序无关。
- 位域跨字节边界时的填充规则同样由实现定义。
- 位序与字节序是两个维度，协议文档应分别规定每一位的位置。
- 需要紧凑存储时可以使用位域，但序列化时必须逐位转换。
- 抓包工具通常按位展开显示，对照协议文档可以确认位序约定是否一致。

### 9.10（条款）对象的字节表示与值表示有什么区别？

- 值表示是决定对象值的那些位，字节表示是对象占用的全部字节，包含填充。
- 相同的值可以有不同的字节表示，填充位的取值不确定。
- 用 `memcmp` 比较两个对象是否相等并不可靠，填充字节可能不同。
- 序列化必须基于值而不是字节表示，逐字段写出才能跨平台稳定。
- `std::bit_cast`（P0476R2）要求两个类型大小相同且可平凡复制，结果依赖字节表示。
- 对可平凡复制类型按字节复制会连同填充一起复制，但填充内容没有语义，不能作为协议内容传输。

### 9.11 C++20 的 std::endian 与 C++23 的 std::byteswap 如何使用？

- `std::endian::native`、`little`、`big` 是 `bit` 头文件中的枚举值，由 P0463R1 引入。
- `std::endian` 是编译期常量，可配合 `if constexpr` 选择是否交换字节。
- `std::byteswap` 由 P1272R4 引入，按值交换字节顺序，对整数类型使用。
- `std::endian` 只做判断，不提供转换函数，二者常一起使用。
- 处理网络协议时仍应显式写出转换，不要因为本机是大端就省略。
- 代码不应假定 `native` 一定是 `little` 或 `big`，理论上还存在混合字节序的实现。
- `std::endian` 要求 C++20，`std::byteswap` 要求 C++23，旧标准项目需要自行实现等价逻辑。

### 9.12（陷阱）memcpy 与类型双关有什么风险？

- 通过 `reinterpret_cast` 把字节缓冲区当作结构体指针访问，违反严格别名规则，优化后行为不可预期。
- 用 `memcpy` 复制到目标对象是安全的，编译器通常会优化为直接加载。
- 从缓冲区读取多字节整数应先 `memcpy` 到整数对象，再按需转换字节序。
- 直接对未对齐地址解引用，在部分架构上会触发异常。
- 联合体双关在 C 中合法，在 C++ 中读取非活跃成员属于未定义行为，尽管多数实现接受。
- C++20 的 `std::bit_cast` 提供了标准的按位复制途径，前提是类型可平凡复制且大小相同。
- 读取网络字节流的推荐路径是字节复制加显式移位，不依赖任何双关技巧。

### 9.13 网络协议中的校验和如何计算？

- IP 头部校验和按 16 位反码求和再取反，计算时校验和字段本身置零。
- TCP 与 UDP 的校验和覆盖伪首部、头部与负载，伪首部包含源地址、目的地址、协议号与长度。
- 求和按网络字节序的 16 位字进行，长度为奇数时末尾补零。
- 校验和字段本身不参与求和，验证时把它视为零。
- 修改负载后必须重算校验和，代理只改头部时同样需要更新。
- 网卡支持校验和卸载时，协议栈可能把校验和计算交给硬件，抓包看到的字段值可能与实际不符。
- 接收端校验失败通常直接丢包，抓包中看不到应用层报错，只能通过计数器发现。

### 9.14（场景）抓包看到数值颠倒如何定位？

- 先确认字段宽度，4 字节值被按 2 字节交换会出现高低半字互换的规律。
- 对比发送端日志中的数值与抓包字节，判断是发送前就错误还是接收端解释错误。
- 检查是否对同一字段做了两次转换，例如转换后又按主机序读取一次。
- 结构体直接发送时填充字节会让字段偏移与协议文档不一致，表现为整体错位而不是单纯颠倒。
- 代理或网关做过一次转换而下游又转换一次，会出现双重交换。
- 用固定值构造测试报文，可以一次性确认两端的字节序约定。
- 日志同时打印十六进制字节与解释后的数值，对照抓包可以减少猜测。

### 9.15 零复制序列化库如何避免中间缓冲区？

- FlatBuffers 把对象按偏移组织成一段连续内存，读取时按偏移直接访问，无需构建对象树。
- 另一类零复制格式的布局在编译期确定，数据段与指针段分离，读取即访问映射的内存。
- 写入端仍需构造缓冲区，省去的是接收端的反序列化分配与复制。
- 变长字段存放在独立区域，通过偏移引用，访问时需要校验边界。
- 版本演进通过在表尾追加字段实现，旧读取器按表大小忽略未知字段。
- 零复制适合大消息与低延迟场景，小消息的构建成本可能高于传统序列化。
- 未经验证的数据直接按偏移访问有安全风险，来自不可信来源时需要先校验。

### 9.16 序列化与网络发送如何减少复制？

- `writev` 一次发送多个缓冲区，头部与负载分开存放时无需先拼接。
- `sendmsg` 支持辅助数据，配合 `MSG_ZEROCOPY` 可以让内核直接引用用户页。
- 环形缓冲区中跨越尾部的消息可用两段 `writev` 发送，避免搬移。
- TLS 需要在用户态加密，零复制在加密层之前失效，瓶颈转为加密开销。
- 内核发送缓冲区满时仍会排队或阻塞，零复制只减少一次复制，不改变流量控制。
- 缓冲区复用必须等发送完成，`MSG_ZEROCOPY` 通过错误队列的完成通知回收，管理复杂度上升。
- 分散聚集 I/O 减少的是用户态拼接，不会减少协议栈内部的处理。

### 9.17（场景）跨语言序列化有哪些差异？

- `bool` 的大小与取值表示由实现定义，C++ 中通常为 1 字节，但不能跨语言假定。
- `long` 在不同平台上的宽度不同，协议中应使用固定宽度类型。
- 枚举的底层类型由实现选择，跨语言时按整数处理更稳妥。
- 字符串编码需要显式约定，UTF-8 与 UTF-16 的字节长度不同。
- 结构体对齐与填充规则各语言不同，直接映射二进制布局容易错位。
- 文本格式的数字精度有限，大整数在 JSON 中可能丢失精度。
- 默认值与字段存在性的语义差异，会导致同一份数据在不同语言中解析出不同结果。

### 9.18 序列化的性能瓶颈通常在哪里？

- 反射式序列化需要遍历字段表并做类型分派，开销高于生成的代码。
- 字符串与容器的内存分配次数是主要成本，预分配与对象池可以缓解。
- 小消息的固定开销占比高，批量合并可以减少每条消息的成本。
- 压缩与加密的 CPU 开销常超过序列化本身，需要按吞吐目标选择算法。
- 跨语言边界的数据复制与上下文切换，成本可能高于编码本身。
- 度量应分别统计编码、加密、系统调用与等待时间，避免把网络延迟归因于序列化。
- 缓存友好性同样重要，字段顺序与内存布局会影响遍历时的缓存命中率。

### 9.19（实现）如何手写一个写入大端整数的函数？

```cpp
inline void put_u32(std::vector<uint8_t>& out, uint32_t v) {
  out.push_back(static_cast<uint8_t>(v >> 24));
  out.push_back(static_cast<uint8_t>(v >> 16));
  out.push_back(static_cast<uint8_t>(v >> 8));
  out.push_back(static_cast<uint8_t>(v));
}
inline uint32_t get_u32(const uint8_t* p) {
  return (uint32_t{p[0]} << 24) | (uint32_t{p[1]} << 16) |
         (uint32_t{p[2]} << 8) | uint32_t{p[3]};
}
```

- 逐字节移位写出，结果与主机字节序无关，不需要条件编译。
- `static_cast` 截取低 8 位，避免窄化转换的告警。
- 读取时把每个字节先提升为无符号类型，防止左移溢出或符号扩展。
- 避免对有符号整数做移位，右移负数在旧标准中语义不确定。
- 批量写入可先按 4 字节扩展缓冲区，再用 `memcpy` 加 `std::byteswap` 的条件分支。
- 写入前检查剩余空间，网络路径上的越界写比数值错误更难排查。

### 9.20 端到端序列化方案如何选型？

- 内部服务之间优先使用 IDL 加代码生成，schema 即接口约定，字段编号可管理。
- 需要人工排查的配置与日志使用文本格式，便于比对与检索。
- 大消息与低延迟场景可考虑零复制格式，代价是构建与校验的复杂度。
- 跨语言边界要验证各语言实现对默认值、未知字段与枚举的处理是否一致。
- 版本兼容与演进策略比编码效率更难变更，应在设计初期确定。
- 选型应以基准测试为依据，覆盖目标消息大小与并发模型。
- 需要长期归档的数据应选择自描述或带 schema 版本的格式。

## 10. 连接管理与生命周期

### 10.1 连接池要解决什么问题？

- 建立一条 TCP 连接至少需要一次往返，启用 TLS 后还要再增加往返与证书验证的开销。
- 连接池把已建立的连接保留下来复用，省去重复握手，也避免内核频繁分配与回收连接结构。
- 池的上限由下游最大连接数、单机 fd 上限与每连接内存共同决定，不能只按 QPS 估算。
- 需要区分最小空闲连接、最大连接数、最大空闲时间与最大生存时间，四者的作用并不相同。
- 取用超时必须有明确上限，否则下游故障时请求线程会全部堆积在等待队列中。
- 池内连接上限与后端连接上限不一致时会出现排队，指标上表现为获取等待时间上升。

### 10.2（实现）连接池取出连接时如何判断可用？

```cpp
bool healthy(int fd) {
    char c;
    int n = ::recv(fd, &c, 1, MSG_PEEK | MSG_DONTWAIT);
    if (n == 0) return false;                  // 收到 FIN
    if (n < 0 && errno == ECONNRESET) return false;
    if (n < 0 && errno != EAGAIN) return false;
    return true;
}
```

- `MSG_PEEK` 只读取不消费，不会取走业务数据，`MSG_DONTWAIT` 保证不阻塞。
- 返回 0 表示对端已发送 FIN，返回 `ECONNRESET` 表示连接已被重置。
- `EAGAIN` 表示当前没有数据可读，属于健康连接的正常状态。
- 该检查只能发现读方向的关闭，对端进程卡死或 NAT 映射失效时仍会返回健康。
- 更完整的做法是记录每条连接的最后使用时间，超过空闲阈值就不再复用。
- 取出后还应重置该连接的状态字段，避免把上一次请求的残留数据带到下一次。

### 10.3（陷阱）池中空闲连接被对端关闭后，首次写入为什么常常成功？

- FIN 只表示对端不再发送数据，本端仍可发送，因此第一次 `send` 会进入发送缓冲区并返回成功。
- 对端进程已退出且端口无接收者时，内核会回应 RST；RST 到达后，下一次 `send` 返回 `EPIPE`。
- 若 RST 在 `send` 之前已经到达，第一次 `send` 直接返回 `ECONNRESET`。
- 已排队但未被确认的数据在 RST 到达后被丢弃，应用看到的是写成功而数据丢失。
- 默认 `SIGPIPE` 会终止进程，服务端应忽略该信号或在发送时使用 `MSG_NOSIGNAL`。
- 因此健康检查要覆盖读方向，并配合应用层心跳，不能只依赖写操作的返回值。

### 10.4 应用层心跳与 TCP keepalive 如何取舍？

- `SO_KEEPALIVE` 只在本端长时间无数据收发时触发，探测报文对应用不可见，也不携带业务语义。
- keepalive 的默认空闲时间为 7200 秒，远大于常见中间设备的会话老化时间。
- keepalive 只能发现链路中断或对端主机失效，无法发现对端进程卡死但内核仍回 ACK 的情况。
- 应用层心跳可以穿过代理与负载均衡，检测端到端可用性，并可携带序号与时间戳。
- 心跳应由单侧主导发送，双方同时探测会增加无谓流量与误判概率。
- 心跳报文要小，与业务报文共用连接时仍需考虑发送队列的排队顺序。

### 10.5 TCP keepalive 的参数与生效条件是什么？

- `SO_KEEPALIVE` 置 1 后才启用；`TCP_KEEPIDLE` 控制空闲多久发送第一个探测，默认 7200 秒。
- `TCP_KEEPINTVL` 为探测间隔，默认 75 秒；`TCP_KEEPCNT` 为失败次数上限，默认 9。
- 全部探测都没有响应时，内核把连接错误置为 `ETIMEDOUT`，阻塞中的读写返回该错误。
- 探测报文是携带一个无效字节的段，序列号为当前待发送序号减一，对端应回复 ACK。
- 连接处于 `ESTABLISHED` 或 `CLOSE_WAIT` 时才发送探测，其他状态不探测。
- 参数按 socket 设置，只影响该连接；全局默认值位于 `/proc/sys/net/ipv4/tcp_keepalive_*`。
- 探测失败后连接被关闭，发送队列中的数据被丢弃，应用只能感知到错误。

### 10.6 心跳周期与判定超时如何设置？

- 心跳周期应小于链路上最短的会话老化时间，包括 NAT、防火墙与负载均衡的空闲超时。
- 判定超时通常取三倍心跳周期，兼顾误判概率与故障发现速度。
- 周期过短会放大唤醒次数与流量，长连接数量大时 CPU 开销可观。
- 超时过短会因偶发丢包或对端停顿而误判，触发不必要的重连。
- 心跳超时要与重连退避配合，避免大量连接在同一时刻集中重连。
- 计算间隔使用单调时钟，避免系统时间调整导致超时判断出错。
- 应答携带序号或时间戳，可用于区分链路缓慢与对端不处理请求。

### 10.7（场景）NAT 映射老化后连接静默失效，抓包有什么特征？

- 两端连接仍显示 `ESTABLISHED`，本端发送的数据没有 ACK，重传若干次后才报错。
- 抓包可见本端持续重传同一段，对端没有任何响应，也没有 RST，因为中间设备已丢弃映射。
- 中间设备若只清空状态而保留表项，可能出现单方向可用、反方向失效。
- 服务端若把同一映射分给其他会话，旧连接的数据可能收到 RST。
- 排查手段是对比两端 `ss -tin` 的发送队列与重传计数，以及中间设备的会话老化配置。
- 缓解方式是让心跳周期小于老化时间，或由长连接代理维持映射。
- 恢复只能依靠重连，客户端应把无响应超时视为连接失效，而不是暂时拥塞。

### 10.8 shutdown(SHUT_WR) 之后还能读吗？

- `shutdown(fd, SHUT_WR)` 发送 FIN，本端进入 `FIN_WAIT_1`，仍可继续调用 `recv`。
- 对端读到 EOF（`recv` 返回 0）后仍可向本端发送数据，这是半关闭的典型用法。
- `SHUT_RD` 关闭读方向，后续 `recv` 返回 0，但不会向对端发送任何报文。
- `SHUT_RDWR` 同时关闭两个方向，效果接近 `close`，但不释放描述符。
- 半关闭适合请求发完即等待响应的协议，对端可据此判断请求结束。
- `shutdown` 作用于 socket 本身，`dup` 或 `fork` 得到的副本会一起受影响。
- 若对端不按半关闭语义实现，收到 FIN 后可能直接关闭连接，导致响应丢失。

### 10.9（辨析）close 与 shutdown 的差别是什么？

- `close` 减少描述符引用计数，计数归零时才发送 FIN 并释放连接。
- `shutdown` 立即改变连接状态，不等待引用计数，也不释放描述符。
- `close` 无法只关闭一个方向，`shutdown` 可以按方向关闭。
- 多线程共享同一 socket 时，一个线程 `close` 后其他线程的读写会失败，甚至访问已释放对象。
- `fork` 后父子进程共享 socket，双方都 `close` 才会真正发送 FIN。
- 需要发完请求继续读响应的场景必须使用 `shutdown`，不能用 `close` 代替。
- `shutdown` 不会唤醒阻塞在 `accept` 上的线程，关闭监听 fd 才有效。

### 10.10（陷阱）SO_LINGER 置 0 会发生什么？

- `l_onoff` 非 0 且 `l_linger` 为 0 时，`close` 丢弃发送缓冲区中的数据并直接发送 RST。
- RST 使对端立即收到错误，未读数据被丢弃，应用层看到 `ECONNRESET`。
- 该行为可以快速释放连接、避免进入 `TIME_WAIT`，但破坏可靠传输语义。
- RST 也可能让中间设备提前清理会话，影响同一 NAT 映射上的其他连接。
- `l_linger` 大于 0 时，`close` 阻塞直到数据发送完毕或超时，超时后仍可能丢弃数据。
- 阻塞期间若持有锁或在事件循环中调用，会造成明显的尾延迟。
- 默认 `l_onoff` 为 0，`close` 立即返回，由内核在后台完成发送与关闭。

### 10.11（场景）服务器出现大量 CLOSE_WAIT 如何定位？

- `CLOSE_WAIT` 表示对端已发 FIN，本端内核已回 ACK，但应用尚未调用 `close`。
- 大量堆积说明应用没有走关闭路径，常见原因是异常分支缺少关闭、回调未执行、线程卡死。
- 用 `ss -tan state close-wait` 统计数量，用 `ss -tanp` 关联进程与描述符。
- 结合 `lsof -p` 确认描述符由哪个对象持有，检查是否存在循环引用或未重置的智能指针。
- 每个未释放的 socket 仍持有读写缓冲区，堆积会同时推高内存与 fd 使用量。
- 连接池或框架把 socket 交给上层后未归还，也会表现为该状态。
- 内核不会自动回收 `CLOSE_WAIT`，等待 `tcp_fin_timeout` 无效，只能由应用关闭。

### 10.12 优雅关闭需要哪些步骤？

- 先从负载均衡或服务发现中摘除，停止接收新请求，再开始关闭。
- 停止 `accept` 并关闭监听 fd，让后续握手无法完成。
- 对已建立连接发送关闭通知，或调用 `shutdown(SHUT_WR)` 表示不再发送新响应。
- 等待在途请求处理完成，设置总期限，超过期限后强制关闭。
- 收敛线程池与事件循环，处理队列中剩余任务，再释放资源。
- 摘除到停止之间的间隔要覆盖健康检查周期与连接排空时间。
- 未做优雅关闭时，重启表现为客户端大量 `ECONNRESET` 与 5xx 响应。

### 10.13（实现）如何实现带期限的优雅关闭？

```cpp
void graceful_stop(int listen_fd, std::vector<int>& conns,
                   std::chrono::steady_clock::time_point deadline) {
    ::close(listen_fd);                        // 停止接收新连接
    for (int fd : conns) ::shutdown(fd, SHUT_WR);
    while (!conns.empty() &&
           std::chrono::steady_clock::now() < deadline) {
        poll_once(conns);                      // 继续处理剩余响应
    }
    for (int fd : conns) ::close(fd);          // 超时后强制关闭
}
```

- 关闭监听 fd 要早于关闭连接，否则新连接会被接受后立刻失败，客户端看到的是 RST。
- `SHUT_WR` 让对端读到 EOF，同时保留读方向以接收未完成的响应。
- 期限用单调时钟计算，避免系统时间调整影响排空时长。
- `poll_once` 中要把已完成的连接从集合移除，否则循环会一直等到期限。
- 强制关闭前可保留默认的 `SO_LINGER`，让内核继续发送剩余数据。
- 多进程模型中，每个工作进程都要收到停止通知，不能只停主进程。

### 10.14 TIME_WAIT 为什么占用四元组，回收有哪些手段？

- `TIME_WAIT` 持续 2MSL，期间该四元组不能被同方向的新连接复用。
- 目的是让迟到的重复段在网络中消亡，并在最后的 ACK 丢失时能够重发 FIN。
- 主动关闭方进入该状态，服务端主动关闭大量短连接时压力落在服务端。
- 回收思路分两类：减少进入该状态的连接数（长连接、由客户端关闭），或允许四元组被复用。
- `net.ipv4.tcp_tw_reuse` 允许在时间戳开启时复用处于 `TIME_WAIT` 的四元组发起新连接。
- `SO_REUSEADDR` 允许绑定处于 `TIME_WAIT` 的本地地址，主要用于服务重启。
- `tcp_tw_recycle` 已在 Linux 4.12 中移除，不应再作为方案。
- 缩短 `tcp_fin_timeout` 只影响 `FIN_WAIT_2`，不会改变 `TIME_WAIT` 的 2MSL。

### 10.15（辨析）SO_REUSEADDR 与 SO_REUSEPORT 的区别是什么？

- `SO_REUSEADDR` 允许 `bind` 到处于 `TIME_WAIT` 的地址端口，也允许通配地址与具体地址并存。
- 对完全相同的地址端口，该选项不允许多个 socket 同时处于监听状态。
- `SO_REUSEPORT` 允许多个 socket 绑定同一地址端口，内核按四元组哈希把新连接分给其中一个。
- 所有绑定者需要相同的有效用户，且都必须在 `bind` 之前设置该选项。
- `SO_REUSEPORT` 常用于多进程各自持有监听 socket，减少 `accept` 竞争。
- 哈希分流在连接数少时可能不均衡，某个进程退出会重置其上的连接。
- `SO_REUSEADDR` 用于重启时避免地址占用错误，`SO_REUSEPORT` 用于并行监听。

### 10.16 tcp_tw_reuse 的生效条件与风险是什么？

- 仅对主动发起连接的 socket 生效，被动接受连接的端口不受影响。
- 需要开启 `net.ipv4.tcp_timestamps`，否则该选项不产生作用。
- 复用要求新连接的时间戳大于此前连接的最新时间戳，以满足 PAWS 检查。
- 复用后旧连接的迟到段可能被当作新连接的数据，这是语义层面的风险。
- 该选项不能解决服务端主动关闭短连接造成的堆积，服务端应改用长连接或由客户端关闭。
- 与已被移除的 `tcp_tw_recycle` 不同，它不依赖全局时间戳递增，在 NAT 环境下相对安全。
- 观测手段是 `ss -s` 的 `timewait` 计数与 `ss -tan` 的状态分布。

### 10.17（场景）客户端出现端口耗尽有什么现象？

- `connect` 返回 -1，`errno` 为 `EADDRNOTAVAIL`，日志常见 `Cannot assign requested address`。
- `ss -s` 显示大量 `TIME_WAIT`，本地端口范围被占满。
- 端口范围由 `net.ipv4.ip_local_port_range` 决定，默认约 2.8 万个。
- 每个目的地址与端口组合都可独立使用全部本地端口，目标单一的服务更容易耗尽。
- 缓解方式是使用连接池与长连接、让服务端主动关闭、增加本地源地址、扩大端口范围。
- 短连接压测时该问题最先暴露，表现为 QPS 上升到某点后连接失败率陡增。
- 该状态的时长固定为 2MSL，无法通过参数缩短，只能改变关闭方或复用四元组。

### 10.18 connect 超时为什么不能靠 SO_SNDTIMEO？

- 阻塞模式下 `connect` 的返回时间由内核的 SYN 重传决定，不受 `SO_SNDTIMEO` 控制。
- 默认 SYN 重传 6 次，总时长约 127 秒，远超多数服务的容忍范围。
- `TCP_SYNCNT` 可以减少 SYN 重传次数，但粒度粗，仍需等待内核定时。
- 通用做法是把 socket 设为非阻塞，`connect` 返回 `EINPROGRESS` 后交给事件循环。
- 等待可写之后必须用 `getsockopt(SO_ERROR)` 读取结果，不能仅凭可写判断成功。
- 超时后要关闭该描述符，避免内核继续重传并占用端口。
- 连接超时与读写超时要分开设置，二者的失败语义不同。

### 10.19（实现）非阻塞 connect 如何判定成功与超时？

```cpp
int connect_timeout(int fd, const sockaddr* sa, socklen_t len, int ms) {
    int flags = ::fcntl(fd, F_GETFL, 0);
    ::fcntl(fd, F_SETFL, flags | O_NONBLOCK);
    if (::connect(fd, sa, len) == 0) return 0;
    if (errno != EINPROGRESS) return -1;
    pollfd p{fd, POLLOUT, 0};
    if (::poll(&p, 1, ms) <= 0) { errno = ETIMEDOUT; return -1; }
    int err = 0; socklen_t n = sizeof(err);
    if (::getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &n) < 0) return -1;
    if (err != 0) { errno = err; return -1; }
    return 0;
}
```

- `EINPROGRESS` 表示握手已发起，此时不能把返回值当作失败。
- `poll` 返回 0 表示超时，返回 -1 要区分 `EINTR` 后重试。
- 可写只说明有了结果，成功与失败都要通过 `SO_ERROR` 确认。
- 成功后恢复原来的文件状态标志，否则后续读写会意外非阻塞。
- 超时后关闭描述符，让内核停止重传，避免资源被长时间占用。
- `poll` 也可能在 `revents` 中报告错误，但仍以 `SO_ERROR` 的值为准。

### 10.20 监听队列满时内核如何处理新连接？

- `listen` 的 `backlog` 会被 `net.core.somaxconn` 截断，实际长度取两者较小值。
- 内核维护 SYN 队列与 accept 队列，前者存半连接，后者存已完成三次握手的连接。
- SYN 队列满时新 SYN 被丢弃，客户端重传，表现为握手延迟上升。
- accept 队列满时默认忽略新到达的 ACK，客户端会重传；`tcp_abort_on_overflow` 置 1 则回 RST。
- 应用 `accept` 不及时是队列溢出的主因，需检查事件循环是否被慢操作阻塞。
- `netstat -s` 中的 `listen overflows` 与 `listen drops` 计数可直接确认溢出。
- `tcp_syncookies` 在队列满时启用，可缓解 SYN 泛洪，但会丢失部分连接选项。

## 11. 高并发服务器模型

### 11.1（辨析）多进程与多线程服务器模型如何取舍？

- 多进程有独立的地址空间，单个进程崩溃不会影响其他进程；多线程共享地址空间，越界写会破坏整个进程。
- 线程切换只切换栈与寄存器，进程切换还要切换页表，后者的开销更大。
- 多进程共享监听 fd 简单，但共享连接状态与缓存需要共享内存或进程间通信。
- 多线程的主要复杂度在于锁与竞态，还需处理伪共享与缓存一致性流量。
- 进程数多时内核结构、页表与 TLB 压力上升，线程数多时调度与栈内存成为约束。
- 常见做法是少量进程各含多个线程，按 CPU 核数划分工作线程。
- 选择依据是故障隔离要求、状态共享程度与运维习惯，不能只看单一性能指标。

### 11.2 prefork 模型中多个子进程如何共享监听 socket？

- 父进程完成 `socket`、`bind`、`listen` 后 `fork`，子进程继承监听 fd，共享同一内核 socket 对象。
- 所有子进程在同一 socket 上调用 `accept`，内核选择一个等待者处理新连接。
- Linux 的等待队列使用互斥唤醒标志，同一时刻只有一个等待者被唤醒，`accept` 惊群已大幅缓解。
- 各子进程独立处理连接，连接状态不共享，需要会话保持时依赖外部存储。
- 子进程退出后由父进程重新 `fork`，并通过 `SIGCHLD` 回收僵尸进程。
- 监听 fd 的引用计数由所有子进程共享，任一进程 `close` 不影响其他进程。

### 11.3（场景）accept 返回 EMFILE 时会发生什么？

- `accept` 返回 -1，`errno` 为 `EMFILE`（进程描述符用尽）或 `ENFILE`（系统描述符用尽）。
- 监听 fd 仍处于可读状态，水平触发的事件循环会反复报告，形成忙循环占满 CPU。
- 一种处理是预留一个空闲描述符，遇到 `EMFILE` 时关闭它、`accept` 新连接并立即关闭，再重新打开预留项。
- 另一种处理是暂时从 `epoll` 中摘除监听 fd，等描述符释放后重新注册。
- 根本手段是限制最大连接数、提高 `RLIMIT_NOFILE`、排查描述符泄漏。
- 使用边缘触发时若不 `accept` 到 `EAGAIN`，新连接会滞留在队列中直到下次事件。
- 监控应同时观察 `EMFILE` 计数与描述符使用率，避免只看到连接数下降。

### 11.4 线程池的队列与拒绝策略如何设计？

- 有界队列能限制内存与排队延迟，无界队列在过载时会把延迟推到不可控。
- 拒绝策略可以是阻塞调用方、直接失败、丢弃最旧任务或交给调用线程执行。
- 网络服务通常选择快速失败并返回错误，避免请求在队列中过期后才被处理。
- 常驻线程数与最大线程数的组合决定扩容时机，空闲超时决定收缩。
- 任务粒度要小且不含阻塞调用，否则增加线程数也无法提高吞吐。
- 队列本身是竞争点，高并发下需要无锁队列或分片队列降低争用。
- 线程池耗尽时应暴露队列长度、拒绝数与执行时间分位，而不是静默排队。

### 11.5（实现）线程池的工作线程如何编写？

```cpp
void worker() {
    for (;;) {
        std::function<void()> job;
        {
            std::unique_lock<std::mutex> lk(m_);
            cv_.wait(lk, [this] { return stop_ || !q_.empty(); });
            if (stop_ && q_.empty()) return;
            job = std::move(q_.front());
            q_.pop();
        }
        job();                              // 队列锁已释放
    }
}
```

- 条件变量的等待必须带谓词，被唤醒后重新检查停止标志与队列状态。
- 取出任务后立即释放锁，任务执行期间不持有队列锁。
- `submit` 中入队后调用 `notify_one`，唤醒一个等待者即可。
- 任务抛出的异常若逃出 `job()` 会终止进程，需要在任务外层捕获。
- 停止时先置停止标志再唤醒全部线程，线程取空队列后退出。
- 队列有界时入队可能阻塞，阻塞策略要与拒绝策略一并设计。

### 11.6 one loop per thread 的线程模型是什么？

- 每个 IO 线程持有独立的 `epoll` 实例与事件循环，连接在建立时固定归属某个线程。
- 同一连接的所有读写都在归属线程执行，操作单条连接时无需加锁。
- 线程之间只通过任务队列与唤醒机制通信，不在其他线程直接操作连接。
- 连接数与线程数解耦，线程数通常取 CPU 核数，连接数可达数万。
- 单个连接的慢处理会阻塞该线程上的其他连接，回调中不能有阻塞调用。
- 归属关系稳定后缓存的局部性更好，配合 CPU 亲和可进一步减少迁移。
- 关闭连接也要回到归属线程执行，跨线程关闭会产生竞态。

### 11.7 每连接一线程模型的代价是什么？

- 每个线程默认栈为 8 MiB 虚拟地址空间，数千连接即消耗数十 GiB。
- 线程创建与销毁需要内核分配结构，频繁短连接会带来明显开销。
- 线程数远超核数时，时间片轮转与上下文切换成为主要成本。
- 阻塞读的线程在无数据时仍占用调度实体，等于用内存换取编程简单。
- 连接活跃度差异大时，大量空闲线程占用内存却不贡献吞吐。
- 该模型在连接数数百以内、逻辑以阻塞调用为主的场景仍可用。
- 超过该规模后需要事件驱动或协程，否则调度开销会吞掉收益。

### 11.8 主从 Reactor 中 acceptor 线程与 IO 线程如何分工？

- 主线程只负责监听 fd 与 `accept`，把新连接按轮询或最少负载分给 IO 线程。
- 每个 IO 线程有独立 `epoll`，注册自己负责的连接，处理读写与业务回调。
- 分配时把连接 fd 通过任务队列投递给目标线程，由目标线程注册，避免多线程同时操作同一 `epoll`。
- acceptor 线程不做业务处理，防止 `accept` 被慢操作拖住导致队列溢出。
- 连接数不均衡时按线程当前连接数分配，比固定轮询更稳。
- 线程间投递需要唤醒机制，通常用 `eventfd`，避免目标线程长时间睡眠。
- 关闭流程要通知所有 IO 线程停止接受新任务，再逐个排空。

### 11.9 惊群在 accept 与 epoll 上的表现有何不同？

- `accept` 惊群指多个进程阻塞在同一监听 socket 上，新连接到达时全部被唤醒，只有一个成功。
- Linux 的等待队列使用互斥唤醒，`accept` 惊群在内核层面已基本消除。
- `epoll` 惊群指多个执行体等待同一事件源，事件到达时全部被唤醒，多数随后发现无事可做。
- `EPOLLEXCLUSIVE` 在注册时使用，多个 `epoll` 实例等待同一目标 fd 时只唤醒其中一个实例。
- 同一 `epoll` 实例被多个线程 `epoll_wait` 时该选项不生效，仍会唤醒全部线程，这种用法本身应避免。
- 多个线程各自持有 `epoll` 并监听同一端口时，需要 `SO_REUSEPORT` 或应用层分发。
- 惊群的表现是 CPU 空转与上下文切换上升而 QPS 不增，可用 `pidstat -w` 确认。

### 11.10（场景）SO_REUSEPORT 的负载为什么可能不均衡？

- 内核按四元组哈希选择监听 socket，短连接分布较均匀，来源集中的长连接可能倾斜。
- 客户端源地址与源端口集中时哈希空间被压缩，部分进程分到更多连接。
- 进程重启后哈希重新计算，已有连接留在原进程，新连接可能集中到存活进程。
- 各进程连接数不等会导致 CPU 与内存使用不均，尾延迟被最忙的进程拉高。
- 缓解方式是应用层再分发、按中断核绑定 `SO_INCOMING_CPU`，或用 `SO_ATTACH_REUSEPORT_EBPF` 自定义分流。
- 监控要按进程观察连接数与事件循环延迟，而不是只看整体 QPS。
- 该选项不保证公平，只保证分配到某个 socket 的连接由该 socket 独占处理。

### 11.11 负载均衡的常见策略与代价是什么？

- 轮询实现简单、分布均匀，但不感知后端负载，慢节点会持续收到请求。
- 最少连接数按当前在途请求分配，能缓解慢节点，但需要维护共享计数。
- 加权策略按容量分配，权重需要随实例规格调整。
- 一致性哈希把同一键固定到同一后端，适合缓存亲和，扩缩容时会迁移部分键。
- 随机策略在实例较多时接近均匀，实现无状态，适合后端无共享状态的服务。
- 四层均衡按连接分配，七层均衡可按请求分配，后者对短请求更均匀。
- 任何策略都需要健康检查与摘除，否则失败节点仍会分到流量。

### 11.12 四层与七层负载均衡的差别是什么？

- 四层工作在传输层，按地址与端口转发，不解析应用协议，开销低、吞吐高。
- 七层解析 HTTP 等协议，可按路径、头部、Cookie 路由，并支持改写与限流。
- 四层保持 TCP 连接语义，适合长连接与任意协议；七层通常终结连接再向后端新建连接。
- 四层可用直接路由或隧道模式让响应绕过均衡器，七层必须经过代理。
- 七层能做 TLS 终止与证书管理，四层只能透传或按 SNI 分流。
- 七层的代价是额外一次连接建立、缓冲区与解析开销，尾延迟更高。
- 选择依据是是否需要按内容路由，以及能否接受代理带来的额外一跳。

### 11.13 为什么需要会话保持？

- 后端把会话状态存在本地内存时，同一用户的请求必须落到同一实例。
- 会话保持可用源地址哈希、Cookie 注入或一致性哈希实现，各有失效场景。
- 源地址哈希在 NAT 后大量用户共享出口时会失衡。
- Cookie 注入依赖七层解析，客户端禁用 Cookie 时失效。
- 更彻底的做法是把会话外置到共享存储，使后端无状态，均衡器可自由调度。
- 实例故障时会话丢失，保持策略越强，故障影响越集中。
- 扩缩容时保持策略会阻碍流量重新分布，需要设置过期时间。

### 11.14（实现）如何限制单机并发连接数？

```cpp
bool try_acquire(std::atomic<int>& cur, int limit) {
    int v = cur.load(std::memory_order_relaxed);
    while (v < limit) {
        if (cur.compare_exchange_weak(v, v + 1,
                std::memory_order_acq_rel))
            return true;
    }
    return false;
}
```

- 超过上限时立即关闭新连接并记录指标，不要静默排队等待。
- 上限要低于 `RLIMIT_NOFILE`，并为日志、监听等用途留出余量。
- 计数还要按每连接缓冲区折算内存，避免连接数达标而内存先耗尽。
- 连接数只能在 `accept` 之后判断，此时握手已完成，拒绝的代价是一次 RST。
- 释放路径要用 RAII 保证归还，异常分支遗漏会让计数只增不减。
- 多实例部署时单机计数无法反映全局负载，需要集中式限流配合。

### 11.15 CPU 亲和与 NUMA 对网络服务有什么影响？

- 连接处理线程与网卡中断不在同一核时，数据要跨核传递，缓存命中率下降。
- `SO_INCOMING_CPU` 可读取连接所属的中断 CPU，用于把连接分配给同核线程。
- `sched_setaffinity` 把线程绑定到固定核，减少迁移与缓存失效。
- 多路 CPU 的 NUMA 架构下跨节点访存延迟明显上升，网卡与内存应尽量同节点。
- 网卡多队列的中断可以绑定到不同核，配合每核一个监听 socket 让处理尽量留在同一核。
- 绑核过度会降低弹性，某核繁忙时无法借用其他核，需要留出余量。
- 观测手段是 `mpstat -P ALL` 的分布与 `perf` 的跨核缓存事件。

### 11.16（场景）CPU 使用率不高但吞吐上不去，可能是什么原因？

- 线程在锁上排队，CPU 处于等待状态，表现为利用率低而延迟高。
- 事件循环被阻塞调用占用，包括域名解析、磁盘读写与同步日志。
- 队列长度上涨而消费者不足，任务在等待调度。
- 连接集中在少数线程，其他线程空闲，负载不均。
- 内核侧存在丢包或重传，有效吞吐被协议行为限制。
- 观测应同时看运行队列、上下文切换、锁竞争与重传计数。
- 优化方向是缩小临界区、把阻塞操作移出 IO 线程、按连接分片。

### 11.17 跨线程投递任务如何唤醒事件循环？

- 目标线程阻塞在 `epoll_wait`，其他线程放入任务后需要让它返回。
- 常用做法是创建 `eventfd` 并注册到目标 `epoll`，投递时写入 8 字节计数。
- 目标线程被唤醒后先读走计数，再一次性取空任务队列，避免逐条唤醒。
- `eventfd` 设为非阻塞并带 `EFD_CLOEXEC`，读取时处理 `EAGAIN`。
- 也可以用管道或 `socketpair`，但会占用两个描述符并多一次数据复制。
- 投递与注册存在竞态：注册完成前的任务要留在队列中，由注册后的首次唤醒兜底。
- 批量投递配合一次唤醒，能显著减少系统调用次数。

### 11.18（陷阱）在 IO 线程中做阻塞操作会怎样？

- 单线程事件循环被阻塞期间，该线程上所有连接都无法读写，延迟按阻塞时长累加。
- 域名解析可能因超时阻塞数秒，应放到独立线程池或改用异步解析接口。
- 同步写日志在磁盘抖动时会阻塞，日志应异步化并设置队列上限。
- 大文件读写、`fsync`、同步数据库调用同理会拖住整个线程。
- 线程数与核数相同时，阻塞会让该核空转等待，整体利用率下降。
- 检测手段是事件循环单次耗时直方图与延迟分位指标。
- 修复方式是把阻塞操作交给专用线程池，结果再投递回 IO 线程。

### 11.19 服务退出时线程池如何收敛？

- 先停止接受新任务，把状态置为停止中，后续提交直接拒绝。
- 通知所有工作线程，唤醒阻塞在条件变量上的线程。
- 等待队列中的任务执行完毕，或按期限丢弃并记录数量。
- 调用 `join` 前必须确保没有线程还在投递任务，否则会访问已析构对象。
- 退出顺序是先停 IO 线程、再停业务线程池，避免回调找不到执行者。
- 强杀进程会丢失队列中的任务，需要与上游的重试策略配合。
- 停止标志与条件变量的组合要避免丢失唤醒，置标志与通知应在同一把锁的保护下完成。

### 11.20 热重启时如何不中断已有连接？

- 新进程启动后通过 `SO_REUSEPORT` 绑定同一端口，与旧进程共同接受新连接。
- 旧进程停止 `accept`，等待已有连接处理完毕后退出，新连接由内核分给新进程。
- 也可以由旧进程把监听 fd 通过 `SCM_RIGHTS` 传给新进程，新进程继承同一个 socket。
- `SCM_RIGHTS` 传递的是描述符引用，两个进程共享同一内核 socket，`accept` 仍会竞争。
- 平滑重启要求连接状态可重建或已外置，否则旧连接上的会话在新进程中不可见。
- 二进制升级需要保证新旧版本协议兼容，滚动期间两种版本会同时在线。
- 退出前要给旧进程足够的排空时间，并监控其残留连接数。

## 12. 零复制与内核旁路

### 12.1 零复制中的「复制」指什么？

- 指内核缓冲区与用户态缓冲区之间的 CPU 复制，以及由此产生的上下文切换。
- 服务器发送响应的常见路径是先读入用户态缓冲区再写入 socket，数据因此被搬运四次。
- 零复制让数据留在页缓存中或直接由网卡 DMA 读取，CPU 只处理描述符与元数据。
- 网络路径上的相关接口包括 `sendfile`、`splice`、`MSG_ZEROCOPY` 与内核 TLS 发送。
- 减少复制同时降低了缓存占用与内存带宽压力，在高带宽场景收益明显。
- 具体复制次数由实现、网卡能力与卸载配置决定，不能一概而论。

### 12.2 sendfile 如何减少发送路径上的复制？

- `sendfile(out_fd, in_fd, offset, count)` 一次调用完成文件页到 socket 的搬运。
- 文件页由 DMA 读入页缓存，内核把页挂到 socket 发送队列的片段上。
- 网卡通过 DMA 直接从页缓存读取数据，CPU 不参与内容搬运。
- 相比读文件再写入，省去了用户态缓冲区与两次上下文切换。
- 支持分散聚集的网卡可以跨页收集数据，无需先拼成连续缓冲区。
- `in_fd` 必须是支持 `mmap` 的文件，`out_fd` 在 Linux 上必须是 socket。
- 不经过用户态意味着无法在发送前压缩、加密或改写内容。

### 12.3（辨析）sendfile 与 read/write 循环的差别是什么？

- `read` 与 `write` 需要应用缓冲区，数据在用户态与内核态之间各复制一次。
- `sendfile` 不经过用户态，应用既无法检查内容，也无法在发送前改写。
- 需要压缩、加密或改写响应体时不能用 `sendfile`，除非把处理下沉到内核。
- `sendfile` 的返回值为已发送字节数，可能小于请求长度，需要循环调用。
- `sendfile` 不分配用户态大缓冲区，减少了内存占用与复制带来的缓存污染。
- 响应头与正文可以用 `writev` 合并发送，减少系统调用次数。
- 小响应场景下两者差距不大，页缓存命中与调用次数的影响更明显。

### 12.4 mmap 加 write 在发送路径上为什么仍有一次复制？

- `mmap` 把文件页映射到用户地址空间，省去了内核到用户的一次复制。
- 写入 socket 时仍需把映射区的内容复制到发送缓冲区，这一次复制无法省去。
- 适合需要先检查或改写内容再发送的场景，例如在文件中替换占位符。
- 冷缓存时的缺页处理会带来额外延迟，随机访问小片段时可能慢于顺序读取。
- 文件被并发截断时访问映射区会触发 `SIGBUS`，需要处理或避免并发截断。
- 长时间持有映射会阻止页回收，发送完成后应及时解除映射。
- 与 `sendfile` 相比多一次复制，但保留了对数据的访问能力。

### 12.5 splice 在代理转发中如何工作？

- `splice` 在两个文件描述符之间移动数据，其中一端必须是管道。
- 数据以页引用的形式在管道缓冲区中传递，不复制内容。
- 代理转发用两个 `splice` 加一个管道即可完成，全程不经过用户态缓冲区。
- 适合不解析内容的正向代理与 TLS 透传，配合非阻塞描述符使用。
- 管道容量有限，默认约 64 KiB，单次搬运量受其限制，需要循环处理。
- `SPLICE_F_MOVE` 提示内核尝试移动页而不是复制，是否生效由实现决定。
- 返回 `EAGAIN` 表示对应方向暂不可用，未搬完的数据留在管道中等待。

### 12.6（陷阱）sendfile 的常见失败原因有哪些？

- `out_fd` 不是 socket 时返回 `EINVAL`，管道与其他文件类型不被接受。
- `in_fd` 不支持 `mmap` 时返回 `EINVAL`，部分特殊文件属于这种情况。
- 非阻塞 socket 的发送缓冲区已满时返回 `EAGAIN`，需要注册可写事件后重试。
- `offset` 为空指针时使用并推进文件偏移，多线程共享同一描述符会互相干扰。
- 文件在发送过程中被截断，返回字节数小于请求值，剩余部分不应继续发送。
- 部分文件系统或内核配置下 `sendfile` 退化为内部复制，性能收益下降。
- 错误处理要与普通 `write` 一致，不能假设一次调用发送完毕。

### 12.7 MSG_ZEROCOPY 的语义与代价是什么？

- `send` 带 `MSG_ZEROCOPY` 时内核引用用户页，省去复制到发送缓冲区这一步。
- 适用于大块发送，小于一页的报文会退回普通路径，收益可能为负。
- 缓冲区在收到完成通知前不能被修改或释放，需要池化与引用计数管理。
- 完成通知通过 socket 错误队列返回，用 `recvmsg` 配合 `MSG_ERRQUEUE` 读取。
- 未完成的引用计入发送内存配额，队列过长会阻塞后续发送。
- 需要内核 4.14 及以上，且并非所有协议与驱动都支持。
- 该机制不减少 DMA 复制，只消除内核内部的 CPU 复制。

### 12.8（实现）如何用 sendfile 发送一个文件？

```cpp
int send_file(int out_fd, int in_fd, off_t& off, off_t size) {
    while (size > 0) {
        ssize_t n = ::sendfile(out_fd, in_fd, &off, size);
        if (n > 0) { size -= n; continue; }
        if (n == 0) return -1;
        if (errno == EINTR) continue;
        if (errno == EAGAIN) return 1;   // 等待可写后从 off 续传
        return -1;
    }
    return 0;
}
```

- 返回值区分成功、需要等待与失败，调用方据此注册可写事件或关闭连接。
- `off` 由调用方持有并在每次成功后被内核更新，重试时从该位置续传。
- `EINTR` 只表示调用被打断，继续循环即可，不计入失败。
- 返回 0 表示没有进展，重试会形成忙循环，应按错误处理。
- 阻塞描述符上该调用会一直等待，可能拖住整个事件循环。
- 发送前用 `fstat` 取得大小，但文件可能被并发修改，发送总量以实际返回字节数为准。

### 12.9 io_uring 的提交与完成模型是什么？

- 用户态与内核共享两个环形队列，分别是提交队列与完成队列。
- 应用把请求描述符写入提交队列，更新尾指针，再通过 `io_uring_enter` 通知内核。
- 内核异步执行后把结果写入完成队列，应用读取后推进头指针。
- 多个请求可以一次提交，系统调用次数与请求数解耦。
- 支持 `IORING_OP_ACCEPT`、`IORING_OP_RECV`、`IORING_OP_SEND` 等网络操作。
- 部分版本支持多-shot 接收与预注册缓冲区，可进一步减少重复提交。
- 指针推进顺序与内存屏障必须遵循接口的内存模型，否则会丢失事件。

### 12.10 SQPOLL 模式省掉了什么？

- `IORING_SETUP_SQPOLL` 让内核创建轮询线程，持续检查提交队列的尾指针。
- 应用提交请求时不再需要 `io_uring_enter`，省去一次系统调用。
- 轮询线程占用一个 CPU 核，空闲时也持续运行，适合高负载场景。
- 需要设置轮询线程的空闲时间，使其在长时间无请求后休眠，否则功耗上升。
- 早期内核要求 `CAP_SYS_ADMIN`，后续版本允许通过注册限制放开。
- 与中断驱动的完成方式相比，该模式延迟更稳定但资源占用更高。
- 容器中受安全策略与权限限制，可能无法启用。

### 12.11（场景）io_uring 在容器中为什么可能不可用？

- Docker 默认的 seccomp 配置在较旧版本中会拒绝 `io_uring_setup` 等系统调用，返回 `EPERM`。
- SQPOLL 模式需要额外权限，受限容器中会被拒绝。
- 注册缓冲区受 `RLIMIT_MEMLOCK` 限制，配额不足时注册失败。
- 内核版本低于 5.1 时没有该接口，返回 `ENOSYS`。
- 部分安全策略禁用共享内存环，导致初始化失败。
- 排查方式是先用最小程序调用 `io_uring_setup`，确认错误码与内核版本。
- 生产环境需要准备 `epoll` 回退路径，避免依赖单一接口。

### 12.12（辨析）epoll 与 io_uring 的适用边界是什么？

- `epoll` 是就绪通知模型，应用仍需自己调用读写，每次都有系统调用。
- `io_uring` 是完成通知模型，提交与完成都通过共享环，系统调用可摊销。
- 连接数多而每连接数据少的场景，`epoll` 足够且更成熟。
- 高 IOPS、小消息密集的场景，`io_uring` 的批量提交收益更明显。
- `io_uring` 的编程复杂度更高，错误处理与生命周期管理更繁琐。
- 两者可以混用，控制面用 `epoll`，数据面用 `io_uring`。
- 延迟敏感场景还要考虑内核版本差异，不同版本的实现成熟度不同。

### 12.13 DPDK 的基本原理是什么？

- 使用轮询模式驱动代替中断，收包后由用户态线程主动轮询网卡队列。
- 通过 UIO 或 VFIO 把网卡寄存器与 DMA 区域映射到用户态，绕过内核协议栈。
- 使用大页内存分配固定大小的 mbuf 池，减少缺页与 TLB 缺失。
- 每个逻辑核绑定一个 lcore 并独占网卡队列，避免锁与跨核通信。
- 收发包以批量方式处理，一次取多个描述符以摊销每次操作的开销。
- 代价是网卡被独占，内核无法使用该设备，运维与调试方式都要改变。
- 需要自行实现或引入协议栈，地址解析、分片重组与传输层逻辑都要在用户态完成。

### 12.14（场景）DPDK 独占网卡后如何与内核共存？

- 管理口与业务口分离，管理流量走未绑定的网卡，业务口交给 DPDK。
- 使用分叉驱动让同一网卡同时支持内核路径与用户态队列。
- 绑定前先关闭链路，解绑后再恢复内核驱动，避免地址与路由残留。
- 与内核通信可用 KNI、`virtio-user` 或共享内存转发。
- 容器中需要挂载设备节点与大页内存，权限不足会导致初始化失败。
- 抓包需要 DPDK 自带的抓包工具或端口镜像，`tcpdump` 看不到该网卡。
- 多进程场景要用主进程与从进程共享内存，避免重复初始化。

### 12.15 用户态协议栈需要实现哪些部分？

- 链路层要处理地址解析、邻居缓存与以太网帧封装。
- 网络层要处理分片重组、校验和、路由表与跳数限制。
- 传输层要实现状态机、序列号管理、重传定时器、拥塞控制与窗口管理。
- 还要实现定时器轮、连接表哈希、端口分配与等待队列。
- 校验和与分段可以卸载到网卡，需要探测并协商卸载能力。
- 与内核协议栈的语义差异会影响应用移植，例如 `TIME_WAIT` 与地址复用选项。
- 调试缺少 `ss`、`netstat` 等工具，需要自建统计与抓包能力。

### 12.16 零复制与 TLS 为什么冲突？

- TLS 需要按记录加密数据，明文必须经过加密模块处理。
- `sendfile` 直接搬运文件页，无法在执行路径中插入加密步骤。
- kTLS 把对称加密下沉到内核，启用发送方向后 `sendfile` 可以继续使用。
- kTLS 只支持部分套件与协议版本，密钥仍由用户态库协商后下发。
- 不支持 kTLS 时只能退化为用户态加密加普通发送，复制次数回升。
- 接收方向的内核解密同样需要单独启用，且对记录边界有要求。
- 选择取决于 CPU 加密开销与复制开销的相对大小。

### 12.17 批量收发如何减少系统调用开销？

- `sendmmsg` 与 `recvmmsg` 一次系统调用处理多个报文，适合小包密集的服务。
- 每个元素携带独立的地址与缓冲区，返回值是本次处理的报文个数。
- UDP 服务的收益最明显，TCP 受流语义限制，批量收益相对有限。
- 网卡的通用分段卸载把大块数据在发送侧切分，减少协议栈遍历次数。
- 通用接收卸载把多个到达报文合并后一次性上交，降低每包中断开销。
- 批量会推迟首个报文的处理时间，需要与延迟目标折中。
- 批量大小受缓冲区与队列深度限制，应通过压测确定而不是取最大值。

### 12.18（场景）抓包看不到流量，可能是什么原因？

- 流量走了 DPDK 或 RDMA 等内核旁路路径，`tcpdump` 依赖的抓包点不经过。
- 网卡开启了硬件卸载，报文在网卡内部被处理，未进入内核可见路径。
- 容器使用独立的网络命名空间，抓包要在对应命名空间内执行。
- `eBPF` 或 XDP 在更早的钩子丢弃或重定向了报文。
- TLS 流量可见但内容加密，只能看到记录层长度与握手信息。
- 排查顺序是先确认抓包接口与命名空间，再确认设备是否绑定了用户态驱动。
- 端口镜像与流量复制是旁路场景下可靠度较高的观测手段。

### 12.19 RDMA 与内核旁路的关系是什么？

- RDMA 让网卡直接访问应用注册的内存，读写不经过内核协议栈。
- 使用队列对与完成队列，应用提交工作请求后轮询或等待完成。
- 内存需要提前注册并锁定，注册开销较大，适合长生命周期的缓冲区。
- 提供可靠连接与不可靠数据报等传输类型，语义与 TCP 不同。
- 绕过内核意味着没有 `ss` 可看，拥塞与丢包信息来自网卡计数器。
- 与 TCP 共存需要网关或双栈方案，应用要区分两类连接。
- 优势是低延迟与低 CPU 占用，代价是编程模型与运维复杂度。

### 12.20（实现）如何用 splice 在代理中转发数据？

```cpp
int pipefd[2];
if (::pipe2(pipefd, O_NONBLOCK) < 0) return -1;
ssize_t n = ::splice(src, nullptr, pipefd[1], nullptr, 65536, SPLICE_F_MOVE);
if (n > 0) {
    // 剩余的 n 字节留在管道中，等目标可写后继续搬运
    ssize_t m = ::splice(pipefd[0], nullptr, dst, nullptr, n, SPLICE_F_MOVE);
}
```

- 管道缓冲区容量有限，单次搬运量应与容量匹配，避免大量数据滞留。
- `splice` 返回 `EAGAIN` 表示对应方向暂时不可用，需要等待事件。
- 未搬完的数据留在管道中，状态机要记录残留字节数。
- 两个方向各需一个管道，不能共用，否则数据会串流。
- `SPLICE_F_MOVE` 只是提示，是否移动页由实现与文件系统决定。
- 错误路径要关闭管道两端，否则每次转发失败都会泄漏描述符。

## 13. 网络安全基础

### 13.1 TLS 1.2 与 TLS 1.3 的握手往返次数有何差别？

- TLS 1.2 完整握手需要两个往返，先协商参数与密钥交换，再切换密码规格并完成。
- TLS 1.3 把密钥交换与参数协商合并，完整握手只需一个往返。
- TLS 1.3 的客户端在第一个报文就发送密钥共享，服务端收到后可直接算出密钥。
- 会话恢复时 TLS 1.2 用一个往返，TLS 1.3 支持在首个报文携带数据的 0-RTT 模式。
- 往返次数直接影响首字节时间，跨地域访问时差距更明显。
- TLS 1.3 移除了静态 RSA 密钥交换、CBC 模式与压缩，减少了攻击面。
- 版本协商通过扩展完成，中间设备干扰可能导致回退到较低版本。

### 13.2（辨析）对称加密与非对称加密在握手中如何分工？

- 非对称算法用于身份认证与密钥交换，运算慢，只处理少量数据。
- 对称算法用于批量加密与完整性保护，速度快，密钥由握手协商产生。
- 证书签名验证使用非对称算法，验证的是服务端持有对应私钥这一事实。
- ECDHE 只做密钥协商，不提供身份认证，认证仍依赖证书签名。
- 会话密钥由双方各自的临时私钥与对方临时公钥计算，双方得到相同结果。
- 长期私钥泄露不影响历史会话，前提是使用临时密钥交换。
- 混合模式中认证用 RSA 或 ECDSA，密钥交换用 ECDHE，二者职责分离。

### 13.3 证书链是如何校验的？

- 客户端从叶子证书开始，逐级用签发者公钥验证上一级证书的签名。
- 每一级都要检查有效期、基本约束（是否为 CA）、路径长度与密钥用途。
- 叶子证书要检查 `subjectAltName` 是否匹配目标域名。
- 链必须终止于本地信任库中的根证书，中间证书通常由服务端一并发送。
- 吊销状态通过 CRL 或 OCSP 检查，也可由服务端附带 OCSP 响应。
- 任一环节失败都会终止握手并返回证书验证错误。
- 时间不同步、根证书过期、缺少中间证书是常见失败原因。

### 13.4（陷阱）只校验证书签名而不校验域名会怎样？

- 攻击者可以用合法 CA 签发给其他域名的证书冒充目标服务。
- 必须校验 `subjectAltName`，不能只看通用名，后者已被弃用。
- 通配符证书 `*.example.com` 不匹配 `a.b.example.com`，也不匹配裸域。
- 域名校验要在证书链验证之后进行，避免对未通过验证的证书读取字段。
- 客户端库通常默认开启主机名校验，自定义回调中容易漏掉。
- 关闭校验的调试开关不能进入生产配置，否则等于放弃认证。
- 内部服务使用自签证书时，应把 CA 加入信任库而不是关闭校验。

### 13.5 SNI 的作用与暴露面是什么？

- 客户端在 `ClientHello` 中通过 SNI 扩展声明要访问的主机名。
- 服务端据此选择对应证书，使同一地址端口可以承载多个站点。
- TLS 1.3 中 SNI 仍为明文，中间设备可以观察访问的域名。
- 加密 SNI 依赖 ECH 扩展，需要域名系统侧配合发布公钥。
- 部分中间设备会剥离或改写 SNI，导致服务端返回错误证书。
- 服务端只配置默认证书时，缺少 SNI 的旧客户端会拿到不匹配的证书。
- 排查时用 `openssl s_client` 的 `-servername` 参数指定主机名验证行为。

### 13.6（场景）中间人为什么能解密 HTTPS 流量？

- 抓包工具在客户端信任库中安装了自签根证书，因此能签发任意域名的证书。
- 客户端与工具建立一条 TLS 连接，工具再与真实服务端建立另一条。
- 两条连接各自独立，工具持有两套会话密钥，可以明文转发。
- 若客户端做证书固定，工具签发的证书无法通过校验，解密失败。
- 企业出口设备做 TLS 检查时同样依赖下发根证书。
- 该场景说明 TLS 的安全性依赖信任库的完整性，而不只取决于协议。
- 检测手段是监控信任库变化与证书链异常的告警。

### 13.7 双向认证的流程与常见问题是什么？

- 服务端在握手时发送 `CertificateRequest`，要求客户端提供证书。
- 客户端发送自己的证书，并用对应私钥对握手消息签名以证明持有私钥。
- 服务端按自己的信任库校验客户端证书链与用途，客户端证书需带 `clientAuth`。
- 客户端证书通常由内部 CA 签发，需要设置有效期与吊销机制。
- 中间证书缺失会导致服务端校验失败，客户端要发送完整链。
- 客户端证书与用户身份绑定后，吊销与轮换需要配套流程。
- 失败时常表现为握手在证书阶段中断，服务端日志只记录验证错误。

### 13.8（辨析）会话复用有哪几种机制？

- TLS 1.2 的会话标识由服务端保存会话状态，客户端在 `ClientHello` 中带上标识。
- 会话票据把状态加密后交给客户端保存，服务端无需存储，适合水平扩展。
- TLS 1.3 统一用预共享密钥恢复，票据在 `NewSessionTicket` 中下发。
- 会话标识依赖服务端存储与负载均衡的会话保持，扩容时需要共享状态。
- 票据密钥需要定期轮换，轮换期内新旧密钥要同时可用。
- 复用能省去证书验证与密钥交换，显著降低握手延迟与 CPU 开销。
- 复用会削弱前向保密性，票据密钥泄露会影响对应会话。

### 13.9 前向保密是如何实现的？

- 每次握手生成临时密钥对，握手结束后临时私钥被丢弃。
- 会话密钥由临时私钥与对方临时公钥计算，长期私钥不参与。
- 即使服务端长期私钥泄露，攻击者也无法恢复历史会话。
- TLS 1.3 强制使用临时密钥交换，TLS 1.2 中需要选择 ECDHE 套件。
- 使用静态 RSA 密钥交换的套件不具备前向保密，已不推荐。
- 会话票据若长期保存会话密钥，会削弱前向保密。
- 代价是每次完整握手都要做一次椭圆曲线运算。

### 13.10（辨析）如何解读一个加密套件的名称？

- `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` 依次表示密钥交换、认证、批量加密与哈希。
- 密钥交换为 ECDHE，认证算法为 RSA，表示使用 RSA 证书签名。
- 批量加密为 AES-128-GCM，属于带关联数据的认证加密，同时提供机密性与完整性。
- 末尾的 SHA256 在 TLS 1.2 中用于密钥派生与握手摘要。
- TLS 1.3 的套件名只保留认证加密算法与哈希，密钥交换与认证由扩展决定。
- 套件顺序由服务端偏好或客户端偏好决定，取决于实现与配置。
- 含 RC4、3DES、CBC 模式与静态 RSA 的套件应在配置中禁用。

### 13.11（陷阱）降级攻击如何发生，防护机制是什么？

- 攻击者篡改握手报文，使双方协商到较低版本或较弱套件。
- TLS 1.3 的服务端在协商到低版本时会在随机数字段末尾写入固定标记，客户端校验后中止。
- TLS 1.2 依赖客户端在重试时发送特定的信令套件，服务端若支持更高版本则拒绝握手。
- 服务端应禁用旧版本与弱套件，减少可降级的空间。
- 中间设备终止 TLS 后重新发起连接时，可能无意中造成版本降级。
- 监控握手统计中的版本分布可以及早发现异常回退。
- 降级防护不能替代证书校验，二者防护的目标不同。

### 13.12 重放攻击在传输层如何被阻止？

- TLS 记录层为每条记录分配序列号，认证加密的随机数由序列号与初始向量导出。
- 重复的记录会因序列号重复或认证失败被丢弃。
- 握手消息通过完成校验值保护，篡改或重放会导致校验失败。
- 记录层防护只覆盖单条连接，跨连接的重放需要应用层机制。
- 0-RTT 数据没有这种保护，可以被重放，因此只允许幂等请求。
- 序列号与密钥绑定到单条连接，同一段密文换到新连接上无法通过认证。
- 传输层不解决业务语义上的重复提交。

### 13.13（场景）应用层如何防止重放？

- 为每个请求分配唯一标识，服务端在有效期内缓存并拒绝重复。
- 请求带时间戳，超出允许偏差的请求直接拒绝，减少缓存窗口。
- 缓存需要设置过期时间与容量上限，避免被大量随机标识撑爆。
- 幂等键与业务操作绑定，同一个键的操作只执行一次并返回相同结果。
- 分布式环境下缓存要集中存储或按一致性哈希分片。
- 仅用时间戳不足以防重放，攻击者可以在窗口内重复提交。
- 序列号方案要求严格递增，乱序与多连接场景需要额外处理。

### 13.14 ALPN 的作用是什么？

- ALPN 在 TLS 握手期间协商应用层协议，避免握手完成后再探测。
- 客户端在 `ClientHello` 的 ALPN 扩展中按偏好列出协议名，如 `h2` 与 `http/1.1`。
- 服务端选择一个放入响应，未协商成功时可拒绝连接或回退。
- 协议名是长度前缀的字节串，不是文本行，单个名称长度上限为 255。
- HTTP/2 的部署依赖 ALPN，否则只能通过升级机制协商。
- 中间设备可能剥离该扩展，导致协商失败或回退到 HTTP/1.1。
- TLS 1.2 中该扩展明文可见，TLS 1.3 中位于加密的扩展内。

### 13.15（实现）如何用 OpenSSL 配置 ALPN？

```cpp
static const unsigned char kProtos[] = {2,'h','2', 8,'h','t','t','p','/','1','.','1'};

// 客户端：声明按偏好排序的协议列表
if (SSL_CTX_set_alpn_protos(ctx, kProtos, sizeof(kProtos)) != 0)
    return -1;

// 握手完成后读取协商结果
const unsigned char* proto = nullptr;
unsigned int plen = 0;
SSL_get0_alpn_selected(ssl, &proto, &plen);   // 名称为 h2 或 http/1.1
```

- 协议列表是长度前缀格式，手写容易出错，建议由辅助函数生成。
- 服务端通过 `SSL_CTX_set_alpn_select_cb` 注册回调，用 `SSL_select_next_proto` 从双方列表中选出一个。
- 回调返回失败会发送无可用协议告警，客户端因此收到明确的握手错误。
- 客户端未提供该扩展时回调不会被调用，服务端需要决定默认协议。
- 协商结果用 `SSL_get0_alpn_selected` 读取，据此决定后续帧格式。
- 服务端不支持客户端列出的任一协议时，应拒绝连接而不是静默回退。
- HTTP/2 要求协商结果与后续帧一致，配置错误会导致协议解析失败。

### 13.16 证书固定的取舍是什么？

- 固定可以是证书哈希、公钥哈希或 CA 哈希，粒度越细安全性越高、轮换越困难。
- 固定公钥允许证书续期而不更换密钥，减少客户端发版次数。
- 固定 CA 的灵活性最高，但该 CA 被滥用时防护随之失效。
- 移动端与客户端发版周期长，固定的哈希需要预留备用值。
- 固定失败会导致全部请求失败，需要谨慎的回退策略与灰度发布。
- 服务端更换证书或密钥前要确认客户端已支持新值。
- 固定不能替代域名与链校验，只是额外的约束。

### 13.17（场景）TLS 握手失败如何排查？

- 先用 `openssl s_client -connect host:443 -servername host -showcerts` 复现并观察证书链。
- 检查返回的错误类型：证书过期、主机名不匹配、链不完整、协议版本不支持。
- 分别指定 TLS 1.2 与 TLS 1.3 尝试，确认是否为版本协商问题。
- 服务端日志通常只记录握手失败，需要提高日志级别才能看到具体原因。
- 中间设备可能拦截并替换证书，对比不同网络环境下的证书链可以确认。
- 客户端时钟偏差超过证书有效期边界时校验失败，应检查时间同步。
- 双方套件交集为空时握手失败，指定单个套件可以验证该假设。

### 13.18 0-RTT 的风险是什么？

- 客户端在首个报文携带应用数据，恢复会话时省去一个往返。
- 这些数据没有前向保密，且可以被攻击者截获后重放。
- 服务端应只对幂等操作接受 0-RTT 数据，或做重放检测。
- 0-RTT 数据与后续握手数据之间存在竞态，服务端要缓冲到握手完成。
- 反重放依赖票据与时间窗口，跨集群共享状态时更复杂。
- 部分中间设备会缓存或重复转发首个报文，放大重放风险。
- 收益主要体现在跨地域的首请求延迟，对已建立连接没有影响。

### 13.19 TLS 终止放在负载均衡还是后端？

- 在均衡器终止可以集中管理证书、统一协商 ALPN 与 HTTP/2，后端 CPU 开销降低。
- 终止后均衡器到后端为明文，需要可信网络或再加密。
- 透传模式保留端到端加密，均衡器只能按 SNI 或四元组分流，无法解析 HTTP。
- 再加密会增加一次握手与加解密开销，但满足合规要求。
- 会话票据与密钥在均衡器集群间需要共享，否则恢复率下降。
- 终止模式下客户端证书身份要传给后端，通常用请求头或后端侧双向认证。
- 选择取决于合规边界、后端技术栈与运维能力。

### 13.20（实现）非阻塞 SSL_read 与 SSL_write 如何处理 WANT_READ？

```cpp
int tls_read(SSL* ssl, char* buf, int len) {
    int n = ::SSL_read(ssl, buf, len);
    if (n > 0) return n;
    int err = ::SSL_get_error(ssl, n);
    if (err == SSL_ERROR_WANT_READ || err == SSL_ERROR_WANT_WRITE)
        return 0;                        // 等待事件后重试
    if (err == SSL_ERROR_ZERO_RETURN)
        return -1;                       // 对端正常关闭
    return -2;                           // 其他错误，连接不可用
}
```

- `SSL_get_error` 必须紧接在失败调用之后，期间不能插入其他 SSL 调用。
- 密钥更新与握手消息会让读操作需要写、写操作需要读，两个方向都要处理。
- `SSL_write` 可能部分写入，需要启用部分写模式或自行重试剩余部分。
- 重试时必须使用相同的缓冲区与长度，否则要启用允许移动写缓冲区的模式。
- `SSL_ERROR_SYSCALL` 要结合 `errno` 判断，返回 0 也可能表示对端未发关闭通知就断开。
- `SSL_pending` 可取出已解密但未读取的数据，避免只依赖底层可读事件。

## 14. DNS 与负载均衡

### 14.1 输入域名后，DNS 解析要经过哪些环节？

- 应用调用 `getaddrinfo`，先查 `/etc/hosts` 与 `nsswitch.conf` 中配置的源，如 `files`、`dns`、`mdns`。
- 未命中时向 `/etc/resolv.conf` 中的递归解析器发起查询，glibc 默认 `timeout:5`、`attempts:2`，并按 `search` 与 `ndots` 追加后缀。
- 解析器查本地缓存，未命中则从根服务器开始，按委派逐级查询顶级域与权威服务器。
- 权威服务器返回记录与 TTL，解析器按 TTL 缓存并向客户端返回剩余值。
- 客户端拿到 A 与 AAAA 记录后建立连接；TLS 场景还需 SNI 与证书校验。
- 冷启动时根、顶级域、权威各一次往返，CNAME 链会再叠加若干次串行查询。

### 14.2（辨析）递归查询与迭代查询有什么区别？

- 递归查询由客户端发给递归解析器，解析器承担后续全部工作，只返回最终结果或错误码。
- 迭代查询由解析器发给根与各级权威，被查询方只返回委派信息，即 NS 记录与必要的 glue 记录。
- 根与顶级域服务器通常不提供递归，应答中 `RA` 位为 0；开放递归会形成放大攻击面。
- 递归解析器负责缓存、并发、超时重试与 DNSSEC 校验，是容量与安全防护的重点。
- 权威服务器只对自己负责的区给出权威应答，`AA` 位为 1。
- 客户端通常只配置少数几个解析器地址，glibc 只使用前 3 个，具体上限由实现定义。

### 14.3 根、顶级域与权威服务器如何通过委派完成解析？

- 根区返回顶级域的 NS 记录与 glue 记录，glue 用于避免解析 NS 名称时产生循环依赖。
- 顶级域返回二级域的 NS 记录；若 NS 名称落在被委派子区内，必须由父区提供 glue。
- 权威服务器返回区内的 A、AAAA、CNAME、MX、TXT 等记录，并置 `AA` 位。
- 委派只转移子树的权威，父区仍保留 NS 与 DS 记录，DNSSEC 依赖 DS 到 DNSKEY 的信任链。
- 解析器按 NS 名称缓存服务器地址，单个 NS 无响应时切换下一个，全部失败返回 `SERVFAIL`。
- 委派层级越深，冷启动往返越多；缓存命中后只需向权威或缓存发一次查询。

### 14.4 DNS 报文头部哪些字段决定解析行为？

- `ID` 为 16 位标识，用于匹配请求与应答，配合源端口随机化降低伪造应答注入的概率。
- 标志位包括 `QR`、`Opcode`、`AA`、`TC`、`RD`、`RA`、`AD`、`CD` 与 4 位 `RCODE`。
- `TC` 为 1 表示应答被截断，客户端应改用 TCP 重试。
- `QDCOUNT`、`ANCOUNT`、`NSCOUNT`、`ARCOUNT` 各 16 位，记录总数受报文长度约束。
- `RCODE` 常见取值：0 表示成功，2 表示 `SERVFAIL`，3 表示 `NXDOMAIN`，5 表示 `REFUSED`。
- 问题区由 `QNAME`、`QTYPE`、`QCLASS` 组成，`QNAME` 采用标签长度前缀编码。
- EDNS0 在附加区放置 OPT 伪记录，声明 UDP 载荷大小、版本与扩展 `RCODE` 的高位。

### 14.5 为什么 DNS 主要使用 UDP，什么时候切换到 TCP？

- UDP 无握手，一次往返即可得到应答，解析器还能同时向多个服务器发问。
- 传统 UDP 载荷上限 512 字节，超长应答置 `TC` 位，客户端据此改用 TCP。
- EDNS0 把通告载荷提高到 1232 字节左右，既减少截断又避免 IP 分片。
- 区域传送 `AXFR` 与 `IXFR`、大响应、DNSSEC 大密钥场景直接使用 TCP。
- TCP 查询带 2 字节长度前缀，连接可复用，代价是维护连接状态与超时。
- 部分网络对 53 端口 UDP 限速或拦截，排错时需区分超时、`REFUSED` 与截断回退失败。

### 14.6（陷阱）DNS 缓存分布在哪几层，TTL 由谁递减？

- 应用与运行时缓存，如浏览器、JVM、部分语言的解析器，可能忽略 TTL 或使用固定缓存时长。
- 操作系统存根缓存，如 `systemd-resolved`、`nscd`；`/etc/hosts` 的条目不参与 TTL 过期。
- 递归解析器缓存，按权威给出的 TTL 存储并逐秒递减，返回时给出剩余值。
- 权威服务器只给出 TTL，本身不缓存；记录修改后旧值仍在各级缓存中存活至过期。
- TTL 过小会增加权威负载与解析延迟，过大则故障切换与扩容生效变慢。
- 缩短 TTL 需在变更前至少一个旧 TTL 周期完成，否则旧缓存仍会把流量导向旧地址。

### 14.7 负缓存与 NXDOMAIN 的 TTL 如何确定？

- 否定应答分两类：`NXDOMAIN` 表示名称不存在，`NODATA` 表示名称存在但没有所查类型的记录。
- 按 RFC 2308，否定缓存时长取 SOA 记录自身 TTL 与 SOA `MINIMUM` 字段的较小值。
- 解析器缓存否定结果后，TTL 内新建同名记录不可见，表现为「刚添加就解析失败」。
- `SERVFAIL` 也可能被短暂缓存，但它表示解析失败而非名称不存在，不应长期缓存。
- 存在通配符记录时，未命中的名称会得到肯定应答，负缓存不再适用。
- 排查时用 `dig +norecurse` 直接询问权威，确认否定结果来自权威还是某一层缓存。

### 14.8 CNAME 链过长会带来哪些代价？

- 每一级 CNAME 需要一次额外查询，冷启动时串行往返，解析延迟逐级叠加。
- 应答体积增大，更容易超过 UDP 载荷而置 `TC` 位，回退到 TCP。
- 部分解析器限制链长度，超过上限返回 `SERVFAIL`，表现为部分地域解析失败。
- CNAME 不能与其他类型记录共存于同一名称，apex 域名通常改用其他接入方式。
- CDN 常用 CNAME 接入，链路上每一层都要单独缓存，TTL 不一致时出现部分过期。
- 排错时用 `dig +trace` 观察每一跳的应答，确认延迟由哪一级引入。

### 14.9 A 与 AAAA 记录同时存在时如何选择？

- `getaddrinfo` 按 `ai_family` 与 `AI_ADDRCONFIG` 过滤，返回顺序遵循 RFC 6724 的地址排序规则。
- 双栈客户端常用 Happy Eyeballs（RFC 8305），先发 IPv6，约 250 ms 后并发 IPv4，取先连通者。
- 仅有 AAAA 可用而本机无 IPv6 路由时，需等连接失败再回退，额外消耗一次超时。
- `AI_ADDRCONFIG` 依据本机已配置地址过滤，容器内缺少全局 IPv6 地址时只返回 IPv4。
- 服务端应同时提供 A 与 AAAA，避免单栈客户端不可达。
- 监控需分别探测两种协议，否则 IPv6 路径故障不会体现在 IPv4 指标上。

### 14.10 DNS 轮询做负载均衡有哪些局限？

- TTL 内客户端与解析器都缓存结果，流量分布滞后于权重调整。
- 没有健康检查，记录指向故障节点时仍会分到流量，直到缓存过期。
- 多条 A 记录的返回顺序与选择策略由客户端决定，实际比例不可控。
- 长连接与连接池把一次解析结果放大为长期流量，新节点难以获得份额。
- 无法感知后端负载，只能靠记录条数近似权重。
- 适合作机房级或地域级的第一层调度，不适合精细分流。

### 14.11（场景）四层与七层负载均衡如何影响故障定位？

- 四层转发不解析应用载荷，超时通常表现为连接已建立但无响应，需靠抓包区分后端未回包与回包丢失。
- 七层代理会终止客户端连接，客户端看到的错误由代理生成，`502` 指向后端不可达，`504` 指向后端超时。
- 四层在 DR 与 TUN 模式下保留源地址，后端日志记录真实客户端 IP；NAT 模式下后端只看到均衡器地址。
- 七层可插入 `X-Forwarded-For` 与请求 ID，链路追踪完整；四层需要靠五元组关联两侧日志。
- 四层出现连接重置时难以判断由哪一端发出，七层代理通常在访问日志中记录上游错误。
- 七层的排队发生在代理内部，表现为 TTFB 升高而服务端处理时间不变。
- 选择层次需同时考虑观测成本，四层节省的 CPU 往往以排错难度为代价。

### 14.12 LVS 的 DR、NAT 与 TUN 模式分别改写哪些字段？

- NAT 模式改写目的 IP 与端口，回包必须经过均衡器，均衡器成为带宽瓶颈。
- DR 模式只改写以太网帧的目的 MAC，IP 头保持不变，后端把 VIP 配置在 `lo` 上并抑制 ARP。
- TUN 模式用 IP 隧道封装原报文送到后端，后端解封装后自行回包。
- DR 与 TUN 的回包不经过均衡器，要求后端网关能直达客户端。
- DR 要求均衡器与后端处于同一二层网络，TUN 可跨网段，NAT 需要后端把网关指向均衡器。
- 只有 NAT 双向经过均衡器，DR 与 TUN 只承担入向流量。

### 14.13（场景）DR 模式下后端回包为何不经过均衡器？

- DR 只改帧头目的 MAC，报文中的目的地址仍是 VIP，后端收到的目的 IP 没有变化。
- 后端在 `lo` 上配置 VIP，并设置 `arp_ignore=1`、`arp_announce=2`，避免应答 VIP 的 ARP 请求。
- 回包按路由表选源地址 VIP、下一跳为物理网关，报文从后端网卡直接发出。
- 均衡器只处理入向流量，出向带宽由各后端分担。
- 若后端默认路由指向均衡器，回包会绕回，形成非对称路径并可能被反向路径过滤丢弃。
- 排查时在均衡器入口与后端网卡同时抓包，比较回包是否出现在均衡器出口。

### 14.14 健康检查分哪些层次，如何避免误判？

- 端口探测只验证 `connect` 成功，无法发现进程假死或依赖不可用。
- 应用层探测请求固定路径并校验状态码与关键字段，可发现线程池耗尽与队列积压。
- 业务层探测校验依赖可用性，但容易把局部故障放大为整体摘除。
- 用 `rise` 与 `fall` 阈值做迟滞，连续多次失败才摘除，连续多次成功才恢复。
- 探测间隔、超时与并发需与实例规模匹配，避免探测流量本身压垮服务。
- 多探针与多可用区交叉验证，减少单点网络抖动导致的误摘。
- 摘除应有过渡期，先停止新流量再等待存量请求结束。

### 14.15 一致性哈希如何减少节点变动时的迁移量？

- 取模哈希在节点数由 N 变为 N+1 时，几乎全部键都需要重新映射。
- 一致性哈希把节点与键映射到同一环，键归属顺时针方向最近的节点。
- 增加一个节点平均迁移 K/N 的键，删除节点则把该节点负责的区间交给后继节点。
- 节点较少时环上弧长随机，区间划分不均，需要虚拟节点改善均衡度。
- 权重可通过给节点分配不同数量的虚拟节点表达。
- 有界负载一致性哈希进一步约束单节点负载上限，代价是额外计算与状态维护。

### 14.16 虚拟节点解决什么问题，代价是什么？

- 物理节点少时，哈希环上的弧长差异可达数倍，负载偏差明显。
- 每个物理节点映射为上百个虚拟节点，弧长趋于均匀，偏差随虚拟节点数增加而下降。
- 虚拟节点使扩容时的迁移分散到多个物理节点，避免单个节点承压。
- 查找需按哈希值在有序结构中二分，虚拟节点越多，内存占用与查找开销越大。
- 节点变更需同步虚拟节点表，表的一致性依赖配置中心或 gossip 传播。
- 虚拟节点比例需与均衡目标、内存预算、迁移代价一起权衡。

### 14.17 SRV 记录在服务发现中如何使用？

- SRV 记录给出目标主机、端口、优先级 `priority` 与权重 `weight`，端口无需写死在配置中。
- 客户端按优先级从低到高尝试，同一优先级内按权重比例选择，权重为 0 的记录仍在列表中但被选中的概率极低。
- 目标字段是主机名，需要再做一次 A 或 AAAA 查询，冷启动多一次往返。
- 记录名遵循 `_service._proto.name` 形式，例如 `_grpc._tcp.example.com`。
- 通用 HTTP 客户端多不支持 SRV，常见于 gRPC、XMPP、SIP 等协议的客户端解析。
- 优先级与权重由权威侧配置，变更仍受 TTL 约束，不适合秒级故障切换。
- 排错时用 `dig SRV` 核对目标与端口，确认客户端是否按优先级回退。

### 14.18 Anycast 与 DNS 调度在就近接入上有何差别？

- Anycast 让多个站点宣告同一前缀，网络按 BGP 选路把报文送到最近站点。
- DNS 调度依据解析器位置与记录选择，客户端使用远端公共解析器时可能被判错地域。
- Anycast 在路由收敛后生效，通常为秒级到分钟级；DNS 受 TTL 约束，切换可能更慢。
- 路由变化会使同一 TCP 连接的前后报文到达不同站点，导致连接中断。
- DNS 可返回不同记录实现按地域、运营商分流，粒度更细但容易被缓存掩盖。
- EDNS Client Subnet（RFC 7871）把客户端子网传给权威，提高调度精度，同时带来隐私与缓存碎片问题。

### 14.19 DNS 解析超时与重试策略如何设计？

- 单次查询超时与请求总预算分开设置，避免重试把总延迟放大数倍。
- 解析器按服务器列表轮转，失败后切换下一个，全部失败才返回错误。
- `search` 域与 `ndots` 会生成多次查询，短名称在容器内尤其容易触发额外往返。
- 连接建立与解析共享同一个用户可见超时，解析占满预算时连接阶段已无时间可用。
- 应用侧可缓存解析结果并异步刷新，缩短请求路径上的阻塞。
- 重试需带抖动，避免大量实例在同一时刻重试压垮解析器。
- 监控需区分 `SERVFAIL`、超时与 `NXDOMAIN`，三者的处置方式不同。

### 14.20（场景）后端扩容后流量没有按预期分摊，如何排查？

- 确认记录已下发：直接向权威服务器查询，排除递归缓存中的旧值。
- 核对 TTL 与变更时机，旧缓存可能在数十分钟内继续生效。
- 观察长连接与连接池：已建立的连接不会因新增记录而重新分配。
- 检查会话保持与一致性哈希，键的分布可能仍集中于旧节点。
- 核对权重表达方式，多条 A 记录的条数与客户端选择策略未必对应预期比例。
- 在客户端统计目标地址分布，与服务端收到的连接数比对。
- 七层网关场景需确认配置已 reload，以及健康检查没有把新节点判为不可用。

## 15. 网络排错与观测

### 15.1 tcpdump 抓包时如何减少丢包？

- `-s 0` 抓取完整报文；默认 snaplen 在多数版本为 262144，截断会丢失应用层内容。
- `-w file.pcap` 直接写文件，避免终端输出与文本解析的开销。
- `-B` 调大内核环形缓冲区，高包速率下默认缓冲区很快耗尽。
- 过滤表达式在附加时编译为 BPF 并在内核执行，减少复制到用户态的报文数量。
- `-i` 指定网卡，`-Q in` 或 `-Q out` 限定方向，只抓必要流量。
- 结束时读取统计中的 `packets dropped by kernel`，非零说明抓包结果不完整。
- 生产环境优先在镜像端口或交换机侧采集，避免在业务机上长时间抓包。

### 15.2 BPF 过滤器在哪个环节生效？

- `tcpdump` 把过滤表达式编译为 BPF 程序，通过 `SO_ATTACH_FILTER` 挂到抓包套接字上。
- 报文进入套接字接收队列前先经 BPF 判定，未命中的报文不复制到用户态。
- 过滤发生在 `AF_PACKET` 层，链路层头已存在，可用 `ether`、`vlan` 等原语。
- 表达式应尽早缩小范围，`host` 与 `port` 比逐字节比较 TCP 标志位更高效。
- BPF 只减少用户态复制，不减少网卡到内核的传递，极高流量下仍需硬件采集。
- `-d` 打印编译后的 BPF 指令，用于确认表达式是否被正确解析。

### 15.3 ss 与 netstat 有什么区别？

- `netstat` 读取 `/proc/net/tcp`、`/proc/net/udp` 等文件并解析，连接数大时开销明显。
- `ss` 通过 netlink 的 `INET_DIAG` 接口按需查询，支持过滤并能输出更多字段。
- `ss -ti` 可给出拥塞窗口、RTT、重传次数等内核 TCP 状态，`netstat` 不提供。
- `ss -lnt` 中 LISTEN 套接字的 `Send-Q` 是 backlog，`Recv-Q` 是已完成握手但未被取走的连接数。
- `ss` 支持按状态过滤，如 `state established`、`state time-wait`，便于统计分布。
- 两者都只反映本机视角，容器与网络命名空间需在对应命名空间内执行。

### 15.4 ss -ti 中的队列与时间字段如何用于判断连接状态？

- `send` 与 `recv` 为发送、接收队列字节数，`send` 长期非零说明对端接收窗口不足或应用未及时写出。
- `unacked` 为已发送未确认的段数，持续偏大说明确认滞后或路径丢包。
- `lastsnd`、`lastrcv`、`lastack` 为距上次发送、接收、确认的毫秒数，用于判断连接是否僵死。
- `retrans` 与 `bytes_retrans` 为累计重传，短时间快速增长说明路径质量恶化。
- `dsack` 计数非零说明出现过伪重传，可据此判断重传是否由乱序引起。
- `skmem` 给出套接字内存分配明细，接收队列积压时该项显著增长。
- 字段按固定间隔刷新，采样过密会读到重复值，过疏会漏掉瞬时拥塞。

### 15.5（场景）conntrack 表满时有哪些现象，如何排查？

- 现象是新连接失败或间歇性超时，`dmesg` 中出现 `nf_conntrack: table full, dropping packet`。
- NAT 网关、Kubernetes 节点与容器出网都依赖 conntrack 记录五元组映射。
- `/proc/sys/net/netfilter/nf_conntrack_count` 与 `nf_conntrack_max` 给出使用率。
- 短连接过多、残留的 `TIME_WAIT` 与长期未清理的 UDP 流都会推高表项数量。
- `conntrack -S` 的 `insert_failed`、`drop` 与 `early_drop` 区分插入失败与主动淘汰。
- 调大上限只是缓冲，需同时缩短 `nf_conntrack_tcp_timeout_time_wait` 并减少短连接。
- 容器场景需在宿主命名空间查看，容器内看不到节点级表项。

### 15.6（场景）连接被重置时如何确认 RST 来自哪一端？

- RST 可由对端应用关闭、对端内核协议栈或中间设备（防火墙、负载均衡）产生。
- 抓包比较 RST 的 TTL 与 IP ID，与路径上已知设备的特征比对，可初步判断来源。
- 若 RST 在请求发出后极短时间内到达且对端日志无记录，多为中间设备按策略重置。
- 服务端 `nstat` 中 `TcpExtTCPAbortOnClose`、`TcpExtTCPAbortOnTimeout` 等计数增长，指向内核主动重置。
- 应用崩溃重启后，旧连接的报文到达会回 RST，客户端表现为连接被重置。
- 负载均衡或 NAT 的空闲超时先于服务端时，复用旧连接会立即收到 RST。
- 在两端与中间设备同时抓包，比较 RST 首次出现的位置。

### 15.7 容器与网络命名空间内如何观测连接？

- 容器内 `ss` 与 `tcpdump` 只看到本命名空间的套接字与网卡，宿主机看不到容器内的进程归属。
- 用 `nsenter -t $(pidof app) -n` 进入目标命名空间执行命令，进程号取自容器主进程。
- 容器内通常只有 `eth0` 与 `lo`，宿主侧对应一对 veth，两侧抓到的是同一条流的不同方向。
- 端口映射场景下容器内看到的对端是网关地址，真实客户端地址需从宿主 conntrack 还原。
- 服务网格的 sidecar 会终止并重建连接，应用侧看到的对端是本地代理。
- 节点级 conntrack、`somaxconn` 与端口范围在宿主命名空间生效，容器内调整无效。
- 容器内缺少抓包工具时可在宿主用 `nsenter` 执行，或把抓包文件复制到宿主分析。

### 15.8 如何统计连接状态分布并定位泄漏？

- `ss -s` 给出各状态汇总，适合快速判断总量与比例。
- `ss -tan state established | wc -l` 按状态精确计数。
- 按对端地址聚合，统计每个对端的连接数，找出异常集中的来源。
- 周期性采样并对比，稳态服务的连接数应随负载波动，而不应单调增长。
- 结合 `/proc/pid/fd` 数量与 `ss -tanp` 的进程归属，判断泄漏在应用还是内核。
- 容器场景需在容器网络命名空间内执行，宿主机的统计不包含其他命名空间。

### 15.9 RTT 应该在哪里测量？

- 内核 `srtt` 由 TCP 采样并按 RFC 6298 做指数加权移动平均，反映传输层往返。
- `ping` 测的是 ICMP 往返，路径与优先级可能与 TCP 不同，只能作参考。
- 应用层 RTT 包含排队、业务处理与序列化，是用户感知的真实延迟。
- 抓包计算 RTT 需匹配请求与响应，注意延迟确认会把 ACK 与数据合并。
- 不同测量点的差异可用于定位瓶颈：内核 RTT 正常而应用 RTT 偏高，问题在服务内部。
- 高负载下内核 `srtt` 会因排队偏高，需结合 `cwnd` 与重传次数判断。

### 15.10 丢包如何区分链路、拥塞与接收端？

- 链路层看网卡统计：`rx_crc_errors`、`rx_frame_errors`、`rx_missed_errors` 增长指向物理层或驱动问题。
- 拥塞丢包表现为重传伴随 `cwnd` 下降与 `ssthresh` 调整，常见于瓶颈链路。
- 接收端丢包看 `netstat -s` 的 `receive buffer errors` 与 `TcpExtTCPRcvCollapsed`。
- `netdev_max_backlog` 溢出计入 `softnet_data` 的丢弃计数，表现为软中断处理不及时。
- 中间设备可能做尾丢弃或流量监管，抓包只能看到结果，需结合 `mtr` 与设备计数。
- 对比两端抓包：发送端已发出而接收端未见，丢包发生在路径上。

### 15.11 重传有哪几种，抓包时如何识别？

- 超时重传由 RTO 触发，间隔按指数退避，抓包中表现为明显停顿后重发同一序列号。
- 快速重传在收到 3 个重复 ACK 后立即重发，无需等待 RTO。
- SACK 重传依据 `SACK` 块选择缺失段，可在一个 RTT 内填补多个空洞。
- 抓包中序列号与载荷重复即为重传，Wireshark 标记为 `tcp.analysis.retransmission`。
- 伪重传指原报文其实已到达，只是 ACK 丢失或乱序，可用 DSACK 判断。
- 重传率用 `TcpRetransSegs / OutSegs` 估算，超过 1% 需关注，跨地域链路另作判断。

### 15.12（场景）抓包看到大量重复 ACK，如何判断是丢包还是乱序？

- 重复 ACK 的确认号不变，说明接收端收到了空洞之后的段，`SACK` 块会标明已收范围。
- 连续 3 个以上重复 ACK 通常意味着中间段丢失，会触发快速重传。
- 只有 1 到 2 个重复 ACK 后即恢复，多为路径乱序，不构成丢包。
- 对比发送端与接收端抓包，接收端从未出现的段才是真正丢失。
- 若接收端已回 SACK 而发送端未重传，问题在 ACK 路径或发送端处理。
- 开启 DSACK 后，`ss -ti` 中的 `dsack` 计数可辅助判断伪重传。

### 15.13 Wireshark 的乱序与重传判定为何可能失真？

- 抓包点在网卡上，GRO 与 LRO 会把多个段合并为大段，序列号与线缆上的报文不一致。
- TSO 使发送端抓到的报文大于 MTU，接收端看到的分段与之不对应。
- 校验和卸载使抓包显示校验和错误，而报文实际有效。
- 分析器依据序列号连续性判定重传与乱序，抓包点两侧不一致时必然误判。
- 需要时用 `ethtool -K eth0 gro off tso off` 关闭卸载后复核，或改在镜像口抓包。
- 时间戳精度同样影响判定，软件时间戳在高速流量下误差可达毫秒级。

### 15.14 单向延迟如何测量，时钟不同步有什么影响？

- 单向延迟要求两端处于同一时间基准，普通 NTP 同步误差在毫秒级，不足以支撑微秒级结论。
- PTP 配合硬件时间戳可达亚微秒级，但要求网卡与交换机支持。
- 无同步条件时用 RTT 近似，前提是路径对称，非对称路由会带来系统偏差。
- 抓包时间戳来自本机时钟，跨机比较前必须先校正偏差。
- 可用一次请求响应估算偏移，公式为两个方向耗时之差的一半，仍以路径对称为前提。
- 应用层埋点更适合观察业务延迟分布，但包含排队与处理时间。

### 15.15 一次请求的耗时如何拆解？

- DNS 解析耗时、TCP 握手 1 个 RTT、TLS 握手耗时（TLS 1.3 为 1 RTT，TLS 1.2 为 2 RTT）。
- 请求发出到首字节返回为 TTFB，包含服务端排队与处理。
- 内容传输时间取决于带宽与拥塞窗口增长，短连接受慢启动限制。
- 连接复用后握手成本消失，队头阻塞与连接池排队成为新的延迟来源。
- 浏览器与服务端指标需通过请求 ID 或 `traceparent` 关联，否则时间线无法对齐。
- 各阶段占比决定优化方向：握手占比高说明连接未复用或 RTT 过大。

### 15.16 traceroute 与 mtr 的探测方式有何差异？

- Linux 的 `traceroute` 默认向高位端口发 UDP 报文，逐步增大 TTL，靠 `ICMP time exceeded` 定位路径。
- Windows 的 `tracert` 默认发 ICMP Echo，部分网络对 ICMP 限速或过滤。
- `-T` 改用 TCP SYN 探测，可穿越只放行特定端口的策略。
- `mtr` 持续探测并统计每跳丢包率与延迟分布，适合定位间歇性问题。
- 中间跳丢包率高而末跳正常，通常是路由器对 ICMP 限速，不代表转发丢包。
- 路径随 ECMP 变化，多次探测的跳数不一致属于正常现象。

### 15.17 全连接队列溢出如何观测？

- `ss -lnt` 的 `Recv-Q` 是已完成握手但未被 `accept` 取走的连接数，`Send-Q` 是 backlog 上限。
- `nstat -az TcpExtListenOverflows TcpExtListenDrops` 统计因队列满而丢弃的连接。
- `ListenOverflows` 增长说明 `accept` 速度不足，或 `somaxconn` 与 `backlog` 偏小。
- 溢出时客户端可能握手完成但请求无响应，也可能直接收到 RST。
- 增大 `backlog` 只能缓冲，根因多为事件循环被阻塞或 `accept` 未被及时调用。
- 同时检查 `TcpExtTCPReqQFullDrop`，区分半连接队列与全连接队列的丢弃。

### 15.18（场景）客户端说慢、服务端说快，如何定位分歧？

- 先对齐时间基准与请求 ID，确认双方讨论的是同一批请求。
- 对比客户端 TTFB 与服务端处理耗时，差值即网络与排队时间。
- 检查服务端指标是否只统计处理阶段，遗漏了排队、TLS 与响应写出。
- 在客户端与服务端同时抓包，比较请求到达时间与响应首包发出时间。
- 观察重传、零窗口与 `send` 队列积压，判断是否受带宽或接收窗口限制。
- 若服务端出口有代理或网关，需在每一跳取时间戳，避免把代理排队计入网络。
- 高百分位差异常由少数慢请求主导，平均值会掩盖问题。

### 15.19 eBPF 在网络排错中的位置与限制？

- 可在内核函数、tracepoint 与套接字层挂载程序，获取连接建立、重传、丢包与延迟分布。
- 与抓包相比，eBPF 在输出前完成聚合，开销远低于全量 pcap。
- 常用工具包括 `bpftrace` 与 bcc 中的 `tcpretrans`、`tcpconnlat`、`tcpdrop`。
- 依赖内核版本与 BTF 支持，CO-RE 可减少跨版本适配工作。
- 内核旁路方案与部分容器环境限制挂载点，观测能力受限。
- eBPF 程序有指令数与栈大小限制，复杂聚合需借助 per-CPU 映射与用户态汇总。

### 15.20 线上观测体系应包含哪些网络指标？

- 连接维度：新建速率、活跃连接数、各 TCP 状态分布、`accept` 队列深度。
- 传输维度：重传率、RTT 分布、零窗口次数、`send` 队列积压。
- 错误维度：RST 计数、`ECONNRESET`、`ETIMEDOUT`、`EMFILE` 与解析失败次数。
- 延迟维度：按阶段拆分 DNS、握手、TLS、TTFB，用直方图统计分位数。
- 资源维度：文件描述符使用率、`somaxconn`、端口范围、conntrack 表占用。
- 指标需带对端、协议与结果标签，同时控制标签基数，避免存储与查询成本失控。

## 16. 跨平台网络编程

### 16.1 Windows 与 POSIX 的套接字句柄有何差异？

- POSIX 用 `int` 文件描述符，套接字与文件共用描述符表；Windows 用 `SOCKET`，其类型为 `UINT_PTR`，64 位平台上为 64 位无符号整数。
- Windows 的套接字句柄与文件句柄不通用，`ReadFile` 与 `WriteFile` 不能直接读写套接字。
- POSIX 上 0 是合法描述符；Windows 上 0 不作为合法套接字使用，`INVALID_SOCKET` 为按位取反的 0。
- 错误获取方式不同：POSIX 读 `errno`，Windows 调 `WSAGetLastError`，套接字错误不会写入 `errno`。
- 关闭函数不同：`close` 与 `closesocket`；关闭正被其他线程使用的套接字时行为由实现定义。
- 超时选项的单位一致，均为毫秒；`accept` 是否受 `SO_RCVTIMEO` 影响由实现定义。

### 16.2 WSAStartup 与 WSACleanup 的作用？

- `WSAStartup(MAKEWORD(2, 2), &wsaData)` 初始化 Winsock 库，加载对应 DLL 并协商版本。
- 每次成功调用使引用计数加一，`WSACleanup` 减一，计数归零才真正卸载。
- 未初始化就调用套接字函数会返回 `WSANOTINITIALISED`。
- 初始化应在进程启动阶段完成，避免多线程并发初始化产生竞态。
- 多模块场景需保证初始化早于任何套接字调用，卸载晚于全部使用结束。
- 请求版本高于系统支持版本时返回 `WSAVERNOTSUPPORTED`，`wsaData.wVersion` 给出实际版本。

### 16.3 IOCP 的完成模型如何工作？

- `CreateIoCompletionPort` 创建完成端口，再用同一函数把套接字句柄关联到端口并指定完成键。
- 读写通过 `OVERLAPPED` 结构提交，内核执行完毕后把完成包排入队列。
- 工作线程调用 `GetQueuedCompletionStatus` 取得完成包，获得字节数、完成键与 `OVERLAPPED` 指针。
- 并发线程数由创建参数决定，传 0 表示每个处理器一个，避免线程争抢导致上下文切换。
- `OVERLAPPED` 与缓冲区必须在操作完成前保持有效，不能放在即将返回的栈帧上。
- `GetQueuedCompletionStatusEx` 一次取多个完成包，减少系统调用次数。
- 取消挂起操作用 `CancelIoEx`，取消仍会产生完成包，需与正常完成一并处理。

### 16.4（辨析）epoll 与 IOCP 的语义差异？

- epoll 是就绪通知：告知哪些描述符当前可读或可写，读写仍由调用者发起。
- IOCP 是完成通知：操作已由内核执行，返回实际传输的字节数。
- 就绪模型允许一次通知后批量处理，完成模型把并发度交给内核与线程池。
- epoll 需配合非阻塞描述符，边缘触发下要读到 `EAGAIN`；IOCP 的挂起操作天然异步。
- 完成模型下缓冲区生命周期由提交者管理，就绪模型下由调用者在使用期间管理。
- `EPOLLONESHOT` 可近似一次性通知，但语义仍是就绪，不改变编程模型。
- 两者都能支撑高并发，差异集中在错误处理路径与取消语义上，不在吞吐上限。

### 16.5 kqueue 的 EV_CLEAR 与 epoll 边缘触发有何异同？

- kqueue 通过 `kevent` 注册 `EVFILT_READ` 与 `EVFILT_WRITE`，`EV_CLEAR` 表示事件报告后清除状态，直到条件再次变化。
- 该行为与 epoll 边缘触发相近，都要求在通知后持续读写直到返回 `EAGAIN`。
- `EV_EOF` 标志直接指示对端关闭，错误码可从 `fflags` 取得。
- `udata` 字段可携带用户指针，省去从描述符反查连接对象。
- kqueue 同时提供定时器 `EVFILT_TIMER` 与信号 `EVFILT_SIGNAL`，事件源比 epoll 更广。
- 不设置 `EV_CLEAR` 即为水平触发，语义与 epoll 默认模式一致。

### 16.6 可移植封装应分几层？

- 句柄层：统一为自有类型，屏蔽 `int` 与 `SOCKET` 的差异，并提供有效性判断。
- 错误层：把 `errno` 与 `WSAGetLastError` 映射为统一枚举或 `std::error_code`。
- 调用层：封装 `socket`、`bind`、`listen`、`accept`、`connect`、`send`、`recv` 与关闭。
- 事件层：统一注册、修改、删除与等待接口，内部按平台选择 epoll、kqueue 或 IOCP。
- 选项层：统一 `TCP_NODELAY`、`SO_REUSEADDR`、`SO_KEEPALIVE` 等语义差异较大的选项。
- 业务代码中不出现平台宏，把 `#ifdef` 限制在少数实现文件内。

### 16.7（实现）错误码如何统一映射？

- 定义内部枚举，如 `would_block`、`in_progress`、`conn_reset`、`timed_out`、`fd_exhausted`。
- POSIX 侧读取 `errno` 后立即保存，后续任何库调用都可能覆盖它。
- Windows 侧调用 `WSAGetLastError`，其值域与 `errno` 完全不同，不能混用。
- 映射需覆盖 `WSAEWOULDBLOCK`、`WSAEINPROGRESS`、`WSAEALREADY`、`WSAECONNRESET` 与 `WSAETIMEDOUT`。
- 可封装为 `std::error_code` 的自定义 category，使错误跨层传递时保留原始码。
- 映射后仍需保留平台原始错误码，排错时需要对照平台文档。

```cpp
std::error_code map_socket_error(int e) {
#ifdef _WIN32
    if (e == WSAEWOULDBLOCK) return net_errc::would_block;
    if (e == WSAEINPROGRESS) return net_errc::in_progress;
    if (e == WSAECONNRESET)  return net_errc::conn_reset;
#else
    if (e == EAGAIN)      return net_errc::would_block;
    if (e == EINPROGRESS) return net_errc::in_progress;
    if (e == ECONNRESET)  return net_errc::conn_reset;
#endif
    return net_errc::unknown;
}
```

### 16.8（陷阱）SOCKET 类型判断有哪些易错点？

- `SOCKET` 在 64 位 Windows 上是无符号 64 位整数，`s < 0` 恒为假。
- 判断失败必须与 `INVALID_SOCKET` 比较，该常量是按位取反的 0。
- 多数套接字函数返回 `int`，失败返回 `SOCKET_ERROR` 即 -1，与句柄判断方式不同。
- POSIX 上描述符可能为 0，不能用真假值区分有效与无效。
- 句柄关闭后其数值可能被复用，持有旧值比较会误判为有效连接。
- 封装应统一提供 `is_valid`，避免业务代码各自判断。

### 16.9（辨析）Windows 与 POSIX 的关闭语义有何不同？

- POSIX 的 `close` 递减引用计数，最后一个描述符关闭时才发送 FIN，复制出的描述符需全部关闭。
- Windows 的 `closesocket` 立即释放套接字；复制套接字需用 `WSADuplicateSocket`，与 `dup` 语义不同。
- 存在挂起的重叠操作时调用 `closesocket`，完成包如何处理由实现定义，通常应先 `CancelIoEx`。
- 关闭后继续操作，POSIX 返回 `EBADF`，Windows 返回 `WSAENOTSOCK`，但句柄可能已被复用。
- 两端都可用 `shutdown` 做半关闭，`SHUT_WR` 发送 FIN 后仍可读取。
- 设置 `SO_LINGER` 且超时为 0 时，两端关闭都会发送 RST 并丢弃未发送数据。

### 16.10（陷阱）非阻塞 connect 在各平台有哪些差异？

- 返回值相同而错误码不同：POSIX 为 `EINPROGRESS`，Windows 为 `WSAEWOULDBLOCK` 或 `WSAEINPROGRESS`。
- 完成通知方式不同：POSIX 等待可写事件，Windows 可用 `select` 或完成端口的完成包。
- 两者都必须查询 `SO_ERROR`，结果为 0 才算连接建立，读取后错误被清除。
- Windows 上 `WSAPoll` 在旧版本中对连接失败的报告不完整，具体行为随系统版本变化，最终仍以 `SO_ERROR` 为准。
- 连接超时需自行计时，超时后调用 `close` 或 `closesocket` 取消。
- 重复调用 `connect` 的错误码不同：POSIX 返回 `EALREADY` 或 `EISCONN`，Windows 返回 `WSAEALREADY` 或 `WSAEISCONN`。

### 16.11（陷阱）select 的 FD_SETSIZE 限制有多大影响？

- POSIX 的 `select` 受 `FD_SETSIZE` 限制，glibc 默认为 1024，描述符超限会越界写入 `fd_set`。
- Windows 的 `fd_set` 是计数加数组的结构，默认 `FD_SETSIZE` 为 64，可在包含头文件前重定义。
- Windows 的 `select` 忽略第一个参数，重定义上限后可容纳更多套接字。
- `select` 每次调用都要把集合从用户态复制到内核并线性扫描，连接数大时开销显著。
- `poll` 没有固定上限但仍是线性扫描，只有 epoll 与 kqueue 能按就绪事件返回。
- 跨平台封装不宜把 `select` 作为主事件循环，只适合连接数很小的场景。

### 16.12 事件循环如何跨线程唤醒？

- Linux 用 `eventfd`，写入 8 字节即可唤醒 `epoll_wait`，读取后计数清零。
- 可移植方案用自管道，把读端注册到事件循环，写入 1 字节触发。
- Windows 可用 `PostQueuedCompletionStatus` 向完成端口投递自定义完成包。
- 也可用 `WSAEventSelect` 配合 `WSAWaitForMultipleEvents`，单次等待上限为 64 个事件。
- 唤醒后应一次性排空任务队列，避免每个任务触发一次系统调用。
- 关闭循环时先停止接受新任务，再唤醒并等待工作线程退出。

### 16.13 定时器如何跨平台实现？

- Linux 可用 `timerfd` 把超时转为可读事件，与 epoll 统一处理。
- kqueue 用 `EVFILT_TIMER`，支持一次性与周期性触发，精度为毫秒。
- Windows 可用可等待计时器配合 `WaitForMultipleObjects`，也可直接用等待超时。
- 通用做法是维护按到期时间排序的最小堆，等待超时取堆顶与当前时间之差。
- 大量定时器需用时间轮或分层时间轮，降低插入与删除的复杂度。
- 定时器回调中不应执行阻塞操作，否则会推迟同一循环内的其他超时。

### 16.14（场景）边缘触发模型在 Windows 上如何落地？

- Windows 没有边缘触发概念，需把「读到 `EAGAIN` 为止」改为「提交重叠读，完成后再提交」。
- 每个方向只挂一个操作，完成后立即续投，避免同一方向并发提交。
- 连接对象持有 `OVERLAPPED`、缓冲区与状态机，生命周期与挂起操作绑定。
- 关闭前先 `CancelIoEx` 并等待完成包，防止缓冲区在回调执行前被释放。
- `WSAECONNRESET` 与 `WSAECONNABORTED` 应按对端关闭处理，不应视为致命错误。
- 抽象层应暴露「提交读」「提交写」「关闭」三个动作，不必模拟就绪事件。

### 16.15（实现）跨平台的发送队列如何管理？

- `send` 返回值小于请求长度表示部分写入，剩余部分进入发送队列。
- 队列非空时不继续调用 `send`，等待可写事件后续写。
- 队列上限决定背压强度，超限时暂停读取上游或断开慢消费者。
- POSIX 上 `send` 返回 `EAGAIN` 表示内核缓冲区满，Windows 上对应 `WSAEWOULDBLOCK`。
- 重叠发送未完成前不能复用同一缓冲区，需按完成包推进偏移。
- `recv` 返回 0 表示对端已关闭，应停止读取并在写完剩余数据后关闭。

### 16.16 字节序转换有哪些平台差异？

- `htonl`、`htons`、`ntohl`、`ntohs` 处理 16 位与 32 位整数，各平台均提供。
- 64 位整数没有标准转换函数，需用两次 32 位转换组合，或使用平台扩展。
- 大端平台上转换函数是恒等映射，不能据此假设网络序与主机序总是不同。
- Windows 需包含 `winsock2.h`，且应在 `windows.h` 之前包含，否则可能出现重定义。
- 浮点数与结构体不能按内存字节直接发送，需定义明确的字段布局与编码。
- 协议字段应显式按固定宽度类型读写，避免依赖 `int` 的平台宽度。

### 16.17（陷阱）SO_REUSEADDR 在各平台语义相同吗？

- BSD 与 Linux 上，`SO_REUSEADDR` 主要用于绕过 `TIME_WAIT` 占用，不能与正在监听的套接字冲突。
- Windows 上该选项允许绑定已被其他套接字占用的地址，语义更宽，可能造成端口被抢占。
- Windows 提供 `SO_EXCLUSIVEADDRUSE` 独占绑定，服务端通常应启用它。
- 允许与已监听端口绑定的具体行为由实现定义，跨平台代码不能依赖统一语义。
- `SO_REUSEPORT` 在 Linux 与部分 BSD 上支持，可实现多进程分摊，Windows 不提供。
- 端口复用与 `SO_LINGER` 组合会影响重启行为，需结合部署方式验证。

### 16.18 SIGPIPE 与 TCP_NODELAY 的平台差异？

- Linux 上向已关闭连接写入会收到 `SIGPIPE`，默认终止进程；可用 `MSG_NOSIGNAL` 或忽略该信号避免。
- macOS 没有 `MSG_NOSIGNAL`，需设置 `SO_NOSIGPIPE`。
- Windows 不产生 `SIGPIPE`，写入返回 `WSAECONNRESET` 或 `WSAECONNABORTED`。
- 忽略 `SIGPIPE` 影响整个进程，库代码不宜擅自修改信号处置。
- `TCP_NODELAY` 默认关闭，小包会等待 Nagle 算法合并，与延迟确认叠加可产生数十毫秒延迟。
- 延迟确认的超时由实现定义，Linux 常见为 40 ms，Windows 常见为 200 ms。

### 16.19 跨平台网络库的抽象边界在哪？

- Asio 统一暴露异步接口，Windows 上基于 IOCP，POSIX 上基于 epoll 或 kqueue。
- libuv 提供句柄与回调，内部同样按平台选择完成端口或事件轮询。
- 抽象无法完全抹平差异：缓冲区生命周期、取消语义与错误码仍需平台分支。
- 协程封装可降低回调复杂度，但取消与超时语义需要显式传播。
- 引入第三方库需评估 ABI 兼容、构建依赖与调试支持，不能只看接口是否简洁。
- 自研封装的成本主要在错误处理与测试矩阵，接口层通常只占少量工作量。

### 16.20 移植后的测试矩阵如何设计？

- 覆盖 Windows、Linux、macOS，以及各主流编译器的 32 位与 64 位构建。
- 覆盖 IPv4、IPv6、双栈监听与仅 IPv6 监听等模式。
- 注入错误：连接被拒绝、对端重置、半关闭、超时、`EMFILE`、地址占用。
- 用代理或故障注入工具模拟丢包、延迟、乱序与带宽限制。
- 对事件循环做压力测试，验证大量连接下的关闭路径与缓冲区回收。
- 用 sanitizer 与静态分析检查缓冲区生命周期，尤其是重叠 I/O 的完成回调。
- 记录各平台的行为差异并固化为回归用例，避免依赖人工记忆。

## 17. 网络设计题

### 17.1 设计一个 HTTP 服务器，连接与请求如何处理？

- 监听套接字设为非阻塞，事件循环中 `accept` 直到返回 `EAGAIN`。
- 每个连接维护读缓冲、解析状态机与写队列，请求行与头部按 CRLF 切分并设长度上限。
- 解析完成后按 `Content-Length` 或 `Transfer-Encoding: chunked` 读取请求体。
- 请求体超过上限返回 413，头部超限返回 431，并关闭连接。
- 响应按状态行、头部、体的顺序写入写队列，未写完时注册可写事件。
- 支持 `Connection: keep-alive` 时复用连接，并设置空闲超时。
- 关闭时先停止读，写完剩余响应，再 `shutdown` 与 `close`。

### 17.2 HTTP/1.1 与 HTTP/2 的实现代价差异？

- HTTP/1.1 每连接一个在途请求，靠多条连接提升并发，解析器只需处理文本头部。
- HTTP/2 使用二进制帧与流标识实现多路复用，需实现帧编解码、流状态机与优先级处理。
- HPACK 需维护静态表与动态表，头部压缩节省带宽，同时增加状态同步复杂度。
- 流量控制分连接与流两级窗口，发送端按窗口分片，接收端需及时回 WINDOW_UPDATE。
- 一条连接承载全部请求，丢包时队头阻塞影响该连接上的所有流。
- 服务端推送在 HTTP/2 中已较少使用，HTTP/3 改用 QUIC 在用户态实现可靠传输。

### 17.3（场景）慢请求攻击如何防御？

- 限制请求行与头部的总大小和数量，超限立即返回 431 或 400 并关闭。
- 分别设置头部读取超时与请求体读取超时，两个阶段独立计时。
- 限制单连接最小数据速率，长时间低速传输的连接直接断开。
- 限制单 IP 的并发连接数与新建速率，可用令牌桶实现。
- 接收请求体前先检查 `Content-Length`，超限直接拒绝，不读取剩余数据。
- keep-alive 空闲连接设置较短超时，避免长期占用文件描述符。
- 反向代理层先做缓冲与限速，应用层只处理已收全的请求。

### 17.4 RPC 框架的调用语义层需要哪些字段？

- 方法标识使用稳定的数字 ID 或全限定名，避免依赖字符串比较与运行时反射。
- 序列号用于匹配请求与响应，使单连接上的并发调用互不干扰。
- 截止时间随请求下传，服务端据此放弃已超时的工作，避免无效计算。
- 取消操作单独定义消息类型，服务端收到后终止执行并回送最终状态。
- 状态码区分应用错误与传输错误，错误详情可携带结构化的附加信息。
- 元数据以键值对承载鉴权、链路追踪与灰度标记。
- 幂等标记由调用方声明，服务端据此决定是否按请求 ID 去重。

### 17.5 超时、重试与幂等如何配合？

- 只有幂等方法或带幂等键的请求才可自动重试，写操作重试前需服务端去重。
- 重试预算按比例控制，例如失败请求的重试量不超过总请求量的一成。
- 退避采用指数增长加随机抖动，避免重试同步形成脉冲。
- 单次超时与总预算分离，重试不得突破调用方给定的截止时间。
- 连接建立失败与请求已发出后的失败需区别对待，后者可能已在服务端生效。
- 重试应切换到其他实例，并配合熔断避免持续打到故障节点。
- 记录重试次数与原因，用于区分系统性故障与偶发抖动。

### 17.6（辨析）正向代理与反向代理的区别？

- 正向代理代表客户端，客户端显式配置代理地址，代理可访问客户端无法直连的资源。
- 反向代理代表服务端，客户端认为访问的是源站，代理负责转发与负载均衡。
- 正向代理需处理 `CONNECT` 以支持 HTTPS 隧道，反向代理通常直接终止 TLS。
- 反向代理改写 `X-Forwarded-For` 与 `X-Forwarded-Proto`，正向代理更关注访问控制与缓存。
- 缓存对象不同：正向代理缓存公共资源，反向代理缓存源站响应。
- 故障域不同：正向代理故障影响一批客户端，反向代理故障影响一个服务入口。

### 17.7 CONNECT 隧道与 TLS 直通如何实现？

- 客户端发送 `CONNECT host:port HTTP/1.1`，代理建立上游连接后返回 `200 Connection Established`。
- 之后代理只做字节双向转发，不解析 TLS 内容，证书由目标服务器提供。
- 双向转发需处理半关闭：一个方向读到 EOF 后 `shutdown` 对应方向，另一方向继续。
- 为隧道设置空闲超时与流量上限，避免长期占用连接与带宽。
- TLS 直通可在四层按 SNI 分流，需解析 ClientHello 中的 SNI 扩展。
- 若要在七层检查内容，必须终止 TLS 并重新签发证书，客户端需信任代理的 CA。

### 17.8 连接池大小如何与后端并发模型匹配？

- 池大小按并发请求数与单请求占用连接的时长估算，二者相乘即在途连接数。
- 后端为每个连接分配线程时，池上限不得超过后端可并发处理的连接数。
- 后端使用事件循环或协程时，约束来自内存与文件描述符，而非线程数。
- HTTP/2 与 gRPC 可在单连接上多路复用，池的作用从提升并发变为故障隔离与分摊。
- 全局共享池与按目标划分子池的取舍，取决于目标数量与流量分布。
- 连接建立包含 TCP 与 TLS 往返，池预热决定冷启动阶段首批请求的延迟。
- 池过大时排队转移至内核与后端，指标表现为延迟升高而吞吐不变。

### 17.9 网关如何用熔断与隔离防止雪崩？

- 熔断器统计失败率与慢调用比例，达到阈值后打开，后续请求直接拒绝。
- 半开状态放行少量探测请求，成功后闭合，失败则重新打开并延长冷却时间。
- 隔离按依赖或租户划分线程池、连接池与信号量，避免单一依赖耗尽全部资源。
- 下游超时需短于上游剩余预算，否则熔断来不及在调用方超时前生效。
- 降级返回缓存、默认值或简化结果，需与业务确认可接受的语义。
- 失败率统计需区分错误类型，连接拒绝与业务校验失败不应合并计算。
- 指标需暴露熔断状态与拒绝量，否则故障会被误判为容量不足。

### 17.10 推送服务选长连接还是轮询？

- 轮询实现简单、服务端无状态，代价是空轮询浪费带宽与电量，实时性受间隔限制。
- 长轮询在无数据时挂起请求，有数据或超时后返回，能复用 HTTP 基础设施。
- WebSocket 提供全双工长连接，适合频繁双向交互，需处理心跳、重连与背压。
- SSE 基于 HTTP 单向推送，支持自动重连，适合服务端到客户端的通知流。
- 移动端受系统后台限制，通常依赖厂商推送通道，自建长连接只在前台运行。
- 连接数决定服务端内存与文件描述符开销，需按在线用户规模估算容量。

### 17.11（场景）推送服务如何保证消息不丢与有序？

- 每个会话维护单调递增的序号，客户端按序号去重与排序，断线后上报已收的最大序号。
- 服务端保留最近一段离线消息，或写入消息队列，补发时按序号区间拉取。
- 发送与确认分离：服务端发出后等待客户端 ACK，超时重发，重复由序号幂等消化。
- 顺序只在单会话内保证，多设备与多连接场景需降级为最终一致。
- 补发窗口设上限，超出后让客户端走全量同步，避免无限堆积。
- 连接重建后先补发缺口再进入增量推送，避免新消息越过旧消息。
- 指标区分发送成功、送达确认与客户端消费，三者之间的缺口指向不同故障。

### 17.12 广播扇出如何避免慢消费者影响整体吞吐？

- 每条连接维护独立发送队列，并为队列长度设上限。
- 队列满时按策略处理：丢弃旧消息、断开连接或降级为拉取模式。
- 广播只写入队列，由各连接的可写事件驱动实际发送，避免在广播线程中阻塞。
- 同一消息只序列化一次，多个连接共享只读缓冲，减少复制与内存占用。
- 按主题分组并批量发送，降低系统调用次数与协议头开销。
- 监控队列深度与丢弃计数，识别慢消费者与热点主题。
- 大规模扇出可采用分层转发，由边缘节点承担最后一跳。

### 17.13 网关限流如何设计？

- 令牌桶允许一定突发，漏桶输出更平滑，按业务对突发的容忍度选择。
- 限流键可为用户、IP、接口或租户，需控制键的基数。
- 超出限额返回 429 并带 `Retry-After`，客户端据此退避。
- 分布式限流需共享计数，可用集中式存储或令牌预分配，注意同步开销与单点风险。
- 本地限流加配额分配可减少中心依赖，代价是全局精度下降。
- 排队与拒绝的取舍取决于请求可延迟性，同步接口通常直接拒绝。
- 阈值应结合后端容量与下游依赖的承受能力设定。

```cpp
bool allow(TokenBucket& b, double cost, long long now_ms) {
    double dt = (now_ms - b.last_ms) / 1000.0;
    b.tokens = std::min(b.capacity, b.tokens + dt * b.rate);
    b.last_ms = now_ms;
    if (b.tokens < cost) return false;
    b.tokens -= cost;
    return true;
}
```

### 17.14 会话粘性与一致性哈希如何取舍？

- 粘性会话保证同一用户命中同一实例，适合有本地缓存的场景。
- 一致性哈希在扩缩容时只迁移部分键，减少缓存失效。
- 粘性依赖负载均衡器的会话表，实例故障时会话随之丢失。
- 无状态化把会话放入共享存储或令牌，可自由调度，代价是额外一次远程访问。
- 一致性哈希配合局部性可兼顾缓存命中与分布均衡。
- 缩容时先摘流量并等待会话自然结束，避免强制迁移。

### 17.15 背压如何贯穿整条链路？

- 每层设置队列上限，队列满时向上游返回可识别的拥塞信号。
- HTTP 层可用 429 或 503，RPC 层可用特定状态码与重试提示。
- TCP 通过接收窗口自然背压，但应用层缓冲会吸收并掩盖压力。
- 流式协议可用流量控制窗口，如 HTTP/2 的 WINDOW_UPDATE。
- 写队列超过高水位时暂停读取上游，低于低水位时恢复。
- 背压必须端到端传播，只在最后一层限流时，中间层队列会持续增长直至耗尽内存。
- 监控队列深度与处理速率的差值，提前发现积压。

### 17.16 反向代理如何设计响应缓存？

- 缓存键由方法、URL 与 `Vary` 指定的头部组成，含鉴权信息的响应不得进入共享缓存。
- 依据 `Cache-Control` 的 `max-age`、`s-maxage`、`no-store` 与 `private` 决定是否缓存。
- 过期后可用 `stale-while-revalidate` 先返回旧内容，同时在后台刷新。
- 同一键的并发未命中需合并回源，避免同时打到源站。
- 缓存对象按大小与热度淘汰，超过阈值的响应单独处理或不缓存。
- 带 `Set-Cookie` 与 `Authorization` 的响应默认不缓存，需显式配置例外。
- 失效以键为单位精确删除，按 URL 前缀删除在带查询参数时容易漏删。

### 17.17 服务发现与健康检查如何集成？

- 注册中心保存实例地址与元数据，客户端通过 watch 或轮询获取变更。
- 主动健康检查由注册中心发起，被动检查依据真实请求的成功率与延迟。
- 被动剔除对连续失败的实例临时降权，恢复后逐步放量。
- 摘除与恢复都需迟滞，避免实例在临界状态反复进出。
- 客户端缓存实例列表，注册中心不可用时仍可按旧列表工作。
- 需处理网络分区：注册中心视角的失联不等于实例不可用。

### 17.18 超时预算如何分配？

- 调用方给定总截止时间，逐跳扣减已消耗时间，不按每跳设置固定超时。
- 下游超时必须小于上游剩余预算，否则上游先超时，下游的工作随之作废。
- 预算需扣除排队与序列化开销，并预留余量。
- 重试消耗同一预算，重试次数受剩余时间约束。
- 跨进程传递截止时间需协议支持，如 gRPC 的 `grpc-timeout` 头部。
- 超时值应基于延迟分布设定，如 p99 加余量；平均值会低估长尾。

### 17.19 可观测性指标如何设计？

- 请求维度用速率、错误率与延迟分布，即 RED 方法。
- 资源维度用利用率、饱和度与错误，即 USE 方法。
- 延迟使用直方图并关注 p99 与 p999，平均值会掩盖长尾。
- 指标标签控制基数，避免用户 ID 与请求 ID 进入标签。
- 链路追踪记录跨服务调用与耗时分解，采样率按流量调整。
- 日志带请求 ID 并与追踪关联，便于从指标下钻到单次请求。
- 告警基于用户可感知的症状，减少由原因指标触发的无效告警。

### 17.20（场景）容量如何估算？

- 连接数上限受文件描述符、内存与内核参数约束，`somaxconn` 与 `backlog` 决定排队能力。
- 每连接内存包含内核套接字缓冲与用户态读写缓冲，按 `rmem`、`wmem` 与队列上限估算。
- 带宽按峰值消息大小乘以消息速率估算，并留出协议头与重传余量。
- CPU 按每请求处理开销与加解密开销估算，TLS 握手单独计。
- 压测需覆盖长连接保持、混合读写比例与故障切换场景。
- 容量规划保留冗余，单实例故障后其余实例不应过载。
- 用排队论粗算等待时间，避免把平均利用率设在接近饱和的位置。
