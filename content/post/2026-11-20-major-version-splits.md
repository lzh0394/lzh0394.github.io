> 软件版本号本来只是发布节奏的刻度，但有些刻度一旦跨过去，旧世界和新世界就不再互通。本文讨论的「大版本分裂」，指一次版本更替同时满足三个条件：新旧版本不兼容、旧版本仍被大量使用或维护、生态被迫在两者之间做选择。它不包括单纯的功能升级，也不包括因许可证或治理争议产生的代码分叉——后者是另一条线，文中只在需要对照时提一句。
>
> 事实口径：以各项目官方发布说明、PEP/RFC、TC39 记录和厂商公告为准；日期尽量精确到日，记不准则写「约」；英文维基只用来找线索。文中的「分裂」是描述性说法，不带褒贬。

## 0. 总览

语言与标准层面的分裂案例：

| 案例 | 时间 | 分裂形态 | 结局 |
| --- | --- | --- | --- |
| Python 2 与 Python 3 | 2008–2020 | 同一语言的硬断代 | 迁移完成，历时约 12 年 |
| Perl 5 与 Perl 6 / Raku | 2000–2019 | 重写导致事实分家 | 两门语言并存，各自维护 |
| ECMAScript 4 与 3.1 | 2000 年代–2008 | 标准层面的路线分裂 | ES4 被放弃，思想进入 ES6 |
| PHP 4/5/6 | 2004–2015 | 换代、跳号与取消 | PHP 7 重新统一 |
| Ruby 1.8 与 1.9 | 2007–2013 | 小版本号、大断裂 | 2.x 收敛 |

平台、框架与桌面层面的案例：

| 案例 | 时间 | 分裂形态 | 结局 |
| --- | --- | --- | --- |
| VB6 与 VB.NET | 1998–2008 | 平台厂商单方面断代 | 社区分流，旧栈长期残留 |
| .NET Framework 与 .NET Core | 2002–2020 | 同一品牌下的平台分裂 | .NET 5 起统一 |
| AngularJS 与 Angular | 2012–2021 | 框架整体重写 | 并存到 AngularJS 停止支持 |
| Mac OS 9 与 Mac OS X | 1999–2007 | 操作系统换代 | 完成，Classic 环境退场 |
| KDE 3 与 KDE 4 | 2008 | 桌面大版本重写 | Trinity 分叉，主干前行 |
| GNOME 2 与 GNOME 3 | 2011 | 桌面交互范式改变 | MATE、Unity 分流 |
| Windows 9x 与 NT | 1993–2001 | 双产品线并行 | XP 合并为一条线 |

一句话结论：分裂的触发点几乎总是「旧设计的兼容性债」和「谁有权宣布断代」，而分裂的结局取决于有没有强制力、有没有迁移工具、以及下游生态是否愿意跟。

## 1. 什么算「大版本分裂」

「大版本」在软件里没有统一定义。语义化版本把主版本号留给不兼容变更，但真正的不兼容有大有小：删掉一个函数是主版本变更，换掉整个运行时也是。日常说的「大版本升级」绝大多数只是发布仪式，用户改几行代码就过去了；真正会留下时代断层的是下面这几种。

第一，同一条产品线的硬断代。新版本取代旧版本，但旧版本还在跑，官方一边说「请升级」，一边不得不继续给旧版本打安全补丁。Python 2 与 Python 3 是标准样本。

第二，重写之后借用了旧名字。新项目在名义上是「下一代」，实际上语法、运行时、生态全部重来，迁移无法机械化。Perl 6 是标准样本。

第三，标准层面的路线之争。参与方对下一代规范的范围与优先级谈不拢，一部分人另起炉灶，最后某一方被取消。ECMAScript 4 是标准样本。

第四，平台或框架换代。操作系统、运行时、UI 框架整体换代，兼容层只能覆盖一部分。Mac OS 9 到 Mac OS X、KDE 3 到 KDE 4、.NET Framework 到 .NET Core 都属于这一类。

还有第五种，版本号被跳过。计划中的大版本因为工程失败没有发布，后续版本直接改了号。PHP 6 是标准样本：它从未发布，但它的失败改变了 PHP 的版本节奏。

把这几种和「代码分叉」（fork）区分开是有必要的。fork 是同一个时间点上代码与社区的复制，比如 XEmacs 从 GNU Emacs 分出、EGCS 从 GCC 分出、io.js 从 Node.js 分出；大版本分裂是同一条血脉在时间轴上的断代，两边通常仍共享历史、文档和一部分用户。两者的交集在于：当断代由社区而不是原维护者推动时，版本分裂往往以 fork 的形式落地——MATE 之于 GNOME 2、Trinity 之于 KDE 3 都是如此。

判断一次升级是否已经构成分裂，可以看四个信号：官方是否停止旧版支持、主流第三方库是否开始双轨维护、发行版或云厂商是否切换默认版本、新项目与教程是否不再提旧版。四个信号都亮，才算真正跨过分界线。下文挑选案例时另加两个条件：影响持续五年以上，且有一手公开记录可查。

## 2. Python 2 与 Python 3：计划了十二年的分手

### 2.1 为什么要重来

Python 由 Guido van Rossum 在 1989 年底开始写，1991 年发布 0.9.0，2000 年发布 2.0。到 2000 年代中期，这门语言积下了一批无法在 2.x 里干净修掉的设计问题：

- print 是语句而不是函数，导致它无法被替换、无法被装饰，也堵死了「统一用函数表达副作用」的演进路线；
- 文本 str 与字节 bytes 混为一谈，Unicode 支持是后补的，编码错误在跨平台时反复出现；
- 整数除法 / 对整数做截断，想得到浮点结果必须写 from `__future__` import division；
- 异常语法是 except E, e，与后来的 with、生成器等新语法风格不一致；
- 标准库布局老化，urllib、urllib2、urlparse 各管一摊；
- 旧式类与新式类两套对象模型并存。

这些问题单看都能忍，合在一起就是「语言被早期设计锁死」。2000 年代中期，核心开发者开始讨论一次不向后兼容的大清理，项目内部称为 Python 3000 或 Py3K，后来以 PEP 3000 系列文档固定下来。方向很明确：与其在 2.x 上继续打补丁，不如一次性还债。

### 2.2 时间线

2008 年 12 月 3 日，Python 3.0 发布。它和 2.x 的差异是全方位的：print 变成函数，str 默认是 Unicode 文本、bytes 单独表示字节，/ 变成真除法、整除改用 //，异常改为 except E as e，标准库重新组织，range、map、filter 返回迭代器。官方同时提供了 2to3 工具，试图把 2.x 源码自动改写成 3.x 语法。

2010 年 7 月 3 日，Python 2.7 发布，官方明确它是 2.x 的最后一个特性版本。此后 2.7 只收安全修复。原本设想的过渡期是五年，实际一再延长：2014 年，核心团队宣布 2.7 的支持延续到 2020 年；2020 年 1 月 1 日，Python 2 正式停止支持；2020 年 4 月 20 日，最后一个版本 2.7.18 作为告别发行。

另一边，3.x 用一系列版本把新语言补齐：3.3 的 yield from、3.4 的 asyncio、3.5 的 async/await、3.6 的 f-string、3.7 的 dataclass、3.8 的海象运算符、3.9 的字典合并运算符、3.10 的结构化模式匹配，以及 3.11 之后以「更快」为目标的解释器优化。到 3.13（2024 年 10 月）时，Python 3 已经演进了十六年，早期移植期的粗糙感基本消失。

### 2.3 迁移为什么慢

2to3 是这次迁移最值得研究的工具，因为它清楚地展示了自动化的边界。它能把 print x 改成 print(x)、把 except E, e 改成 except E as e、把 xrange 改成 range，但它改不了这些之外的东西：

- 语义差异。整数除法、Unicode 与字节的边界、字典遍历顺序与视图对象、排序比较函数，这些没有机械替换规则，只能逐个模块判断；
- 第三方依赖。一个应用能不能迁，取决于它依赖的库有没有迁；而库作者又取决于更底层的库。迁移顺序天然是「标准库 → 基础库 → 框架 → 应用 → 发行版」，链条很长；
- 测试覆盖。没有测试的项目无法确认迁移后的行为一致，于是只能靠人工回归；
- 组织惰性。企业环境里，「能跑就别动」是理性选择，尤其当旧版本还能拿到商业支持时。

因此社区在 2010 年代发明了双栈写法：six 提供兼容层，python-future 提供另一套，库作者同时维护 2 和 3 两个版本，CI 跑两个解释器。这套办法有效，但成本是长期的：每个库都要为一段过渡期付双份维护费。

真正的转折来自生态的合力：Django、NumPy、pandas 等主流框架逐步放弃 2.7；pip 21.0（2021 年 1 月）停止支持 Python 2；各大发行版把默认解释器切到 3，RHEL/CentOS 7 因为生命周期长，把 Python 2.7 一直留到 2024 年 6 月系统退役。到 2020 年前后，继续留在 2.7 的理由只剩下「旧系统动不了」，而不是「3 还不够好」。

### 2.4 结果与代价

按「有没有完成」衡量，Python 2 到 3 是成功的：今天新代码默认 Python 3，2.7 只剩遗留系统与嵌入式场景。但代价同样清楚：十二年里，社区同时维护两套文档、两套教程、两套兼容代码，招聘与教学被迫标注版本；2to3 在真实项目里的成功率远低于宣传，它本身也在 Python 3.13（2024 年 10 月）从标准库中移除；「Python 3 墙」（社区用来记录尚未迁移的库的名单）存在了好几年才逐渐清空。

这次迁移留下的经验后来被反复引用：断代必须有明确的截止日期，必须有工具降低机械成本，必须让生态先动起来，最后必须真的停掉旧版本。四条缺一条，过渡期就会无限延长。Python 3 之后的版本管理也明显吸取了教训：PEP 387 规定了向后兼容与弃用流程，新特性先经过 `__future__` 或可选开关，大版本不再搞「一次性重来」。

## 3. Perl 5 与 Perl 6/Raku：改着改着成了另一门语言

### 3.1 出发点

Perl 5 于 1994 年 10 月发布，是 1990 年代 Web 与系统管理领域最实用的胶水语言。它的设计哲学是「条条大路通罗马」：语法宽松、上下文敏感、正则表达式内置、CPAN 生态庞大。到 1990 年代末，Perl 5 的语法与运行时也开始显老：对象系统是后加的、类型系统几乎没有、并发与线程模型薄弱、解析器与虚拟机耦合。

2000 年 7 月 19 日，Larry Wall 在 O'Reilly 开源大会上发表「State of the Onion」演讲，宣布启动 Perl 6。最初的设想不是「Perl 5 的 6.0」，而是重新设计一门语言：更规整的语法、真正的类型与多重分派、内置并发、可扩展的语法（grammar）、以及一个能同时运行其他语言的虚拟机。为了收集需求，社区在 2000–2001 年提交了三百多份 RFC。

关键在于，兼容 Perl 5 从来不是硬目标。设计文档里明确写着 Perl 6 是「姊妹语言」，会借鉴 Perl 5 的很多想法，但不会保证旧代码能跑。这个决定在当时被认为是合理的：Perl 5 的历史包袱太重，小修小补走不远。但它也埋下了后来的分家。

### 3.2 设计过程与实现

Perl 6 的规格以「Apocalypse」（启示录）与「Exegesis」（注解）系列文档形式逐章发布，语言设计本身持续了十余年。实现路线换过好几次：先是 2001 年启动的 Parrot 虚拟机，目标是承载多种动态语言；2005 年出现用 Haskell 写的 Pugs，作为规格的可执行原型；2007 年启动的 Rakudo，在 Pugs 停摆后成为主实现，2013 年转到自研的 MoarVM 上。

2015 年 12 月 25 日，Perl 6.c（圣诞版）发布，被当作第一个可用的正式版本；2019 年 10 月，Perl 6 更名为 Raku，此后版本号改用年月，例如 Raku 2020.01。更名是一个务实的决定：既然它和 Perl 5 已经是两门语言，继续共用一个名字只会让用户困惑。

### 3.3 为什么变成了分家

Perl 6 与 Perl 5 的差异是语言级别的：语法不同、对象模型不同、正则引擎不同（Raku 的规则是语法的一部分）、运行时不同，CPAN 上的模块基本不能直接用，需要 Inline::Perl5 之类的桥接。这意味着迁移不是「改代码」，而是「重写」。

结果就是长期并存：

- Perl 5 继续按自己的节奏发布，5.44 于 2026 年 7 月发布；大量生产系统、发行版脚本、CPAN 模块仍建立在 5 上；
- Raku 有独立社区、独立文档、独立包管理（zef），语言能力更强，但用户规模远小于 Perl 5；
- 两边共享一部分历史与人物，但在工程上几乎不共享代码。

这不是一次「失败的升级」，而是一次成功的「新语言孵化」——只是它借用了一个让人误以为是升级的名字。2019 年的更名，本质上是对这个既成事实的追认。

### 3.4 和 Python 的对照

把 Perl 6 与 Python 3 放在一起看，会发现决定结局的不是投入多少，而是新旧之间有没有一条可机械化的迁移路径：

- Python 3 是同一门语言的下一代：语法差异有规则，标准库有映射，2to3 和 six 能覆盖大部分机械工作，剩下的靠测试补齐。所以它虽然慢，但终点明确；
- Perl 6 是另一门语言：没有等价映射，没有自动迁移，连「哪些代码需要改」都无法静态判定。所以它不可能作为「升级」被接受，只能作为「新语言」被采用。

教训很直接：版本号是承诺。把重写包装成新版本，短期能借旧名字获得关注，长期会让旧用户觉得被抛弃、新用户觉得门槛高。反过来，如果确实要重写，就该像 Raku 那样早点承认它是新语言，把名字、生态、治理都分开。

## 4. 标准和语言层面的其他断代

Python 与 Perl 之外，还有几次分裂发生在规范或版本号层面，形态各不相同。

### 4.1 ECMAScript 4：被放弃的版本

1999 年发布的 ECMAScript 3（ES3）是 JavaScript 的基础。2000 年代，TC39 开始设计 ES4，目标是大幅扩展语言：类、命名空间、包、类型标注、生成器、运算符重载。Adobe 与 Mozilla 是积极推动方，Adobe 甚至把 ES4 的大量特性实现在 ActionScript 3 里，随 Flash Player 9（2006 年）发布。

微软与 Yahoo 反对这条路线，理由很实际：ES4 太大、太激进，浏览器厂商实现成本高，且会破坏现有网页。2007 年 ES4 草案公布后，分歧公开化。2008 年 8 月，TC39 达成妥协，放弃 ES4，转向代号「Harmony」的新路线（在 ECMA 的版本表里，第 4 版直接标注为「不存在」）：先发布一个小的、向后兼容的 ES5（2009 年 12 月），再把 ES4 的想法拆成可增量落地的特性，最终在 ES6（2015 年 6 月）里交付了类、模块、let/const、生成器、Promise 等大部分内容。

结局是分裂没有发生：没有两个互不兼容的 JavaScript 版本同时存在于浏览器里。但代价是六年的标准空窗期，以及 ActionScript 3 这条「提前实现 ES4」的支线最终随 Flash 一起退场。这个案例说明，标准层面的分裂往往以「一方被取消」收场，而它的思想会以兼容的方式回流。

### 4.2 PHP 4→5 与被取消的 PHP 6

PHP 4 于 2000 年发布，PHP 5 于 2004 年 7 月发布。PHP 5 把对象模型整体重写（Zend Engine 2），引入可见性、接口、抽象类、异常，从「脚本集合」转向「面向对象语言」。PHP 4 并没有立刻退场，一直维护到 2008 年 8 月，期间大量主机商与遗留系统停留在 4 上。2008 年 2 月，GoPHP5 联署生效，主流框架与 CMS 宣布新代码不再支持 PHP 4，生态切换才真正加速。

真正戏剧性的是 PHP 6。它在 2005 年前后启动，核心目标是把 Unicode 支持做进语言层；工程复杂度远超预期，加上社区对「所有字符串都变 Unicode」的顾虑，项目在 2010 年被取消。它的部分成果被拆进 PHP 5.3（命名空间、闭包，2009 年 6 月）与 PHP 5.4（trait，2012 年 3 月），而「PHP 6」这个版本号被永久跳过。2015 年 12 月，PHP 7 发布，以性能翻倍为主要卖点，重新统一了生态。

PHP 的案例提醒一件事：分裂不只表现为「发两个版本」，也表现为「计划中的版本消失」。版本号的连续性本身就是生态预期的一部分，跳过它需要一次成功的下一代发布来弥补。

### 4.3 Ruby 1.8 与 1.9：小版本号，大断裂

Ruby 1.8 于 2003 年发布，1.9.0 于 2007 年 12 月 25 日发布。按版本号看这只是第二位数字的变化，实际却是一次彻底重构；官方把 1.9 系列定位为开发版，直到 1.9.1（2009 年 1 月）才可用于生产：新的字节码虚拟机（YARV）、多语言化（M17N）带来的编码模型、块参数与 lambda 语法变化、String 的遍历语义变化。大量 1.8 时代写的 gem 在 1.9 上需要改动，Rails 生态被迫在很长一段时间里同时支持两个版本。

Ruby 社区的处理方式是并行维护：1.8.7 与 1.9.x 同时发布安全更新，1.9.3（2011 年）成为过渡期的事实标准，2.0（2013 年 2 月）之后才逐渐收敛。1.8.7 在 2013 年 6 月停止支持，1.9.3 在 2016 年 2 月停止支持。此后 Ruby 2.x 大体维持向后兼容，不再出现同等级别的断裂。

### 4.4 VB6 与 VB.NET：平台厂商的断代

Visual Basic 6 于 1998 年发布，是 Windows 桌面与 COM 组件开发的主力工具，拥有庞大的企业开发者群体。2002 年 2 月，微软随 Visual Studio .NET 2002 发布 VB.NET。这不是 VB6 的升级版，而是一门运行在 .NET 上的新语言：没有 On Error GoTo、没有默认属性、没有 COM 式对象生命周期，字符串与数组语义也不同。微软提供的升级向导只能处理最简单的项目。

微软在 2005 年结束 VB6 的主流支持，2008 年 4 月结束扩展支持；社区发起过请愿，希望保留经典 VB 的开发环境，未获采纳。作为补偿，微软长期保证 VB6 运行时在 Windows 上的兼容性（后来的「It Just Works」承诺），但开发工具本身不再更新。

结果是一部分开发者迁移到 VB.NET 或 C#，另一部分留在 VB6 上维护旧系统，直到硬件与操作系统换代逼他们离开。这个案例里没有「社区分裂」，只有平台所有者单方面宣布旧世界结束；用户能做的只是选择什么时候搬。

## 5. 平台与框架的换代

### 5.1 .NET Framework → .NET Core → .NET 5

2002 年发布的 .NET Framework 是 Windows 上的托管运行时，随 Windows 更新，覆盖 WinForms、ASP.NET WebForms、WCF、WPF 等一整套技术栈。2014 年 11 月，微软宣布 .NET Core：开源、跨平台、模块化、支持侧装（不依赖系统自带运行时）。2016 年 6 月，.NET Core 1.0 发布。

这不是一次平滑升级。.NET Core 最初缺少 WinForms、WPF、WebForms、WCF 服务端等大量 API，只能覆盖 ASP.NET Core 与控制台/库场景。大量企业应用因此被迫做选择：留在 .NET Framework 4.x（特性停在 4.8，2019 年 4 月发布；2022 年的 4.8.1 只做兼容与安全修补），或者把代码迁到 Core。微软提供的迁移工具（如 try-convert、.NET Upgrade Assistant）能处理项目文件与部分 API，但架构层面的差异仍需人工重写。

2020 年 11 月，.NET 5 发布，把两条线合并成一个品牌：.NET Framework 不再新增功能，只做维护；新特性全部进入 .NET 5 及之后的版本（6、7、8……）。从宣布到统一，前后约六年。这个案例说明，同一家公司的两条产品线可以长期并行，但最终仍要选一条作为未来；「统一」往往意味着旧线被冻结，而不是两边兼容。

### 5.2 AngularJS 1.x → Angular 2+

AngularJS 1.0 于 2012 年发布，是第一个大规模流行的前端框架。2014 年初，Google 公开了 Angular 2 的重写计划：改用 TypeScript、组件化架构、新的变更检测与依赖注入，与 1.x 的 API 几乎不兼容。2016 年 9 月，Angular 2.0 正式发布。

社区的反应是这次换代里最值得记录的部分：一部分团队认为「同名不同物」的迁移成本不可接受，转向 React 或 Vue；留下的团队使用官方提供的 ngUpgrade 做混合运行，把 1.x 与 2+ 组件逐步拼接。AngularJS 1.x 进入长期支持，最终在 2021 年 12 月 31 日停止支持。

多年后回看，Angular 的案例成了「框架大版本重写」的标准警示：品牌延续能保住一部分用户，但迁移工具只能降低切换成本，无法消除「整个应用要重写」的事实。

### 5.3 Mac OS 9 → Mac OS X

1999 年 10 月，苹果发布 Mac OS 9，这是经典 Mac OS 的最后一个大版本。2001 年 3 月，Mac OS X 10.0 发布，内核换成 Mach 与 BSD 混合的 Darwin，API 分成两套：Carbon 面向从经典系统移植的 C 应用，Cocoa 面向全新的 Objective-C 应用。为了运行老程序，系统提供 Classic 环境，在 Mac OS X 里模拟 Mac OS 9。

苹果用兼容层争取了时间：Classic 一直存在到 2007 年 10 月的 Mac OS X 10.5，之后被移除；64 位 Carbon 的路线也在 2007 年前后被取消，开发者被明确告知转向 Cocoa。到 2000 年代末，经典 Mac OS 应用基本消失。

这个案例的启示是：平台换代可以靠兼容层平滑，但兼容层只是缓冲，不是承诺。一旦平台所有者决定硬切，旧 API 的寿命就进入倒计时。

### 5.4 KDE 3→4 与 GNOME 2→3：桌面换代与 fork

KDE 3.0 于 2002 年发布，KDE 4.0 于 2008 年 1 月发布。KDE 4 基于 Qt 4 重写，引入 Plasma 桌面、Phonon 多媒体框架等新组件，但 4.0 发布时稳定性与功能完整性都不足，引发大量用户不满。部分开发者与用户留在 KDE 3.5，后来形成 Trinity 桌面项目（2010 年前后），继续维护 3.5 分支。KDE 4 在 4.2（2009 年）之后才逐渐稳定，最终在 2014 年被 Plasma 5 接替。

GNOME 2.0 于 2002 年发布，GNOME 3.0 于 2011 年 4 月发布。GNOME 3 改用 GNOME Shell，取消了传统任务栏与桌面图标的工作方式，争议极大。Linux Mint 等发行版转向基于 GNOME 2 代码的 MATE 桌面（2011 年），Ubuntu 则在同一时期推出自己的 Unity。GNOME 3 最终成为主流桌面之一，但 MATE 一直活到今天。

桌面换代的特殊之处在于，用户感知的不是 API，而是每天的操作习惯。大版本重写一旦改变交互范式，就会直接触发用户流失，而 fork 成了旧体验的避难所。

## 6. 为什么总在「大版本」处分裂

把上面的案例放在一起，触发分裂的因素可以归成五类。

第一，兼容性债到期。旧设计挡住了新能力：Python 2 的 str/bytes 混淆让 Unicode 支持无法做干净，Perl 5 的解析器与运行时耦合限制了语言演进，ES4 想解决 ES3 的历史包袱但步子太大，VB6 的 COM 模型与 .NET 托管模型根本不同，KDE 3 的 Qt 3 与 GNOME 2 的 GTK 2 也挡在了新一代图形栈前面。当「在旧框架里修」的成本高于「重写」，分裂就有了技术动机。

第二，决策权结构。谁有权宣布「旧版本结束」，决定了分裂能不能被压住。Python 有 BDFL 与 PEP 流程，Guido 能拍板并坚持执行；Perl 6 由 Larry Wall 发起、社区共同设计，反而没有一个能宣布「不兼容方案终止」的中心；ES4 由多家厂商共同决定，任何一家反对都能让路线停摆；VB6 的生死完全由微软决定。分裂的形态，往往就是治理结构的投影。

第三，商业与竞争。Adobe 需要 ActionScript 3 支撑 Flash 平台，微软需要 .NET 对抗 Java，Google 需要 Angular 2 跟上组件化潮流，苹果需要 Mac OS X 摆脱经典系统的技术债。商业动机让「断代」变得果断，也让「兼容」变得次要。

第四，工程现实。重写比重构容易，迁移工具比重写难做。自动工具能覆盖语法，覆盖不了语义、依赖与测试；兼容层能覆盖 API，覆盖不了行为差异与性能特征。于是每个大版本分裂最终都会落到同一句话上：机械部分可以自动化，判断部分只能靠人。

第五，下游惯性。企业 LTS、发行版、教程、招聘、外包合同都把旧版本固化在时间里。RHEL/CentOS 7 把 Python 2.7 留到 2024 年，就是这种惯性的极端样本；只要还有人在生产环境跑旧版，旧版就不会真正消失。

## 7. 迁移为什么难：成本结构与工具边界

迁移的难度大致与四个变量成正比：代码量、语义差异的深度、依赖树的深度、组织的惰性。四者相乘，才是真实成本。

工具能帮上忙的地方是明确的：

- 语法层：2to3、six、python-modernize、ngUpgrade、.NET Upgrade Assistant、VB 升级向导，都能把一部分机械改写自动化；
- 运行时层：兼容库（如 six 同时支持 2 与 3）、兼容 shim（如 .NET 的兼容包）、双版本并行安装；
- 流程层：CI 同时跑新旧版本、特性开关、灰度切换、strangler 模式逐步替换模块。

工具帮不上忙的地方同样明确：

- 语义差异：整数除法、编码边界、对象生命周期、并发模型，这些没有统一替换规则；
- 依赖生态：迁移速度不会快于最底层依赖的维护者；
- 测试与回归：没有测试就没有迁移的信心，而补测试的成本常常高于改代码；
- 人的习惯：API 可以兼容，肌肉记忆不行。

还有一个常见的陷阱：把「最后一个旧版本」当成安全区。Python 2.7、VB6、AngularJS 1.x、.NET Framework 4.8 都曾被当作「会一直有人在」的终点站，结果是支持周期一到，维护成本陡增，而迁移窗口已经关小。判断一条路线是否值得跟，看三件事：官方 EOL 公告的提前量、自动迁移工具的实际覆盖率、生态里主流库的切换比例。

## 8. 三种结局：合并、并存、淘汰

同样是分裂，收场方式差别很大，大致可以归成三类。

合并。新旧最终回到一条线上：Python 2 迁到 3；io.js 在 2015 年并回 Node.js；EGCS 在 1999 年成为 GCC 的正式版本。合并的前提是「双方承认同一个未来」：要么旧版被明确终止，要么新版的治理结构做了让分叉方满意的调整。合并通常发生在分裂由「流程问题」而非「理念问题」引发的时候。

并存。两套东西各自活着：Perl 5 与 Raku、VB6 与 VB.NET、.NET Framework 与 .NET Core（六年间）、KDE 3 的 Trinity 与 KDE 4、GNOME 2 的 MATE 与 GNOME 3。并存的前提是旧版仍有人维护、仍有人用，但创新已经停止。并存不是稳定状态，它只是把选择权留给了用户，代价是生态的长期分裂。

淘汰。一方没有活下来：ES4 被取消，PHP 6 从未发布，Mac OS 9 被 Mac OS X 取代，XFree86 被 X.Org 取代。淘汰通常发生在「没有发布」或「平台所有者强制」的情况下；它的好处是生态不用长期二选一，坏处是失败一方的投入全部沉没。

还有一种反向结局：收敛。Windows NT 从 1993 年、Windows 9x 从 1995 年起长期并行，前者面向企业、后者面向消费市场，API 与驱动模型并不相同；到 2001 年 Windows XP，两条线合并为一条 NT 路线，9x 内核被放弃。这是「分裂」的反面，但机制相同——平台所有者判断旧路线的维护成本高于切换成本，于是选了其中一条。

判断一次分裂会走向哪一类，可以看三个指标：旧版是否还有活跃的维护者、新版是否给出可执行的迁移路径、下游是否有足够多的重要玩家站队。三者都偏向新版，就会合并或淘汰；三者分歧，就会长期并存。

## 9. 给不同角色的建议

对开发者与团队。选技术栈时先看兼容性政策与支持周期，而不是只看版本号。对可能断代的大版本，提前做三件事：把测试补齐、把依赖树摸清、把迁移拆成可回滚的小步。不要把「旧版还能跑」当成「旧版可以一直跑」。如果项目生命周期超过五年，默认它会经历至少一次大版本分裂，把迁移预算写进规划。

对语言与框架的维护者。断代本身不是错，错的是断代的方式。可用的套路已经被验证过：提前多年公布 EOL；提供自动迁移工具与兼容层；维持双版本 CI；把「重写」和「新版本」区分清楚；在旧版停止支持后真的停止支持。反过来，最伤生态的做法是：用同一个名字发布一个不兼容的东西，然后让用户自己猜这是升级还是新语言。

对企业与用户。关注供应商的路线图与许可证，别把关键系统押在「最后一个旧版本」上。迁移前先做小范围演练，确认兼容层覆盖不到的部分在哪里。对开源项目，看治理结构是否允许社区在维护者失能时接手——这决定了分裂时是否还有第二条路。

结语。大版本分裂不是道德失败，而是软件演化的成本结算。语言要还设计债，平台要换运行时，框架要跟交互范式，这些都得有人付账。真正值得讨论的不是「该不该分裂」，而是「什么时候断、怎么断、由谁承担迁移成本」。把这三件事说清楚的项目，即使分裂也能软着陆；说不清楚的项目，哪怕版本号只动了一位，也会在生态里留下一条很久都合不拢的缝。
