## 1. 应用层与工具链

### 1.1 Flatpak、Snap 与 AppImage：应用分发的新一层

桌面应用有一个发行版包管理器解决不了的问题：应用与系统库的版本节奏不一致。发行版大约每半年（Fedora）到两年（Debian、Ubuntu LTS）才发布一次，而浏览器、IDE、设计工具可能每两周更新一次。让上游为每个发行版各打一份包，成本落在应用作者身上；让用户等发行版升级，体验落在用户身上。

Flatpak、Snap、AppImage 是对这个问题的三种不同回答，共同点是把运行时也一起打包，不再依赖系统提供依赖。在这个共同点之下，三者的形态、隔离与更新策略差别很大；此外还有几种更早或更激进的答案，值得放在一起看。

#### 1.1.1 Flatpak：运行时 + 沙箱 + portal

2015 年 Alexander Larsson 以 xdg-app 起步，2016 年更名 Flatpak，现在由 freedesktop.org 社区维护。它的核心设计是把应用与运行时（runtime）拆开：应用以反向域名标识（`org.gnome.Builder`），运行时是 `org.gnome.Platform`、`org.kde.Platform` 这类带版本分支（如 `46`、`47`）的基础环境，里面是 GTK/Qt、字体与基础库。多个应用共享同一份运行时，因此不会每个应用各带一份 GTK。

存储层用 OSTree，文件按内容寻址，去重与增量更新是天然结果，`flatpak update` 一次更新所有应用与运行时。安装后 `.desktop`、图标、MIME 关联由 Flatpak 自动写入，这一点与系统包管理器一致，也是它与 AppImage 的实质差别。

沙箱基于 bubblewrap 的命名空间，应用要访问文件、网络、设备，必须在 manifest 里声明（`finish-args`），用户可以覆盖：

```bash
flatpak install flathub org.gnome.Builder
flatpak run org.gnome.Builder
flatpak update
flatpak override --user --filesystem=~/projects org.example.App
```

沙箱里的应用打开文件、打印、发通知，走 `xdg-desktop-portal`：宿主弹出文件选择器，应用只拿到被选中的路径，而不是整个家目录。这就是为什么 Flatpak 应用用起来会「隔」一层。

代价同样是结构性的：磁盘上可能并存多个运行时版本；沙箱会让「把路径传进去」这类操作变麻烦；GTK 主题与字体要靠额外的扩展包才能对上宿主观感。

#### 1.1.2 Snap：守护进程与自动更新

Snap 由 `snapd` 守护进程管理，镜像本身是 squashfs，自动更新是默认行为，隔离靠 AppArmor 与 seccomp，分严格（strict）与经典（classic）两种模式。它由 Canonical 独家运营商店，后端高度中心化。

它的优点是跨发行版一致、更新自动化、服务器端也有使用场景。争议同样明确：自动更新的时间窗口不可控（生产环境尤其敏感）、首次启动速度受 squashfs 挂载影响、商店中心化意味着分发权集中在一家公司。企业内网部署通常需要自建 Snap Store 代理。

Snap 与 Flatpak 的分歧不在技术目标，而在治理：一边是单一公司，一边是社区基金会加 Flathub。实践中真正的抱怨大多来自治理后果，而不是格式本身。

#### 1.1.3 AppImage：单文件，不解决依赖

AppImage 是「把应用和它的库打进一个可执行文件」。它的形态是一个 ELF 文件，尾部内嵌 squashfs（type 2），运行时通过 FUSE 把镜像挂到临时目录再执行 `AppRun`，所以 `chmod +x` 之后就能直接跑。

```bash
chmod +x Tool-x86_64.AppImage
./Tool-x86_64.AppImage
```

它不需要安装、不需要 root、在很老的系统上也能跑，这是它最大的价值。适合「一次性工具」「绿色版」和「给老发行版发一个二进制」的场景。

代价是几乎放弃了所有基础设施：默认没有更新机制（除非应用内置了更新组件，如 AppImageUpdate）、没有系统集成（菜单、文件关联要自己处理或依赖第三方工具）、体积大，而且安全修复只能靠用户手动换文件。最低系统要求由打包时链接的 glibc 版本决定，打高了在老系统上起不来；新版发行版不再默认带 `libfuse2` 时，运行会直接报错，可以退回 `--appimage-extract` 解包再跑。

#### 1.1.4 更早的两种回答：0install 与厂商自建源

在 Flatpak 之前，同一个问题已经有两个答案。

0install（Zero Install） 2005 年前后问世，设计上比 Flatpak 更激进：应用用 URL 而不是包名标识，feed 文件声明版本与依赖，全局缓存按内容寻址，多个应用共享同一份库，而且完全去中心化。它有命令行，也有图形界面与桌面集成，Linux、macOS、Windows 都能跑。没成的原因不在设计：没有厂商愿意为它发布 feed，也没有中心商店承担审核与 CDN，用户遇到问题时无处可查。这是应用分发工具最典型的失败方式——技术方向正确，但缺少把开发者与用户连起来的基础设施。

厂商自建源是另一个答案，也是 Flatpak 出现前的默认做法：Chrome、VS Code、Docker CE 都同时发布 `.deb` 与 `.rpm`，并维护自己的 apt/yum 仓库与签名密钥，用户加一行源地址、导入一个 key 就算装好。它解决了版本节奏问题，代价是把分发成本摊给每个厂商，而用户机器上会累积一堆第三方密钥与源配置。第 2 章讨论的供应链问题，有一部分就是从这些源配置开始的。

#### 1.1.5 闭包与单文件：Nix、静态链接与 Apptainer

Nix 与 Guix 把依赖闭包做成第一等公民（机制见[《包管理器（二）》第 1.8 节](/post/2026/09/24/package-managers-os/#18-nix-与-guix把包管理器当成构建系统)）。从分发角度看，`/nix/store` 里的每个路径都自带完整依赖，运行时互不干扰，同一应用的不同版本可以并存，回滚是原子操作。`nix run nixpkgs#gimp` 就是一次性的应用启动，不安装、不留痕。代价是它不遵循 FHS，很多按 `/usr/lib` 写死的二进制在 NixOS 上跑不起来；`nix bundle` 能把闭包压成自包含可执行文件，思路成立，工具链仍偏实验。

静态链接是最朴素的版本：Go、Rust 的 musl target、Zig 默认产出单文件可执行，不依赖任何运行时。代价是证书、NSS、时区数据这类「运行时资源」要自己处理，体积也压不下去。

Apptainer（原 Singularity）在形态上最接近 AppImage：整个用户态装进一个 `.sif` 文件，节点上有 Apptainer 就能跑，不需要 root，也不需要安装依赖。它长在 HPC 场景，因为集群上既不能装包也不能常驻 Docker daemon。2021 年从 Singularity 分叉、迁入 Linux Foundation 后改名 Apptainer。从「单文件自带环境」这个维度看，它比 AppImage 做得更彻底，只是不在桌面生态里。

#### 1.1.6 把容器当应用跑：Distrobox 与 Steam Runtime

Distrobox 与 toolbox 是这几年实际增长最快的方案：用 podman 起一个 Ubuntu 或 Arch 容器，与宿主共享 home、`/tmp`、显卡设备和 D-Bus，再把命令与 `.desktop` 导出到宿主。

```bash
distrobox create --image archlinux:latest --name arch
distrobox enter arch
```

它解决的是 Flatpak 不愿碰的问题——跑别的发行版的包，包括 AUR 和只在旧版本里存在的工具。代价同样明确：它本质上是「在容器里装了一整套发行版」，不是给终端用户的成品，容器与宿主的库版本差异仍然会制造奇怪的 bug。

游戏领域走得更早。Steam Runtime 从 2014 年起就给游戏提供固定的库集合，2018 年后的 Soldier 运行时与 pressure-vessel 改成了容器化实现；Bottles、Lutris 用同一思路管理 Wine 前缀。自带运行时在桌面社区还靠 Flatpak 推动，在游戏里已经是运行多年的基础设施。

#### 1.1.7 边界：哪些机制不属于这一层

rpm-ostree（Fedora Silverblue、Kinoite）与 openSUSE MicroOS 经常和 Flatpak 一起出现，但它们管的是系统：根文件系统不可变，系统更新是镜像式的原子替换，用户应用仍然交给 Flatpak。它们回答的是「系统怎么升级」，不是「应用怎么分发」。

bubblewrap、firejail 只提供隔离，不负责分发与更新，装什么仍由发行版或用户决定。把它们和 Flatpak 混为一谈，会得出「沙箱就等于应用分发」的错误结论。

#### 1.1.8 应用分发机制对比

| 机制 | 分发单位 | 运行时 | 沙箱 | 更新 |
| --- | --- | --- | --- | --- |
| apt / dnf | 包 | 系统提供 | 无 | 系统升级 |
| Flatpak | 应用 + 共享运行时 | 自带 | bubblewrap + portal | `flatpak update` 统一 |
| Snap | snap | 自带，共享 base | AppArmor + seccomp | 自动、后台 |
| AppImage | 单个文件 | 全部打包 | 无 | 无内置 |
| 0install | feed + 共享缓存 | 共享 | 无 | 按 feed |
| Nix | 闭包 | 自带 | 无（可叠加） | 按代际切换 |
| Distrobox | 容器 | 整个发行版 | 容器 | 发行版内更新 |
| rpm-ostree | 系统镜像 | 不涉及 | 不涉及 | 镜像原子更新 |

适合场景：

- apt / dnf：系统组件、驱动、基础工具
- Flatpak：桌面应用日常分发
- Snap：跨发行版一致
- AppImage：一次性工具、老旧系统
- 0install：去中心化分发（已边缘化）
- Nix：开发环境、可复现
- Distrobox：跑其他发行版的包
- rpm-ostree：不可变系统

#### 1.1.9 跨平台对照

同一套问题每个平台都遇到过，答案也收敛到相近的形状：

| 平台 | 同类机制 |
|---|---|
| macOS | `.app` bundle 自带 Framework，签名与公证后分发；Homebrew cask 负责获取与更新；Sparkle 提供应用内更新 |
| Windows | MSIX 提供打包、签名与部分虚拟化（注册表与文件重定向），可走商店或旁加载；Scoop、PortableApps 走解压即用路线；winget 提供仓库式获取 |
| Android | APK + 商店 + 权限沙箱，是「商店分发 + 沙箱」组合最早成规模的实践 |

可见「应用分发层」不是 Linux 独有的发明。各平台都在「系统提供依赖」和「应用自带依赖」之间划线，最后大多收敛到商店 + 沙箱 + 自动更新，因为只有这个组合能同时满足用户、开发者与平台三方。

#### 1.1.10 为什么最后剩下 Flatpak 和 Snap

不是技术更优。0install 的设计在很多方面更干净，AppImage 更简单，Nix 更严谨。活下来的是有分发基础设施的两个：Flathub 与 Snap Store 提供了签名、CDN、审核、桌面集成与厂商关系，这些恰恰是纯格式规范给不了的。

这也解释了 AppImage 的处境：作为格式它很成功，作为生态几乎没有进展——没有商店，就没有统一的自动更新，也就没有安全修复的通道。第 2 章讨论的供应链问题，在这里表现为「用户只能自己记得去换文件」。

#### 1.1.11 它们与系统包管理器的关系

这层机制不替代系统包管理器，而是改变了分工：系统包管理器仍然管内核、驱动、系统库和基础工具；应用层分发机制管那些更新节奏快、依赖复杂的用户态应用。

理解了这一层，也就理解了后面第 1.2 节的容器：容器是把「自带依赖」推到极致的做法，代价同样是体积和重复。

> 一句话总结：应用层分发用「自带运行时」换更新自由，代价是磁盘、重复与集中化的分发权。

### 1.2 容器与 OCI 镜像：分发单元的迁移

容器镜像把分发的单位从「包」变成了「镜像」。这个变化带来一个直接后果：锁定的单位也跟着变了——从锁文件里的版本号，变成镜像的 digest。

```bash
docker pull debian:12.5@sha256:...
```

tag（包括 `latest`）是可变的指针，digest 指向不可变的内容。生产环境如果只写 tag，就等于接受「某天拉到的内容与上次验证的不一样」。这是容器场景里最容易被忽略、后果又最直接的一条规则。

#### 1.2.1 Dockerfile 里调用包管理器的规范做法

```dockerfile
FROM debian:12-slim@sha256:<digest>

# update 与 install 必须在同一个 RUN 里：分开写会命中缓存，
# 导致使用过期的索引安装
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates curl \
 && rm -rf /var/lib/apt/lists/*

# 先复制锁文件再安装依赖，最后复制源码：
# 源码改动不会导致依赖层失效
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY . .
```

四个要点：`update` 与 `install` 合并；装完清理包管理器缓存；先锁文件后源码以利用层缓存；基础镜像按 digest 固定。能固定包版本（如 `curl=7.88.1-10`）时更好，代价是升级要显式改 Dockerfile，而这正是可复现性的本来含义。

#### 1.2.2 多阶段构建与 distroless

多阶段构建把「构建环境」和「运行环境」分开：builder 阶段装编译器、SDK、包管理器，runtime 阶段只复制产物。

```dockerfile
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12
COPY --from=builder /out/app /app
ENTRYPOINT ["/app"]
```

这不仅缩小体积，更是安全上的改进：安装脚本、构建工具、包管理器缓存都留在 builder 阶段，运行镜像里没有它们（呼应[《包管理器（一）》第 3.8 节](/post/2026/09/24/package-managers-principles/#38-安装时执行代码一切矛盾的根源)）。distroless 与 scratch 把这条路走到尽头——没有 shell、没有包管理器，攻击者拿到 RCE 也没有现成的工具可用（但仍能发起网络请求或自带载荷）。代价是调试困难：没有 shell 就得靠临时调试容器或静态编译的调试工具。

#### 1.2.3 镜像里的「包管理」问题

- 无法单包回滚：镜像是一个整体，回滚意味着换 digest。这既是缺点（粒度粗）也是优点（状态明确）。
- 层内的一致性依赖基础镜像：`apt-get install` 在层里装到的版本取决于基础镜像的索引，所以同一个 Dockerfile 在不同时间构建会得到不同结果——除非固定包版本或固定基础镜像 digest。
- 跨架构：多架构构建（amd64/arm64）意味着构建矩阵回来了，而且 Python 的 wheel、npm 的可选依赖在不同架构上差异更大（见[《包管理器（一）》第 3.2、3.5 节](/post/2026/09/24/package-managers-principles/#32-包的形态源码分发与二进制分发)）。
- 层缓存与锁文件：`COPY` 顺序错了，锁文件变化就不会触发依赖重装，于是出现「锁文件改了但镜像里还是旧依赖」。

容器是最彻底的隔离方案，也是最重的：每次构建都要重新获取、每一次运行都有额外的启动与存储开销。它值得，通常是因为部署与一致性收益大于这些成本。

> 一句话总结：容器的锁定单位是 digest，不是版本号——凡是可变的指针，都不能作为可复现的依据。

### 1.3 Bazel、Nx、Turborepo：从依赖管理到构建图

先划边界：包管理器回答「拿哪些代码」，构建工具回答「怎么把这些代码变成产物」。前者管理输入，后者管理过程。混淆两者，就会出现「换了包管理器，构建为什么没变快」这类问题。

#### 1.3.1 Bazel：目标图 + 沙箱动作 + 远程缓存

Bazel 把每个构建步骤建模成动作（action），输入与输出都显式声明。因为输入完全声明，动作可以在沙箱里执行、可以被哈希、结果可以被缓存——输入没变就不重跑，本地或远程缓存命中就直接取产物。

规则（rule）定义「如何构建某类目标」，目标（target）通过依赖关系组成图。外部依赖由 bzlmod（`MODULE.bazel`）管理，并有锁文件保证求解结果稳定。

它的收益在大规模 monorepo 上非常明显：增量构建的正确性由机制保证（不是靠时间戳猜测）、多语言可以共用一套构建与缓存、CI 上能只重跑受影响的目标。代价也很明确：学习曲线陡、要为每种语言适配规则、构建描述文件的维护量不小，而且它的收益随仓库规模增长——小仓库用 Bazel 是纯负债。

#### 1.3.2 Nx 与 Turborepo：JS/TS monorepo 的任务编排

这两个工具不做依赖获取——依赖仍然由 npm/pnpm/yarn 安装。它们补的是「任务图与缓存」：

- 识别项目之间的依赖关系，从而算出受影响的包
- 把 `build`/`test`/`lint` 组织成带依赖的任务图并并行执行
- 本地与远程缓存产物，命中即跳过

在 Node 生态里，这往往就是把 CI 从二十分钟压到两分钟的关键。它们的前提是仓库结构清晰（工作区、包边界明确），否则会陷入「缓存命中率低、配置难维护」的状态。

Pants、Buck2 属于同一位置的其他选择，取舍类似：能力更强、门槛更高。

#### 1.3.3 什么时候值得上

判断标准不是「工具有多先进」，而是三个具体问题：仓库规模是否让全量构建变得不可接受；是否真的存在多语言构建需求；构建结果是否需要强可复现（审计、发布、合规）。三个都不成立时，包管理器加一个简单的任务脚本就够了。

> 一句话总结：包管理器管代码从哪来，构建工具管产物怎么算——把这两件事分开，选型就不再纠结。

### 1.4 版本管理器不是包管理器：nvm、pyenv、rustup、asdf、mise

这两类工具经常被混为一谈，而混淆它们的代价是具体的：装完 nvm 之后发现依赖装不上，于是去查包管理器的文档，方向从一开始就错了。

- 版本管理器（version manager）换的是运行时/工具链版本：Node 18 还是 20，Python 3.11 还是 3.12，rustc 1.7x 还是 1.8x。
- 包管理器（package manager）装的是依赖包：库、框架、工具。

两者是正交的两个维度。

#### 1.4.1 常见工具

| 语言 | 工具 |
|---|---|
| Node | nvm、fnm、volta |
| Python | pyenv |
| Rust | rustup |
| Ruby | rbenv |
| 多语言 | asdf、mise、proto |

#### 1.4.2 机制：shim 与 PATH

主流实现有两类。pyenv、rbenv、asdf、volta 走 shim：把一个代理可执行文件放在 PATH 的最前面，运行 `node` 或 `python` 时，shim 根据当前目录的版本声明（`.nvmrc`、`.python-version`、`.tool-versions`）决定真正执行哪个版本。nvm 不用 shim——它是 shell 函数，`nvm use` 直接把所选版本的 bin 目录前置到 PATH（nvm-windows 则用符号链接指向对应版本目录）。

好处是切换成本极低、可以按目录按 shell 切换。代价是真实路径被隐藏：执行 `pip install` 时，包会装进 shim 背后的那个解释器，而不是预期的那个。

排查方法永远是一样的——先问「真正在跑的是谁」：

```bash
which -a python        # 所有候选
python -c "import sys; print(sys.executable)"
node -v && command -v node
```

Windows 上对应 `Get-Command python -All` 与 `(Get-Command python).Source`。

#### 1.4.3 项目级声明要提交

`.nvmrc`、`.python-version`、`.tool-versions`、`rust-toolchain.toml`、`.mise.toml`，以及 `package.json` 的 `engines` 字段——这些文件的作用和锁文件类似：把「本机恰好是这样」变成「仓库要求这样」。

版本管理器与包管理器配合时，顺序也很重要：先切运行时，再装依赖。反过来的话，依赖会落到上一个运行时上。

#### 1.4.4 rustup 的特殊之处

rustup 同时管工具链、组件（clippy、rustfmt）和目标平台（`x86_64-unknown-linux-musl` 之类），还能根据 `rust-toolchain.toml` 自动下载指定版本。Go 也有类似能力：`go.mod` 里的 `toolchain` 行会在构建时获取指定的 Go 版本（见[《包管理器（三）》第 1.4 节](/post/2026/09/24/package-managers-language/#14-gogopath-的教训与最小版本选择)）。这类「包管理器顺带管工具链」的设计，正在把两个维度合到一起。

#### 1.4.5 与容器、Nix 的关系

把工具链版本也纳入声明式管理，是团队一致性最好的做法：devcontainer 镜像、`nix develop`、`mise.toml` 都能让「新同事的第一条命令」变成一条，而不是七条。

> 一句话总结：先确认真正在运行的解释器是谁，再决定用哪个命令装包——大多数「环境问题」都错在这一步。

### 1.5 私有仓库与依赖代理：企业环境的必修课

很多团队第一次认真对待依赖基础设施，都是在一次事故之后：上游删了包、公网仓库挂了、合规要求出具组件清单、或者发现生产镜像里装着来源不明的包。

#### 1.5.1 为什么需要

- 气隙与网络限制：构建机不能直连公网
- 合规与许可证审查：需要知道实际用了哪些组件与许可证
- 可用性：上游删包或服务故障时，构建不能跟着停
- 内部包分发：私有库不能发到公网仓库
- 审计：谁在什么时候拉取了哪个版本，是事件响应的证据

#### 1.5.2 三种部署形态

| 形态 | 作用 | 典型用途 |
|---|---|---|
| 代理缓存（proxy） | 转发公网仓库并缓存 | 加速、断网可用 |
| 宿主仓库（hosted） | 存放内部发布的包 | 私有库分发 |
| 聚合仓库（group/virtual） | 把多个源聚合成一个 URL | 客户端只配一个源 |

常见实现：Nexus、Artifactory、Cloudsmith、GitHub Packages、GitLab Package Registry；语言专属的还有 devpi（PyPI）、Verdaccio（npm）、Harbor（容器镜像）。

#### 1.5.3 配置要点

- 客户端只配一个聚合源。这样优先级由服务端定义，而不是由客户端的多源合并逻辑决定——后者的典型反例是 pip 的 `--extra-index-url`，它会把多个源合并，同名包可能来自公网（见第 2.2 节）。
- 凭据不要写进仓库。用环境变量或 CI 密钥注入；锁文件、Dockerfile、仓库内配置文件都不应该出现 token。
- 自签证书要装进信任链。否则每个工具都要加例外参数（`--trusted-host` 之类），例外一多就没人记得为什么有。
- 定期验证离线可用性：把外网断开跑一次完整构建。这是最直接能证明代理真的缓存住了的方法。

#### 1.5.4 治理

- 内部包使用命名空间或 scope，并确保公网源不能顶替内部命名空间——这是依赖混淆最直接的防线。
- 保留审计日志：包名、版本、请求者、时间。事件发生时，「到底装了没有」这个问题必须有答案。
- 缓存策略要允许回源：把缓存永久冻结，等于把安全修复也一起冻结了；需要明确什么时候允许拉取新版本。

> 一句话总结：私有仓库的价值不在于「快」，而在于把依赖的可用性与审计权收回到自己手里。

## 2. 供应链安全

### 2.1 威胁模型：依赖链为什么脆弱

装一个依赖，信任的不是一个包，而是：它的全部传递依赖 + 全部维护者 + 整条发布链路（包括仓库账号的安全策略、CI 的 token 权限、以及签名机制覆盖到哪一步）。

#### 2.1.1 攻击面清单

typosquatting（包名抢注与拼写诱导）：注册与流行包相近的名字（如 `reqeusts`），等待手快或拼错的人安装。更精细的做法是同时伪造空壳仓库与虚假文档，让搜索结果看起来可信。

dependency confusion（依赖混淆）：在公网仓库发布与内部包同名的包，并给一个更高的版本号。如果客户端把公网源与内部源合并（比如 pip 的 `--extra-index-url`），求解器可能选中公网那个更高版本——于是内部代码意外地执行了外部代码。

维护者账号接管：钓鱼、凭据泄露、CI token 泄露。攻击者以维护者身份发布一次「正常更新」，所有下游都会在例行升级中拿到它。这类攻击最难防，因为它能通过签名验证——签名只证明「是维护者发布的」，不证明「发布的东西是安全的」。

安装脚本 RCE：npm 12 之前，一步 `postinstall` 就能执行任意代码；npm 12 起生命周期脚本默认不执行、需要显式 allowlist（见[《包管理器（一）》第 3.8 节](/post/2026/09/24/package-managers-principles/#38-安装时执行代码一切矛盾的根源)），但 Python 的 PEP 517 构建后端与 Rust 的 `build.rs` 仍然会在安装或构建时执行。攻击者不必等到运行程序，安装就够了。

上游投毒与长期渗透：三个常被引用的案例代表了三种不同的路径。

- event-stream（2018）：原作者交出维护权后，新维护者通过新增依赖注入针对特定钱包应用的恶意代码。路径是「所有权转移 + 恶意子依赖」。
- ua-parser-js（2021）：维护者账号被劫持，发布带挖矿与窃密代码的版本。路径是「账号接管」。
- xz-utils（2024，CVE-2024-3094）：攻击者用长期社交换取提交权限，逐步植入后门，几乎进入主流发行版。路径是「长周期信任渗透」。

protestware 与自毁代码：作者在包内加入针对特定地区或用户的破坏逻辑，或以删库作为施压手段。它提醒一个事实：作者随时有权改变包的行为，而依赖的是作者此刻的选择。

#### 2.1.2 为什么难防

JS 与 Python 项目的传递依赖动辄几百上千个（Go、Rust 通常少一个量级，但没有本质区别），每个都有自己的维护者、发布流程与安全水平；逐个审计在多数团队里不现实；而「不升级」又意味着放弃安全修复。这是结构性困境，不是态度问题。

从攻击者视角看，经济性也很清楚：一个包名或一次钓鱼的成本极低，影响面却可以覆盖成千上万的下游，归因还困难。

#### 2.1.3 应对的姿态

结论不是「关掉网络、从此不用依赖」，而是把依赖当代码来审计，并承认防护是分层的：

1. 能用机制自动挡住的，不要靠人（第 2.2 节）
2. 能证明来源与构建过程的，比「看起来没问题」更可靠（第 2.3 节）
3. 残余风险要显式记录，而不是默认忽略

> 一句话总结：被信任的不是一个包，而是它背后所有维护者与整条发布链路。

### 2.2 防御（一）：锁定、校验与最小权限

#### 2.2.1 先锁死可复现性

这一步几乎没有争议，而且收益最大：

- 提交锁文件，CI 用冻结模式安装（`npm ci`、`--frozen-lockfile`、`--locked`）
- 容器镜像按 digest 固定，不用可变的 tag
- 保持完整性校验开启：`go.sum`、lockfile 的 integrity 哈希、`cargo` 的校验和，都不要用 `--no-package-lock`、`--no-deps`、`strict-ssl false` 之类的捷径绕过

但必须理解它的边界：哈希与锁文件只能防「验证过之后被篡改」，防不住「第一次就装到被投毒的新版本」——因为那个哈希本来就来自被投毒的包。第一次信任必须靠别的机制：人工过目、发布时间门槛、来源限制。

#### 2.2.2 减少执行面

安装期执行代码是最大的风险来源（[《包管理器（一）》第 3.8 节](/post/2026/09/24/package-managers-principles/#38-安装时执行代码一切矛盾的根源)），所以优先级是：能不执行就不执行，必须执行就隔离执行。

```bash
npm ci --ignore-scripts        # 显式禁用依赖的安装脚本（npm 12 起默认已禁用）
pip install --only-binary :all: -r requirements.txt   # 只装 wheel
```

- 需要跑脚本的包（通常是原生模块）走白名单：npm 12 起用 `package.json` 的 `allowScripts` 配合 `npm approve-scripts` 授权，并逐个说明原因。
- 构建与安装放进容器或沙箱：非 root 用户、只读文件系统、构建期无网络。无网络是性价比最高的一招，它同时挡住了「构建时偷偷下载东西」这一类问题。
- 把「下载」和「执行」分开：先取包并记录哈希，再在受控环境里安装。

#### 2.2.3 依赖最小化

每删掉一个直接依赖，同时删掉了它带来的整棵子树。这一点在审计上极其划算。

新增依赖时的过目清单：

- 维护者是谁，有几个人，最近的发布频率如何
- 是否包含安装脚本、`build.rs`、原生构建步骤
- 包的下载量与依赖它的人有多少（不是安全证据，但影响暴露面）
- 是否可以用几十行代码自己实现，从而免掉一个依赖

#### 2.2.4 组织层面的策略

- 私有源优先：内部命名空间不允许被公网源顶替（第 1.5 节），并避免使用把多个源合并的配置（如 pip 的 `--extra-index-url`）。
- 版本年龄门：新发布的版本先等 N 天再允许进入生产。这不能挡住长期渗透（xz 那种），但能挡住大量「投毒后一小时内被抓」的机会型攻击。
- 生产依赖变更走审批：不是为了卡人，而是为了让「这个依赖是谁批准的、为什么」有记录。

#### 2.2.5 现实提醒

安全措施只有在「能自动执行、不阻断开发」时才活得久。人肉全量审查撑不过三个月，之后会退化成「全都点通过」。所以策略应该是：机制负责大部分，人力集中在新增直接依赖和特权变更上。

> 一句话总结：哈希防篡改、锁文件防漂移，但第一次信任只能靠来源限制与人工判断。

### 2.3 防御（二）：签名、证明与 SBOM

#### 2.3.1 两个不同的问题

这是最容易混淆的一点：

- 签名回答「谁发布的」——身份问题
- 证明（provenance / attestation）回答「它是怎么构建出来的」——过程问题：哪个仓库、哪个 commit、哪个 CI 工作流、什么构建参数

两者都重要，但替代不了彼此。签名挡不住「维护者账号被接管后正常发布」，证明则能显著提高这类攻击的成本——因为攻击者还必须伪造出与源码一致的构建过程记录，而这个记录会进透明日志。前提是构建平台本身可信：如果攻击者能改 CI 工作流或仓库配置，provenance 依然会显示为「真实」，所以还需要 SLSA L3 与工作流保护。

#### 2.3.2 Sigstore 生态

Sigstore 把「密钥管理」这个最大的落地障碍变成了「身份管理」：

- cosign：签名与验证工具
- Fulcio：签发与 OIDC 身份绑定的短期证书，不再需要长期私钥
- Rekor：透明日志，提供「某个签名在某个时间点确实存在」的公开可验证记录

#### 2.3.3 各生态的现状

| 生态 | 机制 | 主要缺口 |
|---|---|---|
| npm | provenance 证明（受支持的 CI 发布时生成），`npm audit signatures` 可校验 | 覆盖面取决于发布者是否启用 |
| PyPI | Trusted Publishing（OIDC，免长期 token）与证明 | 老项目迁移缓慢 |
| crates.io | Trusted Publishing（OIDC，2025-07 起）+ 发布者 token | 仍无强制的构建证明 |
| Go | `go.sum` + 校验和数据库 | 只保证完整性，不证明构建过程 |
| 容器 | cosign 签名、SLSA provenance、in-toto | 采用率不均衡 |

SLSA 是一套描述「构建防篡改性」的分级框架：等级越高，越要求构建平台可信、输入显式声明、过程可审计。它是目标框架而不是一键工具，落地通常从「在 CI 里生成 provenance」开始。

#### 2.3.4 SBOM：审计的起点

SBOM（软件物料清单）的主流格式是 SPDX 与 CycloneDX。两个要点：

1. 在构建产物上生成，而不是在源码目录生成。源码目录里的清单会漏掉实际链接进去的组件。
2. 它是审计起点，不是安全保证。SBOM 只回答「包含了什么」，不回答「其中哪个有已知漏洞、是否可达、是否真的能被利用」。

#### 2.3.5 工具链与排序方法

- 升级：Dependabot、Renovate——配合锁文件与测试，让小步升级成为常规动作
- 漏洞扫描：Trivy、Grype、OSV-Scanner，以及各语言自带的 `cargo audit`、`npm audit`、`pip-audit`
- 生成 SBOM：Syft 之类的工具

扫描结果的排序比数量重要：优先看可达性（这段代码真的会被调用吗）、暴露面（是否在公网服务里）、利用条件（是否需要特定配置或权限）。按 CVSS 分数从高到低处理，通常会让人淹死在告警里，然后开始无视所有告警——那才是真正的安全风险。

> 一句话总结：签名证明身份、证明描述过程、SBOM 记录组成——三者互补，都不能替代「别装不理解的东西」。

### 2.4 平台机制一览与个人清单

#### 2.4.1 一览表

| 生态 | 现有机制 | 成熟度 |
|---|---|---|
| npm | provenance 证明、`npm audit`、签名校验命令 | 中高，取决于发布者 |
| PyPI | Trusted Publishing（OIDC）、2FA 推广、证明 | 中高，老包迁移慢 |
| crates.io | Trusted Publishing（OIDC）、token 安全、yank 政策、`cargo audit`/`cargo deny` | 中 |
| Go | `go.sum`、校验和数据库、模块代理 | 高（完整性），低（构建证明） |
| Maven Central | 签名与校验和、不可变发布 | 高（不可变），中（身份验证） |
| NuGet | 包签名、可信发布流程 | 中 |
| 容器/OCI | cosign 签名、SLSA provenance、in-toto | 中，采用不均衡 |

#### 2.4.2 治理：平台侧在做什么

- 账号安全：2FA 与硬件密钥要求、token 权限最小化、CI 的短期凭据（OIDC 而非长期 token）
- 撤销与 yank 政策：允许撤回但通常不允许覆盖已发布版本；撤回后下游如何应对是各生态的长期痛点
- 命名空间所有权：争议处理机制、商标与企业命名空间、弃用与交接流程
- 不可变性：Maven Central 长期不允许覆盖版本，这类约束看似不灵活，却是可复现性的地基

#### 2.4.3 个人与小团队的可执行清单

1. 提交锁文件；CI 一律用冻结安装
2. 生产镜像按 digest 固定基础镜像
3. 默认禁用安装脚本，例外走白名单
4. 新增直接依赖做一次人工过目：维护者、安装脚本、最近发布
5. 开启自动升级 PR，小步合并，并保证测试覆盖
6. 漏洞扫描按「每个 PR 跑增量 + 每周跑全量」的节奏执行，并按其可达性而不是分数排序处理
7. 对关键产物生成 SBOM 并存档
8. 私有源优先，内部包使用命名空间，避免多源合并配置
9. 凭据只通过环境变量或 CI 密钥注入，绝不进仓库
10. 每季度做一次「从零重建」演练：清空缓存重新安装，验证真的能复现

#### 2.4.4 一句话原则

安全预算要花在能自动执行、且不阻断开发的机制上。做不到这两点中的任何一条，措施通常在几周到三个月内退化。

> 一句话总结：先让机制自动兜住大部分风险，人力只留给新增依赖与特权变更。

## 3. 实践

### 3.1 决策指南：什么场景用什么

先说清一件事：不存在「推荐一个包管理器」这回事。真正要回答的是——在这台机器的这个场景里，谁负责系统、谁负责项目、谁负责用户级 CLI。三条边界划清了，选型基本自动确定。

#### 3.1.1 Linux 服务器

首选：发行版自带的那套（Debian/Ubuntu 用 apt，RHEL 系用 dnf）。备选：需要更新的语言运行时或工具时，用容器，或走语言级工具的用户级安装（`uv`、`rustup` 这类不碰系统目录的方式）。

不要做：在服务器上 `pip install` 到系统 Python；把第三方 PPA/Copr 与官方源混着开却不做优先级控制；用 Nix/Homebrew 覆盖系统库。

理由很朴素：服务器上「可预测」比「新」值钱得多。发行版的安全更新通道，是唯一能自动化处理漏洞公告的路径；一旦关键库被跨平台包管理器替换，安全更新就没人兜底了。

#### 3.1.2 桌面工作站

Linux 滚动发行版（Arch、openSUSE Tumbleweed）：就用 pacman/zypper，代价是必须接受完整升级的纪律，并养成看发布公告的习惯。Debian 系桌面：apt 管系统，Flatpak 管桌面应用，两者分工明确。macOS：Homebrew 管 CLI 与 GUI（cask）。Windows：winget 管常规软件，Scoop 管免管理员的 CLI 工具集，Chocolatey 留给企业内部的既有脚本。

不要做：在滚动发行版上做部分升级（见[《包管理器（二）》第 1.3 节](/post/2026/09/24/package-managers-os/#13-pacman-与-aurarch-的滚动哲学)）；用 Homebrew 覆盖 macOS 系统自带的组件（见[《包管理器（二）》第 1.6 节](/post/2026/09/24/package-managers-os/#16-homebrewmacos-的社区事实标准)）。

#### 3.1.3 容器基础镜像

首选：镜像自带的最小包管理器（Alpine 的 apk、`debian:12-slim` 的 apt），构建期安装、运行期不带构建工具，基础镜像按 digest 固定（见第 1.2 节）。备选：distroless 或 scratch + 静态二进制。

不要做：在容器里执行 `apt upgrade`；把编译器、头文件、包管理器缓存留在运行镜像里。

#### 3.1.4 数据科学环境

首选：conda/mamba 或 pixi 管非 Python 依赖（CUDA、数学库、编译器），pip/uv 管纯 Python 包；重环境用容器固化。不要做：在同一个环境里让 pip 与 conda 都去管同一个包——这是最难排查的一类损坏（见[《包管理器（三）》第 1.2 节](/post/2026/09/24/package-managers-language/#12-python从-requirementstxt-到-uv)）。

#### 3.1.5 多语言 monorepo

首选：每个子项目用自己的语言级工具，外加统一的任务编排与缓存层（Turborepo/Nx/Bazel，见第 1.3 节），CI 里对每种语言都用冻结安装。

不要做：试图用一个包管理器管所有语言。以环境为单位的方案（Nix、conda）能做到，但那是另一套成本模型。

#### 3.1.6 离线与气隙环境

首选：企业代理仓库（Nexus、Artifactory 之类）加定期镜像同步；语言级依赖用 vendor 目录或离线包目录随代码一起进版本库。不要做：让构建依赖公网仓库的实时可用性——它总会在最不方便的时候出问题。

#### 3.1.7 一台机器上的共存规则

1. 系统关键组件（libc、openssl、系统 python3、系统 curl）只由系统包管理器管，任何其他工具都不许覆盖。
2. 项目依赖只进项目目录：venv、node_modules、目标构建目录，而不是全局。
3. 用户级 CLI 交给专用工具（pipx、uvx、Scoop、Homebrew），并且把 PATH 顺序显式写进 shell 配置——不要靠「装的时候顺序刚好对」。
4. 需要两个版本并存时，用版本管理器或容器，而不是覆盖安装（见第 1.4 节）。

#### 3.1.8 反模式清单

- 用系统包管理器装语言库，事后再用语言级工具装同一个包
- 用语言级包管理器装系统库（尤其是编译器和 OpenSSL）
- 把「全局安装」当作部署方案：全局状态无法回滚，也无法在 CI 复现
- CI 用 `npm install`、本地用 `npm ci`（或反之）：两者对锁文件的处理不同，差异会在最坏的时刻暴露
- 依赖「最新版」而不锁定，同时又在生产环境要求稳定

#### 3.1.9 团队层面

只有三条硬要求：锁文件必须提交；本地与 CI 使用同一条冻结安装命令；依赖升级走独立的 PR，而不是顺手 `update` 一把混在功能提交里。前两条保证「本地能跑」等于「CI 能跑」，第三条保证升级可回滚、可二分定位。

> 一句话总结：选型不是挑最好的工具，而是把系统、项目、用户级三条边界钉死并写进文档。

### 3.2 十二个常见陷阱

下面十二条几乎涵盖了日常遇到的绝大部分依赖问题。格式统一为：现象、原因、怎么办。

#### 3.2.1 锁文件没提交，或与清单不同步

现象：本地能跑，CI 或同事机器上装出来的版本不一样。原因：清单里的范围约束在不同时间会求解出不同结果；锁文件要么没进版本库，要么改了清单却没重新生成。怎么办：把锁文件当源码提交，改完清单立刻重新求解并在同一个 PR 里提交锁文件变化；CI 用冻结模式安装。

#### 3.2.2 CI 用 install，本地用 ci（或反过来）

现象：CI 上多装/少装包，偶发失败。原因：`npm install` 会更新锁文件，`npm ci` 只按锁文件装并拒绝不一致；其他生态的 `install`/`--frozen-lockfile`/`--locked` 也是同一组语义差异。怎么办：团队统一一条命令，写进文档和 CI 配置；把不一致交给报错而不是交给运气。

#### 3.2.3 部分升级

现象：滚动发行版上装完一个包，桌面或某个程序崩了。原因：先刷新索引再单独安装，等于把新旧版本的库混在一个系统里（Arch 的 `pacman -Sy` 后接单包装就是典型）。怎么办：永远用一次完整的系统升级（`pacman -Syu`、`zypper dup`），或者用容器隔离新软件。

#### 3.2.4 幻影依赖

现象：代码里 `import` 了一个从没在清单里声明过的包，本地正常，换台机器就报找不到。原因：扁平化安装或提升把传递依赖摆在了可被解析到的位置。怎么办：把它提为直接依赖；用不提升布局的工具（pnpm 的严格结构、Yarn PnP）能从机制上暴露这类问题（见[《包管理器（一）》第 3.6 节](/post/2026/09/24/package-managers-principles/#36-隔离从全局到项目级)、[《包管理器（三）》第 1.1 节](/post/2026/09/24/package-managers-language/#11-javascriptnpm-与它的对手们)）。

#### 3.2.5 跨平台锁文件差异

现象：只能在某个平台复现的安装失败或依赖缺失。原因：可选依赖按平台求解（原生模块、平台专用二进制），不同平台生成或验证锁文件的结果不同；此外换行符与镜像源差异也会造成哈希不匹配。怎么办：锁文件在 CI 覆盖的全部平台上生成或至少验证；不要把平台专用依赖手工删掉。

#### 3.2.6 用范围版本，却从不升级

现象：安全补丁发了半年，项目还在旧版本；某天被迫一次性大升级。原因：范围约束只是「允许升级」，不是「会升级」；锁文件把版本钉住后，没人主动更新。怎么办：让自动升级工具（Dependabot、Renovate 之类）定期开 PR，小步合并；把升级当常规工作而不是紧急事件。

#### 3.2.7 全局 CLI 与项目依赖版本打架

现象：命令行跑的工具行为与项目里配置的不一致，或者两个项目要求不同的工具版本。原因：全局安装只有一个版本，且优先于项目内的版本。怎么办：项目内工具作为开发依赖声明，通过项目脚本或 `npx`/`uvx` 调用；真正的全局工具只留少数与项目无关的（机制见[《包管理器（一）》第 3.6 节](/post/2026/09/24/package-managers-principles/#36-隔离从全局到项目级)，版本切换见第 1.4 节）。

#### 3.2.8 混淆版本管理器与包管理器

现象：装了新版本的运行时，但包还是装进了旧环境；或者 `python`/`node` 指向的工具与预期不同。原因：版本管理器改的是 PATH 与 shim，包管理器装的是包；两者的作用域不一致时，包会落到「另一个」解释器上。怎么办：先确认当前解释器路径（`which python`、`node -v` 与 `Get-Command`），再决定用哪个包安装命令；把版本声明文件（`.nvmrc`、`.python-version`）提交到仓库。

#### 3.2.9 镜像与源滞后

现象：某个新版本在本地装得到、在另一台机器上「找不到」。原因：镜像同步有延迟，企业代理还有缓存过期策略；不同机器配置了不同的源。怎么办：统一团队与 CI 的源配置并纳入版本库；发布流程里避免依赖「刚发布几分钟」的版本。

#### 3.2.10 私有源顺序错误

现象：内部包名被公网同名包顶替，或装到了非预期的版本。原因：源优先级决定了同名包的胜出者，而多数工具默认「先到先得」或合并多个源。怎么办：私有源优先并对内部包使用命名空间/作用域；必要时对公网源启用白名单（这是依赖混淆的防线，见第 1.5、2.2 节）。

#### 3.2.11 开发依赖混进生产

现象：生产镜像或部署包里带着测试框架、构建工具，体积和攻击面同时变大；或者反过来，生产缺了运行必需的包。原因：安装时没有区分依赖分组，或在生产环境用了「装全部」的命令。怎么办：明确区分运行时依赖与开发依赖，生产安装显式排除开发组（`--no-dev`、`--omit=dev`、`--production`），并在 CI 里验证生产安装能跑起来。

#### 3.2.12 无节制全量升级

现象：一次升级几十个主版本，出了问题无法定位是哪一个导致的。原因：把升级当成一次性任务批量处理，且缺少测试覆盖作为安全网。怎么办：分批升级，优先补丁与小版本；把大版本升级拆成独立 PR；用锁文件回滚作为最后手段。

这十二条的共同点只有一个：把「可复现」当成了可选项。可复现不是洁癖，它是出事之后唯一能用的定位手段。

> 一句话总结：依赖事故几乎都能归到两类——状态没钉死，或者边界没划清。

### 3.3 结语：包管理器是社会产物

把这四篇的四十节压成一句话：包管理器是在几对无法同时满足的目标之间选位置的工具。

三对矛盾反复出现：

- 可复现与便利：锁文件让构建确定，代价是升级必须显式进行；自动升级省心，代价是某天早上依赖变了。
- 集中与分散：中央仓库降低发现成本、放大单点风险；vendoring 与私有源提升可控性、增加维护面积。
- 信任与效率：安装脚本让原生扩展开箱即用，同时把宿主权限交给了上游；沙箱与审计把风险压下去，也把成本抬起来。

每个具体工具——apt、pacman、Nix、npm、Cargo、uv、Conan——都只是在这三点之间占了不同的位置。理解了位置，就不需要记住所有命令，也不容易被「某某工具更好」的说法带走。

但包管理器不完全由技术决定。它是社区治理结构的固化：

- 谁有权发布：npm 的命名先到先得、crates.io 的平铺命名、Maven Central 对 groupId 所有权的验证、PyPI 对 2FA 与 Trusted Publishing 的要求，都是治理政策，不是技术必然。
- 谁能撤销：yank 的权限、撤销后下游如何应对、仓库是否允许覆盖已发布版本——这些规则直接决定了「依赖一个包」这件事的长期风险。
- 谁在维护：2024 年的 xz 后门事件提醒所有人，被无数系统依赖的项目可能只由一两个人在业余时间维护。维护者倦怠、账号接管、企业消费开源却难以回馈，都是同一结构性问题的一部分。
- 公共资源的拥挤：包名抢注、占位包、垃圾包、以及为了抢名字而发布的空包，是没有明确产权制度的公共空间的典型症状。

所以，清单文件里写下一行依赖，做的不只是技术选择，而是在给一个具体的维护者、一套治理规则、一条分发链路投票——而这一票的后果，往往在几年之后才显现。

如果这个系列只保留三句话：

1. 把依赖当作负债来管理，而不是当作资产来收集。每增加一个直接依赖，都增加一份长期的升级、审计与替换成本。
2. 先把可复现性修好：锁文件提交、CI 冻结安装、镜像按 digest 固定。这三件事能消掉大部分「本地能跑、线上不行」的玄学问题。
3. 理解机制，而不是背命令。命令会变，机制几乎不变：谁在求解、谁在执行代码、谁在缓存、失败时哪一层在报错。

回到最开始那句话：一台新机器上最先被安装的部件，往往是包管理器。它决定了这台机器几年之后是否还能被干净地重建。选哪一个从来不是最重要的问题，知不知道自己选了什么，才是。

> 一句话总结：工具会换，取舍不换——把依赖当负债管、先把可复现性修好，比记住命令更重要。
