## 一、Dijkstra 原文出处与论证

### 1. 出处

常被引用的那篇短文是 Dijkstra 的一份 EWD 系列内部手稿，不是正式期刊论文：

- 标题：*Why numbering should start at zero*
- 编号 EWD 831，写于 1982 年 8 月 11 日
- 落款 Plataanstraat 5, 5671 AL NUENEN, The Netherlands，署名 prof.dr. Edsger W. Dijkstra, Burroughs Research Fellow

### 2. 论证（两段，共两个 Remark）

原文要解决的问题是：如何不用"…"这种不严谨的省略号表示子序列 2, 3, …, 12。四种写法中，`2 ≤ i < 13`（下闭上开）胜出的理由是：

- 上下界之差等于子序列长度；
- 两个子序列相邻时，前者的上界等于后者的下界；
- 下界用 `≤`，则从最小自然数开始的子序列无需把下界推到"非自然数"；
- 上界用 `<`，则序列收缩到空序列时，上界仍落在自然数范围内。

下标从 0 开始只是这条结论的推论：长度为 N 的序列若用 1 基，下标范围要写成 `1 ≤ i < N+1`；用 0 基则是更整齐的 `0 ≤ i < N`——元素的下标等于排在它前面的元素个数。第一个 Remark 举了 Xerox PARC 的 Mesa 语言作为"四种区间记号都提供"的实践证据；第二个 Remark 点名批评 FORTRAN（下标恒为 1）、ALGOL 60 与 PASCAL（采用闭区间）、SASL（退回 FORTRAN 约定）没有重视这个细节。文章结尾交代缘起：一位数学系同事指责年轻计算机科学家"按习惯从 0 开始编号"是 pedantry。

需要注意两点常见误引。其一，这篇短文论证的核心是**半开区间记号**，而非后来的那些"0 基更优雅"的口号式表述。其二，"Should array indices start at 0 or 1? My compromise of 0.5 was rejected without, I thought, proper consideration" 出自 Stan Kelly-Bootle 的 *The Devil's DP Dictionary*，与 Dijkstra 无关。

## 二、前闭后开区间不合适的场景

`[a, b)` 的优雅来自三条性质同时成立：有最小区间单元、区间可无缝拼接、空区间能平凡表示。凡这三条被破坏，或"边界"本身不是序列上的可数位置，它就不合适。

### 1. 边界值不可达或不可表示

- 实数与浮点：`[0.1, 0.3)` 里"恰好等于 0.1 或 0.3"不是干净概念，浮点表示没法让"不含上界"成为可操作的语义。此时用开区间 `(a, b)` 或"容差 + 闭区间"更诚实。
- 连续统与无限集合：自然数有"下一个"，实数轴上的点没有。Dijkstra 的论证前提是"存在最小自然数、且讨论的是序列下标"；一旦对象是连续统，"上界取不取到"就不再是一个符号能表达清楚的事。
- 数学惯例本身是闭-闭：`[0, 1]` 是紧集、是凸组合的载体、是积分区间、也是概率的取值范围。在这里 0 与 1 完全对称，写成 `[0, 1)` 反而人为破坏对称性，区间运算与测度论的标准记号基本都优先闭区间。

### 2. 上界 +1 算不出来（溢出）

- 定宽整数上 `[lo, hi)` 需要 `hi` 是可表示的值。若上界是类型最大值，`hi + 1` 会溢出，有符号情形在 C++ 中是未定义行为。要表示"一直到末尾（含）"就只能退回闭区间或引入哨兵值。
- 不少环境根本没有"多一个"的位置：文件字节数、8 位颜色分量、0–1023 的传感器量程。用 `[0, 256)` 描述 8 位色阶，就凭空造出一个不存在的值。

### 3. 取模与循环语义

- 环形缓冲、角度、模算术里"从 i 起取 k 个"写成 `[i, i+k) mod n` 时，`i+k` 恰好回绕会带来歧义：究竟表示空区间还是整圈。回绕后再写成 `[i, i+k mod n)` 甚至可能退化成空集。取模场景下必须额外携带"长度"参数，半开记号帮不上忙。
- 全周本身无法用半开区间表示：`[0, 2π)` 与 `[2π, 4π)` 描述同一个圆，区间记号被迫引入冗余的等价类。

### 4. 离散单元没有"中间点"

- 星期、月份、枚举标签、版本号（1.2.3）这类"格子"没有下一个可数位置，`[周一, 周五)` 读出来还得翻译成"周一到周四"。用户和领域专家说的永远是"第 1 天到第 5 天"。
- 跨周期时"起点 + 长度"与"两个端点"是两种不同的操作：月末加一天会遇到闰秒与夏令时跳变，角度加一天会回绕，都不是简单整数加法。

### 5. 面向人和面向协议的闭区间惯例

- RFC 7233 的 `Content-Range` 用闭区间，形如 `bytes 0-499/1234`。
- 电子表格、SQL 的 `BETWEEN`、正则的 `{m,n}` 量词、数学教材普遍是闭-闭。把这些换成半开，就要额外维护一层 off-by-one 的转换。
- 生态本身并不统一：Python 的 `range(n)` 是半开，但 `range(1, n+1)` 很常见；Go 的切片半开，MATLAB 与 Julia 的索引是 1 基闭区间。半开的"优越性"只在同一种约定内部成立。
- 位域与硬件寄存器：`[base, base+size)` 在寄存器手册里常写成 `base..base+size-1`，因为规格书给的是"最后一位的序号"。

### 6. 结构与性能层面

- 末元素需要单独特判：很多算法要么用哨兵，要么把上界写成 `first + n - 1` 再配"闭"语义。链表、B 树这类没有"尾后指针"的结构里，半开边界要么无法表示，要么得到一个不可解引用的非法迭代器，此时闭区间或"元素 + 是否末尾"的标记更自然。
- 与重叠判定不兼容：闭区间的重叠判据是 `a.lo ≤ b.hi && b.lo ≤ a.hi`，半开的是 `a.lo < b.hi && b.lo < a.hi`。对连续值（时间跨度）想表达"端点相接即重叠"，必须再加 `+ε`；而这恰恰是连续域下无法自动化的一步。

一句话概括取舍：只要对象是**有最小单元、可拼接、上界本身又可表示**的合法值，`[a, b)` 就占优；丢掉任何一条（连续域、取模、类型极值、链式结构、面向人的闭区间惯例），它就从"更优雅"变成"多一层转换和特判"。

## 三、语言按索引起点分类

先明确两个判据：**数组/序列的"第几个元素"**与**字符串的"第几个字符"**经常不一致，同一门语言可能在两处采用不同约定；另外有些语言（Verilog、Ada）根本不固定，索引范围由声明决定。下表按"默认序列索引基"分类，备注里是需要注意的例外。

### 1. 0 基为主

| 语言 | 备注 |
| --- | --- |
| C / C++ / Objective-C | 指针运算原生，`a[0]` 即 `*(a + 0)` |
| Java / C# / Kotlin / Scala | VB.NET 同样是 0 基，`Option Base` 只影响 `Array` 构造出的下界 |
| JavaScript / TypeScript / PHP / Perl / Ruby | Ruby 的 `Array#[]` 是 0 基，负下标表示从末尾倒数 |
| Python | 0 基，但业务代码里 `range(1, n+1)` 这类 1 基写法极常见 |
| Go / Rust / Swift / D | Swift 的 `ArraySlice` 切片后仍保留原数组索引，容易踩坑 |
| Haskell / OCaml / F# / Clojure / Scheme / Common Lisp | 以列表操作为主，`nth`、`!!` 等取第 n 个的接口是 0 基 |
| Erlang / Elixir | 序列 0 基，但 `elem/2`、元组"第几段"的叙述常按 1 数 |
| 汇编与机器层、Bash、awk | 内存地址天然 0 基；awk 的 `$0` 是整行、字段从 `$1` 起 |
| J / K | J 明确采用 0 基 |
| Solidity / Move 等区块链 VM | 数组与 `bytes` 0 基，EVM 按字节偏移寻址 |
| GLSL / HLSL / WGSL / Metal SL | 向量与矩阵分量从 0 起，`v.x` 与 `v[0]` 同义 |
| BASIC 系（VB、VBScript、FreeBASIC）、Pascal 的 `array[0..n]` | 传统 BASIC 有 `OPTION BASE`，默认 0 基 |
| 算法伪代码、《算法导论》、CPython 内部 | 算法教材与解释器实现的默认语境都是 0 基 |

### 2. 1 基为主

| 语言 | 备注 |
| --- | --- |
| Fortran | 默认下标从 1 起，但可声明 `integer :: a(0:9)` |
| MATLAB / Octave / Scilab | 全 1 基，非法索引直接报错 |
| R | 1 基，但 `x[0]` 返回空向量而非报错，静默出错风险高 |
| Lua | 表与标准库约定 1 基（`#t`、`ipairs`、`table.insert`），语法仍允许 `t[0]` |
| Julia | 数组默认 1 基，`OffsetArrays` 与自定义 `axes` 可换成任意起点，索引与数组是解耦的 |
| APL（Dyalog、GNU）、Smalltalk 系 | APL 由 `⎕IO` 配置 0 或 1；Pharo 另加 0 基 API 以兼容外部库 |
| Wolfram Language | `Part`、`Take`、`Drop` 等是 1 基 |
| COBOL / RPG / ABAP | 表与内表下标 1 基 |
| Icon / Unicon | 字符串位置 1 基，列表 0 基，同语言内分裂 |
| PostScript、HyperTalk/LiveCode、Scratch、Logo、Maple、Maxima | 教学与脚本语言多取 1 基 |
| XPath / XQuery / XSLT | 节点位置 1 基 |
| 正则量词 `{m,n}`、TeX 计数 | 1 基计数 |
| Windows 注册表、Excel/Calc、SQL `ROW_NUMBER()`/`BETWEEN` | 面向人的一层一律 1 基 |
| MIDI 通道（1–16）与乐理计数 | 领域惯例 1 基 |

### 3. 由声明决定，没有固定基

- Ada：`array (1 .. 10) of ...` 与 `array (0 .. 9)` 都合法，索引类型可以是任意离散类型（含枚举与负数），惯用 `'First`/`'Last` 取代硬编码。
- Verilog / SystemVerilog：`reg [7:0] a` 是"7 到 0"，`reg [0:7] b` 是"0 到 7"，同一语言里两种方向并存；`a[0]` 的含义随声明翻转，跨模块极易出错。
- VHDL：`to` 与 `downto` 决定方向，同样不固定。
- Modula-2 / Oberon / Algol 68：数组声明包含下界，习惯 0 基但允许 1 基。

### 4. 容易被记错的点

- Lua 是 1 基而不是 0 基：`#t`、`table.insert(t, 1, v)`、`ipairs` 全按 1 基，从 C 或 Python 转过来最容易出错。
- Julia 不能笼统说成 1 基：默认轴是 `Base.OneTo(n)`，但 `OffsetArray` 可以让 `a[0]` 或 `a[5]` 都是首元素，库代码必须写 `firstindex(a)`、`eachindex(a)`。
- MATLAB、R 是 1 基且不接受 0；PHP、Perl 是 0 基。定位相似的脚本语言之间并不一致。
- 字符串索引常常与数组索引分裂：Java、C#、JS 用 0 基字符位置，SQL 的 `SUBSTRING(s FROM 1 FOR 3)`、XPath、Excel 的 `MID(s,1,3)` 用 1 基，跨这些边界做字符串处理是 off-by-one 的重灾区。
- BASIC 系有 `OPTION BASE`：VB.NET 数组恒为 0 基，但 `Dim a(1 To 5)` 可显式声明下界，读老代码时别按 0 推。
- 索引起点与区间开闭是两个独立维度：Fortran、MATLAB 是"1 基 + 闭区间"，Python、C 是"0 基 + 半开"。把两件事绑在一起记，换个语言就会出错。

## 四、序数、偏移与计数值

"索引从 1 开始、偏移从 0 开始是不是更合适"是个常见提法。它指向一个真实的分裂，但位置语义下这个组合无法自洽，能被真正分开的只有序数与计数值。

### 1. 位置语义下偏移等于索引

C 里 `a[i]` 的定义就是 `*(a + i)`，同一个 `i` 既是从首元素起的偏移，也是下标；两者相等不是约定凑出来的，而是同一个量的两种叫法（`a[i]` 与 `*(a + i)` 是同一实体）。Dijkstra 的推论同样是这个意思：元素的下标等于排在它前面的元素个数，而这正是"从首元素走了多远"。所以若指的是同一个位置，"索引 1 起、偏移 0 起"等于要求 `1 == 0`。

### 2. 能分开的是序数与计数值

- 序数（ordinal）是"第几个"，属于标签，本身不参与算术。星期、月份、版本号、SQL 的行号、XPath 的节点序都是这一类，用 1 起更自然。
- 计数值（count）是"已有多少个"，属于长度，可以做加减。`a[i]` 恰好等于 `a` 中排在 `i` 之前的元素个数，这也是偏移量的定义。

人们说"索引 1 起、偏移 0 起"时，想表达的其实是表现层的序数用 1 起、内部寻址量用 0 起。这在实践中确实存在，但它不是两套索引，而是单一约定加一层边界转换。

### 3. 现实中的几种形态

| 形态 | 例子 | 说明 |
| --- | --- | --- |
| 双系统并存 | SQL 同一查询里 `OFFSET 0` 与 `ROW_NUMBER() = 1` | 成立，但两者从不在同一次寻址中相遇，各自服务不同的读者 |
| 单一约定 + 边界转换 | MATLAB/Octave 只暴露 1 基，函数内部一律写 `a(i-1)`；Fortran 同理 | 这才是"索引用 1、内部偏移用 0"的实际形态，那个 0 用户看不到 |
| 抽象掉索引 | Julia 的 `axes`/`eachindex`、Rust 的迭代器、Ada 的 `'First`/`'Last` | 让"第几个"与"偏移多少"不再需要人肉换算 |
| 显式声明下界 | Fortran 的 `integer :: a(0:9)`、Ada 的 `array (0 .. 9)`、VB 的 `Option Base` | 下界成为数据的一部分，语言不固定 |

MATLAB 能在只有 1 基的面上活得很好，靠的是 `end` 关键字：`a(end)`、`a(2:end-1)` 直接表达"最后一个""倒数第二个"，绕开了"没有合法 0 开区间"的困难。也就是说它用另一个语言设施补上了 1 基的缺口，而不是偷偷引入一个 0 基偏移。

### 4. 两套数字同时表示一个位置时会出问题

- 每处边界都要 ±1 转换，`a[i+1]` 的含义随"i 是哪一种"而变，这是 off-by-one 的高发区。
- 半开区间的拼接性质失效：混用 `1..=n` 与 `[0, n)` 之后，"相邻两段的上界等于下界"必须经过两个数字系统的换算才能恢复。Dijkstra 那条论证依赖上界是可表示的位置。
- 空序列、越界、切片边界的判定要各写两套；序列为空时"第 1 个"与"偏移 0"指向同一处却不等值。
- 序列化与协议里必须注明是哪一种，否则 `0` 究竟是"第一个"还是"没有偏移"无法分辨。

### 5. 结论

只要索引是位置，0 基偏移与 1 基序数就无法同时充当寻址方案；能够同时存在的是"内部的 0 基偏移"与"展示给用户的 1 基序数"，中间由语言或库自己转换。

Dijkstra 论证的范围也需要说清：他论证的是半开区间记号，而"从 0 开始"只在讨论位置时才是其推论。一旦对象是标签（星期、月份、版本号、枚举、行号）或数学区间（`[0, 1]`、积分区间），1 基与闭区间反而更自然，因为前者不参与算术、后者的端点是对称的——这正是第二节那些失配场景的来源。
