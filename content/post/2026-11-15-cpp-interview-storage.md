## 1. 存储层次与设备

### 1.1 HDD 的一次随机读由哪些延迟构成？

- 访问时间由寻道时间、旋转延迟与传输时间组成，前两项在随机读中占主导。
- 寻道时间取决于磁头臂移动距离，典型值为数毫秒；旋转延迟平均为半圈，7200 RPM 时约 4.17 ms。
- 传输时间等于请求字节数除以持续传输率，4 KiB 随机读时占比很小。
- 磁道由低级格式化划分，现代盘的实际扇区为 4 KiB，对外常报告 512 B 逻辑扇区。
- 同一磁道内的连续扇区读取不需要寻道，跨磁道时才产生额外开销。
- 写操作还需等待目标扇区旋转到磁头下方，小于物理扇区的写可能触发读改写。
- 提高队列深度可让调度器重排请求，减少总寻道距离。

### 1.2（辨析）扇区、块、页与记录分别指什么？

- 扇区是设备的最小寻址单位，`ioctl` 的 `BLKSSZGET` 返回逻辑扇区大小，`BLKBSZGET` 返回物理扇区大小。
- 块是块层的传输与合并单位，通常等于逻辑扇区，上限受 `max_sectors_kb` 约束。
- 页是内存管理与页缓存的最小单位，x86-64 上为 4 KiB，由 `getpagesize` 返回。
- 记录是数据库引擎的逻辑单位，一行或一个键值对可跨多个页，也可在一页内放多条。
- 数据库页是引擎自定义单位，InnoDB 默认 16 KiB，可配置为 4 KiB、8 KiB、16 KiB、32 KiB、64 KiB。
- 物理扇区为 4 KiB 而逻辑扇区为 512 B 时，512 B 对齐的写会触发读改写。
- 分配缓冲区与设置文件偏移时应满足三者中最大的对齐要求。

### 1.3 SSD 的读、写、擦除为何不对称？

- NAND 闪存以浮栅电荷表示位，编程只能把位从 1 写成 0，擦除以块为单位把整块恢复为 1。
- 读以页为单位，典型为 4 KiB 至 16 KiB；写同样以页为单位，且只能写入已擦除的页。
- 擦除以块为单位，典型为数百页，擦除延迟远高于读写。
- 覆写已有页需要先把块内有效页复制到新块，再擦除旧块，产生额外写入。
- 读延迟在几十微秒量级，写延迟在数百微秒量级，擦除在数毫秒量级，具体由实现定义。
- 每个块的编程与擦除次数有限，SLC 约为 10 万次，TLC 约为 1000 至 3000 次，具体由实现定义。
- 随机写的性能取决于剩余空间与垃圾回收状态，与机械寻道无关。

### 1.4（陷阱）SSD 上覆写一个已有页会原地修改吗？

- 不会。闪存页不能原地改写，FTL 把逻辑页重新映射到新的物理页，旧页标记为失效。
- 失效页所在块中的有效页需要在垃圾回收时搬移，搬移量与块内有效页比例成正比。
- 剩余空间充足时垃圾回收可以推迟，写放大较低；空间紧张时搬移量上升。
- 同一逻辑页覆写 N 次会产生 N 个物理页写入，外加搬移开销，写放大可超过 2。
- 顺序写满整块时，块内页一次性写满，搬移的有效页少，写放大接近 1。
- 随机写放大、顺序写放大属于闪存介质特性，与文件系统的写策略叠加。
- 上层可通过日志结构写入、批量合并与预留空间降低写放大。

### 1.5 FTL 的映射粒度如何影响写放大？

- 页级映射为每个逻辑页维护独立映射，随机写灵活，映射表较大。
- 1 TiB 容量、4 KiB 页、每项 4 B 时，映射表约为 1 GiB，无法全部驻留 DRAM。
- 块级映射只维护块号映射，表小，但随机写需要整块读改写，写放大高。
- 混合映射固定块内偏移、只映射块号，在表大小与随机写之间折中。
- 映射粒度越细，随机写越灵活，DRAM 成本与缺页开销越高。
- 映射表本身是持久数据，掉电后需从闪存重建或从日志恢复。
- 映射表未命中会增加一次读延迟，命中率影响随机读性能。

### 1.6（场景）4 KiB 随机写落在有效数据占 80% 的块上，写放大如何估算？

- 设垃圾回收选择有效数据占比为 u 的块，回收 1 字节空闲空间需搬移 u/(1-u) 字节。
- 写放大为 1/(1-u)，u 为 0.5 时为 2，u 为 0.8 时为 5，u 为 0.9 时为 10。
- 随机写不断产生失效页，u 随空间占用上升，写放大随之上升。
- 设备预留空间（over-provisioning）降低可用块的占用率，直接降低 u。
- 端到端写放大还要叠加文件系统日志、数据库 WAL 与页填充带来的放大。
- 用设备写入字节数除以应用写入字节数可得实测倍数，`iostat -x` 的 `wkB/s` 可作为分子。
- 估算应使用稳态下的 u，刚格式化时的空盘状态会低估写放大。

### 1.7 TRIM 与 discard 的作用与代价是什么？

- TRIM 告知设备某些逻辑块不再使用，FTL 可标记为无效，垃圾回收时不必搬移。
- 不下发 TRIM 时，设备认为这些页仍有效，搬移量上升，写放大与延迟增加。
- `fstrim` 定期批量下发，挂载选项 `discard` 在删除时同步下发，后者对延迟不友好。
- discard 只是提示，设备可以忽略；下发后读取该区域的内容由实现定义。
- 加密盘上 discard 与自加密的交互需要确认，部分设备在 discard 后仍可读出旧密文。
- 数据库文件预分配并循环复用时，TRIM 的收益有限，反而增加元数据开销。
- 精简置备卷与虚拟机镜像需要逐层传递 discard，否则空间不会回收。

### 1.8（实现）如何在 C++ 中查询扇区大小并对齐分配？

```cpp
#include <fcntl.h>
#include <sys/ioctl.h>
#include <linux/fs.h>

int sector_size(int fd) {
    int logical = 0;
    if (ioctl(fd, BLKSSZGET, &logical) != 0) return -1;
    int physical = 0;
    if (ioctl(fd, BLKBSZGET, &physical) != 0) return logical;
    return physical > logical ? physical : logical;
}
```

- `BLKSSZGET` 返回逻辑扇区大小，`BLKBSZGET` 返回物理扇区大小，两者可能不同。
- 缓冲区地址、长度与文件偏移都应满足查询结果，`O_DIRECT` 的读写才可能成功。
- 用 `posix_memalign` 或 `std::aligned_alloc` 分配对齐缓冲区。
- `std::aligned_alloc` 要求大小为对齐值的整数倍，不满足时行为由实现定义。
- `new` 不保证超过 `__STDCPP_DEFAULT_NEW_ALIGNMENT__` 的对齐，需要带对齐参数的 `operator new`。
- 查询失败时应回退到 512 B 并记录，不能假定设备为 4 KiB。
- 页大小与物理扇区大小都满足时，直接 IO 才不会触发块层的读改写。

### 1.9 块层如何合并与拆分 IO 请求？

- 相邻逻辑块且方向相同的请求可合并为一个 bio，合并受 `max_sectors_kb` 与 `max_segments` 限制。
- 物理地址不连续的页需要多个段，段数超过 `max_segments` 时请求被拆分。
- 拆分后的请求分别排队，可能乱序完成，上层需按偏移重组。
- 合并减少请求数而不减少字节数，对 HDD 提升明显，对 NVMe 提升有限。
- `blktrace` 可观察 `Q`、`G`、`I`、`D`、`C` 各阶段，区分排队时间与设备时间。
- 请求大小与设备最优传输单位不匹配时，控制器内部仍会拆分。
- 大页与连续映射可减少段数，但受 `max_segments` 与 IOMMU 限制。

### 1.10 IO 调度器的选择依据是什么？

- `none` 不做重排，请求直接下发，适合 NVMe 等低延迟设备。
- `mq-deadline` 为请求设置截止时间，读优先于写，适合多数通用场景。
- `bfq` 按权重分配带宽，适合桌面与交互场景，开销高于前两者。
- `kyber` 按读同步、读异步、写同步、写异步四类限流，适合快速设备。
- HDD 上调度器的重排可显著减少寻道，SSD 上收益主要来自合并与限流。
- 调度器通过 `/sys/block/sda/queue/scheduler` 查看与设置，多队列设备按硬件队列生效。
- 云盘与虚拟化层可能屏蔽调度器，实际行为由实现定义。

### 1.11（辨析）bio、request 与 plug 链表处于块层的哪个阶段？

- bio 描述一次 IO 的页与偏移，携带 `bi_sector`、`bi_iter` 与操作类型。
- 请求队列把相邻 bio 合并为 request，request 是调度与下发的单位。
- plug 链表暂存 bio，延迟提交以增加合并机会，由 `blk_start_plug` 与 `blk_finish_plug` 成对使用。
- `submit_bio` 进入块层，`submit_bio_noacct` 负责拆分与递归提交。
- 多队列块层用 `blk_mq` 把 request 分配到硬件队列，软件队列只做暂存。
- 合并发生在 plug 阶段与调度器入队阶段，两处都受设备参数限制。
- 直接 IO 绕过页缓存，但仍经过 bio 与请求队列。

### 1.12 NVMe 的提交与完成如何工作？

- 主机在提交队列写入命令，再写门铃寄存器 `SQxTDBL` 通知控制器。
- 控制器执行完成后在完成队列写入完成项，产生中断或更新相位位。
- 完成项包含命令标识、状态与队列头指针，主机处理后写 `CQxHDBL`。
- 队列对由提交队列与完成队列组成，深度可达 64 Ki 项，队列数可达 64 Ki。
- 命令以 64 字节固定格式描述读写、flush 与 write zeroes 等操作。
- 多队列与多核一一对应，避免锁竞争，中断可绑定到提交核。
- `io_uring` 的 `IORING_SETUP_IOPOLL` 可轮询完成队列，省去中断开销。

### 1.13（陷阱）队列深度越大，IOPS 一定越高吗？

- 队列深度提高可提升并发，但受设备内部通道数、垃圾回收状态与写缓冲限制。
- 达到饱和点后继续加深队列只增加排队延迟，吞吐不再上升。
- 应用侧线程数、文件系统锁与块层软件队列也会成为瓶颈。
- 同步 IO 的队列深度等于并发线程数，单线程同步读写的深度为 1。
- `io_uring` 与异步 IO 可在单线程内提交多个请求，提高深度而不增加线程。
- 延迟敏感场景应控制深度，避免排队延迟超过服务时间。
- `iostat` 的 `aqu-sz` 与 `%util` 可判断设备是否饱和。

### 1.14（场景）如何用 Little 定律估算随机读的并发需求？

- Little 定律为 L = λ × W，L 为系统中并发请求数，λ 为到达率，W 为平均停留时间。
- 目标为 50 000 IOPS、单次延迟 100 µs 时，所需并发为 5。
- 单次延迟升至 1 ms 时，维持同样吞吐需要 50 个并发请求。
- 给定并发数 N 与延迟 W，吞吐上限为 N / W。
- 该估算假设请求独立且服务时间稳定，实际需按 P99 延迟留余量。
- 写请求的延迟随垃圾回收波动，估算时应使用尾延迟。
- 同步调用模型下线程数即并发数，线程栈与上下文切换成本需一并考虑。

### 1.15 为什么 SSD 上顺序与随机的差距小于 HDD？

- HDD 的随机读需要寻道与旋转，顺序读可省去这两项，差距可达两个数量级。
- SSD 没有机械部件，随机读的延迟由通道并行度与映射表命中率决定。
- 随机写仍受页与块约束，差距主要来自垃圾回收与写放大。
- 大块顺序写在 FTL 中可整块写入，避免读改写，写放大接近 1。
- 随机写分散到多个块，垃圾回收时搬移量上升，长期吞吐下降。
- 设备内部多通道并行使 4 KiB 随机读仍能达到较高 IOPS，但需要足够的队列深度。
- SSD 的优化重点从减少寻道转为减少写放大与保持空闲块。

### 1.16（场景）如何解读 `iostat` 的利用率与队列指标？

- `%util` 表示设备繁忙时间比例，在单队列设备上是接近饱和的判据。
- 多队列与 NVMe 上 `%util` 可长期为 100% 而仍有剩余带宽，不能单独作为瓶颈依据。
- `aqu-sz` 为平均队列长度，结合 `r_await` 与 `w_await` 判断排队延迟。
- `r/s` 与 `w/s` 反映请求数，`rkB/s` 与 `wkB/s` 反映吞吐，两者相除可得平均请求大小。
- 应用写入量与设备写入量之比可估算写放大。
- `%util` 高且 `await` 高说明设备饱和；`%util` 低而 `await` 高说明存在排队或后端延迟。
- 容器内看到的设备指标可能被虚拟化层聚合，需要在宿主机确认。

### 1.17 如何根据 TBW 与 DWPD 估算设备寿命？

- TBW 表示寿命期内可写入的总字节数，DWPD 表示每日可写满全盘的次数。
- 换算关系为 TBW = 容量 × DWPD × 365 × 保修年数。
- 1 TB 容量、1 DWPD、5 年保修对应约 1825 TB。
- 实际写入量需乘以写放大，应用层写入 1 TB 可能对应介质写入数 TB。
- `smartctl -a` 的 `Data Units Written` 与 `Percentage Used` 可用于估算剩余寿命。
- 写放大高的负载应预留更多空间或选用更高耐久度的介质。
- TBW 是保修指标，超过后设备仍可能工作，但误码率上升，具体由实现定义。

### 1.18（场景）设备接近寿命终点时会出现哪些现象？

- 坏块增多，可用块减少，垃圾回收更频繁，写延迟上升。
- 读重试次数增加，`smartctl` 的 `Media and Data Integrity Errors` 上升。
- 写入可能返回 `EIO`，文件系统转为只读，应用需处理写失败。
- 预留空间耗尽后写放大急剧上升，性能出现明显下降。
- 部分设备进入只读模式以保护数据，此时只能读取。
- 监控应覆盖 `Percentage Used`、可用备用块与重试计数。
- 更换设备前应完成数据校验，避免把静默损坏带入新介质。

### 1.19（实现）如何用内存池管理对齐的 IO 缓冲区？

```cpp
struct FreeDeleter {
    void operator()(void* p) const noexcept { std::free(p); }
};
using Buffer = std::unique_ptr<void, FreeDeleter>;

Buffer make_io_buffer(std::size_t size, std::size_t align) {
    void* p = std::aligned_alloc(align, size);
    if (p == nullptr) throw std::bad_alloc();
    return Buffer{p};
}
```

- 缓冲区按页对齐分配，大小取设备逻辑扇区与页大小的较大者。
- 池化避免每次 IO 都调用分配器，也避免长时间运行后的地址空间碎片。
- 归还时不必清零，但含敏感数据时需显式覆盖。
- 缓冲区生命周期必须覆盖 IO 完成，异步 IO 中提前释放会让内核写入已释放内存。
- `unique_ptr` 加自定义删除器表达所有权，异常路径自动归还。
- 池容量应与队列深度匹配，过小会阻塞提交，过大浪费内存。
- 分配失败时抛出异常，避免调用方漏检空指针。

### 1.20（陷阱）把设备缓存、页缓存与数据库缓冲池混为一谈会怎样？

- 三层缓存各自有独立的失效与持久化语义，混用会得出错误的持久性结论。
- 页缓存由内核管理，`write` 返回只表示数据进入页缓存。
- 设备缓存在盘上，`fsync` 是否真正下发 flush 取决于文件系统与设备能力。
- 数据库缓冲池在进程内，提交成功只表示日志已写入，数据页可以延后。
- 掉电时三层缓存的内容都可能丢失，恢复只能依赖已落盘的日志。
- 判断数据是否持久应检查调用链上每一层的保证。
- 基准测试若不区分三层，测得的吞吐可能只是缓存吞吐。

## 2. 文件系统与持久化

### 2.1 inode 保存哪些信息，为什么不保存文件名？

- inode 保存文件类型、权限、所有者、大小、时间戳、链接计数与数据块位置。
- 文件名保存在目录项中，目录是「名字到 inode 号」的映射。
- 硬链接使多个名字指向同一 inode，inode 中无法容纳数量不定的名字。
- ext4 的 inode 用区段树描述数据块，小文件的数据可直接存放在 inode 中。
- 链接计数减为 0 且没有进程打开时才释放数据块。
- inode 号在文件系统内唯一，跨文件系统不唯一。
- inode 数量在 `mkfs` 时确定，耗尽后即使有空间也无法创建文件。

### 2.2（辨析）硬链接、软链接与目录项有何区别？

- 硬链接是目录项指向同一 inode，链接计数加一，删除任一名字不影响其他名字。
- 软链接是独立文件，内容是目标路径，目标不存在时解析失败并返回 `ENOENT`。
- 目录项缓存把「父目录 inode 加名字」映射到 dentry，加速路径解析。
- 硬链接不能指向目录，避免形成环；软链接可以指向目录。
- `rename` 在同一文件系统内原子替换目录项，跨文件系统返回 `EXDEV`。
- 删除打开中的文件只减少链接计数，数据在最后一个引用释放后回收。
- `stat` 的 `st_nlink` 反映硬链接数，软链接本身也占一个 inode。

### 2.3 ext4 的三种日志模式在一致性与性能上有何差异？

- `data=journal` 把数据与元数据都写入日志，一致性最强，吞吐最低。
- `data=ordered` 只记录元数据，并保证数据块先于引用它的元数据提交。
- `data=writeback` 只记录元数据，数据可能晚于元数据落盘，崩溃后可能读到旧块内容。
- 三种模式都保证文件系统结构一致，不保证应用数据的持久性。
- `ordered` 是多数发行版的默认值。
- 日志是环形区域，提交与检查点决定可回收空间。
- 模式通过挂载选项设置，可从 `/proc/mounts` 查看。

### 2.4 fsync 保证了什么，又不保证什么？

- `fsync` 把文件的脏数据与元数据写入存储，并等待设备确认。
- 返回成功表示数据已到达持久介质，前提是设备遵守 flush 语义。
- 不保证目录项持久，新建文件后需对父目录调用 `fsync`。
- 不保证其他文件或其他目录的更新，范围限于该文件描述符对应的 inode。
- 不保证多个文件之间的顺序，除非按顺序逐次调用并等待返回。
- 部分文件系统在 `fsync` 失败后会把错误标记为已写入，后续调用可能不再报错。
- 返回 `EIO` 时应视为数据可能丢失，需要从副本恢复。

### 2.5（陷阱）`rename` 返回成功后新文件一定可见且持久吗？

- `rename` 在同一文件系统内原子替换目录项，崩溃后要么看到旧文件，要么看到新文件。
- 返回成功只表示目录项已更新，数据与目录项可能仍在页缓存中。
- 要保证持久，需先 `fsync` 新文件，再 `rename`，再 `fsync` 父目录。
- 缺少父目录的 `fsync` 时，掉电后可能看不到新名字，即使数据已落盘。
- `rename` 跨文件系统会返回 `EXDEV`，需退化为复制加删除，失去原子性。
- 覆盖已有文件时，旧 inode 在最后一个引用释放后回收。
- `renameat2` 的 `RENAME_NOREPLACE` 可避免覆盖，`RENAME_EXCHANGE` 可原子交换。

### 2.6 fsync 与 fdatasync 的差别在哪里？

- `fdatasync` 只保证数据与读取数据所需的元数据落盘，不等待无关元数据。
- 文件大小变化属于影响数据读取的元数据，`fdatasync` 仍需更新 inode 的大小与块映射。
- 修改时间戳、权限等元数据时，`fdatasync` 可能不落盘，`fsync` 会等待。
- 日志模式下两者都要等待日志提交，差异主要在 inode 表的写入。
- 频繁追加写场景中，`fdatasync` 可省去一次 inode 更新，收益有限，但仍减少一次元数据写入。
- 两者都不保证父目录项，创建与删除仍需目录 `fsync`。
- 语义由 POSIX 定义，具体实现可能把两者等同，由实现定义。

### 2.7 WAL 的写入顺序为什么必须是「日志在前、数据在后」？

- 修改数据页前先把变更写入日志并持久化，崩溃后可用日志重放或回滚。
- 若数据页先于日志落盘，崩溃时页上可能出现未记录的变化，无法判断其有效性。
- 日志记录需要包含页号、前像或后像、事务标识与校验和。
- 提交记录写入并 `fsync` 后才向客户端确认，这是持久性的分界点。
- 重放按 LSN 顺序应用，幂等性由页上的 LSN 比较保证。
- 日志与数据在同一设备上时，顺序由文件系统的屏障与设备 flush 共同保证。
- 组提交把多个事务的日志合并为一次 `fsync`，用延迟换吞吐。

### 2.8（场景）崩溃恢复时如何决定重放还是回滚？

- 分析阶段从检查点开始扫描日志，重建事务表与脏页表。
- 重做阶段从最早未刷盘的 LSN 开始，按页比较 LSN 决定是否应用后像。
- 撤销阶段回滚未提交事务，使用前像或 undo 链。
- 检查点记录活动事务与脏页，缩短恢复时需要扫描的日志范围。
- 日志尾部不完整的记录校验失败，视为日志结束，截断后不再重放。
- 恢复过程必须幂等，重复崩溃后可再次执行。
- 恢复时间与需要扫描的日志量成正比，检查点间隔决定上限。

### 2.9 检查点与日志截断的关系是什么？

- 检查点把脏页刷到数据文件，并记录当时的 LSN 与活动事务。
- 日志截断只能回收「脏页已全部落盘且不再需要前像」的那部分。
- 模糊检查点不阻塞事务，只记录起点，恢复时需从更早的位置开始。
- 一致性检查点阻塞写入，恢复快但影响可用性。
- 日志空间不足时数据库会停止接受写或强制检查点。
- 截断点之前的日志可被覆盖，覆盖前需确认归档或复制已完成。
- 检查点频率影响恢复时间与写放大，需要权衡。

### 2.10 O_DIRECT 绕过页缓存后，语义发生了什么变化？

- 读写直接在用户缓冲区与设备之间进行，不经过页缓存，减少一次复制。
- 对齐要求更严格，缓冲区地址、长度与文件偏移都需按逻辑扇区对齐。
- 不享受预读与写合并，小块随机 IO 的性能可能低于缓冲 IO。
- 与 `mmap` 共享同一文件时可能出现数据不一致，因为页缓存不参与。
- 文件系统仍需维护元数据，`O_DIRECT` 不绕过日志。
- 部分文件系统对 `O_DIRECT` 支持有限，跨块边界的写可能退化为缓冲 IO。
- 数据库自建缓冲池时使用它避免双重缓存，但需自行处理对齐与预读。

### 2.11（辨析）缓冲 IO、`mmap` 与 `O_DIRECT` 的持久化语义有何不同？

- 缓冲 IO 的 `write` 只把数据复制进页缓存，落盘由回写线程或 `fsync` 触发。
- `mmap` 的写通过页表直接修改页缓存，`msync` 才保证回写。
- `O_DIRECT` 的 `write` 等待设备完成，但仍需 `fsync` 保证元数据。
- 三者都不保证父目录项，创建文件后都需目录 `fsync`。
- `mmap` 的缺页可能触发读，`MAP_SHARED` 与 `MAP_PRIVATE` 的语义不同。
- `msync` 的 `MS_SYNC` 等待回写完成，`MS_ASYNC` 只调度回写。
- 崩溃后三种方式的可见性都取决于设备缓存是否被 flush。

### 2.12 文件系统如何实现写屏障？

- 屏障要求前面的写先于后面的写到达介质，由 `REQ_PREFLUSH` 与 `REQ_FUA` 表达。
- 日志提交时先写日志块并 flush，再写提交块，提交块带校验和。
- ext4 通过 `jbd2` 的提交记录与 flush 或 `REQ_FUA` 保证提交块在数据块之后落盘。
- 屏障只保证顺序，代价是每次都要等待设备确认，吞吐受 flush 次数限制。
- 多设备场景需要上层协调，文件系统屏障不跨设备。
- 关闭屏障会破坏一致性保证，只在数据可重建时使用。
- 虚拟化层可能吞掉 flush，需要确认存储栈的语义。

### 2.13（实现）如何写满一次 `pwrite` 并处理短写与 `EINTR`？

```cpp
bool write_all(int fd, const char* buf, std::size_t len, off_t off) {
    while (len > 0) {
        ssize_t n = ::pwrite(fd, buf, len, off);
        if (n < 0) {
            if (errno == EINTR) continue;
            return false;
        }
        if (n == 0) return false;
        buf += n;
        len -= static_cast<std::size_t>(n);
        off += n;
    }
    return true;
}
```

- `pwrite` 不改变文件偏移，适合多线程并发写同一文件的不同区域。
- 返回 0 表示没有进展，继续重试不会前进，应视为错误。
- `EINTR` 需重试，其余错误应上抛并保留 `errno`。
- 部分写在大文件与信号场景下常见，必须循环直到写完。
- `off_t` 在 32 位平台可能溢出，编译时应启用大文件支持。
- 写完后再调用 `fsync` 或 `fdatasync`，否则数据可能仍在页缓存。
- 错误路径应保证缓冲区不被提前释放，异步场景尤甚。

### 2.14 如何原子地替换一个文件？

- 写临时文件，`fsync` 临时文件，`rename` 覆盖目标，`fsync` 父目录。
- 临时文件应与目标位于同一目录或同一文件系统，否则 `rename` 失败。
- 临时文件名需唯一，可用 `mkstemp` 生成，避免并发冲突。
- 缺少第一步的 `fsync` 时，掉电后可能出现空文件或部分内容。
- 缺少最后一步的 `fsync` 时，掉电后可能仍看到旧名字。
- `rename` 的原子性只针对目录项，不针对文件内容。
- 需要保留旧版本时可用 `link` 加 `rename` 的组合，或使用版本号目录。

### 2.15 掉电后文件出现大段零字节的原因是什么？

- ext4 的延迟分配在 `write` 时不立即分配块，块在回写时才分配。
- `data=writeback` 模式下元数据可能先于数据提交，崩溃后文件长度已更新而数据块未写入。
- `data=ordered` 模式保证数据块先于引用它的元数据提交，不会暴露旧块内容。
- 新建文件后未 `fsync` 就 `rename`，掉电后可能得到零长度文件，延迟分配会放大该问题。
- `fallocate` 只保留块，不写入内容，读到的是零。
- `fsck` 修复元数据，无法恢复未写入的数据。
- 应用层应在关键写入后调用 `fsync`，并校验长度与内容。

### 2.16（场景）如何检测掉电造成的页撕裂？

- 页撕裂指一次页写入只有部分扇区落盘，页内出现新旧混合内容。
- 数据库在页头与页尾各放一个校验和，两者一致才认为页完整。
- InnoDB 的 doublewrite 把页先写入连续区域，再写数据文件，崩溃后可从中恢复。
- 校验和不匹配时从 doublewrite 或副本恢复，无法恢复则报错。
- 文件系统日志只保证元数据一致，不保护数据页的原子性。
- 设备原子写可保证一定粒度内的写原子性，需要硬件与文件系统支持。
- 校验和应覆盖整页，包括页头中的 LSN。

### 2.17（实现）磁盘格式中的整数如何序列化？

- 固定宽度整数使用 `std::uint32_t` 等类型，避免 `long` 在不同平台宽度不同。
- 显式按字节写入，避免直接 `memcpy` 结构体，因为填充与对齐由实现定义。
- 小端格式可用移位与掩码逐字节写入，不依赖主机字节序。
- 浮点数应按 IEEE 754 位模式写入，或改用定点数避免格式差异。
- 字符串需记录长度或使用长度前缀，不能依赖 `'\0'` 结尾。
- 魔数与版本号放在头部，便于识别格式与拒绝不兼容文件。
- 反序列化时先校验长度与边界，避免越界读。

### 2.18（输出题）下列代码在小端机器上输出什么？

```cpp
#include <cstdint>
#include <cstdio>

int main() {
    std::uint32_t v = 0x01020304;
    unsigned char b[4];
    for (int i = 0; i < 4; ++i) b[i] = static_cast<unsigned char>(v >> (8 * i));
    std::printf("%02x %02x %02x %02x\n", b[0], b[1], b[2], b[3]);
}
```

- 输出为 `04 03 02 01`，最低有效字节在前。
- 该写法不依赖主机字节序，在任何平台上都得到相同结果。
- 若直接 `memcpy` 到 `unsigned char[4]`，大端机器上的结果相反。
- `printf` 的 `%02x` 接收 `int`，`unsigned char` 会经默认提升转换。
- 读回时按同样顺序移位组合，即可还原原值。
- 网络协议通常使用大端，磁盘格式可自行约定，但需在文档中写明。
- 结构体直接落盘还会受填充影响，跨编译器不可移植。

### 2.19 fallocate 与稀疏文件对持久化有什么影响？

- `fallocate` 预分配块并标记为未初始化，写入前读取返回零。
- 预分配减少运行时的块分配开销，也降低碎片与延迟抖动。
- 稀疏文件的空洞不占块，读取返回零，`du` 与 `ls -l` 显示的大小可能不同。
- 复制稀疏文件时未使用 `SEEK_HOLE` 会展开空洞，占用大量空间。
- `FALLOC_FL_PUNCH_HOLE` 可释放区间，配合 TRIM 回收设备空间。
- 预分配的空间在崩溃后仍属于文件，但内容未初始化。
- 部分文件系统不支持 `fallocate`，会返回 `EOPNOTSUPP`。

### 2.20（陷阱）`readdir` 返回的顺序稳定吗？

- 目录项顺序由文件系统内部结构决定，不保证按名字或创建时间排序。
- ext4 使用哈希树组织大目录，顺序与哈希值相关，增删后可能变化。
- 依赖顺序的测试或分页逻辑在数据量变化后会失效。
- 需要稳定顺序时应显式排序，或使用带序号的主键。
- `readdir` 返回的 `d_off` 用于续读，目录变动后可能失效。
- 遍历大目录时应分批处理，避免一次性加载全部名字。
- 目录项缓存会加速重复遍历，但不改变顺序语义。

## 3. B+ 树与索引

### 3.1（辨析）B 树与 B+ 树的差异在哪里？

- B 树的内部节点同时保存键与记录，查找可能在内部节点结束。
- B+ 树的内部节点只保存键与子指针，记录集中在叶节点，叶节点按键顺序链接。
- B+ 树的叶节点链表使范围扫描只需顺序遍历，不必回溯到上层。
- B+ 树内部节点的扇出更大，同样高度可容纳更多记录。
- B 树的点查可能在较浅的层结束，平均路径略短。
- 数据库多采用 B+ 树及其变体，因为范围查询与全表扫描更高效。
- 两种结构都保持所有叶节点到根的距离相同，即平衡。

### 3.2 节点容量如何由页大小与键长决定？

- 内部节点容量约为页大小除以「键长加子指针长」，再减去页头与槽目录开销。
- 叶节点容量约为页大小除以「键长加记录指针长」。
- 16 KiB 页、8 B 键、6 B 指针时，内部节点扇出约为 1170，三层可索引约十亿条记录。
- 键越长，扇出越小，树高增加，点查的 IO 次数上升。
- 页内需要预留空间给槽目录与空闲空间管理，实际容量小于理论值。
- 填充因子控制分裂后的占用率，影响空间与写放大。
- 大记录可外置到溢出页，叶节点只保存指针。

### 3.3 节点分裂的过程与代价是什么？

- 插入导致叶节点溢出时，分配新页，把一半记录或按键的中位数移到新页。
- 父节点需要插入分隔键与新页指针，若父节点也溢出则继续向上分裂。
- 根分裂时创建新根，树高加一，这是唯一增加树高的路径。
- 分裂需要修改原页、新页与父页，并写日志。
- 随机插入使页填充率落在 50% 至 70%，空间利用率下降。
- 自增键使插入集中在最右页，分裂后可保持较高填充率。
- 分裂的原子性由 WAL 保证，崩溃后看到分裂前或分裂后的状态。

### 3.4 删除时什么时候合并或借位？

- 叶节点记录数低于阈值时，先尝试从兄弟节点借一条记录，只更新父节点的分隔键。
- 兄弟节点也不足时合并两个节点，父节点删除对应指针，可能级联向上。
- 合并会释放页，也可能造成后续插入再次分裂，形成抖动。
- 多数实现延迟合并，只在空间明显浪费时才执行。
- 合并需要修改兄弟页、父页与被删页，日志记录需保证原子性。
- 根节点只剩一个子节点时降低树高。
- 删除后的空间留在页内空闲列表，供后续插入复用。

### 3.5 范围查询在 B+ 树上如何执行？

- 先定位起始键所在的叶节点，再沿叶节点链表向右扫描直到超过上界。
- 定位的代价与树高成正比，每层一次页读；扫描的代价与结果集大小成正比。
- 叶节点链表使跨页扫描不需要回到根，顺序 IO 友好。
- 若查询需要回表，每行还要按主键再查一次聚簇索引。
- 反向扫描需要叶节点有前驱指针，或使用双向链表。
- 扫描期间需持有叶节点的 latch，避免并发分裂导致结构变化。
- 结果集很大时应使用游标分批读取，避免一次性物化。

### 3.6（辨析）聚簇索引与二级索引的差异是什么？

- 聚簇索引的叶节点直接保存整行，表数据按主键顺序组织。
- 二级索引的叶节点保存索引列与主键值，查询非索引列需要回表。
- 聚簇索引的点查一次即可拿到整行，二级索引通常需要两次。
- 主键长度影响所有二级索引的大小，因为每个索引项都带主键。
- 按主键范围扫描是顺序 IO，按二级索引扫描可能退化为随机 IO。
- 更新主键代价高，需要移动行并更新所有二级索引。
- 没有显式主键时，实现可能使用隐藏列作为聚簇键，由实现定义。

### 3.7 覆盖索引如何避免回表？

- 查询涉及的列全部包含在索引中时，直接从索引叶节点返回结果。
- 覆盖索引减少一次随机读，对高并发点查提升明显。
- 联合索引的列顺序决定能否覆盖，把常查列放在索引末尾可提高覆盖率。
- 覆盖索引的代价是索引更大，写入时需要维护更多列。
- 执行计划中的 `Using index` 表示使用了覆盖索引。
- 二级索引已隐含主键列，查询主键时天然覆盖。
- 过宽的索引会增加写放大与缓存压力，需要权衡。

### 3.8 联合索引的最左前缀原则由什么决定？

- 索引按键的字典序排列，先比较第一列，再比较第二列。
- 只有从最左列开始提供等值条件，才能利用后续列的排序。
- 范围条件会截断后续列的使用，范围列之后的列无法用于定位。
- 跳过最左列的条件通常无法使用该索引，除非使用索引跳跃扫描。
- 列顺序应让选择性高、常用于等值查询的列靠前。
- 排序需求可与索引顺序对齐，避免额外排序。
- 前缀索引只索引列的前若干字节，可减少索引大小但选择性下降。

### 3.9（场景）低选择性索引为什么可能比全表扫描更慢？

- 低选择性意味着一个键对应大量行，回表次数接近全表行数。
- 回表是随机 IO，行数多时随机读的代价超过顺序扫描。
- 优化器根据统计信息估算回表行数，超过阈值会选择全表扫描。
- 覆盖索引可消除回表，使低选择性索引重新变得有用。
- 统计信息过期会导致估算偏差，进而选错计划。
- 把低选择性列放在联合索引的非首列，可借助其他列提高过滤效果。
- 分区或聚簇可以改善局部性，减少随机 IO。

### 3.10 并发 B 树如何避免死锁？

- latch coupling 在下降时先持有父节点 latch，再获取子节点，然后释放父节点。
- 严格两阶段加锁会持有整条路径，并发度低，但加锁顺序固定，不会形成环路。
- 乐观下降先不加写锁，只在叶节点加锁，失败时重试。
- 分裂与合并需要同时持有相关页的 latch，按页号顺序加锁可避免环路。
- 读写 latch 允许多个读线程并发，写线程独占。
- 重试需要上限与退避，避免活锁。
- 日志写入顺序与 latch 顺序应保持一致，避免持锁等待 IO。

### 3.11 B-link 树的高键解决了什么问题？

- 每个节点保存高键，表示该节点负责的键上界。
- 分裂时先写新节点与高键，再更新父节点，中间状态可通过高键与右指针导航。
- 查找时若发现键大于当前节点的高键，沿右指针移动到兄弟节点。
- 这样分裂期间不需要对整条路径加写锁，减少锁等待。
- 父节点更新可以延迟，结构在任意时刻都可被正确遍历。
- B-link 树是许多并发 B 树实现的基础。
- 高键与右指针需要在页头中原子更新，或由日志保证顺序。

### 3.12 乐观并发控制如何在索引上工作？

- 读取时不加锁，记录版本号或读取时间戳。
- 提交时校验读取过的记录版本未变，否则中止并重试。
- 版本号可存放在行头或单独的版本表中。
- 长事务冲突概率高，重试成本上升。
- 与 MVCC 结合时，读操作看到快照，写操作检测写写冲突。
- 乐观控制适合读多写少，写冲突多时改用悲观锁更稳。
- 中止需要回滚已写入的索引项，代价与修改量成正比。

### 3.13 页内槽目录如何组织记录？

- 页头保存页号、LSN、槽数量、空闲空间边界与校验和。
- 槽目录从页头向后增长，每条记录一个槽，保存偏移与长度。
- 记录从页尾向前增长，插入时从空闲区分配。
- 删除记录只清空槽并合并空闲空间，记录可移动以整理碎片。
- 槽号是记录的稳定标识，移动记录只需更新槽中的偏移。
- 变长记录使页内可能出现碎片，整理需要额外写入。
- 页头与槽目录的结构决定了页格式的兼容性。

### 3.14（实现）节点分裂时如何保证异常安全？

```cpp
struct PageLatchGuard {
    explicit PageLatchGuard(Page* p) : page_(p) { page_->latch(); }
    ~PageLatchGuard() { page_->unlatch(); }
    PageLatchGuard(const PageLatchGuard&) = delete;
    PageLatchGuard& operator=(const PageLatchGuard&) = delete;
    Page* operator->() const noexcept { return page_; }
private:
    Page* page_;
};
```

- 先分配新页并写入内容，再更新原页与父页，顺序由日志与原子提交保证。
- 用 RAII 管理页 latch 与页引用，异常时自动释放，避免死锁。
- 内存分配失败时不应留下半成品页，可先预留日志空间与页。
- 修改页前写入日志记录，日志落盘后再修改数据页。
- 分裂过程中若抛出异常，需回滚已修改的页或交由恢复流程处理。
- 析构函数应声明 `noexcept`，清理路径上不再抛出。
- 页的引用计数在异常路径上必须递减，否则页无法换出。

### 3.15 索引页的校验和与页撕裂有什么关系？

- 页撕裂使页内部分扇区为新内容、部分为旧内容，校验和不匹配。
- 校验和覆盖页头、槽目录与记录区，任何字节变化都会被发现。
- InnoDB 使用 `innodb_checksum_algorithm` 选择算法，`crc32` 速度较快。
- 校验和只能检测损坏，不能修复，修复依赖副本或 doublewrite。
- 校验和计算应在页写入前完成，并随页一起落盘。
- 页头中的 LSN 也参与校验，恢复时可判断页是否已应用日志。
- 校验失败时应记录页号并从备份恢复，不能继续使用该页。

### 3.16（场景）线上慢查询中索引失效的常见原因有哪些？

- 对索引列使用函数或表达式，导致无法使用索引定位。
- 隐式类型转换使索引列被转换，等价于对列使用函数。
- 联合索引未满足最左前缀，或范围条件截断后续列。
- 统计信息过期导致优化器低估或高估行数。
- 使用 `LIKE` 的前导通配符，无法利用有序性。
- 索引列上存在大量 `NULL` 或重复值，选择性不足。
- 锁等待与 IO 抖动也会表现为慢查询，需区分执行时间与等待时间。

### 3.17 前缀压缩如何影响索引大小与查询？

- 前缀压缩把相邻键的公共前缀只存一份，减少页内占用，提高扇出。
- 页内需要 restart 点定期重建完整键，以便二分查找。
- restart 间隔越大，压缩率越高，查找时需要线性扫描的键越多。
- 压缩后不能直接随机访问单个键，需从 restart 点顺序解码。
- 前缀压缩降低 IO 量，但增加 CPU 开销，适合 IO 密集场景。
- 压缩对长字符串键效果明显，对整数键收益有限。
- 更新键时可能需要重写整页，写放大上升。

### 3.18（陷阱）范围扫描时的锁粒度会带来什么影响？

- 行锁只锁住已存在的行，无法阻止其他事务插入范围内的新行，产生幻读。
- 间隙锁锁定索引区间，阻止插入，但增加锁冲突与死锁概率。
- 范围扫描持锁时间长，扫描行数多时阻塞其他写事务。
- 在可重复读隔离级别下，间隙锁的范围由索引决定，未命中索引时可能锁全表。
- 降低隔离级别或使用快照读可减少锁，但语义随之改变。
- 大批量更新应分批提交，缩短持锁时间。
- 死锁检测会回滚代价较小的事务，应用需处理重试。

### 3.19 页填充因子与写放大有什么关系？

- 填充因子决定分裂后页的占用率，越低则未来插入越少分裂。
- 顺序插入时高填充因子可减少空间浪费，随机插入时低填充因子可减少分裂。
- 每次分裂写入两个页加父页，写放大与分裂频率成正比。
- 页内空闲空间不足时插入需要整理碎片，产生额外写入。
- 批量加载时可预先排序并顺序填充，接近 100% 占用。
- 填充因子过高会导致频繁分裂，过低会增大索引体积与缓存压力。
- 监控页分裂次数可判断填充因子是否合适。

### 3.20（实现）比较器为什么必须满足严格弱序？

- B+ 树的查找依赖键的有序关系，比较器必须满足严格弱序，并对相等键给出确定处理。
- 违反严格弱序会导致查找路径不确定，出现找不到已存在键的情况。
- 浮点 `NaN` 不满足全序，用作键时需定义明确的排序规则。
- 字符串比较应使用字节序或明确的排序规则，避免受区域设置影响。
- 多列比较需逐列比较，最后一列决定等价。
- 比较器应是无状态的，避免依赖全局配置导致索引顺序变化。
- 修改比较规则等于改变索引的物理顺序，需要重建索引。

## 4. LSM 树与 compaction

### 4.1 memtable 为什么多采用跳表？

- 跳表支持无锁或细粒度锁的并发插入，红黑树的旋转会改动多个节点，细粒度加锁的实现复杂。
- 跳表的插入只需修改局部指针，便于用原子操作实现。
- 跳表的范围扫描沿底层链表顺序遍历，缓存友好。
- 跳表的随机层高带来额外指针开销，内存放大高于红黑树。
- 跳表的查找期望复杂度为 O(log n)，最坏为 O(n)，实际由随机数质量决定。
- 内存表通常配合 arena 分配，节点一次性释放，避免逐个析构。
- 只读的 immutable memtable 可以转为有序数组，进一步提高查找效率。

### 4.2 memtable 何时切换，切换期间如何处理写入？

- memtable 达到阈值后转为只读，新的 memtable 接管写入。
- 写入先追加 WAL，再插入 memtable，两者必须对应同一批数据。
- 切换需要短暂加锁，把当前 memtable 指针替换为新的，并把旧的加入 flush 队列。
- 新写入进入新的 WAL 文件，旧 WAL 在对应 SSTable 落盘后才能删除。
- immutable memtable 由后台线程刷成 SSTable，完成后才能推进日志回收点。
- 若 flush 速度跟不上写入，会触发写停顿，限制写入速率。
- 多个 immutable memtable 可并行 flush，但会增加磁盘压力。

### 4.3 SSTable 的内部布局包含哪些部分？

- 数据块按 key 排序存放，块大小通常为 4 KiB 至 64 KiB。
- 块内使用前缀压缩与 restart 点，块尾保存 restart 偏移数组。
- 索引块记录每个数据块的最后一个 key 与偏移，常驻内存。
- 布隆过滤器块用于快速判断 key 是否可能存在于该文件。
- 文件尾部保存元数据索引、footer 与魔数，footer 定长便于定位。
- 校验和覆盖每个块，读取时校验，发现损坏则跳过或报错。
- 块可按需压缩，压缩算法记录在块头。

### 4.4 布隆过滤器的假阳性率如何计算？

- 假阳性率约为 (1 - e^(-kn/m))^k，k 为哈希函数个数，m 为位数，n 为元素数。
- 每个元素占 10 位时，最优 k 约为 7，假阳性率约为 1%。
- 假阳性只会导致多读一个文件，不会漏判，因此不影响正确性。
- 过滤器按 SSTable 构建，查询时逐层检查，减少无效 IO。
- 过滤器常驻内存，内存占用与键数量成正比，需限制总量。
- 删除操作不能直接从过滤器中移除，因为可能影响其他键。
- 过滤器可分区存放，按 key 前缀加载，降低内存占用。

### 4.5 level 的数量与容量如何确定？

- 第 0 层由 memtable 直接刷出，文件之间键范围可能重叠。
- 第 1 层及以下按键范围分区，层内文件不重叠。
- 每层容量按倍数增长，常见为 10 倍，层数由总数据量决定。
- 总容量为各层容量之和，最大层容纳绝大部分数据。
- 层数增加使读放大上升，因为每次查找要检查每层。
- 倍数过小导致层数多，倍数过大导致单次 compaction 数据量大。
- 容量与文件大小共同决定每层文件数，影响 compaction 的并行度。

### 4.6 leveled compaction 的写放大如何推导？

- 每层数据向下移动一次，需重写该层与下一层重叠的部分。
- 稳态下每层数据被重写约 T 次，T 为层容量倍数。
- 写放大约为 T 乘以层数 L，忽略第 0 层。
- 10 倍增长、5 层时写放大可达 50 左右，实际因重叠比例而波动。
- 减小 T 可降低写放大，但增加层数与读放大。
- 增大 T 可减少层数，但单次 compaction 的数据量增大，延迟抖动明显。
- 实际写放大还包含 WAL 与 memtable flush 的写入。

### 4.7 tiered 与 universal compaction 的取舍是什么？

- tiered 把同层文件按时间分组，compaction 合并整组，写放大低。
- universal 是 tiered 的变体，按文件大小与重叠度选择合并。
- 两者读放大高，因为同层文件键范围重叠，查找需检查多个文件。
- 空间放大也较高，旧版本数据保留时间更长。
- 适合写多读少、写入吞吐优先的场景。
- leveled 读放大低，适合读多写少。
- 混合策略在不同层使用不同方式，兼顾读写。

### 4.8（场景）如何估算一次 compaction 的写放大？

- 设第 L 层容量 10 GiB，第 L+1 层容量 100 GiB，本次搬移 1 GiB。
- 若与下一层重叠比例为 10%，输出约为 10 GiB，写放大按输出除以输入计为 10 倍。
- 重叠比例取决于键分布，随机键的重叠比例接近容量比。
- 写放大通常按写入介质的字节数除以应用写入的字节数计算。
- 监控 compaction 的读写字节数可得到真实放大倍数。
- 限速会拉长 compaction 时间，但不改变总写入量。
- 写放大直接决定设备寿命消耗与后台带宽占用。

### 4.9 读放大由哪些部分组成？

- 每层可能查找一个文件，层数为 L 时最坏查找 L 次。
- 第 0 层文件重叠，需要检查所有文件，数量由触发阈值决定。
- 布隆过滤器可跳过大部分不含目标键的文件。
- 索引块常驻内存，定位数据块只需一次 IO。
- 找到多个版本时需按序列号选择可见版本。
- 块缓存命中可减少实际 IO，读放大按逻辑查找次数计。
- 读放大的上限由层数与第 0 层文件数决定。

### 4.10 空间放大如何产生，如何控制？

- 多版本数据同时存在，旧版本要等 compaction 才能回收。
- 删除标记（tombstone）占用空间，直到覆盖所有旧版本。
- 未合并的重叠文件使同一键存在多份。
- 压缩率下降时空间放大上升。
- 控制手段包括提高 compaction 频率、限制快照保留时间与及时清理 tombstone。
- 空间放大与写放大通常此消彼长，需要按场景取舍。
- 监控各层文件总大小可估算空间放大。

### 4.11 compaction 的合并迭代器如何处理多路归并？

- 每层输入文件提供一个迭代器，按 key 排序输出。
- 使用最小堆选出当前最小的 key，复杂度为 O(log k)，k 为路数。
- 相同 key 的多个版本按序列号排序，只保留对可见快照有用的版本。
- 输出按块缓冲，块满后写入新文件并记录索引。
- 归并过程中需处理迭代器的 `Seek`，用于对齐键范围。
- 合并需要保证原子性，新文件写完后才更新 MANIFEST。
- 中途失败时残留文件由启动时的清理流程删除。

### 4.12（陷阱）tombstone 什么时候可以安全删除？

- 只有当更下层不存在该键的旧版本时，tombstone 才能删除。
- 若下层仍有旧版本，删除 tombstone 会让旧数据重新可见。
- 存在更早的快照时，tombstone 必须保留到快照释放。
- 最底层的 compaction 可以丢弃被 tombstone 覆盖的旧版本，并删除 tombstone 本身。
- 范围删除产生的 tombstone 覆盖一个区间，判断更复杂。
- 事务隔离级别影响可见性，需要结合序列号判断。
- 过早删除 tombstone 是常见的正确性缺陷，表现为删除的数据重新出现。

### 4.13 快照与 MVCC 如何影响 compaction？

- 快照固定了可见的序列号，compaction 不能丢弃快照仍需要的版本。
- 最老的活跃快照决定可回收版本的下界。
- 长事务或未释放的快照会阻止空间回收，导致空间放大。
- 序列号通常编码在 key 中，按降序排列，便于取最新版本。
- compaction 输出需保留每个 key 对最老快照可见的版本。
- 快照释放后，下一次 compaction 才能清理旧版本。
- 监控最老快照年龄可发现长事务问题。

### 4.14（实现）SSTable 写入时如何组织块与前缀压缩？

- 按 key 排序写入，累积到块大小后输出一个数据块。
- 块内记录与前一条的公共前缀长度、后缀长度与后缀内容。
- 每隔若干条记录设置 restart 点，保存完整 key 的偏移。
- 块尾写入 restart 偏移数组与数量，供二分查找。
- 索引块保存每个数据块的最后一个 key，便于定位。
- 写入完成后追加 footer，包含索引与过滤器的偏移。
- 整个文件写完后 `fsync`，再原子地加入 MANIFEST。

### 4.15（场景）compaction 引起的长尾延迟如何缓解？

- compaction 与前台读写争抢磁盘带宽与 CPU，导致 P99 延迟上升。
- 限速按字节或按 IOPS 控制后台流量，平滑写入。
- 把 compaction 调度到低峰期，或使用独立的 IO 优先级。
- 增大 memtable 与减少层数可降低 compaction 频率。
- 使用分区 compaction，把大 compaction 拆成小任务，减少单次停顿。
- 监控 compaction 的待处理字节数与停顿计数。
- 在写入放大与延迟之间取舍，必要时改用 tiered 策略。

### 4.16（辨析）LSM 树与 B+ 树在读写放大上如何取舍？

- LSM 的写入是顺序追加，写放大主要来自 compaction；B+ 树原地更新，写放大来自页分裂与日志。
- LSM 的读需要检查多层，读放大高；B+ 树的读路径固定为树高。
- LSM 的空间放大高于 B+ 树，因为多版本共存。
- B+ 树的更新可能引起页分裂与随机写，LSM 的数据文件以顺序追加为主。
- 写多读少适合 LSM，读多写少适合 B+ 树。
- 两者都依赖 WAL 保证持久性，日志先行规则相同。
- 现代引擎常互相借鉴，如 B+ 树使用批量加载，LSM 使用分区索引。

### 4.17（实现）跳表节点的内存如何管理？

- 使用 arena 一次性分配大块内存，节点从中切分，避免逐次调用分配器。
- 节点高度在插入时随机确定，指针数组按高度分配。
- 释放整个 memtable 时只需释放 arena，不需逐个析构。
- 节点中不存放需要析构的对象，键值以字节串形式保存。
- 并发插入使用原子指针与 CAS，配合内存序保证可见性。
- 高度上限限制了单节点内存，避免极端随机导致大块分配。
- arena 的块大小影响内存碎片与分配速度。

### 4.18（输出题）varint 编码的输出是什么？

```cpp
#include <cstdint>
#include <cstdio>

void put_varint(std::uint32_t v) {
    while (v >= 0x80) {
        std::putchar(static_cast<int>((v & 0x7f) | 0x80));
        v >>= 7;
    }
    std::putchar(static_cast<int>(v));
}

int main() { put_varint(300); }
```

- 300 的二进制为 `1 0010 1100`，按 7 位分组为 `0000010` 与 `0101100`。
- 低 7 位先输出并置高位为 1，得到 `0xAC`；剩余 `0x02` 直接输出。
- 输出字节为 `0xAC 0x02`，共 2 字节。
- 解码时遇高位为 0 即结束，按 7 位一组左移组合。
- varint 对小整数节省空间，32 位整数最多占 5 字节。
- 编码不依赖字节序，因为逐位处理。
- 负数需先做 zigzag 变换，否则按无符号解释会占满 5 字节。

### 4.19 WAL 组提交如何摊销 fsync 成本？

- 多个事务的日志记录合并为一次写入与一次 `fsync`，由最后一个提交者触发。
- 等待中的事务在 `fsync` 返回后一起得到确认。
- 组提交的延迟上限由等待窗口决定，吞吐随并发上升。
- 日志写入顺序必须与事务提交顺序一致。
- 需要处理部分写入与崩溃后的尾部截断。
- 组提交与两阶段提交结合时，协调者负责记录提交决定。
- 监控每次 `fsync` 的平均事务数可判断组提交效果。

### 4.20（陷阱）compaction 与读取并发时如何保证一致性？

- compaction 产生新文件后，通过 MANIFEST 的版本切换使新文件对读操作可见。
- 读操作持有版本引用，旧文件在引用释放后才删除。
- 文件删除延迟到所有引用该版本的读操作结束。
- MANIFEST 的更新需要原子替换，或在追加记录时带上校验和。
- 崩溃后根据 MANIFEST 恢复文件集合，未记录的文件视为垃圾。
- 读取时若文件已被删除但版本仍引用，需要文件系统层面的延迟删除。
- 版本切换与文件删除的顺序错误会导致读到不存在的文件。

## 5. 缓冲池与页管理

### 5.1 缓冲池由哪些结构组成？

- 页帧数组保存页数据，每个帧记录有效位、脏位、pin 计数与 latch。
- 页表是哈希表，把页号映射到帧号，查找为 O(1)。
- 空闲链表与替换链表管理可用帧，LRU 链表按访问顺序排列。
- 每个页有引用计数，计数大于 0 时不能被换出。
- 脏页链表记录待刷盘的页，checkpoint 按 LSN 顺序处理。
- 缓冲池大小以页数为单位，通常占系统内存的较大比例。
- 页的元数据与数据分开存放，便于按帧索引。

### 5.2 LRU 与 clock 的差异是什么？

- LRU 按精确的访问时间排序，每次访问都要移动链表节点。
- clock 用环形缓冲区与访问位近似 LRU，命中时只置位，不移动节点。
- LRU 需要额外的链表指针与锁，clock 的开销更低。
- clock 的淘汰精度低于 LRU，但实现简单，适合高并发。
- clock 的扫描指针在内存压力下转动，可能多次经过同一页。
- 两者都可能被顺序扫描污染，需要配合分区或频率统计。
- 实际系统常使用 LRU 的变体，如分代 LRU。

### 5.3 LRU-K 与 2Q 解决了什么问题？

- LRU 无法区分一次性扫描与反复访问的热点，扫描会挤掉热数据。
- LRU-K 记录最近 K 次访问时间，只有访问次数达到 K 才进入热区。
- 2Q 使用两个队列，新页先进入试用队列，再次访问才进入主队列。
- 这样可以抵抗顺序扫描与周期性批量任务。
- 代价是需要维护更多元数据，冷启动时命中率上升较慢。
- K 值的选择影响对突发访问的适应性。
- 分区 LRU 通过把页按访问频率分到不同区域实现类似效果。

### 5.4（陷阱）全表扫描为什么会让缓冲池命中率骤降？

- 扫描按顺序读取大量页，每页只访问一次，却占满 LRU 的头部。
- 热点页被挤出后，后续查询需要重新从磁盘读取。
- 朴素 LRU 对一次性访问没有抵抗能力。
- 解决方式包括扫描时使用小缓冲区、把扫描页放入冷区、或使用 LRU-K。
- 数据库可对大表扫描使用直接 IO，绕过缓冲池。
- 监控命中率时应区分索引查询与全表扫描的流量。
- 扫描并发数过高时，即使有抵抗策略也会造成带宽争抢。

### 5.5 脏页什么时候被写回？

- 事务提交时不必写数据页，只需保证日志落盘，数据页可以延后。
- 后台线程按 LSN 顺序刷脏页，checkpoint 推进可回收日志空间。
- 缓冲池空间不足时，替换算法选择脏页先刷盘再换出。
- 刷脏页的频率影响崩溃恢复时间与写放大。
- 脏页过多时会出现集中刷盘，造成延迟抖动。
- 写回需要持有页 latch，避免读到半写状态。
- 页的 LSN 用于判断是否已应用日志，避免重复写。

### 5.6 脏页刷盘的顺序由什么决定？

- 刷盘按 LSN 递增顺序推进，保证日志先行。
- checkpoint 记录已刷到的 LSN，恢复时从此处开始重做。
- 页的 LSN 小于 checkpoint LSN 时无需重做。
- 刷盘顺序还受脏页链表位置影响，通常按最早修改时间排序。
- 并发刷盘时需保证同一页不被两个线程同时写入。
- 刷盘与事务提交解耦，提交只需日志落盘。
- 刷盘速率需要限制，避免与前台 IO 争抢带宽。

### 5.7 pin 与 latch 有什么区别？

- pin 是引用计数，保证页在缓冲池中不被换出，持续到显式解除。
- latch 是短期锁，保护页内容的并发访问，持有时间应远短于一次 IO。
- pin 的持有时间可以跨越多次 IO 与用户态计算。
- latch 不应跨越用户交互或长时间等待，否则阻塞其他线程。
- 读页时通常先 pin，再加 latch，释放顺序相反。
- pin 泄漏会导致页永远无法换出，缓冲池逐渐耗尽。
- latch 的死锁需要通过加锁顺序或超时检测处理。

### 5.8 页 latch 有哪几种模式？

- 共享模式允许多个读线程并发访问，排他模式只允许一个写线程。
- 更新模式用于即将升级的场景，避免多个升级者互相等待。
- latch 通常不可重入，同一线程重复加锁会死锁。
- latch 的持有时间应尽量短，避免在持锁期间做 IO。
- B+ 树的 crab 加锁在下降时释放父节点 latch。
- latch 与事务锁不同，前者保护内存结构，后者保护数据语义。
- 自旋与阻塞的选择取决于临界区长度。

### 5.9（场景）pin 泄漏会表现为什么现象？

- 缓冲池的空闲帧逐渐减少，命中率下降，IO 增加。
- 换页线程找不到可换出的页，出现等待或报错。
- 长时间运行后缓冲池被少数页占满，性能持续下降。
- 常见原因是异常路径未解除 pin，或异步 IO 回调丢失。
- 使用 RAII 守卫管理 pin，析构时自动递减。
- 监控每个页的引用计数分布可发现异常。
- 泄漏的页若同时被 latch 持有，还会导致其他线程阻塞。

### 5.10 预读策略如何选择预读长度？

- 顺序访问检测到连续页号时，按倍数增加预读窗口。
- 随机访问时预读会浪费带宽与缓冲池空间，应关闭或减小。
- 预读分为同步预读与异步预读，后者在后台填充缓冲池。
- 预读窗口的上限受 IO 大小与设备队列深度限制。
- 预读的页应放入冷区，避免挤掉热点页。
- 索引范围扫描适合预读，点查不适合。
- 预读效果可通过命中率与 IO 大小分布验证。

### 5.11（实现）页表哈希与 LRU 链表的并发如何保护？

- 页表哈希桶使用分段锁或读写锁，查找时只锁对应桶。
- LRU 链表通常用一把全局锁保护，成为高并发下的瓶颈。
- 改进方式包括分片 LRU、时钟算法与批量摘链。
- 命中时更新访问位可延迟批量处理，减少锁争用。
- 换页需要同时修改页表与链表，加锁顺序需固定。
- 使用原子引用计数管理页的生命周期。
- 锁的粒度应与临界区长度匹配，避免持锁做 IO。

### 5.12（实现）如何用 C++ 表达页句柄的生命周期？

```cpp
class PageGuard {
public:
    PageGuard(BufferPool& pool, PageId id) : page_(pool.fetch(id)) {
        page_->pin();
    }
    ~PageGuard() { page_->unpin(); }
    PageGuard(const PageGuard&) = delete;
    PageGuard& operator=(const PageGuard&) = delete;
    Page* operator->() const noexcept { return page_; }
private:
    Page* page_;
};
```

- 构造函数获取页并加 pin，析构函数解除，异常路径也能正确释放。
- 禁止复制，避免同一 pin 被重复释放；需要转移时提供移动构造。
- 移动构造需把源对象置空，析构时判断空指针。
- 页句柄不应跨越异步回调长期持有，否则阻塞换页。
- 加 latch 可用单独的守卫类型，与 pin 分离。
- 析构函数应声明 `noexcept`，避免在栈展开时终止程序。
- 句柄的粒度应尽量小，缩小 pin 的持有范围。

### 5.13（条款）在页缓冲区上构造对象时，生命周期从何时开始？

- 缓冲区提供存储，对象的生命周期在初始化完成后开始，见 `[basic.life]/1`。
- 用 placement new 在缓冲区上构造，需保证对齐与大小满足类型要求。
- 缓冲区被复用前需显式调用析构函数，否则资源不释放。
- 页格式通常以字节数组加偏移访问，避免在缓冲区上构造复杂对象。
- 在缓冲区上构造非平凡类型会引入析构顺序与异常安全问题。
- 用 `std::launder` 获取复用后的对象指针，避免编译器复用旧值。
- 跨进程共享的页布局应使用平凡可复制类型，避免指针与虚表。

### 5.14 页帧内存如何分配与对齐？

- 页大小通常为 4 KiB 至 16 KiB，需按页对齐以支持直接 IO。
- 大块分配可减少 TLB 缺失，透明大页可进一步降低开销。
- 缓冲区在启动时一次性分配，避免运行时碎片。
- 使用 `mmap` 分配可按需提交，减少启动时间。
- 页内数据布局需考虑缓存行对齐，避免伪共享。
- 缓冲区地址在进程生命周期内固定，便于按帧号计算偏移。
- 分配失败时应降低缓冲池大小，并记录告警。

### 5.15（陷阱）latch 与事务锁混用会带来什么问题？

- latch 保护内存结构，事务锁保护数据语义，两者的生命周期与死锁域不同。
- 在持有事务锁时等待 latch，可能与持 latch 等待事务锁的线程形成环路。
- latch 的持有时间应短，不应在其中等待用户输入或网络。
- 加锁顺序应统一，先事务锁后 latch，或反之，需在设计中固定。
- 死锁检测通常只覆盖事务锁，latch 死锁需要超时或顺序保证。
- 页分裂时同时持有多个 latch，顺序按页号可避免环路。
- 混用还会导致优先级反转与长时间阻塞。

### 5.16（场景）缓冲池命中率下降时如何定位？

- 先区分逻辑读与物理读，命中率等于 1 减去物理读除以逻辑读。
- 检查是否有全表扫描或大范围扫描挤占缓冲池。
- 检查缓冲池大小是否被其他组件挤占，如排序区与连接缓冲。
- 检查是否存在 pin 泄漏或长事务持有页。
- 检查预读是否把冷数据带入缓冲池。
- 检查工作集是否超过内存，导致抖动。
- 结合慢查询日志与执行计划确认访问模式。

### 5.17 直接 IO 与缓冲池同时使用时要注意什么？

- 双重缓存会浪费内存，数据库通常用直接 IO 避免页缓存占用。
- 直接 IO 要求对齐，页缓冲区需按扇区对齐。
- 元数据仍走页缓存，日志文件的写入策略需单独设计。
- 直接 IO 不享受预读，需自行实现预读。
- 文件系统的一致性语义仍然适用，`fsync` 仍需调用。
- 混合使用缓冲 IO 与直接 IO 访问同一文件可能导致数据不一致。
- 容器与虚拟化环境下直接 IO 的行为由实现定义。

### 5.18（实现）如何保证刷脏页时的异常安全？

- 刷页前先写日志并确保日志落盘，再写数据页。
- 写数据页失败时保留脏标记，下次重试，不能清除。
- 使用 RAII 管理 latch，异常时释放，避免其他线程永久阻塞。
- 部分写失败可能造成页撕裂，需配合校验和与 doublewrite。
- 刷页完成后才更新页的 LSN 与脏标记，顺序不能颠倒。
- 错误应向上传播并触发告警，不能静默忽略。
- 崩溃恢复会重放日志，未完成的刷页不影响正确性。

### 5.19 页校验和与修复策略如何设计？

- 每个页在写入前计算校验和，存放在页头。
- 读取时校验，失败则尝试从副本或 doublewrite 恢复。
- 校验和算法可选 CRC32C，硬件指令可加速。
- 校验和应覆盖页头中的页号，防止页被写到错误位置。
- 修复失败时应让查询报错，避免返回损坏数据。
- 定期巡检可提前发现介质退化。
- 校验和增加少量 CPU 开销，但能发现静默损坏。

### 5.20（场景）checkpoint 抖动如何缓解？

- 抖动来自集中刷脏页，导致 IO 队列排满，前台延迟上升。
- 平滑刷脏，按 LSN 增量推进，限制每秒刷页数量。
- 增大日志空间可延长 checkpoint 间隔，降低刷页频率。
- 分离日志设备与数据设备，避免 IO 争抢。
- 监控 checkpoint 的待刷页数与刷页速率。
- 在低峰期执行全量 checkpoint。
- 抖动严重时考虑调整缓冲池大小与脏页比例上限。

## 6. 事务与隔离级别

### 6.1（辨析）ACID 中的一致性与另外三项是什么关系？

- 一致性指事务把数据库从一个满足约束的状态带到另一个满足约束的状态，约束来自主键、外键、唯一索引、检查约束与应用层不变量。
- 原子性、隔离性、持久性由数据库机制提供，一致性依赖这些机制配合应用正确的事务边界。
- 单条语句违反约束时由引擎拒绝，跨多条语句的不变量需要应用在同一事务内读写，否则三项机制齐备仍可能破坏一致性。
- 典型反例是转账先扣款提交、再加款，两条独立事务，中间崩溃后总额不守恒。
- 隔离级别降低时，并发事务的中间状态可能被读到，约束检查基于过期数据。
- 把一致性说成完全由数据库保证，通常意味着漏掉了应用层不变量这一半。

### 6.2 原子性在存储引擎内部由什么保证？

- 未提交的修改先写 undo 记录，记录中包含反向操作所需的主键与旧值，并链接到事务的 undo 链。
- 数据页允许在事务提交前刷盘（steal 策略），崩溃后按 undo 链回滚未提交事务。
- 提交点由日志决定：redo 日志中的提交记录完成同步写入后，事务才算持久。
- 回滚不直接撤销页内容，而是执行逻辑反向操作并写入补偿日志，使回滚过程本身可以重放。
- 保存点是 undo 链上的位置标记，回滚到保存点只撤销该位置之后的记录。
- 语句级原子性依赖语句开始时建立的 undo 起点，语句失败只回滚本条语句。

### 6.3（辨析）SQL 标准的四种隔离级别分别禁止哪些现象？

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 禁止 | 可能 | 可能 |
| 可重复读 | 禁止 | 禁止 | 可能 |
| 可串行化 | 禁止 | 禁止 | 禁止 |

- 标准以「禁止哪种现象」定义级别，现象指脏读、不可重复读与幻读三类。
- 现象定义基于单条记录的读写，未覆盖写偏斜与读偏斜，因此标准文本中的可串行化不等同于可串行化执行。
- 快照隔离在分类上接近可重复读，却允许写偏斜，说明该分类不足以描述实现语义。
- 实现可以比标准更严格，例如在可重复读下用间隙锁阻止加锁读的幻读，快照读仍可能看到提交后的新行。
- 级别选择影响锁持有时间与版本链长度：读已提交下每条语句建立新快照，可重复读下整个事务共用一个快照。

### 6.4 MVCC 中的快照如何表示？

- 快照保存一组可见性判定参数：活跃事务 ID 集合、最小活跃 ID、下一个待分配 ID，不复制数据。
- InnoDB 的 ReadView 保存活跃事务列表、最小活跃事务 ID、高水位 ID 与创建者事务 ID，判定时先比较创建者，再查活跃集合。
- PostgreSQL 的快照保存 xmin、xmax 与 xip 列表，判定元组的插入事务是否已提交、删除事务是否仍活跃。
- 判定规则要求事务 ID 单调分配；提交顺序与 ID 顺序不一致时，以提交状态位图为准。
- 快照在事务第一次快照读时建立，之后复用；读已提交下每条语句重建，同一事务内两次查询可能看到不同版本。
- 快照需要持有活跃事务信息，长事务会阻止版本清理，版本链持续变长。

### 6.5（陷阱）MVCC 的版本链为什么会拖慢查询？

- 聚簇索引记录中保存最近修改它的事务 ID 与指向 undo 的回滚指针，旧版本存放在 undo 页中。
- 读取时从最新版本沿回滚指针回溯，直到找到第一个对当前快照可见的版本，回溯深度等于该行被修改的次数。
- 长事务使 purge 无法推进，历史版本堆积，单行回溯可能跨越大量 undo 页，产生额外随机 IO。
- 二级索引不保存版本链，命中后需要回表判断可见性，可能回表多次才找到可见版本。
- 监控指标是历史链长度与 undo 表空间大小，持续增长说明存在长事务或复制延迟。
- 缓解手段是缩短事务、避免大批量更新后长时间不提交，以及为长报表使用只读快照或独立副本。

### 6.6 快照隔离能防止哪些异常，不能防止哪些异常？

- 快照隔离保证读到事务开始时已提交的一致快照，避免脏读与不可重复读，范围查询也看不到快照之后插入的行。
- 写冲突按先提交者获胜处理：两个事务修改同一行时，后提交者失败并回滚。
- 允许写偏斜：两个事务读取同一组数据、各自修改不同行，彼此的写入互不可见，跨行约束被破坏。
- 允许只读事务异常：只读事务看到的快照可能不对应任何串行执行顺序。
- 因此快照隔离弱于可串行化，用快照实现的可重复读不能宣称可串行化。
- 需要可串行化时应改用可串行化快照隔离或加锁读，二者代价不同。

### 6.7（场景）写偏斜是如何发生的？

- 场景：值班表要求至少一名医生在岗，两个事务分别查询到在岗人数为 2，各自把其中一人置为离岗。
- 两个事务修改不同行，写冲突检测不触发，双方都能提交，最终在岗人数为 0。
- 快照隔离的冲突判定只看写集合交集，写偏斜的冲突藏在读集合与写集合之间。
- 修复方式一是在读取时加锁，使用加锁读使两个事务串行。
- 修复方式二是把不变量物化到一行上，例如维护在岗计数行，让两个事务争用同一行形成写冲突。
- 修复方式三是使用可串行化隔离，由串行化快照隔离检测读写依赖形成的环。

### 6.8 可串行化快照隔离如何检测危险结构？

- 在快照隔离之上记录读写依赖：事务 T1 读过的数据被 T2 修改，形成 T1 到 T2 的反依赖边。
- 危险结构是两条连续的反依赖边 T1 到 T2、T2 到 T3，中间事务 T2 称为枢纽。
- 检测到危险结构后回滚其中一个事务即可打破环，通常选择代价较小者。
- PostgreSQL 用 SIREAD 谓词锁记录读集合，锁不阻塞写，只在内存中标记索引页、堆页或元组。
- 谓词锁会升级到页级或关系级，读集合越大内存开销越高，可能产生误判导致不必要的回滚。
- 串行化失败返回 40001，应用必须重试整个事务，重试逻辑需要幂等。

### 6.9 幻读在 MVCC 与锁两种实现中有什么差别？

- 锁实现中幻读由范围锁阻止：可重复读下对扫描区间加 next-key 锁，阻止其他事务在区间内插入。
- 快照实现中幻读由版本可见性阻止：新插入行的事务 ID 大于快照，对当前事务不可见。
- 快照读不阻止其他事务插入，只是看不见；加锁读、更新与删除走最新版本并加锁。
- 同一事务内先快照读、后加锁读，可能看到快照建立后插入的行，表现为同一事务内结果不一致。
- 唯一索引等值查询命中记录时只加记录锁，不加间隙锁。
- 读已提交下间隙锁基本关闭，幻读由语句级快照遮蔽，语句复制与逻辑复制下的行为差异需要单独评估。

### 6.10（输出题）给定调度，出现了哪种异常？

| 时刻 | T1 | T2 |
| --- | --- | --- |
| t1 | 读 A，得 100 | |
| t2 | | 写 A=70、B=130，提交 |
| t3 | 读 B，得 130 | |
| t4 | 计算 A+B=230 | |

- T1 的两次读取跨越 T2 的提交，第二次读到新值，结果为 230，不对应任何一致状态，属于读偏斜。
- 读已提交允许该现象，因为每条语句建立新快照，语句之间没有一致性保证。
- 可重复读下 T1 复用同一快照，两次读到 A=100、B=100，不会出现 230。
- 该异常与脏读不同：T1 读到的都是已提交数据，只是来自不同时刻。
- 若需跨行一致，应在事务开始时固定快照，或对读取的行加共享锁。
- 把调度投影到单行：A 与 B 各自都没有不可重复读，异常来自跨行的组合。

### 6.11 事务的提交点在哪里？

- 提交点是日志中的提交记录完成持久化写入的时刻，而不是应用调用提交接口返回的时刻。
- 提交记录落盘前崩溃，事务回滚；落盘后崩溃，重放 redo 后事务保留。
- 数据页是否已经写出与提交无关，steal 策略允许未提交数据提前落盘，由 undo 回滚。
- 提交接口在同步完成后才返回，因此提交延迟包含一次或多次设备同步。
- 组提交把多个事务的日志合并为一次同步，各事务的提交点仍是自身提交记录的位置。
- 提交后立即返回、由后台线程补同步的配置，会在掉电时丢失最近事务，这是可用性与持久性的取舍。

### 6.12 事务 ID 耗尽会发生什么？

- 事务 ID 通常为 32 位无符号整数并单调递增，回绕后新事务的 ID 会小于旧事务。
- 可见性判定依赖 ID 的大小比较，回绕使旧数据被误判为未来事务写入而不可见。
- PostgreSQL 用冻结把足够旧的元组标记为永久可见，并把插入事务 ID 置为冻结标识。
- 冻结由 VACUUM 完成，需要扫描全表；冻结跟不上消耗时数据库会拒绝新事务以避免数据损坏。
- 监控项是数据库中最旧未冻结事务的年龄，接近上限前需要主动执行冻结或调整阈值。
- InnoDB 的事务 ID 是 64 位计数器，记录中只保存低 48 位，回绕周期远长于 32 位实现，但仍需在监控中考虑。

### 6.13（实现）如何用 C++ 实现一个最小的可见性判定？

```cpp
struct ReadView {
    std::vector<std::uint64_t> active;
    std::uint64_t low = 0;   // 最小活跃事务 ID
    std::uint64_t high = 0;  // 下一个待分配 ID
    std::uint64_t self = 0;

    bool visible(std::uint64_t writer) const {
        if (writer == self) return true;
        if (writer < low) return true;
        if (writer >= high) return false;
        return !std::binary_search(active.begin(), active.end(), writer);
    }
};
```

- 活跃集合按 ID 升序保存，判定用二分查找；集合较小时线性扫描也足够。
- 小于最小活跃 ID 的事务都已提交，大于等于高水位的事务在快照之后开始，两者都可以直接判定。
- 落在区间内的 ID 需要查活跃集合，不在集合中表示已提交。
- 结构体只在事务生命周期内有效，复制时共享同一份活跃集合，用 `std::shared_ptr<const ReadView>` 管理只读共享。
- 版本链遍历时把每条记录的事务 ID 传入判定，第一个可见版本即为结果。
- 该实现省略了提交状态位图，回滚中的事务需要额外状态，否则会被误判为已提交。

### 6.14 隔离级别如何影响加锁读的语义？

- 加锁读（`SELECT ... FOR UPDATE`、`FOR SHARE`）绕过快照直接读最新已提交版本，并对记录加锁。
- 读已提交下加锁读只锁命中记录，间隙锁基本不启用，因此仍可能出现幻读。
- 可重复读下加锁读对扫描区间加 next-key 锁，锁范围取决于索引与查询条件，可能锁住比预期更多的行。
- 条件未命中索引时会退化为全表扫描并锁住扫描到的所有记录，这是线上锁等待的常见来源。
- 同一事务中快照读与加锁读混用会看到不同版本，业务逻辑需要明确区分。
- 以只读模式开启事务可以减少锁与版本开销，部分引擎可把这类事务路由到只读副本。

### 6.15（陷阱）长事务为什么会放大资源占用？

- 长事务持有旧快照，purge 无法清理其可见性判定可能需要的版本，undo 与历史链持续增长。
- 行锁在事务结束前不释放，长事务使其他会话的加锁读排队，表现为锁等待超时。
- 长事务产生的 redo 使检查点无法推进，崩溃恢复需要扫描的日志量增加。
- 主从复制中，长事务会推迟从库可见时间，读副本延迟上升。
- 大批量删除或更新应拆分为多个小事务，提交后短暂让出，避免 undo 膨胀。
- 监控长事务需要按开始时间排序，`information_schema.innodb_trx` 与 `pg_stat_activity` 都提供事务起始时间。

### 6.16 快照隔离下的写冲突如何判定？

- 提交时检查写集合是否与快照建立之后提交的其他事务的写集合相交，相交则回滚。
- 判定依据是行标识而非行内容，同一行的不同列也算冲突。
- 冲突窗口从快照建立持续到提交，期间任何对同一行的提交都会导致失败。
- 判定需要保存最近提交事务的写集合，通常用行上的最近修改事务 ID 近似，可能产生误判。
- 失败后应用需要重试，重试次数与并发度相关，热点行上的冲突率随并发上升。
- 与锁方案相比，写冲突只在提交时暴露，前期工作可能全部作废，适合冲突率低的负载。

### 6.17 隔离级别提高的代价体现在哪些资源上？

- 锁：更严格的级别持有锁更久、范围更大，并发度下降，锁等待与死锁概率上升。
- 版本：快照隔离需要保留旧版本，内存与 undo 空间随并发事务数与事务长度增长。
- 日志：回滚与恢复需要更多 undo 与补偿记录，提交路径的日志量增加。
- CPU：可见性判定需要遍历版本链，冲突检测需要维护读写集合。
- 复制：可串行化下的冲突回滚在从库重放时表现为重试或跳过，需要额外的冲突处理策略。
- 结论是按业务不变量选择级别，而不是一律使用最高级别。

### 6.18（场景）同一查询两次执行结果不同，如何定位？

- 先确认两条查询是否在同一事务、同一连接：连接池可能把两条语句分配到不同会话与不同快照。
- 检查隔离级别与自动提交设置，读已提交下每条语句新建快照，跨语句结果本就可以不同。
- 检查是否读写分离，第二条查询被路由到延迟较大的副本。
- 检查是否混用了快照读与加锁读，后者读取最新版本。
- 检查期间是否有其他会话提交了修改，用二进制日志或审计日志对齐时间线。
- 排除以上因素后再检查缓存：查询缓存、应用层缓存与对象关系映射的一级缓存都会返回旧结果。

### 6.19（条款）事务包装类的异常安全边界在哪里？

- 事务对象在构造时开始事务，析构时若未提交则回滚，这是资源获取即初始化的典型用法。
- 提交函数需要在日志落盘失败时抛出异常，不能吞掉错误后返回成功。
- 析构函数不应抛出异常，回滚失败只能记录日志，否则在栈展开中触发 `std::terminate`。
- 提交成功后对象状态应标记为已完成，避免析构时重复回滚。
- 回滚路径本身可能失败，例如连接已断开，此时应把连接标记为不可用而不是继续复用。
- 事务对象的生命周期不应跨越协程挂起点，除非显式管理其存储；对象生存期规则见 `[basic.life]/1`。

### 6.20 如何在持久性与吞吐之间取舍？

| 同步策略 | 掉电丢失范围 | 提交延迟 | 适用场景 |
| --- | --- | --- | --- |
| 每秒同步 | 最近 1 秒 | 最低 | 可重放日志、批量导入 |
| 每次提交同步 | 无 | 最高 | 账务、订单 |
| 提交时写、每秒同步 | 掉电丢失 1 秒，进程崩溃不丢 | 中等 | 多数在线业务 |

- 每次提交同步是持久性最强、延迟最高的配置，单次提交成本约为一次设备同步。
- 组提交把并发事务的日志合并为一次同步，吞吐随并发上升，单事务延迟增加。
- 每秒同步在掉电时可能丢失最近一秒的已提交事务，适合可以重放的业务。
- 关闭同步只在进程崩溃时不丢数据，机器掉电仍会丢失，不能用于账务类数据。
- 批量导入可以临时降低同步频率，导入完成后做一次检查点并恢复配置。
- 持久性还取决于存储设备是否缓存写，阵列卡写缓存未开电池保护时同步语义由实现定义。

## 7. 锁与并发控制

### 7.1 两阶段封锁的基本规则是什么？

- 增长阶段只能加锁不能释放，缩减阶段只能释放不能加锁，分界点是最后一次加锁。
- 基本两阶段封锁保证冲突可串行化，但不保证可恢复：事务可能读到未提交数据后先行提交。
- 严格两阶段封锁要求排他锁持有到事务结束，避免级联回滚。
- 强严格两阶段封锁要求所有锁，包括共享锁，都持有到事务结束。
- 协议只规定加锁与释放的顺序，不规定粒度，行锁、页锁与表锁都可以套用。
- 死锁是两阶段封锁的固有代价，需要死锁检测或等待超时兜底。

### 7.2 多粒度封锁的相容矩阵如何设计？

- 锁模式包括共享、排他、意向共享、意向排他与共享意向排他五种。
- 在高层次加意向锁表示后代节点将被加相应锁，使冲突检查不必遍历整棵树。
- 意向共享与意向共享、意向排他、共享、共享意向排他都相容；意向排他只与意向共享、意向排他相容。
- 共享与意向排他冲突；共享意向排他只与意向共享相容；排他与其余四种都冲突。
- 对节点加共享锁或排他锁之前，必须先对祖先加意向共享或意向排他，保证表级锁能与行级锁冲突。
- 意向锁之间大多相容，因此不同行上的行锁不会互相阻塞；表级排他锁与所有意向锁冲突，可用于全表操作与结构变更。

### 7.3 行锁在存储引擎中如何表示？

- 锁按页号加记录序号定位，锁对象保存在全局锁哈希表中，键由表空间与页号组成。
- 同一页上的锁共享一个锁对象，内部用位图表示哪些记录被锁，位图长度按页内记录数分配。
- 每个锁对象维护请求队列，记录持有者与等待者的事务 ID、锁模式与等待状态。
- 等待者同时挂在事务的等待链上，双向链接用于死锁检测。
- 锁对象从内存池分配，释放后归还，避免在等待路径上调用系统分配器。
- 锁信息不写入数据页，因此不持久化，崩溃恢复后锁表为空。

### 7.4（辨析）表锁、元数据锁与意向锁有什么区别？

- 表锁是数据层的锁，锁定整张表的行，由显式语句请求。
- 元数据锁在服务层，保护表结构，查询持有共享模式，结构变更请求排他模式。
- 意向锁是数据层的表级锁，表示事务在表中某些行上持有或将要持有行锁，由引擎自动加。
- 元数据锁的等待会阻塞后续所有查询，长时间未提交的查询可使结构变更排队并扩大阻塞范围。
- 意向锁与行锁由同一套锁管理器管理，元数据锁有独立的管理器与等待队列。
- 排查表级阻塞需要同时查看元数据锁表与数据锁表。

### 7.5 间隙锁与 next-key 锁解决什么问题？

- next-key 锁是记录锁与其前面间隙锁的组合，锁住左开右闭区间。
- 间隙锁只阻止其他事务在间隙内插入，不阻止对已有记录的加锁读。
- 插入意向锁在插入前申请，与间隙锁冲突，多个插入意向锁之间相容。
- 唯一索引等值查询命中记录时退化为记录锁；未命中时加间隙锁。
- 范围查询按扫描到的索引记录逐条加 next-key 锁，锁范围与索引顺序一致。
- 间隙锁在可重复读下启用，读已提交下基本关闭，只在唯一性检查与外键检查时使用。

### 7.6（陷阱）锁等待超时与死锁有什么区别？

- 死锁是循环等待，检测器发现环后主动回滚一个事务，MySQL 返回错误码 1213。
- 锁等待超时是单个事务等待超过阈值，阈值由 `innodb_lock_wait_timeout` 控制，默认 50 秒，返回 1205。
- 死锁回滚通常很快，超时需要等满阈值，因此超时对连接池的占用更严重。
- 死锁检测有 CPU 成本，等待图规模大时可采用超时兜底并关闭主动检测。
- 超时可能掩盖设计问题，例如同一事务内按不同顺序访问多行。
- 应用层需要区分两类错误：死锁应重试整个事务，超时应检查是否有长事务持锁。

### 7.7 死锁检测的等待图如何构建？

- 节点是事务，有向边表示等待关系：T1 等待 T2 持有的锁，则边由 T1 指向 T2。
- 事务进入等待时把边加入图，获得锁或超时后删除边。
- 检测从新进入等待的事务出发做深度优先搜索，回到起点即发现环。
- 发现环后选择牺牲者，代价通常按已修改行数、持有锁数量与日志量估算。
- 牺牲者回滚并释放锁，等待者被唤醒继续执行。
- 等待图与锁管理器共享数据，检测期间持锁会放大开销，实现上常分段加锁或使用无锁读。

### 7.8（实现）如何检测等待图中的环？

```cpp
bool reaches(const std::unordered_map<int, std::vector<int>>& wait,
             int from, int target, std::unordered_set<int>& seen) {
    if (from == target) return true;
    if (!seen.insert(from).second) return false;
    auto it = wait.find(from);
    if (it == wait.end()) return false;
    for (int next : it->second)
        if (reaches(wait, next, target, seen)) return true;
    return false;
}
```

- 在事务进入等待时，从该事务出发搜索能否回到自身，等价于判断新增的边是否形成环。
- `seen` 集合防止在已访问节点上重复展开，复杂度与边数线性相关。
- 递归深度受等待链长度限制，生产实现通常改为显式栈以避免栈溢出。
- 环上的所有事务都可作为牺牲者，选择回滚代价最小的一个。
- 检测与加边必须原子，否则可能漏掉同时形成的两条边。
- 该实现只处理单资源等待，队列头阻塞这类多资源等待需要把边指向队首持有者。

### 7.9（辨析）latch 与 lock 的差别在哪里？

- lock 保护逻辑数据，例如行与表，持有到事务结束，可被用户感知，支持死锁检测与等待超时。
- latch 保护内存数据结构，例如页、哈希桶与锁表，持有时间以微秒计，不参与事务。
- latch 通常不检测死锁，依靠固定的加锁顺序避免环。
- latch 的等待者不能被事务回滚，也不需要持久化。
- latch 有共享与排他两种模式，部分实现提供更新模式以减少争用。
- 崩溃后 latch 状态与 lock 状态都丢失，恢复依赖日志而不是锁。

### 7.10 latch 在 C++ 中如何实现与选择？

- 自旋锁适合临界区极短的场景，用 `std::atomic_flag` 或 `compare_exchange_weak` 实现。
- 自旋在竞争激烈时浪费 CPU，通常在自旋若干次后退化为内核等待。
- `std::mutex` 在 Linux 上由 C 库实现，无竞争时只有一次原子操作，竞争时进入内核。
- `std::shared_mutex` 提供读写锁，C++17 起可用，读多写少时减少争用。
- 读写锁可能造成写饥饿，公平性由实现定义，不能假定等待顺序。
- 高并发下可用分段锁或每核计数器降低单一 latch 的争用。

### 7.11（陷阱）B+ 树并发的 latch 顺序如何导致死锁？

- 自顶向下加锁时若先锁子节点再锁父节点，而另一路径顺序相反，两个线程可能互相等待。
- 标准做法是保持父节点先于子节点的顺序，或使用 latch coupling 在下降时持有父节点再申请子节点。
- 悲观下降持有路径上的多个 latch，深度越大持有时间越长，并发度越低。
- 乐观下降先不加写锁读取，版本号或校验和变化时重试，适合读多写少。
- 页分裂需要同时持有左右兄弟页的 latch，按页号升序申请可避免环。
- 索引分裂与缓冲区管理器的 latch 也可能交叉，需要全局约定层次：表、索引、页、记录。

### 7.12 锁粒度如何影响并发与开销？

- 行锁并发度高，但每行一个锁对象，内存与 CPU 开销大，锁表容易成为热点。
- 页锁开销小，但同页不同行会互相阻塞，适合行较大或访问集中的场景。
- 表锁开销最小，适合批量操作与全表扫描，在线事务处理下并发度不足。
- 锁升级在锁数量超过阈值时把细粒度锁替换为表锁，SQL Server 有该机制，InnoDB 没有。
- 意向锁使不同粒度的锁可以共存，避免逐行检查。
- 粒度选择取决于访问模式：点查多用行锁，范围扫描多时分页锁或分区锁更合适。

### 7.13 乐观并发控制的三个阶段是什么？

- 读阶段：事务读取数据到私有工作区，记录读集合，所有写操作只作用于私有副本。
- 验证阶段：提交前检查读集合是否被其他已提交事务修改，并检查写集合是否冲突。
- 写阶段：验证通过后把私有修改写入共享数据库，通常在临界区内完成。
- 向后验证检查本事务读取的数据在读取之后是否被修改，向前验证检查写集合冲突。
- 验证失败的事务回滚重试，适合冲突率低的场景。
- 读不阻塞写、无死锁是优点；高冲突下重试成本高、长事务验证窗口大是缺点。

### 7.14（场景）库存扣减应该选择哪种并发控制？

- 悲观方案：以加锁读锁定库存行，扣减后提交，实现简单，但热点行排队。
- 乐观方案：读取版本号，更新时带版本条件，影响行数为 0 则重试，适合冲突率低。
- 原子方案：执行带条件的自减更新语句，由引擎在行锁内完成读改写。
- 分段方案：把库存拆成多个桶，请求随机选择桶扣减，降低单行争用，查询时需要汇总。
- 预扣方案：先在缓存或独立表扣减，异步落库，需要处理超卖与补偿。
- 选择依据是热点程度与一致性要求，单行热点在上千 QPS 下通常需要分段或排队。

### 7.15 为什么行锁之前需要意向锁？

- 事务要修改某行时，先对表加意向排他锁，再对行加排他锁。
- 其他事务若想加表级共享锁，只需检查表上的意向锁即可判断是否存在行锁，无需遍历所有行。
- 若没有意向锁，表级锁必须扫描整张表的行锁，代价与行数成正比。
- 意向锁之间相容，因此不同行的事务不会因为表级意向锁互相阻塞。
- 意向锁可以有多层：表、分区、页，逐层声明意图。
- 意向锁由引擎自动加，用户接口通常不暴露。

### 7.16 自增锁如何影响插入并发？

- 自增列的值由表级计数器分配，分配方式由 `innodb_autoinc_lock_mode` 决定。
- 模式 0 为传统模式，语句级持有自增锁直到语句结束，并发插入串行化。
- 模式 1 为连续模式，简单插入用轻量互斥量分配，批量插入仍持有表锁。
- 模式 2 为交错模式，所有插入并发分配，值可能不连续，是 MySQL 8.0 的默认值。
- 值不连续本身不是问题，但依赖自增值连续的业务逻辑应改用显式序列。
- 语句复制要求自增值确定，交错模式需要行复制配合。

### 7.17 谓词锁在可串行化中如何实现？

- 谓词锁锁定查询条件覆盖的数据范围，而不是命中的具体行。
- 实现通常用索引区间锁或页级标记近似，无法精确表达任意谓词。
- PostgreSQL 的 SIREAD 锁不阻塞任何操作，只用于检测读写依赖。
- 锁粒度随读集合增大而升级：元组到页，页到关系。
- 升级会提高误判率，产生不必要的串行化失败。
- 只读事务也参与检测，长只读事务会积累大量谓词锁。

### 7.18（输出题）给定加锁顺序，是否会发生死锁？

| 时刻 | T1 | T2 |
| --- | --- | --- |
| t1 | 锁 A | |
| t2 | | 锁 B |
| t3 | 请求 B，等待 | |
| t4 | | 请求 A，等待 |

- T1 持有 A 等待 B，T2 持有 B 等待 A，等待图上形成 A 到 B、B 到 A 的环。
- 检测器回滚其中一个事务，另一个获得锁继续执行。
- 若两个事务都先锁 A 再锁 B，第二个事务只在 A 上等待，不会形成环，表现为串行而非死锁。
- 若 T2 在 t3 之前提交并释放 B，T1 的等待可以满足，环不成立。
- 该调度在严格两阶段封锁下必然死锁，在乐观并发下则以提交时的冲突失败告终。
- 预防手段是全局定义加锁顺序，例如按主键升序访问。

### 7.19 锁对象的内存生命周期如何管理？

- 锁对象由锁管理器分配，引用计数归零后归还内存池，避免每次等待都申请堆内存。
- 事务持有的锁列表与锁的等待队列互相引用，释放时必须同时摘除两侧链接。
- 等待中的事务被取消时，需要从等待队列移除并唤醒后续等待者，否则队列永久阻塞。
- 锁对象不能随事务对象析构立即释放，因为其他事务可能仍在等待队列中引用它。
- 侵入式链表与对象池可以避免额外分配，但要求节点在移除前保持有效。
- 崩溃后内存状态全部丢失，恢复不需要重建锁，只需要回滚未提交事务。

### 7.20 线上如何观测锁等待？

- MySQL 用 `performance_schema.data_locks` 与 `data_lock_waits` 查看当前持锁与等待关系。
- 执行 `SHOW ENGINE INNODB STATUS`，`LATEST DETECTED DEADLOCK` 段保存最近一次死锁的两个事务与加锁语句。
- PostgreSQL 用 `pg_locks` 与 `pg_blocking_pids` 定位阻塞链，`pg_stat_activity` 的等待事件显示等待类型。
- 指标层面关注锁等待时间、死锁次数、超时次数与平均持锁时长。
- 采样应在低峰期进行，查询锁表本身会持有锁管理器的 latch。
- 长事务是锁等待的主要来源，应按事务开始时间排序并设置告警。

## 8. 日志与恢复

### 8.1 redo 与 undo 各自解决什么问题？

- redo 记录如何重做，用于崩溃后恢复已提交事务对数据页的修改，保证持久性。
- undo 记录如何撤销，用于回滚未提交事务，并为 MVCC 提供旧版本。
- steal 策略下未提交的页可能已经落盘，需要 undo 回滚；no-force 策略下已提交的页可能尚未落盘，需要 redo 重放。
- redo 记录页号与页内字节修改，属于物理或物理逻辑日志；undo 记录反向的逻辑操作。
- undo 页本身也写 redo，因为 undo 同样需要持久化与恢复。
- 两类日志共同保证原子性与持久性，在 steal 与 no-force 组合下缺少任一类都无法正确恢复。

### 8.2 预写日志的两条规则是什么？

- 规则一：数据页写入磁盘前，对应的 redo 必须已经持久化，判断依据是页上保存的序列号不小于日志记录的序列号。
- 规则二：事务提交返回前，该事务的日志，包括提交记录，必须持久化。
- 规则一允许日志先行、数据页延迟写出，把随机写合并为顺序写。
- 规则二决定提交延迟，组提交把多个事务的日志合并为一次同步。
- 违反规则一会在崩溃后丢失已提交修改；违反规则二会在掉电后丢失已返回成功的事务。
- 日志缓冲区与数据缓冲区分离，刷日志与刷数据页由不同线程负责。

### 8.3（辨析）fsync、fdatasync 与 O_DIRECT 的边界在哪里？

- `fsync` 把文件数据与元数据写入设备并等待完成，`fdatasync` 只保证数据与读取所需的元数据。
- 两者都要求设备缓存落盘，若设备带易失写缓存且未开启写穿，实际语义由实现定义。
- `O_DIRECT` 绕过页缓存，减少一次内存复制，但仍需同步调用保证设备缓存落盘。
- `O_DIRECT` 要求缓冲区地址与长度按块对齐，未对齐的读写会失败。
- 日志文件通常用直接 IO 或同步写打开，避免日志先进入页缓存再被回写线程重排。
- 每次提交同步与批量同步是权衡：前者保证持久性，后者提高吞吐但增加丢失窗口。

### 8.4 日志记录包含哪些字段？

- 通用头部包括日志序列号、事务 ID、记录类型、长度与指向上一条记录的指针。
- 页修改类记录包含表空间、页号、页内偏移与修改后的字节。
- 事务类记录包括开始、提交、回滚、保存点与补偿记录。
- 检查点记录包含活跃事务表、脏页表与各事务的最后日志序列号。
- 日志序列号单调递增，日志按序写入，页上保存最后修改该页的日志序列号。
- 校验和覆盖记录内容，恢复时先校验再应用，损坏的日志需要从备份补齐。

### 8.5 ARIES 的三个阶段如何执行？

- 分析阶段从最后一个检查点开始扫描日志，重建事务表与脏页表，确定回滚起点。
- 重做阶段从脏页表中最小的恢复日志序列号开始，重复历史：对每条日志比较页上序列号，小于日志序列号才应用。
- 撤销阶段从日志尾部反向扫描，对未提交事务执行 undo，并写入补偿记录。
- 补偿记录包含下一条待撤销记录的位置，回滚过程本身崩溃后可以继续，不会重复撤销。
- 重做是幂等的，因为页上序列号的比较保证同一条日志最多应用一次。
- 三阶段的设计目标是让恢复过程本身可被中断与重启。

### 8.6 检查点保存什么，模糊检查点如何工作？

- 检查点记录活跃事务、脏页及其恢复日志序列号，作为恢复的起点。
- 一致性检查点要求停止所有事务并刷出所有脏页，停顿时间与脏页量成正比。
- 模糊检查点只记录当前状态，不等待脏页刷完，脏页在后台继续写出。
- 恢复时从检查点记录的恢复序列号开始重做，因为更早的修改可能仍未落盘。
- 检查点频率影响恢复时间与运行时开销：越频繁恢复越快，但日志与页的刷写更密集。
- 日志空间是环形的，检查点还必须保证最早需要的日志不被覆盖。

### 8.7（场景）崩溃恢复的完整流程是什么？

- 启动时读取日志文件头与最后一个检查点记录，确定扫描起点。
- 分析阶段重建事务表与脏页表，标记未提交事务。
- 重做阶段按日志序列号顺序重放，确保所有已提交修改进入数据页。
- 撤销阶段回滚未提交事务，写入补偿记录并释放其持有的锁。
- 恢复完成后写入新的检查点，再开放连接。
- 恢复期间需要拒绝写入，或只允许在恢复完成后提供服务。

### 8.8 部分页写入如何检测与修复？

- 页大小通常为 16 KiB，而设备的原子写单位可能是 512 字节或 4 KiB，掉电可能只写入一部分。
- 页头与页尾各存一个校验和，读取时校验失败说明页损坏。
- 双写缓冲把页先顺序写入独立区域，再写回数据文件，恢复时用副本修复损坏页。
- 双写缓冲增加一次写放大，但把随机写合并为顺序写，整体开销有限。
- 文件系统与阵列卡也可能提供原子写或掉电保护，此时可以关闭双写。
- 校验和算法可选 CRC32C 或硬件加速校验，选择影响 CPU 开销与检测强度。

### 8.9 组提交与两阶段提交如何配合？

- 组提交把多个事务的日志合并为一次同步，提交线程收集队列中的事务形成批次。
- 两阶段提交协调 redo 与二进制日志：先写 redo 并置为准备状态，再写二进制日志，最后写 redo 提交记录。
- 崩溃发生在二进制日志写完之前，事务回滚；二进制日志完整而 redo 未提交时，恢复阶段根据二进制日志补提交。
- 两种日志的写入顺序是持久性一致性的核心，二进制日志必须先于 redo 提交记录落盘。
- 同时开启二进制日志同步与 redo 提交同步时，每次提交至少两次设备同步。
- 组提交可以把两次同步合并到同一批次，降低每次提交的平均同步次数。

### 8.10 undo 在物理上如何组织？

- undo 按回滚段组织，每个回滚段包含多个 undo 槽，事务绑定其中一个槽。
- undo 页与数据页一样由缓冲池管理，修改 undo 页也会产生 redo。
- 插入操作的 undo 只用于回滚，提交后可立即丢弃；更新与删除的 undo 还需支持 MVCC 读，由 purge 延迟清理。
- purge 线程按事务提交顺序清理不再需要的 undo，并释放版本链。
- undo 表空间可以独立配置与截断，长事务会阻止截断。
- 回滚段数量影响并发事务数上限，耗尽时新事务无法开始。

### 8.11（陷阱）redo 日志能否省掉？

- 在 no-steal 与 force 策略下，事务提交前所有修改页都刷盘，崩溃恢复不再需要 redo。
- 该策略下每次提交都要等待随机页写入，延迟与写放大都不可接受。
- 若采用 steal 与 no-force，必须同时具备 redo 与 undo，二者缺一不可。
- 只有 redo 没有 undo 无法回滚未提交事务；只有 undo 没有 redo 会在崩溃后丢失已提交修改。
- 日志是顺序写，数据页是随机写，用日志替代部分随机写是性能上的主要动机。
- 因此现代引擎普遍选择 steal 与 no-force 组合，并以预写日志为核心。

### 8.12 恢复的幂等性由什么保证？

- 每条日志记录的序列号唯一且单调，页上保存最后一次修改它的序列号。
- 重做时比较页上序列号与日志序列号，页已包含该修改则跳过。
- 撤销时写入补偿记录，补偿记录指向下一条待撤销记录，避免重复撤销。
- 恢复过程可以在任意点中断，重启后从检查点重新开始，结果一致。
- 幂等性依赖日志不丢失与页上序列号正确持久化，页头损坏会使判断失效。
- 逻辑操作本身不一定幂等，因此 undo 需要记录物理位置。

### 8.13（实现）如何封装一次日志写入？

```cpp
void LogWriter::append(const LogRecord& rec) {
    std::lock_guard<std::mutex> lk(mu_);
    rec.serialize(buf_);
    if (buf_.size() >= kFlushThreshold) flush_locked();
}

void LogWriter::flush_locked() {
    if (buf_.empty()) return;
    write_all(fd_, buf_.data(), buf_.size());
    if (::fdatasync(fd_) != 0)
        throw std::system_error(errno, std::generic_category());
    buf_.clear();
}
```

- 日志缓冲区由互斥量保护，追加与刷盘在同一临界区内完成，保证写入顺序。
- `write_all` 需要处理部分写与信号中断，单次写调用不保证写完整个缓冲区。
- 刷盘失败必须抛出异常，不能把失败当作成功返回，否则持久性失效。
- 缓冲区在刷盘成功后清空，避免重复写入；清空前崩溃会重写日志，依赖恢复的幂等性。
- 批量阈值与提交同步需要区分：提交路径必须无条件刷盘，后台线程只按阈值刷。
- 缓冲区使用预分配的内存池，避免在提交路径上触发堆分配。

### 8.14 mmap 写文件能否替代预写日志？

- `mmap` 把文件映射到地址空间，写入直接修改页缓存，由内核在之后回写。
- `msync` 只发起回写，不保证多个页之间的顺序，也不保证掉电后全部落盘。
- 崩溃时可能只有部分页写入，文件处于中间状态，没有原子性。
- 缺页时若发生 IO 错误，进程收到 `SIGBUS`，而不是可处理的错误码。
- 因此 `mmap` 适合读多写少的场景，写入路径仍需日志或双写保证一致性。
- 用 `mmap` 实现日志文件时，仍需显式同步与校验和，不能省略刷盘。

### 8.15 磁盘格式如何做到跨平台可读？

- 固定宽度整数使用 `std::uint32_t` 与 `std::uint64_t`，不直接序列化结构体。
- 统一字节序，通常选小端，读写时显式转换，不依赖主机字节序。
- 记录前加长度前缀与类型字段，尾部加校验和，支持跳过未知类型。
- 头部包含魔数、格式版本与页大小，版本升级时保留旧版本的读取路径。
- 变长字段用偏移量或长度前缀表示，不使用指针与容器对象的内存布局。
- 需要按固定对齐打包时编写显式序列化函数，直接复制整个结构体会引入填充字节与 ABI 差异。

### 8.16（条款）页缓冲区重建时的对象生命周期如何处理？

- 从磁盘读入的页是字节数组，需要在缓冲区中构造页头对象再访问字段。
- 使用 placement new 在缓冲区上构造，释放时显式调用析构函数。
- 对象生存期从构造完成开始，到析构调用或存储被复用时结束，规则见 `[basic.life]/1`。
- 缓冲区复用前必须结束旧对象的生存期，否则新旧对象重叠。
- 页头若是可平凡复制类型，可以先复制到对齐的缓冲区，再通过 `std::bit_cast` 读取。
- 跨页的变长记录不能用连续对象表示，需要用偏移访问。

### 8.17（场景）恢复时间过长如何优化？

- 恢复时间与需要重放的日志量成正比，检查点间隔越大，重放越多。
- 缩短检查点间隔可以减少重放量，但增加运行时的刷页开销。
- 大事务回滚是另一个瓶颈，回滚需要遍历 undo 链，可能比重做更慢。
- 并行重做按页或按表空间划分，避免同一页冲突，可缩短重做阶段。
- 二级索引可以从主键重建，跳过索引页的日志重放，代价是重建时间。
- 恢复期间关闭双写与校验可以加快速度，但会降低安全性，只应在受控环境使用。

### 8.18 redo 日志的写放大来自哪里？

- 每次页修改都产生日志，小修改也要写记录头、页号与校验和。
- 一个事务修改多页会产生多条记录，记录头开销占比高。
- 检查点强制刷脏页时，日志与数据页同时写入，形成额外 IO。
- 日志文件环形复用，写满后必须等待检查点推进，形成周期性抖动。
- 合并小记录或压缩可以降低写放大，但增加 CPU 开销与恢复复杂度。
- 监控指标是每秒日志字节数与数据页写入字节数的比值。

### 8.19 备份与时间点恢复如何依赖日志？

- 物理备份复制数据文件与日志文件，恢复时重放日志到一致点。
- 时间点恢复需要基础备份加连续归档的日志，按日志序列号或时间戳截断。
- 备份期间不能删除日志，否则恢复链断裂。
- 逻辑备份不依赖日志格式，但恢复速度慢，且不能保证时间点一致。
- 恢复演练应定期执行，验证备份可用与日志链完整。
- 日志归档的保留窗口决定可恢复的时间范围。

### 8.20 如何测试崩溃恢复的正确性？

- 在随机时刻发送终止信号杀死进程，重启后校验不变量与已提交事务。
- 用故障注入工具模拟写丢失、乱序与部分写，验证校验和与双写机制。
- 记录已提交事务集合，恢复后逐条核对，未提交事务必须不可见。
- 测试应覆盖日志写满、检查点并发与恢复中断后再次重启。
- 断言放在恢复完成之后、开放连接之前，失败时保留现场。
- 长时间随机测试比定向用例更容易暴露顺序相关的缺陷。

## 9. 查询执行

### 9.1 火山模型如何组织算子？

- 每个算子实现打开、取下一行与关闭三个接口，取下一行返回一行或结束标记。
- 父算子调用子算子的取下一行拉取数据，控制流自顶向下，数据流自底向上。
- 优点是接口简单、算子可组合、支持流水线；缺点是每行一次虚函数调用，CPU 开销高。
- 排序与哈希构建这类阻塞算子在打开阶段消费全部输入，形成流水线断点。
- 火山模型一次只处理一行，内存占用小，适合行存与磁盘为主的执行环境。
- 现代引擎在此基础上做批处理化，把一次一行的接口改为一次一批。

### 9.2（辨析）拉取模型与推送模型有什么区别？

- 拉取模型由上层调用下层的取下一行，控制权在消费者，容易实现提前终止。
- 推送模型由下层把结果推给上层，算子之间通过回调或队列连接，减少调度开销。
- 推送模型适合向量化与并行，数据以批次流动，编译器容易优化循环。
- 拉取模型在 limit、短路求值与嵌套循环连接上更自然。
- 推送模型需要在算子内部维护状态机，实现复杂度更高。
- 多数引擎在物理计划层用拉取，在批处理层用推送，二者可以混合。

### 9.3 顺序扫描与索引扫描如何选择？

- 顺序扫描按页读取整表，代价约等于表所占页数，适合选择率高或需要大部分列的场景。
- 索引扫描先读索引再回表，代价等于索引页数加命中行数的随机读，适合选择率低且列少。
- 选择率阈值取决于行宽、索引宽度、缓存命中率与随机读代价，不是固定值。
- 覆盖索引可以避免回表，把随机读变为索引顺序读，显著降低代价。
- 索引顺序与聚簇索引不一致时，回表是随机 IO，机械盘上的代价远高于顺序扫描。
- 优化器用统计信息估算选择率，估算偏差会导致访问路径选错。

### 9.4 嵌套循环连接的代价结构是什么？

- 外表每行驱动一次内表扫描，总代价为外表行数乘以单次内表访问代价。
- 内表有索引时单次访问是对数级，无索引时是内表页数，后者代价极高。
- 块嵌套循环按块读取外表，把内表的重复扫描摊薄，适合无索引的连接。
- 连接条件选择性高时嵌套循环优于哈希连接，因为可以提前终止。
- 外表行数估算错误会线性放大代价，连接顺序因此重要。
- 嵌套循环支持非等值连接与相关子查询，哈希连接只支持等值连接。

### 9.5 哈希连接如何工作，溢出如何处理？

- 构建阶段扫描较小输入，以连接键建立哈希表，表项保存行指针或行副本。
- 探测阶段扫描较大输入，逐行查表并输出匹配行。
- 内存不足时使用分区哈希：按哈希值把两侧数据分区写盘，再逐分区构建与探测。
- 分区数不足或数据倾斜时单个分区仍可能超出内存，需要递归分区。
- 布隆过滤器可以在探测前过滤不可能匹配的行，减少 IO。
- 哈希连接要求等值条件，构建侧大小估算影响内存分配与溢出概率。

### 9.6 排序归并连接的前提与代价是什么？

- 两侧输入必须按连接键有序，可以利用已有索引顺序或显式排序。
- 归并阶段用双指针推进，代价与两侧行数线性相关，输出天然有序。
- 输入已有序时代价低于哈希连接；需要排序时代价包含排序的 CPU 与 IO。
- 支持等值连接，也可以在归并后对非等值条件做过滤。
- 排序结果可被上层复用，优化器会把这一收益计入计划比较。
- 数据倾斜不影响正确性，只影响输出顺序与去重逻辑。

### 9.7 外部排序如何减少归并趟数？

- 第一阶段生成有序归并段，缓冲区越大段越长，段数越少。
- 替换选择可以把平均段长提高到缓冲区大小的两倍，减少段数。
- 多路归并把多个段合并，趟数等于段数对路数取对数，路数受缓冲区限制。
- 归并时用最小堆选择当前最小元素，每次取堆顶并补充同段的下一元素。
- IO 代价约为数据量乘以两倍趟数，CPU 代价主要来自比较与堆调整。
- 排序键较短时可以用前缀比较与基数排序降低比较开销。

### 9.8 哈希聚合与排序聚合如何选择？

- 哈希聚合维护分组键到聚合状态的哈希表，一遍完成，输出无序。
- 排序聚合先按分组键排序，再顺序扫描聚合，输出有序，内存需求可预测。
- 分组基数低时哈希聚合占优；分组基数接近行数时哈希表膨胀，排序聚合更稳。
- 哈希聚合可以溢出到磁盘，按分区落盘后逐分区聚合。
- 排序聚合可以利用索引顺序，避免显式排序。
- 聚合函数是否可增量计算影响状态大小，去重计数需要额外结构。

### 9.9（输出题）给定内存与数据量，哈希连接需要多少个分区？

- 构建侧数据量为 6 GiB，可用内存 1 GiB，哈希表负载因子上限为 0.75，行指针与哈希头开销按 20% 计。
- 单分区可用容量为 1 GiB × 0.75 ÷ 1.2，约 0.625 GiB。
- 分区数为 6 GiB ÷ 0.625 GiB，约 9.6，向上取整为 10。
- 实现通常取 2 的幂，向上取到 16，便于用位掩码计算分区号。
- 分区数增加会带来更多文件句柄与更小的写缓冲，写放大上升。
- 倾斜会让最大分区超过均值，应按最大分区校验容量，必要时单独处理热点键。
- 估算应基于行数与平均行长，不能直接用压缩后的字节数。

### 9.10 向量化执行带来哪些收益与约束？

- 一次处理一批行，常见批大小为 1024 至 4096 行，摊薄每行的虚函数调用与分支开销。
- 列式布局使同一列的运算连续，便于 SIMD 与缓存预取。
- 批内可以用选择向量表示有效行，避免逐行分支。
- 约束是内存占用增加，短查询填充批次的成本占比高。
- 表达式求值需要改写为批处理函数，逐节点解释执行的收益有限。
- 向量化与并行化正交，二者可以叠加。

### 9.11 流水线断点出现在哪里？

- 排序、哈希构建、去重与物化算子必须消费全部输入才能产出，构成断点。
- 断点把查询切成多个段，段之间通过临时文件或内存物化传递数据。
- 断点数量影响内存峰值与调度，优化器倾向于减少断点。
- 流水线内部可以并行，段边界需要同步，形成屏障。
- 自适应执行可以在断点处根据实际行数调整后续计划。
- 把 limit 下推到断点之前可以显著减少物化数据量。

### 9.12 并行执行如何划分工作？

- 数据并行按分区或页范围切分扫描，每个工作线程处理独立片段。
- 算子并行在计划中插入交换算子，负责重分区与广播。
- 并行哈希连接要求两侧按连接键重分区到同一组线程。
- 并行度受 CPU 核数、IO 带宽与内存限制，过高会增加协调开销。
- 倾斜键会使单个线程成为瓶颈，需要动态重分区或倾斜处理。
- 并行计划不保证结果顺序，除非显式排序。

### 9.13 表达式求值的实现方式有哪些取舍？

- 解释执行把表达式编译为操作符树，逐节点求值，实现简单但每行开销大。
- 向量化解释按批求值，减少调度开销，仍保留树形结构。
- 代码生成把表达式或整个算子编译为机器码，消除解释开销，编译时间与复杂度上升。
- 即时编译可以利用常量折叠与寄存器分配，但需要处理类型特化与去优化。
- C++ 中可用模板特化在编译期生成算子，避免运行时分支。
- 选择取决于查询复杂度与执行次数，短查询的编译成本可能超过收益。

### 9.14（场景）回表次数过多导致慢查询，如何优化？

- 确认执行计划是否走二级索引回表，回表次数等于命中的索引条目数。
- 建立覆盖索引，把查询需要的列加入索引，消除回表。
- 用索引条件下推把过滤条件下推到索引扫描，减少回表行数。
- 调整查询让过滤条件选择性更高，或改写为子查询先缩小主键集合。
- 延迟物化：先取主键排序分页，再按主键取列，减少随机读。
- 若回表比例过高，全表扫描可能更快，需要比较实际代价而不是假定索引更优。

### 9.15 limit 与 offset 的代价在哪里？

- 偏移量需要先产生并丢弃前若干行，代价与偏移量成正比。
- 深分页应改为按上一页最后一条记录的键做范围查询，即键集分页。
- 排序加 limit 可以用 top-N 堆，内存为 N 而不是全量。
- 索引顺序与排序顺序一致时可以省略排序，直接截断。
- 并行计划下的 limit 需要各线程协调，可能提前终止扫描。
- 分页结果需要稳定顺序，排序列必须唯一或追加主键。

### 9.16 算子内存如何管理？

- 每个算子有独立的内存上限，由查询级内存池分配，超限时触发溢出或报错。
- 内存池按块分配，块大小固定，减少碎片与分配次数。
- 算子注册内存消费者，内存紧张时按优先级回收。
- 溢出到磁盘需要序列化中间结果，格式与磁盘格式共享。
- 内存上限过小导致频繁溢出，过大则并发查询数下降。
- 监控项包括每个算子的峰值内存与溢出次数。

### 9.17（实现）如何写一个批处理的过滤算子？

```cpp
struct Batch {
    std::vector<std::int64_t> keys;
    std::vector<std::int32_t> rows;
};

void filter_gt(const Batch& in, std::int64_t threshold, Batch& out) {
    out.keys.clear();
    out.rows.clear();
    for (std::int32_t i = 0; i < static_cast<std::int32_t>(in.keys.size()); ++i) {
        if (in.keys[i] > threshold) {
            out.keys.push_back(in.keys[i]);
            out.rows.push_back(in.rows[i]);
        }
    }
}
```

- 选择向量用行号数组表示，后续算子按行号取列，避免复制整行。
- 批内循环没有虚函数调用，编译器可以向量化。
- 输出缓冲区复用，容量不足时扩容，避免每批重新分配。
- 谓词为空时可以整批传递，跳过复制。
- 阈值作为参数传入，类型固定；需要泛型时可用模板特化。
- 该实现保持输入顺序，上层不要求顺序时可以并行分段。

### 9.18 运行时过滤如何减少扫描量？

- 构建侧完成后生成布隆过滤器或最小最大范围，下推到探测侧扫描。
- 探测侧在读取数据前先过滤，减少 IO 与解压开销。
- 布隆过滤器有假阳性无假阴性，适合等值连接。
- 范围过滤适合有序数据与分区裁剪。
- 过滤器需要随构建侧数据更新，广播到所有扫描线程有同步成本。
- 过滤器选择性差时收益有限，反而增加 CPU 开销。

### 9.19 排序语义中有哪些易错点？

- 空值的排序位置由实现定义，SQL 标准未规定默认顺序，跨库迁移时需要显式声明。
- 字符串排序依赖排序规则，二进制比较与语言相关比较的结果不同。
- 排序规则影响索引可用性，排序键的规则不一致时无法利用索引顺序。
- 稳定排序在分页场景重要，相等键的相对顺序影响结果。
- 浮点非数的比较不满足全序，排序前需要定义处理方式。
- 多列排序的列顺序必须与索引列顺序一致才能复用索引。

### 9.20 执行器与存储格式如何耦合？

- 行存按行连续存放，适合点查与整行读取，向量化收益有限。
- 列存按列连续存放，适合分析型扫描与压缩，点查需要读取多列。
- 谓词下推到存储层可以跳过不满足条件的数据块，依赖块级统计信息。
- 压缩算法影响随机访问，块压缩需要解压整块，细粒度压缩便于跳过。
- 编码方式决定比较是否需要解码，字典编码的等值比较可以只比较编码值。
- 执行器的批大小应与存储块大小匹配，避免跨块读取放大。

## 10. 查询优化

### 10.1 逻辑优化与物理优化的分工是什么？

- 逻辑优化在关系代数层面重写查询，保持语义等价，输出逻辑计划。
- 常见重写包括谓词下推、投影裁剪、常量折叠、连接消除与外连接转内连接。
- 物理优化为逻辑算子选择实现算法与访问路径，输出执行计划。
- 逻辑优化依赖等价变换规则，物理优化依赖代价模型与统计信息。
- 二者边界并不严格，部分引擎在物理阶段仍会做谓词下推与去重。
- 重写必须保持语义，包括空值语义、重复行与副作用。

### 10.2 谓词下推在哪些情况下不能做？

- 外连接的条件与过滤条件语义不同，把过滤条件下推到外连接的空值侧会改变结果。
- 含窗口函数或聚合的查询，谓词下推需要区分聚合前与聚合后。
- 非确定性函数，例如随机数与当前时间，不能跨越求值次数改变的位置下推。
- 含子查询的谓词下推需要先做解嵌套，否则可能重复求值。
- 排序与 limit 之间的谓词下推需要保持行数语义。
- 下推收益取决于存储层能否利用，例如分区裁剪与索引条件下推。

### 10.3 代价模型由哪些部分组成？

- IO 代价：顺序读页与随机读页的权重不同，固态盘上差距小于机械盘。
- CPU 代价：每行处理、比较、哈希与表达式求值的固定开销。
- 内存代价：哈希表与排序缓冲区的大小，超限触发溢出。
- 网络代价：分布式计划中的数据传输量与重分区次数。
- 启动代价与运行代价分离，limit 与小结果集更关注启动代价。
- 权重需要按硬件校准，默认值在不同存储介质上偏差很大。

### 10.4 统计信息包含哪些内容？

- 表的行数、页数与平均行宽。
- 列的基数、空值比例与最大最小值。
- 直方图：等宽直方图按值域等分，等深直方图按行数等分。
- 高频值列表记录出现频率异常高的值，弥补直方图对倾斜数据的不足。
- 多列统计与函数依赖统计用于相关性强的列。
- 统计信息是采样估算，采样率与更新频率影响准确性。

### 10.5（陷阱）基数估计为什么会指数级失真？

- 单列统计假设列间独立，连接选择率按各列选择率相乘，相关性会使估算偏小。
- 连接键的取值分布假设包含关系，实际重叠度不同，估算可能偏差数量级。
- 多表连接时误差逐层相乘，中间结果估算偏小会导致后续选错连接算法。
- 谓词之间相互独立的假设在范围查询与等值查询混合时失效。
- 参数化查询复用计划时，绑定变量不同会使同一计划对部分参数次优。
- 缓解手段包括多列统计、采样校验、自适应执行与执行反馈。

### 10.6 连接顺序如何搜索？

- 动态规划枚举左深树，状态为已连接的表集合与输出顺序，复杂度随表数指数增长。
- System R 风格的算法在表数较少时可行，阈值通常在十张表左右。
- 表数超过阈值后改用贪心或遗传算法，牺牲最优性换取搜索时间。
- 搜索空间还包含访问路径与连接算法，需要与顺序联合搜索。
- 有趣的顺序（interesting order）影响后续排序与归并连接，需要在状态中保留。
- 启发式规则先做连接图分析，把强相关的表放在一起。

### 10.7 索引选择要考虑哪些因素？

- 索引的选择率、覆盖列、索引顺序与查询的排序需求。
- 多个单列索引可以用索引合并，但代价可能高于单次全表扫描。
- 复合索引遵循最左前缀，范围条件之后的列无法用于定位。
- 覆盖索引避免回表，代价是索引更宽、写入放大更高。
- 索引维护成本随索引数量线性增长，写多读少的表应减少索引。
- 优化器可能高估索引收益，需要用实际执行统计校准。

### 10.8（输出题）给定谓词，应选择哪种访问路径？

- 表有 100 万行，每页 100 行，共 1 万页；列 a 的基数为 1000 且分布均匀。
- 等值条件的选择率为千分之一，命中约 1000 行。
- 索引约 500 页；每次回表按一次随机页读计，随机读折算为 4 个顺序页。
- 索引路径代价约为 500 加 1000 乘 4，按顺序页折算为 4500，低于全表扫描的 1 万页。
- 若该值属于高频值，实际命中 3000 行，索引路径变为 500 加 12000，高于全表扫描，计划应当翻转。
- 因此需要高频值列表或直方图识别倾斜，只用平均基数会选错访问路径。

### 10.9 如何解读执行计划中的行数估算？

- 估算行数是优化器的判断，实际行数来自运行统计，二者比值反映估算质量。
- 逐算子比较估算与实际，偏差最大的节点通常是问题源头。
- 偏差会向上传播，父节点的偏差可能由子节点引起。
- 过滤比例表示应用条件后剩余行的比例，与估算行数相乘得到输出估算。
- 循环次数影响实际总行数，嵌套循环内侧的行数需要乘以循环次数。
- 估算准确但计划仍慢时，问题在代价权重或硬件差异。

### 10.10（场景）执行计划突然改变导致慢查询，如何排查？

- 确认统计信息是否更新，大批量导入或删除后统计未刷新会导致估算突变。
- 检查绑定变量与参数化查询，参数不同可能选择不同计划。
- 检查索引是否被删除、重建或变为不可用。
- 检查数据分布是否变化，例如新增高频值使原计划失效。
- 对比历史计划，确认变化的是访问路径、连接顺序还是连接算法。
- 稳定手段包括计划基线、提示与统计信息锁定，但需要定期复核。

### 10.11 优化器如何比较连接算法的代价？

- 嵌套循环的代价为外表行数乘以内表单次访问代价，内表有索引时优势明显。
- 哈希连接的代价为两侧扫描加构建哈希的 CPU 开销，内存不足时再加溢出代价。
- 排序归并的代价为两侧扫描加排序开销，输入已有序时最低。
- 选择取决于输入规模、选择率、内存与是否需要有序输出。
- 小表驱动大表是嵌套循环的经验规则，优化器更关注总代价而不是表的大小。
- 并行计划还要计入重分区与广播的代价。

### 10.12 子查询如何优化？

- 相关子查询可以解嵌套为半连接或反连接，避免逐行执行。
- `IN` 与 `EXISTS` 在语义上等价于半连接，优化器通常统一处理。
- `NOT IN` 与空值的交互需要特别处理，子查询返回空值时结果为空。
- 标量子查询需要保证至多返回一行，否则运行时报错。
- 无法解嵌套的子查询会按行执行，代价随外表行数线性增长。
- 物化子查询适合结果被多次引用的场景。

### 10.13 如何保持计划稳定？

- 计划基线保存已接受的计划，优化器生成新计划时与基线比较代价。
- 提示可以强制访问路径、连接顺序或并行度，但会随数据变化失效。
- 固定统计信息与采样率可以降低计划漂移，但会掩盖数据变化。
- 参数化查询可以用参数嗅探或强制参数化，取舍在于计划复用与针对性。
- 版本升级后计划可能变化，需要回归测试覆盖关键查询。
- 监控慢查询日志与计划哈希变化，可以在漂移发生时及时发现。

### 10.14 自适应查询执行解决什么问题？

- 运行时收集实际行数，在物化点重新选择连接算法或连接顺序。
- 解决静态统计无法预知中间结果规模的问题，尤其是多表连接。
- 典型做法是在重分区后按实际分区大小合并小分区、拆分倾斜分区。
- 代价是额外的运行时判断与计划切换开销，短查询收益有限。
- 自适应要求算子支持重新规划，实现复杂度高于静态计划。
- 与计划提示冲突时需要明确优先级。

### 10.15（实现）如何在 C++ 中表示计划节点与代价？

```cpp
struct PlanNode {
    virtual ~PlanNode() = default;
    virtual double startup() const = 0;
    virtual double total() const = 0;
    virtual double rows() const = 0;
    std::vector<std::unique_ptr<PlanNode>> children;
};
```

- 代价分为启动代价与总代价，父节点用子节点的总代价累加。
- 输出行数供上层计算选择率与循环次数。
- 用 `std::unique_ptr` 表达所有权，计划树不可复制，避免悬垂指针。
- 访问者模式遍历计划树，便于实现打印、代价校准与规则匹配。
- 虚函数调用只发生在计划阶段，不影响执行期性能。
- 计划节点构建后不再修改，便于缓存与并发共享。

### 10.16 统计信息如何收集与维护？

- 全量统计扫描整表，准确但代价高，通常在低峰期执行。
- 采样统计按比例读取页或行，误差随采样量下降。
- 增量统计记录每张表的修改行数，超过阈值触发刷新。
- 直方图桶数影响精度与统计表大小，桶数过多会增加规划时间。
- 统计信息需要随数据分布变化更新，否则计划基于过期信息。
- 分布式系统中统计信息还需包含分区级与列级信息。

### 10.17 哪些写法会导致索引失效？

- 在索引列上使用函数或表达式，除非存在对应的函数索引。
- 隐式类型转换使列被转换为另一类型，索引顺序无法使用。
- 前导通配的模糊匹配无法使用普通 B+ 树索引。
- 复合索引未使用最左前缀。
- 用 `OR` 连接不同列时可能退化为全表扫描，除非优化器选择索引合并。
- 排序规则或字符集不一致会导致索引不可用。

### 10.18 排序与 limit 如何下推？

- 排序加 limit 可以用 top-N 堆，内存为 N 而不是全量。
- 排序键与索引顺序一致时可以省略排序，直接扫描并截断。
- limit 可以下推到扫描算子，提前终止读取。
- 聚合之后的 limit 不能下推到聚合之前。
- 并行计划中 limit 下推需要各线程协调终止。
- 下推不能改变空值排序与稳定性语义。

### 10.19 优化器如何做回归测试？

- 用固定数据集与查询集对比计划与结果，检测计划回归。
- 结果正确性用差分测试：同一查询用不同计划执行，比较结果。
- 随机生成查询与数据，覆盖边界条件与统计信息极端值。
- 记录代价估算与实际执行的偏差，作为模型校准的输入。
- 版本升级前对关键查询做计划对比，人工审核变化。
- 测试需要覆盖空表、单行、高倾斜与超长字符串等边界。

### 10.20 代价模型如何校准？

- 采集实际执行的行数、页读取数与耗时，与估算值对比。
- 按算子类型分组统计偏差，识别系统性高估或低估。
- 调整 IO 与 CPU 权重，使模型排序与实测一致。
- 硬件变化，例如固态盘、非统一内存访问与远程存储，需要重新校准。
- 校准数据来自生产采样，需要脱敏并控制开销。
- 学习型优化器用模型替代手工权重，但仍需可解释性与稳定性保障。

## 11. 列存与压缩

### 11.1 列式布局与行式布局的差异体现在哪些层面？

- 行存把一条记录的全部字段连续放置，点查读取一个页即可取回整行；列存把同一列的值连续放置，扫描只读涉及的列，IO 量与投影列数成正比。
- 列存同列类型一致、取值分布集中，字典、RLE、Delta 等编码与块级压缩更容易取得高压缩比；行存跨类型混合，压缩器难以利用列内相关性。
- 列存的点更新要读改写整列块，或写入删除位图与增量区；行存可以原地更新单行。更新密集的负载通常选择行存或行列混存。
- 列存的延迟物化先读谓词列得到选择向量，再按行号回读其他列；选择率高时回读成本可能超过全列扫描。
- 列存按行组或条带切分，统计信息支持整块跳过；行存的跳过能力依赖索引结构与聚簇程度。
- C++ 实现中列存常以连续字节缓冲或 Arrow 的 `Buffer` 持有数据，列与列独立分配，生命周期由 batch 或 arena 统一管理。
- 列存的 CPU 效率来自批量循环与 SIMD；行存的逐行虚函数调用在现代 CPU 上受分支预测与缓存缺失限制。

### 11.2 一次列存扫描要经过哪些阶段？

- 打开文件先读尾部 footer，解析 schema、行组列表与列块偏移，建立投影列到列块的映射。
- 用谓词与行组统计裁剪行组，跳过不可能命中的块，再按页索引裁剪页。
- 按列块读取页，先解压再解码；字典页先加载字典，数据页解析下标。
- 对谓词列求值得到选择向量，按需回读其他列，完成延迟物化。
- 结果组装成 batch 交给上层算子，或直接聚合输出，减少物化开销。
- 每个阶段都有代价：footer 解析、IO、解压、解码、回读；优化前要定位瓶颈阶段。
- 并行扫描按行组或文件切分，汇总时保持顺序或按聚合语义合并。

### 11.3（辨析）Parquet 与 ORC 的布局差异是什么？

- Parquet 文件由行组组成，行组内按列切列块，列块内再分数据页与字典页；footer 保存 schema 与各列块元数据。
- ORC 文件由条带组成，条带内含索引、数据与条带 footer，文件尾部有 file footer 与 postscript；索引默认每 10000 行记录一次位置与统计。
- Parquet 的嵌套结构用定义级别与重复级别表示；ORC 用树形结构描述嵌套，读取时按流展开。
- Parquet 的编码以页为单位选择，ORC 的编码按列流选择；两者都支持字典、RLE 与 Delta 类编码。
- 两者都支持块级压缩与谓词下推；Parquet 的页索引提供页级 min/max 与偏移，ORC 的行组索引提供行组级统计。
- Parquet 在 Spark、Presto 与 Arrow 生态中更常见，ORC 在 Hive 生态中使用较多；格式选择常由引擎支持与历史数据决定。

### 11.4 Parquet 的 footer 与页结构如何支持谓词下推？

- footer 保存 `FileMetaData`，包含 schema、行组列表、每个列块的起始偏移、压缩编码与统计信息。
- 读取时先读文件尾部固定长度的 footer 长度与 magic，再按偏移读 footer，不需要扫描全文件。
- 行组级统计用于裁掉不满足谓词的整组；页索引中的列索引提供页级 min/max，偏移索引提供页起始位置。
- 字典页可用于等值谓词：目标值不在字典中时整个列块可跳过；字典页必须位于数据页之前。
- 下推发生在扫描器与存储层之间，引擎把过滤条件下推到读取器，读取器只解压满足条件的页。
- 字符串统计使用截断的 min/max，截断可能使裁剪失效；写入端排序或聚簇能提高裁剪率。
- 加密与校验会改变页布局，页级裁剪需要先解密或校验，成本由实现决定。

### 11.5 字典编码的适用条件与失效路径是什么？

- 字典编码为列中出现的不同值建立字典，数据页只存字典下标，适合低基数列。
- 下标按位宽紧凑表示，字典本身按 plain 编码存放；基数越低，压缩比越高。
- 基数接近行数时字典页膨胀、下标位宽增大，压缩收益消失，写入端通常回退到 plain 或 Delta 编码。
- Parquet 的字典页位于列块开头，回退后同一列块内不能再使用字典；ORC 可在条带级别切换编码。
- 字典构建需要额外内存与一次哈希表插入，高基数列的写入 CPU 与内存占用上升。
- 字典顺序影响 RLE 与位打包效率，按出现频率重排可缩短常见值的码长。
- 读取端解码需要随机访问字典，字典页常驻内存；字典过大时页缓存压力上升。

### 11.6 RLE 与位图编码各自适合什么数据？

- RLE 把连续相同的值表示为值与游程长度，适合排序后重复度高或长时间不变的列。
- 位图编码为每个不同值维护一个位图，适合基数很低的列，等值过滤可直接按位与。
- Parquet 使用 RLE 与位打包的混合编码：短游程用位打包，长游程用 RLE，兼顾随机与重复分布。
- 布尔列天然适合位图；NULL 的有效位图也按位存储，1 表示有效，0 表示空。
- RLE 的随机访问需要跳表或游程索引，否则定位第 n 个值要线性扫描。
- 位图空间随基数线性增长，基数超过阈值后不如字典编码。
- 编码选择应基于数据分布统计，写入端可采样估算游程长度与基数。

### 11.7 Delta 编码与 FOR 编码如何配合？

- FOR 编码先减去块内最小值，把大整数压到较小位宽，再位打包。
- Delta 编码存储相邻值的差，适合单调递增的列；差值通常比原值小。
- Delta-of-delta 对差值再求差，适合等间隔时间序列。
- PFOR 为少量异常大的值保留例外列表，主体仍按窄位宽打包，避免单个离群值抬高整块位宽。
- 解码需要按块顺序累加，随机访问要先定位块起点并重放块内前缀。
- 这些编码对乱序或高方差数据效果差，写入端排序后收益最大。
- 位宽与块大小影响压缩率与解码并行度，块越小随机访问越好，压缩率越低。

### 11.8（陷阱）列存的压缩率越高越好吗？

- 压缩率与解压速度通常反向：Zstd 高等级与 gzip 压缩比高，但解压 CPU 与延迟上升；LZ4 相反。
- 分析扫描是 IO 与 CPU 的平衡，压缩率过高可能把瓶颈从磁盘转移到解压。
- 块级压缩的块越大，压缩率越高，但随机点查要解压整块，读放大增加。
- 压缩算法影响可分割性：gzip 等流式格式难以从中间解压，块级压缩允许按块并行。
- 高压缩率降低存储与网络成本，冷数据归档可以接受较慢解压；热数据应优先解压速度。
- 选择应基于端到端扫描时间的基准测试，而不是单一压缩比指标。

### 11.9 LZ4 与 Zstd 的取舍是什么？

- LZ4 解压速度可达数 GB/s，压缩率较低，适合热数据与低延迟扫描。
- Zstd 在中等压缩率下解压速度接近 LZ4，高等级压缩率更高但压缩耗时明显上升。
- Zstd 支持字典压缩，小对象或小页可用训练字典降低冷启动开销。
- 两者都支持块级帧格式，可按块独立解压；Zstd 的帧头与校验和增加少量开销。
- 压缩级别是写入端的一次性成本，解压是每次读取的成本，读多写少的场景应偏向解压速度。
- 硬件加速可卸载压缩，但增加部署复杂度，收益由实现与负载决定。

### 11.10 列存中的 NULL 如何表示？

- 独立有效位图是最常见做法，值数组仍按稠密方式存放，空值位置的内容未定义。
- Parquet 用定义级别表示嵌套字段是否出现，空值与缺失字段通过级别区分。
- ORC 用 presence 流与 RLE 结合表示空值，读取时先解 presence 再解值。
- 位图可以与谓词计算融合：比较结果要与有效位图相与，避免把空值当作 0。
- 空值不占值数组空间，但位图本身有开销；空值比例极高时可用稀疏表示或单独存非空行号。
- 聚合函数对空值的语义由 SQL 层决定，存储层只负责还原空值位置。
- C++ 中常把有效位图表示为 `uint64_t` 数组，按位测试，尾部不足 64 位要掩码。

### 11.11 Dremel 的重复级别与定义级别如何编码嵌套结构？

- 定义级别表示路径上有多少可选或重复字段实际出现，用于区分空值与缺失。
- 重复级别表示当前值在哪个重复层级上开始新记录，用于还原列表边界。
- 对嵌套列表，写入端按深度优先展开为扁平的（值，重复级别，定义级别）三元组，读取端按级别重建树。
- 例如 `a.b.c` 全为可选时，定义级别等于实际出现的字段数；重复级别为 0 表示新记录开始。
- 编码后的级别序列用 RLE 或位打包压缩，重复结构越多压缩收益越大。
- 重建需要按 schema 递归，列式读取器通常把级别与值分开存放，按需组装。
- 级别的最大值由 schema 深度决定，位宽固定；schema 演进会增加级别语义的复杂度。

### 11.12（实现）向量化执行如何利用批处理？

- 以 batch（常见 1024 至 4096 行）为单位在算子间传递列向量，减少逐行虚函数调用与分支。
- 算子内部对整列做循环，编译器可自动向量化；选择向量把过滤结果压缩成行号列表。
- 哈希连接与聚合使用批量哈希与探测，避免每行一次函数调用；字符串用 `std::string_view` 或偏移加字节池表示。
- 批大小要适配 L1 与 L2 缓存：过大导致列向量溢出缓存，过小则摊薄循环开销。
- 向量化对随机访问与短字符串仍不友好，需要按列类型特化。
- 与编译执行相比，向量化实现简单、编译开销低，适合交互式查询与多变表达式。

### 11.13 向量化与编译执行（codegen）的取舍是什么？

- 向量化按批解释执行，算子边界清晰，调试与扩展容易，但每批仍有解释开销。
- 编译执行把查询编译为机器码，消除算子边界与虚调用，适合复杂表达式与长管道。
- 编译需要时间与代码缓存，短查询可能被编译开销拖累；LLVM 的优化质量高但编译慢。
- 向量化对 SIMD 友好，编译执行可通过循环融合进一步提高寄存器利用率。
- 两者都受内存带宽限制，数据布局与缓存局部性比执行模型更关键。
- 工程上常见混合方案：表达式编译、算子向量化，按查询代价选择。

### 11.14（场景）列存上的点更新为什么代价高，如何缓解？

- 列存按列块存储，更新一行要读改写多列块，写放大与 IO 次数随列数增加。
- 原地更新还会破坏块的压缩与排序，通常采用删除位图加增量区的追加写。
- 读取时要把增量区与基线合并，合并逻辑增加 CPU，增量区过大时查询变慢。
- 后台合并把增量区重写为新的列块，期间占用 IO 与空间，需要限速与优先级。
- 缓解手段包括行列混存、把更新频繁的列单独存放、按主键聚簇减少随机写。
- 事务型负载通常选择行存或 LSM，列存更适合批量导入与追加。
- C++ 实现中删除位图与增量区要有版本号，读快照不能看到未提交的更新。

### 11.15 列存的统计信息为什么会失效？

- 字符串的 min/max 常按前缀截断，前缀相同的值会使区间过宽，裁剪失效。
- 统计信息在写入时计算，删除与更新后未重写列块，min/max 仍覆盖已删除的值。
- 数据未按过滤列排序，min/max 覆盖整个值域，行组之间大量重叠。
- 类型转换与排序规则不一致，存储层的比较结果与查询层不同，统计信息不可用。
- 空值计数不准确会影响 `IS NULL` 与 `IS NOT NULL` 的裁剪。
- 统计粒度是行组或页，粒度越粗，裁剪的精度越低。
- 写入端跳过统计或采样估算，读取端只能保守处理。

### 11.16（陷阱）列存的行组大小如何影响扫描与点查？

- 行组越大，压缩率与顺序扫描效率越高，元数据开销越小。
- 点查只需一行时仍要读整个行组的页，读放大随行组增大。
- 小行组提高裁剪粒度，但 footer 与统计信息膨胀，打开文件变慢。
- 常见取值在 64 MB 至 512 MB，需结合行宽、列数与查询模式调整。
- 聚簇与排序让 min/max 更紧凑，小行组的裁剪收益才明显。
- 对象存储上的列存还要考虑请求大小与延迟，过小的行组增加请求数。

### 11.17 列存如何利用排序与聚簇提升裁剪率？

- 按过滤频率高的列排序，使 min/max 区间不重叠，行组裁剪更有效。
- 多列聚簇可用 Z-order 或 Hilbert 曲线，兼顾多个维度的局部性。
- 排序本身是重写操作，成本高，通常在写入或合并时完成。
- 排序键选择要看查询的过滤与范围条件，低选择性列排序收益有限。
- 聚簇会改变数据分布，可能引入写入热点，需要与分区策略配合。
- 排序后的列更易压缩，RLE 与 Delta 的游程更长。
- 维护聚簇需要合并小文件，否则新写入的数据破坏全局有序。

### 11.18（实现）SIMD 在列存扫描中的典型模式与边界是什么？

- 典型模式是加载一批值、与常量比较得到掩码、用掩码压缩出选择向量。
- 整数比较与位运算容易向量化，字符串比较需要长度前缀与分块处理。
- 对齐不是必须的，但跨缓存行与非对齐加载会增加微操作；尾部不足一个向量时要掩码处理。
- 压缩域上的计算可避免解压，例如在位图上直接做位与，但通用性差。
- 编译器自动向量化受别名与分支影响，可用 `restrict` 语义的指针或循环拆分辅助。
- SIMD 的收益受内存带宽限制，随机访问与短列会抵消优势。
- 结果要与标量路径逐项比对，边界值、NaN 与空值容易出错。

### 11.19（场景）列存扫描比预期慢，排查路径是什么？

- 先看扫描是否发生裁剪：统计行组读取数、页读取数与解压字节数。
- 检查投影是否下推，是否读取了无关列；宽表常见问题是 `SELECT *`。
- 观察解压 CPU 占比，压缩率过高或块过大可能导致解压成为瓶颈。
- 检查对象存储或磁盘的请求延迟与吞吐，小 IO 与高请求数会拖慢扫描。
- 查看数据是否聚簇，min/max 裁剪率低说明排序键与过滤条件不匹配。
- 检查字典页与页索引是否被缓存，冷缓存下的首次扫描明显更慢。
- 对比不同 batch 大小与并行度，单线程扫描与分区倾斜都会限制吞吐。

### 11.20 列存与向量化在 C++ 中的内存布局如何设计？

- 每列用连续缓冲区加有效位图表示，变长列用偏移数组加字节池，避免每行单独分配。
- batch 持有一个 arena 或 `std::pmr::monotonic_buffer_resource`，所有列缓冲从同一资源分配，析构时整体释放。
- 列缓冲按 64 字节对齐，便于 SIMD 加载；分配器要区分对齐与普通分配。
- 所有权用 `std::unique_ptr` 管理 arena，列视图用 `std::span` 传递，避免复制。
- 跨 batch 复用的缓冲用对象池，池化对象在异常路径上通过 RAII 归还。
- 磁盘格式按固定宽度与显式字节序序列化，禁止直接 `reinterpret_cast` 结构体。
- 读取端用 `std::string_view` 指向页缓冲，页缓冲的生命周期必须覆盖整个 batch 的计算。

```cpp
struct ColumnBatch {
    std::pmr::memory_resource* arena;
    std::span<const std::int32_t> ids;
    std::span<const std::uint64_t> valid;    // 位图，1 表示非空
    std::span<const std::uint32_t> offsets;  // 变长列的偏移
    std::span<const char> bytes;
};
```

## 12. 分布式存储

### 12.1 分片键如何选择？

- 分片键决定数据分布与查询路由，应选择高基数、写入均匀、查询常带的字段。
- 单调递增键在范围分片下形成尾部热点，需要加哈希前缀或预分区。
- 哈希分片打散热点，但范围查询要广播到所有分片；范围分片保留局部性，容易倾斜。
- 复合键可兼顾：前缀哈希打散，后缀保留排序，例如 `hash(user_id)` 加时间戳。
- 分片键一旦确定难以更改，跨分片查询与事务的代价要在设计阶段评估。
- 业务上唯一的自然键未必适合分片，订单号与用户 ID 的选择会影响按用户查询的效率。
- 热点键需要单独拆分或加随机后缀，不能只依赖哈希。

### 12.2 范围分片与哈希分片的取舍是什么？

- 范围分片按 key 区间切分，支持高效范围扫描与有序遍历，元数据记录边界。
- 范围分片在写入集中到某个区间时产生热点，需要动态分裂与迁移。
- 哈希分片按 `hash(key) mod N` 或一致性哈希分布，写入均匀，点查路由直接。
- 哈希分片丢失 key 的局部性，范围查询要并行访问所有分片再归并。
- 范围分片的分裂与合并由大小阈值触发，元数据服务负责边界变更与副本迁移。
- 混合方案先按业务维度分区，再在分区内范围分片，兼顾隔离与扫描。
- 选择取决于查询模式：点查为主选哈希，范围与排序为主选范围。

### 12.3（辨析）一致性哈希与取模哈希的差异是什么？

- 取模哈希在节点数变化时几乎重排所有 key，扩容需要全量迁移。
- 一致性哈希把节点与 key 映射到同一环上，key 归顺时针第一个节点，增删节点只影响相邻区间。
- 一致性哈希的迁移量约为 `K/N`，取模哈希约为 `K`，差距随集群规模放大。
- 基本一致性哈希在节点少时分布不均，需要虚拟节点提升均衡性。
- 取模哈希实现简单、路由无状态，适合节点数固定的场景。
- 一致性哈希的元数据要维护环与虚拟节点，客户端需要感知拓扑变化。
- 两者都不解决热点 key，热点需要业务拆分或副本读。

### 12.4 虚拟节点解决什么问题，引入什么代价？

- 虚拟节点把一个物理节点映射为多个环上位置，降低节点少时的负载方差。
- 虚拟节点数越多，分布越均匀，但路由表与元数据越大，查找与更新开销上升。
- 节点故障时其虚拟节点分摊到多个节点，恢复后的负载回流也更平滑。
- 虚拟节点与副本放置结合时，同一物理节点的虚拟节点不能落在同一故障域。
- 权重不同的机器可通过虚拟节点数量体现容量差异。
- 虚拟节点不能消除热点 key，只能均衡 key 数量，不能均衡访问频率。
- 客户端缓存环信息要处理版本变更，否则会路由到已下线的节点。

### 12.5 副本放置策略要考虑哪些故障域？

- 故障域包括机器、机架、可用区、地域，副本应尽量分散到不相关的域。
- 三副本通常跨三个故障域，quorum 写入需要至少两个域可用。
- 相关故障（共享电源、交换机、冷却）会让名义上独立的副本同时失效，放置策略要按实际拓扑。
- 跨地域复制增加延迟与带宽成本，通常异步复制并接受较小的数据丢失窗口。
- 副本放置还要考虑读流量与网络拓扑，就近读降低延迟。
- 副本数增加提高读吞吐与耐久性，但写入要等更多副本，尾延迟上升。
- 集群扩容或故障后要重新满足放置约束，再平衡过程需要限速。

### 12.6 Quorum 读写如何保证一致性？

- N 个副本，写入需 W 个确认，读取需 R 个响应，`R + W > N` 时读写集合必有交集。
- 交集保证读取至少看到一个包含最新写入的副本，配合版本号或时间戳选择最新值。
- 写入失败时已写入的副本可能留下脏数据，需要回滚或依靠后续读修复。
- 读修复在读取时比较副本版本，把最新值写回落后副本。
- sloppy quorum 在故障时把副本写到临时节点，配合 hinted handoff 在恢复后转交。
- `R + W > N` 只保证读写交集，不保证并发写的顺序，也不保证线性一致。
- 强一致需要额外的定序机制，如领导者、租约或共识协议。

### 12.7（陷阱）读写 quorum 满足 `R + W > N` 能保证强一致吗？

- 不等于。交集只保证读集合与写集合有重叠，读仍可能返回旧值，若写入尚未完成或副本选择不同。
- 并发写没有全序，两个客户端可能各自成功，最后值由冲突解决策略决定。
- 读修复是异步的，读到旧值的客户端在修复完成前仍可能返回旧值。
- 时钟回拨与最后写入胜会丢失更新，无法提供线性一致。
- 线性一致要求读看到最近一次已完成写，且操作按实时顺序排列，需要领导者读或共识。
- Quorum 提供的是可调一致性，适合对可用性优先、能容忍短暂旧读的场景。
- 需要强一致时应使用 Raft 或 Paxos 复制的日志，或让读写都经过领导者并确认租约。

### 12.8 Raft 的选举流程与任期作用是什么？

- 节点状态为 follower、candidate、leader，选举超时后 follower 增加任期转为 candidate。
- candidate 向集群请求投票，获得多数票成为 leader；每个任期最多一个 leader。
- 投票要求候选人的日志至少与投票者一样新：最后日志任期更大，或任期相同但索引不落后。
- 任期是逻辑时钟，用于拒绝过期消息；收到更高任期立即转为 follower。
- 随机化选举超时避免分裂投票，心跳间隔远小于选举超时。
- leader 通过心跳维持权威，follower 在超时内未收到心跳则发起新一轮选举。
- 网络分区少数派无法选出 leader，多数派可以继续服务。

### 12.9 Raft 日志复制如何保证提交安全？

- leader 把客户端命令追加到本地日志，并向 follower 发送 `AppendEntries`。
- follower 校验前一条日志的索引与任期，匹配则追加，不匹配则拒绝，leader 回退重试。
- 当日志被多数副本持久化后，leader 提交该条目并应用到状态机。
- leader 只能直接提交当前任期的条目；旧任期条目通过提交新条目间接提交。
- 日志匹配性质保证相同索引与任期的条目内容相同，且之前的所有条目相同。
- 提交索引之前的条目按顺序应用，状态机必须是确定性的。
- leader 崩溃后，新 leader 一定包含所有已提交条目，未提交条目可能被覆盖。

### 12.10（场景）Raft 集群频繁选举如何定位与处置？

- 检查选举超时与心跳间隔是否过小，网络抖动或 GC 停顿会触发误判。
- 查看磁盘 `fsync` 延迟，日志落盘慢会让 follower 错过心跳，表现为反复选举。
- 检查网络分区与丢包，跨可用区的 RTT 抖动会放大超时。
- 启用 pre-vote 防止分区节点带着更高任期回归时打断集群。
- 检查快照传输与日志追赶是否占满带宽，落后节点拖慢心跳处理。
- 调整心跳与选举超时要有足够余量，通常选举超时为心跳的 10 倍以上。
- 观察 leader 变更日志与任期增长曲线，定位是单节点还是全局抖动。

### 12.11 Raft 成员变更为什么需要联合共识或单步变更？

- 直接从旧配置切到新配置会出现两个不相交的多数派，可能同时选出两个 leader。
- 联合共识先进入 `C_old,new`，需要同时获得旧配置与新配置的多数票，再切到新配置。
- 单步变更一次只增加或删除一个节点，任意两个多数派必然相交，安全性容易保证。
- 单步变更实现简单，但一次只变一个节点，扩容大集群耗时长。
- 变更期间 leader 可能被移除，需要先移交领导权再删除自身。
- 成员变更要走日志复制，配置条目提交后才生效，不能只改本地配置。
- 学习者先同步日志再加入投票集合，避免新节点拖慢提交。

### 12.12 日志压缩与快照的边界是什么？

- 日志无限增长会占满磁盘并拖慢重启回放，需要生成快照并截断旧日志。
- 快照包含状态机在某个索引处的完整状态，以及该索引与任期。
- follower 落后太多、所需日志已被截断时，leader 发送 `InstallSnapshot`。
- 快照传输要分块并限速，避免占用复制带宽；接收端先写临时文件再原子替换。
- 快照期间的写入继续追加日志，快照完成后只需回放快照点之后的日志。
- 快照频率影响恢复时间与存储开销，频率过高增加 IO，过低增加回放时间。
- 快照与日志的索引必须一致，否则恢复会重复应用或漏应用。

### 12.13（实现）线性一致读有哪些实现方式？

- 所有读写都走 leader，leader 在任期内处理并等待多数心跳确认，即 ReadIndex。
- ReadIndex 记录当前提交索引，等待状态机应用到该索引后再读，避免读到落后状态。
- 租约读依赖 leader 租约在时钟误差范围内有效，读不经过网络确认，延迟低但受时钟假设约束。
- follower 读可通过向 leader 请求 ReadIndex 并等待本地应用进度，分担读流量。
- 读请求不能绕过日志顺序，否则可能读到未提交或旧状态。
- 时钟回拨、GC 停顿与网络分区会破坏租约假设，需要保守的租约时长。
- 强一致读的代价是额外往返或等待，读多写少的系统常用 follower 读加版本校验。

```cpp
bool wait_applied(std::uint64_t read_index) {
    std::unique_lock lock(mu_);
    cv_.wait(lock, [&] { return applied_index_ >= read_index; });
    return !stopped_;
}
```

### 12.14 再平衡如何避免抖动？

- 设置迁移阈值与滞回区间，负载差异超过上限才触发，低于下限才停止。
- 限制并发迁移数与带宽，按优先级迁移最热或最冷的分片。
- 迁移期间源节点继续服务，目标节点追日志或复制数据，切换用短事务完成。
- 避免同时迁移互为副本的分片，防止可用性下降。
- 监控迁移进度与失败重试，失败的分片要回滚而不是无限重试。
- 再平衡要考虑机架与可用区约束，不能只按负载均衡。
- 扩容时先加入空节点并预热，再逐步迁移，避免新节点被瞬时压垮。

### 12.15（场景）扩容后热点没有迁移，如何排查？

- 检查分片键分布，热点可能集中在少数 key，扩容无法拆分单个分片。
- 查看分片大小与请求量指标，确认是数据量倾斜还是访问量倾斜。
- 检查再平衡是否被阈值或限速阻塞，迁移队列是否长时间未推进。
- 确认新节点是否加入拓扑并被客户端感知，路由缓存是否过期。
- 热点 key 需要业务拆分（加后缀、分桶）或副本读，不能只靠迁移。
- 检查副本放置是否把新节点放在同一故障域，导致无法承接流量。
- 观察迁移后的负载曲线，若热点跟随分片移动，说明是 key 级热点而非节点级。

### 12.16 两阶段提交与 Raft 复制的关系是什么？

- 2PC 解决跨多个参与者的原子提交，协调者先询问再决定提交或回滚。
- Raft 解决单个复制组的日志一致性，保证多数副本按相同顺序应用命令。
- 2PC 的协调者崩溃会导致参与者阻塞，直到协调者恢复或超时裁决。
- 把 2PC 的协调者状态用 Raft 复制，可以提高协调者可用性，但不消除阻塞窗口。
- Raft 复制的是日志，不提供跨分片原子性；跨分片事务仍需 2PC 或等价协议。
- Percolator 用 2PC 加时间戳服务与 MVCC，把锁与提交记录写入分布式 KV。
- 2PC 的性能代价是多次往返与持久化，跨分片事务应尽量少。

### 12.17（辨析）强一致、线性一致与顺序一致的区别是什么？

- 线性一致要求每个操作在其调用与返回之间的某个实时点生效，且所有客户端看到同一顺序。
- 顺序一致要求所有操作存在一个全序，且每个客户端的操作按程序顺序出现，但不要求与实时时间对齐。
- 强一致是泛称，常指线性一致或严格可串行化，需结合上下文。
- 线性一致是单对象属性，严格可串行化把线性一致与可串行化事务结合。
- 最终一致只保证无更新时副本最终收敛，读可能返回旧值。
- 顺序一致允许读到旧值，只要所有客户端同意的顺序一致。
- 分布式存储常以线性一致作为强一致的目标，代价是延迟与可用性。

### 12.18 跨分片事务有哪些实现路径？

- 2PC：协调者统一提交，强一致但阻塞且往返多，适合低并发跨分片写。
- Saga：把事务拆成局部事务与补偿操作，最终一致，补偿需要幂等。
- Calvin：先确定全局顺序再执行，避免冲突检测，适合高冲突、可预知读写集的负载。
- Percolator：基于时间戳与 2PC，锁与数据同存，适合大规模 OLTP。
- 分布式快照隔离：用全局时间戳与 MVCC 提供快照，提交时检测写写冲突。
- 单分片事务优先：通过分片键设计让大部分事务落在单分片，减少跨分片。
- 跨分片事务的隔离级别与失败语义要在协议层明确，补偿不能替代原子性。

### 12.19（陷阱）副本数越多可用性越高吗？

- 副本数增加提高读吞吐与耐久性，但写入需要更多确认，尾延迟上升。
- 多数派 quorum 下，副本数增加使写 quorum 变大，单节点慢会拖累整体。
- 跨故障域副本增加网络成本，同步复制受最慢副本影响。
- 副本过多会放大写放大与存储成本，再平衡与修复时间变长。
- 相关故障会让多个副本同时失效，副本数不等于有效冗余。
- 可用性还取决于故障检测与选主速度，副本多但选主慢仍会中断。
- 需要按 RPO、RTO 与成本选择副本数，常见三副本是耐久性与成本的折中。

### 12.20 故障检测如何设计？

- 心跳加超时是最简单的检测，超时阈值要在误判与检测延迟之间取舍。
- Phi accrual 用心跳间隔的分布计算怀疑度，输出连续值而非布尔值。
- 检测器应区分慢节点与死节点，慢节点继续服务但可能拖慢 quorum。
- 非对称分区下，A 认为 B 死亡而 B 仍能服务，检测结果不能作为唯一裁决。
- 检测结果用于触发选主或副本迁移，必须与共识协议结合，避免双主。
- 心跳要走独立通道或低优先级队列，避免被业务流量挤占。
- 监控检测器的误判率与恢复时间，阈值应随网络环境调整。

## 13. 缓存系统

### 13.1 Redis 的 SDS 与 C 字符串相比解决了什么问题？

- SDS 在字符数组前保存 `len` 与 `alloc`，取长度为 O(1)，C 字符串需要 `strlen` 遍历。
- 追加操作按预分配策略扩容，减少频繁 `realloc`；惰性释放保留空间，后续追加可直接复用。
- SDS 二进制安全，长度由 `len` 决定，可以存放 `\0`；C 字符串以 `\0` 结尾，无法表示任意字节。
- 头部有 `sdshdr5`、`sdshdr8`、`sdshdr16`、`sdshdr32`、`sdshdr64` 等变体，按长度选择以节省内存。
- SDS 仍以 `\0` 结尾，兼容需要 C 字符串的 API，但长度判断不依赖它。
- 扩容策略在小于 1 MB 时翻倍，超过后每次增加 1 MB，具体阈值由实现定义。
- 缓冲区生命周期由 Redis 对象管理，复制时按 `len` 分配，不依赖结尾符。

### 13.2 字典的渐进式 rehash 如何工作？

- 字典维护两张哈希表 `ht[0]` 与 `ht[1]`，rehash 时把 `ht[0]` 的桶逐步迁移到 `ht[1]`。
- `rehashidx` 记录当前迁移到的桶，增删改查操作顺带迁移一个桶，把一次性开销摊到多次操作。
- 迁移期间查找先查 `ht[0]` 再查 `ht[1]`，插入只写 `ht[1]`，保证不丢数据。
- 迁移完成后释放旧表，`ht[1]` 转为 `ht[0]`，`rehashidx` 置为 -1。
- 负载因子超过阈值触发扩容，低于阈值触发缩容；是否触发由 `dict_can_resize` 与持久化状态影响。
- 渐进式 rehash 避免单次操作长时间阻塞，适合单线程命令执行模型。
- 迁移期间迭代器要同时遍历两张表，否则会漏掉元素。

### 13.3 ziplist、listpack 与 quicklist 的取舍是什么？

- ziplist 是连续内存的紧凑列表，每个元素保存前一个元素的长度，插入删除可能触发级联更新。
- listpack 用变长编码保存元素与自身长度，避免记录前驱长度，消除了级联更新。
- quicklist 是链表加 listpack 节点的组合，兼顾插入性能与内存局部性。
- 小列表用 listpack 节省指针开销，元素增多后转为哈希表或跳表。
- 转换阈值由配置决定，例如 `list-max-listpack-size` 与 `hash-max-listpack-entries`。
- 紧凑编码的随机访问是 O(n)，大列表的范围操作应使用合适的数据结构。
- 编码转换是一次性重写，转换后内存占用上升但操作复杂度下降。

### 13.4 跳表与平衡树的取舍是什么？

- 跳表用多层链表实现平均 O(log n) 查找，范围遍历只需沿底层链表前进。
- 平衡树（红黑树、AVL）最坏 O(log n)，但范围查询需要中序遍历与父指针。
- 跳表实现简单，插入删除只需调整局部指针，不需要旋转。
- 跳表的内存开销来自多层指针，平均每元素约 1.33 个指针（p=0.25 时）。
- 并发场景下跳表的局部修改更容易做无锁或细粒度锁，平衡树的旋转影响面大。
- Redis 的 ZSET 同时用字典与跳表，字典提供 O(1) 分值查询，跳表提供范围与排名。
- 选择取决于是否需要稳定最坏复杂度、范围扫描频率与内存预算。

### 13.5（陷阱）Redis 单线程模型是否意味着没有并发问题？

- 命令执行是单线程的，单条命令原子，但多条命令组合不是原子的，需要事务或 Lua。
- Redis 6.0 起 I/O 多线程负责读写与协议解析，命令执行仍在主线程。
- 后台线程执行 `UNLINK`、`fsync`、关闭文件等耗时操作，与主线程共享数据结构时要避免竞争。
- 主从复制与集群故障转移存在异步窗口，客户端可能读到旧值或写入被回滚。
- Lua 脚本在执行期间阻塞其他命令，脚本过长会导致延迟尖峰。
- 模块可以创建自己的线程，访问共享数据需要显式同步。
- 并发问题更多来自客户端的多命令竞态与分布式锁失效，不是单条命令的数据竞争。

### 13.6 过期删除与内存淘汰的区别是什么？

- 过期删除针对设置了 TTL 的键，到达时间后删除；淘汰在 `maxmemory` 达到上限时按策略移除键。
- 惰性删除在访问键时检查过期，主动删除周期性采样并删除过期键。
- 主动删除的频率自适应，过期键比例高时提高采样频率。
- 淘汰策略包括 `noeviction`、`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`volatile-ttl` 等。
- `volatile-*` 只淘汰设置了过期时间的键，可能在没有可淘汰键时返回错误。
- 过期键仍占用内存，直到被删除；大量键同时过期会造成内存峰值与延迟抖动。
- 从库不独立删除过期键，删除由主库的 `DEL` 驱动；从库读取时会过滤已过期键，具体行为取决于版本。

### 13.7 LRU、LFU 与近似实现的差异是什么？

- 精确 LRU 需要维护访问顺序链表，每次访问移动节点，内存与锁开销大。
- Redis 的 LRU 是近似实现，随机采样若干键，选择空闲时间最长的淘汰。
- LFU 记录访问频率，适合抵御偶发扫描导致的缓存污染；计数器有衰减，避免历史热点永久占据。
- Redis 的 LFU 用 8 位计数器与概率递增，`lfu-log-factor` 控制增长速度，`lfu-decay-time` 控制衰减。
- LRU 对突发流量不友好，扫描大量冷键会把热键挤出；LFU 对频率变化响应慢。
- 采样数 `maxmemory-samples` 越大越接近精确策略，CPU 开销也越高。
- 选择策略要结合访问分布，点查为主且热点稳定时 LFU 更稳，访问模式频繁变化时 LRU 更简单。

### 13.8（场景）缓存雪崩、穿透与击穿分别如何处置？

- 雪崩是大量键同时过期或缓存整体失效，请求直接打到数据库；用 TTL 随机抖动、分批预热与多级缓存缓解。
- 穿透是查询不存在的数据，缓存不命中且数据库也没有；用空值缓存、布隆过滤器与参数校验拦截。
- 击穿是单个热点键过期，大量并发请求同时回源；用互斥锁或 singleflight 保证只有一个请求加载。
- 逻辑过期把过期时间放在值内部，后台异步刷新，读取方先返回旧值。
- 熔断与限流在下游故障时保护数据库，降级返回默认值或静态数据。
- 缓存预热在发布前加载热点，避免冷启动时集中回源。
- 监控命中率、回源 QPS 与数据库连接数，区分三类问题的实际表现。

```cpp
std::chrono::seconds ttl_with_jitter(std::chrono::seconds base) {
    thread_local std::mt19937 rng{std::random_device{}()};
    std::uniform_int_distribution<int> delta(0, 300);
    return base + std::chrono::seconds(delta(rng));
}
```

### 13.9 缓存与数据库的一致性如何保证？

- 常用 cache-aside：读先查缓存，未命中查数据库并回填；写先更新数据库，再删除缓存。
- 删除缓存而不是更新缓存，避免并发写导致旧值覆盖新值。
- 更新数据库与删除缓存之间仍有窗口，读请求可能把旧值回填；延迟双删可缩短窗口但不能消除。
- 订阅数据库变更日志异步失效缓存，能把一致性窗口收敛到秒级。
- 强一致需要把缓存纳入事务或使用读写锁，代价是吞吐与复杂度。
- 缓存失效失败要有重试与补偿，否则脏数据会一直存在到 TTL 到期。
- 业务上可接受最终一致时，应明确窗口上限与降级策略。

### 13.10（辨析）先更新数据库再删缓存与先删缓存再更新数据库的差异是什么？

- 先更新数据库再删缓存：并发读可能在删除后读到旧库值并回填，窗口较短。
- 先删缓存再更新数据库：删除后、更新前的读会回填旧值，窗口更长且更易发生。
- 先删缓存再更新数据库若更新失败，缓存已空，后续读回填旧值，需要补偿。
- 延迟双删在更新后延迟一段时间再删一次，覆盖大部分并发回填，但延迟时间难以精确。
- 更新缓存而非删除，在并发写下可能写入旧值，且每次写都要计算缓存内容。
- 使用版本号或 CAS 回填，只有版本不低于缓存时才写入，可从根上避免旧值覆盖。
- 选择取决于读写比例与一致性要求，读多写少时删除缓存的收益更明显。

### 13.11 RDB 与 AOF 的持久化取舍是什么？

- RDB 是某一时刻的快照，文件紧凑、恢复快，但两次快照之间的数据会丢失。
- `BGSAVE` 通过 `fork` 创建子进程，利用写时复制减少内存复制，写入量大时 COW 会放大内存占用。
- AOF 追加写命令，`appendfsync` 可取 `always`、`everysec`、`no`，在持久性与延迟之间取舍。
- `everysec` 每秒刷盘，故障时最多丢失约 1 秒数据；`always` 每条命令刷盘，延迟显著上升。
- AOF 重写通过子进程生成紧凑日志，重写期间的新命令写入重写缓冲区。
- 混合持久化把 RDB 快照与增量 AOF 结合，兼顾恢复速度与丢失窗口。
- 持久化不能替代副本，磁盘损坏与误删需要备份与跨机房复制。

### 13.12（实现）AOF `everysec` 的丢失窗口与阻塞点在哪里？

- 主线程把命令追加到 AOF 缓冲区，后台线程每秒执行一次 `fsync`。
- `fsync` 由后台线程执行，主线程通常不阻塞；但磁盘慢时后台线程积压，缓冲区增长。
- 若上次 `fsync` 未完成，主线程可能被阻塞等待，`aof_fsync` 延迟会反映在命令延迟上。
- 故障时未刷盘的命令丢失，窗口约 1 秒，具体取决于刷盘进度与磁盘缓存。
- `always` 在主线程刷盘，延迟受磁盘 IOPS 限制，不适合高写入负载。
- `no` 交给操作系统回写，丢失窗口不可控，只在可容忍丢失时使用。
- 监控 `aof_delayed_fsync` 与磁盘延迟，能定位刷盘阻塞。

### 13.13 Redis Cluster 的槽位与重定向如何工作？

- 集群把键空间划分为 16384 个槽，键通过 `CRC16(key) mod 16384` 映射到槽。
- 每个主节点负责一部分槽，槽的归属由集群配置纪元与 gossip 传播。
- 客户端访问错误节点时返回 `MOVED`，表示槽已永久迁移，客户端应更新路由表。
- 迁移过程中返回 `ASK`，表示键已迁移到目标节点但槽尚未正式转移，客户端需先发 `ASKING`。
- 集群总线使用独立端口（默认客户端端口加 10000），节点间交换拓扑与故障信息。
- 故障转移需要主节点多数派同意，少数派分区无法完成选主。
- 多键命令要求所有键在同一槽，可用哈希标签 `{user}` 强制同槽。

### 13.14（场景）热 key 与大 key 如何定位与治理？

- 热 key 表现为单节点 CPU 或网络带宽飙升，`redis-cli --hotkeys` 依赖 LFU 统计。
- `MONITOR` 能看实时命令但开销大，只适合短时间排查；`SLOWLOG` 记录慢命令。
- 大 key 用 `MEMORY USAGE`、`--bigkeys` 与 RDB 分析工具定位。
- 热 key 治理包括本地缓存、读写分离、按后缀拆分为多个子键。
- 大 key 治理包括拆分 Hash、List、ZSet，避免单次 `DEL` 阻塞，使用 `UNLINK` 异步释放。
- 大 key 的删除与过期会阻塞主线程，应在低峰期分批处理。
- 代理层或客户端 SDK 可做热点探测与自动拆分，但要处理聚合与一致性。

### 13.15 分布式锁的实现与失效路径是什么？

- 加锁用 `SET key token NX PX ttl`，一条命令完成互斥与过期，避免 `SETNX` 与 `EXPIRE` 之间的崩溃窗口。
- 释放锁用 Lua 比较 token 后删除，防止误删其他客户端持有的锁。
- 锁过期而业务未完成时，其他客户端会获得锁，需要看门狗续期或 fencing token。
- 主从异步复制下，主节点加锁成功后故障切换，从节点可能没有锁记录，导致双持有。
- Redlock 依赖多个独立节点与时钟假设，网络延迟与时钟回拨会破坏安全性。
- fencing token 由单调递增的令牌服务发放，下游拒绝旧令牌的写，能防止过期锁的写冲突。
- 锁的粒度与持有时间要尽量小，长事务应拆分或改用乐观并发控制。

### 13.16（陷阱）`SETNX` 加 `EXPIRE` 为什么必须原子？

- 两条命令之间客户端崩溃或网络中断，键会永久存在，锁无法释放。
- `SETNX` 成功但 `EXPIRE` 失败时，锁没有过期时间，其他客户端永久阻塞。
- 用 `SET key value NX PX ttl` 把互斥与过期合并为一条命令，消除窗口。
- Lua 脚本也能保证原子，但要注意脚本执行时间与集群槽位。
- 即使原子加锁，业务执行超过 TTL 仍会失效，需要续期或 fencing。
- 过期时间应大于业务最长执行时间，并留出时钟与网络余量。
- 监控锁的等待时间与过期次数，能发现 TTL 设置不合理。

### 13.17 缓存预热与降级如何设计？

- 预热在流量进入前加载热点数据，按访问日志或离线统计生成键列表。
- 预热要限速并分批，避免瞬间打满数据库与缓存节点。
- 降级在缓存或下游故障时返回默认值、旧值或静态页面，保证核心链路可用。
- 熔断器统计错误率与延迟，超过阈值后快速失败，避免雪崩扩散。
- 降级开关应支持按接口、按租户灰度，并有自动恢复条件。
- 缓存不可用时要有本地缓存兜底，容量与 TTL 按业务容忍度设置。
- 预热与降级的指标要纳入监控，验证命中率与错误率的变化。

### 13.18（实现）本地缓存与分布式缓存的多级结构如何设计？

- L1 本地缓存（如 Caffeine）访问延迟低，容量受进程内存限制；L2 用 Redis 共享。
- 读路径先查 L1，再查 L2，最后回源，回填时按层级设置不同 TTL。
- 写路径更新数据库后失效 L2，再通过消息或 binlog 通知各节点失效 L1。
- 本地缓存的一致性窗口由失效消息延迟决定，TTL 作为兜底。
- 热点 key 放 L1 能显著降低 Redis 带宽，但要防止本地缓存被大 key 撑爆。
- 缓存击穿在 L1 与 L2 都可能发生，singleflight 要覆盖整个回源链路。
- 多级缓存的命中率与回源率要分层统计，定位是哪一层失效。

### 13.19（场景）缓存命中率突然下降，如何排查？

- 先看请求分布是否变化，新上线功能可能带来大量冷 key。
- 检查缓存节点是否发生故障转移或扩容，槽迁移会导致短暂未命中。
- 查看淘汰策略与内存使用，达到 `maxmemory` 后大量键被淘汰。
- 检查 TTL 设置与批量过期，集中过期会造成命中率骤降。
- 对比键的版本或序列化格式是否变化，格式变更会让旧缓存全部失效。
- 查看是否有大 key 或热 key 打满带宽，导致其他请求超时并回源。
- 统计各层命中率与回源 QPS，区分本地缓存、分布式缓存与数据库的压力。

### 13.20 缓存容量与命中率如何估算？

- 先估算工作集，即活跃访问覆盖的数据量，而不是全量数据。
- 用访问日志画命中率随容量变化的曲线，边际收益递减点即合理容量。
- LRU 的栈距离可估算不同容量下的命中率。
- 预留内存给副本、过期键与碎片，实际可用容量低于 `maxmemory`。
- 命中率提升带来的回源减少要换算成数据库 QPS 与延迟收益。
- 容量规划要考虑增长与突发，按峰值流量与热点集中度留余量。
- 成本上比较内存单价与回源成本，避免为低收益的长尾 key 付高额内存。

## 14. 对象存储与消息队列

### 14.1 S3 的对象模型与一致性语义是什么？

- 对象由 bucket、key 与 value 组成，key 是扁平命名空间中的字符串，没有目录层级。
- 读写按整个对象进行，不支持原地修改部分字节，更新要重写整个对象。
- S3 自 2020 年起对新建与覆盖写提供强一致读，列表操作也强一致；此前是最终一致。
- 强一致指写入成功后立即读到新值，不保证跨区域复制后的读。
- 对象大小上限 5 TB，单次 `PUT` 上限 5 GB，更大对象用分段上传。
- 版本控制开启后，覆盖写生成新版本，删除插入删除标记，旧版本仍可恢复。
- 元数据与数据一起存储，用户元数据有大小限制，系统元数据由服务维护。

### 14.2（辨析）S3 的 PUT 与分段上传的差异是什么？

- 单次 `PUT` 适合小对象，一次请求完成，失败重试要重传整个对象。
- 分段上传把对象切成多个 part，分别上传，最后 `CompleteMultipartUpload` 合并。
- 分段上传支持并行与断点续传，单 part 最小 5 MiB（最后一段除外），最多 10000 段。
- 分段上传在完成前不可见，未完成的段占用存储，需要生命周期规则清理。
- 分段上传的 ETag 不是整个对象的 MD5，而是各段 MD5 拼接后的摘要加段数后缀。
- 分段上传适合大文件与不稳定网络，小文件用 `PUT` 更简单。
- 完成操作是原子的，失败时可重试或放弃并清理已上传段。

### 14.3 S3 的预签名 URL 与权限边界是什么？

- 预签名 URL 把签名信息放在查询参数中，持有者在有效期内可执行指定操作。
- 签名基于 SigV4，包含访问密钥、区域、服务、过期时间与请求方法。
- URL 泄露等于临时授权，有效期应尽量短，并限制到具体对象与操作。
- 使用长期密钥签发的 URL 最长 7 天，临时凭证受会话有效期限制。
- 撤销预签名 URL 不能单独操作，只能轮换密钥、修改桶策略或删除对象。
- 预签名 URL 不经过应用服务器，带宽与鉴权由对象存储承担。
- 签名对请求头与查询参数敏感，代理或 CDN 改写参数会导致签名失效。

### 14.4（陷阱）S3 的 ETag 是否等于对象内容的 MD5？

- 单次 `PUT` 且未加密时，ETag 通常是内容的 MD5，但这只是常见实现，不是协议保证。
- 分段上传的 ETag 由各段 MD5 拼接后再取 MD5，并附加段数后缀，与整体 MD5 不同。
- 服务端加密（SSE-KMS、SSE-C）会改变 ETag 的计算方式，不能当作内容摘要。
- 部分实现或网关可能返回非 MD5 的 ETag，依赖它做完整性校验不可靠。
- 完整性校验应使用 `x-amz-checksum-*` 或客户端计算并保存的哈希。
- ETag 可用于条件请求（`If-Match`）做乐观并发控制，语义是对象版本标识。
- 把 ETag 当内容哈希做去重，会在分段上传与加密场景下出错。

### 14.5 对象存储为什么不适合直接做数据库？

- 对象存储按整对象读写，没有原地更新与追加，随机小写要重写整个对象。
- 延迟在毫秒到数十毫秒，远高于本地 SSD，且按请求计费。
- 列表操作与重命名代价高，目录语义需要应用层维护。
- 没有跨对象的原子事务，多对象更新需要额外协议。
- 适合大块顺序读写、备份、数据湖与静态资源，不适合高并发小事务。
- 可以在对象存储上构建数据库（如 Iceberg、Delta Lake），但需要日志、清单与提交协议。
- 缓存与本地日志常作为对象存储的前置层，吸收随机写。

### 14.6 S3 的强一致对数据湖意味着什么？

- 写入成功后立即可读，简化了数据湖的提交后读校验。
- 列表强一致使分区发现与清单重建不会漏掉刚写入的对象。
- 覆盖写立即生效，旧的读取方可能仍持有已打开的文件句柄，读到旧内容取决于缓存。
- 跨区域复制是异步的，目标区域的读仍是最终一致。
- 强一致不提供多对象原子性，数据湖仍需快照或清单来定义提交点。
- 并发写同一 key 仍可能互相覆盖，需要条件写或唯一命名。
- 依赖最终一致的旧版重试逻辑可以简化，但缓存层仍可能返回旧数据。

### 14.7 Kafka 的分区与顺序保证是什么？

- 主题分为多个分区，分区内按追加顺序有序，分区之间没有全局顺序。
- 生产者指定 key 时按 key 哈希选分区，相同 key 的消息进入同一分区，保证局部顺序。
- 消费者组内每个分区只由一个消费者处理，消费顺序与日志顺序一致。
- 增加分区会改变 key 到分区的映射，可能破坏既有 key 的顺序。
- 未开启幂等时，重试与多个在途请求可能改变分区内的写入顺序。
- 开启幂等生产者后，`max.in.flight.requests.per.connection` 不超过 5 仍可保持顺序。
- 全局顺序需要单分区，吞吐受限；多数场景只需 key 级顺序。
- 分区数是并行度的上限，消费者数超过分区数时会有空闲。

### 14.8 Kafka 的日志段与索引结构是什么？

- 每个分区对应一个目录，日志按段切分，段文件名为起始偏移量。
- 段内有 `.log` 数据文件、`.index` 偏移索引与 `.timeindex` 时间索引。
- 偏移索引是稀疏索引，每写入一定字节记录一条，查找时先二分定位再顺序扫描。
- 时间索引按时间戳查找偏移，用于按时间消费或重置位点。
- 日志段滚动由大小或时间触发，旧段按保留策略删除或压缩。
- 索引文件通过内存映射读取，减少随机 IO。
- 段文件名与内部偏移共同定位消息，消费者提交的是下一条要读的偏移。

### 14.9 Kafka 的页缓存与刷盘策略如何影响持久性？

- Kafka 写入先进入操作系统页缓存，再按配置刷盘，不保证每条消息立即落盘。
- `log.flush.interval.messages` 与 `log.flush.interval.ms` 控制刷盘频率，默认依赖操作系统回写。
- 持久性主要靠副本：`acks=all` 且 `min.insync.replicas` 满足时，消息写入多个副本的页缓存。
- 机器掉电会丢失页缓存中未刷盘的数据，但副本仍可恢复；所有副本同时掉电才可能丢数据。
- 页缓存让 Kafka 的写入接近内存速度，读命中页缓存时不需要磁盘 IO。
- 刷盘频率过高会降低吞吐，过低会扩大单机丢失窗口。
- 文件系统与磁盘写缓存的行为由实现与配置决定，禁用写缓存可提高持久性但降低性能。

### 14.10 Kafka 的 ISR 与 acks 如何影响持久性？

- ISR 是与 leader 保持同步的副本集合，落后超过 `replica.lag.time.max.ms` 的副本被移出。
- `acks=0` 不等待确认，吞吐最高，可能丢失；`acks=1` 等待 leader 写入，leader 故障可能丢失。
- `acks=all` 等待 ISR 中所有副本确认，配合 `min.insync.replicas` 保证至少若干副本有数据。
- `min.insync.replicas` 大于 1 时，可用副本不足会拒绝写入，保护持久性但降低可用性。
- 高水位是已提交消息的边界，消费者只能读到高水位之前的消息。
- leader 选举默认从 ISR 中选，开启 unclean 选举可能选到落后副本，导致数据丢失。
- leader epoch 用于处理副本截断与恢复，避免旧 leader 的数据覆盖新 leader。

### 14.11（场景）消费者重复消费的根因与处置是什么？

- 消费者处理完消息后、提交偏移前崩溃，重启后从上次提交位置重读。
- 再均衡导致分区转移，未提交的偏移由新消费者重新处理。
- 处理超时触发再均衡，`max.poll.interval.ms` 过小会频繁踢出消费者。
- 提交失败或异步提交未完成就继续处理，偏移与实际进度不一致。
- 处置手段是让消费逻辑幂等：唯一键去重、状态机条件更新、写下游时带幂等键。
- 用事务或恰好一次语义可减少重复，但外部副作用仍需幂等。
- 监控消费延迟与重复率，区分重复来自提交策略还是下游重试。

### 14.12 至少一次、至多一次与恰好一次的区别是什么？

- 至多一次：先提交偏移再处理，故障时可能丢消息，不重复。
- 至少一次：先处理再提交，故障时可能重复，不丢失。
- 恰好一次：处理与偏移提交在同一事务中，或下游幂等，保证不重不漏。
- Kafka 的幂等生产者用 PID 与序列号去重，解决生产者重试导致的重复。
- Kafka 事务把多个分区的写入与偏移提交原子化，消费者设置 `isolation.level=read_committed`。
- 恰好一次只在 Kafka 内部链路成立，写外部数据库仍需事务或幂等键。
- 语义选择取决于业务对丢失与重复的容忍度，多数系统选择至少一次加幂等。

### 14.13 Kafka 事务如何实现原子写与读隔离？

- 生产者配置 `transactional.id`，协调器分配 PID 与 epoch，防止旧生产者继续写。
- 事务开始时向协调器注册分区，写入的消息带上事务标记。
- 提交时协调器写事务标记（commit marker），消费者只读到标记之前的消息。
- `read_committed` 消费者过滤未提交消息，LSO 之前的消息才可见。
- 中止事务写 abort marker，消费者跳过该事务的消息。
- 事务超时或生产者崩溃后，协调器中止未完成事务，避免悬挂。
- 事务保证跨分区原子写，但不覆盖外部系统的副作用。

### 14.14（陷阱）幂等生产者能保证端到端恰好一次吗？

- 幂等生产者只保证单个 PID、单个分区内的去重，PID 变化或会话重启后状态失效。
- 生产者崩溃后重新初始化可能获得新 PID，未确认的消息重发时无法去重。
- 消费者仍可能重复处理，偏移提交与业务处理不在同一事务时无法保证。
- 端到端恰好一次需要生产、存储、消费与外部副作用都支持幂等或事务。
- 外部数据库写入要用唯一键或事务表，不能只依赖消息去重。
- 事务消息加 `read_committed` 能覆盖 Kafka 内部链路，跨系统仍需 outbox 或幂等键。
- 宣称恰好一次时要明确边界：哪个链路、哪个存储、哪种失败模型。

### 14.15 消息积压如何定位与扩容？

- 先看消费者 lag 与分区分布，确认是全局积压还是少数分区。
- 检查消费者处理耗时、下游依赖与线程池，瓶颈可能不在 Kafka。
- 增加消费者实例受分区数限制，超过分区数的实例空闲。
- 扩容分区能提高并行度，但会改变 key 映射与顺序保证。
- 优化消费逻辑：批量处理、异步 IO、减少锁竞争与日志。
- 检查再均衡频率与 `max.poll.records`，频繁再均衡会降低吞吐。
- 临时方案可把消息转存到临时主题或降级非核心处理，先恢复延迟。

### 14.16 Kafka 的日志清理（delete 与 compact）差异是什么？

- `delete` 按时间或大小删除整个日志段，适合事件流与短期保留。
- `compact` 按 key 保留每个 key 的最新值，适合变更日志与状态恢复。
- 压缩不会删除所有旧段，而是重写段并保留最新记录，墓碑标记删除。
- 墓碑在 `delete.retention.ms` 后清理，消费者需要在这之前读到删除语义。
- 压缩的延迟由 `min.cleanable.dirty.ratio` 与后台线程决定，不是即时生效。
- 压缩保留 offset，消息的 offset 不连续，消费者不能假设连续。
- 两种策略可组合，按主题配置 `cleanup.policy=compact,delete`。

### 14.17 对象存储上的数据湖如何保证原子提交？

- 对象存储没有跨对象的原子重命名，提交需要清单或快照指针。
- Iceberg 用元数据文件与快照，提交时写新快照并原子替换表指针（依赖 catalog 的 CAS）。
- Delta Lake 用事务日志 `_delta_log`，以 JSON 与 checkpoint 记录文件增删。
- Hudi 用时间线与提交元数据，区分增量与全量视图。
- 条件写（`If-None-Match`）可用于抢占锁或提交指针，减少并发冲突。
- 提交协议要处理部分写入的孤儿文件，用清理任务回收。
- 读取方按快照隔离，看到的是某一提交点的文件集合，不会读到半成品。

### 14.18（场景）S3 请求变慢或返回 503，如何处置？

- 503 `SlowDown` 表示请求速率超过前缀或桶的限制，需要退避重试。
- 使用指数退避加抖动，避免重试风暴；区分可重试与不可重试错误。
- 分散 key 前缀可提高并行度，但请求速率仍受桶级限制。
- 大对象用分段上传并行传输，小对象合并或批量操作。
- 检查 VPC 端点、NAT 与跨区域流量，网络路径可能才是瓶颈。
- 监控请求延迟分位数与错误码，区分服务端限流与客户端超时。
- 对延迟敏感的数据加本地缓存或 CDN，减少直接请求。

### 14.19（辨析）消息队列与日志抽象的区别是什么？

- 队列消费后删除消息，一条消息通常只被一个消费者处理；日志保留消息，多个消费者可按各自偏移读。
- 队列的确认模型是 ack 后删除，日志的确认模型是提交偏移。
- 日志支持重放与多订阅者，队列更适合任务分发与削峰。
- 日志的分区顺序与偏移是核心，队列更强调可见性与重试。
- 日志的保留策略决定存储成本，队列的堆积会占用 broker 内存或磁盘。
- Kafka 兼具日志与队列语义，通过消费者组实现分发，通过偏移实现重放。
- 选择取决于是否需要重放、多消费者与顺序保证。

### 14.20 消息队列的投递确认与幂等如何在 C++ 客户端落地？

- 关闭自动提交，处理成功后同步或异步提交偏移，提交失败要重试。
- 用 RAII 管理消费者与事务，异常路径上回滚事务或放弃提交。
- 幂等键由业务主键加消息版本生成，写入下游时用唯一索引或条件更新。
- 本地消息表与业务数据在同一事务中写入，后台线程转发到队列。
- 消费端用去重表记录已处理的消息 ID，注意去重表的清理与事务边界。
- 批量提交要在吞吐与重复窗口之间取舍，提交间隔越大重复越多。
- 监控重复率、提交失败率与 lag，定位是客户端还是 broker 的问题。

## 15. 存储设计题

### 15.1 设计单机 KV 存储需要哪些模块？

- 写入路径：WAL 保证崩溃恢复，memtable 承接内存写，达到阈值后冻结并转为 SSTable。
- 读取路径：先查 memtable，再查 immutable memtable，最后按层查 SSTable，布隆过滤器跳过不存在的文件。
- 后台：flush、compaction、manifest 更新、旧文件回收。
- 元数据：MANIFEST 记录 SST 文件集合与层级，CURRENT 指向当前 manifest。
- 接口：`Get`、`Put`、`Delete`、`Scan`、`WriteBatch`，事务与快照可选。
- 配置：memtable 大小、层数、压缩算法、缓存大小、限速。
- 监控：写放大、读放大、空间放大、compaction 队列与 P99 延迟。

### 15.2（设计）WAL 的格式与恢复流程如何设计？

- 记录头包含长度、类型、CRC32C 与 LSN，记录体是键值或批量操作。
- 写入按块对齐，跨块记录拆成 first/middle/last 片段，块尾用填充。
- 恢复时从头部顺序扫描，校验 CRC，遇到损坏记录停止或跳到下一个块。
- 重放到 memtable，恢复 LSN 与最后提交点，丢弃未完成的尾部记录。
- 写入成功后按策略 `fsync`，批量提交可合并多次 `fsync`。
- WAL 文件按大小滚动，旧文件在对应 memtable 落盘后可删除。
- 恢复过程要幂等，重复回放同一条记录不能改变结果。

### 15.3（陷阱）WAL 写入成功是否等于数据不丢？

- 写入成功只表示数据进入页缓存，未 `fsync` 时掉电会丢失。
- `fsync` 返回成功也可能被磁盘缓存欺骗，需要确认写缓存策略。
- 单机持久化不等于高可用，磁盘损坏需要副本或备份。
- 批量提交与组提交会合并 `fsync`，崩溃时可能丢失最后一批。
- 文件系统与 RAID 卡的写缓存行为由实现与配置决定。
- 目录项也要 `fsync`，否则新建文件在崩溃后可能不存在。
- 端到端持久性需要 WAL、副本、备份与校验共同保证。

### 15.4 LSM 的写放大从哪来，如何量化？

- 每层 compaction 把数据读出、归并、再写回下一层，写放大约为层数乘以大小比。
- leveled compaction 的写放大约为层数与大小比的乘积量级，层数 7、大小比 10 时可达到数十倍，实际值随键区间重叠程度变化。
- 用户写入还要写 WAL 与 memtable flush，计入总写入字节。
- 写放大等于实际写入磁盘字节除以用户写入字节，可用每层字节统计估算。
- 空间放大来自旧版本与删除标记，读放大来自多层查找。
- 降低写放大可用 tiered compaction、增大层比、减少层数，代价是读放大与空间放大。
- 监控 compaction 的读写字节与 stall 次数，能定位写放大瓶颈。

### 15.5（辨析）leveled 与 tiered compaction 的取舍是什么？

- leveled 每层内键范围不重叠，读放大低，空间放大低，写放大高。
- tiered 每层允许多个有序段重叠，写入只追加，写放大低，读放大高。
- leveled 适合读多写少与空间敏感场景，tiered 适合写密集与高吞吐摄入。
- 混合方案在低层用 tiered 吸收写入，高层用 leveled 控制读放大。
- tiered 的段数增长会拖慢查询与 compaction，需要限制每层段数。
- 选择要综合写放大、读放大、空间放大与 compaction 的 CPU 开销。
- 云存储上写放大直接对应请求费用，tiered 的成本优势更明显。

### 15.6 Memtable 的数据结构与并发控制如何设计？

- 常用跳表，支持有序遍历与范围扫描，插入为平均 O(log n)。
- 内存从 arena 分配，节点不单独 `new`，减少分配开销与碎片。
- 单写多读：写入线程无锁追加，读取线程通过原子指针获取当前 memtable。
- 冻结时把当前 memtable 转为 immutable，新建 memtable，读取按新旧顺序查找。
- 引用计数管理生命周期，读取方持有引用期间不能释放。
- 写入与 WAL 的顺序要明确：先写 WAL 再写 memtable，避免恢复时丢数据。
- 并发写入可用分段锁或单写线程，取决于吞吐与实现复杂度。

### 15.7（场景）LSM 读放大导致慢查询，如何优化？

- 先看查询访问的 SST 文件数与层数，读放大等于各层查找次数之和。
- 布隆过滤器能跳过不包含目标键的文件，减少无效 IO。
- 块缓存命中率低时增加缓存或调整块大小，减少磁盘读。
- compaction 不及时导致 L0 文件堆积，读要合并更多文件。
- 范围查询受墓碑与旧版本影响，及时 compaction 能减少扫描量。
- 热点键集中在少数文件时，可调整层比或使用分区索引。
- 监控每层文件数、缓存命中率与查询延迟，定位是布隆失效还是 IO 瓶颈。

### 15.8 布隆过滤器的误判率与内存如何权衡？

- 误判率约为 `(1 - e^(-kn/m))^k`，m 为位数，n 为键数，k 为哈希函数个数。
- 给定 m/n 时，k 取 `ln 2 * m/n` 最优；每键 10 位时误判率约 1%。
- 误判只会导致多读一个文件，不会漏判，因此适合读路径过滤。
- 位数组常驻内存，每键位数越多内存越大，需要按层或按文件分配。
- 布隆过滤器不支持删除，LSM 中按文件重建，文件删除后一起释放。
- 前缀布隆用于前缀查询，整键布隆用于点查，二者不能混用。
- 分区布隆把过滤器切成块，减少缓存缺失，代价是误判率略升。

### 15.9（实现）SSTable 的块格式与索引如何设计？

- 数据块按 key 排序，块内前缀压缩，每若干键设置重启点，便于二分查找。
- 块尾保存重启点偏移与数量，块头可加 CRC32C 校验。
- 索引块记录每个数据块的最后一个 key 与块偏移、长度，常驻内存或按需加载。
- 过滤器块保存布隆位数组，元索引块指向压缩与过滤信息。
- 文件尾的 footer 保存索引块与元索引块的偏移，并用固定 magic 结尾。
- 读取时先查索引定位块，再解压并二分查找，块缓存减少重复解压。
- 块大小影响压缩率与随机读放大，常见 4 KB 至 16 KB。

### 15.10 崩溃恢复时如何保证 WAL 与 SST 一致？

- flush 完成后先写新的 SST 文件并 `fsync`，再通过 MANIFEST 记录版本变更。
- MANIFEST 追加 VersionEdit，记录新增与删除的文件，`fsync` 后才算提交。
- CURRENT 文件用原子重命名指向新 MANIFEST，目录也要 `fsync`。
- 恢复时读 CURRENT 与 MANIFEST，重建文件集合，忽略未记录的孤儿 SST。
- WAL 回放只恢复最后一次 flush 之后的写入，已落盘的 memtable 不再回放。
- 删除旧文件要延迟到确认没有读取方引用，避免读到半删除状态。
- 任何一步失败都应保持旧版本可用，恢复流程要能重入。

### 15.11（场景）磁盘写满时存储引擎如何处置？

- 预留空间给 compaction 与元数据，达到阈值时停止接收写入或降级为只读。
- 优先删除过期的 WAL、旧 SST 与临时文件，触发紧急 compaction。
- compaction 本身需要额外空间，空间不足时会失败并加剧堆积。
- 写入限速与背压向上游传导，避免 WAL 与 memtable 无限增长。
- 监控磁盘使用率、compaction pending 与写入 stall，提前告警。
- 对象存储后端可把冷数据下沉，但本地缓存仍需要空间。
- 恢复写入前要确认空间回落到安全水位，避免反复抖动。

### 15.12 元数据服务如何设计？

- 命名空间用树形结构或扁平 inode 表，目录项与文件属性分开存储。
- 元数据操作包括创建、删除、重命名、查找、列目录与属性更新。
- 单机元数据服务受内存限制，海量小文件需要分片或联邦。
- 高可用用主备复制或 Raft，编辑日志持久化后再应用到内存。
- 客户端缓存元数据以减少往返，用租约或版本号保证一致性。
- 大目录的列目录操作要分页，避免一次返回过多条目。
- 元数据与数据分离，数据块的位置由块管理器维护。

### 15.13（陷阱）元数据缓存如何失效？

- TTL 过期是最简单的方式，窗口内可能读到旧元数据。
- 租约由服务端授予，客户端在租约期内可缓存，服务端可延迟回收。
- 版本号或 epoch 随元数据更新递增，客户端比较版本后决定是否刷新。
- 服务端主动失效通过回调或订阅通道推送，需要处理消息丢失与重连。
- 重命名与删除要同时失效父目录与目标路径的缓存，否则列目录结果不一致。
- 缓存穿透用负缓存与请求合并，避免热点路径反复回源。
- 失效失败要有兜底 TTL，不能无限期信任本地缓存。

### 15.14（设计）缓存与存储如何配合？

- 读路径先查缓存，未命中查存储并回填，回填要防击穿。
- 写路径可选写穿透、写回与写旁路，写回需要持久化队列与恢复。
- 缓存失效在写后执行，失败要重试或用变更日志补偿。
- 缓存容量按工作集设置，淘汰策略与 TTL 结合。
- 强一致场景让读写都经过同一层，或使用版本号校验。
- 缓存与存储的故障要隔离，缓存故障不能拖垮存储。
- 监控命中率、回源率与失效延迟，评估一致性窗口。

### 15.15 范围分区与负载均衡在 KV 中如何落地？

- 按 key 范围切分，每个分区有起始与结束 key，元数据记录边界与副本位置。
- 分区大小超过阈值时分裂，低于阈值时与相邻分区合并。
- leader 负责读写，follower 提供读或故障接管，Raft 组按分区组织。
- 负载均衡根据 QPS、数据量、CPU 与磁盘使用率迁移分区。
- 热点分区不能只靠分裂解决，需要按 key 拆分或副本读。
- 分裂与迁移要保证原子性，客户端路由在切换期间可重试。
- 分区数过多会增加元数据与心跳开销，过少限制并行度。

### 15.16（实现）存储引擎的异常安全如何保证？

- 文件句柄、锁、缓冲区用 RAII 管理，构造失败不留下半初始化状态。
- 多步更新用 scope guard 回滚，失败时恢复内存与磁盘的一致状态。
- 强异常安全要求操作要么完成要么不改变状态，可用先写日志再修改。
- 析构函数不抛异常，清理失败记录日志并标记需要恢复。
- 热路径可用错误码代替异常，避免栈展开与分配失败。
- 内存分配失败要回滚已写入的 WAL 记录或标记事务中止。
- 测试要覆盖注入失败，验证每个步骤失败后的恢复路径。

### 15.17（条款）磁盘格式中的字节序与对齐如何处理？

- 磁盘格式固定使用小端或大端，写入时显式转换，不能依赖主机字节序。
- `[basic.types.general]/4` 规定对象表示是 `unsigned char` 序列，跨平台读写应按该表示逐字节处理。
- 结构体有填充与对齐，直接 `reinterpret_cast` 读写会因编译器与 ABI 不同而不一致。
- 未对齐访问在部分平台会触发异常或性能下降，解析用 `memcpy` 到局部变量。
- 变长整数减少空间，但解析要检查溢出与截断。
- 校验和覆盖头部与数据，字节序错误能在校验阶段发现。
- C++20 的 `std::endian` 由 P0463R1 引入，只用于判断主机序，转换仍要显式实现。

```cpp
void put_u32(std::byte* p, std::uint32_t v) {
    p[0] = static_cast<std::byte>(v & 0xff);
    p[1] = static_cast<std::byte>((v >> 8) & 0xff);
    p[2] = static_cast<std::byte>((v >> 16) & 0xff);
    p[3] = static_cast<std::byte>((v >> 24) & 0xff);
}
```

### 15.18（场景）线上慢查询如何排查？

- 先看慢查询日志与执行计划，区分全表扫描、索引失效与锁等待。
- 检查锁等待与事务持有时间，长事务会阻塞其他会话。
- 观察 IO 延迟、缓存命中率与 compaction 队列，存储层瓶颈会放大查询时间。
- 检查统计信息是否过期，错误的行数估算会导致糟糕的连接顺序。
- 查看是否有大查询占用 CPU 与内存，影响其他请求。
- 对比不同时间段的指标，区分偶发抖动与持续退化。
- 用 trace 串起客户端、代理、数据库与存储的耗时，定位具体阶段。

### 15.19（设计）如何做容量规划与压测？

- 估算数据量、增长率、副本数与压缩比，得到磁盘需求。
- 按峰值 QPS 与每次请求的 IO 次数估算 IOPS 与带宽。
- 写放大决定实际写入量，容量规划要留出 compaction 余量。
- 压测用真实数据分布与查询比例，避免只测均匀随机键。
- 关注 P99 与 P999 延迟，而不只是平均吞吐。
- 逐步加压找到拐点，记录 CPU、IO、锁竞争与队列深度。
- 预留故障与再平衡的容量，单节点故障后剩余节点不能过载。

### 15.20（综合）从零设计支持事务的分布式 KV，如何取舍？

- 单机引擎用 LSM 或 B+ 树，WAL 保证持久化，MVCC 提供快照隔离。
- 分区按范围切分，每个分区用 Raft 复制，leader 处理写与线性一致读。
- 事务用 2PC 或 Percolator，时间戳服务提供全局顺序，锁与数据同存。
- 跨分区事务提交要写提交记录，失败时由恢复流程裁决。
- 缓存放在事务之外，失效用变更日志，避免脏读。
- 元数据服务管理分区边界与副本位置，客户端缓存路由。
- 权衡点包括延迟、吞吐、一致性级别、运维复杂度与成本。
