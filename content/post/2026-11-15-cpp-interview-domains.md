## 1. 游戏引擎架构

### 1.1 引擎主干如何组织一帧？

- 一帧按输入采集、逻辑模拟、动画与物理、场景更新、渲染提交、呈现的顺序推进，顺序显式写在主干里，不依赖隐式回调串联。
- 平台层负责窗口、输入设备、文件与时间源，把平台事件归一化为引擎内部结构后再交给上层，上层不感知平台差异。
- 帧开始记录时间戳与计数器，帧结束把各阶段耗时写入统计缓冲，供后续采样与离线分析使用。
- 逻辑与渲染的耦合点只有提交给渲染线程的绘制数据，主干本身不直接调用图形 API。
- 主干只依赖时钟、文件系统、渲染设备等抽象接口，无窗口测试与服务器端运行复用同一套循环。
- 关闭顺序与初始化顺序严格相反，先停线程池与异步 IO，再释放设备与全局分配器，最后关闭日志。

### 1.2（辨析）固定步长与可变步长如何选择？

- 固定步长以恒定 `dt` 推进模拟，积分与求解行为稳定，物理与网络同步容易复现；可变步长按真实耗时推进，动画更平滑但误差随帧时间变化。
- 固定步长需要累加器保留剩余时间，并在渲染时对前后两个模拟状态插值，否则高帧率下出现重复步、低帧率下出现追帧。
- 可变步长必须给 `dt` 设上限，一次长卡顿会让位移过大，导致积分发散与碰撞穿透。
- 确定性要求下只能使用固定步长，且步长、迭代次数与舍入行为都要固定并随回放记录。
- 表现层（动画、粒子、摄像机）跟随渲染帧，逻辑层使用固定步长，两层之间通过采样与插值衔接。
- 常见折中是固定步长加最大子步数，超出上限时丢弃时间而不是持续追帧，避免卡顿后出现连锁延迟。

### 1.3 ECS 中实体、组件、系统的职责如何划分？

- 实体只是标识，通常为索引加代次两个整数，不携带数据也不携带行为，复制实体只复制标识与组件集合。
- 组件是纯数据，按类型连续存储，不含虚函数与裸指针，便于批量遍历、序列化与内存统计。
- 系统是按查询条件筛选组件集合的函数，每帧对匹配的实体批处理，行为集中在系统中而不是分散到组件里。
- 查询结果以原型（archetype）或位掩码缓存，避免每次遍历扫描全部实体。
- 组件增删会改变实体所属原型并搬迁整行数据，此前取得的指针与引用全部失效，这是该模型的主要代价。
- 单例组件（时间、输入、渲染设备）放在全局资源表而非实体上，避免为它们引入实体。

### 1.4（实现）组件存储如何做到遍历友好？

- 同一类型的组件放在连续数组，实体到数组下标的映射单独存放，遍历时只触碰组件数组，映射表只在增删时访问。
- 每个原型为每种组件维护一段紧凑存储，系统按原型遍历时顺序访问，缓存命中率接近顺序读。
- 高频访问的小组件与低频的大组件分属不同原型，避免少数大组件把缓存行撑开、挤掉热数据。
- 组件按 16 字节或缓存行对齐，结构体实际大小用 `sizeof` 在构建期断言，不靠估算。
- 只读系统与写入系统分开声明，调度器据此并行，也为后续的脏标记与增量更新留出接口。
- 删除采用与末尾交换再截断的方式，保持紧凑但打乱顺序；需要稳定顺序时另建索引表，不改变存储布局。

```cpp
struct Position { float x, y, z; };
struct Velocity { float x, y, z; };

// 每个原型为每种组件维护一段紧凑数组，实体到下标由映射表给出
void integrate(Position* pos, const Velocity* vel, unsigned count, float dt) {
    for (unsigned i = 0; i < count; ++i) {
        pos[i].x += vel[i].x * dt;
        pos[i].y += vel[i].y * dt;
        pos[i].z += vel[i].z * dt;
    }
}
```

### 1.5 Archetype 与 Sparse Set 如何取舍？

- 原型存储按组件组合分组，遍历某个组合极快，增删组件需要搬迁整行数据，代价与行宽成正比。
- 稀疏集用实体到下标的稀疏数组加紧凑数据数组，增删为常数时间，遍历时需要按稀疏数组逐项跳转。
- 原型适合组件组合稳定、系统按组合查询的场景；稀疏集适合组件频繁增删、以单组件查询为主的场景。
- 原型数量随组合种类增长，组合多时遍历分支与内存碎片上升，需要限制组合种类或合并低频组件。
- 稀疏集的遍历顺序由插入历史决定，缓存局部性弱于原型，但删除不会搬动其他实体，索引稳定性更好。
- 混合方案常见：高频组合用原型，低频或单例数据用稀疏集或映射表，两套接口在查询层统一。

### 1.6 系统之间的执行顺序如何确定？

- 顺序来自系统声明的读写集合，两个系统访问同一组件且至少一方写入时建立依赖边，而非依赖手工排序。
- 依赖图在启动时做拓扑排序，运行时按批并行，同一批内的系统无数据冲突。
- 手工顺序在新增系统后容易失效，且无法在并行调度下表达真正的约束，只应作为打破循环依赖的显式例外。
- 出现环时优先拆分系统，让写操作集中到一个系统；确实无法拆分时声明顺序并在代码注释里写明原因。
- 创建、销毁与组件增删走延迟命令队列，在批末统一提交，避免遍历过程中修改结构。
- 每帧可导出依赖图与批划分，用于排查负载不均与串行化点。

### 1.7（陷阱）ECS 中删除实体为何容易出错？

- 删除后索引被复用，仅用索引比较时旧值会命中新实体，形成过期引用。
- 实体标识加入代次后，旧标识的比较失败，可以捕获大部分过期引用；代次回绕需要足够宽的整数。
- 系统遍历中直接删除会让底层数组失效，必须走延迟销毁队列，在批末统一处理。
- 组件内的指针或句柄指向被删实体时不会自动清理，需要销毁钩子或反向索引维护引用关系。
- 父子层级里的父实体删除要递归删除或重挂子节点，否则留下游离节点，遍历时访问到无效父级。
- 调试构建可在删除时填充标记值并在解析时校验，把延迟暴露的错误提前到断言。

### 1.8 Job System 与 ECS 如何结合？

- 遍历按原型切块，每块生成一个 job，块大小按组件字节数确定而非实体数量，避免宽组件块过大。
- job 只读共享数据、只写自己的分片，调度器不需要加锁；跨系统的共享写入由批划分隔离。
- 主线程在帧末等待所有 job 完成，等待期间执行不依赖结果的提交工作，例如日志刷盘与统计汇总。
- 任务图需要表达汇合点，通常用原子计数器递减到零再唤醒等待者，避免忙等。
- 长任务（寻路、编译、加载）放独立线程池，防止占住短任务的工作线程造成尾部延迟。
- 统计每帧 job 数量、平均耗时与最长耗时，块过小时调度开销占比上升，块过大时负载不均。

### 1.9（场景）帧预算如何分配与监控？

- 以 60 Hz 的 16.6 ms 为总预算，先扣除呈现等待与垂直同步的固定开销，剩余部分按阶段分配。
- 预算表按平台分档（主机、PC 低配、移动），每档单独设定上限并纳入版本管理，不共用一套数值。
- 每帧记录各阶段耗时并输出分位数，均值会掩盖尖刺，P99 与最大值才反映卡顿。
- 超预算时先判断是稳态超标还是单帧尖刺，尖刺多来自资源加载、着色器编译、物理重建，而非逻辑本身。
- 预算检查放进自动化跑图流程，固定场景与固定相机路径保证不同提交之间可比。
- 预算不是平均分配，渲染通常占一半以上，逻辑与物理合计控制在数毫秒内，剩余留给峰值。

### 1.10 帧率不稳时如何定位瓶颈？

- 先区分 CPU 受限与 GPU 受限：降低分辨率或画质若帧率显著上升，偏向 GPU 受限，反之偏向 CPU 受限。
- CPU 侧用采样剖析看热点函数，用插桩计时看阶段划分，两者交叉验证，避免采样盲区误判。
- GPU 侧用厂商工具抓帧，查看每个渲染通道的耗时与占用率，同时注意异步计算与复制队列的干扰。
- 检查提交线程是否被驱动阻塞，队列提交与呈现的等待常被误判为渲染变慢。
- 关闭垂直同步与帧率上限后复测，排除呈现节流造成的假象。
- 对比不同场景与不同画质档位的曲线，确认瓶颈是场景相关还是全局相关。

### 1.11 对象池如何设计回收策略？

- 池按固定大小的块预分配，空闲块用侵入式链表串起，分配与回收都是常数时间且不触发系统分配。
- 块大小按类型分档（例如 32、64、128 字节），档位越细内部浪费越小，池数量与管理开销越大。
- 回收时不释放内存，只调用对象析构并重置状态，下次分配省去系统调用与页映射。
- 池的容量上限与高水位要统计，长期贴着上限说明容量估计偏低或存在未归还对象。
- 多线程访问采用线程本地池加全局后备，减少争用；跨线程回收要回到对象归属的池。
- 关闭时统一释放并校验未归还数量，未归还即视为泄漏，在调试构建中打印来源。

### 1.12（陷阱）对象池为何会掩盖生命周期错误？

- 回收后的内存仍可读写，悬空指针不会立即崩溃，错误被推迟到对象被复用之后才显现。
- 池化对象地址长期不变，以地址为键的映射或缓存会在复用时命中旧条目。
- 构造与析构次数减少，依赖构造期初始化全局状态的代码在复用后不会重新执行。
- 调试构建可在回收时填充标记值、在分配时校验代次，把延迟错误提前暴露。
- 池化对象内部的容器若不 `clear`，容量会一直保留，内存曲线看似正常但实际占用偏高。
- 文件句柄、GPU 资源这类需要显式关闭的对象不适合纯池化，回收语义要与释放语义分开。

### 1.13 模块划分按什么维度切分？

- 按变化频率切分：数学、容器、序列化等稳定部分在内层，玩法与界面等易变部分在外层。
- 按依赖方向切分：底层不引用上层，跨层调用通过接口或事件反转依赖方向。
- 按团队归属切分可以减少合并冲突，但同一技术关注点会被分散，需要接口约定兜底。
- 按运行时边界（进程、动态库）切分能隔离崩溃与内存占用，代价是跨边界调用与数据复制。
- 模块对外只暴露不透明句柄与函数表，内部结构不进入头文件，减少编译依赖。
- 划分结果用依赖图检查，禁止出现环与跨层直连，检查放进持续集成而不是靠人工审阅。

### 1.14（场景）模块之间出现循环依赖如何处理？

- 先判断是数据依赖还是调用依赖：数据依赖可将共享结构下沉到更底层的基础模块。
- 调用依赖可用回调、事件或接口表反转，由上层注册、下层在运行时调用，依赖方向变为单向。
- 头文件层面的循环包含可用前置声明切断，链接层面的循环必须重新划分模块。
- 动态库之间的循环在部分平台无法解析符号，必须在构建期发现，不能留到运行期。
- 允许少量受控反向调用时，把注册点集中到一处并记录原因，避免反向往来扩散。
- 持续集成中加入依赖图检查，新增环即失败，并输出环上的完整路径。

### 1.15 场景图与空间划分的职责如何区分？

- 场景图表达父子变换与逻辑归属，空间划分表达位置邻近关系，两者更新频率与粒度不同。
- 变换沿父子链累积，脏标记只重算受影响子树，否则每帧遍历整棵树会成为热点。
- 空间划分（网格、BVH、八叉树）随对象移动更新，更新代价决定是增量更新还是整棵重建。
- 渲染剔除、物理宽相、音频衰减都查询空间结构，查询粒度不同，可共享一份结构或各建一份。
- 层级过深的场景图会让变换更新成为热点，高频节点适当扁平化。
- 对象跨格移动时先出旧格再入新格，避免同一帧被两个格子重复查询。

### 1.16（实现）事件系统如何避免每帧堆分配？

- 事件按类型分配固定大小的环形缓冲，发布端只做复制，消费端按索引读取。
- 每个订阅者记录游标，事件保留到最慢的订阅者消费之后才可覆盖，容量不足时丢弃并计数。
- 事件结构保持平凡可复制，变长负载用索引指向池化对象，避免每次发布都分配。
- 同步事件在发布调用的栈内立即分发，异步事件入队到帧末或指定线程分发，两者接口分开。
- 分发顺序按订阅优先级稳定排序，不依赖注册顺序，便于复现问题。
- 统计每类事件的发布量与丢弃量，长期丢弃说明容量不足或消费速度落后。

### 1.17 子系统初始化与关闭顺序如何保证正确？

- 显式声明依赖关系，初始化按拓扑序执行，关闭严格逆序，顺序集中在一处而不是分散在各子系统内部。
- 构造期不做重量级工作，避免静态初始化顺序问题，改为显式 `init` 与 `shutdown`。
- 依赖缺失时初始化返回错误而非直接断言，工具与编辑器场景可以降级运行。
- 关闭阶段先停线程与网络，再释放资源与分配器，最后销毁日志，防止日志依赖已释放的内存。
- 关闭流程要幂等且可重入，异常路径下也能安全走完。
- 启动与关闭耗时写入日志，关闭时间过长会造成退出卡顿并被用户感知。

### 1.18（场景）热重载与模块边界如何配合？

- 可安全重载的是数据与脚本，引擎核心模块重载需要平台支持与状态迁移，风险高，通常只在开发构建启用。
- 资源热重载以文件监听触发，重新加载后替换句柄指向的实例，旧实例进入延迟释放队列。
- 脚本重载需要保留运行状态时，把状态放在宿主侧，脚本只包含逻辑，重载后重新绑定。
- 重载失败必须回滚到上一版本并保持可运行，不能把半加载状态暴露给上层。
- 多线程下重载与渲染并发访问同一资源，需要版本号或读写锁保护，句柄解析在锁外完成。
- 编辑器与运行时分属不同构建，重载路径在两者都要验证，不能只测编辑器。

### 1.19 逻辑线程与渲染线程如何解耦？

- 逻辑线程生成绘制数据并写入双缓冲或帧队列，渲染线程只读已提交的数据，两者不共享可变结构。
- 数据所有权通过版本化句柄与延迟释放转移，避免渲染线程读到逻辑线程刚释放的内存。
- 同步点放在帧边界，逻辑可以领先渲染一到两帧，领先过多会放大输入延迟。
- 渲染线程不回调逻辑，所有反馈通过队列回到逻辑线程，避免跨线程重入。
- 队列容量设上限，逻辑过快时阻塞或丢帧，而不是让队列无限增长。
- 两个线程的耗时分别统计，便于判定哪一侧拖慢了帧。

### 1.20（场景）上线后出现单帧尖刺，如何排查？

- 先确认尖刺的分布：固定间隔多为定时任务或回收逻辑，随机出现多为资源加载与驱动行为。
- 抓取尖刺帧的调用栈与阶段耗时，与相邻正常帧逐项对比，先定位到阶段再定位到函数。
- 常见来源包括着色器编译、纹理上传、物理结构重建、日志刷盘、内存整理。
- 检查游戏线程是否做了同步 IO 或等待 GPU，这两类会把外部延迟直接放进帧内。
- 用环形缓冲记录最近数百帧的细粒度事件，事故后可以离线回放定位。
- 修复方向是预编译、预上传、分帧摊平，提高预算只会掩盖尖刺。

## 2. 渲染管线与图形 API

### 2.1 图形管线包含哪些阶段？

- 顶点获取、顶点着色、曲面细分、几何着色、图元装配、裁剪与视口变换、光栅化、片元着色、逐片元操作依次推进。
- 顶点着色与片元着色是可编程阶段，其余多为固定功能或可配置状态，状态组合构成管线对象。
- 图元装配与裁剪在裁剪空间进行，视口变换把归一化坐标映射到像素坐标。
- 光栅化把图元转为片元并插值顶点属性，插值方式由平面插值、中心插值或无透视校正等修饰符决定。
- 逐片元操作包含模板测试、深度测试、混合与写入掩码，顺序固定，不能由着色器重排。
- 现代 API 把管线状态固化进管线对象（Vulkan 的 `VkPipeline`、D3D12 的 PSO），创建昂贵、切换有开销。
- 移动端 TBDR 架构把可见性判断提前到片元着色之前，被遮挡的片元可能从不执行着色器。

### 2.2（辨析）前向渲染与延迟渲染如何取舍？

- 前向渲染每物体一次着色，材质与光照在片元着色器内计算，带宽占用低，天然支持透明与多重采样。
- 延迟渲染把几何信息写入 G-Buffer，光照按屏幕空间计算，光源数量增加时开销近似线性增长。
- 延迟渲染的 G-Buffer 带宽与显存占用高，透明物体仍需前向补充一遍。
- 延迟渲染难以支持每物体不同的着色模型，需要额外分支或按材质分层。
- 混合方案（前向加聚类光照、可见性缓冲）在开放场景与移动平台更常见。
- 选择依据是光源数量、材质多样性、目标平台带宽与是否需要多重采样。

### 2.3（场景）管线状态对象创建导致卡顿如何处理？

- 管线创建包含着色器编译与状态校验，首次创建可达数十毫秒，出现在战斗中途就是明显卡顿。
- 方案一：在加载期按材质与渲染状态组合预创建，需要的组合由离线工具枚举。
- 方案二：后台线程创建，主线程继续，但首次使用时仍需等待，只能把尖刺变成偶发等待。
- 方案三：持久化管线缓存，驱动复用已编译结果，缓存与驱动版本绑定，升级后失效。
- 运行时创建的管线数量应作为指标上报，长期非零说明预热覆盖不足。
- 变体数量来自材质关键字组合，收敛关键字集合比增加预热更有效。

### 2.4 Vulkan 与 D3D12 的对象模型如何对应？

- 设备对应 `VkDevice` 与 `ID3D12Device`，队列对应 `VkQueue` 与 `ID3D12CommandQueue`。
- 命令缓冲对应 `VkCommandBuffer` 与 `ID3D12GraphicsCommandList`，分配器对应 `VkCommandPool` 与 `ID3D12CommandAllocator`。
- 描述符集对应根签名加描述符堆，Vulkan 的描述符集布局必须在管线创建时确定。
- 资源状态在 Vulkan 用屏障与图像布局表达，在 D3D12 用显式状态转换屏障表达。
- 内存由 Vulkan 驱动暴露堆与类型，D3D12 由应用创建堆并放置资源，后者把驻留管理完全交给应用。
- 两者都不提供跨帧的自动同步，生命周期、屏障与延迟释放都需要引擎自己实现。

### 2.5 命令录制与提交如何组织？

- 命令列表录制时独占命令分配器，同一分配器不能与执行并发使用，按帧或按线程轮转分配器。
- 不变的部分预录制为可复用命令列表，动态部分每帧重录，减少 CPU 录制开销。
- 合并批次以减少状态切换与提交次数，提交次数过多会抬高 CPU 开销，调试构建下尤其明显。
- 提交后用围栏确认 GPU 完成，才能复用对应的分配器与上传内存。
- 多线程录制把渲染通道或物体批次分给不同线程，再按依赖顺序提交。
- 录制线程与提交线程分离时，命令列表的所有权转移要显式建模，避免提交后继续录制。

### 2.6 描述符与根签名如何影响性能？

- 描述符堆是 GPU 可见的表，绑定是让着色器按索引读取表项，索引越界不会在 CPU 侧报错。
- Vulkan 的描述符集布局决定绑定频率，高频更新的资源放在更靠前的集合，减少重复绑定。
- D3D12 根签名参数越少、越靠近根参数，访问越快；描述符表需要一次间接寻址。
- 描述符更新要与使用它的帧同步，否则出现读到旧资源或写到正在使用的表项。
- 描述符按帧倍增（每帧一份），避免跨帧写冲突，代价是显存与更新量上升。
- 数量超出实际上限时改用无绑定方案，用索引在着色器内取资源，减少绑定调用。

### 2.7（陷阱）描述符集布局不匹配会怎样？

- 管线布局与绑定时使用的布局不兼容时，验证层报错；未启用验证层可能表现为读取越界或画面异常。
- 兼容性要求布局数量、绑定序号、类型与数组长度一致，着色器可见阶段不影响兼容性但影响可用性。
- 更新已绑定的描述符集在部分实现上不被允许，或在录制与执行之间产生竞争。
- 动态偏移只适用于统一缓冲与存储缓冲，不适用于纹理与采样器。
- 布局对象应集中定义并复用，避免同一管线在不同代码路径下绑定不同布局。
- 调试构建启用验证层与 GPU 断言，把这类错误挡在提交之前。

### 2.8 资源生命周期如何划分阶段？

- 创建、上传、驻留、使用、闲置、销毁六个阶段，每个阶段的同步要求不同。
- 上传走暂存缓冲：先写主机可见内存，再复制到设备内存，最后用屏障保证可见。
- 使用期由渲染图声明读写，编译器据此推导屏障、排序与内存别名复用。
- 闲置资源进入延迟释放队列，等待引用它的帧全部完成后再回收。
- 销毁必须晚于 GPU 完成，用帧围栏或时间线信号量判定，不能只看 CPU 侧引用计数。
- 资源句柄与底层对象分离，句柄失效后仍可安全查询状态，避免直接解引用悬空指针。

### 2.9（场景）资源在 GPU 仍在使用时被释放会怎样？

- 表现为花屏、闪烁、驱动重置或进程崩溃，崩溃位置往往与真实原因相距很远。
- 常见来源是异步加载完成回调里直接替换了正在绘制的纹理。
- 防护手段是引用计数加帧延迟释放，GPU 完成信号发出后才真正销毁。
- 调试期给资源加调试名，用厂商工具定位最后一次使用该资源的命令。
- 验证层能捕获部分「销毁时仍被命令缓冲引用」的情况，覆盖并不完整。
- 生命周期规则要写进代码审查清单，不能只依赖工具。

### 2.10 `fence`、`semaphore` 与 `barrier` 的区别是什么？

- 围栏用于 CPU 等待 GPU，查询的是某个提交的完成状态，通常按帧轮转使用。
- 信号量用于队列之间或队列与呈现之间的顺序，只能等待与发出，不能查询状态。
- 屏障在命令缓冲内部，保证资源的可用性与可见性，并完成图像布局转换。
- 时间线信号量把计数与值暴露给 CPU 与 GPU，可替代多个二元信号量，简化多队列依赖。
- 三者作用域不同，混用会导致等待无效或死锁，例如用围栏代替跨队列信号量。
- 队列提交顺序不等于执行顺序，跨队列依赖必须显式声明。

### 2.11（辨析）管线屏障与内存屏障的作用范围有何不同？

- 管线屏障同时表达执行依赖与内存依赖，参数包含源阶段、目的阶段、源访问与目的访问。
- 只声明阶段而不声明访问类型时，可见性无法保证，读取可能看到旧值。
- 全局屏障开销大，按资源做细粒度屏障可利用渲染图的依赖分析减少过度同步。
- 布局转换必须由屏障完成，转换本身可能触发缓存刷新或压缩数据解压。
- 写后读、读后写、写后写都需要对应方向的依赖，跨帧使用还要考虑呈现引擎的隐式同步。
- 过度保守的屏障会串行化队列，在性能分析中表现为 GPU 空闲等待。

### 2.12 队列家族与所有权转移如何处理？

- 图形、计算、复制、呈现队列的能力在不同硬件上可能合并，必须按队列族标志查询而不是假设。
- 资源在队列族之间共享需要设置共享模式，独占模式下转移所有权要配对释放与获取操作。
- 并发共享模式省去转移，但每次访问的同步由应用负责，错误会表现为随机数据损坏。
- 复制队列适合大块上传，与图形队列并行可减少加载期等待。
- 呈现操作需要与渲染完成建立信号量依赖，否则可能出现呈现未完成的图像。
- 队列数量有限，按负载分配而不是每个用途一个，空闲队列仍占用驱动资源。

### 2.13 交换链与呈现如何避免撕裂与卡顿？

- 交换链图像数量决定可挂起的帧数，双缓冲容易等待，三缓冲能吸收抖动。
- FIFO 模式垂直同步且无撕裂，队列满时阻塞提交；MAILBOX 模式丢弃旧帧，延迟更低。
- 立即模式可能撕裂，通常只在窗口模式且明确需要低延迟时使用。
- 窗口尺寸变化要重建交换链，重建期间暂停提交并等待旧图像释放。
- 呈现前把图像转换为呈现布局，呈现后转回，转换缺失会被验证层报告为布局错误。
- 最小图像数与呈现模式的组合由实现定义，需要查询能力而不是按经验取值。

### 2.14（场景）帧率达标但画面卡顿，如何判断是呈现问题？

- 统计每帧的提交等待与呈现等待，呈现等待占比高说明被垂直同步节流。
- 观察帧时间是否呈规律锯齿：两帧一组的模式常见于双缓冲加垂直同步。
- 用 GPU 抓帧对比 CPU 提交时间线，确认 GPU 是否处于空闲等待而非满载。
- 检查交换链图像数与呈现模式是否与显示器刷新率匹配。
- 窗口失焦或最小化时部分平台会降低呈现频率，需要从统计中剔除。
- 高刷新率显示器上固定 60 Hz 上限会造成均匀但明显的节奏差。

### 2.15 显存类型与资源驻留如何管理？

- Vulkan 暴露内存堆与内存类型，包含设备本地、主机可见、惰性分配等标志，按用途匹配。
- D3D12 由应用创建默认堆、上传堆与回读堆并放置资源，驻留由应用显式管理。
- 设备本地内存带宽高但不可直接映射，上传必须经过暂存。
- 主机可见且一致的内存可直接写，但带宽低，只适合小量频繁更新。
- 驻留预算不足时资源被换出，表现为加载卡顿，需要监控驻留字节与换出次数。
- 大资源按块切分，按可见性逐步驻留，避免一次性提交超出预算。

### 2.16 多帧并行（frames in flight）如何设计？

- 每帧拥有独立的命令分配器、常量缓冲与描述符区，避免与 GPU 正在读取的数据冲突。
- 帧数取 2 到 3，过多会增加输入延迟与显存占用，收益递减。
- 每帧结束用围栏标记，下一轮复用前等待该围栏，等待放在帧首而不是提交前。
- 上传内存在对应帧完成后回收，形成环形缓冲，容量按峰值上传量确定。
- 逻辑侧的资源删除请求进入延迟队列，按帧号回收，避免跨线程同步。
- 调试时可限制为单帧并行以简化问题定位，但会掩盖同步缺陷，不能作为长期配置。

```cpp
struct FrameContext {
    unsigned index;
    void* allocator;
    void* constants;
    unsigned long long fence;  // 该帧提交时写入的围栏值
};

// 复用某一帧之前，等待 GPU 完成该帧的提交
void reuse(FrameContext& ctx, unsigned long long completed) {
    if (ctx.fence > completed) waitFence(ctx.fence);
}
```

### 2.17（实现）纹理上传路径如何组织？

- 创建暂存缓冲并映射，按行复制并处理行间距与对齐要求，行对齐错误会表现为图像错位。
- 记录复制命令，插入屏障把图像从传输目标转为着色器可读布局。
- 大纹理会分块上传，避免单帧占用过多带宽造成加载卡顿。
- 使用异步复制队列时，与图形队列建立信号量依赖，不能依赖提交顺序。
- 上传完成后把暂存内存归还池中复用，减少系统分配次数。
- 统计上传字节数与耗时，加载期的尖刺多数来自这里。

### 2.18 着色器编译与管线缓存如何处理？

- 着色器源码在构建期离线编译为字节码，运行时只做管线创建，避免在运行时处理源码。
- 驱动仍可能在首次使用时做最终编译，产生数十毫秒的卡顿。
- 管线缓存把编译结果持久化到磁盘，缓存与驱动版本、着色器字节码绑定，升级后失效。
- 变体按材质关键字生成，关键字数量增长带来组合爆炸，需要收敛关键字集合。
- 预热阶段在加载界面创建常用变体，并记录耗时分布作为发布指标。
- 运行时创建数量长期非零说明预热覆盖不足，应在测试中设为失败条件。

### 2.19（场景）验证层能发现什么、不能发现什么？

- 能发现参数错误、对象生命周期违规、同步缺失、布局不匹配等 API 使用问题。
- 能通过同步验证发现部分数据竞争与危险屏障，但需要额外开销。
- 不能发现逻辑错误，例如剔除条件写错、材质参数填错、包围体算错。
- 不能保证覆盖平台差异，某些错误只在特定驱动或特定硬件上出现。
- 开启后性能下降明显，只在调试构建与自动化验证任务中启用。
- 验证层无报错不等于正确，仍需 GPU 抓帧与画面比对。

### 2.20（场景）发布后出现花屏与闪烁，如何排查？

- 先确认是否与特定 GPU、驱动版本、画质档位相关，用最小复现条件缩小范围。
- 花屏多与资源释放过早、屏障缺失、描述符越界有关；闪烁多与交换链、深度精度、透明排序有关。
- 用调试标记给关键渲染通道命名，在抓帧工具中逐通道检查中间输出。
- 对比调试构建与发布构建的差异，优化可能改变了同步策略或资源复用方式。
- 保留可复现的场景种子与输入录像，便于在本地稳定复现。
- 修复后补充对应的验证层检查与自动化画面比对，避免同类问题回归。

## 3. 游戏内存与资源管理

### 3.1 游戏为何需要自定义分配器？

- 通用分配器面向通用负载，元数据开销与锁争用在大批量小对象场景下明显。
- 游戏对象生命周期集中且可预测，按帧、按场景、按关卡批量释放可以大幅简化管理。
- 自定义分配器可提供内存标签、预算与统计，便于定位峰值来源。
- 可按内存域（系统内存、显存、可执行内存）分配，减少跨域复制。
- 需要自行处理对齐、线程安全与调试填充，维护成本高于通用分配器。
- 工具与编辑器仍适合通用分配器，只有运行时热路径值得引入专用分配器。

### 3.2（辨析）栈式分配器与池式分配器适用于什么场景？

- 栈式按后进先出释放，分配只移动指针，释放只回退指针，开销接近零。
- 栈式适合帧内临时数据与加载期临时缓冲，乱序或跨帧释放会破坏结构。
- 池式按固定块分配，分配与回收为常数时间，适合同类型对象的大批量创建。
- 池式在块大小种类多时产生内部碎片，种类少时产生浪费。
- 自由链表分配器可处理变长请求，但外部碎片随运行时间增长。
- 选择依据是生命周期模式与大小分布，速度只是其中一个维度。

### 3.3 内存标签与预算如何落地？

- 每个分配点传入标签（渲染、物理、音频、关卡），标签为编译期常量，避免字符串比较开销。
- 分配器按标签累计当前值与峰值，编辑器实时显示，便于在改代码前发现异常。
- 预算按平台与场景设定上限，超限时记录调用栈并告警，而不是直接崩溃。
- 标签层次不宜过深，过细会让统计本身成为可观测性开销。
- 峰值统计要区分瞬时峰值与稳态占用，前者决定容量，后者决定常驻成本。
- 发布构建可保留统计但关闭调用栈采集，用采样方式保留少量样本。

### 3.4（陷阱）过度对齐分配会带来什么问题？

- 请求的对齐大于分配器支持时，返回地址不满足要求，SIMD 访问会崩溃或明显变慢。
- 对齐分配需要额外保存原始指针以便释放，元数据大小随对齐值增长。
- 过度对齐会加剧内部碎片，在大量小对象场景下尤其明显。
- 缓存行对齐可避免相邻对象的伪共享，代价是每个对象多占数十字节。
- 各平台的对齐要求不同，按最严格的平台设计并在构建期断言核实。
- 对齐值应来自类型要求或硬件要求，不凭经验取大值。

### 3.5 地址空间与碎片如何处理？

- 外部碎片来自变长分配的交替释放，表现为总空闲足够却找不到连续块。
- 内部碎片来自按固定档位分配，表现为块内浪费。
- 长时间运行的开放世界与在线服务都会累积碎片，需要定期整理或按大小分档隔离。
- 按大小分档的池把不同尺寸隔离，减少互相影响，代价是池数量上升。
- 64 位平台上虚拟地址不紧张，但虚拟地址到物理页的提交与映射仍有成本。
- 监控最大连续可分配块比监控总空闲更能反映风险。

### 3.6 CPU 与 GPU 内存域如何划分？

- 设备本地内存带宽高，主机内存可直接访问但带宽低，跨域传输要走总线。
- 统一内存架构下物理内存共享，但缓存一致性与访问延迟仍有差异。
- 上传路径尽量批量并异步，避免在渲染线程同步等待。
- 写合并内存适合顺序写，随机写会显著变慢。
- 资源驻留策略按访问频率决定，常驻资源与流式资源分开管理。
- 显存预算要包含中间渲染目标与临时缓冲，不能只算资源本体。

### 3.7 资源句柄如何设计？

- 句柄为索引加代次，索引定位槽位，代次防止旧句柄命中新资源。
- 槽位表拆成紧凑数组与空闲链表，解析为常数时间，空闲槽位可延迟复用。
- 句柄不暴露指针，解析统一经过资源管理器，便于迁移、延迟加载与统计。
- 句柄可携带类型标记，调试构建校验类型不匹配并打印来源。
- 句柄的生命周期与引用计数解耦，引用计数管理实例，句柄只做标识。
- 序列化保存稳定 ID 而非索引，加载时重建映射，避免跨版本失效。

```cpp
struct Handle { unsigned index; unsigned generation; };
struct Slot { void* resource; unsigned generation; bool alive; };

// 解析时校验代次，代次不匹配即视为失效句柄
void* resolve(const Slot* slots, Handle h) {
    const Slot& s = slots[h.index];
    return (s.alive && s.generation == h.generation) ? s.resource : nullptr;
}
```

### 3.8（陷阱）悬空句柄为何难以发现？

- 句柄失效后解析返回空或默认资源，调用方不检查时静默使用占位内容。
- 代次回绕后旧句柄重新有效，概率低但确实存在，代次位宽要足够。
- 多线程下句柄解析与销毁并发，需要原子读或锁保护槽位。
- 资源管理器重启或整包热重载后槽位表重建，所有旧句柄同时失效。
- 调试构建可在销毁时把槽位标记为墓碑并保留一段时间，便于定位来源。
- 断言应覆盖解析失败路径，而不是返回默认值后继续执行。

### 3.9 引用计数与资源生命周期如何配合？

- 引用计数适合共享资源，计数增减要原子操作或限定在单线程内完成。
- 循环引用需要弱引用或显式打破，资源之间的相互引用是常见来源。
- 计数归零时未必能立即释放，GPU 可能仍在使用，需要延迟释放队列。
- 计数更新在热路径上会造成缓存行争用，按线程本地缓存批量合并可缓解。
- 正在加载的资源被再次请求时返回同一实例，避免重复解码与重复占用。
- 释放顺序影响峰值，批量释放会造成内存尖峰，应分帧摊平。

### 3.10 流式加载的分级与优先级如何确定？

- 资源按距离、可见性、玩法重要性分级，分级决定驻留策略与预取时机。
- 优先级队列按需求动态调整，玩家朝向与移动方向影响预取顺序。
- 预取窗口按移动速度与加载耗时估算，速度越快窗口越大。
- 低优先级请求可被抢占，取消要能中断 IO 与解码，而不只是从队列移除。
- 带宽受限时按预算分配，避免加载挤占渲染所需的传输带宽。
- 统计加载队列长度与等待时间，长期积压说明预算或分级策略有问题。

### 3.11（场景）开放世界跨区时卡顿如何解决？

- 卡顿来自同步加载、解码峰值、上传峰值或物理结构重建，需要先定位到具体阶段。
- 把区域切分得更细，单次加载量下降，但请求数量与索引开销上升。
- 加载与上传分帧摊平，每帧限制字节数与解码任务数，用预算而不是完成时间驱动。
- 预取提前到玩家到达边界前若干秒，窗口按当前速度动态调整。
- 低优先级资源可以丢弃并重新请求，避免阻塞关键资源。
- 用加载耗时直方图与单帧峰值定位，均值无法反映卡顿。

### 3.12 IO 与解压线程如何分工？

- IO 线程负责读取与校验，解压线程负责解码，两者用有界队列衔接。
- 队列有界可形成背压，避免内存被未处理数据占满。
- 解压后的数据直接写入目标内存或暂存区，减少一次中间复制。
- 优先级要在 IO 层生效，否则解压线程只能按到达顺序处理。
- 机械硬盘与光驱的随机读代价高，按块顺序读并做预读。
- 统计各阶段吞吐与队列深度，瓶颈通常集中在其中一个阶段。

### 3.13 资源打包与索引如何设计？

- 资源按加载单元打包，同一区域或同一关卡的资源放在相邻偏移，减少寻道。
- 索引记录偏移、长度、压缩方式与校验值，加载时只读索引，不读数据段。
- 包内对齐影响直接映射（零复制）的可行性，按页对齐可整块映射。
- 增量更新以包为单位替换，需要版本号与哈希校验。
- 索引本身要小且可缓存，避免启动时读取大量元数据。
- 打包工具与运行时格式都要版本化，防止新旧版本不兼容。

### 3.14（实现）异步加载的完成与取消如何处理？

- 请求对象携带状态、优先级、取消标志与完成回调。
- 完成回调在指定线程执行，避免在 IO 线程直接触碰渲染资源。
- 取消要区分尚未开始与已经开始：前者从队列移除，后者等待安全点。
- 请求期间持有引用，防止资源在使用中被回收。
- 失败要回传错误码与路径，便于定位缺失资源。
- 回调中不得批量发起同级请求，防止递归放大造成队列拥堵。

### 3.15 热重载的触发与一致性如何保证？

- 文件监听触发重载，按路径映射到资源 ID，再通知依赖该资源的对象。
- 重载要原子替换：新实例加载成功后才切换句柄指向，失败保持旧实例。
- 依赖资源（材质引用纹理）需要级联失效，否则出现新旧混用。
- 重载期间禁止部分线程读取旧实例，用读写锁或版本号控制。
- 重载失败要保留错误信息与文件路径，不进入半加载状态。
- 重载频率要限流，编辑器一次保存可能触发多个文件事件。

### 3.16（场景）热重载后崩溃如何排查？

- 常见原因是旧实例已释放但仍有引用，或新实例的格式与旧代码不匹配。
- 检查是否缓存了裸指针，改为句柄后所有访问都经过解析。
- 检查资源尺寸变化（纹理尺寸、网格顶点数）是否让依赖的缓冲区失效。
- 检查重载回调是否在错误线程执行，触碰了非线程安全的资源。
- 调试构建加入重载后的完整性校验，遍历依赖关系检查空引用。
- 记录重载前后的资源版本与文件哈希，便于复现。

### 3.17 内存峰值与预算告警如何处理？

- 峰值出现在场景切换、加载新区域、生成光照数据、编译着色器时。
- 预算按标签与总量双重限制，超限时记录快照而不是只打印一行日志。
- 快照包含各标签占用与最大分配栈，便于归因到具体系统。
- 加载期与稳态分别设限，加载期允许更高但必须有上限。
- 告警要进入自动化测试，避免只在人工试玩时才发现。
- 预留应急余量，临界时仍能分配关键资源而不是整体失败。

### 3.18（场景）内存泄漏如何定位？

- 先看总量曲线：单调上升不回落，或每次进出场景后台阶式上升。
- 用分配器统计按标签对比进出场景的差值，缩小到具体系统。
- 记录分配调用栈并做差分，找出只增不减的调用点。
- 检查容器容量未收缩、事件订阅未取消、句柄未释放这三类常见遗漏。
- 检查循环引用与延迟释放队列是否卡住，后者会让内存长期不归还。
- 数小时的长跑测试比短测试更容易暴露缓慢泄漏。

### 3.19 资源版本与补丁如何管理？

- 每个资源有内容哈希与格式版本，格式版本变化需要重新导出。
- 补丁可按包或按文件粒度分发，包粒度适合大改动，文件粒度适合小修。
- 校验使用哈希，避免半包与损坏文件进入运行环境。
- 旧版本资源保留以便回滚，回滚要能在一分钟内完成。
- 版本号写入清单，客户端按清单校验完整性并修复缺失项。
- 补丁大小与安装时间要作为发布指标持续跟踪。

### 3.20（场景）发布包资源缺失如何排查？

- 症状是特定界面黑块、模型缺失、音频静音，日志里有加载失败记录。
- 原因多为打包规则遗漏、路径大小写不一致、路径在打包时被规范化。
- 大小写问题在 Windows 上不显现，在主机与移动平台上暴露。
- 打包后做清单比对：运行时引用的资源 ID 与包内索引求差集。
- 持续集成中用最小场景跑一遍全资源加载测试，失败即阻断发布。
- 修复后把资源完整性检查固化进发布流程，而不是依赖人工抽查。

## 4. 物理与动画

### 4.1 宽相与窄相如何分工？

- 宽相用包围体与空间结构快速排除不可能相交的物体对，输出候选对。
- 窄相在候选对上做精确相交测试，输出接触点、法线与穿透深度。
- 宽相的输出规模决定窄相成本，包围体拟合过松会让候选对数量激增。
- 动态物体每帧更新包围体并移动其在空间结构中的位置，静态物体可批量合并。
- 候选对按物体对去重，避免同一对在两个格子中被测试两次。
- 统计候选对数量与窄相命中率，命中率过低说明宽相过松，过高说明包围体偏大。

### 4.2 空间结构如何选择？

- 均匀网格适合分布均匀、尺寸相近的物体，查询为常数时间。
- 层次包围盒适合静态与尺寸差异大的场景，构建成本高，查询为对数时间。
- 空间哈希适合稀疏大场景，格子大小决定冲突率。
- 动态物体频繁移动时网格更新便宜，层次结构需要增量更新或定期重建。
- 物体跨多个格子时用多格注册或松散网格，避免格子边界处漏检。
- 选择依据是物体数量、尺寸分布与移动频率，三者共同决定维护成本。

### 4.3（辨析）离散与连续碰撞检测如何取舍？

- 离散检测在固定步长采样位置，快速物体可能在一帧内穿过薄物体。
- 连续检测用扫掠形状或时间区间求最早接触时刻，能避免穿透。
- 连续检测代价高，通常只对快速物体或关键物体启用。
- 连续检测需要处理旋转扫掠，多数实现只做平移扫掠并配合子步近似。
- 混合方案：默认离散，速度超过阈值时切换到连续检测。
- 连续检测的结果要参与求解，否则下一帧仍会穿透。

### 4.4 接触流形如何生成与保持？

- 接触点包含位置、法线、穿透深度与摩擦相关数据，是求解器的输入。
- 多点流形比单点稳定，单点接触会让静止物体抖动。
- 流形需要在帧间保持，用特征 ID 匹配新旧接触点，避免冲量被重置。
- 特征 ID 来自顶点与边的组合，形状变化后失效，需要重新匹配。
- 接触点数量按求解预算裁剪，保留穿透最深的若干点。
- 流形缓存错误会导致抖动、缓慢滑动与能量注入，表现为物体自己移动。

### 4.5 冲量求解如何迭代收敛？

- 顺序冲量法逐约束求解，每次修正速度，多次迭代逼近可行解。
- 迭代次数与收敛程度相关，次数不足表现为穿透与抖动。
- 需要暖启动：用上一帧的冲量作为初值，可显著减少所需迭代次数。
- 位置修正与速度求解分离，减少能量注入与反弹过度。
- 摩擦锥用两个切向约束近似，各向异性摩擦需要额外约束轴。
- 求解顺序影响结果，固定顺序才能保证可复现。

### 4.6（陷阱）穿透与隧道效应如何区分？

- 穿透来自单步位移大于物体厚度，或求解迭代不足。
- 隧道效应是高速物体整帧跨过薄物体，离散检测无法产生接触。
- 缓解手段包括子步、连续检测、速度上限与加厚碰撞体。
- 穿透发生后物体可能卡在内部，需要分离冲量或回退位置处理。
- 穿透修正依赖流形，流形缺失时不会产生任何修正。
- 监控穿透深度与最大速度，超过阈值时告警并记录物体标识。

### 4.7 睡眠与唤醒如何判定？

- 速度与角速度低于阈值并持续一段时间后进入睡眠，跳过积分与求解。
- 睡眠物体被接触或受力时唤醒，唤醒需要沿接触链传播。
- 唤醒阈值过低会导致频繁唤醒与抖动，过高会让物体该动时不动。
- 睡眠物体仍参与宽相，或按岛屿整体剔除以减少查询。
- 岛屿按接触图划分，整岛睡眠比单物体睡眠更稳定。
- 统计清醒物体数量，异常偏高说明阈值设置不当或存在持续微振动。

### 4.8 固定步长与子步如何设置？

- 固定步长让积分与求解可复现，渲染帧率变化不影响物理结果。
- 子步把一帧拆成多次小步，减少穿透并提高稳定性。
- 子步数增加会线性提高 CPU 开销，需要与物体数量一起权衡。
- 累加器要处理剩余时间，否则步数与帧数不同步会造成位置抖动。
- 单帧最大步数设上限，长卡顿后丢弃多余时间。
- 步长与迭代次数写入配置，并随回放记录，否则无法复现问题。

```cpp
// 固定步长累加器：超出最大子步数后丢弃剩余时间
void step(double frameTime, double fixedDt, int maxSteps, double& acc,
          void (*simulate)(double)) {
    acc += frameTime;
    int steps = 0;
    while (acc >= fixedDt && steps < maxSteps) {
        simulate(fixedDt);
        acc -= fixedDt;
        ++steps;
    }
    if (steps == maxSteps) acc = 0.0;
}
```

### 4.9（场景）确定性回放失败如何排查？

- 首要排查浮点运算顺序：并行求解会改变加法顺序，结果随之变化。
- 检查不同平台的数学库实现，三角函数与开方结果可能不同。
- 检查未初始化内存与哈希容器的遍历顺序。
- 检查物理步长、迭代次数、随机种子是否逐帧一致。
- 检查编译器优化选项是否启用了改变浮点结合律的快速数学。
- 回放记录输入与初始状态，逐帧比对状态哈希，定位首个分叉帧。

### 4.10 浮点确定性与定点数如何取舍？

- IEEE 754 的加减乘除与开方在相同舍入模式下结果一致，超越函数不保证。
- 融合乘加会改变结果，需要禁用或统一使用，不能在不同编译单元混用。
- 定点数用整数运算，结果完全确定，代价是范围与精度固定。
- 定点适合网络同步与回放，不适合动态范围大的模拟。
- 跨平台一致性还受 x87 扩展精度影响，需要统一使用 SSE 类指令集。
- 确定性通常以同一二进制、同一平台为前提，跨平台确定性的代价很高。

### 4.11 角色控制器为何常用运动学而非刚体？

- 角色需要精确响应输入，刚体的惯性与约束会让操作手感变差。
- 运动学控制器直接设定速度或位置，再用碰撞检测修正。
- 斜坡、台阶、天花板与地面吸附在刚体上难以稳定实现。
- 与动态物体交互时用推力或附加冲量近似，而非完全物理耦合。
- 胶囊体是常用形状，便于滑动与台阶检测。
- 需要单独处理高速移动与卡角，避免抖动与卡在几何接缝处。

### 4.12 动画混合树如何组织？

- 混合树按参数在多个片段之间插值，一维按标量、二维按平面分布。
- 混合权重需要归一化，权重和为零时要有兜底片段。
- 同步组让不同片段按相位对齐，避免脚步错位。
- 混合空间中的采样点应覆盖常用速度与方向组合，边界外需要钳位。
- 层级混合先混合下半身再覆盖上半身，用遮罩限定影响范围。
- 节点数量影响求值开销，深层树在大量角色同屏时成为热点。

### 4.13（辨析）线性混合与加法混合如何区分？

- 线性混合按权重加权平均姿态，权重和为 1，结果位于输入姿态的凸包内。
- 加法混合在基础姿态上叠加差值，用于呼吸、受击等局部效果。
- 加法混合的差值需要缩放，缩放过大骨骼会超出合理范围。
- 线性混合在差异大的姿态之间会产生塌陷，例如手臂穿过躯干。
- 遮罩限制混合影响的骨骼，避免上半身动作污染下半身。
- 选择依据是动作是否需要覆盖基础姿态，覆盖用线性，叠加用加法。

### 4.14 骨骼与蒙皮如何实现？

- 骨骼以层级变换表示，蒙皮把顶点按权重绑定到多根骨骼。
- 每顶点四根骨骼是常见上限，权重归一化后按量化格式存储。
- 蒙皮矩阵可在 CPU 或 GPU 计算，GPU 蒙皮把矩阵写入常量缓冲或纹理。
- 骨骼数量影响每帧上传的数据量与着色器开销。
- 双四元数蒙皮可减少关节处的体积损失，代价是额外计算与实现复杂度。
- 骨骼命名与索引映射要稳定，动画重定向与资源热重载都依赖它。

### 4.15 动画数据如何压缩与采样？

- 关键帧按误差容限剔除，曲线用线性或三次插值重建。
- 旋转用四元数压缩，去掉绝对值最大的分量并在解码时重建，注意符号连续性。
- 平移与缩放可量化，量化步长直接决定误差上限。
- 采样率降低会丢失高频细节，需要按动作类型分别设定。
- 压缩后的数据要能随机访问，否则混合时需要解码整段，影响流式加载。
- 误差指标用最大角度偏差与位置偏差，而不是压缩后的字节数。

### 4.16 反向运动学如何求解？

- 反向运动学由末端目标反解关节角度，常用两骨解析解与多骨迭代解。
- 两骨求解有闭式解，稳定且快，适合手臂与腿。
- 多骨求解用循环坐标下降或雅可比方法，收敛慢且可能抖动。
- 关节限位必须在求解中约束，否则出现反关节。
- 结果要与动画混合，权重过高会破坏原动作风格。
- 目标点不可达时要有伸展策略，避免求解发散或反复振荡。

### 4.17（场景）动画状态机切换抖动如何解决？

- 抖动多来自切换条件在边界反复满足，缺少迟滞。
- 加入进入与退出条件的时间窗或阈值差，避免临界振荡。
- 过渡时长过短会让姿态跳变，过长会让响应迟钝。
- 过渡期间再次触发切换要有优先级与打断规则。
- 根运动在过渡期叠加会导致位移突变，需要按权重分配。
- 记录切换日志，统计每秒切换次数定位异常状态。

### 4.18 物理与动画的更新顺序如何安排？

- 常见顺序是输入、动画、物理、动画后处理（反向运动学、布料），最后渲染。
- 动画驱动根运动时，物理读取根运动位移并移动胶囊体。
- 物理修正后的位置要回写给动画，否则角色与碰撞体分离。
- 布料与头发在物理之后更新，读取最终骨骼变换。
- 顺序错误会造成一帧延迟与穿模，在网络同步下还会放大。
- 固定步长物理与可变步长动画之间需要采样与插值衔接。

### 4.19（实现）动画事件与根运动如何实现？

- 动画事件按时间点触发，需要处理跨越多个事件与重复触发两种情况。
- 事件在混合时可能重复触发，按片段与归一化时间做去重。
- 根运动提取位移与旋转，应用到角色变换并从骨骼中扣除。
- 根运动在混合时按权重插值，位移需要按角色朝向变换。
- 事件回调不能在动画求值线程直接修改场景，入队到逻辑线程处理。
- 根运动与位移修正冲突时以物理结果为准，并记录偏差用于调试。

### 4.20（场景）上线后角色抖动或穿地如何排查？

- 抖动常见原因是物理与动画互相覆盖位置、求解未收敛、接触流形不稳定。
- 穿地常见原因是碰撞体与模型不匹配、地面缺失碰撞、单步位移过大。
- 检查是否有两套系统同时写角色位置，这是最常见的原因。
- 检查碰撞体的偏移与缩放是否随动画或换装变化。
- 检查地形 LOD 切换是否造成碰撞面变化。
- 用可视化调试绘制碰撞体与接触点，录制复现路径后逐帧检查。

## 5. 音视频基础

### 5.1 容器与编码的关系是什么？

- 容器负责封装：轨道、时间基、索引与元数据；编码负责压缩：把原始采样转为码流。
- 同一编码可放入不同容器，容器决定可用的封装特性与播放端兼容性。
- 容器不改变编码数据，只提供分片、索引与时间戳。
- 播放端先解析容器，再按轨道初始化解码器，两步失败原因需要分开上报。
- 封装与编码的组合要按播放端支持矩阵选择，不能只按压缩率决定。
- 转封装不重新编码即可更换容器，代价是保留原码流与原有编码参数。

### 5.2 封装格式如何选择？

- MP4 兼容性好，支持随机访问与分段，适合点播。
- Matroska 灵活，支持多轨道与字幕，播放端支持程度参差。
- MPEG-TS 适合广播与流式传输，固定包长便于丢包恢复。
- WebM 面向浏览器，编码格式受限。
- 分段格式（fMP4、HLS、DASH）适合自适应码率分发。
- 选择依据是分发方式、随机访问需求与播放端支持范围。

### 5.3（辨析）帧率、时间基与时间戳有何区别？

- 帧率是每秒帧数，时间基是时间刻度的分母，两者不是同一概念。
- 时间戳以时间基为单位，换算到秒需要除以时间基。
- 29.97 这类非整数帧率需要用有理数时间基表示，浮点会累积误差。
- 变帧率内容的时间戳不按固定间隔递增，不能假设等间隔。
- 时间基转换要避免整除截断，按有理数运算并保持单调性。
- 显示时间与解码时间分离，重排由解码顺序决定。

### 5.4 PTS、DTS 与重排如何处理？

- PTS 是显示时间，DTS 是解码时间，存在 B 帧时两者不同。
- 解码器输入顺序是解码顺序，输出顺序是显示顺序。
- 重排缓冲大小由编码的参考结构决定，缓冲不足会丢帧。
- 时间戳缺失时按帧率推算，误差会随时间累积。
- 时间戳回退或重复会导致播放端丢帧、卡住或反复跳转。
- 容器索引记录关键帧位置与时间戳，用于跳转与快速起播。

### 5.5（陷阱）时间戳回绕与不连续如何处理？

- 32 位时间戳在长时间播放后回绕，比较必须用模运算求差而不是直接比较大小。
- 直播流因重连产生时间戳跳变，需要检测并重置基准。
- 拼接不同来源的片段会产生不连续，需要重新打时间戳。
- 回绕处理错误表现为瞬间跳转或长时间卡住。
- 内部统一使用 64 位单调时间可规避，边界处再做转换。
- 检测间隔超过阈值时按不连续处理，插入静音或重置基准。

```cpp
// 32 位时间戳用模运算求差，回绕后不会误判为回退
bool isLater(unsigned a, unsigned b) {
    return static_cast<int>(a - b) > 0;
}

// 相邻时间戳间隔超过阈值时按不连续处理
bool isDiscontinuous(unsigned prev, unsigned cur, unsigned limit) {
    unsigned delta = cur - prev;
    return delta == 0 || delta > limit;
}
```

### 5.6 有损音频编码如何利用听觉特性压缩？

- 变换编码把时域采样转到频域，按临界频带分组量化，量化步长随频带能量调整。
- 心理声学模型估计掩蔽阈值，低于阈值的成分直接置零，听感上不易察觉。
- 时域掩蔽让强信号前后的弱信号可以用更粗的量化，编码器据此调整分析窗口。
- 量化噪声需要整形，把噪声推向掩蔽阈值以下的频段，避免集中在敏感区域。
- 长窗频率分辨率高，短窗抑制瞬态处的预回声，窗口切换由瞬态检测触发。
- 无损编码只做预测与熵编码，压缩率有限；有损编码才能获得数量级的压缩。

### 5.7 色彩空间与色域如何转换？

- 色彩空间由原色坐标、白点与传递函数共同定义，缺一不可。
- sRGB、Rec.709、Rec.2020 的原色与白点不同，转换需要矩阵与传递函数配合。
- 色域转换超出目标范围时需要映射，简单裁剪会改变色相。
- 元数据缺失时按默认值假设，这是偏色的常见来源。
- 合成应在线性空间完成，输出前再编码到目标传递函数。
- 不同色域的内容混用会出现偏色与过饱和，需要在合成前统一。

### 5.8（陷阱）YUV 范围与偏移如何判断？

- 有限范围把亮度映射到 16 至 235，全范围映射到 0 至 255。
- 范围标记错误会让画面发灰，或让暗部与亮部被裁切。
- 色度平面通常以半分辨率存储，采样位置影响锐度。
- 转换矩阵有 BT.601 与 BT.709 之分，标准清晰度与高清晰度内容不同。
- 矩阵与范围都来自元数据，缺失时按分辨率做启发式判断。
- 错误通常表现为整体偏绿或偏紫，而不是局部异常。

### 5.9 传递函数与 HDR 如何处理？

- 传递函数描述编码值与线性光的关系，标准动态范围常用伽马曲线，HDR 用 PQ 或 HLG。
- PQ 面向绝对亮度，HLG 面向相对亮度并兼容标准动态范围显示。
- HDR 需要元数据描述最大亮度与母版信息。
- 色调映射把高动态范围压到显示能力内，策略直接影响观感。
- 位深不足会在暗部产生色带，10 位比 8 位改善明显。
- 标准动态范围与 HDR 内容混播，需要按显示能力选择输出。

### 5.10 色度采样 4:2:0 有何影响？

- 亮度全分辨率，色度在水平与垂直方向各减半。
- 人眼对色度分辨率不敏感，相同码率下 4:2:0 明显优于 4:4:4。
- 色度子采样会让细密彩色边缘出现色渗。
- 上采样到 RGB 需要插值，插值方式影响锐度与振铃。
- 图形界面与文字内容对色度敏感，不适合 4:2:0。
- 编码前与解码后的转换都要使用同一组矩阵与范围参数。

### 5.11 码率控制模式如何选择？

- 恒定码率保持输出稳定，适合固定带宽通道，画质随内容波动。
- 可变码率按内容分配，平均码率可控，瞬时峰值可能超出通道。
- 恒定质量按量化参数分配，码率不可控，适合本地存储。
- 两遍编码先分析复杂度再分配，质量更均匀，耗时接近翻倍。
- 码率上限与缓冲区大小共同约束峰值，只设上限不设缓冲仍会突增。
- 选择依据是传输通道能力与存储成本，而不是单纯追求画质。

### 5.12（场景）码率突增导致卡顿如何解决？

- 高运动、场景切换、复杂纹理会让瞬时码率远超平均值。
- 播放端缓冲区不足时等待数据，表现为周期性卡顿。
- 缓解方式包括限制峰值码率、增大缓冲区、缩短 GOP 长度。
- 自适应码率需要多档码流与切换策略，切换点应选在关键帧。
- 监控播放端缓冲水位与卡顿次数，平均码率不能反映体验。
- 区分网络抖动与码率突增，要看丢包与重传指标。

### 5.13 GOP 与关键帧如何设置？

- GOP 是两个关键帧之间的帧序列，长度影响随机访问与压缩率。
- 关键帧可独立解码，跳转与码流切换都依赖它。
- GOP 过长会让跳转等待变长，过短会降低压缩率。
- 开放 GOP 允许参考前一个 GOP，压缩率更高但切流更复杂。
- 关键帧间隔与分段长度对齐，便于自适应码率切换。
- 场景切换处强制插入关键帧，可避免质量骤降。

### 5.14 B 帧与延迟如何权衡？

- B 帧参考前后帧，压缩率高，但需要重排缓冲。
- 重排增加解码延迟，实时通信通常禁用 B 帧。
- B 帧的参考结构决定解码顺序与显示顺序的差异。
- 低延迟配置用 P 帧与分层参考，牺牲部分压缩率换取延迟。
- 编码端与解码端的缓冲都要按最大重排深度配置。
- 延迟预算要计入网络、解码与渲染三部分，不能只看编码参数。

### 5.15 硬件解码与零复制如何实现？

- 硬件解码器输出到专用表面，格式常为半平面格式，与 RGB 不同。
- 零复制要求解码表面可直接被渲染或转换，避免回读到系统内存。
- 跨图形 API 共享需要平台特定的互操作扩展。
- 硬件解码对分辨率、位深与配置档有限制，需要提前查询能力。
- 回读会显著增加带宽与延迟，色彩转换尽量在 GPU 侧完成。
- 硬件解码失败要有软件回退路径，并在日志中记录回退原因。

### 5.16 声道布局与下混规则如何确定？

- 声道布局由通道数与排列定义，5.1 与 7.1 的通道顺序与含义不同，解析依赖布局标记。
- 下混按系数把环绕声道混入左右声道，系数过大会削波，过小会让对白变弱。
- 上混不能用复制填充，需要去相关或延迟处理，否则声场塌陷。
- 中置声道承载对白，下混时要保持其电平，不能与其他声道简单平均。
- 低频效果声道带宽有限，下混时通常单独处理而不是并入主声道。
- 布局标记缺失时按通道数猜测，多声道内容容易出现左右颠倒。

### 5.17 容器的编辑列表起什么作用？

- 编辑列表描述媒体在时间轴上的映射，可以插入空白、裁剪首尾与偏移起点。
- 音视频轨道起点不一致时用编辑列表对齐，忽略它会出现固定偏移。
- 开头的空白编辑产生静音或黑帧，不同播放器的处理差异会造成起播时长不同。
- 裁剪编辑去掉编码器预滚产生的多余帧，不裁剪会多出若干帧画面。
- 不支持编辑列表的播放器按原始时间戳播放，需要另外提供兼容封装。
- 对齐问题先用工具打印编辑列表，再判断是封装错误还是播放器忽略。

### 5.18（实现）解码器封装与送包取帧如何组织？

- 送包与取帧分离，解码器内部维护输入队列与输出队列。
- 送包返回需要更多输入或需要输出，按返回值驱动循环。
- 冲刷用于跳转与结束，跳转后要重置解码器状态。
- 输出帧的生命周期由调用方管理，硬件表面需要显式释放。
- 错误码要区分可恢复的坏包与不可恢复的流错误。
- 统计解码耗时与队列深度，定位解码瓶颈。

### 5.19 码流中的参数集与头信息起什么作用？

- 序列头描述分辨率、位深、色彩参数与配置档，解码器据此选择解码路径。
- 参数集可带外传输并被多帧引用，重复发送能提高抗丢包能力，代价是带宽。
- 图像头描述帧类型、参考关系与量化参数，缺失时该帧无法正确解码。
- 参数变化（例如分辨率切换）要求解码器重新初始化，播放端要能处理中途重建。
- 参数集与码流不一致是花屏与解码失败的常见原因，需要校验一致性。
- 带外参数集要随码流一起存储与分发，单独丢失会导致整段内容不可解。

### 5.20（场景）播放中出现块状花屏如何定位？

- 先确认花屏是否只出现在特定片段，集中在某几秒多为码流损坏或丢包。
- 查看解码器错误码，区分参考帧缺失、参数集错误与解码器内部错误。
- 用码流分析工具检查该段的参考结构与关键帧位置，确认是否缺少依赖帧。
- 检查色彩转换参数与表面格式，参数错误通常表现为整体偏色而不是块状。
- 检查硬件解码表面的同步，未完成同步就读取会出现块状异常。
- 修复方向是补发关键帧、增加冗余参数集，或切换软件解码做对照验证。

## 6. 实时音频与媒体

### 6.1 实时音频回调中为什么不能加锁、分配内存与写日志？

- 回调由驱动按固定周期触发，48 kHz、128 帧的周期为 2.67 ms，截止时间就是下一次 DMA 中断到来之前。
- 互斥锁在存在竞争时进入内核睡眠，等待时间取决于持锁者，无法给出上界；优先级反转还会进一步放大阻塞。
- `malloc` 的最坏耗时不可界，首次触碰新页会触发缺页并进入内核分配物理页，耗时从纳秒升到毫秒量级。
- 日志经 `write` 落到文件系统，涉及页缓存回写与磁盘调度，单次阻塞可达数十毫秒。
- 可行做法是在启动阶段预分配全部缓冲，回调内只做复制与索引推进，跨线程交接用无锁队列。
- `mlockall(MCL_CURRENT | MCL_FUTURE)` 可减少缺页，但栈与堆的页应在进入实时状态前全部触碰一遍。
- 若必须输出诊断信息，写入预分配的环形缓冲，由普通优先级线程异步取走。

### 6.2 自适应抖动缓冲的控制器如何设计？

- 控制目标是让播放缓冲占用稳定在目标深度，同时把附加延迟压到预算之内。
- 观测量取每个包到达时刻相对期望播放时刻的偏差，按秒级滑动窗口统计分位数。
- 目标深度按分位数乘安全系数计算并设上下限，语音场景通常落在 60 ms 至 200 ms。
- 加深要快，一次到位；减浅要慢，每若干帧降一档，并设置滞回区间避免来回调整。
- 深度变化会引起播放时间轴跳变，需用变速播放平滑，而不是直接丢包或插入静音。
- 估计器要区分网络抖动与发送端节拍不稳，后者无法通过加深缓冲消除。
- 监控延迟 P95 与欠载率的联合曲线，单独优化其中一项会牺牲另一项。

### 6.3 音频链路的端到端延迟如何拆解与测量？

- 采集侧延迟由 ADC 转换、驱动 period 与环形缓冲占用组成。
- 播放侧结构相同，period 越小延迟越低，中断频率同步上升。
- 处理侧包括回声消除、降噪、自动增益与混音，按帧处理时存在整帧延迟。
- 传输侧包括编码帧长、打包间隔、网络排队与抖动缓冲。
- 测量用硬件环回：输出接回输入，播放脉冲并测两个脉冲的间隔，得到含声卡的往返延迟。
- 驱动报告的 `snd_pcm_status_get_delay` 只反映内核缓冲，不含应用队列与网络。
- 拆解后逐段埋点，才能判断延迟回归发生在哪一段。

### 6.4（辨析）采样率与缓冲区大小对延迟的影响有何不同？

- 延迟按秒计算等于帧数除以采样率，48 kHz 下 128 帧为 2.67 ms，44.1 kHz 下同样帧数为 2.90 ms。
- 采样率决定抗混叠与抗镜像滤波器的过渡带，采样率越低过渡带越窄，滤波器阶数与群延迟越高。
- 缓冲区大小决定单次处理量与调度裕度，过小导致欠载概率上升，过大抬高延迟。
- 提高采样率缩短每块时长，但每秒回调次数与总计算量同步上升。
- 降低采样率减少带宽与计算，代价是可表示的最高频率下降。
- 采样率与设备原生值不一致时进入重采样路径，额外引入群延迟。
- 两者不可互相替代，压缩延迟应先改帧数，因为采样率受设备与内容约束。

### 6.5 音频欠载与溢出如何检测与恢复？

- ALSA 下 `snd_pcm_writei` 返回 `-EPIPE` 表示欠载，`snd_pcm_status_get_state` 返回 `SND_PCM_STATE_XRUN`。
- 恢复路径是 `snd_pcm_prepare` 后重新预填充，期间必须继续向设备送入静音，否则产生阶跃。
- 采集侧溢出表现为环形缓冲写满，需丢弃最旧数据并记录时间戳跳变。
- 统计量取欠载次数、每次恢复耗时与回调间隔直方图，分布尾部比均值更能说明问题。
- 常见根因是优先级不足、临界区过长、缺页、CPU 降频与驱动 period 过小。
- 内核提供 `xrun_debug` 开关，可在欠载时打印调用栈，用于区分应用侧与驱动侧。
- 恢复逻辑本身要可重入，连续欠载时不能累积未完成的恢复操作。

### 6.6 播放主时钟如何由已播放样本数推算？

- 主时钟取设备已播放的样本数除以采样率，得到单调递增的媒体时间。
- 已消费帧数由 `snd_pcm_delay` 一类接口给出，需扣除驱动内部缓冲与硬件 FIFO 的部分。
- 样本计数在设备暂停、重采样与切换输出时出现跳变，需做连续性校正。
- 媒体时间与流时间戳的映射由首个成功播放的包确定，之后只做缓慢修正。
- 设备时钟与系统时钟的比率由长期观测估计，用于把媒体时间换算到墙钟时间。
- 主时钟必须单调，回退会使视频调度反复等待或连续丢帧。
- 设备重置后要重建映射并通知下游，不能沿用旧的偏移。

### 6.7（输出题）下面的时基换算输出什么？

```cpp
#include <cstdint>
#include <cstdio>

int main() {
    const int64_t tb_den = 90000;   // 时基 1/90000
    const int64_t pts = 90001;
    const int64_t a = pts * 1000 / tb_den;
    const int64_t b = (pts * 1000 / tb_den) * tb_den / 1000;
    std::printf("%lld %lld\n", static_cast<long long>(a),
                static_cast<long long>(b));
}
```

- 输出为 `1000 90000`，第一次除法截掉约 1 个刻度（11 微秒），回算后 PTS 从 90001 变成 90000。
- 先除后乘会把截断误差按乘数放大，换算链越长偏差越大。
- 刻度的中间乘积在 90 kHz 时基下播放 24 小时约为 7.8e9，超过 32 位范围，必须用 64 位整数。
- 统一用整数刻度比较，避免浮点在长时间播放后累积误差。
- 需要舍入时显式加上半个除数，四舍五入方向要全局一致。
- 不同流的时基不同，比较前先换算到同一刻度。
- 负 PTS 合法，出现在 B 帧重排或起始偏移，类型必须有符号。

### 6.8 声卡回调周期与 DMA 如何配合？

- 驱动把硬件缓冲切成若干 period，DMA 每完成一段触发一次中断，回调在其中填充下一段。
- 硬件播放指针与软件写入指针之差给出可写帧数，`snd_pcm_avail` 返回该值。
- 中断到用户态回调的延迟计入总延迟，period 越小延迟越低，中断次数越多。
- 只有两段时，处理时间必须小于一段的时长，裕度很窄；四段更稳但延迟更高。
- 设备时钟由声卡晶振驱动，应用只能跟随，不能反向校正硬件指针。
- 使用 `poll` 等待时，唤醒延迟取决于调度器，定时精度不如中断驱动。

### 6.9 采样率转换为什么引入群延迟？

- 线性相位 FIR 滤波器的群延迟为 `(N - 1) / 2` 个输入样本，抽头越多延迟越大。
- 44.1 kHz 与 48 kHz 互转需要数十到数百个抽头才能达到可用的阻带衰减，群延迟随之上升。
- 多相实现按有理数比 L/M 分解，滤波器按相位分表，计算量与抽头数成正比。
- 群延迟必须计入端到端预算，否则链路延迟会比预期高出数毫秒。
- 低延迟实现缩短滤波器，牺牲阻带衰减，产生混叠与镜像。
- 频域重采样以块为单位，块长本身构成延迟。
- 比率不是有理数时只能近似，长期运行需要配合漂移补偿。

### 6.10 设备时钟漂移如何补偿？

- 声卡与对端晶振偏差典型为 ±50 ppm 至 ±100 ppm，100 ppm 在 1 小时累计 0.36 s。
- 表现为缓冲占用单调增长或单调减少，最终触发丢帧或插入静音。
- 补偿手段包括调整重采样比、周期性丢弃或复制单个样本、微调播放速率。
- 估计方法比较长期平均消费速率与到达速率，用比例积分控制器更新比率。
- 样本级增删要在幅度接近零处进行，否则产生可闻的咔嗒声。
- 估计器需滤除网络抖动，时间常数取数十秒，避免把抖动当成漂移。
- 播放速率微调会改变音调，超过一定比例可被察觉，因此只在必要时使用。

### 6.11 Android 上的低延迟采集有哪些约束？

- API 26 起提供 `AAudio`，`AAUDIO_PERFORMANCE_MODE_LOW_LATENCY` 用于申请快速通道。
- 快速通道通常要求采样率与设备原生值一致（常见 48000）、样本格式为 `FLOAT` 或 `I16`、缓冲不超过若干毫秒。
- 条件不满足时静默退化到普通通道，延迟显著上升且不报错。
- `AudioTrack` 在 API 26 起提供 `PERFORMANCE_MODE_LOW_LATENCY`，此前只能用 `OpenSL ES`。
- 实际延迟由时间戳接口结合已写帧数估算，各厂商实现差异大，属于由实现定义的量。
- 蓝牙链路延迟在百毫秒量级，不适合监听类场景。
- 音频焦点与路由变化会重建流，重建期间必须保持上层缓冲不中断。

### 6.12（场景）通话中出现与缓冲周期同频的咔嗒声，如何定位？

- 周期与缓冲周期一致，首先怀疑欠载恢复时波形不连续。
- 打印每次回调的实际间隔，与标称周期比较，观察分布的尾部。
- 用 `cyclictest` 或 `perf sched` 测调度延迟，确认是否存在更高优先级的抢占。
- 检查回调路径上的分配、锁、日志与 `std::function` 的堆分配。
- 检查 CPU 调频策略，`powersave` 下调频会使处理时间超过一段的时长。
- USB 音频设备还要看 `snd-usb-audio` 的 `nrpacks` 与隐式反馈配置。
- 修复后在波形上确认无阶跃，并长期运行确认欠载计数为零。

### 6.13（实现）如何把音频线程设置为实时优先级？

```cpp
#include <pthread.h>
#include <sys/mman.h>

bool make_realtime(int prio, int cpu) {
    if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) return false;
    sched_param sp{};
    sp.sched_priority = prio;
    if (pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp) != 0)
        return false;
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    return pthread_setaffinity_np(pthread_self(), sizeof(set), &set) == 0;
}
```

- `SCHED_FIFO` 无时间片，同优先级按入队顺序运行；`SCHED_RR` 才有时间片轮转。
- 需要 `RLIMIT_RTPRIO` 或 `CAP_SYS_NICE`，否则调用返回 `EPERM`。
- 优先级不应高于音频驱动自身的实时线程，否则回调等待驱动时反而延长整体延迟。
- 绑定到隔离核可减少干扰，隔离核上不运行普通任务与中断处理。
- cgroup 的 CPU 带宽限制同样造成延迟，实时线程需放在不受限的控制组。
- 用 `cyclictest` 观察 P99.9 的唤醒延迟，而不是只看平均值。

### 6.14 音频路径上的无锁队列如何设计？

```cpp
template <class T, size_t N>
class SpscQueue {
    static_assert((N & (N - 1)) == 0, "N 必须是 2 的幂");
    T slot_[N];
    alignas(64) std::atomic<size_t> head_{0};
    alignas(64) std::atomic<size_t> tail_{0};
public:
    bool push(const T& v) {              // 仅生产者调用
        const size_t t = tail_.load(std::memory_order_relaxed);
        if (t - head_.load(std::memory_order_acquire) == N) return false;
        slot_[t & (N - 1)] = v;
        tail_.store(t + 1, std::memory_order_release);
        return true;
    }
};
```

- 只有单生产者单消费者时，序号读写用 acquire/release 即可，无需互斥。
- 索引按 2 的幂取模，用掩码代替除法。
- 头尾指针分处不同缓存行，避免写端使读端的缓存行反复失效。
- 容量为 N 时最多存 N 个元素，用差值判断满与空，不浪费槽位。
- 消费端取不到数据时必须返回静音，不能在回调里自旋等待。
- 元素类型需可平凡复制，构造与析构都在实时路径之外完成。

### 6.15 视频解码与渲染的帧调度如何做？

- 解码与渲染解耦，中间队列保存带 PTS 的帧，队列长度决定可容忍的解码抖动。
- 渲染按显示刷新对齐，常用 `Choreographer`、`CVDisplayLink` 或 DRM 的 page flip。
- 迟到帧的处理是丢帧或重复上一帧，选择取决于内容是实时通话还是点播。
- 硬件解码输出到纹理，避免回读到 CPU 再上传，回读一次即增加数毫秒。
- 解码器缓冲深度与队列容量直接影响首帧延迟。
- 可变帧率内容按 PTS 调度，不能按固定间隔提交。

### 6.16 媒体管线的背压如何实现？

- 每级队列设上限，满时按策略丢弃：丢最旧、丢最新或只保留关键帧。
- 采集端可降帧率、降分辨率或降码率，从源头减少产出。
- 编码码率控制与网络拥塞信号联动，拥塞时主动降码率。
- 阻塞式背压会沿管线传导到采集并累积延迟，实时场景通常不接受。
- 取舍按场景确定，通话优先保证延迟，直播优先保证连续。
- 监控队列深度、丢帧率与端到端延迟的分布，而不只是均值。

### 6.17（场景）切换输出设备后播放短暂加速，原因是什么？

- 输出设备切换意味着音频时钟源更换，新旧设备的播放进度无法直接衔接。
- 若把新设备的已播放计数直接接到旧时钟上，会得到错误的时间跳变。
- 为追上流时间，播放器可能临时提高重采样比，表现为音调升高与语速加快。
- 正确做法是重建时钟映射，用一段时间的时间伸缩逐步吸收差值，单次调整幅度控制在听感阈值内。
- 蓝牙设备还有编解码缓冲与延迟报告不准的问题，切换后需要重新测量。
- 切换期间应暂停视频对齐，等主时钟稳定后再恢复丢帧策略。
- 验证方法是记录切换前后音频时钟与流时间的差值曲线，确认单调收敛而不是阶跃。

### 6.18 固定块长下的重采样与混音有哪些实现要点？

- 重采样器必须跨块保持滤波器状态，块边界不能重置。
- 混音前统一为同一采样率与样本格式，通常用 32 位浮点非交织布局。
- 相加后要预留余量或做软限幅，硬截断产生高次谐波。
- 增益变化与流切换在块边界做等功率交叉淡化，避免阶跃。
- 固定块长便于向量化与缓存复用，也便于与硬件 period 对齐。
- 采样率切换要整体重建重采样状态，不能只改参数。

### 6.19 回声消除对延迟对齐有哪些要求？

- 参考信号必须与扬声器实际播放的信号严格对齐，误差几个样本即明显降低回声抑制量。
- 采集与参考若来自不同时钟域，需要异步重采样后再送入自适应滤波器。
- 滤波器长度决定可消除的回声尾长，室内混响要求数百毫秒。
- 双讲检测决定是否冻结自适应，误判会造成回声泄漏或近端语音损伤。
- 非线性处理残留抑制用于压制线性滤波器无法消除的失真。
- 延迟由硬件与缓冲共同决定，需用脉冲响应实测峰值位置，不能只按配置推算。

### 6.20（场景）弱网通话中延迟持续增长，如何定位？

- 延迟单调增长说明抖动缓冲只加深不回收，控制器缺少收敛条件。
- 检查目标深度的计算是否只依赖历史最大值，或者降档条件永远无法满足。
- 检查是否持续触发重传与丢包隐藏，重传本身会推高延迟。
- 检查发送端的编码与打包节拍是否被拥塞控制拖慢，导致到达间隔整体后移。
- 缓冲中的旧包若按到达顺序播放而不按时间戳丢弃，延迟会不断累积。
- 修复方向是在占用超过上限时按时间戳丢弃过期包，并把延迟纳入拥塞控制信号。
- 验证方法是用固定的丢包与抖动注入，观察延迟曲线是否收敛到目标值。

## 7. 嵌入式与 RTOS

### 7.1 中断上下文为什么不能睡眠？

- 中断处理运行在被中断任务的栈上，没有独立的进程上下文，调度器无法把它挂起再恢复。
- 主动睡眠会触发调度，而调度要求可抢占的上下文，在中断中调用会破坏就绪队列与栈状态。
- 中断期间通常关闭中断或屏蔽同级中断，睡眠会使中断延迟不可控。
- 中断上下文中不能获取可能睡眠的锁，否则持锁者无法运行，形成死锁。
- 中断处理应尽快返回，把耗时工作交给下半部或任务。
- 需要等待资源时把请求入队，由任务在可睡眠的上下文中处理。
- 中断里可用的原语只有不睡眠的一类，例如自旋锁、原子操作与无锁队列。

### 7.2 上半部与下半部如何划分？

- 上半部在中断上下文执行，只做读取状态、应答中断与搬运少量数据。
- 下半部在可抢占、可睡眠的上下文执行，完成协议处理、内存分配与阻塞操作。
- 划分依据是时限，硬件要求在规定时间内应答的部分放在上半部。
- Linux 中常见的下半部机制有软中断、tasklet、工作队列与线程化中断。
- 下半部延迟计入响应时间，其与高优先级任务之间的优先级关系需要明确。
- 上半部过长会推迟同级与低优先级中断，直接抬高最坏中断延迟。
- 划分后要测量上半部的最长执行时间，而不是平均时间。

### 7.3（辨析）中断延迟、调度延迟与响应时间有何区别？

- 中断延迟指硬件产生中断到执行第一条中断指令，含流水线排空与向量取指。
- 中断响应时间指产生中断到中断服务程序完成，等于中断延迟加处理时间。
- 调度延迟指任务就绪到实际开始执行，含关中断区、内核临界区与更高优先级任务的影响。
- 响应时间指事件发生到任务完成处理，是上述各项与任务自身执行时间的总和。
- 关中断时间是中断延迟的主要来源，需统计最长关中断区而不是平均长度。
- 抢占被禁用时，调度延迟由当前任务的最长不可抢占段决定。
- 可调度性分析使用最坏响应时间，平均值对结论没有帮助。

### 7.4 RTOS 就绪表如何选出下一个任务？

- 就绪表按优先级组织位图与队列，查找最高优先级用前导零指令，代价为常数时间。
- 同优先级任务用双向链表排队，时间片耗尽后移到队尾。
- 调度决策发生在中断退出、系统调用返回与任务阻塞时。
- Cortex-M 上用 `PendSV` 完成上下文切换，把它设为最低优先级以保证中断可以嵌套。
- 切换保存的寄存器集合由 ABI 决定，调用者保存寄存器在异常入口已经入栈。
- 位图宽度决定支持的优先级级数，超出级数需要软件分组。
- 抢占式调度下，任何使高优先级任务就绪的动作都必须触发调度。

### 7.5 优先级反转如何发生，如何避免？

- 低优先级任务持有互斥量，高优先级任务等待该互斥量而被阻塞。
- 中优先级任务就绪后抢占低优先级任务，使高优先级任务的等待时间被任意延长。
- 优先级继承让持锁任务临时提升到等待者中的最高优先级，释放后恢复原值。
- 优先级天花板把互斥量的优先级设为所有可能使用者中的最高值，持有期间直接提升。
- 继承只在直接阻塞链上生效，多级嵌套时要沿链逐级传递。
- 继承不消除阻塞时间，只把阻塞限制在临界区长度之内。
- 优先级天花板可静态分析，继承更节省优先级资源，选择取决于系统规模。

### 7.6（场景）启用优先级继承后仍然超时，原因可能是什么？

- 临界区内调用了可能长时间阻塞的操作，例如写 flash 或访问慢速总线。
- 继承只覆盖直接持有者，若持锁者又在等待另一个锁，需要沿链逐级继承。
- 中断服务程序不参与继承，它在等待同一资源时仍会推迟高优先级任务。
- 多个中间优先级任务共享同一资源时，继承链会被反复重建。
- 也可能问题不在反转，而是高优先级任务本身的执行时间超出预算。
- 排查方法记录阻塞起止时间与持锁者身份，画出完整的阻塞链。
- 修复方向是缩短临界区、把 I/O 移出临界区，或改用单生产者单消费者队列。

### 7.7 看门狗如何设计才有效？

- 喂狗动作必须依赖全部关键任务都已按时运行，而不是由一个最低优先级任务定时喂狗。
- 常用做法是每个关键任务在周期内设置自己的标志位，监控任务检查全部标志后统一喂狗。
- 窗口看门狗要求喂狗落在时间窗口内，过早喂狗同样触发复位，可发现周期异常变短。
- 喂狗点不能放在会被阻塞的路径上，否则系统卡死时仍可能喂狗。
- 复位后要能区分看门狗复位与其他复位源，读取复位状态寄存器并记录。
- 调试阶段可先只记录不复位，避免开发过程被反复重启打断。
- 喂狗周期要小于溢出时间，并留出覆盖最长合法执行时间的裕度。

### 7.8 窗口看门狗与独立看门狗有何区别？

- 独立看门狗由独立时钟源驱动，主时钟失效时仍能复位。
- 窗口看门狗除超时上限外还有下限，喂狗过早被视为异常。
- 独立看门狗的时钟精度低，溢出时间偏差较大，配置时按最坏情况留裕度。
- 窗口看门狗适合检测程序跑飞后的节奏异常，例如死循环导致喂狗过快。
- 独立看门狗在低功耗模式下仍可运行，可作为深睡眠期间的兜底。
- 两者可同时启用，分别覆盖时钟失效与逻辑异常。
- 关闭看门狗只能通过特定的解锁序列，防止误写寄存器将其关闭。

### 7.9 低功耗模式与唤醒延迟如何权衡？

- 睡眠越深，关闭的时钟域与电源域越多，唤醒所需时间越长。
- 浅睡眠只关闭 CPU 时钟，唤醒在微秒级；深睡眠断电 RAM 与外设，唤醒在毫秒级。
- 选择依据是两次唤醒之间的空闲长度与可容忍的响应延迟。
- 外设唤醒源要单独配置，部分外设只能在特定睡眠模式下工作。
- 唤醒后外设需要重新初始化，这段时间计入响应时间。
- 频繁进出深睡眠的能耗可能高于保持浅睡眠，需要按占空比计算。
- 用功耗分析仪测量各模式的静态电流与唤醒波形，而不是只看数据手册。

### 7.10 tickless 空闲如何实现？

- 关闭周期性系统节拍，把下一个到期定时器的时间设为硬件唤醒点。
- 空闲期间 CPU 进入低功耗模式，定时器到期或外设中断将其唤醒。
- 唤醒后补偿流逝的时间，更新系统节拍计数，避免时间漂移。
- 长睡眠需要级联计数器，并注意定时器精度与溢出。
- 存在周期任务时收益有限，收益主要来自长空闲的应用。
- 补偿算法要处理中断延迟带来的额外时间，否则长期运行会累积误差。
- 调试时可用 GPIO 翻转观察实际睡眠时长与唤醒次数。

### 7.11 临界区为什么常与关中断绑定？

```cpp
// Cortex-M 上的关中断临界区，保存并恢复先前的中断屏蔽状态
uint32_t primask = __get_PRIMASK();
__disable_irq();
shared_counter += 1;
__set_PRIMASK(primask);
```

- 单核系统上，关中断即可阻止任务切换与中断服务程序并发访问共享数据。
- 关中断的代价是中断延迟上升，因此临界区要尽可能短。
- 多核系统上关中断只能屏蔽本核，跨核互斥还需要自旋锁。
- 关中断的嵌套需要保存与恢复先前状态，而不是无条件开中断。
- 临界区内不能调用可能睡眠的函数，否则关中断状态会延续到调度点。
- 只读共享数据且写入是原子的情况下，可用原子操作代替关中断。
- 最长关中断时间是实时性分析的关键输入，需要插桩或工具测量。

### 7.12 RTOS 中自旋锁与关中断如何配合？

- 多核上访问跨核共享数据时，先关本核中断，再取自旋锁，顺序不能颠倒。
- 先取锁后关中断会留下窗口：持锁期间被中断，中断处理再取同一把锁即自锁。
- 释放顺序相反，先放锁再开中断。
- 自旋期间浪费 CPU，临界区应只包含几条指令。
- 单核系统上自旋锁退化为关中断加标志位，不应真正自旋。
- 自旋锁不提供优先级继承，持锁任务被抢占会拖长其他核的等待。
- 中断处理与任务共享数据时，可用每核变量或禁用抢占来减少锁的使用。

### 7.13 栈溢出如何检测与预防？

- 启动时用固定图案填充栈空间，运行一段时间后检查未被覆盖的最高地址，得到高水位。
- 栈末端放置保护字，切换任务时校验，被改写即判定溢出。
- 有 MPU 时可把栈末页设为不可访问，越界立即触发异常。
- 递归、大局部数组与深调用链是常见原因，编译期可用 `-fstack-usage` 得到每个函数的用量。
- 中断嵌套会在中断栈上叠加，最坏情况要按嵌套深度计算。
- 栈大小依据高水位加裕度，裕度要覆盖最长中断路径。
- 溢出后果取决于相邻内存内容，可能静默改写其他任务的栈。

### 7.14 RTOS 的内存分配策略如何选？

- 静态分配在编译期确定全部对象，运行期无碎片，最坏耗时为零。
- 固定大小块池的分配时间是常数，碎片仅存在于不同块大小的池之间。
- 首次适配的堆分配在长期运行后产生碎片，最坏情况可能分配失败。
- TLSF 一类算法把分配时间限制在常数级，但仍需处理失败。
- 分配失败必须有确定的处理路径，不能假设总能成功。
- 堆与栈的边界在链接脚本中固定，运行时不能互相借用。
- 长期运行的系统应统计最大同时占用，再据此设定池大小。

### 7.15 消息队列与信号量的优先级语义是什么？

- 就绪任务的调度按优先级进行，但队列中消息的取出顺序由队列实现决定。
- 多数 RTOS 的队列按先进先出取消息，与发送者优先级无关。
- 等待同一信号量的多个任务被唤醒时，通常唤醒优先级最高的任务。
- 若唤醒顺序是先进先出，高优先级任务可能被低优先级任务抢先取走资源。
- 邮箱与队列在满时的行为不同：覆盖最旧、阻塞发送或返回错误，需按场景选择。
- 在中断中发送消息要用 `FromISR` 变体，并处理是否需要触发切换。
- 队列长度是延迟与内存的权衡，过短导致发送失败，过长增加排队延迟。

### 7.16 如何做可调度性分析？

- 周期任务的响应时间由自身执行时间、阻塞时间与所有更高优先级任务的干扰相加。
- 固定优先级抢占式调度可用响应时间分析迭代求解，直到收敛或超过截止时间。
- 阻塞时间取最长临界区，并考虑优先级继承后的实际上界。
- 中断与下半部要作为更高优先级的干扰项计入。
- 抖动与时钟精度要单独加到结果上，不能假设周期严格恒定。
- 分析结论依赖最坏执行时间，缺少可信的 WCET 时结论只能作为参考。
- 分析通过后仍需在目标板上测量最坏响应时间，两者互相印证。

### 7.17（场景）设备偶发死机，如何定位？

- 先确认复位源，区分看门狗、电源跌落、硬件异常与软件主动复位。
- 保留复位前的现场：把关键状态与异常栈帧写入备份寄存器或非易失存储。
- 启用 HardFault 处理，从栈帧中取出出错指令地址与状态寄存器。
- 检查是否在中断中发生了阻塞调用或栈溢出。
- 统计死机前最后执行的任务与中断，观察是否存在固定模式。
- 若与温度、供电或外设负载相关，需在相应条件下长时间复现。
- 加入轻量级的执行路径跟踪，用环形缓冲记录最近若干次任务切换。

### 7.18 看门狗复位后如何保留现场？

- 使用复位状态寄存器区分复位源，读取后清除，避免下次误判。
- 备份域寄存器在复位后保持内容，适合存放少量关键变量与计数。
- 需要更多信息时写入非易失存储，注意写入次数限制与掉电保护。
- 记录内容包括复位源、当前任务、最近一次喂狗时间与关键计数器。
- 上电时读取并上报，形成可统计的故障分布。
- 若复位发生在写入非易失存储的过程中，要有校验与版本号以识别半写状态。
- 现场记录本身不能依赖可能已经损坏的堆。

### 7.19 RTOS 与 PREEMPT_RT 的差异在哪里？

- RTOS 的内核按实时性设计，最坏关中断与关抢占区间在微秒到数十微秒量级。
- PREEMPT_RT 在通用 Linux 上把大部分不可抢占区改为可抢占，中断线程化，自旋锁改为可睡眠的互斥量。
- RTOS 的内存占用在几十 KiB 到几 MiB，Linux 通常在数十 MiB 以上。
- RTOS 缺少完整的进程隔离与虚拟内存，Linux 提供 MMU 保护与丰富的驱动。
- PREEMPT_RT 的最坏延迟仍高于专用 RTOS，来源主要是驱动与内核路径。
- 选择依据是功能复杂度与延迟指标的组合，而不是单一指标。
- 迁移时要注意页错误、调度类与中断线程的优先级配置。

### 7.20（场景）电池供电设备续航不达标，如何定位功耗异常？

- 先测整机平均电流与占空比，判断是静态电流偏高还是唤醒过频。
- 用功耗分析仪抓取唤醒波形，统计单位时间内的唤醒次数与每次持续时间。
- 常见原因是外设时钟未关闭、GPIO 悬空导致漏电、上拉电阻持续导通。
- 定时器周期过短会使 CPU 频繁唤醒，需合并周期性工作。
- 调试接口与日志输出在量产固件中未关闭，会持续消耗电流。
- 电源管理状态机要与外设状态一致，进入深睡眠前确认外设已挂起。
- 修复后在同一工况下重测平均电流与最坏唤醒延迟，两者都要满足指标。

## 8. 嵌入式 C++ 约束

### 8.1 关闭异常后错误如何传播？

- 编译选项 `-fno-exceptions` 使 `throw` 无法编译，标准库中依赖抛异常的路径随之不可用。
- 常用做法是返回错误码或状态对象，调用点必须显式检查。
- 需要携带错误上下文时用返回值加输出参数，避免动态分配。
- 构造函数无法返回错误，改用工厂函数返回状态并通过输出参数构造对象。
- 错误必须逐层传递，不能被静默忽略，可用 `[[nodiscard]]` 让编译器提示。
- 即使禁用异常，标准库的部分函数仍可能终止程序，例如 `std::vector::at` 越界。
- 若必须使用会抛异常的第三方库，应隔离在独立编译单元并核对实际行为。

### 8.2 关闭 RTTI 后多态如何实现？

- `-fno-rtti` 去掉 `typeid` 与 `dynamic_cast` 所需的类型信息，常见 ABI 下虚表不再附带类型描述指针。
- 需要运行时类型判别时，在基类中放显式的类型标识字段，用 `enum class` 或整数编码。
- 向下转换改为静态转换加类型标识校验，校验失败走错误路径。
- 访问者模式或标签分发可替代基于 RTTI 的分支。
- 去掉 RTTI 会减少只读数据与代码体积，减少量由实现定义。
- 部分标准库设施依赖 RTTI，例如 `std::function::target` 与异常类型匹配。
- 若链接了使用 RTTI 的目标文件，仍需保留类型信息，需核对全部依赖。

### 8.3 为什么嵌入式系统避免堆分配，静态分配如何落实？

- 堆分配的最坏耗时不恒定，无法满足实时约束。
- 长期运行后碎片化会使分配失败，而失败时机不可预测。
- 静态分配在编译期确定内存布局，链接阶段即可检查是否超限。
- 用固定容量的容器替代动态容器，容量作为模板参数。
- 需要可变数量对象时用对象池，池大小按最大并发数确定。
- 大对象放在静态存储区，避免占用栈。
- 若必须使用堆，应在初始化阶段完成全部分配，运行期不再申请。

### 8.4 全局对象的构造在启动流程中处于什么位置？

- 启动文件先初始化栈指针，再调用 `SystemInit` 配置时钟。
- 然后把 `.data` 段从 flash 复制到 RAM，把 `.bss` 段清零。
- 之后调用 `__libc_init_array`，逐个执行 `.init_array` 中的函数指针，完成全局对象构造。
- 最后进入 `main`，此时静态存储期对象已经构造完成。
- 同一编译单元内按定义顺序构造，跨编译单元的顺序由链接顺序决定，属于由实现定义的范畴。
- 依赖其他编译单元对象的构造函数存在初始化顺序问题，应改为显式初始化函数。
- 构造阶段发生致命错误会停在启动路径上，表现为反复复位，因此硬件自检应放在构造之前。

### 8.5 已初始化数据段与零初始化数据段在启动时分别如何处理？

- `.data` 保存有非零初值的变量，镜像存放在 flash，启动时复制到 RAM。
- `.bss` 保存零初始化变量，不占 flash 空间，启动时整段清零。
- 链接脚本给出 `_sdata`、`_edata`、`_sidata`、`_sbss`、`_ebss` 等符号供启动代码使用。
- 复制与清零的时间计入启动时间，大数组会明显延长启动。
- 未清零的 `.bss` 在复位后仍保留上次内容，依赖零初值会出错。
- 用 `__attribute__((section(...)))` 放置自定义段时，要同步更新链接脚本与启动代码。
- `.noinit` 段用于需要在复位后保留的变量，启动代码不得触碰。

### 8.6 链接脚本如何决定段布局？

- `MEMORY` 命令声明 flash 与 RAM 的起始地址、长度与属性。
- `SECTIONS` 命令按顺序放置段，中断向量表必须位于 flash 起始处。
- 段内用 `KEEP` 防止未被引用的符号被回收删除，向量表与初始化数组需要保留。
- `ALIGN` 用于满足 DMA 缓冲或缓存行对齐要求。
- 通过符号导出段边界，供启动代码与运行时使用。
- 栈顶符号通常设为 RAM 末端，栈向下增长。
- 段溢出在链接时报错，比运行时越界更早暴露问题。

### 8.7 栈大小如何确定？

- 先按任务划分栈，再用高水位统计得到每个任务的实际峰值。
- 峰值要包含最深调用链、最大局部数组与中断嵌套的开销。
- 中断若使用独立栈，需单独按嵌套深度计算。
- 递归与变长数组会使峰值不可静态分析，应在编码规范中禁用。
- 栈溢出检测依赖保护字或 MPU 区域，检测到后进入安全状态。
- 运行期统计比静态估算可靠，但要在覆盖全部工况的测试中采集。
- 最终大小取峰值加裕度，裕度按最坏中断路径与编译器版本变化预留。

### 8.8 虚函数与模板在嵌入式系统中的代价是什么？

- 虚函数通过虚表间接调用，多一次访存，且通常无法 inline 展开。
- 每个多态对象携带虚表指针，增加对象大小；虚表本身位于只读数据段。
- 模板实例化增加代码体积，多个实例可能显著膨胀 flash 占用。
- 模板可在编译期完成分派，避免运行时间接调用，适合性能敏感路径。
- 过度使用模板会导致调试信息膨胀与编译时间上升。
- 在中断处理中调用虚函数需确认目标实现的最坏执行时间。
- 是否使用取决于代码体积预算与调用频率，而不是风格偏好。

### 8.9 placement new 与内存池如何配合？

```cpp
#include <new>

alignas(16) static unsigned char storage[sizeof(Widget)];

Widget* p = new (storage) Widget(args);   // 在预分配存储上构造
// ...
p->~Widget();                              // 显式析构，存储仍可复用
```

- placement new 只调用构造函数，不分配内存，返回传入的地址。
- 存储必须满足类型的对齐要求，用 `alignas` 指定，只读存储区不能用于构造对象。
- 对象生命周期结束要显式调用析构函数，否则资源不会释放。
- 复用存储前必须确认旧对象已经析构，否则违反对象生存期规则。
- 分配器可用空闲链表管理固定大小的块，分配与释放都是常数时间。
- 重载 `operator new` 时注意 placement 形式由 `[new.delete.placement]` 规定，不可替换。

### 8.10（陷阱）`-fno-exceptions` 下 `new` 失败会怎样？

- 标准规定 `operator new` 失败时抛出 `std::bad_alloc`，禁用异常后该路径不可用。
- 常见实现改为返回空指针或直接终止，具体行为由实现定义。
- 使用 `new (std::nothrow)` 可显式要求返回空指针，但调用点仍需检查。
- 若实现选择终止，分配失败表现为复位或死循环，很难定位。
- 嵌入式项目通常重载全局 `operator new`，改为从静态池分配并在失败时记录。
- 需要核对工具链文档与实际反汇编，不能假设行为。
- 关键路径应完全避免 `new`，把失败可能性在设计阶段消除。

### 8.11 中断向量表如何定位与重定位？

- 向量表默认位于 flash 起始地址，由链接脚本固定。
- 启动时把向量表地址写入 `VTOR` 寄存器，可在 bootloader 跳转后重定位。
- 跳转到应用前要关闭中断、设置栈指针、更新 `VTOR` 并清除挂起位。
- 向量表项是函数地址，Cortex-M 上地址最低位表示 Thumb 状态。
- 用 `__attribute__((section(".isr_vector")))` 定义表并保证不被优化删除。
- 向量表长度要与实际中断数一致，越界项会进入默认处理。
- 重定位后要核对实际生效的地址，避免 bootloader 与应用共用向量表造成混乱。

### 8.12 如何把常量数据放到 flash 而不占用 RAM？

- 用 `const` 修饰且初值为编译期常量的对象通常放在只读段。
- `constexpr` 变量在可能时完全在编译期求值，不产生存储。
- 大查找表声明为 `const` 并放在只读段，链接脚本将其映射到 flash 地址。
- 含指针成员的常量结构在 flash 中仍可读，但指针必须指向 flash 内的地址。
- 需要 DMA 从 flash 直接读取时，确认总线矩阵允许该访问。
- 把只读数据错误地放入 `.data` 会同时占用 flash 与 RAM。
- 用 `size` 工具对比各段大小，确认数据落在预期的段。

### 8.13（条款）C++ 标准对动态初始化的顺序如何规定？

- `[basic.start.dynamic]` 规定，同一编译单元内具有静态存储期的对象按定义顺序初始化。
- 不同编译单元之间的顺序未指定，除少数情形外不得依赖。
- 函数内静态局部变量在首次执行到声明处时初始化。
- C++11 起该初始化是线程安全的，代价是每次访问都有一次原子检查。
- 嵌入式可用 `-fno-threadsafe-statics` 去掉该检查，代价是并发首次访问不安全。
- 常量初始化在静态初始化阶段完成，早于任何动态初始化。
- 跨单元依赖应改为显式初始化函数，由启动代码按确定顺序调用。

### 8.14 `volatile` 与 `std::atomic` 在寄存器访问上如何选择？

- 访问内存映射寄存器必须用 `volatile`，防止编译器合并、删除或重排相邻访问。
- `volatile` 不提供原子性与线程间同步语义，不能用它保护共享变量。
- 多核共享的数据用 `std::atomic`，需要顺序保证时显式指定内存序。
- 寄存器位域操作用读改写序列，读回的值可能因硬件变化而与写入不同。
- 部分外设要求访问之间插入屏障或延时，需按手册补数据同步指令。
- 编译器可能把两次 `volatile` 访问之间的普通访存重排，必要时加编译屏障。
- 同一对象不应同时承担外设寄存器与线程同步两种角色。

### 8.15 无异常环境下 RAII 如何保证资源释放？

- RAII 依赖析构函数，与异常无关；无异常时析构在正常返回与提前返回路径上都会执行。
- 提前返回要用返回值传递错误，析构仍由作用域退出触发。
- 需要跳到统一清理点时用 `goto` 或把代码封装成函数，避免手工重复释放。
- 析构函数不应失败，嵌入式里常见做法是析构只做状态复位。
- 若系统直接复位，析构不会执行，硬件状态需由启动代码重置。
- 长生命周期对象应显式提供关闭接口，析构仅作兜底。
- 析构顺序与构造顺序相反，依赖关系要按此设计。

### 8.16 如何减少 HardFault 与未定义行为？

- 打开 `-Wall -Wextra` 并处理全部告警，未初始化变量与窄化转换在嵌入式里很常见。
- 启用 `-fno-strict-aliasing` 或用 `memcpy` 做类型双关，避免别名分析导致的错误优化。
- 检查数组越界与空指针解引用，必要时用 MPU 把关键区域设为只读。
- 除零、移位越界与有符号整数溢出都是常见来源。
- 栈溢出会破坏返回地址，表现为跳转到非法地址。
- 中断与主循环共享的变量要正确标注，避免被优化掉。
- 用静态分析工具与单元测试覆盖边界条件。

### 8.17（实现）如何实现一个固定容量的对象池？

```cpp
template <class T, size_t N>
class Pool {
    alignas(T) unsigned char raw_[N][sizeof(T)];
    bool used_[N]{};
public:
    T* create() {
        for (size_t i = 0; i < N; ++i)
            if (!used_[i]) { used_[i] = true; return new (raw_[i]) T(); }
        return nullptr;
    }
    void destroy(size_t i);   // 调用 raw_[i] 对应对象的析构并复位标志
};
```

- 池的存储用 `alignas(T)` 保证对齐，块大小固定，分配是线性扫描或空闲链表。
- 线性扫描的代价是 O(N)，N 较大时改用位图加前导零指令。
- `create` 失败返回空指针，调用点必须处理。
- 对象与槽位通过下标关联，避免用指针差值反推索引。
- 池本身是静态对象，不参与堆分配。
- 并发访问需要加锁或按核分区，中断与任务共享时要关中断。

### 8.18 关键的编译与链接选项有哪些？

- `-fno-exceptions -fno-rtti -fno-threadsafe-statics` 去掉异常、类型信息与静态局部变量的保护。
- `-ffunction-sections -fdata-sections` 与 `-Wl,--gc-sections` 配合删除未引用代码。
- `-Os` 优先体积，`-O2` 优先速度，中断处理路径要核对生成的代码。
- `-Wl,-Map=out.map` 生成映射文件，用于分析段占用与符号位置。
- `-specs=nano.specs` 使用精简 C 库，`-u _printf_float` 才会链接浮点格式化。
- `-mfloat-abi` 与 `-mfpu` 要和硬件一致，混用会导致链接失败或运行异常。
- 链接顺序影响静态库的符号解析，循环依赖要用 `--start-group`。

### 8.19（场景）固件升级后启动卡死，如何定位？

- 先确认卡死位置：在启动各阶段翻转 GPIO，或用调试器暂停查看 PC。
- 常见原因是链接脚本改动导致向量表偏移，复位后取到错误入口。
- `.data` 复制源地址错误会让全局对象初值异常，构造时访问非法指针。
- 时钟配置失败会使后续外设初始化等待超时，表现为停在某个循环。
- 启动代码与库版本不匹配时，`__libc_init_array` 可能调用到未定义的符号。
- 对比升级前后的映射文件，检查段大小与符号地址变化。
- 修复后在目标板上验证冷启动、热复位与看门狗复位三条路径。

### 8.20 如何控制固件的 ROM 与 RAM 占用？

- 用 `size` 查看 text、data、bss 三段，建立每次构建的基线并纳入持续集成。
- 映射文件按符号排序，找出占用最大的函数与对象。
- 模板实例化与 inline 展开是代码膨胀的主要来源，可合并实例或改为运行时分派。
- 字符串常量与日志格式化占用可观，量产固件可移除或改为数值编码。
- `-ffunction-sections` 加 `--gc-sections` 能删除未引用代码，但被 `KEEP` 的段无法删除。
- 大数组放入 `.bss` 不占 flash，但占 RAM，两者要分别核算。
- 设置段溢出的链接期检查，并在持续集成中比较增量。

## 9. 机器人、自动驾驶

### 9.1 ROS 2 为什么选择 DDS 作为默认中间件？

- DDS 提供以数据为中心的发布订阅模型，自带服务发现、QoS 与多种传输实现。
- 去中心化发现使节点可以动态加入与退出，不需要中心 broker。
- QoS 可表达可靠性、持久性、时限与历史深度，适配从传感器数据到控制指令的不同需求。
- DDS 有标准化接口与多家实现，便于替换与互操作。
- ROS 2 通过 `rmw` 抽象层隔离具体实现，默认使用 Fast DDS，可切换到 Cyclone DDS 等。
- 代价是发现流量与配置复杂度，大规模系统需要按域划分。
- 实时性仍取决于操作系统与传输层，DDS 本身不保证截止时间。

### 9.2 DDS 的 QoS 策略如何影响行为？

- `Reliability` 取 `RELIABLE` 或 `BEST_EFFORT`，前者重传丢失样本，后者不重传。
- `Durability` 取 `VOLATILE` 或 `TRANSIENT_LOCAL`，后者让晚加入的订阅者收到历史样本。
- `History` 取 `KEEP_LAST` 加深度或 `KEEP_ALL`，决定缓存多少样本。
- `Deadline` 声明期望的更新周期，超时触发回调，可用于检测传感器掉线。
- `Liveliness` 检测发布者存活，`Lifespan` 让过期样本被丢弃。
- 发布者与订阅者的 QoS 不兼容时不会建立连接，而且通常没有明显报错。
- 控制指令多用 `RELIABLE` 加小深度，高频点云多用 `BEST_EFFORT`。

### 9.3（辨析）控制回路中应选 `RELIABLE` 还是 `BEST_EFFORT`？

- `RELIABLE` 保证不丢样本，但重传引入不确定延迟，拥塞时延迟持续增长。
- `BEST_EFFORT` 允许丢样本，延迟更可控，适合周期性传感器数据。
- 控制指令丢一条会导致状态不一致，通常需要可靠传输，但历史深度要小。
- 高频状态估计输出适合 `BEST_EFFORT`，丢弃旧样本比延迟送达更有价值。
- 选择依据是数据的时间价值，过期数据即使送达也没有用处。
- 混合策略常见：状态用 `BEST_EFFORT`，模式切换与故障通知用 `RELIABLE`。
- 需要在链路上实测丢包率与延迟分布，而不是只按语义选择。

### 9.4 ROS 2 执行器与回调组如何影响实时性？

- 单线程执行器顺序执行所有回调，任一回调阻塞都会推迟其余回调。
- 多线程执行器用线程池并行执行，并行度受回调组约束。
- `MutuallyExclusive` 回调组内同一时刻只有一个回调运行，`Reentrant` 允许并发。
- 定时器回调与订阅回调共享执行器资源，长回调会挤占控制周期。
- 实时控制回路建议使用独立线程与独立执行器，避免与其他节点竞争。
- 回调内阻塞等待服务响应会造成执行器饥饿甚至死锁。
- 需要确认执行器线程数与 CPU 核数、优先级配置相匹配。

### 9.5（场景）两个节点无法建立通信，如何排查？

- 先确认 `ROS_DOMAIN_ID` 一致，不同域之间默认不发现。
- 检查 `ROS_LOCALHOST_ONLY` 与网络接口配置，多网卡时 DDS 可能绑定到错误的接口。
- 用 `ros2 topic list` 与 `ros2 node list` 确认发现是否成功。
- 检查组播是否被交换机或防火墙阻断，必要时改为单播发现的对端列表。
- 核对 QoS 兼容性：可靠发布者与尽力而为订阅者可以连接，反向则不行。
- 检查消息类型版本是否一致，类型哈希不匹配时不会建立连接。
- 抓包确认 SPDP 与 SEDP 报文是否到达，定位是发现阶段还是数据阶段的问题。

### 9.6 时间同步为什么用 PTP 而不是 NTP？

- PTP 在局域网内的同步精度可达亚微秒级，NTP 通常在毫秒级。
- PTP 依赖硬件时间戳，把时间戳点尽量靠近物理层，消除软件栈抖动。
- gPTP（IEEE 802.1AS）面向车载与工业网络，定义了时间域与桥接行为。
- 主时钟由最佳主时钟算法选出，主时钟失效后可自动切换。
- 需要交换机支持透明时钟或边界时钟，否则排队延迟进入误差。
- 同步建立需要时间，系统启动后应等待同步稳定再启用依赖时间的算法。
- 同步状态可通过 `pmc` 或驱动接口查询，算法应能感知失步。

### 9.7 硬件时间戳与软件时间戳的差异在哪里？

- 硬件时间戳在 MAC 或 PHY 处记录报文收发时刻，不受中断延迟与调度影响。
- 软件时间戳在驱动或应用层取时间，包含中断处理与排队延迟，抖动在微秒到毫秒级。
- 相机与激光雷达的硬件触发时间戳来自传感器内部时钟，需要与系统时钟建立映射。
- 使用硬件时间戳需要网卡与驱动支持，并配置 PTP 硬件时钟设备。
- 混合使用时必须把不同时钟域换算到同一基准，换算误差直接进入融合结果。
- 传感器内部时钟也有漂移，长时间运行需要周期性重新估计偏移。
- 时间戳的来源要在消息中明确标注，下游算法不能假设精度。

### 9.8 多传感器的时间戳如何对齐？

```cpp
struct Sample { int64_t stamp_ns; double value; };

// 判断测量是否落在参考时刻附近的窗口内
bool in_window(int64_t ref_ns, const Sample& s, int64_t half_ns) {
    return s.stamp_ns >= ref_ns - half_ns &&
           s.stamp_ns <= ref_ns + half_ns;
}
```

- 统一到同一时钟域，通常以 PTP 同步后的系统时钟为基准。
- 对离散测量做插值或外推，高频 IMU 用于状态传播，相机与激光雷达用于更新。
- 对齐窗口要覆盖各传感器的最小刷新周期，窗口过小会丢失配对。
- 队列按时间戳排序，处理时取窗口内的全部测量，避免只取最新值造成信息损失。
- 时间戳误差要作为噪声项进入滤波器，不能当作精确值。
- 丢帧与乱序要有明确处理策略，不能静默跳过。
- 对齐逻辑应可离线回放验证，使用录制的数据包复现。

### 9.9（陷阱）用接收时间代替采集时间会有什么后果？

- 接收时间包含传输、排队与调度延迟，抖动可达数十毫秒。
- 高速运动时，时间误差直接换算成位置误差，30 m/s 下 10 ms 对应 0.3 m。
- 抖动使融合滤波器把时间误差误判为过程噪声，导致估计滞后或发散。
- 多传感器各自用接收时间会破坏彼此的相对时序，融合结果出现系统性偏差。
- 正确做法是使用传感器或驱动打上的采集时间戳，并补偿已知的固定延迟。
- 驱动无法提供硬件时间戳时，应测量并补偿固定偏移，同时记录抖动水平。
- 回放数据时若使用回放时刻而非记录时刻，结论不可复现。

### 9.10 相机与 IMU 的在线时间偏移如何估计？

- 把时间偏移作为状态量加入滤波器，用残差对偏移的雅可比做联合估计。
- 需要足够的激励，静止或匀速运动时偏移不可观。
- 偏移与相机外参、IMU 零偏存在耦合，需分阶段或联合标定。
- 估计收敛需要数秒到数十秒的数据，期间结果不可用于安全功能。
- 偏移初值来自硬件触发配置与数据手册，在线估计只做小范围修正。
- 偏移估计的置信度要输出给下游，失准时降级。
- 离线标定可用标定板加运动序列，结果作为在线估计的先验。

### 9.11（场景）控制环周期出现规律性抖动，如何定位？

- 先测量从定时器到期到控制输出发布的完整时间，关注分布而非均值。
- 检查控制线程的调度策略与优先级，确认是否被日志、录包或其他节点抢占。
- 检查是否有页错误、内存分配与锁竞争进入控制路径。
- 确认执行器是否与其他回调共享线程，长回调会造成周期性推迟。
- 检查 CPU 频率调节与核间迁移，绑定核心可减少抖动。
- 网络与 DDS 的发送路径也可能阻塞，确认发送是否为同步调用。
- 修复后用长时间运行的直方图验证 P99.9，而不是只看单次测量。

### 9.12 通用 Linux 上实现确定性受哪些限制？

- 默认内核存在不可抢占区，关中断与自旋锁会推迟高优先级任务。
- 页错误与内存回收会在任意时刻引入毫秒级延迟。
- 缓存与内存带宽被其他任务共享，访存延迟不可控。
- 中断可能落在任意核上，需用中断亲和性与隔离核减少干扰。
- 调度器为公平性设计，实时任务需要显式设置策略与优先级。
- PREEMPT_RT 可显著改善最坏延迟，但仍高于专用 RTOS。
- 确定性是统计意义上的上界，需要长期测量而不是单次验证。

### 9.13 消息零复制与借出消息如何工作？

- 零复制让发布者直接在中间件管理的共享内存中构造消息，避免序列化与复制。
- ROS 2 提供借用接口，发布者从中间件借出缓冲，填充后发布，所有权随之转移。
- 前提是中间件与传输支持共享内存，且发布者与订阅者在同一主机。
- 消息类型必须是可平凡复制的，内部不能含指针或动态容器。
- 订阅者数量与生命周期影响缓冲回收，缓冲耗尽时借用失败。
- 跨主机的场合仍要序列化，零复制只在进程内或共享内存路径有效。
- 使用前确认中间件实现是否真正启用共享内存传输，而不是静默退化。

### 9.14（场景）点云话题导致 CPU 占用过高，如何优化？

- 先确认瓶颈在序列化、传输还是反序列化，用剖析工具区分。
- 大点云在 `RELIABLE` 下重传会放大带宽与 CPU 开销，改为 `BEST_EFFORT` 并限制历史深度。
- 启用共享内存传输与零复制，避免每帧复制与序列化。
- 降低点云密度，或改为按需发布感兴趣区域。
- 检查订阅者数量，多订阅者会成倍增加复制与反序列化开销。
- 若下游只用部分字段，考虑自定义精简的消息类型。
- 优化后同时验证端到端延迟与 CPU 占用，避免牺牲时效换取占用。

### 9.15 回放与仿真如何保证可复现？

- 使用记录的原始数据包回放，时间戳取自记录而非回放时刻。
- 启用仿真时间，让所有节点使用同一时钟源。
- 固定随机种子与线程调度顺序，避免结果依赖并发时序。
- 记录完整的配置、标定参数与软件版本，作为回放的前置条件。
- 回放速度要与算法的时间假设一致，加速回放会改变超时行为。
- 逐帧比对结果时注意浮点运算顺序差异导致的微小偏差。
- 可复现性验证应包含从冷启动开始的完整流程。

### 9.16 从感知到控制的延迟预算如何分配？

- 先确定整车层面的闭环延迟上限，再按环节拆分。
- 采集与驱动占一部分，传感器曝光与读出不可忽略。
- 传输与中间件序列化占一部分，共享内存可将其压到最低。
- 感知算法按帧处理，帧内延迟与批处理大小相关。
- 规划与控制按周期运行，周期本身构成平均半周期的延迟。
- 执行器响应时间必须计入，制动与转向都有机械延迟。
- 预算要按 P99 分配并留出余量给最坏情况，而不是按均值分配。

### 9.17（场景）定位漂移导致误刹，如何排查？

- 先确认是否为定位跳变，比较相邻时刻的位姿差与速度的一致性。
- 检查时间同步状态，失步会让融合使用错误时间戳的数据。
- 检查传感器健康状态，包括卫星数、点云匹配得分与 IMU 饱和标志。
- 检查地图与标定版本是否匹配，外参变化会导致系统性偏差。
- 检查融合滤波器的协方差是否被低估，导致异常值被过度信任。
- 回放该时段数据，逐模块替换输入以定位引入偏差的环节。
- 修复后在同类场景复测，并把该场景加入回归用例。

### 9.18 功能安全标准对 C++ 代码有哪些约束？

- 编码规范限制语言子集，禁用动态内存、递归与部分未定义行为。
- 要求静态分析与度量，覆盖圈复杂度、注释率与函数长度等指标。
- 要求双向可追溯，需求、代码与测试用例之间建立映射。
- 对工具链做认证，编译器需提供资质材料或使用合格版本。
- 运行时要有故障检测与降级路径，例如看门狗、内存校验与合理性检查。
- 安全相关与非安全相关组件需要隔离，避免共因失效。
- 标准合规不等于安全，具体目标等级由危害分析确定。

### 9.19 多传感器融合中坐标与标定误差如何传递？

- 每个传感器有独立的坐标系，融合前统一到车辆坐标系或世界坐标系。
- 外参误差经几何关系放大，远处目标的定位误差与距离成正比。
- 内参误差影响像素到射线的映射，图像边缘区域的畸变更大。
- 标定误差要作为不确定度进入滤波器，不能当作零。
- 温度与振动会引起外参缓慢变化，需要在线监测或定期重标定。
- 坐标系手性、单位与旋转顺序的错误会造成系统性偏差，需在接口处固定约定。
- 用已知靶标做端到端验证，检查融合输出与真值的偏差分布。

### 9.20（场景）新版本发布后 CPU 负载上升两成，如何做回归定位？

- 先确认负载上升出现在哪个进程与哪个线程，用采样剖析定位热点。
- 对比版本间的消息频率、消息大小与订阅者数量变化。
- 检查是否启用了调试日志、录包或额外的可视化节点。
- 检查 QoS 变化是否引发重传或额外的反序列化。
- 检查编译器优化选项与构建类型，发布构建是否误用了调试配置。
- 用固定数据集回放，比较两个版本的函数级耗时，排除场景差异。
- 修复后在相同硬件与相同数据上复测，并把负载指标加入发布门禁。

## 10. HPC 与科学计算

### 10.1 roofline 模型如何指导优化方向？

- 横轴是算术强度，单位为每字节访存对应的浮点运算次数。
- 纵轴是可达性能，取峰值浮点性能与带宽乘以算术强度两者中的较小值。
- 拐点位于峰值浮点性能除以峰值带宽，拐点左侧为带宽受限，右侧为计算受限。
- 把内核的实际算术强度与可达性能标在图上，与实测值比较可判断差距来源。
- 带宽受限的内核应减少访存并提高复用，计算受限的内核应做向量化与指令级并行。
- 峰值性能要用实测微基准校准，厂商标称值通常不可达。
- 模型忽略延迟与缓存层次，结论需要结合硬件性能计数器验证。

### 10.2 算术强度如何计算？

- 算术强度等于浮点运算次数除以搬运字节数，字节数按实际发生的内存层次计算。
- 只统计必要访存会高估强度，应把缓存行填充与写回计入。
- 分块后每块数据在缓存中复用，有效强度按块计算。
- 不同层次的带宽不同，分别计算一级缓存、二级缓存与内存的强度更有意义。
- 可用硬件性能计数器验证浮点指令数与缓存未命中数。
- 强度接近拐点时，优化收益对常数因子敏感，需实测确认。
- 计算时区分单精度与双精度，两者的峰值差异很大。

### 10.3 如何确认循环被向量化？

- GCC 用 `-fopt-info-vec-optimized` 与 `-fopt-info-vec-missed` 输出向量化决策与原因。
- Clang 用 `-Rpass=loop-vectorize` 与 `-Rpass-missed=loop-vectorize`。
- 查看生成汇编中的向量指令与寄存器宽度，确认实际使用的宽度。
- 用性能计数器统计浮点指令数与周期数，估算每周期完成的元素数。
- 指针别名可能阻止向量化，可加入 `restrict` 或运行期别名检查。
- 循环内的函数调用、分支与数据依赖是常见阻碍。
- 向量化后性能未必提升，需检查是否引入额外的掩码与打包开销。

### 10.4（陷阱）开启 `-O3` 就一定会向量化吗？

- `-O3` 打开更多优化，但向量化仍受依赖分析与成本模型限制。
- 指针别名、非对齐访问与不确定的行程计数都会阻止向量化。
- 编译器可能判断收益不足而主动放弃向量化。
- 需要显式指定目标指令集，未开启对应扩展时不会生成宽向量指令。
- `-ffast-math` 放宽浮点语义，可能使原本不可向量化的归约变为可向量化。
- 向量化后可能出现频率下降或与标量代码混排，实际收益需测量。
- 确认方式以编译报告与汇编为准，不能只看优化级别。

### 10.5 AoS 与 SoA 的数据布局如何选择？

- AoS 把同一对象的字段放在一起，适合按对象整体访问的场景。
- SoA 把同一字段集中存放，适合按字段批量运算，便于向量化与连续访存。
- 粒子模拟、有限元等按字段遍历的内核通常从 SoA 获益。
- 需要与外部接口交换数据时，AoS 更贴近序列化格式。
- 可在热路径用 SoA、在边界处转换，转换开销要计入预算。
- 结构体填充会影响缓存行利用率，可用 `alignas` 与字段重排减少浪费。
- 选择依据是访存模式，而不是抽象的设计偏好。

### 10.6 内存带宽受限时有哪些手段？

- 提高数据复用，分块使一块数据在缓存中被多次使用。
- 降低数据宽度，精度允许时用单精度代替双精度。
- 减少不必要的写回，用流式存储避免为即将覆盖的数据触发读操作。
- 合并访问，保证连续地址与对齐，充分利用缓存行与突发传输。
- 用非临时加载绕过缓存，避免污染正在复用的数据。
- 多核共享带宽时，减少核数可能反而提高有效吞吐。
- 用带宽测试与性能计数器确认实际达到的带宽占比。

### 10.7 OpenMP 的调度策略如何选？

- `static` 在编译期划分迭代，开销最小，适合每次迭代耗时均匀的循环。
- `dynamic` 按块动态领取，适合负载不均，调度开销随线程数上升。
- `guided` 的块大小递减，兼顾负载均衡与调度开销。
- 块大小过小会加剧缓存行争用与调度开销，过大则失去均衡效果。
- `schedule(runtime)` 允许运行时通过环境变量调整，便于现场调优。
- 循环体访存密集时，划分方式会影响 NUMA 局部性。
- 选择依据是迭代耗时的方差，可先用分块计时测量分布。

### 10.8 OpenMP 线程绑定与 NUMA 如何配置？

- `OMP_PROC_BIND` 取 `close`、`spread` 或 `master`，控制线程在核间的分布。
- `OMP_PLACES` 指定绑定粒度，可取 `threads`、`cores` 或 `sockets`。
- `close` 把线程集中到同一 NUMA 节点的相邻核，利于共享缓存。
- `spread` 把线程分散到不同节点，利于利用总带宽。
- 首次触碰决定页的 NUMA 归属，并行初始化会让数据分散到各节点。
- 需要按节点分配数据时用 `numactl` 或显式的内存策略接口。
- 配置错误的表现是跨节点访存比例上升，可用计数器确认本地访存比例。

### 10.9（场景）48 核机器只发挥出 8 核的吞吐，如何定位？

- 先确认程序是否真的启动了 48 个线程，检查线程数与亲和性设置。
- 绘制扩展性曲线，从 1 核逐步增加，找出吞吐开始饱和的核数。
- 带宽饱和是最常见原因，用带宽计数器确认是否已接近峰值。
- 检查是否存在串行段，串行比例限制了加速比的上限。
- 检查锁竞争与原子操作，热点锁会把并行退化为串行。
- 检查 NUMA 局部性，跨节点访存会显著降低有效带宽。
- 检查是否触发降频，全核加速频率通常低于单核加速频率。

### 10.10 MPI 点对点通信如何避免死锁？

- 阻塞式 `MPI_Send` 在消息较大时可能等待接收者取走，双方同时发送会死锁。
- 用 `MPI_Isend` 与 `MPI_Irecv` 发起非阻塞通信，再统一 `MPI_Waitall`。
- 或按固定顺序通信，避免环形依赖。
- 非阻塞通信需要保证发送缓冲在完成前不被改写。
- `MPI_Sendrecv` 把发送与接收合并，可用于环形交换。
- 消息大小影响底层协议选择，小消息走 eager，大消息走 rendezvous。
- 调试可在单进程或小规模下用超时检测确认死锁位置。

### 10.11 MPI 集合通信的算法如何影响性能？

- `MPI_Allreduce` 常用递归倍增或 Rabenseifner 算法，后者在大消息下减少通信量。
- `MPI_Bcast` 常用二叉树或分散聚集算法，选择与消息大小和进程数相关。
- 实现会按消息大小切换算法，阈值由实现定义，可查询或调整。
- 通信域的进程排列影响拓扑感知，节点内与节点间应分层聚合。
- 同步型集合操作会放大负载不均，需先做负载均衡。
- 用工具记录每次集合通信的耗时与数据量，定位异常点。
- 自定义归约函数通常比内置函数慢，因为无法利用向量化。

### 10.12 强扩展与弱扩展如何度量？

- 强扩展固定问题规模，增加进程数，观察时间下降与效率。
- 弱扩展固定每进程的问题规模，增加进程数，观察时间是否保持恒定。
- 强扩展受串行段与通信开销限制，通常较早饱和。
- 弱扩展更能反映大规模计算的可持续性。
- 效率定义为加速比除以进程数，低于某个阈值说明扩展性不佳。
- 两种度量的基准都应包含初始化与 I/O，否则结论偏乐观。
- 报告结果时说明进程数、问题规模与硬件配置。

### 10.13（辨析）Amdahl 定律与 Gustafson 定律的适用场景有何不同？

- Amdahl 定律假设问题规模固定，加速比上限由串行比例决定。
- Gustafson 定律假设问题规模随进程数增长，以固定时间度量可扩展性。
- 前者适合评估已有问题的加速潜力，后者适合评估大规模系统的实际用途。
- 两者的串行比例定义不同，不能直接互换。
- 实际系统介于两者之间，问题规模往往随资源增长而扩大。
- 引用结论时要说明假设，否则加速比数字没有意义。
- 通信开销在两个模型中都没有直接体现，需要单独度量。

### 10.14 浮点归约为什么不可复现？

```cpp
#include <vector>

double dot(const std::vector<double>& a, const std::vector<double>& b) {
    double sum = 0.0;
    #pragma omp parallel for reduction(+ : sum) schedule(static)
    for (std::size_t i = 0; i < a.size(); ++i) sum += a[i] * b[i];
    return sum;
}
```

- 浮点加法不满足结合律，不同的求和顺序得到不同结果。
- 并行归约的划分依赖线程数、调度与分块方式，每次可能不同。
- 编译器在放宽浮点语义后可重排表达式，进一步改变结果。
- `std::reduce` 允许重排，`std::accumulate` 按顺序累加。
- 结果差异在条件数大的问题上会被放大，影响收敛判定。
- 需要可复现时固定归约树结构，并行划分与线程数保持一致。
- 补偿求和可降低对顺序的敏感性，但不能保证逐位相同。

### 10.15 Kahan 求和与 FMA 的取舍是什么？

- 朴素求和的误差随求和项数增长，正负抵消严重时相对误差显著上升。
- Kahan 求和用补偿项记录丢失的低位，代价是每次迭代增加数次浮点运算。
- 补偿项在编译器重排后可能失效，需要关闭浮点收缩或限制优化。
- 成对求和把误差从线性增长降到对数增长，且天然可并行。
- FMA 把乘加合并为一次舍入，减少误差也提高吞吐，但改变了逐位结果。
- 开启 FMA 后结果与标量版本不同，回归测试不能用逐位相等。
- 选择依据是精度要求与性能预算，而不是默认使用补偿求和。

### 10.16 GPU offload 的数据传输为什么成为瓶颈？

- 主机与设备之间的链路带宽通常远低于设备内存带宽。
- 可分页内存必须先固定才能直接传输，未固定的内存会走额外的复制路径。
- 用固定内存与异步传输可重叠计算与传输。
- 多次小传输的开销高于一次大传输，应合并批量。
- 统一内存依赖页错误迁移，首次访问开销大，且可能反复迁移。
- 计算量不足时传输时间占比高，整体反而慢于 CPU。
- 用时间线工具确认传输与计算是否真正重叠。

### 10.17 占用率与寄存器压力如何权衡？

- 每个线程使用的寄存器数决定同时驻留的线程数上限。
- 共享内存用量与线程块大小同样限制驻留块数。
- 占用率高有利于隐藏访存延迟，但寄存器溢出到本地内存会显著变慢。
- 计算密集且访存规律的内核不必追求最高占用率。
- 用编译选项限制寄存器数可提高占用率，代价是溢出到本地内存。
- 需要按实际内核测量不同配置下的吞吐，而不是只看占用率数字。
- 性能计数器可给出实际驻留线程数与停顿原因。

### 10.18（场景）GPU 版本比 CPU 版本更慢，原因可能是什么？

- 数据规模太小，传输与启动开销超过计算收益。
- 内核访存不合并，有效带宽远低于峰值。
- 分支发散严重，同一 warp 内的路径不同导致串行执行。
- 占用率过低，无法隐藏访存延迟。
- 频繁的主机与设备同步打断了流水。
- 精度选择不当，例如在消费级设备上大量使用双精度。
- 用时间线工具拆分传输、内核与同步三段耗时，再判断优化方向。

### 10.19 `-ffast-math` 与 `-march=native` 带来哪些风险？

- `-ffast-math` 放宽结合律，假设不存在 NaN 与无穷，并可能启用不精确的倒数与开方。
- 依赖 NaN 传播或逐步比较的算法在开启后会得到错误结果。
- 结果不再满足 IEEE 754 的逐位语义，回归测试必须改为容差比较。
- `-march=native` 针对构建机器的指令集生成代码，换机器可能触发非法指令。
- 两种选项都影响可复现性，需要跨平台一致的场景应禁用。
- 发布构建应显式指定目标指令集，而不是依赖构建机特性。
- 开启前先量化收益，并准备关闭后的回退路径。

### 10.20（场景）集群升级后性能回归一成半，如何定位？

- 先确认回归是全局的还是集中在特定节点与特定阶段。
- 对比升级前后的编译器版本、库版本与构建选项。
- 检查新硬件的核数与频率变化，全核频率下降会直接反映在计算受限的内核上。
- 检查 NUMA 拓扑与内存通道数是否变化，原有的绑定策略可能不再合适。
- 检查 MPI 实现的默认算法与切换阈值是否随版本改变。
- 用固定输入运行基准，记录各阶段耗时，与升级前的基线逐项比较。
- 修复后在相同节点上复测，并把基准纳入持续集成以便及早发现回归。

## 11. GUI 与桌面

### 11.1 事件循环的基本结构是什么？

- 事件循环由消息队列、等待原语与分发函数组成；Windows 上为 `GetMessage`、`TranslateMessage`、`DispatchMessage`，X11 上为 `XNextEvent` 与文件描述符轮询，Wayland 上为 `wl_display_dispatch`。
- 循环在无消息时进入内核等待，由窗口消息、定时器、I/O 完成与跨线程投递唤醒，避免忙轮询占用 CPU。
- 分发阶段同步调用窗口过程，窗口过程内的耗时直接计入该消息的处理时间，队列中的后续消息被推迟。
- 定时器精度受系统时钟节拍限制，`SetTimer` 的到期消息与输入消息共享队列，负载高时多个到期消息会合并。
- 循环退出条件通常是 `WM_QUIT`，由 `PostQuitMessage` 投递；直接调用 `exit` 会跳过窗口销毁与资源释放。
- 框架层把原生消息翻译为抽象事件，Qt 的 `QEventLoop` 还支持嵌套的局部循环，嵌套层次影响退出顺序。

```cpp
MSG msg;
while (GetMessage(&msg, nullptr, 0, 0) > 0) {
    TranslateMessage(&msg);
    DispatchMessage(&msg);
}
```

### 11.2 消息泵如何处理重入？

- 重入来源包括窗口过程内调用 `SendMessage` 到同一线程窗口、`DialogBox` 启动嵌套循环、菜单与拖放跟踪，以及 COM 套间调用期间的模态等待。
- 嵌套循环继续抽取同一线程队列的消息，外部输入可以在内层循环被处理，外层假设的状态因此被修改。
- 判定手段包括 `InSendMessage`、`GetMessageTime`、`GetQueueStatus`，以及显式的处理中标志与窗口禁用状态。
- 缓解方式是用 `PostMessage` 替代同步调用，把状态修改折叠为幂等操作，并在入口处校验对象是否已销毁。
- COM 在单线程套间中通过消息过滤完成跨套间调用，重入发生在同步调用等待期间，引用计数与状态机需要支持并发进入。
- 跨线程 `SendMessage` 在目标线程阻塞时一并挂起；目标窗口销毁后句柄失效，返回值不可靠。
- 嵌套循环依赖内层 `WM_QUIT` 退出，错误处理路径必须保证 `EndDialog` 或 `PostQuitMessage` 只执行一次。

### 11.3（实现）`WM_PAINT` 与无效区域如何工作？

- `InvalidateRect` 把矩形并入窗口更新区域，`ValidateRect` 清除区域；区域非空且队列中没有更高优先级的消息时，系统合成 `WM_PAINT`。
- `BeginPaint` 返回裁剪到更新区域的设备上下文，`EndPaint` 验证该区域；在两者之外绘制的内容会被后续绘制覆盖。
- `WM_ERASEBKGND` 负责擦除背景，返回非零表示已经处理；双缓冲可以避免闪烁，`WS_EX_COMPOSITED` 改变重绘顺序。
- 更新区域按窗口累积，`RedrawWindow` 可以强制立即重绘；相邻失效合并为一次绘制，成本与区域面积相关。
- 最小化、窗口遮挡与桌面合成都会影响重绘，`PrintWindow` 与 `WM_PRINTCLIENT` 用于离屏捕获。
- 避免在 `WM_PAINT` 内调用 `UpdateWindow` 或再次失效，否则形成递归绘制并造成消息饥饿。
- 高刷新率场景按帧节流，用 `DwmFlush` 或合成器回调对齐呈现，减少无效绘制。

### 11.4 GUI 线程为什么不能阻塞？

- 消息队列由单线程抽取，阻塞期间输入、重绘、定时器与跨线程回调全部停止，窗口进入无响应状态。
- Windows 在数秒无响应后把窗口标记为挂起，并代绘灰度窗口；`IsHungAppWindow` 可以检测该状态，自动化测试也会因此失败。
- 等待另一线程的回调容易形成环：对方通过 `SendMessage` 回到 UI 线程，双方互相等待。
- 正确做法是把耗时工作移到工作线程，完成后用 `PostMessage`、`Invoke` 或队列化回调切回 UI 线程。
- 无法避免的同步等待应使用带超时的接口，并在等待期间抽取消息，`MsgWaitForMultipleObjects` 支持这种模式。
- 长任务拆分与主动让出可以降低单次占用，消息循环的响应上限仍由最长不可分割片段决定。

### 11.5（辨析）`SendMessage` 与 `PostMessage` 有什么区别？

- `SendMessage` 同步调用目标窗口过程，同一线程内直接调用，跨线程时阻塞到对端处理完毕；`PostMessage` 只入队并立即返回。
- 跨线程发送的消息由目标线程在抽取消息时处理，发送线程挂起；目标线程忙或阻塞时，发送线程一并挂起。
- 投递消息按先进先出处理，发送消息优先级更高；`WM_PAINT` 与 `WM_TIMER` 只在队列空闲时合成。
- `SendMessage` 的返回值取决于窗口过程，窗口销毁后返回值不可靠；`PostMessage` 返回布尔值表示入队是否成功。
- 跨线程发送指针参数没有生命周期保证，接收方处理时发送方可能已经释放内存；应改用共享内存、COM 封送或复制数据。
- `SendMessageTimeout` 提供超时与 `SMTO_ABORTIFHUNG`，`InSendMessage` 与 `ReplyMessage` 用于处理发送期间的等待。
- 用户界面特权隔离会阻止低完整性进程向高完整性窗口发送消息，`ChangeWindowMessageFilterEx` 只对指定消息放行。

### 11.6 跨平台 GUI 抽象如何组织？

- 分层通常为平台后端、窗口与事件层、控件与布局层；后端暴露原生句柄，用于嵌入与系统集成。
- 事件翻译把平台消息映射为统一事件类型，键盘扫描码到字符的转换依赖键盘布局与输入法，不能只按虚拟键处理。
- 窗口句柄的生命周期与 C++ 包装对象解耦，销毁请求先标记状态，再在事件循环的安全点释放对象。
- 坐标系分为屏幕、窗口、客户区与设备像素四类，抽象层需要明确每个接口使用的单位与原点。
- 原生控件嵌入需要处理焦点、Z 序、裁剪与 DPI 变化，混合控件的事件路由比纯自绘复杂。
- 后端差异体现在模态、菜单、拖放与剪贴板协议上，统一接口往往需要保留平台特有扩展。
- 抽象成本是额外一层间接与事件转换，热路径上的分发应避免虚调用与堆分配。

### 11.7 Qt 的信号槽与事件循环如何交互？

- 信号槽由 moc 生成元对象数据，连接时记录发送者、接收者与槽索引，发射时按连接类型分发。
- `Qt::DirectConnection` 在发射线程同步调用槽，`Qt::QueuedConnection` 把调用打包为事件投递到接收者线程的队列。
- `Qt::AutoConnection` 在发射时比较线程，跨线程自动转为队列连接；队列连接要求接收者线程运行事件循环。
- 队列参数需要可复制并注册元类型，缺少 `qRegisterMetaType` 时连接失败，运行时只输出警告。
- 接收者在事件处理前被销毁时连接自动断开，裸指针捕获与 `deleteLater` 的时序仍需检查。
- 跨线程使用直接连接会在发射线程执行槽，访问接收者线程的数据需要额外同步。
- 嵌套事件循环改变队列处理顺序，模态对话框与同步等待期间仍会分发事件。

```cpp
QObject::connect(worker, &Worker::finished,
                 ui, &Widget::onFinished,
                 Qt::QueuedConnection);
```

### 11.8 COM 的引用计数有哪些规则？

- 所有接口继承 `IUnknown`，`QueryInterface` 返回新接口时递增计数，`AddRef` 与 `Release` 必须成对出现。
- 入参接口指针由调用方持有，被调方需要保存时调用 `AddRef`；出参由被调方返回已经递增的引用。
- `Release` 返回剩余计数，该值只用于调试，不能据此决定对象生命周期。
- `Microsoft::WRL::ComPtr` 与 `ATL::CComPtr` 在析构时释放，异常路径下也能避免泄漏。
- 循环引用需要弱引用或显式断开，COM 没有自动回收机制。
- 聚合与包含影响 `QueryInterface` 的转发规则，外部接口与内部接口需要分别处理。
- 跨套间传递接口指针必须封送，直接传指针只在同一套间内有效。

### 11.9（陷阱）COM 套间模型如何影响线程？

- 单线程套间每个线程一个，对象由创建线程的消息循环服务，跨套间调用通过代理封送；多线程套间由一组线程共享。
- `CoInitializeEx` 的 `COINIT_APARTMENTTHREADED` 与 `COINIT_MULTITHREADED` 决定套间类型，同一线程不能重复更改初始化模式。
- 单线程套间线程必须抽取消息，否则跨套间调用无法完成，调用方表现为挂起。
- 跨套间指针需要 `CoMarshalInterThreadInterfaceInStream` 或全局接口表，封送后的代理负责线程切换。
- 同步调用等待期间会发生重入，对象状态需要支持重入，或显式拒绝重入。
- 进程初始化需要 `CoInitializeSecurity`，默认安全级别可能阻止跨进程激活。
- 线程退出前必须配对 `CoUninitialize`，否则套间与代理资源泄漏。

### 11.10 插件 ABI 如何设计？

- 边界使用 C 调用约定与稳定布局的结构体，避免 STL 容器、异常与 RTTI 跨编译器边界传递。
- 导出工厂函数与销毁函数，版本号与结构体大小放在头部，新增字段追加到尾部并保留填充。
- 分配与释放必须在同一侧完成，插件分配的内存由插件释放，或统一使用宿主提供的分配器。
- 符号可见性用 `-fvisibility=hidden` 与显式导出宏控制，避免不同插件之间的符号冲突。
- 插件依赖的运行时（CRT、Qt、ICU）版本需要与宿主一致，或静态链接并隔离。
- 入口函数返回错误码，失败原因写入调用方提供的缓冲区，跨边界抛异常的行为由实现定义。
- 卸载前必须销毁全部对象与回调注册，否则析构代码会在已经卸载的模块中执行。

```cpp
extern "C" __declspec(dllexport)
IPlugin* CreatePlugin(uint32_t abi_version, HostServices* host);

using DestroyPlugin = void (*)(IPlugin*);
```

### 11.11 插件加载与卸载的失败路径有哪些？

- `LoadLibrary` 失败的原因包括路径错误、依赖缺失、位数不匹配、签名策略阻止，`GetLastError` 返回具体错误码。
- 依赖搜索顺序受 `SetDefaultDllDirectories`、`AddDllDirectory` 与清单影响，搜索当前目录会引入劫持风险。
- `dlopen` 的 `RTLD_NOW` 在加载时解析全部符号，`RTLD_LAZY` 把失败推迟到首次调用。
- 插件初始化可能崩溃或挂起，宿主应在独立进程或带超时的守护中加载不可信插件。
- 版本不匹配应在入口处拒绝，不能等到调用中途失败；ABI 版本与插件 API 版本分开管理。
- 卸载时仍有线程执行插件代码会导致崩溃，需要引用计数与显式的停用流程。
- 崩溃转储应记录插件路径与版本，便于区分宿主缺陷与插件缺陷。

### 11.12（场景）高 DPI 与混合缩放如何处理？

- 进程需要声明 DPI 感知级别，`SetProcessDpiAwarenessContext` 或清单中的 `dpiAwareness` 决定系统是否代为缩放；未声明时位图拉伸导致模糊。
- 每显示器 DPI 变化发送 `WM_DPICHANGED`，窗口按建议矩形调整，字体与位图需要重新加载。
- 布局使用设备无关单位，绘制前转换到物理像素，取整误差会累积为 1 像素缝隙。
- 位图资源提供多倍率版本或矢量源，缩放时按目标 DPI 选择最接近的版本。
- 窗口跨显示器拖动时可能同时覆盖不同缩放，命中测试与光标坐标必须统一到同一坐标系。
- Qt 的 `QT_SCALE_FACTOR` 与高 DPI 属性影响逻辑坐标，第三方控件可能重复应用缩放。
- 远程桌面与虚拟机的 DPI 会动态变化，测试需覆盖 100%、150%、200% 与混合缩放。

### 11.13 输入法与组合输入如何处理？

- Windows 通过 `WM_IME_STARTCOMPOSITION`、`WM_IME_COMPOSITION`、`WM_IME_ENDCOMPOSITION` 传递组字串与候选，应用负责定位候选窗口并插入最终字符。
- 组合期间不应把中间串写入文档模型，提交后再合并为一次编辑，撤销栈按一次操作记录。
- `ImmGetContext` 与 `ImmSetCompositionWindow` 设置组字位置，光标与选区变化需要同步更新。
- 文本服务框架提供更完整的文本服务，支持内嵌编辑与语音输入，接口基于 COM，需要在 UI 线程初始化。
- 自绘控件与非客户区需要显式处理输入法消息，否则候选窗口位置错误或输入丢失。
- 输入法切换、全角半角与死键影响字符映射，快捷键处理应让出尚未提交的组合。
- 跨平台框架把输入法事件映射为组合事件与提交事件，两者的顺序必须保持。

### 11.14 渲染线程与 UI 线程如何协作？

- UI 线程构建场景并提交绘制命令，渲染线程执行 GPU 提交，两者通过双缓冲或命令队列解耦。
- 垂直同步把呈现限制在刷新周期，`Present` 的等待策略影响输入延迟与撕裂。
- 提交频率高于刷新率会积压帧并增加延迟，低于刷新率则出现卡顿，需要帧率控制与丢帧策略。
- 纹理与缓冲区跨线程共享，释放必须延迟到 GPU 使用完毕，常用围栏或帧计数实现。
- 窗口尺寸与 DPI 变化需要重建交换链，重建期间绘制暂停，旧资源释放与新资源创建必须同步。
- 桌面合成器在独立进程合成，应用呈现的帧还要经过一次复制或直接扫描输出。
- 帧延迟测量用 `DwmGetCompositionTimingInfo`、GPU 时间戳与呈现统计，只统计 CPU 帧时间会低估端到端延迟。

### 11.15 模态对话框如何实现？

- 模态通过禁用所有者窗口并运行嵌套消息循环实现，`DialogBox` 的内部循环在对话框关闭时返回。
- 嵌套循环继续分发消息，主窗口的重绘与定时器仍会执行，业务代码必须假设重入。
- `EndDialog` 设置返回值并退出循环，重复调用或跨线程调用会破坏状态。
- 自定义模态应使用 `EnableWindow(FALSE)` 与独立的 `IsDialogMessage` 处理 Tab 与加速键。
- 模态期间所有者窗口不接受输入，系统菜单、任务栏激活与关闭消息仍需处理。
- 无模式窗口共享主循环，状态管理简单，但需要显式管理生命周期与焦点。
- 模态循环会推迟 `WM_QUIT` 的处理，退出流程必须保证所有嵌套循环都能结束。

### 11.16 窗口销毁与对象生命周期如何管理？

- 关闭请求先到 `WM_CLOSE`，可以在此取消；确认后 `DestroyWindow` 依次发送 `WM_DESTROY` 与 `WM_NCDESTROY`。
- `WM_NCDESTROY` 是窗口过程的最后一条消息，之后句柄失效，不能再调用窗口 API。
- 子窗口随父窗口销毁，销毁顺序决定持有资源的释放顺序。
- 跨线程投递的消息可能在销毁后到达，处理函数必须先校验句柄与对象状态。
- C++ 包装对象与原生窗口的生命周期可以分离，使用句柄映射表并在 `WM_NCDESTROY` 中移除。
- 进程退出时 `PostQuitMessage` 只结束循环，未销毁的窗口由系统回收，用户态资源仍需显式释放。
- 会话结束消息 `WM_QUERYENDSESSION` 与 `WM_ENDSESSION` 用于保存状态，处理时间受系统限制。

```cpp
case WM_NCDESTROY: {
    Widget* w = FromHandle(hwnd);
    w->OnFinalDestroy();
    return 0;
}
```

### 11.17 辅助功能接口如何暴露 UI？

- Windows 上通过 `WM_GETOBJECT` 返回 `IAccessible` 或 UIA 提供程序，跨进程调用由 COM 封送。
- 控件需要提供名称、角色、状态、值与操作，虚拟化列表按需生成子项，避免一次性构建完整树。
- UIA 调用在辅助技术进程中执行，提供程序应避免长时间阻塞 UI 线程，属性批量返回。
- 自绘控件没有系统语义，必须显式实现接口，否则屏幕阅读器只能看到空白区域。
- 焦点变化、属性变化与结构变化需要发送事件，事件过多会拖慢辅助技术。
- 高对比度、放大镜与键盘导航依赖相同的语义信息，测试可用 Inspect 与 Accessibility Insights。
- 跨进程 COM 调用的线程模型需要与套间匹配，提供程序通常在单线程套间中实现。

### 11.18（场景）桌面应用如何做崩溃恢复？

- 未处理异常通过 `SetUnhandledExceptionFilter` 或向量化异常处理程序捕获，写小型转储后终止进程。
- 崩溃报告包含模块列表、版本、命令行与最近日志，符号服务器用于还原调用栈。
- 自动保存采用增量日志与定期快照，写入临时文件后原子替换，避免半写状态。
- 恢复流程在下次启动时检测未完成会话，提示恢复或丢弃，恢复数据需要版本化。
- `RegisterApplicationRestart` 让系统在更新或重启后重新启动应用，命令行参数传递恢复标识。
- 持久化格式向前兼容，新增字段有默认值，损坏数据可以跳过，不必阻止启动。
- 转储上传受隐私与网络限制，需要脱敏并提供关闭选项。

### 11.19（辨析）Wayland 与 X11 的差异对应用有什么影响？

- X11 客户端通过协议与 X 服务器通信，窗口位置、全局坐标与输入抓取由服务器仲裁；Wayland 由合成器决定布局。
- Wayland 客户端不能直接设置全局窗口位置，弹出窗口通过 `xdg_popup` 与父表面关联，由合成器放置。
- 客户端装饰与服务器装饰通过 `xdg-decoration` 协商，标题栏与阴影需要自行绘制。
- 输入抓取、全局快捷键与屏幕捕获需要协议扩展或门户，权限模型比 X11 严格。
- X11 的网络透明性允许远程显示，Wayland 协议面向本机套接字，远程场景依赖转发层。
- 缓冲区提交与帧回调由 `wl_surface` 与 `wl_callback` 驱动，应用按合成器节奏重绘。
- 延迟与撕裂表现取决于合成器与扫描输出路径，测量需要区分合成与直出。

### 11.20（场景）界面卡顿如何定位？

- 先区分 UI 线程忙、等待同步调用、GPU 受限与合成受限，采样剖析器观察 UI 线程栈。
- Windows 上用 ETW 与 WPA 查看 `Microsoft-Windows-Win32k` 的消息处理时间，应用程序挂起事件给出无响应窗口。
- 检查跨线程 `SendMessage` 与 COM 调用，调用栈通常停在 `NtUserMessageCall` 或等待函数上。
- 绘制问题看 `WM_PAINT` 的频率与区域面积，GPU 问题看呈现队列深度与合成器丢弃的帧数。
- 定时器与动画按固定间隔触发，累积的无效区域合并后仍可能超出帧预算。
- 输入延迟与帧率下降是不同指标，需要分别记录消息入队到处理的时间与呈现时间。
- 复现环境固定 DPI、刷新率与电源模式，避免节能策略改变测量结果。

## 12. 浏览器与插件

### 12.1 浏览器多进程模型如何划分？

- 浏览器进程负责窗口、导航、权限与进程管理，渲染进程承载 Blink 与 V8，GPU 进程执行命令缓冲，网络进程处理请求，工具进程运行解码与插件。
- 站点隔离按站点分配渲染进程，跨站 iframe 以独立进程渲染，即 OOPIF。
- 进程模型由 `SiteInstance` 与 `RenderProcessHost` 管理，导航到不同站点可能触发进程交换。
- 进程复用降低内存占用，同站页面共享进程会削弱隔离，侧信道攻击推动了更细的进程划分。
- 渲染进程崩溃只影响当前站点，浏览器进程显示错误页并允许重新加载。
- Linux 上借助 zygote 预加载并派生进程，Windows 上使用受限令牌与 Job 对象创建沙箱进程。
- 进程数量受内存与策略限制，达到上限后复用进程或降级隔离。

### 12.2 站点隔离解决什么问题？

- 同源策略在渲染进程内由 Blink 执行，进程被攻破后同进程其他站点的数据暴露。
- 站点隔离把不同站点放入不同进程，跨站 iframe 通过 OOPIF 独立渲染，攻击面限制在单一站点。
- Spectre 类侧信道依赖同进程的高精度计时与共享内存，跨进程隔离提高利用门槛。
- 代价是进程数量与内存上升，跨站 iframe 的合成、输入与脚本访问需要跨进程协调。
- 隔离粒度是站点而非源，同站不同端口或子域可能仍在同一进程。
- 同步脚本访问跨站 iframe 需要代理与 IPC，部分旧接口因此受限。
- 策略可通过命令行开关或企业策略控制，调试时常关闭以简化。

### 12.3（实现）`TaskRunner` 与序列语义是什么？

- `base::SequencedTaskRunner` 保证任务按提交顺序执行，不绑定固定线程；`SingleThreadTaskRunner` 绑定线程。
- 序列是逻辑线程，多个序列可以共享线程池，序列内串行，序列间并行。
- `PostTask` 接收任务闭包与 `TaskTraits`，任务在目标序列上按序执行。
- `SequenceChecker` 与 `ThreadChecker` 在调试构建中检测跨序列访问，断言失败立即终止。
- 任务优先级由 `TaskTraits` 指定，例如 `TaskPriority::BEST_EFFORT`，队列按优先级与公平性调度。
- 序列销毁时未执行的任务被丢弃，`WeakPtr` 回调可以检测对象失效。
- 可能阻塞的任务标记 `MayBlock`，进入独立线程池，避免占满默认池。

```cpp
auto runner = base::SequencedTaskRunner::GetCurrentDefault();
runner->PostTask(FROM_HERE, base::BindOnce(&Session::Flush,
                                           weak_session));
```

### 12.4 渲染主线程与合成线程如何分工？

- 主线程执行脚本、样式、布局与绘制记录，合成线程负责滚动、变换动画与提交到 GPU。
- 合成线程持有层树与滚动偏移，主线程卡顿时滚动与不透明度动画仍可继续。
- 主线程把绘制记录提交为合成帧，合成线程按分块栅格化并按需更新。
- 主线程阻塞超过一帧时合成线程复用旧帧，输入滚动不中断，新内容延迟显示。
- 合成器线程与 Viz 组件协作，`BeginFrame` 驱动帧生产，提交与激活分离。
- 强制同步布局会延长主线程帧时间，合成线程无法弥补内容更新的延迟。
- 层树以不可变快照跨线程传递，引用计数避免锁竞争。

### 12.5 Blink 的 Oilpan 垃圾回收如何工作？

- Oilpan 是 Blink 的堆，管理 DOM 节点与脚本包装对象，采用标记清除与增量标记。
- 根包括栈、`Persistent` 句柄、跨堆引用与正在执行的任务，`Member` 表示强引用。
- 写屏障记录跨代与跨堆引用，增量标记分片执行以缩短单次停顿。
- 与 V8 的协作通过 `Trace` 与统一调度，V8 堆与 Oilpan 堆分别回收。
- 需要确定性释放的外部资源使用 `pre-finalizer` 或显式清理，不能依赖回收时机。
- 频繁创建 DOM 节点会增加标记成本，批量操作应减少临时对象。
- 调试用 DevTools 的 Memory 面板与堆快照观察存活对象与回收周期。

### 12.6 浏览器沙箱如何实现？

- Windows 上渲染进程使用受限令牌、低完整性级别、Job 对象与 AppContainer，限制文件、注册表与进程创建。
- Linux 上使用命名空间、`seccomp-bpf` 系统调用过滤与 `no_new_privs`。
- 沙箱进程通过 IPC 请求浏览器进程代为执行文件、网络与设备操作。
- 渲染进程没有直接文件系统访问，下载与上传通过共享内存与句柄传递。
- 沙箱策略按进程类型区分，GPU、网络与工具进程的权限集不同。
- 逃逸通常来自代理接口的输入校验缺陷或内核漏洞，IPC 消息必须视为不可信输入。
- 启动失败需查看 `chrome://sandbox` 与系统日志，企业策略可能禁用沙箱。

### 12.7 Mojo 的消息与接口绑定如何工作？

- Mojo 提供消息管道与数据管道，前者传控制消息，后者传字节流。
- 接口通过 `.mojom` 定义，生成代理与 stub，调用被序列化为消息，跨进程与跨线程透明。
- 消息包含接口 ID、方法序号、负载与句柄，句柄可以传递共享内存与管道。
- `mojo::Remote` 与 `mojo::Receiver` 绑定到序列，回调在绑定序列上执行。
- 关联接口保证与另一接口的消息顺序，避免额外同步。
- 同步调用被限制，阻塞等待可能死锁，异步回调是常规写法。
- 版本化通过接口版本与兼容规则处理，新增方法需要默认行为。

```cpp
mojo::Remote<mojom::OrderService> service;
service.Bind(std::move(pending));
service->Submit(std::move(order), base::BindOnce(&OnAck));
```

### 12.8 IPC 消息为什么必须做输入校验？

- 渲染进程可能被攻破，发给浏览器进程的消息不可信，字段长度、枚举值与句柄类型都要验证。
- 反序列化器检查数组长度与偏移，避免整数溢出导致越界读写。
- Mojo 生成代码做基础类型检查，语义校验仍由接收方完成，例如路径规范化与权限判断。
- 消息大小设上限，防止内存耗尽；共享内存映射前验证大小与对齐。
- 句柄传递限制类型，渲染进程不能伪造文件句柄访问任意路径。
- 校验失败应关闭管道并记录，不能继续使用部分解析的状态。
- 模糊测试 IPC 接口是发现校验缺失的常用手段。

### 12.9 GPU 进程与命令缓冲区如何工作？

- 渲染进程把图形 API 调用序列化为命令缓冲区，通过共享内存提交给 GPU 进程。
- GPU 进程维护上下文与资源，验证命令后转发给驱动，渲染进程不能直接访问 GPU。
- 资源跨进程共享使用共享内存、纹理句柄或 `GpuMemoryBuffer`，同步通过栅栏与信号量。
- 命令缓冲区有大小上限，超出时分片提交；上下文丢失需要重建资源并重放命令。
- 命令验证检查枚举、状态与资源归属，非法命令导致上下文丢失，进程本身不崩溃。
- 多进程共享 GPU 时调度影响帧延迟，优先级与抢占由 GPU 调度器决定。
- GPU 不可用时回退软件渲染，性能与特性集下降。

### 12.10 跨进程同步调用为什么危险？

- 同步 IPC 阻塞调用线程直到对端回复，若对端等待本线程持有的资源则死锁。
- 浏览器进程阻塞会停止所有渲染进程的 IPC 服务，形成全局卡顿。
- 同步调用可能触发嵌套消息循环，重入当前栈上的状态机。
- Chromium 逐步移除同步 IPC，改用异步回调与 `mojo::Remote` 的 `Then`。
- 必须同步的场景使用超时与看门狗，失败时按降级处理，不无限等待。
- IPC 日志与堆栈采样可以定位阻塞点，`chrome://tracing` 显示跨进程等待。
- 沙箱策略可能拒绝某些同步调用，错误路径需要覆盖。

### 12.11（辨析）NPAPI 与 PPAPI 为何被淘汰？

- NPAPI 让插件直接调用浏览器与系统 API，运行在进程内，崩溃与安全问题影响整个浏览器。
- PPAPI 把插件放入独立进程，提供受限接口与 2D/3D 图形，但仍需维护专有 SDK 与多进程桥接。
- 两者依赖浏览器暴露的稳定 ABI，接口演进困难，插件分发与更新不受浏览器控制。
- 现代替代是 WebAssembly、WebGL/WebGPU 与扩展 API，能力受权限模型约束。
- PDF 阅读器已经内置，Flash 已停止支持，企业场景通过独立应用或远程渲染迁移。
- 插件进程仍可作为隔离手段，CEF 等嵌入框架沿用多进程模型。
- 移除后浏览器攻击面缩小，旧插件的兼容性由外部进程或虚拟化承担。

### 12.12 CEF 的多进程集成如何组织？

- 主进程实现 `CefApp` 与 `CefClient`，子进程通过 `CefExecuteProcess` 进入对应入口。
- 进程类型包括 browser、renderer、GPU 与 utility，命令行开关决定行为。
- 回调在特定线程执行：UI 线程、IO 线程与渲染主线程，跨线程用 `CefPostTask`。
- `CefBrowserHost::SendKeyEvent` 等接口要求 UI 线程，错误线程调用会断言或崩溃。
- 自定义消息通过 `CefProcessMessage` 携带 `CefListValue` 跨进程传递。
- 关闭流程需等待 `OnBeforeClose`，浏览器对象与宿主窗口的生命周期分离。
- 版本升级要求二进制与资源文件匹配，分发包体积较大。

### 12.13 扩展的隔离模型如何工作？

- 内容脚本运行在隔离世界，共享 DOM 但使用独立的 JavaScript 全局对象。
- 扩展页面与后台脚本拥有扩展 API 权限，内容脚本通过消息传递请求特权操作。
- Manifest V3 用 Service Worker 替代持久后台页，生命周期由事件驱动。
- 权限在安装时声明，主机权限与 API 权限分开，运行时权限可以再次请求。
- 跨源请求受 CORS 与主机权限约束，扩展不能绕过同源策略读取任意响应。
- 隔离世界防止页面脚本篡改扩展逻辑，共享 DOM 仍存在点击劫持与原型污染风险。
- 扩展更新或禁用会断开消息端口，内容脚本需要处理重连。

### 12.14（实现）`v8::Isolate` 与上下文如何管理？

- `v8::Isolate` 是独立的堆与执行状态，同一 Isolate 内对象可以直接引用，跨 Isolate 需要序列化。
- `v8::Context` 是全局对象与内建对象的容器，同源页面可以共享上下文，跨源 iframe 使用独立上下文。
- 进入 Isolate 与上下文需要 `Isolate::Scope` 与 `Context::Scope`，异常用 `TryCatch` 捕获。
- 句柄作用域管理局部句柄，持久句柄跨调用存活。
- 渲染进程通常按站点或进程划分 Isolate，站点隔离后跨站对象不能直接传递。
- 微任务与事件循环由 Blink 驱动，`MicrotasksScope` 控制微任务检查点。
- 启动快照加速初始化，上下文创建仍需初始化全局对象。

```cpp
v8::Isolate::Scope isolate_scope(isolate);
v8::HandleScope handle_scope(isolate);
v8::Local<v8::Context> ctx = v8::Context::New(isolate);
v8::Context::Scope context_scope(ctx);
```

### 12.15 渲染管线的各阶段是什么？

- 解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，合并为渲染树，随后计算样式与布局。
- 绘制生成绘制记录，分块栅格化为位图，合成器按层合成。
- 样式与布局在主线程，栅格化与合成可以在合成线程或 GPU 进程完成。
- 重排影响几何，重绘只影响像素，合成只改变变换。
- 强制同步布局读取布局属性会打断批处理，导致额外重排。
- 图层提升减少重绘，但图层过多增加内存与合成成本。
- 帧预算按刷新率分配，60 Hz 为 16.7 毫秒，长任务会跨帧。

### 12.16 帧生命周期与 `requestAnimationFrame` 如何工作？

- 浏览器按 `BeginFrame` 节奏驱动帧，主线程在帧开始时执行 rAF 回调，然后执行样式、布局与绘制。
- rAF 回调在下次重绘前执行，回调内的 DOM 修改合并到同一帧。
- 帧被丢弃时 rAF 不执行，后台标签页降低频率或暂停。
- 回调时间戳是帧开始时间，与 `performance.now()` 使用同一时间基准。
- 长 rAF 回调推迟提交，合成线程可能复用旧帧。
- `requestIdleCallback` 在帧末尾空闲时执行，截止时间不保证。
- 使用 `transform` 与 `opacity` 的动画可以交给合成线程，避免主线程每帧工作。

### 12.17 渲染进程崩溃后浏览器如何处理？

- Mojo 管道断开触发 `RenderProcessHost` 的崩溃处理，浏览器标记该进程上的页面。
- 页面显示崩溃提示，用户可以重新加载，表单状态通常丢失。
- 同进程的其他站点页面一并失效，站点隔离限制了影响范围。
- 崩溃转储由 Crashpad 收集，包含进程类型、模块列表与小型转储。
- 自动重启受策略限制，连续崩溃会触发降级或禁用 GPU。
- 未提交的 IPC 消息被丢弃，浏览器侧状态需要回滚或重建。
- 扩展与 Service Worker 在渲染进程崩溃后由浏览器重新拉起。

### 12.18 网络进程与资源加载如何组织？

- 网络服务独立进程处理 DNS、连接、HTTP 缓存与代理，渲染进程通过 `URLLoader` 发起请求。
- 请求在浏览器进程做安全校验，包括 CORS、CORB 与权限检查，网络进程执行实际传输。
- 响应体通过数据管道流式传递，渲染进程按需读取，避免整体复制。
- 缓存分区按顶层站点隔离，防止跨站跟踪与缓存探测。
- 代理与证书错误在浏览器进程提示，网络进程只返回错误码。
- 请求优先级与限流影响首屏，预加载与预连接由浏览器调度。
- 网络进程崩溃只影响进行中的请求，页面可以重试。

### 12.19 浏览器中的内存安全加固有哪些？

- `PartitionAlloc` 按大小与类型分区，隔离不同对象的分配，降低溢出利用。
- 指针压缩与地址随机化提高地址猜测难度，控制流完整性限制虚调用目标。
- `raw_ptr` 与 `BackupRefPtr` 检测悬垂指针，`MiraclePtr` 在对象释放后延迟回收，直到引用计数归零。
- 沙箱与站点隔离限制漏洞影响范围，渲染进程按站点拆分。
- 堆隔离延迟复用内存，增加释放后使用的检测概率。
- 测试构建启用 sanitizer，生产构建依赖上述缓解机制。
- 分区与检查在热路径上有成本，需要按性能预算选择组合。

### 12.20（场景）页面滚动卡顿如何定位？

- 用 DevTools 的 Performance 面板录制，区分主线程长任务、合成线程与栅格化限制。
- 查看长任务与 rAF 回调耗时，定位强制同步布局与大量 DOM 修改。
- 滚动是否在合成线程处理取决于是否存在非被动滚动监听器与图层结构。
- `chrome://tracing` 查看 `BeginFrame`、`Commit`、`Raster` 与 `Draw` 的时间线。
- 图片解码与大型图层增加栅格化时间，检查图片尺寸与 `content-visibility`。
- 移动端受 CPU 与内存限制，降级策略包括减少图层与降低分辨率。
- 复现时固定设备像素比与网络条件，避免缓存与节流干扰。

## 13. 金融交易系统

### 13.1 交易系统的时延预算如何分解？

- 端到端路径分解为行情接入、解码、策略计算、风控、订单编码、网关发送与交易所确认，每段用硬件时间戳记录。
- 测量区分单向时延与往返时延，回报路径与下单路径可能不对称。
- 预算按分位数分配，P50 由主路径决定，P99 与 P999 受中断、调度与缓存未命中影响。
- 同机托管减少网络跳数，跨城链路受光速限制，微波与专线用于降低传播时延。
- 内核旁路与用户态协议栈把网络处理移出内核，代价是运维复杂度与硬件绑定。
- 每段预算保留余量，时钟同步误差计入测量不确定度。
- 预算需要与业务约束对齐，例如做市报价的有效期与撤单时限。

### 13.2（实现）行情解码如何设计？

- 常见协议包括 ITCH、FAST、SBE 与 MoldUDP64；定长字段按网络字节序读取，变长字段带长度前缀。
- 解码器避免逐字段复制，直接在接收缓冲区上解析，输出视图或就地更新订单簿。
- 消息序号用于检测丢包与乱序，缺口触发重传请求或快照恢复。
- 校验和与长度校验在边界完成，内部路径信任已经验证的数据。
- 模板化与编译期字段偏移减少分支，协议版本变化需要保留兼容路径。
- 解码线程与策略线程通过无锁队列交接，批量处理降低唤醒次数。
- 未知消息类型与字段越界记录后跳过，不能中断整个会话。

```cpp
struct MsgHeader {
    uint16_t length;   // 网络字节序
    uint16_t type;
    uint32_t seq;
};
```

### 13.3 订单簿的数据结构如何选择？

- 价格档位用数组索引，档位数量由涨跌停范围与最小变动价位决定，访问为常数时间。
- 每档内的订单用侵入式双向链表，取消订单通过订单 ID 直接定位节点。
- 订单 ID 到节点指针的映射用开放寻址哈希表，容量预分配，热路径不扩容。
- 最优价用位图或游标维护，更新时只移动游标，避免全表扫描。
- 档位结构与订单节点按访问频率布局，减少指针追逐与缓存未命中。
- 快照与增量更新分离，快照用于恢复，增量用于实时维护。
- 多品种共享内存池但按品种隔离容量，防止单品种峰值耗尽全局池。

### 13.4 订单状态机如何设计？

- 状态包括待发送、已报、部分成交、全部成交、待撤、已撤与拒绝，迁移由交易所回报驱动。
- 客户端订单 ID 用于幂等，重复发送同一 ID 视为重试，服务端去重并返回原状态。
- 状态迁移保持单调，乱序回报按序号缓存或丢弃，不能回退到旧状态。
- 本地状态与交易所状态可能短暂不一致，定时对账与查询接口用于修复。
- 撤单与成交存在竞争：撤单请求发出后仍可能成交，状态机需要允许撤单失败且已成交的终态。
- 状态变更先写日志再更新内存，崩溃恢复可以重放。
- 订单对象由池管理，终态后延迟回收，避免回报引用悬空。

```cpp
enum class OrderState : uint8_t {
    PendingNew, New, PartiallyFilled,
    Filled, PendingCancel, Canceled, Rejected
};
```

### 13.5 撮合引擎为什么通常单线程？

- 价格时间优先要求全序，单线程天然提供确定性，无需锁与原子操作。
- 单核处理能力可达数百万消息每秒，限制点通常在网络、风控与持久化。
- 多线程按品种或撮合单元并行，同一订单簿仍由单线程处理。
- 单线程避免锁竞争与缓存行抖动，延迟分布更稳定。
- 输入由定序器分配序号并写日志，重放时得到相同结果。
- 单线程故障影响全部品种，需要快速重启与状态快照。
- 水平扩展按品种分区，跨品种原子性由上层协调。

### 13.6 事前风控与事后风控如何分工？

- 事前风控在订单发出前检查额度、持仓、价格带、单笔数量与自成交，拒绝则不下发。
- 事后风控在成交后计算敞口与盈亏，用于监控与限额调整，不能阻止已经发生的成交。
- 事前检查需要在微秒级完成，数据常驻内存，避免锁与远程调用。
- 风控与策略分离部署会增加一跳，同进程内嵌可以省时延但耦合故障。
- 限额包括单笔、日内累计、按品种与按账户，检查顺序影响拒绝原因的归类。
- 自成交防范需要识别同账户或同组的对手方，订单簿需要携带账户标识。
- 风控规则变更需要版本化与回放验证，避免历史重放结果不一致。

### 13.7（实现）资金与持仓如何实时计算？

- 持仓由成交回报增量更新，下单前冻结可用数量，撤单释放冻结。
- 可用资金等于初始资金加已实现盈亏减冻结保证金，逐笔或逐日盯市由业务决定。
- 保证金按品种与组合计算，组合保证金需要跨品种风险模型，计算量更大。
- 浮盈浮亏依赖最新价，行情缺失时使用上次价格并标记陈旧。
- 并发更新采用单写者模型，读侧用快照或顺序锁，避免读到半更新状态。
- 日终结算与实时状态对账，差异需要定位到具体成交。
- 价格与金额用定点整数表示，避免浮点累积误差。

### 13.8 低延迟网络有哪些手段？

- 内核旁路：DPDK 轮询收包，Onload 在用户态实现 TCP，RDMA 用于低延迟传输。
- 忙轮询替代中断降低唤醒延迟，代价是独占 CPU 与更高功耗。
- CPU 隔离与绑核，关闭 C-states 与频率调节，减少调度抖动。
- NUMA 本地内存分配，网卡与 CPU 位于同一节点，避免跨节点访问。
- 减少内存复制：零复制收包、预分配缓冲区与批量处理。
- 协议栈裁剪：巨帧、`TCP_NODELAY`、拥塞控制与中断合并参数。
- 每种手段都有运维与兼容性成本，需要按业务时延目标取舍。

### 13.9 时钟同步如何保证？

- 使用 PTP（IEEE 1588）硬件时间戳，网卡与交换机支持透明时钟，精度可达亚微秒。
- GNSS 提供绝对时间，PTP 主时钟通常由 GNSS 驯服。
- `clock_gettime(CLOCK_TAI)` 避免闰秒跳变，日志与监管时间戳使用 TAI 或 UTC 并标注。
- 软件时间戳受中断与调度影响，精度低于硬件时间戳。
- 时钟漂移监控用 `pmc`、`phc_ctl` 与偏移直方图，超过阈值告警。
- 监管规则要求最大偏差与 UTC 溯源，审计需要保留同步证据。
- 跨机器比较时间戳前先确认时间源与同步状态一致。

### 13.10 确定性重放如何实现？

- 输入事件按序写入日志，包括行情、订单与定时器，重放时按同一顺序注入。
- 业务逻辑避免读取墙钟、随机数与未定义顺序的容器遍历。
- 浮点运算在相同编译选项与硬件下可复现，跨平台需要定点或固定舍入。
- 内存分配地址不影响结果，哈希容器遍历顺序可能影响输出，需要排序或使用稳定结构。
- 多线程重放需要固定调度或改为单线程事件循环，否则交错顺序不可复现。
- 重放用于故障复现、策略回测与合规审计，日志需要包含版本与配置。
- 重放速度可以快于实时，外部依赖需要替换为桩。

### 13.11 审计日志如何保证不丢？

- 日志先写入本地追加文件，批量 `fsync` 或使用 `O_DSYNC`，在时延与持久性之间取舍。
- 每条记录带全局序号与时间戳，接收端检测缺口并请求补发。
- 日志格式版本化，字段向前兼容，保留原始报文与解析结果。
- 多副本异步复制到异地，复制延迟计入恢复点目标。
- 磁盘写满或写入失败时进入保护状态，拒绝新订单，避免静默丢弃。
- 一次写入多次读取的存储与哈希链防止篡改，监管要求保留期限。
- 审计日志与调试日志分离，避免调试输出淹没关键记录。

### 13.12 行情数据的二进制编码为什么常用定点数？

- 交易所报价以最小变动价位为单位，定点整数可以直接表示，避免浮点舍入误差。
- 价格字段用固定宽度整数加隐含小数位，解析时不做除法，比较与累加都在整数域完成。
- 数量同样使用整数，乘价格得到金额时需要 128 位或十进制类型，避免中间溢出。
- 二进制协议按固定偏移布局，配合长度与校验和，解析可以不分配内存。
- 字节序与对齐必须显式约定，跨语言实现依赖代码生成与一致性测试。
- 文本协议（如 FIX）适合接入与审计，热路径通常在网关转换为二进制。

### 13.13（实现）交易系统如何避免动态内存分配？

- 启动时预分配订单池、行情缓冲区与队列节点，运行期只做取出与归还。
- 使用固定容量环形队列，满时按策略丢弃或阻塞，不能隐式扩容。
- 字符串与变长字段使用固定大小缓冲或 arena，避免 `std::string` 的堆分配。
- 智能指针的引用计数在热路径上有原子操作成本，可以用侵入式计数或裸指针加池管理。
- 替换分配器为线程本地缓存仍可能有锁，热路径优先使用无锁池。
- 内存不足在启动时暴露，运行期不处理 `bad_alloc`。
- 监控池的使用率与高水位，防止长尾耗尽。

```cpp
Order* o = pool_.Acquire();
if (o == nullptr) {
    metrics_.RecordPoolExhausted();
    return false;
}
```

### 13.14 交易系统中锁与无锁如何取舍？

- 单写者与多个读取线程并发时用顺序锁或原子快照，读侧无锁但可能重试。
- 跨线程队列用单生产者单消费者环形缓冲，生产者与消费者各占一个缓存行，避免伪共享。
- 多生产者需要比较交换循环或分片队列，竞争激烈时退化为锁。
- 锁的持有时间应短，避免在临界区内做 I/O 与分配。
- 实时线程使用支持优先级继承的互斥量，减少优先级反转。
- 无锁结构难以验证，内存序错误在弱内存模型上才会暴露。
- 确定性要求高的模块倾向单线程与消息传递，减少共享状态。

### 13.15 订单网关的会话管理如何做？

- FIX 会话用 `BeginString`、`SenderCompID`、`TargetCompID` 与序号标识，登录时交换序号。
- 发送序号单调递增，接收序号检测缺口，缺口触发 `ResendRequest`。
- 心跳与 `TestRequest` 检测链路存活，超时断开并重连。
- 重连后按序号补发或请求重传，应用层消息需要幂等。
- 会话状态持久化到磁盘，崩溃恢复后从最后确认序号继续。
- 多个会话共享连接时按会话 ID 路由，避免序号串扰。
- 注销与强制断开需要区分，交易所可能保留未完成订单。

### 13.16 行情缺口如何恢复？

- 每个通道维护期望序号，收到更大序号时判定缺口，缓存后续消息并请求重传。
- 重传窗口有限，超出窗口需要用快照重建订单簿。
- 快照带序号，应用后从该序号继续增量，避免重复应用。
- 多路行情源按序号与时间戳仲裁，防止状态回退。
- 缺口期间策略降级或暂停报价，避免基于陈旧订单簿交易。
- 恢复过程记录耗时与丢失消息数，用于评估链路质量。
- 心跳丢失与序号缺口是不同故障，处理路径分开。

### 13.17 尾延迟的来源有哪些？

- 中断与软中断处理、调度延迟、CPU 频率变化与 C-state 退出。
- 缓存未命中、TLB 失效、NUMA 远端访问与内存带宽争用。
- 页故障与透明大页整理，运行期应锁定内存（`mlock`）。
- 锁竞争、优先级反转、日志写入与磁盘抖动。
- 网络重传、拥塞控制、交换机缓冲与微突发。
- 监控用高精度直方图记录分位数，平均值会掩盖尾部。
- 隔离关键线程、关闭超线程与节能特性可以降低抖动。

### 13.18 灾备与主备切换如何设计？

- 主备模式分为冷备、温备与热备，恢复时间目标与恢复点目标由业务与监管决定。
- 热备持续接收行情与成交回报，状态通过复制或重放保持同步。
- 切换需要仲裁避免双主，租约与 fencing token 防止旧主继续写入。
- 未完成订单在切换后与交易所对账，必要时全部撤销。
- 会话序号与订单 ID 在切换后保持连续，避免交易所拒绝。
- 切换演练定期执行，测量实际恢复时间与数据丢失。
- 跨城复制受光速限制，强一致与低延迟存在冲突。

### 13.19 监管合规对系统有哪些约束？

- 算法交易需要报备策略标识、参数与变更，交易记录保留期限通常为 5 至 7 年。
- 时钟同步精度按监管技术标准分级，高频场景要求 100 微秒以内。
- 交易前风控与紧急停止能力是强制要求，异常时能快速停止下单。
- 审计轨迹覆盖订单全生命周期，包含决策依据与人工干预。
- 市场滥用监控需要分析订单与撤单模式，识别虚假申报与分层挂单。
- 测试环境与生产隔离，算法变更需要经过回放与仿真验证。
- 数据主权与跨境传输限制影响日志与备份的位置。

### 13.20（场景）开盘瞬间延迟飙升如何排查？

- 先确认延迟来自自身还是交易所侧，对比网关收发时间戳与交易所回报时间。
- 检查行情突发是否导致队列积压，解码线程 CPU 饱和或策略处理超时。
- 查看网络指标：丢包、重传、交换机队列丢弃与微突发。
- 检查日志与审计写入是否阻塞，磁盘 IOPS 与 `fsync` 延迟是否上升。
- 检查定时任务与批处理是否与开盘重叠，绑核是否被其他进程占用。
- 用 `perf`、off-CPU 分析与内核跟踪定位阻塞点，结合直方图观察分位数变化。
- 复盘时重放当日输入，确认修复后尾延迟回到基线。

## 14. 领域设计题

### 14.1（辨析）帧同步与状态同步如何选择？

- 帧同步只传输输入，各客户端按固定步长执行同一逻辑，带宽低，逻辑必须确定。
- 状态同步由服务器计算并下发状态，客户端插值表现，带宽随实体数增长，反外挂能力强。
- 帧同步要求定点数、稳定排序与固定时间步，浮点差异与容器遍历顺序会破坏一致性。
- 状态同步依赖兴趣管理与增量编码，服务器承担全部模拟成本。
- 混合方案由服务器权威判定关键状态，客户端预测本地表现并在纠偏时回滚。
- 选择依据包括玩家规模、作弊风险、网络抖动与开发成本。
- 回放与观战系统在两种模型下的实现差异明显，帧同步可以直接重放输入。

```cpp
constexpr int kTickMs = 33;
while (running) {
    Accumulate(elapsed);
    while (accumulator >= kTickMs) {
        StepSimulation(kTickMs);
        accumulator -= kTickMs;
    }
}
```

### 14.2 游戏服务器如何做分区与无缝地图？

- 按区域划分服务进程，玩家跨越边界时切换归属，边界两侧保留实体副本。
- 兴趣区域用九宫格或四叉树，只同步附近实体，广播量随密度上升。
- 跨服交互通过消息总线，实体 ID 全局唯一，避免不同分区冲突。
- 副本独立进程，生命周期由匹配系统管理，结束后回收端口与存档。
- 单地图承载上限由广播量与 CPU 决定，超出后分线分流。
- 边界切换需要保证状态一致，交接期间冻结或双写。
- 监控每区域实体数、消息量与帧时间，动态调整分片。

### 14.3（场景）匹配系统与对局生命周期如何设计？

- 匹配队列按评分与延迟分桶，等待时间延长后逐步放宽条件。
- 匹配成功后预留服务器资源，分配失败则回队并优先重试。
- 对局状态机包括创建、准备确认、加载、进行、结算与回收。
- 玩家掉线允许重连窗口，超时后由托管或结算规则处理。
- 资源回收释放进程、端口与存档，异常退出由看门狗清理。
- 匹配服务无状态，对局服务有状态，两者通过队列解耦。
- 指标包括匹配时长、取消率、对局质量与服务器利用率。

### 14.4 服务端反外挂有哪些约束？

- 服务器权威校验移动速度、攻击距离、冷却与视野，客户端只负责表现。
- 输入频率与时间戳异常检测，拒绝超出人类反应能力的操作。
- 随机数由服务器生成，客户端不能预测掉落与暴击。
- 行为分析用统计与机器学习识别异常胜率与操作模式。
- 客户端完整性校验提高门槛，不能作为唯一防线。
- 举报与回放系统用于人工复核，处罚分级。
- 误判成本高，封禁前需要证据链与申诉通道。

### 14.5 游戏服务器的灰度发布与回滚如何设计？

- 按服务器分组、玩家比例与地区切流，灰度批次之间保留观察窗口。
- 协议与配置版本随对局固定，新旧客户端通过能力协商共存。
- 匹配池按版本隔离，避免新版本玩家进入旧版本对局。
- 升级前停止新对局并把现有对局排空，超时对局按规则结算。
- 回滚保留旧二进制、配置与数据迁移脚本，迁移需要可逆。
- 监控错误率、匹配时长、对局完成率与崩溃率，异常时自动切回。
- 回滚后保留现场日志与版本号，便于定位兼容性问题。

### 14.6（辨析）直播与点播的媒体管线差异如何体现？

- 直播以低延迟为目标，缓冲小，允许丢帧与降质；点播以连续播放为目标，缓冲大，允许预取。
- 直播的时钟跟随源，不能暂停；点播的时钟由播放器控制，支持变速与跳转。
- 直播需要抗抖动与丢包恢复，常用前向纠错与选择性重传；点播依赖缓存与预读。
- 直播的启动延迟预算紧张，点播可以用启动缓冲换取抗抖动能力。
- 直播的 GOP 通常更短以便快速接入，点播可以用更长 GOP 提高压缩率。
- 点播跳转需要关键帧索引，直播跳转只能到最新关键帧或触发新请求。
- 两条管线共用解码与渲染，差异集中在源、缓冲与时钟策略。

### 14.7 录制与转码管线如何设计？

- 录制从解码后的帧或原始码流取数据，按时间戳切片，切片边界对齐关键帧。
- 转码包括解码、滤镜、缩放、重编码与封装，硬件编码器降低 CPU 占用。
- 多路输出用同一解码结果分发，编码器按目标码率与分辨率独立配置。
- 时间戳在转码后重新计算，避免累积漂移；B 帧与重排改变输出顺序。
- 切片与封装需要处理音视频交错、索引与元数据，崩溃后可从最后一个完整切片恢复。
- 质量与速度的取舍体现在预设、码率控制与前瞻帧数，实时转码通常关闭前瞻。
- 转码管线的背压由编码器吞吐决定，队列满时丢帧或降速。

### 14.8 媒体管线的错误恢复与降级如何设计？

- 错误分类为源断开、解复用失败、解码错误、渲染设备丢失与网络抖动。
- 解码错误可以跳过损坏帧、重置解码器或请求关键帧，连续失败升级为重建管线。
- 源断开按指数退避重连，保留播放位置与缓冲策略。
- 渲染设备丢失需要重建交换链与纹理，音频设备切换需要重新打开设备。
- 降级路径包括降低分辨率、关闭硬件加速、切换协议或仅保留音频。
- 用户可见状态区分缓冲、重连与失败，错误码上报用于统计。
- 恢复过程记录耗时与丢失帧数，避免静默降质。

### 14.9 多路视频解码如何调度硬件资源？

- 硬件解码会话数有限，超出后回退软件解码或拒绝新流。
- 按分辨率、帧率与可见性分配优先级，后台流降低帧率或暂停。
- 显存与表面池按流预分配，超出预算时降级分辨率。
- 解码器实例可以共享上下文，但状态独立，切换需要同步。
- 多路输出共享渲染器时按合成顺序提交，避免频繁切换上下文。
- 调度策略需要防止单流占满硬件，使用配额与抢占。
- 监控每路解码耗时、丢帧与硬件队列深度。

### 14.10 媒体管线的可观测性指标如何设计？

- 指标覆盖各阶段队列深度、处理耗时、帧率、丢帧与错误码。
- 端到端延迟用采集、编码、传输、解码与呈现的时间戳差值计算。
- 音视频偏移单独记录，避免被平均延迟掩盖。
- 指标按流与会话维度聚合，直方图保留分位数。
- 追踪采样避免在回调内做字符串拼接与锁操作。
- 日志环形缓冲记录最近事件，崩溃时随转储保存。
- 告警区分源侧、网络侧与本地渲染侧，减少误报。

### 14.11 安全启动与固件度量如何设计？

- 信任根存放在不可修改的引导区，逐级校验下一级镜像的签名与哈希。
- 签名使用私钥在发布端生成，设备端只保存公钥或公钥哈希。
- 度量值扩展到受保护的寄存器或 TPM，启动日志用于远程证明。
- 校验失败进入恢复模式，允许签名的恢复镜像重新烧写。
- 回滚保护用单调计数器防止降级到有漏洞的旧版本。
- 调试接口在生产固件中关闭或鉴权，防止绕过校验。
- 启动时间与校验范围需要权衡，可以只校验关键段并延迟校验其余部分。

### 14.12 固件的内存保护与任务隔离如何设计？

- MPU 区域划分代码只读段、外设、任务栈与共享数据，权限按任务配置。
- 任务切换时重配 MPU，切换开销计入调度延迟。
- 栈溢出用保护页与填充检测，故障处理程序识别访问地址与任务。
- 共享缓冲区通过消息队列复制或所有权转移，避免越界写入。
- 驱动运行在特权级，应用任务受限，服务请求通过受控入口进入。
- 隔离不能替代静态分析与边界检查，仍需断言与参数校验。
- 调试时保留故障现场，记录区域配置与最近一次切换。

### 14.13 固件 OTA 如何保证原子性？

- 下载到备用分区，校验签名与版本后切换启动标志。
- 写入过程掉电时，引导程序检测镜像不完整并回退到旧分区。
- 引导程序维护启动尝试计数，连续失败自动回滚。
- 元数据双份存储并带 CRC，更新顺序保证任一时刻有有效副本。
- 传输层支持断点续传与分块校验，减少重传。
- 升级期间延长看门狗超时或暂停喂狗，避免误复位。
- 回滚后上报失败原因，便于定位兼容性问题。

```cpp
struct SlotMeta {
    uint32_t version;
    uint32_t length;
    uint32_t crc;
    uint8_t  valid;
};
```

### 14.14 安全关键固件的故障降级如何设计？

- 区分失效安全与失效可用：前者关闭输出，后者保留有限功能。
- 冗余通道比较输出，偏差超限时切换到备用通道或进入安全状态。
- 降级模式定义明确的能力集合与切换条件，避免部分功能不可预测。
- 故障检测覆盖传感器、执行器、通信与电源，检测延迟计入响应时间。
- 降级与恢复需要防抖，避免在阈值附近反复切换。
- 所有切换记录时间、原因与版本，供事后分析。
- 安全状态的设计需要独立于主处理器，必要时由外部监控电路执行。

### 14.15 固件的现场诊断数据如何设计？

- 环形日志保存在非易失存储，按严重级别与模块过滤，写入磨损均衡。
- 复位原因、程序计数器、栈指针与任务状态在启动时保存。
- 断言与硬件异常处理程序收集寄存器与调用栈，写入故障记录区。
- 诊断数据带版本与 CRC，读取时校验完整性。
- 上传按网络条件批量进行，失败保留在本地并限制总量。
- 隐私与安全要求脱敏，调试接口在生产环境关闭。
- 诊断数据的写入路径不能阻塞实时任务，使用独立低优先级任务。

### 14.16（场景）交易网关如何做多交易所订单路由？

- 路由表按品种、账户与交易所状态选择目的地，支持主备与拆分下单。
- 决策依据包括报价、延迟、手续费与可用额度，最优执行需要实时行情。
- 拆单需要保证总量与价格约束，子单状态汇总为父单状态。
- 撤单按原路由返回，交易所不可达时进入待确认状态。
- 路由切换需要防止重复下单，客户端订单 ID 全局唯一。
- 每个交易所的会话与序号独立管理，路由层不共享序号空间。
- 监控各交易所的成交率、延迟与拒绝率，异常时调整权重。

### 14.17 交易网关的过载保护如何设计？

- 入口用令牌桶与并发上限限制速率，按账户与消息类型分配配额。
- 队列按优先级分层，撤单与风控指令优先于新单。
- 队列深度与处理延迟触发背压，向上游返回可重试错误。
- 过载时拒绝新单并保留撤单能力，避免风险敞口失控。
- 批量发送与合并减少系统调用，但不改变消息顺序与语义。
- 限流参数动态调整并审计，防止误配置导致全部拒绝。
- 监控丢弃数、拒绝率与队列等待时间，压测验证上限。

### 14.18 交易网关的灰度升级如何保证订单不丢？

- 升级前停止接收新会话，等待在途订单进入终态或转交。
- 新旧版本共享会话状态存储，序号与订单状态保持一致。
- 协议保持向后兼容，新增字段可选，旧版本忽略未知字段。
- 滚动升级按实例分批，负载均衡摘除旧实例后排水。
- 升级期间禁止修改路由表与风控参数，减少变量。
- 回滚保留旧二进制与会话快照，回滚后核对未完成订单。
- 升级窗口与交易所维护窗口对齐，避免跨日或开盘时段。

### 14.19 多协议适配层如何设计？

- 协议层抽象为编码、解码、会话与错误映射，业务层使用统一订单模型。
- FIX、二进制与私有协议在网关转换，字段映射表版本化。
- 枚举与状态码映射需要处理未知值，保留原始码。
- 协议差异包括序号、心跳、重传与撤单语义，适配层不能假设一致。
- 代码生成减少手工解析错误，生成代码纳入版本管理。
- 一致性测试用录制回放与交易所仿真环境。
- 新协议上线灰度，按账户或品种切流。

### 14.20（场景）如何为交易网关做端到端可观测性？

- 每条消息记录硬件与软件时间戳，覆盖入队、出队、发送与确认。
- 指标用直方图而非平均值，暴露 P50、P99 与 P999。
- 追踪 ID 贯穿策略、风控与网关，采样避免热路径开销。
- 日志异步写入，环形缓冲满时丢弃低优先级记录并计数。
- 告警基于滑动窗口与基线，区分行情突增与系统故障。
- 时钟同步状态作为指标，时间戳不可比时告警。
- 复盘工具按序号重放并对比预期与实际的时延分布。
