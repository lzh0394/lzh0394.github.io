C 与 C++ 共享同一套单独编译（separate compilation）模型：每个源文件通常独立翻译成目标文件，链接器再把目标文件与库合成可执行文件或共享库。模型的核心约束只有一条：编译器一次只处理一个翻译单元，跨翻译单元的信息只剩符号、重定位与 ABI 约定。

标准规定这条链上的语义边界：翻译单元如何构成（`[lex.separate]/1`）、名字的链接性（`[basic.link]/1`）、多份定义何时一致（`[basic.def.odr]/16`）、静态初始化何时发生（`[basic.start.static]/2`）。目标文件格式、符号修饰、调用约定、链接算法由平台与工具链约定，标准不规定。

把这两层分开，可以解释一批常见现象：头文件为什么需要在每个使用它的翻译单元中被包含，inline 与模板为什么能在头文件里定义，链接错误为什么分成未定义引用与重复定义，ABI 不一致为什么在链接成功之后才发作。

本文以 C17（N2176）与 C++ 工作草案（<https://eel.is/c++draft/>，快照 2026-11-14）为语义依据。引用 C++ 条款时标注锚点与段号，引用 C 标准时标注章节号。实现部分以 ELF、PE/COFF、Itanium C++ ABI 与 MSVC ABI 为例，平台差异单独说明。

## 1. 模型总览：从源文件到程序

从源文件到运行中的进程，包含预处理、编译、汇编、链接、加载五个阶段。前四个阶段把源文件变成可执行文件或共享库，第五个阶段把可执行文件变成进程。

| 阶段 | 输入 | 输出 | 主要工作 |
| --- | --- | --- | --- |
| 预处理 | 源文件与头文件 | 预处理翻译单元 | 宏展开、条件编译、`#include` 文本替换 |
| 编译 | 预处理翻译单元 | 汇编代码或目标文件 | 语义分析、模板实例化、优化、代码生成 |
| 汇编 | 汇编代码 | 目标文件 | 指令编码、生成符号表与重定位 |
| 链接 | 目标文件与库 | 可执行文件或共享库 | 符号解析、重定位、COMDAT 合并 |
| 加载 | 可执行文件与共享库 | 进程映像 | 动态链接、重定位、执行初始化函数 |

标准用翻译阶段描述翻译过程的先后顺序（`[lex.phases]/1`），目标文件格式、汇编器与链接器不在标准规定的范围内。阶段划分是概念上的：实现可以把编译与汇编合并成一次 `-c`，也可以直接生成目标文件。`g++ -S` 停在汇编，`g++ -c` 停在目标文件，`g++` 一次完成链接，这些是驱动程序的约定，不改变模型。

模型的关键信息流在表里已经出现：翻译单元内部有完整的声明、类型与函数体，跨翻译单元只剩目标文件里的符号与重定位。链接器不认识 C++ 类型，也不看函数体，它按符号名与符号属性合并。所有跨翻译单元的约定都压在这一层。

由此可以得到四条推论，后面几章依次展开。

1. 声明必须在每个使用它的翻译单元中可见，头文件承担这件事。
2. 允许重复的定义必须在每份拷贝之间保持一致，这是 ODR（One Definition Rule，单一定义规则）的职责。
3. 跨翻译单元的类型、布局与调用约定必须一致，这是 ABI 的职责。
4. 优化器一次只能看一个翻译单元，跨单元优化需要 LTO 这类额外机制。

## 2. 翻译单元与单独编译

### 2.1 翻译单元是什么

翻译单元（translation unit，TU）是预处理之后的源文件。标准把它描述为：一个源文件连同它用 `#include` 引入的头文件与源文件，去掉条件编译跳过的行，构成预处理翻译单元（`[lex.separate]/1`）。C 的翻译单元定义在 C17 5.1.1.1，翻译阶段在 5.1.1.2。

`#include` 的语义是文本替换：整条指令被头文件内容取代，头文件里的 `#include` 继续递归展开（`[cpp.include]/3`）。头文件在哪里查找由实现决定（`[cpp.include]/1`），`-I`、`-isystem` 与系统路径共同决定搜索结果。

标准特意说明，源文件、预处理翻译单元与翻译后的翻译单元都不必与外部文件一一对应（`[lex.separate]/1` 注 2）。一个 `.cpp` 通常翻译成一个目标文件，这是构建系统的映射，不是语言要求。`-include` 注入的头文件、生成代码与统一构建都会打破这种对应。

### 2.2 单独编译的收益与代价

单独编译的历史理由是资源与增量构建：改一个源文件只需要重新翻译一个翻译单元，多个翻译单元可以并行，编译器不必把整个程序放进内存。标准也明确说明程序不必一次翻译完，可以分别翻译再链接（`[lex.separate]/1` 注 1、`[basic.link]/1`）。

代价集中在信息损失上。编译器看不到其他翻译单元的函数体、类型定义与常量定义，只能依据当前翻译单元中的声明做假设，跨翻译单元的优化、检查与诊断都因此受限。

| 维度 | 单独编译 | 整程序编译 |
| --- | --- | --- |
| 增量构建 | 只重新编译变化的翻译单元 | 全量重编 |
| 并行 | 可并行 | 依赖分析后并行 |
| 跨翻译单元优化 | 需要 LTO | 全局可见 |
| 一致性检查 | 只能靠 ODR、ABI 与工具 | 编译器可见 |
| 单次内存 | 一个翻译单元 | 整个程序 |

表里的取舍决定了很多工具的定位：静态库、预编译头、LTO 与模块都在填补单独编译留下的缺口，而不改变模型本身。

### 2.3 翻译单元边界上的信息

翻译单元之间传递的信息可以列成一张清单。声明与类型定义靠头文件文本复制；普通函数与全局变量靠目标文件里的符号；inline 函数、模板实例化与虚表以弱符号或 COMDAT 的形式存在，由链接器合并；常量可能被折叠进指令，也可能作为对象存在；调试信息按目标文件生成，链接时合并。

清单里没有「函数体」这一项。普通函数在另一个翻译单元里只有符号，没有可供分析的代码，这正是 LTO 要解决的信息缺口。

## 3. 预处理与头文件

### 3.1 头文件模型

头文件由预处理器的文本包含实现，不是独立的语言设施。它的作用有两个：让声明在每个使用点可见；让允许重复的定义在每个翻译单元各有一份。

类定义、枚举定义、模板定义、inline 函数与 inline 变量可以放在头文件里，因为标准允许它们在多个翻译单元中出现（`[basic.def.odr]/16`、`[dcl.inline]/2`）。具有外部链接的非 inline 函数与非 inline 变量的定义放在头文件里，会在每个包含它的翻译单元生成一个强定义；只要被两个翻译单元包含，链接期就报重复定义。

头文件保护（include guard）与 `#pragma once` 解决同一翻译单元内的重复包含。`#pragma once` 不是标准指令，按文件路径判断；同一文件经不同路径、符号链接或大小写差异出现时，可能被当成两个文件。

### 3.2 宏与条件编译

宏在预处理阶段完成展开，编译器看不到宏名。同一份头文件在不同宏状态下展开成不同的记号序列，包含它的翻译单元因此可能得到不同的定义。

标准要求多份定义具有相同的记号序列（`[basic.def.odr]/16.4`），但标准不要求跨翻译单元诊断。用 `#ifdef` 切换类成员、虚函数集合、inline 函数体或默认实参，会直接违反这条要求，链接器不会报错。

工程上的对策是把配置差异收进少数头文件，用链接期校验或 LTO 诊断暴露不一致（第 8 章），并避免用宏改变布局。

### 3.3 头文件卫生与预编译头

头文件应当自包含：自身包含所需声明，不依赖包含顺序；每个头文件只暴露接口需要的最小内容。前向声明可以减少依赖，但只在不需要完整类型的地方有效。PIMPL 把实现细节移出头文件，减少重编译与布局耦合，代价是一次间接访问与额外分配。

预编译头（precompiled header，PCH）把解析后的状态序列化，跳过重复解析。GCC 的 `-include` 前缀头、MSVC 的 `/Yc` 与 `/Yu`、Clang 的 `-include-pch` 都属这类机制。PCH 只加速解析，不改变翻译单元边界，也不改变 ODR；它要求使用同一组编译选项与宏状态。

## 4. 编译：语义、名字与代码生成

### 4.1 前端与优化边界

编译器的输入是预处理后的记号序列。前端做语法分析、名字查找、重载决议、模板实例化与语义检查，生成中间表示；中端做与目标无关的优化，后端生成目标代码。

翻译单元内的信息是完整的，因此内联优化、常量传播、死代码消除、去虚化（在动态类型已知时）与别名分析都在这一层做。别名分析决定编译器能重排多少内存访问，详见[别名分析概述](/post/2026/10/22/alias-analysis/)。

跨翻译单元的部分只能靠 LTO（第 8 章）。在此之前，编译器对另一个翻译单元里的函数体、常量取值与类型布局一无所知。

### 4.2 名字修饰

链接器按名字合并符号，C++ 的重载、命名空间、模板与函数签名因此必须编码进符号名，这套编码叫名字修饰（name mangling）。标准不规定修饰规则；`[dcl.link]/1` 注 1 只说明名字表示与调用约定由实现决定。

| 声明 | Itanium（GCC、Clang） | MSVC |
| --- | --- | --- |
| `void f(int)` | `_Z1fi` | `?f@@YAXH@Z` |
| `int add(int, int)` | `_Z3addii` | `?add@@YAHHH@Z` |
| `extern "C" void f(int)` | `f` | `f` |

Itanium C++ ABI 的修饰规则公开且稳定，GCC、Clang 与多数 Unix 平台使用；MSVC 的修饰规则由 Microsoft 文档描述。两套规则产生的符号名不同，调用约定与对象布局也不同，C++ 目标文件不能直接互链。

`extern "C"` 给出 C 语言链接：名字按 C 的方式表示（通常不再带 C++ 修饰），调用约定按平台的 C ABI。它不改变类型系统、对象布局与异常模型，只改变名字与语言链接，不能把任意 C++ 接口变成稳定的 C 接口。

按名字查找符号的接口（`dlsym`、`GetProcAddress`、插件系统）通常要求 `extern "C"` 包装，否则需要知道修饰后的名字。

### 4.3 inline、模板与代码生成

具有外部链接或模块链接的 inline 函数允许在多个翻译单元定义，链接器把它们视为同一实体，地址唯一（`[dcl.inline]/2` 注 1）。每个使用它的翻译单元通常各生成一份代码，用弱符号或 COMDAT 标记，链接器只保留一份。`inline` 只是提示实现优先做 inline 替换，实现可以不展开（`[dcl.inline]/3`）；没有展开的调用仍走普通调用。

模板的隐式实例化发生在使用点（`[temp.inst]/2`），每个需要该特化的翻译单元通常都会生成代码。显式实例化定义（`template class X<int>;`）用于把生成集中到一个翻译单元，其他翻译单元用显式实例化声明（`extern template class X<int>;`）抑制重复生成（`[temp.explicit]/1`、`/2`）。

显式实例化定义会生成特化的代码。实现通常把它作为弱符号或 COMDAT 发出，多个翻译单元重复给出定义时由链接器合并；放在头文件中会让每个包含它的翻译单元都做一次实例化，失去减少重复生成与编译时间的作用。`extern template` 只是抑制生成，不提供定义；缺少定义时仍会报未定义引用。

虚表与 RTTI 也按类似方式生成。Itanium ABI 用 key function 决定由哪个翻译单元生成虚表；没有 key function 时，每个需要的翻译单元各生成一份弱定义，由链接器合并。函数内静态变量的初始化需要线程安全保证（C++11 起），实现通常使用 ABI 规定的 guard 变量与 `__cxa_guard_acquire` 一类函数。这类细节也进入跨翻译单元的契约。

## 5. 目标文件：节、符号与重定位

### 5.1 格式与节

目标文件的核心内容有三部分：按用途分节的代码与数据、符号表、重定位表。格式由平台决定，主流是 ELF、PE/COFF 与 Mach-O。

| 格式 | 典型系统 | 节名示例 | 备注 |
| --- | --- | --- | --- |
| ELF | Linux、多数 Unix | `.text`、`.data`、`.bss`、`.rodata` | 可重定位文件、可执行文件、共享对象共用格式 |
| PE/COFF | Windows | `.text`、`.data`、`.rdata`、`.CRT$XCU` | 目标文件与映像格式；导入库是归档 |
| Mach-O | macOS、iOS | `__TEXT,__text`、`__DATA,__data` | 段与节两级命名 |

| 内容 | ELF | PE/COFF | Mach-O |
| --- | --- | --- | --- |
| 代码 | `.text` | `.text` | `__TEXT,__text` |
| 已初始化数据 | `.data` | `.data` | `__DATA,__data` |
| 零初始化数据 | `.bss` | `.bss` | `__DATA,__bss` |
| 只读数据 | `.rodata` | `.rdata` | `__TEXT,__const` |
| 初始化函数指针 | `.init_array` | `.CRT$XCU`（MSVC）、`.ctors`（MinGW） | `__DATA,__mod_init_func` |
| 异常与展开信息 | `.eh_frame`、`.gcc_except_table` | `.pdata`、`.xdata` | `__TEXT,__eh_frame` |

节的划分影响链接粒度。默认一个函数与相邻函数共享 `.text`，链接器只能整节保留或丢弃；`-ffunction-sections -fdata-sections` 让每个函数、每个数据对象独立成节，配合 `-Wl,--gc-sections` 可以丢弃未使用的部分。MSVC 对应 `/Gy` 与 `/OPT:REF`。

### 5.2 符号

符号表记录名字、绑定（局部、全局、弱）、所在节、偏移、大小与类型。符号表本身不记录 C++ 类型信息（调试信息另行保存类型信息）；类型检查发生在编译期，链接期只有名字与属性。

`nm` 的字母可以快速判断符号类别：`U` 未定义，`T` 与 `t` 代码，`D` 与 `d` 已初始化数据，`B` 与 `b` 零初始化数据，`W` 与 `w` 弱符号，`C` 公共符号。小写表示局部符号。

`static` 函数与变量仍然出现在符号表里，但绑定为局部，链接器不把它们暴露给其他目标文件。调试与重定位仍需要这些符号。

允许重复的实体用 COMDAT 组表达「多份里只留一份」：ELF 用 `SHT_GROUP` 节与 `GRP_COMDAT` 标志，PE/COFF 用带 `IMAGE_COMDAT_SELECT_ANY` 的 COMDAT 节。链接器按组名去重，保留其中一份。

以 ELF 为例，一个包含调用、inline 函数与模板实例化的目标文件可以观察到三类符号：

```bash
g++ -c demo.cpp -o demo.o
nm demo.o
# 0000000000000000 T _Z3usev
#                  U _Z3addii
# 0000000000000000 W _Z5twiceIiET_S0_
```

`_Z3usev` 是本翻译单元定义的普通函数，`_Z3addii` 只有声明、没有定义，`_Z5twiceIiET_S0_` 是弱符号的模板实例化。`T` 表示可供其他目标文件使用的定义，`U` 表示需要在别处找到定义，`W` 表示允许其他目标文件重复提供；链接器按这些属性做解析与合并。

### 5.3 重定位

编译器生成目标文件时不知道函数与全局变量的最终地址：可执行文件的地址由链接器决定，共享库的地址由加载器决定。指令里留下空位与一条重定位记录，链接时由链接器回填。

重定位记录包含偏移、类型、目标符号与加数。x86-64 ELF 常见 `R_X86_64_PC32`、`R_X86_64_PLT32`、`R_X86_64_64`；PE/COFF 常见 `IMAGE_REL_AMD64_REL32`、`IMAGE_REL_AMD64_ADDR64`。类型决定如何计算、是否相对当前指令。

共享库必须位置无关：`-fPIC` 让代码通过全局偏移表（GOT）访问外部数据、通过过程链接表（PLT）调用外部函数；`-fPIE` 用于可执行文件，配合地址空间布局随机化。非 PIC 代码包含绝对地址重定位，加载时需要修改代码页；共享库中出现这类重定位会带来安全与性能代价，通常应避免。

GOT/PLT 把一部分符号解析推迟到第一次调用（延迟绑定）；`-Wl,-z,now` 或 `LD_BIND_NOW` 在加载时完成全部解析。非 PIC 可执行文件访问共享库数据时可能产生 copy relocation，在可执行文件中复制一份数据，地址与共享库中的副本不同。

### 5.4 初始化与运行期表

全局对象的动态初始化被编成函数，函数指针放进 `.init_array`（ELF）、`.CRT$XCU`（MSVC）或 `__mod_init_func`（Mach-O）等节；启动代码在 `main` 之前遍历执行。GCC 的 MinGW 目标通常使用 `.ctors`。

静态初始化在动态初始化之前完成（`[basic.start.static]/2`）。动态初始化的时机标准留有余地：非 inline 变量的初始化可以在 `main` 前完成，也可以延迟（`[basic.start.dynamic]/5`）；inline 变量同理（`/6`）。

全局对象的析构通常通过 `__cxa_atexit` 或 `atexit` 注册，在 `main` 返回后逆序执行。`std::exit` 会执行这些析构，`_exit` 与 `abort` 不会。

异常与栈展开依赖 `.eh_frame`、`.gcc_except_table`（ELF）或 `.pdata`、`.xdata`（PE/COFF）；RTTI 数据与虚表一起放在只读节；线程局部存储有专门的节与访问模型。调试信息（DWARF、CodeView/PDB）不参与语义，链接器负责合并。

## 6. 链接：解析、合并与加载

### 6.1 静态链接

静态链接的输入是目标文件与静态库。静态库是目标文件的归档，链接器按命令行顺序扫描：只抽取定义了当前未定义符号的成员，成员带来的新未定义符号继续在后续输入中解析。

因此库的顺序在 Unix 链接器上有意义：被依赖的库放在依赖它的目标文件之后。循环依赖需要 `--start-group` 与 `--end-group`，或者重复命令行；`--whole-archive` 强制包含归档的全部成员，常用于注册表式的静态初始化。

符号解析遵循强弱规则：强定义重复报错；强定义优先于弱定义；多个弱定义时链接器选一个。COMDAT 组按组名去重，链接器保留一份，丢弃其余。

| 符号类别 | 典型来源 | 链接器行为 |
| --- | --- | --- |
| 强定义 | 普通函数、全局变量 | 只能有一份，重复报错 |
| 未定义 | 声明但未在本目标文件定义 | 在后续输入中查找，找不到报错 |
| 弱定义 | `__attribute__((weak))`、`#pragma weak` | 让位于强定义，多个弱定义选一个 |
| COMDAT 组 | inline 函数、模板实例化、虚表、RTTI | 按组名去重，保留一份 |

链接器只比较符号名与属性，不比较定义内容。两份内容不同的同名弱符号会被合并成一份，程序只保留其中一份，ODR 违规因此常常不产生诊断。

### 6.2 动态链接

共享库在链接期只记录依赖与重定位信息；运行期加载器把库映射进地址空间，按符号名解析，回填 GOT/PLT。默认情况下，查找顺序靠前的同名符号会覆盖靠后的符号，这称为符号插入（interposition）。

符号插入是 `LD_PRELOAD` 与运行时替换的基础，也是优化与兼容性的问题来源。`-Bsymbolic` 与 `-Bsymbolic-functions`、`-fvisibility=hidden`、版本脚本可以限制插入；`-fno-semantic-interposition` 允许编译器假设库内调用不被替换。

动态库的工程选项包括 `-Wl,-soname`（记录 soname）、`-Wl,-rpath`（运行时搜索路径）、`-Wl,--as-needed`（只记录真正用到的依赖）与版本脚本（导出指定符号与版本）。

Windows 用导入库与导出表：`__declspec(dllexport)` 把符号放进导出表，`__declspec(dllimport)` 让调用方通过导入表调用；`LoadLibrary` 与 `GetProcAddress` 对应 `dlopen` 与 `dlsym`。

共享库的初始化函数在加载时执行，顺序按依赖关系；相互独立的共享库之间没有语言层的初始化顺序保证。

### 6.3 常见错误形态

| 现象 | 常见原因 | 出现阶段 |
| --- | --- | --- |
| `undefined reference to ...` | 声明可见但定义未链接；库顺序错误；符号被隐藏 | 链接 |
| `multiple definition of ...` | 头文件中具有外部链接的非 inline 定义；两个翻译单元定义同一强符号 | 链接 |
| 链接成功但行为不一致或崩溃 | 类布局、inline 函数体、编译选项或 ABI 不一致 | 运行期 |
| `dlsym` 找不到符号 | 名字修饰未处理、符号未导出 | 运行期 |

前两类错误是模型直接给出的诊断；第三类落在链接器看不见的位置，只能靠 LTO、sanitizer 与构建配置约束来发现。链接器提供 `-Wl,-Map=build.map` 输出映射文件，`nm`、`objdump -dr`、`readelf` 与 `dumpbin /symbols` 可以检查符号与重定位。

跨翻译单元的一致性要求由 ODR 规定（`[basic.def.odr]/16`），违反不要求诊断；链接器只按符号名合并，无法比较定义内容。

## 7. ABI：跨翻译单元的二进制契约

### 7.1 契约的范围

ABI（Application Binary Interface）是编译器、链接器与运行库之间的二进制约定，标准不规定。它至少包含以下几项。

- 调用约定：参数与返回值放在哪里，栈如何对齐，谁清理栈，`this` 如何传递。
- 名字修饰：符号名如何编码。
- 数据布局：类型大小、对齐、结构体填充、位域、空基类优化、虚表与 RTTI 布局。
- 异常与展开：异常表格式、展开过程、`noexcept` 的二进制含义。
- 运行库：标准库容器与字符串布局、分配器、调试模式、线程局部存储模型。
- 初始化：初始化数组、析构注册、guard 变量。
- 符号可见性与版本：导出哪些符号，如何版本化。

标准规定语言链接，并把名字表示与调用约定留给实现（`[dcl.link]/1` 注 1）；C 标准同样只规定语义，不规定二进制接口。

### 7.2 调用约定

x86-64 上有两套主流 ABI：System V AMD64 与 Windows x64。它们在寄存器分配、栈布局与返回方式上不同。

| 项目 | System V AMD64 | Windows x64 |
| --- | --- | --- |
| 整数参数 | `RDI`、`RSI`、`RDX`、`RCX`、`R8`、`R9` | `RCX`、`RDX`、`R8`、`R9` |
| 浮点参数 | `XMM0` 至 `XMM7` | `XMM0` 至 `XMM3` |
| `this` | 第一个整数参数（`RDI`） | 第一个整数参数（`RCX`） |
| 栈 | 调用前 16 字节对齐，无影子空间 | 调用前 16 字节对齐，32 字节影子空间 |
| 返回 | `RAX` 与 `RDX`，`XMM0` 与 `XMM1` | `RAX`，`XMM0` |

返回大型对象时，调用方提供隐藏的返回指针，它会占用第一个整数参数寄存器，`this` 因此后移；表里列的是普通调用情形。

x86 32 位还有 `cdecl`、`stdcall`、`thiscall`、`fastcall` 等约定，Windows 上 `__stdcall` 会改变名字修饰与栈清理方式。聚合体参数按 ABI 的分类规则放到寄存器或内存；小对象返回、可变参数与向量类型都有专门规则。两套 ABI 在这些细节上不同，混用会在运行期破坏栈或读到错误的值。

MinGW-w64 使用 Itanium C++ ABI 的名字修饰与对象布局，调用约定按 Windows 平台 ABI；它与 MSVC 的 C++ 目标文件通常不能直接互链。C 目标文件在 x64 上共用调用约定，但 CRT 与异常模型仍要匹配。

### 7.3 对象布局与虚表

Itanium ABI 的虚表包含 offset-to-top、RTTI 指针、虚函数指针与虚基类偏移；MSVC 的虚表布局、RTTI 结构与异常表是另一套。标准不规定 vptr 位置、虚表内容与 `sizeof` 结果，这些都属于实现。

标准布局类型是 C 互操作的常用基础，但布局兼容仍取决于 ABI；`bool`、`wchar_t`、枚举底层类型、位域布局与 `long` 宽度在平台间不同。跨语言接口应使用固定宽度整数与显式布局。更细的布局规则见[C++ 对象模型](/post/2026/10/14/cpp-object-model/)。

### 7.4 标准库与调试 ABI

标准库 ABI 是单独的一层。libstdc++ 从 GCC 5 起提供双 ABI：`_GLIBCXX_USE_CXX11_ABI=1` 使用 C++11 的 `std::string` 与 `std::list` 布局，`=0` 保持旧布局；混用会在链接期出现 `__cxx11` 符号缺失，或更隐蔽地破坏对象布局。

`_GLIBCXX_DEBUG` 改变容器布局与迭代器检查；MSVC 的 `_ITERATOR_DEBUG_LEVEL` 不匹配会在链接期报 `LNK2038`。libc++ 的 ABI 与 libstdc++ 不同，同一进程混用两个标准库通常不可行。

标准库 ABI 与语言 ABI 是两层：即使编译器兼容，标准库版本不同也可能不兼容。

### 7.5 稳定接口

需要跨编译器、跨版本发布的接口，通常退到 C ABI：`extern "C"` 函数、不透明结构体、显式创建与销毁、固定宽度类型、错误码。C++ 对象、模板、异常与 `std::` 类型不应作为边界类型。

PIMPL 减少头文件依赖与布局耦合，但仍是 C++ ABI 接口，跨编译器不保证。虚接口与 COM 式 vtable 可以跨编译器，前提是双方遵守同一套二进制约定，这不是标准保证。

符号版本用于在同一库中保留旧符号：GNU 的版本脚本与 `.symver`，Windows 的导出名与转发。版本化让旧二进制继续工作，同时给新代码新的入口。

## 8. 跨翻译单元优化：LTO、可见性与 PGO

### 8.1 LTO

链接时优化（Link Time Optimization，LTO）把中间表示留在目标文件里，链接时由链接器插件调用编译器后端做跨翻译单元优化。GCC 用 `-flto` 保存 GIMPLE，Clang 用 `-flto` 或 `-flto=thin` 保存 LLVM IR，MSVC 用 `/GL` 编译、`/LTCG` 链接。

LTO 能看到多个翻译单元的类型与函数体，因此可以做跨单元的内联优化、过程间常量传播、去虚化与死代码消除，也能发现一部分 ODR 违规（GCC 与 Clang 的 `-Wodr` 都需要 LTO 信息）。LTO 不改变语义：多份定义仍须一致，LTO 只是让实现有机会比较它们。

限制主要来自可见性边界：共享库导出的符号可以被外部替换，插件与 `dlsym` 可能在运行期找到函数，外部可见的符号因此不能被随意 inline 展开或删除。`-fvisibility=hidden` 把不需要导出的符号隐藏，能显著扩大 LTO 的优化范围。

代价是链接时间、内存占用、调试信息质量与构建可复现性。`-flto-partition` 控制划分，`-ffat-lto-objects` 让目标文件同时包含机器码以便非 LTO 链接，`-fno-lto` 可以排除个别目标文件。

### 8.2 可见性

默认可见性由 ABI 决定：ELF 上全局符号默认导出，Windows 上默认不导出。`-fvisibility=hidden` 把默认改成隐藏，再用 `__attribute__((visibility("default")))` 显式导出；`-fvisibility-inlines-hidden` 单独处理 inline 函数。

隐藏符号让编译器知道调用不会被插入，可以做直接调用、内联优化与去虚化；导出符号保留插入语义。`-fno-semantic-interposition` 是另一条路：保留导出，但放弃插入语义。Windows 用 `__declspec(dllexport)`、`.def` 文件或 `/EXPORT` 控制导出，导入方用 `__declspec(dllimport)` 或导入库。

### 8.3 PGO 与后链接优化

基于 profile 的优化（Profile-Guided Optimization，PGO）用实际运行收集的 profile 指导内联优化、分支布局与寄存器分配：GCC 与 Clang 用 `-fprofile-generate` 与 `-fprofile-use`，MSVC 用 `/GENPROFILE` 与 `/USEPROFILE`。BOLT 在链接之后重排代码布局，进一步优化指令缓存与分支预测。PGO 与 BOLT 都不改变编译模型，只改变优化决策。

段级垃圾回收与相同代码折叠（ICF）是链接期的另一类优化：`--gc-sections` 与 `/OPT:REF` 丢弃未使用节；`--icf=all` 与 `/OPT:ICF` 合并相同代码。ICF 可能让不同函数的地址相等，依赖函数地址唯一性的代码需要留意。

## 9. 替代模型：统一构建与模块

### 9.1 与其他执行模型对照

| 模型 | 编译单元 | 地址确定时机 | 跨单元优化 |
| --- | --- | --- | --- |
| 单独编译与链接 | 翻译单元 | 链接期（动态符号在运行期） | 仅 LTO |
| 整程序编译 | 整个程序 | 编译期 | 全局可见 |
| 字节码加 JIT | 类、方法或模块 | 运行期 | 运行期可见 |
| 解释执行 | 语法单元 | 运行期 | 不适用 |

单独编译把翻译与链接分开，换来增量构建与并行；整程序编译与 JIT 能看到更多信息，代价是启动时间或构建时间。模型选择取决于分发方式与优化目标，没有绝对优劣。

### 9.2 统一构建

统一构建（unity build）把多个源文件合成一个翻译单元：直接在一个 `.cpp` 里 `#include` 其他 `.cpp`，或用脚本拼接。翻译单元边界消失，跨文件内联优化与 ODR 检查都变成翻译单元内的事。

代价是 `static` 符号与宏冲突、增量构建失效、单次编译内存上升、代码组织变差。小项目与发布构建可以使用，日常开发通常不合适。

### 9.3 C++20 模块

C++20 模块（P1103R3）把文本包含改成显式导入。模块单元是含模块声明的翻译单元（`[module.unit]/1`）；接口单元用 `export` 暴露声明，实现单元放定义；导入方读取编译器生成的二进制模块接口（BMI），不再展开头文件文本。

变化有四点。

1. 宏不跨越模块边界，头文件保护宏与包含顺序问题消失。
2. 附着于具名模块的重复定义必须诊断：当后一个定义出现时前一个定义可达，标准要求诊断（`[basic.def.odr]/16` 末句）。
3. 解析成本下降，导入方读取 BMI，不重复解析头文件。
4. 构建系统需要扫描 `import` 依赖并管理 BMI 的生成与缓存。

没有改变的部分同样重要：翻译单元仍是编译单位，模板实例化与 inline 代码生成仍可能在多个翻译单元重复，ABI 不变，模块也不自动解决 ABI 兼容问题。

支持状态：GCC、Clang、MSVC 都提供模块支持，标准库模块与构建系统集成程度不同，跨编译器、跨版本的 BMI 不通用。头文件单元（header unit）允许 `import <vector>;` 这类写法，把传统头文件当作模块导入，可移植性与工具链支持弱于具名模块。

## 10. C 与 C++ 的差异

两者共享同一套阶段与链接模型，差异集中在语言表面与运行时设施。这些差异会直接改变头文件写法、链接行为与 ABI 边界。

| 主题 | C | C++ | 编译与链接后果 |
| --- | --- | --- | --- |
| 名字修饰 | 不编码重载与命名空间 | 编码重载、命名空间与模板 | C++ 符号不能按名字直接查找，需 `extern "C"` 包装 |
| 暂定定义 | `int x;` 可以是暂定定义 | `int x;` 就是定义 | 多份定义在 C 中曾由公共符号合并，C++ 中直接违规 |
| inline | 外部链接的 inline 函数不提供外部定义 | 允许多个翻译单元定义 | 头文件里的写法不同 |
| 文件作用域 const | 默认外部链接 | 默认内部链接 | 头文件中的 `const` 变量语义不同 |
| 动态初始化 | 无 | 有，通常在 `main` 前执行 | C++ 有初始化顺序与析构问题 |
| 异常与 RTTI | 无 | 有，依赖 ABI | 跨语言边界需要展开支持 |

### 10.1 名字与链接

C 不编码重载与命名空间，外部名基本等于标识符本身；部分平台的 ABI 会在符号名前加下划线前缀，但语义名字不变。C++ 用修饰编码重载、命名空间与模板，符号冲突与查找都建立在修饰名上。

`extern "C"` 是 C++ 的机制，C 没有语言链接说明符，C 函数的语言链接由语言本身决定。C 的文件作用域 `const` 变量默认具有外部链接（C17 6.2.2），C++ 的命名空间作用域 `const` 变量默认具有内部链接（`[basic.link]/3`），头文件里的 `const int N = 42;` 在两种语言中语义不同。

### 10.2 定义与 inline

C 允许暂定定义：文件作用域的 `int x;` 在翻译单元结束时若没有其他定义，就成为零初始化的定义（C17 6.9.2）。多个翻译单元各写一份，历史上由链接器把公共符号合并；C 标准要求被使用的标识符在程序中恰好有一个外部定义（C17 6.9），GCC 10 起默认 `-fno-common` 把这类代码变成链接错误。

C++ 没有暂定定义，`int x;` 就是定义，多份定义直接违反 ODR。

C99 的 `inline` 语义与 C++ 不同：带 `inline` 的函数在 C 中提供 inline 定义，不提供外部定义，还需要某个翻译单元提供外部定义（C17 6.7.4）；C++ 中具有外部链接的 inline 函数允许多个翻译单元定义，由链接器合并（`[dcl.inline]/2`）。头文件里的 `static inline` 是 C 的常用写法，C++ 中则用 `inline` 或 `constexpr`。

### 10.3 初始化与运行期设施

C 的静态存储期对象只能用常量表达式（包括地址常量）或字符串字面量初始化（C17 6.7.9），没有动态初始化，也没有析构。C++ 允许动态初始化，通常在 `main` 之前执行，标准允许部分变量延迟到首次使用前（`[basic.start.dynamic]/5`），并在退出时调用析构。

这带来 C 没有的问题：跨翻译单元的初始化顺序、全局对象构造期间的虚函数派发、`main` 之前的异常（调用 `std::terminate`）。函数内静态变量的线程安全初始化依赖 ABI 中的 guard 变量。

### 10.4 异常、RTTI 与类型兼容

C 没有异常与 RTTI。C++ 的异常依赖目标文件里的展开表与运行库；`-fno-exceptions` 关闭异常，`-fno-rtti` 关闭 RTTI，二者都会改变目标文件的内容与跨翻译单元的行为。

两种语言都要求跨翻译单元的声明一致：C 用兼容类型（C17 6.2.7），C++ 用 ODR。两者都不要求跨翻译单元检查；声明不一致时链接器可能成功，运行期才出问题。

`extern "C"` 只统一名字与语言链接，不统一对象布局、异常与标准库。C 与 C++ 共享的头文件应保持类型简单：固定宽度整数、标准布局结构体、不透明指针。

## 11. 工程规则与诊断工具

模型本身不能改变，能做的是把它的约束写进工程流程。以下规则按收益排序。

1. 头文件只放声明、类定义、模板与 inline 定义；具有外部链接的非 inline 函数与非 inline 变量放进 `.cpp`。
2. 共享常量用 `inline constexpr`（C++17 起）；C 中用 `extern` 声明、在一个 `.c` 中定义。
3. 对外接口优先 C ABI：`extern "C"`、不透明结构体、固定宽度类型、错误码；C++ 类型不作为边界类型。
4. 默认隐藏符号，显式导出；共享库用版本脚本与 soname 管理兼容性。
5. 统一工具链、标准库与 ABI 配置：`_GLIBCXX_USE_CXX11_ABI`、`_ITERATOR_DEBUG_LEVEL`、`-fno-exceptions`、`-fno-rtti` 不应在不同目标间混用。
6. 不依赖跨翻译单元的静态初始化顺序；需要时用函数内静态变量或显式初始化函数。
7. 静态库注意顺序与循环依赖；必要时用 `--start-group` 或 `--whole-archive`，并避免把注册表式代码放进静态库。
8. 在 CI 中启用 LTO 与 `-Wodr`、ASan 的 `detect_odr_violation`、`-Wl,--no-undefined`，把一部分跨翻译单元问题前移。
9. 用 `nm -C`、`objdump -dr`、`readelf -r`、`dumpbin /symbols` 与链接映射检查符号与重定位，构建产物保留 map 文件。
10. 构建可复现：固定工具链版本与路径，使用 `-ffile-prefix-map` 与确定性链接选项；模块项目让构建系统扫描 `import` 依赖并缓存 BMI。

| 工具 | 用途 |
| --- | --- |
| `nm -C` | 查看符号、未定义引用与弱符号 |
| `objdump -dr` | 反汇编并显示重定位 |
| `readelf -r`、`readelf -s` | 查看 ELF 重定位与符号表 |
| `dumpbin /symbols` | 查看 PE/COFF 符号 |
| `-Wl,-Map=build.map` | 查看符号来源与节布局 |

构建系统在这一层的职责是把源文件映射成翻译单元、把翻译单元映射成目标文件，再管理库与链接选项。CMake、Bazel、Meson 的差异在依赖图与缓存，不在编译模型。

---

## 12. 小结

编译模型可以写成一条链：源文件到预处理翻译单元，再到目标文件、链接产物与进程。每一段只传递有限信息：文本、符号、重定位、ABI。

标准规定语义边界：翻译单元如何构成、名字的链接性、多份定义的一致性、初始化的顺序；目标文件格式、名字修饰、调用约定、链接算法由平台与工具链约定。判断一个问题属于哪一层，比记住具体规则更有用。

工程上的稳定做法是缩小头文件中的定义范围、以 C ABI 作为边界、统一构建配置，并用 LTO、符号可见性与诊断工具把跨翻译单元的问题暴露出来。需要更强边界时，模块提供了另一条路径，但它改变的是声明的传递方式，不改变整条链。
