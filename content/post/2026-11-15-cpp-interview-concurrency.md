## 1. 线程与任务模型

### 1.1 线程与任务有何区别？

- 线程是内核调度的执行实体，持有独立的栈、寄存器上下文与调度属性；任务是一段可被调度的计算，与执行它的线程可以分离。
- 任务通常表示为可调用对象加完成通知，提交到队列后由任意工作线程取出执行，执行位置不构成任务身份的一部分。
- 线程的创建与销毁进入内核，代价通常在微秒量级；任务的创建只是对象构造与入队，代价低一个数量级以上，具体数值由实现决定。
- 任务可以携带取消状态、优先级、依赖关系与截止时间，线程只提供执行能力，不描述这些语义。
- 一个线程可以顺序执行多个任务，一个任务也可以拆成多个子任务并行执行。
- 线程局部状态与任务生命周期不一致时会出现状态残留，复用线程执行任务需要显式重置。
- 区分两者的意义在于调度策略作用在任务上，资源控制（栈大小、亲和性、cgroup 归属）作用在线程上。

### 1.2 执行上下文包含哪些状态？

- 寄存器上下文：通用寄存器、指令指针、栈指针与标志寄存器；协程切换主要保存与恢复这部分。
- 栈：线程栈由内核或运行时分配，协程栈由运行时分配，大小、增长方向与溢出检测方式不同。
- 线程局部存储：TLS 块、`errno`、浮点环境与信号掩码属于线程，不随任务切换。
- 调度状态：优先级、亲和性掩码、调度类与 cgroup 归属由内核维护。
- 同步状态：持有的互斥量、等待中的条件变量、正在等待的 futex 字。
- 运行时状态：异常传播状态、`std::stop_token`、分配器与执行器关联。
- 上下文切换的代价包括寄存器保存、栈切换与缓存局部性损失；协程切换省去内核往返，但仍有寄存器与栈的保存开销。

### 1.3（辨析）协作式与抢占式调度的边界在哪里？

- 抢占式调度由内核在时钟中断或更高优先级任务就绪时强制切换，任务无法长期独占处理器。
- 协作式调度只在任务显式让出时切换，切换点由代码决定，临界区不会被任意打断。
- 协作式的风险是一个任务长时间不让出会阻塞同一承载线程上的其他任务，需要拆分长任务或插入检查点。
- 抢占式要求在任意点都能安全切换，锁与不变量必须假定执行会被中断；协作式可以在让出点之间使用更弱的同步。
- 协程通常是协作式的，运行在由线程池承载的调度器上，阻塞调用会占住整个承载线程。
- 实时系统倾向抢占式并配合优先级继承，吞吐型服务倾向协作式以减少切换与锁竞争。
- 两种模型可以组合：线程之间抢占式，线程内部的任务之间协作式。

### 1.4 任务窃取调度器如何工作？

- 每个工作线程持有本地双端队列，自己从一端取任务，其他线程从另一端窃取。
- 所有者按后进先出取任务，刚产生的子任务优先执行，缓存局部性较好；窃取者按先进先出取任务，较早的大任务先被拿走，减少冲突。
- 本地队列通常只需原子操作，窃取路径需要原子读改写，冲突集中在队列接近空时。
- 窃取失败后线程进入自旋、让出或休眠，唤醒由条件变量或 futex 完成。
- 任务粒度决定窃取收益：粒度过细时窃取开销超过计算，粒度过粗时负载不均。
- 递归分治任务适合窃取；长尾阻塞任务会把工作线程拖住，通常放到单独的阻塞池。
- 调度器需要维护未完成任务计数与唤醒机制，否则主线程无法判断整棵任务树何时结束。

### 1.5（实现）无锁工作窃取双端队列如何设计？

- 队列由环形缓冲区、`top` 与 `bottom` 两个索引组成，`bottom` 只由所有者修改，`top` 由窃取者用 CAS 推进。
- 所有者入队时写入 `bottom` 位置，再以释放语义递增 `bottom`；出队时先递减 `bottom`，再与 `top` 比较。
- 窃取者以获取语义读取 `top` 与 `bottom`，区间非空时读取元素并 CAS 推进 `top`。
- 最后一个元素存在所有者与窃取者的竞争，需要一次 CAS 决定归属，失败方视为队列为空。
- 索引需要防止溢出与伪共享，`top` 与 `bottom` 通常放在不同缓存行。
- 缓冲区扩容只由所有者执行，窃取者可能仍在读旧缓冲区，旧内存需要延迟回收。
- 弱序架构上需要额外的顺序约束，原始 Chase-Lev 算法在 ARM 一类平台上存在正确性问题，需要使用修正后的版本。

```cpp
// buf_、top_、bottom_ 为成员，省略其余部分
bool steal(Task& out) {
    size_t t = top_.load(std::memory_order_acquire);
    std::atomic_thread_fence(std::memory_order_seq_cst);
    size_t b = bottom_.load(std::memory_order_acquire);
    if (t >= b) return false;
    out = buf_[t % buf_.size()];
    return top_.compare_exchange_strong(t, t + 1,
               std::memory_order_seq_cst,
               std::memory_order_relaxed);
}
```

### 1.6 线程亲和性有什么作用与代价？

- 亲和性把线程限制在一组 CPU 上，减少迁移造成的缓存与 TLB 失效。
- Linux 通过 `sched_setaffinity` 设置掩码，`pthread_setaffinity_np` 是 glibc 封装；容器层由 cgroup 的 `cpuset` 限制。
- 延迟敏感线程可以绑定到隔离核，配合 `isolcpus` 减少调度器干扰。
- CPU 绑定会降低负载均衡能力，线程数超过可用核时会造成排队，而其他核可能空闲。
- 超线程拓扑中同一物理核的两个逻辑核共享执行单元，绑定策略需要读取拓扑后再决定。
- CPU 绑定与 NUMA 亲和不同，内存位置由首次触页、`mbind` 与 `numa_*` 接口决定。
- 容器内可见的 CPU 编号与宿主机不同，需要按 `cpuset.cpus` 解析。

### 1.7 NUMA 感知的调度如何减少远端访问？

- NUMA 节点内访问本地内存的延迟与带宽优于跨节点访问，跨节点还要经过互连。
- 默认首次触页策略把页分配到触发缺页的 CPU 所在节点，线程迁移后访问变为远端。
- 调度器尽量把任务留在原节点，内核的 `numa_balancing` 会周期性扫描并迁移页面，减少任务与数据分离。
- 应用层可以用 `numa_alloc_onnode`、`mbind` 指定内存位置，或按节点维护独立内存池。
- 线程池可按节点分片，任务与数据同节点分配，跨节点只传递句柄或消息。
- CPU 绑定与内存绑定需要一起设计，只绑定 CPU 不绑定内存仍可能跨节点访问。
- 远端访问的具体代价由拓扑与实现决定，不能仅凭节点距离推断。

### 1.8（场景）线程数超过核心数时会发生什么？

- 就绪线程数大于逻辑核数，调度器按时间片轮转，线程被抢占后重新排队。
- 每次切换保存与恢复上下文，工作集被挤出缓存，缓存命中率下降。
- 阻塞型任务在等待 I/O 时让出处理器，超额订阅可以提高利用率；计算型任务则相反。
- 线程栈与 TLS 占用内存，线程数很大时内存压力与页表开销上升。
- 锁竞争加剧，持有锁的线程被抢占会让其他线程等待更久。
- 尾延迟对超额订阅敏感，排队时延在高分位被放大，p99 可能远高于均值。
- 常见做法是按任务类型分池：计算池取核数，阻塞池按并发 I/O 数配置。

### 1.9 任务粒度如何选择？

- 粒度过细时，提交、唤醒与窃取的开销超过任务本身的计算。
- 粒度过粗时，负载不均与尾延迟由最慢的任务决定，其他线程空闲。
- 经验做法是让单个任务运行数十微秒以上，阈值取决于调度器开销与任务分布。
- 分治任务可以设置切割深度或最小块大小，递归到阈值后改为串行处理。
- 任务内部应避免阻塞调用，阻塞会占住工作线程并破坏窃取的负载均衡。
- 批处理能摊薄提交开销，但会增大单次延迟，需要与响应时间目标权衡。
- 粒度是否合适依赖测量，队列长度分布与调度统计比单一平均值更有参考价值。

### 1.10 任务的生命周期应如何建模？

- 任务状态通常包括已提交、已调度、运行中、挂起、完成与取消，状态迁移需要原子化。
- 完成与取消之间存在竞争，最终状态只能有一个，通常用一次比较交换决定。
- 挂起状态适用于携带独立执行上下文的任务，例如协程；线程承载的任务阻塞时占住的是线程。
- 状态查询接口应返回快照，不能暴露内部可变状态。
- 任务对象的所有权在提交后转移给调度器，调用方只保留句柄或 future。
- 异常与取消都走完成路径，资源清理在状态迁移到终态时执行一次。
- 状态机是取消协议与关闭流程的基础，缺少终态会导致重复完成或泄漏。

### 1.11 任务队列的公平性如何保证？

- 公平性可以指先提交的任务先执行，也可以指先就绪的任务先执行，两种定义不同。
- 单一 FIFO 队列提供提交顺序，但工作窃取会打乱执行顺序。
- 优先级队列保证高优先级先执行，低优先级任务可能饥饿。
- 多队列按优先级分层，层内先进先出、层间加权，可以兼顾吞吐与延迟。
- 公平性需要原子序号或时间戳，分布式场景还要处理时钟偏差。
- 批处理与任务合并会改变任务粒度，从而改变公平性的可观察结果。
- 公平性通常让位于吞吐，只有在延迟敏感或存在依赖时才需要显式保证。

### 1.12（场景）任务提交后调用方如何取消？

- 取消是协作式的，调用方通过 `std::stop_source` 发出请求，任务通过 `stop_token` 轮询。
- 任务在等待点应使用支持停止的等待，例如 `std::condition_variable_any` 接收 `stop_token` 的重载。
- 阻塞在系统调用上的任务需要把停止请求转换为唤醒，例如关闭 fd、写 `eventfd` 或发送信号。
- 取消后的结果语义要明确：返回失败、抛出特定异常，或以部分结果完成。
- 已完成的任务无法取消，取消请求与完成之间存在竞争，需要原子地决定最终状态。
- 协程中取消通常表现为 `await_resume` 抛出或返回错误，随后销毁协程帧。
- 资源清理应放在析构或 `scope_exit` 中，取消路径与正常路径共用清理逻辑。

### 1.13（场景）任务调度中的尾延迟由哪些因素决定？

- 单个长任务会占住工作线程，其他任务排队，尾延迟由最长任务决定。
- 任务粒度过细会增加调度与窃取开销，形成大量小任务排队。
- 窃取只在被窃取队列非空时发生，任务分布不均时部分线程空闲而部分线程排队。
- 阻塞调用会让承载线程停止取任务，尾延迟出现尖峰。
- 递归分治的切割不平衡会使某些子任务远大于其他子任务。
- 观测任务等待时间与执行时间的分位数，可以区分排队与执行。
- 调整粒度、拆分长任务与隔离阻塞任务都能降低尾延迟。

### 1.14 任务迁移到另一线程需要满足哪些条件？

- 迁移要求任务没有绑定到特定线程的资源，例如线程局部存储、线程绑定的分配器。
- 持有互斥量或正在等待条件变量的任务不能迁移，锁的所有权与等待队列绑定线程。
- 协程可以在挂起点迁移，前提是挂起期间不持有线程绑定的资源。
- C++20 协程的局部变量位于协程帧，帧不随恢复线程改变，引用在迁移后仍然有效；线程栈上的对象不能随任务迁移。
- 线程局部存储中的缓存与句柄需要重新建立，或改为显式上下文对象。
- 迁移会破坏缓存局部性，跨 NUMA 节点迁移还要考虑内存位置。
- 调度器应在挂起点或任务边界检查迁移条件，不能在中途任意迁移。

### 1.15（辨析）线程池、纤程与协程如何映射？

- 线程是内核调度单位，纤程与协程是用户态执行流，由运行时调度到线程上。
- 协程切换只保存少量寄存器与栈指针，不进入内核，代价远低于线程切换。
- 有栈协程为每个协程分配独立栈，切换时换栈；无栈协程把状态放在堆上的协程帧。
- C++20 协程是无栈的，挂起时局部变量保存到协程帧，恢复由调用方或调度器驱动。
- M:N 调度把多个协程映射到少量线程，阻塞调用会阻塞整个承载线程，需要异步化。
- 协程适合高并发 I/O，线程适合需要并行计算与抢占的场景，两者通常混合使用。
- 抽象层数增加后调试与观测更难，协程栈不出现在系统调用栈中，需要运行时提供回溯。

### 1.16（辨析）fork-join 与续延传递的任务模型有何差异？

- fork-join 把任务表示为可阻塞的调用栈，父任务等待子任务完成后继续。
- 续延传递把剩余计算封装为回调或续延，任务结束时不保留调用栈。
- fork-join 的栈空间随并行深度增长，续延传递的堆对象随链长度增长。
- fork-join 适合分治与结构化并行，续延传递适合事件驱动与异步 I/O。
- 续延传递需要处理回调嵌套与生命周期，C++ 中用协程或发送器缓解。
- 两种模型都可以在工作窃取调度器上实现，切换成本与栈管理方式不同。
- 阻塞等待在 fork-join 中是合法的，在事件循环中会阻塞整个线程。

### 1.17（场景）任务依赖图如何调度？

- 依赖图用有向无环图表示，节点是任务，边是先后约束，入度为零的节点就绪。
- 调度器维护就绪队列与入度计数，任务完成后原子递减后继入度，减到零时入队。
- 依赖图适合一次性批处理；动态依赖需要在运行时增量构建，注意并发修改。
- 关键路径决定最短完成时间，调度应优先关键路径上的任务。
- 环检测在构建阶段完成，运行期发现环只能报错终止。
- 任务失败需要向下游传播，后继任务转为跳过或失败；等待语义要区分全部成功与全部完成。
- 分布式 DAG 调度还要处理节点故障与重复执行，需要幂等与状态持久化。

### 1.18 长任务如何在不阻塞调度器的前提下推进？

- 长任务应拆成多个阶段，每个阶段结束后重新入队，让其他任务获得执行机会。
- 阶段之间通过续延或状态对象传递中间结果，避免占用调用栈。
- 拆分点应选在天然边界，例如一批数据处理完、一次 I/O 完成。
- 拆分增加调度开销与状态保存成本，粒度需要与延迟目标权衡。
- 无法拆分的计算应放到专用线程，避免占住协作式调度器。
- 进度与取消状态要跨阶段保存，阶段之间不能依赖线程局部变量。
- 阶段划分也影响尾延迟，最后一段过长仍会阻塞。

### 1.19（场景）结构化并发如何约束任务的生命周期？

- 结构化并发要求子任务的生命周期嵌套在父任务的作用域内，父任务退出前必须等待或取消子任务。
- 作用域对象负责启动、等待与取消，异常沿作用域向上传播。
- 取消是协作式的，作用域发出停止请求后等待子任务到达检查点。
- 子任务不能逃逸作用域，避免悬空引用与资源泄漏。
- 并发组合操作（`when_all`、`when_any`）需要明确部分失败时的语义。
- 作用域可以限制并发度，形成背压。
- 结构化并发使线程数与任务树深度解耦，但阻塞等待仍需调度器配合。

### 1.20（辨析）批处理与流式处理的任务模型有何差异？

- 批处理按有界数据集组织任务，重视吞吐与资源利用率，允许较高延迟。
- 流式处理按无界事件序列组织任务，重视单条延迟与背压。
- 批处理可以排序与合并，流式处理必须按到达顺序或键分区处理。
- 批处理的失败可以整批重试，流式处理需要逐条确认与去重。
- 批处理的任务粒度较大，流式处理的任务粒度小且持续到达。
- 流式处理需要水位线与窗口，批处理需要分区与倾斜处理。
- 两种模型可以组合，例如微批处理在延迟与吞吐之间折中。

## 2. 同步原语与锁

### 2.1 futex 的等待与唤醒机制如何工作？

- futex 是内核提供的等待队列，绑定一个用户态 32 位整数，系统调用只在发生竞争时进入内核。
- `FUTEX_WAIT` 先比较用户态值与期望值，相等才把线程挂到该地址的等待队列，比较与挂起在内核中原子完成。
- `FUTEX_WAKE` 唤醒指定数量的等待者，返回值是实际唤醒数。
- 无竞争时加锁只执行用户态原子指令，不进入内核，这是 futex 相对每次加锁都进入内核的实现的主要优势。
- 条件变量广播在部分实现中使用 `FUTEX_REQUEUE` 把等待者迁移到互斥量的 futex，减少全部唤醒后的竞争。
- 优先级继承通过 `FUTEX_LOCK_PI` 实现，持有者临时继承等待者的优先级。
- 等待队列按地址哈希，哈希冲突只增加唤醒时的检查开销，不影响正确性。

### 2.2（辨析）互斥量的快速路径、慢路径与内核切换有何差异？

- 快速路径用一次原子比较交换把状态从未锁改为已锁，成功即返回。
- 慢路径在发现已被持有时进入自旋或直接 futex 等待，具体策略由实现定义。
- 慢路径可能先自旋再睡眠，是否自旋与自旋次数由实现决定，也受同核与跨核的影响。
- 内核切换的代价包括系统调用入口、调度与唤醒延迟，通常在微秒量级。
- 临界区极短时自旋可能优于睡眠；临界区长或可能阻塞时必须睡眠。
- 自适应策略由实现决定，不能假定某个互斥量一定自旋或一定睡眠。
- 统计上下文切换与 futex 调用次数可以判断锁是否频繁进入慢路径。

### 2.3（辨析）条件变量、原子等待与事件通知如何选择？

- 条件变量适合等待由互斥量保护的复合谓词，等待期间释放互斥量。
- 原子等待适合单个原子变量的值变化，不涉及其他共享数据，也不需要互斥量。
- 事件通知使用 `eventfd` 或管道，适合跨线程、跨进程通知，并可与 I/O 多路复用集成。
- 条件变量要求谓词修改与通知在同一同步协议下，否则会丢失唤醒。
- 原子等待不能释放互斥量，持有锁等待会阻塞通知方，形成死锁。
- 事件通知带文件描述符与系统调用开销，但可以被事件循环统一等待。
- 选择依据是等待条件的复杂度、是否需要与 I/O 循环集成，以及通知的跨进程需求。

### 2.4 条件变量的无效唤醒与延迟如何权衡？

- `notify_one` 只唤醒一个等待者，唤醒开销低，但被唤醒者可能发现谓词不成立而重新等待。
- `notify_all` 唤醒全部等待者，适合状态变化影响全部等待者的场景，代价是惊群。
- 多个谓词共用一个条件变量时，`notify_one` 可能唤醒错误的等待者，导致其他等待者延迟。
- 拆分条件变量可以减少无效唤醒，但增加状态管理与遗漏通知的风险。
- 通知在持锁时发出，等待者醒来后先竞争锁；在释放锁后发出，等待者可以直接获取锁。
- 等待者数量很大时，唤醒风暴会推高尾延迟，需要按条件分组或改用信号量。
- 选择依据是谓词分布与等待者数量，压力测试时应观察无效唤醒次数。

### 2.5 读写锁应优先读操作还是写操作？

- 读操作优先允许新的读操作在已有读操作持有时进入，写操作可能长期饥饿。
- 写操作优先在有写操作等待时阻塞新的读操作，读延迟上升，写吞吐提高。
- glibc 的 `pthread_rwlock_t` 默认偏向读操作，具体行为由实现定义，并受 `PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP` 一类属性影响。
- 读多写少且读临界区短时，读写锁的收益来自并行读；写比例上升后收益迅速消失。
- 读写锁的簿记比互斥量多，短临界区下可能更慢。
- 同一线程重复获取共享锁不被标准支持，行为未定义，不能依赖递归语义。
- 需要公平性时可以使用票据锁或队列化读写锁，代价是额外原子操作。

### 2.6 读写锁在什么情况下比互斥量更慢？

- 临界区只有几条指令时，读写锁的原子计数与唤醒逻辑开销超过并行收益。
- 写操作频繁时，读锁与写锁交替使缓存行来回失效，吞吐低于互斥量。
- 读操作持有锁期间被抢占，写操作的等待时间被放大。
- 读锁升级为写锁不被标准支持，需要释放后重新获取，期间状态可能变化。
- 读写锁内部通常仍有一个互斥量保护状态，竞争激烈时退化。
- 只保护一次指针读取时，`std::mutex` 往往比读写锁更快。
- 读多写少且读操作较长时，读写锁才有明显价值。

### 2.7 信号量与条件变量的语义有何差异？

- 信号量是计数器，获取在计数大于零时递减并继续，否则阻塞；释放递增并唤醒等待者。
- 条件变量没有状态，必须与共享谓词配合，等待与通知都可能丢失。
- 信号量的计数在释放时保存，之后到达的等待者可以直接通过，适合事件计数与资源池。
- 二元信号量可以当互斥量用，但没有所有权概念，任意线程都可以释放。
- 条件变量适合等待某个状态成立，信号量适合等待若干资源可用。
- C++20 的 `std::counting_semaphore` 与 `std::binary_semaphore` 提供标准接口（P1135R6）。
- 信号量释放不要求持有者身份，误用会导致计数错误且难以排查。

### 2.8（实现）如何用互斥量与条件变量实现信号量？

- 计数、互斥量与条件变量构成基本结构，获取在计数为零时等待。
- 释放递增计数并通知一个等待者，通知在锁内或锁外均可。
- 支持超时的版本使用 `wait_for`，返回超时时要区分未获取与已获取。
- 公平性取决于条件变量的唤醒顺序，标准不保证先进先出。
- 计数上限由构造参数决定，释放超过上限属于使用错误。
- 该实现在无竞争时也要加锁，性能低于原子计数加 futex 的实现。

```cpp
class Semaphore {
    std::mutex m_;
    std::condition_variable cv_;
    int count_ = 0;
public:
    void acquire() {
        std::unique_lock<std::mutex> lk(m_);
        cv_.wait(lk, [this] { return count_ > 0; });
        --count_;
    }
    void release() {
        std::lock_guard<std::mutex> lk(m_);
        ++count_; cv_.notify_one();
    }
};
```

### 2.9 自旋锁与阻塞锁如何选择？

- 自旋锁在获取失败时循环重试，不放弃处理器，适合临界区短于两次上下文切换的场景。
- 阻塞锁在失败时进入内核等待，适合临界区长或可能睡眠的场景。
- 自旋的前提是临界区内不阻塞、不睡眠，且持有者能很快被调度。
- 持有者被抢占时其他自旋线程空转，优先级反转更严重。
- 单核上自旋通常没有意义，持有者无法与自旋者同时运行。
- 混合策略先自旋若干次再睡眠，阈值由实现或测量决定。
- 用户态自旋循环应使用 `pause` 指令或 `std::this_thread::yield` 降低总线与功耗开销。

### 2.10（实现）自适应自旋锁如何实现？

- 先以原子操作自旋有限次数，失败后进入原子等待。
- C++20 的 `std::atomic::wait` 与 `notify_one` 可以替代条件变量，省去单独的互斥量。
- 自旋次数与临界区长度、核心数相关，固定阈值只能作为起点。
- 释放时用释放语义存储 `false`，再调用 `notify_one`；先通知后改值会让等待者重新睡眠。
- 唤醒可能是虚假的，等待必须放在循环中并重新尝试获取。
- 自适应策略依赖平台，不能假定某种锁一定自旋或一定睡眠。
- 自旋阶段消耗处理器时间，线程数远超核数时应缩短自旋。

```cpp
void lock() {
    for (int i = 0; i < 64; ++i) {
        bool expected = false;
        if (locked_.compare_exchange_weak(expected, true,
                std::memory_order_acquire)) return;
        std::this_thread::yield();
    }
    bool expected = false;
    while (!locked_.compare_exchange_weak(expected, true,
               std::memory_order_acquire)) {
        locked_.wait(true, std::memory_order_relaxed);
        expected = false;
    }
}
```

### 2.11 锁粒度如何划分？

- 粒度指一把锁保护的数据范围，范围越大竞争越高，范围越小簿记与死锁风险越高。
- 划分依据是不变量：必须一起保持一致的数据应放在同一临界区。
- 把大锁拆成多把锁需要保证跨锁操作有明确的顺序与一致性方案。
- 过细的锁会让一次逻辑操作变成多次加解锁，原子性与性能都受影响。
- 读多写少时可以用读写锁或不可变数据结构替代细粒度锁。
- 分片（striping）按哈希把数据分到多把锁，冲突概率随分片数下降。
- 锁粒度调整应以竞争测量为依据。

### 2.12（场景）分段锁如何设计？

- 分段锁把容器划分为若干桶，每个桶一把锁，操作只锁对应桶。
- 分段数通常取 2 的幂，用哈希高位或低位选择段，避免取模开销。
- 全局操作（扩容、遍历、尺寸统计）需要跨段协调，通常加一把全局锁或使用版本号。
- 跨段操作需要按固定顺序加锁，否则两个线程反向加锁会死锁。
- 分段数过少退化为单锁，过多增加内存与缓存占用。
- 迭代器语义在分段结构上变复杂，需要快照或弱一致性保证。
- 标准容器不提供并发访问保证，分段需要外层包装或使用并发容器库。

### 2.13 锁的持有时间如何测量与缩短？

- 持有时间从加锁成功到解锁，包含临界区内的计算、内存分配与系统调用。
- 测量可以在加锁与解锁处记录时间戳，代价是额外时钟读取与存储。
- 临界区内不应调用可能阻塞的函数，也不应执行与不变量无关的计算。
- 把昂贵操作移出临界区，先在锁内复制必要状态，再在锁外处理。
- 缩短持有时间会增大操作次数，可能增加竞争与缓存行流量。
- 持有时间的分布比均值更重要，长尾持有会放大其他线程的等待。
- 测量结果受观测开销影响，生产环境需要采样，全量记录会放大观测开销。

### 2.14（场景）锁的护航效应如何形成？

- 护航效应（lock convoy）指线程排队等待同一把锁，持有者被抢占或阻塞后整个队列停滞。
- 持有者时间片耗尽、发生缺页或被更高优先级线程抢占都会触发。
- 护送使吞吐骤降、延迟分布拉长，CPU 利用率可能不高。
- 缩短临界区、降低锁竞争与避免持锁阻塞可以缓解。
- 自旋锁在持有者被抢占时会加剧护送，因为等待者空转。
- 观测上下文切换与锁等待时间可以识别护送。
- 把锁拆分为读写锁或无锁结构可以减少排队，但需要重新验证不变量。

### 2.15（辨析）互斥量的所有权语义带来哪些约束？

- 互斥量有所有者，只有加锁的线程可以解锁；信号量没有所有者。
- 所有权使互斥量可以实现优先级继承与错误检查。
- 带错误检查的互斥量（`PTHREAD_MUTEX_ERRORCHECK`）在重复加锁或非所有者解锁时返回错误，普通互斥量行为未定义。
- 所有权不允许跨线程移交锁，协程在挂起点迁移时需要显式处理。
- 递归互斥量记录所有者与递归深度，非递归互斥量重复加锁属于未定义行为。
- 所有权语义是条件变量必须与互斥量配合的原因之一。
- 所有权语义也影响锁的封装接口，解锁不能由其他线程代劳。

### 2.16（场景）锁字伪共享如何影响性能？

- 多个互斥量位于同一缓存行时，不同线程分别加锁也会使缓存行来回失效。
- 表现是线程数增加而吞吐不增，缓存一致性流量上升。
- 把热点锁分开到不同缓存行，或把锁与受保护数据分离，可以缓解。
- 伪共享的代价来自写操作，读取方也会因缓存行失效而变慢。
- 锁字与数据同行的布局可能让临界区访问也产生额外一致性流量。
- `perf c2c` 可以报告缓存行级别的争用。
- 填充会增加内存占用，锁数量很多时需要权衡。

### 2.17（实现）读写锁的读取线程计数如何用原子变量维护？

- 读取线程计数用原子变量记录当前数量，进入时递增，退出时递减。
- 写线程需要一个标志表示独占，读取线程进入前检查标志，写线程进入前等待计数归零。
- 检查与递增之间存在竞争，需要把状态打包进一个字做 CAS，或用互斥量保护状态。
- 计数溢出需要处理，通常用足够宽的整数并限制并发读取线程数。
- 写线程等待计数归零需要条件变量或 futex，唤醒策略影响公平性。
- 读取与写入的状态转换需要防止写线程插入导致读取线程饿死。
- 标准库的 `shared_mutex` 只规定接口语义，内部实现由实现定义。

### 2.18 锁竞争如何观测？

- 上下文切换次数与 futex 系统调用次数反映阻塞频率，`pidstat -w` 与 `perf stat` 可以采集。
- `perf lock` 统计锁的争用与持有时间，需要内核支持。
- eBPF 可以在 futex 入口与返回处记录等待时长，按锁地址聚合。
- 用户态可以用 `try_lock` 计数近似竞争程度，代价是额外原子操作。
- 采样调用栈可以看到持锁点与等待点，火焰图能显示锁的调用路径。
- 吞吐随线程数增加而下降，通常指向竞争或伪共享。
- 观测本身会改变时序，生产环境需要控制采样率与开销。

### 2.19（辨析）顺序锁与读写锁有何差异？

- 顺序锁的写入线程不阻塞读取线程，读取线程在读取前后检查版本号，版本变化则重试。
- 读写锁的读取线程阻塞写入线程，写入线程等待所有读取线程退出。
- 顺序锁适合读多写少且数据较小的场景，读取线程可能重试与饥饿。
- 读写锁适合读临界区较长且读操作昂贵的场景，写入延迟较高。
- 顺序锁的读侧需要屏障，防止数据读取被重排到版本检查之外。
- 顺序锁不保证读取期间数据不变，读取线程可能读到撕裂数据后重试。
- 读写锁提供互斥，读取线程看到的是稳定状态，不需要重试。

### 2.20（辨析）文件锁、futex 与互斥量有何差异？

- 互斥量在进程内有效，依赖共享内存与线程库，所有者是线程。
- futex 是内核等待队列，用户态原子变量与内核等待配合，可跨进程共享映射。
- 文件锁由文件系统维护，可跨进程与跨主机，网络文件系统上的语义由实现定义。
- 文件锁的粒度是文件或字节范围，释放依赖关闭文件描述符或显式解锁。
- 进程崩溃时文件锁通常由内核释放，互斥量不会自动释放。
- 文件锁的性能受文件系统与网络影响，不适合高频短临界区。
- 三种机制的故障模型不同，跨进程协调需要选择与故障模型匹配的原语。

## 3. 无锁与原子

### 3.1 CAS 循环应如何编写与处理失败？

- CAS 循环先读取当前值，计算新值，再以比较交换尝试更新，失败时重新读取。
- 失败意味着期间有其他线程修改了变量，需要基于最新值重新计算，不能复用旧的计算结果。
- `compare_exchange_weak` 允许伪失败，必须放在循环中；`compare_exchange_strong` 不会伪失败，在部分平台上需要额外指令。
- 成功与失败的内存序分别指定，失败序不能是 `release` 或 `acq_rel`，也不能强于成功序。
- 昂贵计算应放在 CAS 成功之后，循环内只保留必要的工作。
- 高竞争下循环次数上升，需要退避或改用阻塞方案。
- 返回值语义要区分 CAS 成功与值恰好等于目标，后者不一定需要写入。

### 3.2（陷阱）CAS 循环为什么会出现活锁与饥饿？

- 多个线程持续失败并重试时，系统整体仍在推进，但某个线程可能长期无法成功。
- 活锁指线程不断重试却无法完成，通常由对称的退避策略或固定冲突模式引起。
- 饥饿指低优先级线程在竞争中长期失败，无锁结构不保证公平。
- 随机延时与指数退避可以打破对称，但会增加延迟与尾延迟。
- NUMA 系统上远端 CAS 延迟更高，竞争会放大不均衡。
- 需要严格有界完成时间时应选择 wait-free 结构或加锁。
- 观测 CAS 失败率可以用性能计数器或插桩，失败率高说明竞争已超过无锁结构的收益区间。

### 3.3 ABA 问题如何检测与规避？

- ABA 指值从 A 变为 B 又变回 A，CAS 只比较值，无法发现中间变化。
- 无锁栈的弹出、释放与重新分配是典型场景，地址复用使比较失效。
- 带版本号的指针把值与计数打包成双字，CAS 同时比较两者。
- 双字 CAS 需要平台支持，x86-64 上使用 `cmpxchg16b`，要求 16 字节对齐。
- 延迟回收（hazard pointer、epoch、RCU）保证被观察的地址在访问期间不被复用。
- 用索引加代数替代裸指针也可以避免地址复用带来的 ABA。
- 版本号会回绕，回绕周期需要大于并发操作数，实际宽度由实现决定。

### 3.4 安全内存回收需要满足哪些条件？

- 回收必须保证没有线程仍能访问该对象，访问窗口从取得指针开始到最后一次解引用结束。
- 仅靠 CAS 成功不能证明独占，其他线程可能仍持有旧指针。
- 回收方案需要让读侧发布其访问意图，或在宽限期结束后统一释放。
- 读侧发布与指针读取之间需要顺序约束，否则发布前的读取可能看到已回收对象。
- 回收延迟越短，内存占用越低，但扫描越频繁。
- 回收方案必须处理线程崩溃或长时间阻塞，否则宽限期无法结束。
- 回收的正确性依赖所有访问路径都遵守协议，混用普通指针会破坏保证。

### 3.5（场景）回收滞后导致内存上涨如何定位？

- 待回收队列长度与宽限期时长是主要指标，队列持续增长说明回收跟不上分配。
- 读侧临界区过长、线程阻塞或停滞会推迟宽限期。
- 回收线程优先级过低或扫描周期过长会导致释放延迟。
- 分配速率突增时，回收吞吐不足会放大内存占用。
- 观测可以结合分配器统计、待回收队列长度与线程状态。
- 限制临界区长度、提高回收线程优先级或改用引用计数可以缓解。
- 回收滞后与内存泄漏的表现相似，需要区分对象是否仍可达。

### 3.6（辨析）CAS 与 LL/SC 有何差异？

- CAS 比较值，LL/SC 通过加载链接与条件存储检测期间是否有任何写。
- 单次 LL/SC 不存在 ABA，因为任何写都会使链接失效。
- CAS 在 x86 上是单条指令，LL/SC 在 ARM、Power 上由两条指令组成。
- LL/SC 可能伪失败，条件存储可能在没有冲突时失败，需要循环。
- 在 LL/SC 上模拟 CAS 需要循环，在 CAS 上模拟 LL/SC 需要额外标记。
- 两种原语的进度保证不同，LL/SC 的伪失败会影响 wait-free 的实现。
- 可移植代码应使用 `std::atomic` 的 compare_exchange，由实现选择底层原语。

### 3.7 无锁队列的线性化点如何确定？

- 线性化点是操作看起来原子生效的瞬间，入队通常是链接新节点的那次 CAS。
- 出队的线性化点通常是推进 `head` 的 CAS，读取节点值不构成线性化点。
- 辅助操作（帮助推进 `tail`）不改变操作的线性化点，但影响可观察顺序。
- 内存序必须保证线性化点之前的写入对读到该点的线程可见。
- 回收协议必须在最后一个可能观察该点的线程离开后才能释放节点。
- 线性化点不唯一，选择不同实现会得到不同的并发语义。
- 验证线性一致性需要为每个操作记录调用与返回区间，并检查存在合法顺序。

### 3.8（辨析）lock-free、wait-free 与 obstruction-free 有何区别？

- lock-free 保证系统整体在有限步内推进，至少一个线程完成操作，个别线程可能饥饿。
- wait-free 保证每个线程在有限步内完成，不受其他线程影响，实现难度最高。
- obstruction-free 只保证无竞争时单线程能完成，竞争时需要回退，实用价值有限。
- 三者都不保证公平性，lock-free 下某个线程可能长期失败。
- 结构越复杂，达到 lock-free 的难度越高，队列比栈难，哈希表更难。
- 判断一个结构是否 lock-free 需要分析所有交错，不能只看是否使用了 CAS。
- 标准库容器不提供无锁保证，`std::atomic` 只保证单个对象的原子性。

### 3.9（辨析）原子操作与缓存一致性协议如何交互？

- 原子读改写需要独占缓存行，核心通过一致性协议获取所有权。
- 独占导致其他核心的副本失效，后续访问需要重新取数。
- 缓存行在核心之间迁移的延迟远高于命中本地缓存。
- 原子操作的开销主要来自所有权转移，而非指令本身。
- 放松内存序不能消除独占，只能减少屏障与顺序约束。
- 只读的原子加载可以保持共享状态，但仍需处理失效。
- 伪共享与原子竞争都会放大一致性流量，需要分开测量。

### 3.10 原子操作的开销如何测量？

- 无竞争时原子读写的开销接近普通访存，原子读改写需要锁定缓存行。
- 竞争时开销来自缓存行所有权转移与一致性协议流量，随核心数上升。
- 测量应区分吞吐与延迟，微基准要固定频率、隔离核并防止编译器优化掉结果。
- `perf stat` 的缓存未命中、总线周期与带 `lock` 前缀的指令计数可以作为间接指标。
- 基准必须包含互斥量版本，无锁不一定更快。
- 结果受 NUMA 拓扑与超线程影响，跨节点访问需要单独评估。
- 微基准中的预热不足与协调遗漏会低估延迟。

### 3.11（陷阱）原子变量能保证复合操作的正确性吗？

- 单个原子操作具有原子性，多个原子操作组合起来不构成一个原子操作。
- 读取计数、判断、再写入需要 CAS 循环或锁，否则检查与写入之间状态可能变化。
- 两个原子变量之间没有原子性，跨变量的不变量仍需锁或版本号。
- 原子性不提供顺序，缺少内存序时其他线程可能看到部分更新。
- 把复合状态打包进单个机器字可以用一次 CAS 完成，但受字宽限制。
- 原子操作不能替代对不变量的设计，先明确哪些状态必须一起变化。

### 3.12 引用计数如何支撑无锁对象生命周期？

- `std::shared_ptr` 的引用计数是原子的，控制块与对象的析构顺序由标准规定。
- 多线程对同一个 `shared_ptr` 对象读写仍需要同步，`std::atomic<std::shared_ptr<T>>` 才提供原子替换（P0718R2）。
- 原子 `shared_ptr` 在部分平台上需要 16 字节原子操作，否则内部加锁，由实现定义。
- 侵入式引用计数把计数放在对象内，减少一次间接访问，但要求对象配合。
- 计数归零时的析构发生在最后一个释放者线程，可能造成延迟尖峰。
- 循环引用需要弱引用打破，弱引用升级为强引用需要原子地检查计数。
- 无锁结构中的引用计数需要防止计数归零后仍被访问，通常配合 hazard pointer。

### 3.13（实现）无锁计数器如何分片？

- 所有线程对同一个原子计数器做读改写会形成单点竞争，吞吐随核心数下降。
- 分片为每线程或每核心一个计数器，读取时汇总，写入无竞争。
- 汇总读取只提供近似值，不构成线性一致的快照。
- 分片数通常取核心数或 2 的幂，分片之间按缓存行对齐。
- 需要精确计数时使用单个原子变量，或定期合并分片。
- 分片的生命周期与线程绑定，线程退出时需要把计数归并到全局。
- 分片计数适合监控、限流与采样，不适合需要严格顺序的序号生成。

```cpp
struct Shard { alignas(64) std::atomic<long> n{0}; };
Shard shards[8];

void add(int i, long v) {
    shards[i % 8].n.fetch_add(v, std::memory_order_relaxed);
}
long total() {
    long s = 0;
    for (auto& sh : shards) s += sh.n.load(std::memory_order_relaxed);
    return s;
}
```

### 3.14 内存序在无锁队列中如何选择？

- 生产者的数据写入必须在发布索引之前完成，索引用释放语义存储。
- 消费者用获取语义读取索引，保证看到索引时也能看到对应数据。
- 只读取自己写入的索引时可以用 relaxed，避免不必要的屏障。
- 需要全局顺序时用 `seq_cst`，多数队列只需 acquire/release。
- 索引与数据分离存放时，数据本身的发布还需要额外的释放操作或屏障。
- 内存序的最小化需要逐个操作证明，过度弱化会产生难以复现的竞态。
- 在 x86 上 acquire/release 大多编译为普通指令，错误往往在 ARM 上才暴露。

### 3.15（场景）读多写少的无锁结构如何优化？

- 读多写少时读侧的无锁路径决定吞吐，写侧可以承担更高代价。
- 读侧避免原子读改写，使用获取语义加载或每线程副本。
- 写侧采用复制后发布的方式，读取线程继续使用旧版本。
- 版本号或代际计数可以让读取线程检测结构变更并重试。
- 读侧缓存可以进一步减少共享访问，但需要失效协议。
- 写侧批量合并可以减少发布次数，代价是更新延迟。
- 优化后需要重新验证内存回收与 ABA。

### 3.16（场景）原子操作在 NUMA 系统上有哪些额外代价？

- 跨节点原子读改写需要经过互连，延迟高于本地节点。
- 缓存行所有权在节点之间转移，可能产生远端流量与排队。
- 远端核心在原子竞争中的失败率更高，公平性更差。
- 把热点原子变量放在访问最频繁的节点，或按节点分片。
- 线程迁移会改变访问的远近关系，CPU 绑定与内存绑定需要配合。
- 观测远端内存访问与互连流量可以判断原子操作是否跨节点。
- 具体代价由拓扑与固件决定，不能仅凭节点编号推断。

### 3.17 无锁代码如何测试与验证？

- 常规单元测试难以覆盖所有交错，需要压力测试与模型检查结合。
- 压力测试用多线程反复执行操作，配合断言检查不变量，运行时间长。
- 模型检查工具可以枚举弱序下的执行，发现仅在特定重排下出现的错误。
- ThreadSanitizer 可以检测数据竞争，但不能证明无锁算法正确。
- 在弱序架构上运行测试可以发现 x86 上不暴露的重排问题。
- 形式化验证需要写出线性化点与不变量，成本高但适合核心结构。
- 代码评审应逐个检查内存序与回收路径，这两处最容易出错。

### 3.18（场景）跨节点的 CAS 为什么不能直接使用？

- CAS 依赖共享内存与缓存一致性，跨节点没有共享地址空间。
- 分布式场景用共识协议或租约模拟原子读改写，代价是网络往返。
- 网络分区下无法同时保证可用性与强一致，需要在两者之间选择。
- 重试与超时会导致操作重复执行，需要幂等或去重。
- 版本号与条件写接口可以近似 CAS，但仍受分区与延迟影响。
- 分布式事务的提交协议比单机 CAS 复杂得多，故障模型不同。
- 把单机无锁算法直接搬到分布式系统，会在故障与延迟上失效。

### 3.19 原子操作在信号处理与中断上下文中的限制？

- 信号处理程序只能调用异步信号安全的函数，标准库的多数设施不可用。
- 与信号处理程序共享的变量应使用 `std::atomic` 并确认 `is_lock_free`，或使用 `volatile std::sig_atomic_t`。
- 信号处理程序运行在被打断线程的上下文中，加锁可能自死锁。
- 内存序在信号上下文中仍然有效，可用的同步手段有限。
- 中断上下文不能睡眠，自旋等待可能死锁。
- 跨信号与主流程的通信通常用原子标志加 `eventfd` 或管道唤醒。
- 未确认无锁的原子操作可能内部加锁，不适合放在信号处理程序中。

### 3.20（陷阱）用普通变量加编译器屏障能实现原子吗？

- 编译器屏障只阻止编译器重排，不阻止处理器重排，也不保证访问原子。
- 普通变量的读写在多线程下构成数据竞争，行为未定义。
- 对齐的机器字读写在某些平台上恰好原子，但语言不保证，编译器也可能拆分。
- `volatile` 只保证访问不被优化掉，不提供原子性与顺序。
- 需要原子性时必须使用 `std::atomic` 或平台提供的原子内建函数。
- 依赖恰好原子的实现会在编译器升级或平台迁移时失效。
- 正确做法是把同步需求写成标准原子操作，由编译器与硬件共同保证。

## 4. 内存模型与内存序

### 4.1 happens-before 能保证哪些可见性？

- 若操作 A happens-before 操作 B，A 的普通内存写对 B 之后的读可见，这是发布数据的基础。
- 该关系是偏序，不要求任意两个操作之间可比。
- 它不保证执行时间上的先后，也不保证其他线程以相同顺序观察到无关操作。
- 它不提供原子性，冲突访问仍需要原子操作或锁。
- 线程创建、`join`、锁的加解锁、原子释放获取与 `promise`/`future` 都能建立该关系。
- 两个操作之间没有该关系且至少一个为写时，构成数据竞争。
- 传递性使可见性可以沿链传播，但链上每一环都需要合法的同步。

### 4.2（辨析）sequenced-before 与 inter-thread happens-before 有何差异？

- sequenced-before 描述单线程内的求值顺序，由语言规则确定。
- inter-thread happens-before 包含 synchronizes-with 与依赖排序，再取传递闭包。
- 单线程内的先后只保证该线程观察到的顺序，不保证其他线程以相同顺序观察。
- 编译器可以在不改变单线程可观察行为的前提下重排，sequenced-before 不阻止这种重排。
- 需要跨线程可见性时，必须通过同步操作建立 synchronizes-with。
- 依赖排序曾由 `memory_order_consume` 表达，C++17 起该内存序被弃用（P0460R0）。

### 4.3 发布订阅模式中为什么不能用 relaxed 存储指针？

- relaxed 只保证原子性，不建立跨线程的先后关系，构造写入可能被重排到指针存储之后。
- 订阅方读到非空指针时，对象成员可能尚未初始化，访问属于数据竞争。
- 发布方应使用 release 存储，订阅方使用 acquire 加载，才能让构造写入对读线程可见。
- 如果发布方与订阅方已有其他同步（如互斥量），relaxed 才可能够用，但需要证明。
- 回收旧对象仍需 hazard pointer 或 RCU，内存序不解决生命周期问题。
- 这类错误在强序的 x86 上可能长期不出现，迁移到 ARM 后才暴露。

### 4.4（条款）数据竞争的定义与后果是什么？

- 两个线程访问同一内存位置，至少一个为写，且两者之间没有 happens-before，构成数据竞争（`[intro.races]`）。
- 数据竞争导致未定义行为，程序不再受语言语义约束。
- 未定义行为不一定崩溃，可能表现为读到撕裂值、访问被优化掉或偶发错误。
- 原子操作本身不会构成数据竞争，但缺少正确内存序仍可能破坏不变量。
- 数据竞争与竞态条件不同，后者是逻辑层面的顺序依赖。
- ThreadSanitizer 可以检测多数数据竞争，存在漏报与误报。
- 消除数据竞争需要为每次冲突访问建立 happens-before，或改用原子操作。

### 4.5 无锁栈的 push 与 pop 需要哪些内存序？

- push 先构造新节点，再用 release 语义更新头指针，保证节点内容先于指针可见。
- pop 用 acquire 语义读取头指针，成功后再用 CAS 更新，失败时重试。
- CAS 的失败序通常用 relaxed，因为失败分支不读取节点内容。
- ABA 问题需要 tagged pointer、hazard pointer 或 epoch 回收配合，内存序不能替代。
- 高竞争下 CAS 失败率上升，退避策略与缓存行填充比内存序更影响吞吐。
- 正确性论证应基于 happens-before，而不是某款处理器的实际重排行为。

### 4.6 relaxed 在什么条件下仍然安全？

- relaxed 保证原子性与同一对象的修改顺序，不建立跨线程顺序。
- 适合独立计数器、统计采样，以及不需要同步其他数据的标志。
- 不能用 relaxed 发布指针或缓冲区，读取线程可能看到新指针但看不到内容。
- 同一线程对同一对象的 relaxed 操作仍保持程序顺序。
- relaxed 读改写可以参与释放序列，帮助传递可见性。
- 弱序架构上 relaxed 仍可能需要原子指令，只是不带屏障。

### 4.7 seq_cst 的代价在什么情况下值得支付？

- 所有顺序一致操作存在单一总顺序，且与 happens-before 一致，这是 acquire/release 不提供的。
- 需要多个变量之间不依赖 happens-before 的全局顺序时，只能使用 seq_cst 或显式屏障。
- 单一生产者发布、单一消费者读取的路径通常不需要总顺序，acquire/release 足够。
- x86 上顺序一致存储需要 `xchg` 或 `mfence`，弱序架构需要完整屏障，成本高于单向约束。
- 把 seq_cst 改为 acquire/release 前，需要证明算法不依赖跨对象的全局顺序。
- 默认使用 seq_cst 更安全，热路径再按测量结果放宽。

### 4.8（输出题）store buffering 在两个线程上可能输出什么？

- 两个线程各自先写后读，若严格按程序顺序执行，至少有一个线程读到对方的写，两个读不会同时为 0。
- 在允许 store-load 重排的平台上，两个读都可能发生在对方的写之前，出现两个读都为 0 的结果。
- x86 的 TSO 允许 store-load 重排，因此该结果在 x86 上也可以观察到。
- 把四个操作都改为 `seq_cst` 后，该结果不再允许出现。
- 只把存储改为释放、加载改为获取，仍不能排除该结果。
- 该例说明原子性不提供顺序，内存序决定允许的结果集合。

```cpp
std::atomic<int> x{0}, y{0};
int r1 = 0, r2 = 0;

void t1() {
    x.store(1, std::memory_order_relaxed);
    r1 = y.load(std::memory_order_relaxed);
}
void t2() {
    y.store(1, std::memory_order_relaxed);
    r2 = x.load(std::memory_order_relaxed);
}
// 两个线程 join 之后，r1 == 0 && r2 == 0 是允许的结果
```

### 4.9 内存屏障与带序原子操作有何区别？

- `std::atomic_thread_fence` 不绑定某个原子对象，约束屏障两侧的内存操作。
- 释放屏障与获取屏障之间仍需一次原子读写建立同步，仅有两个屏障不构成同步。
- 原子操作的 acquire/release 语义只作用于该操作，屏障可以一次约束多个 relaxed 操作。
- 屏障的代价可能低于多个带序原子操作，但更难推理。
- `std::atomic_signal_fence` 只约束编译器，不生成硬件指令，用于同一线程内的信号处理。
- 屏障不能替代原子性，普通变量的数据竞争仍需原子操作或锁解决。
- 在 x86 上释放屏障与获取屏障通常只编译为编译器屏障，弱序架构上才生成指令。

### 4.10 编译器如何在不违反语义的前提下重排？

- as-if 规则允许编译器改变执行方式，只要可观察行为不变。
- 单线程内，编译器可以重排不影响结果的读写，合并或消除冗余访问。
- 原子操作与 `volatile` 访问的顺序受语言规则约束，编译器不能随意跨越。
- 函数调用、异常与 `setjmp` 等会限制优化，具体由编译器决定。
- 数据竞争使程序行为未定义，编译器没有义务保留竞争访问的顺序。
- 需要精确控制时使用原子操作或屏障，不能依赖编译器的当前行为。
- 不同优化级别下的重排可能不同，调试构建正常不代表发布构建正确。

### 4.11 x86 的 TSO 与 ARM 的弱序有何差异？

- x86 的 TSO 允许 store-load 重排，不允许 load-load、load-store 与 store-store 重排。
- ARMv8 是弱序模型，四类重排都可能发生，需要 `LDAR`、`STLR` 或 `DMB` 约束。
- x86 的 `lock` 前缀指令与 `mfence` 提供完整屏障，普通 `mov` 不提供。
- ARM 上的释放存储与获取加载有专门指令，比完整屏障便宜。
- 在 x86 上正确的代码可能依赖了较强的硬件顺序，移植到 ARM 后暴露问题。
- C++ 内存模型屏蔽这些差异，按标准写代码才能在两种架构上正确。
- 弱序架构上 relaxed 操作仍可能需要原子指令，只是不带顺序约束。

### 4.12（实现）如何用 release/acquire 实现发布订阅？

- 发布方先完成对象的构造与初始化，再以释放语义写入指针。
- 订阅方以获取语义读取指针，读到非空即可安全访问对象成员。
- 释放语义保证构造写入不会被重排到指针存储之后，获取语义保证成员读取不会被提前。
- 旧对象的回收需要额外机制，读取线程可能仍持有指针，不能立即释放。
- 多个读取线程可以配合引用计数或 hazard pointer。
- 该模式是 RCU 与无锁数据结构发布节点的基础。

```cpp
struct Config { int a; int b; };
std::atomic<Config*> slot{nullptr};

void publish() {
    auto* c = new Config{1, 2};
    slot.store(c, std::memory_order_release);
}
void consume() {
    Config* c = slot.load(std::memory_order_acquire);
    if (c) use(c->a, c->b);
}
```

### 4.13 修改顺序与一致性规则如何约束读值？

- 每个原子对象都有修改顺序，所有线程对该顺序的观察一致。
- 写写一致性：同一线程对同一对象的两次写，按程序顺序进入修改顺序。
- 读读一致性：线程两次读同一对象，后一次读不会读到修改顺序中更早的值。
- 读写一致性：读到某次写之后，后续写不会排在它之前。
- 修改顺序由实现维护，但所有线程看到同一顺序。
- 这些规则由 `[atomics.order]` 描述，是原子操作可推理的基础。
- 修改顺序不建立跨线程 happens-before，只约束同一对象的可观察值。

### 4.14（场景）自旋锁需要哪种内存序？

- 获取锁的原子操作需要获取语义，释放锁需要释放语义。
- 只用 relaxed 会让临界区内的读写逸出到锁外，破坏互斥。
- 测试后再测试并设置（TTAS）的第一次测试用 relaxed 即可，成功获取的那次用获取语义。
- 解锁用释放语义，保证临界区写入在解锁前完成。
- 需要睡眠时，futex 的等待与唤醒由原子状态机配合，内存序仍由原子操作决定。
- `seq_cst` 更简单，但自旋锁通常用 acquire/release 即可。
- 锁的公平性与内存序无关，由排队策略决定。

### 4.15（场景）跨进程共享内存中的原子操作需要满足哪些条件？

- 共享内存映射到不同进程，原子对象要求相同的布局与对齐，类型需可平凡复制。
- `std::atomic` 的无锁性由实现定义，跨进程使用前要确认 `is_lock_free` 与 ABI 一致。
- 不同进程可能使用不同编译器或标准库版本，原子对象的布局与锁实现可能不同。
- 进程崩溃不会释放互斥量，健壮互斥量可以在持有者死亡后恢复。
- 内存序语义在共享内存上仍然适用，映射属性由平台决定。
- 需要跨进程通知时使用 futex 或共享内存上的原子等待；结构中保存指针时，映射地址必须一致。
- 共享内存必须使用共享映射，私有映射的写时复制会让各进程看到不同副本，原子操作不再作用于同一对象。

### 4.16（场景）对象所有权跨线程移交时如何避免释放后使用？

- 所有权传递要求发送方在释放写之前完成对象状态设置，接收方以获取读取得指针或索引。
- 传递的是访问权而非对象本身时，发送方必须停止访问，否则仍有数据竞争。
- 队列传递对象需要保证元素构造完成后再发布索引。
- 接收方析构对象时，发送方不能再持有引用，引用计数可以简化判定。
- 所有权传递不保证实时顺序，接收方可能延迟看到对象。
- 失败路径（队列满、取消）必须把所有权归还或销毁，避免泄漏。
- 跨进程传递还要考虑地址空间与析构责任。

### 4.17（场景）内存序错误在生产环境为何难以复现？

- 错误依赖特定的重排与交错，测试负载与硬件可能长期不触发。
- x86 的强序模型掩盖缺失的获取释放，代码在 ARM 上才失败。
- 优化级别改变会改变重排与寄存器分配，调试构建正常不代表发布构建正确。
- 线上流量、核心数与 NUMA 拓扑与测试环境不同，暴露概率不同。
- 错误一旦触发可能表现为数据损坏而非崩溃，难以定位。
- 复现需要压力测试、弱序平台与模型检查结合。
- 代码评审与静态检查应重点检查发布路径与回收路径。

### 4.18 静态存储期的原子对象如何安全初始化？

- 能常量初始化的静态原子对象在常量初始化阶段完成，不产生动态初始化竞争。
- 局部静态变量的初始化由语言保证线程安全（`[stmt.dcl]`），不需要额外的双检锁。
- 动态初始化的原子对象在其他线程使用前必须有 happens-before，不能依赖零初始化。
- C++20 起 `std::atomic` 的默认构造进行值初始化，此前默认构造不初始化值（P0883R2）。
- 全局对象的构造顺序跨翻译单元未指定，原子对象也不例外。
- 用函数内静态对象延迟初始化可以避免初始化顺序问题。
- 线程启动后再动态初始化共享原子对象，需要同步保证其他线程不会同时访问。

### 4.19（陷阱）两次 acquire 读能得到一致快照吗？

- 分别以获取语义读取两个原子变量，两次读之间可能被其他线程修改，结果来自不同时刻。
- 两个读都成功只说明各自读到了某个合法值，不说明二者属于同一状态。
- 需要一致快照时应把数据打包进单个原子对象，或使用序列锁。
- 序列锁用版本号：读取线程先读版本（偶数）、读数据、再读版本，版本变化或为奇数则重试。
- 读侧需要屏障，防止数据读取被重排到版本检查之外。
- 写入线程递增版本、写数据、再递增版本；读取线程可能读到撕裂数据，必须重试。
- 序列锁适合读多写少且数据较小的场景，读侧无锁但可能饥饿。

### 4.20 atomic_ref 对普通内存有什么要求？

- `std::atomic_ref` 为已有对象提供原子访问，不改变对象类型（P0019R8）。
- 对象对齐必须满足 `required_alignment`，否则行为未定义。
- 在 `atomic_ref` 引用对象期间，所有访问都必须通过 `atomic_ref`，混用普通访问构成数据竞争。
- 适合无法修改类型定义的场景，例如第三方结构体或内存映射区域。
- 无锁性与 `std::atomic` 一致，由实现定义。
- 不能用于 `const` 对象、位域或生命周期尚未开始的对象。
- 多个 `atomic_ref` 可以指向同一对象，前提是所有访问都经由原子接口。

## 5. 线程池与任务队列

### 5.1 线程池由哪些部分组成？

- 一组工作线程，数量可以固定，也可以按负载伸缩，每个线程循环取任务并执行。
- 一个任务队列，保存尚未开始的任务，队列容量决定背压能力与内存上限。
- 同步机制，包括互斥量与条件变量，或原子操作与等待策略，用于协调生产者与消费者。
- 生命周期状态，至少区分运行、停止接收、排空与终止，避免关闭过程中的竞态。
- 拒绝策略与监控指标，覆盖队列长度、等待时间、活跃线程数、完成数与失败数。
- 可选的调度策略，例如优先级、线程亲和性与工作窃取，决定任务到线程的映射。

### 5.2 固定线程池为什么在任务突增时出现尾延迟？

- 线程数固定，队列长度随到达率超过服务率而增长，排队时间随之放大。
- 任务粒度不均时，长任务占用工作线程，短任务排在后面，形成队头阻塞。
- 线程池没有区分 I/O 密集与计算密集任务，阻塞调用把线程从可用资源中移除。
- 突发流量下，唤醒与锁竞争增加，上下文切换成本上升，服务率进一步下降。
- 尾延迟通常由排队而非执行时间主导，需要分别测量等待时间与服务时间。
- 扩容、限流、任务拆分与优先级隔离可以缓解，但不能消除容量上限。

### 5.3 有界队列满时有哪些处理策略？

- 阻塞生产者，直到队列出现空位，背压最直接，但可能把阻塞传播到调用链上游。
- 立即失败并返回错误，由调用方决定重试或降级，适合延迟敏感的服务。
- 丢弃新任务或丢弃最旧任务，前者保护已接收工作，后者降低陈旧任务的影响。
- 由提交任务的线程直接执行，即 `caller-runs`，把压力反馈给上游并维持吞吐。
- 按优先级拒绝，先丢弃低优先级或可重试任务，保留关键路径任务。
- 策略需要与超时、重试和幂等性一起设计，单纯丢弃会造成静默数据丢失。

### 5.4 背压如何从队列传递到上游？

- 队列容量是背压的物理边界，容量为零的 rendezvous 队列把生产与消费严格同步。
- 阻塞式提交把压力转化为调用方线程的等待，适合线程模型简单的服务。
- 异步接口返回 `std::future` 或错误码，队列满时以明确状态拒绝，避免无限缓存。
- 以队列等待时间而非长度作为信号，超过阈值即降低准入速率。
- 上游使用令牌桶、并发上限或自适应限流，把端到端延迟控制在目标内。
- 背压必须覆盖重试流量，否则重试会绕过限流并放大拥塞。

### 5.5 无界队列为什么容易导致内存耗尽？

- 到达率持续高于服务率时，队列没有上限，积压任务的对象与捕获状态持续增长。
- 每个任务可能持有缓冲区、连接或大对象，队列长度只是表象，实际占用按任务大小放大。
- 内存压力触发换页与分配器竞争，服务率下降，积压进一步加速。
- 进程被 OOM 终止时，队列中的任务全部丢失，且没有拒绝记录可供排查。
- 无界队列掩盖了容量问题，监控只看到延迟上升，看不到明确的过载信号。
- 应设置硬上限，并按任务大小估算内存预算，而不是只限制任务个数。

### 5.6 条件变量任务队列如何避免丢失唤醒与虚假唤醒？

- 等待必须使用谓词循环，条件为队列非空或进入停止状态，不能只判断一次。
- 入队与出队在同一个互斥量保护下修改队列，通知放在解锁之后或之内均可，但不能遗漏。
- 停止时使用 `notify_all`，让所有工作线程重新检查停止谓词并退出。
- 虚假唤醒由谓词循环吸收，不能假设 `wait` 返回就一定有任务。
- 若使用带超时的 `wait_for`，超时后同样要重新检查谓词与停止状态。
- 关闭与入队并发时，先置停止标志再通知，避免新任务进入已排空的队列。

```cpp
std::unique_lock<std::mutex> lk(m);
cv.wait(lk, [&] { return !q.empty() || stopping; });
if (stopping && q.empty()) return;
auto task = std::move(q.front());
q.pop_front();
lk.unlock();
task();
```

### 5.7 任务队列的锁粒度如何选择？

- 单队列单锁实现简单，入队与出队串行化，核心数增加后锁成为竞争点。
- 分片队列按哈希或线程编号划分，降低竞争，但负载不均时需要迁移或窃取。
- 每线程双端队列让所有者从一端取任务，其他线程从另一端窃取，减少公共锁。
- 锁的临界区只保护指针与计数，任务对象的构造与析构移到锁外，缩短持有时间。
- 伪共享会让相邻原子计数器互相失效，高频字段应按缓存行对齐。
- 无锁队列并不必然更快，ABA、内存回收与内存序成本可能超过互斥量。

### 5.8 工作窃取如何降低调度开销？

- 每个工作线程维护本地双端队列，任务提交到本地，减少全局队列的竞争。
- 所有者从队列一端取任务，窃取者从另一端取，减少与所有者的冲突。
- 本地队列为空时随机选择受害者，批量窃取一半任务，分摊窃取成本。
- 父任务等待子任务时，工作线程可以转而执行其他任务，减少空转。
- 窃取会增加缓存行迁移与内存分配，任务过小反而降低吞吐。
- 负载不均与长任务仍会造成尾延迟，需要任务拆分与窃取超时。

### 5.9 线程池关闭的状态机如何设计？

- 状态机至少包含运行、停止接收、排空与终止，关闭请求只允许从运行进入停止接收。
- 停止接收后，提交接口返回明确错误，已接收任务继续执行。
- 排空阶段等待队列清空与在途任务完成，设置总超时，避免无限等待。
- 超时后请求协作取消，仍未完成则记录未完成任务，由上层决定是否终止进程。
- 工作线程在谓词循环中检查停止状态，退出前完成当前任务并释放线程局部资源。
- 关闭操作应幂等，重复调用返回相同结果，且不能在 `worker` 线程内 `join` 自身。

### 5.10 「停止接收」与「等待排空」为什么要分开？

- 只停止接收而不排空，已入队任务可能被丢弃，调用方无法区分拒绝与丢失。
- 只排空而不停止接收，生产者持续入队，排空条件永远无法满足。
- 分开后可以给上游一个明确的拒绝窗口，同时给已接收任务一个完成期限。
- 排空阶段仍要处理任务异常，否则一个失败任务会中断整个关闭流程。
- 关闭超时后需要区分「已完成」「已取消」「未开始」三类结果，便于补偿。
- 状态转换应使用原子变量或受锁保护，提交路径与关闭路径共享同一状态判断。

### 5.11 线程池中的异常如何传播？

- 工作线程在任务外层捕获所有异常，绝不能让异常越过线程入口，否则调用 `std::terminate`。
- 通过 `std::promise` 或 `std::exception_ptr` 保存异常，提交方在 `future::get` 时重新抛出。
- 对于没有返回值的任务，写入错误通道或日志，并记录任务标识与异常类型。
- 异常处理本身不能抛出，捕获块中避免分配失败导致二次异常。
- 任务的部分副作用可能已经发生，异常传播不等于事务回滚，需要业务层补偿。
- 线程池应统计失败率，连续失败时触发降级或熔断，而不是无限重试。

### 5.12 任务抛异常导致工作线程退出会有什么后果？

- 线程函数未捕获异常时，标准要求调用 `std::terminate`，整个进程终止而非仅损失一个线程。
- 若实现或封装捕获后让线程退出，线程池可用线程数减少，队列继续增长。
- 线程局部存储与未完成的任务不会被清理，可能泄漏连接或锁。
- 依赖该线程的任务永远得不到执行，提交方等待的 `future` 可能一直不就绪。
- 退出原因若未记录，表现为吞吐下降而无明显错误，排查成本高。
- 线程入口统一加 `try/catch`，并在异常后继续循环或按策略重建线程。

### 5.13 线程池如何实现动态扩缩容？

- 以队列长度、等待时间与活跃线程数作为扩容信号，避免仅看 CPU 利用率。
- 扩容使用滞回区间与冷却时间，防止在阈值附近反复创建与销毁线程。
- 新线程创建可能失败，需要捕获 `std::system_error` 并回退到拒绝或排队。
- 缩容只回收空闲超过阈值的线程，回收前确认没有在途任务与线程局部资源。
- 最大线程数受内存、文件描述符与下游容量限制，不能只按 CPU 核数设定。
- 扩容解决的是排队，若瓶颈在下游，增加线程只会提高下游压力。

### 5.14 核心线程数与最大线程数如何落地？

- 核心线程数保持常驻，减少冷启动与线程创建开销，适合稳定负载。
- 最大线程数是过载时的上限，超过后触发队列或拒绝策略。
- 空闲线程超过 `keep_alive` 后回收，但保留核心线程，避免频繁抖动。
- 计算密集任务以硬件线程数为基准，I/O 密集任务按阻塞比例估算。
- 容器环境中 CPU 配额与 `nproc` 可能不一致，应读取 `cgroup` 限制。
- 线程数不是越多越好，超过下游并发能力会增加切换与排队。

### 5.15 空闲线程回收的判定条件是什么？

- 线程在等待队列时使用带超时的等待，超时后重新检查队列与空闲计数。
- 仅当空闲线程数大于核心线程数，且超过 `keep_alive` 时才允许退出。
- 退出前需要减少空闲计数并与扩容路径同步，避免刚决定退出又被分配任务。
- 回收应与任务提交竞争，使用同一把锁或原子状态保证判定原子性。
- 线程退出时释放线程局部存储、栈与注册的清理函数。
- 回收速度过快会导致频繁创建，过慢则浪费内存与调度资源。

### 5.16 阻塞任务与计算任务混合执行有什么问题？

- 阻塞调用占住工作线程，线程池的有效并行度下降，队列等待时间上升。
- 线程数按 CPU 核数设置时，少量阻塞任务即可耗尽全部线程。
- 阻塞任务持有的锁可能被计算任务需要，形成优先级反转或死锁。
- 应为阻塞任务设置独立线程池或专用执行器，按依赖隔离容量。
- 可异步化的阻塞点可以转为挂起，但底层仍需要线程执行就绪回调。
- 监控应区分阻塞时长与 CPU 时间，避免用 CPU 利用率误判容量。

### 5.17（场景）任务依赖同一线程池造成死锁如何排查？

- 症状是队列非空、线程全部处于等待状态，CPU 利用率接近零。
- 父任务提交子任务后同步等待，子任务排在队列尾部，所有线程都执行父任务并等待。
- 用线程转储查看调用栈，若多个线程停在 `future::get` 或条件变量等待，可确认该模式。
- 检查是否存在有界队列加同步等待的组合，这是典型的线程饥饿死锁。
- 修复方式是分离父子任务到不同池、使用 `caller-runs`、改为异步续接或限制等待超时。
- 预防手段包括禁止在池内同步等待、依赖图检测与队列水位告警。

### 5.18（场景）下游超时引发线程池级联阻塞如何处理？

- 下游变慢后，调用线程被阻塞，池内可用线程减少，上游请求排队。
- 上游超时后重试，重试流量进一步占用线程，形成正反馈。
- 为每个下游依赖设置独立池与并发上限，隔离故障域。
- 传播截止时间，任务在超时后不再发起新的下游调用。
- 使用熔断与快速失败，避免线程在已知故障的下游上排队。
- 监控排队时间、在途请求与重试比例，区分容量不足与下游故障。

### 5.19（实现）定时任务如何接入线程池？

- 使用最小堆按到期时间排序，堆顶是最早到期的任务。
- 定时线程等待到堆顶到期时间，使用 `wait_until` 并检查停止标志。
- 到期任务从堆中取出后提交到工作池，避免在定时线程执行长时间任务。
- 取消使用惰性删除，任务句柄标记取消，弹出时跳过。
- 系统时钟回拨会影响 `system_clock`，间隔计时使用 `steady_clock`。
- 堆操作需要锁保护，高频定时任务可分片或使用时间轮。

### 5.20（实现）线程池如何减少任务对象的分配与复制？

- 任务队列通常存储类型擦除的可调用对象，`std::function` 在捕获对象较大时可能分配堆内存。
- 使用 C++23 的 `std::move_only_function` 或自定义任务类型，避免复制并支持仅移动捕获。
- 小对象优化只在可调用对象足够小且移动构造不抛出时生效，是否生效由实现定义。
- 任务按值移动入队，避免复制捕获的 `shared_ptr` 导致引用计数原子操作增加。
- 使用侵入式队列节点，把任务存储与链表节点合并，减少一次分配。
- 对象池或 arena 分配器可以复用任务存储，但需要处理生命周期、对齐与异常安全。

## 6. future、promise 与 async

### 6.1 `std::future` 的共享状态包含什么？

- 一个存储值或异常的联合区域，以及表示结果是否就绪的标志。
- 引用计数，决定共享状态何时销毁，`future`、`promise` 与 `packaged_task` 各持有一份引用。
- 等待队列或同步对象，让 `get` 与 `wait` 在结果未就绪时阻塞。
- 创建时记录的启动策略，`std::async` 需要据此决定是否等待任务完成。
- 共享状态不与 `future` 一一对应，`shared_future` 可以有多个观察者。
- 标准在 `[futures.state]/1` 中描述共享状态，具体布局与锁策略由实现定义。

### 6.2 `std::promise` 与 `std::future` 如何建立关联？

- `promise` 构造时创建共享状态，`get_future` 返回关联的 `future`。
- `get_future` 只能调用一次，重复调用抛出 `future_error`，错误码为 `future_already_retrieved`。
- `promise` 通过 `set_value`、`set_exception` 或 `set_value_at_thread_exit` 让状态就绪。
- `future` 通过 `get` 读取值或异常，调用后不再持有共享状态。
- `promise` 与 `future` 只能移动，不能复制，转移所有权后原对象不再关联共享状态。
- 共享状态至少存活到最后一个引用释放，`promise` 先销毁不一定立即销毁状态。

### 6.3 `std::packaged_task` 与 `std::promise` 有什么差别？

- `packaged_task` 包装一个可调用对象，调用 `operator()` 时执行并自动把返回值或异常写入共享状态。
- `promise` 只提供设置结果的接口，执行逻辑由调用方编写。
- `packaged_task` 只能移动，不能直接放入要求可复制函数的 `std::function`。
- `packaged_task::get_future` 只能调用一次，任务被调用后状态就绪。
- `packaged_task` 可以 `reset` 后复用，但会放弃旧的共享状态。
- `promise` 更适合回调适配，`packaged_task` 更适合把函数提交给执行器。

### 6.4 `std::future::get` 为什么只能调用一次？

- `get` 返回并移出共享状态中的值，类型可移动时按移动构造，调用后 `future` 进入无效状态，`valid` 返回 `false`。
- 再次调用 `get` 抛出 `future_error`，错误码为 `no_state`。
- 共享状态中的结果只能被消费一次，避免对同一结果重复读取。
- 需要多次读取时使用 `shared_future`，其 `get` 返回 `const T&`。
- `wait` 不消费值，可以在 `get` 之前多次调用。
- 对 `future<T&>`，`get` 返回引用，不复制对象。

### 6.5 `share` 与移动语义如何影响所有权？

- `future::share` 把独占的 `future` 转为 `shared_future`，原 `future` 失效。
- `shared_future` 可以复制，多个线程可以同时等待与读取。
- `future` 只能移动，移动后源对象不再拥有共享状态。
- 把 `future` 放入容器需要使用移动迭代器或 `emplace_back`。
- 共享状态的引用计数归零时销毁，值的生命周期与最后一个 `shared_future` 绑定。
- 多个 `shared_future` 读取同一值时不加锁，要求值本身不可变或由调用方同步。

### 6.6 `std::promise` 析构时未设置值会发生什么？

- 若共享状态尚未就绪，析构函数存储 `std::future_error`，错误码为 `broken_promise`。
- 等待该状态的 `future::get` 会抛出该异常，而不是永久阻塞。
- 若已经调用过 `set_value` 或 `set_exception`，析构不再修改状态。
- 若 `future` 已销毁而 `promise` 仍存在，`set_value` 仍然可以成功，结果无人读取。
- 若 `promise` 被移动，只有持有共享状态的最后一个 `promise` 负责设置或放弃。
- 这一机制用于检测生产者提前退出，但不能替代业务错误码。

### 6.7 异常如何从任务传到 `std::future`？

- `std::async` 与 `packaged_task` 捕获可调用对象抛出的异常，存入共享状态。
- `promise::set_exception` 显式写入 `std::exception_ptr`，由 `get` 重新抛出。
- `get` 重新抛出共享状态中保存的异常，异常类型保持不变。
- 异常由库在任务边界捕获，不会直接终止执行线程。
- 异常传播不包含堆栈信息，需要在线程入口记录日志或使用错误上下文。
- 对 `future<void>`，异常同样通过 `get` 传播，返回值无关。

### 6.8 `std::async` 的 `launch` 策略如何选择？

- `std::launch::async` 要求在新线程上执行，若无法创建线程抛出 `std::system_error`。
- `std::launch::deferred` 延迟到首次 `get` 或 `wait`，在调用线程执行。
- 默认策略是 `std::launch::async | std::launch::deferred`，具体选择由实现定义，可能延迟执行。
- 需要并发保证时显式传 `std::launch::async`，不能依赖默认策略。
- 需要惰性求值时传 `std::launch::deferred`，但要接受调用线程被占用。
- 策略按位或组合，传入其他位的行为未定义。

### 6.9 `std::launch::deferred` 在什么时机执行？

- 首次调用 `get` 或 `wait` 时，函数在调用线程同步执行。
- `wait_for` 对 deferred 返回 `std::future_status::deferred`，不会等待指定时长。
- 执行发生在调用 `get` 的线程，线程局部变量与调用栈属于该线程。
- 若始终不调用 `get` 或 `wait`，函数不会执行。
- deferred 不创建新线程，适合延迟计算，不适合需要后台并行的场景。
- 在 deferred 函数中阻塞会直接阻塞调用者。

### 6.10 `std::async` 返回的 `future` 析构为什么会阻塞？

- 标准允许 `future` 析构在满足条件时等待共享状态就绪。
- 条件是共享状态由 `std::async` 创建、尚未就绪，且当前 `future` 是最后一个引用。
- 临时 `future` 在完整表达式结束时析构，可能把异步调用变成同步等待。
- 阻塞行为由实现定义，标准使用「可能阻塞」的措辞。
- 若策略为 `deferred`，任务尚未开始，析构通常不会等待执行。
- 这是 `std::async` 与线程池提交任务的重要差异。

### 6.11 如何避免 `future` 析构阻塞？

- 把 `future` 保存到变量或容器，延长到任务完成之后再销毁。
- 使用线程池提交任务，由线程池管理任务生命周期，不依赖 `future` 析构。
- 需要分离执行时，使用 `std::jthread` 时由析构函数 `join`，显式线程需要主动 `join`。
- 不要用 `std::async` 创建临时 `future` 后立即丢弃，除非确实需要同步。
- 对批量任务，收集 `future` 后统一等待，避免逐个析构造成串行化。
- 若只需要触发而不需要结果，使用 `detach` 风险高，应改用受管执行器。

### 6.12 `wait_for` 超时后能否继续等待？

- `wait_for` 返回 `std::future_status::timeout` 只表示当前未就绪，不取消任务。
- `future` 仍然有效，可以再次调用 `wait_for`、`wait` 或 `get`。
- 超时是轮询手段，循环等待需要计算绝对截止时间，避免每次重新计时。
- 返回 `std::future_status::deferred` 表示任务尚未开始，需要 `get` 触发执行。
- 返回 `std::future_status::ready` 后 `get` 不会阻塞，但可能抛出保存的异常。
- 对有效 `future`，`wait_for` 以返回值表示超时；无效 `future` 会抛 `future_error`。

### 6.13 多个 `future` 如何等待？

- 标准 `std::future` 没有 `wait_all`，需要逐个等待或轮询。
- 顺序 `get` 会按提交顺序等待，后面的结果即使先完成也要等前面的 `future` 就绪。
- 使用 `shared_future` 与条件变量，所有任务完成时唤醒等待者。
- 使用 `wait_for` 加截止时间，可以在总超时后放弃等待，但任务仍在运行。
- C++26 的 `std::execution` 提供 `when_all` 等组合器，基于 sender 而非 `future`。
- 等待多个结果时要保留每个 `future` 的异常，不能因第一个异常提前退出而丢失其他结果。

### 6.14 `shared_future` 的并发读取语义是什么？

- 多个线程可以同时调用 `get`，返回同一共享状态的引用。
- `get` 不消费状态，可以重复调用，直到最后一个 `shared_future` 销毁。
- 对 `shared_future<T>`，`get` 返回 `const T&`，多个观察者共享只读视图。
- 对 `shared_future<T&>`，`get` 返回 `T&`，写操作仍需外部同步。
- `shared_future` 的复制与赋值不是原子操作，跨线程共享句柄仍需同步。
- 若保存的是指针或引用，生命周期由调用方保证，共享状态不延长被引用对象。

### 6.15 `future` 能直接放入线程池任务队列吗？

- `std::future` 本身不是可调用对象，不能直接作为任务交给线程池执行。
- `std::future` 只能移动，而 `std::function` 要求可复制，包装为任务会编译失败。
- `std::packaged_task` 把可调用对象与共享状态绑定，可由线程池执行。
- `std::packaged_task` 也只能移动，常用 `std::shared_ptr` 包装或改用 C++23 的 `std::move_only_function`。
- `std::packaged_task` 被移动后，原对象不再持有任务，调用会抛 `future_error`。
- 任务被拒绝时，需要让对应的 `promise` 进入就绪状态，否则等待者永久阻塞。

### 6.16 `std::promise` 多次设置结果会怎样？

- 第二次调用 `set_value` 或 `set_exception` 抛出 `future_error`，错误码为 `promise_already_satisfied`。
- 第一次设置后共享状态就绪，后续设置不会覆盖已有值。
- 重复设置通常来自回调重入，或超时与完成路径的竞争，适配层应用原子标志保证恰好一次。
- 若后到的结果被丢弃，仍应记录协议违例，便于定位上游行为。
- `set_value_at_thread_exit` 在退线程时设置，仍受同一约束。
- 对可能重复的回调，应在适配层做一次性封装，而不是依赖 `promise` 报错。

### 6.17（陷阱）`future` 与 `promise` 的生命周期如何错配？

- 把局部 `promise` 按引用传给线程，函数返回后引用悬空，写入是未定义行为。
- 把 `promise` 按值传给线程需要使用 `std::move`，否则编译失败。
- 先销毁 `promise` 再等待 `future`，`get` 收到 `broken_promise`。
- 在回调中捕获 `future` 的引用，回调触发时 `future` 已销毁。
- 使用 `shared_ptr<promise>` 延长生命周期，并确保只设置一次。
- 结构化并发把生产者与消费者放在同一作用域，减少生命周期错配。

### 6.18（场景）异步任务超时后线程仍占用资源如何处理？

- `std::future` 没有取消接口，超时只放弃等待，不停止任务。
- 任务继续占用线程、内存与下游连接，可能耗尽线程池容量。
- 为任务传入 `std::stop_token`，在检查点轮询并提前返回。
- I/O 操作使用带超时的接口，或通过取消机制中断阻塞调用。
- 结果写入使用共享状态，超时后仍要允许任务完成并释放资源。
- 对不可取消的任务，限制并发数并隔离到独立池，避免影响关键路径。

### 6.19（实现）如何用 `promise` 包装回调式 API？

- 创建 `promise`，取出 `future`，把 `promise` 移动到回调对象中。
- 回调成功时调用 `set_value`，失败时调用 `set_exception`。
- 回调可能被调用多次，使用 `std::atomic<bool>` 或一次性状态保证只设置一次。
- 回调可能永不触发，需要在超时路径设置 `broken_promise` 或显式异常。
- 回调对象销毁时若仍未设置结果，`promise` 析构会写入 `broken_promise`。
- 异步操作可能引用调用方缓冲区，`future` 就绪前不能销毁缓冲区。

```cpp
std::promise<int> p;
auto f = p.get_future();
auto sp = std::make_shared<std::promise<int>>(std::move(p));
start([sp](int v) { sp->set_value(v); });
return f;
```

### 6.20（条款）`future` 的错误码与异常如何区分？

- `std::future_error` 表示 `future` 与 `promise` 协议使用错误，如重复 `get`、重复设置、无共享状态。
- 任务本身抛出的异常通过 `get` 原样传播，类型由任务决定。
- `std::system_error` 可能来自线程创建失败或底层资源不足。
- 对有效 `future`，超时通过 `wait_for` 的返回值表达，不抛异常。
- 业务错误建议放入返回值或 `std::error_code`，不要与协议错误混用。
- `future_error` 也可能由任务自身抛出，判断来源需要结合调用位置与任务边界，不能只看异常类型。

## 7. 协程与异步 I/O

### 7.1 协程帧包含哪些内容？

- `promise` 对象，保存返回值、异常与恢复后继所需的协程状态。
- 形参副本，按值传递的参数被移动或复制到帧中，引用参数仍只保存引用。
- 跨挂起点的局部变量与临时对象，其生命周期与协程帧一致。
- 恢复点索引或状态机字段，记录下次恢复从何处继续。
- 协程句柄与销毁函数，用于恢复、查询完成状态与释放帧。
- 帧的大小与对齐在编译期确定，具体布局由实现定义。

### 7.2 协程帧在堆上还是栈上？

- 标准只要求协程状态在挂起后仍然存活，不规定具体存储位置。
- 常见实现通过协程的分配函数在堆上分配，若 `promise_type` 定义了 `operator new` 则使用它。
- 编译器可以执行分配省略，把帧放到调用者栈上，是否省略由实现定义。
- 帧大小影响缓存局部性与分配开销，捕获大对象会放大成本。
- 自定义 `operator new` 与 `operator delete` 可以使用池分配器，但必须匹配大小与对齐。
- 挂起后原调用栈可以销毁，恢复不依赖原栈帧。

### 7.3 `promise_type` 需要提供哪些定制点？

- `get_return_object` 创建返回给调用者的协程对象。
- `initial_suspend` 决定创建后立即执行还是先挂起。
- `final_suspend` 决定结束时是否保留帧，以便恢复等待者。
- `return_value` 或 `return_void` 处理 `co_return`。
- `unhandled_exception` 捕获协程体内未处理的异常。
- `yield_value` 与 `await_transform` 分别支持 `co_yield` 和自定义等待表达式。

### 7.4 `initial_suspend` 与 `final_suspend` 如何选择？

- `suspend_always` 让协程惰性启动，调用者获得句柄后再决定何时恢复。
- `suspend_never` 让协程立即执行，适合急切求值，但调用者可能无法获得已完成对象的句柄。
- `final_suspend` 返回 `suspend_always` 时帧保留，等待者可以在结束时恢复。
- `final_suspend` 返回 `suspend_never` 时帧自动销毁，之后访问句柄是未定义行为。
- `final_suspend` 应声明 `noexcept`，避免结束路径抛出异常。
- 需要对称转移时，`final_suspend` 的 `await_suspend` 返回后继句柄。

### 7.5 `co_await` 的变换过程是什么？

- 编译器先尝试 `promise.await_transform(expr)`，否则直接使用表达式。
- 若存在 `operator co_await`，调用它得到 awaiter；否则表达式本身作为 awaiter。
- 依次调用 `await_ready`、`await_suspend`、`await_resume`。
- `await_ready` 返回 `true` 时跳过挂起，直接执行 `await_resume`。
- `await_suspend` 接收当前协程句柄，负责注册回调或转移控制。
- `await_resume` 的返回值成为整个 `co_await` 表达式的结果。

### 7.6 awaiter 的三个成员各自职责？

- `await_ready` 判断结果是否已就绪，避免不必要的挂起。
- `await_suspend` 在挂起前执行，保存句柄并安排恢复条件。
- `await_resume` 在恢复后执行，返回结果或重新抛出异常。
- `await_suspend` 中可以注册 I/O、启动定时器或提交到执行器。
- `await_resume` 不应再次挂起，必须同步返回。
- 三个函数中抛出的异常会沿协程传播，需要保证协程状态一致。

### 7.7 `await_suspend` 的返回类型如何影响控制流？

- 返回 `void` 表示协程挂起，控制权回到调用者或恢复者。
- 返回 `bool` 时，`false` 表示不挂起，立即恢复当前协程。
- 返回 `coroutine_handle<>` 时执行对称转移，恢复该句柄而不增加调用栈。
- 返回 `std::noop_coroutine()` 表示挂起且没有后继。
- 返回句柄必须保证在恢复前存活，否则是悬空句柄。
- 选择合适的返回类型可以减少一次调度器往返。

### 7.8 对称转移如何避免栈溢出？

- 协程 A 恢复协程 B 时，若直接调用 `B.resume()`，调用栈会增长。
- 返回 B 的句柄让编译器以尾调用方式跳转，A 的栈帧不再保留。
- 链式恢复大量协程时，栈深度保持常量。
- 对称转移后 A 不会立即恢复，返回前不能依赖 A 的局部状态继续执行。
- `std::noop_coroutine` 用于终止转移链，回到调度器。
- 恢复链很长时，分段让出可以避免单个调度轮次占用过久。

### 7.9 `co_yield` 与 `co_return` 的语义是什么？

- `co_yield expr` 等价于 `co_await promise.yield_value(expr)`。
- `yield_value` 通常保存值并返回 `suspend_always`，把值交给消费者。
- `co_return expr` 调用 `promise.return_value(expr)`。
- `co_return;` 调用 `promise.return_void()`。
- 同一个 `promise` 类型不能同时提供 `return_value` 与 `return_void`。
- `co_return` 之后协程进入结束路径，执行 `final_suspend`。

### 7.10 协程如何传播异常？

- 协程体内未捕获的异常进入 `promise.unhandled_exception()`。
- 常见实现用 `std::current_exception()` 保存 `std::exception_ptr`。
- 等待者在 `await_resume` 或 `get` 中调用 `std::rethrow_exception`。
- `final_suspend` 恢复等待者时，等待者读取 `promise` 中的异常。
- 等待者应先检查异常状态，再读取返回值，避免访问未构造的对象。
- 帧的销毁路径不应抛出异常。

### 7.11 协程取消如何设计？

- 取消是协作式的，协程需要在挂起点或检查点观察取消信号。
- 使用 `std::stop_token` 与 `std::stop_source` 传递取消请求，二者由 `P0660R10` 引入。
- `stop_callback` 可以注册回调，在取消时唤醒挂起的协程或取消 I/O，回调应短小且不阻塞。
- 取消状态与完成状态需要原子仲裁，保证只有一方决定最终结果。
- 取消后仍需释放缓冲区、注销 `fd`、归还连接。
- 取消不应销毁仍在执行的帧，必须等回调返回或完成事件到达。

### 7.12 取消与完成同时发生如何处理？

- 使用状态机区分等待、完成、取消与已释放，所有转换由原子操作仲裁。
- 完成事件先到则取消请求变为无操作，结果按成功路径返回。
- 取消先到则完成事件到达后只释放资源，不再恢复协程。
- 回调中持有帧句柄时，取消路径不能立即销毁帧，需延迟回收。
- 使用 generation 或序列号识别过期事件，避免旧事件恢复新协程。
- 资源释放放在统一的完成路径，避免两条路径重复释放。

### 7.13 readiness 与 completion 模型有什么区别？

- readiness 模型通知 `fd` 可读或可写，应用仍需执行系统调用并处理 `EAGAIN`。
- completion 模型提交操作，内核完成后再返回结果与状态。
- readiness 模型需要应用维护缓冲区与状态机，completion 模型由内核持有请求。
- completion 模型可以减少系统调用次数，但需要管理提交队列与完成队列。
- readiness 模型在水平触发下容易正确实现，边缘触发需要读到耗尽。
- 两种模型都受内核版本与平台限制，跨平台接口通常只暴露 readiness。

### 7.14 边缘触发下协程如何正确读取？

- 等待到可读后循环调用 `read`，直到返回 `EAGAIN` 或读到 EOF。
- 若只读一次就重新挂起，边缘触发不会再次通知，协程可能永久停住。
- 每次读取后处理缓冲区边界，避免半包与粘包。
- 若读到的数据触发业务处理，先把数据取走再恢复后续协程。
- 使用 `EPOLLONESHOT` 时，每次事件后需要重新注册。
- 水平触发可以简化实现，但可能带来重复唤醒。

### 7.15 协程与回调混合时如何避免悬空引用？

- 回调捕获协程所属对象的 `this` 或帧内对象的引用，帧销毁后回调仍可能触发。
- 使用 `shared_ptr` 管理共享状态，回调持有弱引用或强引用。
- 在帧销毁前注销回调，或让回调检查取消标志与 generation。
- I/O 完成事件可能已进入队列，注销不能保证回调立即停止。
- 延迟回收帧，直到所有在途回调返回。
- 对捕获 `this` 的成员协程，确保对象生命周期覆盖挂起期间。

### 7.16 协程的尾延迟来自哪里？

- 帧分配与释放造成分配器竞争和缓存失效，分配省略可以降低这部分成本。
- 恢复操作跨线程投递，增加队列等待与缓存迁移。
- 定时器精度不足，批量处理导致到期任务集中唤醒。
- 单个事件循环上的长任务阻塞其他协程，形成队头阻塞。
- 续接链过长导致某些协程长时间得不到调度。
- 监控需要分别记录挂起时长、就绪排队时长与执行时长。

### 7.17（场景）协程取消后回调仍触发如何排查？

- 症状是取消后仍出现日志、连接复用或对象已销毁的崩溃。
- 检查取消路径是否只标记状态，却没有注销 `fd` 或取消定时器。
- 检查回调是否持有裸指针，帧是否在回调返回前被释放。
- 使用 generation 计数，旧回调到达时比对当前代次并丢弃。
- 在回调入口检查取消标志，但不要依赖检查代替资源注销。
- 复现时打开事件跟踪，记录提交、完成、取消与释放的时间顺序。

### 7.18（实现）如何用协程封装 `epoll`？

- awaiter 保存 `fd`、事件掩码与当前协程句柄。
- `await_suspend` 把 `fd` 注册到 `epoll`，把句柄存入事件循环的映射。
- 事件循环收到事件后取出句柄并恢复协程。
- `await_resume` 返回就绪事件或错误码，由调用方处理。
- 取消时从 `epoll` 注销 `fd`，并从映射中移除句柄。
- 使用 `EPOLLONESHOT` 或重新注册避免同一 `fd` 的并发等待。

### 7.19（实现）如何实现一个简单的 task 类型？

- `task<T>` 持有 `coroutine_handle<promise_type>`，析构时销毁帧。
- `promise_type` 提供 `get_return_object`、`initial_suspend`、`final_suspend`、`return_value` 与 `unhandled_exception`。
- `initial_suspend` 返回 `suspend_always`，让任务惰性启动。
- `final_suspend` 返回 `suspend_always`，保留帧供等待者读取结果。
- `await_suspend` 保存调用者句柄，恢复被等待的任务。
- 完整实现还需要处理移动语义与 continuation，避免两个 `task` 对象销毁同一帧。

```cpp
template <class T> struct task {
    struct promise_type {
        T value{};
        std::exception_ptr error;
        task get_return_object();
        std::suspend_always initial_suspend() { return {}; }
        std::suspend_always final_suspend() noexcept { return {}; }
        void return_value(T v) { value = std::move(v); }
        void unhandled_exception() { error = std::current_exception(); }
    };
    std::coroutine_handle<promise_type> h;
    ~task() { if (h) h.destroy(); }
};
```

### 7.20（陷阱）协程参数按引用传递有什么风险？

- 协程形参在创建时复制到帧中，引用形参仍然只是引用。
- 调用者传入临时对象或局部对象，协程挂起后对象销毁，恢复时引用悬空。
- `const T&` 形参不延长实参生命周期，与普通函数相同。
- 协程 lambda 按引用捕获，闭包销毁后帧中的引用悬空。
- 需要跨挂起点使用时按值捕获，或使用 `shared_ptr` 管理生命周期。
- 引用参数适合调用者保证生命周期的情况，例如成员协程中的 `this`。

## 8. 执行器与调度

### 8.1 executor 与 scheduler 的职责区别是什么？

- executor 接受一个可调用对象并安排执行，接口通常是 `execute`。
- scheduler 是执行上下文的工厂，返回一个 sender，表示在该上下文完成。
- scheduler 支持组合与完成通知，executor 更接近即发即忘。
- executor 不暴露完成时机，难以表达依赖与错误传播。
- sender 可以携带值、异常与停止信号。
- C++26 的 `std::execution` 使用 scheduler 与 sender/receiver，提案编号为 `P2300R10`。

### 8.2 `execute` 与 `schedule` 的语义差异是什么？

- `execute(f)` 把 `f` 提交到执行上下文，调用返回不代表 `f` 已执行。
- `schedule()` 返回 sender，调用 `connect` 与 `start` 后才提交。
- sender 是惰性的，可以多次连接，每次连接产生独立操作。
- `execute` 通常不提供完成信号，异常处理依赖执行器策略。
- `schedule` 的完成可以继续组合 `then`、`when_all` 等算法。
- 需要结构化并发与取消传播时，优先使用 sender 模型。

### 8.3 sender/receiver 模型解决什么问题？

- 把异步操作表示为可组合的值，而不是回调或 `future`。
- sender 描述做什么，receiver 接收完成信号，`connect` 建立两者关系。
- 完成信号分为值、错误与停止三类，调用方必须处理全部。
- 组合器在编译期确定完成签名，减少运行时分发。
- 取消通过停止令牌沿操作链传播。
- 生命周期由 `connect` 返回的 operation state 管理，避免悬空回调。

### 8.4 任务优先级如何实现而不饿死低优先级？

- 使用多个队列按优先级分层，调度器每次从高优先级队列取任务。
- 低优先级队列采用 aging，等待时间超过阈值后提升优先级。
- 使用 deficit round robin 或加权公平队列，按权重分配执行配额。
- 高优先级任务也要有并发上限，避免占满所有线程。
- 优先级反转时使用优先级继承或临时提升持有锁的任务。
- 监控各优先级队列的等待时间，而不是只看总吞吐。

### 8.5 批处理如何降低调度开销？

- 一次从队列取出多个任务，减少锁、唤醒与上下文切换次数。
- 批量提交 I/O 请求，摊薄系统调用与内核入口成本。
- 批大小需要上限，过大增加单批延迟并恶化公平性。
- 自适应批大小根据队列长度与最近服务时间调整。
- 批处理与优先级结合时，先处理高优先级批次，再处理低优先级。
- 批处理不能掩盖队头阻塞，长任务仍需拆分或隔离。

### 8.6 工作窃取如何影响尾延迟？

- 窃取把忙核心队列中的任务转移到空闲核心，提升吞吐并降低平均等待。
- 窃取本身有延迟，长任务无法拆分时其他核心只能等待其结束，形成尾部拖尾。
- 随机选择受害者与批量窃取可以减少冲突，但增加缓存失效。
- 任务粒度过小导致窃取开销占比高，过大导致负载不均。
- 嵌套并行任务需要限制窃取深度，避免递归创建过多任务。
- 尾延迟敏感的场景应结合任务拆分、优先级与截止时间调度。

### 8.7 容器 CPU 配额如何影响调度器配置？

- cgroup v2 用 `cpu.max` 表示配额与周期，`cpu.weight` 表示相对权重，二者都不是物理核数。
- `nproc` 与 `sysconf(_SC_NPROCESSORS_ONLN)` 都不读取 CPU 配额，前者可能反映亲和性，后者通常反映在线核数。
- 工作线程数按可用配额估算，CPU 密集型任务不应按宿主机核数配置。
- CPU throttling 会在周期边界暂停任务，表现为尾延迟尖峰，需监控 `cpu.stat` 的 `nr_throttled` 与 `throttled_usec`。
- `cpuset` 限制可运行核，NUMA 拓扑可能被隐藏，线程亲和性设置要考虑实际掩码。
- 配额变化时应重新计算线程数与批大小，避免固定配置在扩容后失效。

### 8.8 调度器如何处理阻塞调用？

- 事件循环线程上的阻塞调用会停止所有协程的推进。
- 把阻塞操作提交到独立的阻塞池，完成后把续接投递回事件循环。
- 使用异步 I/O 接口，避免线程在系统调用中睡眠。
- 为阻塞池设置并发上限，防止下游故障耗尽线程。
- 监控事件循环的轮询延迟，超过阈值时告警。
- 协程中误用阻塞调用是常见的尾延迟来源之一。

### 8.9 时间轮与最小堆定时器如何选择？

- 最小堆按到期时间排序，插入与删除为 `O(log n)`，适合稀疏且范围大的定时器。
- 时间轮按固定刻度分桶，插入与删除接近 `O(1)`，适合大量短定时器。
- 时间轮精度受刻度限制，跨轮次需要记录剩余圈数。
- 最小堆的取消通常是惰性删除，堆顶弹出时跳过已取消项。
- 定时器应基于 `steady_clock`，避免系统时钟调整影响间隔。
- 大量定时器同时到期会造成批处理尖峰，需要分散或限流。

### 8.10 `io_uring` 的提交与完成队列如何工作？

- 应用把 `SQE` 写入提交队列，通过 `io_uring_enter` 通知内核。
- 内核处理请求后把 `CQE` 写入完成队列，应用读取结果。
- `SQ` 与 `CQ` 是共享内存环形缓冲区，使用头尾指针协调。
- `user_data` 字段用于关联请求与上层状态，通常存放句柄或指针。
- 提交可以批量进行，减少系统调用次数。
- 队列满时需要等待完成或扩容，不能无限写入。

```cpp
io_uring_sqe* sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, len, offset);
sqe->user_data = reinterpret_cast<uintptr_t>(&op);
io_uring_submit(&ring);
```

### 8.11 `io_uring` 与 `epoll` 的模型差异是什么？

- `epoll` 通知 `fd` 就绪，应用仍需调用 `read` 或 `write`。
- `io_uring` 提交具体操作，完成时直接返回结果与错误码。
- `epoll` 适合事件驱动状态机，`io_uring` 适合完成驱动的协程。
- `io_uring` 可以减少系统调用次数，部分操作支持零复制。
- `epoll` 的边缘触发需要读到 `EAGAIN`，`io_uring` 的一次操作有明确完成。
- 两者可以共存，例如用 `io_uring` 处理文件 I/O，用 `epoll` 处理网络。

### 8.12 `io_uring` 与协程结合的关键设计是什么？

- 每个挂起操作分配一个请求槽，保存协程句柄与缓冲区。
- `await_suspend` 准备 `SQE`，把槽位索引写入 `user_data`。
- 完成队列处理程序根据 `user_data` 找回槽位并恢复协程。
- 缓冲区生命周期必须覆盖内核访问期间，不能在提交后立即释放。
- 取消需要提交取消请求，并等待原请求的 `CQE` 到达。
- 多线程提交时使用每线程环或锁保护，避免 `SQ` 竞争。

### 8.13 `SQPOLL` 模式的代价是什么？

- 内核线程轮询提交队列，应用无需每次调用 `io_uring_enter`。
- 轮询线程持续占用一个 CPU 核心，空闲时也消耗功耗。
- 需要足够的提交速率摊薄轮询成本，低频场景收益有限。
- 内核线程的唤醒与睡眠由 idle 超时控制，配置不当会增加延迟。
- 部分内核版本或安全策略限制 `SQPOLL` 的使用。
- 是否启用由基准测试与部署环境决定，不能默认认为更快。

### 8.14 多核下如何避免调度器的单点竞争？

- 每个核心维护独立运行队列，减少全局队列的原子操作。
- 任务按提交线程或哈希分片，跨分片迁移通过窃取完成。
- 定时器与完成队列也要分片，避免所有核心竞争同一缓存行。
- 共享计数器使用批量更新或每核累加，减少缓存行弹跳。
- 跨核唤醒需要评估缓存迁移成本，必要时绑定生产者与消费者。
- 全局锁只用于低频控制路径，不用于每个任务的入队。

### 8.15 分布式任务调度如何做故障检测？

- 心跳加超时是最简单的模型，超时时间需要权衡误判与检测速度。
- lease 把持有权与时间绑定，持有者必须在到期前续约，过期后其他节点才能接管。
- phi accrual 根据心跳间隔分布计算怀疑度，适应网络抖动。
- 故障检测不能区分慢节点与死节点，需要配合幂等与 fencing。
- 网络分区时可能出现双主，写路径需要 fencing token 或租约。
- 检测结果应触发重试、迁移或摘除，并记录决策依据。

### 8.16 至少一次投递与幂等如何配合？

- 至少一次意味着消息可能重复，消费者必须能识别重复。
- 使用业务唯一键做去重，去重表需要与业务写入在同一事务或原子操作中。
- 幂等键应有有效期，过期后重复消息可能被再次处理。
- 重试要带退避与抖动，避免故障时形成重试放大。
- 副作用操作使用条件写或版本号，防止旧请求覆盖新状态。
- 端到端恰好一次需要事务性消息或幂等消费者，单靠 broker 不能保证。

### 8.17（场景）时钟回拨对定时任务有什么影响？

- `system_clock` 受 NTP 调整与人工修改影响，可能向前或向后跳变。
- 基于墙钟的定时器在回拨后会延迟触发，甚至长时间不触发。
- 间隔计时与超时应使用 `steady_clock`，它单调递增。
- 若租约直接依赖墙钟，回拨可能导致两个节点同时认为租约有效。
- 使用单调时钟加逻辑版本，或由中心服务分配租约。
- 记录时钟跳变事件，便于解释定时任务的异常行为。

### 8.18（场景）尾延迟突增如何判断是排队还是执行？

- 分别记录任务入队时间、开始执行时间与完成时间。
- 排队时间上升而执行时间稳定，说明容量不足或调度延迟。
- 执行时间上升，说明下游变慢、锁竞争或资源饱和。
- 使用直方图而不是平均值，尾部分位数才能反映问题。
- 协调遗漏会低估尾延迟，压测时需要按固定速率发请求。
- 分布式追踪可以定位跨服务的等待段落。

### 8.19（实现）如何实现批量提交的调度循环？

- 从就绪队列一次取出最多 N 个任务，避免长时间占用调度线程。
- 对每个任务执行到下一个挂起点，把续接放入下一轮队列。
- I/O 完成事件批量回收，按 `user_data` 恢复对应协程。
- 每轮检查停止标志与截止时间，保证调度循环可退出。
- 批量大小与轮询超时根据负载调整，兼顾延迟与吞吐。
- 避免在循环中执行无界任务，必要时让出线程。

```cpp
for (;;) {
    auto batch = queue.pop_batch(64);
    for (auto& task : batch) task.resume();
    reap_completions();
    if (stopping) break;
}
```

### 8.20（辨析）协程调度器与操作系统调度器的边界是什么？

- 操作系统调度线程或进程，负责抢占、优先级与 CPU 亲和性。
- 协程调度器调度用户态任务，依赖协作式挂起，不能强制抢占。
- 阻塞系统调用会阻塞整个 OS 线程，协程调度器无法切换出去。
- OS 调度器决定哪个线程运行，协程调度器决定线程上运行哪个协程。
- 用户态调度器可以利用 I/O 事件提高并发，但 CPU 密集型任务仍需 OS 抢占。
- 两层调度需要避免过度订阅，线程数与协程就绪队列长度都要监控。

## 9. 并发数据结构

### 9.1 无锁栈的 push 与 pop 如何用 CAS 实现？

```cpp
struct Node { int value; Node* next; };
std::atomic<Node*> head{nullptr};

void push(int v) {
    Node* n = new Node{v, head.load(std::memory_order_relaxed)};
    while (!head.compare_exchange_weak(n->next, n,
               std::memory_order_release, std::memory_order_relaxed)) {}
}
```

- push 先分配节点，令 `next` 指向当前栈顶，再用 `compare_exchange_weak` 把 `head` 从旧栈顶改为新节点；失败时 `next` 被更新为最新栈顶，循环重试。
- 成功路径使用 release 语义发布节点内容，pop 使用 acquire 读取，保证节点字段在新栈顶可见之前完成写入。
- pop 读取 `head` 与 `head->next`，用 CAS 把 `head` 改为 `next`；CAS 失败说明栈顶已被其他线程改写，需要重读并重试。
- CAS 成功只表示该节点从栈中摘除，其他线程可能仍持有它的地址，回收必须交给 hazard pointer 或 epoch 机制。
- `compare_exchange_weak` 允许伪失败，循环内使用它比 `compare_exchange_strong` 更合适；后者在重试路径上会重复比较。
- 该实现只让栈顶指针原子化，节点内部的字段仍需在发布前写好，发布后不得修改。

### 9.2（陷阱）无锁栈的 ABA 问题如何产生？

- 线程 A 读到栈顶为节点 X 与其后继 Y，准备把 `head` 由 X 改为 Y。
- A 被抢占期间，B 依次弹出 X、弹出 Y，再把 X 压回栈顶，此时 X 的 `next` 已指向新节点。
- A 恢复后 CAS 成功，因为 `head` 的值仍是 X，但写入的 `next` 是过期快照 Y，栈结构被破坏。
- 根因是地址比较无法区分「同一节点未变」与「地址被复用后状态已变」。
- 若每次修改都改变一个与指针一同比较的版本号，CAS 会失败并触发重试。
- 提高内存序无法消除该问题，内存序只约束可见性与顺序，不提供多字段的原子比较。

### 9.3 带标签指针如何缓解 ABA？

- 把 64 位指针与 64 位计数器打包成 16 字节结构，用 `std::atomic` 对该结构整体做 CAS。
- x86-64 上 16 字节比较交换由 `cmpxchg16b` 实现，是否无锁可用 `is_lock_free()` 查询，结果由实现定义。
- 每次修改栈顶递增计数，地址被复用时计数不同，ABA 转化为 CAS 失败与重试。
- 计数回绕后才可能再次误判，64 位计数在常规频率下回绕时间远超系统寿命。
- 打包结构必须 16 字节对齐，否则原子操作可能退化为内部加锁或直接不支持。
- 该方案只保护栈顶，节点回收仍需独立机制；16 字节原子操作的成本也高于 8 字节。

### 9.4 无锁栈的 pop 为什么难以做到无等待？

- pop 在读取栈顶与执行 CAS 之间，栈顶可能被其他线程修改，CAS 失败就要重试，因此不满足无等待。
- 竞争加剧时 CAS 失败率上升，重试消耗的周期随并发度增长，吞吐不能线性扩展。
- 弹出成功后还要回收节点，回收可能等待宽限期或调用分配器，路径上存在不确定延迟。
- 无等待要求每个操作在有限步内完成，通常需要帮助机制，让其他线程代为完成被阻塞的操作。
- 工程库给出的保证多为无锁：系统整体有进展，单个线程可能反复重试。
- 若业务要求延迟上界，应改用预分配节点的有界队列，把分配与回收移出关键路径。

### 9.5 Michael-Scott 队列的入队如何工作？

```cpp
void enqueue(int v) {
    Node* n = new Node{v, nullptr};
    for (;;) {
        Node* t = tail_.load(std::memory_order_acquire);
        Node* next = t->next.load(std::memory_order_acquire);
        if (t != tail_.load(std::memory_order_acquire)) continue;
        if (next) { tail_.compare_exchange_weak(t, next); continue; }
        if (t->next.compare_exchange_weak(next, n)) break;
    }
    tail_.compare_exchange_weak(n, n);
}
```

- 队列使用哑元节点，`head` 指向哑元，`tail` 指向最后一个节点，空队列时二者指向同一哑元。
- 入队读取 `tail` 与 `tail->next`，若 `next` 为空，用 CAS 把 `tail->next` 从空改为新节点，这是唯一的线性化点。
- 链接成功后用 CAS 把 `tail` 前移到新节点，失败不影响正确性，只说明其他线程已经推进。
- 若读到 `tail->next` 非空，说明有线程已链接但未前移 `tail`，当前线程帮助推进后重试。
- 帮助机制使队列在任意线程停顿后仍能推进，避免 `tail` 永久落后。
- 代码对指针读取使用 acquire 语义，CAS 使用默认的顺序一致语义，生产实现可把部分 CAS 放宽为 release。

### 9.6 出队为什么要辅助推进 head？

- 出队读取 `head`、`tail` 与 `head->next`，若 `head == tail` 且 `next` 为空，队列为空。
- 若 `next` 为空而 `head != tail`，说明 `tail` 已经落后，出队帮助把 `tail` 前移后重试。
- 否则用 CAS 把 `head` 从当前哑元改为 `next`，成功者取得 `next` 的值，旧哑元留待回收。
- 旧哑元不能立即删除，其他线程可能仍持有指向它的指针并读取 `next`。
- 节点回收依赖 hazard pointer、epoch 或引用计数，回收策略决定内存上界。
- 入队与出队共享 `tail` 推进逻辑，任一方都可以帮助另一方，减少单点停顿。

### 9.7（辨析）有界队列与无界队列的同步差异是什么？

- 无界链式队列在入队时分配节点，分配器本身成为共享资源，回收又被延迟，内存上界难以控制。
- 有界数组队列预分配存储，入队与出队只修改下标，缓存局部性好，满时需要阻塞、丢弃或返回失败。
- 有界队列用序号区分空与满，避免用元素个数做 CAS 引入 ABA；无界队列用链接 CAS 作为线性化点。
- 阻塞式有界队列用条件变量或信号量实现等待，无锁有界队列在满时只能自旋或返回失败。
- 背压通常由有界队列提供，无界队列把压力转移到内存与排队延迟。
- 选择依据是流量是否可预测、生产者能否阻塞、是否需要严格的内存上限。

### 9.8 环形队列如何用序号避免 ABA？

```cpp
struct Cell {
    std::atomic<size_t> seq;
    int data;
};
```

- 每个槽位带一个序号，生产者要求序号等于当前位置，消费者要求序号等于位置加一。
- 生产者用 CAS 把序号从 `pos` 改为 `pos + 1` 表示数据已写入，消费者用 CAS 把序号改为 `pos + capacity` 表示已读走。
- 序号单调递增，槽位被复用时序号不同，CAS 由此识别出陈旧状态。
- 容量取 2 的幂时用位掩码取模，避免除法，序号与槽位一一对应。
- 生产与消费各自 CAS 自己的槽位，不共享单一计数器，争用范围小。
- 该结构是无锁的，线程在 CAS 前停顿会让其他线程重试，不满足无等待。

### 9.9（实现）如何实现一个 SPSC 环形队列？

```cpp
template <class T, size_t N>
class SpscQueue {
    static_assert((N & (N - 1)) == 0, "N must be power of two");
    alignas(64) std::atomic<size_t> write_{0};
    alignas(64) std::atomic<size_t> read_{0};
    alignas(64) T slots_[N];
public:
    bool push(const T& v) {
        size_t w = write_.load(std::memory_order_relaxed);
        if (w - read_.load(std::memory_order_acquire) == N) return false;
        slots_[w & (N - 1)] = v;
        write_.store(w + 1, std::memory_order_release);
        return true;
    }
};
```

- 单生产者只写 `write_`，单消费者只写 `read_`，各自可以缓存对方下标，减少对共享原子变量的读取。
- 生产者写入槽位后用 release 语义发布 `write_`，消费者用 acquire 读取，保证数据先于下标可见。
- 下标使用无符号整型并允许回绕，`write_ - read_` 在模运算下仍能得到正确的元素个数。
- `write_` 与 `read_` 分处不同缓存行，避免伪共享；缓存行宽度由实现定义，常用值为 64 字节。
- 队列满时 `push` 返回 false，由调用方决定自旋、丢弃还是阻塞。
- 该结构没有 CAS，只有加载与存储，代价是只支持单生产者与单消费者。

### 9.10 伪共享如何影响队列吞吐？

- 两个线程修改同一缓存行内的不同变量时，一致性协议让该行在核心之间来回失效。
- `head` 与 `tail` 相邻存放时，生产者与消费者的每次写入都会使对方的缓存行失效。
- 用 `alignas` 填充或把变量放入独立缓存行可以消除伪共享，代价是内存占用增加。
- `std::hardware_destructive_interference_size` 由实现定义，跨平台传递结构布局时需要谨慎。
- 过度填充浪费缓存与带宽，只应在确认存在争用的热点上使用。
- 伪共享只影响性能，不影响正确性，应先用性能计数器确认再调整布局。

### 9.11 并发哈希表的锁粒度如何选择？

- 全局锁最简单，所有操作串行，只适合低并发或读极多的缓存。
- 分段锁把桶划分为若干段，每段一把锁，段数取 2 的幂，扩容按段迁移。
- 桶级锁粒度最细，锁对象数量与桶数相同，内存与锁管理成本上升。
- 读多写少可以用读写锁或 RCU，读侧不阻塞，写侧复制桶并原子替换头指针。
- 锁粒度与哈希函数质量相关，分布不均时细粒度锁也会退化为热点。
- 选择依据是读写比例、键空间与尾延迟目标，分段锁在通用场景下通常足够。

### 9.12 开放寻址哈希表如何做并发插入？

- 元素存放在桶数组中，冲突时按探测序列寻找空槽，没有链式指针。
- 插入用 CAS 把空槽从「空」改为「写入中」，写入键值后再用 release 语义改为「已占用」。
- 直接标记为已占用会让其他线程看到写了一半的槽位，三态标记消除了这个窗口。
- 删除需要墓碑标记，否则探测链断裂，后续查找可能提前终止。
- 扩容期间旧表只读，新表逐步填充，查找同时检查两张表。
- 探测序列必须在扩容前后保持一致，通常要求容量为 2 的幂并使用相同的探测函数。
- 负载因子必须低于阈值，否则探测长度与 CAS 冲突率同时上升。

### 9.13 哈希表扩容时如何并发访问？

- 停止世界式扩容在全局锁内完成迁移，停顿与元素数成正比。
- 分段迁移维护新旧两张表，读操作先查新表再查旧表，迁移期间两张表都可读。
- 迁移进度用原子下标记录，多个线程用 CAS 领取桶区间，避免重复迁移。
- 每个桶迁移完成后打上标记，读线程遇到标记后转向新表。
- 旧表的内存回收要等所有读线程离开，通常借助 epoch 或引用计数。
- 渐进式扩容把迁移成本摊到每次操作，换取更短的停顿，适合延迟敏感服务。

### 9.14 跳表为什么适合并发有序容器？

- 查找从最高层开始逐层下降，期望复杂度为对数级，实现不依赖树的重平衡。
- 插入只修改局部指针，用 CAS 链接新节点，冲突范围限于相邻节点。
- 删除先标记节点再逐层摘除指针，标记与摘除分步完成，其他线程可以观察到中间状态。
- 层数由随机函数决定，不需要全局旋转或分裂，写操作之间的干扰小。
- 底层链表支持顺序遍历，范围查询与迭代器语义容易实现。
- 代价是节点含多层指针，内存开销高于平衡树，随机层数使最坏情况退化为线性。

### 9.15 RCU 的读侧为什么可以不加锁？

- 读线程在 `rcu_read_lock` 与 `rcu_read_unlock` 之间访问数据，这两个调用只限制重排，不获取锁。
- 写线程不原地修改读线程可见的节点，复制一份后修改副本，再用原子指针替换发布。
- 旧版本在宽限期结束后释放，宽限期保证替换前已经开始的读侧临界区全部结束。
- 读侧没有原子写与缓存行争用，读多写少时扩展性接近线性。
- 读侧临界区中不能睡眠，否则宽限期被延长，旧版本无法回收。
- 读侧的无锁以写侧的复制与延迟回收为代价，写多时成本明显。

### 9.16（辨析）RCU 的宽限期与静止状态是什么？

- 宽限期从新版本发布开始，到所有在发布前已存在的读线程离开临界区为止。
- 静止状态表示线程不持有读侧临界区，例如上下文切换、系统调用返回用户态与空闲循环。
- 内核通过调度器钩子记录每个处理器经过静止状态，据此判断宽限期是否结束。
- 用户态实现常用 epoch 计数，写线程等待所有线程的 epoch 都前进一次。
- `synchronize_rcu` 阻塞等待宽限期结束，`call_rcu` 注册回调在宽限期后异步执行。
- 宽限期长度取决于最慢的读线程，长时间持有读侧临界区会推迟回收并放大内存占用。

### 9.17 Hazard pointer 如何保证安全回收？

```cpp
Node* acquire_head(int tid) {
    for (;;) {
        Node* p = head.load(std::memory_order_acquire);
        hazard[tid].store(p, std::memory_order_seq_cst);
        if (head.load(std::memory_order_seq_cst) == p) return p;
    }
}
```

- 每个线程维护若干 hazard pointer，访问节点前把地址写入槽位并发布。
- 读线程发布 hazard pointer 后重新读取头指针，确认仍指向该节点，避免与替换操作竞态。
- 回收线程扫描所有槽位，待回收节点不在任何槽位中时才释放。
- 扫描成本与线程数和槽位数成正比，通常累积一批待回收节点后批量处理。
- 槽位数量有限，嵌套保护多个节点时可能耗尽，需要重试或改用引用计数。
- hazard pointer 提供有界内存占用，代价是每次访问多一次发布与一次确认读取。

### 9.18 Epoch 回收与引用计数回收如何取舍？

- 引用计数在每次访问时增减计数，读侧存在原子写与缓存行争用，回收及时。
- epoch 回收把释放推迟到所有线程经过一次静止状态，读侧只有轻量检查，适合读多写少。
- 引用计数可以支持跨线程长期持有，epoch 要求对象只在受保护的临界区内访问。
- 引用计数存在循环引用问题，epoch 只关心线程进度，不涉及对象关系。
- epoch 的回收延迟由最慢线程决定，内存占用随临界区长度上升。
- 常见组合是用 epoch 保护节点访问，用引用计数保护外部持有的句柄。

### 9.19（场景）无锁队列在什么情况下不如互斥锁？

- 竞争极低时，互斥量的无竞争路径只有一次原子操作，与一次 CAS 相当，代码更简单。
- 临界区包含多个操作或需要复合原子性时，无锁结构难以表达。
- 需要阻塞与背压时，条件变量配合互斥量更省处理器，无锁队列只能自旋或返回失败。
- 元素较大或生命周期复杂时，安全回收的成本可能超过锁的开销。
- 无锁代码的错误在压力测试下才暴露，调试与维护成本长期存在。
- 判断依据是实测的争用与尾延迟，只有锁成为瓶颈且临界区足够短时才考虑无锁。

### 9.20（场景）读多写少的配置表应选择哪种并发结构？

- 写时复制加原子指针：读线程只做一次 acquire 加载，写线程复制整表后替换，适合表小、更新少的场景。
- RCU：读侧没有原子写，写线程复制并延迟回收，适合读极多、更新可以延迟的场景。
- 分段锁哈希表：读侧加锁，实现简单，适合读写比例不极端的场景。
- `std::atomic<std::shared_ptr<const Table>>`：读线程复制指针，写线程构造新表，C++20 起提供该偏特化，代价是原子引用计数。
- 选择依据是读频率、表大小、更新延迟容忍度与内存预算，读侧开销与回收机制是主要区分点。

## 10. 死锁、活锁与饥饿

### 10.1 死锁的四个必要条件在代码中如何体现？

- 互斥：`std::mutex` 保护的资源同一时刻只允许一个线程持有，对应不可共享的资源。
- 持有并等待：线程持有 A 的同时请求 B，过程中不释放 A，例如嵌套调用两个各自加锁的函数。
- 不可剥夺：互斥量不能被其他线程强制夺取，只能由持有者解锁，等待者无法收回资源。
- 循环等待：线程 1 等待线程 2 持有的锁，线程 2 等待线程 1 持有的锁，等待关系成环。
- 四个条件同时成立才可能死锁，破坏其中任一条件即可预防，工程上最容易落实的是破坏循环等待。
- 这些是必要条件：不满足一定不死锁，满足也不必然死锁，是否发生取决于调度时序。

### 10.2（辨析）自旋锁与互斥锁的死锁表现有何不同？

- 自旋锁等待时持续占用处理器，死锁表现为核心满载而没有进展，性能计数器显示大量周期消耗在原子指令。
- 互斥锁竞争时进入内核睡眠，死锁表现为线程全部阻塞、处理器空闲，线程状态为可中断睡眠。
- 自旋锁通常关闭抢占，持有者被调度出核心时，等待者会自旋到时间片结束，形成长时间停顿。
- 互斥锁的等待队列由内核管理，调试器可以看到等待对象；自旋锁的等待状态只在寄存器与内存中。
- 单核上自旋等待一个被换出的持有者永远不会成功，因此自旋锁要求临界区不睡眠且极短。
- 两者的根因都是等待关系成环，区别在于观测信号与恢复手段。

### 10.3 std::lock 与 std::scoped_lock 如何避免死锁？

```cpp
std::mutex a, b;
void transfer() {
    std::scoped_lock lock(a, b);   // locks both, order independent
}
```

- 标准要求多锁接口使用避免死锁的算法，常见实现是 try-and-back-off：依次尝试加锁，失败时释放已持有的锁再重试。
- 释放已持有的锁破坏了持有并等待，线程不会在持有一把锁时无限等待另一把。
- C++17 的 `std::scoped_lock` 接受多个互斥量，构造时执行该算法，析构时按相反顺序解锁。
- 该算法不需要额外的顺序约定，代价是重试期间可能反复加锁与解锁。
- 若某个线程先用 `std::lock_guard` 单独锁 A，再调用 `std::scoped_lock(a, b)`，仍可能与其他线程成环。
- 该算法不保证公平，竞争激烈时重试次数上升，临界区应尽量短。

### 10.4 锁顺序约定如何落实到工程中？

- 为每类锁分配全局层级编号，规定只能按编号递增的顺序加锁，禁止反向获取。
- 把层级写入类型名或注释，并在锁封装中断言当前线程已持有的最高层级小于新锁层级。
- 代码评审重点检查跨模块调用：A 模块持锁调用 B 模块，B 模块又回调 A 模块并加锁。
- 用静态分析检查锁获取路径，运行时用死锁检测器记录等待图。
- 回调与观察者模式最容易破坏顺序，约定持锁期间不调用外部代码。
- 动态创建的锁无法预先编号，需要由统一管理器分配层级并登记。

### 10.5（场景）线上服务无响应如何判定是死锁？

- 观察信号：工作线程全部阻塞，吞吐归零，处理器空闲，连接数持续堆积。
- 用 `gdb -p` 附加后执行 `thread apply all bt`，查看线程栈中 `pthread_mutex_lock` 或 `futex` 的等待位置。
- Linux 上可以用 `pstack` 或 `eu-stack` 获取全部线程栈，比较各线程持有的锁与被等待的锁。
- 死锁的栈呈环状：线程 A 在 B 持有的锁上等待，线程 B 在 A 持有的锁上等待，两处地址互相指向。
- 需要与长时间持锁区分：单线程持锁执行慢操作也会让其他线程堆积，但持锁线程仍在运行。
- 复现困难时开启锁顺序日志，把加锁路径写入环形缓冲区，事后还原等待关系。

### 10.6（实现）等待图检测算法如何实现？

```cpp
bool reaches(const std::map<int, std::vector<int>>& wait,
             int from, int target, std::set<int>& seen) {
    if (from == target) return true;
    if (!seen.insert(from).second) return false;
    auto it = wait.find(from);
    if (it == wait.end()) return false;
    for (int next : it->second)
        if (reaches(wait, next, target, seen)) return true;
    return false;
}
```

- 节点是线程或事务，边从等待者指向持有者，线程进入等待前加边，获得锁或超时后删边。
- 新边加入时从等待者出发搜索能否回到自身，等价于判断新增边是否形成环。
- `seen` 集合防止重复展开，复杂度与边数线性相关。
- 递归深度受等待链长度限制，生产实现通常改为显式栈以避免栈溢出。
- 发现环后选择一个牺牲者，让其放弃获取并释放已持有的资源。
- 等待图只反映显式等待关系，自旋与条件变量等待需要额外登记才能纳入。

### 10.7（场景）线程池中的嵌套任务等待为何会死锁？

- 任务 A 在线程池线程中提交任务 B 并同步等待结果；若线程池已无空闲线程，B 永远无法开始。
- 这是资源耗尽型死锁：等待的是执行线程而非锁，等待图算法无法发现。
- 常见触发条件是把线程池大小固定，并在任务中递归提交子任务。
- C++ 的 `std::async` 返回的 future 在析构时可能阻塞，把 future 存放在池内任务中同样会耗尽线程。
- 解决办法包括禁止池内任务同步等待、使用工作窃取让等待线程帮忙执行、为阻塞任务设置独立线程池。
- 超时只能缓解症状，根因是等待关系与执行资源耦合。

### 10.8 超时加锁能否消除死锁？

- 超时让等待者在限定时间内放弃，破坏不可剥夺条件，把死锁转化为可恢复的失败。
- `std::timed_mutex` 提供 `try_lock_for` 与 `try_lock_until`，返回 false 表示超时。
- 超时只保证线程不会永久阻塞，不保证系统有进展：所有线程同时超时并重试，可能长期无法推进。
- 超时值难以设定：过短导致正常业务频繁失败，过长使故障恢复时间不可接受。
- 超时后的状态可能不一致，调用方需要回滚已完成的修改，错误处理路径随之增加。
- 超时适合作为兜底，配合固定锁顺序与死锁检测使用。

### 10.9（陷阱）超时重试为什么会引入活锁？

- 两个线程各持一把锁并请求对方的锁，同时超时释放并重试，可能再次同时获取并再次冲突。
- 重试没有随机化时，线程节奏趋于同步，冲突概率不随时间下降。
- 系统整体在运行，但没有线程完成有效工作，处理器利用率高而吞吐为零，符合活锁特征。
- 退避与随机抖动可以打破同步，使线程在不同时刻进入临界区。
- 重试次数需要上限，否则故障被掩盖，调用方看到延迟上升，得不到明确错误。
- 活锁难以通过线程栈发现，需要观察操作成功率与重试计数。

### 10.10（辨析）死锁、活锁与饥饿的边界是什么？

- 死锁：所有相关线程永久阻塞，资源不释放，系统没有进展。
- 活锁：线程持续执行并改变状态，但没有完成目标的操作，资源反复获取与释放。
- 饥饿：某个线程长期得不到资源，其他线程持续进展，系统整体仍有吞吐。
- 三者都表现为等待过久，区分依据是线程状态与系统整体进展。
- 死锁可以由等待图判定；活锁只能通过操作成功率与重试行为识别；饥饿需要按线程统计等待时间。
- 同一种现象在不同粒度上可能归入不同类别，例如全局活锁在单个线程看来像饥饿。

### 10.11 指数退避与随机化如何打断活锁？

- 冲突后等待时间随失败次数指数增长，使两个线程的下一次尝试在时间上错开。
- 单纯的指数增长不足以保证错开，需要加入随机抖动，让同时失败的线程选择不同等待值。
- 抖动区间取冲突窗口的量级，区间过小无法错开，过大使恢复变慢。
- 退避期间不应持有任何锁，否则其他线程仍被阻塞，退避失去意义。
- 重试次数上限与放弃条件必须明确，避免活锁转化为长时间的无效重试。
- 多个线程共享同一资源时，可以用票据或排队序号替代随机退避，得到确定的顺序。

### 10.12 自旋等待在什么条件下退化为饥饿？

- 自旋线程持续占用处理器，若等待的条件由低优先级线程提供，条件可能永远不成立。
- 单核系统上自旋等待另一个线程释放锁，持有者无法被调度，等待者自旋到时间片耗尽。
- 自旋次数不设上限时，竞争激烈的锁让线程长期做无用功，进度由少数线程完成。
- 解决办法是自旋若干次后调用 `std::this_thread::yield` 或进入阻塞等待。
- 优先级不同的线程共享核心时，自旋会加剧优先级反转。
- 自旋适合临界区短于两次上下文切换成本的场景，超过该阈值应让出处理器。

### 10.13 优先级反转如何发生？

- 低优先级线程 L 持有互斥量，高优先级线程 H 请求同一互斥量而阻塞。
- 中优先级线程 M 就绪后抢占 L，L 无法继续执行，也就无法释放锁。
- H 的有效优先级被 M 压低，表现为高优先级任务被中优先级任务延迟，延迟时间不可预测。
- 该问题在实时系统中后果严重，1997 年火星探路者号的任务重启与优先级反转有关，地面通过启用优先级继承修复。
- 只要存在共享锁与优先级差异就可能出现，与锁的具体实现无关。

### 10.14 优先级继承与优先级天花板如何选择？

- 优先级继承：高优先级线程阻塞在低优先级线程持有的锁上时，临时把持有者提升到等待者的优先级，释放后恢复。
- 优先级天花板：为每把锁设定天花板优先级，持有者一旦加锁就提升到该优先级，无论是否有等待者。
- 继承按需提升，开销出现在阻塞路径；天花板在加锁时提升，开销固定且可预测。
- 天花板协议在任务遵守约定时可以防止死锁，继承只解决反转。
- 继承需要跟踪等待链，链式阻塞时可能多次提升，实现复杂度更高。
- POSIX 提供 `PTHREAD_PRIO_INHERIT` 与 `PTHREAD_PRIO_PROTECT` 属性，Linux 通过 PI futex 实现继承。

### 10.15 读写锁的写线程饥饿如何避免？

- 读优先实现中，新读线程可以在写线程等待时继续获取读锁，写线程长期得不到机会。
- 写优先实现中，一旦有写线程等待，新读线程排队，读吞吐下降。
- 公平实现按到达顺序排队，避免任一方向饥饿，代价是额外的唤醒与上下文切换。
- `std::shared_mutex` 的公平性由实现定义，标准不保证写优先或读优先。
- 读多写少且写延迟敏感时，可以用写时复制替代读写锁，写线程不阻塞读线程。
- 长时间持有读锁会推迟写线程，应把读锁范围限制在复制或计算所需的最小范围。

### 10.16 公平锁的代价是什么？

- 公平锁按等待顺序授予，等待线程不会被后到的线程插队，因此不会饥饿。
- 非公平锁允许新到达的线程直接竞争，减少唤醒开销，可能让等待者长期排队。
- 公平性通常通过等待队列实现，队首线程被唤醒后仍要重新竞争，除非实现保证直接交接。
- 高竞争下公平锁的吞吐通常低于非公平锁，差距随竞争程度扩大，具体幅度由实现与负载决定。
- 公平性有利于尾延迟，不利于吞吐，选择取决于服务等级目标。
- `std::mutex` 不提供公平性开关，需要公平语义时应使用带队列的锁实现。

### 10.17（场景）条件变量的唤醒顺序为何会导致饥饿？

- `notify_one` 唤醒哪个等待者由实现定义，标准不保证先进先出。
- 多个等待者竞争同一条件时，某些线程可能连续被跳过，表现为长时间得不到执行。
- 若唤醒后条件被其他线程抢先满足，被唤醒的线程重新等待，可能反复空转。
- Linux 的 futex 等待队列按先进先出组织，但唤醒与实际获取锁的顺序仍可能不同。
- `notify_all` 可以避免单个线程被长期跳过，代价是惊群与无效唤醒。
- 需要严格顺序时应显式维护队列，用序号或票据决定谁可以继续。

### 10.18 递归锁与锁层级如何诱发死锁？

- `std::recursive_mutex` 允许同一线程多次加锁，掩盖了持锁调用另一个需要同一把锁的函数的问题。
- 递归锁只在同线程重入时有效，两个线程交叉请求两把锁仍会死锁。
- 递归锁使持有时间难以确定，解锁次数必须与加锁次数严格匹配。
- 递归锁无法与 `std::lock` 的算法配合，混用会破坏加锁协议。
- 递归锁通常比普通互斥量慢，并掩盖了需要重构的调用链。
- 若确实需要重入，应把内部实现拆成要求已持锁的私有函数，由外层统一加锁。

### 10.19（实现）如何实现带超时的加锁封装？

```cpp
std::unique_lock<std::timed_mutex> acquire(std::timed_mutex& m,
        std::chrono::milliseconds timeout) {
    std::unique_lock<std::timed_mutex> lk(m, std::defer_lock);
    if (!lk.try_lock_for(timeout))
        throw std::runtime_error("lock timeout");
    return lk;
}
```

- 用 `std::unique_lock` 配合 `std::defer_lock`，把加锁与所有权管理分开，异常路径也能自动解锁。
- `try_lock_for` 使用相对时间，`try_lock_until` 使用绝对时间；多次等待时应使用绝对时间避免累积误差。
- 超时后必须明确语义：抛出异常、返回错误码或降级执行，调用方需要处理部分完成的状态。
- 超时时间应包含在请求的截止时间内，避免外层超时已到而内层仍在等待。
- 同一封装可以被协程的等待器复用，取消时返回未获得锁并唤醒等待者。
- 超时日志需要记录锁地址、持有者与等待时长，便于事后定位环。
- 该封装只提供可恢复性，不提供无死锁保证。

### 10.20（场景）如何建立死锁预防与检测的工程流程？

- 设计阶段规定锁层级、禁止持锁调用外部代码、禁止在池内任务中同步等待。
- 编码阶段用 RAII 封装锁，提供 `std::scoped_lock` 与超时接口，禁止裸调用 `lock` 与 `unlock`。
- 测试阶段在压力测试中注入随机延迟与随机调度，提高交叉加锁的暴露概率。
- 运行阶段开启锁等待超时日志与死锁检测线程，采集线程栈与等待图。
- 复盘阶段把每次死锁还原为加锁顺序图，补充到层级约定与静态检查规则。
- 工具方面：ThreadSanitizer 发现数据竞争但不检测死锁，Helgrind 可以报告锁顺序违规。

## 11. 线程安全设计

### 11.1 线程安全通常划分为哪些层级？

- 不可变：对象构造完成后状态不再变化，任意线程并发读取都安全，不需要同步。
- 线程安全：多线程并发调用成员函数不会破坏内部状态，调用方不需要额外同步。
- 条件安全：不同线程操作不同对象安全，操作同一对象需要调用方提供同步。
- 非线程安全：即使操作不同对象也可能因共享的静态状态而出错。
- 层级描述的是接口对调用方的承诺，文档必须写明属于哪一层、哪些函数可以并发调用。
- C++ 标准库的序列容器属于条件安全：不同元素的并发修改有保证（`vector<bool>` 除外），同一容器结构的并发修改需要同步。

### 11.2 不可变对象为什么天然线程安全？

- 所有字段在构造完成后不再修改，不存在两个线程同时读写同一内存位置的情况。
- 对象在发布前完成构造，其他线程通过正确的同步读取即可看到完整状态。
- 不可变对象可以自由共享，读取路径不需要锁，也不需要引用计数以外的生命周期管理。
- 代价是每次修改都要创建新对象，分配与复制成本随对象大小增长。
- 结构共享可以降低复制成本，持久化数据结构复用未修改的子树。
- 不可变对象适合配置、消息、事件与函数式的数据流。

### 11.3（实现）如何用 const 与值语义表达不可变性？

```cpp
class Config {
public:
    Config with_timeout(int ms) const {
        Config next = *this;
        next.timeout_ms_ = ms;
        return next;
    }
    int timeout_ms() const { return timeout_ms_; }
private:
    int timeout_ms_ = 1000;
};
```

- 数据成员私有且不提供修改接口，构造后不再变化，成员函数声明为 `const`。
- 修改操作返回新对象，不修改自身，调用方持有旧版本，旧版本对其他人仍然有效。
- 按值传递与返回，配合移动语义与返回值优化，复制开销可控。
- `const` 只阻止通过该接口修改，不阻止 `mutable` 成员与 `const_cast`，需要代码评审配合。
- 提供 `with_xxx` 形式的转换函数，保持原对象不变。
- 不可变类型应删除赋值运算符，避免意外破坏不变式。

### 11.4 线程封闭有哪些形式？

- 栈封闭：对象只在一个线程的栈上创建与使用，其他线程无法获得引用。
- 对象封闭：对象由一个线程独占，通过消息传递把所有权转移给其他线程，不在线程间共享。
- `thread_local` 封闭：每个线程持有独立实例，适合缓存、随机数发生器与错误码。
- 任务封闭：对象绑定到特定执行器或事件循环，所有访问都在该循环的线程上串行执行。
- 封闭的关键是所有权边界清晰，任何逃逸的引用都会破坏假设。
- 封闭比加锁简单，但难以在编译期检查，依赖约定与代码评审。

### 11.5 thread_local 的开销与陷阱有哪些？

- 访问 `thread_local` 变量需要经过线程控制块，动态初始化的变量还有一次初始化检查。
- 首次访问触发初始化，初始化抛出异常时变量保持未初始化状态，再次访问会重试。
- 线程退出时按构造的逆序析构，若析构函数访问其他 `thread_local` 对象，顺序依赖可能导致访问已销毁对象。
- 动态库卸载时 `thread_local` 的析构与 TLS 模型相关，跨模块使用需要谨慎。
- `thread_local` 增加线程创建成本，线程数很多时内存占用显著。
- 它是线程封闭的实现手段，不提供线程间可见性，不能用于传递状态。

### 11.6 所有权转移如何避免共享？

- 用 `std::unique_ptr` 表示独占所有权，移动后源对象为空，编译器阻止复制。
- 把对象放入队列时移动所有权，消费者取得唯一引用，生产者不再访问。
- 转移过程中队列本身是共享结构，元素的所有权在入队与出队之间转移。
- 转移后原线程持有的悬空引用是主要风险，接口应返回值或智能指针，避免返回引用。
- 独占所有权使销毁时机确定，避免引用计数的原子开销。
- 需要共享只读数据时，用不可变对象加 `std::shared_ptr<const T>`，区分共享读与独占写。

### 11.7 unique_ptr 与 shared_ptr 的所有权语义差异是什么？

- `unique_ptr` 独占所有权，可移动不可复制，析构在持有者线程执行，没有原子操作。
- `shared_ptr` 共享所有权，控制块中的引用计数是原子的，复制与销毁都涉及原子增减。
- `shared_ptr` 的引用计数线程安全，被管理对象本身的访问仍需要同步。
- 同一个 `shared_ptr` 实例的并发读写不是线程安全的，多个线程修改同一实例需要加锁或使用原子版本。
- `weak_ptr` 不增加强引用计数，用于打破循环引用与观察者场景。
- 选择依据是所有权是否唯一，能用 `unique_ptr` 时优先使用。

### 11.8（陷阱）shared_ptr 的引用计数为什么不能保证对象访问安全？

- 引用计数只保护控制块，保证对象在最后一个持有者释放前不被销毁。
- 两个线程通过同一个 `shared_ptr` 访问对象成员时，成员读写没有任何同步。
- `shared_ptr` 实例的赋值同时修改指针与控制块两个字段，多线程同时赋值会产生数据竞争。
- C++20 提供 `std::atomic<std::shared_ptr<T>>` 偏特化，对实例的操作是原子的，对象内容仍需同步。
- 常见错误是把 `shared_ptr` 当作线程安全的共享容器，忽略对象内部状态。
- 正确做法是让对象不可变，或在对象内部提供同步。

### 11.9（实现）锁的封装应暴露什么接口？

```cpp
template <class F>
auto with_lock(F&& f) {
    std::lock_guard<std::mutex> lk(m_);
    return f(data_);
}
```

- 只暴露在锁保护下执行函数的接口，不暴露锁本身，也不返回内部数据的引用。
- 回调在锁内执行，接口文档必须写明这一点，禁止回调中再次获取同一把锁或调用外部代码。
- 提供 `try_with_lock` 与带超时的版本，避免调用方无限等待。
- 条件变量等待需要与锁配合，封装应提供 `wait(pred)` 形式，避免调用方手动检查条件。
- 锁的粒度与顺序在封装内部固定，调用方无法破坏。
- 返回值按值返回，必要时用 `std::optional` 表示未获得锁。

### 11.10 为什么不应返回受锁保护对象的引用？

- 返回引用后锁在函数返回时释放，调用方持有引用期间对象可能被其他线程修改。
- 引用的生命周期无法与锁的持有期绑定，编译器也不会检查。
- 返回指针、引用或迭代器都有同类问题，迭代器还会因容器修改而失效。
- 需要返回数据时应返回值或不可变快照，复制成本由调用方承担。
- 数据很大时可以返回 `std::shared_ptr<const T>`，指向不再修改的版本。
- 接口设计上应把读取并复制与修改分开，避免调用方在锁外操作内部状态。

### 11.11（实现）如何实现线程安全的队列接口？

```cpp
void push(T v) {
    { std::lock_guard<std::mutex> lk(m_); items_.push(std::move(v)); }
    cv_.notify_one();
}
bool pop(T& out) {
    std::unique_lock<std::mutex> lk(m_);
    cv_.wait(lk, [this] { return closed_ || !items_.empty(); });
    if (items_.empty()) return false;
    out = std::move(items_.front());
    items_.pop();
    return true;
}
```

- `push` 在锁内修改容器，解锁后调用 `notify_one`，减少被唤醒线程立即阻塞在锁上的概率。
- `pop` 使用带谓词的 `wait`，循环检查条件，天然处理虚假唤醒与丢失唤醒。
- 关闭标志与容器状态在同一把锁下修改，关闭之后 `pop` 返回 false，消费者不会永久等待。
- `notify_one` 只唤醒一个消费者，一次入队多个元素时应逐个通知或使用 `notify_all`。
- 队列无界时内存不受控，有界版本需要在 `push` 中等待未满条件。
- 接口只暴露值语义的 `push` 与 `pop`，不暴露内部容器与迭代器。

### 11.12 快照式接口的取舍是什么？

- 读操作在锁内复制必要数据后立即释放锁，后续处理在锁外进行。
- 优点是锁持有时间与业务处理时间解耦，尾延迟可控，死锁风险低。
- 代价是复制开销与内存占用，数据量大时复制本身成为瓶颈。
- 快照可能过期，读到的是一致性时刻的状态，业务需要接受这种弱一致。
- 用不可变对象加原子指针替换可以避免复制，写线程构造新版本，读线程取指针。
- 快照适合读多写少、单次读取数据量适中的场景。

### 11.13 在锁内执行回调有哪些风险？

- 回调可能再次获取同一把锁，非递归锁下直接死锁。
- 回调可能获取另一把锁，若其他路径的加锁顺序相反，形成环。
- 回调可能阻塞或执行耗时操作，锁被长期占用，其他线程排队。
- 回调可能抛出异常，锁由 RAII 释放，但对象状态可能处于中间态。
- 回调可能销毁持有锁的对象，解锁时访问已释放内存。
- 约定是持锁期间只操作内部数据，把回调移到锁外执行，必要时在锁内复制参数。

### 11.14（场景）读多写少的配置对象如何设计？

- 写时复制：写线程构造新配置对象，用原子指针替换，读线程只做一次 acquire 加载。
- 写侧需要串行化，多个写线程同时替换会丢失更新，通常用一把写锁或单写者线程。
- 读线程拿到的指针在替换后仍然有效，旧对象由引用计数或宽限期保护。
- 更新需要原子地替换多个字段时，把整组字段放进一个不可变对象。
- 配置更新应校验后再发布，避免读线程看到半成品。

### 11.15 条件变量封装如何避免误用？

- 等待必须与谓词一起使用，封装提供 `wait(lk, pred)`，避免调用方只做单次 `if` 判断。
- 通知应在修改共享状态之后、释放锁之后进行，避免被唤醒线程立即阻塞。
- 谓词读取的状态必须由同一把锁保护，否则存在数据竞争。
- 关闭与错误状态应纳入谓词，等待者能退出，不会永久阻塞。
- 超时等待使用 `wait_for` 或 `wait_until`，返回后仍需检查谓词。
- 封装不应在析构时通知等待者，析构与等待并发本身就是生命周期错误。

### 11.16（辨析）线程安全与可重入有什么区别？

- 可重入指函数在执行过程中被再次调用仍能正确工作，通常不依赖静态或全局的可变状态。
- 线程安全指多线程并发调用不会破坏状态，可以通过加锁实现，加锁的函数通常不可重入。
- 可重入函数不应调用不可重入函数，也不应使用共享缓冲区或无条件加锁。
- 信号处理函数要求异步信号安全，条件比可重入更严格，只能调用白名单中的函数。
- 只使用参数与栈变量的可重入函数天然线程安全；把状态交给调用方保存的实现需要调用方保证状态不共享。
- 设计接口时应先确定目标：并发安全、可重入还是异步信号安全，三者的约束不同。

### 11.17 单例的线程安全初始化如何实现？

- C++11 起函数内静态变量的初始化是线程安全的，并发进入时只有一个线程执行初始化，其他线程等待。
- 该保证由 `[stmt.dcl]/4` 规定，编译器通常用守卫变量与原子操作实现。
- 局部静态对象在程序退出时析构，析构顺序与构造顺序相反，跨翻译单元的依赖仍可能出问题。
- 需要显式控制生命周期时，可以用 `std::call_once` 与 `std::once_flag`。
- 双检查锁定需要原子变量与正确的内存序，用普通指针配合锁的实现存在数据竞争。
- 单例引入全局状态，测试与并发设计应优先考虑依赖注入。

### 11.18（场景）如何为不支持线程安全的第三方库加外壳？

- 用一把全局互斥量串行化所有调用，实现简单，吞吐受限于库的内部并发能力。
- 按对象分锁：为每个句柄维护一把锁，调用前加锁，减少不同对象之间的争用。
- 线程封闭：每个线程持有独立句柄，库的内部状态不共享，适合句柄创建成本低的场景。
- 用任务队列把调用投递到专用线程，调用方异步等待结果，库只在单线程中运行。
- 外壳需要处理库的全局初始化与清理，这些操作通常只能执行一次。
- 封装应记录库的错误码与线程约束，避免调用方绕过外壳直接使用。

### 11.19 线程安全设计文档应包含哪些内容？

- 每个类的线程安全层级，以及哪些成员函数可以并发调用。
- 锁的层级与获取顺序，哪些函数内部加锁，哪些要求调用方已经持锁。
- 回调的执行上下文：在锁内还是锁外，在哪个线程执行，是否允许阻塞。
- 对象的生命周期与所有权，跨线程传递时的销毁责任。
- 已知的阻塞点与超时语义，以及关闭流程中的行为。
- 测试策略：压力测试、竞争检测工具与死锁注入方式。

### 11.20（场景）如何评审一个类的线程安全性？

- 列出所有共享可变状态，确认每处访问都在同一把锁或同一原子协议下。
- 检查是否存在先检查后使用的复合操作，锁是否覆盖整个复合操作。
- 检查锁的获取顺序是否与全局层级一致，是否存在持锁调用外部代码。
- 检查发布过程：对象构造完成后是否通过 release 语义或锁发布给其他线程。
- 检查回调、异常与析构路径，确认锁在任何路径上都能释放。
- 用 ThreadSanitizer 跑并发测试，用随机延迟放大竞争窗口。
- 评审结论应落到接口文档与代码约束，不能只存在于评审记录中。

## 12. 分布式基础

### 12.1 CAP 的准确表述是什么？

- 一致性指线性一致性：所有节点看到同一份数据，读操作返回最近一次写的结果。
- 可用性指每个非故障节点在有限时间内对每个请求返回非错误响应。
- 分区容忍指网络分区发生时系统仍能继续运行。
- 三者不能同时全部满足，分区在真实网络中不可避免，取舍实际发生在一致性与可用性之间。
- 定理讨论的是分区期间的行为，分区恢复后的补偿与修复不在其范围内。
- 常见误读是把 CAP 当作静态的三选二属性，准确理解是分区期间的二选一。

### 12.2（辨析）CP 与 AP 在分区时的行为差异是什么？

- CP 系统在分区时拒绝少数派节点的写请求或读请求，保证返回的数据是最新的。
- AP 系统在分区时继续接受读写，允许不同分区返回不同版本，分区恢复后合并。
- CP 的代价是可用性下降，客户端看到超时或错误；AP 的代价是一致性下降，客户端可能读到旧值。
- 多数派 quorum 是常见的 CP 实现手段，少数派凑不齐法定人数，只能拒绝服务。
- AP 实现通常配合冲突解决策略，例如最后写入胜出、版本向量或应用层合并。
- 选择取决于业务：支付与库存偏向 CP，社交动态与购物车偏向 AP。

### 12.3 线性一致性、顺序一致性与因果一致性如何区分？

- 线性一致性要求每个操作在其开始与结束之间的某个时刻原子生效，且与实时顺序一致。
- 顺序一致性要求所有节点看到相同的操作总序，但不要求该顺序与真实时间一致。
- 因果一致性只要求有因果关系的操作按因果顺序可见，并发操作可以不同顺序。
- 线性一致性最强，实现代价最高，通常依赖共识或单点协调。
- 顺序一致性弱于线性一致性，允许读到尚未在实时上完成的值。
- 因果一致性弱于顺序一致性，适合跨地域复制，延迟低但需要跟踪因果依赖。

### 12.4 最终一致性与读己之写如何保证？

- 最终一致性只保证停止写入后副本最终收敛，不保证读取时看到最新值。
- 读己之写是会话级保证：同一客户端后续读请求至少能看到自己之前的写结果。
- 实现方式包括把读请求路由到写过的副本、记录版本号并等待副本追平、使用粘性会话。
- 版本号方案在读请求中携带最后写入的版本，副本未追平时等待或转发到主副本。
- 粘性会话实现简单，客户端切换节点或节点故障时保证失效。
- 该保证只覆盖单个客户端的写，不覆盖其他客户端的读。

### 12.5（场景）会话一致性与粘性会话如何取舍？

- 粘性会话把同一客户端的请求固定到同一副本，实现简单，负载均衡能力下降。
- 会话一致性在协议层携带版本或令牌，允许请求落到任意副本，实现复杂但更均衡。
- 粘性会话在副本故障或扩容时失效，需要迁移或重建会话状态。
- 会话令牌可以编码为逻辑时钟或版本向量，副本据此判断是否需要等待。
- 移动网络下客户端地址变化频繁，基于地址的粘性策略不可靠。
- 选择依据是副本数量、故障频率与实现成本。

### 12.6 幂等键如何设计？

- 客户端为每个逻辑操作生成唯一键，重试时复用同一个键。
- 键应包含业务标识与操作序号，避免每次重试生成新键。
- 服务端用键做去重，记录处理状态与结果，重复请求返回首次结果。
- 键需要全局唯一，常用 UUID 或客户端标识加单调序号。
- 去重记录的保留时间应覆盖最大重试窗口，过短会导致重复执行。
- 键不能包含易变字段，例如时间戳或随机数，否则重试失效。

### 12.7（实现）如何用去重表实现幂等？

```cpp
auto [ok, row] = store.insert_if_absent(key, hash(req));
if (!ok) return wait_or_replay(row);
try {
    auto result = handle(req);        // business logic
    store.complete(key, result);      // same transaction
    return result;
} catch (...) {
    store.abort(key);
    throw;
}
```

- 表结构包含幂等键、请求摘要、处理状态、结果与创建时间，键上建唯一索引。
- 先插入占位记录，插入冲突说明请求已存在，读取状态决定返回结果还是等待首个请求完成。
- 处理成功后在同一事务中更新状态与结果，保证去重记录与业务数据一致。
- 处理失败时删除记录或标记失败，允许客户端用同一键重试。
- 并发重复请求由唯一索引与行锁串行化，后到者在锁上等待。
- 去重表需要定期清理，按创建时间分区或设置存活时间。

### 12.8 哪些错误可以重试？

- 网络层错误：连接超时、连接重置、临时不可达，通常可以重试。
- 服务端过载：`429` 与 `503` 响应，尤其带 `Retry-After` 时，应退避后重试。
- 幂等性前提：非幂等操作重试前必须有幂等键，否则可能重复执行。
- 参数错误、认证失败、权限不足属于永久错误，重试没有意义。
- 超时是模糊状态：请求可能已被处理，只有幂等操作才能安全重试。
- 重试策略应区分立即重试与退避重试，并设置总预算。

### 12.9（陷阱）重试风暴如何形成？

- 下游故障导致大量请求超时，客户端立即重试，请求量成倍增加。
- 重试放大系数等于重试次数加一，多层调用链上按层数相乘。
- 服务端过载时响应变慢，超时比例上升，触发更多重试，形成正反馈。
- 同步重试在同一线程内进行，占用连接与线程，进一步降低服务能力。
- 缺少全局重试预算时，单个慢节点可以使整条调用链过载。
- 解决办法包括重试预算、限流、退避抖动与服务端主动拒绝。

### 12.10 重试预算与退避参数如何配合？

```cpp
std::chrono::milliseconds backoff(int attempt) {
    long long cap = std::min<long long>(10000, 100LL << attempt);
    std::uniform_int_distribution<long long> d(0, cap);
    return std::chrono::milliseconds(d(rng));
}
```

- 退避参数（基础间隔、上限、抖动比例）决定单次重试的节奏，重试预算决定整体的重试量。
- 重试预算通常表示为重试请求占总请求的比例，例如 10%，超出预算的请求直接失败。
- 预算按下游依赖维护，单个依赖故障不会耗尽全局预算。
- 服务端返回的建议等待时间优先于本地计算，客户端在其基础上加抖动。
- 退避与预算都受截止时间约束，超过请求剩余预算立即停止。
- 参数应可配置并有上限，避免极端值延长恢复时间。

### 12.11 超时应该如何分层设置？

```cpp
struct Deadline {
    std::chrono::steady_clock::time_point at;
    bool expired() const { return std::chrono::steady_clock::now() >= at; }
};

void call(const Deadline& d, Client& client) {
    if (d.expired()) return;      // deadline already passed
    auto left = d.at - std::chrono::steady_clock::now();
    client.invoke(request, left); // propagate remaining time
}
```

- 客户端超时应大于服务端处理时间的分位数，小于上游给本服务的截止时间。
- 每层超时逐层递减，预留网络与序列化开销，避免下层超时晚于上层。
- 调用链中传递绝对截止时间，避免每跳重新计算相对超时。
- 超时值基于延迟分布设定，例如取高分位数的若干倍，并随负载调整。
- 连接超时与读写超时分开设置，连接超时通常更短。
- 超时后需要取消下游请求，否则下游继续占用资源。

### 12.12（场景）超时与重试叠加如何放大尾延迟？

- 单次超时为 T、重试 N 次时，最坏延迟接近 `(N + 1) * T`，远超上游的截止时间。
- 上游已经超时放弃，下游仍在重试，资源被无效请求占用。
- 异步框架中取消要沿等待链传播，取消不及时会让已放弃的请求继续执行到结束。
- 重试请求与正常请求竞争同一资源池，排队时间上升，尾延迟进一步升高。
- 解决方法是把截止时间沿调用链传递，下游在截止时间到达后立即停止。
- 重试预算与并发限制配合，避免单个请求占用过多资源。
- 监控应区分首次请求与重试请求的延迟分布，否则平均值掩盖问题。

### 12.13 背压有哪些实现方式？

- 阻塞式：队列满时生产者阻塞，简单有效，但可能阻塞上游线程。
- 拒绝式：队列满时立即返回错误，保护自身，要求调用方处理失败。
- 丢弃式：丢弃最旧或最新的请求，适合允许丢失的指标与日志。
- 速率限制：用令牌桶或漏桶限制入口速率，平滑突发流量。
- 信用机制：下游发放信用额度，上游按额度发送，适合长连接与流式传输。
- 拉模式：由消费者主动拉取，按处理能力消费，避免推送过载。

### 12.14 队列长度与丢弃策略如何选择？

- 队列长度决定可吸收的突发量，过长会增加排队延迟与内存占用。
- 排队延迟近似为队列长度除以处理速率，尾延迟随长度线性增长。
- 丢弃队首会破坏顺序，丢弃队尾保留旧数据，选择取决于业务语义。
- 优先级队列可以为关键请求保留容量，但需要防止低优先级请求饥饿。
- 队列长度应结合处理速率与超时设置，使排队时间不超过请求预算。
- 持续增长的队列深度说明下游容量不足，应触发扩容或限流。

### 12.15（场景）如何避免级联故障？

- 为每个下游依赖设置独立的连接池与并发上限，防止单个依赖耗尽全部资源。
- 熔断：连续失败达到阈值后快速失败，给下游恢复时间。
- 资源隔离：按业务或租户划分资源池，限制故障影响范围。
- 超时与重试预算：避免请求在故障依赖上无限堆积。
- 降级：下游不可用时返回缓存或默认值，保证核心链路可用。
- 通过压测与故障演练验证上述策略在真实流量下的效果。

### 12.16 两阶段提交与 Saga 的取舍是什么？

- 两阶段提交由协调者先询问所有参与者，再统一提交，保证原子性，但同步阻塞。
- 协调者故障会导致参与者长时间锁定资源，恢复依赖日志与超时。
- Saga 把长事务拆成多个本地事务，每步提供补偿操作，失败时逆序补偿。
- Saga 没有隔离性，中间状态对外可见，需要业务容忍或加语义锁。
- 两阶段提交适合短事务与强一致场景，Saga 适合跨服务长流程。
- 两者都需要幂等与重试，补偿操作本身也必须幂等。

### 12.17 跨数据中心部署时 Quorum 如何取舍？

- 跨地域往返延迟远高于同机房，等待 W 个远端确认会把写延迟推高到数百毫秒。
- 常见做法是把副本按地域分组，写只在本地数据中心凑齐 Quorum，再异步复制到远端。
- 异步复制会引入复制延迟窗口，故障切换时可能丢失最近写入，需要业务接受。
- 读请求可以优先本地副本，读不到最新值时再回源或等待复制追赶。
- 同城双活与异地多活的取舍取决于 RPO 与 RTO，Quorum 参数只是手段。
- 跨地域时钟不同步，版本号或混合逻辑时钟比时间戳更可靠。

### 12.18（场景）时钟漂移如何影响分布式顺序？

- 物理时钟存在漂移，网络时间同步误差在毫秒级，跨机房可达数十毫秒。
- 用本地时间戳做最后写入胜出会丢失更新，时钟快的节点总是获胜。
- Lamport 时钟给出偏序，不能判断两个事件的实时先后。
- 混合逻辑时钟把物理时间与逻辑计数结合，接近实时顺序且保持因果。
- 需要强顺序时使用共识分配的单调序号，避免依赖物理时钟。
- 时间戳只应在同一节点内比较，跨节点比较需要附加节点标识与逻辑计数。

### 12.19 分布式追踪如何帮助定位超时？

- 每个请求分配全局 trace 标识，跨服务传递，各段记录 span 的开始与结束时间。
- 通过 span 的耗时分布可以区分服务自身处理慢、下游慢还是网络慢。
- 时钟漂移会使跨节点的时间线错位，追踪系统需要做时钟偏移校正。
- 采样率过高带来开销，过低会漏掉长尾请求，通常对慢请求全采样。
- 追踪数据与指标、日志关联，可以在同一 trace 中看到重试与错误码。
- 追踪只记录已发生的调用，未发起的重试与排队时间需要通过指标补充。

### 12.20（场景）如何为一个跨机房服务设计故障模型？

- 列出故障类型：机器宕机、网络分区、丢包、延迟抖动、时钟漂移、依赖超时。
- 为每类故障定义检测信号与恢复动作，例如心跳超时触发主备切换。
- 明确一致性目标与可用性目标，决定分区时选择 CP 还是 AP。
- 设计降级路径与数据修复流程，分区恢复后需要对账与补偿。
- 用混沌工程注入故障，验证超时、重试、熔断与切换的实际效果。
- 记录演练结果，更新容量规划与告警阈值。

## 13. Raft 与共识

### 13.1 为什么 Raft 把共识拆成领导者选举、日志复制和安全性三部分？

- 分解降低理解与实现难度。选举只决定谁在某个任期收集投票，复制只把客户端命令追加到多数派日志，安全性约束两者交界处的提交规则。
- 选举保证每个任期至多一个领导者。日志复制保证领导者把条目传播到跟随者，安全性保证已提交条目在领导者更替后仍然存在。
- 三部分共享任期、`commitIndex` 与 `lastApplied` 等状态，但职责边界清晰，测试可以分别注入网络分区、日志落后与重启故障。
- 拆分不改变共识问题的下界。一次客户端请求仍需多数派持久化后才能确认，跨地域部署的延迟由往返时延决定。
- 实现中常把状态机应用独立成线程，复制线程只推进 `commitIndex`，避免用户状态机阻塞网络循环。
- 代价是模块之间存在时序耦合。选举完成前不能提交新日志，快照安装期间需要暂停对应跟随者的复制。

### 13.2（辨析）Raft 的任期和投票规则如何避免同一任期出现两个领导者？

- 每个节点维护单调递增的 `currentTerm`，任期号只增不减。收到更大任期立即转为跟随者并清空投票记录。
- 候选人在竞选前把 `currentTerm` 加一，先给自己投票，再向其他节点发送 `RequestVote`。
- 跟随者在同一任期内最多投一票，投票持久化到稳定存储后才回复，重启后不能重复投票。
- 候选人获得多数派投票才成为领导者。任意两个多数派至少有一个交集节点，该节点在同一任期只能投一票。
- 投票还要求候选人的日志至少与投票者一样新。比较时先看最后一条日志的任期，任期相同再比较索引。
- 持久化 `currentTerm` 与 `votedFor` 是正确性条件，只在内存中保存会在崩溃重启后破坏选举安全。

### 13.3 选举超时为什么通常要随机化？

- 固定超时会让多个跟随者在领导者失效后同时转为候选人，选票被分散，可能出现连续多轮无人获得多数派。
- 随机化把候选人的超时错开，通常在一个或少数几个选举周期内产生领导者，降低冲突概率。
- 随机区间要大于一次心跳往返时间，避免网络抖动把正常领导者误判为失效。
- 区间过宽会拉长故障恢复时间，过窄会提高冲突概率。取值需要结合心跳间隔与部署环境的尾延迟。
- 节点重启后也应对超时做随机化，否则批量重启可能同步进入竞选。
- 随机化只降低冲突，不消除分裂投票。预投票和退避重试可以进一步减少无谓的任期增长。

### 13.4（辨析）预投票与领导者租约分别解决什么问题？

- 预投票在正式增加任期前先询问其他节点是否愿意支持，减少被隔离节点反复抬高任期、恢复后打断现任领导者的现象。
- 预投票请求不改变 `currentTerm`，只有获得多数派支持才进入正式选举，避免无效任期扩散。
- 领导者租约让领导者在租约期内相信自身仍被多数派认可，从而直接服务读请求，省去每读一次的 ReadIndex 往返。
- 租约依赖时钟假设。各节点时钟漂移必须小于租约余量，否则旧领导者可能在租约未到期时已失去多数派。
- 预投票增加一轮往返，故障恢复略慢。租约读降低延迟，但时钟跳变或长时间暂停会破坏安全性。
- 两者都不替代日志复制。租约只影响读路径，写请求仍要经过多数派持久化。

### 13.5 日志匹配性质如何保证已提交条目不会被覆盖？

- Raft 要求同任期、同索引的日志条目命令相同，且领导者不会改写自己的日志，只会追加。
- `AppendEntries` 携带前一条日志的索引与任期，跟随者只有在本地匹配时才接受新条目，不匹配就拒绝并让领导者回退。
- 领导者通过递减 `nextIndex` 找到最后一个共同前缀，再覆盖跟随者其后的冲突条目。冲突条目从未提交。
- 已提交条目意味着多数派已持久化。新领导者必须包含这些条目才能获得多数派投票，因为投票规则比较日志新旧。
- 新领导者用自身日志中的条目覆盖跟随者冲突条目。提交判断只认当前任期条目，旧任期条目随当前任期条目间接提交。
- 实现必须保证日志截断与追加的原子性。落盘顺序通常为先写新条目、再更新元数据，崩溃恢复时校验日志连续性。

### 13.6（实现）`commitIndex` 与 `lastApplied` 有什么区别？

- `commitIndex` 表示已知被多数派持久化的最高日志索引，是复制层的提交点。`lastApplied` 表示已经交给状态机的最高索引。
- 两者可以分离。提交后日志仍需按序应用到状态机，应用速度慢时 `lastApplied` 落后于 `commitIndex`。
- 状态机应用必须单线程按索引递增执行，不能并发应用同一分区内的日志，否则命令顺序改变。
- 应用线程不应持有复制状态锁调用用户代码。用户状态机回调若反向读取集群状态，可能造成锁顺序反转和死锁。
- 快照点通常取 `lastApplied`。快照必须包含该索引之前的所有状态，安装快照后跳过已覆盖的日志。
- 确认客户端前只需等待 `commitIndex` 推进。是否已应用由读一致性策略决定，线性一致读通常要求读到已应用状态。

```cpp
void apply_loop(Raft& raft, StateMachine& sm) {
    while (raft.running()) {
        auto batch = raft.take_committed();
        for (const auto& entry : batch) {
            sm.apply(entry);                 // 不持有 Raft 状态锁
            raft.set_last_applied(entry.index);
        }
    }
}
```

### 13.7 领导者如何维护 `nextIndex` 与 `matchIndex`？

- 每个跟随者有一对状态。`nextIndex` 是下一次要发送的日志位置，`matchIndex` 是已确认复制的最高位置。
- 初始时 `nextIndex` 设为领导者最后索引加一，`matchIndex` 设为 0。失败后按冲突任期快速回退，避免每次只减一。
- 成功追加后更新 `matchIndex`，并按多数派的 `matchIndex` 排序推进 `commitIndex`，只提交当前任期的条目。
- 快速回退需要跟随者在拒绝响应中携带冲突条目的任期和该任期首个索引，减少日志差距大时的往返次数。
- 领导者要限制未完成追加的并发度，避免对同一跟随者乱序发送导致旧响应覆盖新状态。
- 心跳与日志追加共用 `AppendEntries`。空心跳也会携带前一条日志信息，用于探测匹配位置和维持权威。

### 13.8 为什么 Raft 只允许通过当前任期的条目间接提交旧任期日志？

- 假设领导者直接提交旧任期条目，可能出现新领导者尚未包含该条目却已当选的情形，破坏已提交条目的持久性。
- Raft 的规则是领导者只有在当前任期有条目被多数派复制后，才把 `commitIndex` 推进到该条目，并连带提交之前的条目。
- 这条规则把提交判断绑定到当前领导者的权威，避免依赖前任领导者的局部观察。
- 实现中不能因为旧任期条目出现在多数派日志中就单独标记提交，必须等待当前任期条目形成新的多数派。
- 该规则会增加一次日志复制的等待，但换取了领导者更替时的安全性。
- 测试应覆盖旧任期条目分散在多数派、领导者刚当选就崩溃等边界场景。

### 13.9 网络分区下旧领导者还能服务线性一致读吗？

- 不能无条件服务。旧领导者可能已失去多数派，读到的状态可能落后于新领导者已提交的写入。
- 安全做法是 ReadIndex。领导者先向多数派确认自己仍是领导者，再等待本地状态机应用到该读请求对应的提交索引。
- 更严格的做法是把读请求也写入日志，按日志顺序应用，代价是增加一次磁盘写和复制往返。
- 领导者租约可以在租约期内直接读，但依赖时钟漂移上界和租约续期成功。
- 跟随者读需要向领导者获取 ReadIndex 或租约信息，不能仅凭本地日志位置判断线性一致。
- 分区恢复后旧领导者必须退位，客户端应能识别领导者变更并重试到新领导者。

### 13.10 ReadIndex 与 Lease Read 的代价和失效边界是什么？

- ReadIndex 需要一次多数派心跳往返，读延迟至少增加一个 RTT，但不依赖时钟同步。
- Lease Read 把确认结果缓存为租约，读延迟接近本地内存访问，但租约长度必须覆盖时钟漂移与调度暂停。
- 租约期内发生全局暂停、虚拟机迁移或时钟回拨，旧领导者可能误以为自己仍有效。
- ReadIndex 还要等待 `lastApplied` 达到读请求对应的 `commitIndex`，否则会读到旧状态。
- 高并发读可以批量合并 ReadIndex 请求，用一次心跳服务多个读，降低控制面开销。
- 跨地域部署时，把读请求发到最近副本仍需回到领导者确认，无法同时获得低延迟与强一致。

### 13.11 快照安装与日志压缩如何避免阻塞前台写入？

- 快照由状态机在某个 `lastApplied` 点生成。生成期间可以继续应用后续日志，但快照内容必须对应一致的时间点。
- 常见做法是写时复制或分代存储，先冻结快照边界，再把后续写入放到新段，避免长时间停写。
- 安装快照时先传元数据与校验和，再分块传输数据，最后原子替换本地状态并更新 `lastApplied`。
- 安装期间该跟随者的日志复制可以暂停，但领导者不应因此停止对其他多数派节点的复制。
- 快照传输要限速并支持断点续传，否则大快照会挤占心跳带宽，触发新的选举。
- 快照完成前不能删除本地旧日志和旧快照，崩溃恢复需要回退到最后一个完整快照。

### 13.12 成员变更为什么不能一次替换多数派？

- 一次性替换可能让新旧配置的多数派没有交集，两个配置同时选出领导者，出现双主。
- 联合共识先进入 `C_old` 与 `C_new` 的共同配置，任何决策都需要同时在两个配置中获得多数派。
- 共同配置提交后再切换到 `C_new`。切换期间仍要求两个多数派，保证任意时刻只有一个有效决策路径。
- 联合共识的代价是可用性下降。需要更多节点在线，跨配置的写延迟增加。
- 实现要把配置作为日志条目复制，不能只修改本地配置文件，否则节点间对成员集的理解不一致。
- 变更期间要处理新增节点的日志追赶，避免新配置已生效但新节点长期落后。

### 13.13 单节点成员变更与联合共识如何取舍？

- 单节点变更一次只增加或删除一个节点，利用新旧多数派必然相交的性质保持安全，流程比联合共识简单。
- 单节点变更在节点数较少时可能连续多次操作，期间可用性仍然受多数派约束。
- 联合共识适合一次替换多个节点或跨机房迁移，但需要额外状态和更复杂的恢复逻辑。
- 删除领导者自身时，单节点变更要求领导者先完成配置提交再退位，否则可能留下无人推进的配置。
- 新增节点必须先追上日志再参与投票，否则会增加选举失败概率并拖慢提交。
- 无论哪种方案，都要限制未完成变更的数量，避免配置版本链过长导致恢复困难。

### 13.14（辨析）PreVote 能解决哪些故障，不能解决哪些？

- 能减少被网络分区隔离的节点在恢复后以更高任期打断现任领导者的情况。
- 能减少节点反复重启、磁盘暂停或长时间垃圾回收后引发的无效选举。
- 不能解决真正的多数派丢失。多数节点不可达时，集群仍然无法提交写请求。
- 不能替代持久化投票与日志。如果 `currentTerm`、`votedFor` 或日志未落盘，崩溃恢复仍可能破坏安全性。
- 不能消除选举竞争，只能降低无谓的任期增长。极端同时超时仍可能分裂投票。
- 预投票本身也要防止被旧消息欺骗，响应需要携带任期与配置版本。

### 13.15 客户端如何识别领导者变更并安全重试？

- 客户端不应缓存领导者地址作为永久事实。收到 `NotLeader` 或超时后应重新查询集群元数据。
- 写请求要携带请求标识，服务端在状态机中记录最近处理的请求标识与结果，重复请求返回同一结果。
- 仅靠 RPC 层重试不能保证幂等。领导者可能在提交后、回复前崩溃，客户端无法区分未执行与已执行。
- 去重表需要设置合理的保留窗口。窗口过短会在客户端长时间重试时失效，窗口过长会占用内存。
- 读请求可以重试到新领导者，但必须重新执行 ReadIndex 或租约校验，不能沿用旧领导者的读结果。
- 客户端应设置总 deadline，并让每次重试共用剩余时间，否则故障期间请求会无限延长。

### 13.16 日志复制流水线与批量提交如何影响尾延迟？

- 流水线允许领导者连续发送多个 `AppendEntries`，不必等待每个响应，提高带宽时延积较大链路的吞吐。
- 但同一跟随者的日志必须按序落盘，后续请求可能在磁盘队列中排队，尾延迟由最慢的一次 `fsync` 决定。
- 批量提交把多个客户端请求合并为一次磁盘同步。吞吐上升，单个请求的等待时间可能增加。
- 领导者应限制每个跟随者的在途请求数量，避免内存膨胀和超时误判。
- 将各节点的 `matchIndex` 排序，取多数派对应的分位值作为可提交上界。落后节点不应阻塞整体提交，但会影响故障切换后的恢复时间。
- 监控要区分复制延迟、磁盘同步延迟与排队延迟。单看平均 RTT 会掩盖尾部的磁盘抖动。

### 13.17（实现）磁盘 `fsync`、批处理与组提交怎样影响 Raft 的吞吐？

- 每条日志都单独 `fsync` 会把吞吐限制在磁盘每秒同步次数，延迟由设备写缓存与介质决定。
- 组提交把多个并发追加合并为一次同步。多个请求共享一次持久化代价，吞吐随批量增大而上升。
- 批量过大会增加排队时间，尾延迟上升。批量过小则无法摊薄同步开销。
- 日志写入应顺序追加，避免随机写。预分配与分段文件可以减少元数据更新。
- 任期与投票必须在回复投票前落盘，日志条目必须在回复追加成功前落盘。`commitIndex` 是易失状态，重启后通过领导者复制与提交过程重新建立。
- 使用 `fdatasync` 还是 `fsync`、是否绕过页缓存，由文件系统与存储设备决定，需要按部署环境验证。

### 13.18（辨析）Raft、Paxos 与 Zab 的核心差异是什么？

- Raft 强调强领导者、日志连续和易于理解的选举规则。Paxos 更接近一组一致性原语，允许更灵活的实现结构。
- Multi-Paxos 可以并发提案，但日志可能出现空洞，恢复时需要填补。Raft 通过领导者串行追加避免空洞。
- Zab 与 Raft 都使用领导者与任期或纪元，Zab 的提交规则和恢复阶段与 Raft 不同，常用于 ZooKeeper。
- Raft 的成员变更、快照和客户端会话在协议层有明确设计，Paxos 把这些留给上层系统。
- 三者都依赖多数派持久化，写入延迟下界都是一个以上网络往返加一次稳定存储。
- 选择时看实现生态与运维工具，单看协议名称不能判断延迟或吞吐。

### 13.19 什么场景不适合使用 Raft？

- 单机或单副本场景不需要共识，引入 Raft 只会增加日志与选举开销。
- 跨洲部署且要求个位数毫秒写延迟时，多数派往返无法满足，需改用本地写入加异步复制并接受一致性下降。
- 极高写入吞吐且允许丢数据的场景，可以用无共识的日志聚合或消息队列。
- 需要多主并发写的场景，Raft 的单领导者模型会成为瓶颈，需考虑分片或 CRDT 等方案。
- 运维能力不足时，三节点集群的磁盘、时钟和网络故障会放大恢复难度。
- Raft 适合元数据、配置、协调状态和需要线性一致的少量关键写入，不适合大对象数据面传输。

### 13.20（场景）三节点 Raft 集群频繁选举，如何定位与修复？

- 先看选举次数与任期增长曲线，区分周期性超时、单节点反复重启和网络抖动三类模式。
- 检查心跳间隔、选举超时与快照传输是否争用同一网卡，确认心跳没有被大流量阻塞。
- 检查磁盘 `fsync` 尾延迟与日志增长，落盘慢会让跟随者错过心跳并被误判为失效。
- 检查节点时钟与调度暂停，虚拟机的 CPU 抢占或长时间垃圾回收会造成心跳丢失。
- 检查成员配置是否包含已下线节点，联合共识未完成或配置版本不一致会导致多数派计算错误。
- 修复后保留选举原因指标与日志，避免只调大超时掩盖磁盘或网络问题。

## 14. RPC 与服务治理

### 14.1 RPC 框架的关键路径由哪些层组成？

- 接口层负责 IDL 生成、方法分发与错误码映射，序列化层把请求与响应编码为字节流。
- 传输层管理连接、帧边界、多路复用与背压，执行器层把回调或协程恢复到合适的线程。
- 治理层处理服务发现、负载均衡、超时、重试、熔断、限流与链路追踪。
- 关键路径上的每次内存复制、锁竞争与线程切换都会放大尾延迟。零复制与批量写只应作为有边界的优化。
- 同步 RPC 与异步 RPC 的线程模型不同。同步调用容易占满工作线程，异步回调要防止在 I/O 线程执行阻塞逻辑。
- 错误模型要区分可重试错误、不可重试错误与结果未知。结果未知只能依赖幂等键或查询接口。

### 14.2（辨析）序列化协议如何选型？

- 文本协议可读性好，调试成本低，但体积大、解析慢。二进制协议体积小、解析快，排障需要专门工具。
- IDL 驱动的协议能生成强类型代码并管理兼容性。直接按内存布局读写的结构体则受对齐、字节序和版本影响。
- 选型要看跨语言支持、结构定义演进、零复制能力与生态工具，不能只看单次编解码的微基准测试。
- 大对象适合分块或引用传递，避免在 RPC 层整体序列化。小对象要控制字段数量与嵌套深度。
- 压缩会降低带宽但增加 CPU 与尾延迟，是否压缩应按消息大小分布决定。
- 序列化库的安全边界很重要。解析不可信输入要限制长度、嵌套层数与递归深度。

### 14.3（陷阱）Protobuf 字段编号与兼容性有哪些陷阱？

- 字段编号一旦发布就不能复用。删除字段应保留编号并标记 `reserved`，否则旧数据会被错误解释。
- 修改字段类型可能破坏线格式兼容性。定长与变长编码互换、`int32` 与 `sint32` 的负数编码都不同。
- 新增字段要有默认值语义。旧客户端读到新字段会忽略，不能依赖字段存在性表达业务状态。
- `required` 在 proto3 中已移除，缺失字段与默认值无法区分，需要显式 `optional` 或包装类型。
- 枚举新增值对旧客户端是未知值，代码生成器可能把它放在未知字段集合，业务逻辑要有兜底。
- 结构定义仓库要保存历史版本并做兼容性检查，禁止直接修改已发布字段的含义。

### 14.4 为什么长度前缀与帧边界是 RPC 编解码的基础？

- TCP 是字节流，没有消息边界。一次读取可能得到半个消息、一个消息或多个消息。
- 长度前缀让接收方先读固定头部，再按长度读取负载，避免依赖分隔符转义。长度字段要约定字节序。
- 头部要限制最大帧长，否则恶意长度会触发超大内存分配。
- 变长长度字段要检查溢出与截断。解析失败必须关闭连接，不能继续按错误边界读取。
- 多路复用协议还需要请求 ID，把响应帧映射回等待中的调用。
- 批量与零复制优化不能改变帧语义，发送方要保证头部与负载的可见顺序。

```cpp
bool read_frame(Connection& conn, Frame& out) {
    std::uint32_t len = 0;
    if (!conn.read_exact(&len, sizeof(len))) return false;
    len = ntohl(len);
    if (len == 0 || len > kMaxFrame) return false;
    out.payload.resize(len);
    return conn.read_exact(out.payload.data(), len);
}
```

### 14.5 连接池应该按什么维度划分？

- 按目标地址、协议、TLS 配置与租户隔离划分，避免不同安全域或优先级共享连接。
- 长连接适合高频小请求，减少握手与慢启动。短连接适合低频或需要独立隔离的调用。
- 多路复用连接可以减少连接数，但单连接上的队头阻塞会影响所有请求，需要应用层流控。
- 池大小要结合并发请求数、单请求持有时间与下游承载能力，不能只按 CPU 核数设置。
- 连接要有最大生命周期与空闲回收，避免 DNS 变更或负载均衡后长期复用旧地址。
- 获取连接必须带超时，等待队列要有上限，否则下游变慢会耗尽调用方线程与内存。

### 14.6（场景）连接池耗尽的故障如何定位与隔离？

- 观察活跃连接数、等待队列长度、获取连接耗时与连接创建失败率，区分泄漏、慢请求与下游拒绝。
- 连接泄漏常由异常路径未归还引起，RAII 包装与作用域守卫可以保证归还。
- 慢请求占满连接时，仅扩大池会加重下游压力，应配合超时、舱壁与并发上限。
- 连接建立失败要快速失败并进入退避，避免大量线程同时重连造成惊群。
- 为关键业务保留独立池或预留连接，防止低优先级流量挤占。
- 线程池与连接池可能形成嵌套等待。工作线程持有连接等待另一个任务，而该任务又在等待工作线程，需限制跨池调用并加超时。

### 14.7 超时与协程取消为什么要分层设计？

- 至少区分连接超时、单次读写超时、整体调用超时与排队超时。整体超时是客户端愿意等待的上界。
- 重试必须共享同一个总 deadline，每次重试从剩余时间里分配，不能重置计时。
- 服务端超时应略小于调用方超时，留出响应编码与网络回传时间，避免调用方先放弃而服务端继续执行。
- 长尾请求需要单独预算，固定超时会把正常慢请求与故障请求混在一起。
- C++20 协程没有内建取消语义，需要由 `stop_token`、awaiter 或框架状态机实现协作式取消。取消要传播到下游并释放连接。
- 取消与完成之间存在竞态，结果可能已经提交但取消信号尚未处理。状态机要允许取消失败，并保证资源只释放一次。

### 14.8 重试放大与集中重试如何避免？

- 只重试幂等或可安全重复的请求，并对错误类型分类。参数错误、认证失败不应重试。
- 使用指数退避加随机抖动，限制最大重试次数与总时间，避免所有客户端同步重试。
- 服务端要用重试预算或令牌控制整体重试量，客户端重试不能绕过服务端过载保护。
- 下游已经过载时，重试会把局部失败放大为级联故障。熔断与限流应优先于重试。
- 重试要区分连接失败、请求未送达与响应丢失，后两者可能已在服务端执行。
- 记录重试次数与最终结果，按调用链聚合。单看客户端成功率会掩盖放大效应。

### 14.9（实现）至少一次投递下，RPC 重试如何保证安全？

- 客户端为每个逻辑操作生成稳定幂等键，重试复用同一个键，不能每次生成新键。
- 服务端在事务内把幂等键与业务结果一起写入，重复请求返回已保存的结果。
- 幂等键要有作用域与过期时间，避免不同用户或不同操作冲突。
- 对不可幂等的操作，先查询执行状态再决定是否重试，或改成可补偿的流程。
- 结果未知时不能简单返回失败，否则上层可能再次提交，造成重复副作用。
- 去重存储的可用性会影响主流程，需明确降级策略与一致性要求。

### 14.10 熔断器的状态机与半开探测如何设计？

- 典型状态为关闭、打开与半开。关闭状态统计失败率，超过阈值后进入打开。
- 打开状态直接拒绝请求并快速失败，经过冷却时间后只允许少量探测请求进入半开。
- 半开探测成功达到阈值后回到关闭，任一探测失败则重新打开并延长冷却时间。
- 统计窗口要能反映近期状态，滑动窗口比固定窗口更能适应突发流量。
- 熔断粒度可以是接口、实例或租户。粒度过粗会误伤健康流量，过细会增加状态开销。
- 熔断只保护调用方，不替代服务端限流。打开期间要有降级结果与告警。

### 14.11 熔断、重试、超时与舱壁如何组合？

- 超时限制单次等待，重试在超时之外增加尝试次数，熔断在连续失败后停止尝试，舱壁限制并发占用。
- 组合顺序通常是先舱壁隔离资源，再限流，再超时，最后按策略重试。熔断跨越多次调用生效。
- 重试次数乘以超时不能超过总 deadline，否则请求会在后台继续占用资源。
- 舱壁按业务或下游划分线程池、连接池与队列，防止一个依赖耗尽全部调用资源。
- 熔断打开后重试应被短路，避免无效流量冲击下游。
- 这些机制都会改变可观测性，指标要标注是否经过重试、是否被熔断，否则延迟归因失真。

### 14.12（辨析）令牌桶、漏桶与滑动窗口限流有何差异？

- 令牌桶按固定速率补充令牌，允许短时突发，桶容量决定突发上限。
- 漏桶以固定速率处理请求，输出平滑，超出容量的请求排队或拒绝，适合保护下游。
- 固定窗口实现简单，但窗口边界可能出现两倍突刺。滑动窗口记录更细粒度，内存与计算开销更高。
- 滑动日志精度最高，适合低 QPS 场景。高 QPS 常用滑动窗口计数或令牌桶近似。
- 分布式限流还要考虑时钟偏差、网络往返与状态同步，单机算法不能直接外推。
- 限流应返回明确的重试时间或降级结果，避免客户端立即重试加剧拥塞。

### 14.13 分布式限流如何兼顾精度与可用性？

- 集中式计数器精度高，但每次请求都要访问中心存储，延迟与单点风险明显。
- 本地预取令牌可以降低中心压力，代价是各节点额度使用不均，需要租约与回收机制。
- 固定配额把总量按节点数切分，扩缩容时要重新分配，可能出现空闲额度与热点节点。
- 滑动窗口同步可以用版本号与批量上报减少往返，但要处理并发更新与丢失。
- 限流存储不可用时，应明确放行还是拒绝。关键业务通常选择本地保底限流，完全放开只适用于可容忍超载的场景。
- 监控要区分拒绝率、误拒率与额度利用率，单看总 QPS 无法判断限流是否合理。

### 14.14 服务发现应该选客户端发现还是服务端代理？

- 客户端发现由调用方获取实例列表并自行负载均衡，少一次代理跳转，但每个语言栈都要实现治理逻辑。
- 服务端代理把发现与负载均衡集中到基础设施，客户端简单，但多一跳延迟与代理容量风险。
- 客户端发现要处理列表缓存、推送延迟与过期实例。缓存时间过长会把流量打到已下线节点。
- 代理模式要防止单代理故障，需要多实例与健康检查，并考虑连接复用。
- 大规模集群中，推送全量实例列表会造成带宽与内存压力。分片或按需订阅更可控。
- 选择还取决于发布体系与故障域，不能只看一次调用的延迟。

### 14.15 健康检查与实例摘除如何避免流量抖动？

- 存活检查判断进程是否运行，就绪检查判断是否可接收流量，两者不能混用。
- 摘除要有延迟与排空期，等待负载均衡器停止转发并让在途请求完成。
- 健康检查阈值过敏感会导致实例在瞬时慢查询时被摘除，阈值过钝会让故障实例长期接流量。
- 摘除后要有恢复探测与预热，避免瞬时流量超过刚恢复实例的承载能力。
- 多级健康检查要区分进程、端口、依赖与业务就绪。依赖故障不应一律摘除所有实例。
- 监控摘除率与重新加入率，频繁抖动通常说明检查超时或资源不足。

### 14.16（辨析）轮询、最小连接、P2C 与一致性哈希分别适合什么场景？

- 轮询假设实例同质且请求代价相近，实现简单，但无法感知慢实例。
- 最小连接按当前负载分配，适合长连接或请求耗时差异较大的场景，需要准确统计在途请求。
- P2C 随机选两个实例并选择负载较低者，状态开销小，对尾部延迟更友好。
- 一致性哈希把相同键映射到稳定实例，适合缓存亲和，但扩缩容会造成部分键迁移。
- 负载均衡要结合实例权重、区域亲和与故障摘除，单看算法会忽略网络拓扑。
- 任何算法都需要避免把重试流量再次打到同一故障实例。

### 14.17 金丝雀与灰度发布中如何控制流量？

- 按用户 ID、请求头或百分比分流。分流键要稳定，避免同一用户在不同实例间来回切换。
- 金丝雀实例要使用独立资源池或至少独立指标，防止与基线流量混在一起无法归因。
- 灰度比例应逐步提升，每一步观察错误率、延迟与饱和度，并设置自动回滚条件。
- 数据库与消息格式变更要向前兼容，灰度期间新旧版本可能同时读写。
- 会话粘性会影响灰度覆盖，需明确是否需要粘性以及粘性失效后的行为。
- 回滚要能在不依赖新版本的情况下完成，配置与结构定义变更需支持双读或版本兼容。

### 14.18 如何用指标与追踪定位 RPC 尾延迟？

- 延迟直方图要按接口、实例、错误码与重试次数拆分，平均值会掩盖长尾。
- 追踪要记录客户端发送、服务端接收、排队、处理、序列化与网络回传各阶段耗时。
- 区分服务端处理慢、连接池等待、DNS 解析与 TLS 握手，定位点不同。
- 高并发下要采样追踪，避免追踪本身成为瓶颈。错误请求应提高采样率。
- 尾延迟常来自排队与锁竞争，需结合 CPU 调度、垃圾回收与连接队列指标。
- 重试会把一次慢请求放大为多次调用，追踪要保留重试链路与最终结果。

### 14.19 跨语言 RPC 的回调与执行器队列应如何设计？

- I/O 线程只负责读写与解码，业务回调应切换到独立执行器，避免阻塞事件循环。
- 执行器要有有界队列与拒绝策略，回调排队过长会放大尾延迟。
- 协程恢复要回到绑定的执行器。跨线程发布任务时，入队与出队需要 `std::memory_order_acquire` 与 `std::memory_order_release` 配对，`std::memory_order_relaxed` 可能让执行线程读到未同步的任务字段。
- 回调中再次发起 RPC 要避免同步等待，否则可能耗尽执行器线程。
- 取消要传播到回调与下游，已排队但未执行的任务应能跳过。执行器内部队列可以采用有界互斥队列或无锁队列，无锁队列要额外处理内存回收与批量唤醒。
- 线程局部存储与请求上下文要在切换执行器时显式传递，不能依赖 I/O 线程的线程局部状态。

```cpp
void on_response(Response resp) {
    auto ctx = current_context();
    compute_pool.submit([ctx, resp = std::move(resp)]() mutable {
        handle(ctx, std::move(resp));     // 业务在计算执行器运行
    });
}
```

### 14.20（场景）一次发布后 RPC 的 P99 延迟上升，如何排查？

- 先确认是全局还是特定实例、接口与客户端版本，比较发布前后的延迟分位数。
- 检查连接池等待、执行器队列与 DNS 解析时间，区分客户端排队与服务端处理。
- 检查新版本是否增加序列化字段、同步日志或锁范围，CPU 使用率与系统调用次数可提供线索。
- 检查下游依赖的延迟与重试次数，发布可能改变了超时或重试默认值。
- 检查实例数量与负载均衡权重，滚动发布期间流量可能集中到少数旧实例。
- 用追踪对比慢请求的阶段耗时，确认尾延迟来自网络、排队还是业务逻辑。

## 15. 消息队列与事件驱动

### 15.1（辨析）最多一次、至少一次与恰好一次分别意味着什么？

- 最多一次：发送后不等待确认或失败不重试。消息可能丢失，但不会重复。
- 至少一次：失败后重试直到确认。消息不丢，但可能重复，这是多数消息队列的默认语义。
- 恰好一次：在生产者到 broker、broker 到消费者的特定边界内，通过事务、幂等或去重实现，无法覆盖所有副作用。
- 端到端恰好一次需要业务状态机参与，数据库写入与消息确认必须原子化或可重放。
- 语义越强，延迟、吞吐与实现复杂度越高。选择应基于业务能否容忍重复或丢失。
- 「恰好一次」描述处理效果，网络传输仍可能重复。

### 15.2 为什么恰好一次通常只在特定边界内成立？

- 网络确认可能丢失，生产者无法区分 broker 未收到与确认未到达，只能重试。
- 消费者处理成功但提交位移前崩溃，重启后会再次消费。
- broker 的幂等生产者只能去重同一生产者会话内的重复批次，跨会话或跨集群不保证。
- 事务消息可以保证本地事务与消息发送的原子性，但消费端副作用仍需幂等。
- 端到端恰好一次需要把消费位移与业务结果放在同一事务存储中。
- 边界外的系统调用、邮件与支付等副作用无法回滚，只能补偿。

### 15.3 生产者发送确认与重试如何避免消息丢失？

- 使用持久化 topic 与 `acks=all` 一类确认策略，确保消息写入多个副本后才返回成功。
- 生产者要处理可重试错误与不可重试错误，缓冲区满时不能静默丢弃。
- 重试要限制次数与总时间，并与 broker 的请求去重配合。
- 发送队列要有上限与背压，无限缓冲会在 broker 故障时耗尽内存。
- 关闭生产者前要刷新未确认消息，进程崩溃仍可能丢失缓冲区中的消息。
- 监控未确认队列、重试率与失败率。确认成功不等于消息已被消费。

### 15.4 分区与消费者组如何决定并行度？

- 同一分区在同一消费者组内只能由一个消费者处理，分区数决定最大并行度。
- 消费者数超过分区数时，多余消费者空闲，扩容前要评估分区数。
- 分区数增加会改变键到分区的映射，可能破坏顺序与缓存亲和。
- 再均衡期间分区会暂停或迁移，时间过长会导致消费延迟与重复。
- 消费者组要使用会话超时与心跳，避免假死消费者占住分区。
- 并行度还受下游数据库连接数与处理线程数限制，仅增加分区可能加剧下游竞争。

### 15.5 分区键如何选择才能避免热点？

- 分区键应具有足够基数且分布均匀。用户 ID 与订单 ID 通常比日期、地区更均匀。
- 相同业务实体需要顺序时，使用实体 ID 作为键，把同一实体的消息放到同一分区。
- 空键或固定键会把所有消息压到一个分区，形成写热点。
- 键的哈希分布会随数据倾斜变化，需要监控分区流量与堆积。
- 热点键可以把大键拆成子键，但会牺牲该实体的全局顺序。
- 分区数变更后键映射可能改变，顺序敏感的业务要避免在运行中扩容。

### 15.6 顺序消息如何实现？

- 全局顺序要求所有消息进入同一分区或同一队列，吞吐受单点限制。
- 分区顺序只保证同一分区内有序。生产端按业务键路由，消费端单分区单线程处理。
- 生产端重试可能改变消息顺序，需启用幂等生产者或按序号去重。
- 消费端并发处理同一分区会破坏顺序，异步提交位移也可能在失败时跳过消息。
- 顺序与重试冲突。失败消息阻塞后续消息还是跳过，需要明确的策略。
- 顺序消费的吞吐通常低于并发消费。扩容应增加分区，单分区增加消费者不会提升并行度。

### 15.7（陷阱）位移提交时机如何影响重复与丢失？

- 先处理后提交：处理成功但提交前崩溃会重复消费，不会丢失。
- 先提交后处理：提交后处理失败会丢失消息，通常不采用。
- 自动提交按时间间隔进行，可能提交尚未处理完的位移。
- 批量提交要确保批次内所有消息都已处理，否则部分失败会导致跳过。
- 位移存储要与业务结果的事务边界对齐，才能实现消费端恰好一次。
- 再均衡前要提交已完成位移并停止旧消费者，避免两个消费者同时处理同一分区。

### 15.8（实现）幂等消费的键如何设计？

- 键应来自消息中的业务唯一标识，例如订单号加事件类型，不能使用随机数。
- 去重表与业务写入放在同一事务，保证检查与写入原子。
- 去重记录要保存处理结果或状态，重复消息可以返回同一结果。
- 过期时间要覆盖最大重试与回溯窗口，过短会让旧消息重新生效。
- 高并发下唯一键冲突要正确处理，不能先查询再插入而留下竞态。
- 去重存储本身要有容量与清理策略，无限增长会拖慢写入。

### 15.9 事务消息如何与本地事务表配合？

- 生产者先发送半消息，broker 暂存但不对消费者可见。
- 本地事务执行成功后提交半消息，失败则回滚，broker 根据事务状态决定是否投递。
- 本地事务与消息发送之间仍有时间窗口，需要事务回查补偿。
- 事务表记录本地事务状态与消息 ID，回查时按消息 ID 查询。
- 消费者仍可能重复收到消息，业务侧幂等不可省略。
- 事务消息适合保证本地事务与消息发送的原子性，不适合跨多个服务的分布式事务。

### 15.10 事务消息的回查与悬挂如何避免？

- 回查要能根据消息 ID 找到本地事务记录，记录必须在发送半消息前或同一事务中写入。
- 回查接口要幂等，重复回查返回同一状态。
- 悬挂指半消息已写入 broker，但本地事务状态长期未确定，消息既未提交也未回滚。
- 事务记录要有超时与终态，长期未知状态需要人工或补偿任务处理。
- broker 回查次数与间隔要有限制，避免故障期间无限重试。
- 生产者重启后要能恢复未完成事务，内存状态不足以支撑回查。

### 15.11 死信队列的触发条件与再投递策略如何设计？

- 触发条件包括超过最大重试次数、消息过期、反序列化失败与业务明确拒绝。
- 死信队列要保留原始消息、错误原因、重试次数与时间戳，便于排查。
- 死信要经过修复、重放或丢弃流程。重放要限速，避免再次导致下游过载。
- 重试队列与死信队列要分开，避免正常重试占用死信容量。
- 死信积压要告警，长期不处理会掩盖消费端缺陷。
- 再投递要带幂等键与限速，不能直接全量回灌生产队列。

### 15.12 延迟队列如何实现？

- 定时扫描数据库实现简单，但精度受扫描间隔限制，数据量大时查询压力高。
- 时间轮把定时任务按槽位组织，插入与删除接近常数时间，适合大量短延迟任务。
- 时间轮的分层设计可以覆盖长延迟，但实现复杂，槽位溢出需要降级。
- broker 原生延迟消息通常有固定等级，任意延迟需要多级组合或外部调度。
- 延迟消息要防止重复投递与提前投递，消费者仍需幂等。
- 进程重启后延迟任务要持久化，纯内存时间轮会丢失未到期任务。

### 15.13 消息积压时应该扩容消费者还是分区？

- 先看分区数与消费者数的关系。消费者已覆盖所有分区时，增加消费者不会提升并行度。
- 若消费逻辑是瓶颈，优化批处理、减少同步调用与数据库往返更直接。
- 若分区不足，扩容分区可以提升并行度，但会改变键映射与顺序。
- 临时扩容消费者要考虑再均衡成本与下游承载能力，避免把压力转移给数据库。
- 积压消息若已过期，扩容可能只是加速丢弃，需要先确认业务语义。
- 监控消费速率、处理耗时与分区倾斜。积压常由少数热点分区造成。

### 15.14 消息 TTL 与队列容量限制会带来哪些语义变化？

- 消息生存时间（TTL）到期后可能被删除或转入死信，生产者已确认不代表消费者一定收到。
- 队列满时 broker 可能阻塞生产者、拒绝写入或丢弃最旧消息，行为由配置决定。
- TTL 与重试结合时，重试消息可能因剩余时间不足而提前进入死信。
- 容量限制是背压手段，但会改变可用性，需要与生产端限流配合。
- 过期策略要区分业务过期与传输过期，不能把两者混为一个时间。
- 监控过期率与拒绝率，才能判断容量是否不足。

### 15.15（辨析）广播消费与集群消费的位移管理有何差异？

- 集群消费中同一消费者组共享位移，每个分区只由一个消费者处理。
- 广播消费中每个消费者都收到全量消息，位移通常按消费者实例独立管理。
- 广播消费者的上下线不会触发分区再均衡，但会改变整体处理能力。
- 广播模式下重复消费更常见，幂等键要包含消费者实例或业务维度。
- 广播消费适合配置刷新与缓存失效通知，不适合高吞吐数据处理。
- 位移存储要区分共享与独立，混用会导致重启后跳过或重复大量消息。

### 15.16 去重与顺序消费如何共同作用？

- 去重表只能消除重复副作用，不能恢复被并发打乱的顺序。
- 顺序消费要求同一键的消息串行处理，去重检查与业务写入应在同一事务。
- 若先写业务再写去重记录，崩溃窗口会留下重复副作用。
- 若先去重再写业务，业务失败后重试会被误判为已处理。
- 分区内单线程处理可以简化顺序，但会降低吞吐，需按业务键分片并行。
- 重试消息应回到原分区与原位置之后，不能直接追加到队尾破坏顺序。

### 15.17（实现）Outbox 模式如何保证本地事务与事件发布的原子性？

- 业务表与 outbox 表在同一本地事务中写入，保证业务状态与待发事件同时提交或回滚。
- 独立发布器扫描 outbox 并发送消息，成功后标记已发送，失败则重试。
- 发布器可能重复发送，消费者必须幂等。outbox 记录要保留事件 ID。
- 扫描要使用索引与批量读取，避免全表扫描拖慢数据库。
- 多实例发布要使用行锁、租约或分区所有权，避免同一事件被多个发布器同时处理。
- outbox 表要定期清理，保留时间应覆盖最大重试与审计需求。

### 15.18 事件结构定义如何演进才能兼容旧消费者？

- 只新增可选字段，不删除或重命名已有字段，不改字段含义与类型。
- 消费者要忽略未知字段，不能因为出现新字段而反序列化失败。
- 事件版本可以与事件类型分离，消费者按版本选择解析逻辑。
- 破坏性变更应发布新事件类型，旧类型继续维护一段时间。
- 结构定义注册中心要拒绝不兼容变更，并保留历史版本供回放。
- 回放旧事件时要用当时的结构定义，不能只用最新代码解释历史数据。

### 15.19 消息队列的故障模型有哪些？

- broker 崩溃可能导致未刷盘消息丢失，确认策略决定持久性边界。
- 副本同步不足时，主副本切换可能丢失最新消息。同步副本集合（ISR）机制要配合最小同步副本数。
- 网络分区可能造成消费者假死、重复再均衡与位移回退。
- 确认丢失会让生产者重试并产生重复消息，消费者要幂等。
- 磁盘满、文件句柄耗尽与页缓存回写拥塞会表现为写入超时，未必立即报错。
- 故障恢复后要限制回放速度，避免积压流量瞬间超过下游承载能力。

### 15.20（场景）促销活动后出现消息积压与重复消费，如何排查？

- 先看积压分布是全局还是少数分区，区分热点键、消费者故障与下游变慢。
- 检查消费者处理耗时、错误率与再均衡次数，频繁再均衡会导致重复消费。
- 检查位移提交是否早于业务完成，以及重试是否回到原分区。
- 检查下游数据库连接池与慢查询，消费线程可能阻塞在 I/O。
- 检查幂等键是否稳定、去重表是否已过期或写入失败。
- 处理顺序应是先限流保护下游，再修复消费逻辑，最后按分区逐步回放积压。

## 16. 分布式设计题

### 16.1 分布式锁的正确性条件是什么？

- 互斥：任意时刻最多一个持有者。锁必须有唯一持有令牌，释放时校验令牌。
- 活性：持有者崩溃后锁能自动释放，通常依赖租约与续期。
- 安全性：锁服务多数派确认后才能认为加锁成功，避免网络分区下双持有。
- 对共享存储的写还应携带单调递增的隔离令牌（fencing token），由存储端拒绝旧持有者。
- 可重入与公平性是可选项，需在接口上明确，不要默认所有锁都支持。
- 锁的粒度、持有时间与失败策略要结合业务。锁越粗，尾延迟越高。
- 分布式锁不能替代数据库唯一约束或幂等。网络超时下仍可能出现结果未知。

### 16.2（实现）基于 Redis 的分布式锁如何避免误删他人的锁？

- 加锁时写入唯一令牌，释放时用 Lua 脚本比较令牌后再删除，保证比较与删除原子。
- 令牌不能使用客户端 ID 之类的可预测值，避免不同进程碰撞。
- 锁要设置过期时间，防止持有者崩溃后永久占用。
- 过期时间必须大于业务最大执行时间，或通过续期延长。
- 主从切换可能丢失锁写入，异步复制下不能提供严格互斥。
- 删除失败要重试并告警，不能默默忽略。

### 16.3（辨析）Redlock 的争议与适用边界是什么？

- Redlock 在多个独立 Redis 实例上加锁，试图降低单点故障影响。
- 反对观点认为它依赖时钟与网络延迟假设，进程暂停可能让锁在临界区内过期。
- 即使多数实例加锁成功，客户端长时间停顿后仍可能失去锁而不自知。
- 对安全性要求高的场景，应使用具备线性一致能力的协调服务或 fencing token。
- Redlock 适合对偶发双持有有一定容忍、且希望避免单点 Redis 的场景。
- 选择前要明确故障模型，不能把 Redlock 当作强一致锁的通用替代。

### 16.4 基于 etcd 或 ZooKeeper 的锁如何工作？

- etcd 用租约绑定键，客户端续租维持持有。租约过期后键自动删除。
- 加锁通过事务比较版本号并创建唯一键，失败则监听前一个键的删除事件。
- ZooKeeper 用临时顺序节点，序号最小者持有锁，其余节点监听前驱。
- 会话超时决定锁的自动释放时间。网络分区可能导致会话过期与锁丢失。
- 持有者要在临界区内检查租约有效性，不能假设锁一直有效。
- 协调服务自身需要多数派，跨地域部署会增加加锁延迟。

### 16.5 锁续期失效会导致什么问题？

- 续期线程被调度延迟、网络分区或进程暂停时，锁可能在业务完成前过期。
- 另一个持有者获得锁后，两个进程同时修改共享资源，破坏互斥。
- 仅靠续期不能消除风险。临界区写操作应携带 fencing token，由存储端拒绝旧令牌。
- 续期失败要立即停止业务或进入只读状态，不能继续执行未受保护的写。
- 续期间隔应小于租约时间，并留出网络往返与时钟漂移余量。
- 续期线程要与业务线程隔离，避免业务阻塞导致续期饥饿。

### 16.6 分布式锁与本地锁如何组合？

- 本地锁保护进程内共享状态，分布式锁保护跨进程临界区，两者职责不同。
- 常见顺序是先获取分布式锁，再获取本地锁。统一顺序可降低死锁风险。
- 持有分布式锁期间调用可能再次加锁的函数，要避免不可重入导致自锁。
- 本地锁等待时间应计入总超时，不能无限等待。
- 锁粒度按资源 ID 分片，避免一个全局锁串行化所有请求。
- 释放顺序与获取顺序相反，异常路径也要保证释放。

### 16.7（场景）分布式任务调度如何保证不重复执行？

- 调度器为每个任务实例生成唯一执行 ID，执行器以该 ID 做幂等或去重。
- 通过中心存储的租约或抢占记录选出唯一执行者，租约到期后才允许接管。
- 任务结果与状态更新放在同一本地事务，外部副作用要幂等或补偿。
- 允许至少一次执行，业务侧用唯一约束或幂等键兜底。
- 时钟偏差会让多个调度器同时认为任务到期，需要中心时间或版本比较。
- 监控重复执行与漏执行，二者需要不同的修复策略。

### 16.8 调度器主备与分片如何避免单点？

- 主备模式通过选主保证同一时刻只有一个调度器，备节点热备或冷备。
- 分片模式把任务按哈希分配到多个调度器，每个分片独立选主。
- 选主依赖共识服务，网络分区时少数派必须停止调度。
- 分片迁移要等待旧所有者租约过期，避免两个调度器同时处理同一分片。
- 调度器只负责触发，实际执行交给工作节点，避免调度器被长任务拖住。
- 脑裂防护要结合 fencing token 与存储端条件写。

### 16.9 定时任务用时间轮还是数据库扫描？

- 时间轮适合大量短延迟任务，插入删除快，内存占用随任务数增长。
- 数据库扫描实现简单、持久性好，但扫描间隔决定精度，数据量大时查询压力高。
- 时间轮需要持久化与恢复机制，进程重启后未到期任务不能丢失。
- 数据库扫描要用索引与分页，避免全表扫描和锁竞争。
- 混合方案可以用数据库存任务、时间轮做近期调度，兼顾持久性与精度。
- 任务量、延迟精度与运维复杂度决定选择，不能只看单次触发延迟。

### 16.10 任务失败重试、补偿与幂等如何设计？

- 区分可重试错误与永久错误，永久错误直接进入失败状态并告警。
- 重试使用指数退避与最大次数，避免故障期间反复冲击下游。
- 补偿操作要可重复执行，补偿失败也要有记录与人工介入入口。
- 任务状态机要明确待执行、执行中、成功、失败与补偿中，避免状态跳跃。
- 执行 ID 与业务键要稳定，重试复用同一 ID 以便去重。
- 长任务要支持取消与超时，取消后要清理已分配的资源。

### 16.11 配置中心的推拉模型如何取舍？

- 推模型实时性好，但大量客户端同时收到变更会产生推送峰值。
- 拉模型由客户端轮询，服务端压力可控，但变更生效有延迟。
- 长轮询结合两者。客户端挂起等待，变更时立即返回，超时后重新拉取。
- 客户端要缓存配置并支持本地快照，配置中心不可用时仍能启动。
- 推送要带版本号与校验和，客户端按版本去重与排序。
- 大规模集群要分片推送或按订阅关系推送，避免全量广播。

### 16.12 配置变更如何避免惊群与全量推送？

- 变更发布前做合并与去抖，短时间内的多次修改只推送最终版本。
- 按应用、机房或租户分片推送，控制单批客户端数量。
- 客户端收到变更后加随机延迟再拉取，错开请求峰值。
- 服务端对拉取请求做限流与合并，避免每个客户端都触发一次全量查询。
- 配置监听要支持只订阅相关键，减少无关变更唤醒。
- 监控推送成功率、拉取延迟与客户端错误率，避免只看服务端 QPS。

### 16.13 配置灰度、回滚与版本管理如何设计？

- 每次变更生成不可变版本，记录操作者、时间、差异与审批信息。
- 灰度按实例、用户或机房分批，观察错误率与业务指标后再扩大。
- 客户端要能回退到上一个稳定版本，回滚不能依赖重新生成配置。
- 配置内容要做结构校验与类型检查，避免错误值扩散到全集群。
- 删除配置要有引用检查，防止其他应用依赖的键被误删。
- 审计日志要保留足够时间，支持定位某次变更的影响范围。

### 16.14（实现）分布式令牌桶如何原子更新？

- 集中式实现把令牌数、上次填充时间与速率放在同一存储，用 Lua 脚本原子计算。
- 计算时先按时间差补充令牌，再判断是否足够，最后扣减并写回。
- 时钟要用单调时间或服务端时间，客户端时间不可信。
- 多级限流可以本地预取一批令牌，减少中心访问，但要处理未用完令牌的回收。
- 单机令牌桶的填充与扣减逻辑如下，分布式版本把同样的计算放进 Lua 脚本或事务中原子执行。
- 桶容量与速率要分开配置，容量决定突发，速率决定平均吞吐。
- 存储故障时要有本地保底限流，避免完全放行。

```cpp
bool TokenBucket::try_acquire(std::chrono::steady_clock::time_point now) {
    std::lock_guard lock(mu_);
    const auto dt = std::chrono::duration<double>(now - last_).count();
    tokens_ = std::min(capacity_, tokens_ + dt * rate_);
    last_ = now;
    if (tokens_ < 1.0) return false;
    tokens_ -= 1.0;
    return true;
}
```

### 16.15（陷阱）固定窗口限流的边界突刺如何修复？

- 固定窗口在窗口切换时可能允许两个窗口的满额流量，瞬时达到两倍限额。
- 滑动窗口把大窗口拆成小格，按时间加权统计，降低边界突刺。
- 令牌桶通过持续补充令牌平滑突发，桶容量仍允许一定突刺。
- 漏桶按固定速率输出，适合严格平滑，但会增加排队延迟。
- 分布式环境下窗口边界要对齐同一时钟，避免各节点窗口错位。
- 修复突刺会增加状态与计算开销，需按业务对突发的容忍度选择。

### 16.16 事件总线的订阅关系与投递模型如何设计？

- 订阅关系要支持按主题、事件类型与属性过滤，避免消费者收到无关事件。
- 投递模型分为推与拉。推模型实时但需要背压，拉模型由消费者控制速率。
- 每个订阅要有独立位移与重试策略，避免一个消费者失败影响其他订阅。
- 事件总线要定义至少一次或最多一次语义，并明确重复与丢失边界。
- 订阅变更要版本化，删除订阅前要等待在途事件处理完成。
- 事件总线自身要做多副本与故障转移，避免成为单点。

### 16.17 事件总线的顺序、重复与死信如何处理？

- 全局顺序代价高，通常只保证同一聚合根或同一分区内有序。
- 消费者按分区串行处理。失败重试要阻塞该分区，或转入死信后继续。
- 重复事件由消费者幂等处理，事件 ID 与业务键共同去重。
- 死信要记录失败原因与重试次数，支持按订阅重放。
- 重放会再次产生重复，必须限速并确保幂等。
- 顺序与并发冲突时，优先保证业务不变量，再考虑吞吐。

### 16.18 分布式追踪上下文如何跨线程与协程传播？

- 追踪上下文包含 `trace_id`、`span_id` 与采样标志，进入新线程或协程时要显式复制。
- 线程局部存储不会自动跨线程传递，线程池复用还会让旧上下文残留。
- 协程挂起与恢复可能切换线程，上下文应绑定在协程帧或任务对象上。
- 跨进程通过请求头传播，边界处要校验格式并生成缺失的 ID。
- 异步回调与定时任务要携带父 span，否则追踪链会断裂。
- 采样策略要一致，避免下游采样而上游未采样导致链路不完整。

### 16.19 分布式系统排障如何区分超时、重试与级联故障？

- 超时是单次调用超过 deadline，重试是同一逻辑操作被多次执行，级联故障是故障从单点扩散到全局。
- 查看调用次数与请求数之比，比值上升说明重试放大。
- 查看超时发生位置，连接超时、读写超时与排队超时对应不同层。
- 查看线程池、连接池与队列饱和度，资源耗尽通常先于错误率上升。
- 查看下游依赖的故障传播路径，熔断与限流是否按预期生效。
- 保留请求 ID 与重试链，单看聚合指标无法还原一次请求的完整路径。

### 16.20（场景）设计跨机房任务编排系统，关键取舍是什么？

- 明确一致性目标。任务状态需要强一致还是允许短暂不一致，决定是否跨机房共识。
- 调度器按机房分片，任务归属一个主机房，避免跨机房双主执行。
- 跨机房复制采用异步还是同步，取决于恢复点目标与写延迟预算。
- 任务执行要幂等并带 fencing token，机房切换时旧执行者必须失效。
- 故障转移要定义脑裂处理、租约过期与人工接管流程。
- 监控要覆盖跨机房延迟、复制滞后、任务重复与漏执行，按机房分别看指标。
