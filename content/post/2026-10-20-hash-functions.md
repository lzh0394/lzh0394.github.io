哈希函数（hash function）是一个映射 `H: {0,1}* → {0,1}^n`：把任意有限长的比特串映射成固定 n 位的比特串，n 称为摘要（digest）长度，输出也叫哈希值或散列值。对每个输入 x，H(x) 由 x 唯一确定，并且存在多项式时间算法算出它。键控哈希多一个密钥参数，写成 `H: K × {0,1}* → {0,1}^n`，固定密钥 k 之后，H(k, ·) 符合哈希函数的定义。

哈希函数按用途和性质，大致可以分成四类：

| 类别 | 性质要求 | 典型用途 |
| --- | --- | --- |
| 非密码学哈希 | 快、分布均匀、最坏情况可控 | 哈希表、布隆过滤器、一致性哈希、去重、检错 |
| 无键密码学哈希 | 抗原像、抗第二原像、抗碰撞 | 完整性校验、数字签名、内容寻址 |
| 键控哈希（MAC/PRF） | 没有密钥就无法伪造 | 消息认证、抗 HashDoS 的哈希表 |
| 口令哈希 | 慢、内存硬、每个口令独立加盐 | 口令存储 |

CRC-32 严格说是检错码，习惯上与非密码学哈希放在一起讨论。

注意：哈希不是加密。哈希一般不可逆，也不提供保密性；键控哈希虽然带密钥，但那是认证用的，并非加密。

## 1. 非密码学哈希

### 1.1 解决什么问题

非密码学哈希是哈希表、布隆过滤器、一致性哈希、内容去重、检错码的基础，要求吞吐高、输出分布均匀、最坏情况可控，不要求抗碰撞、单向等密码学性质。下面的介绍以哈希表为主，因为哈希表对哈希函数的要求最苛刻。

哈希表把键映射到桶下标，理想情况下每次查找、插入、删除都是常数时间，因此哈希函数必须满足三项要求：

- 相等键的哈希值必须相同，否则相等的键会落到不同桶，查找和删除都会失效。
- 哈希计算要快，访存局部性要好。
- 输出在桶下标空间上要均匀；表长取 2 的幂时，低位也要均匀。

哈希质量要看实测：桶长分布、最大桶长、扩容频率，以及不同键集上的稳定性。

键空间远大于桶空间，碰撞按鸽笼原理不可避免。表长 m、存入 n 个键时，期望碰撞对数约为 n²/(2m)，所以装载因子 n/m 要控制住，常见阈值是 0.75 左右，超过就扩容并重新散列。随机键下各项操作均摊 O(1)，最坏情况是 O(n)：所有键挤进同一个桶。键由对手挑选时，最坏情况就变成现实攻击，见下文 HashDoS。

### 1.2 哈希表的碰撞

哈希表处理碰撞有两种方式：链地址法把同一桶的键串成链表（或树），实现简单、删除方便；开放寻址法在冲突时按探测序列找下一个空位，缓存友好但删除要用墓碑标记，装载因子也不能太高。

### 1.3 对 Hash 表的 DoS 攻击

如果攻击者能控制进入哈希表的键，他就可以预先算出一大批哈希值相同的键。插入第 i 个键要扫描 i 个已有元素，n 个键总共 O(n²)。一个几十 KB 的 HTTP 请求（大量同名参数、表单字段、JSON 键）就能让服务端 CPU 跑满几分钟到几小时，带宽成本极低。这是算法复杂度攻击，利用的是最坏情况退化，与密码学意义上的碰撞、原像无关。

防御 DoS 攻击的核心思路是让攻击者算不出碰撞：哈希函数带一个每个进程（或每次启动）随机生成的密钥，攻击者离线构造的碰撞到了线上就不成立了。这类构造里最有名的是 SipHash（Aumasson 与 Bernstein，2012），一个面向短输入的 PRF，目标场景就写着「保护哈希表查找免受 hash-flooding」；Rust 的 `RandomState`、Python 的哈希随机化、Ruby 1.9 起的随机化都是这个思路，SipHash 本身的介绍放在后面的键控哈希一节。

### 1.4 代表算法：xxHash、MurmurHash、CRC-32

xxHash 由 Yann Collet 在 2012 年发布，目标是在保持高性能的同时，尽可能减少哈希冲突。XXH32/XXH64 之后又加了 XXH3（2019 年公布），zstd 的帧校验、不少数据库和文件系统用它；但是要注意，它没有任何抗碰撞保证，只适合输入不受对手控制的场合。

MurmurHash 由 Austin Appleby 在 2008 年发布，MurmurHash3 是当前版本，x86 与 x64 各有变体，Hadoop、Cassandra 这类分布式系统用它做分区和布隆过滤器的哈希；它可设种子、分布好，但同样不是密码学函数。

CRC-32 严格说不是哈希函数的同类，而是循环冗余校验：CRC 由 Peterson 在 1961 年提出，CRC-32 的标准生成多项式 `0x04C11DB7` 由 IEEE 802.3 规定。CRC 靠多项式除法的余数检测随机比特错误。它线性且可预测，攻击者能轻易构造出 CRC 相同的不同文件。

### 1.5 怎么用、别怎么用

哈希表键直接选语言默认即可；Rust 与 Python 默认已经带随机化，C++ 标准库没有，面对不可信输入（比如拿 HTTP 参数当 `unordered_map` 的键）应自定义带随机盐的 hasher，或者先对键做一次 HMAC 再用结果作键。

- 布隆过滤器（Bloom filter）：用 k 个独立哈希把元素映射到位数组的 k 个位置。查询返回「可能存在 / 一定不存在」，有假阳性、无假阴性；标准版本不能删除元素，计数布隆过滤器可以。适合缓存穿透防护、爬虫 URL 去重这类允许误判的场景。
- 一致性哈希：把键和节点都哈希到一个环上，节点增减时只影响相邻区间，用于分布式缓存与分片（Karger 等，1997）。虚拟节点用来改善负载均衡。
- 内容分块与去重：按内容定义边界（content-defined chunking）再对块哈希，备份与同步工具据此只传变化的块。

CRC-32 这类校验和只检测传输中的随机比特错误，不能用它做防篡改：它和密码学哈希解决的不是同一个问题。同样，也别拿密码学指标去评价这类函数——问 xxHash 抗不抗碰撞，是把尺子用错了地方。

## 2. 无键密码学哈希

密码学哈希的三条性质：

- 抗原像（preimage resistance）：给定摘要 h，找 m 使 H(m)=h。
- 抗第二原像（second preimage resistance）：给定 m₁，找 m₂≠m₁ 使 H(m₂)=H(m₁)。
- 抗碰撞（collision resistance）：找任意两条不同的消息 m₁≠m₂ 使 H(m₁)=H(m₂)。

由于生日攻击的存在，碰撞的难度只有寻找原像的平方根。密码学哈希的摘要长度直接决定安全上限：128 位摘要的碰撞强度只有 64 位，早就不能用于签名；256 位摘要的碰撞强度是 128 位，目前够用。抗碰撞在实践中也蕴含抗第二原像（能找第二原像就找到了一个碰撞），但反过来不成立。

除此之外还有两条要求：

- 雪崩效应：输入翻转一位，输出大约一半的位翻转
- 符合随机预言模型：输出在计算上不可区分于随机串

这两条是设计目标和统计检验的对象，不是可以逐条验证的规范条款。

### 2.1 怎么工作

密码学哈希的通用模式：将任意长输入（填充到输入的整数倍后）切成定长块，用压缩函数折叠，最后输出或者截断。

主流的迭代模式有：

- Merkel-Damgård
- 海绵
- 树状

MD5、SHA-1、SHA-2 都属于 Merkle–Damgård 结构：把消息填充到分组长度的整数倍，然后用同一个压缩函数逐块迭代，最后一块的输出就是摘要。填充里包含消息长度，所以填充本身是可计算的。

这个结构有一个天然缺陷：已知 H(m) 和 m 的长度，不需要知道 m 的内容，就能算出 H(m ‖ padding ‖ 任意后缀)。这就是长度扩展攻击。它本身不破坏抗碰撞性，但会让「把密钥拼在消息前面当 MAC」的用法（H(secret ‖ message)）彻底失效——攻击者可以在不知道密钥的情况下给消息追加内容并算出合法 MAC。HMAC 用内外两层哈希把密钥夹在中间，就是为了堵这个洞，具体构造见键控哈希一节。

SHA-3 换成了海绵结构（sponge）：状态分成吸收（absorb）和挤压（squeeze）两个阶段，消息被异或进状态再做置换，最后从状态里挤出任意长度的输出。海绵结构没有「迭代压缩函数 + 长度填充」那套链式关系，天然不受长度扩展影响，还支持可变长度输出（SHAKE128/256）。

### 2.2 代表算法：SHA-256、SHA-3、BLAKE3

- MD5：1992 年，RFC 1321，128 位。碰撞早已实用化，任何安全用途都不应再用。
- SHA-1：1995 年，FIPS 180-1，160 位。2017 年 Google 与 CWI 给出真实碰撞（SHAttered），此后签名、证书里都应视为已破。
- SHA-2：FIPS 180-2（2002 年 8 月）定义 SHA-256/384/512；SHA-224 由 2004 年的修订补入；2012 年的 FIPS 180-4 又加入 SHA-512/224 与 SHA-512/256。目前全轮没有实用攻击。其中 SHA-256 由 NSA 设计，是 TLS、代码签名、比特币以及 Git 向 SHA-256 迁移的基础。
- SHA-3：FIPS 202（2015 年 8 月），基于 Keccak，是 NIST SHA-3 竞赛（2007–2012）的胜者；包括 SHA3-224/256/384/512 与 SHAKE128/256。它与 SHA-2 是并行标准，不是替代关系。
- BLAKE2：RFC 7693（2015 年 11 月），比 MD5 快但强度更高，常作为 SHA-3 的补充；
- BLAKE3：2020 年发布，加入树形并行与可扩展输出，目前是社区规范而非 NIST 标准。

### 2.3 用法

- 适用：完整性与去重。发布软件时附上 SHA-256，用户下载后重算比对。这里的前提是摘要通过可信渠道传播；如果摘要和文件放在同一台被攻破的服务器上，校验形同虚设。Git 用内容哈希给对象命名（blob、tree、commit），天然去重、可校验，早期用 SHA-1，正在向 SHA-256 迁移。
- 适用：数字签名。签名方案（RSA-PKCS#1 v1.5、ECDSA、Ed25519）大多先对消息做哈希再签。哈希的抗碰撞性是签名不可伪造性的基础：SHA-1 碰撞公开后，攻击者可以拿一张合法证书的哈希去撞出一张伪造证书，这也是 2017 年后各大 CA 与浏览器强制停用 SHA-1 证书的原因。
- 适用：工作量证明。比特币用 SHA-256d（连续两次 SHA-256）构造「找到一个带若干前导零的哈希」的难题，算力即投票权。
- 适用：哈希签名。SPHINCS+ 一类后量子签名只依赖哈希函数的抗碰撞性，已进入 NIST 后量子标准（FIPS 205，SLH-DSA）。

- 不适用：用 MD5、SHA-1 给证书或签名做摘要：这两种函数的碰撞已经实用化
- 不适用：把快速哈希当口令哈希用

## 3. 键控哈希（MAC 与 PRF）

键控哈希（keyed hash）是把密钥作为额外输入的哈希：H(k, m)，k 保密，m 是消息，输出叫标签（tag）或 MAC。固定 k 之后，H(k, ·) 就是一个普通哈希函数；没有 k 的一方算不出正确标签，所以键控哈希用来认证消息，或者当作伪随机函数（PRF）。它是对称的：验证方也持有密钥，所以只能向本来就信任的双方证明消息完整，无法向第三方证明；需要向第三方证明时用数字签名。抗 HashDoS 的哈希表也靠它。

### 3.1 怎么工作

HMAC（RFC 2104，1997）的定义是 H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ text))，其中 K 先补齐到分组长度，ipad 是 0x36、opad 是 0x5C 重复到分组长度。密钥同时进入内外两层，长度扩展在不知道密钥的情况下无从下手；它不依赖具体哈希函数，MD5、SHA-1、SHA-2 都能套。

KMAC 走另一条路：SHA-3 的海绵结构本身就适合吸收密钥，不需要 HMAC 那层包裹，SP 800-185 定义在 cSHAKE 之上的 KMAC128 与 KMAC256 就是这类构造。

SipHash 是面向短输入的 PRF（Aumasson 与 Bernstein，2012），输出 64 位、密钥 128 位，SipHash-1-3 与 SipHash-2-4 两种参数在速度与安全余量之间取舍；论文标题就写着保护哈希表查找免受 hash-flooding，16 字节输入、新密钥下在 AMD FX-8150 上约 140 个周期。

### 3.2 代表算法：HMAC、KMAC、SipHash

HMAC 由 Bellare、Canetti、Krawczyk 在 1996 年提出，1997 年成为 RFC 2104，后来收入 FIPS 198-1；TLS、JWT 的 HS256、AWS 的请求签名都用它。

KMAC 由 NIST SP 800-185（2016）定义，分 KMAC128 与 KMAC256，属于 SHA-3 生态；它的定位和 HMAC 相同，只是换了底层结构。

SipHash 由 Aumasson 与 Bernstein 在 2012 年提出，主战场是哈希表的抗 HashDoS：Rust 的 `RandomState`、Python 的字符串哈希、Ruby 1.9 起的哈希表随机化都把它用作底层函数。

### 3.3 用法

- 适用：消息认证用 HMAC-SHA-256 或 KMAC。
- 适用：验证时要按常数时间比较，例如 Python 的 `hmac.compare_digest`；用普通 `==` 比较摘要会泄露时序信息。
- 适用：抗 HashDoS 的哈希表用每进程随机的密钥，让对手离线构造的碰撞失效。

- 不适用：把 H(secret ‖ message) 当 MAC 用：长度扩展让攻击者能在不知道密钥的情况下追加内容（见无键密码学哈希一节），正确做法是 HMAC
- 不适用：把 MAC 当签名：MAC 没有不可否认性。

## 4. 口令哈希

口令哈希用于防止攻击者拿到密码哈希之后批量爆破，加盐防止攻击者打表和彩虹表攻击，盐不需要保密，但是需要每个用户的盐独立且随机。

### 4.1 代表算法：Argon2id、scrypt、bcrypt

Argon2id 是 Argon2 的混合变体，Argon2 由 Biryukov、Dinu、Khovratovich 设计，2015 年赢得 Password Hashing Competition，2021 年 RFC 9106 将其定为主推；推荐参数是 t=1、p=4、m=2²¹（2 GiB），内存受限时用 t=3、p=4、m=2¹⁶（64 MiB）。

scrypt 由 Colin Percival 在 2009 年提出，2016 年成为 RFC 7914，参数是 N、r、p；莱特币的工作量证明用了它。

bcrypt 由 Provos 与 Mazières 在 1999 年提出，基于 Blowfish 的密钥扩展，用 cost 参数控制迭代轮数；它至今仍广泛部署，但输入超过 72 字节会被截断。

### 4.2 用法

- 适用：每个用户独立随机盐，参数随硬件调整，并在登录成功时用新参数重新散列旧口令，为将来升级留出路径。

- 不适用：SHA-256、MD5 加盐存口令，全库共用一个盐，

## 5. 选型速查

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 哈希表键 | 语言默认（Rust/Python 已随机化）；C++ 对不可信输入自定义加盐 hasher | 抗 HashDoS，快 |
| 非对抗场景的快速哈希 | xxHash、MurmurHash | 追求吞吐；输入不受对手控制 |
| 传输检错 | CRC-32 | 检测随机比特错误，不防篡改 |
| 文件完整性 / 去重 | SHA-256 或 BLAKE3 | 抗碰撞，生态成熟 |
| 消息认证 | HMAC-SHA-256，或 KMAC/SHA-3 | 不受长度扩展影响 |
| 数字签名 | SHA-256/SHA-384/SHA-512 | 与签名方案配套 |
| 口令 | Argon2id（RFC 9106 参数优先） | 慢且内存硬 |
| 内容寻址 | SHA-256、BLAKE3 | 确定、抗碰撞 |
