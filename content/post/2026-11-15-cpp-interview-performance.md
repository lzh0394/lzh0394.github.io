## 1. 性能度量与基准

### 1.1 为什么性能结论必须绑定测量条件？

- 同一段代码的耗时取决于 CPU 型号与频率策略、缓存状态、编译器版本与优化级别、输入规模以及同机负载。
- 报告应记录可复现的最小信息集：代码版本、编译命令、CPU 型号、操作系统与内核版本、内存与 NUMA 拓扑、负载生成方式。
- 绝对时间只在相同环境下可比；跨机器比较应使用相对基线的比率，或同时运行对照程序。
- 性能结论的适用范围止于测量条件，条件改变后需要重新验证，不能直接外推。
- 发布前的基准若未记录这些条件，出现回归时无法区分代码变化与环境漂移。
- 统计上应报告样本数与分布，不只给一个最快值或单轮平均值。

### 1.2（陷阱）`steady_clock` 与 `system_clock` 的选择边界在哪里？

- `system_clock` 表示墙上时间，可被 NTP 或管理员调整，可能向前或向后跳变，用于间隔计时会得到负值或异常大的值。
- `steady_clock` 保证 `now()` 的返回值不随时间减小，并以相对真实时间的稳定速率前进，适合测量间隔与实现超时。
- `high_resolution_clock` 可以是 `system_clock` 或 `steady_clock` 的别名：libstdc++ 中别名 `system_clock`，MSVC 中别名 `steady_clock`，选择由实现定义。
- `steady_clock::period` 只描述计数单位的换算比例，实际分辨率由平台与时钟源决定；POSIX 上底层通常为 `clock_gettime(CLOCK_MONOTONIC)`。
- 跨进程或跨机器比较时间点需要 `system_clock`，并接受时钟同步误差。
- 需要绝对截止时间（例如证书有效期）时使用 `system_clock`，需要经过时长时使用 `steady_clock`。
- `steady_clock` 的纪元与速率调整策略由实现定义，不能把两次读数之差当作墙钟经过时间。

### 1.3 如何用 `steady_clock` 测量一段代码的耗时？

- 两次 `now()` 之间只放被测代码，计时调用本身的开销应单独测量并在报告中说明。
- 单次调用若在数十纳秒量级，时钟分辨率与读数噪声会淹没信号，应测量一批迭代再除以次数。
- 迭代之间要有数据依赖或输入变化，否则循环不变的计算可能被提到循环外。
- 结果需要被消费或通过 `DoNotOptimize` 约束，避免整个计算被判定为死代码。
- 批处理循环自身的递增、比较与分支开销应单独测量，作为基线扣除或说明。
- 计时点不要跨越线程同步、系统调用或 I/O，除非这些正是被测对象。
- 报告应给出迭代次数、总时间与每次迭代的时间，避免只给总时间。

```cpp
auto t0 = std::chrono::steady_clock::now();
work();
auto t1 = std::chrono::steady_clock::now();
const auto ns =
    std::chrono::duration_cast<std::chrono::nanoseconds>(t1 - t0).count();
```

### 1.4 基准测试为什么需要预热？

- 首次执行会触发代码页与数据页缺页，页表与 TLB 尚未建立，耗时不代表稳态。
- 指令缓存、uop 缓存、数据缓存与分支预测器需要若干次迭代才能进入稳定状态。
- 动态链接的延迟绑定、分配器首次向内核申请内存、线程池创建等一次性成本落在第一次调用上。
- CPU 频率受 governor 与 turbo 影响，从空闲频率升到稳态需要时间，短基准可能大部分时间处于升频过程。
- 预热轮次应使用与测量轮次相同的输入与调用路径，预热结果单独丢弃。
- 预热不能消除所有一次性成本，透明大页合并与后台回收仍可能在后续轮次发生。
- 预热不足会高估耗时，预热过长则浪费测试时间，应通过分段统计判断进入稳态的时刻。

### 1.5 预热应当持续多久，如何判断已经稳定？

- 按固定窗口统计每轮的均值或中位数，观察随轮次变化的曲线是否进入平台。
- 判据可以是连续若干窗口的中位数差异小于预设阈值，例如 2%。
- 同时观察 `cycles`、`cache-misses`、`branch-misses` 的比率是否稳定，不只看时间。
- CPU 频率是否达到目标可参考 `/proc/cpuinfo` 的 `cpu MHz` 或 `turbostat` 的输出，采样本身有开销。
- 冷启动成本高的服务型基准需要更长预热，纯计算微基准通常数百毫秒到数秒即可。
- 预热与测量应使用同一分布，不能用小输入预热再用大输入测量。
- 曲线始终不收敛说明存在外部干扰或状态累积，应先隔离环境，仅延长预热无法解决。

### 1.6（辨析）平均值、中位数与分位数分别回答什么问题？

- 平均值是总和除以次数，受长尾样本强烈影响，适合核算总资源消耗，不适合描述典型延迟。
- 中位数是第 50 百分位，对离群值不敏感，描述一次随机请求的典型体验。
- 分位数描述分布尾部，p99 表示 99% 的观测不超过该值，用于评估尾延迟与超时预算。
- 平均值低于 p99 是常态，平均值高于中位数说明分布右偏。
- 分位数不能直接相加或求平均，跨实例聚合需要合并直方图或保留原始样本。
- 样本量不足时高分位数不可靠，估计 p999 通常需要上万个样本，否则结果接近最大值。
- 报告应同时给出样本数、最小值、最大值与分布形状，避免只给一个数字。

| 指标 | 回答的问题 | 适用场景 | 局限 |
| --- | --- | --- | --- |
| 平均值 | 总耗时按次数摊薄 | 容量规划、资源核算 | 受长尾样本影响 |
| 中位数 | 典型请求的耗时 | 用户体验的常态描述 | 不反映尾部 |
| p99 | 绝大多数请求的上界 | SLO、超时预算 | 需要足够样本 |
| 最大值 | 观测到的最慢一次 | 故障复盘 | 受单次异常支配 |

### 1.7 尾延迟为什么用 p99 与 p999 描述？

- 尾延迟对应少量慢请求，但在扇出场景会被放大：一次页面请求调用上百个服务，任一慢调用拖慢整体。
- p99 与 p999 对应不同的超时与重试预算，p999 更接近最坏体验，但需要更多样本才能稳定估计。
- 尾延迟来源包括排队、锁竞争、缺页、内存回收、后台任务、网络重传与调度延迟。
- 平均值会隐藏尾延迟，SLO 通常按分位数定义，例如 p99 小于 10 ms。
- 高分位数对测量方法敏感，闭环压测会低估排队延迟，需要开环压测或按到达时间计算。
- 直方图桶的边界决定分位数精度，桶过粗会在 SLO 边界附近失真。
- 尾延迟优化常以牺牲吞吐或平均值为代价，报告需要同时给出两端。

### 1.8 如何设计一个可复现的微基准？

- 固定输入数据与随机种子，数据集大小覆盖缓存内与缓存外两种情形。
- 固定编译器版本、优化级别、目标架构与标准库版本，记录完整命令行。
- 关闭或固定频率策略，绑定 CPU，隔离同机其他负载；容器内确认 cpuset 与 CPU 配额。
- 使用交错 A/B 运行，避免温度与频率漂移系统性地偏向某一版本。
- 每个配置重复多轮，报告分布与置信区间，不只报告最好一轮。
- 基准应包含已知成本的对照组，用于发现环境异常。
- 纳入 CI 时设定噪声下限，小于该阈值的差异不作为回归。

### 1.9（实现）`DoNotOptimize` 阻止了哪些优化？

- 它来自 Google Benchmark，不是标准库设施；在 GCC 与 Clang 上用空的行内汇编把值约束到寄存器或内存，并声明 `"memory"` clobber。
- `"memory"` clobber 告诉编译器该点之后内存可能已改变，阻止编译器把内存访问跨越该点重排，或复用寄存器中的旧值。
- 它强制操作数被计算并物化，阻止计算结果因无人使用而被删除。
- 它不阻止循环不变的计算被提到循环外：输入不变时，计算仍可能只执行一次。
- 它不阻止编译器展开或向量化循环，迭代次数与数据依赖仍需自行控制。
- `benchmark::ClobberMemory()` 用于让挂起的写操作真正落地，二者常配合使用。
- 手写 `asm volatile("" : "+r"(x))` 可以达到类似效果，但可移植性与语义保证弱于库设施。

```cpp
for (int i = 0; i < n; ++i) {
    const auto y = f(data[i]);
    benchmark::DoNotOptimize(y);
}
```

### 1.10（陷阱）编译器把被测代码整体删除时如何发现？

- 现象是耗时接近空循环，且随输入规模增大几乎不变。
- 检查生成的汇编：用 `objdump -d` 或 Compiler Explorer 确认被测函数是否仍有调用或指令。
- 检查结果是否只写入随后不再读取的局部变量，或所有路径都未使用结果。
- 检查循环是否被强度削减为闭式结果，累加、求和与长度计算最容易被整体替换。
- 用 `volatile` 接收结果可以保底，但会引入存储开销并抑制向量化，改变被测代码。
- 用 `DoNotOptimize` 约束结果，并让输入依赖上一次输出，维持数据依赖。
- 对比 `-O0` 与 `-O2` 的耗时差异只能提供线索，不能证明代码被删除。

### 1.11 基准循环的迭代次数如何确定？

- 先做一次标定运行，估算单次成本，再选择使总时长落在数十毫秒到数秒的迭代次数。
- 迭代过少时计时器分辨率与启动成本占比过高，过多时受频率漂移与中断影响。
- 基准框架通常按时间预算自动调整迭代次数，并以批处理为单位计时。
- 迭代次数应写入报告，不同配置使用相同预算以便比较。
- 固定迭代次数适合比较算法复杂度，固定时间预算适合比较常数因子。
- 迭代之间存在状态累积时（例如容器增长），固定次数会改变每次迭代的工作量，需要在每轮前重置状态并计入重置成本。
- 结果按迭代次数归一化，同时保留总时间用于判断测量是否可靠。

### 1.12 为什么单次测量要重复多轮并交错执行？

- 机器状态随时间漂移：温度、频率、后台任务与内存碎片都会改变结果。
- 连续运行 A 再运行 B 会把漂移全部归因于版本差异，交错 A/B/A/B 可让漂移平摊到两者。
- 多轮重复可以估计方差，判断观测到的差异是否超过噪声。
- 轮次之间应重新随机化顺序或对称排列，避免缓存与预热顺序造成偏差。
- 报告应给出每轮的中位数与轮间离散程度，不只给合并后的一个数字。
- 若两个版本的差异小于轮间波动，需要增加轮次或改进测量方法，不能据此宣布结论。

### 1.13（场景）线上耗时分布与基准结果不一致，如何排查？

- 先确认两者测量同一段逻辑：线上可能包含排队、序列化、鉴权、网络与重试，基准只测核心函数。
- 检查输入分布：基准多用均匀或小规模数据，线上可能是长尾键、超大请求或高基数。
- 检查并发与资源竞争：线上共享缓存、连接池、锁与内存带宽，基准多为单线程独占。
- 检查运行环境：线上容器有 CPU 配额与 cpuset，可能与其他负载共享物理核，频率策略也不同。
- 检查观测方式：埋点计时有开销，采样可能只覆盖部分请求，时钟可能受 NTP 调整。
- 用回放流量在预发环境复现，逐步剥离差异，确认主导因素后再优化。
- 若差异来自排队，优化单次处理时间不一定改善端到端延迟，需要同时看利用率与队列长度。

### 1.14 频率调节与 CPU 迁移如何影响测量？

- CPU 频率随负载、温度与电源策略变化，短基准可能测到升频前的低频状态。
- Linux 的 `intel_pstate` 常见策略包括 `powersave` 与 `performance`，可用值由驱动与内核版本决定。
- 线程迁移会丢失私有缓存与 TLB 条目，也会改变 NUMA 距离，绑定 CPU 可减少这类方差。
- 同一物理核的两个超线程共享执行端口与缓存，绑核时应避开兄弟线程。
- 容器内的 CPU 配额会导致 throttling，`cpu.stat` 中的 `nr_throttled` 与 `throttled_usec` 可以确认。
- 测量前后读取频率与迁移计数，波动大时结果不可比。
- 固定频率会改变 turbo 行为，绝对值与生产环境不同，但版本间比较更稳定。

### 1.15（陷阱）测量本身的开销如何估算？

- 用空函数或空循环替换被测体，保留相同的计时与循环结构，得到基线开销。
- 两次 `now()` 调用的开销在常见平台上通常为数十纳秒量级，具体由时钟源与实现决定。
- 计时调用会污染缓存与分支预测器，被测代码越短，影响越大。
- 采样剖析器按固定频率中断，开销与采样频率、调用栈展开方式成正比。
- 日志与埋点的时间戳、字符串格式化与 I/O 开销可能超过被测逻辑。
- 硬件性能计数器在多路复用时会引入误差，需要查看启用比例。
- 报告应说明开销是否已扣除；未扣除时结论只适用于相对比较。

### 1.16 内存分配与缺页如何污染微基准？

- 首次分配触发 `brk` 或 `mmap`，缺页由内核处理，单次成本远高于后续复用。
- 分配器按尺寸分级，首次使用某个尺寸会初始化 arena 或缓存，后续分配走快速路径。
- 大块分配可能触发 `mmap` 与 `munmap`，每次调用都伴随页表操作与 TLB 失效。
- 释放后内存可能归还内核，下一次分配再次缺页；glibc 的 `MALLOC_TRIM_THRESHOLD_` 会改变归还行为。
- 透明大页的合并与拆分在后台异步发生，相邻轮次的缺页成本因此不同。
- 基准应在测量轮之前完成分配与触页，或把分配成本作为被测对象单独测量。
- 需要评估分配器本身时，固定请求尺寸分布与线程数，并报告常驻内存。

### 1.17（场景）性能回归从 5% 开始，CI 如何判定？

- 先测噪声：同一二进制重复运行多轮，得到轮间波动分布，判断 5% 是否落在噪声内。
- 设定最小可检测效应，小于该值的差异不触发告警，避免频繁误报。
- 使用与基线相同的机器、容器镜像、编译器与负载，基线随代码版本更新。
- 交错运行基线与候选，按轮次比较，不比较历史绝对值。
- 用非参数检验或置信区间判断差异是否显著，同时报告效应大小。
- 回归告警应附剖析数据或火焰图，便于区分代码变化与环境漂移。
- 对尾延迟单独设阈值，平均值不变而 p99 恶化同样是回归。

### 1.18 基准测试的输入数据如何选择？

- 覆盖典型值与长尾值：小键、大键、空值、重复值、随机值分别影响分支与缓存行为。
- 数据规模跨越缓存层级：小于 L1、接近 L2、超过 LLC、超过内存容量。
- 分布固定并可复现，随机数生成器的种子与算法写入报告。
- 避免全零或高度规则的数据，它会触发特殊路径，例如全零页与易学的分支模式。
- 输入的对齐与地址布局影响缓存组冲突与伪共享，必要时用多组偏移重复。
- 线上流量回放比合成数据更接近真实，但要处理隐私字段并控制回放速率。
- 报告应说明输入分布，否则结果无法外推。

### 1.19（条款）`std::chrono::steady_clock` 的时钟特性由什么规定？

- 标准规定 `steady_clock` 的 `time_point` 值不随时间减小，并以相对真实时间的稳定速率前进，见 `[time.clock.steady]`。
- 它的 `is_steady` 为 `true`，`now()` 返回 `time_point`，`duration` 的具体类型由实现定义。
- 标准不规定时钟源、分辨率与纪元，只规定单调性与稳定性，因此不同平台的原点不可比较。
- 标准不保证 `steady_clock` 与 `system_clock` 之间存在固定偏移。
- `high_resolution_clock` 可以是两者的别名，标准允许；需要稳定时钟时应显式使用 `steady_clock`。
- 单调性针对单次进程运行中的读数，跨重启或跨机器的比较没有意义。
- 需要可序列化的绝对时间时使用 `system_clock`，并接受它可能跳变。

### 1.20 发布前基准通过、上线后变慢，复盘应检查什么？

- 二进制与配置是否一致：优化级别、LTO 与 PGO 剖面、目标架构、标准库版本、编译宏。
- 运行环境是否一致：CPU 型号与代际、频率策略、NUMA 绑定、容器配额、邻居负载。
- 输入是否一致：请求分布、并发度、连接复用、缓存命中率与数据规模。
- 依赖是否变化：动态库版本、内核版本、DNS 与下游服务延迟。
- 观测是否一致：埋点位置、采样率、时钟源与统计口径。
- 变更是否包含布局效应：函数顺序、inline 决策与代码对齐改变可能带来几个百分点的差异。
- 复盘应保留发布前后的剖析数据与二进制哈希，否则只能推测。

## 2. CPU 微架构与流水线

### 2.1 一条指令从取指到退休经历哪些阶段？

- 前端按程序计数器取指，指令缓存提供指令字节，uop 缓存（Intel 称 DSB）提供已解码的微操作。
- 解码器把变长的 x86 指令切分为微操作，复杂指令可能拆成多个 uop，并受解码宽度限制。
- 重命名阶段把架构寄存器映射到物理寄存器，消除写后写与读后写造成的假依赖。
- 调度器在操作数就绪后把 uop 分派到执行端口，乱序执行；结果写回物理寄存器并唤醒等待者。
- 退休单元按程序顺序提交结果，保证异常与中断的精确性，并释放旧物理寄存器。
- 任一级阻塞都会限制 IPC：前端供给不足、端口冲突、依赖链过长或分支预测失败。
- 各阶段宽度与缓冲深度由微架构决定，不同代际差异明显。

### 2.2（辨析）流水线深度增加带来什么收益与代价？

- 更深的流水线把每条指令的工作拆得更细，单级逻辑更短，理论主频可以提高。
- 分支预测失败的惩罚随深度增加：需要清空更多在途指令，恢复时间更长。
- 深流水线需要更多流水寄存器和时钟树，功耗与面积上升。
- 现代高性能核的流水线深度通常在十几级到二十级量级，具体由微架构决定。
- 流水线加深不提升 IPC，IPC 取决于并行度与阻塞，收益来自主频。
- 在分支密集或依赖链长的代码上，深流水线的实际收益可能被惩罚抵消。
- 取舍取决于目标负载，吞吐型服务与延迟敏感负载对深度的容忍度不同。

### 2.3 数据冒险与转发如何影响 IPC？

- 写后读冒险发生在后一条指令需要前一条的结果时，转发把结果从执行单元直接送到消费者，避免写回后再读。
- 转发有延迟，算术结果通常需要一到数个周期才能被消费，加载结果更久。
- 加载后立即使用通常无法完全转发，需要插入停顿，代价约数个周期。
- 编译器可以通过指令调度拉开距离，但受寄存器压力与指令可移动性限制。
- 乱序执行能在窗口内寻找独立指令填补停顿，窗口耗尽时仍会阻塞。
- 依赖链长度决定吞吐下限，每周期只能推进链上一条指令，增加发射宽度无帮助。
- 减少依赖链的手段包括拆分累加器、改变结合顺序与预先计算，浮点运算需注意语义。

### 2.4（陷阱）CPI 小于 1 是否说明程序高效？

- CPI 是每指令周期数，小于 1 表示每周期退休多于一条指令，这是超标量执行的正常结果。
- 它不表示程序高效，只表示该区间内指令级并行度较高。
- 向量化会减少指令数，每条指令完成更多工作，CPI 与工作量的关系更弱。
- 自旋等待可以 CPI 很低但没有任何有效产出。
- 比较不同指令集或不同编译器版本的 CPI 意义有限，指令数本身已经改变。
- 更有用的指标是每工作单元的周期数、IPC 与前端/后端受限比例的组合。
- 计数器通常只统计未停机周期，睡眠与阻塞不进入分母，需结合墙钟时间解读。

### 2.5 乱序执行如何隐藏延迟？

- 处理器在窗口内动态调度指令，先执行操作数就绪的指令，把长延迟操作与独立工作重叠。
- 重命名消除假依赖，使不同指令可以复用架构寄存器而不互相等待。
- 保留站保存等待中的 uop，操作数就绪后唤醒并分派到执行端口。
- 乱序窗口有限，超出窗口的指令无法提前执行，窗口大小由微架构决定。
- 内存依赖预测允许加载越过更早的存储，预测失败时需要回滚并重放。
- 乱序执行不改变程序语义，异常与提交仍按程序顺序处理。
- 依赖链与窗口共同决定可提取的并行度，单纯增加发射宽度对长依赖链无效。

### 2.6 重排序缓冲区与保留站的作用是什么？

- 重排序缓冲区按程序顺序记录在途指令，负责退休、异常处理与物理寄存器回收。
- 保留站按操作数就绪情况调度，容量决定能同时等待的 uop 数量。
- 重排序缓冲区满时前端停止取指与解码，形成背压，这是后端受限的典型表现。
- 保留站满时调度器无法接收新 uop，同样造成停顿。
- 物理寄存器文件的大小限制重命名深度，寄存器耗尽会阻塞前端。
- 分支预测失败时需要清除错误路径的条目，清除范围与缓冲区占用相关。
- 缓冲区容量是微架构参数，代码优化应针对实际平台测量，不能照搬某代产品的数值。

### 2.7（实现）分支预测失败为什么要清空流水线？

- 取指阶段在分支解析前就按预测方向继续取指，错误路径上的指令已经进入流水线。
- 这些指令可能修改重命名表或读取寄存器，必须撤销其架构可见影响。
- 前端停止取指，按正确目标重新取指，正确路径的指令重新经过解码与重命名。
- 已进入重排序缓冲区的错误路径条目被标记并清除，物理寄存器映射回滚到分支点。
- 惩罚取决于流水线深度、前端重启延迟与正确路径是否在缓存中，通常在十几到二十几个周期。
- 失败率不高但分支密集时，累计惩罚仍然显著，紧循环内的分支尤其明显。
- 无分支实现可以消除惩罚，但条件传送可能引入依赖，查表可能增加访存，需要权衡。

### 2.8 分支预测器如何学习循环与模式？

- 两位饱和计数器根据历史结果在强弱状态之间迁移，能容忍偶发的反向分支。
- 全局历史寄存器记录最近分支的方向，索引模式历史表，可识别重复的方向序列。
- TAGE 一类预测器使用不同长度的历史与多个表，选择置信度最高的预测。
- 循环预测器识别固定次数的循环，在最后一次迭代预测退出，避免每次误判。
- 间接分支由分支目标缓冲区提供地址，历史相关的间接预测器可以处理多目标调用。
- 返回地址栈预测函数返回，递归深度超过栈容量时预测失败。
- 预测器容量有限，多个分支映射到同一条目时会互相干扰，形成别名。

### 2.9（场景）分支预测失败率 2% 为何仍然昂贵？

- 失败率的分母是分支指令数；按指令总数理解会低估失败的影响，分支密集代码中 2% 仍可能对应大量失败。
- 每次失败的惩罚是十几到二十几个周期，若分支每几十条指令出现一次，摊销后占比可观。
- `branch-misses` 需要与 `branches`、`cycles` 一起看，换算成每千条指令的失败数。
- 失败集中在少数难以预测的分支上，例如数据相关的比较、哈希表探测与协议解析。
- 失败会阻塞前端并清空窗口，乱序执行无法跨过错误路径继续。
- 数据分布变化会让原本可预测的分支变成随机，压测数据与线上数据不同会掩盖问题。
- 优化方向是消除分支或改用无分支计算，是否有效需用计数器验证。

### 2.10 指令缓存如何影响性能？

- 指令缓存按缓存行取指，容量通常为 32 KiB 到 64 KiB 量级，具体由微架构决定。
- uop 缓存保存已解码的微操作，命中时绕过解码，容量以微操作条数计。
- 代码体积增大导致指令缓存与 uop 缓存缺失，前端供给不足，表现为前端受限比例上升。
- 热路径被冷代码分隔会增加取指行数与 TLB 压力，函数布局影响实际占用。
- 循环展开与 inline 能减少分支但增大代码体积，收益取决于热路径是否仍在缓存容量内。
- 指令缓存缺失的代价取决于下一级缓存与内存延迟，可能达到数十周期。
- 分析可结合指令缓存缺失事件与 `llvm-mca` 的代码体积估算。

### 2.11（陷阱）代码体积增大为什么反而变快？

- 循环展开减少了分支与循环控制开销，提高了每周期退休的指令数。
- inline 消除调用开销，并使常量传播与跨函数优化成为可能。
- 更大的代码可能让热路径获得更好的对齐，减少跨缓存行取指。
- 若热路径仍能放入 uop 缓存，体积增大的负面影响有限。
- 展开与 inline 的收益在分支可预测性差或调用频繁时更明显。
- 当热路径超出缓存容量，体积增大会导致前端缺失，性能下降。
- 结论依赖具体代码与微架构，应以计数器确认前端缺失是否变化。

### 2.12 端口压力如何限制吞吐？

- 每个执行端口支持一组操作类型，整数 ALU、加载、存储、分支与向量单元分布在不同端口。
- 发射宽度是每周期可分派的 uop 上限，端口数量与类型决定持续吞吐。
- 多条同类指令集中到少数端口时形成瓶颈，即使其他端口空闲也无法提升。
- 加载与存储端口通常少于 ALU 端口，访存密集代码更容易受端口限制。
- 端口压力可用性能计数器观察，事件名与可用性随微架构变化。
- `llvm-mca` 可以静态估算吞吐与端口占用，适合比较不同写法的指令组合。
- 减少端口压力的手段包括合并访存、使用向量指令与调整指令混合，向量单元本身也占用特定端口。

### 2.13 如何判断瓶颈是前端还是后端？

- 前端受限表现为取指、解码或 uop 缓存供给不足，IDQ 未能向重命名阶段交付 uop 的周期比例升高。
- 后端受限表现为执行端口饱和或等待操作数，分派的 uop 数与端口计数接近上限。
- 退役受限表示流水线充分利用，此时提升 IPC 需要减少指令数或改用更宽的指令。
- 错误推测表示分支预测失败或内存消歧失败浪费了槽位。
- Top-down 方法把周期划分为 retiring、bad speculation、frontend bound、backend bound 四类。
- `perf stat --topdown` 与 `toplev` 可以给出分类比例，支持情况随 CPU 与内核版本变化。
- 单看 IPC 无法区分前端与后端，必须结合事件比率与代码特征；两类问题的优化方向不同。

### 2.14（实现）依赖链为什么限制乱序执行？

- 乱序执行只能重排独立指令，同一数据依赖链上的指令必须按顺序完成。
- 若链上每条指令延迟为 4 周期，则无论发射宽度多大，每 4 周期只能推进一条。
- 加载与使用之间的延迟更高，缓存缺失时可达数百周期，窗口很快被填满。
- 增加独立累加器或把归约拆成多路可以缩短关键路径。
- 浮点加法不满足结合律，改变求和顺序会改变结果，编译器默认不会重排。
- 依赖链也可能来自寄存器复用、标志寄存器与内存别名，需要查看汇编确认。
- 关键路径分析应结合 `llvm-mca` 的依赖图与实测周期数，不能只看源代码。

```cpp
float sum4(const float* a, int n) {
    float s0 = 0, s1 = 0, s2 = 0, s3 = 0;
    for (int i = 0; i + 3 < n; i += 4) {
        s0 += a[i]; s1 += a[i + 1];
        s2 += a[i + 2]; s3 += a[i + 3];
    }
    return (s0 + s1) + (s2 + s3);  // 省略尾部；求和顺序改变，浮点结果可能不同
}
```

### 2.15 存储转发与 4K 别名是什么？

- 存储转发让后续加载直接从尚未提交的存储缓冲区取值，避免等待写回缓存。
- 加载与存储地址完全一致且宽度对齐时转发最快，部分重叠或跨缓存行时可能转发失败。
- 转发失败需要等待存储提交，惩罚约为十几个周期，具体由微架构决定。
- 4K 别名指加载地址与较早存储地址的低 12 位相同但实际不同，硬件误判为可能相关而延迟加载。
- 内存消歧预测器会学习这种模式，预测失败时回滚重放。
- 避免手段包括调整数据结构布局与分配对齐，减少同页内的地址碰撞。
- 这类问题难以从源码看出，需要性能计数器与微基准定位。

### 2.16 同一函数在不同调用点性能不同，原因有哪些？

- 调用点的分支历史不同，同一函数内的分支在不同上下文中的可预测性不同。
- inline 决策不同：一个调用点被 inline 后能做常量传播，另一个仍是真实调用。
- 数据局部性不同：不同调用点传入的数据位于不同缓存层级或不同 NUMA 节点。
- 代码对齐与缓存占用不同：函数被放置的位置影响取指与指令缓存组冲突。
- 调用点所在的循环结构不同，乱序窗口能重叠的独立工作不同。
- 多态调用点的类型分布不同，间接分支预测的成功率不同。
- 分析时应按调用点分别采样，火焰图合并同名函数会掩盖差异。

### 2.17 SIMD 指令为什么不一定提升吞吐？

- 若瓶颈在内存带宽或延迟，计算单元再宽也无法加快数据供给。
- 向量化需要数据连续且对齐，收集与散射、解包与重排会引入额外指令。
- 向量指令的吞吐取决于执行端口与向量单元宽度，某些操作需要多个周期。
- 部分处理器上宽向量指令可能触发频率下降，具体行为由处理器与电源策略决定。
- 数据依赖链在向量化后仍然存在，水平归约会把并行度重新串行化。
- 尾部处理与边界检查可能抵消主体循环的收益，小规模数据尤其明显。
- 是否有效应以每元素周期数与内存流量衡量，不能只看是否生成了向量指令。

### 2.18（场景）同一程序在性能核与能效核上表现不同，如何解释？

- 性能核与能效核的发射宽度、缓存容量、频率范围与支持的指令集不同，同一二进制在每个核上的 IPC 与延迟不同。
- 能效核通常不支持某些宽向量扩展，依赖这些指令的线程被调度到能效核时会退化或迁移。
- 线程迁移会丢失私有缓存与分支预测器状态，跨核迁移的代价高于同核内切换。
- 操作系统的调度器根据负载类型与能耗策略决定放置，绑定策略会覆盖默认行为。
- 共享 LLC 的争用与内存带宽在不同核簇之间不对称，NUMA 距离也可能不同。
- 用固定线程数与绑核做 A/B，对比每核的吞吐与尾延迟，才能判断是否需要按核类型分流。
- 把延迟敏感线程绑定到性能核、把后台任务放到能效核是常见做法，代价是资源利用率下降。

### 2.19 线上服务 CPU 利用率下降但延迟上升，如何分析？

- 利用率下降可能来自频率降低、CPU 配额 throttling 或线程被阻塞，需要先确认 CPU 时间去了哪里。
- 检查 `cpu.stat` 的 throttling 计数与 `steal` 时间，虚拟化环境下宿主机争抢会表现为 steal。
- 检查锁竞争与 futex 等待：线程睡眠时利用率下降，请求排队导致延迟上升。
- 检查内存带宽与 LLC 争用：计算单元空闲但访存排队，利用率与延迟同时恶化。
- 检查下游依赖与重试：等待远端响应时本机 CPU 空闲，延迟由外部服务决定。
- 检查频率与温度：散热受限时频率下降，完成同样工作的时间变长。
- 结合 off-CPU 分析与分布式追踪区分本机阻塞与外部等待。

### 2.20（条款）C++ 抽象机与硬件执行之间是什么关系？

- 标准定义抽象机的可观察行为，编译器可以在不改变可观察行为的前提下做任意变换，见 `[intro.abstract]`。
- 执行时间、指令数与缓存行为不属于可观察行为，标准不规定性能。
- 数据竞争与越界访问属于未定义行为，优化可以基于「不会发生」的假设，结果可能与源码直觉不同。
- `volatile` 只保证对它的访问按抽象机规则执行，不提供原子性或内存序。
- 原子操作与内存序规定跨线程可见性，具体性能仍由硬件与实现决定。
- 性能优化不能依赖标准保证的时序，只能依赖具体实现与测量。
- 需要可移植的性能保证时，应使用标准库的复杂度要求与分析工具，不能假设指令级行为。

## 3. 缓存与内存层次

### 3.1 缓存层次如何影响访问延迟？

- 寄存器访问在指令内完成，L1 命中通常为 4 到 5 周期，L2 为十几周期，L3 为数十周期，内存为数百周期，具体数值由微架构决定。
- L1 通常分为指令缓存与数据缓存，容量为数十 KiB；L2 为单核私有，容量数百 KiB 到数 MiB；L3 为多核共享，容量数十 MiB。
- 缓存与下一级之间按缓存行传输，缺失时整行填入，空间局部性因此重要。
- 容量与关联度决定能保留多少工作集，工作集超过 LLC 后每次访问都可能到内存。
- 多核共享 LLC 时，核间争用会降低有效容量，表现为命中率下降而代码未变。
- 延迟与带宽是两个维度，随机访问受延迟限制，顺序流式访问受带宽限制。
- 优化顺序通常是先把热数据放进缓存，再减少访存次数，最后提高访存并行度。

| 层级 | 典型延迟 | 典型容量 | 可见范围 |
| --- | --- | --- | --- |
| L1 | 4 到 5 周期 | 数十 KiB | 单核私有 |
| L2 | 十几周期 | 数百 KiB 到数 MiB | 单核私有 |
| L3 | 数十周期 | 数十 MiB | 多核共享 |
| 内存 | 数百周期 | 系统容量 | 全系统 |

### 3.2 缓存行为什么按 64 字节组织？

- 缓存行是缓存与下一级之间传输的最小单位，行大小由微架构决定，x86-64 常见为 64 字节。
- 较大的行提高空间局部性收益，但会放大不必要的数据传输与冲突。
- 行大小与一致性协议的单位一致，伪共享因此以行为粒度发生。
- 硬件预取以行为单位抓取相邻数据，顺序访问能利用整行。
- 行大小不是 C++ 标准规定的内容，`std::hardware_destructive_interference_size` 由实现定义。
- 编写可移植代码时不应假定 64 字节，应使用实现提供的常量或运行时探测。
- 缓存行对齐影响结构体布局与分配器行为，跨行访问会增加一次缓存访问。

### 3.3（陷阱）顺序访问一定比随机访问快吗？

- 顺序访问通常能利用预取与整行传输，随机访问每次都可能缺失，差距可达一个数量级以上。
- 顺序写会触发写分配与读改写流量，带宽利用率不一定高于随机写。
- 数据全部在缓存内时，顺序与随机的差距缩小，随机访问的地址计算开销可能占主导。
- 多线程顺序访问同一缓存行会产生一致性流量，分散访问反而可能减少争用。
- 预取器对顺序模式最有效，对随机模式无效，还可能因预取而污染缓存。
- 顺序访问的收益取决于工作集大小与预取距离，超过内存带宽后增加顺序性无帮助。
- 结论应以缓存缺失率与带宽计数验证，不能仅凭访问模式判断。

### 3.4 关联度与冲突缺失如何产生？

- 组相联缓存把地址映射到固定组，组内行数即关联度；映射到同一组的多个热门地址会互相逐出。
- 直接映射缓存关联度为 1，冲突最严重；全相联没有冲突但硬件成本高。
- 冲突缺失发生在工作集小于缓存容量但地址映射集中时，增加容量未必解决。
- 以 2 的幂为步长的访问容易落在同一组，例如按 4 KiB 跨步遍历二维数组。
- 缓解手段包括调整数据布局、填充使热点分散、改变遍历顺序。
- 硬件用替换策略与哈希减少冲突，具体策略由实现定义。
- 分析冲突需要看每级缓存的缺失率与地址分布，总缺失率无法区分容量与冲突。

### 3.5（实现）如何用 `alignas` 消除伪共享？

- 把高频写的变量放进独立结构体，并用 `alignas` 指定与缓存行一致的对齐。
- 对齐只保证起始地址对齐，若结构体大于缓存行或与其他数据相邻，仍可能共享行。
- 更稳妥的做法是让结构体大小也为缓存行大小，或加入填充数组。
- `std::hardware_destructive_interference_size` 在 C++17 提供，值由实现定义，可替代硬编码的 64。
- 对动态分配的对象，C++17 的过对齐分配会满足 `alignas` 要求，自定义分配器需要自行保证。
- 消除伪共享会增加内存占用与缓存行浪费，只对高频写字段值得。
- 修改后应以一致性流量计数验证收益，不能只看变量地址是否不同。

```cpp
struct alignas(64) Counter {
    std::atomic<long> value{0};
};
Counter a, b;  // 各占一个缓存行
```

### 3.6（场景）两个线程各写各的计数器，为什么吞吐骤降？

- 两个计数器落在同一缓存行，任一写都需要取得该行的独占权，另一核的副本随之失效。
- 每次写都触发缓存行在核间来回迁移，跨核互连成为瓶颈。
- 这种伪共享不影响正确性，只表现为扩展性差：线程数增加，吞吐不增反降。
- 定位时在支持的平台上用 `perf c2c` 查看 HITM 次数与冲突地址。
- 解决方式是把计数器分到不同缓存行，或改为每线程本地累加、定期汇总。
- 只读共享不会产生伪共享，多个核可以同时持有共享状态的副本。
- 伪共享的代价与写频率成正比，低频写即使共享一行也可能无关紧要。

### 3.7 硬件预取器识别哪些模式？

- 顺序预取器跟踪连续地址的访问，按固定步长提前抓取后续缓存行。
- 步长预取器识别固定跨步模式，例如按固定字节间隔遍历数组。
- 流预取器处理多个并发流，容量有限，流数量超过能力时预取失效。
- 预取通常只覆盖同一 4 KiB 页内，跨页需要软件预取或依赖页表预取。
- 预取器不跨越不可预测的间接访问，链表与哈希探测难以受益。
- 预取过早会污染缓存，过晚无法隐藏延迟，距离由硬件启发式决定。
- 预取对带宽敏感，内存带宽饱和时预取会增加无效流量。

### 3.8（陷阱）显式预取为什么有时没有收益？

- `__builtin_prefetch` 只是提示，硬件可以忽略；地址未映射时不会触发异常，但也没有数据。
- 预取距离难以确定：太近无法隐藏延迟，太远会逐出仍在使用的数据。
- 预取本身占用加载端口与带宽，密集预取会与真实加载竞争。
- 若访问模式已被硬件预取器覆盖，软件预取是重复工作。
- 预取不解决依赖链，必须能在预取完成前找到独立工作。
- 预取到 L1 还是 L2 影响收益，`locality` 参数的语义由实现定义。
- 应在缺失率与带宽计数确认瓶颈是延迟后再尝试，并用 A/B 验证。

### 3.9 TLB 是什么，页表遍历的代价有多大？

- TLB 缓存虚拟页到物理页的映射，命中时地址转换在一个周期内完成。
- 缺失时需遍历多级页表，x86-64 通常为 4 级或 5 级，每次遍历可能多次访存。
- 页表项本身也经过缓存，命中缓存时遍历较快，全部缺失时可达数十到上百周期。
- L1 数据 TLB 通常有数十到上百项，L2 TLB 有数千项，具体由微架构决定。
- 大工作集与随机访问会快速耗尽 TLB，表现为 `dTLB-load-misses` 升高。
- 页表遍历由硬件完成，部分处理器有页表遍历缓存，行为由实现定义。
- 减少 TLB 压力的手段包括大页、提高局部性、减少工作集与使用连续内存。

### 3.10 大页如何减少 TLB 缺失？

- 4 KiB 页下，覆盖 1 GiB 需要 26 万个页表项；2 MiB 大页只需 512 个，1 GiB 大页只需 1 个。
- 同样的 TLB 项数可以覆盖更大的地址范围，随机访问的 TLB 命中率上升。
- Linux 的透明大页在 `madvise` 或 `always` 模式下自动合并，`khugepaged` 后台扫描。
- 显式大页通过 `mmap` 的 `MAP_HUGETLB` 或 hugetlbfs 预留，需要预先配置页池。
- 大页会增加内部碎片，分配与回收粒度变大，内存紧张时更难获得。
- 透明大页的合并与拆分会造成延迟抖动，延迟敏感服务通常设为 `madvise` 并显式管理。
- 大页不减少缓存缺失，只减少地址转换开销，对缓存内工作集无明显收益。

### 3.11 内存带宽打满时增加线程为什么更慢？

- 多线程争用同一内存控制器与互连，队列变长，单次访问延迟上升。
- 缓存一致性流量随核数增加，写共享数据会放大带宽消耗。
- 超线程共享执行单元与缓存，增加逻辑核不一定增加访存并行度。
- 预取与乱序执行在带宽饱和时无法隐藏延迟，只会增加在途请求。
- 表现为核数增加而吞吐持平或下降，内存带宽计数接近峰值。
- 解决方向是减少访存、提高数据复用、使用非临时存储或调整线程数与亲和性。
- 评估应看每字节成本与带宽利用率，不能只看 CPU 利用率。

### 3.12 NUMA 下首次触页与迁移如何影响延迟？

- 首次触页把物理页分配到触发缺页的 CPU 所在节点，之后线程迁移会使访问变为远端。
- 远端访问延迟通常比本地高数十个百分点，带宽也受互连限制，具体比例由平台决定。
- 页迁移可以把页搬到本地，但迁移本身有复制成本，频繁迁移会抖动。
- 线程绑核与内存绑定应一致，否则绑核反而固定了远端访问。
- `numactl --membind`、`mbind` 与 `set_mempolicy` 可以指定内存策略。
- 多线程首次触页的并行初始化会把页分散到多个节点，需按线程归属分配。
- 容器内 NUMA 拓扑可能被隐藏，需要读取 cgroup 与 `lscpu` 的实际视图。

### 3.13 如何检测跨节点访问？

- `numastat` 按节点统计命中与缺失，`numastat -p PID` 可以查看进程分布。
- `perf stat` 的 `node-load-misses`、`node-loads` 一类事件在部分平台可用，支持由实现决定。
- `/sys/devices/system/node/node*/meminfo` 提供各节点内存使用量。
- 在代码中可用 `getcpu` 或 `sched_getcpu` 记录当前 CPU，再映射到节点。
- 微基准可以对比本地分配与远端分配下的延迟，确认差异量级。
- 跨节点访问不一定表现为高延迟，带宽争用与一致性流量也可能拖慢。
- 检测应结合拓扑、绑定策略与实际延迟，不能只看一个计数。

### 3.14（辨析）缓存缺失与 TLB 缺失如何区分？

- 两者症状相似，但计数器不同：缓存缺失看 `cache-misses`、`LLC-load-misses`，地址转换看 `dTLB-load-misses`。
- 用大页做 A/B：访问模式不变而大页显著改善，说明 TLB 是主要因素。
- 固定随机访问并缩放工作集：TLB 缺失随页数增长，缓存缺失随字节数增长。
- 页表遍历本身也要访存，缓存缺失会放大 TLB 缺失的代价，两者可能叠加。
- `perf mem` 可按地址采样数据源，区分命中层级与内存访问。
- 指针追逐微基准可以单独测缓存延迟，再用大页对照测页表遍历开销。
- 归因错误会导致优化方向错误，例如对缓存友好但 TLB 不友好的大数据结构继续调布局。

### 3.15 多个线程只读共享数据为什么仍可能变慢？

- 只读共享的缓存行可以在各核的 L1 中同时处于共享状态，读不会使其他副本失效。
- 每个核仍需从 LLC 或内存取行，首次访问与容量缺失的流量随核数增加。
- 若工作集超过 LLC，多个核重复读取同一数据会消耗内存带宽，扩展性受带宽限制。
- 伪共享只在至少一个写者时发生，只读共享的扩展性问题来自容量与带宽。
- 读取的共享计数器若被频繁写，则回到伪共享；只读快照不受影响。
- 把数据复制到每线程本地可以减少争用，代价是内存占用与同步更新。
- 判断依据是一致性流量计数与带宽利用率，不能只看缓存行地址。

### 3.16 非临时存储适合什么场景？

- 非临时存储提示数据不会被立即重用，绕过缓存或使用写合并缓冲区。
- 它避免写分配带来的读流量，适合大块顺序写与一次性输出。
- 需要 16 或 32 字节对齐，部分平台要求完整的缓存行写入才能合并。
- 与后续读取混合时会强制从内存取回，反而变慢。
- 非临时存储在 C++ 标准中没有对应设施，属于编译器内建或平台 intrinsic。
- 写合并缓冲区容量有限，写入速率过高会退化为普通存储。
- 使用后通常需要 `sfence` 保证非临时存储对其他代理的可见顺序。

### 3.17（场景）结构体从 32 字节增到 72 字节后性能下降，如何分析？

- 72 字节跨越两个缓存行，数组元素访问会触及两行，缓存行利用率下降。
- 若结构体数组按字段遍历，跨度增大导致每次加载只用一小部分，浪费带宽。
- 对齐到 64 的倍数会把每个元素放大到 128 字节，进一步增加内存占用。
- 拆分热字段与冷字段可以恢复密度，把常用字段放入紧凑数组。
- 检查 `sizeof`、`alignof` 与字段偏移，确认填充来自哪里。
- 用缓存缺失计数与 `perf mem` 采样确认瓶颈是否在数据加载。
- 结论取决于访问模式，若只访问一个字段，密度比结构体总大小更重要。

### 3.18（实现）如何用微基准测量各级缓存的延迟？

- 用指针追逐构造串行依赖链，每个节点指向下一个节点，削弱乱序与预取的重叠。
- 改变工作集大小，从小于 L1 到超过 LLC，记录每次访问的平均周期数。
- 在曲线上识别平台段，平台之间的跃迁对应缓存层级边界。
- 减去循环控制与地址计算开销，可用空循环或固定地址访问作为基线。
- 指针追逐的节点应分散到不同缓存组，避免冲突缺失干扰层级判断。
- 用大页重复实验，若延迟曲线变化，说明部分开销来自 TLB 而非缓存。
- 单线程测延迟，多线程测带宽，两者不能互相替代。

### 3.19 发布后 p99 抖动，怀疑 NUMA 或透明大页，如何验证？

- 先确认抖动是周期性还是随机：周期性指向 `khugepaged`、日志刷盘与定时任务，随机指向远端访问或内存回收。
- 检查 `numastat` 与线程亲和性，确认线程与内存是否位于同一节点。
- 检查透明大页状态：`/sys/kernel/mm/transparent_hugepage/enabled` 与 `defrag`，并查看 `/proc/vmstat` 的 `compact_stall` 计数。
- 内存回收的直接回收会引入毫秒级停顿，查看 `/proc/vmstat` 的 `allocstall`。
- 容器 CPU 配额 throttling 会造成周期性延迟尖峰，查看 `cpu.stat`。
- 用同一请求在不同节点绑定下对比分布，验证 NUMA 假设。
- 若抖动来自大页合并或回收，固定页策略或预触页可能比改代码更有效。

### 3.20（条款）C++ 标准对缓存行与数据竞争分别规定了什么？

- 标准不规定缓存行大小、缓存层次或访存延迟，性能不属于可观察行为。
- C++17 在 `<new>` 中提供 `std::hardware_destructive_interference_size` 与 `hardware_constructive_interference_size`，值由实现定义。
- 这两个常量只是估计值，不保证等于实际缓存行，也不保证跨平台一致。
- 数据竞争的定义基于冲突访问：两个求值中一个写同一内存位置，另一个读或写，见 `[intro.races]/2`。
- 数据竞争导致未定义行为，编译器可以假定其不发生，不能用普通变量替代同步。
- 标准库容器的并发访问规则见 `[container.requirements.dataraces]`，不涉及缓存布局。
- 跨线程通信应使用原子或同步设施，缓存一致性不提供语言级可见性保证。

## 4. 分支预测与代码布局

### 4.1 `[[likely]]` 与 `[[unlikely]]` 改变了什么？

- 它们是 C++20 的标准属性，用于提示某个分支被执行的可能性显著高于或低于其他分支，见 `[dcl.attr.likelihood]`。
- 属性只影响代码生成，不改变程序语义；错误标注不会导致错误结果。
- 编译器可据此调整基本块顺序、分支方向与 inline 决策，把冷路径移出热路径。
- 在 x86 上，静态预测通常把前向分支预测为不跳转，布局优化可以让热路径成为直落路径。
- 属性对动态分支预测器没有直接控制作用，现代处理器主要依赖运行时历史。
- 标注错误会把热代码放到远端，增加取指跳转与指令缓存压力，可能造成性能下降。
- 收益依赖编译器版本与优化级别，应以生成的汇编与基准验证。

```cpp
if (ptr != nullptr) [[likely]] {
    return *ptr;
}
return fallback();
```

### 4.2（陷阱）`[[likely]]` 标注错误会怎样？

- 语义上无害，程序结果不变；性能上可能变差，因为热路径被移出直落路径。
- 错误标注会误导 inline 决策，让编译器把冷函数 inline 进热路径，增大代码体积。
- 同一分支上的多个标注或与 PGO 冲突时，最终布局由编译器决定。
- 对不可预测的分支，标注方向无法改变运行时预测失败率，收益接近于零。
- 若剖面上该分支接近 50/50，任何静态提示都只会让一半情况受损。
- 应先用性能计数器确认该分支的失败率与占比，再决定是否标注。
- 有 PGO 剖面时，实测概率通常优先于源码提示。

### 4.3（辨析）`__builtin_expect` 与 `[[likely]]` 有何差别？

- `__builtin_expect(expr, 1)` 是 GCC 与 Clang 的内建函数，返回 `expr` 的值并把期望值作为提示。
- `[[likely]]` 是标准属性，可以标注语句或 `if` 的分支，语义更明确。
- 两者都只提供静态概率提示，不保证布局结果。
- `__builtin_expect` 可用于任意表达式，属性只能出现在语法允许的位置。
- C++20 之前没有标准属性，跨编译器代码通常用宏封装两者。
- 某些编译器对属性的处理更保守，实际效果需要查看汇编。
- 两者都不应替代 PGO，静态提示的精度远低于实测剖面。

### 4.4 分支布局如何影响前端取指？

- 前端按缓存行与取指块抓取指令，分支目标与顺序路径的排列影响取指行数。
- 热路径连续放置时，取指可以顺序进行，减少跳转与缓存行切换。
- 冷路径穿插在热路径之间会造成取指空洞，增加指令缓存占用与 TLB 压力。
- inline 后基本块可能重排，`-freorder-blocks` 一类优化在 `-O2` 及以上默认开启。
- 分支目标对齐到取指块边界可以减少跨行取指，过度对齐会浪费空间。
- 布局收益在紧循环与小型热点函数上最明显，大函数受影响较小。
- 分析用 `objdump -d` 查看基本块顺序，用性能计数器看前端缺失。

### 4.5（实现）热冷分离如何减少指令缓存压力？

- 把错误处理、日志与罕见分支抽出为独立函数，函数用 `__attribute__((cold))` 标记，调用点的分支用 `[[unlikely]]` 标注。
- 热函数只保留成功路径，代码体积缩小，更容易放入指令缓存与 uop 缓存。
- 冷函数放到单独的段（例如 `.text.unlikely`），链接器可以把它们排到远处，减少热路径的行占用。
- 拆分后调用边界增加一次跳转与栈帧开销，只对冷路径值得。
- 冷函数不应 inline 到热路径，可用 `noinline` 或属性阻止。
- 分离还会改变寄存器分配与栈帧大小，可能带来额外收益或副作用。
- 验证方式是看热函数的代码尺寸、前端缺失计数与基准结果。

### 4.6 冷代码应该放到哪里？

- GCC 与 Clang 支持 `__attribute__((cold))`，把函数标记为极少执行，影响布局与优化决策。
- 链接器脚本可以把 `.text.unlikely` 放到可执行文件的远端，减少热代码的页占用。
- Linux 内核使用 `__cold`、`noinline` 与 `.text.unlikely` 实现类似布局。
- 冷代码放在独立段还便于用 `--gc-sections` 裁剪未使用部分。
- 冷代码不应与热代码共享缓存行，否则取指会带入无用字节。
- 段布局受链接器与平台 ABI 影响，效果由实现定义。
- 过度分离会增加长跳转与 PLT 开销，需要权衡。

### 4.7（场景）错误处理路径拖慢热路径，如何重构？

- 先确认热路径被拖慢的机制：代码体积、分支预测、异常表或栈帧大小。
- 把参数校验与错误构造移到独立函数，热路径只保留一个条件跳转。
- 用错误码或 C++23 的 `std::expected` 替代异常抛出，减少异常表与清理代码。
- 日志格式化延迟到确认错误后执行，避免在热路径构造字符串。
- 使用 `[[unlikely]]` 帮助编译器把错误块移出直落路径。
- 保留必要的检查，不能为了性能删除安全校验，可以把检查合并或提前。
- 重构后验证错误路径的延迟与正确性，避免把成本转移到故障场景。

### 4.8 函数拆分与 `noinline` 的取舍是什么？

- 拆分降低单个函数的体积，改善指令缓存局部性，但增加调用开销与寄存器保存。
- `noinline` 阻止编译器把冷函数 inline 进热路径，控制代码膨胀。
- 对只调用一次的函数，inline 通常有益；对多调用点的冷函数，inline 会复制代码。
- 拆分后编译器可能失去跨函数的常量传播与别名信息，需要重新评估。
- 热函数内部拆分可能破坏原有的调度与寄存器分配，收益不确定。
- LTO 下 inline 决策跨越翻译单元，`noinline` 仍应生效，但需确认属性传播。
- 判断依据是代码尺寸、调用频率与基准，不应凭函数长度决定。

### 4.9 PGO 如何改变基本块布局？

- 插桩或采样得到每个基本块与调用边的执行次数，编译器据此识别热路径。
- 热基本块被排成连续序列，冷块移到函数尾部或独立段，减少取指跳转。
- 分支方向按实测概率选择，热后继成为直落路径。
- 调用图上的高频边影响 inline 决策，热调用点优先 inline。
- 间接调用在剖面中若以单一目标为主，可做去虚拟化或守卫式直接调用。
- 布局改变后，代码对齐与缓存行占用随之变化，收益不完全可预测。
- 剖面过期会把旧的热路径当成当前热路径，布局与实际执行不符。

### 4.10（陷阱）PGO 剖面失真会造成什么后果？

- 训练负载与生产流量分布不同，热路径判断错误，优化资源投向冷代码。
- 剖面过期（代码改动后未重建）会导致计数器与基本块不匹配，编译器可能忽略剖面或产生错误布局。
- 多进程或多线程运行时剖面文件合并不当，计数被重复累加或丢失。
- 采样 PGO 的符号映射错误会把样本归到错误函数，布局决策失准。
- 失真严重时性能可能低于无 PGO 的构建，尤其是热路径被拆分到远端。
- 应在接近生产的负载下采集，并在发布前用真实流量回放验证。
- 保留无 PGO 的基线，出现回归时可以快速回退。

### 4.11 间接跳转为什么难以预测？

- 直接分支的目标在指令中编码，间接跳转的目标来自寄存器或内存，取指时未知。
- 分支目标缓冲区按分支地址缓存目标，单目标间接跳转可以预测，多目标会冲突。
- 虚函数调用点在类型分布多样时，目标随对象变化，预测器需要历史与类型关联。
- 间接预测器容量有限，大量调用点竞争同一表项会造成别名。
- 预测失败不仅要重新取指，还要等待目标地址计算，惩罚高于普通分支失败。
- 安全的间接分支缓解措施会改变执行路径，进一步增加开销。
- 优化方向是减少间接调用、把热点类型特化、使用去虚拟化或分支守卫。

### 4.12（实现）虚函数调用的间接跳转如何优化？

- 把类型信息传入模板，在编译期确定具体类型，消除虚调用。
- 对热点类型做守卫：先比较类型标签，命中时直接调用，未命中回退虚调用。
- 使用 CRTP 或 `std::variant` 加 `visit`，把动态分派转为静态分派或跳转表。
- PGO 与 LTO 可以在单态调用点去虚拟化，推测性去虚拟化需要类型假设成立。
- 把虚函数按类型分组批量处理，减少每个对象的间接调用次数。
- 去虚拟化会增加代码体积与编译时间，类型集合变化时需要重新评估。
- 优化前应确认间接调用确实是瓶颈，虚调用在现代处理器上可能只是一次可预测的跳转。

### 4.13 switch 分发器的性能如何评估？

- 编译器可能生成跳转表、比较链或二分树，选择取决于 case 数量、密度与目标架构。
- 跳转表是一次间接跳转，目标分布集中时预测友好，分散时失败率高。
- 比较链在 case 少且有序时更快，分支可预测性取决于输入分布。
- 用 `objdump -d` 确认生成形式，用性能计数器看间接分支失败与指令缓存缺失。
- 为热分支加 `[[likely]]` 或调整比较链顺序只影响比较链，对跳转表无帮助。
- PGO 可以把热 case 拆成直接分支，冷 case 留在跳转表。
- 评估应使用真实分布，均匀分布的微基准会高估跳转表的失败率或低估比较链成本。

### 4.14 如何用段属性或链接脚本调整代码布局？

- `__attribute__((section(".text.hot")))` 把函数放入指定段，链接脚本控制段之间的顺序。
- 链接脚本用 `SORT_BY_NAME` 或显式输入段列表安排布局，`KEEP` 防止段被回收。
- `-Wl,-T` 指定脚本，`-Wl,--verbose` 查看默认链接脚本与段映射。
- 段属性会阻止某些优化（例如函数合并），并影响调试信息与异常表的位置。
- 段名约定由链接器与平台 ABI 决定，ELF 与 Mach-O 的机制不同。
- 用 `readelf -S` 与 `nm` 验证函数落在哪个段，用基准验证布局收益。
- 手工布局难以维护，函数增删后需要重新评估，PGO 或 BOLT 通常更可持续。

### 4.15 同样的代码在 GCC 与 Clang 下性能差 15%，如何解释？

- inline 阈值与启发式不同，导致热路径是否被 inline、代码体积与布局不同。
- 循环优化与向量化决策不同，生成的指令组合与端口压力不同。
- 标准库实现不同（libstdc++ 与 libc++），容器与算法的常数因子不同。
- 异常表、栈展开与 RTTI 的生成方式不同，影响代码体积与热路径。
- 分支布局与对齐不同，可能造成指令缓存与分支目标缓冲区的行为差异。
- 目标架构默认值不同，例如默认 `-march` 与 `-mtune`。
- 应对比汇编、代码尺寸与性能计数器，定位差异来源后再决定是否值得平台特化。

### 4.16 发布后指令缓存缺失上升，如何定位？

- 对比发布前后的二进制代码尺寸与热函数布局，查看是否新增 inline 或模板实例。
- 用性能计数器的 `iTLB-load-misses` 与指令缓存事件确认缺失确实上升。
- 用采样剖析查看热点函数的代码地址分布，判断是否跨缓存行。
- 检查链接顺序与 LTO 或 PGO 是否改变，热函数可能被排到冷区域。
- 检查是否新增宏展开、日志字符串或异常处理代码，扩大了热路径。
- 检查编译器的 inline 决策是否因新增调用点而变化。
- 回退可疑变更或调整布局后，用同一基准验证。

### 4.17 代码对齐为什么会显著影响性能？

- 循环入口与分支目标跨缓存行时，取指需要两次访问，前端吞吐下降。
- 对齐到 16 或 32 字节边界可以配合取指块大小，减少跨行。
- 过度对齐会增大代码体积，浪费指令缓存空间，反而增加缺失。
- 函数对齐影响分支目标缓冲区索引与指令缓存组映射，可能产生冲突。
- 链接器与编译器会自动对齐热函数，`-falign-functions` 一类选项可以控制。
- 对齐收益具有平台相关性，微架构的取指宽度与缓存行大小不同。
- 应通过布局微调与基准验证，不应全局强制大对齐。

### 4.18 LTO 与 PGO 同时启用后性能反而下降，如何排查？

- 检查剖面是否在 LTO 构建上采集，插桩与使用阶段的优化级别和代码结构应一致。
- LTO 改变函数边界与 inline 决策，旧剖面可能对应已不存在的基本块。
- 代码体积可能因跨模块 inline 膨胀，超出指令缓存容量。
- PGO 可能把冷代码布局到热路径附近，或把热函数拆散，需要查看生成的布局。
- 检查剖面缺失时编译器是否静默退化，构建日志中应有提示。
- 对比有无 LTO、有无 PGO 的四种组合，分别测量代码尺寸与前端缺失。
- 若收益依赖特定组合，应固定构建配置并在 CI 中验证。

### 4.19（条款）`[[likely]]` 的标准语义是什么？

- C++20 引入 `likely` 与 `unlikely` 属性，可标注语句，常见形式是标注 `if` 的分支语句，见 `[dcl.attr.likelihood]`。
- 标准规定它们是对实现的提示，表示该路径被执行的可能性显著高于或低于替代路径。
- 属性不改变控制流、不求值操作数、不引入运行时检查。
- 标准不规定编译器必须如何利用提示，布局与优化结果由实现决定。
- 同一分支重复标注或与 PGO 冲突时，最终代码生成由实现决定。
- 与 `[[nodiscard]]` 一类语义属性不同，likelihood 属性不影响良构性。
- 提案为 `P0479R5`。

### 4.20（场景）分支密集的状态机如何优化？

- 先测量分支失败率与状态转移分布，确认瓶颈在预测而非其他部分。
- 把状态转移表化，用查表加函数指针替代 switch，减少分支但增加间接跳转。
- 把高频状态转移写成直接分支，低频转移走通用路径。
- 使用 computed goto（GCC 扩展）把分发变为一次间接跳转，减少比较链。
- 把状态机改写为循环加事件队列，按状态批量处理事件，减少分发次数。
- 对可预测的模式，保持分支可能比查表更快，因为间接跳转同样依赖预测。
- 优化后用状态分布的线上数据验证，均匀分布的基准不能代表真实负载。

## 5. 数据布局与 AoS/SoA

### 5.1 结构体的大小由哪些因素决定？

- 成员的大小与声明顺序决定基础布局，编译器按各成员的对齐要求插入填充字节，使每个成员的偏移满足对齐。
- 结构体的对齐要求等于成员中最严格的对齐要求，结构体大小向上取整到该对齐的整数倍。
- 基类子对象、虚表指针与虚基类偏移会改变布局，多继承与虚继承的具体规则由实现定义。
- 位域的分配顺序与跨存储单元方式由实现定义，不应当作为跨编译器接口的一部分。
- `#pragma pack` 与 `__attribute__((packed))` 会取消填充，代价是部分平台上的非对齐访问变慢或触发异常。
- 空基类通常不占空间，但两个同类型空基类子对象需要不同地址，可能各占一字节。
- 跨进程或跨版本传递的结构体应当使用定长整数类型，按对齐从大到小排列成员，并用序列化层隔离布局。

### 5.2（辨析）填充字节在什么场景下会显著浪费内存？

- 成员按「大、小、大」交替声明时，小成员前后都会出现填充，浪费量可达结构体大小的数倍。
- 典型情形是 `char` 与 `double` 交替出现，单个 `double` 之前的填充可达 7 字节。
- 大量同构对象存放在连续数组中时，填充浪费按对象数量线性放大，十万个对象即可产生数 MB 差异。
- 填充字节不参与构造语义，`memcpy` 会连同填充一起复制，按字节比较则会读到未初始化的填充。
- 按对齐从大到小排列成员通常能消除大部分填充，代价是字段顺序变化会影响可读性与聚合初始化。
- 高频访问的字段放在一起比单纯压缩大小更重要，填充浪费与缓存利用率需要同时评估。
- `sizeof` 与各成员 `sizeof` 之和的差值可以快速估算单个对象的填充量。

### 5.3 AoS 与 SoA 的适用边界如何判断？

- AoS 把同一对象的字段连续存放，适合以对象为单位访问全部字段的场景。
- SoA 把同一字段的所有对象连续存放，适合只访问少数字段、按列扫描的场景。
- SoA 的收益来自缓存行利用率与向量化：一次载入的缓存行全部是有效数据，编译器也更容易生成 SIMD 指令。
- SoA 的代价是随机访问单个对象需要多次跨数组跳跃，跨字段计算变成多个数据流的合并。
- 判断依据是访问模式：每次处理都读取全部字段时 AoS 更好，多数处理只读取一到两个字段时 SoA 更好。
- 中间形态是按字段分组的分块布局，例如每 4 个对象一组的 AoSoA，兼顾顺序扫描与对象级访问。
- 布局变更属于全局性改动，应当先用性能剖析确认瓶颈在访存而非其他环节，再评估迁移成本。

### 5.4（实现）如何实现热字段与冷字段的拆分？

- 拆分依据是字段的访问频率统计：对字段读取采样，把高频字段留在热结构体，低频字段放入冷结构体，用下标关联。
- 热结构体应当压缩到缓存行以内或缓存行的整数倍，避免一条缓存行跨越两个对象的热数据。
- 冷结构体单独存放，只在需要时按下标访问，顺序扫描热数组时不再为冷字段付出缓存代价。
- 拆分后对象身份由下标而非指针表达，热数组扩容会使引用失效，外部句柄应当使用下标加版本号。
- 冷字段访问密集时，拆分引入的间接访问反而变慢，需要按访问比例权衡。
- 上线时先灰度，比较指令数与末级缓存未命中的变化，再决定是否全量。

```cpp
struct OrderHot {                    // 常用字段，24 字节
    std::uint64_t id;
    std::int64_t  price;
    std::uint32_t qty;
};

struct OrderCold {                   // 少用字段，按同一下标存放
    std::string note;
    std::array<std::byte, 32> signature;
};

std::vector<OrderHot>  hot;
std::vector<OrderCold> cold;         // cold[i] 对应 hot[i]
```

### 5.5（实现）对象池如何复用已构造的对象？

- 池预先分配连续存储，构造时在存储上做 placement new，销毁时显式调用析构函数而不释放存储。
- 空闲对象用空闲链表串起来，链表节点复用对象自身的内存，不额外分配。
- 句柄可以是下标加代际，也可以是池内指针；下标方案在池扩容搬移时仍然有效。
- 归还前必须释放对象持有的资源，池本身只负责存储，不负责资源回收。
- 池的容量上限决定峰值内存，超出上限时需要明确的降级路径：阻塞、拒绝或回退到通用分配。
- 对象大小固定时才适合池化，变长对象应当按大小分级或改用 arena。

```cpp
template <class T, std::size_t N>
class Pool {
    alignas(T) std::byte buf_[N * sizeof(T)];
    std::vector<T*> free_;
public:
    Pool() { for (std::size_t i = 0; i < N; ++i) free_.push_back(slot(i)); }
    T* slot(std::size_t i) { return reinterpret_cast<T*>(buf_ + i * sizeof(T)); }
    T* acquire() {
        if (free_.empty()) return nullptr;
        T* p = free_.back();
        free_.pop_back();
        return ::new (static_cast<void*>(p)) T();
    }
    void release(T* p) { p->~T(); free_.push_back(p); }
};
```

### 5.6（陷阱）对象归还后仍被使用会带来什么问题？

- 对象归还到池后存储被复用，先前保存的裸指针仍指向同一地址，但对象已经属于新的持有者。
- 池在归还时并不清零存储，调试构建下的断言可能全部通过，错误只在特定时序暴露。
- 下标加代际的句柄可以在解引用时检出悬垂引用，代价是每次访问多一次代际比较。
- 归还时填充固定模式（如 `0xDD`）能在调试时放大错误，但会增加每次归还的开销。
- 析构函数未调用时，池化对象持有的文件描述符与堆内存不会被释放，表现为句柄泄漏而非崩溃。
- 对象含自引用指针时，存储复用后自引用失效，需要改为基于下标的引用。

### 5.7 空闲链表如何嵌入对象本身？

- 空闲节点复用对象存储的前若干字节存放后继指针，要求对象大小不小于指针大小且对齐满足要求。
- 归还时写入后继指针会覆盖对象内容，因此不能依赖归还后的残留数据。
- 侵入式链表不占额外内存，但空闲期间对象字段不可读，调试时难以区分「已归还」与「未初始化」。
- 后进先出的空闲链表复用最近释放的对象，缓存局部性较好；先进先出能推迟复用，更容易暴露悬垂访问。
- 多线程池需要为每个线程维护独立空闲链表，或者对共享链表加锁，前者要处理线程退出时的归还。
- 空闲链表本身也是共享数据，跨线程频繁取还会引入缓存行争用，与池化的初衷冲突。

### 5.8 遍历顺序如何影响缓存命中率？

- 行主序遍历二维数组时，内层循环沿最后一维前进，相邻元素位于同一缓存行，命中率高。
- 交换循环顺序后退化为按列访问，每次访问都落在新的缓存行，缓存行内的其余数据被浪费。
- 大对象数组的顺序遍历能被硬件预取器识别，跨步大于缓存行的访问会绕过预取。
- 链表遍历的地址不连续，无法预取，每次跳转都可能是一次末级缓存未命中。
- 遍历前按地址排序可以改善链表或指针容器的局部性，代价是排序本身的成本。
- 分块把工作集限制在 L1 或 L2 容量内，适合矩阵乘法一类重复访问同一数据的场景。
- 遍历顺序同时改变写入模式，跨缓存行写入同一行会触发读改写，写密集场景代价更高。

### 5.9 值数组与指针数组如何选择？

- 值数组把对象连续存放，一次缓存行可覆盖多个对象，插入删除需要搬移后续元素。
- 指针数组或下标数组把对象分散存放，地址稳定且插入删除为常数时间，每次访问多一次间接寻址。
- 间接寻址的代价取决于被指向对象的分布，堆上分散分配时每次访问都可能未命中。
- 需要稳定地址时（例如对象被外部注册的回调引用），指针或下标加稳定存储是必要条件。
- 排序与查找只涉及键时可以维护独立的索引数组，避免搬移大对象。
- 选择依据是访问次数与修改次数的比例，访问远多于修改时值数组通常更优。

### 5.10 多维数组的步长如何影响遍历性能？

- C++ 的数组按行主序存储，最后一维连续，步长为 1 的维应当作为最内层循环。
- 跨步访问使每次访存落在不同的缓存行，缓存行内其余数据被浪费，有效带宽按步长成比例下降。
- 步长为 2 的幂时可能引发缓存组冲突，同一组被反复换出，表现为命中率异常低。
- 分块可以同时缓解容量与冲突问题，把矩阵划分为能放入 L1 的方块，逐块计算。
- 结构化绑定与多维下标封装不应当改变存储顺序，否则优化器难以识别连续访问。
- 对角线与转置访问属于天然跨步，需要显式重排数据或使用分块转置。

### 5.11（实现）如何封装 SoA 而不引入额外开销？

- 用 `std::span` 暴露单个字段的连续区间，调用方按字段处理，不构造代理对象。
- 需要对象视图时使用轻量结构体持有各字段的指针，按值传递，编译器可以完全展开。
- 代理引用能让 `operator[]` 返回可赋值对象，但每次访问都要构造临时对象，容易抑制向量化。
- 迭代器应当返回字段值，或者在循环体内按字段分别处理。
- 编译期断言字段数组长度一致，避免新增字段时遗漏某个数组。

```cpp
struct Positions {
    std::vector<float> x, y, z;      // 长度始终一致

    void push(float px, float py, float pz) {
        x.push_back(px); y.push_back(py); z.push_back(pz);
    }
    std::size_t size() const { return x.size(); }
};

void scale(Positions& p, float k) {
    for (std::size_t i = 0; i < p.size(); ++i) p.x[i] *= k;   // 只访问 x
}
```

### 5.12（辨析）SoA 对随机访问与顺序访问的代价差异是什么？

- 顺序访问下 SoA 的每条缓存行都携带有效数据，AoS 则把无关字段一并载入。
- 随机访问下 SoA 需要三次独立载入才能读完一个对象，AoS 一次载入即可。
- 随机访问的代价可以部分抵消：若后续处理同一批对象的其他字段，多出的载入会被摊薄。
- 先查索引表再访问数组的间接访问，会让两种布局都失去预取能力。
- 写密集场景下 SoA 的写合并更友好，AoS 的单字段写会污染整条缓存行。
- 混合负载可以按访问比例选择，或者把最常随机访问的字段留在 AoS 部分。

### 5.13 结构体排序如何减少内存占用？

- 按对齐要求从大到小排列成员，通常可以把填充降到零或对齐边界内的最小值。
- 从 32 位迁移到 64 位会放大填充问题，指针与 `long` 的对齐从 4 变为 8。
- 排序改变字段顺序，影响聚合初始化与序列化映射，需要同步更新相关代码与文档。
- `sizeof` 断言可以防止后续新增字段破坏已经调整过的布局。
- 结构体需要与外部二进制格式对应时不能排序，应当通过序列化层解耦。
- 排序只解决单对象浪费，数组层面的浪费还要看对象大小与缓存行的整除关系。

### 5.14（场景）发布后 RSS 上涨，如何判断是填充还是泄漏？

- 先比较对象数量与单对象 `sizeof` 的乘积和进程 RSS，差值远大于池预留量时倾向填充或分配器元数据。
- 用分配剖析记录分配点的调用栈与存活字节数，存活字节随请求数线性增长指向泄漏。
- 检查新增字段是否改变了结构体大小，从 24 字节增至 40 字节会跨越缓存行并带来额外占用。
- 检查容器容量增长策略，容量可能远大于元素个数，差值是隐性占用。
- 区分虚拟内存与常驻内存：大块预留只计入虚拟内存，不应当作为泄漏证据。
- 回滚到上一版本，在相同负载下对比 RSS 曲线，可以确认是否为本次发布引入。

### 5.15 小对象数组与侵入式链表如何取舍？

- 小对象数组连续存放，遍历快，删除需要搬移或使用墓碑标记。
- 侵入式链表把链接指针放进对象，插入删除为常数时间，遍历时每次跳转都可能未命中。
- 数量小且遍历频繁时数组更优，数量大且修改频繁时链表或索引结构更优。
- 墓碑标记删除后需要周期性压缩，压缩期间存在双倍内存与停顿。
- 侵入式链表要求对象不可搬移，与数组扩容互斥。
- 混合方案是数组加空闲下标栈，删除时把下标压栈，遍历时跳过墓碑。

### 5.16（实现）如何守住布局假设？

- `static_assert(sizeof(T) == 32)` 把预期大小写进编译期检查，字段增删会立即失败。
- `offsetof` 只能用于标准布局类型，对含虚函数或私有成员的类使用属于未定义行为。
- `alignof`、`std::is_standard_layout`、`std::is_trivially_copyable` 可以在编译期约束可用于 `memcpy` 与外部接口的类型。
- 网络协议与文件格式的结构体应当使用定长整数类型，避免 `long` 与指针宽度随平台变化。
- 断言旁应当注明预期布局的原因，否则后续维护者会直接改掉断言。

```cpp
struct Header {
    std::uint32_t magic;
    std::uint16_t version;
    std::uint16_t flags;
    std::uint64_t length;
};
static_assert(sizeof(Header) == 16);
static_assert(alignof(Header) == 8);
static_assert(offsetof(Header, length) == 8);
```

### 5.17 缓存行对齐如何影响跨核共享的数据布局？

- 两个线程分别写同一缓存行内的不同变量时，缓存行在核心之间来回传递，写操作互相拖慢。
- 把高频写的变量用 `alignas(64)` 隔离到独立缓存行可以消除这种争用，代价是内存占用增加。
- 缓存行大小由实现定义，x86-64 通常为 64 字节，部分 ARM 实现为 128 字节，可移植代码不应当硬编码。
- 只读共享数据不需要隔离，多个核心同时读取同一缓存行没有写无效开销。
- 结构体数组按线程分片时，分片边界应当对齐到缓存行，避免相邻分片共享一行。
- 对齐会增加对象大小，池化时需要按对齐后的实际占用计算容量。

### 5.18（场景）序列化格式与内存布局耦合会带来什么问题？

- 直接把结构体按字节写入文件或网络，会把填充字节、字节序与对齐规则一并固化。
- 更换编译器、优化级别或目标平台后布局可能变化，旧数据无法正确解析。
- 填充字节的内容不确定，按字节比较或计算校验和会产生不一致的结果。
- 版本升级时新增字段会改变后续字段的偏移，旧版本读取新数据会错位。
- 正确做法是显式序列化每个字段，指定字节序与字段宽度，并对未知字段做跳过处理。
- 需要零复制时可以使用固定布局的平凡可复制类型，但必须显式指定对齐与字节序，并在两端加静态断言。

### 5.19（辨析）结构体拆分对 ABI 兼容性的影响是什么？

- 结构体大小与字段偏移属于 ABI 的一部分，改变布局会使已编译的调用方与新库不兼容。
- 在公开头文件中调整字段顺序或新增字段，可能改变按值传递的调用约定与栈布局。
- 私有实现中的结构体可以自由调整，前提是它不出现在导出符号的签名里。
- 使用不透明句柄（前置声明加指针）可以把布局变化限制在库内部。
- 拆分热冷字段若把指针改为下标，属于接口变更而不只是布局调整。
- 动态库升级需要保证新旧布局的读取兼容，或者通过版本化的接口隔离。

### 5.20（场景）订单簿数据结构如何选择布局？

- 订单簿的核心操作是按下标更新价格档位、按价格查找，以及对外发布快照。
- 价格档位数量固定且按下标访问时，档位数组比映射结构更快。
- 档位内的订单队列用侵入式链表，订单对象存放在池中，避免每次增删都向系统分配。
- 快照发布需要顺序扫描全部档位，SoA 布局能让扫描只触碰数量字段。
- 订单与档位分离存放，查询单笔订单走订单池，扫描行情走档位数组，两种访问互不干扰。
- 布局变更需要通过回放历史行情验证正确性，并对比撮合延迟的分位数而非均值。

## 6. 分配器与内存池

### 6.1 `malloc` 的一次分配包含哪些开销？

- 查找空闲块：按大小分类的空闲链表或索引结构，命中快慢取决于大小类与碎片状态。
- 元数据：块头记录大小与状态，通常为 8 至 16 字节，小对象上元数据的占比可能超过有效载荷。
- 对齐与取整：请求大小向上取整到最小粒度，常见粒度为 16 字节，小请求的实际占用被放大。
- 同步：多线程分配需要互斥，主流实现用线程缓存承担快速路径，缓存耗尽时回落到共享区并加锁。
- 系统调用：空闲区不足时通过 `brk` 或 `mmap` 扩展，涉及内核路径与页表操作，代价远高于用户态操作。
- 填充与校验：调试模式或部分实现会填充、清零与校验，增加每次分配的成本。
- 释放路径同样有开销：合并相邻空闲块、归还线程缓存，必要时通过 `madvise` 归还物理页。

### 6.2 为什么小对象分配的开销占比更高？

- 固定开销与请求大小无关，请求越小，摊销到每个字节的成本越高。
- 16 字节的请求在 16 字节粒度下连同块头会占用 32 字节，有效利用率接近一半。
- 大量小对象分散在堆上，破坏遍历局部性，缓存未命中的代价超过分配本身。
- 同一大小反复分配释放会命中线程缓存的快速路径，跨线程释放则把块推回远端缓存。
- 批量分配把固定开销摊到一批对象上，是小对象场景的主要优化手段。
- 对象池或 arena 把分配降为指针加法，适合生命周期一致的小对象。
- 分配次数本身就是可观测指标，按请求统计分配次数可以判断优化是否命中热路径。

### 6.3 arena 分配器的适用边界是什么？

- arena 一次申请大块内存，分配时只推进偏移，释放只支持整体重置或按标记回退。
- 适合生命周期一致、批量创建批量销毁的数据，例如单次请求的解析结果与单帧的临时对象。
- 不适合长短生命周期混合的对象，一个长寿对象会阻止整块内存回收。
- 不支持单独释放，误用会导致内存无法回收，表现为 RSS 随请求数单调上涨。
- 与标准容器结合需要分配器满足分配器要求，`std::pmr::monotonic_buffer_resource` 提供了现成实现。
- 多线程共享 arena 需要加锁或按线程分段，分段后线程退出时的内存归还需要专门处理。
- arena 的峰值占用等于同时存活的块总量，容量上限应当由并发请求数与单请求用量估算。

### 6.4（实现）如何实现一个单调递增的 arena？

- 内部维护块链表，每块是一段对齐的大内存，当前块剩余空间不足时申请新块。
- 分配时把偏移向上对齐到 `alignof(T)`，检查剩余空间，返回指针并推进偏移。
- 重置时把偏移归零并保留块，避免反复向系统申请；整体销毁时统一归还。
- 对齐分配需要记录原始指针以便释放，或者在块头保存基址。
- 单块大小应当明显大于常见请求，否则个别大请求会独占一块，浪费剩余空间。
- 后续可以加入按标记回退，用于嵌套作用域，但必须先保证严格的后进先出。

```cpp
class Arena {
public:
    void* alloc(std::size_t n, std::size_t align = alignof(std::max_align_t)) {
        std::size_t off = (cur_ + align - 1) & ~(align - 1);
        if (!buf_ || off + n > block_) {              // 简化：只保留当前块
            buf_ = static_cast<std::byte*>(::operator new(block_));
            off = 0;
        }
        cur_ = off + n;
        return buf_ + off;
    }
private:
    std::size_t block_ = 1 << 20, cur_ = 0;
    std::byte* buf_ = nullptr;
};
```

### 6.5 slab 分配器如何按对象大小分类？

- 把对象按大小划分为若干类，例如 8、16、32、64 字节，每类维护独立的页集合。
- 每页切分为等大的槽，空闲槽用位图或空闲链表管理，页头记录所属大小类。
- 分配时定位大小类，从当前页取一个空闲槽；页满时从部分空闲页链表取下一页。
- 释放时根据地址定位页头，把槽标记为空闲，页从满变为部分空闲时挂回链表。
- 大小类造成内部碎片，请求 33 字节会占用 48 或 64 字节的槽。
- 页级回收允许把完全空闲的页归还系统，缓解长时间运行的内存增长。
- slab 适合固定大小的小对象，变长与超大对象需要单独路径。

### 6.6（陷阱）arena 释放顺序错误会带来什么问题？

- arena 只支持整体重置或按标记回退，先分配的块仍在使用时重置会让所有指针悬垂。
- 按标记回退要求严格后进先出，跨层释放会把仍在使用的对象一并回收。
- 在外层 arena 上分配、在内层释放，通常不会立即崩溃，后续访问才会读到被复用的内存。
- 症状常表现为数据结构内容随机变化与校验失败，难以与分配器建立关联。
- 调试构建可以给重置区域填充标记字节，并在访问前校验，缩小排查范围。
- 设计上应当让 arena 的生命周期与请求或帧严格对齐，避免跨层共享。

### 6.7（辨析）`malloc` 与 `new` 的失败路径有何差异？

- `malloc` 失败返回空指针，`new` 失败抛出 `std::bad_alloc`，`new(std::nothrow)` 返回空指针。
- `new` 在分配成功后调用构造函数，构造函数抛出异常时会自动释放已分配的内存。
- 数组 `new` 需要记录元素个数以便析构，`malloc` 没有这个概念。
- 自定义 `operator new` 可以改变失败行为，覆盖全局版本会影响整个进程。
- 内存不足时过度提交可能让 `malloc` 成功，而实际触碰页面时进程被内核终止，失败路径不可依赖。
- 释放必须匹配，`new` 配 `delete`，`malloc` 配 `free`，混用属于未定义行为。

### 6.8 `std::pmr` 的 `memory_resource` 如何替换默认分配？

- `std::pmr::memory_resource` 是抽象基类，`do_allocate`、`do_deallocate`、`do_is_equal` 由派生类实现。
- 容器接受 `memory_resource*`，通过 `polymorphic_allocator` 转发分配请求。
- 常用资源包括 `monotonic_buffer_resource`、`unsynchronized_pool_resource` 与 `synchronized_pool_resource`。
- 资源可以串联，池资源在上游资源之上做大小分类，单调资源为其提供大块内存。
- `polymorphic_allocator` 的传播规则与 `std::allocator` 不同，容器复制与移动时的资源归属需要显式指定。
- 虚函数调用给每次分配增加一次间接开销，相对分配本身通常可以忽略，但在极小对象上需要测量。

### 6.9（实现）如何用 `pmr` 实现每请求内存池？

- 每个请求创建一个 `monotonic_buffer_resource`，上游为线程局部的池资源，请求结束时整体释放。
- 请求内的容器统一使用该资源的分配器，例如 `std::pmr::vector` 与 `std::pmr::string`。
- 资源对象放在栈上或请求上下文中，生命周期覆盖所有使用它的容器。
- 释放顺序要求容器先于资源销毁，否则析构时会访问已经失效的资源。
- 资源可以给一段栈上的初始缓冲区，减少小请求对上游的申请次数。
- 请求处理抛出异常时资源随栈展开销毁，前提是容器也在此前析构。

```cpp
void handle(Request& req, std::pmr::memory_resource& upstream) {
    std::pmr::monotonic_buffer_resource pool{&upstream};
    std::pmr::vector<Item> items{&pool};
    std::pmr::string name{&pool};

    items.reserve(req.count);          // 一次取够，避免扩容
    for (const auto& raw : req.raw) items.push_back(parse(raw, &pool));
    // 返回前 items 与 name 先析构，pool 最后销毁
}
```

### 6.10 批量分配为什么能降低总开销？

- 一次系统调用或一次加锁覆盖多个对象，固定开销被摊薄。
- 连续分配的对象地址相邻，提高遍历时的缓存命中率与预取效率。
- 批量分配便于整体释放，避免逐个释放时的合并与同步。
- 批量大小需要与缓存容量匹配，过大的批次会把工作集推出缓存。
- 预分配会提高峰值内存，需要按并发请求数估算上界。
- 分配与构造分离时要注意异常安全，中途失败必须释放已经分配的部分。

### 6.11 内存碎片如何度量？

- 内部碎片是分配器实际占用与请求大小之差，按大小类统计可以得到比例。
- 外部碎片是空闲总量足够但无法满足最大请求，用最大可分配块与空闲总量之比衡量。
- 常驻内存与活跃字节数之差反映保留但未使用的部分，包括线程缓存与空闲页。
- 分配剖析可以给出按大小分布的存活对象数与字节数，用于识别碎片来源。
- 长期运行的服务应当观察碎片随时间的变化，稳定值可以接受，单调上升需要处理。
- 度量必须在真实负载下进行，合成负载的对象分布与线上差异很大。

### 6.12（场景）长时间运行的服务 RSS 持续上涨如何排查？

- 先区分泄漏与碎片：存活字节稳定而 RSS 上涨指向碎片或分配器保留。
- 检查分配器是否归还空闲页，长时间不归还会表现为阶梯式上涨。
- 检查线程数变化，每个线程的缓存分区占用固定内存，线程池扩容会推高 RSS。
- 检查大块分配走的路径，阈值附近的请求可能在不同路径之间摇摆。
- 用分配剖析按调用栈排序存活字节，增长最快的调用点通常是直接原因。
- 排除缓存与连接池的增长，它们有明确上界，超过上界说明回收逻辑或配置有问题。

### 6.13 分配器的线程缓存如何取舍？

- 线程缓存把空闲块保留在线程本地，分配与释放无需加锁，是主流分配器的快速路径。
- 缓存容量有限，超出后批量归还共享区，批量粒度影响内存占用与同步频率。
- 一个线程分配、另一个线程释放时，块最终回到释放线程的缓存，形成跨线程的缓存漂移。
- 线程数多且生命周期短时，线程缓存会放大内存占用，需要在销毁时归还。
- 关闭线程缓存可以降低内存占用，代价是每次分配都可能进入加锁路径。
- 生产者消费者模式下按线程分区分配可以让内存留在本地，减少迁移。

### 6.14 `mmap` 与 `brk` 对分配器行为的影响是什么？

- `brk` 扩展堆顶，只能整体伸缩，适合小分配与连续增长；`mmap` 建立独立映射，适合大块分配。
- 大块分配走 `mmap` 可以在释放时直接归还系统，避免堆顶被大块长期占住。
- `brk` 区域内的空闲块只有位于堆顶时才能归还，堆中间的空洞无法释放。
- 映射与解除映射涉及页表操作与 TLB 失效，频繁调用代价高，分配器用阈值与缓存规避。
- `mmap` 的地址与页对齐要求使小于一页的分配浪费明显。
- 过度提交配置影响 `mmap` 的实际物理页分配时机，进而影响首次触碰的延迟。

### 6.15（陷阱）跨线程释放有什么代价？

- 块必须回到其所属的 arena 或线程缓存，跨线程时需要加锁或走远程释放队列。
- 远程队列的批量处理引入延迟，回收不及时会推高峰值占用。
- 对象元数据所在的缓存行在核心之间迁移，释放线程与被释放对象反复互相失效。
- 分配与释放线程不一致时线程缓存命中率下降，快速路径退化为慢路径。
- 高并发下跨线程释放会成为扩展性瓶颈，表现为线程数增加而吞吐不增。
- 设计上应尽量让分配与释放在同一线程完成，或者使用按线程分区的池。

### 6.16 透明大页对分配器的影响是什么？

- 透明大页把连续的 4 KiB 页合并为 2 MiB 页，减少 TLB 未命中。
- 合并需要内存整理，后台整理线程会带来不确定的延迟。
- 分配器的大块预留更容易被合并，小对象密集区域可能因碎片无法合并。
- 部分场景下大页会增加内存占用与延迟尖峰，需要按负载选择 `madvise` 或 `never`。
- 显式对特定区域调用 `madvise(MADV_HUGEPAGE)` 可以只对关键数据启用大页。
- 大页的收益在随机访问大工作集时最明显，工作集小于 TLB 覆盖范围时收益有限。

### 6.17（场景）分配风暴导致的尾延迟尖峰如何定位？

- 观察尖峰是否随并发上升而放大，分配风暴通常与请求量正相关。
- 用分配剖析统计单位时间内的分配次数与字节数，尖峰期间调用栈集中在少数路径时可直接定位。
- 检查热路径上是否创建临时容器或字符串，按值传参与日志拼接是常见来源。
- 检查容器扩容，未预留容量时按倍数增长会触发多次复制与释放。
- 检查分配器慢路径，线程缓存耗尽、共享区加锁或向系统申请都会引入明显停顿。
- 用固定容量的对象池替换热路径分配，再对比分位数确认改善幅度。

### 6.18（实现）如何满足容器的分配器要求？

- 需要提供 `value_type`、`allocate` 与 `deallocate`，以及相等比较与重绑定支持。
- C++11 起通过 `allocator_traits` 提供默认实现，只需实现最少的接口。
- 有状态的分配器必须定义 `operator==`，容器在移动赋值与交换时依赖它判断能否接管内存。
- 分配器对象随容器复制而复制，状态需要可复制且生命周期覆盖容器。
- 分配失败应当抛出 `std::bad_alloc`，不应当返回空指针。
- 与 `polymorphic_allocator` 相比，静态分配器没有虚调用开销，但资源类型在编译期固定。

```cpp
template <class T>
struct BumpAllocator {
    using value_type = T;
    Arena* arena;
    BumpAllocator(Arena* a) : arena(a) {}
    template <class U> BumpAllocator(const BumpAllocator<U>& o) : arena(o.arena) {}
    T* allocate(std::size_t n) {
        return static_cast<T*>(arena->alloc(n * sizeof(T), alignof(T)));
    }
    void deallocate(T*, std::size_t) {}     // 由 arena 统一回收
    friend bool operator==(const BumpAllocator& a, const BumpAllocator& b) {
        return a.arena == b.arena;
    }
};
```

### 6.19（辨析）对象池与内存池的区别是什么？

- 内存池管理字节块，不关心块上构造的对象；对象池管理已构造的对象，负责构造与析构。
- 对象池通常建立在内存池之上，内存池提供存储，对象池在其上做 placement new 与析构。
- 对象池可以复用构造好的对象，适合构造成本高且重置成本低的类型。
- 内存池的分配单位可变，对象池通常固定大小或按大小分类。
- 释放语义不同，对象池归还对象，内存池归还字节块。
- 混用会导致析构未调用或重复构造，接口设计上应当明确职责边界。

### 6.20（场景）固定大小的消息如何选择分配策略？

- 消息大小固定且生命周期短时，按大小分类的池配合空闲链表是首选。
- 消息跨线程排队时，池的所有权需要明确，通常由接收方负责归还。
- 需要零复制时把消息头与载荷放在同一块连续内存，避免二次分配。
- 高峰期超出池容量时应当有背压或拒绝策略，回退到通用分配会放大延迟。
- 消息只有少数几档大小时，为每档建立独立池，避免大小类带来的内部碎片。
- 用空闲数量监控池的使用情况，长期接近零说明容量不足，长期满额说明预留过多。

## 7. 优化器行为与内联优化

### 7.1 为什么开启 `-O3` 后性能反而下降？

- 更激进的内联与循环展开增大代码体积，指令缓存未命中可能抵消收益。
- 向量化提高寄存器压力，复杂循环可能产生溢出到栈的代码。
- 自动向量化有时引入额外的运行时检查与分支，短循环收益为负。
- 过度内联会让热点函数膨胀，影响分支预测与指令预取。
- 需要按函数或文件粒度对比基准，定位回退来自内联、向量化还是代码布局。
- 优化级别不是单调关系，最终以目标架构上的测量为准。

### 7.2 `-O0` 下的代码为什么不能用于性能结论？

- `-O0` 关闭内联优化与大部分变换，函数调用、临时对象与栈变量都会真实存在，开销结构与发布版本不同。
- 在 `-O0` 下测得的瓶颈可能来自调试构建特有的内存往返，与优化后的瓶颈位置无关。
- `-O0` 为便于调试保留额外存储，寄存器分配差异很大，指令数会成倍增加。
- 性能结论必须来自与发布一致的编译选项，包括优化等级、LTO、目标架构与宏定义。
- 需要调试优化后的代码时，可以保留调试信息并使用优化构建，无须退回 `-O0`。
- 基准测试应当在构建脚本中固定优化选项，避免不同机器使用不同默认值。

### 7.3 编译器在什么条件下放弃内联优化？

- 函数体过大时内联优化会显著增加代码体积，超过启发式阈值后放弃。
- 递归函数通常只展开有限层，完全展开会无限增长。
- 调用点过多时全部做内联优化会使总代码量膨胀，编译器按调用点的边际成本决定。
- 取地址、通过函数指针调用与虚调用难以确定目标，无法直接替换调用。
- 跨翻译单元调用在缺少 LTO 时看不到函数体，只能对头文件中可见的定义做内联优化。
- 异常处理、可变参数与汇编语句会提高成本估计，降低被选中的概率。
- 决策是启发式的，同一份代码在不同编译器版本上的结果可能相反。

### 7.4（实现）如何用属性控制内联优化？

- `[[gnu::always_inline]]` 与 `__forceinline` 要求编译器做内联优化，无法满足时通常给出诊断。
- `[[gnu::noinline]]` 阻止内联优化，适合把冷路径移出热函数以减小指令缓存占用。
- `[[gnu::flatten]]` 要求把被调函数全部纳入当前函数，容易造成代码膨胀。
- `inline` 关键字只影响链接规则，不构成内联优化的要求。
- 属性属于编译器扩展，可移植代码应当用宏隔离并按编译器分支。
- 强制内联优化之前应当确认热点，盲目使用会让指令缓存成为新的瓶颈。

```cpp
#if defined(__GNUC__) || defined(__clang__)
#  define HOT_INLINE inline __attribute__((always_inline))
#  define COLD __attribute__((noinline))
#else
#  define HOT_INLINE inline
#  define COLD
#endif

HOT_INLINE int clamp(int v) { return v < 0 ? 0 : (v > 255 ? 255 : v); }

COLD void log_overflow(int v);   // 冷路径，避免进入热函数的指令流
```

### 7.5 内联优化带来的代码膨胀如何度量？

- 比较构建产物代码段的大小，内联优化会增加总指令数。
- 用优化报告（如 `-fopt-info-inline`、`-Rpass=inline`）列出决策与被拒原因。
- 指令缓存未命中可以通过硬件计数器观察，膨胀严重时未命中率上升。
- 在剖析结果中查看热点函数自身的指令数，内联优化后热点会集中到调用者。
- 膨胀对分支密集的小函数影响小，对大函数的重复展开影响显著。
- 评估应当以端到端分位数为准，代码体积只是中间指标。

### 7.6 虚函数调用为什么难以做内联优化？

- 虚调用在运行期才能确定目标，编译器需要证明动态类型唯一才能去虚化。
- 对象在局部构造且未被取地址时，编译器可以确定动态类型，从而直接调用。
- 类型标记为 `final`，或者成员函数标记为 `final`，可以排除覆写并帮助去虚化。
- 通过基类引用传入的对象，若调用点可见完整类型信息（如模板实例化或 LTO），也可能去虚化。
- 去虚化失败时每次调用都有一次间接跳转，预测器对多态调用点的表现取决于目标分布。
- 性能敏感的接口可以用模板或函数指针替代虚调用，代价是代码体积与编译时间。

### 7.7（陷阱）把 `inline` 当作性能提示会带来什么后果？

- `inline` 的语义是允许多个翻译单元出现相同定义，由链接器合并为一份，与是否做内联优化无关。
- 类内定义的成员函数隐式带有 `inline`，同样不保证被内联优化。
- 标记 `inline` 的函数被取地址时，编译器仍需生成独立副本。
- 在头文件中定义非 `inline` 函数会触发重复定义错误，这属于链接问题。
- 把 `inline` 当作性能提示是常见误解，影响内联优化的是可见性与成本估计。
- 跨翻译单元做内联优化需要 LTO，或者把定义放到头文件中。

### 7.8 别名分析如何影响优化？

- 编译器需要证明两个指针不指向同一对象，才能把读操作提前到写操作之前，或者把值缓存到寄存器。
- 通过 `char*` 与 `std::byte*` 访问对象是允许的，编译器因此必须假定任意字节指针可能别名任何对象。
- 同类型指针之间的别名关系无法排除时，每次写入后都要重新载入。
- 别名信息缺失会导致循环无法向量化，因为写操作是否影响后续读无法确定。
- 帮助编译器的方式包括使用局部变量、收窄指针作用域、使用 `__restrict`。
- 别名假设错误会让优化后的代码产生错误结果，属于难以复现的一类缺陷。

### 7.9（实现）如何用 `__restrict` 表达无别名？

- `__restrict` 是编译器扩展，声明在该指针生命周期内，通过它访问的对象不会通过其他指针访问。
- 适用于参数互不重叠的接口，例如复制、逐元素运算与矩阵乘法。
- C++ 标准没有 `restrict`，可移植代码需要宏封装，并按编译器提供不同写法。
- 违反约定属于未定义行为，调用方传入重叠区间会得到错误结果。
- 与 `const` 组合可以同时表达只读与无别名，帮助编译器提前载入。
- 该限定只影响优化假设，不改变函数签名与调用约定。

```cpp
// 逐元素相加，要求三个区间互不重叠
void add(float* __restrict dst, const float* __restrict a, const float* __restrict b, std::size_t n) {
    for (std::size_t i = 0; i < n; ++i) dst[i] = a[i] + b[i];
}
```

### 7.10 严格别名规则导致的优化事故如何避免？

- 通过不相关类型的指针访问同一对象违反严格别名规则，优化后可能读到旧值或丢失写入。
- 常见触发方式是把浮点数组当整数数组读取，或者用自定义结构体覆盖网络缓冲区。
- 正确做法是使用 `std::memcpy` 或 `std::bit_cast` 做类型转换，编译器通常能优化为单条指令。
- 联合体的类型双关在 C++ 中只允许读取共同初始序列，其他用法不可移植。
- 编译器的 `-fno-strict-aliasing` 可以关闭相关假设，代价是部分优化失效。
- 代码审查应当关注所有 `reinterpret_cast`，它们是别名问题的主要来源。

### 7.11 编译器如何权衡向量化的收益与代价？

- 收益取决于每次迭代的运算量与可并行的通道数，运算密度低的循环容易受内存带宽限制。
- 代价包括余数处理、跨步访问需要的数据重排，以及向量寄存器压力。
- 循环长度未知时编译器会生成运行时检查与标量回退路径，代码体积随之增加。
- 迭代之间存在依赖，或者访存无法按固定步长组织时，候选资格在代价模型之前就被排除。
- 目标指令集与编译选项决定可用宽度，关闭对应扩展时不会生成该宽度的指令。
- 强制向量化的编译指示会绕过代价模型，结果可能慢于标量版本。
- 优化报告（`-fopt-info-vec`、`-Rpass=loop-vectorize`）给出估计收益与拒绝原因，可与实测对照。

### 7.12（辨析）`-ffast-math` 的收益与风险是什么？

- 收益是允许重排浮点运算、忽略 NaN 与无穷、把除法转为乘法，从而提高向量化机会。
- 风险是结果不再符合 IEEE 754 语义，涉及 NaN 传播、符号零与结合律的代码会得到不同结果。
- 依赖浮点确定性的逻辑，例如校验和、回放与跨平台一致性，不能开启该选项。
- 该选项会设置多个子选项，可以只开启允许重排的部分，保留 NaN 处理。
- 科学计算中的收益可能显著，金融与图形管线需要逐项评估。
- 测试用例应当包含边界值，否则差异在回归中难以发现。

### 7.13 常量传播与死代码消除如何被阻止？

- 通过 `volatile` 访问、汇编语句或外部函数调用会阻断常量传播。
- 取地址并传递给不透明函数会让编译器假定对象可能被修改。
- 动态库边界与函数指针调用使编译器无法看到实现。
- 调试构建为便于观察保留了变量，也会阻止部分消除。
- 虚函数与异常路径增加控制流复杂度，降低消除效果。
- 把配置读取放在初始化阶段并存入常量全局或传值参数，可以让热路径享受常量传播。

### 7.14 `volatile` 对优化的限制有多大？

- `volatile` 要求每次访问都真实发生且顺序不变，编译器不能缓存、合并或删除。
- 它不提供线程间同步语义，不能替代原子操作。
- 每次访问都是一次内存操作，在热循环中会显著降低性能。
- 用于内存映射寄存器时是必要的，用于普通共享变量时通常是误用。
- `volatile` 还会阻止周围的变换，例如把循环内的读提到循环外。
- 需要原子性时使用 `std::atomic`，需要顺序时使用内存序参数。

### 7.15（场景）换编译器后性能下降如何归因？

- 先确认构建选项一致：优化等级、目标架构、LTO、数学库与宏定义。
- 比较关键循环的生成代码，查看向量化与展开是否发生。
- 用优化报告对比两套编译器的内联优化与向量化决策。
- 用硬件计数器对比 IPC、缓存未命中与分支预测失败，判断差异属于前端、后端还是访存。
- 检查是否依赖了未定义行为，不同编译器对未定义行为的处理不同，可能同时改变性能与正确性。
- 若差异集中在少数函数，可以针对这些函数添加属性或改写循环，避免依赖启发式。

### 7.16 LTO 与 PGO 分别改善什么？

- LTO 让编译器在链接期看到跨翻译单元的函数体，改善内联优化、去虚化与跨过程常量传播。
- LTO 增加链接时间与内存占用，并可能因过度内联优化导致代码膨胀。
- PGO 用真实负载采集分支与调用频率，让内联优化与代码布局按实际热路径决定。
- PGO 的收益依赖训练负载的代表性，训练集偏离线上分布时结果可能变差。
- 两者可以组合，先用 PGO 数据指导跨模块内联优化，再观察布局对指令缓存的影响。
- 使用 PGO 需要把采样数据纳入构建流水线，并随代码变化定期重新采集。

### 7.17（实现）如何用编译指示控制向量化？

- `#pragma omp simd` 要求对循环做 SIMD 化，需要编译器支持对应的 OpenMP 语法。
- `#pragma GCC ivdep` 声明迭代之间无依赖，用于消除编译器的保守假设。
- `#pragma clang loop vectorize(enable)` 与 `vectorize_width(8)` 控制是否向量化与向量宽度。
- 这些指示只是对编译器的承诺，承诺错误会产生错误结果。
- 指示应当配合优化报告确认是否被采纳，未被采纳时不会静默生效。
- 可移植代码应当把指示封装在宏中，按编译器能力启用。

```cpp
void axpy(float a, const float* x, float* y, std::size_t n) {
#if defined(__clang__)
#  pragma clang loop vectorize(enable) interleave(enable)
#elif defined(__GNUC__)
#  pragma GCC ivdep
#endif
    for (std::size_t i = 0; i < n; ++i) y[i] += a * x[i];   // 要求 x 与 y 不重叠
}
```

### 7.18 循环展开的收益边界在哪里？

- 展开减少循环控制开销与分支，提高指令级并行。
- 展开增加寄存器压力，超出寄存器数量会产生溢出到栈的读写。
- 展开增大代码体积，可能超出指令缓存或循环缓冲。
- 迭代次数少或循环体很大时，展开收益有限。
- 编译器通常自动展开小循环，手动展开主要用于配合向量化或消除余数处理。
- 展开因子应当通过基准测试确定，不同微架构的最优值不同。

### 7.19（场景）发布后出现正确性回归，怀疑优化导致，如何定位？

- 先用同一份源码在 `-O0` 与发布优化等级下运行测试，确认差异是否随优化等级出现。
- 用未定义行为检测器与地址检测器构建并运行，捕获越界、溢出与别名违规。
- 检查近期改动中的 `reinterpret_cast`、指针算术与有符号溢出。
- 用二分法定位到具体优化项，例如关闭向量化或关闭严格别名假设后差异消失。
- 被优化暴露的缺陷通常早已存在，修复应当针对未定义行为本身，长期关闭优化只是临时措施。
- 回归测试应当覆盖边界输入，优化相关的缺陷常出现在循环边界与对齐假设上。

### 7.20 如何建立防止优化假设失效的基准测试？

- 基准测试使用与发布一致的编译选项与目标架构，并记录编译器版本。
- 用 `DoNotOptimize` 一类屏障防止被测代码被整体消除，同时不引入额外内存操作。
- 报告分位数与吞吐，而不只是均值，并固定 CPU 频率与亲和性以减少噪声。
- 把基准测试纳入持续集成，按提交记录趋势，超过阈值触发告警。
- 对关键循环保存优化报告，编译器升级后对比决策变化。
- 基准中应当排除首次运行的冷启动成本，需要预热并重复测量。

```cpp
template <class T>
inline void do_not_optimize(T const& v) {
    asm volatile("" : : "r,m"(v) : "memory");   // 阻止消除，同时保持值语义
}

std::uint64_t sink = 0;
for (int i = 0; i < reps; ++i) {
    auto t0 = std::chrono::steady_clock::now();
    auto r = run_once();
    auto t1 = std::chrono::steady_clock::now();
    do_not_optimize(r);
    sink += std::chrono::duration_cast<std::chrono::nanoseconds>(t1 - t0).count();
}
```

## 8. 剖析工具与火焰图

### 8.1 `perf stat` 能给出哪些层次的结论？

- 给出整段时间内的计数汇总：周期数、指令数、缓存与 TLB 事件、上下文切换与页错误。
- 派生指标如 IPC、每千条指令的缓存未命中与分支预测失败率，用于判断瓶颈类型。
- 默认事件集有限，更多事件需要 `-e` 指定，事件名称与可用性取决于 CPU 型号与内核版本。
- 计数是进程级或系统级汇总，无法直接定位到函数。
- 适合验证假设与对比两次运行的差异，不适合首次定位热点。
- 事件数超过计数器数量时内核按时间片轮转多路复用，结果按比例估算，精度下降。

### 8.2 `perf record` 的采样频率如何选择？

- 默认按周期采样，`-F` 指定每秒采样次数，频率越高开销越大、统计越细。
- 高频采样适合短时定位，长时运行的低频采样更适合观察整体分布。
- 采样也可以绑定到具体事件，例如按缓存未命中或分支预测失败触发。
- 采样本身会污染缓存并增加内核开销，开销过大时结论会发生偏移。
- 频率过低会漏掉执行时间占比小但调用频繁的函数。
- 需要按进程、CPU 或 cgroup 过滤，避免系统其他负载混入样本。

### 8.3 火焰图的横轴与纵轴分别表示什么？

- 横轴表示样本占比，所有矩形宽度之和等于总样本量，宽度不代表时间顺序。
- 纵轴表示调用栈深度，自下而上是调用关系，顶部是正在执行的函数。
- 每个矩形是该栈帧在样本中出现的次数，相同栈合并后形成层级。
- 颜色通常只用于区分不同栈，不承载性能含义。
- 顶部宽而平的矩形表示该函数自身消耗大量时间，顶部窄而深的分支表示调用链碎片化。
- 火焰图不显示调用次数与单次耗时，只显示样本占比。

### 8.4（陷阱）火焰图缺少帧意味着什么？

- 栈不完整时样本会归到未知帧，常见原因是缺少帧指针或缺少展开信息。
- 优化构建省略帧指针会让基于栈回溯的采集失效，需要改用基于调试信息的展开或保留帧指针。
- 被内联优化的函数不会出现在栈中，其耗时计入调用者，看到的热点可能是外层函数。
- 即时编译生成的代码缺少符号，需要运行时提供的映射表才能展开。
- 内核栈与用户栈的混合采集需要正确的权限与配置，缺失一侧时调用链断裂。
- 尾调用会消除栈帧，使调用关系与源码不一致。

### 8.5 如何区分 on-CPU 与 off-CPU 耗时？

- on-CPU 剖析只采样正在运行的线程，阻塞、等待锁与睡眠的时间不会出现在样本中。
- off-CPU 剖析记录线程离开 CPU 与重新被调度的时间及阻塞栈，反映等待原因。
- 一个请求的总延迟等于 on-CPU 时间与 off-CPU 时间之和，只分析前者会低估等待占比。
- 锁竞争、I/O 等待、缺页与调度延迟都属于 off-CPU 范畴。
- off-CPU 采集需要内核支持与足够权限，开销高于 on-CPU 采样。
- 两者结合才能判断延迟来自计算还是等待。

| 维度 | on-CPU 剖析 | off-CPU 剖析 |
| --- | --- | --- |
| 采样对象 | 正在运行的线程 | 已离开 CPU 的线程 |
| 主要信息 | 热点函数与指令 | 阻塞原因与等待栈 |
| 典型事件 | 周期、缓存未命中 | 调度切换、唤醒 |
| 开销 | 较低 | 较高 |
| 适用问题 | 计算热点 | 延迟构成 |

### 8.6 IPC 偏低如何进一步归因？

- IPC 低于微架构的可持续水平说明流水线存在停顿，需要区分前端、后端与退休阶段。
- 前端停顿来自指令缓存未命中、分支预测失败与指令译码带宽不足。
- 后端停顿来自数据缓存未命中、执行单元饱和与寄存器依赖链过长。
- 用顶层停滞事件拆分周期占比，例如前端空闲周期与后端无退休周期。
- 结合热点函数的指令构成判断，访存密集与计算密集的停顿来源不同。
- IPC 受频率与超线程邻居影响，跨机器对比需要在相同配置下进行。

### 8.7 缓存未命中的计数器如何解读？

- 需要区分 L1、L2 与末级缓存的访问与未命中，以及从内存填充的次数。
- 未命中率高不必然意味着瓶颈，命中延迟与未命中代价共同决定影响。
- 预取命中会掩盖真实的内存访问模式，统计上表现为未命中率低但带宽高。
- 伪共享表现为同一缓存行被多个核心反复失效，需要结合核心级事件分析。
- 事件名称与统计口径由微架构定义，跨平台对比可能不成立。
- 用改动前后的填充次数做差分，比看绝对值更有意义。

### 8.8 分支预测失败如何度量？

- 硬件计数器提供分支指令数与预测失败数，比值反映预测质量。
- 间接调用与多态分派是预测失败的主要来源，目标分布随机时代价高。
- 一次预测失败会造成流水线清空，代价约为十几个周期，具体数值由实现定义。
- 编译器可以用条件传送替代分支，避免预测失败但增加无条件计算。
- 数据相关的分支（二分查找、文本解析）难以预测，可以改为无分支写法或分块处理。
- 预测失败率与分支密度共同决定影响，分支稀少时即使失败率高也可以忽略。

### 8.9（实现）如何在不改代码的情况下增加观测点？

- `perf probe` 可以在函数入口、返回或指定行插入动态探针，依赖调试信息定位。
- 用户态探针适用于已部署的二进制，需要保留符号与调试信息。
- 探针命中时执行内核注入的处理逻辑，开销高于普通采样，不适合高频路径。
- 探针可以读取寄存器与参数，用于确认调用次数与入参分布。
- 在生产环境使用应当限制命中次数并设置超时，避免影响服务。
- 探针不修改被测代码，适合确认假设而非长期监控。

### 8.10 VTune 的微架构分析视图适合回答什么问题？

- 自顶向下的瓶颈分类按退休、前端绑定、后端绑定与投机给出占比，直接指向主要瓶颈。
- 内存访问分析给出缓存层级、远端内存访问与带宽饱和度。
- 线程与并发分析给出等待、同步开销与负载不均。
- 向量化分析给出循环是否向量化、使用的指令宽度与对齐问题。
- 平台支持与事件可用性依赖 CPU 型号，非对应厂商的平台功能受限。
- 图形化视图便于定位，结论仍需要回到代码与数据结构验证。

### 8.11（场景）线上无法安装工具时如何采样？

- 优先使用内核自带的采样能力，若 `perf` 可用则记录到文件后离线分析。
- 没有 `perf` 时可以读取 `/proc` 下的统计与内核跟踪点，获取有限信息。
- 托管运行时的内置剖析接口可以绕过系统工具，代价是只能看到运行时层面的栈。
- 在应用内嵌入采样器，按固定频率读取调用栈并写入环形缓冲区。
- 采样数据应当限速并本地缓冲，避免采集本身引发磁盘或网络压力。
- 任何线上采集都需要先评估开销与权限，并在灰度实例上验证。

### 8.12 分配剖析如何定位泄漏与碎片？

- 记录每次分配的调用栈、大小与存活状态，按调用栈聚合存活字节数。
- 泄漏表现为某条调用栈的存活字节随请求数单调增长。
- 碎片表现为存活字节稳定但分配器占用持续上升。
- 采样式分配剖析开销低但会漏掉小分配，全量记录开销高，适合短时排查。
- 需要区分缓存、连接池等有界结构与无界增长的结构。
- 结合 `/proc` 中的映射信息可以判断增长来自堆还是匿名映射。

### 8.13（辨析）采样与插桩的偏差来源有何不同？

- 采样偏差来自采样点分布，短函数被采到的概率低，热点容易被系统性高估或低估。
- 插桩偏差来自观测代码本身，每次调用都记录会改变时序、缓存状态与内联优化决策。
- 采样对程序影响小但统计精度受频率限制，插桩精确但会改变被测对象。
- 采样无法记录未被调度到 CPU 的等待，插桩可以在事件点记录时间戳，覆盖等待。
- 采样适合定位热点，插桩适合计数与顺序分析。
- 两种方法的结论应当互相印证，单一方法的异常值需要复核。

### 8.14 火焰图与调用图相比缺少什么信息？

- 火焰图不显示调用次数，同一函数被调用一次与一万次在宽度上可能相同。
- 火焰图不显示时间顺序与并发，多线程样本合并后无法还原交错的执行。
- 调用图可以显示环与多重调用关系，火焰图把递归折叠为重复帧。
- 火焰图忽略被内联优化的中间层，调用关系与源码不一致。
- 需要次数与时序时应当使用调用计数、跟踪或时间线视图。
- 火焰图的价值在于快速识别占比最大的路径，不用于精确归因。

### 8.15 如何用差分火焰图定位性能回归？

- 采集改动前后的相同负载样本，按栈对齐后相减，得到各栈的样本增减。
- 差异为正的栈对应变慢的路径，差异为负的栈对应变快的路径，颜色含义由工具约定。
- 差分要求两次采集的负载、采样频率与代码路径可比，否则差异混入噪声。
- 回归集中在少数栈时可以直接定位，分散在大量栈时说明是系统性变化。
- 采样量不足时差分结果抖动明显，需要增加采样时长或重复采集。
- 差分结果应当与分位数指标一起判断，样本占比变化不必然对应端到端延迟变化。

### 8.16 容器与虚拟化环境下的计数器为何不可用？

- 硬件性能计数器通常不允许在虚拟机内直接访问，宿主机会拦截或虚拟化部分事件。
- 容器共享内核，`perf` 需要的能力常被安全策略禁用。
- 即使事件可读，多租户环境下的计数包含邻居负载，无法归因到单一容器。
- 部分云平台提供虚拟化的计数器，事件集合与语义受限，由平台定义。
- 可以退回到软件事件，例如上下文切换与页错误，配合应用内埋点。
- 需要硬件计数时应当在独占的物理机上定位，再把结论带回生产环境验证。

### 8.17（场景）压测显示 P99 高但 CPU 不满，如何继续分析？

- CPU 不满说明瓶颈不在计算，优先检查等待：锁、I/O、连接池与线程池队列。
- 观察 off-CPU 时间与运行队列长度，区分线程可运行但缺少 CPU 与线程阻塞。
- 检查外部依赖的响应时间，下游的尾延迟会传导到上游。
- 检查调度延迟与频率变化，节能策略降频会让延迟上升而利用率不高。
- 检查垃圾回收或周期性任务的停顿，它们不占满 CPU 但会造成集中延迟。
- 用请求级分段计时确认时间花在哪个阶段，再对该阶段做剖析。

### 8.18 即时编译生成的代码如何出现在剖析结果中？

- 即时编译（JIT）生成的代码没有静态符号，采样得到的地址需要运行时提供的符号映射才能解析。
- 运行时通常提供映射文件或登记接口，把生成的代码段登记为可解析区域。
- 未登记时样本会落到匿名映射或未知符号，表现为大量无法归因的样本。
- 优化会进一步模糊源码对应关系，需要保留调试信息或映射表。
- 生成的代码生命周期短时，符号表需要及时更新，否则地址会映射到错误函数。
- 分析时应当先确认符号解析覆盖率，再解读热点分布。

### 8.19（实现）如何降低剖析自身的开销？

- 先测量无观测时的基线，再逐级增加观测，比较指标变化幅度。
- 采样频率与探针密度是主要开销来源，应当从低开销配置开始。
- 观测会改变缓存与分支预测状态，热路径上的探针尤其明显。
- 记录缓冲区使用无锁环形队列，避免观测路径引入锁竞争。
- 采集数据的落盘与聚合应当异步进行，避免阻塞被测线程。
- 结论需要在关闭观测后复测确认，观测期间的表现不应当作为最终数据。

```cpp
struct Sample { std::uintptr_t pc; std::uint32_t tid; };

class SampleRing {                       // 采样线程写，分析线程读
    static constexpr std::size_t N = 1u << 16;
    std::array<Sample, N> buf_{};
    std::atomic<std::size_t> head_{0};
public:
    void push(const Sample& s) {
        std::size_t h = head_.load(std::memory_order_relaxed);
        buf_[h & (N - 1)] = s;
        head_.store(h + 1, std::memory_order_release);
    }
    std::size_t size() const { return head_.load(std::memory_order_acquire); }
};
```

### 8.20（场景）如何为一套服务建立持续的性能基线？

- 固定硬件、内核、编译选项与负载模型，基线才有可比性。
- 采集端到端分位数、吞吐与资源使用，同时保留剖析样本用于回归分析。
- 每次发布自动运行同一套基准，结果与历史版本对比并记录差异原因。
- 对波动较大的指标使用多轮采样取中位数，并记录离散程度。
- 把性能预算写成阈值，超过阈值阻断发布或要求补充说明。
- 基线需要随容量规划定期复核，负载模型变化后旧基线失效。

## 9. 低延迟技术

### 9.1 忙等与阻塞等待的延迟差异来自哪里？

- 阻塞等待涉及陷入内核、加入等待队列与调度器切换，唤醒延迟通常在微秒量级，由实现与系统负载决定。
- 忙等停留在用户态反复检查条件，条件满足到继续执行只隔几条指令。
- 忙等的代价是占满一个核心，核心数不足时会挤占其他线程的 CPU 时间。
- 混合策略是先短时自旋再阻塞，兼顾低延迟与 CPU 占用。
- 自旋期间的内存访问持续占用缓存与带宽，多个线程同时自旋会加剧争用。
- 忙等适合延迟敏感且等待时间短的场景，等待时间不可预测时应当阻塞。

### 9.2（实现）自旋等待如何避免过度占用？

- 在自旋循环中插入暂停指令（x86 的 `pause`），降低功耗并让出超线程资源。
- 限制自旋次数，超过阈值后让出 CPU 或阻塞在等待队列上。
- 进入循环前先检查一次条件，避免无谓自旋。
- 使用退避策略，随失败次数增加暂停时间，减少缓存行争用。
- 自旋线程应当绑定到独立核心，避免与关键线程共享物理核。
- 记录自旋次数与超时次数，作为容量与配置调整的依据。

```cpp
void wait_ready(std::atomic<bool>& flag) {
    for (int i = 0; i < 1000; ++i) {
        if (flag.load(std::memory_order_acquire)) return;
        __builtin_ia32_pause();            // x86：让出超线程与流水线资源
    }
    while (!flag.load(std::memory_order_acquire))
        std::this_thread::yield();         // 退化为让出，避免长期占用
}
```

### 9.3 无锁路径的最坏延迟由哪些部分构成？

- 无竞争时一次比较交换相当于一条带锁前缀的指令，代价约为数十个周期，具体由实现定义。
- 竞争时失败方需要重新读取、重新计算并重试，冲突概率上升会放大重试次数。
- 缓存行在核心之间迁移时，写方需要等待其他副本失效，互连延迟进入关键路径。
- 要求顺序一致语义时，屏障会限制重排并等待存储缓冲排空，进一步拉长临界路径。
- 节点回收机制在释放路径上引入额外同步，回收延迟会转嫁到申请方。
- 中断、频率变化与调度抢占会推高最坏值，与算法本身无关。
- 评估应当看 P999 与最大值，均值会掩盖重试与迁移造成的长尾。

### 9.4 内核旁路绕过了哪些开销？

- 系统调用与内核协议栈处理，包括上下文切换、套接字层与网络层解析。
- 数据从内核缓冲区到用户缓冲区的复制。
- 中断处理与软中断调度带来的不确定延迟。
- 旁路后网卡直接写入用户态缓冲区，应用轮询收包。
- 代价是失去内核提供的连接管理、路由、防火墙与拥塞控制，需要自行实现或裁剪。
- 旁路方案通常独占网卡或队列，与常规内核网络共存需要额外配置。

### 9.5 DPDK 的轮询模式为什么能降低延迟？

- 轮询模式驱动在用户态持续检查接收描述符，数据到达后立即可见，不需要等待中断。
- 无中断意味着没有中断合并与中断上下文的切换开销。
- 大页内存与预分配缓冲池减少运行期的分配与缺页。
- 每核独占队列与无锁环形队列避免跨核同步。
- 代价是核心被轮询占满，空闲时同样消耗功耗，核心不足时吞吐下降。
- 轮询线程与业务线程的核间布局需要协调，避免共享数据在核心之间迁移。

### 9.6（场景）网卡队列与 CPU 核如何绑定？

- 多队列网卡把不同流哈希到不同队列，每个队列由一个核心处理，减少跨核迁移。
- 通过中断亲和性或驱动配置把队列绑定到固定核心，避免软中断在核心之间漂移。
- 绑定后需要确认实际分布，用中断统计与队列计数验证。
- 接收端缩放哈希对同一连接稳定，但连接数少时可能出现队列倾斜。
- 队列数与核心数不匹配时应当调整，队列多于核心会造成切换。
- 绑定降低弹性，核心故障或负载变化时需要重新分配。

### 9.7 跨 NUMA 节点的内存访问延迟从哪里来？

- 处理器通过互连访问远端节点的内存，额外延迟约为本地访问的 1.5 至 2 倍，具体比例由平台决定。
- 只有缓存未命中才会触发远端访问，命中本地缓存不经过互连，访存模式决定远端访问的实际占比。
- 首次触碰决定页的归属，初始化阶段由哪个线程触碰内存会固定其节点。
- 线程与内存分属不同节点时，每次未命中都要跨互连，带宽也受互连容量限制。
- 按节点分区数据并就近绑定线程，可以把远端访问降到接近零；共享的热点数据应当复制到各节点。
- 绑定时应当同时约束 CPU 与内存，只绑定 CPU 时页分配仍由内核按默认策略决定。
- 验证方式是对比本地与远端访问的计数，而不是只看进程的整体延迟。

### 9.8（实现）如何把线程绑定到指定 CPU？

- Linux 上使用 `sched_setaffinity` 设置线程的 CPU 掩码，或使用 `pthread_setaffinity_np`。
- 绑定时应当排除被内核占用的核心，结合 `isolcpus` 或 cgroup 隔离。
- 绑定后线程不再迁移，缓存局部性稳定，但负载不均时无法自动平衡。
- 需要读取实际绑定结果确认，容器内的 CPU 编号可能与宿主机不同。
- 多线程程序应当为每个线程指定不同核心，避免同一物理核的超线程兄弟争抢。
- 绑核属于部署配置，应当与启动脚本和监控一起管理，避免手工设置被覆盖。

```cpp
void pin_to_core(std::thread& t, int cpu) {
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    int rc = pthread_setaffinity_np(t.native_handle(), sizeof(set), &set);
    if (rc != 0)
        throw std::system_error(rc, std::generic_category(), "setaffinity");
}
```

### 9.9 中断与内核线程如何干扰实时性？

- 网卡与磁盘中断会打断用户态线程，中断处理占用核心并使缓存失效。
- 后台内核线程的周期性工作会引入不确定的调度。
- 通过中断亲和性把中断移出关键核心，或用 `isolcpus` 隔离核心可以减少干扰。
- 完全隔离需要配合 `nohz_full` 与 `rcu_nocbs`，减少时钟中断与回调处理。
- 隔离后关键核心不再承担系统工作，代价是可用核心减少。
- 隔离配置需要验证，检查中断统计与内核线程的实际位置。

### 9.10 延迟敏感路径上的时间戳如何获取？

- `clock_gettime` 走 vDSO 时不需要系统调用，开销在几十纳秒量级，具体由实现定义。
- 时钟源由内核选择，`tsc` 的读取代价最低，`hpet` 一类需要访问外设寄存器，代价高一个数量级。
- 不变 TSC 在频率变化时保持恒定速率，是纳秒计时的常用基础；非不变 TSC 不能用于跨核计时。
- 跨核比较时间戳需要确认各核 TSC 已同步，否则差值包含固定偏移。
- 读取 TSC 需要防止乱序，序列化指令会显著增加开销，只在测量区间端点使用。
- 时间戳应当在请求入口与出口各取一次，中间分段按需增加，避免热点路径频繁读取。
- 单调时钟优于墙上时钟，后者会因校时跳变产生负的持续时间。

### 9.11 批处理与合并如何影响尾延迟？

- 批处理把多个请求合并为一次处理，提升吞吐但让先到的请求等待后到的请求。
- 批次越大，单个请求的排队等待越长，尾延迟上升幅度超过平均值。
- 超时触发的批次可以限制最长等待，代价是批次大小波动。
- 中断合并与协议栈聚合属于同类机制，合并窗口直接决定延迟下界。
- 日志与指标上报的批量刷写应当放在关键路径之外，或者由独立线程承担。
- 批处理参数应当按分位数调优，按吞吐调优容易掩盖尾延迟恶化。

### 9.12（辨析）实时调度策略的适用边界是什么？

- `SCHED_FIFO` 与 `SCHED_RR` 按优先级抢占普通任务，适合必须按时执行的短任务。
- 实时任务不受时间片限制，长时间占用会阻塞同核上的所有普通任务，需要自行限时。
- 内核的实时带宽限制会截断持续占用，超限后实时任务被降级，表现为周期性停顿。
- 优先级反转需要优先级继承或协议处理，否则低优先级任务持锁会拖住高优先级任务。
- 实时策略需要相应权限，容器内通常被禁止，部署前要确认能力与内核参数。
- 实时任务只应覆盖关键路径，I/O 与日志放在普通优先级线程，避免优先级倒挂。

### 9.13 大页如何降低 TLB 未命中？

- 使用 2 MiB 或 1 GiB 页时，单个 TLB 表项覆盖的地址范围扩大，所需表项数量下降。
- TLB 未命中需要页表遍历，代价可达数十个周期，随机访问大工作集时影响明显。
- 显式大页需要预留与配置，透明大页由内核自动合并，行为不完全可控。
- 大页会提高内存占用粒度，小对象密集的分配可能浪费。
- 大页与 NUMA 结合时，首次触碰的位置决定节点归属。
- 启用后应当用计数器确认 TLB 未命中下降，并观察是否出现分配失败。

### 9.14（辨析）轮询与中断在吞吐和延迟上如何取舍？

- 中断在低负载时节省 CPU，响应延迟受中断合并与调度影响。
- 轮询在低负载时浪费 CPU，但响应延迟稳定且低。
- 高负载下中断频繁触发，中断风暴会降低吞吐，轮询在高负载下效率更高。
- 混合模式在低负载时使用中断，高负载时切换到轮询，兼顾两种场景。
- 选择依据是负载水平、延迟要求与可用核心数。
- 延迟敏感场景通常牺牲空闲时的功耗换取确定性。

### 9.15 内存屏障对延迟的影响如何评估？

- 屏障限制指令重排，可能阻止编译器与处理器重叠执行，增加流水线停顿。
- 全屏障代价最高，获取与释放语义在多数平台上只需单向约束。
- x86 的加载与存储顺序较强，多数获取释放操作不需要额外指令，具体由实现定义。
- 弱序平台需要显式屏障，代价与屏障类型相关。
- 评估方法是对比不同内存序下的分位数与吞吐，单次操作的测量不足以支撑结论。
- 在热路径上减少共享写入，比调整内存序更有效。

### 9.16 RDMA 与共享内存的适用边界是什么？

- RDMA 通过网卡直接访问远端内存，绕过对端 CPU，适合跨机低延迟通信。
- 共享内存适合同一主机内的进程间通信，延迟在百纳秒量级，不经过网络协议栈。
- RDMA 的延迟仍高于本机共享内存，且需要处理连接管理、内存注册与完成队列。
- 共享内存需要额外的同步机制，跨进程通知仍可能进入内核。
- 跨机场景中 RDMA 相比内核套接字能显著降低延迟与 CPU 占用。
- 选型取决于通信范围、消息大小与可靠性要求，小消息高频场景对延迟最敏感。

### 9.17（场景）内核旁路方案如何设计故障降级？

- 旁路路径绕开内核，驱动或网卡异常时没有协议栈兜底，需要显式的健康检查与切换。
- 启动时应当验证网卡绑定、队列数量与大页配置，失败则退回内核路径，而不是启动后静默丢包。
- 队列满时需要明确的策略：丢弃、反压或切换到内核路径，策略应当可配置并可观测。
- 双路径并存时连接状态需要两侧同步，切换会造成已建立的会话中断。
- 监控指标应当覆盖每队列收发包数、丢包数与轮询线程心跳。
- 演练要包含网卡重置与驱动重载，确认恢复后能重新接管队列。

### 9.18（实现）如何实现无竞争的统计计数？

- 每个线程维护本地计数器，读取时汇总，避免所有线程写同一缓存行。
- 本地计数器按缓存行对齐，防止相邻计数器互相失效。
- 汇总读取允许短暂不一致，统计用途通常不需要全局原子快照。
- 需要单调一致的快照时使用版本号或双缓冲，读侧重试。
- 高频更新低频读取时，本地聚合的开销接近普通自增。
- 计数器数量随线程数增长，线程退出时需要把本地值合并到全局。

```cpp
struct alignas(64) Counter {
    std::atomic<std::uint64_t> value{0};
};

Counter shard[8];                    // 每个线程按下标取自己的分片

void record(std::size_t idx) {
    shard[idx].value.fetch_add(1, std::memory_order_relaxed);
}

std::uint64_t total() {
    std::uint64_t sum = 0;
    for (auto& c : shard) sum += c.value.load(std::memory_order_relaxed);
    return sum;
}
```

### 9.19（陷阱）延迟敏感线程与普通任务混部会带来什么后果？

- 共享物理核时，普通任务的突发计算会挤占超线程兄弟的发射资源与缓存。
- 内存带宽与末级缓存被其他任务占用，延迟敏感线程的未命中代价上升。
- 调度器会把普通任务迁移到空闲核心，迁移过程伴随缓存失效与 TLB 影响。
- 容器配额按 CPU 时间计，短时突发仍可能占满一个核，配额不构成延迟保证。
- 混部还会带来页缓存与网络软中断的争用，表现为与自身负载无关的抖动。
- 隔离手段包括独占核心、cgroup 的 CPU 与内存带宽限制，以及中断亲和性。

### 9.20（场景）低延迟系统的上线验收应当包含哪些检查？

- 确认绑核与隔离生效：线程亲和性、隔离核心列表与中断分布都与设计一致。
- 确认大页与内存策略生效：页大小、NUMA 归属与预分配容量符合预期。
- 用稳定负载测量分位数与最大值，并记录观测开销，避免把采集成本算进业务延迟。
- 验证降级路径：旁路故障、队列满与依赖超时都能按预期切换且不丢关键请求。
- 验证监控与告警：尾延迟、丢包、自旋超时与队列深度的阈值都能触发。
- 保留回滚方案，并在灰度实例上对比新旧版本的分位数。

## 10. 尾延迟与确定性

### 10.1 为什么平均延迟不能代表尾延迟？

- 平均值会被大量快请求拉低，10 万次 1 ms 的请求中混入 100 次 1 s 的请求，均值只上升约 1 ms。
- 用户侧耗时由最慢的下游调用决定，一次重试就可能把单次延迟放大数倍。
- 排队系统中利用率接近 1 时，平均延迟与 P99 同时上升，后者的斜率更大。
- 监控应同时保留 P50、P99、P999 与最大值，并记录样本数与统计窗口。
- 均值受样本量影响较小，尾部分位数对样本量敏感，样本不足时读数不可信。
- 服务等级目标应写成分位数加窗口的形式，例如 1 分钟内 P99 小于 10 ms。

### 10.2（辨析）P99 与 P999 的观测差异体现在哪里？

- P99 覆盖 99% 的请求，常作为面向用户的指标；P999 反映更极端的排队与调度事件。
- 每秒 1 万个请求时，P999 对应每秒 10 个慢请求，P9999 对应每秒 1 个慢请求。
- 分位数不可直接平均，两个实例的 P99 求平均不等于集群 P99，需要合并直方图后计算。
- 长尾常呈多峰：P99 落在第一段慢峰，P999 才暴露锁等待或内存回收造成的第二段。
- 统计窗口过短时 P999 由个别事件决定，尾部样本需要达到数百个才有参考价值。
- 对外承诺用 P99，内部诊断同时看 P999 与最大值，避免只盯一个数字。

### 10.3（实现）如何实现一个低开销的延迟直方图？

- 线性分桶在高精度下内存过大，常用指数分桶：每个倍频固定桶数，相对误差有界。
- HdrHistogram 以 3 位有效数字记录，覆盖纳秒到小时量级，内存为数百 KB。
- 记录路径使用每线程直方图，读取时逐桶合并，避免全局锁进入热路径。
- 合并只能逐桶相加，分位数在合并后的直方图上计算。
- 分桶边界决定误差上限，对外报告应给出分辨率，例如 1% 相对误差。
- 记录本身有开销，时钟读取约为几十纳秒，需要用空操作基线扣除或评估。

### 10.4 协调遗漏如何扭曲压测结果？

```cpp
auto due = start + i * interval;
std::this_thread::sleep_until(due);
call();
auto t1 = Clock::now();
record(t1 - due);                       // queueing delay included
```

- 压测工具按固定间隔发请求，某次请求阻塞 1 s 时，后续请求被推迟而非按时发出，慢样本被系统性跳过。
- 结果是分位数偏乐观，真实用户会遇到排队叠加后的延迟。
- 修正方法是以计划发送时间为起点记录延迟，把等待时间计入样本。
- wrk2 用固定速率与校正直方图实现该修正，JMeter 等工具需要自行补偿。
- 开环压测与闭环压测结论不同，闭环在系统饱和时自动降速，掩盖排队。
- 报告延迟时必须同时给出到达率与并发模型，否则数字不可比较。

### 10.5 长尾延迟的来源如何分类？

- 排队：利用率过高、线程池耗尽、连接池不足、队列积压。
- 调度：处理器争用、优先级反转、cgroup 限流、虚拟化环境的窃取时间。
- 内存：缺页、TLB 未命中、分配器竞争、内存回收。
- 同步：锁竞争、原子操作造成的缓存行迁移、条件变量唤醒延迟。
- 外部依赖：下游慢调用、DNS 解析、TLS 握手、磁盘抖动。
- 运行时：日志落盘、动态链接、异常路径、定时器集中触发。
- 分类的作用是选择观测手段：排队看利用率，调度看 off-CPU 时间，内存看缺页计数。

### 10.6（场景）线上 P99 从 8 ms 升到 80 ms，如何定位？

- 先确认范围：单机房还是全局、单版本还是全版本、固定时段还是随机出现。
- 对照发布与配置变更时间线，检查新版本、连接池参数、日志级别与下游超时设置。
- 观察利用率与队列长度：处理器饱和指向容量问题，处理器空闲而延迟高指向等待。
- 用 `perf top` 查看热点，用 `perf sched` 或 off-CPU 分析查看阻塞点。
- 分布式追踪按阶段拆分耗时，确认时间花在服务内、下游还是网络。
- 检查慢请求的共性：同一台机器、同一分片、同一请求类型，逐步缩小到具体资源。
- 若只在高峰出现，优先怀疑排队与共享资源争用。

### 10.7 用户态分配如何进入尾延迟路径？

- 分配快路径只做空闲链表操作，慢路径进入 arena 锁或向内核申请内存。
- 大块分配走 `mmap`，释放走 `munmap`，伴随页表修改与 TLB 刷新，延迟可达数十微秒。
- 多线程竞争同一 arena 时出现锁等待，arena 数量受 `M_ARENA_MAX` 限制。
- 分配器元数据与用户数据可能共享缓存行，频繁分配释放造成缓存行在核心间迁移。
- 尾延迟敏感路径应预分配、使用固定大小分配器或对象池，并把批量释放移出请求路径。
- 判断依据是分配耗时直方图，以及剖析中分配与释放符号的占比。

### 10.8（陷阱）预分配内存一定优于按需分配？

```cpp
void prefault(void* p, std::size_t bytes) {
    auto* b = static_cast<volatile char*>(p);
    for (std::size_t i = 0; i < bytes; i += 4096)
        b[i] = 0;                       // touch one byte per page
}
```

- 预分配只保留地址空间，未触碰的页面在首次访问时仍会触发缺页。
- 预热关键路径可以摊薄缺页成本，代价是启动时间变长。
- 大页减少缺页与 TLB 未命中，但需要对齐与预留，且增加内存占用。
- 预分配过多会挤占页缓存与其它进程内存，触发全局回收，反而制造抖动。
- 按需增长在稳定负载下成本可摊薄，突发流量下才暴露。
- 恒定高负载适合预分配并预热，波峰明显的负载需要限制单次增长幅度并保留回收手段。

### 10.9 C++ 不依赖垃圾回收，回收仍会造成尾延迟吗？

- 引用计数：`std::shared_ptr` 的原子增减在跨核共享时产生缓存行争用，析构可能递归释放大量对象。
- 侵入式引用计数把计数放入对象，仍使用原子操作，但省去控制块的额外分配。
- 延迟回收：RCU 与 epoch 把释放推迟到读侧临界区全部退出，降低单次停顿但增加内存占用。
- 删除大树或大容器会在一次调用中释放大量内存，形成毫秒级停顿，应拆分或交给后台线程。
- 循环引用使对象长期不释放，内存增长最终触发系统级回收与换页。
- 度量手段是析构耗时直方图与堆增长曲线，不能只看分配耗时。

### 10.10 大块内存释放为什么会制造毛刺？

- glibc 对超过 `M_MMAP_THRESHOLD` 的块使用 `munmap`，每次释放都涉及系统调用与 TLB 失效。
- 阈值会随历史分配动态调整，大块释放行为随程序运行而变化，抖动难以复现。
- 频繁分配释放造成碎片，后续分配需要合并或向内核续租，延迟不可预测。
- `malloc_trim` 主动归还未用内存，代价是页表操作，不宜在请求路径调用。
- 固定大小对象池把释放变成链表操作，代价是内存不归还给系统。
- 观测可用 `mallinfo2`、`malloc_info` 与 `perf` 中的 `munmap` 事件。

### 10.11 锁竞争如何放大尾延迟？

- 竞争时线程进入 futex 等待，唤醒涉及调度延迟，通常为微秒到毫秒级。
- 持锁线程被抢占后，其余等待者排队，临界区的实际完成时间被拉长。
- 公平锁减少饥饿，但增加上下文切换；非公平锁吞吐高，尾部可能更长。
- 读写锁在写者频繁时退化，读操作可能长时间拿不到锁。
- 分段锁把竞争分散到多个桶，代价是内存占用与遍历复杂度。
- 观测手段包括锁等待直方图、`perf lock` 与 futex 跟踪。

### 10.12（辨析）无锁队列一定降低尾延迟？

- 无锁结构避免睡眠与唤醒，但高竞争下 CAS 失败重试消耗处理器，尾部由重试次数决定。
- 缓存行在核心间迁移的代价可能高于一次短临界区的互斥锁。
- 无锁队列的内存回收复杂，hazard pointer 与 epoch 增加读侧开销。
- 有界无锁队列在满时仍需策略：丢弃、阻塞或覆盖，阻塞就回到锁语义。
- 低竞争场景两者差异有限，高竞争场景要看临界区长度与核心数。
- 选择依据是实测分位数与竞争程度，名称本身不构成理由。

### 10.13 CPU 隔离如何降低抖动？

```cpp
cpu_set_t set;
CPU_ZERO(&set);
CPU_SET(3, &set);
pthread_setaffinity_np(pthread_self(), sizeof(set), &set);
```

- `isolcpus` 把核心从通用调度器移出，`nohz_full` 减少该核的调度时钟中断，`rcu_nocbs` 把 RCU 回调移走。
- 隔离核仍需处理本地中断与核间中断，需要配合中断亲和性设置。
- 线程绑定用 `pthread_setaffinity_np` 或 `taskset`，内存与网卡队列应落在同一 NUMA 节点。
- 隔离减少迁移与争用，代价是这些核心不能承载通用负载，容量规划要留余量。
- 绑定后检查返回值，容器内可能因 cpuset 限制失败。
- 容器环境受 cgroup 与宿主调度影响，隔离效果需要实测确认。
- 验证指标是上下文切换次数、中断计数与延迟直方图的尾部。

### 10.14（场景）网络中断引起的周期性抖动如何排查？

- 查看 `/proc/interrupts` 的增长是否集中在少数核心，确认中断是否打到业务核。
- 网卡多队列用 `ethtool -l` 查看，用 `ethtool -X` 调整 RSS 分流。
- 中断亲和性写入 `/proc/irq/<n>/smp_affinity`，把中断与业务线程分到不同核心。
- 软中断在中断上下文或 `ksoftirqd` 中执行，可能挤占业务线程。
- 高频小包场景可调整 NAPI 批处理参数，代价是单包延迟上升。
- 用 `perf` 的 `irq:softirq_entry` 事件与延迟直方图按时间戳对齐。

### 10.15 频率调节与 C-state 如何影响尾延迟？

- 默认调频器按负载调整频率，负载突增时频率爬升需要时间，短请求落在低频区间。
- `performance` 调频器固定高频，降低爬升延迟，代价是功耗与散热。
- 深 C-state 的唤醒延迟可达数十到数百微秒，`intel_idle.max_cstate=1` 可限制深度。
- 长时间空闲后的第一个请求最容易受 C-state 影响，可用周期性空转缓解。
- 虚拟化环境下频率由宿主控制，客户机内的调优可能无效。
- 验证方法是同时记录频率、C-state 驻留时间与延迟分位数。

### 10.16 NUMA 访问如何影响尾延迟？

- 跨节点访问内存的延迟约为本地访问的两倍，带宽也受互联限制。
- 首次触碰决定页面落在哪个节点，线程迁移后可能长期远程访问。
- `numactl --membind` 与 `--cpunodebind` 把线程与内存绑定到同一节点。
- 网卡与中断应落在处理线程所在节点，否则数据复制跨节点。
- 同节点内也存在竞争：所有核心共享内存控制器与末级缓存。
- 观测用 `numastat`、`perf mem` 与按节点拆分的延迟分位数。

### 10.17 SMT 争用如何影响 P99？

- 同一物理核上的两个逻辑核共享执行单元与缓存，邻居的密集计算会拉长本线程延迟。
- 关闭 SMT 可降低抖动，但损失吞吐，需要按业务目标权衡。
- 邻居影响与指令组合有关，向量化负载对执行端口争用更敏感。
- 把延迟敏感线程绑定到不同物理核，或关闭同核的第二个逻辑处理器，可降低干扰。
- 观测方法是比较开启与关闭 SMT 的分位数，并记录同核邻居的利用率。
- 容器编排常忽略拓扑，两个延迟敏感线程可能落到同一物理核。

### 10.18（输出题）以下计时片段输出的耗时为何不可信？

```cpp
timespec a{}, b{};
clock_gettime(CLOCK_REALTIME, &a);
work();
clock_gettime(CLOCK_REALTIME, &b);
long ns = (b.tv_sec - a.tv_sec) * 1000000000L
        + (b.tv_nsec - a.tv_nsec);
std::printf("%ld\n", ns);
```

- `CLOCK_REALTIME` 受系统时间调整影响，NTP 校正时差值可能为负。
- 单次调用受调度、缓存与频率影响，方差远大于被测函数的耗时。
- 计时开销包含两次时钟读取，可能超过纳秒级函数本身的耗时。
- 编译器可能把无副作用的 `work` 调用删除，测量结果接近空操作。
- 应用 `CLOCK_MONOTONIC` 测量间隔，并批量重复后除以次数。
- 报告应给出最小值、中位数与分位数，单次最快值不代表典型性能。

### 10.19（场景）发布后 P99 回归如何归因到具体变更？

- 灰度发布按实例或流量比例放量，比较灰度组与对照组在同一窗口的分位数。
- 采集变更前后的剖析数据，比较热点函数与调用栈占比的变化。
- 检查二进制差异：编译器版本、优化级别、链接顺序、依赖库版本。
- 排除环境漂移：同机对比、固定频率、暂停后台任务。
- 若回归只出现在特定请求类型，按参数与数据分布分层统计。
- 无法复现时保留现场：核心转储、剖析数据、直方图快照与配置快照。

### 10.20 如何为尾延迟制定预算？

- 把端到端目标拆到各阶段：网络、排队、计算、下游调用、序列化，各阶段分配上限。
- 预算要包含重试放大，一次用户请求可能触发多次下游调用。
- 用排队论估算利用率上限，M/M/1 在利用率 80% 时排队延迟约为服务时间的 4 倍。
- 按峰值而非均值规划容量，为突发留出余量。
- 预算要可观测：每阶段埋点并输出分位数，超出预算时告警。
- 定期用压测验证预算假设，负载模型变化后重新标定。

## 11. 并行与向量化

### 11.1 如何判断一个循环能否向量化？

- 依赖分析：跨迭代的写后读、读后写、写后写会阻止并行化。
- 归约（求和、最值、点积）可以向量化，需要编译器识别或显式声明。
- 指针别名是主要障碍，编译器无法证明不重叠时生成保守代码或运行时检查。
- 循环体内有函数调用、异常或复杂分支时，需要内联优化或改写为掩码运算。
- 访问模式应连续，跨步与间接索引需要收集与散射指令，收益下降。
- 以编译器的向量化报告为准，源码形态不能作为结论。

### 11.2 如何确认编译器生成了向量指令？

- GCC 用 `-fopt-info-vec-optimized` 与 `-fopt-info-vec-missed` 输出成功与失败原因。
- Clang 用 `-Rpass=loop-vectorize` 与 `-Rpass-missed=loop-vectorize`。
- 汇编中查找 `vaddps`、`vmovups`、`vpaddd` 等指令，确认向量宽度与展开方式。
- `objdump -d --no-show-raw-insn` 或 `llvm-objdump` 便于阅读。
- 编译器可能生成多版本循环，运行时根据指针对齐选择路径。
- 报告必须结合优化级别与目标架构，例如 `-O3 -march=native`。

### 11.3 自动向量化失败的常见原因有哪些？

- 指针可能别名，编译器插入运行时检查或直接放弃向量化。
- 迭代次数未知，编译器需要生成向量循环与标量尾部，或放弃展开。
- 条件分支无法转换为掩码，尤其含函数调用或异常。
- 数据类型没有对应的 SIMD 指令，或需要软件模拟。
- 跨步访问与非连续布局使收集、散射开销超过收益。
- 浮点严格语义阻止重排，归约无法并行。

### 11.4 `restrict` 如何帮助向量化？

- `restrict` 限定指针是访问所指对象的唯一途径，编译器据此消除别名假设。
- C++ 标准没有 `restrict`，GCC 与 Clang 提供 `__restrict`，MSVC 同样提供。
- 违反限定产生未定义行为，不能仅凭逻辑上不重叠就添加。
- 对引用参数不适用，需要改为指针参数或局部指针变量。
- 添加后检查汇编与报告，确认运行时版本检查确实消失。
- 它只解决别名一类障碍，不处理控制流与数据依赖。

### 11.5（实现）如何用 AVX2 实现浮点点积？

```cpp
#include <immintrin.h>

float dot(const float* a, const float* b, std::size_t n) {
    __m256 acc = _mm256_setzero_ps();
    std::size_t i = 0;
    for (; i + 8 <= n; i += 8)
        acc = _mm256_fmadd_ps(_mm256_loadu_ps(a + i),
                              _mm256_loadu_ps(b + i), acc);
    alignas(32) float lane[8];
    _mm256_store_ps(lane, acc);
    float s = lane[0] + lane[1] + lane[2] + lane[3]
            + lane[4] + lane[5] + lane[6] + lane[7];
    for (; i < n; ++i) s += a[i] * b[i];
    return s;
}
```

- `_mm256_loadu_ps` 允许非对齐地址，地址对齐时改用 `_mm256_load_ps` 可减少拆分。
- FMA 把乘加合并为一条指令，减少一次舍入，需要目标支持 `-mfma`。
- 水平求和只在循环外执行一次，循环内保持向量累加。
- 尾部用标量循环处理，避免越界读取。
- 浮点归约改变求和顺序，结果与标量版本不完全相同，需要评估误差要求。
- 用 `-mavx2 -mfma` 编译，并在目标机器上确认指令集支持。

### 11.6 AVX-512 是否总是更快？

- 512 位指令在部分处理器上触发频率下降，短时负载的收益被抵消。
- 掩码寄存器减少尾部处理与分支，适合稀疏与条件计算。
- 需要更多向量寄存器与更高内存带宽，数据不在缓存时收益有限。
- 同一份代码在不同微架构上表现可能相反，客户端与服务端的差异尤其明显。
- 应比较 256 位与 512 位版本的分位数与吞吐，不能只看峰值浮点性能。
- 频率切换策略取决于具体处理器，结论必须在目标机器上验证。

### 11.7（辨析）SMT 对向量化负载有什么影响？

- 向量指令占用执行端口与缓存带宽，同核邻居会争用这些资源。
- 计算密集且缓存友好的向量循环在 SMT 下吞吐提升有限，甚至下降。
- 内存受限的负载在 SMT 下可隐藏部分延迟，收益更明显。
- 延迟敏感线程应独占物理核，避免邻居干扰。
- 观测需要固定绑定，比较同机开启与关闭 SMT 的数据。
- 结论取决于微架构与负载类型，不存在通用配置。

### 11.8 AoS 与 SoA 如何影响向量化收益？

- AoS 把同一对象的多个字段放在一起，遍历单字段时需要跨步加载。
- SoA 把同一字段连续存放，可以直接使用连续加载与 SIMD 运算。
- 同时访问多个字段时 AoS 的缓存局部性更好，SoA 需要多次流式加载。
- 布局转换有成本，适合在数据入口或批处理阶段完成。
- 结构体的字段顺序与对齐会影响编译器能否合并访问。
- 选择依据是访问模式，而不是抽象的缓存友好。

### 11.9 向量循环的尾部如何处理？

- 向量循环处理整数个向量后，剩余元素用标量循环，代码简单但可能成为瓶颈。
- 掩码加载可一次处理剩余元素，避免逐元素分支。
- 把数组补齐到向量宽度并用中性值填充，可消除尾部但改变内存占用。
- AVX-512 的掩码寄存器支持逐元素条件执行，尾部处理更自然。
- 尾部长度固定时可用重叠加载，最后一次向量访问与前一次重叠。
- 越界读可能触发页错误或读到敏感数据，不能以多余字节不影响结果为前提。

### 11.10 循环并行化后为什么没有加速？

- 数据依赖或循环携带依赖使迭代不能独立执行，并行化只能退化为串行。
- 共享数据的伪共享与缓存行争用会抵消多核收益，需要按线程填充或分片。
- 内存带宽或单核性能成为瓶颈时，增加线程只会加剧竞争。
- 任务粒度过小，调度与同步开销超过计算量；需要合并迭代或分块。
- Amdahl 定律限制了可加速比例，串行段与同步点决定上限。
- 用可扩展性测试与剖析工具确认瓶颈，再决定是否并行。

### 11.11（陷阱）并行归约为什么会变慢？

```cpp
double sum = 0.0;
#pragma omp parallel for reduction(+:sum)
for (int i = 0; i < n; ++i)
    sum += a[i];
```

- 编译时需要开启 `-fopenmp`，否则 `#pragma omp` 被忽略并退化为串行执行。
- `reduction` 为每个线程创建私有副本，结束时合并，避免每次迭代写共享变量。
- 手写归约把结果写进共享数组时，多个线程写同一缓存行的不同元素，形成伪共享。
- 按缓存行填充各线程的槽位，可把争用降到最低。
- 对齐可用 `alignas(64)`，但缓存行大小由实现定义，需要查询目标平台。
- 读写混合的共享计数器应改为每线程计数，最后汇总。
- 用 `perf c2c` 查看缓存行争用与来源。

### 11.12 任务并行的粒度如何确定？

- 粒度过细时任务创建、入队与唤醒的开销超过计算本身。
- 粒度过粗时负载不均，尾部由最慢任务决定。
- 经验做法是让单个任务至少执行数微秒，或按迭代块切分。
- 工作窃取适合不规则任务，窃取开销与双端队列实现相关。
- 递归分治设置截断阈值，低于阈值直接串行处理。
- 用任务执行时间分布与线程空闲率验证粒度。

### 11.13 Amdahl 定律如何限制加速比？

- 加速比上限由串行部分决定，串行占 5% 时加速比不超过 20。
- 公式为 1 / (s + (1 - s) / n)，s 为串行比例，n 为处理器数。
- 串行部分包括初始化、结果合并、I/O 与锁保护的临界区。
- 强扩展固定问题规模，弱扩展随核数增大问题规模。
- 测量加速比以单线程版本为基线，固定算法与数据。
- 优化串行部分往往比增加核数更有效。

### 11.14（场景）8 核之后扩展性停滞如何排查？

- 先确认是否受内存带宽限制，多核流式访问时带宽容易饱和。
- 检查 NUMA：跨节点访问与远程缓存一致性流量拖慢扩展。
- 检查共享资源：全局锁、原子计数器、分配器、日志。
- 用 `perf c2c` 检查伪共享与缓存行争用。
- 检查线程绑定与拓扑，避免线程集中在少数物理核。
- 改变核数绘制扩展曲线，观察拐点对应的饱和资源。

### 11.15 并行开销如何量化？

- 线程创建成本约为数十微秒，线程池把该成本移出请求路径。
- 屏障同步成本随核数增长，集中式屏障在数十核时可达微秒级。
- 唤醒延迟取决于调度器与 C-state，空闲核心唤醒更慢。
- 原子操作在无竞争时约十几纳秒，竞争时由缓存行迁移主导。
- 用微基准测同步原语，用整体剖析确认其占比。
- 并行收益等于计算节省减去同步与调度开销，接近零时应重新划分任务。

### 11.16 条件变量为什么必须循环等待？

```cpp
std::mutex m;
std::condition_variable cv;
bool ready = false;

void wait_ready() {
    std::unique_lock lock(m);
    cv.wait(lock, [] { return ready; });
}
```

- `wait` 可能在未收到通知时返回，标准允许虚假唤醒。
- 谓词可能在唤醒与重新加锁之间被其他线程改变。
- 循环检查谓词，`wait` 的谓词重载在内部执行该循环。
- 通知早于等待会丢失，谓词检查保证不会永久阻塞。
- 共享状态必须由同一互斥量保护，否则检查与等待之间存在竞争。
- 唤醒开销包括重新加锁与调度，批量通知可能造成惊群。

### 11.17（辨析）忙等、让出与阻塞等待如何取舍？

- 忙等延迟最低，但占用处理器，等待时间长时浪费算力并影响同核邻居。
- `sched_yield` 让出后可能立即被调度回来，适合极短等待。
- 阻塞等待释放处理器，唤醒延迟由调度器决定。
- 自旋加退避先自旋若干次再阻塞，兼顾短等待与长等待。
- 实时性要求高的线程可独占核心忙等，需要配合隔离与固定频率。
- 选择依据是预期等待时长的分布，平均值不足以决定。

### 11.18（场景）并行结果偶发不一致如何定位？

- 先用 ThreadSanitizer 复现，记录竞争的内存位置与访问栈。
- 检查共享状态是否有同步保护，特别是惰性初始化与缓存。
- 检查并发读写下的迭代器失效与内存回收。
- 用固定种子与确定性调度缩小范围，必要时插入屏障放大竞争。
- 检查编译器是否把非原子访问提升或合并，`volatile` 不能替代原子。
- 修复后用压力测试与 TSan 回归，单次通过不构成结论。

### 11.19 伪共享如何检测与消除？

```cpp
struct alignas(std::hardware_destructive_interference_size) Counter {
    std::atomic<std::uint64_t> value{0};
};
```

- 伪共享是两个线程写同一缓存行的不同变量，一致性协议使该行在核心间往返。
- 典型症状是多核扩展性差，剖析显示高缓存未命中与一致性流量。
- `perf c2c record` 与 `perf c2c report` 可定位共享缓存行的读写来源。
- 消除方法是填充使变量独占缓存行，或改为线程私有副本后合并。
- `std::hardware_destructive_interference_size` 提供可移植的间隔常量。
- 该常量由实现定义，实际缓存行大小可能不同，跨平台需要验证。

### 11.20（场景）开启 `-O3` 后性能反而下降，如何归因？

- 检查代码膨胀：过度展开与向量化增加指令缓存压力，热点循环反而变慢。
- 检查别名检查与多版本循环带来的额外分支。
- 检查浮点语义变化，`-ffast-math` 改变结果与异常行为。
- 对比不同优化级别与目标架构的剖析数据，定位热点变化。
- 检查内联优化导致的调试信息丢失与采样归因偏差。
- 用固定输入与同机对比，排除频率与后台任务干扰。

## 12. 性能设计题

### 12.1 低延迟队列如何选型？

- 单生产者单消费者用环形缓冲区，读写下标各自独占缓存行，写入只做普通存储。
- 多生产者需要 CAS 或分段，竞争随核心数上升，尾延迟由重试次数决定。
- 有界队列提供背压与可预测内存，无界队列在过载时延迟无上限。
- 元素较大时队列存指针，对象由池管理，减少复制成本。
- 跨进程使用共享内存环形队列，需要处理崩溃恢复与内存序。
- 选型依据是生产者与消费者数量、突发程度与丢弃策略。

### 12.2（实现）SPSC 环形队列的关键点是什么？

```cpp
template <class T, std::size_t N>
class Ring {
    alignas(64) std::atomic<std::size_t> head_{0};
    alignas(64) std::atomic<std::size_t> tail_{0};
    std::array<T, N> buf_{};
public:
    bool push(const T& v) {
        auto t = tail_.load(std::memory_order_relaxed);
        auto h = head_.load(std::memory_order_acquire);
        if (t - h == N) return false;
        buf_[t % N] = v;
        tail_.store(t + 1, std::memory_order_release);
        return true;
    }
};
```

- 生产者只写 `tail_`，消费者只写 `head_`，两个下标分处不同缓存行。
- `release` 与 `acquire` 保证元素写入先于下标可见。
- 下标用无符号数自然回绕，容量取 2 的幂时可用掩码代替取模。
- 判断满用下标差等于容量，判断空用下标差为零。
- 元素类型需要可默认构造，或改用未初始化存储加手工构造。
- 队列不负责元素生命周期，回收责任在调用方。

### 12.3 队列满时如何处理？

- 阻塞等待提供背压，但把生产者延迟与消费者进度耦合。
- 丢弃最旧数据适合以最新状态为目标的场景，例如行情快照。
- 丢弃新数据适合不允许破坏已有序列的场景。
- 覆盖写需要消费者能检测丢失，通常配合序号与间隙标记。
- 返回错误让上层降级，避免在队列内部替调用方做策略决定。
- 策略必须可观测，记录丢弃数、阻塞时长与队列水位。

### 12.4 定长内存池如何设计？

- 按对象大小分级，每级维护空闲链表，分配与释放为常数时间。
- 从大块切分，减少系统调用与元数据开销。
- 空闲链表节点通常复用对象内存，避免额外存储。
- 每线程缓存减少锁竞争，跨线程释放需要归还到所属线程或中央池。
- 池只管理内存，对象的构造与析构由调用方控制。
- 监控空闲率与碎片，长期不归还的内存会推高常驻内存。

### 12.5 变长分配如何控制碎片？

- 按大小分级把变长请求归入固定档位，用内部碎片换取管理简单。
- 大块单独管理，使用伙伴系统或按页分配。
- 元数据与用户数据分离，降低越界写破坏元数据的风险。
- 合并相邻空闲块需要边界标记，代价是每块额外头部。
- 定期整理或迁移可降低碎片，但需要暂停或双缓冲。
- 碎片指标是分配失败率与最大可用块，而不是空闲总量。

### 12.6（场景）内存池上线后常驻内存持续增长如何排查？

- 确认是池未归还还是对象泄漏，对比分配与释放计数。
- 检查线程缓存上限，线程退出后缓存是否回收。
- 检查大块是否由 `mmap` 分配后未 `munmap`，或未用 `madvise` 标记可回收。
- 检查对象析构是否释放池外资源，例如文件描述符与嵌套容器。
- 用堆剖析工具按调用栈统计存活对象。
- 区分虚拟内存与常驻内存，`mmap` 后未触碰的页面不计入常驻内存。

### 12.7 二进制序列化为什么通常快于文本？

- 文本需要解析数字与分隔符，涉及分支与错误处理。
- 二进制按固定布局直接读取，减少格式判断与内存分配。
- 变长整数减小体积，但解码有分支，极端值更慢。
- 对齐与填充影响复制效率，紧凑布局可能与非对齐访问冲突。
- 文本的可读性带来排错便利，二进制不具备。
- 选择取决于吞吐、兼容性与调试需求，单一速度指标不足以决定。

### 12.8 零复制序列化如何实现？

- 扁平缓冲区把字段偏移写入表，读取时直接定位，无需构造对象。
- 原地访问要求字节序、对齐与版本兼容在格式层面解决。
- 字符串与数组以偏移引用，跨缓冲区需要复制或重新定位。
- 写入端需要预分配与回填偏移，接口比流式编码复杂。
- 可变字段与模式演进需要预留字段号与默认值。
- 零复制降低处理器与分配开销，代价是缓冲区生命周期管理与格式约束。

### 12.9 序列化格式如何演进？

- 字段编号发布后不宜复用，删除字段应保留编号并标记为保留。
- 新增字段必须可选，旧版本读取时使用默认值。
- 枚举新增值需考虑旧版本遇到未知值的处理策略。
- 不要依赖字段顺序与内存布局，跨编译器与跨版本不稳定。
- 版本号放在消息头或由协议层协商，二者各有兼容性代价。
- 变更后用旧版本程序读取新数据做回归。

### 12.10 本地缓存如何选择淘汰策略？

- LRU 命中率较高，但每次访问都要更新链表，并发下需要锁或分段。
- CLOCK 用引用位近似 LRU，开销低，适合高并发读。
- 分段缓存把键空间切分，降低锁竞争，代价是全局淘汰不精确。
- TTL 适合容忍陈旧的数据，需要处理集中过期造成的尖峰。
- 容量按工作集设定，过小导致抖动，过大挤占内存。
- 监控命中率、淘汰率与回源延迟，缓存大小本身不足以说明问题。

### 12.11（陷阱）缓存穿透与热点失效如何处理？

- 不存在的键每次都回源，可用空值缓存或布隆过滤器拦截。
- 空值缓存需要较短 TTL，避免数据出现后长期不可见。
- 热点键过期瞬间大量请求同时回源，可用请求合并（singleflight）避免重复。
- TTL 加随机抖动，避免同一时刻批量失效。
- 逻辑过期允许先返回旧值并异步刷新，代价是短暂不一致。
- 限制回源并发，避免缓存故障传导为下游雪崩。

### 12.12 缓存一致性如何保证？

- 失效通知比写穿透更常见，写数据库后删除缓存，再由读请求回填。
- 删除与更新之间仍有竞态，可用版本号或延迟双删降低概率。
- 多级缓存需要逐级失效，否则本地缓存长期返回旧值。
- 订阅变更日志异步失效，能解耦但引入延迟。
- 强一致通常意味着放弃缓存或使用租约。
- 最终一致需要给出可接受的不一致窗口，并监控旧值比例。

### 12.13 同步日志与异步日志如何取舍？

- 同步写入在返回前完成 `fsync`，才能保证崩溃前落盘，代价是每次写都要等待 I/O。
- 批量提交把多个请求合并为一次 `fsync`，显著提升吞吐。
- 异步日志把格式化与写入放到后台线程，请求路径只入队。
- 异步日志在崩溃时可能丢失队列中的数据，需要明确可接受的丢失窗口。
- `O_DSYNC` 与 `fsync` 语义不同，前者只保证数据与读取所需元数据，后者还同步全部元数据。
- 日志级别与采样策略决定实际写入量，比微调缓冲区更有效。

### 12.14（实现）异步日志的缓冲区如何设计？

```cpp
class LogRing {
    static constexpr std::size_t kCap = 1 << 20;
    std::atomic<std::size_t> head_{0};
    char buf_[kCap];
public:
    bool append(std::string_view s) {
        auto h = head_.load(std::memory_order_relaxed);
        auto n = static_cast<std::uint32_t>(s.size());
        if (h + sizeof n + n > kCap) return false;
        std::memcpy(buf_ + h, &n, sizeof n);
        std::memcpy(buf_ + h + sizeof n, s.data(), n);
        head_.store(h + sizeof n + n, std::memory_order_release);
        return true;
    }
};
```

- 单生产者写入只需移动原子头指针，消费者读取已提交区间。
- 多生产者需要 CAS 预留空间，失败重试会引入尾部延迟。
- 记录长度前缀，消费者可跳过未完成写入。
- 缓冲区满时丢弃或阻塞，策略决定日志的可靠性。
- 后台线程按大小或时间批量落盘。
- 崩溃恢复时扫描记录，丢弃尾部不完整记录。

### 12.15 日志格式化的开销来自哪里？

- 时间戳获取、数字转字符串、内存分配与系统调用是主要开销。
- `std::format` 与 fmt 通常快于流式输出，但仍需构造格式化结果。
- 缓存时间戳可减少时钟读取，代价是精度下降。
- 预分配缓冲区与避免临时 `std::string` 能显著降低分配次数。
- 结构化日志把字段编码为二进制，减少文本转换但增加工具依赖。
- 采样与惰性求值，只在需要时格式化昂贵字段。

### 12.16（场景）日志导致 P99 抖动如何定位？

- 对比关闭日志与开启日志的分位数，确认相关性。
- 检查是否在请求路径同步写文件、刷盘或加锁。
- 检查日志轮转，重命名与重新打开会造成锁竞争与 I/O 尖峰。
- 检查异常路径是否打印大量堆栈或对象转储。
- 检查日志库的全局锁与缓冲区分配。
- 改造方向是异步、批量、限流与采样，并保留关键字段。

### 12.17（实现）配置热更新如何做到低延迟？

```cpp
struct Config { int timeout_ms; int workers; };
const Config kDefault{100, 4};
std::atomic<const Config*> current{&kDefault};

void publish(std::unique_ptr<Config> next) {
    const Config* old = current.exchange(next.release(),
                                        std::memory_order_acq_rel);
    retire(old);                        // free after readers drain
}
```

- 双缓冲：新配置构建完成后原子交换指针，读路径无锁。
- 交换后的旧配置延迟释放，等待所有读侧临界区退出。
- 解析与校验在后台完成，失败时保留旧配置。
- 版本号与生效时间写入配置，便于回滚与排查。
- 订阅变更需要处理丢失通知，定期全量拉取兜底。
- 读路径缓存配置指针，避免每次访问全局变量。

### 12.18 批处理与延迟如何平衡？

- 批处理提高吞吐，代价是等待批次填满的时间。
- 按时间与大小双阈值触发，避免低流量时无限等待。
- 批次大小受下游单次处理能力限制，过大导致尾延迟。
- 流水线中的批处理会把排队延迟传递给后续阶段。
- 延迟敏感的请求走单独通道，不参与批处理。
- 监控批次大小分布与等待时间，而不只看平均吞吐。

### 12.19（场景）如何为 P99 1 ms 的服务做容量估算？

- 用 Little 定律估计并发，并发数等于到达率乘以平均停留时间。
- 按排队模型估算目标利用率，利用率越高排队延迟增长越快。
- 把单请求预算拆分到处理器、内存、下游与网络，逐项验证。
- 压测用开环模型并校正协调遗漏，避免分位数偏乐观。
- 考虑重试与突发系数，按峰值的 2 至 3 倍规划。
- 上线后按实际分位数校正模型，不能沿用初始假设。

### 12.20 设计评审中如何论证方案不会退化？

- 提供基线：同机、同输入、同编译选项下的分位数与吞吐。
- 说明失败路径：队列满、下游超时、内存不足时的行为。
- 列出可观测性：关键指标、日志与追踪埋点。
- 给出回滚方案与灰度范围。
- 说明容量假设与验证方式。
- 评审结论应包含未验证的假设，避免把推测当成结论。

## 13. 性能反模式

### 13.1 如何识别过早优化？

- 在没有基线与剖析数据时修改热点之外的代码。
- 以可能慢为理由引入复杂数据结构或手写汇编。
- 优化后没有可重复的测量结果，只凭代码观感判断。
- 为尚未出现的负载预先设计，例如超大并发与极端数据。
- 正确顺序是测量、定位、修改、再测量。
- 过早优化的主要成本是复杂度与维护负担，处理器时间的节省往往可以忽略。

### 13.2 微基准为什么容易得出错误结论？

- 编译器可能删除无副作用的计算，测量结果接近空循环。
- 输入过小导致数据全在缓存，真实负载需要访问内存。
- 分支预测器在重复输入下几乎总是命中，真实数据分布更复杂。
- 未预热时包含缺页、动态链接与频率爬升。
- 单线程测量忽略并发下的缓存行争用。
- 需要固定输入、预热、重复多次并报告分布。

### 13.3 如何防止编译器优化掉被测代码？

```cpp
std::uint64_t sink = 0;
for (int i = 0; i < n; ++i)
    sink += work(i);
benchmark::DoNotOptimize(sink);
```

- 使用 `benchmark::DoNotOptimize` 或编译器屏障，让结果被视为可观测。
- `volatile` 能阻止部分优化，但会引入额外内存访问，改变被测行为。
- 把结果写入跨翻译单元使用的全局变量，可降低被消除的概率。
- 检查生成的汇编，确认核心循环仍然存在。
- 测量空函数作为开销基线，扣除计时与调用成本。
- 不要依赖 `printf` 等外部调用制造副作用。

### 13.4（陷阱）用系统时钟测量纳秒级函数有什么问题？

- `clock_gettime` 的分辨率与开销可能接近被测函数耗时。
- 单次调用受调度、缓存与频率影响，方差极大。
- 应批量重复并在外层计时，再除以次数。
- 重复之间要有数据依赖，避免编译器合并相同调用。
- 报告最小值、中位数与分位数，单次最快值不代表典型性能。
- 需要高精度时使用 `rdtsc`，并说明频率与跨核问题。

### 13.5 缓存污染如何影响后续请求？

- 大表遍历把热点数据挤出缓存，后续请求需要重新加载。
- 流式访问可使用非临时存储指令，减少对缓存的占用。
- 预取过度会挤占带宽与缓存，反而增加延迟。
- 后台任务应限制并发与优先级，避免与请求路径争用缓存。
- 观测用缓存未命中率与每指令周期数，总时间不足以定位。
- 隔离核心或分时调度可降低相互干扰。

### 13.6 过度使用内联优化有什么代价？

- 代码体积增大，指令缓存命中率下降，热点循环可能被挤出。
- 编译时间与调试信息体积上升。
- 内联优化后调用栈被展开，采样剖析更难归因。
- 虚函数调用点的内联优化需要去虚拟化，失败时反而增加分支。
- 强制 `always_inline` 会阻止编译器按成本模型决策。
- 应依赖编译器的成本模型，只在剖析显示调用开销显著时干预。

### 13.7（辨析）`inline` 关键字与内联优化是什么关系？

- `inline` 主要解决多重定义问题，允许函数在多个翻译单元中定义。
- 是否展开由编译器决定，与是否写 `inline` 没有必然关系。
- 类内定义的成员函数隐式 `inline`，同样不保证展开。
- `always_inline` 与 `__forceinline` 是编译器扩展，破坏可移植性。
- 递归函数、取地址的函数、未开启 LTO 的跨翻译单元调用通常无法展开。
- 讨论性能时应说内联优化，讨论链接语义时才说 `inline`。

### 13.8 凭直觉更换容器为什么危险？

- `std::list` 在中间插入为常数时间，但节点分配与缓存局部性差，遍历通常慢于 `std::vector`。
- `std::unordered_map` 的哈希与冲突处理在小规模数据下可能慢于有序 `std::map`。
- 容器选择依赖访问模式、规模与内存预算，不能只看复杂度。
- 更换容器会改变迭代器失效规则与内存占用，影响正确性。
- 需要以真实数据分布做基准，合成小样本不足以代表。
- 关注点应包括分配次数、缓存未命中与尾延迟。

### 13.9 `std::move` 与 `reserve` 有哪些常见误用？

```cpp
std::vector<int> make() {
    std::vector<int> v(1024);
    return v;                           // NRVO, no std::move needed
}
```

- 对 `const` 对象使用 `std::move` 会退化为复制。
- 返回局部变量时写 `std::move` 可能阻止复制消除。
- `reserve` 过大浪费内存，过小仍需扩容。
- 对不提供移动构造的类型，移动语义没有收益。
- 移动后对象处于有效但未指定状态，继续使用是逻辑错误。
- 优化应基于分配次数与复制成本的测量。

### 13.10 虚函数与类型擦除的代价在哪里？

- 间接调用阻碍内联优化，分支预测器面对多态调用可能失败。
- 对象布局增加虚表指针，影响缓存密度。
- 去虚拟化在类层次封闭时生效，需要编译器看到全部实现。
- `std::function` 可能分配堆内存，调用经过类型擦除。
- 热路径可用模板或函数指针替代，代价是代码膨胀。
- 设计应权衡扩展性与调用开销，不宜默认禁用多态。

### 13.11 模板膨胀会带来哪些成本？

- 每个实例化生成独立代码，增加二进制体积与指令缓存压力。
- 编译时间随实例化数量增长。
- 显式实例化可把实现集中到一个翻译单元，减少重复生成。
- 类型擦除可减少实例化数量，代价是间接调用。
- 调试信息膨胀，链接与加载变慢。
- 用二进制大小与编译时间作为指标，而非只看运行时。

### 13.12 智能指针有哪些隐性开销？

- `std::shared_ptr` 的引用计数是原子操作，跨核共享时缓存行争用明显。
- 控制块与对象分开分配时局部性较差，`std::make_shared` 合并为一次分配。
- 按值传参会增加引用计数，按 `const` 引用可避免。
- `std::unique_ptr` 通常零开销，自定义删除器可能增加体积。
- 循环引用导致泄漏，`std::weak_ptr` 打破环但增加检查成本。
- 热路径可用侵入式引用计数或裸指针加明确所有权。

### 13.13（场景）关闭异常与 RTTI 会带来什么后果？

- `-fno-exceptions` 下异常无法传播，标准库的抛出路径通常以终止进程结束。
- `new` 失败无法以 `std::bad_alloc` 传播，通常直接终止进程；需要改用 `nothrow` 版本并检查返回值。
- `-fno-rtti` 使 `dynamic_cast` 与 `typeid` 不可用，影响插件与序列化框架。
- 第三方库可能依赖异常，混用可能导致终止进程或未定义行为。
- 关闭后二进制略小，但错误处理改为返回码，调用方负担增加。
- 决策应基于错误模型与依赖库，体积差异不足以支撑决策。

### 13.14 `volatile` 与内存屏障有哪些误用？

```cpp
std::atomic<bool> stop{false};
while (!stop.load(std::memory_order_acquire)) {
    // work
}
```

- `volatile` 只保证访问不被优化掉，不提供原子性与线程间同步。
- 用 `volatile` 做自旋标志不建立同步，其他线程的写入不保证按预期顺序可见。
- 内存屏障有成本，全屏障会阻止编译器与处理器重排。
- 应优先使用 `std::atomic` 的默认顺序，确有需要再放宽。
- 过度使用 `seq_cst` 会引入不必要的栅栏，影响扩展性。
- 正确性优先，先证明无数据竞争，再讨论屏障开销。

### 13.15 微优化如何掩盖算法问题？

- 在平方复杂度的算法上做常数优化，规模翻倍后仍然变慢。
- 应先确认复杂度与数据规模，再处理常数因子。
- 剖析中的热点函数可能只是症状，根因是调用次数。
- 缓存与索引结构的选择比指令级优化影响更大。
- 规模测试要覆盖生产上限，不能只测小样本。
- 优化顺序是算法、数据结构、内存布局、指令。

### 13.16（场景）基准环境不干净会导致什么错误结论？

- 频率调节、Turbo 与温度墙使不同轮次结果不可比。
- 后台任务、容器邻居与中断抢占核心。
- 关闭与开启超线程的结论不能混用。
- 内存分配与页缓存状态在轮次之间残留。
- 应固定频率、绑核、隔离环境并多次重复。
- 记录环境配置与版本，保证结论可复现。

### 13.17 只测吞吐不测尾延迟有什么后果？

- 吞吐提升可能以更长的排队为代价，用户侧延迟变差。
- 批处理与缓冲会提高吞吐，同时增加单请求等待。
- 平均值掩盖长尾，P99 才反映超时与重试。
- 需要同时报告吞吐、分位数与错误率。
- 压测应使用开环模型，避免系统饱和后自动降速。
- 容量规划按尾延迟目标反推可承载的到达率。

### 13.18 过早池化与对象复用有什么问题？

- 池化引入生命周期管理，对象状态残留导致难以复现的缺陷。
- 小对象的池化收益可能被索引与同步开销抵消。
- 池化会延长内存占用，峰值后不释放。
- 线程本地池在跨线程释放时复杂化。
- 应先确认分配是热点，再选择池化或替换分配器。
- 池化对象必须可安全重置，构造与析构语义要明确。

### 13.19（场景）性能回归发布事故缺少基线怎么办？

- 没有基线时无法判断变慢来自本次变更还是环境漂移。
- 应在持续集成中保留固定基准与历史曲线。
- 回归门禁按分位数设阈值，并允许噪声范围内的波动。
- 发布前用相同硬件与数据集对比候选版本。
- 事故后补建基线，分析变更与硬件事件的时间线。
- 记录编译器版本与优化选项，避免不可复现。

### 13.20 如何在团队中减少性能反模式？

- 评审清单包含复杂度、分配、锁与 I/O 四类问题。
- 性能预算写入设计文档，作为验收条件。
- 持续基准与生产分位数监控结合，覆盖实验室与真实负载。
- 复盘聚焦可验证的因果链，个人经验不作为结论依据。
- 优化提交必须附带测量数据与回滚方案。
- 培训以真实案例为主，强调测量先于修改。
