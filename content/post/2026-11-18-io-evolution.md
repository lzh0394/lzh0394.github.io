> 范围：从 1950 年代的程序控制 I/O 到 2019 年的 io_uring，按「等待方式」与「抽象层次」两条线梳理。硬件细节只保留与软件接口相关的部分。
>
> 本篇是系列第 0 篇，作为背景；第 1 篇比较异步模型，第 2 至 5 篇讨论 C++ 协程、任务库、执行器与定制点。史料以 Unix 手册、BSD/Linux 内核文档、项目发布记录与 WG21 提案为准，无法精确到日的写「约」。

## 0. 结论摘要

1. I/O 演化的主线是等待方式：忙等、中断、阻塞系统调用、就绪通知、完成通知、共享环形队列。每一次变化都在改变「谁在等、等的时候做什么」。
2. 中断把 CPU 从轮询设备状态中解放，DMA 把数据搬运从 CPU 解放。两者奠定了现代 I/O 的硬件基础。
3. Unix 用文件描述符统一设备、文件、管道与套接字，`read`/`write` 的阻塞语义简单直接，代价是每个等待占一个执行流。
4. `select` 在 1983 年把「等待多个描述符」变成一次系统调用；`poll` 解除了描述符数量上限；`epoll` 与 `kqueue` 把全量扫描改成事件通知。
5. C10K 问题在 1999 年被明确提出，事件循环加非阻塞 I/O 成为高并发服务的标准结构。
6. Windows 的 IOCP 在 1994 年走完成式路线，操作提交后由内核在完成队列中报告结果；POSIX AIO 提供了另一套完成式接口，但实现与适用范围长期受限。
7. 事件驱动框架把平台差异封装起来：libevent、Boost.Asio、nginx、Node.js、Go 运行时各自选择了不同的抽象层次。
8. C10M 与内核旁路（DPDK、SPDK、RDMA）把数据面移出内核，用专用核心与轮询换取吞吐，代价是失去通用性与可组合性。
9. io_uring 在 2019 年把提交队列与完成队列放进共享内存，用批量提交降低系统调用次数，同时保留完成式语义。
10. 语言层从回调、future 到协程与 sender，试图恢复顺序控制流；底层 I/O 的差异仍然会透过抽象泄漏出来。

## 1. 早期 I/O：轮询、中断与 DMA

### 1.1 程序控制 I/O

最早的 I/O 由 CPU 直接控制。程序向设备控制器写入命令与参数，然后反复读取状态寄存器，直到设备就绪，再搬运数据。这种方式称为程序控制 I/O（programmed I/O），也叫轮询（polling）。

轮询的代价很直接：CPU 在等待期间不能做别的事。设备越慢，浪费越多。早期计算机的 I/O 设备速度与 CPU 差距不如今日悬殊，轮询还能接受；随着外设增多，CPU 时间迅速成为瓶颈。

### 1.2 中断

中断（interrupt）改变了等待的主体。设备完成一次操作后向 CPU 发出中断信号，CPU 保存现场，跳转到中断处理程序，处理完再返回原来的工作。程序不再需要反复查询状态。

中断在 1950 年代中后期进入计算机体系结构，最初用于处理外部事件与 I/O 完成。它把「等待」从软件循环转移到硬件信号，CPU 的时间可以分配给其他任务。

中断带来两个新问题：

- 中断处理程序运行在受限上下文，不能做耗时工作。
- 中断会打断正在执行的指令流，共享数据的并发访问需要同步。

这两个问题在此后的驱动程序中反复出现。

### 1.3 DMA 与通道

中断解决了「何时通知」，没有解决「谁搬数据」。程序控制 I/O 下，数据仍要经过 CPU 寄存器。直接内存访问（DMA，direct memory access）让设备控制器直接把数据写入内存或从内存读出，CPU 只负责设置起始地址、长度与方向。

DMA 在 1950 年代末到 1960 年代逐步普及。IBM System/360 在 1964 年引入的通道（channel）是更进一步的形态：通道是一台独立的 I/O 处理器，可以执行通道程序，控制多台设备，完成后用中断通知 CPU。

硬件层的分工由此稳定下来：

- CPU 发起操作。
- 设备或通道搬运数据。
- 完成后通过中断通知。

### 1.4 缓冲与假脱机

设备速度与 CPU 速度不匹配，需要缓冲（buffering）来吸收差异。操作系统在内存中维护缓冲区，读操作先填满缓冲区，写操作先写入缓冲区再择机刷出。

假脱机（spooling）把独占设备改造成共享设备。打印机一类设备不能同时被多个进程使用，系统先把输出写入磁盘队列，再由后台进程依次送出。这个模式后来演化成打印服务与批处理队列。

到 1960 年代末，硬件层已经具备「异步」的雏形：CPU 发起操作后可以继续执行，完成时由中断通知。软件层还没有统一的接口来表达这种异步，等待仍然要由每个程序自己安排。

## 2. Unix 的阻塞抽象

### 2.1 文件描述符

Unix 在 1970 年代初引入文件描述符（file descriptor）。`open` 返回一个非负整数，`read`、`write`、`close` 用这个整数操作对象。设备、普通文件、管道、终端都通过同一组接口访问。

统一接口的价值在于组合。程序可以把文件、管道与设备当作同一种东西处理，用 `dup` 复制描述符，用 `fork` 继承描述符，用管道连接进程。Unix 的「一切皆文件」只是一组接口约定，并没有把所有对象变成同一种实现。

套接字在 1983 年的 4.2BSD 中加入，同样使用文件描述符。网络 I/O 从此进入同一套接口体系。

### 2.2 阻塞语义

`read` 在数据未就绪时阻塞，`write` 在缓冲区满时阻塞。阻塞期间，进程或线程进入睡眠，让出 CPU；数据到达或缓冲区有空位时，内核唤醒它。

阻塞语义的优点是程序好写：

```cpp
char buf[4096];
ssize_t n = read(fd, buf, sizeof(buf));
if (n > 0) {
  process(buf, n);
}
```

调用返回时，数据已经在缓冲区里，错误已经通过返回值报告。程序不需要保存「等待中」的状态，也不需要注册回调。

代价是等待与执行流绑定。一个阻塞调用占住一个线程，线程在等待期间不能服务其他连接。要让多个连接并发，就需要多个线程或进程。

### 2.3 进程、线程与连接

Unix 早期的并发单位是进程。`fork` 创建子进程，每个进程处理一个连接。进程有独立地址空间，隔离性好，创建与切换成本高。

线程在 1990 年代成为主流。POSIX 线程（pthreads）在 1995 年标准化，线程共享地址空间，创建与切换比进程轻。一连接一线程的模型随之普及。

这个模型在连接数不大时工作良好。连接数上升后，三件事同时恶化：

- 每个线程保留栈空间，虚拟地址与物理页随线程数增长。
- 可运行线程数超过核心数后，调度与上下文切换占用 CPU。
- 共享状态的锁竞争增加，尾延迟上升。

C10K 问题把这些矛盾集中暴露出来。

## 3. 多路复用

### 3.1 select

`select` 出现在 1983 年的 4.2BSD，与套接字同一时期。它允许程序把多个描述符交给内核，等待其中任意一个就绪：

```cpp
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(fd, &readfds);
select(fd + 1, &readfds, nullptr, nullptr, nullptr);
if (FD_ISSET(fd, &readfds)) {
  read(fd, buf, sizeof(buf));
}
```

`select` 的接口有三个限制：

- 描述符集合用位图表示，上限由 `FD_SETSIZE` 决定，通常是 1024。
- 每次调用都要把集合从用户态复制到内核态，返回后再复制回来。
- 内核要扫描全部描述符，复杂度与集合大小成正比。

在连接数几百的场景，这些限制可以接受。连接数上升到几千、几万时，全量扫描与复制成为瓶颈。

### 3.2 poll

`poll` 在 1980 年代中期的 System V Release 3 中出现，用数组代替位图，解除了 `FD_SETSIZE` 的限制。每个元素包含描述符与关注的事件，返回时填写实际发生的事件。

`poll` 仍然要扫描整个数组，复杂度是 O(n)。它解决了数量上限，没有解决「每次都要检查全部描述符」这一结构问题。

### 3.3 C10K

1999 年，Dan Kegel 在文章中提出 C10K 问题：如何让单台服务器同时处理一万个连接。文章比较了阻塞 I/O 加线程、非阻塞 I/O 加事件循环、`select`/`poll` 等方案，指出一连接一线程在连接数上升后不可行。

C10K 的结论指向模型的选择：把等待从线程上拿掉，用少量线程管理大量连接。这个思路后来被称为事件驱动（event-driven）或反应式（reactive）。

### 3.4 epoll

`epoll` 由 Davide Libenzi 开发，在 2002 年进入 Linux 2.5.44，随后进入 2.6。它把「注册兴趣」与「等待事件」分开：

- `epoll_create` 创建实例。
- `epoll_ctl` 增删改关注的文件描述符。
- `epoll_wait` 返回就绪的事件数组。

内核维护兴趣列表与就绪列表，`epoll_wait` 只返回就绪条目，复杂度与就绪数相关。描述符只在注册时复制一次，不需要每次调用传入全量集合。

`epoll` 支持水平触发（level-triggered）与边缘触发（edge-triggered）：

- 水平触发：只要描述符可读，每次 `epoll_wait` 都会报告。编程简单，可能重复唤醒。
- 边缘触发：状态变化时报告一次。必须一次读到 `EAGAIN`，否则可能丢失事件。

边缘触发减少了唤醒次数，提高了吞吐，代价是读写循环必须写对。

### 3.5 kqueue 与其它接口

FreeBSD 在 2000 年的 4.1 版本中引入 `kqueue`。它用「过滤器」描述关注的事件类型，支持文件描述符、信号、定时器、进程事件等，接口比 `select` 更通用。

其他平台也有类似设施：

- Solaris 的 `/dev/poll` 与 event ports。
- Windows 的 IOCP 走完成式路线，不提供 Unix 风格的就绪通知。
- AIX 与 HP-UX 各有自己的多路复用扩展。

跨平台库的主要工作之一，就是把这些接口收敛成同一套事件循环。

### 3.6 复杂度对比

| 接口 | 出现时间 | 每次调用扫描 | 描述符上限 | 触发方式 |
| --- | --- | --- | --- | --- |
| `select` | 1983 | 全部 | `FD_SETSIZE` | 水平 |
| `poll` | 1986 | 全部 | 无固定上限 | 水平 |
| `epoll` | 2002 | 就绪 | 无固定上限 | 水平或边缘 |
| `kqueue` | 2000 | 就绪 | 无固定上限 | 过滤器 |

多路复用把「等待多个 I/O」变成一次系统调用，但没有改变「数据还要程序自己读写」这一事实。就绪之后，`read` 与 `write` 仍然是同步调用。

## 4. 完成式 I/O

### 4.1 IOCP

Windows NT 3.5 在 1994 年引入 I/O 完成端口（I/O completion port，IOCP）。应用把文件句柄绑定到完成端口，发起 overlapped I/O，操作完成后内核把完成包放入队列，工作线程用 `GetQueuedCompletionStatus` 取出。

IOCP 的核心是完成队列与线程池调度：

- 应用提交操作时指定 `OVERLAPPED` 结构，内核保存操作状态。
- 操作完成时，完成包包含错误码、传输字节数与用户上下文。
- 多个工作线程可以并发从同一完成端口取包，内核控制并发度。

IOCP 不要求应用先等待「可读」，再调用 `read`。应用直接提交读操作，内核在数据到达后完成它。这个模型后来被称为 proactor。

### 4.2 POSIX AIO

POSIX 在 1993 年的实时扩展（POSIX.1b）中定义了异步 I/O 接口：`aio_read`、`aio_write`、`aio_return`、`aio_error`、`aio_suspend`。应用提交请求，通过信号或轮询获知完成。

POSIX AIO 的实现长期不理想：

- glibc 的用户态实现在后台用线程执行阻塞调用，线程数受限制。
- Linux 内核的原生 AIO（`io_submit`）在 2.5 系列加入，主要支持 `O_DIRECT` 与块设备，对缓冲文件与网络套接字支持有限。
- 取消与错误处理的语义在不同实现之间不一致。

结果是，POSIX AIO 在 Linux 上没有成为通用异步 I/O 的基础，网络服务更多依赖就绪通知加事件循环。

### 4.3 两种语义

| 维度 | 就绪通知 | 完成通知 |
| --- | --- | --- |
| 应用等待的对象 | 描述符可读或可写 | 操作结果 |
| 数据读写 | 应用在就绪后调用 | 内核在提交时接管 |
| 缓冲区 | 调用时传入 | 提交时绑定 |
| 操作状态 | 应用保存 | 内核或运行时保存 |
| 典型接口 | `select`、`poll`、`epoll`、`kqueue` | IOCP、POSIX AIO、io_uring |

就绪通知把「等待」与「读写」分成两步，应用可以在就绪后决定读多少、写多少。完成通知把两步合并，应用提交操作后等待结果。前者更贴近 Unix 的 `read`/`write` 语义，后者更容易表达真正的并行 I/O。

## 5. 事件驱动框架

### 5.1 Reactor 与 Proactor

1990 年代中期，Douglas Schmidt 等人把事件处理结构归纳为 Reactor 模式：事件多路分离器等待事件，分发给对应的处理器。Proactor 模式则把异步操作的发起与完成分离，由完成处理器处理结果。

两种模式对应两种内核接口。Reactor 建立在就绪通知上，Proactor 建立在完成通知上。框架可以在就绪接口之上模拟 Proactor：先等待就绪，再执行读写，最后调用完成处理器。这种模拟增加了状态管理，但让接口在不同平台上保持一致。

### 5.2 libevent

libevent 由 Niels Provos 在 2000 年发布，目标是提供跨平台的事件循环。它封装 `select`、`poll`、`epoll`、`kqueue` 等后端，提供定时器、信号、缓冲区与 HTTP 等组件。

libevent 的接口以回调为中心：应用注册事件与回调，事件循环在事件到达时调用。它把平台差异收敛到一套 API，成为早期网络服务与工具的基础库之一。

### 5.3 Boost.Asio

Boost.Asio 由 Christopher Kohlhoff 在 2003 年开始开发，2008 年随 Boost 1.35 发布。它把异步操作抽象为「发起函数 + 完成令牌」：

- `async_read`、`async_write`、`async_accept` 发起操作。
- 完成令牌可以是回调、future、协程或自定义类型。
- `io_context` 驱动事件循环，执行器决定完成处理器的运行位置。

Asio 在就绪通知之上实现了 Proactor 语义，并支持 Windows 的 IOCP。它的接口影响了后来的 Networking TS 与多个语言的异步库。

### 5.4 nginx

nginx 在 2004 年发布，用事件驱动架构处理高并发连接。主进程管理配置与工作进程，工作进程各自运行事件循环，使用 `epoll`、`kqueue` 等接口。

nginx 的设计强调：

- 工作进程数量通常与核心数相当。
- 连接状态在进程内管理，减少锁与跨进程共享。
- 阻塞操作交给独立线程或进程，避免阻塞事件循环。

C10K 之后，nginx 成为「少量进程加事件循环」的典型实现。

### 5.5 Node.js 与 libuv

Node.js 在 2009 年发布，把 JavaScript 的单线程事件循环与异步 I/O 结合。文件 I/O、DNS 解析等可能阻塞的操作交给线程池，网络 I/O 由事件循环处理。

跨平台的事件循环后来由 libuv 承担。libuv 封装 `epoll`、`kqueue`、IOCP 与 event ports，提供定时器、线程池、文件系统与网络接口。Node.js 的编程模型把回调放在语言层，随后的 Promise 与 `async`/`await` 逐步改善了控制流表达。

### 5.6 Go 的 netpoller

Go 在 2009 年发布，运行时包含网络轮询器（netpoller）。goroutine 用阻塞语法调用网络接口，运行时把操作注册到 `epoll`/`kqueue`/IOCP，在 goroutine 阻塞时切换到其他任务。

Go 的模型把异步藏进运行时与调度器：

- 程序员写同步代码。
- 运行时把网络 I/O 变成非阻塞操作。
- goroutine 在等待时让出执行线程。

代价是运行时承担了调度、栈增长与垃圾回收的复杂度，且阻塞式系统调用仍可能占住线程。

### 5.7 语言级 async/await

| 语言 | 时间 | 形式 |
| --- | --- | --- |
| C# | 2012 | `async`/`await`，基于任务 |
| Python | 2014 | `asyncio`，协程与事件循环 |
| JavaScript | 2017 | `async`/`await`，基于 Promise |
| Rust | 2019 | `async`/`await`，基于 Future |
| C++ | 2020 | 协程语言机制，库提供任务类型 |

这些机制的共同点是把异步操作写成顺序代码，由编译器或运行时保存挂起状态。不同点在于调度由谁负责：C# 有同步上下文，Python 有事件循环，Rust 有执行器，C++ 只提供语言机制。

## 6. C10M 与内核旁路

### 6.1 C10M

C10K 解决后，目标很快上升到一千万连接（C10M）。此时瓶颈从连接管理转向数据路径：系统调用、内核协议栈、内存复制、缓存失效与中断处理都成为开销。

C10M 的讨论在 2012 年前后兴起，核心观点是：在通用内核协议栈上，用常规接口很难达到千万级并发与线速转发；需要把数据面移到用户态，或用专用硬件卸载。

### 6.2 DPDK

DPDK（Data Plane Development Kit）由 Intel 在 2010 年前后启动，2013 年开源。它让应用在用户态直接访问网卡队列：

- 使用大页内存与轮询模式驱动。
- 每个核心绑定一个队列，避免锁与跨核通信。
- 绕过内核网络栈，自己实现协议处理。

DPDK 的吞吐很高，代价是核心被轮询占满、无法使用通用网络工具、需要自己处理协议与安全。

### 6.3 SPDK 与 NVMe

SPDK（Storage Performance Development Kit）把同样的思路用于存储。它用用户态驱动、轮询队列与无锁环形队列访问 NVMe 设备，减少系统调用与中断。

NVMe 本身是面向队列的协议，支持多提交队列与多完成队列。用户态驱动把这些队列直接映射到应用，适合高性能存储服务。

### 6.4 RDMA

RDMA（remote direct memory access）允许一台机器直接读写另一台机器的内存，绕过双方内核。InfiniBand 在 2000 年前后标准化，RoCE 在 2010 年前后出现，把 RDMA 带到以太网。

RDMA 的代价是网络配置、内存注册与错误处理复杂，且需要专用网卡与交换机支持。它在高性能计算与存储网络中常见，通用互联网服务使用较少。

### 6.5 零复制

传统 `read`/`write` 要在用户态与内核态之间复制数据。零复制（zero-copy）接口减少复制次数：

- `sendfile` 在 1990 年代末出现，把文件内容直接送到套接字。
- `splice` 在 Linux 2.6.17 中加入，用管道连接两个文件描述符。
- `mmap` 把文件映射到地址空间，避免显式复制。

零复制减少 CPU 与内存带宽消耗，但增加了缓冲区生命周期与错误处理的复杂度。

## 7. io_uring

### 7.1 设计

io_uring 由 Jens Axboe 开发，在 2019 年的 Linux 5.1 中引入。它把提交队列（submission queue，SQ）与完成队列（completion queue，CQ）放在与应用共享的内存中：

- 应用填充提交队列条目（SQE）。
- 内核读取 SQE，执行操作。
- 内核填充完成队列条目（CQE）。
- 应用读取 CQE，获取结果。

系统调用 `io_uring_enter` 负责提交与等待，`io_uring_setup` 创建环形队列，`io_uring_register` 注册文件、缓冲区等资源。

### 7.2 批量与注册

io_uring 的收益主要来自三处：

1. 批量提交：一次系统调用提交多个操作，减少上下文切换。
2. 资源注册：文件描述符与缓冲区提前注册，省去每次操作的查找与锁定。
3. 共享内存：SQ 与 CQ 不需要每次复制，应用与内核直接读写。

后续版本加入了 SQPOLL（内核轮询线程）、多 shot accept、提供缓冲区等特性，进一步减少提交次数。

### 7.3 多 shot 与取消

多 shot 操作允许一次提交持续接收连接或数据，直到取消或出错。提供缓冲区让应用预先登记一组缓冲区，接收操作完成时返回缓冲区标识。

取消通过 `IORING_OP_ASYNC_CANCEL` 提交。取消本身是一个异步操作，目标操作可能已经完成，缓冲区要等到目标操作的 CQE 到达后才能释放。

### 7.4 局限

io_uring 是 Linux 专用接口，且受安全策略限制。部分容器运行时通过 seccomp 禁用 `io_uring_setup`，部分发行版通过 sysctl 关闭。内核版本与特性位决定可用功能，跨平台服务通常保留 epoll 或 IOCP 后端。

与 epoll 相比，io_uring 的编程模型更接近完成式：应用提交操作，等待完成。与 IOCP 相比，它把队列放在用户态共享内存，批量能力更强。两者都要求应用管理操作状态与缓冲区生命周期。

## 8. 语言与标准

### 8.1 回调

回调是最早的异步表达。应用注册完成处理器，事件循环在操作完成后调用。控制流被切开，生命周期与错误传播要手工维护。

### 8.2 future

future 提供结果的汇合点。生产者写入结果，消费者阻塞等待。标准 future 没有续接与取消，适合把并发结果收回当前线程，不适合作为事件驱动服务的核心抽象。

### 8.3 协程

C++20 引入无栈协程。编译器把协程体改写成状态机，局部变量保存在协程帧中。`co_await` 把异步操作接入顺序控制流，挂起与恢复由 awaiter 决定。

协程解决了控制流表达，没有解决 I/O 接口、调度与取消。任务库与执行器仍然要自己设计。

### 8.4 sender/receiver

C++26 的 `std::execution` 把异步操作拆成 sender、receiver 与 operation state，用完成签名描述结果，用调度器描述执行位置。它把组合、取消与调度提升到类型层面，代价是模板复杂度与编译期开销。

### 8.5 标准缺口

C++ 标准至今没有网络库与通用异步 I/O 接口。Networking TS 没有并入标准，平台 I/O 仍由 Asio 等库封装。语言层提供了协程与 sender，底层接口的差异仍然需要库来收敛。

## 9. 主线

### 9.1 等待方式

| 阶段 | 等待主体 | 等待方式 | 主要代价 |
| --- | --- | --- | --- |
| 程序控制 | CPU | 轮询状态寄存器 | CPU 空转 |
| 中断与 DMA | CPU 发起，设备搬运 | 中断通知 | 中断处理与同步 |
| 阻塞系统调用 | 线程 | 睡眠与唤醒 | 线程占用 |
| 就绪通知 | 事件循环 | 多路复用 | 应用管理状态 |
| 完成通知 | 内核或运行时 | 完成队列 | 操作与缓冲区生命周期 |
| 共享队列 | 应用与内核 | 批量提交与收割 | 平台绑定与复杂度 |

### 9.2 抽象层次

I/O 接口的抽象层次不断上升：

- 设备寄存器与中断。
- 文件描述符与 `read`/`write`。
- 事件与回调。
- 异步操作与完成令牌。
- sender 与完成签名。

每上升一层，应用少管理一些细节，库或运行时多承担一些责任。抽象泄漏的地方集中在三处：缓冲区生命周期、取消语义、执行位置。

### 9.3 代价转移

I/O 演化没有消除等待，只是把等待的代价转移：

- 从 CPU 转移到设备与中断控制器。
- 从线程转移到事件循环。
- 从内核转移到用户态运行时。
- 从通用路径转移到专用核心与网卡。

选择 I/O 模型，本质上是选择把代价放在哪一层，以及是否愿意为该层承担复杂度。

### 9.4 年表

| 时间 | 事件 | 等待方式 |
| --- | --- | --- |
| 1950 年代 | 中断与 DMA 进入计算机 | 硬件通知 |
| 1971 | Unix 文件描述符与 `read`/`write` | 阻塞 |
| 1983 | 4.2BSD 套接字与 `select` | 就绪通知 |
| 1986 | System V `poll` | 就绪通知 |
| 1994 | Windows NT IOCP | 完成通知 |
| 1999 | C10K 问题提出 | 事件驱动 |
| 2000–2002 | kqueue、epoll、Linux 原生 AIO | 就绪与完成 |
| 2009 | Node.js、Go netpoller | 运行时事件循环 |
| 2019 | Linux io_uring | 共享队列与完成通知 |
