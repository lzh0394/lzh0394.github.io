## 0. 结论摘要

`list` 的行为可以从一个结构事实推出：元素各自放在独立分配的节点里，节点用两个指针连成环形，容器只保存哨兵与元素个数。插入与删除改的是指针，元素本身不移动，因此除被删元素外，迭代器与引用在修改之后继续有效。

常数时间的边界由「是否要数节点」决定。单元素插入删除、整表 `splice`、单元素 `splice`、同一表内的范围 `splice` 都是 O(1)；跨表的范围 `splice` 是 O(distance)，因为要数出搬走了多少个节点才能维护 `size()`。`splice` 不分配节点、不构造元素，分配器相等是前置条件，不相等时行为未定义（N2525 之后的规定）。

异常保证比 `vector` 简单。节点先分配、元素在节点内构造、成功后才接入链表，插入抛出时容器不变（[list.modifiers]/2）；`erase`、`clear`、`pop_back` 不抛。代价不在异常路径上，而在常态：每个元素一次分配，节点地址分散，遍历是一次次依赖加载。

工程上可执行的四条规则：

- 只在需要「元素身份稳定」或「插入删除位置由迭代器给出」时选择 `list`，默认容器仍是 `vector`。
- 删除满足条件的元素用 `remove` 或 `remove_if`，不用「先 `find` 再 `erase`」的循环。
- 需要排序时用成员 `sort`；需要全量去重时先 `sort` 再 `unique`。
- 跨容器搬移元素优先用 `splice`，但必须保证两个容器的分配器相等。

## 2. 标准要求

### 2.1 要求集合与不提供的接口

`list` 的规范身份由 [draft][list.overview]/1 至 /2 给出：它是序列容器，支持双向迭代器，允许在序列任意位置常数时间插入与删除，存储管理自动完成，不提供快速随机访问。它满足容器、可逆容器、分配器感知容器与序列容器的要求，例外是 `operator[]` 与 `at` 不提供。

与 `vector` 的接口差异集中在容量与下标两处：`list` 没有 `data`、`capacity`、`reserve`、`operator[]`、`at`。位置一律由迭代器表示，`insert` 的第一个参数是「插入到哪个元素之前」，`erase` 接受迭代器而不是下标。这套接口的形状决定了成员算法的写法：`sort`、`merge`、`splice` 都是成员函数，因为它们需要直接操作节点之间的链接，通用算法拿不到这个权限。

C++17 起 `list` 可以用不完整类型实例化，特性宏为 `__cpp_lib_incomplete_container_elements`，条件与 `vector` 相同：分配器满足完整性要求，且在使用处元素类型完整。C++26 起全部成员函数标为 `constexpr`（P3372R3，特性宏 `__cpp_lib_constexpr_list` 取 202502L），迭代器满足 constexpr 迭代器要求。

### 2.2 复杂度

复杂度条款合并成一张表：

| 操作 | 复杂度 | 失效范围 | 异常保证 |
| --- | --- | --- | --- |
| 构造 n 个元素 | 线性于 n | 不适用 | 构造失败时对象未完成 |
| `insert` 单元素 | 常数，一次构造 | 不失效 | 无效果 |
| `insert` 多元素 | 线性于插入数，等量构造 | 不失效 | 无效果 |
| `erase` 单元素 | 常数，一次析构 | 仅被删元素 | 不抛 |
| `erase` 范围 | 线性于范围大小 | 仅被删元素 | 不抛 |
| `splice` 整表或单元素 | 常数 | 不失效 | 不抛 |
| `splice` 范围 | 同表常数，跨表线性 | 不失效 | 不抛 |

复杂度条款的写法需要单独说明。单元素插入是「常数时间，且恰好一次元素构造函数的调用」（[draft][list.modifiers]/1）；多元素插入是「线性于插入个数，且复制或移动构造函数的调用次数恰好等于插入个数」。后一句是关键：`list` 不会为了插入而复制已有元素，与 `vector` 的中间插入形成对照。

`erase` 的复杂度按被删元素计，不按剩余元素计（[draft][list.modifiers]/5）：单元素常数并一次析构，范围版本线性于范围大小并恰好等量的析构调用。这解释了为什么 `list` 从中间删除便宜：代价只落在被删元素上。

### 2.3 失效规则

四条规则可以覆盖全部成员函数：

1. `insert`、`emplace`、`push_front`、`push_back` 不影响任何已有迭代器与引用（[draft][list.modifiers]/2）。
2. `erase` 只使被删元素的迭代器与引用失效（[draft][list.modifiers]/3），`clear` 使全部失效。
3. `splice`、`sort`、`merge`、`reverse` 不使任何迭代器或引用失效（[draft][list.ops]）。
4. `end()` 不指向元素，标准不承诺它在修改之后仍然可用。

第 3 条的依据是节点地址不变：这些操作只改 `next` 与 `prev`，不移动元素，也不重新分配节点。第 4 条在实践中容易忽略：三家实现都把哨兵放在固定地址，libstdc++ 与 libc++ 内嵌在容器对象里，MSVC 分配一次之后不再移动，因此保存的 `end()` 迭代器通常仍指向同一个哨兵；标准不保证这一点，代码不应依赖[推断]。

### 2.4 异常保证

容器通用要求给出两条底线：[draft][container.reqmts] 规定单元素 `insert`/`emplace` 抛出时函数无效果，`erase`、`clear`、`pop_back`、`pop_front` 不抛异常。

`list` 的插入保证比这条底线更强。[draft][list.modifiers]/2 的措辞是「若抛出异常，则无效果」，作用于该小节的全部 `insert` 重载，包括范围插入与 `insert_range`。实现之所以能做到，是因为节点插入可以拆成「分配并构造」与「接入链表」两个阶段：前一段失败时容器还没有被改动。范围插入则先在一张临时表或一条临时节点链里构造全部元素，全部成功之后才接入。

`erase` 不抛的前提是元素的析构函数不抛。析构函数在 C++11 起默认 `noexcept`，若元素析构抛出，程序终止，这条路径不产生可恢复的状态。

成员算法的保证分三档：`splice` 不分配也不构造，没有抛出点；`merge` 在比较函数抛出时无效果；`sort` 在比较函数抛出时只保证元素不丢失，顺序未指定（[draft][list.ops]）。`remove`、`remove_if`、`unique` 在谓词抛出时保留已经删除的部分，属于基本保证。

### 2.5 分配器感知

`list` 是分配器感知容器。存储以「一个节点」为单位申请：容器把 `Allocator` 重绑定到节点类型，每次插入调用一次 `allocate(1)`，删除时调用一次 `deallocate(p, 1)`。元素的构造与析构通过 `allocator_traits` 作用在节点内的存储上，节点本身不用 `new` 创建。

分配器传播由三个 traits 决定，与 `vector` 相同：复制赋值、移动赋值、`swap` 是否带走分配器。差异在代价上：`vector` 的跨分配器移动赋值在有容量时可以退化为逐元素移动，`list` 的节点绑定在分配器上，跨分配器只能重新分配节点并移动元素，无法直接搬运节点。

`list` 的类型参数是元素分配器，内部使用节点分配器，`get_allocator()` 需要把节点分配器转回元素分配器。这一层转换由实现完成，标准只规定返回类型。

## 3. 节点与哨兵

### 3.1 环形结构

三家实现都用带哨兵的环形双向链表。哨兵不存元素，`next` 指向首元素，`prev` 指向末元素；空表时两个指针都指向哨兵自身。

```text
sentinel.next -> first node
sentinel.prev -> last node
last.next     -> sentinel
first.prev    -> sentinel
```

这个结构带来三个直接后果。`begin()` 是哨兵的下一个节点，`end()` 就是哨兵本身，因此 `--end()` 是合法的尾元素迭代器，双向迭代器「从末尾往回退一步」不需要特判。插入与删除只改相邻节点的指针，不涉及其他节点。空表与单元素表不需要特殊表示，哨兵自环即可。

### 3.2 三家实现的节点

| 实现 | 节点类型 | 节点内容 | 哨兵位置 |
| --- | --- | --- | --- |
| libstdc++ | `_List_node_base` 与 `_List_node` | 两个指针加 `__aligned_membuf` | `_List_impl` 内嵌 `_List_node_header` |
| MSVC STL | `_List_node` | `_Next`、`_Prev`、`_Myval` | `_Myhead` 指向分配的哑节点 |
| libc++ | `__list_node_base` 与 `__list_node` | `__prev_`、`__next_`、`__value_` | `__list_imp` 内嵌 `__end_` |

libstdc++ 把节点拆成两层：`_List_node_base` 只含 `_M_next` 与 `_M_prev`，`_List_node` 在此基础上用 `__aligned_membuf` 保存元素。这样 `splice`、`reverse`、`sort` 中只改链接的部分可以写在基类上，不必实例化元素类型相关的代码。基类上的 `_M_transfer`、`_M_hook`、`_M_unhook`、`_M_reverse` 正是这些原语[impl]。

MSVC 的 `_List_node` 把两个指针与 `_Myval` 放在同一个结构里，头节点的 `_Myval` 不构造，源码注释写明它「unused if head」。libc++ 同样分两层：`__list_node_base` 含 `__prev_` 与 `__next_`，`__list_node` 增加 `__value_`，并提供 `__as_link()` 在节点指针与基节点指针之间转换。

### 3.3 哨兵内嵌还是分配

哨兵的位置是三家实现最直观的差异。libstdc++ 在 `_List_base::_M_impl` 中内嵌一个 `_List_node_header`，libc++ 在 `__list_imp` 中内嵌一个 `__node_base __end_`；两者都随容器对象一起构造，空表不分配内存。MSVC 的 `_List_val` 只保存 `_Myhead`，头节点由 `_Buyheadnode` 通过分配器申请，因此默认构造的 `list` 也持有一次节点分配。

后果有两处。其一，MSVC 的默认构造可能抛 `bad_alloc`，标准没有禁止这一点，也没有规定 `list` 的默认构造不分配。其二，空表的析构在 MSVC 上要归还头节点，在另外两家只是重置两个指针。两种做法都符合标准，差别属于实现质量与异常行为的细节。

### 3.4 容器对象大小

`list` 对象只保存哨兵（或指向哨兵的指针）与元素个数，元素类型不进入 `sizeof`。64 位平台上，libstdc++ 与 libc++ 通常是三个机器字，MSVC 是两个机器字加分配器占位，空分配器经空基类优化后不占空间。调试模式会改变这个结果，见第 10 章。

### 3.5 元素计数的位置

计数与哨兵放在一起。libstdc++ 的 `_List_node_header` 继承 `_List_size`，`_M_size` 在 C++11 ABI 下存在，接口是 `_M_get_size`、`_M_set_size`、`_M_inc_size`、`_M_dec_size` 四个函数，旧 ABI 下它们是空实现。MSVC 的 `_List_val` 有独立的 `_Mysize` 字段。libc++ 把 `size_type` 与节点分配器放进一个 `__compressed_pair`。

计数为什么放在那里、旧 ABI 付出什么代价，是第 8 章的内容。

## 4. 迭代器与引用稳定性

### 4.1 一个节点指针

`list` 的迭代器只保存一个节点指针。libstdc++ 的 `_List_iterator` 存 `_List_node_base*`，MSVC 的 `_List_iterator` 存 `_List_node*`，libc++ 的 `__list_iterator` 存基节点指针。`operator++` 读取 `next`，`operator--` 读取 `prev`，关闭调试检查后没有其他状态。

由此得到几条成本结论。迭代器的大小与一个指针相同，复制迭代器是一次指针复制。没有 `operator+` 与 `operator[]`，`std::next(it, n)` 与 `std::distance` 都是线性。任何按「跳 n 步」设计的算法在 `list` 上都会退化为平方，`std::sort`、`std::binary_search`、`std::nth_element` 因此不能用于 `list`。

### 4.2 稳定性从哪里来

稳定性来自「元素不移动」。`vector` 的插入要腾位置，元素被移动或复制，地址随之改变；`list` 的插入只改相邻节点的两个指针，已有节点留在原地址。引用稳定性与迭代器稳定性是同一个事实的两种表述：节点地址不变，指向节点的迭代器不变。

这条性质有明确边界：只对当前容器内的元素成立，且只对未被删除的元素成立。`erase` 使被删元素的迭代器与引用失效，其他元素不受影响；`clear` 使全部失效。

### 4.3 `erase` 与遍历

`erase` 返回被删元素之后的迭代器，因此「边遍历边删除」的写法是 `it = l.erase(it)`。这个返回值在 C++11 起提供，C++98 的 `erase` 返回 `void`。

需要按条件删除一批元素时，`remove_if` 比手写循环更合适：它只遍历一次，删除个数由返回值给出（C++20 起），也不需要维护迭代器。

### 4.4 `splice` 之后的归属

`splice` 转移节点，不复制元素。指向被转移元素的迭代器与引用继续指向同一元素，但归属从 `x` 变成 `*this`（[draft][list.ops]/4）。用 `x.erase(it)` 删除一个已经属于 `*this` 的元素是错误用法；比较来自两个容器的迭代器是未定义行为，标准只保证这些迭代器「behave as iterators into `*this`」。

调试迭代器会检查归属：libstdc++ 的 `_GLIBCXX_DEBUG`、MSVC 的 `_ITERATOR_DEBUG_LEVEL` 取 2 时，这类错误会立刻触发断言，发布构建里则可能静默破坏链表。

## 5. 修改操作

### 5.1 单元素插入

单元素插入的顺序固定：分配一个节点，在节点内构造元素，再把节点接入链表，最后把计数加一。前两步失败时容器还没被改动，异常保证因此是「无效果」。

三家实现的差别只在守卫对象的名字。libstdc++ 的 `_M_create_node` 用分配守卫 `__allocate_guarded_obj` 持有节点，构造成功之后 `release()`；MSVC 的 `_List_node_emplace_op2` 继承 `_Alloc_construct_ptr`，构造成功之后用 `_Transfer_before` 完成接入；libc++ 先分配节点再 `__link_nodes`，失败路径上归还节点。

插入位置不影响成本：在头部、中间、尾部插入都是常数时间，都是一次分配加一次构造。这是 `list` 与 `vector`、`deque` 最根本的差别。

### 5.2 范围插入

范围插入的复杂度是线性于插入个数，且复制或移动构造次数恰好等于插入个数（[draft][list.modifiers]/1）。异常保证仍是「无效果」（[draft][list.modifiers]/2），实现方式有两种：先构造一张临时 `list` 再 `splice` 到目标位置，或者先构造整条临时节点链再一次性接入。

libstdc++ 走前一条路：`insert(pos, first, last)` 先用输入范围构造 `list __tmp`，非空时把整张临时表 `splice` 到 `pos` 之前，返回第一个插入位置。MSVC 走后一条路：`_List_node_insert_op2` 先把 n 个节点构造好并串成一条链，全部成功之后才挂到目标位置，源码注释写明它「maintains exception safety」。

两条路的共同点是「先全部构造、后统一接入」。范围插入因此比「循环调用单元素插入」多一层管理：临时表或临时链本身要构造，随后整段转移。对 `list` 来说这不是额外复制，节点被直接搬走，代价是临时的容器对象与一次分配器比较。

### 5.3 `erase` 与 `clear`

`erase` 的顺序是：摘链，析构元素，归还节点，计数减一。单元素删除是常数时间并恰好一次析构（[draft][list.modifiers]/5），不抛异常。

`clear` 线性于元素个数，逐节点析构与归还，声明为 `noexcept`。它不释放哨兵：内嵌哨兵的实现只把两个指针指回自身并把计数置零，MSVC 保留头节点。

### 5.4 `remove`、`remove_if`、`unique`

`remove` 删除所有等于给定值的元素，`remove_if` 删除谓词为真的元素，两者都恰好调用 `size()` 次比较或谓词（[draft][list.ops]）。`unique` 删除相邻的重复元素，调用 `size() - 1` 次比较，空表不调用。

libstdc++ 的实现有一处细节：`remove_if` 与 `unique` 把命中的节点 `splice` 到一张局部 `list` 里，遍历结束之后由局部对象统一析构。这样遍历过程中不会析构元素，也不会在循环里反复调整计数。C++20 起三者的返回值由 `void` 改为删除个数（P0646R1），libstdc++ 在旧 ABI 下仍返回 `void`，用宏在编译期选择返回类型。

`unique` 只比较相邻元素，因此全量去重需要先 `sort`：

```cpp
l.sort();
l.unique();  // 只合并相邻重复，因此必须先排序
```

`sort` 加 `unique` 是 `list` 去重的惯用法，代价是 O(n log n) 次比较与一次线性遍历。

### 5.5 `resize` 与 `assign`

`resize` 缩小时从尾部逐个删除，线性于删除个数；增大时在尾部插入默认值或给定值。缩小不涉及元素移动，因此被保留元素的迭代器与引用仍然有效。

`assign` 先清空再插入，异常时容器处于有效但内容不完整的状态，属于基本保证。需要「要么全换、要么不动」时，先构造临时 `list` 再 `swap` 更稳妥。

## 6. `splice`

### 6.1 三种形式

`splice` 有三个形式，C++11 起每个形式都有左值与右值两个重载，共六个签名：

```cpp
void splice(const_iterator pos, list& x);
void splice(const_iterator pos, list& x, const_iterator i);
void splice(const_iterator pos, list& x, const_iterator first, const_iterator last);
```

第一个把 `x` 的全部元素搬到 `pos` 之前，第二个搬单个元素，第三个搬范围。三个形式都不复制、不移动元素，只改链接。

### 6.2 语义与消耗

整表版本之后 `x` 为空；单元素版本之后 `x` 少一个元素；范围版本之后 `x` 失去该范围。被转移元素的迭代器与引用继续有效，归属变为 `*this`（[draft][list.ops]/4、/8）。

前置条件写在 [draft][list.ops] 中：三个形式都要求两个容器的分配器相等，否则行为未定义（/2）；整表版本要求 `addressof(x) != this`（/3）；范围版本要求 `[first, last)` 是 `x` 中的有效范围，且 `position` 不在其中；单元素版本要求 `i` 是 `x` 的有效可解引用迭代器。

### 6.3 复杂度

单元素版本与整表版本都是常数时间。单元素版本的常数性与是否跨容器无关，计数加一减一即可；整表版本把两张表接起来并把两个计数相加，也是常数。

范围版本分两种：`addressof(x) == this` 时是常数时间，总数不变，只需要改链接；跨容器时线性于 `distance(first, last)`（[draft][list.ops]）。跨容器之所以线性，是因为要数出搬走了多少个节点才能更新两边的计数。这条复杂度是 C++11 引入常数时间 `size()` 之后的必然结果，第 8 章会回到这里。

### 6.4 N2525 与分配器相等

C++98 的措辞在分配器不相等时只要求线性复杂度，实现可以逐个复制元素。N2525 把这种情况改为行为未定义，于是「常数时间」成为无条件的保证。代价是跨分配器搬移元素只能用 `insert` 加 `erase`，元素被复制或移动，节点被重新分配。

这条规则对泛型代码有影响：接受两个 `list` 并打算 `splice` 的函数，应当把「分配器相等」写成前置条件，或者在运行期检查并回退到 `insert`。

### 6.5 用途

`splice` 的典型用途有三类。第一类是把最近使用的元素移到表头，实现 LRU 缓存：命中的迭代器直接 `splice` 到 `begin()` 之前，常数时间，且不失效缓存中保存的其他迭代器。第二类是在容器之间搬运节点，避免元素的复制与移动，例如把任务从待处理表转到执行表。第三类是 `list` 自己的 `sort`：libstdc++ 用 64 张 `_Scratch_list` 与 `merge` 完成归并，全部操作都是节点重连。

```cpp
void touch(std::list<Item>& lru, std::list<Item>::iterator it) {
  lru.splice(lru.begin(), lru, it);  // 命中后移到表头，常数时间
}
```

`splice` 与 `merge` 的分工是：`merge` 假设两张表已经有序，按比较结果交错搬运；`splice` 不关心顺序，整段搬运。

## 7. `sort`、`merge`、`reverse`

### 7.1 为什么 `sort` 是成员函数

`std::sort` 要求随机访问迭代器，`list` 不满足，编译期就会失败。`std::stable_sort` 接受双向迭代器，但它通过赋值移动元素，并且需要额外缓冲。成员 `sort` 只改链接，不移动元素，因此元素类型不必可移动或可复制，只需要可比较。

`sort` 是稳定排序，复杂度约为 N log N 次比较（[draft][list.ops]）。这两个性质使它可以用于「元素不可移动但需要排序」的场景，例如元素内含自引用，或元素地址已经被外部观察者持有。

### 7.2 三家实现的归并路径

| 实现 | 归并方式 | 额外空间 |
| --- | --- | --- |
| libstdc++ | 自底向上，64 个 `_Scratch_list` 桶 | 固定桶数组 |
| MSVC STL | 递归 `_Sort`，按计数二分 | 递归栈 |
| libc++ | 递归 `__sort`，`std::next` 找中点 | 递归栈 |

三家的共同点是不分配节点、不复制元素。libstdc++ 的桶数组大小 64 与「2 的 64 次方足够覆盖任何 `size_type`」有关：第 i 个桶保存长度为 2 的 i 次方的已排序段，取出元素时按桶的长度顺序逐级合并。归并过程中节点暂时被摘出容器，异常时 `__catch` 把临时表里的节点全部放回 `*this` 再重抛，因此元素不会丢失。

MSVC 与 libc++ 采用自顶向下的递归：按计数把链切成两半，分别排序后合并。libc++ 用 `std::next` 定位中点，这一步是线性的，总代价仍是 O(n log n)；MSVC 的 `_Sort` 直接按节点数递归，返回新的首节点。

### 7.3 `merge`

`merge` 把另一张已排序表合并进来，结果是稳定的：相等元素保持原有相对顺序，标准措辞引用 [algorithm.stable]。比较次数至多 `size() + x.size() - 1`，同表 `merge` 无效果（[draft][list.ops]）。

`merge` 的前置条件是两张表都已按同一比较器排序，且分配器相等。它不复制元素，只搬运节点，因此迭代器与引用在合并之后仍有效，归属变为 `*this`。

### 7.4 `reverse`

`reverse` 交换每个节点的 `next` 与 `prev`，线性时间，不使迭代器失效（[draft][list.ops]）。libstdc++ 的 `_M_reverse` 写在 `_List_node_base` 上，与元素类型无关，三家实现的结构相同。

### 7.5 比较函数抛出之后

`sort` 与 `merge` 的异常保证不同。`merge` 在比较抛出时无效果：实现先比较再搬运，比较失败时还没有改链接。`sort` 只保证元素不丢失，顺序未指定：归并过程中节点已经被摘下并重新组合，无法恢复到原来的顺序。

需要「排序失败仍保持原顺序」时，只能自己保存副本，或者在异常后重新排序。这条差异在写异常安全的排序包装时容易被忽略。

## 8. `size()` 的复杂度历史

### 8.1 从线性到常数

C++98 的复杂度表允许 `list::size()` 是线性时间，早期实现因此不保存计数，`size()` 退化为一次遍历。C++11 起容器要求把 `size()` 统一为常数时间，容器必须自己记账。

这次改写改变的不只是 `size()`。整表 `splice` 要把两张表的计数相加，仍然是常数；跨表的范围 `splice` 需要知道搬走了多少个节点，于是变成线性于距离。两处改动合起来，`splice` 的复杂度才成为今天这样：整表与单元素是常数，范围跨表是线性。

### 8.2 记账的代价

多一个机器字是显性成本。隐性成本在每个修改操作上：插入要加一，删除要减一，`splice` 要加或减一个区间，`merge` 要把两边的计数合并。这些操作都是 O(1)，但都在热路径上。

### 8.3 libstdc++ 的实现时间线

libstdc++ 直到 2014 年才在新 ABI 下缓存计数，对应缺陷报告 PR 49561（2011 年提交，标题是 `std::list::size` 的复杂度）。当前实现在 `_List_base` 上提供 `_M_get_size`、`_M_set_size`、`_M_inc_size`、`_M_dec_size` 四个函数：C++11 ABI 下它们读写 `_List_size::_M_size`，旧 ABI 下是空实现，`_M_node_count()` 改为调用 `_S_distance` 遍历整条链[impl]。

因此同一份 GCC 头文件在不同 ABI 宏下给出不同的复杂度：`-D_GLIBCXX_USE_CXX11_ABI=0` 时 `size()` 是 O(n)。这是宏层面的行为差异，来源是历史兼容，标准没有留下这样的自由度。

### 8.4 MSVC 与 libc++

MSVC 的 `_List_val` 一直保存 `_Mysize`，libc++ 的 `__list_imp` 在压缩对中保存 `__size_`，两家的 `size()` 都是常数时间。差异在计数的位置：MSVC 与哨兵指针并列，libc++ 与分配器共享压缩对。

### 8.5 对使用者的影响

依赖 `size()` 常数时间的代码在旧 ABI 下会退化为二次复杂度，典型写法是在循环条件里反复调用 `size()`，或者用 `size()` 判断是否为空。判断空表用 `empty()`，它在三家实现里都比较指针，与计数无关。

`std::distance` 与旧 ABI 下的 `size()` 同价，都是遍历。需要频繁取长度时，把结果存进局部变量，不要每次重算。

## 9. 分配器、内存成本与选型

### 9.1 每个元素一次分配

`list` 的存储单位是节点，每个元素对应一次 `allocate(1)`。节点大小等于两个链接指针加元素本身，再按对齐补齐；64 位平台上 `int` 的节点通常是 24 字节，其中 16 字节是链接，4 字节是值，4 字节是填充。分配器自身还会在块外记录管理信息，具体大小由实现定义。

与 `vector` 的对照很直接：`vector` 的元素没有逐元素开销，扩容时一次性分配大块；`list` 每个元素都带固定开销与一次分配调用。元素越小，这笔开销的相对比例越大。

### 9.2 分配器传播

三个传播 traits 的作用与 `vector` 相同：复制赋值与移动赋值是否带走分配器，`swap` 是否交换分配器。`swap` 的 `noexcept` 条件由 `propagate_on_container_swap` 与 `is_always_equal` 的析取给出。

节点把容器与分配器绑得更紧。`vector` 的缓冲区可以逐元素移动，`list` 的节点不能跨分配器转移：两个分配器不相等时，移动赋值必须为每个元素分配新节点、移动元素、归还旧节点，代价是线性的，且元素的地址改变。需要「移动赋值是常数时间」时，两个容器的分配器必须相等。

### 9.3 `pmr` 与池资源

`std::pmr::list` 是 `list` 对 `polymorphic_allocator` 的别名，C++17 起提供。节点分配恰好是池资源擅长的场景：所有请求大小相同，`unsynchronized_pool_resource` 可以按固定尺寸切块，把每次分配的管理成本降到几次指针操作；`monotonic_buffer_resource` 适合「一次构造、整体释放」的容器。

两点限制需要注意。`polymorphic_allocator` 的传播 traits 全为 `false`，容器不会带走资源，资源的生命周期必须覆盖容器。`monotonic_buffer_resource` 不归还单块内存，只在析构时整体释放；`unsynchronized_pool_resource` 把归还的块留在池内复用，也不逐块还给上游。长生命周期与短生命周期的容器混用同一个资源，会导致内存占用只增不减。

### 9.4 遍历成本

遍历 `list` 的每一步都是一次依赖加载：读当前节点的 `next`，再按这个地址读下一个节点。地址由分配顺序决定，通常不连续；一个缓存行装不下几个节点；硬件预取器无法沿指针链提前取数。于是遍历的吞吐由访存延迟决定，而非指令数[推断]。

`vector` 的遍历是顺序读，预取器可以提前把后续缓存行取进来，每次迭代的成本接近一次加法与一次比较。两者的差距来自存储布局，不来自实现质量，也不随优化等级消失。

### 9.5 与 `vector`、`deque`、`forward_list` 的对比

| 容器 | 随机访问 | 中间插入删除 | 地址稳定 | 每元素额外开销 |
| --- | --- | --- | --- | --- |
| `vector` | 是 | 线性 | 重分配后失效 | 无 |
| `deque` | 是 | 线性 | 首尾插入不影响 | 块索引 |
| `list` | 否 | 常数 | 是 | 两个指针 |
| `forward_list` | 否 | 常数，需前驱 | 是 | 一个指针 |

选择规则：

- 默认用 `vector`。连续存储的遍历优势通常超过插入成本之差。
- 元素地址必须稳定，且插入删除位置由已有迭代器给出时，用 `list`。
- 只需要头部插入删除、且希望每个元素少一个指针时，用 `forward_list`。
- 需要两端插入删除、又不需要元素地址稳定时，用 `deque`。
- 需要稳定地址但不想承担逐节点分配时，用 `vector<std::unique_ptr<T>>`：对象在堆上，指针在连续存储里，遍历时只需一次间接寻址。

Stroustrup 在 2012 年的公开演讲里用随机插入删除的实验说明：即使负载看起来适合链表，`vector` 往往仍然更快，原因是移动元素的成本低于链表的访存成本（<https://www.youtube.com/watch?v=YQs6IC-vgmo>）。这个结论依赖元素大小、插入模式与硬件，不构成普遍规律，但足以说明「链表插入是 O(1)」不等于「链表更快」。

### 9.6 适用场景

适合 `list` 的场景有共同特征：元素身份比元素位置重要，插入删除的位置由迭代器给出，或者需要 `splice` 的整段转移语义。观察者模式里的回调注册表、LRU 缓存、需要保持地址稳定的对象池、需要在容器之间搬运任务节点的调度器，都属于这一类。

不适合的场景同样明确：以遍历为主、元素小、需要随机访问、对内存敏感。这些场景里 `list` 的每次访问都要付一次指针追逐，节点开销还会把内存占用放大数倍。

## 10. ABI、调试模式与误用

### 10.1 ABI

`list` 的布局是二进制接口的一部分。libstdc++ 的新旧 ABI 在计数上不同：旧 ABI 的哨兵只有两个指针，新 ABI 多一个 `size_t`，两种布局的 `list` 不能互换。MSVC 的 `_ITERATOR_DEBUG_LEVEL` 改变 `_List_val` 是否带容器代理、迭代器是否带容器指针。libc++ 用 `_LIBCPP_ABI_VERSION` 选择布局与行为。

混用不同档位构建的目标文件属于 ODR 违背，症状通常是运行时崩溃或静默的数据破坏，而不是链接错误。库的公开接口里出现 `std::list` 时，这条约束要写进构建要求。

### 10.2 调试与加固

三家的调试机制都在迭代器上加检查：

- libstdc++：`_GLIBCXX_DEBUG` 把 `std::list` 换成 `__gnu_debug::list`，迭代器记录所属序列，解引用与比较时检查归属；`_GLIBCXX_ASSERTIONS` 只加轻量断言，不改变容器类型。
- MSVC：`_ITERATOR_DEBUG_LEVEL` 取 0、1、2。大于 0 时容器带代理指针，迭代器带容器指针；取 2 时解引用还要确认不是 `end()`。
- libc++：`_LIBCPP_HARDENING_MODE` 取 `none`、`fast`、`extensive`、`debug`，加固以断言为主。

调试模式放大的是每个迭代器与每次操作，不只是容器对象。对以迭代器为参数的接口，这意味着调试构建与发布构建的函数签名相同而对象布局不同，跨库传递迭代器必须保证档位一致。

### 10.3 常见误用

| 写法 | 问题 | 修正 |
| --- | --- | --- |
| 先 `find` 再 `erase` 的循环 | 每次查找线性，整体平方 | 用 `remove` 或 `remove_if` |
| `std::sort(l.begin(), l.end())` | 需要随机访问迭代器 | 用成员 `sort` |
| `l[i]` 或 `l.at(i)` | `list` 不提供下标访问 | 用 `std::next` 或迭代器 |
| 跨分配器 `splice` | 行为未定义 | 保证分配器相等，或改用 `insert` 与 `erase` |
| 保存被删元素的迭代器 | 该迭代器失效 | 用 `erase` 的返回值 |
| `unique` 后仍有重复 | 只删除相邻重复 | 先 `sort` 再 `unique` |
| 缓存 `end()` | 标准不保证有效 | 每次调用 `end()` |

表中第一条最容易被低估。`list` 的插入是常数时间，查找不是；把「插入 O(1)」当成「操作 O(1)」是常见误读，定位插入点通常要先遍历，整体仍是线性。同样，`std::distance` 需要遍历，`size()` 不需要。

## 11. 演进

### 11.1 版本变化

| 版本 | 与 `list` 相关的变化 |
| --- | --- |
| C++98 | 基本接口；`size()` 允许线性；分配器不等时 `splice` 可线性 |
| C++11 | `size()` 常数时间；分配器不等时 `splice` 行为未定义（N2525）；`emplace` 系列；右值 `splice` 与 `merge` |
| C++17 | 不完整类型实例化；`std::pmr::list` |
| C++20 | `remove` 与 `unique` 返回删除个数（P0646R1）；`std::erase` 与 `std::erase_if`（P1209R0）；`<=>` |
| C++23 | `assign_range`、`insert_range`、`prepend_range`、`append_range`（P1206R7） |
| C++26 | 成员函数 `constexpr`（P3372R3）；容器加固（P3471R4） |

### 11.2 C++20 的返回值与自由函数

P0646R1 把 `remove`、`remove_if`、`unique` 的返回值从 `void` 改为删除个数，使「删除并计数」不必再手写循环。P1209R0 为容器加入统一的 `std::erase` 与 `std::erase_if`，`list` 的版本在 `<list>` 中提供，语义等价于成员函数。

这两项改动不改变复杂度，改变的是调用端的形状：删除元素的代码从「迭代器循环加计数器」变成一次函数调用，出错的机会随之减少。

### 11.3 C++23 与 C++26

C++23 通过 P1206R7 为容器增加 `assign_range`、`insert_range`、`prepend_range`、`append_range`，`list` 四个都有。范围接口省掉 `begin()` 与 `end()` 的样板，实现仍然走「先构造、后接入」的路径。

C++26 有两项相关变化。P3372R3 把全部成员函数标为 `constexpr`，特性宏 `__cpp_lib_constexpr_list` 取 202502L；常量求值中的分配必须在同一次求值内释放，因此 `constexpr` 的 `list` 只能作为局部对象使用，不能作为常量表达式的结果带出。P3471R4 引入容器加固，把越界与前置条件违反变成库内可诊断的失败。

GCC 主干另有一个实验性改动 `_GLIBCXX_USE_ALLOC_PTR_FOR_LIST`，让节点的链接指针也使用分配器给出的指针类型，服务于指针类型不是裸指针的分配器；这项改动仍在实现中，不属于标准要求[impl]。

---

## 12. 结论

`list` 的规范语义可以压缩成一句话：元素存放在独立节点里，容器只改链接，因此插入删除是常数时间，除被删元素外一切有效。这句话同时给出了它的成本：每个元素一次分配、两个指针的固定开销、遍历时的指针追逐。

可执行的规则有五条：

1. 默认用 `vector`；只有元素身份必须稳定，或插入删除位置由迭代器给出时，才用 `list`。
2. 删除按条件筛选的元素用 `remove_if`，不要写「先 `find` 再 `erase`」的循环。
3. 排序用成员 `sort`，去重先 `sort` 再 `unique`；两者都只改链接，不需要元素可移动。
4. 跨容器搬移节点用 `splice`，并保证分配器相等；否则改走 `insert` 加 `erase`。
5. 不要缓存 `end()`，不要在 `splice` 之后用原容器的迭代器删除元素。

判断一个 `list` 是否值得，不需要测量：看遍历次数与插入次数谁占主导。遍历占主导时，连续存储的收益超过插入的代价；插入占主导且位置已知时，`list` 的常数时间才有意义。
