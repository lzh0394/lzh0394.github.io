## 1. 导读：为什么值得把包管理器当一门学问

一台新机器上最先被安装的东西往往是包管理器，而它也是整台机器上最少被人真正读懂的部件。

大多数人跟它的关系停留在几组条件反射：

- 缺个工具，`apt install` 或 `dnf install` 一下
- 项目跑不起来，`rm -rf node_modules && npm install` 一下
- 版本不对，`nvm use` 或 `pyenv global` 一下

这些反射大部分时候有效，直到某天失效：包装不上、装上了跑不起来、昨天还是绿的 CI 今天红了、某条构建日志里冒出一个没听说过的包名。失效的原因几乎从不在命令本身，而在于命令背后那台机器没被搞清：谁在决定版本、谁在执行代码、谁在缓存什么、失败时到底是哪一层在报错。

本系列把包管理器当成一个可分析的对象，而不是一串要背的命令。本系列分四篇：

| 篇 | 内容 |
| --- | --- |
| [（一）依赖管理的原理](/post/2026/09/24/package-managers-principles/) | 包的形态、依赖求解、版本约束、锁文件、隔离、仓库、安装脚本（本篇） |
| [（二）系统级包管理器](/post/2026/09/24/package-managers-os/) | apt、dnf、pacman、apk、Homebrew、winget、Nix 等 |
| [（三）语言级包管理器](/post/2026/09/24/package-managers-language/) | JS、Python、Rust、Go、JVM、.NET、C/C++ 等 |
| [（四）应用层、供应链与实践](/post/2026/09/24/package-managers-practice/) | Flatpak、容器、构建图、版本管理器、私有源、供应链安全、选型与陷阱 |

两种读法：想建立完整认知，从头读大约需要一小时；只想查某个工具，直接跳到对应章节即可。如果时间有限，建议至少读第 3.5 节（锁文件）、第 3.6 节（隔离）和第 3.8 节（安装时执行代码）——这三节解释的失败模式横跨所有生态，也是后面所有具体工具争议的源头。

有一点先说清楚：本系列不会给出「最好的包管理器」。这类排名在技术上是无意义的，因为设计空间由生态年龄、语言构建特性、包的规模量级和社区治理方式共同决定，而这些条件不可迁移。更有用的做法是理解每个工具在哪条轴上做了取舍，然后判断那条轴对具体场景是否重要。

事实、命令与版本现状经过抽样核对（多数结论对着官方文档与 man page 又过了一遍）；包管理器变化很快，涉及生产环境的决定请以官方文档为准。

## 2. 术语与约定

中文技术写作里最容易含糊的几组词，这里先定死：

- 包（package）：可被安装的最小分发单位。它可能是二进制（`.deb`、`.rpm`、wheel），也可能是构建脚本或源码（crate、sdist、PKGBUILD、ebuild）。
- 制品（artifact）：构建设计产出并被分发的东西，范围比「包」更宽，容器镜像也属于制品。
- 仓库（registry / repository）：发布与索引服务，如 npm registry、PyPI、crates.io、Maven Central。本系列一律叫「仓库」。
- 源（source / mirror）：镜像、代理或本地私有服务，如 `sources.list` 里的条目、国内镜像站、企业 Nexus。需要区分形态时叫「镜像」（完整复制）与「代理」（按需缓存），统称时叫「源」。
- 清单（manifest）：声明约束的文件，如 `package.json`、`Cargo.toml`、`pyproject.toml`、`requirements.in`。
- 锁文件（lockfile）：记录求解结果的文件，如 `package-lock.json`、`Cargo.lock`、`poetry.lock`。清单与锁文件的区别是理解全系列的一把钥匙。
- 求解（resolution）：从约束集合中选出一组具体版本的过程。
- 隔离（isolation）：让不同项目或不同版本的依赖互不干扰的机制，形式从目录嵌套到内核命名空间都有。
- 系统级 / 语言级 / 应用层：分别指发行版包管理器、语言生态包管理器、以及 Flatpak／容器这类以整个应用或镜像为单位的分发机制。

命令示例以 Debian/Ubuntu、macOS 和 Windows 为主，涉及其他发行版时单独标注。示例中的包名、路径与版本以写作时（2026 年）的现状为准；包管理器是变化最快的软件之一，遇到不一致时以官方文档为准。

## 3. 原理

### 3.1 包管理器替代了哪些手工劳动

在没有包管理器的年代，装一个库有一套固定的手工流程：去项目主页找下载页，挑一个 tarball，解压到 `/usr/local/src`，读 `README` 和 `INSTALL`，跑 `./configure`。`configure` 常常在第一步就失败，因为缺头文件——需要先知道这个库依赖谁，而这件事通常只写在 `README` 的一行小字里。补完依赖再 `make`，编译报错指向某个 API 变了，于是回头换一个更旧的版本重来。最后 `make install`，文件散进 `/usr/local/lib`、`/usr/local/include`、`/usr/local/bin`。半年后要卸载，只能凭记忆删文件，或者干脆留着。

这段流程的每个环节都不是技术难点，而是账本问题：谁依赖谁、装了什么版本、文件放在哪、怎么回退。人脑不擅长记账，所以问题会以最别扭的形式爆出来——编译到一半缺头文件，或者升级一个库之后另一个程序启动就段错误。

包管理器的价值可以拆成九件事，前六件让它能替代手工流程，后三件让它比手工流程更可靠：

| 承诺 | 具体含义 | 机制所在 |
|---|---|---|
| 发现 | 按名字找到包，不用记住下载地址 | 仓库与索引（见第 3.7 节） |
| 版本选择 | 从多个版本里挑一个满足约束的 | 依赖求解（见第 3.3 节） |
| 传递依赖 | 自动把依赖的依赖也装上 | 同上 |
| 构建 | 需要编译时由工具代跑构建 | 源码分发（见第 3.2 节）、安装脚本（见第 3.8 节） |
| 安装到正确位置 | 文件落点由工具决定并登记 | 数据库 |
| 冲突检测 | 两个包要同一个文件时能发现 | 求解器与数据库 |
| 升级 | 知道当前版本，能算出可升级的版本 | 数据库 + 求解器 |
| 卸载 | 精确删除自己装的文件，不动别人的 | 文件清单 |
| 来源校验 | 校验哈希与签名 | 见[《包管理器（四）》第 2.2、2.3 节](/post/2026/09/24/package-managers-practice/#22-防御一锁定校验与最小权限) |

把这张表压成一句话：包管理器本质上是数据库 + 求解器 + 分发网络。数据库记录「本机装了什么、每个包装了哪些文件」；求解器决定「应该装哪些版本」；分发网络负责「把内容取下来，且取到的东西可以验证」。下载只是分发网络里最不重要的那一环——`curl` 也能下载。

这个视角能解释很多看似奇怪的现象。为什么 `apt` 需要先 `update`？因为「哪个包有哪些版本」存在本地索引里，索引过期，求解器就是在解一道错误的题。为什么在 PEP 668 之前 `pip install` 会建议 `--user`？因为写入系统目录需要权限，而在数据库层面，用户级安装与系统级安装是两套账本。为什么两个包管理器装同一个软件会打架？因为两套数据库互不知情，各自的文件清单都认为自己拥有那些文件。

边界也要划清。包管理器不负责「怎么把代码变成产物」——那是构建系统的事（见[《包管理器（四）》第 1.3 节](/post/2026/09/24/package-managers-practice/#13-bazelnxturborepo从依赖管理到构建图)）；不负责「装哪个语言运行时版本」——那是版本管理器的事（见[《包管理器（四）》第 1.4 节](/post/2026/09/24/package-managers-practice/#14-版本管理器不是包管理器nvmpyenvrustupasdfmise)）；也不负责「把整个应用连同运行时一起发出去」——那是容器与 Flatpak 这类机制的事（见[《包管理器（四）》第 1.1、1.2 节](/post/2026/09/24/package-managers-practice/#11-flatpaksnap-与-appimage应用分发的新一层)）。它们经常被混为一谈，因为它们都要读写磁盘、都要改 `PATH`，但账本是分开的。

> 一句话总结：包管理器的核心是账本与求解器，下载只是它最容易被替代的一部分。

### 3.2 包的形态：源码分发与二进制分发

同一个包名，可能是两种完全不同的东西：一份可以直接铺到磁盘上的预编译产物，或者一份必须先在当前机器上编译的源码加构建脚本。

二进制分发是发行版的主流形态。Debian 的 `.deb`、Fedora 的 `.rpm`、Alpine 的 `.apk`、Windows 的 MSI、Python 的 wheel，里面都是已经编译好的文件加元数据。Python 的 wheel 文件名把兼容性写进了名字里：`numpy-2.0.0-cp312-cp312-manylinux_2_17_x86_64.whl` 依次声明 CPython 3.12、CPython ABI、Linux 的 glibc 下限 2.17、x86-64 架构。装不上的时候，pip 报的错通常是「找不到匹配的发行版」——它其实在说：索引里没有一份能在当前机器上运行的二进制，而源码构建又失败了。

源码分发则是另一套账。Rust 的 crate 发布到 crates.io 的是源码，用户本地用 `cargo build` 编译；Go module 也是源码；Debian 的 source package、Arch 的 `PKGBUILD`、Gentoo 的 ebuild、Nix 的 derivation，都是「构建配方」而非产物。配方的价值在于用户能改：Gentoo 的 `USE` 标记、Nix 的 derivation 参数、`PKGBUILD` 里的编译选项，都允许在构建时做选择。代价同样明确：用户机器上得有完整工具链，构建时间从几十秒到几小时不等，构建过程中还得联网取更多依赖，而且同源码不同机器不一定编译出同样的东西（见第 3.8 节）。

二进制分发的代价集中在构建矩阵。一个包要覆盖 glibc 与 musl 两套 C 库、x86-64 与 aarch64 两种架构、若干 Python 版本，产物数量很快变成两位数。这就是为什么 manylinux 这类规范存在：它把「最低 glibc 版本」变成一个可以写进文件名的标签，让一份产物能覆盖一片系统。这也解释了 Alpine 上装 Python 包的经典困境——musl 与 glibc 不兼容，linux 版 wheel 直接不可用。CPU 指令集同理：为 `x86-64-v3` 编译的二进制在老机器上会直接非法指令退出，而包管理器在解析阶段无从得知。

元数据是两种形态共有的部分，也是包管理器的真正抓手：包名与版本、依赖声明、冲突声明、文件清单、安装与卸载脚本、以及哈希或签名。差别在于谁来生成。二进制包的元数据由打包者写好后封进包里，安装时直接读；源码包的元数据部分来自包自己的清单（`Cargo.toml`、`pyproject.toml`），部分要跑一遍构建才能得到——Python 的 `setup.py` 时代尤其如此，依赖声明甚至可能在安装时动态计算出来，这使得「先求解、后安装」的顺序在 Python 里长期无法彻底成立（见[《包管理器（三）》第 1.2 节](/post/2026/09/24/package-managers-language/#12-python从-requirementstxt-到-uv)）。

各生态的选择很能说明问题。Rust 与 Go 习惯源码分发，因为语言自带构建系统、生态包普遍很小、跨平台编译足够简单；Debian 与 Arch 严格二进制，因为「用户机器上什么都装得出来」是发行版不能接受的假设；Nix 两头都做，但无论源码还是二进制都先落进 store，用输入哈希决定路径，把两种形态统一到同一个寻址模型里（见[《包管理器（二）》第 1.8 节](/post/2026/09/24/package-managers-os/#18-nix-与-guix把包管理器当成构建系统)）。没有哪种更先进，只是对「谁来承担构建成本」这一问题给出了不同答案。

> 一句话总结：源码分发把成本推给用户换灵活性，二进制分发把成本压给打包者换速度。

### 3.3 依赖求解：从贪心到 SAT

依赖求解（dependency resolution）可以形式化得很干净：给定一组包、每个包的若干版本、每个版本的依赖约束，求一组版本赋值，使所有被选中版本的依赖都成立，且「同一个包最多选一个版本」这条隐含约束也成立。后者是关键，它把「顺着图走一遍」变成了搜索。

把每个包版本看作布尔变量，「选 A 就必须选 B 的某个版本」写成逻辑蕴含，问题就等价于布尔可满足性问题（SAT），而 SAT 是 NP 完全的。但最坏情况不等于常见情况：真实图里相邻版本的需求高度相似、可选解极多，多数求解根本不必回溯。uv 的官方文档说得很直接——理论上要穷举所有组合，实践中「对大多数解析，求解器不需要回溯，迭代地挑版本就够了」。所以衡量求解器的标准有两个：需要回溯时是否高效，失败时能否解释原因。

现实策略大致分四类。

优先取最新的深度优先回溯（没有冲突学习）：按顺序把依赖排成队列，每个依赖优先挑最新的可行版本，走不通就回溯到上一个决策点换一个候选，直到找到一组解或穷尽所有候选。Cargo 官方文档的伪代码正是这个形状（`pick_next_dep` 选依赖、`pick_next_version` 优先取最新、失败则回溯）；`pip` 自 20.3 起默认的解析器（resolvelib）也属于这一类，它偶尔长时间卡在「正在解析依赖」正是回溯在起作用。代价是最坏情况要遍历大量组合，而且失败时说不出为什么：没有冲突学习的实现给不出跨多层传递依赖的解释。

回溯加冲突学习在采用回溯的求解器里已是主流做法之一（PubGrub 系：uv、Poetry、Dart 的 pub），源自 SAT 里的 CDCL（冲突驱动子句学习）：冲突时把根因记成一条「不可兼得」的事实，以后遇到同样组合直接跳过。PubGrub 的实现文档说明它据此生成人类可读的解释，形如「因为 `foo <1.1.0` 依赖 `a ^1.0.0`，而 `a` 依赖 `b ^2.0.0`，所以 `foo <1.1.0` 需要 `b ^2.0.0`；又因为 `foo <1.1.0` 依赖 `b ^1.0.0`，`foo <1.1.0` 被禁止」。uv 用 Rust 的 pubgrub-rs，Dart 的 pub 属同一谱系。

完整的 SAT 求解把问题编码成布尔公式交给通用求解器，libsolv 是这条路线最知名的实现，被 openSUSE 的 zypper 使用。它能力上限高，能顺带表达「两个包不能共存」「尽量保留已安装版本」这类非依赖约束；代价是编码开销，以及错误信息是求解器视角的（「不可满足的子句集」），离用户的语言较远。

放弃全局求解换了一条路：让同一包的多个版本共存于不同子树，冲突自然消失。npm 早期的嵌套 `node_modules` 就是这个模型，代价是目录爆炸、同一份代码被装多次、幻影依赖（见第 3.6 节）。Maven 的依赖调解（dependency mediation）按「最近优先」挑版本，同深度时先声明者胜出；它不搜索，所以不会解析失败，而是可能悄悄选错版本，症状变成运行时的 `NoClassDefFoundError`（见[《包管理器（三）》第 1.5 节](/post/2026/09/24/package-managers-language/#15-jvmmaven-的约定与-gradle-的灵活)）。Go 的 MVS 更彻底，把「选最新可行版本」换成「取所有约束里最高的最小版本」，问题退化成图遍历，代价是升级不积极（见[《包管理器（三）》第 1.4 节](/post/2026/09/24/package-managers-language/#14-gogopath-的教训与最小版本选择)）。

最后是判断标准。「找不到解」和「解不符合预期」是两回事：前者是求解空间为空，需要解释谁和谁冲突、卡在哪条路径；后者是合法解很多而求解器选得意外——Cargo 文档承认，`>=0.6` 这类开放约束会让求解器不做去重，产出两份本可合并的依赖，要用 `cargo update --precise` 收拾。两类问题的修复手段完全不同。

> 一句话总结：求解器之间的差距不在能不能解，而在回溯效率与失败时能否讲清原因。

### 3.4 版本约束的方言

语义化版本（SemVer）只承诺一件事：`MAJOR.MINOR.PATCH` 中只有 major 递增才允许破坏兼容。它管不到的比管得到的更多——行为兼容、性能、传递依赖变化都不在承诺内（见第 3.9 节）。而各生态「如何把约束写下来」的方言差异，比语义本身大得多。

同一个意图——「至少 1.2.3，但不跨到 2.0.0」——写法如下：

| 生态 | 写法 | 展开后的实际范围 |
|---|---|---|
| npm / Cargo | `^1.2.3` | `>=1.2.3 <2.0.0` |
| Cargo 默认 | `1.2.3` | 同 `^1.2.3`，Cargo 的裸版本号就是 caret |
| npm 默认 | `1.2.3` | 恰好 `1.2.3`，npm 的裸版本号是精确匹配 |
| Python（PEP 440） | `>=1.2.3,<2.0.0` | 需要显式写出上下限 |
| Maven | `[1.2.3,2.0.0)` | 方括号含、圆括号不含 |

上表里最值得记住的是第三、四行：裸版本号在 npm 与 Cargo 里含义相反。`npm install lodash@1.2.3` 与 `Cargo.toml` 里写 `lodash = "1.2.3"` 看似一样，前者钉死一个版本，后者是一个区间。这是两套默认值哲学：npm 把「测过这个版本」当默认，Cargo 把「要兼容的语义范围」当默认。

其他方言的细节同样不能凭直觉。npm 的 `~1.2` 和 `1.2.x` 都等价于 `>=1.2.0 <1.3.0`；npm 的 caret 在 0.x 上会收紧，`^0.2.3` 是 `>=0.2.3 <0.3.0`，`^0.0.3` 是 `>=0.0.3 <0.0.4`，因为 0.x 没有兼容性承诺。Cargo 的兼容性定义是「最左侧非零位相同」，`"0.2.3"` 同样等于 `>=0.2.3, <0.3.0`；Cargo 的 `~1` 是 `>=1.0.0 <2.0.0`，npm 的 `~1` 同样等价于 `1.x`。Python 的 `~=` 是「兼容发布」子句，语义反直觉：`~=2.2` 等价于 `>=2.2, ==2.*`（不允许写成 `~=2`），`~=1.4.5` 等价于 `>=1.4.5, ==1.4.*`，想收紧范围就多补一个零，`~=2.2.0` 变成 `>=2.2.0, ==2.2.*`。Maven 的区间支持并集与排除：`(,1.0],[1.2,)` 表示「≤1.0 或 ≥1.2」。

`*` 与 `latest` 是另一个坑：Cargo 官方建议避免 `*`，crates.io 不允许发布带裸 `*` 的依赖，因为它会在一次普通的 `cargo update` 里把不兼容的 major 拉进来。Go 把所有约束写成「最小版本」：`require example.com/mod v1.2.3` 意思是「至少 1.2.3」，最终取图中所有约束里最高的最小版本，所以 Go 的约束不含上限。日期版本（CalVer）也常见：Ubuntu 用 `24.04` 表示 2024 年 4 月，排序天然正确、人能读懂时间，代价是它不携带兼容性语义。

预发布、构建元数据、本地版本号这三类差异最集中。预发布（`1.0.0-beta.1`）几乎在所有生态里都默认被排除，除非显式写出：Cargo 的 `foo = "1.0"` 不匹配 `1.0.0-alpha`，要写 `foo = "1.0.0-alpha"`；PEP 440 规定已安装的预发布可被接受，别处的预发布只在没有正式版本能满足时才考虑；uv 把这条做成开关，默认 `if-necessary`，另有 `allow`、`disallow`。构建元数据（`+` 之后的部分）几乎一律被忽略：Cargo 明确说版本元数据不应用于约束，Go 会把带构建元数据的版本转成伪版本（pseudo-version）以维持全序。本地版本号（`1.0.0+local`）是 Python 特有机制，PEP 440 允许下游用它标记「与上游 API 兼容但打了补丁的重建版本」，同时明确要求 PyPI 不接受它——它是给发行版与私有源用的。

最后是上限（upper bound）之争：库该不该在依赖里写 `<2.0`？

主张设上限的理由是：库可能在小版本里悄悄破坏构建，上限能保证发布时验证过的组合在未来也成立。反对的理由是上限会传染：若 A 依赖 `B >=1.2,<2`，而 `B 2.0` 早已发布且被 C 需要，整张图可能因 A 的上限而无解。更糟的是上游被卡住时的常见应对是「发布一个去掉上限的旧版本补丁」，求解器于是回溯到更老、更少人用的版本，问题被掩盖而非解决——uv 的文档把这个现象写进了它忽略 `requires-python` 上限的理由里。

现实分布：npm 与 Cargo 默认不设上限（Cargo 建议不要写比下一个不兼容版本更窄的上限，如 `~2.0`、`>=2.0,<2.4`）；Python 社区偏向设上限，尤其是带 C 扩展或与运行时强耦合的包。判断条件可以写出来：叶子依赖（被单一项目独占）的上限成本与收益都归该项目；公共库的上限成本会转嫁给整张依赖图。区间越宽越好装、越窄越可复现，这是同一枚硬币的两面；真正的解法通常不是调区间，而是把可复现性交给锁文件（见第 3.5 节）。

> 一句话总结：约束方言的差异是默认值哲学之争，上限问题该按「谁承担成本」判断。

### 3.5 锁文件：可复现性的最小代价

#### 3.5.1 锁文件记录的是求解结果

清单（`package.json`、`Cargo.toml`、`pyproject.toml`）写的是约束，锁文件写的是这台机器在某个时刻对约束求解出来的答案。约束是「允许哪些版本」，答案是「这次安装拿了哪个版本、从哪个地址拿的、哈希是多少」。这个区别决定了很多事：改清单不一定让锁文件失效（放宽区间、加一个可选依赖都可能不需要重解），改锁文件却几乎一定要求清单能解释它——`npm ci` 和 `--frozen-lockfile` 检查的正是这条一致性；同一条清单在不同时间、不同平台、不同镜像上可以解出不同的答案。

求解器默认偏向「最新可行版本」，所以不提交锁文件的项目，今天的构建和六个月后的构建不是同一个东西。

一个具体的例子：同一个 `package-lock.json` 里，`node_modules/lodash` 对应的条目会写明 `4.17.21`、`resolved` 里的下载地址，以及 `integrity` 里的内容哈希。三样东西分别回答了「哪个版本」「从哪拿」「拿到的是不是同一份字节」。清单里对应的只是 `"lodash": "^4.17.0"` 这一行约束。

#### 3.5.2 各生态的形态对照

| 生态 | 文件 | 粒度与校验 |
|---|---|---|
| npm | `package-lock.json` | 完整依赖图 + `integrity` 哈希 |
| pnpm | `pnpm-lock.yaml` | 完整图 + 完整性哈希，导入方与快照分离 |
| Yarn | `yarn.lock` | 完整图 + 校验和 |
| Python（uv） | `uv.lock` | 全域锁，覆盖所有平台与 Python 版本标记 |
| Rust | `Cargo.lock` | 完整图 + 校验和 |
| Go | `go.mod` + `go.sum` | 没有锁文件；`go.sum` 只做校验 |
| .NET | `packages.lock.json` | 需显式开启锁定恢复 |
| Ruby | `Gemfile.lock` | 完整图，含平台标记 |

Go 是个例外中的例外：最小版本选择是确定性的，构建列表每次重新计算都一样，所以不需要像 npm 那样保存一份答案，`go.sum` 只负责防止内容被篡改。这也说明「锁文件」不是包管理的必备件，而是「求解结果不稳定」这个前提的补丁。

#### 3.5.3 库与应用：惯例不同

应用提交锁文件，库通常不提交。理由是库的消费者会自己求解，库锁死自己的依赖只会把过时的版本钉在别人身上。Rust 官方在 2023 年调整过这条指引：不再区分库与二进制，建议以提交 `Cargo.lock` 为默认，`cargo new` 也不再把库的锁文件写进忽略规则；理由是便于二分定位问题、验证 MSRV，以及给 CI 一个稳定的起点。

升级靠改锁文件而不是改清单：`npm update`、`cargo update`、`uv lock --upgrade` 都在不动约束的前提下重解。CI 则相反，要拒绝重解：`npm ci`、`pnpm install --frozen-lockfile`、`uv sync --locked`、`cargo build --locked`，锁文件与清单不一致时直接失败。

#### 3.5.4 锁文件锁不住的东西

常见事故有三类。Git 合并锁文件时冲突，人肉手改的版本组合多半没被求解器验证过，正确做法是接受任一版本后重新生成。跨平台可选依赖会漏：`esbuild`、`sharp` 这类包把平台二进制放在 `optionalDependencies` 里，锁文件只记下了求解时所在平台的条目，换平台需要重解。镜像源与锁文件的哈希对不上时，安装器会拒绝而不是降级使用，这是设计如此。

更根本的一点：锁文件只固定了包，不固定工具链。Node 版本、Python 解释器、C 编译器、构建时的环境变量都不在锁文件里，而它们同样影响结果。真正的可复现要一路钉到工具链和构建环境（见[《包管理器（四）》第 1.2、1.3 节](/post/2026/09/24/package-managers-practice/#12-容器与-oci-镜像分发单元的迁移)）。

> 一句话总结：锁文件把「这次解出了什么」变成可提交的产物，但它只锁住依赖，锁不住工具链和构建环境。

### 3.6 隔离：从全局到项目级

#### 3.6.1 三种隔离目标

隔离要解决三个层次的问题：依赖版本互不干扰、可执行文件指向正确的那个版本、构建环境互不污染。多数工具只做前两件。前两件是显而易见的失败——同一个库的两个版本装在同一处必然互相覆盖；第三件要隐蔽得多，它在涉及原生扩展、需要头文件和编译器时才会暴露，而且暴露的方式是「在本机能编过」。

| 机制 | 做法 | 代价 |
|---|---|---|
| 嵌套 `node_modules` | 每个包带自己的依赖目录 | 目录极深、重复安装 |
| 提升（hoisting） | 能合的依赖提到顶层共享 | 产生幻影依赖 |
| pnpm store + 符号链接 | 内容寻址存储 + 硬链接 + 严格符号链接 | 布局非常规，工具兼容问题 |
| venv | 改 `sys.prefix`，隔离 `site-packages` | 只隔离 Python 包，不隔离解释器与系统库 |
| conda 前缀 | 每个环境一个前缀目录 | 需要单独分发二进制，体积大 |
| Nix store | 输入哈希决定路径 | 路径不像 FHS，编译适配麻烦 |
| 容器 | 文件系统与进程命名空间 | 最彻底，也最重 |

这张表里没有「免费」的选项：隔离越强，构建与调试的隐式假设就越多地被打破，团队要么接受这份成本，要么在某个环节重新放开。

#### 3.6.2 hoisting 与幻影依赖

历史上 npm 早期用的是纯嵌套布局，目录能深到突破 Windows 的路径长度限制，磁盘占用也成倍增加。扁平化是对这个问题的直接回应。

npm 从嵌套改成扁平化，是为了让共用依赖只装一份。规则是：同名同版本尽量提到顶层 `node_modules`，版本冲突的留在需要它的包的 `node_modules` 里。结果是顶层目录里堆了一大批未声明过的包。

Node 的解析算法会沿父目录逐级向上找 `node_modules`，于是 `require('semver')` 这种代码即使从未声明 `semver`，只要它恰好被别的依赖提升上来，本地就能跑。这就是幻影依赖（phantom dependency，也叫幽灵依赖）。CI 挂掉的原因是安装顺序、包管理器版本或锁文件状态的细微差别让那次提升没有发生。

pnpm 用符号链接把「谁能看到谁」写死在目录结构里，只暴露声明过的依赖，因此天然拒绝幻影依赖；代价是它默认仍会为兼容破损包做一层提升，要完全严格需要显式关闭提升。Yarn PnP 更进一步，直接不生成 `node_modules`，改用 `.pnp.cjs` 这个解析器接管 `require`，把未声明的访问变成带包名的报错。代价是生态里那些依赖幻影依赖的包会当场报错，编辑器与工具链也要额外适配。

诊断手段：`npm ls <pkg>` 会打印这个包在树里的位置以及是谁依赖了它；`npm dedupe --dry-run` 能看出还有哪些重复版本可以被合并；pnpm 的 `why <pkg>` 直接给出解析路径。

#### 3.6.3 PATH 与 shim

可执行文件是第二层隔离。`node_modules/.bin` 下的脚本是 npm 生成的 shim，Windows 上会额外生成 `.cmd` 与 `.ps1`，共三个文件；`bundle exec`、`uv run`、`poetry run`、`npx` 走的都是「先切环境再执行命令」这条路。它们的差别在隐式程度：`bundle exec` 要求显式调用，`direnv` 和 Nix devShell 直接改 shell 环境，方便但让「当前用的是哪个版本」变得不可见。隐式的代价是排查变难，显式的代价是每条命令都要多打几个字。

全局安装没有被淘汰，是因为它服务的是另一类需求：CLI 工具需要在任何目录下可用，系统集成需要固定路径。当同一个包既有 CLI 又是库，全局安装与项目依赖就会打架——全局的 `eslint` 和项目里的 `eslint` 版本不同，报错行为也不同。这类工具更适合用「独立环境安装」的办法（见[《包管理器（三）》第 1.2 节](/post/2026/09/24/package-managers-language/#12-python从-requirementstxt-到-uv)、[《包管理器（四）》第 3.1 节](/post/2026/09/24/package-managers-practice/#31-决策指南什么场景用什么)）。

> 一句话总结：隔离的难点不在版本，而在可执行文件与构建环境；hoisting 用便利换来了幻影依赖。

### 3.7 仓库、镜像与私有源

#### 3.7.1 中央仓库的构成

一个仓库由四件事组成：包文件的存储、可查询的元数据索引、搜索与发布 API、命名空间与所有权规则。前两个决定安装能不能成功，后两个决定生态能长成什么样。

命名空间是最容易被忽略的一条。npm 的全局命名空间先到先得，scope 只是可选的一层，因此名字冲突只能靠争议处理流程解决；crates.io 干脆不提供命名空间，包名先到先得；Maven Central 用 `groupId` 做组织边界；PyPI 也没有命名空间，只能靠项目名唯一性。名字的所有权规则直接决定了仿冒包（typosquatting）的空间有多大，这个代价在供应链安全一章会再次出现（见[《包管理器（四）》第 2.1 节](/post/2026/09/24/package-managers-practice/#21-威胁模型依赖链为什么脆弱)）。

#### 3.7.2 索引形态决定能力边界

索引怎么组织，决定了搜索、镜像与离线能做到什么程度。

npm 的索引是「每个包一个元数据文档」，客户端拿到包名就能取版本列表与下载地址。PyPI 的 Simple API 是「每个项目一个页面，列出全部文件链接」，简单到可以用静态文件实现。Cargo 从 Git 索引换成了稀疏 HTTP 索引：客户端不必克隆整个索引仓库，只请求自己需要的那几个前缀路径。Debian 走的是另一条路：`apt update` 把仓库的 `Packages` 索引与签名一起下载到本地，此后查询、依赖计算全部离线完成。Go 的模块代理是一套定义明确的 HTTP 协议，`GOPROXY` 可以列多个地址，前一个返回 404 就试下一个。

理解这个差异，就能解释很多现象：为什么 `apt` 需要 `update`，而 `npm install` 不需要；为什么在 Debian 上离线仍然能 `apt-cache policy`，而在 Node 里离线连版本列表都拿不到。

#### 3.7.3 镜像、代理与离线

镜像（mirror）是完整复制，代理（proxy）是按需缓存。两者的失败模式不同：镜像会滞后，滞后期间查到的版本列表是旧的，锁文件里写着一个镜像上还不存在的版本时，安装直接失败；代理则可能在首次请求时变慢或失败，但它缓存过的制品是确定的。

企业里常见的是 Nexus、Artifactory 这类工具，它们同时扮演三种角色：远程代理、内部包宿主仓库、聚合多个源的虚拟仓库。虚拟仓库的源顺序是有语义的——顺序错了，内部包名可能被公网同名包抢先（见[《包管理器（四）》第 1.5、2.1 节](/post/2026/09/24/package-managers-practice/#15-私有仓库与依赖代理企业环境的必修课)）。

离线安装的手段按生态各不相同：`apt-get download` 拿的是已编译的二进制包，可以直接进离线仓库；`pip download` 与 `npm pack` 拿的是注册表里的分发产物（可能是预编译 wheel，也可能是 sdist 或源码 tarball），离线环境里仍然可能要编译；`cargo vendor`、`go mod vendor` 复制的是源码，离线环境里仍然要能编译。后者看起来更「干净」，但它把编译器和构建依赖也变成了必须在离线环境里解决的问题。

#### 3.7.4 可用性是被低估的风险

中央仓库挂掉，全球 CI 一起红。这不是假设，而是大多做过大规模 CI 的团队都遇到过的事。缓解办法有几层：在企业代理里缓存已有制品，让已发布版本的安装不依赖上游；给 `npm install` 这类命令设好重试与超时；把「必须联网」这一步压到最小——有了锁文件和本地代理，只有首次拉取新版本才需要真正的网络。

> 一句话总结：仓库的索引形态决定了查询与离线的能力上限，而命名空间规则决定了生态要付多少仿冒成本。

### 3.8 安装时执行代码：一切矛盾的根源

#### 3.8.1 谁在安装时执行代码

「安装」这个动作在很多生态里并不只是把文件复制到某个目录。

npm 里，依赖包可以声明 `preinstall`、`install`、`postinstall`，以及发布前的 `prepare`；原生模块还会隐式触发 `node-gyp` 编译。Python 装 sdist 时要走构建后端（PEP 517）：pip 先临时装好 `[build-system] requires` 里的依赖，再调用后端把源码变成 wheel，这一步执行的是上游仓库里的构建代码。Cargo 把 `build.rs` 编译成可执行文件，在构建包之前运行它；它能读环境变量、跑任意命令、把产物写进 `OUT_DIR`。Debian 的 `preinst`、`postinst`、`prerm`、`postrm` 由 dpkg 以 root 执行。Nix 则把构建放进沙箱，限制网络与可写路径，让「构建时执行代码」这件事变成可控输入。

#### 3.8.2 为什么它无法回避

因为它承担了三件正事：编译原生扩展、在安装时下载平台相关的二进制、生成代码（解析器、协议定义、绑定）。这些工作都发生在制品被消费的那一刻，而不是打包的那一刻。

代价也很直白：安装脚本的权限等同于运行安装的那个用户。一个依赖链深达几十层的包，它的 `postinstall` 和自写脚本的权限完全一样：能读凭据文件、能改 shell 配置、能向外发请求。这就是[《包管理器（四）》第 2.1 节](/post/2026/09/24/package-managers-practice/#21-威胁模型依赖链为什么脆弱)那一整套威胁模型的物理基础：投毒不需要攻击构建系统，只要让包管理器去装它。

#### 3.8.3 三种应对及其代价

| 应对 | 做法 | 代价 |
|---|---|---|
| 禁止 | `npm ci --ignore-scripts`、只允许 wheel | 需要编译的包直接装不上 |
| 隔离 | 容器内安装、非 root 用户、Nix/Bazel 沙箱 | 搭建与维护成本，构建产物要重建 |
| 审计 | provenance、attestation、只允许 allowlist | 生态覆盖不全；只证明构建来源（谁、从哪个 commit、什么流程），不代表内容安全 |

三种应对都不是免费午餐。禁止最省事，但把「需要编译」的包全判了死刑，实践中往往只在 CI 或不可信依赖上使用，本地开发又放开，于是策略在最需要它的地方被绕过。隔离最彻底，但要求构建环境也声明化，否则沙箱只是换了个地方执行同样的命令。审计依赖仓库与构建服务的配合，它回答的是「这个制品从哪个 commit、由谁构建」，而不是「这段构建脚本干了什么」（见[《包管理器（四）》第 2.3 节](/post/2026/09/24/package-managers-practice/#23-防御二签名证明与-sbom)）。

近两年最大的变化是默认值在移动。npm 12 起，依赖的生命周期脚本与隐式 `node-gyp` 构建默认不再执行，Git 依赖与远程 URL 依赖默认也不解析，需要显式允许并提交一份 allowlist。这说明「默认拒绝执行」在主流生态里已经可行，剩下的问题是如何处理那批确实需要构建的包。

#### 3.8.4 与可复现构建的冲突

安装脚本与可复现构建天然冲突：脚本可以读网络、读时间、读编译器版本、读环境变量，同样的输入不保证同样的输出。哈希锁定只能保证「同一个文件」，保证不了「同一次构建」。

Bazel 和 Nix 走的路线是把构建动作本身建模成有输入输出的动作，谁执行了、读了什么、产出了什么都要能被记录和缓存，这样才谈得上可复现。代价是必须为构建产物建立缓存和描述，而不是简单地运行一个脚本。

> 一句话总结：安装脚本的安全等级，等于给予仓库和整条上游依赖链的信任等级。

### 3.9 兼容性、语义化版本与现实

#### 3.9.1 SemVer 承诺了什么，又管不到什么

语义化版本（Semantic Versioning）的承诺只有一句：主版本号增加才允许破坏向后兼容。它管不到的东西比管得到的多：类型定义可以变严（同样调用在新版本里编译不过）、运行时行为可以变（边界条件、错误类型、默认值）、性能特征可以变、传递依赖可以变。最后一条最容易被忽略——一个 patch 版本可以只是升级了自己的依赖，然后经由那条路径传进来一个不兼容变更。

多数生态还给 `0.x` 开了后门：Cargo 把 `0.x` 的次版本升级视为可能破坏兼容的变更，Go 明确写着主版本为 0 的模块不受兼容性要求约束。这不是漏洞，是承认「还没定型的东西不能假装有承诺」。

#### 3.9.2 依赖数量是乘法

假设单个依赖在一个月内发生破坏性变更的概率是 p，共有 n 个传递依赖，那么「至少有一个出问题」的概率是 1−(1−p)^n。p 很小时这个数看似可以忽略，但现代应用的 n 常常是几百到上千，于是它迅速逼近某个不能忽略的值。这就是定期升级比一次性大升级更安全的原因：不是升级本身变安全了，而是每次升级引入的未知量变小了。

left-pad 事件是另一种失败：不是兼容性破坏，而是上游撤包。2016 年，一个作者撤下了自己的 273 个包，其中一个被 `babel`、`webpack`、React Native 等通过 `line-numbers` 间接依赖且明确要求了 `0.0.3` 这个版本，全球构建在几十分钟内成批失败。这次事故之后 npm 收紧了撤回策略。它说明可复现性不仅依赖版本号存在，还依赖那个版本的制品仍然存在。

#### 3.9.3 两种策略

宽区间 + 锁文件 + 定期小步升级：日常开发不用频繁重解，CI 用冻结模式保证一致，每周或每两周由升级机器人提 PR，冲突小、可回滚。它的代价是锁文件里的版本会逐渐落后于上游，安全修复需要有人推动。

严格 pin + 定期大升级：版本确定，纪律性强，适合发布节奏固定的产品。代价是升级变成一件大事，攒得越久越难做，最终常常演变为「不升级」。

判断条件很实际：如果项目依赖多、人力少、发布频繁，选前者；如果合规要求版本可追溯、或者依赖很少，后者也成立。

#### 3.9.4 monorepo 与上游弃维护

monorepo 里的内部包通常走本地链接而不是发布，好处是改动即刻反映，坏处是「本地能跑」不再需要发布验证，容易掩盖版本声明错误。一旦要对外发布，就出现了一致性问题：多个包如何同版本发布、依赖内部包时写范围还是写精确版本、发布顺序怎么保证。

上游不再维护时只有四条路，每条都有代价：fork 并自行维护，需要接住后续的安全修复与兼容适配；vendor 进仓库，一劳永逸地冻结，但从此收不到任何上游更新；换成替代实现，迁移成本集中在 API 差异与测试覆盖；接受风险，但要写下来并规定复查时间，否则「暂时先用着」会变成默认状态。

> 一句话总结：SemVer 只承诺 API 兼容，不承诺行为与依赖树兼容；依赖越多，唯一安全的升级方式是步子迈小。
