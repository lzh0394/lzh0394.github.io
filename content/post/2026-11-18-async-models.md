## 0. 结论摘要

1. 异步要解决的核心问题是等待与线程的绑定：阻塞调用让线程在等待期间不可用，连接数上升后，线程数量、栈占用与调度开销一起成为瓶颈。
2. 并发（concurrency）指多个任务在时间上重叠，并行（parallelism）指多个任务同时执行。异步属于并发手段，是否并行由执行资源决定。
3. 线程加阻塞的优点是控制流连续、调试直观、与系统调用语义一致；缺点是每个等待都占一个线程，适合连接数有限或计算密集的场景。
4. 事件循环加回调把等待交给内核的多路复用接口，单线程可以管理大量连接；代价是控制流被拆成回调，生命周期、错误传播与取消需要手工维护。
5. `std::future` 提供结果的汇合点，不提供续接与调度。`get` 与 `wait` 会阻塞调用线程，标准 `future` 也没有取消接口，因此它更适合把已有并发结果收回当前线程。
6. 协程把挂起点固定在函数体内，编译器生成状态机，局部变量保存在协程帧中；顺序写法与异步执行可以同时存在。
7. 协程的代价在帧分配、间接调用、跨挂起点的生命周期管理和调试信息的丢失，不在「切换」本身；无栈协程没有独立栈，不能从普通函数内部挂起。
8. 四种模型的差异最终落在五个横切问题上：组合、取消、生命周期、执行位置和可观测性。选型时先确定这五项，再选语法。
9. 组合需求强、取消需要逐层传播、执行位置需要显式表达时，sender/receiver 模型把这些问题提升到类型层面；代价是学习曲线与编译期开销。
10. 一句话版本：连接数有限或计算密集用线程，海量 I/O 用事件循环或协程，结果汇合用 future，需要类型级组合与调度用 sender。

## 1. 等待从哪里来

### 1.1 三类等待

程序停下来等的东西可以分成三类，异步手段对它们的作用并不相同。

- I/O 等待：网络读写、磁盘读写、管道与设备。等待由外部事件结束，内核提供就绪通知或完成通知。
- 同步等待：互斥量、条件变量、信号量、future。等待由另一个执行体结束，通常发生在共享状态上。
- 计算等待：任务本身占用 CPU，等待的是处理器时间。这类等待靠并行缩短，异步只能改变排队方式。

异步编程主要处理前两类。第三类需要的是更多核心或更高效的算法，把计算任务放进协程不会让它变快。

### 1.2 并发、并行与队列

并发是任务在时间上重叠：一个任务等待时，另一个任务可以运行。并行是任务在同一时刻运行，需要多个执行单元。单核上的事件循环可以并发处理一万个连接，但同时只有一个回调在运行。

衡量系统需要区分三个量：

- 吞吐（throughput）：单位时间完成的任务数。
- 延迟（latency）：单个任务从到达到完成的时间。
- 尾延迟（tail latency）：高分位延迟，通常看 p99 与 p999。

利特尔法则（Little's law）把三者联系起来：系统中的平均任务数等于到达率乘以平均停留时间。每秒 1 万个请求、每个请求平均 50 毫秒，系统里平均有 500 个请求同时存在。若每个请求占一个线程，就需要 500 个线程；若每个线程的栈保留 8 MB 虚拟地址，虚拟地址占用约 4 GB，物理页按实际触碰分配。这个等式解释了为什么连接数上升后线程模型的瓶颈先出现在调度与内存占用上，CPU 通常不是首先耗尽的部分。

### 1.3 异步的目标

异步手段要同时满足两个目标：

1. 等待期间不占用执行线程，让少量线程服务大量任务。
2. 代码仍然能表达「先做 A，再做 B，失败则做 C」的顺序关系。

第一个目标由内核接口与执行器完成，第二个目标由控制流表达完成。四种模型的区别，主要就在第二个目标上。

## 2. 线程与阻塞

### 2.1 一请求一线程

最直接的写法是每个连接一个线程，线程里按顺序调用阻塞函数：

```cpp
void serve(socket s) {
  std::vector<char> buf(4096);
  for (;;) {
    auto n = s.read_some(buf);   // 阻塞，直到有数据或出错
    if (n == 0) break;
    s.write_all(process(buf.data(), n)); // 阻塞，直到写完
  }
}
```

控制流与业务逻辑一致：读、处理、写、循环。异常可以直接向上抛，栈回溯包含完整的调用链，调试器可以在任意一行停下。这些优点来自线程栈保存了全部中间状态。

### 2.2 成本构成

线程的成本不在创建那一刻，而在它存在期间占用的资源，以及切换时付出的代价。

| 项目 | 结构 | 随连接数增长的部分 |
| --- | --- | --- |
| 栈 | 每线程一段虚拟地址，物理页按需提交 | 虚拟地址与页表项 |
| 内核对象 | 调度实体、文件描述符、信号掩码 | 内核内存与调度队列长度 |
| 上下文切换 | 保存与恢复寄存器、切换地址空间 | 切换次数与缓存失效 |
| 同步 | 锁、条件变量、原子操作 | 竞争概率与等待时间 |
| 生命周期 | 创建、回收、异常退出 | 管理复杂度 |

栈的虚拟地址保留不等于物理内存占用。把栈上限调小可以缓解地址空间压力，线程仍然要参与调度：可运行线程数超过核心数后，调度器按时间片轮转，每个线程的缓存工作集被反复换出。连接空闲时线程仍在等待队列中，连接活跃时线程可能在锁上排队。

### 2.3 阻塞与唤醒

阻塞式 `read` 在数据未就绪时把线程状态改为可中断睡眠，把控制权交回调度器；数据到达后，内核唤醒线程，系统调用返回。一次等待涉及两次调度决策与一次上下文切换。请求密集时，这些切换与真实工作争夺 CPU。

线程池把线程创建与销毁的成本摊薄，等待仍然存在：池中线程全部阻塞时，新任务排队；池扩大后，上下文切换与内存占用随之上升。线程池解决的是复用，不解决「等待占着执行单元」这一结构问题。

### 2.4 线程仍然适用之处

- 连接数有限，例如内部服务之间几十到几百条长连接。
- 任务是计算密集的，线程本来就要占满核心。
- 依赖的库只有阻塞接口，改造成本高于收益。
- 需要与现有同步代码、调试工具、性能分析工具直接配合。

线程模型的问题在规模，不在语义。把线程数控制在核心数附近，阻塞调用是合理的工程选择。

## 3. 事件循环与回调

### 3.1 Reactor 的部件

Reactor 模式把「等待哪些文件描述符」交给内核的多路复用接口，事件到达后分发给对应的处理器。典型部件有四个：

- 事件多路分离器：`epoll_wait`、`kqueue`、`select` 一类调用，返回就绪的文件描述符。
- 事件循环：反复执行「等待事件、取出事件、调用处理器」。
- 处理器：每个连接或每类事件对应一个回调。
- 定时器与唤醒机制：处理超时，并让其他线程能把任务投递进循环。

文件描述符设为非阻塞后，读写要么立即完成，要么返回 `EAGAIN`。事件循环只在就绪时调用回调，回调内部不再等待。

### 3.2 回调把控制流拆成状态机

顺序流程被拆成多个回调后，中间状态必须显式保存：

```cpp
void session::start() {
  socket_.async_read_some(buffer_,
    [self = shared_from_this()](error_code ec, size_t n) {
      if (ec) return self->close(ec);
      self->handle(buffer_.data(), n);
      self->start();                 // 继续下一次读
    });
}
```

「读、处理、再读」还能用一个递归回调表达。加入超时、重试、并发请求合并后，状态机的分支迅速增长。每个异步步骤都要定义：成功走哪里、失败走哪里、取消走哪里、对象已销毁时怎么办。

### 3.3 控制反转的代价

回调模型把控制权交给事件循环，调用方不再拥有连续栈帧。由此产生四类问题：

1. 生命周期：操作可能在对象销毁后完成，回调捕获裸指针会访问已释放内存。常用 `shared_from_this`、弱引用或独立的生命周期令牌。
2. 错误传播：错误码要沿回调链手工传递，任何一层遗漏都会把失败变成静默的成功。
3. 取消：没有统一接口，库通常提供自己的句柄、信号槽或状态标志。
4. 调试：调用栈只显示事件循环到回调的那一段，业务链路的前半段已经返回，栈回溯无法还原完整路径。

这些问题与回调语法本身无关，根源是控制流被切开后，编译器不再能自动维护跨步骤的状态。

### 3.4 事件循环的纪律

事件循环的吞吐取决于回调是否短。回调里做阻塞调用、长时间计算或同步等待，整个循环停摆。工程上通常约定：

- 回调只做状态推进与短处理，重活交给工作线程池。
- 每个连接或会话绑定到固定循环，避免跨线程访问状态。
- 跨线程投递任务时使用循环提供的队列与唤醒机制。
- 定时器按截止时间组织，避免每次轮询全部定时器。

这些约定无法由类型系统强制，违反后通常不会产生编译错误，表现为尾延迟上升。

## 4. future 与 promise

### 4.1 共享状态

`std::promise` 与 `std::future` 通过一块共享状态传递结果。生产者调用 `set_value` 或 `set_exception`，消费者调用 `get` 等待并取走结果。共享状态由双方共同引用，生产者先销毁而消费者仍在等待时，`get` 抛出 `std::future_error`，错误码为 `std::future_errc::broken_promise`。

`future` 只能移动，表示单消费者；`shared_future` 可以复制，支持多消费者。`future::get` 只能调用一次，再次调用是未定义行为；`shared_future::get` 可以重复调用。

### 4.2 阻塞边界

`future` 把异步结果转成同步接口：`get` 与 `wait` 阻塞调用线程。标准没有提供续接（continuation），也没有提供取消。多个 future 的组合需要调用方轮询、阻塞等待，或使用库扩展。

因此 `future` 适合作为并发计算的汇合点：主线程把任务分发出去，最后在少数几个点上等待结果。把它当作事件驱动服务的核心抽象，会把等待重新压回线程。

### 4.3 std::async 的陷阱

`std::async` 的启动策略由实现决定：可能在新线程执行，也可能延迟到 `get` 或 `wait` 时才执行。由 `std::async` 创建且未取得结果的 future，在析构时可能等待任务完成，作用域结束时产生隐式阻塞。

```cpp
{
  auto f = std::async(std::launch::async, [] { return work(); });
  // 忘记 f.get()
} // 这里可能阻塞到 work() 完成
```

需要明确执行位置时，显式指定 `std::launch::async`，并确保结果被取走或 future 被移动出去。

### 4.4 适用面

- 把已有线程池或并行算法的结果收回当前线程。
- 一次性任务的结果汇合，调用方愿意阻塞。
- 与旧接口对接，`future` 是现有的公共类型。

需要续接、取消、执行位置或大规模并发时，`future` 的能力不够，通常要换模型或引入库。

## 5. 协程

### 5.1 无栈协程的挂起与恢复

C++20 协程是无栈协程（stackless coroutine）。编译器把协程体改写成状态机，局部变量、参数副本、挂起点与 promise 对象放在一块堆上的协程帧中。挂起时保存当前状态并返回调用者，恢复时从挂起点继续。

```cpp
task<void> session::run() {
  for (;;) {
    auto n = co_await socket_.async_read_some(buffer_, use_awaitable);
    if (n == 0) break;
    co_await process(buffer_, n);
  }
}
```

这段代码的语法与阻塞版本接近，执行却是异步的：`co_await` 在操作未完成时挂起协程，把线程还给事件循环；操作完成后，执行器恢复协程，从下一行继续。

### 5.2 顺序表达

协程的价值在于把「跨步骤的状态」交给编译器保存。局部变量、循环计数器、异常处理范围都留在帧里，业务代码不需要显式定义状态机。与回调相比，错误可以用 `try`/`catch` 表达，清理可以用析构函数表达。

挂起只发生在协程体内。普通函数调用协程时，协程帧独立于调用者栈；协程挂起后，调用者的栈可以正常返回。这个性质让协程能接入事件循环，而不需要为每个任务保留线程栈。

### 5.3 代价

- 帧分配：默认通过 `operator new` 分配，大小在编译期确定；编译器可以做分配省略，标准不保证。
- 间接调用：恢复通过函数指针或句柄进行，优化器难以跨挂起点做内联优化。
- 生命周期：帧的销毁时机由 promise 与句柄所有者决定，传错所有权会造成泄漏或重复销毁。
- 调试：挂起后栈回溯断开，调试器看到的是执行器到恢复点的调用链，业务链路需要额外记录。
- 线程迁移：协程可能在不同线程恢复，帧内数据在没有同步的情况下跨线程访问是数据竞争。

这些代价与「协程切换比线程切换快」不是同一层面的问题。无栈协程没有内核切换，但仍有函数调用、内存分配与缓存访问。

### 5.4 有栈协程

有栈协程（stackful coroutine）为每个协程保留独立栈，可以在任意函数调用深度挂起。Go 的 goroutine、Boost.Context 的 fiber、部分用户态线程库属于这一类。优点是挂起位置不受语法限制，缺点是要为每个协程预留栈空间，切换涉及栈指针与寄存器保存，栈大小与溢出处理需要额外机制。

C++20 协程选择了无栈形式，挂起点由 `co_await` 标出，编译器能在编译期确定帧布局。这个选择换来了更小的单任务开销，也限制了挂起只能发生在协程体内。

## 6. 横切问题

### 6.1 组合

组合指把多个异步操作拼成一个：串行、并行、任一完成、超时、重试。四种模型的组合方式不同：

- 线程：用阻塞调用与同步原语组合，组合结果就是普通代码，但每个并发分支占线程。
- 回调：用组合函数或手写状态机组合，组合层要转发错误、取消与执行位置。
- future：缺少标准续接，组合通常退化为阻塞等待或库扩展。
- 协程：用 `co_await` 顺序组合，用任务类型与组合算法表达并行；组合逻辑接近同步代码。
- sender：用算法组合，完成签名在类型层面合并，错误与停止沿通道传播。

组合越深，中间状态与分配越多。接口需要允许定制分配器与执行器，否则组合层会成为新的瓶颈。

### 6.2 取消

取消是协作式的：请求方设置标志或发出信号，执行方在安全点检查并退出。没有语言级强制中断，因为强制终止可能留下未释放的资源与不一致的状态。

四种模型的取消能力：

- 线程：依赖系统调用超时、信号或关闭句柄，取消粒度由平台决定。
- 回调：由库定义句柄或状态标志，取消后要保证完成回调不再访问已销毁的对象。
- future：标准不提供取消；`std::stop_token` 需要任务主动轮询。
- 协程：取消状态放在 promise 或执行上下文中，在挂起点与恢复后检查；`std::stop_token` 可以沿调用链传递。
- sender：取消通过停止通道表达，完成时调用 `set_stopped`，组合算法负责向子操作传播。

取消与销毁的顺序必须明确：先停止新操作，再取消在途操作，最后释放缓冲区与对象。顺序错误会产生「完成回调在对象析构后到达」这一类问题。

### 6.3 生命周期

异步操作的生命周期通常长于发起它的函数。需要回答三个问题：

1. 谁拥有操作状态：调用方、库、还是执行器。
2. 谁拥有缓冲区：操作完成前缓冲区不能失效。
3. 谁拥有续接对象：协程帧、回调闭包、还是 shared_ptr。

C++20 协程把帧的生命周期交给返回对象与 promise 的设计者。任务对象析构时销毁帧，或把帧交给续接者；销毁正在运行或已挂起的帧语义不同，恢复已销毁的句柄是未定义行为。

### 6.4 结构化并发

结构化并发要求父任务等待所有子任务结束后才结束，子任务的失败与取消沿父子关系传播。它把并发生命周期绑定到词法作用域，避免任务泄漏与悬垂引用。

四种模型对结构化并发的支持程度不同：

- 线程：需要手工 join，异常退出时容易漏掉。
- 回调：需要引用计数或作用域对象追踪在途操作。
- 协程：任务类型可以在析构时取消并等待子任务，作用域对象可以表达 nursery。
- sender：`when_all` 一类算法在完成前等待所有子操作，停止请求自动传播。

### 6.5 调试与观测

同步代码的栈回溯包含完整调用链。异步代码的栈只包含当前执行片段，业务链路要靠上下文对象、trace id 或协程帧中的记录串起来。

工程上通常需要：

- 给每个请求分配唯一标识，在日志中传递。
- 记录异步操作的发起点与完成点，计算排队时间与执行时间。
- 统计帧分配次数、事件循环延迟、就绪队列长度。
- 在协程帧或任务对象中保存创建时的回溯，用于诊断泄漏。

## 7. 选型

### 7.1 对比

| 模型 | 控制流 | 等待时占用 | 取消 | 组合 |
| --- | --- | --- | --- | --- |
| 线程加阻塞 | 连续 | 一个线程 | 平台相关 | 同步原语 |
| 事件循环加回调 | 拆成回调 | 无 | 库定义 | 手工状态机 |
| future | 分段阻塞 | 等待线程 | 无标准接口 | 阻塞汇合 |
| 协程 | 连续 | 协程帧 | 协作式 | 顺序加任务算法 |
| sender | 声明式 | 操作状态 | 停止通道 | 类型级算法 |

### 7.2 决策顺序

1. 先看等待类型。计算密集用线程或并行算法；I/O 密集进入下一步。
2. 再看连接规模。几十到几百，线程加阻塞足够；上万连接，事件循环或协程。
3. 再看组合需求。流程短、分支少，回调可以接受；流程长、错误路径多，协程更合适。
4. 再看取消与超时。需要在多层之间传播，选带停止令牌或取消槽的库。
5. 最后看团队与生态。已有 Asio 时优先用它的协程接口；需要标准演进路径时关注 `std::execution`。

异步模型没有全局最优解。把等待从线程上解绑的代价，会转移到生命周期、取消与调试上；选型是在这些代价之间分配。
