## 1. 异步编程模型

### 1.1 阻塞调用为什么不能直接扩展为高并发服务？

- 阻塞调用把等待时间绑定到线程，线程在系统调用返回前不能执行其他任务。
- 每个连接一个线程时，线程栈、内核调度实体与上下文切换都随连接数增长；栈的虚拟地址占用通常远大于实际使用量。
- 连接空闲时线程仍占用调度资源，连接数超过线程数后新请求排队，尾延迟上升。
- 阻塞调用难以在同一线程内表达超时、取消与并发组合，通常需要额外线程或信号机制。
- 线程创建与销毁进入内核，频繁短连接会把这部分代价放大。
- 该模型适合连接数有限、逻辑简单的场景；连接数大且等待占比高时，事件驱动或协程更合适。

### 1.2 回调模型如何把异步操作接续下去？

- 发起函数注册完成处理器后立即返回，实际操作由执行上下文推进。
- 完成时执行上下文调用处理器，参数携带错误码与传输字节数等结果。
- 多步流程由处理器继续发起下一步操作，形成显式的状态机或续接链。
- 处理器通常绑定执行器，决定回调在哪个线程运行。
- 控制流从调用方转移到库，调用方不再持有连续栈帧。
- 组合操作把多个底层回调封装为一个完成处理器，减少手写状态机。

### 1.3（辨析）回调模型的控制反转带来哪些生命周期问题？

- 发起异步操作后，操作可能在上游对象销毁之后完成，处理器若捕获裸指针就会访问已释放内存。
- 处理器捕获 `this` 时，对象必须保证活到完成回调；常用 `shared_from_this` 或独立生命周期令牌。
- 取消与销毁的顺序必须明确：先停止新操作，再取消在途操作，最后释放缓冲区与对象。
- 处理器可能重入或递归调用，栈深度与锁的持有范围需要重新检查。
- 循环引用会让对象无法释放，`shared_ptr` 捕获需要配合 `weak_ptr` 或显式断开。
- 组合操作的中间处理器也持有状态，任一环节遗漏清理都会造成泄漏。

### 1.4 `std::future` 与 `std::promise` 如何分离结果生产与消费？

- `std::promise` 持有共享状态，`set_value` 或 `set_exception` 写入结果。
- `std::future` 通过 `get` 等待并取走结果，`wait` 只等待就绪。
- 共享状态由双方共同引用，生产者先销毁而消费者仍等待时，`get` 抛出 `std::future_error`，错误码为 `std::future_errc::broken_promise`。
- `future` 不可复制，只能移动，表示单消费者；`shared_future` 可复制并支持多消费者。
- `future::get` 只能调用一次，再次调用是未定义行为；`shared_future::get` 可以重复调用。
- 生产者与消费者的线程关系由调用方安排，`future` 本身不提供调度。

### 1.5 为什么 `std::future` 的阻塞等待不等同于异步？

- `get` 与 `wait` 阻塞调用线程，等待期间该线程不能执行其他任务。
- `std::async` 的启动策略由实现决定，可能延迟执行，也可能在新线程执行。
- 标准 `future` 没有续接接口，无法直接表达完成后执行下一步。
- 多个 `future` 的组合需要调用方轮询或阻塞等待，缺少统一的取消与调度语义。
- `future` 的析构在由 `std::async` 创建时可能等待任务完成，容易在作用域末尾产生隐式阻塞。
- 它适合把已有并发结果汇合到当前线程，不适合作为事件驱动服务的核心模型。

```cpp
std::promise<int> p;
std::future<int> f = p.get_future();
std::thread t([&] { p.set_value(42); });
int v = f.get();
t.join();
```

### 1.6 协程如何把回调式异步操作写成顺序代码？

- 协程帧保存局部变量、挂起点与续接状态，`co_await` 在等待时挂起当前协程。
- 编译器把 `co_await` 表达式转换为 awaiter 的 `await_ready`、`await_suspend`、`await_resume` 调用。
- 异步操作完成后恢复协程句柄，控制流从挂起点继续，局部变量仍在帧内。
- `await_suspend` 可以把句柄交给执行器或另一个协程，对称转移可避免恢复链增长调用栈。
- 协程的 `promise_type` 决定初始挂起、最终挂起、返回值与异常处理。
- 顺序写法只改变控制流的表达，挂起与恢复仍由底层异步操作驱动。

### 1.7 协程帧的生命周期由谁负责？

- 帧在协程调用时由编译器生成的分配逻辑创建，大小在编译期确定；是否立即挂起由 `initial_suspend` 决定。
- 帧的销毁由 `coroutine_handle::destroy` 或最终挂起策略触发；`final_suspend` 返回 `suspend_never` 时可由运行时自动销毁。
- 恢复一个已销毁的协程是未定义行为，异步操作完成前必须保证句柄有效。
- 协程的所有者可以是 `shared_ptr`、任务对象或事件循环；所有权规则需要在接口中写明。
- 取消时要先停止底层操作，再销毁帧，避免完成回调恢复已释放的帧。
- 自定义分配器可以降低帧分配开销，但分配与释放必须配对。

### 1.8 `sender` 与 `receiver` 和 `future` 的核心差异是什么？

- `sender` 描述一段尚未开始的异步工作，`connect` 把它与 `receiver` 连接成操作状态，`start` 才启动。
- 完成通过 `set_value`、`set_error`、`set_stopped` 三个通道报告，接收器必须处理其一。
- 完成签名在类型层面描述可能的值、错误与停止，组合算法可据此检查。
- `sender` 不要求共享状态，结果可以直接沿调用链传递，减少堆分配与共享状态同步。
- 调度通过 `scheduler` 表达，工作在哪执行是类型的一部分。
- `future` 侧重结果汇合，`sender` 侧重可组合的异步流程与执行位置。

### 1.9（辨析）`sender` 的惰性与立即执行如何区分？

- 构造 `sender` 只生成描述，不启动 I/O，也不分配操作状态。
- `connect` 生成操作状态，仍不执行；`start` 才把工作提交给调度器或直接运行。
- `start` 允许在调用线程同步完成，这不等于构造时立即执行。
- `then` 等适配器只在 `start` 后调用函数，函数可能在完成线程就地执行。
- `std::this_thread::sync_wait` 会阻塞当前线程并驱动操作，直到收到完成信号。
- 惰性使组合、复用与取消可以在启动前完成，代价是操作状态的生命周期需要显式管理。

### 1.10 完成签名如何表达成功、错误与停止？

- `set_value(...)` 表示成功，参数类型构成值完成签名。
- `set_error(...)` 表示失败，参数通常是异常指针或错误类型。
- `set_stopped()` 表示因停止请求而结束，不携带错误，也不等同于成功。
- 一个 `sender` 可以有多组完成签名，接收器必须对每组都可调用。
- 停止是正常控制流，不应被当作异常重试或记录为故障。
- 组合算法需要合并各输入的签名，错误与停止的传播规则由算法定义。

### 1.11 异步模型的取消能力如何比较？

- 阻塞调用依赖系统调用超时、信号或关闭句柄，取消粒度由平台决定。
- 回调模型没有统一取消接口，通常由库自定义句柄或状态标志。
- 标准 `future` 不提供取消；`std::stop_token` 需要任务主动轮询或等待。
- 协程可以把取消状态放入 `promise_type`，在挂起点或恢复后检查。
- Asio 用 `cancellation_slot` 表达逐操作取消，取消请求是协作式的。
- P2300 用停止通道表达取消，完成时调用 `set_stopped`，组合算法负责向子操作传播。

### 1.12 执行器在异步模型中承担什么职责？

- 执行器决定任务在哪个执行上下文、以何种方式运行。
- 它提供提交接口，区分就地执行与排队执行，影响顺序与栈深度。
- 执行器可以携带亲和性、优先级、分配器等属性，具体能力由实现定义。
- 关联执行器把完成处理器送回正确的线程或串行域。
- 执行器不是线程，也不保证并行；串行执行器仍可在多个线程间迁移。
- 调度器描述执行资源，部分 `sender` 还能报告完成调度器。

### 1.13 异步操作的组合性如何影响库设计？

- 回调库用组合函数封装状态机，组合层需要转发取消、分配器与执行器。
- `future` 缺少标准续接，组合通常退化为阻塞等待或库扩展。
- 协程把组合写成顺序代码，但需要 awaiter 与帧生命周期支持。
- `sender` 把组合做成算法，完成签名在编译期参与检查。
- 组合层必须定义错误短路、停止传播与部分完成的处理。
- 组合越深，中间状态与分配越多，接口需要允许定制分配与调度。

### 1.14 回调、`future`、协程与 `sender` 的性能代价分别在哪里？

- 回调通常需要一次堆分配保存完成状态，类型擦除会再增加间接调用。
- `future` 需要共享状态与同步，跨线程唤醒有原子操作与系统调用开销。
- 协程帧一次分配，挂起与恢复保存寄存器与局部状态；对称转移可减少栈增长。
- `sender` 的操作状态通常一次分配，组合算法可被编译器展开，避免虚调用与共享状态。
- 上下文切换、缓存局部性与批处理往往比抽象本身的微小开销更重要。
- 具体数值由实现、编译器优化与负载决定，不能脱离测量比较。

### 1.15 无栈协程与有栈协程的差异是什么？

- 无栈协程把局部状态保存在帧中，只能在语言规定的挂起点挂起。
- 有栈协程拥有独立栈，可以在调用链深处挂起，切换时保存栈指针与寄存器。
- 无栈协程的帧大小在编译期确定，内存占用较小，但跨层挂起需要逐层支持。
- 有栈协程的栈通常较大，创建成本高，但能与阻塞式代码互操作。
- C++20 协程是无栈协程；有栈协程通常由库或平台设施提供。
- 选择取决于挂起深度、内存预算与现有代码的改造范围。

### 1.16 异步代码的调用栈为什么难以回溯？

- 完成处理器由事件循环恢复，逻辑上的调用链分散在多个栈帧中。
- 调试器看到的是当前恢复点，而不是发起异步操作的原始调用链。
- 优化与尾调用会进一步合并帧，发布构建下定位更困难。
- 处理器跟踪、异步栈 instrumentation 与日志中的请求标识可以补足上下文。
- 协程帧包含挂起点信息，但需要调试信息与工具支持才能展开。
- 设计阶段保留操作标识与阶段字段，比事后从栈回溯更可靠。

### 1.17 结构化并发在异步代码中如何体现？

- 父操作在返回前等待所有子操作结束，子操作不逃逸作用域。
- 子操作失败或停止时，父操作负责请求其余子操作停止并汇总结果。
- `when_all` 提供启动全部、等待全部的组合，失败时向其余输入请求停止。
- 作用域对象需要管理操作状态、取消源与完成计数，避免子操作比父对象活得久。
- 回调与 `future` 默认不提供结构化并发，需要库或应用层约束。
- 结构化并发改善生命周期与错误传播，代价是父操作必须等待最慢的子操作。

### 1.18（陷阱）`when_any` 在 P2300R10 中是否存在？

- `when_any` 存在于部分实验实现与扩展库中，用于等待首个完成并停止其余操作。
- P2300R10 的设施列表中没有 `when_any`，C++26 的 `std::execution` 保留的是 `when_all` 等算法。
- `transfer` 是早期修订中的名称，P2300R10 对应设施为 `continues_on`；旧名不能当作 C++26 接口。
- 标准库实现可能以扩展形式提供类似设施，名称与语义由实现决定。
- 需要首个完成语义时，可在应用层用停止令牌与共享状态组合，或使用库扩展。
- 不能把实验实现的 `when_any` 写成 C++26 已定标准。

### 1.19 异步接口的异常安全如何保证？

- 发起函数可能因分配失败或参数错误抛出异常，此时不应留下半注册的操作。
- 异步完成阶段的运行期错误通常走错误通道，不跨线程抛出。
- 完成处理器抛出的异常由调用 `run` 的线程处理，可能导致事件循环退出。
- 操作状态与缓冲区用 RAII 管理，取消与失败路径都要释放。
- 析构函数不应抛出异常；清理失败应记录并终止，而不是让异常逃逸。
- 组合算法要保证接收器只被完成一次，异常路径也不能重复完成。

### 1.20 选型时应如何权衡异步模型？

- 连接数与等待占比决定是否需要事件驱动；CPU 密集型任务另有调度需求。
- 组合深度、取消传播与错误处理决定抽象的成本。
- 协程改善可读性，但需要编译器、库与调试工具支持。
- `sender` 提供类型安全的组合与调度，但学习成本与编译期开销较高。
- Asio 生态成熟，适合网络与定时器；P2300R10 已进入 C++26，标准库实现仍在推进。
- 选型应基于团队经验、现有依赖、可观测性与性能目标，不能只看基准数字。

## 2. Asio 基础

### 2.1 `io_context` 的本质是什么？

- 它是 Asio 的执行上下文，持有任务队列、定时器与 I/O 完成事件的状态。
- `run` 系列函数驱动事件循环：等待就绪事件、取出处理器并调用。
- 它本身不是线程；同一上下文可由一个或多个线程驱动。
- I/O 对象在构造时绑定执行器，操作完成后的处理器回到该上下文。
- 处理器只会在调用 `run`、`run_one`、`poll` 等函数的线程中执行。
- 上下文还管理服务对象、内部状态与工作计数。

### 2.2 `run()` 与 `poll()` 的区别是什么？

- `run()` 阻塞直到没有未完成工作、上下文停止或处理器抛出异常。
- `poll()` 不阻塞，只执行当前已就绪的处理器，然后返回。
- `run_one()` 最多执行一个处理器并返回执行数量；`poll_one()` 非阻塞地尝试一个。
- 两者都只在调用线程内执行处理器，都不创建线程。
- `run()` 适合事件循环线程；`poll()` 适合把 Asio 嵌入外部循环。
- 处理器抛出的异常会从对应调用中传播出去。

### 2.3 `io_context` 停止后如何重新使用？

- `stop()` 让 `run()` 尽快返回，未执行的处理器留在队列中，不保证被调度。
- 停止状态下再次调用 `run()` 会立即返回，必须先调用 `restart()`。
- `restart()` 不能在 `run()` 或 `poll()` 尚未返回时调用，否则行为未定义。
- 重启后队列中的旧处理器可能继续执行，业务状态需要能处理这种恢复。
- 如果目标是正常退出，优先重置工作守卫，让已排队工作完成。
- 销毁上下文会销毁未执行的处理器，处理器捕获的资源随之释放。

### 2.4 Asio 的 `executor` 是什么？

- 执行器是提交函数的句柄，绑定到某个执行上下文。
- 它提供 `execute`、`post`、`dispatch`、`defer` 等提交方式，语义不同。
- `io_context::executor_type` 是具体类型；`any_io_executor` 是类型擦除包装。
- I/O 对象的 `get_executor()` 返回其关联执行器，完成处理器默认回到该执行器。
- 执行器可以适配成 `strand`，在不改变底层上下文的情况下增加串行保证。
- 执行器不是线程，也不保证任务立即运行或并行运行。

### 2.5 `post` 与 `dispatch` 的差异是什么？

- `post` 保证不在当前调用栈内执行处理器，总是排队到目标执行器。
- `dispatch` 在目标执行器允许时就地执行，否则排队。
- 在同一个 `io_context` 的 `run` 线程中调用 `dispatch`，处理器可能立即运行。
- 就地执行会改变调用栈深度与顺序，递归提交时可能造成栈增长。
- 需要确定性的延后与公平性时使用 `post`；需要减少一次排队开销时使用 `dispatch`。
- 两者都受关联执行器影响，显式传入执行器可覆盖默认绑定。

### 2.6 `defer` 与 `post` 有什么区别？

- 两者都保证处理器不在当前函数返回前执行。
- `defer` 表达这是当前调用上下文的延续，允许执行器推迟入队并优化。
- `post` 表达尽快入队，更倾向于立即把任务放入队列。
- `defer` 不保证在 `post` 之前或之后执行，顺序仍由执行器与提交时序决定。
- 在 `strand` 上使用时，两者都不就地执行，但排队策略可能不同。
- 选择取决于是否需要让执行器识别续接关系，不能把 `defer` 当作同步调用。

```cpp
asio::post(ctx, [] { /* queued */ });
asio::defer(ctx, [] { /* continuation */ });
```

### 2.7 `work_guard` 解决什么问题？

- `io_context` 在没有未完成工作时会让 `run()` 返回，工作守卫增加一个未完成计数。
- 守卫存在期间，即使当前没有异步操作，`run()` 也保持阻塞等待新工作。
- `reset()` 释放计数，允许 `run()` 在没有其他工作时退出。
- 守卫通常放在事件循环对象的成员中，析构时自动释放。
- `stop()` 放弃排队工作并让 `run()` 返回；`reset()` 不取消工作，让 `run()` 在队列清空后退出。
- 忘记重置守卫会让程序在关闭阶段无法退出。

### 2.8 为什么 `io_context::run()` 会立即返回？

- 没有任何未完成异步操作，也没有工作守卫时，上下文认为无事可做。
- 所有处理器已经执行完，队列为空，`run()` 正常返回。
- 之前调用过 `stop()` 且没有 `restart()`，`run()` 直接返回。
- 启动阶段先 `run()` 再发起操作会产生竞态，通常先提交操作或先持有守卫。
- 处理器抛出异常也会让当前 `run()` 提前返回。
- 排查时检查工作计数、停止状态与操作是否真正发起。

### 2.9 `handler` 的分配器如何工作？

- Asio 通过关联分配器 trait 获取处理器要使用的分配器。
- 异步操作可能为操作状态、定时器节点或组合操作中间状态分配内存。
- `get_associated_allocator(handler, fallback)` 优先使用处理器自带的分配器。
- `bind_allocator` 可以把分配器绑定到处理器，`associated_allocator` 可以特化。
- 分配器必须满足 Allocator 要求，并在处理器释放前保持有效。
- 自定义池分配器可以减少通用堆分配，但会增加生命周期与线程安全约束。

```cpp
std::allocator<std::byte> alloc;
asio::post(ctx, asio::bind_allocator(alloc, [] { /* work */ }));
```

### 2.10 如何为 `handler` 绑定分配器与执行器？

- `bind_executor` 绑定关联执行器，决定完成处理器在哪运行。
- `bind_allocator` 绑定关联分配器，影响操作内部存储的分配。
- 两个适配器可以嵌套，关联 trait 会逐层传播。
- 组合操作会沿用完成处理器的关联执行器与分配器处理中间步骤。
- 绑定顺序通常不影响结果，但类型与可读性会受影响。
- 绑定后的处理器必须满足原操作的完成签名。

### 2.11 `handler` 的关联执行器如何确定？

- `get_associated_executor(handler, fallback)` 先查处理器嵌套的 `executor_type` 或 `get_executor()`。
- 没有关联执行器时使用回退执行器；异步操作通常以 I/O 对象的执行器作为回退。
- `bind_executor` 可以显式覆盖关联执行器。
- 组合操作的所有中间处理器都应使用同一个关联执行器，避免跨线程访问共享状态。
- 关联执行器只决定提交位置，不保证串行；需要串行时绑定 `strand`。
- 自定义处理器可以特化 `associated_executor`，但必须满足执行器要求。

### 2.12 `io_context` 的线程安全边界在哪里？

- 不同 `io_context` 对象可以并发使用。
- 同一 `io_context` 的 `run`、`post`、`stop` 等成员函数通常可并发调用，`restart()` 与 `notify_fork()` 例外。
- I/O 对象本身通常不是线程安全的，共享对象需要外部同步或 `strand`。
- 处理器可能在不同线程并发执行，共享业务状态需要保护。
- 在 `run` 线程之外直接调用 I/O 对象成员，可能与完成处理器竞争。
- 线程安全规则应按对象与操作分别核对，不能只看上下文。

### 2.13 一个 `io_context` 配多个线程时 `handler` 在哪执行？

- 任一正在调用 `run` 的线程都可能执行处理器。
- 同一个处理器不会同时执行两次，但不同处理器可以并发。
- 处理器的关联执行器决定提交到哪个上下文，不决定具体线程。
- `strand` 可以把一组处理器限制为不并发，并在线程间迁移。
- 线程局部变量在处理器之间不保持，处理器可能每次落在不同线程。
- 需要固定线程时使用专用上下文或显式亲和性，不能依赖调度巧合。

### 2.14 独立 Asio 与 Boost.Asio 有哪些接口差异？

- 独立 Asio 使用 `asio` 命名空间，Boost.Asio 使用 `boost::asio`。
- 独立 Asio 默认使用 `std::error_code`，Boost.Asio 使用 `boost::system::error_code`。
- 头文件路径分别为 `asio/...` 与 `boost/asio/...`，宏前缀也不同。
- 新设施通常先在独立 Asio 出现，再进入 Boost 发行版，是否可用由版本决定。
- 取消槽等设施需要检查 `ASIO_VERSION` 或 Boost 版本，不能假定所有版本都有。
- 迁移代码时优先统一错误类型与命名空间别名，避免混用两套类型。

### 2.15 `io_context::executor_type` 与 `any_io_executor` 有什么区别？

- `io_context::executor_type` 是具体执行器类型，编译期已知，调用可被编译器展开。
- `any_io_executor` 是类型擦除执行器，可以容纳 `io_context` 执行器、`strand` 等。
- 类型擦除带来间接调用与可能的堆分配，代价由实现决定。
- 较新版本的 I/O 对象默认使用 `any_io_executor`，旧版本可能使用具体类型。
- 默认类型由版本与配置宏决定，迁移代码时应检查 `executor_type` 的实际定义。
- 需要模板泛化或运行时切换执行器时使用 `any_io_executor`；性能敏感路径可用具体类型。

### 2.16 `handler` 抛出异常时 `run()` 如何反应？

- 异常从处理器传播到调用 `run()` 的线程，当前 `run()` 调用退出。
- 其他正在运行 `run()` 的线程不受影响，继续处理各自的任务。
- 捕获异常后可以再次调用 `run()`，不需要先 `restart()`。
- 处理器应自行捕获业务异常，避免事件循环因单个请求退出。
- 若处理器被标记为 `noexcept` 而抛出，程序调用 `std::terminate`。
- 异常路径同样要释放操作状态与缓冲区，避免泄漏。

### 2.17 如何观察 `io_context` 的队列积压？

- Asio 没有稳定的公开接口直接读取待执行处理器数量。
- 可以在提交与执行时记录计数与时间戳，计算排队延迟。
- 定时器的实际触发时间与设定时间之差可以反映事件循环延迟。
- 处理器跟踪与日志可以定位长耗时处理器，但会改变运行时开销。
- 监控 `run` 线程的 CPU 使用率与唤醒频率，区分空转与过载。
- 需要精确指标时使用应用层埋点，不能依赖内部实现细节。

### 2.18 什么时候需要多个 `io_context`？

- 需要隔离延迟敏感流量与后台批处理时，分开上下文可减少队头阻塞。
- 每个线程一个上下文可以减少队列竞争，但增加跨上下文通信。
- 不同上下文可以绑定不同线程数与亲和性，便于资源控制。
- I/O 对象与构造时的执行器绑定，跨上下文迁移通常需要重建对象。
- 跨上下文提交用 `asio::post(target, handler)`，不要直接调用目标对象的成员。
- 多上下文增加关闭、负载均衡与调试复杂度，连接数不大时未必值得。

### 2.19（代码阅读）这段 `post` 与 `run` 的顺序说明了什么？

```cpp
asio::io_context ctx;
asio::post(ctx, [] { /* A */ });
asio::post(ctx, [] { /* B */ });
ctx.run();
```

- 两个处理器都在 `run()` 之前提交，但都不会在 `post` 调用内执行。
- `run()` 在当前线程驱动队列，A 与 B 最终由该线程执行。
- 两次 `post` 的先后不构成跨线程同步，也不保证与业务事件顺序一致。
- 若 `run()` 先返回，后续 `post` 需要再次调用 `run()` 或由工作守卫保持循环。
- 需要严格串行与顺序时，把处理器绑定到同一 `strand` 并明确提交点。
- 这段代码没有工作守卫，队列清空后 `run()` 会返回。

### 2.20 如何组织一个最小的 Asio 事件循环？

- 创建 `io_context`，在启动线程前提交初始操作或持有工作守卫。
- 用一个或多个线程调用 `run()`，并用 `try` 捕获处理器异常。
- 关闭时先停止接受新操作，再取消在途操作，最后重置守卫并 `join`。
- 工作守卫的生命周期应覆盖整个运行阶段，避免 `run()` 提前退出。
- 所有跨线程提交使用 `post`，共享状态用 `strand` 或互斥量保护。
- 上下文销毁前确保所有线程已退出，避免处理器访问已销毁对象。

```cpp
asio::io_context ctx;
auto guard = asio::make_work_guard(ctx);
std::thread t([&] {
    try { ctx.run(); } catch (...) { /* log */ }
});
asio::post(ctx, [] { /* start */ });
guard.reset();
t.join();
```

## 3. Asio 异步操作

### 3.1 `async_read` 与 `async_read_some` 的完成条件有何不同？

- `async_read_some` 在至少传输一个字节或发生错误时完成，可能短读。
- `async_read` 是组合操作，重复调用底层读直到缓冲区填满或出错。
- 默认完成条件是 `transfer_all`，也可以传 `transfer_at_least` 等条件。
- 流提前关闭时，`async_read` 以 `eof` 完成，`bytes_transferred` 可能小于缓冲区大小。
- 完成处理器不会在发起函数内调用；即使操作立即完成，也按异步方式投递。
- 固定长度协议适合 `async_read`；需要边读边处理时使用 `async_read_some`。
- 两者都要求同一流上不能有其他读操作同时进行。

### 3.2 `async_write` 与 `async_write_some` 的完成条件有何不同？

- `async_write_some` 只保证一次底层写，可能只传输部分数据。
- `async_write` 重复调用底层写，直到所有缓冲区数据写完或出错。
- 短写是正常现象，发送缓冲区满、信号中断等都可能造成。
- `async_write` 的 `bytes_transferred` 在出错时表示已写字节数。
- 需要全部发送时使用 `async_write`；需要自己控制分片时使用 `async_write_some`。
- 同一流上不能同时存在多个写操作。

### 3.3 为什么同一个 `socket` 上不能并发调用 `async_read`？

- `async_read` 是组合操作，内部会多次调用 `async_read_some`。
- 两个读操作同时挂起会让同一接收流上的数据归属与完成顺序相互干扰。
- Asio 对读操作要求串行：前一个读完成前不能发起下一个读。
- 需要流水线时在完成处理器中发起下一次读，或使用显式读队列。
- `strand` 只能保证处理器不并发，不能替代同一时刻一个读操作的先决条件。
- 违反先决条件的行为未定义，可能丢数据或破坏流状态。

### 3.4 为什么异步操作的缓冲区必须在 `handler` 调用前保持有效？

- `asio::buffer` 只保存指针与长度，不拥有底层内存。
- 异步操作把缓冲区地址交给内核或内部状态，完成前可能随时访问。
- 局部数组或临时 `std::string` 在发起函数返回后销毁，处理器会读写悬空内存。
- 缓冲区应是会话对象的成员，或用 `shared_ptr` 管理生命周期。
- 完成处理器执行前不能调整容器大小，否则指针可能失效。
- `asio::streambuf` 与 `dynamic_buffer` 可以提供所有权与动态扩容。

### 3.5 `asio::buffer` 与 `dynamic_buffer` 的所有权差异是什么？

- `asio::buffer` 生成的是视图，底层内存由调用方管理。
- `dynamic_buffer` 包装 `std::string` 或 `std::vector`，按需扩容并提供所有权语义。
- `asio::streambuf` 自带存储，适合按行或按分隔符读取。
- 视图适合固定大小、生命周期明确的缓冲区；动态缓冲适合未知长度数据。
- 动态扩容可能使旧指针失效，操作进行中不能让容器重新分配。
- 两者的缓冲区序列都可以包含多个连续区间。

### 3.6（陷阱）`async_write` 的缓冲区在调用后修改会发生什么？

- 接口要求缓冲区在完成处理器调用前保持有效，并且内容不被修改。
- 修改正在被异步写入的内存构成数据竞争，行为未定义。
- 即使写入已经进入内核，库仍可能持有指针用于重试或分片。
- 正确做法是使用独立的发送缓冲区，或在完成回调后再复用。
- 需要零复制时把缓冲区所有权转移到会话对象，并保证只读。
- 发送队列中的每个缓冲区都要有明确的释放时机。

### 3.7 `steady_timer` 的 `expires_after` 如何处理未完成的等待？

- 修改到期时间会取消所有挂起的 `async_wait`，返回被取消的数量。
- 返回 0 表示等待处理器已经执行或即将执行，不能再假定取消成功。
- 被取消的等待以 `asio::error::operation_aborted` 完成。
- 重新计时后需要重新发起 `async_wait`，旧等待不会自动延续。
- 多个等待同时挂起时，`expires_after` 会全部取消；`cancel_one` 只取消一个。
- 定时器对象需要在等待期间保持有效。

### 3.8 定时器 `handler` 一定准时执行吗？

- 到期时间只表示最早可执行时刻，不保证处理器在该时刻运行。
- 事件循环被长处理器占用时，定时器回调会延迟。
- 操作系统调度、时钟精度与处理器队列都会影响实际延迟。
- `steady_timer` 使用单调时钟，不受系统时间调整影响。
- 实时性要求高的场景需要专用线程、实时优先级与独立定时机制。
- 延迟监控应记录到期时间与回调时间的差值。

### 3.9 `resolver` 的异步解析流程如何组织？

- 构造 `resolver`，调用 `async_resolve` 传入主机与服务名。
- 完成处理器接收 `error_code` 与 `results_type`，成功时结果非空。
- 结果对象持有解析数据，可以复制或移动，生命周期不必绑定到 `resolver`。
- 解析失败时结果为空，错误码说明失败原因。
- 得到结果后通常交给 `async_connect`，由它逐个尝试端点。
- 解析与连接都应绑定 `strand` 或保证会话状态不被并发访问。

### 3.10 `async_connect` 的完成条件是什么？

- 单端点重载在连接建立或失败时完成，处理器只接收 `error_code`。
- 端点序列重载逐个尝试，成功时返回已连接的端点。
- 全部失败时返回最后一次尝试的错误；空序列返回 `not_found`。
- 套接字未打开时会自动打开；失败后不会自动恢复为关闭状态。
- 连接操作可以被取消，完成码为 `operation_aborted`。
- 连接成功后才能发起读写，不要把连接与读写并发启动。

### 3.11 如何为连接建立设置超时？

- 启动 `async_connect` 的同时启动 `steady_timer`。
- 定时器到期后关闭或取消套接字，连接操作以 `operation_aborted` 完成。
- 连接成功时取消定时器，避免超时处理器继续执行。
- 两个完成路径都可能先到达，需要状态标志保证只处理一次。
- 超时原因与主动取消要分别记录，不能只看 `operation_aborted`。
- 所有操作绑定同一 `strand`，避免关闭与完成处理器竞争。

### 3.12 为什么 I/O 对象不可复制？

- 一个 I/O 对象通常拥有一个操作系统句柄，复制会导致重复关闭。
- 复制还会让两个对象共享同一底层状态，完成处理器归属不清。
- Asio 的 I/O 对象通常可移动，移动后源对象不再拥有句柄。
- 移动后的源对象状态由实现定义，不能继续用于发起操作。
- 需要共享访问时使用 `shared_ptr` 持有对象，而不是复制对象。
- 执行器在构造时绑定，移动不改变完成处理器的目标上下文。

### 3.13 `close()` 与 `shutdown()` 的差异是什么？

- `close()` 释放底层句柄，并取消未完成的发送、接收与连接操作。
- 被取消的操作以 `operation_aborted` 完成。
- `shutdown()` 只禁用发送、接收或双向能力，不立即释放句柄。
- 关闭发送方向可以发送 FIN，对端读到 EOF；关闭接收方向影响本地读。
- 优雅关闭通常先 `shutdown_send`，等待对端关闭，再 `close`。
- `shutdown()` 后能否继续操作由方向与平台决定，不能假定套接字仍可用。

### 3.14 如何区分 EOF、短读与错误？

- `asio::error::eof` 表示对端有序关闭，不是本地故障。
- `bytes_transferred` 表示出错前已传输的字节数，可能大于 0。
- `async_read` 在缓冲区未填满时遇到 EOF，会以 `eof` 完成。
- 非空缓冲区的 `async_read_some` 返回 0 字节时通常伴随 EOF 或错误，需要检查错误码。
- 应用层协议要定义帧边界，不能把一次短读当成完整消息。
- 遇到 EOF 后应停止读，按协议决定是否还能写。

### 3.15 分散聚集 I/O 有什么收益与限制？

- 缓冲区序列可以一次提交多个不连续区间，减少系统调用次数。
- 内核使用分散聚集接口读写，适合头部与载荷分段存储。
- 区间数量受平台限制，超过限制时实现可能分批处理。
- 每个区间仍然需要保持有效，生命周期规则与单缓冲区相同。
- 过多小区间会增加内核与库的遍历开销，未必比复制更快。
- 需要连续内存的协议字段仍要在应用层拼装。

### 3.16 为什么 `async_write` 不能与 `async_write_some` 混用？

- 两者都要求同一流上不存在其他写操作。
- `async_write` 内部可能分多次写，其他写操作会插入到分片之间。
- 交错写入会破坏应用层帧的顺序，接收方无法解析。
- 需要并发发送时使用发送队列，由单一写循环依次取出缓冲区。
- `strand` 可以串行化发起动作，但不能让两个写操作同时挂起。
- 所有写路径都应经过同一个队列或状态机。

### 3.17 异步操作链的启动顺序与完成顺序一致吗？

- 启动顺序只表示发起调用的先后，不表示完成先后。
- 不同操作可能在不同线程或不同就绪事件上完成。
- `strand` 保证处理器不并发，并按特定 happens-before 条件排序，不保证所有启动顺序。
- 组合操作内部的分片完成顺序由协议与实现决定。
- 需要严格顺序时在完成处理器中启动下一步，或使用显式队列。
- 不能依赖先发起一定先完成来保护共享状态。

### 3.18（代码阅读）这段顺序启动的读操作有什么问题？

```cpp
asio::async_read(socket, asio::buffer(header), on_header);
asio::async_read(socket, asio::buffer(body), on_body);
```

- 两个 `async_read` 在第一个完成前同时挂起，违反同一流只允许一个读操作的先决条件。
- 第二个读会与第一个读竞争同一接收流，数据归属不确定。
- 两个完成处理器的顺序没有保证，`body` 可能在 `header` 之前被处理。
- 正确做法是在 `on_header` 中根据头部长度发起 `body` 的读。
- 若需要并行处理多个连接，应为每个连接维护独立状态，而不是共享 `socket`。
- 违反先决条件的行为未定义，不能依赖测试偶然通过。

### 3.19 如何设计一个请求-响应式异步会话？

- 会话对象持有 `socket`、读缓冲区、写队列、定时器与状态字段。
- 同一时刻只保留一个读操作和一个写操作，读写可以并行。
- 读循环先解析头部，再按长度读取载荷，避免粘包与短读。
- 写队列由单一写循环消费，写完成后取出下一项。
- 所有状态变更绑定同一 `strand`，超时与关闭也提交到该 `strand`。
- 错误、EOF 与取消都走统一关闭路径，释放缓冲区并取消定时器。
- 会话用 `shared_ptr` 管理，异步处理器持有强引用，避免提前销毁。

### 3.20 `async_read_until` 适合哪些场景？

- 适合以分隔符结束的文本协议，例如按行读取。
- 它读取到分隔符出现为止，`bytes_transferred` 包含分隔符。
- 通常配合 `asio::streambuf` 或 `dynamic_buffer` 使用。
- 分隔符迟迟不出现时缓冲区会持续增长，需要设置上限。
- 二进制长度前缀协议更适合先读固定头部，再按长度读载荷。
- 分隔符可能一次读入多个，后续解析要处理缓冲区中的剩余数据。

## 4. Asio 错误与取消

### 4.1 异步操作为什么用 `error_code` 报告运行期错误？

- 网络断开、超时、取消属于正常控制流，不适合用异常逐层传播。
- 完成处理器签名直接携带错误码，调用方在一个位置统一处理。
- 异常跨异步边界传播需要额外捕获与存储，代价和语义都更复杂。
- 发起函数本身的参数错误或分配失败仍可能抛异常。
- 错误码让组合操作可以决定短路、重试或取消。
- 编程错误不应伪装成可恢复的 `error_code`。

### 4.2 Asio 异步操作的异常路径有哪些？

- 发起函数可能因分配失败、无效参数或同步打开失败抛出 `system_error`。
- 异步完成阶段的运行期错误通过 `error_code` 传给处理器。
- 处理器抛出的异常会传播到调用 `run()` 的线程。
- 析构函数中抛异常会导致 `std::terminate`。
- 组合操作的中间处理器抛异常时，资源清理与完成状态必须保持一致。
- 异常安全要求发起失败时不留下半注册的操作。

### 4.3 `redirect_error` 解决什么问题？

- 它把完成签名中的 `error_code` 捕获到外部变量，处理器不再接收该参数。
- 适合已有大量不检查错误码的处理器，或希望把错误处理集中到一处。
- 它不改变操作的错误语义，只改变完成签名的形状。
- 被捕获的 `error_code` 必须在处理器执行期间保持有效。
- 多个操作共享同一个 `error_code` 会产生数据竞争。
- 需要区分错误来源时，仍应在处理器中记录操作标识。

```cpp
asio::error_code ec;
socket.async_read_some(asio::buffer(buf),
    asio::redirect_error(
        [&](std::size_t n) { /* use ec and n */ }, ec));
```

### 4.4 `asio::error::operation_aborted` 在什么情况下出现？

- 套接字关闭或取消时，未完成的发送、接收与连接操作以该错误完成。
- 定时器到期时间被修改或定时器被取消时，等待操作以该错误完成。
- 逐操作取消信号生效时，目标操作通常也以该错误完成。
- 它表示操作被中止，不表示对端发送了错误数据。
- 重试逻辑应把该错误与真实网络故障分开处理。
- 该错误也可能与成功竞争，不能仅凭它推断操作一定没有产生副作用。

### 4.5 `cancellation_slot` 与 `cancellation_signal` 如何配对？

- `cancellation_signal` 持有单个槽，`slot()` 返回与该信号关联的 `cancellation_slot`。
- 异步操作在槽上安装取消处理器，信号 `emit` 时同步调用该处理器。
- 槽只能连接一个信号，信号与槽都必须活到操作完成。
- 没有安装处理器时，`emit` 不产生效果。
- 取消处理器运行在调用 `emit` 的线程，不应在其中执行阻塞操作。
- 逐操作取消需要操作本身支持对应的取消类型。
- Boost.Asio 1.77 与独立 Asio 1.19 起提供取消槽设施，具体可用性由版本决定。

```cpp
asio::cancellation_signal sig;
socket.async_read_some(asio::buffer(buf),
    asio::bind_cancellation_slot(sig.slot(),
        [&](const asio::error_code& ec, std::size_t n) { /* ... */ }));
sig.emit(asio::cancellation_type::terminal);
```

### 4.6 `cancellation_state` 如何形成父子取消链？

- `cancellation_state` 附着到父槽，并创建自己的子槽。
- 父槽收到取消时，状态按过滤器转换取消类型，再转发给子槽。
- 组合操作把子槽绑定到各子操作，形成逐层传播。
- `cancelled()` 返回已触发的取消类型，`clear()` 可以清除标记。
- 默认构造允许终止取消；也可以用过滤器只允许部分类型。
- 状态对象必须活到所有子操作完成。

### 4.7 取消如何传播到组合操作？

- 组合操作在启动时创建子取消状态，把子槽绑定到每个底层操作。
- 父信号到达后，组合操作按自身策略转发终止、部分或总取消。
- 不是所有底层操作都支持所有取消类型，支持范围由操作与版本决定。
- 组合操作可能等待所有子操作结束，再以 `operation_aborted` 完成。
- 中间处理器也应绑定同一取消链，避免取消只到达第一层。
- 自定义组合操作需要显式实现转发与清理。

### 4.8 为什么 Asio 的取消是协作式的？

- 取消信号只是调用槽上的处理器，由操作决定如何响应。
- 操作可以选择忽略、延迟或转换为底层系统调用取消。
- 正在完成的操作可能成功，取消请求会输掉竞争。
- 没有强制栈展开，也没有跨线程杀死操作。
- 因此取消后仍必须等待完成处理器，不能立即释放缓冲区。
- 协作式取消的延迟取决于操作的检查点与系统调用行为。

### 4.9 取消与关闭 `socket` 的语义差异是什么？

- 取消槽针对单个操作，关闭套接字影响该对象上的所有未完成操作。
- `close()` 释放句柄并让操作以 `operation_aborted` 完成。
- 取消请求可以只终止一次读，套接字仍可用于后续操作。
- 终止取消可能使对象只能关闭或销毁，具体语义由操作定义。
- 关闭是更强的同步点，但会破坏连接状态。
- 需要保留连接时使用逐操作取消，需要丢弃连接时使用关闭。

### 4.10 取消后完成处理器还会被调用吗？

- 会，取消是异步完成的一种，处理器仍会被调用一次。
- 典型错误码是 `operation_aborted`，但也可能与成功竞争。
- 操作状态与缓冲区必须保持到处理器执行完毕。
- 处理器负责释放资源、更新状态并决定是否重试。
- 如果处理器被销毁或不再等待，资源可能泄漏。
- 不能假设取消后不会再有回调，从而提前销毁会话。

### 4.11 如何区分超时、主动取消与真实错误？

- 在发起操作时记录原因字段，而不是只看最终错误码。
- 超时通常由定时器触发，随后关闭或取消操作，错误码也是 `operation_aborted`。
- 主动取消由业务状态触发，应在取消前设置对应标志。
- 真实错误来自网络栈或协议解析，错误码与类别不同。
- 完成处理器读取原因字段，决定重试、关闭或上报。
- 多个路径竞争时用原子状态或 `strand` 保证只记录一次原因。

### 4.12 部分完成时取消会怎样？

- 完成处理器仍会收到已传输的字节数，缓冲区中可能已有部分数据。
- `cancellation_type::partial` 表示操作可能产生部分副作用，对象仍处于已知状态。
- `terminal` 表示取消后只能关闭或销毁对象。
- `total` 表示取消后不应留下可观察的副作用。
- 协议层需要决定丢弃部分帧、回滚状态还是关闭连接。
- 不能把部分完成的数据当作完整消息交给上层。

### 4.13 `cancellation_filter` 有什么用途？

- 它把父信号中的取消类型按掩码过滤后再传给子槽。
- `enable_terminal_cancellation` 只允许终止取消。
- `enable_partial_cancellation` 允许终止与部分取消。
- `enable_total_cancellation` 允许全部类型。
- `disable_cancellation` 阻止取消向下传播。
- 过滤器用于让不支持某些取消类型的子操作只看到它能处理的部分。

### 4.14 为什么不能从任意线程直接销毁正在取消的 I/O 对象？

- 完成处理器可能正在另一线程访问该对象，销毁会造成释放后使用。
- 取消信号处理器也可能在发射线程同步运行。
- I/O 对象本身通常不是线程安全的，关闭与销毁需要串行化。
- 正确做法是把关闭与销毁提交到对象所属的 `strand`。
- 使用 `shared_ptr` 让处理器持有强引用，最后一个引用释放时再销毁。
- 销毁前应等待在途操作完成，或确保处理器不再访问对象。

### 4.15 协程中如何接入 Asio 取消？

- `asio::awaitable` 的协程可以通过 `asio::this_coro::cancellation_state` 读取取消状态。
- 取消状态从协程的取消槽传播到 `co_await` 的异步操作。
- `co_await` 的等待被取消时，通常以错误或异常结束，具体由等待方式决定。
- 协程应把取消与业务错误分开处理，避免把 `operation_aborted` 当成失败重试。
- 协程帧的销毁必须发生在所有子操作完成之后。
- 不同 Asio 版本的协程取消接口有差异，使用前核对版本文档。

### 4.16 组合操作如何汇总多个错误？

- 顺序组合通常返回第一个失败的错误，后续步骤不再执行。
- 并行组合可能等待所有子操作结束，再选择第一个或最后一个错误。
- `when_all` 在首个错误到达后请求其余输入停止，但等全部结束后再完成。
- 取消与错误同时存在时，需要定义优先级，通常停止信号不覆盖真实错误。
- 错误汇总要保留操作标识与阶段，不能只返回一个通用码。
- 组合层应避免重复完成接收器。

### 4.17 错误码比较与分类应注意什么？

- 使用 `error_code` 的类别与值比较，不要直接比较整数。
- `ec == asio::error::eof` 这类比较会同时检查类别与值。
- 不同平台的系统错误值不同，跨平台代码应使用 Asio 的通用错误枚举。
- `message()` 适合日志，不适合作为分支条件。
- 自定义错误类别需要定义 `category()` 与等价关系。
- 取消、EOF、超时与协议错误应分别归类。

### 4.18 重试策略如何避免把取消当成失败？

- 在重试前检查取消状态与 `operation_aborted`。
- 记录取消原因，区分超时、业务取消与连接关闭。
- 只对幂等操作重试，并设置最大次数与退避上限。
- 重试等待本身也要可取消，避免关闭后仍长时间挂起。
- 连接已关闭或对象已进入终止状态时不再重试。
- 重试计数与原因应进入日志与指标。

### 4.19 资源清理应放在哪个完成路径？

- 缓冲区、定时器、取消槽与操作状态应在完成处理器中统一清理。
- 关闭路径先停止新操作，再取消在途操作，最后释放对象。
- 使用 RAII 管理会话成员，处理器只负责触发状态转换。
- 不要在析构函数中阻塞等待事件循环，以免死锁。
- 最后一个 `shared_ptr` 释放前确保没有处理器仍持有裸指针。
- 清理路径也要处理重复回调与竞争完成。

### 4.20（陷阱）取消槽在操作完成后仍然触发会怎样？

- 操作完成后，槽是否仍安装处理器由操作与版本决定，业务侧不能依赖。
- 继续 `emit` 可能没有效果，也可能调用仍然安装的处理器并访问已失效状态。
- 取消槽与信号的生命周期必须覆盖操作，但不应超过操作完成。
- 完成处理器中应清除或重置槽，业务侧不再复用旧槽。
- 多个操作共享一个信号时，发射会影响所有仍连接的槽。
- 关闭流程应先停止发射，再销毁信号与槽。

## 5. Asio 并发模型

### 5.1 `strand` 保证什么？

- 同一 `strand` 上的处理器不会并发执行。
- 满足特定 happens-before 条件时，处理器按提交顺序执行；例如先 `post(a)` 后 `post(b)`。
- 不同 `strand` 之间没有顺序或互斥保证。
- 处理器可以运行在不同线程，但同一时刻只有一个在运行。
- 组合操作的中间处理器也应绑定同一个 `strand`，否则共享状态仍可能竞争。
- `strand` 是执行器适配器，不是线程，也不保证处理器不迁移。

### 5.2 `strand` 与互斥量有什么区别？

- `strand` 通过排队与串行调用避免并发，不阻塞调用线程。
- 互斥量保护任意临界区，等待时阻塞线程。
- `strand` 只对通过它提交的处理器生效，直接调用不受保护。
- 同一 `strand` 内 `dispatch` 可能就地执行并形成重入；递归互斥量需要显式选择。
- `strand` 不会因为处理器等待另一处理器而自动让出，仍可能死锁业务逻辑。
- 选择取决于保护对象是处理器序列还是普通共享数据。

### 5.3 多线程运行同一 `io_context` 时 `handler` 如何并发？

- 每个调用 `run()` 的线程都可能取出并执行处理器。
- 不同处理器可以在不同线程同时运行。
- 同一个处理器不会被两个线程同时执行。
- I/O 对象的完成处理器默认回到对象关联的执行器，不绑定固定线程。
- 共享会话状态需要 `strand` 或互斥量保护。
- 线程数增加会提高并行度，也会增加锁竞争与缓存失效。

### 5.4 如何让一组 `handler` 串行执行？

- 创建一个 `strand`，让这组操作共用同一个 `strand` 对象。
- 用 `bind_executor(strand, handler)` 绑定完成处理器。
- 组合操作的中间处理器会继承关联执行器，需确认整条链都使用该 `strand`。
- 从外部发起操作时通过 `asio::post(strand, ...)` 进入串行域。
- 不要绕过 `strand` 直接调用共享对象。
- 需要顺序保证时明确提交点，不能依赖线程调度。

### 5.5 跨 `strand` 调用 `dispatch` 会发生什么？

- 当前线程不在目标 `strand` 内时，`dispatch` 可能排队，也可能在目标执行器允许时就地执行。
- 就地执行会绕过队列，改变调用栈与顺序。
- 需要确定延后时使用 `post`。
- 跨 `strand` 调用不会自动获得目标 `strand` 的保护，除非调用本身通过该执行器提交。
- 在持有锁时调用 `dispatch` 可能把目标处理器拉入当前栈，增加死锁风险。
- 明确执行位置比依赖 `dispatch` 的优化行为更可靠。

### 5.6 在 `strand` 内调用 `dispatch` 与 `post` 有什么差异？

- 已在同一 `strand` 内时，`dispatch` 通常立即执行，`post` 排队到稍后。
- `dispatch` 的就地执行会增加栈深度，递归提交可能造成栈溢出。
- `post` 保持队列顺序与公平性，但多一次入队开销。
- `dispatch` 可能让当前处理器在返回前看到新处理器的副作用。
- 需要延后状态变更或避免重入时使用 `post`。
- 两者都不改变底层执行器的线程选择。

```cpp
asio::strand<asio::io_context::executor_type> strand{ctx.get_executor()};
asio::dispatch(strand, [] { /* may run inline */ });
asio::post(strand, [] { /* queued */ });
```

### 5.7 多个 `io_context` 如何分工？

- 按延迟目标拆分：I/O 上下文与 CPU 工作上下文分离。
- 按线程拆分：每个线程一个上下文，减少共享队列竞争。
- 按连接类型拆分：长连接与短连接使用不同上下文。
- 跨上下文提交用 `asio::post`，不要直接操作对方的 I/O 对象。
- 多上下文增加负载均衡与关闭顺序的复杂度。
- 划分应基于测量，而不是按连接数机械切分。

### 5.8 `io_context` 之间如何传递任务？

- 使用 `asio::post(target_ctx, handler)` 把处理器提交到目标上下文。
- 处理器捕获的数据要有明确所有权，避免源上下文销毁后悬空。
- 目标上下文必须有人调用 `run()`，否则任务不会执行。
- 跨上下文调用不要用 `dispatch` 期待同步完成。
- 需要请求-响应时使用 `future`、回调或 `sender` 组合，不能用共享队列裸轮询。
- 关闭时先停止跨上下文提交，再逐个停止上下文。

### 5.9 线程池与 `io_context` 的关系是什么？

- `io_context` 本身不是线程池，它只提供事件循环与任务队列。
- 多个线程调用同一个 `io_context` 的 `run()`，形成事实上的工作线程池。
- 工作守卫维持循环运行，线程数由调用方决定。
- CPU 密集任务不应长期占用 I/O 线程，应提交到独立执行资源。
- P2300R10 没有提供标准线程池设施，实验实现可能提供 `static_thread_pool` 一类扩展。
- 线程池大小与 I/O 线程数的配比需要按负载测量。

### 5.10 为什么 `handler` 中不能执行长时间阻塞操作？

- 阻塞处理器占住 `run()` 线程，其他已就绪处理器无法执行。
- 定时器回调延迟，连接超时与心跳失真。
- 同一上下文的所有连接共享该线程，尾延迟被放大。
- 阻塞系统调用还可能阻止关闭信号被处理。
- 把阻塞工作移到独立线程或线程池，完成后用 `post` 回到 I/O 上下文。
- 无法避免阻塞时增加专用线程，但仍要限制并发数。

### 5.11 `strand` 的吞吐代价在哪里？

- 每次提交通常都要入队，涉及原子操作或互斥量。
- 跨线程唤醒与缓存行迁移带来额外开销。
- 串行化限制了同一 `strand` 上的并行度。
- 每个连接一个 `strand` 会增加对象与队列的内存占用。
- 批量提交与合并小任务可以降低单位开销。
- 开销由实现与竞争程度决定，需按实际负载测量。

### 5.12 每个连接一个 `strand` 的内存代价如何？

- `strand` 通常持有共享实现、底层执行器与队列状态。
- 连接对象、读缓冲区、写队列与定时器也会随连接数增长。
- 百万连接场景下，每连接固定开销会放大到可观的内存量。
- 可以用一个 `strand` 保护一组连接，但组内处理器会互相排队。
- 复用会话对象与缓冲区池可以降低分配次数，不改变串行语义。
- 具体字节数由实现与分配器决定，不能给出通用常数。

### 5.13 如何保证 `socket` 关闭与 `handler` 串行？

- 所有关闭动作通过 `asio::post(strand, ...)` 提交。
- 会话对象用 `shared_ptr` 持有，处理器捕获强引用。
- 关闭前设置状态标志，拒绝新的读写。
- 关闭后等待在途操作完成，再释放缓冲区。
- 不要在另一个线程直接调用 `close()` 或析构 `socket`。
- 超时与错误路径也走同一关闭函数。

```cpp
asio::post(strand, [self = shared_from_this()] {
    self->socket.close();
});
```

### 5.14 多 `io_context` 下如何做负载均衡？

- 由一个 `acceptor` 接受连接，再按轮询或负载指标分配到工作上下文。
- 多个 `acceptor` 使用 `SO_REUSEPORT` 时由内核分配连接，均衡性由平台决定。
- 分配后连接固定绑定某个上下文，迁移需要重建 I/O 对象。
- 监控各上下文的队列延迟与线程利用率，而不是只看连接数。
- 负载倾斜时可以把新连接导向空闲上下文，已有连接不轻易迁移。
- 过度分配会增加跨上下文通信与关闭复杂度。

### 5.15 如何检测 `handler` 的并发冲突？

- 使用 ThreadSanitizer 运行并发测试，捕获数据竞争报告。
- 在调试构建中断言 `strand.running_in_this_thread()`。
- 记录处理器线程 ID 与操作标识，分析是否存在非预期并发。
- 用可控的延迟与屏障放大竞争窗口。
- 单元测试覆盖关闭、超时与完成同时发生的路径。
- 工具只能提高发现概率，不能证明没有竞争。

### 5.16 线程局部状态在 `handler` 中有哪些问题？

- 处理器可能在不同线程运行，线程局部缓存不随会话迁移。
- `strand` 只保证串行，不保证固定线程。
- 线程局部分配器或日志缓冲区可能在切换线程后失效。
- 会话状态应放在会话对象中，线程局部只用于临时 scratch。
- 需要线程亲和性时使用专用上下文或显式绑定。
- TLS 析构顺序也可能与上下文销毁顺序冲突。

### 5.17 为什么不能在 `handler` 中析构所属 I/O 对象？

- 处理器可能仍持有该对象的引用，析构后继续访问造成释放后使用。
- 析构会取消在途操作，但完成处理器可能已经排队。
- 在处理器内销毁对象还可能让当前调用栈上的成员失效。
- 应把销毁延后到 `post`，或由最后一个 `shared_ptr` 释放触发。
- 关闭与销毁前确保没有其他处理器会访问对象。
- 会话对象与 I/O 对象的生命周期要分开设计。

### 5.18 `strand` 与取消如何交互？

- 取消信号处理器在调用 `emit` 的线程同步执行，不一定在目标 `strand` 上。
- 完成处理器仍按关联执行器回到 `strand`。
- 若取消处理器访问会话状态，必须把 `emit` 提交到同一 `strand`。
- 取消与完成可能竞争，状态标志要在 `strand` 内更新。
- 信号与槽的生命周期要覆盖操作，但发射要停止在销毁之前。
- 不要在取消处理器中阻塞等待完成。

### 5.19（场景）一个 `acceptor` 配多个 worker `io_context` 如何关闭？

- 先关闭 `acceptor`，停止接受新连接。
- 再通知各 worker 停止，取消或等待在途会话。
- 重置工作守卫，让 `run()` 在队列清空后返回。
- 按顺序 `join` 所有线程，避免上下文先于线程销毁。
- 会话对象在完成处理器中释放，关闭路径要允许重复调用。
- 关闭过程中拒绝新的跨上下文提交。

### 5.20 如何选择单 `io_context` 多线程还是多 `io_context`？

- 连接数不大、逻辑简单时，单上下文多线程更容易管理。
- 需要隔离延迟或减少队列竞争时，多上下文更合适。
- 单上下文的多线程共享一个队列，竞争随线程数增加。
- 多上下文需要处理跨上下文提交、负载均衡与关闭顺序。
- I/O 对象与执行器绑定，迁移连接的成本要纳入设计。
- 选择应基于队列延迟、CPU 利用率与运维复杂度的测量。

## 6. Asio 协程

### 6.1 `awaitable` 的两个模板参数分别表示什么？

- 第一个参数是协程的结果类型，`awaitable<void>` 不产生值，`awaitable<T>` 以 `T` 结束。
- 第二个参数是协程的关联执行器类型，默认值由版本决定，较新版本为 `any_io_executor`，早期为 `executor`。
- `co_spawn` 传入的执行器成为协程的关联执行器，可用 `co_await this_coro::executor` 取出。
- 关联执行器决定协程恢复时在哪个线程排队，也决定协程帧中 promise 保存的执行器对象。
- `awaitable` 的复制构造被删除，同一对象不能交给两个 `co_spawn`。
- 结果类型不同则完成签名不同，`awaitable<void>` 的完成处理器只接收 `std::exception_ptr`。

### 6.2 `co_spawn` 的完成签名由什么决定？

- 对 `awaitable<T>`，完成处理器的签名为 `void(std::exception_ptr, T)`。
- 对 `awaitable<void>`，完成处理器的签名为 `void(std::exception_ptr)`。
- 协程执行 `co_return value;` 时，值被移动到处理器的第二个参数。
- 协程抛出异常时，异常被存入 `std::exception_ptr`，第一个参数非空，第二个参数不构造。
- 处理器在 `co_spawn` 传入的执行器上调用，排队方式由完成令牌决定。
- 完成令牌为 `use_future` 时，值通过 `future` 取得，异常在 `get` 时重新抛出。

### 6.3（陷阱）`co_spawn` 返回时协程执行到哪一步？

- 协程在 `co_spawn` 内部被恢复，同步执行到第一个挂起点之后才返回调用点。
- 因此首次挂起前构造的局部对象仍在使用中，按引用捕获的做法要求其生命周期覆盖整个协程。
- 若协程在首次挂起前抛出异常，异常同样经完成处理器报告，不从 `co_spawn` 向调用方抛出。
- `co_spawn` 接管协程帧，不接管参数的所有权，按值传入的实参在协程帧内存有副本。
- 需要严格异步启动时，在协程开头 `co_await asio::post(asio::use_awaitable)` 显式让出。
- 依据「调用返回即已并发」的顺序假设组织代码，容易在首个挂起点上访问已销毁的对象。

### 6.4 用 `detached` 作为完成令牌会丢弃什么？

- `detached` 的完成处理器为空，协程结束时的 `exception_ptr` 不会交给任何代码。
- 未捕获异常在完成时被忽略，进程不终止，也不产生日志或计数。
- `detached` 不提供完成通知，调用方无法得知协程结束时刻。
- 需要观测失败时改用自定义令牌，在处理器中记录异常并递减未完成任务计数。
- 适合生命周期与进程一致的后台任务，例如常驻的接受循环。
- 与 `use_future` 相比，`detached` 不构造共享状态，分配开销更低。

### 6.5 `use_awaitable` 如何把异步操作变成可等待表达式？

- `use_awaitable` 是完成令牌，异步函数通过 `async_initiate` 把它转换为 `awaitable` 对象。
- 表达式类型由操作的完成签名决定，`void(error_code, std::size_t)` 变为 `awaitable<std::size_t>`。
- `co_await` 该表达式时协程挂起，操作完成、处理器被调用后恢复。
- 非零 `error_code` 被转换为 `system_error` 异常抛出，成功时返回其余参数。
- 该令牌要求编译器支持协程，且所在函数返回 `awaitable` 类型。
- 需要避免异常时改用 `as_tuple` 或 `redirect_error`，把错误作为返回值处理。

```cpp
asio::awaitable<void> relay(tcp::socket in, tcp::socket out) {
  char buf[4096];
  for (;;) {
    std::size_t n = co_await in.async_read_some(
        asio::buffer(buf), asio::use_awaitable);
    co_await asio::async_write(
        out, asio::buffer(buf, n), asio::use_awaitable);
  }
}
```

### 6.6 协程内的异常如何传播到外层？

- 被等待的 `awaitable` 以 `exception_ptr` 结束时，等待方在挂起点重新抛出该异常。
- 异常沿 `co_await` 链逐层向外传递，每层先展开局部变量，再交给上一层。
- 传播到最外层协程后，由 `co_spawn` 的完成处理器接收，匿名函数通常先判空再重抛。
- 异常类型保持不变，标准异常与自定义异常的处理路径相同。
- 处理器自身抛出异常时，异常从处理器内逸出，行为与该执行器上的其他处理器一致。
- 异常的代价包含一次或多次堆分配（`exception_ptr` 与异常对象），高频失败路径宜用错误码。

```cpp
asio::co_spawn(io, relay(std::move(a), std::move(b)),
    [](std::exception_ptr e) {
      if (!e) return;
      try { std::rethrow_exception(e); }
      catch (const std::exception& ex) { log_error(ex.what()); }
    });
```

### 6.7 `redirect_error` 与 `as_tuple` 有何差别？

- `redirect_error(use_awaitable, ec)` 把 `error_code` 写入外部变量，`co_await` 只返回其余结果。
- `as_tuple(use_awaitable)` 把全部结果打包为元组，`error_code` 作为元组第一项。
- 前者共享同一个 `error_code` 对象，两个协程并发等待时不能共用该变量。
- 后者每次 `co_await` 产生独立元组，可用结构化绑定解包，适合分支较多的读取循环。
- `as_tuple` 在较新版本才提供，起始版本由版本决定。
- 两者都不抛异常，适合把错误作为正常返回值、并需要区分超时与断开的场合。

```cpp
auto [ec, n] = co_await sock.async_read_some(
    asio::buffer(buf), asio::as_tuple(asio::use_awaitable));
if (ec == asio::error::eof) co_return;
```

### 6.8 `this_coro::executor` 取到的是什么？

- 返回协程的关联执行器，类型与 `awaitable` 的第二个模板参数一致。
- 默认来自 `co_spawn` 的第一个参数，传入 `strand` 时取到该 `strand` 的包装执行器。
- 该对象用于 `co_await asio::post(ex, asio::use_awaitable)` 切换执行上下文。
- 执行器保存在协程帧的 promise 中，挂起期间依然有效，可在任意挂起点之后取出。
- 协程内不能替换关联执行器，需要换执行器时用 `bind_executor` 包装单个操作。
- 把执行器交给其他线程使用前，应确认其类型可复制且线程安全，`strand` 满足这一要求。

### 6.9 `co_await` 之后恢复执行在哪个线程？

- 恢复由完成处理器触发，处理器的关联执行器默认为协程的关联执行器。
- `co_spawn` 传入 `io_context` 且多个线程调用 `run` 时，恢复线程是当时运行该执行器的某个线程。
- 需要固定线程时，`co_spawn` 传 `strand`，相关操作也绑定同一 `strand`。
- 操作在别的执行上下文完成时，恢复被派发回协程的关联执行器。
- 派发可能就地执行，完成发生在本执行器且无重入保护时，恢复在同一调用栈内发生，递归深度随之增加。
- 「恢复一定进入新线程」的假设不成立，线程局部状态不能代替同步。

### 6.10 协程帧在什么时机释放？

- 帧由 `co_spawn` 在内部创建，返回的 `awaitable` 临时对象在调用后不再持有帧。
- 协程以 `co_return`、异常或取消结束时，帧在完成处理器被调用之后销毁。
- 帧内按值捕获的实参与局部变量此时析构，顺序与构造相反。
- 若执行上下文停止且不再运行处理器，帧与其中的对象不会被销毁。
- 对 `awaitable<T>`，`co_spawn` 返回 `void`，没有句柄可查询或等待结束。
- 需要确定结束时刻时改用 `use_future` 或自定义令牌，在处理器中设置完成标志。

### 6.11 取消信号如何进入协程？

- `co_spawn` 的完成令牌可绑定取消槽，例如经 `bind_cancellation_slot(sig.slot(), token)`。
- 槽被触发后，协程内挂起的可取消操作收到取消请求。
- 协程用 `co_await this_coro::cancellation_state` 取到状态对象，用 `cancelled()` 查询已请求的类型。
- 定时器与套接字操作被取消后以 `operation_aborted` 完成，`use_awaitable` 把它转为 `system_error`。
- 未绑定取消槽时状态处于未连接，`cancelled()` 恒为空，取消无从传递。
- 取消是协作式的，协程不查询状态也不等待可取消操作时，请求不会自行终止协程。

```cpp
asio::cancellation_signal sig;
asio::steady_timer timer(io);
timer.expires_after(std::chrono::seconds(3));
timer.async_wait([&sig](asio::error_code ec) {
  if (!ec) sig.emit(asio::cancellation_type::terminal);
});
```

### 6.12 部分取消与总取消对协程意味着什么？

- `cancellation_type::terminal` 表示立即终止，`partial` 表示允许保留中间结果，`total` 表示二者之一。
- 定时器与单次套接字读写把请求视为立即取消，直接以 `operation_aborted` 结束。
- 组合操作可能只在 `terminal` 时放弃，收到 `partial` 时继续等待剩余数据。
- 以 `total` 触发时，操作可选择按 `terminal` 或按 `partial` 处理，由实现定义。
- 协程用 `cancelled()` 读取已请求的类型，据此决定丢弃结果还是提交部分结果。
- 设计取消协议时需写明支持的类型，调用 `cancellation_slot::clear` 后不再投递请求。

### 6.13 嵌套 `co_await` 另一个 `awaitable` 时发生什么？

- 调用返回 `awaitable` 的函数时协程帧即已创建，`co_await` 负责恢复并等待其结束。
- 内层协程的关联执行器默认继承自等待它的协程，两者通常相同。
- 内层不会自动获得外层的取消槽，取消需要经参数或 `bind_cancellation_slot` 显式传递。
- 内层以异常结束时，外层在挂起点重抛，先销毁内层帧，再展开外层局部变量。
- 内层的完成处理器绑定外层执行器，因此恢复仍在外层执行器上进行。
- 深层嵌套使栈展开路径变长，异常经过的每一层都可能分配 `exception_ptr`。

### 6.14 `awaitable` 能否保存起来延后启动？

- `awaitable` 不可复制，不能放入容器，也不能按值多次传递。
- 主用法是作为返回值，由 `co_spawn` 或外层 `co_await` 取得帧的所有权。
- 已创建但从未 `co_await` 的 `awaitable` 析构时销毁帧，协程不会执行完毕。
- 因此不能在 `co_spawn` 之前构造并长期保存，除非确实打算延迟启动。
- 需要延迟启动或重复执行时，把逻辑写成返回 `awaitable` 的普通函数，在需要处调用。
- `awaitable` 对象本身只持有帧指针与执行器，复制成本可以忽略，需要注意的只有所有权。

### 6.15（陷阱）协程中调用阻塞接口会有什么后果？

- 阻塞的是运行该协程的线程，同线程上其余就绪处理器全部延后。
- 线程数为 1 时，整个服务在阻塞期间停止响应，包括定时器与取消。
- 协程挂起才让出线程，普通函数调用不让出，`co_await` 之前的长循环同样占用线程。
- 需要执行阻塞逻辑时提交到独立线程池，再用协程等待其结果返回。
- 阻塞期间取消请求无法被处理，只在下一次挂起点生效。
- 磁盘 I/O、名称解析、日志落盘常属于此类，应换成异步接口或专用线程。

### 6.16 `co_spawn` 使用 `use_future` 时如何取得结果？

- 返回 `std::future<T>`，协程的返回值即该 `future` 的值。
- 协程异常存于共享状态，`get` 时重新抛出，类型不变。
- `future` 析构不阻塞，既不 `get` 也不 `wait` 时结果被丢弃，帧在完成时仍会销毁。
- `future` 只能消费一次，多处等待需改用 `shared_future` 或自定义令牌。
- 等待该 `future` 的线程被阻塞，不要在同一执行上下文的线程上等待它。
- 早期版本的 `use_future` 返回 Boost 的 `future`，具体类型由版本决定。

### 6.17 协程与 `strand` 组合时注意什么？

- `co_spawn(strand, ...)` 使协程的每次恢复都在该 `strand` 上串行执行。
- 同一连接上的读写因此不会并发，无需额外的互斥量保护连接状态。
- 某个操作绑定到其他执行器时，恢复仍派发回 `strand`，串行性不被破坏。
- 多个协程共用同一 `strand` 时彼此串行，长计算会延迟同一 `strand` 上的其他协程。
- 串行性只覆盖经该 `strand` 派发的处理器，直接调用的函数不受保护。
- 在 `strand` 上等待由同一 `strand` 完成的操作不会死锁，等待通过挂起实现。

### 6.18（场景）协程内如何实现超时？

- 常见做法是让业务操作与定时器并行推进，先完成者决定结果，另一个被取消。
- 定时器到期时触发 `cancellation_signal`，业务操作以 `operation_aborted` 结束。
- 需要区分超时与对端断开时，检查定时器是否到期，或单独记录标志。
- `asio::experimental::awaitable_operators` 提供等待两个 `awaitable` 之一的运算符，属实验接口。
- 取消之后必须等业务操作真正结束再释放缓冲区，否则处理器可能访问已失效内存。
- 超时作用于整个请求还是单次读写，按业务语义确定，混用会让重试逻辑失控。

### 6.19（实现）协程被取消后资源如何清理？

- 取消只是让挂起的操作以错误结束，协程代码仍继续执行到 `co_return` 或异常点。
- 清理逻辑写在正常路径上，或用析构时执行的守卫对象，两条路径共用同一段代码。
- 未捕获的 `system_error` 使协程栈展开，局部对象按逆序析构。
- 套接字与定时器析构会取消未完成操作，但处理器仍可能被调用，缓冲区须保持有效。
- 使用 `detached` 的后台协程清理失败时异常被丢弃，排查只能靠日志与计数。
- 清理在 `strand` 上执行，可避免与仍在运行的处理器并发访问同一连接状态。

### 6.20（辨析）协程与回调混用时注意什么？

- 同一条连接上混用两种模型时，完成顺序仍由执行器与 `strand` 决定，需统一串行化。
- 协程内的 `co_await` 只约束本协程的挂起顺序，不约束其他回调的先后。
- 从回调侧推进协程应经 `asio::dispatch` 或 `post` 投递，不能直接恢复挂起中的协程。
- 共享状态跨两个上下文传递时，生命周期由持有者保证，通常用 `shared_ptr` 捕获。
- 协程结束后的完成处理器可能仍在队列中，销毁连接对象前需确认没有待处理操作。
- 两种模型的调试工具不同，接口边界宜只暴露一种，混用限制在单个类内部。

## 7. Asio 完成令牌

### 7.1 完成令牌在 Asio 的类型体系中承担什么角色？

- 令牌是异步函数的最后一个参数，其类型决定结果的投递方式：回调、`future`、`awaitable` 或丢弃。
- 异步函数按「初始化函数加完成令牌」组织，令牌只参与发起阶段的类型推导。
- `async_result` 把令牌与完成签名映射为返回类型，早期接口经 `async_completion::result` 完成同样的映射。
- 令牌可以是 lambda、`std::function`、成员函数指针，也可以是 `use_future` 这类适配器对象。
- 令牌携带的关联执行器、关联分配器与取消槽经 `associated_*` 特性传给处理器。
- 自定义令牌只改变投递方式与返回类型，不改变操作的 I/O 语义与错误来源。

### 7.2（实现）`async_initiate` 与 `async_result` 如何协作？

- `async_initiate` 是异步函数的统一入口，参数为初始化函数、令牌与其余实参。
- 它查询 `async_result` 对令牌与签名的特化，取得返回类型与 `initiate` 成员。
- 发起阶段调用 `initiate(handler_factory, args...)`，由该成员决定何时真正启动操作。
- 适配器令牌的 `initiate` 先包装用户处理器，再把包装结果传给下层初始化函数。
- 返回类型完全由 `async_result` 决定，可以是 `void`、`future` 或 `awaitable`。
- 较新版本用 `completion_token_for` 概念约束形参，不满足约束时在重载决议阶段报错。

### 7.3 `use_future` 返回的 `future` 类型如何推导？

- 签名 `void(error_code, T)` 映射为 `std::future<T>`，`error_code` 不进入结果类型。
- 签名 `void(error_code)` 与 `void()` 都映射为 `std::future<void>`。
- 成功参数多于一个时结果为元组，例如 `void(error_code, T1, T2)` 得到 `future<std::tuple<T1, T2>>`。
- 推导在编译期完成，由 `async_result` 特化给出，运行时没有类型判断。
- 返回值类型随操作签名固定，同一个令牌用于不同操作会得到不同 `future`。
- 早期版本返回 Boost 的 `future`，改用标准库 `future` 的版本由版本决定。

### 7.4 `use_future` 中的错误如何呈现？

- 第一个参数为 `error_code` 时，非零值被转换为 `system_error` 存入共享状态。
- `get` 抛出该异常，`wait` 不抛出，只等待状态就绪。
- 操作本身抛出异常时同样存入共享状态，`get` 原样重抛。
- 调用方无法从返回值区分错误类别，只能捕获异常后检查 `code()`。
- 失败频繁的路径上异常开销明显，宜改用回调或元组形式。
- 共享状态不能被重复消费，第二次 `get` 抛出 `future_error`。

### 7.5（辨析）`use_awaitable` 与 `use_future` 如何取舍？

- `use_awaitable` 在协程内使用，挂起期间不占线程，恢复由执行器调度。
- `use_future` 需要另一个线程等待，或者在被阻塞的线程上 `get`，与事件循环的线程模型容易冲突。
- 协程中两者都可用，`use_future` 会把异步结果变成显式阻塞点，抵消协程的意义。
- 只有需要在非协程代码中把结果交给其他线程时，`use_future` 才占优势。
- 两者都以异常表达错误，需要错误码风格时都要配合 `as_tuple` 或 `redirect_error`。
- `use_future` 的操作至少多一次共享状态分配，`use_awaitable` 复用协程帧。

| 令牌 | 返回形式 | 错误呈现 | 适用场景 |
| --- | --- | --- | --- |
| 回调 | 无返回值 | 第一个参数 | 传统回调代码 |
| `use_future` | `std::future` | 异常 | 跨线程取结果 |
| `use_awaitable` | `awaitable` | 异常 | 协程 |
| `as_tuple(use_awaitable)` | `awaitable` 元组 | 元组第一项 | 错误分支较多 |
| `redirect_error` | 由内层令牌决定 | 外部变量 | 复用错误码变量 |
| `detached` | 无返回值 | 丢弃 | 常驻后台任务 |

### 7.6 `as_tuple` 改变了什么？

- 它是令牌适配器，把处理器的多个参数合并成一个 `std::tuple` 参数。
- 签名 `void(error_code, std::size_t)` 变为 `void(std::tuple<error_code, std::size_t>)`。
- 与 `use_awaitable` 组合时，`co_await` 的结果即该元组，可用结构化绑定解包。
- 与回调组合时，用户处理器只接收一个元组参数，参数个数固定。
- 它不改变错误的产生方式，只改变错误在调用点的传递形态。
- 该适配器在较新版本提供，起始版本由版本决定。

```cpp
auto [ec, n] = co_await sock.async_read_some(
    asio::buffer(buf), asio::as_tuple(asio::use_awaitable));
if (ec == asio::error::eof) co_return;
if (ec) throw asio::system_error(ec);
```

### 7.7 `bind_executor` 的语义是什么？

- 把执行器与令牌或处理器关联，处理器被调用时经该执行器派发。
- 形式为 `bind_executor(ex, token)`，返回类型中包含执行器，属于新的令牌类型。
- 常用于把回调固定到 `strand`，避免同一连接的两个操作并发访问状态。
- 与 `use_awaitable` 组合时，协程的恢复改投递到指定执行器。
- 关联沿令牌传播，`as_tuple`、`redirect_error` 等适配器保留该关联。
- 它不改变操作本身的执行位置，只影响完成处理器的调用位置。

```cpp
asio::strand<asio::io_context::executor_type> st = asio::make_strand(io);
char* buf = buffer_;
sock.async_read_some(asio::buffer(buf, size),
    asio::bind_executor(st, [buf](asio::error_code ec, std::size_t n) {
      if (!ec) handle(buf, n);
    }));
```

### 7.8（实现）自定义完成令牌需要实现哪些部分？

- 特化 `async_result`，提供返回类型与 `initiate`，两者决定令牌的全部可见行为。
- 旧接口使用 `type` 与双参数 `initiate`，新接口形式由版本决定，移植时需确认。
- `initiate` 接收处理器工厂与其余实参，返回类型必须与返回类型别名一致。
- 生成的处理器需可移动、可调用，并尽量提供关联执行器与关联分配器。
- 需要参与取消时提供取消槽类型，并把槽绑定到处理器上。
- 特化必须对操作可能产生的全部签名可见，缺一个签名就会在编译期失败。

```cpp
namespace asio {
template <typename Handler>
struct async_result<log_token, void(error_code, std::size_t)> {
  using return_type = void;
  template <typename Init, typename... Args>
  static void initiate(Init&& init, log_token, Args&&... args) {
    std::forward<Init>(init)(
        [](error_code ec, std::size_t n) { record(ec, n); },
        std::forward<Args>(args)...);
  }
};
}
```

### 7.9 `deferred` 与 `detached` 有什么区别？

- `detached` 表示立即发起，完成时结果被丢弃，接口没有返回值。
- `deferred` 表示延迟发起，返回一个可调用对象，调用该对象时才启动操作。
- 可调用对象可以保存、传递、稍后执行，便于把操作排入自有队列。
- 调用该对象时仍需传入完成令牌，由该令牌决定结果的去向。
- 两者都不需要共享状态，适合极轻量的发起动作。
- `deferred` 的引入版本由版本决定，早期版本只有 `detached`。

### 7.10 完成令牌如何影响堆分配？

- 每个异步操作需要一个操作对象，通常从 `io_context` 的分配器取得，位于堆上。
- 处理器随操作对象一起存放，处理器较大时占用更多内存并多一次移动。
- `use_future` 额外分配共享状态，`detached` 的处理器为空，分配量最小。
- 关联分配器可替换默认分配器，来源是 `bind_allocator` 或处理器自带的 `allocator_type`。
- 协程路径的主要分配是协程帧，操作对象仍各分配一次。
- 短小且高频的操作上，分配次数对吞吐的影响通常大于处理器体积。

### 7.11 处理器的关联执行器如何确定？

- 优先采用令牌上经 `bind_executor` 关联的执行器。
- 其次采用处理器自身通过 `executor_type` 与 `get_executor` 提供的执行器。
- 两者都没有时使用操作的默认执行器，通常取自发起操作的对象。
- 派发按 `dispatch` 语义进行，条件满足时就地调用，不进入队列。
- 关联在发起阶段确定，操作进行中无法更改。
- 绑定的执行器类型与操作要求的类型不匹配时，错误在编译期暴露。

### 7.12 关联分配器如何生效？

- 处理器提供 `allocator_type` 与 `get_allocator` 时，Asio 用它分配操作对象。
- `bind_allocator(alloc, token)` 可为任意令牌附加分配器，无需修改处理器。
- 分配器只覆盖操作对象与处理器的存储，不覆盖缓冲区。
- 池式分配器能减少通用堆分配，但需要线程安全，除非限定单线程运行。
- 分配器类型进入操作的类型，替换分配器会改变模板实例化与目标文件体积。
- 早期版本通过两参数分配钩子参与分配，改用关联分配器的版本由版本决定。

### 7.13 完成令牌与取消槽如何组合？

- `bind_cancellation_slot(slot, token)` 把取消槽关联到令牌，再传给操作。
- 操作保存该槽，取消信号到达时向底层请求终止。
- 适配器令牌无需感知槽，只要把关联继续传递即可。
- `co_spawn` 的协程通过同一机制获得取消能力。
- 一个槽只应绑定一个处理器，重复绑定的行为由版本决定。
- 取消之后仍要等待处理器被调用，资源清理才发生在确定的时刻。

### 7.14 `redirect_error` 做了什么？

- 把签名中的 `error_code` 参数移出实参列表，写入调用方提供的变量。
- 处理器签名从 `void(error_code, T)` 变为 `void(T)`。
- 与 `use_awaitable` 组合时，`co_await` 不抛异常，错误写入指定变量。
- 变量必须比操作存活更久，通常放在协程帧或连接对象中。
- 多个并发操作写同一变量时产生数据竞争。
- 它只处理第一个 `error_code` 参数，其余参数顺序不变。

### 7.15（陷阱）同一个完成令牌对象能否复用于多个操作？

- 令牌按值传递，多数量适配器每次使用都产生独立状态。
- `use_future` 每次使用创建自己的共享状态，复用同一对象不共享结果。
- 带计数器的自定义令牌被复制后状态分离，计数不再累加。
- 令牌中保存的引用若指向临时对象，操作未完成前对象已销毁。
- lambda 令牌被复用于两个操作时，两个操作各存一份副本，捕获的指针仍指向同一对象。
- 需要共享状态时在令牌内保存 `shared_ptr`，不要依赖令牌对象本身。

### 7.16（陷阱）完成处理器被调用两次会发生什么？

- 前提条件是处理器恰好被调用一次，重复调用破坏该前提，行为未定义。
- 典型表现是资源被释放两次、状态被覆盖、事件循环的任务计数错乱。
- 常见成因是把同一处理器交给两个操作，或在手工完成操作之后又让原操作完成。
- 手工完成操作应经 `asio::post` 投递，并确认原操作已被取消且不会再回调。
- 原子标志只能掩盖症状，无法修复前提条件被破坏的问题。
- 协程路径上重复恢复同一协程帧同样属于未定义行为。

### 7.17 非协程函数能否直接使用 `use_awaitable`？

- 不能，该令牌产生 `awaitable`，只能在返回 `awaitable` 的协程函数中被 `co_await`。
- 普通函数中构造该对象并丢弃，不会启动任何操作，帧在析构时销毁。
- 需要同步结果时改用 `use_future` 再 `get`，并接受调用线程被阻塞。
- 也可以在非协程处用 `co_spawn` 启动协程，再由完成令牌取回结果。
- 阻塞点应放在事件循环之外的线程，否则同线程上的其他操作全部延迟。
- 两种形态可以在同一进程共存，接口边界按调用方是否为协程划分。

### 7.18 `io_context` 停止时未完成的操作会怎样？

- `stop` 使 `run` 尽快返回，事件循环不再等待新事件。
- 未完成的异步操作不会被取消，处理器仍留在队列中。
- 再次 `run` 之前需要 `restart`，之后队列中的处理器继续被调用。
- `io_context` 析构时未调用的处理器被销毁，处理器持有的资源随之释放，清理代码不会执行。
- 因此关闭流程应先关闭套接字或取消操作，再等处理器结束，最后停止与销毁。
- `work_guard` 只影响 `run` 的退出条件，与停止语义无关。

### 7.19 把 `std::function` 当完成令牌的代价是什么？

- 处理器被类型擦除，每次完成多一次间接调用，通常无法内联优化。
- 捕获较大时 `std::function` 自身堆分配，捕获较小时可能使用内部缓冲。
- 类型擦除丢失关联执行器与关联分配器信息，需要显式 `bind_executor` 与 `bind_allocator`。
- 模板实例化次数减少，编译时间与二进制体积可能下降。
- 语义与普通回调一致，代价集中在调用开销与分配上。
- 处理器很短时间接调用相对占比高，处理器较长时可以忽略。

### 7.20（场景）何时需要自定义完成令牌？

- 需要统一记录每个操作的结果、耗时或错误分布时。
- 需要在完成时自动续期、递减计数或上报指标时。
- 需要把 Asio 操作接入自有任务框架、日志框架或追踪系统时。
- 需要为全部异步接口提供统一的包装类型时。
- 标准令牌已覆盖回调、`future` 与协程三种形态，自写令牌只在存在横切需求时值得。
- 自定义令牌属于公共基础设施，需要编译期测试覆盖多种签名与错误路径。

## 8. Asio 性能与调优

### 8.1 一次异步操作在堆上分配了哪些对象？

- 操作对象与处理器通常合并为一次分配，大小由处理器体积决定。
- 定时器还要在定时器队列插入节点，节点随操作对象一并分配。
- 套接字的待处理操作队列条目占用额外内存，深度与在途操作数同阶。
- 缓冲区不参与分配，`asio::buffer` 只生成指向调用方内存的视图。
- 关联分配器可把这些分配导向池，减少通用堆调用次数。
- 分配次数与操作次数同阶，高频短操作上分配占比通常高于处理器计算。
- 处理器自带关联分配器时，分配来源换成该分配器，块大小与对齐方式由分配器实现。

### 8.2 如何减少处理器的堆分配？

- 让处理器尽量小，能放进内部缓冲时不再单独分配。
- 用关联分配器接管操作对象的分配，例如每线程一个定长池。
- 避免在处理器中按值捕获大对象，改为捕获指针或 `shared_ptr`。
- 用 `bind_allocator` 附加分配器，不必修改处理器类型。
- 短命操作可用延迟令牌分批发起，把多次分配集中到同一阶段。
- 分配器需要线程安全，除非执行上下文只用单线程运行。

### 8.3 `bind_allocator` 如何使用？

- 形式为 `bind_allocator(alloc, token)`，把分配器附加到令牌再传给操作。
- 分配器需满足 Allocator 要求，通常以字节为单位分配。
- 分配器被复制进操作对象，复制应廉价并共享底层资源。
- 处理器自带 `allocator_type` 时可直接复用，无需再绑定。
- 分配器只覆盖 Asio 内部对象，缓冲区由调用方自行管理。
- 池容量与线程数相关，需要按压测结果确定，过小会退化为通用分配。
- 池化分配常用于会话对象，可把每连接的分配次数压到常数级。

### 8.4 `io_context` 的并发提示如何影响性能？

- 构造时可传并发提示，声明单线程或少线程使用，实现据此简化内部同步。
- 提示为不安全值时要求只有一个线程调用 `run`，违反时行为未定义。
- 提示只影响内部锁策略，不改变执行模型，也不额外提供线程安全。
- 减少锁竞争可降低高并发下的开销，收益幅度由平台与版本决定。
- 默认值由版本与编译宏决定，部分平台默认即为单线程优化。
- 线程数需要动态调整时使用默认提示，避免误入不安全模式。

### 8.5 `strand` 的同步代价在哪里？

- 每个经 `strand` 派发的处理器需要维护顺序，涉及原子操作或队列。
- `strand` 之间相互独立，热点集中在一个 `strand` 上会把处理器串行化。
- 在 `strand` 上执行长任务会阻塞同一 `strand` 的其他处理器。
- 跨 `strand` 等待需要额外投递，增加一次队列往返。
- 只读共享数据可以放在 `strand` 之外，缩短串行区间。
- 线程数远大于 `strand` 数时，锁争用转化为队列争用，收益有限。
- 未绑定 `strand` 的处理器与 `strand` 上的处理器混用时，串行性只覆盖后者。

### 8.6 `dispatch` 与 `post` 在性能上差别多大？

- `post` 总是入队，保证不在当前调用栈内执行。
- `dispatch` 在满足条件时就地执行，省去一次队列往返与一次唤醒。
- 就地执行可能加深递归，长链式完成会耗尽栈空间。
- 就地条件由执行器判断，跨执行器时 `dispatch` 退化为入队。
- 需要严格顺序或避免重入时用 `post`，代价是一次队列操作。
- 协程恢复遵循相近规则，同步完成的链可能在同一调用栈内连续推进。

### 8.7 为什么对同一套接字并发 `async_write` 会退化？

- 并发写入会让不同消息的字节交错，破坏协议规定的帧边界。
- 即使加锁，多个写操作各自持有缓冲区，内存占用与系统调用次数都上升。
- 正确做法是写队列加单一在途写操作，写完一条再取下一条。
- 队列满时停止读取，形成背压，避免内存随发送速度无序增长。
- 每条消息单独一次系统调用开销高，批量合并后更省。
- 合并提高吞吐的同时增加延迟，需要按业务在两者之间取值。
- 队列同时按条数与字节数设阈值，分别约束延迟与内存。

```cpp
void send(std::string msg) {
  bool idle = out_.empty();
  out_.push_back(std::move(msg));
  if (idle) write_next();
}
void write_next() {
  asio::async_write(sock_, asio::buffer(out_.front()),
      [this](asio::error_code ec, std::size_t) {
        out_.pop_front();
        if (!ec && !out_.empty()) write_next();
      });
}
```

### 8.8 如何复用读缓冲区？

- 每条连接持有固定大小的数组，生命周期与连接对象一致。
- 用 `async_read_some` 读取已到达的数据，避免按需扩容。
- 数据需要跨多次读取保留时，复制到解析缓冲或环形缓冲。
- 避免每次读取构造 `std::string`，那会带来一次分配与一次复制。
- 缓冲区大小与 MTU、协议帧长匹配，过大浪费内存，过小增加调用次数。
- 缓冲区地址在操作完成前不得改变，扩容会让挂起操作持有悬空指针。

### 8.9 `asio::streambuf` 的代价是什么？

- 它是动态缓冲，容量不足时重新分配并复制已有数据。
- 长期运行后内部区域碎片化，读写位置维护本身也有开销。
- `async_read_until` 配合它使用时可能反复扩容，直到分隔符出现。
- 已知长度上界时改用固定数组或自定义动态缓冲，可消除扩容复制。
- `prepare` 与 `commit` 分离，使用不当会重复提交或漏提交。
- 解析大报文前一次性预留足够空间，可显著减少复制次数。

```cpp
asio::streambuf buf(8192);
co_await asio::async_read_until(
    sock, buf, "\r\n\r\n", asio::use_awaitable);
```

### 8.10 分散聚合 I/O 如何减少复制？

- `asio::buffer` 接受缓冲区数组，一次操作可传入多段内存。
- POSIX 后端通常映射为 `readv` 与 `writev`，一次系统调用处理多段。
- 头部与载荷分处两段时，无需拼接成连续内存即可发送。
- 段数存在上限，超过时实现会拆分为多次调用，具体行为由实现定义。
- Windows 后端使用缓冲区数组描述符，同样避免中间复制。
- 每段内存必须存活到操作完成，临时对象不能作为段。

```cpp
std::array<asio::const_buffer, 2> parts{
    asio::buffer(header), asio::buffer(payload)};
asio::async_write(sock, parts, handler);
```

### 8.11 Asio 中零复制能到什么程度？

- `asio::buffer` 只构造视图，不复制数据，发送时直接读取原内存。
- 接收侧仍需把数据从内核复制到用户缓冲区，这一层无法避免。
- 内核到内核的转发不在可移植接口中，需要平台特定调用。
- 应用层拼接与 `std::string` 构造是主要的可优化点。
- 接收缓冲大小由套接字选项控制，容量不足会增加读取次数与系统调用。
- 缓冲区复用可消除每次操作的分配与清零。
- 声称零复制时需要说明具体环节，端到端的零复制通常不成立。

### 8.12 `async_read` 的完成条件如何影响系统调用次数？

- 默认条件为读满整个缓冲区，未读满时继续读取。
- `transfer_at_least(n)` 在至少读到 n 字节后完成，适合按批处理。
- `transfer_exactly(n)` 要求恰好 n 字节，多读的数据留在流中。
- 条件越宽松返回越早，调用方处理次数随之增加。
- 条件越严格单次覆盖的数据越多，但完成延迟上升。
- 自定义完成条件在每次底层读取之后求值，注意其代价与副作用。

```cpp
std::size_t n = co_await asio::async_read(
    sock, asio::buffer(buf), asio::transfer_at_least(4096),
    asio::use_awaitable);
```

### 8.13 批处理小消息的常见手段有哪些？

- 应用层聚合：多条消息拼进同一缓冲再一次写出。
- 达到阈值立即发送，兼顾延迟与吞吐。
- 以固定间隔冲刷队列，控制最坏延迟。
- 协议使用长度前缀，接收端一次解析多条消息。
- 关闭或保留 Nagle 会影响小包的合并方式。
- 批处理改变时延分布，需要按业务指标评估，吞吐只是其中一项。
- 合并后的数据超过路径 MTU 会触发 IP 分片，批量大小需要与之匹配。

### 8.14 `TCP_NODELAY` 与批处理如何取舍？

- 关闭 Nagle 后每次写入尽快发出，交互型请求的尾延迟下降。
- 小包增多会提高单位数据的头部开销与中断次数。
- 请求响应模式通常关闭 Nagle，避免与延迟确认相互等待。
- 大流量单向传输可保留 Nagle，让协议栈合并小段。
- 应用层已合并数据时，Nagle 的作用有限。
- 该选项只影响发送侧的合并，不改变接收侧行为。

### 8.15 定时器数量对性能有什么影响？

- 每个定时器在定时器队列中占一个节点，插入与删除有对数开销。
- 大量短定时器集中到期时，回调在同一轮事件循环中堆积。
- 定时器精度受时钟粒度与事件循环负载影响，由实现定义。
- 用单个定时器驱动时间轮或最小堆，可替代每连接一个定时器。
- 到期回调中耗时较长的处理会推迟同批其他定时器。
- 取消后仍需让处理器执行一次，生命周期管理不能省。

### 8.16 后端选择对性能有什么影响？

- Linux 常用 `epoll`，BSD 与 macOS 用 `kqueue`，Windows 用 IOCP。
- 后端由平台与编译宏决定，切换后端需要重新编译。
- 较新版本提供 io_uring 后端，需要内核与编译配置支持，可用性由版本决定。
- 不同后端的系统调用次数与批量提交能力不同，收益随负载形态变化。
- IOCP 的完成模型与就绪模型不同，影响代码对并发与缓冲的假设。
- 后端细节不应进入业务代码，接口只暴露执行器与套接字。

### 8.17 多线程运行同一 `io_context` 的扩展性如何？

- 多个线程调用 `run` 时，处理器被分派到空闲线程，天然并行。
- 无 `strand` 保护的共享状态需要自行同步，容易成为瓶颈。
- 线程数超过核数后，上下文切换与缓存失效抵消并行收益。
- 长处理器造成负载不均，短处理器更利于分摊到多个线程。
- 每线程一个 `io_context` 可减少共享缓存行争用，代价是跨线程投递更复杂。
- 扩展性取决于临界区宽度，而不只取决于线程数量。
- 绑核可减少线程迁移与缓存失效，代价是负载均衡能力下降。

### 8.18 每连接一个 `strand` 与每线程一个 `io_context` 如何选择？

- 每连接一个 `strand` 的模型简单，共享事件循环，连接之间靠 `strand` 隔离。
- 每线程一个 `io_context` 减少跨核共享，适合 CPU 密集的协议处理。
- 前者受单个事件循环的唤醒与队列争用限制，后者需要处理跨线程投递。
- 连接数很大时 `strand` 数量上升，内存与调度开销随之增加。
- 跨线程投递需要生命周期管理，常用投递加 `shared_ptr` 捕获。
- 选择依据是每连接状态大小与每请求计算量，两者差异大时收益明显。

### 8.19（场景）如何定位异步服务的性能瓶颈？

- 先看事件循环的占用率，判断瓶颈在 I/O 等待还是处理器计算。
- 统计每个处理器的耗时分布，找出长尾处理器。
- 检查分配次数与分配器命中率，短操作上分配常是主因。
- 检查锁与 `strand` 的争用，确认串行区间是否过长。
- 观察队列深度与背压是否生效，避免内存随负载增长。
- 分阶段替换缓冲、批处理与分配器，并保持基准可重复。
- 基准需固定连接数、消息大小与并发度，否则不同轮次的数据不可比。

### 8.20 协程与回调在性能上有什么差别？

- 协程帧一次分配，包含局部变量与挂起状态，嵌套深度增加时帧数线性增长。
- 回调链把状态分散到各处理器的捕获中，分配次数随链长增加。
- 协程的恢复同样经执行器派发，与回调调用路径接近。
- 协程把异常路径与清理逻辑集中在同一段代码，遗漏较少。
- 协程帧较大时内存占用高于回调，长连接上需评估每连接的帧大小。
- 协程版本的编译开销与调试信息体积通常高于回调版本。

## 9. Asio 实战

### 9.1 异步 TCP 服务器的接受循环如何组织？

- 一个 `acceptor` 持续发起 `async_accept`，每次完成后再发起下一次，形成循环。
- 新连接以移动方式交给会话对象，`acceptor` 不持有已建立的连接。
- 会话在堆上分配，用 `shared_ptr` 管理，处理器捕获该指针保证存活。
- 接受循环可以写成协程，异常经 `co_spawn` 的完成令牌统一上报。
- `acceptor` 关闭后挂起的接受以 `operation_aborted` 结束，协程在挂起点抛出异常，循环随之退出，该异常需与真实错误区分。
- 接受路径本身开销很小，瓶颈通常出现在每连接的读写与解析上。

```cpp
asio::awaitable<void> accept_loop(tcp::acceptor& acc) {
  for (;;) {
    tcp::socket sock(co_await asio::this_coro::executor);
    co_await acc.async_accept(sock, asio::use_awaitable);
    asio::co_spawn(acc.get_executor(),
        session(std::move(sock)), asio::detached);
  }
}
```

### 9.2 为什么 `async_accept` 要传入一个套接字对象？

- 传入套接字的重载把新连接直接放进调用方提供的对象，所有权清晰。
- 不传套接字时由处理器接收新建对象，调用方需自行管理其移动与销毁。
- 提前构造套接字可复用执行器与已设置的选项，减少一次构造。
- 传入的套接字必须已打开且未连接，否则接受立即失败。
- 协程形式下每轮构造新套接字，不能复用上一轮已连接的套接字。
- 接受失败后该套接字的状态由实现定义，重新构造更稳妥。

### 9.3 会话对象的生命周期如何管理？

- 用 `shared_ptr` 管理，每个在途处理器捕获一份，最后一个处理器释放时销毁。
- 处理器中捕获裸 `this` 需要额外的存活保证，否则对象可能先于处理器销毁。
- 关闭流程先停止读写，再由最后一个处理器触发析构。
- 循环引用会把会话永久留住，定时器与会话之间不要互相持有强引用。
- 定时器回调中可用 `weak_ptr` 检查会话是否已销毁。
- 析构时取消未完成操作并关闭套接字，已排队的处理器仍会被调用。
- 会话对象与其缓冲区合并分配，可减少每连接一次以上的堆调用。

### 9.4 半关闭与 `eof` 如何处理？

- 对端关闭写方向时，读操作以 `asio::error::eof` 结束，连接此时仍可写。
- 需要继续发送响应时，收到 `eof` 后停止读取，写完再关闭整个连接。
- `socket.shutdown(shutdown_send)` 发送 FIN，读方向依然可以接收数据。
- 收到 `eof` 后继续读取会反复得到同一错误，读循环应在此结束。
- 写方向已关闭后再写返回管道类错误，具体错误值由平台决定。
- HTTP/1.1 中 `Connection: close` 依赖半关闭界定响应结束。

### 9.5 为什么同一套接字不能并发写？

- 并发 `async_write` 会让两条消息的字节交错，破坏帧边界。
- 底层 `async_write_some` 不保证一次写完，整个写序列必须串行化。
- 正确结构是写队列加单一在途写操作，完成后从队列取下一项。
- 读与写可以并发，两者操作同一套接字的不同方向。
- 队列长度需要上限，否则慢客户端会使内存增长失控。
- 关闭连接时应清空队列，避免向已关闭的套接字继续写入。
- 队列中的消息应已完成序列化，写操作只引用其内存，不再修改内容。

### 9.6 写队列如何实现背压？

- 队列达到上限时暂停读取，不再发起新的读操作。
- 队列回落到低水位后恢复读取，两个阈值形成滞回，避免频繁抖动。
- 背压也可以上抛给业务层，例如直接拒绝新请求并返回过载错误。
- 定时器可检测队列长时间不下降，判定客户端异常并关闭连接。
- 队列用双端队列保存已序列化的消息，在途期间不得修改其内容。
- 背压只作用于当前连接，单个慢客户端不影响其他连接。

### 9.7 HTTP 请求的读取如何界定边界？

- 先读到头部结束标记，再按 `Content-Length` 读取定长请求体。
- 头部边界用 `async_read_until` 配合动态缓冲处理，同时限制头部总长度。
- 没有 `Content-Length` 时按分块传输编码逐块读取。
- 单行长度与头部字段数量都要设上限，防止内存被畸形请求耗尽。
- 请求体读取期间不能再解析下一个请求，流水线请求需要排队。
- 头部解析结束后，缓冲中剩余的字节要交给体解析，否则会丢失已到达的数据。
- Boost.Beast 提供完整解析器，独立 Asio 不包含 HTTP 解析设施。

### 9.8 为什么不能用 `async_read_until` 读整个请求体？

- `read_until` 以分隔符为界，请求体是二进制数据，可能包含该分隔符。
- 请求体长度由头部字段给出，与分隔符无关。
- 依赖分隔符会把后续请求一并读入，导致解析位置错位。
- 大请求体场景下动态缓冲持续扩容，内存不可控。
- 正确顺序是先解析头部，再按长度读取定长数据。
- 分块编码需要按块长度逐段读取，不能一次读完整个体。

### 9.9 发送响应时如何组织缓冲区？

- 头部与体分别构造，再用分散聚合一次写出，减少中间复制。
- 小响应可合并进一个缓冲区，减少系统调用次数。
- 大文件分块发送，避免把整个文件读入内存。
- 缓冲区必须在写操作完成前保持有效，临时对象不能直接作为写来源。
- `keep-alive` 场景需要准确的 `Content-Length`，否则对端无法判断边界。
- 发送完成后按 `Connection` 请求头决定继续读下一请求还是关闭连接。

### 9.10 超时应该加在哪一层？

- 连接建立、请求读取、业务处理、响应写分别设置超时。
- 只设一个总超时会掩盖阶段差异，排障时难以定位。
- 超时由 `steady_timer` 驱动，到期后取消相关操作或直接关闭套接字。
- 超时值过短会造成误杀，需要与对端行为和历史分布匹配。
- 关闭连接是取消 I/O 最直接的方式，代价是无法区分超时的具体原因。
- 计时在操作开始时重置，避免多次操作累积到同一超时预算。
- 同一连接共用定时器时，阶段切换需要重新设置到期时间。

```cpp
asio::steady_timer timer(co_await asio::this_coro::executor);
timer.expires_after(std::chrono::seconds(10));
timer.async_wait([&sock](asio::error_code ec) {
  if (!ec) sock.close();
});
co_await asio::async_read(sock, asio::buffer(buf), asio::use_awaitable);
timer.cancel();
```

### 9.11 优雅关闭的顺序是什么？

- 先关闭 `acceptor`，停止接受新连接。
- 再通知现有连接不再接受新请求，处理完在途请求。
- 等待写队列清空，然后关闭发送方向。
- 等待读方向收到 `eof` 或超时，再关闭套接字。
- 所有处理器结束后停止事件循环，最后汇合工作线程。
- 顺序颠倒会丢失在途响应，或让退出流程永久等待。

### 9.12 关闭时仍在途的处理器如何清理？

- 关闭套接字使挂起操作以 `operation_aborted` 完成，处理器仍会被调用。
- 处理器先检查错误码，再决定是否继续处理剩余数据。
- 捕获 `shared_ptr` 的处理器释放后对象自然销毁，无需手工删除。
- 定时器到期必定调用处理器，会话销毁前应取消定时器或改用弱引用。
- 事件循环析构前必须让处理器执行完，否则清理逻辑来不及运行。
- 关闭流程应有整体超时兜底，避免个别连接阻塞进程退出。
- 处理器中未捕获的异常会从 `run` 逸出，线程入口需要捕获并记录。

### 9.13 `io_context::stop` 之后还能重启吗？

- 可以，调用 `restart` 后再次 `run` 会继续处理队列中的处理器。
- `stop` 不取消未完成操作，套接字状态保持不变。
- 停止期间新提交的处理器进入队列，等待下次 `run`。
- 重启后已过期的定时器会立即到期，可能触发补偿逻辑。
- 关闭流程中通常先取消操作再停止，避免重启后执行过期回调。
- 析构 `io_context` 前必须确保没有线程仍在 `run` 中。

### 9.14 连接池需要维护哪些状态？

- 每个后端地址的空闲连接列表与在途连接计数。
- 连接的空闲起始时间，用于淘汰长时间空闲的连接。
- 每条连接的健康状态与最近一次错误。
- 池的上限、获取超时与排队策略。
- 连接能否复用取决于协议，HTTP/1.1 需要 `keep-alive` 才可复用。
- 池自身的操作在 `strand` 上串行，避免并发修改列表。
- 池满时排队需要超时，否则请求会无限等待。

### 9.15 如何检测池中的失效连接？

- 取出连接时检查套接字是否可读，可读通常意味着对端已关闭或已有数据。
- 发送前无法完全确认健康，只能在首次使用时处理错误并重建连接。
- 设置空闲超时，超过时限未使用的连接直接关闭。
- 对端主动关闭时下一次写入返回管道类错误，捕获后重建。
- 重试需要幂等保证，非幂等请求不能盲目重发。
- 主动健康检查会增加额外负载，按业务对延迟的容忍度决定是否启用。

### 9.16 `async_connect` 的超时与重试如何实现？

- `async_connect` 依次尝试解析出的多个端点，全部失败才返回错误。
- 超时用定时器触发，关闭套接字使连接尝试结束。
- 重试采用指数退避并设置次数上限，避免故障期间重试放大。
- 连接成功后关闭定时器，避免其到期误关新连接。
- 连接失败的套接字不能复用，重试前重新构造。
- 名称解析本身可能阻塞，应使用异步解析接口。

### 9.17 大量连接下的资源边界在哪里？

- 每条连接占用一个文件描述符，受进程与系统上限约束。
- 每连接的内存包括套接字对象、读写缓冲、会话状态与发送队列。
- 缓冲区总量随连接数线性增长，缓冲区大小需要按业务调低。
- 定时器与 `strand` 各占额外内存，数量与连接数同阶。
- 描述符耗尽时接受操作返回错误，应暂停接受并记录告警。
- 内存上限应显式配置，超出时拒绝新连接，不再继续分配。
- 描述符上限可通过系统参数调整，调整后内存与调度开销随之上升。

### 9.18 异步代码的错误如何分类与记录？

- 区分对端正常关闭、协议错误、超时、资源耗尽与内部缺陷。
- 判断依据是错误码的类别与值，字符串描述不用于分支。
- 每条连接的记录包含连接标识、所处阶段与错误码。
- 高频错误需要限流记录，避免日志本身成为瓶颈。
- 内部缺陷保留异常信息与调用位置，正常关闭不必记为错误。
- 错误分类决定重试策略，混在一起会导致无限重试。

### 9.19 Windows 与 POSIX 上写失败有何差异？

- POSIX 上向已关闭连接写入可能触发 `SIGPIPE`，默认终止进程。
- 忽略 `SIGPIPE` 后写操作返回 `EPIPE`，Asio 将其转换为 `broken_pipe`。
- Windows 没有该信号，写失败直接返回错误码。
- 服务器应在启动时忽略该信号，或使用平台提供的逐次抑制手段。
- 关闭套接字后再写属于使用错误，返回值由平台决定。
- 错误处理统一按 `error_code` 判断，不依赖平台差异。

### 9.20（场景）把回调式服务器迁移到协程需要哪些步骤？

- 先把共享状态收拢到会话对象，明确所有权与生命周期。
- 为每条回调链编写等价协程，用 `co_await` 取代回调嵌套。
- 用取消状态与定时器补齐取消与超时路径。
- 统一错误处理，协程内用异常或元组，边界处集中转换。
- 保留旧实现的测试与压测基准，按连接类型分批迁移。
- 迁移后复核线程模型，确认 `strand` 与执行器语义没有改变。
- 保留新旧实现的切换开关，出现异常时可按连接灰度回退。

## 10. P2300 基础

### 10.1 sender 描述什么？

- sender 描述一段异步工作及其可能的完成方式，本身不执行，也不持有执行状态。
- 它可被连接，携带完成签名，并能与其他 sender 组合成更大的 sender。
- 是否可重复连接由具体类型决定，普通 sender 不保证可以连接多次。
- 真正执行所需的存储放在操作状态中，sender 只描述如何产生该状态。
- sender 通常可复制，复制只复制描述，不复制执行进度。
- 执行上下文由完成调度器查询给出，不写死在 sender 类型里。

### 10.2 receiver 提供什么？

- 三个完成通道：`set_value`、`set_error`、`set_stopped`，一次操作只走其中一个。
- `get_env` 返回环境，环境提供调度器、停止令牌与域等查询。
- receiver 只在连接之后使用，其生命周期需要覆盖操作状态。
- 完成后继续使用 receiver 属于未定义行为，适配器会结束该操作状态。
- receiver 可按值保存，也可按引用保存，取决于连接时的写法。
- 完成调用可能发生在任意线程，线程安全由下游的处理逻辑保证。

```cpp
struct env_t {};
struct int_receiver {
  using receiver_concept = std::execution::receiver_t;
  void set_value(int v) && noexcept { store(v, {}); }
  void set_error(std::exception_ptr e) && noexcept { store(0, e); }
  void set_stopped() && noexcept { store(0, {}); }
  auto get_env() const noexcept { return env_t{}; }
};
```

### 10.3 sender 的完成签名如何表达？

- 完成签名由 `completion_signatures` 列出，每个通道对应一个标签类型。
- 常见形式为成功携带值、失败携带异常指针、停止不携带参数。
- 签名只声明可能发生的完成方式，不表示每条路径都会出现。
- 下游适配器依据签名推导自己的签名，签名不匹配会在编译期失败。
- 查询结果依赖环境，同一 sender 在不同环境下的签名可以不同。
- `sender_in` 概念用于判断某环境下签名是否可计算，是约束连接的前提之一。

```cpp
namespace ex = std::execution;
using work_sigs = ex::completion_signatures<
    ex::set_value_t(int),
    ex::set_error_t(std::exception_ptr),
    ex::set_stopped_t()>;
```

### 10.4 `set_value`、`set_error`、`set_stopped` 如何分工？

- `set_value` 表示成功，可携带零个或多个结果值。
- `set_error` 表示失败，通常携带异常指针，也可携带自定义错误类型。
- `set_stopped` 表示被取消或提前结束，不携带任何值。
- 三个通道互斥，一次操作只会经过其中一个。
- `then` 只在 `set_value` 时调用函数，其余通道原样传给下游。
- 停止与失败语义不同，下游可据此区分正常取消与真实错误。

### 10.5 `connect` 做了什么？

- 把 sender 与 receiver 绑定，返回操作状态，执行所需的存储在此时创建。
- 连接只做构造，不启动工作，也不允许在连接期间产生完成调用。
- sender 与 receiver 的所有权按值或按引用转移，方式由具体 sender 决定。
- 签名不满足 receiver 的要求时，连接在编译期失败。
- 返回的操作状态不可复制，必须就地构造并保持存活。
- 连接后不调用 `start` 则永不完成，操作状态销毁时释放资源。

```cpp
auto op = ex::connect(std::move(work), int_receiver{});
ex::start(op);
```

### 10.6 `start` 有什么约束？

- 每个操作状态只能调用一次 `start`，重复调用属于未定义行为。
- `start` 不抛异常，也不返回值，错误经 `set_error` 报告。
- 调用后可能立即完成，也可能稍后在其他线程完成。
- `start` 返回之前完成是允许的，调用方不能假设完成发生在返回之后。
- 调用方需保证操作状态存活到完成，销毁时机由上游适配器规定。
- `start` 内部阻塞会阻塞调用线程，与异步语义相悖。

### 10.7 operation_state 的职责是什么？

- 保存一次执行的全部状态，包括子操作状态、已接收的值与缓冲。
- 提供 `start`，并保证三个完成通道之一恰好发生一次。
- 生命周期从 `connect` 开始，到完成且下游释放为止。
- 不可复制、不可移动，地址稳定，因为完成回调可能保存其内部指针。
- 析构时释放资源，未 `start` 就析构不产生任何完成调用。
- 操作状态可以嵌套，外层持有内层，整体构成树状结构。

### 10.8 为什么 `start` 可能同步完成？

- 操作无需等待时，例如已在目标执行上下文上或数据已就绪，完成可以就地发生。
- 同步完成使调用栈可能变深，大量同步子操作会累积递归深度。
- 适配器必须处理完成早于 `start` 返回的情况，不能把启动当作完成的前置事件。
- 下游代码需假设完成可能在任何时刻发生，包括 `start` 内部。
- 需要强制异步时，先用 `schedule` 切到调度器再继续。
- 同步完成不违反语义，只是对栈深度与重入提出了要求。

### 10.9 `then` 的语义是什么？

- 在 `set_value` 时调用给定函数，用返回值构成新的值继续向下传递。
- 函数抛出的异常被捕获，转为 `set_error` 携带异常指针。
- `set_error` 与 `set_stopped` 直接透传，不调用该函数。
- 它不引入新的执行上下文，函数在完成线程上就地执行。
- 返回类型决定下游签名，返回 `void` 时值列表为空。
- 函数中做耗时计算会占用完成线程，需要换线程时先用 `transfer`。

```cpp
// pool 为已就绪的执行上下文，main_sched 为目标调度器
ex::sender auto work =
    ex::schedule(pool.get_scheduler())
    | ex::then([] { return 42; })
    | ex::transfer(main_sched);
```

### 10.10（辨析）`let_value` 与 `then` 的差别在哪里？

- `then` 的函数返回普通值，`let_value` 的函数返回 sender。
- `let_value` 会等待返回的 sender 完成，再把它的完成作为整体完成。
- 传入的值在内部 sender 执行期间保持存活，可按引用捕获而无需额外复制。
- 内部 sender 的错误与停止直接成为整体结果。
- 适合先取得资源再用资源执行下一步的链式场景。
- 内部 sender 的执行上下文由它自己决定，不自动继承外层。

### 10.11 `when_all` 的完成规则是什么？

- 连接并启动全部子 sender，全部结束后才完成。
- 任一子操作以 `set_error` 完成时，整体以该错误完成，其余子操作收到停止请求。
- 只有停止而没有错误时，整体以 `set_stopped` 完成。
- 全部成功时，结果值是各子 sender 值的拼接，按连接顺序排列。
- 子操作数量与签名在编译期确定，结果类型是元组。
- 子操作全部同步完成时，整体完成可能发生在 `start` 内部。

### 10.12 `when_any` 的取消行为是什么？

- 第一个完成的子操作决定整体结果，其余子操作被请求停止。
- 结果用 variant 承载，类型是各子 sender 值类型的并集。
- 被停止的子操作不保证立刻结束，其操作状态仍需存活到各自完成。
- 共享状态要等所有子操作结束后才能释放，不响应的子操作会推迟整体收尾。
- 停止经停止令牌传播，子操作可以选择忽略。
- 适合超时、竞速与故障转移等场景。

### 10.13 `schedule` 与 `transfer` 的分工是什么？

- `schedule(sched)` 返回一个 sender，在该调度器上启动并立即以空值完成。
- `transfer(sndr, sched)` 把上游的完成转移到指定调度器，再交给下游。
- 前者用于进入某个执行上下文，后者用于切换已有链的完成位置。
- `transfer` 引入一次调度开销，跨线程时包含一次队列往返。
- `transfer` 只改变完成位置，不改变值的类型与数量。
- 调度器查询决定下游默认执行位置，`transfer` 显式覆盖该查询。

### 10.14 `bulk` 的语义是什么？

- 对上游的值执行 shape 次函数调用，索引从 0 到 shape 减 1。
- 执行发生在完成调度器上，允许分块并行，具体划分由实现定义。
- 提案要求该函数不抛异常，异常路径不参与语义定义。
- 上游的错误与停止直接透传，不执行函数。
- 适合对已就绪的数据做并行处理，不适合包含阻塞 I/O 的工作。
- shape 很大时，下游要等全部调用结束才收到完成。

### 10.15 `split` 解决什么问题？

- 让一个 sender 的结果被多个下游共享，源只执行一次。
- 返回的 sender 可被多次连接，每个下游收到相同的值。
- 首次连接触发执行，后续连接等待同一结果。
- 结果需要被复制给每个下游，值类型因此需要可复制。
- 所有下游都完成或放弃后，共享状态才释放。
- 适合把一次昂贵计算广播给多个消费者。

### 10.16 `sync_wait` 的用途与限制是什么？

- 在调用线程阻塞，等待 sender 完成后返回结果。
- 成功时返回可选的元组，`set_stopped` 时返回空。
- 错误类型为异常指针时，重新抛出该异常。
- 内部用 `run_loop` 驱动完成，不能在完成线程上再调用它，否则形成死锁。
- 只应在测试、脚本或线程边界使用，不适合放在事件循环内部。
- 阻塞期间停止请求无法生效，超时控制需要外部机制。

```cpp
auto r = ex::sync_wait(std::move(work));
if (r) {
  int v = std::get<0>(*r);
}
```

### 10.17 `run_loop` 提供什么？

- 一个可手动驱动的事件循环，`run` 处理队列直到 `finish` 被调用。
- `get_scheduler` 返回对应的调度器，可用于 `schedule` 与 `transfer`。
- `finish` 之后 `run` 返回，队列中剩余任务不再执行。
- 常用于测试与 `sync_wait` 的实现，也用于把回调接口桥接为 sender。
- 单线程模型，跨线程投递需要额外同步。
- 一个实例的 `run` 通常只调用一次，重复使用的语义按该类型的说明确定。

### 10.18 sender 与 receiver 的生命周期由谁保证？

- 连接后 sender 的存活需求取决于具体类型：有的按值保存，有的保存引用。
- 右值 sender 通常被移动进操作状态，之后原对象不再需要。
- 左值 sender 被按引用保存时，必须存活到操作完成。
- `let_value` 传入的值由外层操作状态持有，覆盖内部 sender 的执行期。
- 共享状态由操作状态或引用计数管理，释放时机由适配器决定。
- 左右值混用时以类型说明为准，不能假设连接过程一定复制。

### 10.19 停止令牌如何传播？

- 环境中的 `get_stop_token` 查询提供停止令牌，下游可读取。
- 停止请求经令牌通知，操作通过轮询或注册回调响应。
- `when_all`、`when_any`、`transfer` 等适配器把令牌传给子操作。
- 适配器可创建自己的停止源，使部分子操作被单独停止。
- `set_stopped` 是停止的结果通道，与错误通道分开。
- 不响应停止的操作会延迟整体完成，停止机制是协作式的。

### 10.20（场景）sender/receiver 与 Asio 集成到什么程度？

- P2300R10 已进入 C++26，标准库提供 sender/receiver 与基础调度设施。
- 与 Asio 的集成属于提案与实验实现，尚未成为标准的一部分。
- 现有实验实现提供把 Asio 执行器适配为调度器的桥接，可用于 `schedule` 与 `transfer`。
- 桥接的做法是把完成回调投递到执行器，再由 `set_value` 通知下游。
- 协程与 sender 之间也存在桥接，适配层由库提供，不在标准之内。
- 两者共存时把边界放在 I/O 发起处，避免两套取消模型混用。

## 11. P2300 算法

### 11.1 组合算法如何保证子操作状态的生命周期？

- 组合算法在 connect 时构造一棵 operation state 树，外层状态直接持有或引用内层状态。
- start 从外层向内层传播，只有所有子操作完成后，外层才允许释放整棵树。
- `when_all` 与 `when_any` 在首个错误或停止后仍保留子状态，直到每个子操作报告完成。
- 同步完成会让析构发生在 start 的调用栈内，完成函数返回后不得再访问外层成员。
- 自定义算法若在子操作完成前销毁其状态，回调或 I/O 会访问悬空内存。
- 组合算法的资源释放顺序应与构造顺序相反，并覆盖 value、error、stopped 三条路径。

### 11.2 then 的续体为什么可能不在调用线程运行？

- `then` 只附加续体，不插入调度，f 在触发上游完成的执行代理上运行。
- 上游若通过 `schedule` 或 I/O 完成，线程可能是事件循环线程、池线程或内核回调线程。
- 同一条链的不同段可以使用不同 scheduler，线程身份由实现定义。
- f 中访问调用线程的局部状态时，需要确认该状态仍然存活且未被并发修改。
- 阻塞 f 会占住完成线程，可能拖慢同一上下文的其它操作。
- 需要固定线程时，在 f 之前使用 `transfer` 或把续体提交到目标 executor。

### 11.3（陷阱）then 中访问共享状态为什么仍可能竞争？

- `then` 不提供互斥，也不保证不同链在同一条线程上运行。
- 上游 sender 可以在任意执行代理完成，f 跟随该代理，线程身份由实现定义。
- 捕获引用时，被引用对象的生命周期至少要覆盖完成时刻，异步链常比局部作用域长。
- 多个续体并发写同一对象仍需要同步，sender 组合不会消除数据竞争。
- 需要串行化时，把续体放到 strand 或单线程 scheduler 上执行。
- 不能根据线程名或调用栈推断完成位置，应以 scheduler 的语义为准。

### 11.4 let_value 如何保证传入值活到内层 sender 完成？

- `let_value` 把输入值复制或移动到自己的 operation state，再调用 f 生成内层 sender。
- f 收到的是这些存储值的引用，内层 sender 可以继续引用它们，直到内层完成。
- 外层完成等待内层完成，因此值的生命周期覆盖整个嵌套操作。
- f 抛异常或 connect 抛异常时，外层以 `set_error` 完成，已存储的值随状态析构。
- 上游 error 或 stopped 时不会调用 f，也不会创建内层 sender。
- 值若持有独占资源，应通过移动传入，避免复制失败或额外开销。

### 11.5（代码阅读）let_value 返回捕获引用的 sender 有什么风险？

```cpp
auto make_work() {
    std::string table = "users";
    return ex::schedule(pool.get_scheduler())
         | ex::let_value([&table] {
               return ex::then(ex::schedule(io.get_scheduler()),
                               [&table] { return load(table); });
           });
}
```

- `make_work` 返回时局部变量 `table` 销毁，两个 lambda 都持有悬空引用。
- sender 是惰性的，返回时尚未 connect 或 start，引用不会自动延长生命周期。
- 即使 `let_value` 保存了自己的值参数，也不会保存外部捕获的引用。
- 改为按值捕获 `table`，或让状态由 `std::shared_ptr` 持有。
- connect 可能复制 sender，引用成员被复制后仍指向同一已销毁对象。
- 这类错误通常在异步完成后才暴露，开启地址检查工具有助于定位。

### 11.6 when_all 在子操作失败后为什么还要等待全部结束？

- 首个 error 或 stopped 会请求其余子操作停止，但停止是协作的，子操作可能仍在运行。
- 复合 operation state 持有所有子状态，提前析构会让仍在运行的回调访问悬空内存。
- `when_all` 通常用计数器等待每个子操作报告完成，最后一个到达时才向外完成。
- 有 error 时保存首个错误并优先报告 error；只有 stopped 时才报告 stopped。
- 后续 error 不覆盖首个错误，但仍会请求停止并参与计数。
- 这种 join 语义保证结构化并发，代价是慢速子操作会推迟整体完成。

### 11.7（辨析）when_all 的「全部完成」是否等于「全部成功」？

- 不等于；全部完成只表示没有子操作仍在运行。
- 只有全部以 `set_value` 完成，才产生拼接后的值。
- 首个 error 决定错误通道，后续 error 被忽略。
- error 优先于 stopped；存在 error 时不报告 stopped。
- 停止请求是协作的，子操作可以忽略，`when_all` 仍等待其结束。
- 调用方必须处理 error 与 stopped，不能只按值路径解包。

### 11.8 when_any 的结果类型为什么需要 variant？

- 各输入 sender 的值类型可以不同，统一的结果类型必须能容纳任意一个分支。
- 常见实现用 variant 保存 decayed tuple，索引对应胜者的类型。
- 访问结果前要判别索引，不能假设胜者一定是第一个参数。
- error 与 stopped 也是完成通道，variant 之外还需要对应的错误与停止路径。
- 胜者完成后其余子操作收到停止请求，但状态保留到它们结束。
- `when_any` 不在 P2300R10 的标准设施表内，结果形态以所用实现为准。

### 11.9（陷阱）when_any 中其余操作未结束就销毁状态会怎样？

- 胜者完成只表示结果已确定，不表示其他子操作已经停止。
- 立即析构复合 operation state 会销毁仍在运行的子状态，行为未定义。
- 停止回调可能在稍后的线程执行，捕获的对象必须仍然有效。
- 正确实现要等所有子操作报告完成，再释放共享状态。
- 资源清理应放在各子操作的完成路径，不能只依赖胜者。
- 需要严格等待全部结束时，使用 `when_all` 而不是 `when_any`。

### 11.10 transfer 为什么不能把阻塞调用移走？

- `transfer` 只移动完成位置，不移动上游工作的起点。
- 阻塞读取仍在原线程执行，`transfer` 要等读取完成后才生效。
- 要移动阻塞调用本身，应把调用放进 `schedule` 的目标上下文。
- `transfer` 引入一次队列跳转，跨线程时包含入队与唤醒成本。
- 调度失败时以 `set_error` 完成，停止请求可能使调度以 `set_stopped` 完成。
- P2300R10 把这一算法命名为 `continues_on`，`transfer` 是早期修订的名称。

### 11.11 transfer 的调度点发生在链的哪个位置？

- `transfer` 的调度点在源 sender 完成之后、下游接收值之前。
- 上游的启动位置不变，阻塞调用仍占用原来的执行代理。
- 目标 scheduler 负责把续体排入队列，下游在目标代理上看到值。
- 调度失败以 `set_error` 完成；停止请求可能使调度以 `set_stopped` 完成。
- 需要移动的是整段工作的起点时，应在链首使用 `schedule`，而不是 `transfer`。
- 多次 `transfer` 会累积队列往返，链路过长时延迟明显。

### 11.12 schedule 的完成签名是什么？

- `schedule(sch)` 在 sch 的执行代理上以 `set_value()` 完成，不带值。
- 调度失败时以 `set_error(std::exception_ptr)` 完成。
- 接收者停止令牌已经请求时，可以 `set_stopped` 而不执行工作。
- `run_loop` 的 schedule 不会失败，只有 value 与 stopped 两条路径。
- sender 与 operation state 只在执行上下文存活期间有效。
- 常作为链的起点，后接 `then`、`let_value` 或 `bulk`。

### 11.13（陷阱）schedule 之后一定在新线程执行吗？

- scheduler 只承诺执行代理，不承诺新建线程。
- 单线程事件循环的 scheduler 会在循环线程执行。
- 某些 scheduler 可能直接在调用线程完成，具体行为由实现定义。
- 线程身份由实现定义，不能把 scheduler 当作线程池大小的同义词。
- 在 scheduler 线程上阻塞会拖住同一上下文的其它工作。
- 需要线程亲和性时，应显式使用对应上下文并查阅其文档。

### 11.14 bulk 的索引与执行代理如何对应？

- `bulk` 为区间 `[0, shape)` 的每个索引调用 f，索引与上游值一起传入。
- 默认实现顺序遍历索引，执行代理与上游完成代理相同。
- 执行资源可以定制 `bulk`，把索引区间分块并分配给多个代理。
- 并行划分由实现定义，f 不能假设相邻索引在同一线程执行。
- 索引类型与 shape 的符号性要一致，避免负数或溢出导致越界。
- f 抛异常时停止后续调用并以 `set_error` 完成，已执行的副作用不会回滚。

### 11.15（陷阱）bulk 中写入共享容器为什么可能竞争？

- 标准不保证 f 一定串行，执行资源可以并行化 `bulk`。
- 多个索引同时向同一容器插入元素会破坏内部状态。
- 即使当前实现串行，也不能把偶然行为当作接口保证。
- 按索引预分配槽位，或让每个索引写独立分区。
- 需要汇总时使用原子计数或额外的归约步骤，`bulk` 本身不提供归约。
- 捕获引用时要确认整个 `bulk` 完成前对象一直存活。

### 11.16 split 的共享结果在什么时候释放？

- `split` 的共享状态保存源 sender、缓存结果与接收者列表。
- 源只启动一次，结果在完成后保留，供后续连接复用。
- 所有接收者都完成或放弃后，共享状态才可以释放。
- 单个接收者先完成不会销毁缓存，否则后到者拿不到结果。
- 缓存大对象会延长内存占用，必要时存 `std::shared_ptr<const T>` 并控制生命周期。
- 若源一直不完成，共享状态与所有等待者都会一直存在。

### 11.17（场景）split 适合哪些场景？

- 多个下游需要同一份昂贵结果，例如启动时读取配置。
- 消费者出现时间不同，后到者仍需拿到已完成的结果。
- 源操作是单次且不可重复，例如一次性握手。
- 结果较大时缓存 `std::shared_ptr<const T>`，避免每个消费者复制。
- 消费者需要独立重试或独立取消时，不适合共享同一个 `split`。
- 源操作长期不完成会使所有等待者无法结束，需要超时与取消策略。

### 11.18（陷阱）split 的取消如何影响其他消费者？

- 单个接收者请求停止不应直接取消共享源，否则其他接收者会失去结果。
- 实现通常把停止请求与源操作分离，源继续为其余接收者运行。
- 全部接收者都停止后是否取消源，由实现定义。
- 源完成后才连接的接收者仍可能收到缓存结果或 stopped。
- 停止回调的生命周期必须覆盖共享状态，不能随单个接收者销毁。
- 需要每个消费者独立取消时，应使用独立 sender 而不是 `split`。

### 11.19（实现）如何组合「读取-计算-回写」的链？

```cpp
auto work = ex::schedule(io.get_scheduler())
          | ex::then([] { return read_request(); })
          | ex::transfer(cpu.get_scheduler())
          | ex::then([](Request req) { return compute(std::move(req)); })
          | ex::transfer(io.get_scheduler())
          | ex::then([](Result result) { write_response(std::move(result)); });
```

- 起点在 I/O 上下文，读取不阻塞计算线程。
- `transfer` 把计算段放到 CPU 上下文，完成后再回到 I/O。
- 每段的值按移动传递，避免大对象复制。
- 任一阶段 error 或 stopped 会短路后续 `then`，资源由各 operation state 清理。
- 最后才用 `sync_wait` 或 co_await 等待，链内部不阻塞。
- 线程数与队列深度要匹配负载，否则 `transfer` 只是把等待转移到别处。

### 11.20（辨析）sender 算法组合与手写回调相比有什么代价？

- 组合在编译期展开，类型变长，编译时间与代码体积增加。
- operation state 往往直接存储子状态，栈占用与对象大小上升。
- 某些算法需要分配或同步，`split` 与 `when_all` 的共享状态更明显。
- 运行时开销主要来自调度跳转、原子操作与状态存储，算法本身通常可以优化。
- 调试时调用栈跨多个模板层，错误信息较长。
- 收益是生命周期与取消路径由算法统一管理，手写回调容易漏掉分支。

## 12. P2300 调度器

### 12.1 scheduler 概念的最小要求是什么？

- scheduler 必须可复制、可比较相等，复制、析构与相等比较都不抛异常。
- `schedule(sch)` 返回一个 sender，调度调用本身不抛异常。
- 相等只表示两个句柄指向同一执行资源，不表示同一线程或同一优先级。
- `schedule` sender 的完成调度器查询在可查询时应等于 sch。
- scheduler 是轻量句柄，不拥有执行上下文，也不保证新建线程。
- 标准不要求公平、可取消或固定并发度，这些性质由具体实现决定。

### 12.2（辨析）scheduler 与 execution context 的职责如何划分？

- 执行上下文拥有线程、队列、定时器等资源，scheduler 只是访问这些资源的句柄。
- 复制 scheduler 不延长上下文寿命，scheduler 失效不等于上下文停止。
- scheduler、sender 与 operation state 必须先于上下文销毁。
- scheduler 相等用于判断是否同一资源，不同上下文产生的 scheduler 不相等。
- 上下文负责启动、停止与 join，scheduler 只负责提交工作。
- `run_loop` 是执行资源，`get_scheduler()` 返回与之关联的句柄。

### 12.3 schedule 的完成路径有哪些？

- 正常路径在目标执行代理上以 `set_value()` 完成。
- 入队失败或资源已经停止时，以 `set_error(std::exception_ptr)` 完成。
- 接收者的停止令牌已经请求时，可以 `set_stopped` 而不执行工作。
- `run_loop` 的 schedule 不会失败，只有 value 与 stopped 两条路径。
- operation state 在完成前必须存活，`start` 只负责入队。
- 完成可能晚于 `start` 很久，不能假设调度是同步的。

### 12.4（陷阱）scheduler 比执行上下文活得久会怎样？

- scheduler 成为悬空句柄，`schedule` 访问已销毁的队列，行为未定义。
- 把 scheduler 捕获到长生命周期对象不会延长上下文寿命。
- 关闭顺序应为停止接收新工作、排空队列、join 线程、销毁上下文。
- `run_loop` 在队列非空或仍在运行时析构会调用 terminate。
- 静态对象或全局对象中的 scheduler 尤其危险，析构顺序难以控制。
- 用所有权对象封装上下文，scheduler 只在其作用域内使用。

### 12.5 run_loop 的线程模型是什么？

- `run_loop` 维护线程安全的先进先出队列，自身不创建线程。
- `run()` 在调用线程循环取出工作并执行。
- 任意线程都可以通过 scheduler 向队列投递工作。
- 队列为空时 `run()` 阻塞，`finish()` 唤醒并使其退出。
- 一个 `run_loop` 只能由一个线程调用一次 `run()`。
- 适合主线程事件循环、单线程执行上下文与需要线程亲和性的场景。

### 12.6（实现）如何包装一个单线程上下文？

```cpp
class single_thread_context {
public:
    single_thread_context() : thread_([this] { loop_.run(); }) {}

    ~single_thread_context() {
        loop_.finish();
        thread_.join();
    }

    auto get_scheduler() noexcept { return loop_.get_scheduler(); }

private:
    std::execution::run_loop loop_;
    std::jthread thread_;
};
```

- `loop_` 声明在 `thread_` 之前，保证线程对象先析构并完成 join。
- 构造函数启动线程执行 `run()`，此后队列中的工作都在该线程运行。
- 析构先调用 `finish()` 再 join，已入队的工作会被排空。
- scheduler 按值返回，句柄不拥有 `run_loop`。
- `finish()` 之后不再投递新工作，否则可能访问已销毁队列。
- 异常退出路径也要 join，避免 `std::thread` 析构时终止进程。

### 12.7 finish 为什么不取消已经排队的工作？

- `finish()` 只把状态置为 finishing，`run()` 继续取队列直到为空。
- 已入队工作已经持有 operation state，直接丢弃会让等待者永远收不到完成。
- `finish()` 可以在 `run()` 之前调用，此时 `run()` 仍会排空队列后返回。
- `finish()` 只能调用一次，重复调用行为未定义。
- 需要取消排队工作时应使用停止令牌，让每个操作自行以 `set_stopped` 结束。
- 结束循环与取消操作是两件事，前者不改变后者的完成语义。

### 12.8（陷阱）run_loop 析构时仍有排队工作会怎样？

- 析构在队列计数非零或仍在运行时调用 terminate。
- 必须先 `finish()`、等待 `run()` 返回，并确保队列为空。
- 只调用 `finish()` 而不 join，仍可能在线程运行时销毁对象。
- 使用 detached 线程无法保证析构顺序。
- 用成员声明顺序或作用域守卫保证 join 先于析构。
- 排队操作的 operation state 仍需其所有者保持存活。

### 12.9 run_loop 上的 schedule 如何响应取消？

- schedule sender 在出队时检查接收者的停止令牌。
- 已请求停止则以 `set_stopped` 完成，不执行值完成。
- 检查发生在执行代理上，不是入队时。
- 停止请求与出队竞争时，最终结果由实现定义的时序决定。
- 已出队的操作可能已经通过检查，停止只能协作。
- 被停止的操作仍占用队列位置，直到出队才释放。

### 12.10 static_thread_pool 的基本模型是什么？

- 固定数量的线程从共享队列取工作，通过 `get_scheduler()` 暴露 scheduler。
- 常见实现还提供停止与 join 接口，具体名称由实现决定。
- 工作可以在任意池线程运行，链的后续段可能换线程。
- 公平性、工作窃取与队列策略由实现定义。
- P2300R10 未标准化该类型，标准库可用性由实现与版本决定。
- 适合 CPU 密集型任务，不适合长时间阻塞的调用。

### 12.11（陷阱）在 static_thread_pool 上执行阻塞调用会怎样？

- 所有池线程阻塞后，队列无人消费，后续任务饥饿。
- 阻塞 I/O、sleep、等待 future 都会占用池线程。
- 线程数固定时，少量阻塞调用就能把并发度降到零。
- 把阻塞工作放到独立上下文，计算池只做 CPU 工作。
- 取消通常不能中断已经进入的阻塞系统调用。
- 监控队列等待时间比只看 CPU 利用率更容易发现该问题。

### 12.12（辨析）static_thread_pool 与普通线程池的差异是什么？

- 底层都是线程加队列，本章关注 scheduler 接口与完成语义。
- P2300 风格的池把提交表达为 sender，完成通过 receiver 传递。
- 生命周期与停止需要和 sender 链配合，不能只销毁池对象。
- 不重复讨论互斥量、条件变量与内存序基础。
- 线程池大小、队列策略与任务分配仍由实现决定。
- 选择池时先看任务是否阻塞，再看核数与尾延迟目标。

### 12.13（场景）CPU 密集任务应如何选择 scheduler？

- 使用与硬件线程数匹配的专用池，避免与 I/O 线程争抢。
- I/O 完成回调中只做轻量解析，重计算通过 `transfer` 移到 CPU 池。
- 计算完成后再次 `transfer` 回 I/O 线程，再写 socket 或更新界面。
- `bulk` 可以把规则一致的计算分摊到多个执行代理。
- 避免在计算池中同步等待 I/O，容易形成循环等待。
- 用队列等待时间与尾延迟验证池大小，不能只看平均利用率。

### 12.14 事件循环中的长任务如何影响调度延迟？

- 单线程事件循环一次只执行一个任务，长任务会推迟同一循环上的所有续体。
- 多线程运行同一循环时，长任务占用一个工作线程，降低可用并发度。
- `schedule` 的完成虽然已入队，仍要等当前任务让出线程。
- 定时器精度受同一循环影响，长任务会让到期回调晚执行。
- 队列长度增长时，尾延迟比平均延迟更早暴露问题。
- 把 CPU 密集段 `transfer` 到独立池，只把结果送回循环。
- 用循环排队延迟与任务执行时长共同判断是否需要拆分任务。

### 12.15 时间调度为什么不属于 P2300R10？

- P2300R10 只定义 scheduler 与 `schedule`，没有时间参数。
- 没有标准定时器、时钟类型或 sleep sender。
- 定时调度由实现或后续提案提供，接口与可用性由版本决定。
- 可移植做法是用自定义 scheduler 包装平台定时器。
- 超时通常使用 `steady_clock`，墙上时间使用 `system_clock`。
- 不能假设 `schedule` 会延迟、周期执行或按 deadline 排序。

### 12.16（实现）定时器 sender 的基本结构是什么？

- 定时器服务维护按 deadline 排序的队列，由单线程等待最近到期项。
- sender 保存 deadline 与目标 scheduler，connect 时生成 operation state。
- operation state 向队列注册节点，并保存唤醒后要投递的目标上下文。
- 到期后把完成投递到目标 scheduler，而不是在定时器线程直接运行续体。
- 取消时从队列移除节点或标记为已取消，已触发则等待完成路径收敛。
- 用原子状态保证到期与取消竞争时恰好完成一次。

### 12.17（陷阱）定时器在错误线程完成会怎样？

- 续体默认在触发完成的线程运行，可能不是 I/O 线程。
- 共享状态在没有同步的情况下被两个线程访问，产生数据竞争。
- 到期后 `transfer` 到目标 scheduler，或使用 strand 串行化。
- 定时器回调本身要短，不能阻塞等待其它线程。
- 取消与到期可能并发，状态机要能处理两种顺序。
- 线程归属由实现定义，不能靠 sleep 或线程名猜测。

### 12.18 周期任务如何避免漂移？

- 下一次 deadline 基于上一次 deadline 加周期，而不是当前时间加周期。
- 处理时间超过周期时，要决定跳过错过的周期或补执行。
- 补执行必须有上限，否则积压会持续增长。
- 使用 `steady_clock`，避免系统时间调整造成跳变。
- 取消时同时停止下一次注册，避免残留定时器。
- 抖动与漂移是两个指标，分别度量单次偏差与长期累计偏差。

### 12.19 把 io_context 包装成 scheduler 时如何保证线程归属？

- 包装层的 `schedule` sender 应把完成投递到 io_context，而不是在调用线程直接 `set_value`。
- 使用 post 或 dispatch 时，要明确是否允许在 io_context 线程内同步完成。
- 多线程 run 的 io_context 没有固定线程，续体可能落到任意一个运行线程。
- 需要串行化时在包装层绑定 strand，而不是假设 `schedule` 提供互斥。
- Boost.Asio 与独立 Asio 的命名空间不同，实验性适配的可用性由版本决定。
- io_context 与 work guard 的生命周期必须覆盖所有挂起操作。

### 12.20（实现）Asio 定时器与取消的边界是什么？

```cpp
asio::steady_timer timer(ctx);
timer.expires_after(std::chrono::milliseconds(100));
timer.async_wait([&](std::error_code ec) {
    if (ec == asio::error::operation_aborted) {
        return;
    }
    on_timeout(ec);
});
timer.cancel();
```

- `expires_after` 设置相对超时，`expires_at` 设置绝对时间。
- `cancel()` 让未完成的等待以 `operation_aborted` 结束。
- 处理器只调用一次，取消与到期竞争时仍只有一个结果。
- 定时器对象必须存活到处理器执行，不能先于 io_context 销毁。
- 多线程 io_context 下用 strand 保护共享状态。
- Boost.Asio 与独立 Asio 的 API 基本一致，细节差异由版本决定。

## 13. P2300 取消与错误

### 13.1 三个完成通道为什么必须互斥？

- 一个 operation state 表示一次操作，完成即结束，不能再次进入。
- `set_value`、`set_error` 与 `set_stopped` 分别对应成功、失败与取消，语义不同。
- 重复完成会让 receiver 被移动或销毁后再次使用，行为未定义。
- 适配器依赖恰好一次完成来释放子状态与注销回调。
- 完成函数应为 noexcept，异常逃出会 terminate，无法作为第二条完成路径。
- 需要报告多个结果时，应把结果放入一个值或错误对象，而不是多次完成。

### 13.2（辨析）set_stopped 与 set_error 的边界在哪里？

- stopped 是协作取消的结果，不是故障；error 表示操作失败。
- stopped 通常没有负载，error 可以携带诊断与重试信息。
- `sync_wait` 对 stopped 返回空 optional，对 error 抛出异常。
- `when_all` 存在 error 时优先报告 error，只有 stopped 时才报告 stopped。
- 把超时或业务失败编码成 stopped 会丢失诊断信息。
- 把取消编码成 error 会让调用方把正常控制流当成异常处理。

### 13.3 取消请求与取消完成有什么区别？

- `request_stop` 置位停止状态并调用已注册回调，操作可能仍在运行。
- `set_stopped` 是操作观察到取消后主动放弃的结果。
- 取消是协作式的，标准不提供强制终止线程的手段。
- 停止请求可以在 start 前、运行中或完成之后到达，完成之后的请求应被忽略。
- 操作必须在释放资源后完成，并且只完成一次。
- 不响应停止请求的操作仍然可以正常以 `set_value` 完成。

### 13.4 停止令牌如何到达 sender？

- receiver 的环境携带停止令牌，sender 通过环境查询取得。
- sender 通常在 connect 或 start 时保存令牌副本。
- 令牌共享停止状态，`request_stop` 之后所有副本都能观察到。
- 不需要取消时可以使用不可停止的令牌类型。
- 组合算法可以为子操作创建独立 stop_source，并把父请求转发给它们。
- 令牌类型影响完成签名，是否可能发送 stopped 由类型决定。

### 13.5 stop_source、stop_token 与 stop_callback 的职责如何划分？

- `stop_source` 拥有停止状态，`request_stop` 发出停止请求。
- `stop_token` 观察状态，提供 `stop_requested` 与 `stop_possible`。
- `stop_callback` 注册反应，析构时注销。
- 一个 source 可以发出多个 token，多个 callback 可以注册到同一状态。
- `request_stop` 返回本次调用是否是第一次请求。
- callback 在 `request_stop` 的调用线程同步执行。

### 13.6（陷阱）stop_callback 在哪个线程执行？

- 在调用 `request_stop` 的线程执行。
- 构造时若状态已经停止，在构造线程立即执行。
- 不保证在操作所属执行器的线程运行。
- 回调需要线程安全，不能假设单线程访问。
- 析构会等待正在执行的回调结束。
- 回调中获取锁时，要与 `request_stop` 路径保持一致的锁序。

### 13.7 stop_callback 中阻塞或抛异常会怎样？

- 阻塞会延长 `request_stop` 的处理时间，延迟其它回调的执行。
- 等待的线程若正是请求停止的线程，可能形成死锁。
- `request_stop` 为 noexcept，异常逃出回调通常导致 terminate。
- 回调应只置位、投递或唤醒，不做耗时操作。
- 需要分配的资源应在注册回调之前准备好。
- 用原子标志加 post 把实际处理移到安全线程。

### 13.8 停止请求为什么可能被忽略？

- sender 的完成签名不包含 `set_stopped` 时，它不会报告停止。
- receiver 环境中的令牌可能是不可停止类型，请求根本无法发出。
- 阻塞系统调用通常不会因为停止令牌而中断，操作要等调用返回。
- 操作可能只在启动时检查一次令牌，运行中不再轮询。
- scheduler 可以不支持停止，已排队工作仍会按原计划执行。
- 组合算法只能转发请求，不能替子操作强制放弃，超时仍需外层兜底。

### 13.9 then 对 set_stopped 的处理是什么？

- `then` 只处理 `set_value`，stopped 原样传给下游。
- `then` 不提供清理回调，资源应由 operation state 的 RAII 管理。
- f 抛出异常产生 error，不会变成 stopped。
- f 运行期间收到的停止请求不会被 `then` 自动中断。
- f 需要周期检查令牌，或把工作拆成可取消的步骤。
- 下游收到 stopped 后不应再期待值。

### 13.10 let_value 对错误与停止如何短路？

- 上游 error 或 stopped 时不调用 f，直接转发。
- 内层 sender 不会在错误路径创建。
- f 抛异常或 connect 抛异常时以 `set_error` 完成。
- 内层 error 或 stopped 原样向外转发。
- 输入值保存在 `let_value` 的 operation state 中，直到内层完成才销毁。
- 内层 operation state 由外层状态持有，析构时统一清理。

### 13.11 when_all 如何聚合取消？

- 每个子操作看到内部 stop_source 的令牌。
- 父 receiver 请求停止时，回调把请求转发给所有子操作。
- 任一子操作 error 或 stopped 时，请求其余子操作停止。
- 所有子操作结束后才向外完成，避免销毁仍在运行的状态。
- 有 error 时优先 error，只有 stopped 时才 `set_stopped`。
- 后续 error 不会覆盖首个错误。

### 13.12 when_any 同时完成时如何决定胜者？

- 多个子操作可能同时完成，复合状态用一次原子交换决定谁写入结果。
- 先完成写入者获胜，其余完成信号被忽略，顺序不确定。
- 胜者的 value、error 或 stopped 决定整体通道，败者的错误不会覆盖。
- 败者仍会收到停止请求，但其操作状态要保留到各自完成。
- 父停止请求会传播给所有子操作，包括尚未完成的胜者候选。
- 标准设施状态需要核对版本，参考实现的胜者规则如上。

### 13.13 transfer 与取消如何交互？

- 停止令牌随 receiver 环境进入调度段。
- 已排队但未执行的 schedule 可能直接以 `set_stopped` 完成。
- 已开始执行的上游工作不会被 `transfer` 强制中断。
- 取消可能发生在源线程，完成发生在目标线程，共享状态需要同步。
- 目标调度器不支持停止时，取消只能延后生效。
- 要保证恰好一次完成，避免源与目标同时报告。

### 13.14（实现）自定义 sender 如何响应停止？

- connect 保存 receiver 与停止令牌，构造 operation state。
- start 注册 `stop_callback`，回调请求底层 I/O 取消或置位标志。
- 在安全点检查标志，放弃未完成的工作。
- 完成前注销回调，避免回调访问已销毁状态。
- 用状态机保证 value、error 与 stopped 只出现一次。
- 先释放缓冲区与句柄，再调用完成函数。

### 13.15 取消与 operation state 生命周期如何配合？

- 停止请求不会缩短 operation state 的生命周期。
- 必须等操作真正结束并完成，才能销毁状态。
- 提前析构会让回调或 I/O 访问悬空内存。
- 完成函数可能同步销毁 operation state，调用后不得再访问成员。
- 共享状态用引用计数时，回调持有一份强引用。
- 取消路径与正常路径共用同一套清理逻辑。

### 13.16 错误类型与 exception_ptr 的边界是什么？

- `set_error` 可以携带 `std::exception_ptr`、`std::error_code` 或自定义错误。
- `sync_wait` 把 error 转成异常，`std::error_code` 通常转成 `std::system_error`。
- 组合算法用 variant 保存不同错误类型。
- `std::exception_ptr` 通过 `std::current_exception` 或 `std::make_exception_ptr` 构造。
- 错误对象需要可复制或可移动，具体约束由算法决定。
- receiver 的 `set_error` 不应抛出，否则 terminate。

### 13.17（场景）超时取消如何组合？

- 用 `when_any` 竞争业务操作与定时器。
- 定时器先完成时，请求业务操作停止，并返回超时错误或标记。
- 业务操作先完成时，取消定时器，避免多余唤醒。
- 两个分支都要保留到败者结束，不能提前销毁。
- 超时是 error 还是 value 由接口语义决定，不能混用 stopped。
- 定时器与业务操作使用同一停止域，确保取消能够传播。

### 13.18 资源清理与完成顺序如何安排？

- 资源在 operation state 构造时获取，在析构时释放。
- 完成前先停止底层操作、注销回调、关闭句柄。
- 调用 `set_value`、`set_error` 或 `set_stopped` 后不再访问 operation state 成员。
- 清理函数声明为 noexcept，异常路径应终止而不是泄漏。
- 多个资源的释放顺序与获取顺序相反。
- 共享所有权用 RAII 包装，避免分支遗漏。

### 13.19（陷阱）析构时仍有 stop_callback 注册会怎样？

- 回调捕获 this，operation state 销毁后触发即访问悬空对象。
- `stop_callback` 析构会等待正在执行的回调结束，并注销注册。
- 必须在销毁捕获状态之前注销回调，通常由 operation state 的析构顺序保证。
- 源 stop_source 可能比操作活得久，不能依赖源先销毁来避免回调。
- 回调与析构并发时需要互斥或引用计数。
- 成员声明顺序要保证回调对象先于被捕获状态析构。

### 13.20（代码阅读）错误路径是否发生了二次完成？

```cpp
void on_done(std::error_code ec) {
    if (ec) {
        ex::set_error(std::move(rcvr), ec);
    }
    ex::set_value(std::move(rcvr));
}
```

- ec 非空时先调用 `set_error`，随后仍执行 `set_value`，完成两次。
- 第一次完成后 receiver 可能已经销毁，第二次使用悬空对象。
- 每个分支必须 return，或用 else 保证互斥。
- 用状态标志或原子变量确保只完成一次。
- 同步完成与异步完成路径都要覆盖。
- 测试应同时覆盖成功、错误与取消三种路径。

## 14. P2300 与协程

### 14.1（辨析）P2300R10 是否提供 task 类型？

- P2300R10 定义 sender、receiver、scheduler 与组合算法，不定义协程任务类型。
- C++26 的 `std::execution::task` 由 P3552R3 引入，不属于 P2300R10 本身。
- task 本身是 sender，可以 connect 与 start，也可以被另一个 task 协程 co_await。
- 实验库常自带 task，接口与完成签名由实现决定。
- 不要把 task 的调度器亲和性当成所有 sender 的性质。
- 使用前检查头文件、命名空间与特性宏。

### 14.2 task 的惰性启动如何体现？

- 调用返回 task 的协程只创建协程帧，不执行函数体。
- `initial_suspend` 返回 `std::suspend_always`，协程停在起点。
- connect 把协程句柄移入 operation state，start 才恢复协程。
- task 只能移动，connect 需要右值，避免多个 operation state 共享同一帧。
- 未 connect 的 task 析构时销毁协程帧。
- 一个 task 只能启动一次。

### 14.3 task 的 promise 需要哪些成员？

- `get_return_object` 构造 task 并保存协程句柄。
- `initial_suspend` 与 `final_suspend` 控制启动与结束。
- `return_value` 或 `return_void` 保存结果。
- `unhandled_exception` 保存 `std::exception_ptr`，最终转为 `set_error`。
- `await_transform` 把 sender 或 awaitable 转成可等待对象。
- `final_suspend` 把完成交给 receiver 或 continuation。

### 14.4 co_await sender 的桥接过程是什么？

- `await_transform` 识别 sender，把它包装成 awaitable。
- `await_ready` 返回 false，协程准备挂起。
- `await_suspend` 连接 sender 与内部 receiver，并启动操作。
- receiver 在 `set_value` 时保存值并恢复协程。
- `await_resume` 返回值；error 重新抛出；stopped 不恢复。
- sender 的 operation state 必须存活到完成，通常由 awaitable 持有。

### 14.5 awaitable 的三个接口分别做什么？

- `await_ready` 决定是否跳过挂起。
- `await_suspend` 接收协程句柄，安排恢复。
- `await_resume` 在恢复后产生 co_await 表达式的值。
- `await_suspend` 可以返回 void、bool 或另一个协程句柄。
- awaitable 对象本身要存活到 `await_resume`。
- 协程被销毁时不会调用 `await_resume`，资源需由 awaitable 的析构处理。

### 14.6 await_suspend 返回 bool 与返回句柄有何差异？

- 返回 void 表示协程挂起，控制权返回调用者或恢复者。
- 返回 bool 时，true 表示挂起，false 表示立即恢复。
- 返回协程句柄表示对称转移，直接恢复目标协程而不增加栈。
- 返回 false 时，`await_suspend` 不得再安排异步恢复。
- 返回句柄时目标必须有效，并且最终恢复当前协程。
- 对称转移适合 task 链，能避免递归 resume 持续增长调用栈。

### 14.7（陷阱）await_suspend 返回 false 后异步操作又完成会怎样？

- 协程已经立即恢复并继续执行，之后回调再次 resume 会重复进入。
- 同一个协程帧不能被两个线程同时 resume。
- 状态机要区分未挂起、已挂起与已完成三种状态。
- 启动操作应放在确定挂起的路径，或让同步完成走同步分支。
- 用原子标志防止二次恢复。
- 测试要覆盖立即完成与延迟完成两种 sender。

### 14.8 set_error 如何变成协程异常？

- receiver 把错误存入 awaitable 的结果区，再恢复协程。
- `await_resume` 重新抛出 `std::exception_ptr`。
- `std::error_code` 通常转成 `std::system_error`，其它错误按 task 规则抛出。
- 异常可以被协程内的 catch 捕获，否则进入 `unhandled_exception`。
- task 的 `unhandled_exception` 再以 `set_error(std::exception_ptr)` 完成。
- task 的错误签名不包含该异常类型时，可能调用 terminate。

### 14.9 set_stopped 如何终止协程？

- 停止完成不恢复协程，awaitable 通知 task 结束。
- task 销毁协程帧，局部变量按构造逆序析构。
- 外层 receiver 收到 `set_stopped`，不进入 catch。
- stopped 之后不得再访问协程帧或 awaitable。
- 资源清理依赖帧内 RAII，不依赖异常路径。
- 停止是正常控制流，不是错误。

### 14.10 task 的取消如何传播？

- task 从 receiver 环境取得停止令牌。
- 令牌类型不同时，task 内部创建 stop_source 并转发停止。
- co_await 的 sender 通过环境看到同一停止请求。
- 挂起期间收到停止，协程被销毁并以 `set_stopped` 完成。
- 运行期间收到停止，需要协程主动检查或由被等待操作响应。
- task 不强制终止正在执行的函数。

### 14.11 task 的调度器亲和性是什么？

- task 在 receiver 提供的启动 scheduler 上开始。
- co_await 完成后默认回到同一 scheduler。
- 被等待 sender 在别的线程完成时，task 会切回启动 scheduler。
- 需要把工作放到别处时，先 co_await 一个在目标 scheduler 上启动的 sender。
- 某些 scheduler 可以配置为无亲和性，具体行为由实现定义。
- scheduler 的生命周期必须覆盖 task 的整个执行过程。

### 14.12（陷阱）在 task 中调用 sync_wait 会怎样？

- `sync_wait` 阻塞当前线程，并驱动一个 `run_loop`。
- 当前线程若正是 task 依赖的 scheduler 线程，队列无人驱动，形成死锁。
- 即使不立即死锁，也会占用池线程，降低并发度。
- 在协程内应使用 co_await，不要嵌套阻塞等待。
- `sync_wait` 只放在程序边界或测试入口。
- 嵌套 `sync_wait` 可能违反前向进展保证。

### 14.13 sync_wait 为什么要求 sender 只有一种值完成签名？

- `sync_wait` 的返回类型是可选的 tuple，只能对应一种值类型组合。
- 若 sender 有多种值签名，返回类型需要 variant，调用方应先统一值类型。
- 值完成时返回 engaged optional；error 时抛出；stopped 时返回空 optional。
- `std::error_code` 会转换为 `std::system_error`，`std::exception_ptr` 会重新抛出。
- `sync_wait` 在当前线程运行 `run_loop`，阻塞到完成或停止。
- 它只适合边界处使用，不适合事件循环线程。

### 14.14（场景）协程中如何串联多个异步操作？

```cpp
ex::task<Report> build_report() {
    auto header = co_await load_header();
    auto body = co_await load_body();
    auto stats = co_await compute_stats(header, body);
    co_return Report{std::move(header), std::move(body), stats};
}
```

- 顺序 co_await 表达依赖关系，后一步等待前一步完成。
- 无依赖操作可以用 `when_all` 并发，再解包结果。
- error 以异常短路，未捕获时 task 以 `set_error` 完成。
- 取消沿 task 的停止令牌传播到每个被等待操作。
- 大对象按移动传递，避免复制。
- 协程内不调用 `sync_wait`。

### 14.15 Asio awaitable 与 P2300 task 有何差异？

- `asio::awaitable<T>` 是 Asio 的协程返回类型，依赖 executor 与 `co_spawn`。
- `use_awaitable` 把 Asio 异步操作的完成令牌转成 co_await 结果。
- Boost.Asio 与独立 Asio 的命名空间不同，可用设施由版本决定。
- P2300 task 是 sender，强调 scheduler 亲和性与完成签名。
- Asio 的取消走 cancellation slot，P2300 走停止令牌，语义不能直接等同。
- 两者的桥接属于实验实现，跨模型混用要明确线程与生命周期。

### 14.16（辨析）awaitable 与 sender 的抽象差异是什么？

- awaitable 是协程协议，必须由协程消费；sender 是惰性异步描述。
- sender 有编译期完成签名，awaitable 只有 `await_resume` 的返回类型。
- sender 可以组合成图，awaitable 通过 co_await 线性书写。
- sender 可以多播或单播，awaitable 通常一次性。
- 错误与停止在 sender 中是通道，在协程中转为异常或不恢复。
- 桥接层负责把完成签名映射为协程结果。

### 14.17 协程帧分配消除在什么条件下才能发生？

- 编译器只有在能证明协程帧不会逃逸、且分配大小与对齐在编译期确定时才可能消除分配。
- 分配消除不是标准保证，是否发生由实现与优化选项决定。
- 协程参数按值复制进帧，引用参数仍指向原对象，影响逃逸分析。
- 自定义 `operator new` 或 allocator 会改变分配路径，可能阻止消除。
- 帧在 `final_suspend` 后由 task 或 operation state 销毁。
- 帧销毁后，指向局部变量的引用全部悬空。

### 14.18（陷阱）协程局部变量在恢复后是否仍然有效？

```cpp
ex::task<void> run() {
    std::string name = "db";
    co_await ex::schedule(pool.get_scheduler());
    use(name);
}
```

- `name` 是协程帧的一部分，挂起期间不会销毁，恢复后仍然有效。
- 引用调用方局部变量则不同，调用方返回后即悬空。
- 按引用捕获到 lambda 再交给异步操作，风险相同。
- 成员函数协程捕获 this 时，对象必须活到协程结束。
- 需要跨协程共享时使用值捕获或 `std::shared_ptr`。
- 帧销毁后继续使用引用是未定义行为。

### 14.19 task 与 sender 组合的代价是什么？

- 每个 task 有一次协程帧分配，可能被消除但不保证。
- 每次 co_await 可能引入一次调度跳转，用于维持亲和性。
- 对称转移减少栈增长，但仍有恢复与状态保存成本。
- 模板组合增加编译时间与代码体积。
- 调试栈跨协程帧，定位比同步代码困难。
- 收益是顺序代码表达复杂异步流程，错误与取消路径集中。

### 14.20（实现）final_suspend 如何交回结果？

```cpp
struct final_awaiter {
    bool await_ready() noexcept { return false; }

    std::coroutine_handle<> await_suspend(
        std::coroutine_handle<promise_type> h) noexcept {
        auto& p = h.promise();
        if (p.continuation) {
            return p.continuation;
        }
        return std::noop_coroutine();
    }

    void await_resume() noexcept {}
};
```

- `final_suspend` 在协程体结束后执行，结果已经写入 promise。
- 返回 continuation 实现对称转移，恢复等待者。
- 没有 continuation 时返回 `noop_coroutine`，避免恢复已结束的帧。
- `await_ready` 返回 false，确保 final_suspend 挂起，帧由所有者销毁。
- 不能在 `await_suspend` 中销毁当前帧，否则返回的句柄悬空。
- 结果存储与 continuation 的同步由 promise 或 operation state 保证。

## 15. P2300 与 Asio 集成

### 15.1（辨析）sender 与 Asio 异步操作在发起时机上有何差异？

- Asio 异步操作在调用发起函数时立即开始，完成令牌只决定结果如何交付。
- sender 是惰性描述，`connect` 生成操作状态，`start` 之后才开始执行。
- 立即发起要求调用方在调用点保证参数与对象存活；sender 允许先构造、后启动。
- sender 可以重复连接，配合 `split` 让多个接收器共享一次执行结果。
- 集成层把 sender 当作 Asio 操作发起时，要显式保存操作状态并调用 `start`。
- 惰性带来组合空间，也带来构造后未启动的失败模式，接口应避免暴露未启动的 sender。

### 15.2（实现）如何用 `async_initiate` 把 sender 暴露给 Asio 调用方？

- 启动函数接收处理器，把 sender 移动进接收器，`connect` 之后调用 `start`。
- 操作状态不能放在启动函数的栈上，`start` 返回后它仍要存活到完成。
- 接收器的 `set_value` 调用处理器，`set_error` 与 `set_stopped` 转成错误码或异常。
- 处理器只允许调用一次，接收器要防止两条完成路径同时触发。
- 立即完成的 sender 要在接收器里用 `post` 投递，避免在启动函数内回调。
- 令牌的返回类型由 `async_result` 决定，适配层不需要按令牌分支。

### 15.3 完成签名如何映射为 sender 的完成签名？

- 一组 `void(std::error_code, std::size_t)` 通常映射为 `set_value(std::size_t)` 加 `set_error(std::exception_ptr)`。
- 也可以保留 `set_value(std::error_code, std::size_t)`，由使用方判断错误，避免异常开销。
- 取消完成映射为 `set_stopped`，不要折叠进 `set_error`，否则 `when_all` 的停止语义失效。
- 多组签名映射为多个 `set_value` 重载，接收器要接受全部形式。
- 映射要保证每条路径只触发一次完成，错误之后不能再发值。
- 签名决定 `then` 等算法的参数形式，改动会波及整条链的类型。

### 15.4（陷阱）`start` 内同步完成会带来什么问题？

- sender 允许在 `start` 返回前完成，调用方若假定异步，会在发起函数内被回调。
- 同步完成会让上层状态在建好之前被使用，出现空指针或半初始化状态。
- 深层同步完成会累积调用栈，链长与栈深相关。
- 修正方式是在接收器里把完成投递到执行器，用 `post` 推迟调用处理器。
- 用 `dispatch` 时当前线程已在执行器上下文中仍可能同步执行，严格要求异步时不能使用。
- 测试要覆盖会立即完成的 sender，例如没有子操作的 `when_all`。

### 15.5 关联执行器如何转换为 scheduler？

- scheduler 需要提供 `schedule()`，返回在该执行资源上完成的 sender。
- 包装 Asio 执行器时，`schedule()` 内部调用 `post`，在投递的函数里完成 `set_value`。
- 包装对象要能被复制并保持相等比较语义，仅保存执行器句柄不足以支持调度判断。
- 处理器上的关联执行器与 scheduler 是两套机制，转换时不要互相替代。
- 转换层要处理执行器已停止的情况，否则 `schedule()` 产生的 sender 永不完成。
- 每次转换都引入一次投递，热路径上应缓存包装结果。

### 15.6 `any_io_executor` 与具体执行器在集成层如何取舍？

- 具体类型在编译期已知，scheduler 包装可以去掉虚调用，适合库内部。
- `any_io_executor` 自 Asio 1.18 与 Boost 1.74 起提供，擦除执行器类型，便于在运行期更换执行资源，适合公共接口。
- 擦除带来一次间接调用，部分实现还会分配状态对象。
- 泛型算法按 scheduler 类型实例化，擦除之后模板实例数量下降，二进制体积可控。
- 协程恢复依赖执行器类型，擦除后的恢复路径无法在编译期特化。
- 公开接口使用 `any_io_executor`，内部按具体类型实现，是常见的分层方式。

### 15.7 `strand` 如何映射为串行执行的 sender？

- `strand` 保证同一链上的处理器不并发执行，映射为 scheduler 后 `schedule()` 在其上投递。
- 每个连接一个 strand，映射为每条链一个 scheduler，串行范围与连接一致。
- strand 只提供互斥，不提供完成顺序，`when_all` 的子操作完成次序仍不确定。
- 同一 strand 上的多个 sender 并行启动时，完成仍可能交错。
- 跨 strand 共享状态需要额外同步，串行范围之外没有保护。
- strand 包装对象要随执行器一起存活，销毁后投递的任务不会执行。

### 15.8 停止请求如何转换为取消信号？

- sender 的停止请求通过接收器环境中的停止令牌传播，Asio 的取消通过 `cancellation_slot` 传播。
- 桥接时把停止令牌的回调注册到槽位，或把槽位中的取消处理器转成停止请求。
- 两个方向都要处理：外部取消进入 sender，sender 的 `set_stopped` 转成 `operation_aborted`。
- 停止请求是协作式的，接收器只发出请求，底层操作仍要主动检查。
- 注册的回调要能解除，否则操作结束后令牌仍持有已销毁对象的指针。
- 取消类型 `terminal`、`partial`、`total` 在 sender 一侧没有对应概念，映射时要选定策略。

### 15.9 如何让包装的接收器响应取消？

- 接收器在构造时从环境取得停止令牌，并把回调注册到取消槽位。
- 槽位回调只设置一个原子标志或调用底层 `cancel()`，不在回调里做耗时操作。
- 完成路径要检查标志，已请求取消时以 `set_stopped` 结束而不是 `set_value`。
- 操作结束后要清除槽位回调，避免信号持有已销毁的接收器。
- 接收器要可移动且完成函数为 `noexcept`，否则适配层无法通过编译期检查。
- 取消与正常完成可能竞争，最终只允许一条路径调用完成函数。

### 15.10（条款）两套模型在完成次数与完成通道上如何对齐？

- sender 的接收器必须恰好被完成一次，Asio 的处理器同样只能调用一次，见 `[exec.recv]`。
- sender 有三条完成通道，Asio 的处理器只有一条，错误与取消都要编码进参数或异常。
- sender 的完成可以在任意执行资源上发生，处理器的执行位置由关联执行器决定。
- sender 的错误用 `exception_ptr` 承载，Asio 用 `error_code`，映射时要注意信息损失。
- 两套模型都不承诺完成的线程，线程约束要由执行器或 scheduler 显式表达。
- 标准只规定 sender 一侧，Asio 一侧的约定由库文档规定。

### 15.11 把 sender 接入完成令牌需要哪些映射？

```cpp
template <typename Handler>
struct to_handler {
    Handler h;
    void set_value(std::error_code ec, std::size_t n) noexcept { std::move(h)(ec, n); }
    void set_error(std::exception_ptr) noexcept {
        std::move(h)(asio::error::operation_aborted, 0);
    }
    void set_stopped() noexcept {
        std::move(h)(asio::error::operation_aborted, 0);
    }
    // 环境查询略
};
```

- 接收器的 `set_value` 把结果转给处理器，参数顺序要与完成签名一致。
- `set_error` 与 `set_stopped` 没有对应的成功通道，转成错误码或异常。
- 接收器要转发关联执行器、取消槽位与分配器查询，否则绑定信息在桥接后丢失。
- 完成函数声明为 `noexcept`，异常不能穿过 `start`。
- 处理器按值或按移动捕获，调用之后不再触碰。
- 桥接层要保证操作状态的生命周期覆盖完成，不能依赖栈对象。

### 15.12 如何把 `then` 链包装成一个异步操作？

- 先用 `then`、`let_value` 把业务步骤组合成 sender，再把末端接收器接到处理器。
- 操作状态由堆上的共享对象持有，接收器持有其 `shared_ptr`，并避免与处理器形成环引用。
- 启动前保存操作状态，`start` 之后不能让它离开作用域。
- 完成时先取出结果，再销毁操作状态，避免在接收器调用栈内析构自身。
- 取消要接到链上的停止源，只取消末端操作不会中断已经开始的上游步骤。
- 包装后的类型对调用方只暴露完成签名，sender 类型不外泄。

### 15.13（场景）`io_context` 与 `static_thread_pool` 如何在同一进程内协作？

- `io_context` 负责 I/O 就绪事件，`static_thread_pool` 负责计算任务，两者各自提供 scheduler。
- 用 `transfer` 把完成切到线程池，计算结束后再切回 I/O 执行器投递响应。
- 线程池的 `schedule()` 每次投递都可能在不同线程执行，共享状态要加保护。
- `io_context` 停止后，切回它的 sender 不会推进，退出顺序要先停计算再停 I/O。
- 两个执行资源各自运行事件循环，阻塞调用不能在任一循环线程上执行。
- 线程数按计算占比设置，线程池过大只会增加竞争。

### 15.14 跨执行器恢复时哪些上下文会丢失？

- 线程局部存储不会随完成迁移，切换执行器后读到的是目标线程的值。
- 关联执行器只影响完成位置，不影响操作发起位置。
- 请求上下文要显式挂在操作状态或处理器上，不能依赖栈上局部变量。
- 目标执行资源已停止时，投递的完成不会执行，链上的后续步骤停滞。
- `transfer` 每次引入一次调度，切换频繁时延迟上升。
- 追踪上下文要随接收器一起传递，跨线程后仍能关联到同一条链路。

### 15.15 如何把 `deferred` 操作接成 sender？

- `deferred` 保存发起动作，调用时才真正开始；sender 也是惰性描述，二者形态接近。
- 把 `deferred` 操作包成 sender，需要在 `start` 时用令牌调用它，并在完成时通知接收器。
- 完成令牌选择 `as_tuple` 可以保留错误码，便于映射为值通道。
- 操作状态的生存期由 sender 的操作状态管理，不能在 `start` 返回后销毁。
- 取消能力取决于原操作是否接受槽位，包装层无法凭空增加取消。
- 这类包装适合渐进迁移，先把回调式接口变成 sender，再统一组合。

### 15.16（实现）如何测试集成适配层？

- 用记账 scheduler 统计投递次数，确认完成确实发生在目标执行资源上。
- 用只允许完成一次的接收器包装，重复完成时立即失败。
- 覆盖四条路径：值完成、错误完成、停止完成、`start` 内同步完成。
- 在完成函数里断言线程标识，核对与 scheduler 的约定一致。
- 用假 I/O 对象制造同步完成，验证适配层没有在发起函数内回调。
- 检查类型：完成签名变化时，接收器与处理器的参数映射应同步更新。

### 15.17 错误与停止信号如何映射才不丢信息？

- `set_error` 携带的 `exception_ptr` 若被压成 `error_code`，原始异常类型与消息会丢失。
- `error_code` 转 `exception_ptr` 再转回，需要保留 category 与 value。
- 取消完成映射为 `operation_aborted` 时，超时与主动取消无法区分，需要附加来源。
- 错误完成后不能再发值，接收器只接受一次完成。
- 未知异常要转成 `set_error(std::current_exception())`，不能穿过 `noexcept` 边界。
- 映射表要写进文档，调用方据此判断哪些错误可以重试。

### 15.18（辨析）把实验性集成接口写进公共头文件有什么代价？

- 实验接口可能随提案修订调整，公共头文件会把不稳定性扩散到全部使用方。
- P2300R10 已进入 C++26，但 Asio 与它的互操作不在标准内，接口由实现定义。
- 头文件暴露实验类型会拉长编译时间，并使模板实例数量上升。
- 版本升级可能改变完成签名或命名空间，二进制接口随之破裂。
- 隔离方式是在实现文件内使用实验接口，对外只暴露稳定类型。
- 需要跨版本兼容时，用适配层加条件编译，并在文档中标注支持的版本区间。

### 15.19 集成层如何隔离版本差异？

- 把版本相关代码收敛到一个适配文件，其余代码只依赖项目内定义的类型。
- 用特性检测宏或构建配置选择实现，不在业务代码里散布条件编译。
- Asio 与 Boost.Asio 的头文件路径、命名空间不同，构建系统要能区分两者。
- 完成令牌与协程支持的起始版本由版本决定，最低版本要写进构建要求。
- 升级时先跑适配层测试，再替换业务代码，缩小回归范围。
- 文档记录每个受支持版本的已知差异，避免使用方自行猜测。

### 15.20（场景）把回调式代码迁移到 sender/receiver 的步骤如何安排？

- 先固定回调边界，把每个异步操作封装成只调用一次完成处理器的函数。
- 再引入完成令牌，使调用点可以选择回调、future 或协程，行为保持不变。
- 把令牌适配层替换为 sender，用 `then`、`let_value` 表达顺序与依赖。
- 用 `when_all` 与 `when_any` 替换手工的计数与竞速逻辑，取消交给停止通道。
- 每次替换后运行同一组测试，覆盖错误、取消与并发完成。
- 迁移期间保留旧接口，适配层同时支持两种模型，避免一次性重写。

## 16. 异步陷阱

### 16.1（陷阱）异步操作捕获引用会在哪些路径上悬垂？

- 启动函数按引用捕获局部变量，操作在函数返回后才完成，引用指向已析构对象。
- 完成处理器捕获 `this`，对象在回调执行前被销毁，成员访问落在已释放内存上。
- 缓冲区以引用或指针传入，异步读写未完成时缓冲区被复用或释放。
- 引用捕获在单线程测试中往往正常，负载变化导致完成时机改变后才暴露。
- 修正方式是按值捕获所需数据，或传入 `shared_ptr` 延长生存期，并明确所有权转移点。
- 回调中只应使用已确认存活的对象，编译器无法检查这一点，需要接口设计约束。

### 16.2（场景）对象在回调执行前被销毁，如何防护？

- 用 `std::shared_ptr` 持有对象，处理器捕获 `shared_ptr`，回调结束后引用计数归零才销毁。
- 用 `std::weak_ptr` 加 `lock()`，对象已销毁时放弃回调，代价是一次原子操作。
- 在对象析构时取消所有未完成操作，并等待取消完成，确保没有处理器在途。
- 对象销毁由最后一个 `shared_ptr` 决定时，回调排队期间对象不会析构，但可能已经逻辑关闭。
- 共享所有权不能替代取消，回调仍可能访问已经逻辑失效的对象，需要状态标志配合。
- 单线程事件循环内，析构若发生在处理器执行中，要避免在栈上销毁正在使用的对象。

### 16.3 `enable_shared_from_this` 在异步链中的使用边界是什么？

- 对象由 `shared_ptr` 管理时，成员函数内用 `shared_from_this()` 取得所有权，供处理器捕获。
- 构造函数内不能调用 `shared_from_this()`，此时内部弱引用尚未初始化，行为未定义。
- 对象未由 `shared_ptr` 管理时调用，自 C++17 起抛出 `std::bad_weak_ptr`。
- 栈对象或 `unique_ptr` 管理的对象不能用它延长生存期。
- 每个异步步骤捕获一次 `shared_ptr` 会让对象在整条链上存活，链过长时内存占用上升。
- 断开链的方式是显式释放捕获，或在回调末尾重置指针。

### 16.4 协程挂起期间 `this` 的有效性由谁保证？

- 成员协程的 `this` 来自调用对象，协程帧只保存指针，不延长对象生存期。
- 调用方在协程挂起后销毁对象，恢复时访问成员即为悬垂。
- 成员协程应在入口取得 `shared_from_this()` 并保存在帧内，或由调用方保证对象活到协程结束。
- 协程参数按值传递时参数被复制进帧，按引用传递时仍指向调用方对象。
- `co_await` 之后的代码可能运行在另一个线程，对象的线程安全需要另行保证。
- 协程被销毁时不会自动取消底层操作，需要显式取消，否则操作继续持有资源。

### 16.5（辨析）回调重入与并发执行有何区别？

- 重入是同一线程上的嵌套调用，外层处理器尚未返回，内层处理器已经开始执行。
- 并发是两个线程同时执行处理器，共享数据需要同步。
- 重入破坏的是状态机的顺序假设，并发破坏的是数据访问的原子性。
- 修复重入用队列化投递，修复并发用互斥量或 strand，两者不能互相替代。
- 重入在单线程程序中即可出现，压测时线程数为 1 也可能触发。
- 同一个回调既可能重入又可能并发，设计时要同时考虑。

### 16.6（实现）如何用队列化投递消除重入？

```cpp
void enqueue(std::function<void()> f) {
    bool idle = queue_.empty();
    queue_.push_back(std::move(f));
    if (idle) drain();
}
void drain() {
    while (!queue_.empty()) {
        auto f = std::move(queue_.front());
        queue_.pop_front();
        f();                       // 回调内的 enqueue 只入队，不再递归
    }
}
```

- 队列非空时不递归调用 `drain`，新的任务排到队尾，由外层循环继续处理。
- 队列需要上限，无界队列在生产者快于消费者时耗尽内存。
- 多线程投递时队列加锁，`drain` 只允许一个线程进入。
- 任务抛异常时要保证队列状态一致，通常捕获异常后继续处理后续任务。
- 队列化改变了执行时机，依赖同步返回的调用方需要改为回调或等待完成。
- 关闭时先停止入队，再处理剩余任务，最后销毁队列。

### 16.7 递归投递如何导致栈溢出？

- 在处理器内用 `dispatch` 重新提交自身，当前线程已在执行器上下文中，调用同步执行，栈帧逐层累积。
- 用 `post` 提交时任务进入队列，当前调用返回后才执行，栈深度不增长。
- 协程中同步完成的等待对象会在同一栈上继续恢复，递归深度同样累积。
- 深链式 `then` 在同步完成时可能形成嵌套调用，链长与栈深相关。
- 定时器立即到期、缓冲区已就绪等场景最容易触发同步完成路径。
- 诊断方法是观察崩溃栈的重复帧，或在处理器入口记录递归深度。

### 16.8 在回调中销毁自身对象有什么风险？

- 处理器执行期间对象被 `delete`，随后访问成员即为悬垂，包括日志与状态更新。
- 析构函数中销毁 `io_context` 时，事件循环仍在该对象的调用栈上，属于未定义行为。
- 处理器对象本身由库持有，析构时销毁正在执行的处理器同样危险。
- 安全做法是把销毁推迟到处理器返回之后，用 `post` 投递一个删除任务。
- 使用 `shared_ptr` 时，最后一个引用在处理器内释放会立即析构，仍需确认后续代码不再访问。
- 关闭流程应分层：先停止提交、再取消、再等待、最后释放。

### 16.9 异步锁与回调组合为何会死锁？

- 在单线程事件循环中同步等待一个需要该线程推进的操作，事件循环被阻塞，完成永远不会到达。
- 持有 `std::mutex` 跨越 `co_await`，同一线程上的另一个协程尝试加锁时阻塞整个线程。
- 异步锁的等待队列若在持锁状态下调用用户回调，回调再次请求同一把锁会永久等待。
- 两个异步操作互相等待对方的完成，且都在同一执行器上串行，形成循环等待。
- 修复方式是缩短临界区、禁止跨挂起点持锁、用 `strand` 替代互斥量。
- 超时是兜底手段，不能替代对锁顺序与执行器拓扑的分析。

### 16.10（陷阱）在事件循环线程上等待 `future` 会怎样？

- `use_future` 返回的 future 需要事件循环运行才能完成，在循环线程上 `get()` 会永久阻塞。
- `sync_wait` 同样阻塞调用线程，在事件循环线程上调用会让整个循环停摆。
- 多线程 `run()` 时阻塞一个线程可能只是降低吞吐，线程数为 1 时必然死锁。
- 阻塞等待还会让定时器与取消处理器无法执行，超时机制随之失效。
- 正确做法是把等待移到循环之外的线程，或改用回调与协程。
- 需要同步语义时，用条件变量配合显式的完成通知，并确保通知线程不被阻塞。

### 16.11 取消与对象销毁的竞态如何消除？

- 取消请求与对象析构可能并发，取消处理器持有的指针在处理器执行时可能已经失效。
- 取消处理器应捕获 `weak_ptr`，`lock()` 失败时直接返回。
- 触发取消后要等待操作真正结束，再销毁其依赖的状态。
- `cancellation_signal` 的生存期必须覆盖槽位，销毁信号前要确保没有在途取消。
- 取消是异步的，`emit` 返回不代表操作已终止，完成回调仍可能稍后到达。
- 关闭路径要幂等，重复取消与重复销毁都不能产生二次释放。

### 16.12 定时器回调如何安全地持有对象？

- 回调捕获 `this` 时，定时器到期与对象析构的先后顺序决定是否悬垂。
- 析构定时器会取消等待，但等待处理器仍会以 `asio::error::operation_aborted` 被调用一次。
- 因此析构函数不能假定取消后回调不再执行，回调内要先检查对象是否仍然有效。
- 使用 `weak_ptr` 或代际计数判断回调是否属于当前周期。
- 重复设置到期时间会取消前一次等待，旧处理器同样会以取消错误被调用。
- 周期任务应在回调内重新设置定时器，而不是在外部循环中反复创建。

### 16.13 完成顺序与完成线程分别约束什么？

- 完成顺序描述多个操作完成的先后，完成线程描述处理器在哪个线程上执行。
- 单线程运行不代表顺序确定，I/O 就绪事件与定时器的相对顺序由实现定义。
- 多线程运行也不代表完全不可控，`strand` 可以固定一段处理器序列的串行范围。
- 依赖顺序的状态机要用序号或状态标志，不能依赖投递顺序。
- 依赖线程的共享数据要用 `strand` 或互斥量，与顺序问题分开处理。
- 关闭标志同时涉及两者，在串行上下文中读写才能避免检查与使用之间的窗口。

### 16.14 回调链中如何传递所有权？

- 用 `std::unique_ptr` 表示独占所有权，通过移动构造传给下一段回调，所有权转移点明确。
- 处理器需要可复制时改用 `shared_ptr`，并注意引用计数的原子开销。
- 缓冲区用 `std::shared_ptr<std::vector<char>>` 持有，避免异步读写期间被释放。
- 捕获列表使用初始化捕获移动对象，例如 `[buf = std::move(buf)]`。
- 每一步只转移一次所有权，重复移动会留下空指针。
- 链结束时释放资源，长链要检查是否存在隐式的多次复制。

### 16.15（陷阱）异常从完成处理器逃逸会怎样？

- `io_context::run()` 会把处理器抛出的异常传播给调用者，`run()` 随即返回。
- 未执行完的处理器留在队列中，需要再次调用 `run()`，否则操作停滞。
- 异常发生在库内部状态更新中途时，对象可能处于不一致状态。
- 处理器应在入口捕获异常，转成错误结果或记录后不再向外抛出。
- 协程中的异常会存入协程帧，等待方 `co_await` 时重新抛出，需要在合适层级捕获。
- 事件循环外层要有兜底 `try`，捕获后继续运行，避免整个服务退出。

### 16.16 析构时取消异步操作的顺序如何安排？

- 先停止接受新操作，把状态置为关闭，阻止新的异步调用进入。
- 再取消在途操作：定时器 `cancel()`、套接字 `close()`、取消信号 `emit()`。
- 然后等待处理器执行完毕，确认没有回调还在访问对象。
- 最后释放缓冲区与执行器相关资源，关闭 `io_context` 前要保证队列已排空。
- 在处理器内部触发析构时，等待自身完成会死锁，应把销毁投递到循环之外。
- 顺序错误表现为偶发崩溃或析构后访问，单线程复现概率低。

### 16.17 `detached` 与真正的后台任务有何差别？

- `detached` 只是丢弃完成结果，操作仍在原执行器上运行，没有独立线程。
- 真正的后台任务需要独立执行资源，例如线程池或单独的 `io_context`。
- 使用 `detached` 后无法取消、无法等待完成，也无法获知失败。
- 进程退出时 `detached` 操作可能被直接丢弃，资源清理不保证发生。
- 需要可观测性时应改用 `deferred` 加显式启动，或保留 future 便于等待。
- `detached` 的可用版本由版本决定，旧版本需要自行实现等价的令牌。

### 16.18 `shared_ptr` 循环引用如何在异步链中形成？

- 对象持有会话的 `shared_ptr`，会话的处理器又捕获对象的 `shared_ptr`，引用计数无法归零。
- 定时器周期任务在回调内重新注册并捕获自身，形成永不释放的环。
- 取消与关闭路径未断开捕获，导致对象在逻辑结束后仍然存活。
- 诊断方式是统计对象数量，观察关闭后计数是否回落。
- 修复方式是把一侧改为 `weak_ptr`，或在关闭时显式重置处理器。
- 长连接服务中这类泄漏累积缓慢，需要长期运行的对象计数监控。

### 16.19 多线程 `run()` 下处理器并发执行要注意什么？

- 同一 `io_context` 上多个线程调用 `run()` 时，不同处理器可能并发执行。
- 同一套接字的多个异步操作不会并发完成，但不同套接字之间没有顺序保证。
- 处理器内的阻塞调用会占用线程，线程数少时拖慢全部连接。
- 关闭时先 `stop()` 再 `join()`，`stop()` 只让 `run()` 尽快返回，不会中断正在执行的处理器。
- 线程数接近 CPU 核数是常见起点，I/O 密集与计算密集的配比不同。
- 并发带来的共享状态问题要在设计阶段确定串行范围，事后补锁的代价更高。

### 16.20（实现）弱引用加标志位如何安全投递？

```cpp
void post_update(std::weak_ptr<Session> weak, Data d) {
    asio::post(ioc_, [weak, d = std::move(d)]() mutable {
        if (auto sp = weak.lock()) sp->apply(std::move(d));
    });
}
```

- `weak_ptr` 不延长对象生存期，`lock()` 成功说明对象仍然存活。
- 标志位用于表达逻辑关闭，对象存活但已停止服务时仍需丢弃回调。
- 标志位与对象状态在同一串行上下文中读写，避免检查与使用之间的窗口。
- 投递的数据按值捕获，避免引用指向调用方的临时对象。
- `lock()` 与析构之间没有竞态，引用计数保证对象在 `sp` 存活期间不被销毁。
- 关闭时先置标志再取消，已在队列中的回调会因标志检查而快速返回。

## 17. 异步性能与观测

### 17.1 延迟瓶颈与吞吐瓶颈如何区分？

- 延迟看单次请求从发起到完成的时间分布，吞吐看单位时间完成的数量。
- 固定并发下增加负载，延迟上升而吞吐不变，说明系统已达到容量上限。
- 吞吐随并发线性上升、延迟基本不变，说明系统尚未饱和，瓶颈不在服务端。
- 两者同时恶化通常是排队加剧，需要同时观察队列长度与处理器占用时间。
- 测量要在同一并发度下进行，混淆并发与负载会得出错误结论。
- 观测点要包含排队时间与执行时间，只统计总时长无法定位。

### 17.2 异步任务的延迟由哪些部分组成？

- 事件就绪到 handler 被调度之间的排队时间，取决于 `io_context` 的负载与线程数。
- handler 执行时间，包括业务逻辑、序列化与内存分配。
- 定时器精度与到期队列的处理延迟，批量到期时可能集中触发。
- 执行器切换与跨线程投递的开销，strand 与线程池的争用会放大。
- 下游依赖的等待时间，异步并没有消除 I/O 延迟，只改变了等待方式。
- 背压不足时队列积压，尾部请求的延迟由排队长度决定。

### 17.3 事件循环中的长任务如何影响排队延迟？

- 事件循环串行执行处理器，单个处理器占用时间直接加到同一线程上所有请求的延迟。
- 处理器内做磁盘读写、压缩、正则匹配等阻塞操作会阻塞整个循环。
- 定时器精度受处理器执行时间影响，到期任务要等当前处理器返回。
- 拆分长任务为多个小步骤并让出循环，可以降低单次排队延迟。
- 把 CPU 密集工作移到独立线程池，循环只做 I/O 与状态推进。
- 监控单次处理器耗时，比监控平均耗时更容易发现长任务。

### 17.4 如何为异步链路设定延迟预算？

- 先确定端到端的延迟目标，例如 P99 在 200 毫秒以内，再按阶段分配。
- 预算要覆盖排队、处理、下游调用与重试，各阶段之和不超过总目标。
- 每阶段设定独立超时，超时值小于预算余量，留出清理与返回时间。
- 重试次数乘以单次耗时不能超过剩余预算，否则重试挤占其他请求的配额。
- 预算要作为参数在调用链上传递，而不是散落在各处的常量。
- 观测时对比实际分布与预算，持续超出说明容量或实现需要调整。

### 17.5 背压不足时系统会出现哪些现象？

- 队列持续增长，内存占用上升，延迟随负载呈非线性恶化。
- 上游继续生产，下游完成速率不变，排队时间成为主要延迟来源。
- 超时比例上升，重试进一步增加负载，形成放大。
- 进程被操作系统换出或触发内存回收，尾延迟出现尖峰。
- 关闭或重启时积压任务被丢弃，出现数据缺口。
- 这些现象在指标上表现为队列长度、内存与超时的同步上升，可作为告警组合。

### 17.6（辨析）队列长度与延迟指标如何配合解读？

- 队列长度与等待时间正相关：到达速率不变时，队列越长，平均等待越久。
- 队列短不代表延迟低，处理速率下降同样会推高延迟。
- 队列长度持续增长说明到达速率超过处理速率，需要扩容或限流。
- 队列长度为零可能是容量不足导致请求被拒绝，不能直接视为健康。
- 观测队列长度要同时看到达速率与完成速率，单看绝对值意义有限。
- 有界队列会把排队转化为拒绝，延迟下降但错误率上升。

### 17.7 异步 tracing 如何跨回调传播上下文？

- 上下文需要随处理器一起传递，通常放在处理器的关联对象或捕获列表中。
- 线程局部存储只能覆盖同步调用段，跨线程完成时丢失。
- Asio 可用关联执行器或自定义处理器包装注入上下文，包装要保留完成签名。
- 每条异步链要生成独立的 span，父 span 标识在发起时记录，完成时结束。
- 取消与错误路径也要记录结束事件，否则 span 悬挂，统计失真。
- 采样决策在链的入口做一次，后续步骤继承，避免同一请求部分采样。

### 17.8（实现）如何为完成处理器注入 tracing 上下文？

```cpp
template <typename Handler>
struct traced {
    Handler h;
    Span span;
    template <typename... Args>
    void operator()(Args&&... args) {
        span.end();
        std::move(h)(std::forward<Args>(args)...);
    }
};
```

- 包装处理器并保存 span，在调用时记录结束时间与结果状态。
- 包装类型要转发关联执行器、取消槽位与分配器查询，否则绑定信息在包装后丢失。
- 先 `bind_executor` 再包装，或让包装类型自行转发查询，顺序会影响结果。
- span 的父子关系在发起操作时建立，不在完成时推断。
- 记录错误码与取消状态，失败路径的耗时同样需要统计。
- 包装引入一次间接调用与额外存储，热路径上要评估开销。

### 17.9 计时点应放在哪些位置？

- 客户端侧记录发起时间、收到首字节时间与完成时间，区分网络与服务处理。
- 服务端记录入队时间、开始处理时间、完成时间，才能分离排队与执行。
- 异步回调链中每个阶段单独计时，总时长无法指出瓶颈。
- 使用单调时钟，避免系统时间调整导致负值。
- 计时本身有开销，高频路径上用批量聚合替代逐条记录。
- 时间戳要与 trace 关联，否则无法把慢请求与具体链路对应。

### 17.10（陷阱）用平均延迟评估性能有什么问题？

- 平均值被大量快请求拉低，掩盖少数极慢请求。
- 延迟分布通常右偏，平均值高于中位数，不能代表典型体验。
- 超时与重试阈值应参考高分位数，例如 P99 与 P999。
- 平均值对采样窗口敏感，突发流量会显著改变结果。
- 只报告平均值无法区分普遍变慢与少数极慢。
- 应同时报告分位数、最大值与超时计数。

### 17.11 测量本身的开销如何影响结果？

- 每次计时至少是一次时钟读取，高频路径上会累加成可观测的额外开销。
- 逐条记录日志涉及格式化与加锁，可能比被测逻辑本身更慢。
- 采样与聚合可以摊薄开销，但会改变统计口径。
- 计时点放在热路径中间时，编译器可能因额外调用放弃部分优化。
- 观测线程与业务线程共享缓存行会引发伪共享，抬高延迟。
- 报告结果时要说明测量方式与开销量级，否则不同环境的数字不可比。

### 17.12（场景）如何测量事件循环的排队延迟？

- 在投递任务时记录时间戳，任务开始执行时计算差值，得到排队时间。
- 用一个周期性心跳任务测量循环的响应间隔，间隔变大说明循环被长任务占用。
- 心跳间隔要与业务定时器精度匹配，过密会增加自身开销。
- 排队延迟按分位数统计，平均值会掩盖尖峰。
- 区分 I/O 就绪事件与定时器事件的排队，两者的触发路径不同。
- 结合处理器耗时统计，定位是排队变长还是执行变慢。

### 17.13（实现）如何统计异步操作的延迟分布？

```cpp
void observe(std::chrono::nanoseconds d) {
    auto us = std::chrono::duration_cast<std::chrono::microseconds>(d).count();
    std::size_t i = 0;
    while (i < bounds.size() && us >= bounds[i]) ++i;
    if (i == bounds.size()) overflow.fetch_add(1, std::memory_order_relaxed);
    else buckets[i].fetch_add(1, std::memory_order_relaxed);
}
```

- 用固定边界的直方图累计计数，边界按业务量级设置，避免运行期扩容。
- 记录开始与结束时间戳，差值落入对应桶，桶计数用原子变量或串行上下文更新。
- 定期导出并重置，导出周期与聚合窗口匹配。
- 除直方图外单独记录超时计数与最大值，便于定位极端情况。
- 超出上界的样本单独计数，避免上界之外的信息完全丢失。
- 统计代码本身要轻量，避免在热路径上做字符串格式化。

### 17.14 tracing 采样与开销如何权衡？

- 全量采集的存储与序列化开销可能超过业务本身。
- 头部采样在入口决定，实现简单，但未被采样的慢请求无法进入链路。
- 尾部采样在请求结束后按耗时决定，需要缓冲完整链路。
- 采样率要按接口分别设置，高频低价值接口可以更低。
- 采样决策要沿链路传递，避免部分节点记录导致链路断裂。
- 观测系统自身要有容量上限，否则故障时放大问题。

### 17.15 计时器精度与时钟选择有哪些问题？

- `system_clock` 会随系统时间调整跳变，不适合测量间隔。
- `steady_clock` 单调，适合超时与耗时统计。
- 定时器精度受事件循环调度与操作系统计时粒度限制，不保证准点。
- 到期时间集中时，同一轮循环要处理多个定时器，形成尖峰。
- 大量短定时器的插入与删除成本高，时间轮可以降低到接近常数时间。
- 超时判断要留余量，恰好等于阈值的比较在调度延迟下容易误判。

### 17.16 如何观测取消率与超时率？

- 在完成路径上区分正常完成、错误完成与取消完成，分别计数。
- 超时通常实现为取消，需要在发起侧记录超时原因，否则与调用方取消混在一起。
- 取消率按接口与调用方维度拆分，整体比例会掩盖局部问题。
- 统计取消到实际终止的时间差，反映取消是否及时生效。
- 取消率突增常与下游变慢相关，要与延迟指标联动分析。
- 取消后仍完成的请求要单独计数，说明取消没有被遵守。

### 17.17 并发度与下游容量如何匹配？

- 并发度上限由下游连接数、处理能力与配额共同决定，超过上限的部分只会排队。
- 用受控实验逐级提高并发，观察吞吐与 P99 的拐点。
- 下游扩容后要同步调整并发度，固定值在容量变化后可能偏低或偏高。
- 并发度与线程数不是同一概念，异步模型下少量线程可以承载大量在途请求。
- 每增加一档并发记录队列长度与超时率，判断是否越过拐点。
- 容量规划按峰值流量的比例预留余量，不留余量的配置在突发时迅速饱和。

### 17.18 吞吐提升但尾延迟恶化是什么原因？

- 批处理与合并提交提高吞吐，单条请求等待批次成形，尾延迟上升。
- 并发度提高后资源竞争加剧，少数请求排队时间变长。
- 缓存命中率下降，部分请求走慢路径。
- 队列变长吸收突发流量，吞吐稳定但排队时间增加。
- 下游限流触发重试，重试流量进一步推高尾部。
- 需要在吞吐与尾延迟之间设定目标，按分位数而不是平均值验收。

### 17.19 批处理的观测指标如何设计？

- 记录批次大小分布、批次等待时间与单批处理耗时，三者共同决定尾延迟。
- 统计因批次上限与等待窗口分别触发的比例，判断参数是否失衡。
- 记录刷新失败与重试次数，批量失败的影响面大于单条失败。
- 观测关闭时残留的批次数，残留说明刷新策略没有覆盖退出路径。
- 批次与请求的关联要能追溯，否则慢请求无法定位到具体批次。
- 指标上报本身要批量，逐条上报会与业务争抢同一资源。

### 17.20（场景）生产环境如何定位长尾请求？

- 先按接口与分位数确认长尾范围，排除整体变慢。
- 用 trace 找到慢请求的公共阶段，比较快慢请求的阶段耗时。
- 检查排队时间占比，区分容量不足与单请求处理慢。
- 检查共享资源：连接池、线程池、锁与下游配额。
- 检查周期性任务与批量刷新是否与尖峰时间吻合。
- 复现时保持相同并发与数据分布，低负载复现通常无效。

## 18. 异步设计题

### 18.1 设计一个异步 HTTP 客户端需要哪些组件？

- 连接管理：连接池、DNS 解析、TLS 握手与连接复用。
- 请求编码与响应解析：状态行、头部、分块传输与内容长度。
- 调度层：执行器、超时定时器与取消信号。
- 重试与重定向策略：幂等方法判定、退避与次数上限。
- 观测：每阶段计时、错误分类与连接池指标。
- 背压：在途请求上限与等待队列，避免无限增长。

### 18.2（场景）请求排队与连接获取如何避免队头阻塞？

- 每个主机独立排队，避免一个慢主机阻塞其他主机的请求。
- 同一连接上除协议支持多路复用的情况外，请求按连接串行发送。
- 长请求占用连接时，短请求应能使用其他连接，池容量决定并行度。
- 队首请求超时后要显式移除，否则后续请求被无谓等待。
- 队列按优先级分层时，低优先级请求需要防止饥饿。
- 连接获取与请求发出之间要检查截止时间，已过期的请求不应继续排队。

### 18.3 取消如何沿请求的各阶段传播？

- 取消信号在请求对象上维护，各阶段注册处理器并在完成时解除。
- DNS 解析、连接建立、TLS 握手、发送与接收都可能阻塞，逐段检查取消状态。
- 已发出部分请求时取消，连接不能复用，直接关闭并记录。
- 取消与超时共用同一条路径，但原因要分开记录。
- 取消后仍可能收到完成回调，回调要检查状态并丢弃结果。
- 关闭流程取消全部在途请求时，要等待回调结束再释放请求对象。

### 18.4（实现）重试与退避如何设计？

```cpp
asio::awaitable<Response> attempt(int n) {
    auto r = co_await send_once(req_);
    if (!retryable(r) || n == 0) co_return r;
    timer_.expires_after(backoff(n));
    co_await timer_.async_wait(asio::use_awaitable);
    co_return co_await attempt(n - 1);
}
```

- 只对幂等方法或带幂等键的请求重试，非幂等请求重试可能产生重复副作用。
- 退避采用指数增长并加随机抖动，避免大量客户端同时重试。
- 总重试时间受截止时间约束，单次退避不能超过剩余时间。
- 重试要区分可重试错误与不可重试错误，连接重置可重试，协议错误不可重试。
- 每次重试前检查取消状态，取消后立即返回。
- 记录重试次数与最终结果，重试率是容量规划的重要指标。

### 18.5 定时任务调度器的数据结构如何选择？

- 有序容器按到期时间排序，插入与删除为对数复杂度，适合任务量中等的场景。
- 最小堆实现简单，取消任务需要惰性删除或额外的索引表。
- 时间轮适合大量短延迟任务，插入与删除接近常数时间。
- 分层时间轮覆盖长延迟，实现复杂度高。
- 同一时刻大量任务到期时，要分批处理，避免单轮循环过长。
- 任务取消要能从结构中移除或标记失效，否则到期时仍需判断。

### 18.6（实现）令牌桶限流器如何实现？

```cpp
bool try_acquire(std::size_t n) {
    auto now = std::chrono::steady_clock::now();
    double add = std::chrono::duration<double>(now - last_).count() * rate_;
    tokens_ = std::min(capacity_, tokens_ + add);
    last_ = now;
    if (tokens_ < n) return false;
    tokens_ -= n;
    return true;
}
```

- 令牌按速率补充，桶容量决定允许的突发量。
- 补充用时间差计算，不需要后台定时器。
- 拒绝时要返回建议等待时间，调用方据此退避。
- 多线程访问需要加锁或原子更新，浮点累加在并发下误差累积。
- 时钟使用单调时钟，系统时间跳变会影响速率计算。
- 分布式场景需要共享计数或按实例分摊配额，单机限流无法约束全局。

### 18.7 并发限流与排队策略如何配合？

- 并发限流限制同时在途的操作数，速率限流限制单位时间的请求数。
- 两者解决不同问题：前者保护下游连接与内存，后者保护下游处理能力。
- 排队会引入延迟，队列满时应快速拒绝，避免无限等待。
- 队列按优先级或公平性调度，避免大请求饿死小请求。
- 等待队列中的请求到期要移出，否则占用配额。
- 限流阈值要可动态调整，硬编码阈值在流量变化时失效。

### 18.8 如何限制同时在途的请求数？

- 用计数信号量表示剩余配额，获取成功才发起请求，完成时释放。
- Asio 可用 `steady_timer` 加等待队列实现异步信号量，避免阻塞线程。
- 释放必须在所有完成路径上执行，包括错误与取消。
- 获取配额也要支持取消，否则关闭时等待者无法退出。
- 配额释放与下一次获取在同一串行上下文中执行，避免丢失唤醒。
- 监控等待队列长度与等待时长，判断配额是否过小。

### 18.9 流水线各阶段的背压如何设计？

- 阶段之间用有界队列连接，队列满时上游暂停生产。
- 上游暂停通过完成通知实现，而不是忙等。
- 每个阶段独立限流，慢阶段不应让上游无限缓冲。
- 队列容量按阶段耗时差异设置，容量过小会降低吞吐，过大增加延迟。
- 关闭时按从上游到下游的顺序停止，再排空队列。
- 丢弃策略要明确，不允许静默丢数据。

### 18.10 有序流水线如何保持顺序？

- 为每个键维护序号，处理完成后按序号提交结果。
- 同一键的任务串行执行，不同键并行，兼顾顺序与吞吐。
- 乱序完成时用重排缓冲区暂存，等待缺失的序号。
- 重排缓冲区要有上限，长时间缺失时判定失败并跳过，避免无限等待。
- 键的哈希要稳定，否则重排时找不到对应的槽位。
- 顺序保证的粒度要在接口中写明，全局顺序的代价远高于按键顺序。

### 18.11（实现）优雅退出的宽限期如何设定？

```cpp
void begin_shutdown() {
    stopping_ = true;                       // 拒绝新请求
    acceptor_.close();                      // 停止接受连接
    grace_.expires_after(std::chrono::seconds(10));
    grace_.async_wait([this](std::error_code) {
        for (auto& s : sessions_) s->force_close();   // 超时强制关闭
    });
}
```

- 宽限期从停止接受新请求开始计，覆盖在途请求的完成时间。
- 宽限期应大于 P99 请求耗时，并按业务可接受的最大等待设定上限。
- 到期后强制关闭剩余连接，不再等待，避免进程无法退出。
- 宽限期内要持续观测剩余在途数量，判断是否需要提前终止。
- 强制关闭产生的错误要单独统计，与正常运行时的错误区分。
- 宽限期与负载均衡的下线时间配合，先摘除流量再开始计时。

### 18.12 退出时未完成的请求如何返回错误？

- 对已建立连接的请求返回明确的错误响应，例如 503，并带上重试提示。
- 响应已部分写入时无法补充状态码，只能关闭连接，由客户端识别截断。
- 尚未发送请求头的请求可以直接丢弃，不产生半成品响应。
- 取消原因要写入日志，区分主动退出与超时。
- 批量返回错误时注意限速，避免退出瞬间产生大量写操作。
- 客户端侧要能区分服务不可用与请求已受理但未完成，决定是否重试。

### 18.13 信号处理与事件循环如何配合？

- 信号处理函数只能执行异步信号安全的操作，不能直接调用 Asio 接口。
- 用 `signalfd`、`sigwait` 或自管道把信号转成文件描述符事件，交给事件循环。
- 信号处理器中只写一个字节，循环线程读取后执行关闭流程。
- Windows 上使用控制台事件或窗口消息，机制与 POSIX 不同。
- 关闭流程要在事件循环线程执行，避免与处理器并发。
- 重复信号要幂等处理，第二次信号可以触发强制退出。

### 18.14（场景）可取消的批量任务如何设计？

- 为批次建立取消信号，所有子任务共享同一个槽位。
- 子任务完成时检查是否已取消，已取消则跳过后续工作。
- 取消后等待所有子任务结束，保证资源释放完成再返回。
- 已完成的部分结果要明确处理：丢弃或返回部分成功。
- 批次级截止时间与子任务超时需要统一，避免子任务比批次活得久。
- 取消原因要记录，区分调用方取消、超时与关闭。

### 18.15 如何用 `when_all` 与 `when_any` 组合超时？

- `when_all` 等待全部子操作完成，适合汇总多个独立请求，参见 `[exec.when.all]`。
- `when_any` 在至少一个子操作以 `set_value` 完成时返回，适合竞速。
- 超时实现为定时器 sender 与业务 sender 的竞速，超时分支完成后取消业务分支。
- `schedule` 与 `transfer` 用于把超时处理切到定时器所在的执行资源。
- 竞速结果只保留一个值，其余子操作的结果要显式忽略。
- 组合后的取消要沿停止通道传播，否则业务操作在超时后继续运行。

### 18.16 连接池耗尽时请求如何排队与降级？

- 等待队列有上限，超出上限直接失败，避免无限堆积。
- 等待时间超过截止时间时移除请求并返回超时。
- 降级策略包括复用其他主机的连接、降低并发或返回缓存结果。
- 池耗尽通常是下游变慢的信号，要同时检查连接建立耗时与在途请求数。
- 排队顺序按截止时间排序可以降低超时率，先到期先获取。
- 池容量调整要结合下游承载能力，单纯扩大池会把压力转移给下游。

### 18.17（辨析）重试放大与限流如何相互作用？

- 重试会增加请求量，限流会拒绝超出配额的部分，两者叠加可能形成振荡。
- 下游故障时大量重试挤占配额，正常请求被拒绝，故障范围扩大。
- 退避与抖动降低同步重试的概率，是控制放大的主要手段。
- 重试应计入限流配额，否则限流对真实负载的估计偏低。
- 熔断在错误率超过阈值时直接失败，比重试更适合持续性故障。
- 重试预算按总请求的比例设置，可以给放大设置上限。

### 18.18 流水线的错误隔离如何设计？

- 每个阶段独立处理错误，失败的任务不阻塞其他任务。
- 关键错误向上传播，可恢复错误在阶段内重试或降级。
- 用独立的取消信号隔离批次，一个批次失败不影响其他批次。
- 资源按阶段分别限额，避免一个阶段耗尽全部连接或内存。
- 错误分类要稳定，便于告警与自动化处理。
- 失败任务进入死信或补偿流程，不能静默丢弃。

### 18.19（场景）截止时间如何沿调用链传播？

- 入口记录绝对截止时间，向下传递剩余时间而不是固定超时。
- 每跳减去已消耗时间，剩余时间不足时快速失败。
- 下游超时应小于上游剩余时间，留出返回与清理的余量。
- 截止时间要与取消信号绑定，到期自动触发取消。
- 跨进程传递时需要时钟同步或改用相对时间，时钟偏差会导致误判。
- 记录剩余时间与各阶段耗时，才能判断时间消耗在哪个环节。

### 18.20（实现）如何测试取消与优雅退出路径？

- 用可控的假 I/O 对象制造挂起，验证取消后能在限定时间内返回。
- 在关闭过程中持续发起新请求，确认被拒绝且不产生资源泄漏。
- 统计关闭前后的对象数量与连接数量，确认全部释放。
- 覆盖取消发生在各阶段的场景：解析中、连接中、传输中。
- 用超时兜底测试本身，避免测试因死锁永久挂起。
- 在压力下重复执行关闭流程，暴露竞态与二次释放。
