ODR（One Definition Rule，单一定义规则）约束定义在一个翻译单元中的数量，以及同一个实体在程序里出现多份定义时各份之间必须满足的一致性。编译器、链接器与优化器都依赖这套规则，但只有一部分违反会被诊断出来。

定义判定、链接性与 inline 的规则分散在 `[basic.def]`、`[basic.link]`、`[dcl.inline]`，ODR 本身写在 `[basic.def.odr]`。把这些条款分开看，可以解释三件事：头文件为什么能承载类定义、inline 函数与模板，模板为什么能在每个用到它的翻译单元里各自实例化，以及不同翻译单元用不同宏或编译选项构建时为什么可能出错却不报错。

本文以 C++ 工作草案（<https://eel.is/c++draft/>，快照 2026-11-14）为准，段号按该快照引用。草案不是正式标准，正式文本是 ISO/IEC 14882；C++20 与 C++23 的措辞和段号分别以 N4861、N4950 对照标注。链接器合并、LTO 检查、sanitizer 这类实现行为集中在第 10 章说明，不当作规范。

## 1. 规则全景：数量约束与一致性约束

ODR 约束的对象是定义；声明在数量上不受它限制。规则可以拆成一组数量约束和一条一致性约束，层与层的违反后果不同。

| 层次 | 规则 | 依据 | 违反后果 |
| --- | --- | --- | --- |
| 翻译单元内 | 任何可定义项最多一个定义 | `[basic.def.odr]/2` | 通常必须诊断 |
| 整个程序 | 被 odr-use 的函数与变量至少有一个定义 | `[basic.def.odr]/12` | 不要求诊断；链接器通常报未定义引用 |
| 整个程序 | 非 inline、非模板的函数与变量不得有多份定义 | `[basic.def.odr]/16.1` | 不要求诊断；链接器通常报重复定义 |
| 整个程序 | 其他可定义项可有多份定义，须满足一致性条件 | `[basic.def.odr]/16.2` 至 `/16.12` | 不要求诊断；附着于具名模块且前一定义可达时必须诊断 |

各版本的段号与措辞不同，引用时需要区分。

- C++17（N4659）：`[basic.def.odr]` 共 6 段。数量规则是 `/4` 的「恰有一个定义」，多定义条件在 `/6`。
- C++20（N4861）：共 17 段。P0588R1 把 odr-use 改写为「指名」与「潜在求值」的表述，并引入 odr-usable（`/3`、`/4`、`/9`）；模块措辞引入 definition domain（`/11`）；P1815R2 引入 TU-local 与 exposure；数量规则仍在 `/10`。
- C++23（N4950）：数量规则改为「至少一个定义」（`/11`），多定义条件新增常量初始化与常量求值两项（`/14`），并引入 definable item 术语（`/1`）。
- 当前快照（2026-11-14）：共 20 段。`/12`、`/13` 承接数量与可达性要求，`/16` 集中多定义条件与诊断例外，反射带来 `/15` 与 `/16.12`。

这些差异属于措辞与条件细节的变化，数量约束与一致性约束的框架没有改变。

前三条是数量约束，决定程序能不能链接；最后一条是一致性约束，决定多份定义能否被视为同一份。数量违反通常由编译器或链接器给出诊断；一致性违反落在两者都看不到的位置，标准因此把它定为 ill-formed、不要求诊断。

「不要求诊断」的含义由 `[intro.compliance.general]/1` 与 `/2.2` 给出：diagnosable rule 指除「不要求诊断」与「未定义行为」以外的规则；程序违反不要求诊断的规则时，标准对实现不再提出任何要求。实现可以拒绝，也可以接受并生成任意代码。它与未定义行为在形式上不同，前者描述程序本身不符合标准，后者描述某次执行没有语义保证；在「没有可依赖结果」这一点上两者一致。

### 1.1 为什么需要 ODR

ODR 要处理的是「定义出现在多个翻译单元」时的合法性与一致性。必要性来自两个前提：单独编译要求编译器一次只处理一个翻译单元；文本包含把头文件复制进每个翻译单元，类定义、inline 函数与模板定义因此天然重复。

由此产生两难。只允许每个实体有一份定义，头文件就只能放声明，模板无法实例化；允许任意重复，链接器只能保留其中一份，行为取决于实现保留哪一份。C++ 选择中间路线：承认重复，但要求多份定义在词法、名字绑定、常量与模板等价上一致，并规定行为如同只有一份（第 5 章）。

| 方案 | 重复定义 | 多份的语义 | 代价 |
| --- | --- | --- | --- |
| 只允许一份 | 不允许 | 唯一 | 头文件只能放声明，模板无法实例化 |
| 任意重复 | 允许 | 由实现任选一份 | 没有一致性保证 |
| ODR（C++ 采用） | 特定实体允许 | 要求一致，行为如同只有一份 | 跨翻译单元无法检查，违规为 IFNDR |
| 模块（C++20） | 具名模块内不允许 | 唯一；诊断条件见第 9 章 | 模板实例化与代码生成仍重复 |

这个交换有三个后果。一致性条件无法在编译期比较，因为编译器互相看不到对方的定义，违规因此只能是 IFNDR（第 10 章）。合法的多份定义必须由实现合并，弱符号与 COMDAT 承担这件事，规范因此承诺 inline 函数与变量的地址唯一、函数体内静态局部变量唯一（`[dcl.inline]/2` 注 1）。任何改变定义内容的操作，例如宏、编译选项与 `#pragma`，都在破坏约定（第 8 章）。

历史演进沿着同一条线。C 已有单一外部定义的传统；C++98 引入 `inline`，让函数定义进入头文件；C++17 用 inline 变量（P0386R2）把许可扩展到变量；C++20 模块（P1103R3）把文本包含改成显式导入，具名模块内的定义只允许一份且必须诊断（第 9 章）。这些变化都在缩小「必须靠 ODR 容忍重复」的范围，但模板实例化与 inline 函数的代码生成仍会在多个翻译单元产生重复，等价性要求因此保留。

替代设计同样说明这一点。单编译单元（unity build）把所有实现文件合成一个翻译单元，跨翻译单元比较不再必要，代价是编译时间、增量构建与并行化；预编译头只节省解析，不改变模型；模块缩小了重复出现的范围，没有消除代码生成层的重复。当前编译模型下，ODR 是让多份定义仍有唯一语义的代价最低的方案。判断一个写法是否安全，本质上是在判断它产生的那几份定义能否满足最后一条约束。

## 2. 定义与可定义项

### 2.1 定义与声明的判定

`[basic.def]/2` 用排除法界定定义：先说明声明定义哪些实体，再列出哪些声明不是定义。常见的判定如下。

| 写法 | 性质 | 说明 |
| --- | --- | --- |
| `void f(int);` | 声明 | 没有函数体 |
| `void f(int) { }` | 定义 | 有函数体 |
| `extern int x;` | 声明 | 没有初始化器 |
| `extern const int c = 1;` | 定义 | 有初始化器 |
| `int x;` | 定义 | 命名空间作用域变量的定义 |
| `struct S;` | 声明 | 前置声明 |
| `struct S { int m; };` | 定义 | 类定义 |
| `using T = int;` | 声明 | 别名声明 |
| `class S { static int m; };` | 声明 | 静态数据成员声明，定义在类外 |

表里最后一行依赖「非 inline 的类内静态数据成员声明不是定义」（`[class.static.data]/3`）。C++17 起，带 `inline` 的静态数据成员可以在类内初始化并同时构成定义，不再需要在 `.cpp` 里补一份定义；这是 inline 变量规则的一部分，见第 7 章。

### 2.2 可定义项

`[basic.def.odr]/1` 列出可定义项（definable item）：类类型、枚举类型、函数、变量、templated entity、函数参数的默认实参、默认模板实参。判断 ODR 是否适用，第一步是确认对象属于这张列表。

列表里有两点与直觉不同。

- 默认实参与默认模板实参也是可定义项。同一作用域内不能重复给出默认实参（`[dcl.fct.default]/4`）；头文件里的默认实参被多个翻译单元包含时，作为可定义项受 `/2` 与 `/16` 约束。inline 函数另有一条要求：同一 inline 函数在不同翻译单元中的默认实参累积集合在翻译单元末尾必须相同，不要求诊断（`[dcl.fct.default]/4`）。函数模板与类模板成员函数的默认实参被视为定义，必须遵守 ODR（`[temp.pre]/6` 注 4）。
- 模板被归入 templated entity。`[temp.pre]/8` 把模板本身、在模板中定义或创建的实体、模板的成员、模板中 lambda 表达式的闭包类型等都算作 templated entity。模板的多份定义与实例化都按这一条处理。

### 2.3 链接性：名字能否跨翻译单元

ODR 讨论「同一实体的多份定义」之前，需要先确定名字能否在多个翻译单元中指称同一实体。这由链接性决定（`[basic.link]/2`）。

- 外部链接：名字可以在整个程序中指称同一实体。模块链接：只能在附着于同一模块的翻译单元中指称。
- 内部链接：所有声明只出现在一个翻译单元内（`[basic.link]/2` 注 1）。命名空间作用域的 `static` 声明、非模板的非 volatile const 变量默认属于这一类（`[basic.link]/3`）；const 变量在模块接口单元的 purview 中、显式 `extern`、声明为 `inline`、或先前声明不带内部链接时不成立。
- 无链接：不在上述规则内的名字；块作用域名字通常无链接（`[basic.link]/7`）。

这个区分直接决定 ODR 的判断对象。头文件里的 `static` 函数与 `const` 变量在每个翻译单元各产生一个内部链接实体，属于「多个实体各有一个定义」，不触发多定义例外；只有外部链接或模块链接实体的多份定义，才需要第 5 章的一致性条件。

## 3. 翻译单元内：不得重复定义

`[basic.def.odr]/2` 的原文只有一句：一个翻译单元不得包含任何可定义项的多于一个定义。这一层通常可诊断，典型错误有三类。

- 头文件缺少 include guard 或被同一翻译单元包含两次，类定义在同一个翻译单元里出现两次。
- 同一作用域内重复定义变量或函数。
- 显式特化在同一个翻译单元里定义两次。

这里要区分「同一实体多个定义」与「多个实体各有一个定义」。头文件里写 `static void helper() { }`，每个包含它的翻译单元各自定义一个内部链接函数，这些定义属于不同实体，不违反本层规则，也不违反程序层的数量约束。

C++ 没有 C 的暂定定义（tentative definition）。命名空间作用域的 `int x;` 在 C++ 里是定义；C 允许暂定定义重复出现，这套机制在 C++ 中不存在。

## 4. 整个程序：数量约束

`[basic.def.odr]/12` 规定：每个程序对每个在丢弃语句之外被 odr-use 的函数或变量，至少有一个定义；不要求诊断。定义可以显式出现在程序里，可以来自标准库或用户库，也可以在合适的时候隐式生成（默认构造、复制构造、析构、复制赋值等）。

`[basic.def.odr]/13` 对 inline 函数与 inline 变量提出更强的要求：定义必须从每个 odr-use 它的定义域（definition domain）末尾可达。定义域指私有模块片段，或翻译单元去掉私有模块片段后的部分，定义域的定义写在 `/13` 第 1 句。对普通翻译单元，定义域就是整个翻译单元，这条要求落在「定义在该翻译单元中可达」。与 `/12` 不同，`/13` 没有「不要求诊断」的注记，按 `[intro.compliance.general]/1` 属于可诊断规则；定义缺失时实现应当给出诊断，常见表现是编译器提示 inline 函数未定义，或链接期报未定义引用。

`[basic.def.odr]/16.1` 从另一侧限制数量：如果一个可定义项在多个翻译单元里有定义，而它是非 inline、非模板的函数或变量，程序 ill-formed。与 `/2` 合起来，非 inline、非模板的函数与变量在程序里只能有一份定义。

违反数量约束有三种表现。

1. 程序里完全没有定义：链接器报未定义引用，属于可诊断错误。
2. 多个翻译单元各有一份外部链接定义：链接器报重复定义，同样可诊断；该诊断由实现提供，标准并未要求。
3. 定义存在于某个目标文件，但没有被链接进来：静态库成员未被抽取、目标文件被排除，最终仍表现为未定义引用。

链接器的处理方式决定了后续所有现象。外部链接的强符号在每个目标文件中出现一次，链接器按符号名合并，重名报错；inline 函数、模板实例化这类允许重复的实体以弱符号（COMDAT，实现术语 vague linkage）出现，链接器保留其中一份、丢弃其余。

这套机制只比较符号名与符号属性，不比较定义内容。多定义例外能工作的前提是实现允许重复符号，ODR 违规难以发现的原因也在这里：两份内容不同的定义在链接器看来是两个同名符号，合并后程序只剩其中一份。

## 5. 多定义例外：一致性条件

`[basic.def.odr]/16` 的开头给出判定框架：对在多个翻译单元中定义的可定义项 D，除注入声明（`/15`，反射带来的附加规则）外，只要 D 是非 inline、非模板的函数或变量，或各份定义不满足下列要求，程序 ill-formed。只有一种情形必须诊断：D 附着于具名模块，且后一定义处前一定义可达（`/16` 末句）。

| 条件 | 要求 |
| --- | --- |
| 不附着具名模块 | 每份定义都不附着于具名模块（`/16.3`） |
| token 序列 | 各份定义由相同的 token 序列构成；闭包类型的定义按对应 lambda 表达式的 token 序列比较（`/16.4`） |
| 名字与实体 | 对应名字经名字查找、重载决议与偏特化匹配后指称同一实体；内部链接或无链接的 const 对象与引用按所列条件例外（`/16.5`） |
| 闭包类型 | 对应的 lambda 表达式具有相同闭包类型，默认实参与默认模板实参中的除外（`/16.6`） |
| 语言链接 | 对应实体具有相同语言链接（`/16.7`） |
| 常量初始化 | 静态或线程存储期的 const 对象在任一份定义中常量初始化，则每份定义都常量初始化；对应的、非值依赖的 manifestly constant-evaluated 表达式取值相同（`/16.8`、`/16.9`） |
| 运算符与隐式调用 | 重载运算符、隐式转换函数、构造函数、`operator new` 与 `operator delete` 指向同一函数（`/16.10`） |
| 默认实参 | 调用中用到的默认实参与默认模板实参，视为其 token 序列出现在该定义中，递归参与比较（`/16.11`） |

条件满足时，`/18` 规定这些要求同样适用于各份定义内部定义的对应实体（闭包类型、局部类等；默认实参内的实体除外）；对这些实体与 D 本身，行为如同只有一个实体、一份定义。这些实体在多个翻译单元中仍然各自声明，`[basic.link]` 对声明的规则仍然适用。

快照里还有两条与 C++26 反射相关的要求：注入声明（`/15`）与 `reflect-expression` 取值等价（`/16.12`）。它们只影响反射代码，本文不展开。

### 5.1 token 序列相同

比较的是预处理之后的 token 序列。注释、空白、换行、缩进不构成 token，不影响结果；宏展开结果不同则一定不同。这一条把「看起来一样但编译出来不一样」的写法排除在外，也解释了为什么用宏切换函数体容易触发 ODR 违规。

token 相同是比语义相同更窄的要求。两份定义可以做同样的事，但只要多一条 `using` 声明、把 `x + 1` 写成 `1 + x`、或在函数体里多一句空语句，就不再满足。

模板参数名有一个明确的例外：判断表达式等价时，`[temp.over.link]/5` 允许命名同一模板参数的 token 不同。普通函数的参数名不在这个例外范围内，严格按条款比较，参数名不同即不满足 token 序列要求；实现通常不做这种比较，因此这类写法在实践中普遍存在。这两件事应当分开记：语言层面的结论是 ill-formed，工程层面的事实是普遍没有被诊断。

### 5.2 名字必须指称同一实体

每份定义中对应的名字，要么指称定义内部声明的实体，要么指称同一个外部实体。这一条覆盖 inline 函数体里调用的函数、引用的全局变量、使用的类型与模板。

典型违反是 inline 函数体引用了头文件里用 `static` 定义的辅助函数：每个翻译单元各自绑定到内部的 `helper`，名字指称的不是同一实体，程序 ill-formed。修正方式有两条：把辅助函数改为 `inline`，两份外层定义因此指称同一个实体；或把外层函数连同辅助函数一起移进 `.cpp`，此时匿名命名空间中的函数只在一个翻译单元里使用。

例外只针对特定对象，且条件逐条可查（`/16.5.1`）。

- 对象是内部链接或无链接的 const 对象，非 volatile。
- 各份定义中对象具有同一字面类型（literal type）。
- 对象以常量表达式初始化。
- 对象在 D 的任一份定义中都没有被 odr-use。
- 对象在各份定义中取值相同。

引用另有对应条件：内部链接或无链接的引用以常量表达式初始化，且在各份定义中指向同一对象或函数（`/16.5.2`）。

头文件里的 `const int N = 42;` 在每个包含它的翻译单元里各有一份对象，地址不同、实体不同。数组边界、模板实参、常量表达式里的读取都不 odr-use，多份定义可以满足上述条件；取地址、绑定引用会 odr-use，此时名字指称不同实体，违反条件。C++17 起的 `inline constexpr` 变量是更稳妥的写法：inline 使变量具有外部链接且允许重复定义，一致性由本节条件保证，地址唯一。

### 5.3 闭包、语言链接与常量初始化

lambda 表达式在 inline 函数体里出现时，各份定义中的闭包类型必须是同一类型（`/16.6`）；闭包类型的 token 比较按对应 lambda 表达式进行（`/16.4`）。`/19` 的例子给出对照：函数体里使用 lambda 的 inline 函数满足条件；函数通过默认实参间接使用 lambda 时，默认实参的 token 序列被视作出现在定义中（`/16.11`），各份定义得到不同闭包类型，程序 ill-formed（不要求诊断）。

语言链接要求对应实体具有相同语言链接（`/16.7`）。同一实体在有的翻译单元里用 `extern "C"` 声明、在另一些里按 C++ 链接声明，不满足条件。

常量初始化与常量求值的要求（`/16.8`、`/16.9`）针对两类可观察差异：静态或线程存储期的 const 对象在一份定义中是常量初始化、在另一份中不是；对应的 manifestly constant-evaluated 表达式在不同翻译单元取到不同值。这两类差异会影响常量折叠结果，属于「链接器看不出来」的典型情形。

### 5.4 运算符、默认实参与模板

重载运算符与隐式调用必须指向同一函数（`/16.10`）：各份定义中选择的 `operator+`、转换函数、构造函数、`operator new` 与 `operator delete` 都算在内。即使运算符的声明在 header 里完全一致，只要重载决议因为某个翻译单元的额外声明而选了不同函数，就不满足条件。

默认实参按 `/16.11` 处理：调用中用到的默认实参与默认模板实参，视为其 token 序列出现在该定义中，并递归参与比较。inline 函数的默认实参集合另有一条独立要求（`[dcl.fct.default]/4`，见第 2.2 节）。

模板有两层要求。定义本身按本节条件比较；对模板的依赖名，要求延伸到实例化点（`/17.3`）。模板的等价判定在 `[temp.over.link]`，比 token 相同宽：`/5` 允许命名同一模板参数的 token 不同，也给出了表达式等价的判定方式。等价仍比「语义上起同样作用」窄，不在等价规则内的改写一律算不同。

## 6. odr-use：什么时候必须有定义

数量约束与 inline 的可达性要求都只对 odr-use 的实体生效。判断一个函数或变量是否被 odr-use，是 ODR 实践的核心问题。

### 6.1 判定步骤

第一步是表达式是否潜在求值（`[basic.def.odr]/3`）。潜在求值排除未求值操作数（`sizeof`、`decltype`、`noexcept`、`typeid` 的非多态操作数等）及其子表达式。未求值操作数里的名字不参与求值，但名字查找与重载决议仍然进行，所以声明必须可见、定义不需要。

第二步是名字指称哪个实体。函数按 `/4` 判定：在重载决议中被选中的函数被该表达式或转换指名；纯虚函数不被指名，但对它写显式限定名的 `id-expression` 是例外（`/4.1`）。构造函数即使调用被消除也算被指名；类专用的释放函数按 `/4.2`、`/4.3` 判定，分配函数由 `/4.1` 与注 2 覆盖。变量按 `/5` 判定：被 `id-expression` 或 splice 表达式指名的变量，在潜在求值表达式里被 odr-use，除非命中例外。

例外有两组（`/5.1`、`/5.2`）。一组针对可用于常量表达式的引用；另一组针对「读取」的情形：指名出现在丢弃值表达式中且未应用左值到右值转换，或对象是可用于常量表达式的非 volatile 对象且没有 mutable 子对象，再按成员访问或左值到右值转换的具体形态判定。`/5` 的例 2 用五个表达式展示了边界。

还有几条补充规则：结构化绑定被潜在求值表达式指名即 odr-use（`/6`）；`*this` 出现在潜在求值表达式中即 odr-use（`/7`）；非纯虚的虚函数被 odr-use（`/8`）；构造函数与析构函数按 `/9` 判定。局部实体还受 odr-usable 规则约束（`/10`）：在 lambda 或默认实参中使用外层局部变量时，如果中间隔着不允许的作用域，程序 ill-formed，且必须诊断。

### 6.2 常见写法的判定

| 写法 | 是否 odr-use | 是否需要定义 |
| --- | --- | --- |
| `sizeof(x)`、`decltype(x)`、`noexcept(f())` | 未求值操作数 | 不需要定义，声明可见即可 |
| `constexpr int N = 42; int a[N];` | 常量表达式读取 | 不需要 |
| `const int N = 42; const int* p = &N;` | 取地址 | 需要 |
| `int& r = x;` | 绑定引用 | 需要 |
| `extern int x; int f() { return x; }` | 读取，odr-use | 需要 |
| `f()` | 调用，被指名 | 需要 |
| 非纯虚的虚函数 | 非纯虚即 odr-use（`/8`） | 需要，即使从未调用 |
| `if constexpr` 的丢弃分支 | 丢弃语句 | 不要求定义（`[stmt.if]/2` 注 1） |

最后两行需要补充。虚函数只要不是纯虚就会进入虚表，因此即使程序里没有任何显式调用，也需要它的定义。丢弃语句中的 odr-use 不要求实体有定义（`[stmt.if]/2` 注 1），这也是 `[basic.def.odr]/12` 与 `/13` 都写「丢弃语句之外」的原因。

### 6.3 与「需要完整类型」的区别

odr-use 与「需要完整类型」是两套独立规则。`sizeof(x)` 不需要 `x` 的定义，但需要 `x` 的类型完整；取 `&x` 需要定义，不需要在取地址处类型完整。类定义的要求写在 `[basic.def.odr]/14`：在需要类类型完整的每个上下文中，类定义必须可达。把两套规则混在一起，会把「前向声明够不够」判断错。

## 7. inline：让定义进入头文件

### 7.1 inline 的规范含义

`[dcl.inline]` 的规则可以归纳为五条。

- `inline` 说明符只能用于函数或变量的声明，不能出现在块作用域声明与函数参数的声明上（`[dcl.inline]/1`）。
- 带 `inline` 的函数或变量声明是 inline 函数或 inline 变量。具有外部链接或模块链接的 inline 函数与变量可以在多个翻译单元中定义，是同一实体、同一地址；在函数体内定义的类型与静态变量也因此是单一实体（`[dcl.inline]/2` 与注 1）。
- inline 只是内联替换的提示，实现可以不展开，但 inline 的其他规则仍然适用（`[dcl.inline]/3`）。
- 若一个函数或变量在首次声明为 inline 之前其定义已经可达，程序 ill-formed（`[dcl.inline]/4`）。在某个定义域中声明为 inline 后，每个出现该声明的定义域末尾都必须可达一个 inline 声明；不要求诊断（`[dcl.inline]/4`）。
- 附着于具名模块的 inline 函数或变量在某个定义域中声明后，必须在该定义域中定义（`[dcl.inline]/5`）。

这五条合起来就是 inline 的语义：允许重复定义、地址唯一、局部静态状态共享、声明与定义必须配套。它约束 ODR 与链接，与代码生成无关。

### 7.2 隐式 inline

以下情形不需要写 `inline` 也是 inline（`[dcl.constexpr]/1` 与 `[dcl.inline]/5` 注 4）。

- 在类定义内部定义的成员函数，在全局模块中隐式 inline。
- 首次声明带 `constexpr` 或 `consteval` 的函数。
- 首次声明带 `constexpr` 的静态数据成员。

C++17 起还允许 inline 变量（P0386R2），头文件中的命名空间作用域变量与静态数据成员因此可以只有一份定义。

### 7.3 链接性与 exposure

inline 不改变链接性（`[dcl.inline]/2` 注 2）。`static inline` 函数具有内部链接，每个翻译单元一份，跨翻译单元地址不同。内部链接实体本来就不参与多定义例外，因此 `static inline` 与 `static` 的 ODR 效果相同：合并与地址保证只对外部链接或模块链接的实体生效。

`[dcl.inline]/2` 注 2 还提示另一条限制：某些情况下 inline 函数不能使用内部链接的名字。这条限制来自 `[basic.link]/14` 定义的 exposure 概念与 `/17`、`/18` 的后果，见第 9 章。

### 7.4 inline 变量

C++17 的 inline 变量解决的是「头文件里定义共享变量」的问题。命名空间作用域的 `inline constexpr int limit = 100;` 具有外部链接、允许重复定义、全程序一个实体；静态数据成员写成 `inline static` 后可以直接在类内定义并初始化。inline 变量与 inline 函数受同一套多定义条件约束。

## 8. 头文件里的定义：能放什么

把「链接性」与「是否属于多定义例外」两个维度合起来，头文件里可以放什么就清楚了。

| 头文件中的内容 | 多翻译单元包含的结果 |
| --- | --- |
| 类、枚举、模板定义 | 允许，受第 5 章的条件约束 |
| inline 函数与 inline 变量 | 允许，同一实体、同一地址 |
| `constexpr` 函数、`constexpr` 静态数据成员 | 隐式 inline，允许 |
| 非 inline 函数定义、非 inline 变量定义 | 各翻译单元各一份强定义，链接期重复定义错误 |
| `static` 函数与变量、匿名命名空间实体 | 合法，每个翻译单元一份独立实体 |
| 命名空间作用域的 `const` 变量 | 每个翻译单元一份内部链接对象；被 odr-use 时受第 5 章的条件约束 |
| `extern` 声明 | 只有声明，定义放在 `.cpp` |

除了语言规则，还有两类因素会破坏跨翻译单元的一致性。

- 宏：预处理之后的 token 由各翻译单元的宏状态决定。用 `#ifdef` 改变类成员、虚函数集合或 inline 函数体，直接落在第 5 章的条件之外。
- 编译选项与 `#pragma`：`#pragma pack`、`-fshort-enums`、`_GLIBCXX_DEBUG`、`-DNDEBUG` 之类会改变布局或定义内容，同样使多份定义不一致。

工程上的做法收敛为一句：头文件只放声明和允许重复的定义，非 inline 定义放进 `.cpp`；确实需要在头文件里定义共享状态时用 `inline` 变量。

## 9. C++20 模块：附着、可达与诊断

C++20 模块把声明分为附着于全局模块与附着于具名模块两类，包含模块声明的翻译单元称为模块单元。附着关系由 `[module.unit]/7` 判定：除少数例外，声明附着于它所在 purview 的模块。多定义例外的第一条条件就是每份定义都不附着于具名模块（`[basic.def.odr]/16.3`）。

由此产生三处差异。

1. 具名模块中的定义只能有一份。同一个可定义项在多个翻译单元中被定义、其中某份附着于具名模块时，不满足 `/16.3`，程序 ill-formed；并且当附着于具名模块、后一定义处前一定义可达时，必须诊断（`/16` 末句）。这比头文件模型严格：重复的定义由实现负责发现。
2. inline 的定义域要求收紧。附着于具名模块的 inline 函数或变量在某个定义域中声明后，必须在该定义域中定义（`[dcl.inline]/5`）。跨模块导入的 inline 定义由模块接口提供，不再依赖每个翻译单元各自包含一份头文件。
3. TU-local 实体不能穿越翻译单元。TU-local 实体（`[basic.link]/15`）包括名字具有内部链接的类型、函数、变量与模板，以及在 TU-local 实体定义内部声明的无链接实体；`[basic.link]/17` 规定，模块接口单元中非 TU-local 实体的声明若构成对 TU-local 实体的 exposure，程序 ill-formed，其他上下文中的这类声明被弃用（deprecated）；`[basic.link]/18` 规定，一个翻译单元中的声明指名另一个翻译单元（头文件单元除外）声明的 TU-local 实体时，程序 ill-formed。

模块没有消除的部分同样要正视。模板实例化与 inline 函数的代码生成仍可能出现在多个翻译单元，第 5 章的等价性要求不变；模块把「定义写在哪里」从文本包含改成显式导入，代码生成层面的重复仍然存在。

## 10. 违规为什么不报错：IFNDR 与检测手段

### 10.1 无法诊断的原因

编译器一次处理一个翻译单元，看不到另一个翻译单元里同名实体的定义内容；链接器按符号名与符号属性合并，不比较 token、类布局、常量取值、默认实参。跨翻译单元的一致性问题落在两者都看不到的位置，标准因此把它们定为 ill-formed、不要求诊断。

可以诊断的只有少数情形：同一翻译单元内的重复定义（编译错误）、强符号的重复定义（链接错误）、未定义引用（链接错误）、附着于具名模块且前一定义可达的重复定义（必须诊断）。

### 10.2 检测手段

| 手段 | 能发现的问题 | 前提与限制 |
| --- | --- | --- |
| 链接器重复定义检查 | 外部链接强符号的多份定义 | 不覆盖 COMDAT 实体与类定义 |
| GCC 与 Clang 的 `-Wodr` | 跨翻译单元的类布局、函数签名、虚表不一致 | 均需 LTO（`-flto`）才有跨翻译单元信息 |
| MSVC `/GL` 与 `/LTCG` | 同类问题 | 需要链接时优化 |
| MSVC `#pragma detect_mismatch` | 手工声明的配置不一致 | 需在头文件里标注宏与取值 |
| ASan `detect_odr_violation` | 同名全局变量的多份定义 | 需要 AddressSanitizer；默认值 2 报告检测到的 ODR 违规，取 1 时只报告两份变量大小不同的情形 |
| 统一构建配置与 CI | 宏、选项、标准库配置不一致 | 依赖流程约束，不检查语言层一致性 |

这些手段覆盖的都是「能比较」的部分。类布局不一致而符号相同的情况，只有 LTO 带上类型信息时才有机会被发现；运行时行为差异则完全没有自动检查。

### 10.3 典型违规

- 头文件里定义非 inline 全局变量，被多个翻译单元包含。后果是可诊断的重复定义错误。
- 用宏改变类成员或继承关系。各翻译单元的 `sizeof` 与成员偏移不同，链接器不报错，运行期读写错位。
- 只对部分翻译单元启用 `_GLIBCXX_DEBUG` 或改变 `_GLIBCXX_USE_CXX11_ABI`。容器与 `std::string` 的布局不一致，跨翻译单元传递对象时出错。
- 头文件中的 inline 函数体因 `#ifdef NDEBUG` 不同。两份定义 token 不同，违反第 5 章。
- 头文件里的 `const int N` 被 inline 函数取地址。各翻译单元绑定到各自的内部链接对象。
- 匿名命名空间中的类型出现在头文件函数签名里。不同翻译单元得到不同类型，跨翻译单元调用违反 ODR。
- 不同编译选项（`-fno-exceptions`、`-fshort-enums`、`-m32` 与 `-m64`）混链。类型布局与异常模型不一致。

## 11. 工程规则

1. 非 inline 函数与非 inline 变量只在 `.cpp` 中定义，头文件放声明。
2. 头文件中的共享常量使用 `inline constexpr`（C++17 起）；只能用 `constexpr` 时，确认它只在常量表达式中被使用，不被取地址或绑定引用。
3. 一个函数或变量只要在某个定义域里声明为 inline，就在所有出现它的定义域里保持 inline 声明可达。
4. 不用宏改变类布局、虚函数集合、inline 函数体与默认实参；配置差异用链接期校验暴露。
5. 内部辅助函数与类型放在 `.cpp` 的匿名命名空间，不放进头文件。
6. 跨翻译单元传递的类型必须有外部链接的唯一定义；不传递匿名命名空间或 `static` 局部类型。
7. 所有目标使用同一套编译选项、标准库版本与 ABI 配置，CI 与发布构建保持一致。
8. 在 CI 中启用 LTO 并打开 `-Wodr`（GCC、Clang）或 `/GL /LTCG`（MSVC），把一部分 IFNDR 变成诊断。
9. 用 ASan 的 `detect_odr_violation` 检查全局符号重复，作为链接期检查的补充。
10. 使用模块时把定义放进模块接口单元，利用「附着于具名模块的定义只有一份」及其诊断要求，替代头文件的重复定义模型。

---

## 12. 小结

ODR 可以压缩成一句：同一个实体在程序里只允许有一份定义；语言为了头文件与模板必须允许多份时，多份必须在 token、名字绑定、常量取值、模板等价与默认实参上完全一致。

判断一个写法是否安全，按顺序回答五个问题：它是不是定义、是不是可定义项、在一个翻译单元里出现几次、在程序里允许几份、使用它的地方是否 odr-use。

代价最大的是跨翻译单元的一致性违反：没有编译错误、没有运行时检查，链接器只按名字合并。可行的控制手段是缩小头文件中的定义面、统一构建配置，并在 CI 中用 LTO 与 sanitizer 把一部分不可见的违规变成可见的诊断。
