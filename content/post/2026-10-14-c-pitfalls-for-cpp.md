这篇笔记谈的不是「C 的缺点」——很多决定放在 1972 年看是合理甚至聪明的——而是 C 的这些决定被 C++ 继承、并且因为兼容性承诺而难以回头之后，留下的长期约束。判断一条属于哪一类，用三个问题过一遍：这是 C 当年有意的选择，还是当时的妥协；C++ 有没有修补过；修补是从哪个标准版本开始的。

需要先立一条界线：C++ 从来不是 C 的超集，它只承诺一个受控的兼容层——C 兼容头文件、`extern "C"` 语言链接、standard-layout 类型。所以下面说的「坑」，不是 C++ 没做到什么，而是它明明可以另做设计，却因为要和 C 对上而只能沿用、并在沿用中付出代价。本文以 C++ 草案（<https://eel.is/c++draft/>）和 cppreference 为准，C 一侧引用 ISO C 的条款编号与 WG14 文稿编号。

## 1. 整数的类型名与宽度脱钩

C 的五个有符号整数类型是从机器的字长历史里长出来的：`char`、`short`、`int`、`long`，`long long` 是后来补的。草案只规定最小宽度——`int` 最低 16 位、`long` 最低 32 位——实际宽度由实现决定（`[basic.fundamental]` 第 4 段）。程序里写下的 `int`、`long` 因此不是「32 位」「64 位」的同义词，而是「这台机器上那个叫 int / long 的东西」。

字面量的类型同样不由写法决定。`0xFFFFFFFF` 在 `int` 为 32 位的平台上类型是 `unsigned int`，在 `int` 为 64 位的平台上则是 `int`；`1 << 31` 在 `int` 为 32 位时直接踩到有符号溢出的 UB。同一份源码在两个平台上算出不同的类型，重载解析和比较表达式跟着变。

C++ 一直在补这个洞，但补的是「带后缀的固定宽度类型」，不是「让名字有确定含义」：

| 补丁 | 版本 | 它替换掉的 C 式写法 |
| --- | --- | --- |
| `<cstdint>` 的 `int32_t` / `uint64_t` | C++11（承自 C99 的 `<stdint.h>`） | `int` / `long` / `unsigned` 靠赌字长 |
| 定宽类型只保证「存在即可用」，宽度可有可无 | C++11 | 无 |
| `std::cmp_less` / `cmp_greater` / `cmp_equal` | C++20 | `a < b` 在混符号时按模比较 |
| 强制二进制补码 | C++20（P0907R4） | 允许反码、原码的旧措辞 |
| `char8_t` / `std::byte` | C++20 / C++17 | 用 `char` 同时表示字符与原始字节 |

关键在最后一行之前的那几行：`std::cmp_less` 的存在，本身就是承认 `a < b` 这个最基本的操作在两个操作数符号不同时没有正确答案。这不是语法糖，是对 C 的转换规则的一次事后补丁，而转换规则本身没变。

## 2. 声明符：「模仿使用」的语法

C 的声明符被设计成和使用表达式同形：`int *p` 里 `*p` 是取值，`int a[10]` 里 `a[i]` 是取元素。这个「declaration mimics use」在单个指针或单个数组上很好懂，一旦指针和数组互相嵌套就立刻失控。草案自己举了例子（`[dcl.fct]` 第 21 段的 Note）：

```cpp
int i, *pi, f(), *fpi(int), (*pif)(const char*, const char*), (*fpif(int))(int);
```

`*fpi(int)` 绑定为 `*(fpi(int))`——先调用函数、再对返回值解引用；`(*pif)(const char*, const char*)` 的括号必不可少。同一段还专门给出建议：函数返回类型复杂时用 `typedef` 或尾置返回类型。

C++ 没有改声明符语法的结构，反而在上面又叠了引用（`int&`）、成员指针（`int S::*`）、`const` 与引用的组合（`T const&`、`T&&`）以及 cv/ref 限定和 `noexcept` 说明。于是最丑的类型拼写也一起继承过来：指向成员函数的指针、返回函数指针的函数、带 ref-qualifier 的成员函数指针。

值得注意的是「参数里的数组其实是指针」这条也来自这里。草案 `[dcl.fct]` 第 5 段规定：参数类型中的「array of T」或函数类型 T 一律调整为「pointer to T」，并且举例说明 `void f(char[])` 与 `void f(char*)` 是同一定义、`char* const` 参数与 `char*` 参数冲突。这条规则是 C 的 ABI 决定（数组作为参数必须传地址），代价是类型里再没有长度。

## 3. 数组到指针的退化与字符串长度

C 里数组不是一等值，除了 `sizeof`、`&` 和绑定到引用等少数场合，数组左值会退化成首元素指针（`[conv.array]`）。于是：

- `void f(int a[10])` 与 `void f(int* a)` 是同一个函数（见上一节 `[dcl.fct]`）；
- `sizeof(a)` 在函数体内给的是指针大小；
- 字符串字面量是 `const char[N]`（`[lex.string]`、`[dcl.init.string]`），一旦离开 `sizeof` 就只剩一个指针，「字符串」这个概念在类型系统里从来不存在。

字符串这一条尤其值得单列，因为它把长度信息、所有权和编码全推给了约定：`'\0'` 结尾是约定，谁分配谁释放是约定，宽字符与多字节的编码是约定。C++ 从 C++03 起就把字符字面量到 `char*` 的隐式转换列为 deprecated，C++11 正式删除，但没有改变字面量的类型——它仍然是数组，仍然会退化。

C++ 给这条坑打的补丁是一条清晰的时间线：

- C++11：`std::array`（长度在类型里）；
- C++17：`std::string_view`（指针 + 长度，但不拥有）；
- C++20：`std::span`（任意类型的连续区间）、`std::ssize`（带符号的长度）；
- C++23：`std::string_view::contains`、`std::ranges` 视图把「区间」提升为算法接口。

这些设施共同的前提是「指针 + 长度要分开保存」——这本身就是 C 的遗产，标准库花了三十年才把它包装成类型。

## 4. 预处理器与头文件模型

C 缺 `const`、缺 `inline`、缺模板，于是常量、小函数、泛型全部落在 `#define` 上。C++ 继承了整个预处理器，尽管标准明确说翻译阶段先做宏展开、语言语法事后才起作用——宏对类型一无所知。

由此而来的具体麻烦是具体的：宏没有作用域，只在翻译单元里按名字生效，所以 `<windows.h>` 里的 `min` / `max` 会直接破坏 `std::min` 的调用，解决办法是 `NOMINMAX` 或到处加括号；宏不参与查找，所以「用命名空间隔离一下」对它无效，只能靠全大写这种社会约定。`assert` 是标准库里少数由宏定义的设施，它的开关是 `NDEBUG`，语义也来自宏系统。

头文件是 C 唯一的模块机制，每个翻译单元都要重复解析一遍；守卫宏、包含顺序、`#pragma once` 与 ODR 是同一套模型的后遗症。C++ 的替代品是 `inline` 函数、`inline` 变量（C++17）、模板、`if constexpr`（C++17）、`constexpr` 与 `constinit`（C++20）——注意 `inline` 在 C 里只是优化提示，在 C++ 里变成了「允许在多个翻译单元重复定义同一个实体」的 ODR 例外，语义被重新定义过。标准库还专门加了 `[[nodiscard]]` / `[[noreturn]]` / `[[deprecated]]` 这套标准属性，它们对应的正是过去靠宏和实现扩展才能表达的东西。

C++20 的模块是对 C 的头文件模型唯一一次真正的结构性修改，但要注意边界：模块解决的是文本包含与名字可见性，不解决二进制兼容；而模块接口单元里依然可以 `#define` 宏，标准也没有规定 `import` 之后宏的可见性规则，各家实现给了不同答案（比如标准库模块要不要顺带导出 C 的宏）。

## 5. C 风格库接口：类型擦除是默认，类型安全是例外

C 没有异常，也没有重载，所以错误报告只能靠返回值约定：`-1`、`NULL`、以及全局 `errno`。C++ 继承了这套返回值接口的写法，也继承了它最直接的两个后果。

第一是带长度（或不带）的指针参数。`strcpy`、`strcat`、`sprintf` 的签名里没有目标容量，保护只能靠调用方纪律；`memcpy(dst, src, n)` 只能按字节数工作，对非平凡类型会让生命期规则出问题（`std::launder`、隐式创建对象这些规则直到 C++17/20 才补齐）。`malloc` 返回 `void*`，在 C 里隐式转换成任何对象指针，在 C++ 里必须显式 `static_cast`——这既是 C++ 的麻烦，也是 C++ 唯一能拦住它的地方。`realloc` 更麻烦：它只按字节数搬移，不会调用拷贝/移动构造，对非平凡类型根本不适用。

第二是以 `void*` 为核心的泛型。`qsort` 的比较函数是 `int (*)(const void*, const void*)`，每个比较都要写两个 `static_cast`，而且因为尾参只有 `void*`，传上下文只能靠全局变量；`std::sort` 用比较器模板替掉了它，这是 C++ 对 C 接口少见的彻底胜利。同理，`printf` 家族只能靠格式串描述类型，参数错配是 UB，而 C++11 的变参模板让类型安全成为默认——但 `printf` 本身没法替换，因为它要和 C 的 `FILE*`、和 `std::format` 之前的生态共存。

还有一个容易忽略的连锁反应：C 的 `sizeof` 返回 `size_t`（无符号），C++ 全盘继承了「长度是无符号」这个选择。于是 `std::string::find` 失败时返回 `npos`（一个 `size_t` 的最大值），比较、相减、循环条件处全是混符号陷阱；`std::ssize`（C++20）之所以存在，就是给这个问题开的正规出口。

## 6. C 的整数语义：四个未定义的角落

C 把「字长」和「表示」都交给实现，同时不给有符号溢出、负值右移、越界移位任何保证。C++ 把这些 UB 原样继承，只修了其中一半。

| 行为 | C 的处境 | C++ 的处境 |
| --- | --- | --- |
| 无符号加减乘、左移 | 按 2^N 取模，定义良好 | 同，`[basic.fundamental]` 第 2 段「unsigned arithmetic does not overflow」 |
| 有符号加减乘溢出 | UB | UB（C++20 只强制了补码表示，没定义溢出） |
| 有符号右移负数 | 实现定义（C17 6.5.7；多数实现做算术移位） | C++20 起规定为算术右移、按负无穷取整（`[expr.shift]` 第 3 段） |
| 移位量 ≥ 位宽或为负 | UB | UB，草案里单列了 UB 条目 `[ub:expr.shift.neg.and.width]` |
| 除法/取余：`INT_MIN / -1` | UB | UB |
| 整数除法舍入方向 | C99 起才规定向零截断，C89 是实现定义 | 一直向零截断 |
| 补码表示 | C23 才强制（此前允许反码、原码） | C++20 起强制 |

这张表值得反复看的只有一行：有符号溢出至今是 UB。C++20 把补码写进标准只影响表示形式，不影响溢出行为——「现在都是补码机器，所以溢出就是回绕」是错的，回绕只是当前编译器的实现选择。

右移那一行的版本差异也要记住方向：C++20 之前，实现可以选择算术右移或逻辑右移，标准不管；C++20 起算术右移成为语言保证。C 一侧则是 C99/C11 到现在依然把负操作数的右移留在 implementation-defined 里。

## 7. 隐式转换与运算符优先级

C 允许大量隐式转换，因为没有重载和模板，转换是表达「同一台机器上的同一批位」的唯一手段。在 C++ 里，这套转换会和重载、模板、`bool`、`char` 的区分度叠加，效果从「方便」变成「误导」：

- `unsigned` 与 `int` 混比时按模比较，`i >= 0` 对无符号恒真（`[expr.arith.conv]` 的常用算术转换）；
- `bool` 是整数类型，可以隐式参与算术和转换（`[conv.integral]` 第 2 段：`true` 转成 1）；
- `char` / `signed char` / `unsigned char` 是三个不同类型，`char` 是否有符号由实现决定（`[basic.fundamental]` 第 7 段），而 `sizeof('a')` 在 C 里等于 `sizeof(int)`、在 C++ 里是 1；
- 空指针常量 `0` 能隐式转成任何指针类型，这个从 C 继承的规则导致重载解析歧义，`NULL` 在 C++ 里始终是个半残的兼容物。

C++ 的对策是给「不要隐式」提供出口，而不是改规则：`explicit`（C++11 起可用于转换函数）、列表初始化的窄化检查（C++11）、`std::cmp_*` 系列（C++20）、`char8_t`（C++20）、`[[nodiscard]]`（C++17）。

运算符优先级是另一条不可逆的坑。C 把位运算排在比较之后，于是 `a & b == c` 被解析成 `a & (b == c)`。这条规则在 C++ 里不能改——改了会让大量现存代码静默地变语义，属于标准委员会最不愿意做的事（静默改变程序含义）。同样地，逗号运算符的优先级、`?:` 的结合性、`else` 的悬垂绑定都原样保留。能做的事只有警告：`-Wparentheses` 之类是编译器实现选择，不是语言修复。

## 8. 平坦符号表与链接模型

C 的编译模型是「文本包含 + 平坦符号表」：全局名字共用一个命名空间，没有重载，符号表里一个名字对应一个实体。C 的链接器也因此只认「名字 + 地址」，不需要任何类型信息。

C++ 要支持命名空间、重载、模板、函数默认参数，就必须让同一个源码名字对应多个二进制符号，于是有了名字修饰（name mangling）。随之而来的实现自由是巨大的：修饰规则、模板实例化与合并、内联函数的弱符号处理、RTTI 类型描述符、异常表全部是 ABI 层面的事，标准只规定语义。这造成一个反直觉的现象——标准没有规定 C++ 的 ABI，同一声明在不同编译器或不同版本之间可能对不上，二进制兼容是平台承诺而不是语言承诺。

为了和 C 对上，C++ 提供了 `extern "C"`（`[dcl.link]`）：关闭名字修饰、关闭重载。它是单向的：C 头文件能被 C++ 直接包含，C++ 的名字修饰对 C 不可见。于是出现「C++ 写库、C 写 ABI」这个通行做法的代价——C++ 的类型系统在接口边界上被主动抹掉，模板、重载、异常都只能在边界之内存在。

C++20 的模块改的是文本包含的那一半；上一节已经说过，它不碰 ABI。

## 9. C 有而 C++ 不接的东西，以及 C 后来反过来抄 C++ 的

视角反过来看也成立：C++ 对 C 的许多设施是有取舍的，只是这些取舍留下了「C 写法在 C++ 里没有标准对应物」的空档。

C 有、C++ 没有标准对应物的：变长数组（C99 起标准，C++ 自始至终没有，GCC/Clang 的 `-std=c++` 下能用只是扩展，`-pedantic` 会警告，替代品是 `std::vector` 或非标准的 `alloca`）、`restrict` 别名限定符（C99 起，C++ 没纳入，只有 `__restrict` / `__restrict__` 扩展）、复合字面量 `(T){...}`、`_Generic`（C++ 用重载和 `if constexpr` 这套完全不同的机制替代）、`_Atomic`（C11；C++ 走 `std::atomic` 模板）。`malloc` 与 `memcpy` 的生命期问题在第十节的对照表里更清楚：C 里「字节就是字节」，C++ 里要先问有没有活对象。

另一头，C 自己在往 C++ 的方向补。C23（ISO/IEC 9899:2024）新增了 `nullptr` 与 `nullptr_t`、`constexpr` 对象、`typeof` / `typeof_unqual`、`true` / `false` 成为关键字、`static_assert` 单参数形式、对象定义的类型推断（`auto` 风格）、固定底层类型的枚举与改进的枚举、`_BitInt(N)`、二进制字面量、数字分隔符 `'`、`#elifdef` / `#elifndef` / `#warning` / `#embed`、`[[deprecated]]` 等一整套属性；同时删掉了两个老包袱——非补码的有符号整数表示和旧式（无原型）函数声明与定义，并让 `<stdbool.h>` / `<stdalign.h>` / `<stdnoreturn.h>` 变为过时。`__STDC_VERSION__` 升到 `202311L`。

也就是说，第六节表里「补码表示」那一行的 C 侧，迟至 2023 年才对齐 C++20；而「非补码表示」和「旧式函数声明」这两个 C 早期妥协，C 用了三十年才删。这反向说明：本文列的大部分条目，问题本身两边都承认，难的是删。

## 10. 把这些坑归到一起看

按共同结构归类，这些条目其实是三种不同的东西，混着讲容易得出错误的结论：

- C 的有意设计，C++ 全盘继承：平坦符号表与 `extern "C"`、返回值错误约定、无符号长度、`sizeof` 语义。它们不是失误，是 C 的模型本身；C++ 只能在外围加类型安全设施。
- C 的当时妥协，C++ 长期照抄：非补码表示、旧式函数声明、有符号溢出的 UB、移位语义、声明符语法。这一类里 C 自己在 C23 删掉了一部分，C++ 删了一部分（C++11 删隐式 `int`、C++17 删 K&R 风格函数定义），剩下的仍在。
- C 的设计在 C++ 里被放大成伤害：预处理器（因为 C++ 更有能力取代它）、隐式转换（因为 C++ 有重载和模板）、数组退化（因为 C++ 有引用和泛型）、`void*` 类型擦除（因为 C++ 有继承和模板）。

真正的结论不是「这些坑都该铲平」，而是每个坑的成本都要单独算：改了会静默改变现存代码含义的（运算符优先级、隐式转换），标准委员会选择不动；只影响新代码表达能力的（`std::span`、`std::cmp_less`、`char8_t`），就以外加设施的形式慢慢补；而需要 ABI 层面配合的（名字修饰、异常模型、模块），语言标准能做的本来就有限。
