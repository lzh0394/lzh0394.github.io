## 1. 编译流程与翻译单元

### 1.1 编译器驱动程序如何把一条 `g++` 命令拆成多个子进程？

- `g++` 是驱动程序，按文件后缀与选项调用预处理器、编译器、汇编器与链接器；C++ 前端通常是 `cc1plus`。
- `g++ -v hello.cpp` 在标准错误输出完整命令行，可看到 `cc1plus`、`as` 与 `collect2` 的调用参数。
- 预处理与编译通常在同一前端进程内完成，`-E` 只输出预处理结果，`-S` 在前端之后停止。
- `collect2` 是链接阶段的包装程序，负责构造 `ld` 命令行并处理构造函数表等目标；真正合并目标文件的是 `ld`。
- `-pipe` 让各阶段通过管道传递中间文件，减少临时文件读写，失败时仍可能留下部分中间产物。

### 1.2 `-save-temps` 会保留哪些中间文件？

- `-save-temps` 保留 `.i` 或 `.ii`、`.s`、`.o`；`-save-temps=obj` 把中间文件放到输出目录，避免污染源码目录。
- C 源文件生成 `.i`，C++ 源文件生成 `.ii`；二者都是预处理后的完整翻译单元，可由编译器再次读取。
- `.s` 是目标机器汇编文本，`-S` 停止于此；`.o` 是汇编器输出的可重定位 ELF 文件。
- `-save-temps=obj` 与 `-o build/app` 并用时，中间文件按对象文件路径命名，便于定位某个翻译单元。
- `.i` 可脱离原始头文件重新编译，但 `#line` 标记仍保留原始文件与行号，诊断会指向头文件。

### 1.3 预处理后的 `.ii` 为何仍包含大量空行和 `#` 行？

- `#` 行是行标记（linemarker），格式为 `# 12 "foo.h" 1`，数字为行号，字符串为文件名，尾部标志表示进入或返回文件。
- 空行保留用于维持行号映射，`-P` 可抑制行标记，但会破坏诊断定位与 `__LINE__` 的对应关系。
- `-E` 默认写标准输出，`-o` 写文件；`-C` 保留注释，`-CC` 连宏展开中的注释也保留。
- `__LINE__`、`__FILE__` 依赖行标记与预处理器内部位置，拼接 `.ii` 时不能简单删除这些行。
- `-fpreprocessed` 告诉编译器输入已预处理，可加快读取，但宏与条件编译不再展开。

### 1.4 标准如何定义一个翻译单元？

- `[lex.separate]/1` 规定：源文件连同 `#include` 引入的头文件，扣除条件编译跳过的行，构成一个翻译单元。
- 每个翻译单元独立进行预处理、语法与语义分析，编译器一次只看到一个翻译单元；跨单元的一致性由 ODR 与链接器约束。
- 头文件内容以文本方式进入翻译单元，因此同一头文件在多个翻译单元中各有一份声明与定义。
- `#include` 不共享符号表或宏状态；每个翻译单元从相同的预定义宏与命令行宏开始，此后的宏状态独立演化。
- 命令行 `-D`、`-U`、`-include` 也属于该翻译单元的预处理环境，不同选项会产生不同的翻译单元。

### 1.5 （陷阱）一个 `.cpp` 能否包含另一个 `.cpp`？

- 语法上可以，预处理后两个文件的内容进入同一翻译单元，只产生一个目标文件；若构建系统不再单独列出被包含的 `.cpp`，它就不会产生第二个目标文件。
- 若两个 `.cpp` 都参与构建，被包含者的定义会出现两次，链接时报多重定义。
- 这种做法把内部链接对象与宏状态混在一起，破坏按文件并行编译与增量编译。
- 常见例外是测试或生成代码中的 `#include "foo.inc"`，此时文件后缀应表明它不是独立翻译单元。
- 判断依据是构建系统是否把该文件列为源文件，后缀本身不决定编译行为。

### 1.6 （陷阱）头文件中定义非 `inline` 函数为何会重复定义？

- 头文件中的普通函数定义在每个包含它的翻译单元中都是一个定义，违反 ODR 的至多一个定义要求。
- 若函数具有外部链接，链接器会看到多个同名的 `STB_GLOBAL` 符号，报 `multiple definition`。
- 在函数声明前加 `inline` 使定义可出现在多个翻译单元，链接器把各副本归入 COMDAT 并保留一份。
- 类内定义的成员函数隐含 `inline`，但类外定义仍需显式 `inline` 或放入单个源文件。
- 变量同理：C++ 中头文件里的 `int x;` 是定义，C++17 起可用 `inline` 变量；C 中可用 `static`，但每个翻译单元各有一份。

### 1.7 「编译单元」与「翻译单元」是同义词吗？

- 标准文本使用「翻译单元」，不定义「编译单元」；工程语境中的编译单元通常指一次编译器调用处理的源文件及其包含内容。
- 一个 `.cpp` 可以因不同宏配置被编译多次，产生多个翻译单元与多个目标文件。
- 构建系统可能对同一源文件先做代码生成，再编译生成物；源文件数与翻译单元数不再一一对应。
- 预编译头与 `-include` 会改变编译器读取翻译单元文本的方式，但不改变「一次编译器调用对应一个翻译单元」的边界。
- 回答时应区分标准术语与工具习惯，避免把「编译单元」当成标准中的正式名词。

### 1.8 `-fsyntax-only` 与 `-c` 的停止点有何不同？

- `-fsyntax-only` 只做预处理、语法与语义分析，不生成汇编或目标文件，适合编辑器与持续集成快速检查。
- `-S` 生成 `.s`，停在汇编之前；`-c` 继续生成 `.o`，仍不链接；按停止点从早到晚为 `-fsyntax-only`、`-S`、`-c`。
- `-fsyntax-only` 仍会展开头文件、实例化被使用的模板并执行 `static_assert`，耗时不一定低。
- 它不会发现链接期错误，例如缺少函数定义、库顺序错误或符号版本不匹配。
- Clang 的 `-fsyntax-only` 可与 `-Xclang -ast-dump` 组合，仅打印语法树而不写目标文件。

### 1.9 `-S` 输出与直接生成目标文件有何差别？

- `-S` 在编译器生成汇编后停止，输出 `.s`；`-masm=intel` 切换 Intel 语法，默认是 AT&T 语法。
- `-fverbose-asm` 在汇编中插入源变量名与注释，便于对照 `-O2` 后的代码。
- `-S -o -` 把汇编写到标准输出，适合与 `grep`、`sed` 组合检查某条指令。
- 汇编文本仍含符号名与重定位指令，例如 `call foo@PLT`、`.section .rodata`，不是最终地址。
- `-Wa,` 把选项传给汇编器，`-Xassembler` 作用相同；`-S` 阶段不会经过汇编器。

### 1.10 汇编器如何处理尚未解析的外部符号？

- `as` 把汇编文本编码为机器指令，生成可重定位目标文件，未解析符号留到链接阶段。
- 对 `call foo` 这类外部引用，汇编器生成 `R_X86_64_PLT32` 重定位项，偏移字段先填 `-4`。
- 对本节内已定义符号，汇编器尽量计算相对位移；无法确定时仍写重定位项。
- `-Wa,-alh` 让 `as` 输出带机器码的列表文件，可核对指令编码与节偏移。
- `objdump -dr` 同时显示反汇编与重定位，能看出哪些立即数或位移等待链接器修补。

### 1.11 链接 C++ 程序时 `collect2` 起什么作用？

- `g++` 调用 `collect2`，由它再调用 `ld`，并补充 `crtbegin.o`、`crtend.o` 等启动文件。
- `collect2` 扫描目标文件中的构造函数表，生成全局构造与析构的辅助符号，具体名称由目标平台与工具链决定。
- `-v` 输出中 `collect2` 命令行含 `-plugin` 与 `-plugin-opt` 时，说明启用了 LTO 插件。
- 直接调用 `ld` 通常缺少 C++ 运行库与启动文件，出现 `undefined reference to __libc_start_main` 或 `_start` 缺失。
- `-nostartfiles`、`-nodefaultlibs`、`-nostdlib` 逐级削减驱动程序自动加入的内容，嵌入式链接脚本常配合使用。

### 1.12 程序入口是 `main` 还是 `_start`？

- 内核加载 ELF 后跳到 `e_entry` 指向的入口，通常为 `_start`；`main` 由启动代码调用。
- 在 glibc 的 x86-64 启动代码中，`_start` 从栈上取 `argc`、`argv`，设置对齐，调用 `__libc_start_main`，后者再调用 `main`。
- `main` 的返回值交给 `__libc_start_main`，最终经 `exit` 刷新 stdio 并运行 `atexit` 回调。
- `-Wl,-e,my_entry` 可改入口符号；用错时程序在动态加载后立即崩溃，调试器停在无符号地址。
- `readelf -h` 的 `Entry point address` 可核对入口，`nm` 可确认 `_start` 是否存在。

### 1.13 （场景）为什么 `-c` 编译通过，链接时仍报未定义引用？

- `-c` 只编译不链接，外部符号以 `U` 状态留在 `.o` 的符号表中，编译器不要求其定义存在。
- 只有被 odr 使用的符号才进入未定义集合；仅声明未使用的函数通常不产生 `U`。
- 模板未实例化、`inline` 函数未被调用时也可能没有符号，链接错误与源码中的「已声明」无直接对应。
- 链接器按命令行顺序处理归档库，定义出现在引用之后的静态库可能不被提取，表现为未定义。
- 用 `nm -C` 查看 `.o` 的 `U`，再用 `nm -A` 在库中搜索定义，可区分「未编译进目标文件」与「未被链接器提取」。

### 1.14 （场景）如何用 `nm` 判断目标文件提供了哪些符号？

- `T` 与 `t` 表示 `.text` 中的定义，大写为全局，小写为局部；`U` 表示未定义，`W` 与 `w` 表示弱符号。
- `nm -C` 还原 C++ 名称，`nm -S` 显示大小，`nm -A` 在多个库中标注来源文件。
- 目标文件出现 `U _Z3fooi` 而库中只有 `T _Z3foov`，说明参数签名不一致。
- `T` 变为 `t` 常见于匿名命名空间或 `static`，此时其他翻译单元无法链接到该定义。
- `nm` 读取 `.symtab`；已 `strip` 的发布二进制可能只剩 `.dynsym`，需用 `nm -D`。

### 1.15 增量编译为何不能只依赖文件时间戳？

- `make` 默认比较目标与先决条件的修改时间，只改内容不改时间戳或时钟回拨都会漏判。
- 头文件依赖未写入 Makefile 时，改头文件不会触发重编，`-MMD -MP` 可自动生成 `.d` 文件。
- 网络文件系统的时间精度与时钟偏差会让目标早于源文件，出现随机不重编。
- 构建脚本若先创建空目标再写入，或复制时保留旧时间戳，可能让目标与先决条件的先后关系失真。
- 用 `make -d` 查看依赖比较过程，或改用内容哈希的构建系统，并配合正确的 depfile。

### 1.16 `ccache` 的命中条件与失效原因是什么？

- `ccache` 以预处理后的输入、编译器版本、编译选项、目标平台等计算哈希，命中时直接复制缓存中的 `.o`。
- 宏与头文件内容变化会改变预处理结果，从而失效；仅改注释也可能因预处理输出变化而失效。
- `-g` 下调试信息含工作目录与随机化内容时，缓存命中率下降，`-fdebug-prefix-map` 可稳定路径。
- `CCACHE_BASEDIR`、`CCACHE_SLOPPINESS` 可放宽路径与时间戳检查，但会带来错误复用风险。
- `ccache -s` 查看命中率；`CCACHE_DISABLE=1` 可对比无缓存构建，定位缓存污染。

### 1.17 分布式编译对编译环境有哪些一致性要求？

- 远程编译要求客户端与服务端的编译器版本、目标三元组、选项完全一致，否则目标代码可能不兼容。
- 头文件必须能被远端访问，通常通过相同的挂载路径，或用 `-frewrite-includes` 发送预处理结果。
- `distcc` 默认只做编译，链接仍在本地；链接阶段的库与启动文件不参与分发。
- 预处理在本地或远端执行会影响宏环境，`--scan-includes` 可估算可分发范围。
- 调试信息中的路径与时间戳差异会导致构建不可复现，需统一 `-fdebug-prefix-map` 与 `SOURCE_DATE_EPOCH`。

### 1.18 统一构建如何改变翻译单元的划分？

- 把多个 `.cpp` 文本包含进一个翻译单元，减少重复解析头文件与重复实例化，提升全量构建速度。
- 匿名命名空间与 `static` 符号在同一翻译单元内合并，可能产生重名冲突；宏定义也会相互污染。
- 单个翻译单元变大后并行度下降，增量构建一次改动会重编整组文件。
- 头文件中的 `using namespace` 与宏在拼接后作用范围扩大，诊断位置也更难定位。
- 适合生成代码或中小型库，不适合依赖隔离强、编译内存紧张的项目。

### 1.19 （场景）修改头文件导致全量重编，如何定位包含链？

- `-H` 在标准错误打印每个被打开的头文件，缩进深度表示包含层级，可快速找到重量级头文件的入口。
- `-M` 输出完整依赖并包含系统头，`-MM` 排除系统头；配合 `-MG` 可把缺失头当作生成目标。
- Clang 的 `-H` 输出格式略有不同，`-fshow-skipped-includes` 可显示被 include guard 跳过的文件。
- `clangd` 的 `--background-index` 与 `compile_commands.json` 可建立包含图，但不等同于预处理依赖。
- 减少头文件传递包含的常用手段是前向声明、Pimpl 与把实现移入 `.cpp`，而非单纯调整 `-I` 顺序。

### 1.20 （场景）公共头文件只增加一个声明，为何整个项目重编？

- 先用 `-H` 或 `clang -E -M` 确认哪个公共头被几乎所有翻译单元包含。
- 检查该头是否只用到前向声明；把成员改为指针或引用可去掉对完整类型的依赖。
- 若头中定义了模板或 `constexpr` 函数，模板或函数的实体必须对使用点可见，无法简单移到 `.cpp`。
- 用 `-MMD -MP` 生成的 `.d` 检查依赖是否过宽，避免把整个目录加入 `-I` 后误命中同名头。
- 拆分稳定接口头与实现细节头，并让构建系统只对真正包含者重编。

## 2. 预处理与头文件

### 2.1 `#include "..."` 与 `#include <...>` 的搜索顺序有何不同？

- 引号形式先查当前文件所在目录，再查 `-iquote`、`-I`、`-isystem` 与系统目录；当前文件目录的处理由实现定义。
- 尖括号形式不查当前文件目录，按 `-I`、`-isystem`、标准系统目录的顺序搜索。
- `#include_next` 从当前搜索位置之后继续，常用于包装系统头，结果依赖包含路径的顺序。
- 绝对路径直接打开，不参与搜索；`-I` 的相对路径相对编译器工作目录，而非源文件目录。
- `-v` 与 `-H` 可打印实际搜索路径与命中的文件，排查同名头冲突。

### 2.2 `-I`、`-isystem`、`-iquote`、`-idirafter` 有何区别？

- `-I` 加入用户头搜索路径并参与引号与尖括号两种形式；`-isystem` 标记为系统头，默认抑制其警告。
- `-iquote` 只影响引号形式，适合项目内部头，避免污染尖括号形式的搜索。
- `-idirafter` 放在系统目录之后，适合补丁式覆盖；`-isystem` 放在系统目录之前。
- `-nostdinc` 移除标准系统目录，`-nostdinc++` 只移除 C++ 标准库目录，交叉编译常用。
- 路径顺序决定同名头命中，`-I` 放在 `-isystem` 前会让项目头遮蔽系统头，需用 `-v` 验证。

### 2.3 include guard 与 `#pragma once` 的差异是什么？

- include guard 用宏名标识文件，第二次包含时整个文件被条件编译跳过；宏名冲突会导致头被误跳过。
- `#pragma once` 由编译器按文件身份去重，同一文件经不同路径或符号链接可能被当作不同文件，行为由实现定义。
- `#pragma once` 不保证跨编译器一致，include guard 完全基于预处理，可移植性更好。
- 两者可同时使用：`#pragma once` 加速常见路径，include guard 作为补充；GCC、Clang 与 MSVC 均支持 `#pragma once`。
- include guard 不能防止同一文件被复制成不同路径后的重复定义，也不能替代声明与定义分离。

### 2.4 宏参数何时预展开，何时被 `#` 或 `##` 抑制？

- 展开时先对参数做预扫描，除非参数参与 `#` 或 `##`，再把替换列表中的参数替换为展开结果。
- `#` 把参数转为字符串字面量，`##` 拼接记号，二者都抑制参数的预扫描。
- 宏替换结果会重新扫描以发现更多宏，但当前宏在自身展开期间被标记为不可再次展开，避免无限递归。
- 函数式宏要求实参个数匹配，空实参与缺失实参在 C++ 中都可能导致诊断；可变参数宏用 `...` 与 `__VA_ARGS__`。
- `-E -dD` 保留宏定义输出，`-dM` 只输出最终宏表，便于确认展开结果。

### 2.5 （输出题）下面两行分别展开成什么？

```cpp
#define STR(x) #x
#define XSTR(x) STR(x)
#define A 42
STR(A)   // "A"
XSTR(A)  // "42"
```

- `STR(A)` 得 `"A"`，因为 `#` 直接字符串化实参记号，不展开 `A`。
- `XSTR(A)` 先把参数展开为 `42`，再传给 `STR`，得 `"42"`。
- `STR(__LINE__)` 得 `"__LINE__"`，`XSTR(__LINE__)` 得当前行号的字符串。
- 若 `A` 是函数式宏，`STR(A)` 仍是 `"A"`，因为不写参数列表不构成调用。
- 需要字符串化展开结果时，必须经一层转发宏，这是日志与断言宏的常见写法。

### 2.6 可变参数宏如何处理空参数与逗号？

- C++11 起 `...` 与 `__VA_ARGS__` 是标准写法；C++20 起可用 `__VA_OPT__` 条件包含逗号。
- 空参数包传给 `__VA_ARGS__` 时，`f(a, ##__VA_ARGS__)` 的逗号删除是 GCC 扩展，不是标准行为。
- C++20 的 `__VA_OPT__(,)` 在参数包非空时展开为逗号，空时展开为空，可移植性更好。
- 参数包中的逗号会被当作多个实参，除非用括号包裹；宏无法直接遍历任意长度的参数包。
- 调试时用 `-E` 查看展开，注意 `##` 与逗号的交互在 GCC、Clang、MSVC 上可能不同。

### 2.7 （辨析）宏与函数应如何取舍？

- 宏在预处理阶段做记号替换，不进行类型检查、不遵守作用域，也不产生调用帧。
- 函数在语义分析阶段检查类型，参数只求值一次，调试信息可映射到源码行。
- `inline` 只是允许定义出现在多个翻译单元并提示优化，不保证函数体被插入调用点；宏则必然在预处理阶段替换。
- 宏适合条件编译、字符串化与断言等需要源码位置或记号操作的场景，不适合复杂表达式。
- 用 `constexpr` 函数或模板替代可类型检查的宏，可减少副作用与优先级错误。

### 2.8 `defined` 在 `#if` 中如何求值？

- `defined X` 与 `defined(X)` 等价，只判断宏是否已定义，不展开 `X` 的值。
- `#if X` 会把未定义标识符替换为 `0`，因此宏定义为 `0` 时，`#ifdef X` 为真而 `#if X` 为假。
- `#if` 中的 `&&`、`||` 按短路求值，但整个表达式仍须在语法上合法。
- `-Wundef` 对 `#if` 中未定义标识符告警，`-Werror=undef` 可把它变成错误。
- 用 `#if defined(A) && A > 0` 可同时判断存在性与值，避免未定义宏被当成 `0` 的歧义。

### 2.9 为什么 `#if` 中不能使用 `sizeof` 或类型转换？

- 预处理条件表达式以整型常量表达式为基础，可含字符常量、`defined` 与 `__has_include` 等运算符，不能出现 `sizeof`、类型名、浮点常量或字符串。
- 预处理阶段尚未建立类型与符号表，`constexpr` 变量、枚举值与 `static_assert` 都不可见。
- 未定义标识符替换为 `0`，除法与取模按整数运算，除数为 `0` 时产生诊断。
- 移位与算术按 `intmax_t` 或 `uintmax_t` 规则计算，不遵循目标平台上较小的整型宽度。
- 需要复杂条件时，把结果写入生成的头文件，用 `#define` 输出 `0` 或 `1`。

### 2.10 依赖文件生成选项 `-M`、`-MM`、`-MD`、`-MMD` 有何差别？

- `-M` 输出依赖规则到标准输出并包含系统头，`-MM` 排除系统头，通常用于用户头。
- `-MD` 在正常编译的同时生成 `.d`，`-MMD` 同样但排除系统头；`-MF file` 指定输出名。
- `-MT target` 指定规则目标，`-MQ` 对目标中的特殊字符做转义，适合含空格或 `$` 的路径。
- `-MP` 为每个依赖生成空规则，头文件被删除后 `make` 不会因缺少先决条件而失败。
- 依赖文件只记录预处理实际打开的文件，条件编译未走到的分支不会出现；生成头需在编译前完成。

### 2.11 预编译头的原理与限制是什么？

- 预编译头保存预处理后的记号流与部分语义状态，常见扩展名为 `.gch`（GCC）与 `.pch`（Clang）。
- GCC 要求预编译头与使用它的源文件编译选项一致，且一次编译只能使用一个预编译头。
- Clang 的 `-include-pch` 显式指定预编译头，模块则用 `.pcm`，二者格式与语义不同。
- 预编译头对头文件顺序敏感，首个头变化会使缓存失效；它不适合频繁变动的项目头。
- CMake 的 `target_precompile_headers` 把指定头编译为预编译头，生成结果需与目标编译选项一致。
- 预编译头能减少重复解析，但不减少链接期符号与代码体积，也不改变 ODR 规则。

### 2.12 `-include` 强制包含会带来哪些问题？

- `-include file` 在每个源文件预处理前强制包含该文件，等价于在首行写 `#include "file"`。
- GCC 的 `-include` 先查当前工作目录，再查 `-I` 等路径；Clang 行为类似，细节由实现定义。
- 强制包含会改变所有翻译单元的宏与声明环境，使缺失的显式包含不易被发现。
- 与预编译头同用时，若 `-include` 的头正是预编译头的源，编译器可直接加载；否则预编译头失效。
- 用 `-H` 确认强制包含的实际路径，避免命中构建目录中的同名生成头。

### 2.13 include-what-you-use 如何判断包含是否必要？

- include-what-you-use 基于 Clang AST 判断每个符号的实际来源，建议直接包含声明它的头，而非依赖传递包含。
- 它区分直接使用、间接使用与重新导出，对模板、宏与特化场景误报较多。
- `--mapping_file` 提供项目私有映射，`--keep` 与 `IWYU pragma: keep` 可保留有意为之的包含。
- 工具默认只输出建议，需配合 `fix_includes.py` 应用；批量修改前应在小范围验证。
- 它不替代构建系统的依赖生成，后者记录实际打开的文件，前者判断声明来源是否合理。

### 2.14 前向声明何时足够，何时必须包含完整定义？

- 只使用指针、引用或函数声明中的不完全类型时，前向声明足够；按值传参、继承与成员访问需要完整定义。
- `std::unique_ptr<T>` 的析构函数需要 `T` 完整，若析构在头文件中隐式生成，仅前向声明会导致编译错误。
- 前向声明不能替代模板定义：模板实体必须对使用点可见，除非使用显式实例化。
- 前向声明缩短编译依赖，但把完整性要求转移到 `.cpp`，漏包含时错误位置可能在调用方。
- 对标准库类型做前向声明属于未定义行为，标准库头可能包含额外声明或 inline 命名空间。

### 2.15 头文件中的 `static` 变量与匿名命名空间会产生什么后果？

- 头文件中的 `static` 函数或变量在每个包含它的翻译单元中各有一份，增加代码体积且地址不同。
- 匿名命名空间具有内部链接，效果类似，但每个翻译单元的实体不同，不能跨单元取同一地址。
- C++17 的 `inline` 变量提供唯一实体，适合头文件中的常量与单例式对象。
- 函数模板与类模板的静态成员在多个翻译单元中由 COMDAT 合并，不需要 `static`。
- 用 `nm` 比较多个 `.o` 中同名局部符号，可确认是否产生多份副本。

### 2.16 `__has_include` 适合解决什么问题？

- `__has_include` 是 C++17 的预处理运算符，C++11 与 C++14 编译器多以扩展提供，使用前用 `#ifdef __has_include` 保护。
- 它只判断头文件能否被找到，不判断其中是否有所需声明，也不保证版本兼容。
- 与 `#if defined(__cpp_lib_...)` 配合可区分「头存在」与「特性可用」。
- 参数必须是头名或字符串字面量，不能是任意表达式；不同编译器的搜索路径影响结果。
- 用于可选依赖时，应在配置阶段记录结果，避免同一项目不同翻译单元看到不同的头可用性。

### 2.17 `#error`、`#warning` 与 `static_assert` 分别在哪一阶段生效？

- `#error message` 在预处理阶段产生诊断并终止，消息不要求引号，其余记号组成诊断消息。
- `#warning` 在 C++23 起成为标准，C++20 及更早使用需确认编译器支持。
- `_Pragma("...")` 可移植地在宏中发出实现定义的 pragma，避免 `#pragma` 不能由宏生成的问题。
- `static_assert` 在语义分析阶段求值，能检查类型与常量表达式，`#error` 只能检查预处理条件。
- 用 `#error` 阻止不支持的平台或标准版本时，应把条件写成正向判断，避免遗漏未知平台。

### 2.18 如何导出并比较预处理器的最终宏表？

- `g++ -dM -E -x c++ /dev/null` 输出编译器预定义宏与命令行 `-D` 的最终集合，便于比较环境差异。
- `-dD` 与 `-E` 同用会保留 `#define` 指令，能看到宏定义出现的位置与顺序。
- 宏污染常表现为系统头或第三方头定义了通用名，如 `min`、`check`，在包含后展开用户代码。
- 用 `-dM` 对比两个编译器的宏表，可发现 `_GLIBCXX_USE_CXX11_ABI` 等 ABI 相关开关。
- 不要依赖未文档化的内部宏；标准宏以 `__cplusplus`、`__STDC__` 等为准。

### 2.19 （场景）头文件循环包含会出现什么症状？

- A 包含 B、B 包含 A 时，include guard 使第二次包含被跳过，先遇到的声明可能不完整。
- 典型症状是类型未定义或不完整类型不能使用，错误位置常在另一个头文件。
- 处理方法是将共同依赖抽到第三个头，或用前向声明打断循环。
- 仅靠调整包含顺序能暂时通过编译，但会把依赖顺序问题留给下一个包含者。
- `-H` 的缩进层级可显示循环路径，`clang -E` 的行标记可确认实际展开顺序。

### 2.20 （场景）第三方头文件的宏与项目符号冲突，如何隔离？

- 第三方头定义的函数式宏可能与项目同名函数冲突，预处理后调用点被替换成意外表达式。
- 在包含第三方头前后用 `#pragma push_macro("name")` 与 `#pragma pop_macro("name")` 隔离宏。
- `#undef` 只删除当前宏定义，无法恢复被覆盖的旧定义；需要保存时用 `push_macro`。
- 把第三方头封装在单独的 `.cpp` 中，避免宏进入公共头，是更彻底的隔离。
- 编译错误指向宏展开位置时，用 `-E` 查看展开结果，再用 `-dM` 确认宏来源。

## 3. 词法语法语义分析与 AST

### 3.1 词法分析的最大匹配原则如何影响 `a+++++b`？

- 词法分析从左到右取最长可识别记号，`a+++++b` 被切为 `a`、`++`、`++`、`+`、`b`。
- 该序列只能解析为 `(a++)++ + b`，第二次 `++` 作用于右值，语义检查报错。
- `a---b` 切为 `a`、`--`、`-`、`b`，可解析为 `(a--) - b`。
- `y = x/*p` 中 `/*` 开始注释，而非除法后接解引用，这是最大匹配的另一后果。
- 词法阶段只保证记号合法，不判断运算符组合是否有意义，错误留给语法或语义分析。

### 3.2 预处理记号与 C++ 记号有何差别？

- 预处理记号比 C++ 记号宽松，允许头名、预处理数字与尚未分类的单个非空白字符。
- 预处理阶段识别 `#include` 的头名、宏名与 `##`，不要求知道类型或作用域。
- 转换到 C++ 记号发生在预处理之后，字符串拼接、转义与数字后缀在此阶段检查。
- `and`、`or`、`not` 是 C++ 的替代记号，在 C++ 记号层面分别与 `&&`、`||`、`!` 等价。
- `%:`、`<%` 等 digraph 在词法阶段映射为 `#`、`{`，在字符串与注释外生效。

### 3.3 C++11 起嵌套模板的 `>>` 如何解析？

- C++11 之前连续两个 `>` 会被词法分析为右移记号，嵌套模板需写成 `> >`。
- C++11 起在模板参数列表上下文中把 `>>` 拆成两个 `>`，由语法分析根据上下文处理。
- `std::vector<std::vector<int>>` 在 C++11 及以后合法，`>>=` 不参与该拆分。
- 括号表达式内的 `>>` 仍是右移，例如 `A<(1 >> 2)>`，上下文决定记号解释。
- 词法分析仍按最大匹配产生 `>>`，拆分发生在语法分析阶段，不能简单说词法器识别模板。

### 3.4 （陷阱）`Widget w();` 声明了什么？

```cpp
struct Widget {};
Widget w();    // function declaration
Widget v{};    // object
```

- `Widget w();` 被解析为函数声明：返回 `Widget`、名为 `w`、无参数，而非默认构造对象。
- `Widget v{};` 是 C++11 起的列表初始化，`Widget v;` 也可避免该歧义。
- `Widget w(Widget());` 也可被解析为函数声明，参数类型是返回 `Widget` 的函数。
- 函数指针与对象声明共享语法形式，语法分析在声明与表达式之间按声明优先的规则消解。
- 编译器诊断「function declared but never defined」或链接时缺少 `w` 定义，常是此陷阱的表现。

### 3.5 符号表在语义分析中记录哪些信息？

- 符号表记录名字、种类（命名空间、类、函数、变量、模板）、类型、作用域与链接性。
- 名称查找按作用域与 using 指令收集候选，重载决议再按参数类型与转换序列选择。
- 符号表在语义分析阶段建立，模板的依赖名可能延迟到实例化时才完成查找。
- 调试信息中的 `DW_TAG_subprogram` 与符号表不是同一结构，前者服务调试器。
- 目标文件 `.symtab` 只保留链接所需符号，局部变量与类型信息通常不进入。

### 3.6 声明与定义在 C 与 C++ 中有何差别？

- C 的 `int x;` 在文件作用域是暂定定义，同一翻译单元可有多个，最终合并为一个。
- C++ 的 `int x;` 是定义，同一翻译单元重复出现即违反 ODR，编译器报重定义；不同翻译单元各有一份时，链接器可能报多重定义。
- `extern int x;` 是声明，`extern int x = 1;` 是定义；C++ 中 带初始化的 `extern` 声明仍是定义。
- 函数声明可重复，函数定义在 C++ 中只能一次（`inline` 除外），在 C 中同一翻译单元也不允许重复定义。
- `-fcommon` 与 `-fno-common` 可改变 C 中未初始化全局变量的合并行为，GCC 10 起默认 `-fno-common`。

### 3.7 抽象语法树与具体语法树有何差别？

- 具体语法树保留括号、分号与关键字等全部记号，抽象语法树只保留语义相关结构。
- Clang 的 AST 同时保留源码位置与类型，节点如 `FunctionDecl`、`CallExpr`、`CXXRecordDecl`。
- `clang -Xclang -ast-dump` 打印树形结构，`-ast-dump-filter=name` 只显示匹配的声明。
- AST 是预处理之后的产物，宏展开后的节点带有 `SpellingLoc` 与 `ExpansionLoc` 两套位置。
- 编译器内部 AST 与语言服务器使用的 AST 可能因版本与序列化格式不同而不兼容。

### 3.8 如何导出 Clang AST 供工具处理？

- `clang++ -Xclang -ast-dump -fsyntax-only file.cpp` 无需生成目标文件即可查看 AST。
- `-Xclang -ast-dump=json` 输出 JSON，适合脚本处理；输出结构随 Clang 版本变化，脚本应固定版本。
- `-Xclang -ast-dump-filter=foo` 只保留名字含 `foo` 的声明，减少输出。
- `libclang` 与 `clang.cindex` 提供稳定的 C API，适合工具读取 AST；`clangd` 使用自己的索引。
- AST 转储不能替代语义检查，某些错误在转储之前已终止编译。

### 3.9 语义分析阶段具体检查什么？

- 语义分析完成类型检查、隐式转换、重载决议、访问控制与 `constexpr` 求值。
- ODR 检查跨翻译单元无法在单次编译完成，链接器只能发现符号层面的冲突。
- 名字查找与模板实例化可能触发额外的语义检查，错误位置常在实例化点而非定义点。
- `-Wconversion`、`-Wshadow`、`-Wodr` 属于不同层级的检查，`-Wodr` 需要 LTO 才能跨翻译单元。
- 诊断中的 note 链展示推导与实例化路径，`-fdiagnostics-show-template-tree` 可简化模板类型差异。

### 3.10 模板的两阶段查找如何划分检查时机？

- 模板定义在解析时检查非依赖名，实例化时检查依赖名，这两阶段合称两阶段查找。
- 非依赖名在定义点按普通名称查找，依赖名在实例化点结合 ADL 查找。
- MSVC 历史上对两阶段查找支持不完整，`/permissive-` 可启用更严格的一致模式。
- 缺失 `typename` 或 `template` 关键字会导致依赖名被误解析，错误常在实例化时出现。
- 两阶段规则使模板定义处可见的声明与实例化处可见的声明都影响结果，头文件顺序因此重要。

### 3.11 模板实例化发生在什么位置？

- 隐式实例化的点（point of instantiation）通常紧跟使用该特化的声明之后，具体位置由 `[temp.point]/1` 规定。
- 函数模板可能有两个实例化点：使用点之后与翻译单元末尾，用于处理后置声明。
- 类模板的成员函数在被 odr 使用时才实例化，未调用的成员不生成代码。
- 显式实例化 `template class Foo<int>;` 立即生成所有成员，可能增加目标文件体积。
- 实例化错误在实例化点报告，模板定义中的静态断言可能在使用点才触发。

### 3.12 （辨析）`extern template` 与显式实例化有何分工？

- `extern template class Foo<int>;` 抑制当前翻译单元的隐式实例化，要求别处提供显式实例化定义。
- 显式实例化定义 `template class Foo<int>;` 在一个翻译单元中生成代码，其他翻译单元只引用。
- 该机制减少重复实例化与编译时间，但若没有任何翻译单元提供定义，链接时报未定义符号。
- `extern template` 只抑制隐式实例化，不改变模板定义的可见性，也不替代显式实例化定义。
- 共享库边界使用时要确保实例化定义在库内可见，否则消费者可能生成自己的副本。

### 3.13 依赖名为何需要 `typename` 与 `template` 消歧？

- 依赖限定名默认按非类型解析，`typename T::value_type` 告诉编译器它是类型。
- 在模板中调用依赖成员模板需写 `obj.template foo<int>()`，否则 `<` 被当作小于号。
- C++20 起部分上下文可省略 `typename`，但依赖基类与复杂限定名仍建议显式写出。
- 缺少关键字时错误可能是「expected primary-expression」或比较表达式，位置偏离真实原因。
- 在 using 声明中引入依赖类型名时，同样需要 `typename`，例如 `using value_type = typename T::value_type;`。

### 3.14 SFINAE 发生在哪个阶段？

- SFINAE 指替换模板实参失败只把该候选从重载集中移除，不使整个编译失败。
- 失败必须发生在立即上下文，例如签名、返回类型或模板参数；函数体中的错误是硬错误。
- `std::enable_if_t`、`decltype` 与 `void_t` 常用于构造 SFINAE 条件。
- C++20 的 concepts 把约束写在声明上，错误信息更清晰，但底层仍涉及替换与约束检查。
- `requires` 表达式中的无效类型不直接报错，只使约束不满足。

### 3.15 `constexpr` 求值发生在编译期还是运行期？

- `constexpr` 函数在常量求值上下文中必须在编译期求值，例如数组边界、`static_assert` 与模板实参。
- 同一函数在运行期调用时可走普通代码路径，是否常量求值由使用上下文决定。
- `consteval` 强制立即求值，`constinit` 要求静态初始化，但不使变量成为常量。
- `static_assert` 在语义分析阶段检查，失败会终止编译；C++17 起消息可省略。
- 常量求值有步数限制，GCC 的 `-fconstexpr-ops-limit` 与 Clang 的 `-fconstexpr-steps` 可调整。

### 3.16 如何控制诊断信息的数量与格式？

- `-fmax-errors=N` 限制错误数量，`-Wfatal-errors` 在第一个错误后停止。
- `-fdiagnostics-color=auto` 控制颜色，持续集成日志通常设为 `never`。
- `-fno-diagnostics-show-caret` 去掉源码插入符，`-fno-diagnostics-show-option` 去掉警告对应选项。
- GCC 的 `-fdiagnostics-format=json` 输出机器可读诊断，字段随版本变化，使用前需固定版本。
- `-ftemplate-backtrace-limit=0` 关闭模板回溯深度限制，定位深层实例化错误。

### 3.17 `clang-tidy` 依赖哪些编译信息？

- `clang-tidy` 基于 Clang AST 与 `compile_commands.json`，需要与构建一致的宏与包含路径。
- `-checks=-*,bugprone-*` 选择检查项，`--fix` 应用修复，`--fix-errors` 连错误一起修。
- 缺少编译数据库时，工具使用回退参数，结果可能与真实构建不同。
- 检查在 AST 上运行，模板未实例化时只能看到模板定义，部分诊断不会触发。
- `clang-tidy` 不执行链接，无法发现符号冲突或库顺序问题。

### 3.18 `compile_commands.json` 为语言服务器提供什么？

- 该文件为每个源文件记录 `directory`、`command` 或 `arguments`、`file`。
- CMake 用 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` 生成，Meson 默认生成，Bear 可拦截构建生成。
- 语言服务器据此还原宏、包含路径与标准版本，缺少条目时回退到猜测，诊断会偏移。
- 生成数据库后修改 CMake 配置需重新生成，否则编辑器看到的选项与构建不一致。
- 路径应为绝对路径或相对 `directory` 解析，跨机器复制时需重新生成。

### 3.19 （场景）头文件缺失为何产生大量级联错误？

- 首个错误常是找不到头文件，后续大量语法错误是缺少声明后的级联结果。
- 用 `-H` 确认缺失头的搜索路径，检查 `-I` 是否指向构建目录而非源码目录。
- 生成头（如 `config.h`）未在编译前生成时，先修构建依赖，不要用 `-I` 临时指向源码树。
- 在持续集成中从干净目录构建，可使本地残留头文件造成的问题暴露出来。
- 只看第一个错误并修复后重编，比逐条处理级联错误更有效。

### 3.20 （场景）模板错误栈过长，如何定位真实错误？

- 实例化回溯从最外层使用点逐层指向模板定义，最内层通常是真实错误，最外层是触发实例化的调用。
- `-ftemplate-backtrace-limit=N` 限制 GCC 输出的实例化层数，`0` 表示不限制。
- Clang 的 `-fmacro-backtrace-limit` 控制宏展开，`-ftemplate-backtrace-limit` 控制模板。
- `-fdiagnostics-show-template-tree` 用树形展示模板实参差异，适合定位类型不匹配。
- 用 `static_assert` 与 `std::is_same_v` 在关键层提前检查，可把错误定位到语义层。

## 4. IR 与优化 pass

### 4.1 LLVM IR 由哪些层级组成？

- LLVM IR 的顶层是 `Module`，包含全局变量、函数声明与定义、元数据与目标三元组。
- 函数由基本块组成，基本块以终结指令（`br`、`ret`、`switch`）结束，形成控制流图。
- 指令是 SSA 形式，每条指令的结果有唯一名字，基本块可有标签与 PHI 节点。
- IR 有三种等价表示：内存中的对象、文本 `.ll`、位码 `.bc`；`llvm-as` 与 `llvm-dis` 可互转。
- 目标相关细节由 `DataLayout` 与 `Triple` 描述，`opt` 与 `llc` 分别负责优化与代码生成。

### 4.2 SSA 形式对优化意味着什么？

- SSA 要求每个变量只赋值一次，使用点直接引用定义，数据流显式化。
- 控制流汇合处用 `phi` 指令按前驱选择值，`phi` 必须位于基本块开头。
- `alloca` 提升把可变局部变量转换为 SSA 值，是优化流水线的早期步骤。
- SSA 简化常量传播、死代码消除与寄存器分配，但增加 PHI 维护成本。
- `-O0` 下变量通常保留为 `alloca` 内存对象，mem2reg 通常不运行，调试器可读取栈槽中的值。

### 4.3 GCC 的 GIMPLE 与 GENERIC 有何关系？

- GCC 前端生成 GENERIC，一种与语言无关的树表示，保留较多高层结构。
- GENERIC 经 gimplify 转换为 GIMPLE，语句被拆成三地址形式，控制流显式化。
- GIMPLE 在优化流水线中先以非 SSA 形式存在，随后转换为带 SSA 名字与 PHI 节点的形式。
- `-fdump-tree-gimple` 输出 GIMPLE，`-fdump-tree-optimized` 查看最终优化后的形态。
- GIMPLE 是 GCC 中端优化的输入，LLVM 对应的是 LLVM IR，两者不可直接互换。

### 4.4 如何用 GCC 的转储选项观察优化过程？

- `-fdump-tree-all` 输出所有中端 pass 的转储，文件数量多，适合定位某个优化何时发生。
- `-fdump-tree-optimized` 输出最终优化后的 GIMPLE，`-fdump-tree-cfg` 查看控制流图。
- `-fdump-rtl-expand` 与 `-fdump-rtl-final` 位于后端，分别对应 RTL 展开与最终汇编前形态。
- 转储文件名含 pass 名与编号，`-fdump-tree-<pass>-details` 可输出更细的决策信息。
- `-fopt-info` 以诊断形式报告优化成功或失败的位置，适合与 `-fdump` 配合。

### 4.5 `-O0`、`-O1` 与 `-Og` 的取舍是什么？

- `-O0` 默认不启用大多数优化，保留变量与语句边界，便于调试，但代码体积与运行时间较大。
- `-O1` 启用基础优化：常量传播、死代码消除、部分内联优化与尾调用，编译时间适中。
- `-Og` 以接近 `-O1` 的优化集合为基础，关闭影响调试体验的优化，GCC 文档建议用于调试构建。
- `-O0` 下仍可能发生必要的转换，如模板实例化、`constexpr` 求值与寄存器分配。
- 优化级别不保证具体 pass 集合，GCC 与 Clang 的 `-O2` 内容不同，跨编译器比较需看实际选项。

### 4.6 常量折叠与常量传播有何区别？

- 常量折叠在编译期直接计算 `2 + 3` 这类纯常量表达式，替换为 `5`。
- 常量传播把已知为常量的变量值代入使用点，可能跨基本块进行。
- 稀疏条件常量传播结合控制流，只在所有可达路径上一致时传播。
- 二者常与死代码消除配合：分支条件变为常量后，不可达分支被删除。
- `volatile` 访问与 `asm` 副作用会阻止相关传播，编译器不得改变可观察行为。

### 4.7 死代码消除在哪些层次进行？

- 死代码消除删除结果未被使用且无副作用的指令，以及不可达基本块。
- 函数级死代码消除在 IR 上进行，链接级回收依赖 `-ffunction-sections` 与 `--gc-sections`。
- 具有副作用的调用、`volatile` 访问与异常抛出点不能被随意删除。
- `__attribute__((used))` 与 `retain` 可阻止编译器或链接器删除特定符号。
- 调试信息可能引用已删除的变量，`-g` 下调试器显示「optimized out」即由此产生。

### 4.8 内联优化由哪些因素决定？

- 内联优化的收益取决于函数体大小、调用点数量、是否热路径与寄存器压力。
- `always_inline` 强制展开，`noinline` 禁止展开；两者都是实现扩展，标准只规定 `inline` 的 ODR 语义，函数体是否展开由实现决定。
- 递归函数通常只展开有限层，间接调用与虚调用需要去虚化后才能展开。
- LTO 让跨翻译单元的函数体可见，扩大内联优化的候选集。
- `-finline-limit`（GCC）与 `-mllvm -inline-threshold`（Clang）可调整阈值，具体含义由实现定义。

### 4.9 （辨析）`inline` 关键字会触发内联优化吗？

- `inline` 的核心作用是允许函数定义在多个翻译单元中出现，并满足 ODR 的合并要求。
- 编译器可以不展开任何 `inline` 函数，也可以展开未标记 `inline` 的函数。
- 类内定义的成员函数隐含 `inline`，与是否展开无关。
- `inline` 变量（C++17）保证跨翻译单元唯一实体，常用于头文件常量。
- 把 `inline` 当作性能开关会误导优化决策，应依赖 profile 与编译器报告。

### 4.10 循环不变量外提受哪些条件限制？

- 循环不变量外提把循环体内不随迭代变化且可安全执行的表达式移到循环前。
- 前提是表达式无副作用、不会抛出可观察异常，且外提不会引入新的异常或未定义行为。
- 别名分析决定内存读取能否外提：循环中可能有写操作修改同一对象时不能提升。
- `-fno-move-loop-invariants` 可关闭该优化，`-fdump-tree-lim` 查看 GCC 的决策。
- 外提可能增加寄存器压力，编译器会用代价模型权衡。

### 4.11 循环展开何时有效？

- 循环展开复制循环体以减少分支与递增开销，并为指令调度提供更大窗口。
- `-funroll-loops` 可显式启用循环展开，`-fno-unroll-loops` 关闭；默认是否启用由优化级别与实现决定。
- 展开因子由编译器根据迭代次数、代码体积与目标架构选择，`#pragma GCC unroll` 或 `#pragma unroll` 可给提示。
- 过度展开增加指令缓存压力与二进制体积，热循环外通常收益有限。
- 带复杂控制流或未知迭代次数的循环可能只做部分展开或循环剥离。

### 4.12 自动向量化需要满足什么条件？

- 自动向量化把标量循环转换为 SIMD 指令，前提是迭代间无依赖且访存对齐可知。
- `-O3` 在 GCC 中启用 `-ftree-vectorize`，GCC 12 起 `-O2` 也启用部分向量化。
- `-fopt-info-vec` 报告成功向量化的循环，`-fopt-info-vec-missed` 报告失败原因。
- `#pragma omp simd` 可断言迭代间无依赖，`-fopenmp-simd` 让编译器识别该指令；错误断言会导致结果错误。
- 别名、非连续访存、数据依赖与异常语义是常见阻碍，`restrict` 可帮助消除别名疑虑。

### 4.13 严格别名规则如何影响优化？

- 严格别名规则允许编译器假定不同类型指针不指向同一对象，从而重排读写。
- `restrict`（C）与 `__restrict`（C++ 扩展）进一步承诺同一对象只经该指针访问。
- `-fno-strict-aliasing` 关闭基于类型的别名假设，常用于内核与旧代码。
- `memcpy` 与 `union` 的类型双关在不同标准版本与编译器下有不同合法性，不能依赖未定义行为。
- 用 `-Wstrict-aliasing` 检查可疑代码，再对比 `-fno-strict-aliasing` 前后的生成代码，可确认是否命中别名优化。

### 4.14 `-O2` 与 `-O3` 的差异在哪里？

- `-O2` 侧重在编译时间与代码质量间平衡，启用大多数标量优化与部分向量化。
- `-O3` 增加向量化、循环变换与更激进的函数展开，代码体积通常增大。
- `-O3` 不一定更快，指令缓存与寄存器压力可能抵消收益，需基准测试。
- `-Os` 优化体积，Clang 的 `-Oz` 进一步压缩，`-Ofast` 放松浮点一致性。
- 不同 GCC 版本的 `-O2` 内容会变化，构建脚本不应假设固定 pass 集合。

### 4.15 LTO 如何改变优化边界？

- LTO 把 GIMPLE 或 LLVM IR 写入目标文件，链接时由插件合并并重新优化。
- `-flto` 开启 LTO，Clang 的 `-flto=thin` 使用 ThinLTO，兼顾并行与跨模块优化。
- `-ffat-lto-objects` 在目标文件中同时保留中间表示与本机代码，便于非 LTO 链接，代价是体积增大；`-fno-fat-lto-objects` 只保留中间表示。
- LTO 可发现跨翻译单元的内联优化机会与未使用符号，也使 ODR 违规更容易在链接或运行时暴露。
- 链接时需使用相同版本的插件与编译器，混合 GCC 与 Clang 的 LTO 目标通常不可链接。

### 4.16 PGO 的两个阶段各做什么？

- PGO 分两步：`-fprofile-generate` 插桩运行，`-fprofile-use` 用采集的计数优化。
- 采样式 PGO 用外部 profiler 数据，例如 GCC 的 `-fprofile-sample-use`，不需要插桩构建。
- 计数数据影响分支布局、内联优化与寄存器分配，热路径优先。
- profile 与源码或编译选项不一致时，GCC 会警告计数数据缺失或校验失败。
- 构建应固定工作目录与源路径，否则 profile 中的文件名无法匹配。

### 4.17 BOLT 在链接之后做什么？

- BOLT 在链接后的可执行文件上做布局优化，基于采样 profile 重排热代码与冷代码。
- 它不改变源码级语义，但依赖符号表与调试信息定位函数与基本块。
- `llvm-bolt app -o app.bolt -data=perf.fdata` 是典型调用形式，具体选项随版本变化。
- BOLT 可与 PGO 叠加，先由编译器优化，再由 BOLT 调整代码布局。
- 缺少 profile 或符号被 strip 时，优化效果下降，甚至无法识别函数边界。

### 4.18 优化构建中如何保留可调试性？

- `-Og` 在保持可调试性的前提下启用轻量优化，适合日常调试构建。
- `-O2 -g` 下变量可能被寄存器分配或常量传播消除，调试器显示「optimized out」。
- `-fvar-tracking` 与 `-fvar-tracking-assignments` 改善优化后变量位置信息，但增加编译时间与调试信息体积。
- `-g3` 包含宏定义，便于调试宏；`-gdwarf-5` 指定 DWARF 版本。
- 调试信息与优化级别不匹配时，行号可能指向错误的语句，断点行为也会异常。

### 4.19 `volatile` 能提供哪些保证？

- `volatile` 要求每次访问都实际发生，不能合并或删除，顺序相对于其他 `volatile` 访问保持不变。
- `volatile` 不提供线程间同步，也不阻止 CPU 或编译器把非 `volatile` 访问重排到其周围。
- 编译器屏障 `asm volatile("" ::: "memory")` 阻止编译器重排内存访问，但不生成硬件屏障。
- 原子类型与内存序用于线程同步，`volatile` 只适合内存映射 I/O 与信号处理等场景。
- `std::atomic` 的 `volatile` 重载在 C++20 弃用，混用会失去原子性保证。

### 4.20 （场景）`-O2` 下行为异常而 `-O0` 正常，如何排查？

- `-O2` 下编译器基于有符号溢出不发生、对象生命周期有效等假设优化，未定义行为会表现为结果异常或代码被删除。
- 用 `-fsanitize=undefined` 构建并运行，可在触发点报告具体类型与位置；`-fno-sanitize-recover` 让其终止。
- `-fsanitize=address` 检查越界与释放后使用，`-fsanitize=thread` 检查数据竞争。
- 对比 `-O0` 与 `-O2` 的行为只能定位嫌疑，不能证明代码正确；应消除未定义行为，而非关闭优化。
- `-fno-strict-aliasing` 可规避部分别名问题，但会降低优化机会，且不修复越界或生命周期错误。

## 5. 目标文件与重定位

### 5.1 ELF 文件类型有哪些，各自用于什么场景？

- `ET_REL` 是可重定位目标文件（`.o`），含节、符号表与重定位，地址尚未最终确定。
- `ET_EXEC` 是固定地址可执行文件，`ET_DYN` 是位置无关可执行文件或共享库，加载时基址可变。
- `ET_CORE` 是核心转储，记录进程内存与寄存器，供调试器分析。
- `readelf -h` 的 `Type` 字段给出文件类型，`e_entry` 给出入口地址。
- `file` 只能粗略识别，`readelf` 与 `objdump` 才能查看节与重定位细节。

### 5.2 ELF 的节与段有何区别？

- 节是链接器视角的最小组织单位，按权限与用途划分；段是加载器视角的映射单位。
- 链接脚本的 `SECTIONS` 把输入节放到输出节，`PHDRS` 或程序头把输出节聚合为段。
- `readelf -S` 查看节表，`readelf -l` 查看程序头与段到节的映射。
- 一个段可包含多个节，例如只读段包含 `.text`、`.rodata` 与 `.eh_frame`。
- 节表在运行时通常不加载，`strip` 可删除 `.symtab` 等非分配节而不影响执行。

### 5.3 `.text`、`.data`、`.bss`、`.rodata` 分别存放什么？

- `.text` 存可执行指令，`.rodata` 存只读常量，`.data` 存已初始化可写数据，`.bss` 存零初始化可写数据。
- `.bss` 不占文件空间，只记录大小，加载时由内核清零；`.data` 在文件中占实际字节。
- `const` 全局变量通常进入 `.rodata`，但局部 `const` 可能被优化掉或放在栈上。
- 字符串字面量在 GCC 中常进入 `.rodata.str1.1` 等合并节，链接器可合并相同内容以节省空间。
- `-fdata-sections` 与 `-ffunction-sections` 让每个对象或函数独立成节，配合 `--gc-sections` 回收。

### 5.4 `.symtab` 与 `.dynsym` 有何区别？

- `.symtab` 是静态符号表，包含局部符号与全局符号，不参与动态链接，可被 `strip` 删除。
- `.dynsym` 是动态符号表，保存导出与导入的动态符号，运行时链接器据此解析。
- `.dynstr` 存动态符号名，`.strtab` 存静态符号名；静态符号表被删除后，`.strtab` 常随之消失，`.dynstr` 在存在动态符号时必须保留。
- `nm` 默认读 `.symtab`，`nm -D` 读 `.dynsym`；`readelf --dyn-syms` 查看动态符号。
- 共享库导出符号受 `-fvisibility=hidden` 与版本脚本控制，未导出的符号不会进入 `.dynsym`。

### 5.5 ELF 符号绑定有哪些类型？

- `STB_LOCAL` 符号只在本目标文件可见，如 `static` 函数与 `.L` 标号。
- `STB_GLOBAL` 符号可被其他目标文件引用，同名强符号重复会导致多重定义。
- `STB_WEAK` 符号在存在强定义时被忽略，未定义弱符号可解析为零地址。
- `STB_GNU_UNIQUE` 用于 C++ `inline` 变量与某些模板静态成员，保证进程内唯一，属于 GNU 扩展。
- `readelf -s` 的 `Bind` 列显示绑定，`Vis` 列显示默认、隐藏或保护可见性。

### 5.6 （填空）`nm` 输出中的 `T`、`U`、`W`、`B` 分别表示什么？

- `T` 表示全局代码符号，`t` 表示局部代码符号，`D` 与 `d` 表示已初始化数据，`B` 与 `b` 表示 `.bss`。
- `U` 表示未定义引用，`W` 与 `w` 表示弱符号，`V` 与 `v` 表示弱对象。
- `R` 与 `r` 表示只读数据，`A` 表示绝对地址符号，`?` 表示未知类型。
- 小写表示局部符号，大写表示全局符号；`nm -C` 还原 C++ 名称。
- `nm` 对无符号表的文件输出 `no symbols`，此时应检查是否 `strip` 或只看 `.dynsym`。

### 5.7 `.rela.text`、`.rela.dyn` 与 `.rela.plt` 分别处理什么？

- `.rela.text` 记录代码节中的重定位，链接器据此修补调用、跳转与地址常量。
- `.rela.dyn` 记录动态重定位，如 GOT 表项与数据指针，在加载或运行时由动态链接器处理。
- `.rela.plt` 专用于 PLT 的跳转槽，惰性绑定下首次调用才解析符号。
- 静态链接时所有重定位在链接阶段解决，动态链接保留部分重定位到加载时。
- `readelf -r` 列出重定位的偏移、类型、符号与加数，`objdump -R` 查看动态重定位。

### 5.8 REL 与 RELA 两种重定位格式有何差别？

- `REL` 格式只存偏移、类型与符号索引，加数隐含在被修改位置的原值中。
- `RELA` 格式显式存加数 `r_addend`，链接器无需从被修改位置读取加数，x86-64 使用 `RELA`。
- 32 位 x86 的 ELF 常用 `REL`，AArch64 使用 `RELA`，具体由 psABI 规定。
- `R_X86_64_PC32` 的计算需要 `S + A - P`，其中 `A` 来自 `r_addend`，`P` 是重定位位置。
- 混合 `REL` 与 `RELA` 的工具链假设不同，手写汇编或自定义链接脚本时需确认格式。

### 5.9 x86-64 常见重定位类型如何计算？

- `R_X86_64_64` 写入 64 位绝对地址，`R_X86_64_32` 写入 32 位零扩展地址，超出范围会报错。
- `R_X86_64_PC32` 写入相对当前指令的 32 位位移，常用于同一可执行文件内的直接引用。
- `R_X86_64_PLT32` 指向 PLT 条目，配合延迟绑定与符号抢占使用，外部函数调用常用。
- `R_X86_64_GOTPCREL` 用于通过 GOT 访问外部数据，位置无关代码依赖它。
- 链接报 `relocation R_X86_64_32S against ... can not be used when making a PIE object` 时，说明绝对重定位与 PIE 冲突。

### 5.10 COMDAT 组如何合并重复定义？

- COMDAT 组把多个翻译单元中的同一实体（模板实例化、`inline` 函数、虚表）标记为可合并。
- 链接器保留一个组，丢弃其余副本，组内符号与重定位一起处理。
- ELF 用 `.group` 节与 `GRP_COMDAT` 标志，段名常为 `.text._Z3fooIiEvT_`。
- `-fno-weak` 关闭 GCC 对弱符号的支持，可能改变模板与 inline 实体的链接行为，主要用于测试。
- ODR 违规时不同翻译单元的 COMDAT 副本内容不一致，链接器通常不报错，运行时行为由保留的副本决定。

### 5.11 强符号与弱符号冲突时链接器如何选择？

- 链接器在多个强定义中选择一个会报错；强定义与弱定义并存时选强定义。
- 多个弱定义并存时选第一个遇到的，其他被忽略，具体顺序依赖命令行与目标文件顺序。
- 未定义弱符号可解析为零地址，代码必须检查后再使用，否则解引用会崩溃。
- 弱符号常用于可替换的实现与可选功能，跨平台行为由链接器与目标格式决定。
- `__attribute__((weak))` 是 GCC 与 Clang 扩展，MSVC 用 `__declspec(selectany)` 或 `alternatename`。

### 5.12 `weakref` 与 `weak` 有何不同？

- `__attribute__((weakref("target")))` 声明一个弱引用别名，目标不存在时符号为零。
- `weakref` 是引用别名，`weak` 是带弱绑定的定义，两者在符号表与链接行为上不同。
- 使用前必须检查地址，直接调用未解析的弱引用会导致空指针跳转。
- 该属性是 GCC 扩展，Clang 部分支持，标准 C++ 没有对应设施。
- 动态库中弱引用的解析受加载顺序影响，`LD_BIND_NOW` 改变绑定时机，不能用于强依赖。

### 5.13 符号可见性如何影响二进制体积与加载？

- `-fvisibility=hidden` 默认隐藏符号，减少动态符号表与符号抢占开销，加快加载。
- 需要导出的符号用 `__attribute__((visibility("default")))` 或版本脚本显式标记。
- `-fvisibility-inlines-hidden` 隐藏 `inline` 函数，避免多个库导出同名弱符号。
- 隐藏符号仍可在静态链接时使用，但不进入 `.dynsym`，无法被其他共享库解析。
- `readelf --dyn-syms` 与 `nm -D` 可验证导出集合，`objdump -T` 显示动态符号表。

### 5.14 静态库的链接顺序为何重要？

- 链接器从左到右扫描命令行，归档库只提取当前未定义符号所需的成员。
- 若库 A 依赖库 B，命令行应写 `-lA -lB`；顺序颠倒时 B 先扫描，A 的未定义无法回查 B。
- `--start-group` 与 `--end-group` 让链接器反复扫描组内库，解决循环依赖，代价是链接时间增加。
- `--whole-archive` 强制包含归档全部成员，常用于注册机制与插件，之后用 `--no-whole-archive` 恢复。
- `-Wl,--trace-symbol=foo` 可追踪符号由哪个目标文件或库提供。

### 5.15 `--gc-sections` 删除哪些节？

- `-ffunction-sections` 与 `-fdata-sections` 让每个函数与数据对象独立成节，为细粒度回收做准备。
- `-Wl,--gc-sections` 从入口、`KEEP` 指令与动态引用等根集合出发，删除不可达的节。
- 未标记 `used` 或未从入口可达的函数可能被删除，反射式注册与脚本调用需保留。
- `-Wl,--print-gc-sections` 列出被删除的节，便于核查误删。
- 回收发生在链接阶段，静态库中未被引用的成员本来就不会被提取，二者作用层次不同。

### 5.16 如何用 `readelf` 检查节、符号与重定位？

- `readelf -S` 查看节头表，`-l` 查看程序头，`-s` 查看符号表，`-r` 查看重定位。
- `readelf -d` 查看动态节，`--dyn-syms` 只看动态符号，`-n` 查看 note 节。
- `readelf -x .rodata` 以十六进制转储节内容，`-p .comment` 查看编译器版本字符串。
- `readelf --debug-dump=info` 解析 DWARF 调试信息，`--debug-dump=decodedline` 查看行号表。
- `readelf` 不依赖 BFD，读取畸形文件时比 `objdump` 更稳健，适合分析崩溃产物。

### 5.17 （场景）同名符号为何在链接时报多重定义？

- 错误 `multiple definition of 'foo'` 表示多个目标文件提供了同名强符号。
- 常见原因包括头文件中定义非 `inline` 函数或全局变量、同一源文件被编译两次、C 与 C++ 混编时同一符号在两侧各有一份定义。
- 用 `nm -A *.o | grep ' T foo'` 定位提供者，再用 `ld --trace-symbol=foo` 查看链接顺序。
- C++ 中把定义移入 `.cpp`、在头文件用 `inline` 或 `static` 可消除冲突，后者会带来每翻译单元副本。
- `-fcommon` 可让 C 的未初始化全局变量合并，但会使真实重复定义不易被发现，不建议作为修复手段。

### 5.18 （场景）`undefined reference` 如何定位到具体库？

- `undefined reference to 'foo'` 表示链接器找不到符号定义，声明存在不代表定义存在。
- 用 `nm -C` 检查目标文件是否为 `U`，用 `nm -A` 在库中搜索 `T foo`。
- C++ 名称修饰导致 C 库符号找不到时，用 `extern "C"` 或 `c++filt` 还原名字。
- 静态库顺序、缺少 `-l`、`--as-needed` 未记录库依赖都可能导致未定义，`-Wl,--verbose` 可查看搜索路径。
- 模板成员未实例化时链接错误指向成员函数，需显式实例化或把定义放回头文件。

### 5.19 （场景）发布二进制缺少调试信息，如何确认与补救？

- `-g` 生成调试信息，默认 DWARF 版本由编译器决定，`-gdwarf-5` 可显式指定。
- `strip` 删除 `.symtab` 与 `.debug_*`，`strip --strip-debug` 只删调试节，保留符号表。
- 分离调试信息用 `objcopy --only-keep-debug app app.debug` 与 `--add-gnu-debuglink`。
- 调试器找不到源码时用 `set substitute-path` 或 `-fdebug-prefix-map` 修正路径。
- `readelf --debug-dump=info` 与 `dwarfdump` 可确认调试信息是否存在及编译单元列表。

### 5.20 （场景）二进制体积异常增大，如何归因？

- `size` 查看 `.text`、`.data`、`.bss` 的总量，`bloaty` 按节、符号与编译单元归因。
- `-Os` 优化体积，Clang 的 `-Oz` 进一步压缩，`-ffunction-sections` 与 `--gc-sections` 删除未用代码。
- 模板实例化与 `inline` 函数重复是常见来源，`nm --size-sort -C` 可列出大符号。
- 调试信息与符号表可能远大于代码，发布包应分离或 strip，但保留可解析的构建 ID。
- 静态链接会引入库中未使用的成员，`-Wl,--gc-sections` 与按需链接可减小体积。

## 6. 符号表与链接器

### 6.1 符号表条目包含哪些字段？

- ELF 符号表项为 `Elf64_Sym`，含 `st_name`（字符串表偏移）、`st_info`（绑定与类型）、`st_other`（可见性）、`st_shndx`（所在节索引）与 `st_value`、`st_size`。
- 绑定字段取 `STB_LOCAL`、`STB_GLOBAL`、`STB_WEAK`，GCC 另有 `STB_GNU_UNIQUE`，用于保证模板静态数据在进程内唯一。
- 类型字段区分 `STT_OBJECT`、`STT_FUNC`、`STT_SECTION`、`STT_FILE`、`STT_TLS` 与 `STT_GNU_IFUNC`，`STT_NOTYPE` 常见于汇编标签。
- `st_shndx` 为 `SHN_UNDEF` 表示该符号在本目标文件中没有定义，为 `SHN_ABS` 表示绝对值，为 `SHN_COMMON` 表示暂定定义。
- `.symtab` 保存全部符号，供静态链接使用；`.dynsym` 只保存动态链接需要的符号，二者由 `readelf -s` 与 `readelf --dyn-syms` 分别查看。
- `strip` 删除 `.symtab` 后 `.dynsym` 仍在，动态库的导出符号不受影响。

### 6.2 `nm` 的输出字母如何解读？

- `U` 表示未定义，`T` 与 `t` 分别表示全局与局部的代码符号，`D` 与 `d` 对应已初始化数据，`B` 与 `b` 对应 `.bss`。
- `W` 与 `w` 表示弱符号，`V` 与 `v` 表示弱对象，`C` 表示 COMMON 符号，`R` 与 `r` 表示只读数据。
- 小写字母表示局部符号，大写表示全局符号，`nm -C` 对 C++ 符号做反修饰，`nm -D` 只列出动态符号。
- `nm -u` 只显示未定义符号，适合在链接前检查依赖；`nm --defined-only` 用于核对导出清单。
- `nm` 读取的是符号表而不是重定位表，剥离符号表的可执行文件只给出 `no symbols`，此时需要 `readelf -r` 或反汇编。
- `objdump -t` 给出相同信息并附带节索引，`readelf -sW` 不截断长符号名。

### 6.3（辨析）未定义引用与运行时未定义符号的区别？

- 静态链接阶段的 `undefined reference to 'foo'` 由链接器 `ld` 或 `lld` 报告，表示所有输入目标文件与库中都没有 `foo` 的定义。
- 若 `foo` 来自动态库，链接时给出 `-lfoo` 即可通过，符号在 `.dynsym` 中标记为未定义，由动态链接器在加载时解析。
- 运行时错误形如 `undefined symbol: foo`，由 `ld.so` 在重定位阶段报告，原因通常是库未加载、版本不匹配或符号被隐藏。
- 共享库默认允许未定义符号，`-Wl,--no-undefined` 或 `-z defs` 可把这类问题提前到链接阶段。
- `dlopen` 的插件在 `RTLD_NOW` 下立即解析全部符号，`RTLD_LAZY` 推迟函数符号，报错时机随选项变化。
- 排查时先区分错误来源：`ld` 的报错带输入文件列表，`ld.so` 的报错带库名与版本节点。

### 6.4 强弱符号的解析规则是什么？

- 多个强定义同时出现时链接器报 `multiple definition`，C++ 中同名的非 inline 函数与已初始化全局变量都属于强符号。
- 一个强定义与若干弱定义共存时选择强定义；只有弱定义时选择链接顺序中先出现的一个。
- 弱引用使用 `__attribute__((weak))` 声明，未找到定义时地址为 0，调用前必须判空，否则跳到地址 0。
- 弱符号适合提供可被覆盖的默认实现，例如日志钩子、平台桩函数与可选的功能入口。
- C 的暂定定义在 `-fcommon` 下进入 COMMON，多个目标文件的同名暂定定义在链接时合并；GCC 10 起默认 `-fno-common`，同名定义直接冲突。
- 强弱规则只作用于静态链接；动态链接的符号抢占由加载顺序与可见性决定，与弱符号规则不同。

```cpp
extern "C" int hook(void) __attribute__((weak));

int run() {
    if (hook != nullptr) {
        return hook();
    }
    return 0;
}
```

### 6.5（场景）升级到 GCC 10 后出现大量多重定义的原因？

- GCC 10 起默认 `-fno-common`，此前 C 的暂定定义 `int counter;` 生成 COMMON 符号，多个目标文件可以共存并在链接时合并。
- 改为 `-fno-common` 后每个暂定定义进入 `.bss` 并成为强符号，两个目标文件同时定义即报 `multiple definition of 'counter'`。
- 头文件中写 `int counter;` 并被多个源文件包含是最常见的触发方式，正确做法是头文件用 `extern int counter;`，在一个源文件中定义。
- 临时恢复可用 `-fcommon`，但会掩盖真实的重复定义；`-Wl,--warn-common` 可以在合并时给出警告。
- C++ 没有 COMMON 机制，同样的写法在 C++ 中一直是多重定义错误；C++17 的 inline 变量通过 COMDAT 保证唯一。
- 排查用 `nm` 查看 `C` 与 `B` 字母，或 `readelf -s` 查看 `SHN_COMMON`，确认符号来源后再修改声明。

### 6.6 链接顺序为什么影响静态库的符号解析？

- 传统 Unix 链接器从左到右扫描输入，维护未定义符号集合，遇到归档文件时只抽取能解决当前未定义符号的成员。
- 若库出现在引用它的目标文件之前，扫描库时未定义集合为空，库中成员不会被抽取，随后出现的引用无人解决。
- 修正方式是把库放在目标文件之后，多个库按依赖方向排列，被依赖的库放在右边。
- 循环依赖用 `--start-group` 与 `--end-group` 包裹，链接器反复扫描组内归档直到没有新符号被解析。
- `--whole-archive` 强制抽取全部成员，会增大体积并可能引入重复定义，适合注册表式的静态初始化。
- CMake 的 `target_link_libraries` 按声明顺序生成链接行，`LINK_INTERFACE_MULTIPLICITY` 用于处理静态库循环依赖。

### 6.7 `-u` 选项解决什么问题？

- `-u sym` 把 `sym` 加入未定义集合，强制链接器从归档中抽取定义该符号的成员，即使没有其他引用。
- 该选项常用于保留构造函数、注册项或插件入口，避免因没有显式引用而被归档忽略。
- 与 `--gc-sections` 配合时，`-u` 指定的符号同时成为根，其所在节不会被回收。
- `-Wl,-u,symbol` 是 GCC 驱动转发形式，顺序上需要放在归档之前或与之同组。
- 对共享库无效：动态库的全部导出符号本来就参与解析，`-u` 不改变 `.dynsym` 的内容。
- `--require-defined=sym` 要求符号最终必须有定义，否则报错，适合检查配置宏是否生效。

### 6.8 `--gc-sections` 的根集合如何确定？

- 根包括入口符号 `_start`、`-u` 与 `--undefined` 指定的符号、动态导出符号、`KEEP` 指令保护的节，以及 `.init_array` 等由启动代码引用的节。
- 从根出发按重定位关系遍历节图，未被访问且带 `SHF_ALLOC` 的节被丢弃。
- 回收单位是节，默认 `.text` 整体保留；配合 `-ffunction-sections -fdata-sections` 才能细化到函数与变量。
- 未加 `SHF_ALLOC` 的调试节不参与回收，`.debug_*` 仍会保留，需要 `strip --strip-debug` 单独处理。
- `--gc-keep-exported` 保留所有导出符号，适合共享库；可执行文件通常不需要该选项。
- `--print-gc-sections` 列出被删除的节，用于确认回收是否符合预期。

### 6.9 `-ffunction-sections` 与 `-fdata-sections` 为何必须配合 `--gc-sections`？

- 默认编译把全部函数放进一个 `.text`，回收只能整节进行，删除一个函数等于删除全部。
- `-ffunction-sections` 为每个函数生成独立节，`-fdata-sections` 对变量做同样处理，节名带符号名后缀。
- 节数量增加会放大目标文件与链接输入，链接时间与重定位数量随之上升，通常在发布构建启用。
- 静态库成员被抽取后，未被引用的函数才能被逐节删除；没有这两个选项时只能删除整个未被抽取的成员。
- C++ 的模板实例与 inline 函数位于 COMDAT 组，回收按组进行，组内节一同保留或删除。
- 检查手段是 `readelf -S` 观察节名，或对比开启前后的 `size -A` 输出。

### 6.10 `KEEP` 解决什么回收问题？

- 链接脚本中 `KEEP(*(.init_array))` 把匹配的输入节标记为根，即使没有重定位引用也不会被 `--gc-sections` 删除。
- 函数指针表、中断向量表与注册表只通过数据引用，链接器无法从根到达时会被误删。
- `KEEP` 只影响回收与孤儿节分配，不改变节的地址与属性。
- 未使用链接脚本时，`__attribute__((used))` 让编译器保留定义，`retain` 属性（GCC 11 起）进一步设置 `SHF_GNU_RETAIN`，由较新的链接器识别。
- 回收过度表现为运行时不执行初始化函数或跳转到错误地址，用 `--print-gc-sections` 可以确认节是否被删。
- 回收不足则体积偏大，`KEEP` 的范围应尽量窄，避免整节保留。

### 6.11 链接脚本的 `MEMORY` 与 `SECTIONS` 分别负责什么？

- `MEMORY` 声明存储区域的名字、起始地址、长度与属性，例如 `ROM (rx) : ORIGIN = 0x08000000, LENGTH = 256K`。
- `SECTIONS` 用输入节模式匹配目标节，`>` 指定 VMA 所在区域，`AT>` 指定 LMA，`. = ALIGN(8)` 推进位置计数器。
- 位置计数器 `.` 表示当前地址，赋值可以制造空洞或定义符号，符号在 C 中用 `extern` 声明后取地址。
- 输出节由输入节按模式收集，`*(.text .text.*)` 同时匹配基础节与 `-ffunction-sections` 生成的节。
- 未匹配的输入节成为孤儿节，链接器按名称与属性放置并给出警告，`--orphan-handling=warn` 可显式检查。
- `MEMORY` 只定义区域，不负责放置；区域溢出在链接阶段报 `region 'RAM' overflowed`。

### 6.12（场景）链接脚本中 VMA 与 LMA 不一致会导致什么问题？

- 嵌入式镜像常把 `.data` 的 VMA 设在 RAM，LMA 设在 Flash，启动代码需要把初值从 LMA 复制到 VMA。
- 若启动代码没有完成复制，全局变量的初值是 Flash 中的内容或随机值，表现为初始化失效。
- `objcopy -O binary` 按 LMA 生成镜像，VMA 与 LMA 的差异决定镜像中是否出现填充空洞。
- 使用 `AT>` 后需要检查 `.data` 的 `LOADADDR` 符号与复制循环的起止地址是否一致。
- 链接器不会自动生成复制代码，启动文件需要手工配合。
- 排查时用 `readelf -S` 与 `objdump -h` 对比 VMA 与 LMA 两列。

### 6.13 版本脚本如何控制导出符号？

- 版本脚本语法为 `VERS_1.0 { global: foo; bar; local: *; };`，`local: *` 把未列出的符号降为局部。
- 链接时用 `-Wl,--version-script=lib.map`，生成带版本节点的 `.dynsym`，符号显示为 `foo@@VERS_1.0`。
- 未写 `local: *` 时，未列出的符号仍按原可见性导出；脚本显式列出的符号优先。
- 版本脚本同时写入 `.gnu.version_d`，供动态链接器按 `DT_VERNEED` 检查依赖版本。
- 只有 `local: *;` 的脚本隐藏全部符号，常用作最小导出面。
- 与 `-fvisibility=hidden` 相比，版本脚本在链接阶段生效，不需要重新编译，但不能改变代码生成。

### 6.14 `.symver` 如何为同一函数提供多个版本？

- 在汇编或 C 源码中写 `__asm__(".symver foo_v1,foo@VERS_1.0")`，把实现绑定到指定版本节点。
- `foo@VERS_1.0` 是非默认版本，`foo@@VERS_1.0` 是默认版本，链接新代码时解析到默认版本。
- 旧版本实现与新版本实现可以共存于同一共享库，调用方按链接时记录的版本需求选择。
- 版本节点需要在版本脚本中声明，否则 `.symver` 会产生未定义的版本引用。
- `dlvsym(handle, "foo", "VERS_1.0")` 允许运行时显式选择版本，`dlsym` 只返回默认版本。
- 该机制由 GNU 扩展提供，不属于 ELF 标准，其他链接器与平台的支持程度不同。

### 6.15 符号版本后缀 `@GLIBC_2.14` 表示什么？

- `readelf --dyn-syms` 输出中的 `memcpy@GLIBC_2.14` 表示该未定义符号要求版本节点 `GLIBC_2.14`。
- 版本需求记录在 `.gnu.version_r`，对应 `DT_VERNEED` 项，动态链接器加载时逐项检查。
- 同一符号可以有多个版本实现，旧版本用于兼容旧二进制，新版本修复语义或性能问题。
- 构建环境比运行环境新时，可能引用运行环境不存在的版本，报 `version 'GLIBC_2.34' not found`。
- 查看依赖版本下限可用 `objdump -T` 与 `readelf -V`，交叉检查目标系统的 `libc.so.6`。
- 规避方式是在较旧的发行版或容器中构建，而不是在运行环境升级 `glibc`。

### 6.16 `--wrap` 的用途与边界？

- `-Wl,--wrap=malloc` 把对 `malloc` 的未定义引用改写为 `__wrap_malloc`，原符号可通过 `__real_malloc` 调用。
- 该选项只影响链接阶段的引用解析，对已经定义 `malloc` 的目标文件与已被 inline 优化的调用无效。
- 常用于单元测试替换系统调用、统计分配次数、注入故障，避免修改被测源码。
- 包装函数必须与原名具有相同的签名与调用约定，否则参数传递与返回值会错位。
- 对动态库内部的调用无效：共享库内部的调用已经绑定，`--wrap` 不能拦截。
- 与 LTO 同时使用时，inline 优化可能把调用提前展开，包装点消失，需要关闭相关优化。

### 6.17 `--defsym` 在什么场景下使用？

- `-Wl,--defsym=__stack_top=0x20001000` 在链接时定义一个绝对符号，供启动代码引用。
- 符号值可以是常量或另一个符号加偏移，表达式在链接脚本的表达式语法内求值。
- 该符号没有类型与大小，`nm` 显示为 `A`，调试器只能看到地址。
- 适合在没有链接脚本的小型工程中提供栈顶、堆边界或版本字符串地址。
- 与链接脚本中的赋值冲突时，后处理者覆盖先处理者，行为依赖链接器实现。
- 现代工程更倾向用链接脚本或 `PROVIDE`，`--defsym` 适合一次性覆盖。

### 6.18 map 文件能回答哪些问题？

- `-Wl,-Map=app.map` 生成映射文件，列出每个输入节到输出节的归属、地址与大小。
- 归档成员被抽取的原因记录在 `Archive member included` 段，可直接定位是哪个未定义符号拉入了成员。
- `Discarded input sections` 段对应 `--gc-sections` 的回收结果，`Memory Configuration` 段给出区域布局。
- 符号表部分列出链接脚本定义的符号与绝对符号，`--defsym` 与 `PROVIDE` 的结果在此可见。
- 体积分析可以按输出节汇总，`.text`、`.rodata`、`.data`、`.bss` 的占比一目了然。
- map 文件不包含调试信息与运行时行为，不能替代 `size` 与性能分析。

### 6.19 `relocation truncated to fit` 的成因？

- 重定位类型如 `R_X86_64_PC32` 只有 32 位有符号偏移，目标地址与指令的距离超过约 2 GiB 时报错。
- 常见于超大 `.text`、链接脚本把节放到相距很远的区域，或 `-mcmodel=small` 下使用高地址。
- x86-64 可改用 `-mcmodel=medium` 或 `-mcmodel=large`，代价是更多指令与寄存器占用。
- 部分嵌入式架构提供 `-mlong-calls`，让调用经过跳板；RISC-V 的 `--relax` 与 `--no-relax` 影响跳转 Relaxation，不解决 x86 的距离问题。
- 可把热点代码放到近地址，或调整链接脚本使调用方与被调方落在同一 2 GiB 范围内。
- 报错信息包含重定位类型、符号名与节名，先确认是代码距离还是数据放置问题。

### 6.20（场景）多个目标文件定义同一符号但链接未报错，可能的原因？

- 符号被声明为弱符号，多个弱定义按链接顺序取第一个，其余被忽略。
- 链接选项包含 `--allow-multiple-definition`（旧写法 `-z muldefs`），链接器取第一个定义且不报错。
- 定义位于 COMDAT 组（模板实例、inline 函数），链接器按组去重，保留一份副本。
- 两个定义所在的目标文件没有被同时链接，例如其中一个只存在于未被抽取的归档成员中。
- 符号被版本脚本或可见性设置降为局部，不同库中的同名符号互不冲突。
- 排查用 `nm -A` 列出所有输入中的定义，或用 `ld -y symbol` 跟踪符号解析过程。

## 7. 静态库与动态库

### 7.1 归档文件的结构与索引如何工作？

- `ar` 生成的 `.a` 是若干目标文件加符号索引的容器，成员按顺序存放，头部记录成员名、大小与偏移。
- GNU 格式的索引名为 `/`，BSD 格式为 `__.SYMDEF`，索引记录符号到成员的反向映射，供链接器快速抽取。
- `ar rcs libfoo.a a.o b.o` 中的 `s` 生成索引，`ranlib` 单独完成同一动作；缺少索引时链接器仍需线性扫描。
- `ar t` 列出成员，`ar x` 抽取成员，`ar d` 删除成员；传统格式限制成员名长度，GNU 格式用扩展名表保存长名。
- 归档本身不进行链接，成员中的未定义符号保持原样，重复定义的检查推迟到最终链接。
- 嵌套归档不会被链接器递归抽取，内层成员无法解析外层引用，出现嵌套通常意味着构建脚本有误。

### 7.2 静态库与共享库在链接阶段的差别？

- 静态库在链接时抽取成员并复制进可执行文件，产物不依赖 `.a`；共享库只记录 `DT_NEEDED`，符号在加载时解析。
- 静态库的符号解析遵循从左到右的抽取规则，共享库默认全部导出符号参与解析，不受抽取顺序影响。
- 同一个 `.a` 被多个可执行文件使用时各自复制一份，代码与只读数据无法在进程间共享。
- 共享库有 SONAME 与版本节点，升级可以只替换文件；静态库升级必须重新链接。
- 静态链接的可执行文件启动更快，不依赖 `ld.so` 查找路径，但体积更大，静态链接 `glibc` 还会限制 NSS 与 `dlopen` 功能。
- 混合链接用 `-Wl,-Bstatic` 与 `-Wl,-Bdynamic` 切换，顺序错误会导致意外的静态或动态绑定。

### 7.3（场景）只引用一个函数为何把整个目标文件链入？

- 归档的抽取单位是成员，即编译后的目标文件，链接器无法只取其中一个函数。
- 目标文件中的其他函数、静态数据与初始化代码随成员一起进入产物，`-ffunction-sections` 只帮助后续回收。
- 把工具函数拆成更小的源文件可以减小抽取粒度，代价是编译单元增多。
- 使用 `-Wl,--gc-sections` 并配合函数级节，可以删除未被引用的函数，但不能避免成员中的静态初始化。
- 构造函数随成员进入 `.init_array`，即使没有调用也会在启动时执行，可能带来副作用。
- 用 map 文件的 `Archive member included` 段确认是哪个符号拉入了成员。

### 7.4 PIC 与 PIE 的区别？

- `-fPIC` 生成位置无关代码，通过 GOT 与 PLT 访问外部符号与全局数据，可被加载到任意地址。
- `-fpie` 用于可执行文件，允许编译器利用符号在可执行文件内绑定的假设，少一次 GOT 间接。
- `-pie` 让链接器生成 `ET_DYN` 可执行文件，加载时随机化基址；`-no-pie` 生成固定地址的 `ET_EXEC`。
- 共享库必须使用 PIC；可执行文件是否 PIE 由发行版默认值决定，Ubuntu 等默认开启。
- PIE 的代价是地址随机化带来的重定位处理与启动开销，以及部分架构上寄存器占用增加。
- 检查用 `readelf -h` 看类型，`readelf -d` 看是否存在 `TEXTREL`，后者表示代码段含绝对重定位。

### 7.5 `-fPIC` 在 x86-64 上的主要开销？

- 访问外部全局变量走 GOT，多一次内存加载；调用外部函数走 PLT，首次调用还要解析。
- 编译器使用 `%rip` 相对寻址，x86-64 不需要像 x86-32 那样牺牲一个通用寄存器保存 GOT 基址。
- 默认可见性的符号仍可能被抢占，编译器不能把地址常量折叠，循环中的地址计算可能重复加载 GOT。
- `-fno-semantic-interposition` 允许编译器假设库内调用不被替换，可恢复部分内联优化与常量传播。
- 隐藏可见性把符号绑定到本库，访问可直接用 `%rip` 相对寻址，减少 GOT 与 PLT 使用。
- `-fPIC` 与 `-fpic` 的差别在 GOT 大小限制，x86-64 上通常没有区别，其他架构上 `-fpic` 可能报错。

### 7.6 动态链接器的启动流程？

- 内核加载 ELF 后读取 `PT_INTERP`，把控制权交给 `/lib64/ld-linux-x86-64.so.2`。
- `ld.so` 读取主程序的 `DT_NEEDED`，按搜索路径加载依赖，递归处理依赖的依赖，形成加载顺序。
- 加载完成后进行重定位：先处理 `R_X86_64_RELATIVE` 等本地重定位，再解析 `R_X86_64_GLOB_DAT` 与 `JUMP_SLOT`。
- 构造函数按依赖顺序逆序执行，`DT_INIT`、`DT_INIT_ARRAY` 与 `__attribute__((constructor))` 都在此阶段运行。
- 符号解析遵循全局作用域，先加载的库优先；`RTLD_LOCAL` 打开的库不进入全局作用域。
- `LD_DEBUG=libs,reloc,bindings` 输出加载与解析过程，`ldd` 只列出依赖，不运行程序主体。

### 7.7 PLT 与 GOT 的惰性绑定如何完成？

- 调用外部函数时先生成对 PLT 桩的调用，桩的第一条指令跳转到 GOT 中对应的槽位。
- 首次调用时槽位指向桩内下一条指令，该指令把符号索引压栈并跳到 PLT0。
- PLT0 调用 `_dl_runtime_resolve`，动态链接器查找符号、写入 GOT，然后跳转到真实函数。
- 后续调用直接经 GOT 跳到目标，只剩一次间接跳转；`-z lazy` 是默认策略，`-z now` 在启动时解析全部。
- 惰性绑定把解析成本推迟到首次调用，但首次调用延迟不可预测，实时系统通常选择 `-z now`。
- 查看重定位用 `readelf -r`，`JUMP_SLOT` 对应函数，`GLOB_DAT` 对应数据。

### 7.8 RELRO 与 `-z now` 的关系？

- 启用 `-z relro` 时链接器把 `.got` 等重定位节放入 `PT_GNU_RELRO`，加载完成后设为只读。
- 部分 RELRO 只保护 `.got.plt` 之外的 GOT；`-z now` 配合 `-z relro` 构成完整 RELRO，`.got.plt` 也在启动时解析并只读。
- 完整 RELRO 阻止改写 GOT 劫持控制流，代价是启动时完成全部符号解析。
- 检查用 `readelf -l` 查看 `GNU_RELRO` 段，`readelf -d` 查看 `BIND_NOW` 标志。
- 静态链接的可执行文件没有动态重定位，RELRO 只对动态链接产物有意义。
- 加固构建通常组合 `-fstack-protector-strong`、`-D_FORTIFY_SOURCE=2`、`-z noexecstack` 与完整 RELRO。

### 7.9 RPATH 与 RUNPATH 的区别？

| 项目 | `DT_RPATH` | `DT_RUNPATH` |
| --- | --- | --- |
| 搜索位置 | `LD_LIBRARY_PATH` 之前 | `LD_LIBRARY_PATH` 之后 |
| 传递性 | 对间接依赖生效 | 只对直接依赖生效 |
| 生成选项 | `--disable-new-dtags` | `--enable-new-dtags` |
| 查看方式 | `readelf -d` 的 `RPATH` | `readelf -d` 的 `RUNPATH` |

- 两者都写在动态节的字符串表中，值为冒号分隔的目录列表，支持 `$ORIGIN` 等扩展。
- 同时存在时 `DT_RPATH` 被忽略，多数发行版的 GCC 默认传递 `--enable-new-dtags`，实际行为由工具链配置决定。
- `DT_RPATH` 的传递性会让间接依赖也搜索主程序的路径，容易引发版本冲突。
- 安全加固要求移除可写目录与相对路径，`$ORIGIN` 只在受控布局中使用。
- 查找顺序依次为 `DT_RPATH`、`LD_LIBRARY_PATH`、`DT_RUNPATH`、`ld.so.cache` 与默认目录。
- 用 `readelf -d` 同时查看 `RPATH`、`RUNPATH` 与 `NEEDED`，可以还原运行时的搜索路径。

### 7.10 `$ORIGIN` 的用法与风险？

- `$ORIGIN` 在运行时展开为包含该对象的目录，`-Wl,-rpath,'$ORIGIN/../lib'` 让安装目录可重定位。
- 需要单引号防止 shell 展开，链接器把字面量写入 `DT_RUNPATH`。
- `$ORIGIN` 依赖加载器获取对象路径，在 chroot 与特殊加载方式下可能不可用，由实现定义。
- 可写目录中的 `$ORIGIN` 允许攻击者放置同名库，加载时被优先选中。
- 更好的做法是固定安装路径、使用 `RUNPATH` 加绝对路径，或由启动脚本设置 `LD_LIBRARY_PATH`。
- 调试时用 `LD_DEBUG=libs` 观察 `$ORIGIN` 展开后的实际搜索目录。

### 7.11（场景）构建机可运行、部署机报找不到共享库，如何排查？

- 先用 `readelf -d app` 查看 `NEEDED` 与 `RPATH`、`RUNPATH`，确认依赖名与搜索路径。
- 用 `ldd app` 查看解析结果，注意 `not found` 项与解析到的绝对路径；对不可信文件改用 `objdump -p`。
- 检查 `LD_LIBRARY_PATH` 是否在部署环境中被清空，systemd 服务与容器不会继承登录 shell 的变量。
- 确认 `ldconfig` 缓存是否包含安装目录，`/etc/ld.so.conf.d/` 修改后需要重新运行 `ldconfig`。
- 核对 SONAME 与文件名：`libfoo.so.1` 存在但缺少开发用的 `libfoo.so` 链接只影响链接阶段，不影响运行。
- 用 `LD_DEBUG=libs ./app` 获取搜索顺序与失败原因，或用 `strace -e openat` 观察实际打开路径。

### 7.12 符号可见性如何影响动态库的导出面？

- 默认可见性 `default` 让符号进入 `.dynsym` 并可被其他对象引用；`hidden` 只在链接单元内可见，不进入动态符号表。
- `-fvisibility=hidden` 把默认值改为隐藏，需要导出的符号用 `__attribute__((visibility("default")))` 标注。
- `protected` 在定义它的库内部绑定，不允许被其他库抢占，但仍在 `.dynsym` 中可见。
- 隐藏符号减少动态符号表与重定位处理，缩短加载时间，也避免命名冲突与意外抢占。
- 隐藏 inline 函数、vtable 与 `type_info` 会破坏跨库的 RTTI 与异常匹配，需要保留默认可见性。
- 检查导出面用 `readelf --dyn-syms` 或 `nm -D --defined-only`，`-Wl,--exclude-libs,ALL` 可隐藏静态库带入的符号。

### 7.13（陷阱）隐藏符号后为什么出现 undefined symbol？

- 类模板实例、vtable、`type_info` 与 inline 函数可能只在一个库中生成，隐藏后其他库无法引用。
- 异常抛出与捕获依赖 `type_info` 的跨库可见性，隐藏后 `catch` 可能匹配失败。
- 导出类的成员函数在库外被调用时，只有声明为 default 的成员函数进入 `.dynsym`。
- `std::string` 等标准库类型的符号由 libstdc++ 导出，隐藏自身符号不影响这些符号。
- 修正方式是给整个导出类加 `visibility("default")`，或用版本脚本显式列出需要导出的符号。
- 用 `nm -D` 对比修改前后的导出清单，可以快速定位被隐藏的符号。

### 7.14 `--exclude-libs` 解决什么问题？

- 静态链接第三方库时，库中的全局符号默认进入可执行文件或共享库的导出表。
- `-Wl,--exclude-libs,libfoo.a` 把来自该归档的符号降为局部，避免污染导出面与命名冲突。
- `--exclude-libs,ALL` 隐藏全部归档符号，适合共享库只导出自身接口的场景。
- 该选项只影响动态符号表，不影响静态链接的解析与调试符号。
- 与 `-fvisibility=hidden` 不同，它按输入文件过滤，不需要重新编译第三方代码。
- 若插件需要引用静态库中的符号，过滤后会导致 `dlsym` 失败，需要保留对应符号。

### 7.15 插件架构中 `dlopen` 与 `dlsym` 的关键选项？

- `dlopen(path, RTLD_NOW | RTLD_LOCAL)` 立即解析符号并让插件符号不进入全局作用域，避免多个插件冲突。
- `RTLD_GLOBAL` 把插件符号加入全局作用域，供后续加载的库解析，也带来符号抢占风险。
- `dlsym` 返回 `void *`，转换为函数指针需要 `reinterpret_cast`，C++ 标准不保证函数指针与对象指针互转，POSIX 保证可用。
- 插件入口通常导出 `extern "C"` 的工厂函数，避免名称修饰与 ABI 差异。
- `dlclose` 只减少引用计数，静态对象析构与 `__attribute__((destructor))` 在卸载时执行，顺序与构造相反。
- 用 `dlerror()` 清除并读取错误，`RTLD_NODELETE` 可阻止卸载，适合不能安全析构的插件。

```cpp
#include <dlfcn.h>

using create_fn = Plugin *(*)();

void *h = dlopen("./plugin.so", RTLD_NOW | RTLD_LOCAL);
auto create = reinterpret_cast<create_fn>(dlsym(h, "create_plugin"));
Plugin *p = create();
```

### 7.16（场景）插件卸载后崩溃的可能原因？

- 插件中的静态对象在 `dlclose` 时析构，若主程序仍持有其回调或引用，后续调用访问已卸载代码。
- 主程序注册的回调位于插件内，卸载前没有注销，事件循环在卸载后触发调用。
- 插件与主程序各自链接了同一份静态库，类型信息与全局状态出现两份副本，析构顺序难以保证。
- `RTLD_NODELETE` 或链接选项 `-z nodelete` 可阻止卸载，牺牲地址空间换取稳定性。
- 线程仍在插件代码中执行时卸载会导致指令页失效，卸载前需要停止并汇合相关线程。
- 用 AddressSanitizer 或 Valgrind 检查 `dlclose` 后的悬空函数指针，`/proc/<pid>/maps` 可确认代码段是否已消失。

### 7.17 SONAME 与版本符号链接如何工作？

- 共享库的 `DT_SONAME` 在链接时用 `-Wl,-soname,libfoo.so.1` 指定，可执行文件记录该名字而不是文件名。
- 安装布局通常为 `libfoo.so.1.2.3` 实体文件、`libfoo.so.1` 指向它的 SONAME 链接、`libfoo.so` 指向最新版本的开发链接。
- 运行时只查找 SONAME，升级到 `libfoo.so.1.3.0` 只需更新链接，不需要重新链接程序。
- SONAME 的主版本号变化表示 ABI 不兼容，新旧版本可以并存。
- 缺少 SONAME 时动态链接器记录构建时的文件名，库文件改名会导致加载失败。
- 用 `readelf -d libfoo.so` 查看 `SONAME`，`objdump -p` 给出同样的信息。

### 7.18 静态链接与动态链接在体积上的权衡？

- 动态链接的可执行文件只含自身代码，公共库在多个进程间共享物理页。
- 静态链接把库代码复制进每个可执行文件，多个程序同时部署时总体积更大。
- 静态链接省去 PLT 与 GOT 间接跳转，启动时没有符号解析，适合短生命周期工具。
- `-static` 链接 `glibc` 会限制 `getaddrinfo`、`dlopen` 等功能，安全更新也需要重新分发。
- `-static-libstdc++` 与 `-static-libgcc` 只静态链接 C++ 运行库，保留系统库的动态链接。
- 体积分析用 `size` 与 `bloaty`，按节与符号排序找出主要贡献者。

### 7.19（陷阱）混用 `-Bstatic` 与 `-Bdynamic` 的常见错误？

- `-Wl,-Bstatic -lfoo -Wl,-Bdynamic` 只对紧随其后的库生效，后续库恢复动态链接。
- 忘记恢复 `-Bdynamic` 会让后续系统库也被静态链接，出现重复定义或缺失的 `libc`。
- 同名的静态库与动态库并存时，`-lfoo` 选择哪一个取决于当前的 `-B` 状态与搜索顺序。
- 静态链接的库若依赖动态库，链接行仍需显式列出被依赖的库。
- `-Wl,-Bstatic` 不支持在单个 `-l` 上限定，需要借助完整路径 `libfoo.a` 精确指定。
- 检查最终产物用 `ldd` 与 `readelf -d`，确认 `NEEDED` 列表符合预期。

### 7.20（场景）动态库升级后程序启动失败，可能的原因？

- 新库的 SONAME 主版本未变但删除了旧符号，加载时报 `undefined symbol`，说明 ABI 不兼容。
- 新库提高了符号版本要求，旧程序请求的版本节点不再提供。
- 新库依赖更高版本的 `libstdc++` 或 `glibc`，运行环境的系统库过旧。
- 新库的构造函数失败或初始化顺序变化，表现为启动早期退出或 `std::terminate`。
- 排查用 `LD_DEBUG=libs,reloc` 与 `ldd`，结合 `readelf --dyn-syms` 对比新旧导出清单。
- 回滚是第一步，随后用 `abidiff` 或 `abi-compliance-checker` 确认破坏点。

## 8. 名称修饰与 ABI

### 8.1 Itanium C++ ABI 的修饰名由哪些部分组成？

- 全局符号以 `_Z` 开头，随后是名字与参数类型编码，`_Z3fooi` 对应 `foo(int)`。
- 源名字以长度加标识符表示，`3foo` 表示 3 个字符的 `foo`；嵌套名字用 `N` 开头、`E` 结尾，内部各层仍带长度前缀。
- 内建类型用单字母编码，`i` 为 `int`、`c` 为 `char`、`d` 为 `double`、`v` 为 `void`、`b` 为 `bool`。
- 函数参数按声明顺序编码，返回类型不参与普通函数修饰，只有模板函数与转换运算符会编码返回类型。
- 成员函数带 `const` 限定符时在名字后加 `K`，`volatile` 加 `V`，右值引用限定加 `O`。
- 该规范由 Itanium C++ ABI 文档定义，GCC、Clang 与多数 Unix 工具链遵循，MSVC 不遵循。

### 8.2 命名空间与类成员如何编码？

- `ns::foo()` 编码为 `_ZN2ns3fooEv`，`N` 与 `E` 之间依次是命名空间名与函数名。
- 成员函数 `C::f()` 编码为 `_ZN1C1fEv`，构造函数与析构函数分别用 `C1`、`C2` 与 `D0`、`D1`、`D2` 表示不同变体。
- 构造函数 `C1` 为完整对象构造，`C2` 为基类子对象构造；析构函数 `D1` 为完整析构，`D2` 为基类子对象析构，`D0` 为删除析构。
- 运算符重载使用固定编码，`operator+` 为 `pl`，`operator<<` 为 `ls`，`operator new` 为 `nw`。
- 静态成员函数没有 `this` 参数，修饰形式与普通函数类似，但仍在类作用域内编码。
- 匿名命名空间的符号带内部链接，名称中仍包含 `12_GLOBAL__N_1` 之类的占位，便于调试识别。

### 8.3 模板实例的修饰名如何生成？

- 模板名后跟 `I`、模板实参编码与 `E`，`foo<int>(double)` 编码为 `_Z3fooIiEvT_`。
- 模板参数在函数参数中回引时使用 `T_` 等替换编码，减少重复展开。
- 非类型模板实参按值编码，`foo<3>` 中的 `3` 直接出现在名字中，负号用 `n` 表示。
- 替换压缩用 `S_`、`S0_` 等引用先前出现的类型，深层嵌套模板名会显著缩短。
- 实例化后的符号进入 COMDAT 组，链接器按组去重，保证多个翻译单元只保留一份。
- 修饰名长度没有标准上限，超长名字在部分链接器与调试器中会被截断，由实现定义。

### 8.4 MSVC 的修饰规则与 Itanium 有何不同？

- MSVC 名字以 `?` 开头，函数名后接 `@@` 与作用域、调用约定、返回类型和参数类型编码，`?f@@YAHH@Z` 对应 `int __cdecl f(int)`。
- 调用约定用单字母表示，`A` 为 `__cdecl`，`G` 为 `__stdcall`，`I` 为 `__fastcall`，成员函数的 `this` 约定另有编码。
- 类成员以 `?name@Class@@` 开头，访问级别与虚函数属性用 `Q`、`E`、`M` 等字母编码。
- 返回类型参与修饰，`H` 表示 `int`，`X` 表示 `void`，与 Itanium 省略返回类型的做法不同。
- x64 只有一种调用约定，修饰中的约定字母仍保留，用于区分 32 位与 64 位编译结果。
- 两种修饰互不兼容，混用目标文件会在链接阶段报未定义符号或符号冲突。

### 8.5（辨析）`extern "C"` 解决了什么问题？

- `extern "C"` 关闭 C++ 名称修饰，符号名与 C 编译器生成的一致，便于与 C 库、动态库接口对接。
- 它同时影响语言链接（language linkage），使函数类型在重载解析中与 C 函数区分。
- `extern "C"` 函数不能重载，因为符号名不携带参数信息；不同参数列表会产生同名符号冲突。
- 该说明可以出现在头文件中，通常配合 `#ifdef __cplusplus` 包裹，使同一头文件可被 C 与 C++ 包含。
- `extern "C"` 不改变调用约定，Windows 上仍需 `__stdcall` 等修饰与 DLL 导出声明。
- C++ 标准只规定语言链接的存在，具体符号名由实现定义，跨编译器混用需要遵循平台 ABI。

```cpp
#ifdef __cplusplus
extern "C" {
#endif

int compute(int x);

#ifdef __cplusplus
}
#endif
```

### 8.6 常见调用约定的差异？

| 约定 | 参数位置 | 栈清理方 | 典型用途 |
| --- | --- | --- | --- |
| `__cdecl` | 全部入栈 | 调用方 | C 接口与可变参数 |
| `__stdcall` | 全部入栈 | 被调方 | Windows API |
| `__fastcall` | 前两个整数参数入寄存器 | 被调方 | 32 位性能敏感接口 |
| `__thiscall` | `this` 入寄存器，其余入栈 | 被调方 | 32 位成员函数 |
| x86-64 System V | 前六个整数参数入寄存器 | 调用方 | Linux 与 macOS |
| Windows x64 | 前四个参数入寄存器 | 调用方 | Windows |

- `__cdecl` 由调用方清理栈，支持可变参数；`__stdcall` 由被调方清理，C 符号名在链接时带 `@` 与参数字节数后缀。
- `__fastcall` 的具体寄存器由实现定义，32 位 MSVC 使用 `ecx` 与 `edx`。
- `__thiscall` 把 `this` 放入 `ecx`，其余参数入栈，是 32 位 MSVC 成员函数的默认约定。
- x86-64 System V 用 `rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9` 传整数参数，浮点用 XMM 寄存器，调用方清理栈。
- Windows x64 用 `rcx`、`rdx`、`r8`、`r9` 传前四个参数，调用方分配 32 字节阴影空间。
- 调用约定不一致会导致参数错位与栈失衡，跨模块接口必须显式统一。

### 8.7 在已有类中新增虚函数为何可能破坏 ABI？

- 虚函数表按声明顺序排列，在中间插入虚函数会改变后续槽位，旧目标文件按旧偏移调用会跳到错误函数。
- 在末尾追加虚函数对 Itanium ABI 的既有槽位影响较小，但仍改变 vtable 大小与 RTTI 信息，兼容性由实现定义。
- 新增虚函数可能改变对象的 `sizeof`，尤其是多重继承与虚继承场景，按值传递的接口随之失效。
- 覆盖已有虚函数不改变槽位数，通常保持二进制兼容。
- 修改虚函数的签名等于新增一个槽位并移除旧槽位，破坏兼容。
- 需要扩展接口时应新增派生类或使用 pimpl，避免改动已发布的类布局。

### 8.8 增加非虚成员函数或静态成员是否破坏 ABI？

- 非虚成员函数不进入对象布局，新增或删除不改变 `sizeof` 与 vtable，通常二进制兼容。
- 若新增函数是 inline，调用方需要重新编译才能使用，但已有二进制不受影响。
- 静态成员函数不占用对象空间，同样不影响布局。
- 改变参数列表或 cv 限定会改变修饰名，旧符号消失，属于 ABI 破坏。
- 仅改变返回类型不改变 Itanium 修饰名，但调用方按旧类型解释返回值，同样破坏兼容。
- 头文件中的默认参数属于编译期信息，修改后需要重新编译调用方才能生效。

### 8.9（场景）只重编部分目标文件为何出现布局错乱？

- 类定义改变后，旧目标文件仍按旧的 `sizeof` 与成员偏移生成代码，与新目标文件对同一对象的解释不同。
- 常见表现是写入越界、读取错位、虚函数调用跳到错误槽位，且不一定立即崩溃。
- 构建系统未跟踪头文件依赖时，修改头文件不会触发相关源文件重编，产生混合布局。
- 解决方式是完整清理重建，或使用 `-MMD -MP` 生成依赖文件并纳入构建图。
- ABI 检查工具可以在发布前比较两个版本的布局，`abidiff` 会报告成员偏移与大小变化。
- 若必须混用，应通过稳定的 C 接口或 pimpl 隔离布局，不直接暴露类定义。

### 8.10（陷阱）在类末尾追加数据成员是否安全？

- 部分 ABI 兼容规范允许在类末尾追加数据成员，但前提是没有派生类复用基类的尾部填充。
- 若基类尾部填充被派生类成员复用，追加成员会与派生类成员重叠，破坏布局。
- 标准布局类型的 `sizeof` 在追加后改变，按值传递的接口、数组与序列化格式都会受影响。
- 通过指针或引用传递的对象，调用方若在栈上分配，仍按旧大小分配，导致越界。
- 因此追加成员只对调用方不分配对象、不依赖大小的接口安全，条件苛刻。
- 稳妥做法是预留保留字段或使用 pimpl，把布局变化限制在库内部。

### 8.11 `-fabi-version` 与 `-Wabi` 的作用？

- `-fabi-version=n` 选择 GCC 实现的 ABI 版本，用于复现旧编译器行为或规避已知缺陷。
- 不同版本可能改变空类、尾部填充与模板参数相关的修饰方式。
- `-Wabi` 在编译时警告可能与旧 ABI 不兼容的构造，`-Wabi-tag` 检查带有 ABI 标签的类型。
- `-Wabi=11` 等取值对应特定版本，具体含义随 GCC 版本变化，由实现定义。
- 修改该选项后所有目标文件必须用同一版本重编，否则修饰名与布局可能不一致。
- 跨编译器场景更可靠的做法是用 `abidiff` 比较二进制，而不是依赖警告。

### 8.12 ABI 检查工具如何工作？

- `abidiff` 读取两个 ELF 的 DWARF 与符号表，比较类型布局、函数签名、虚表与枚举值。
- `abi-compliance-checker` 生成 ABI 报告，按兼容性等级列出删除、新增与变更的接口。
- `abi-dumper` 把共享库的 ABI 提取为中间格式，便于在无源码时比较。
- 检查依赖调试信息，发布库需要保留带 `-g` 的副本或单独的调试文件。
- 工具只能发现可静态比较的差异，调用约定、inline 展开与运行期行为需要测试补充。
- 把检查纳入 CI，在发布前对比基线版本，可以阻止不兼容变更进入制品。

### 8.13 `_GLIBCXX_USE_CXX11_ABI` 双 ABI 的由来？

- GCC 5 为符合 C++11 调整了 `std::string` 与 `std::list` 的实现：`string` 从写时复制改为短字符串优化，`list` 增加大小成员。
- 新旧实现不二进制兼容，libstdc++ 同时提供两套符号，用 `_GLIBCXX_USE_CXX11_ABI` 宏选择。
- 宏为 1 时使用新 ABI，符号名带 `__cxx11` 命名空间；为 0 时使用旧 ABI。
- 该宏影响头文件中的类定义与 inline 函数，必须在编译所有使用标准库的翻译单元时保持一致。
- 默认值由 libstdc++ 配置决定，现代发行版默认为 1。
- 混用会导致 `std::string` 的布局与符号不匹配，表现为链接错误或运行时内存破坏。

### 8.14（陷阱）双 ABI 混用的典型症状？

- 链接阶段报 `undefined reference to std::__cxx11::basic_string...`，说明一处按新 ABI 引用、另一处只提供旧 ABI 符号。
- 编译通过但运行时崩溃，常见于跨库传递 `std::string`，两边的对象布局不同。
- `nm -C` 可以看到同一函数的新旧两套符号，`__cxx11` 是区分标志。
- 第三方预编译库通常按旧 ABI 构建，接入时需要统一宏或重新编译。
- 在头文件中定义宏只能覆盖包含顺序在前的翻译单元，可靠做法是在构建系统中全局设置。
- 检查产物用 `readelf --dyn-syms` 搜索 `__cxx11`，确认依赖的 ABI 版本。

### 8.15 `c++filt` 与 `__cxa_demangle` 的用途？

- `c++filt _Z3fooi` 把修饰名还原为 `foo(int)`，`nm -C` 与 `objdump -C` 内部使用同样的反修饰。
- `abi::__cxa_demangle` 是 libstdc++ 提供的运行时接口，调用方负责释放返回缓冲区。
- 反修饰结果依赖编译器版本，新标准引入的编码可能不被旧工具识别。
- `c++filt` 支持 `-s gnu-v3` 等格式选择，较旧的 binutils 不识别部分新编码。
- 修饰名是链接与调试的稳定标识，日志中记录修饰名比记录反修饰名更可靠。
- 对 MSVC 符号使用 `undname` 或 `llvm-cxxfilt`，`c++filt` 对 `?` 开头的符号支持有限。

### 8.16（场景）模板实例导致的符号膨胀如何控制？

- 每个翻译单元实例化同一模板会生成弱符号，链接器去重后只保留一份，但目标文件与链接输入仍然膨胀。
- `extern template` 抑制隐式实例化，把实例化集中到一个翻译单元。
- 显式实例化定义放在源文件中，其他翻译单元只看到 `extern template` 声明。
- 常用模板在多个共享库中重复实例化，动态库之间无法去重。
- 隐藏可见性会让不同库各自保留一份实例，避免冲突但增加体积。
- 用 `nm -C --defined-only` 统计重复的弱符号，或用 `bloaty` 按符号归因。

### 8.17 一个定义规则在二进制层面意味着什么？

- 同一实体在多个翻译单元中允许有多个定义（类、inline 函数、模板），前提是各定义完全相同。
- 链接器通过 COMDAT 组去重，只保留一份，其余副本被丢弃。
- 若各翻译单元的类定义不一致，去重后的代码与数据可能按不同布局解释，属于未定义行为。
- 违反该规则通常不产生诊断，链接成功而运行结果错误，跨库混编时最难定位。
- 头文件中的条件编译、宏差异与版本不一致是常见诱因。
- 检查手段包括对比预处理结果、在 LTO 下查看 `-Wodr` 警告，以及统一构建配置。

### 8.18 稳定 ABI 的常用设计手段？

- pimpl 把实现细节移入不透明指针，类大小固定为指针大小，成员变化不影响调用方。
- 纯 C 接口只暴露不透明句柄与函数，避免名称修饰、异常与布局差异。
- 虚接口配合工厂函数，调用方只依赖抽象基类的 vtable 布局，实现可以替换。
- 版本化符号或新增入口点保留旧行为，旧二进制继续解析到旧版本。
- 避免在接口中按值传递标准库容器，容器实现随标准库版本变化。
- 预留虚函数槽位与数据成员可以吸收部分变化，但会增加对象大小与维护成本。

### 8.19（实现）GCC 与 Clang 生成的修饰名为何通常可以互通？

- 两者都实现 Itanium C++ ABI，修饰规则由同一份规范定义，符号名可以互相解析。
- 例外包括标准库实现差异、`__int128` 等扩展类型，以及各编译器对 ABI 缺陷的修正版本。
- `-fabi-version` 与 `-fclang-abi-compat` 可以调整兼容版本，默认值随版本演进。
- 异常、RTTI 与虚表布局也遵循 Itanium ABI，因此目标文件通常可以混合链接。
- 标准库不同（libstdc++ 与 libc++）时，容器与字符串的布局不兼容，不能混用。
- 混合工具链的可行范围由实现定义，发布前需要实际链接与运行验证。

### 8.20（场景）第三方库只提供头文件与二进制，如何确认 ABI 匹配？

- 检查库的编译信息：`readelf -p .comment` 读取编译器版本，`readelf -h` 确认目标架构与位宽。
- 确认 C++ 标准库与 `_GLIBCXX_USE_CXX11_ABI` 一致，必要时向供应商索取构建说明。
- 用 `nm -D -C` 查看导出符号，确认所需函数存在且签名一致。
- 编译一个最小程序链接该库，覆盖构造、析构、异常与回调路径。
- 用 `abidiff` 对比库的多个版本，确认升级不会破坏已使用的接口。
- 若头文件与二进制版本不匹配，可能出现布局错乱而非链接错误，测试需要覆盖对象创建与销毁。

## 9. 异常与 RTTI 的二进制实现

### 9.1 Itanium 异常处理的两阶段展开如何工作？

- 第一阶段从抛出点向外搜索，逐个栈帧调用 personality 例程，判断是否存在匹配的 handler，不执行清理代码。
- 找到 handler 后进入第二阶段，再次从抛出点展开到 handler，执行每个栈帧的清理代码并调用析构函数。
- 两阶段设计保证搜索阶段没有副作用，栈状态在找到 handler 前保持不变。
- `_Unwind_RaiseException` 驱动两阶段流程，personality 返回 `_URC_HANDLER_FOUND` 或 `_URC_CONTINUE_UNWIND`。
- 没有 handler 时调用 `std::terminate`，默认行为是异常未被捕获。
- 展开过程中可以查询 `std::uncaught_exceptions`，用于判断当前是否处于栈展开状态。

### 9.2 `.eh_frame` 与 `.gcc_except_table` 分别保存什么？

- `.eh_frame` 保存调用帧信息（CFI），描述每个 PC 范围如何恢复寄存器与栈指针，供展开器使用。
- `.gcc_except_table` 保存 LSDA，描述 try 块的地址范围、对应的 landing pad 与可捕获的类型。
- 两者都带 `SHF_ALLOC`，随程序加载；`.debug_frame` 不加载，只供调试器使用。
- `.eh_frame` 的 CIE 中记录 personality 例程地址与编码格式，FDE 覆盖具体函数。
- LSDA 通过 FDE 的 augmentation 数据定位，展开器在进入每个栈帧时读取。
- 用 `readelf --debug-dump=frames` 查看 CIE 与 FDE，用 `objdump -s -j .gcc_except_table` 查看 LSDA 原始字节。

### 9.3 LSDA 的内部结构是什么？

- LSDA 头部含 LPStart、TType 编码与调用点表偏移，后面依次是调用点表、动作表与类型表。
- 调用点表每项给出 try 覆盖的起止地址、landing pad 地址与动作表下标，地址以 LPStart 为基准编码。
- 动作表描述捕获顺序与是否继续搜索，正数指向类型表中的类型，负数表示清理块。
- 类型表保存 `type_info` 指针或对类型名的引用，捕获匹配时逐项比较。
- landing pad 是编译器生成的代码块，负责调用析构、执行 catch 或继续展开。
- 一个函数的所有 try 块共享一份 LSDA，嵌套 try 通过调用点范围与动作链表达。

### 9.4 `__cxa_throw` 与相关运行库函数的职责？

- `__cxa_allocate_exception` 在异常存储区分配空间，头部保存 `__cxa_exception` 结构，含类型信息、析构函数与引用计数。
- 抛出表达式把异常对象复制或移动到该空间，再调用 `__cxa_throw` 启动展开。
- `__cxa_begin_catch` 在进入 handler 时调用，返回异常对象地址并增加捕获计数。
- `__cxa_end_catch` 在 handler 结束时调用，计数归零后执行异常对象的析构并释放存储。
- `__cxa_rethrow` 重新抛出当前异常，`__cxa_get_exception_ptr` 在构造 catch 参数前读取对象。
- 这些函数由 libstdc++ 或 libc++abi 提供，符号属于 C++ ABI，跨库抛异常要求双方使用兼容的实现。

### 9.5 栈展开器如何恢复寄存器？

- 展开器从当前 PC 查找覆盖它的 FDE，读取 CIE 中的初始规则与 FDE 中的指令序列。
- CFA（规范帧地址）由规则计算，例如 `DW_CFA_def_cfa rsp, 8` 表示 CFA 等于 `rsp + 8`。
- 保存的返回地址与 callee-saved 寄存器位置由 `DW_CFA_offset` 描述，展开器据此恢复上一帧。
- `DW_CFA_advance_loc` 按 PC 推进规则，同一函数内不同地址区间可以有不同的 CFA 偏移。
- 恢复后的返回地址成为上一帧的 PC，循环直到找到 handler 或到达栈顶。
- 手写汇编必须提供 `.cfi_startproc`、`.cfi_def_cfa_offset` 等指令，否则展开会中断。

### 9.6（场景）异常跨越 C 回调帧为什么可能终止？

- C 代码通常没有异常表，展开器经过这些帧时找不到 FDE，无法继续向外传播。
- C 函数若由 C++ 编译器以 `-fexceptions` 编译，会生成展开信息，可以安全穿过。
- 通过 `extern "C"` 调用的 C 库回调没有展开信息时，异常会在边界处触发 `std::terminate`。
- 解决方式是在 C++ 侧捕获异常，把错误码传给 C 回调，或确保回调编译时开启异常支持。
- pthread 的线程入口函数是常见边界，线程函数应自行捕获所有异常。
- 排查时在 `std::terminate` 与 `__cxa_throw` 上设断点，确认异常是否到达边界。

### 9.7 跨共享库抛异常需要满足什么条件？

- 抛出方与捕获方必须使用兼容的 C++ ABI 与异常运行库，通常同为 libstdc++ 或同为 libc++abi。
- 两边的 `type_info` 必须比较相等：地址不同时按类型名比较，名称一致才能匹配。
- 异常对象的析构函数在捕获方执行，要求双方使用兼容的分配器与运行时。
- 共享库的符号可见性不能隐藏 `type_info` 与 `__cxa_*` 符号，否则匹配或清理会失败。
- 使用 `-fvisibility=hidden` 时，异常类型需要显式导出，或改用错误码接口。
- 跨语言边界（C、Rust）不能直接传播 C++ 异常，需要在边界处转换。

### 9.8 `-fno-exceptions` 的后果与边界？

- 该选项禁止 `throw`、`try`、`catch` 语法，编译期直接报错，不生成 LSDA。
- 标准库头文件中的 `try` 与 `catch` 被条件编译排除，标准库实现仍以异常方式报告错误，异常可能穿过没有清理代码的帧。
- 由其他库抛出的异常仍可能经过本模块的栈帧，但这些帧没有清理代码，析构函数不会执行。
- LSDA 不再生成，`.eh_frame` 仍可能为回溯保留，需要 `-fno-asynchronous-unwind-tables` 才会移除。
- 内核、嵌入式与实时项目常用该选项，配套策略是禁用异常与 RTTI，改用返回码。
- 与 `-fno-rtti` 一起使用时，`dynamic_cast` 与多态 `typeid` 都不可用。

### 9.9（陷阱）`noexcept` 被违反时为什么直接终止？

- `noexcept` 是函数类型的一部分，调用方可以假设函数不抛出，从而省略展开路径上的清理准备。
- 若异常从 `noexcept` 函数中逸出，运行库调用 `std::terminate`，不会尝试向外展开。
- 该检查发生在异常传播经过该帧时，由 personality 例程或编译器生成的检查触发。
- 移动构造函数标注 `noexcept` 后，容器扩容会选用移动而非复制，若移动实际抛出则终止。
- `noexcept(false)` 是默认值，析构函数默认隐含 `noexcept(true)`。
- 调试时在 `std::terminate` 与 `__cxa_throw` 上设断点，可以区分未捕获异常与 `noexcept` 违反。

### 9.10 异常对象的复制与切片如何发生？

- 抛出表达式按静态类型复制对象，`throw derived;` 以 `derived` 类型存入异常存储，捕获基类引用仍可访问派生部分。
- `throw *base_ptr;` 的静态类型是基类，发生切片，派生部分丢失。
- 异常对象的生命周期持续到最后一个 catch 块结束，按引用捕获不产生额外复制。
- 按值捕获会再复制一次，且同样可能切片。
- `std::make_exception_ptr` 与 `std::current_exception` 把异常保存在 `exception_ptr` 中，引用计数管理生命周期。
- `std::rethrow_exception` 重新抛出保存的异常，类型信息保持不变。

### 9.11 RTTI 的二进制表示是什么？

- 多态类的 vtable 在地址点之前的槽位保存 `type_info` 指针，位置由 ABI 规定。
- `type_info` 对象含类型名指针与比较函数，名称是修饰名或可读名，由实现定义。
- `typeid` 对多态类型在运行时读取 vtable，对非多态类型在编译期确定。
- `dynamic_cast` 依赖 vtable 中的类型信息遍历继承图，进行指针调整。
- `-fno-rtti` 移除这些信息，多态 `typeid` 与 `dynamic_cast` 无法使用。
- 跨库比较 `type_info` 时地址可能不同，实现需要按名称比较，隐藏可见性会破坏这一机制。

### 9.12 `dynamic_cast` 的运行时流程？

- 向下转型从源对象的 vtable 找到完整类型信息，再沿继承图搜索目标类型。
- 目标类型在源类型的基类中唯一且可访问时，返回调整后的指针；否则返回空指针。
- 交叉转型（兄弟类之间）需要遍历到公共基类再向下查找，成本高于普通向下转型。
- 引用形式的失败抛出 `std::bad_cast`，指针形式返回空指针。
- 转换需要目标类型完整，且源类型必须多态，否则编译期报错。
- `dynamic_cast` 不能在 `-fno-rtti` 下使用，也不能跨越不共享 `type_info` 的模块边界。

### 9.13 `type_info` 的名称与比较如何处理？

- `std::type_info::name()` 返回实现定义的名称，GCC 与 Clang 返回 Itanium 修饰名，MSVC 返回可读名称。
- 名称不保证唯一或稳定，不能作为序列化标识或持久化键。
- `operator==` 在地址相同时直接返回真，地址不同时按名称比较，具体规则由实现定义。
- `hash_code()` 在 C++11 起提供，可用于容器索引，但不同进程间不保证一致。
- `before()` 提供实现定义的顺序，只用于排序，不表示继承关系。
- 跨共享库时，`type_info` 的地址与名称都受可见性影响。

### 9.14 `-fno-rtti` 的适用场景与代价？

- 该选项移除 RTTI 数据与 `dynamic_cast`、多态 `typeid` 的支持，减小二进制体积。
- 异常处理不依赖 RTTI，`-fno-rtti` 与异常可以同时启用。
- 依赖 `dynamic_cast` 的框架（如部分 GUI 与序列化库）无法直接使用。
- 可用访问者模式、类型标签或 `std::variant` 替代运行时类型查询。
- 移除 RTTI 后，调试器仍可通过 DWARF 获取类型信息，二者来源不同。
- 与 LTO 一起使用时，未使用的 RTTI 数据可能被进一步回收。

### 9.15 异常表对二进制体积的影响？

- 每个含 try 或需要清理的函数生成 LSDA，`.gcc_except_table` 随 try 块数量增长。
- `.eh_frame` 为每个函数生成 FDE，开启 `-fasynchronous-unwind-tables` 后所有函数都有记录。
- `-fno-exceptions` 移除 LSDA，但 `.eh_frame` 可能仍保留，需配合 `-fno-asynchronous-unwind-tables`。
- `-gz` 只压缩调试节，不压缩 `.eh_frame` 与 `.gcc_except_table`。
- `strip --strip-debug` 不删除 `.eh_frame` 与 `.gcc_except_table`，它们属于分配节。
- 用 `size -A` 对比各节大小，可以量化异常支持的成本。

### 9.16 C 代码如何与 C++ 异常共存？

- 以 C++ 编译器编译 C 源文件并开启 `-fexceptions`，生成的帧带展开信息，异常可以安全穿过。
- C 代码中的 `__attribute__((cleanup))` 在展开时执行，可用于资源释放。
- 纯 C 编译的目标文件没有展开信息，异常穿过时行为由实现定义，通常终止。
- `setjmp` 与 `longjmp` 是另一套机制，与异常展开混用会跳过析构函数。
- 在 C 边界处用 `try` 与 `catch` 包裹，把异常转换为错误码，是最稳妥的隔离方式。
- 动态库导出的 C 接口不应让异常逸出，否则调用方的语言运行时无法处理。

### 9.17（场景）`catch` 不到预期类型的原因？

- 捕获按声明顺序匹配，基类 `catch` 放在派生类之前会提前截获。
- 异常类型在跨库时 `type_info` 不一致，名称比较失败，handler 被视为不匹配。
- 抛出的是指针或值类型，与捕获的引用类型不匹配，`catch (Derived&)` 无法接住 `Derived*`。
- 抛出发生在 `noexcept` 函数内，异常未到达 `catch` 就被终止。
- 异常在另一个线程抛出，当前线程的 `catch` 不会收到。
- 用 `catch (...)` 兜底并打印 `abi::__cxa_current_exception_type()->name()`，可以确认实际类型。

### 9.18 异常与栈展开对性能的影响？

- 表驱动实现让正常路径没有额外指令，成本主要在异常表占用的只读空间。
- 抛出路径需要搜索 FDE、执行 personality、复制异常对象，耗时远高于普通函数调用，具体量级由实现与展开深度决定。
- `throw` 频繁用于控制流会放大成本，热路径应使用返回值或状态码。
- 展开过程中执行的析构函数可能分配内存或加锁，异常安全与实时性需要一起考虑。
- `std::optional` 与 `std::expected` 提供无异常的错误传递方式。
- 测量时区分抛出频率与捕获深度，深层展开的成本主要来自帧数与清理代码。

### 9.19 `std::exception_ptr` 如何保存异常？

- `std::current_exception` 在 `catch` 块中捕获当前异常，返回引用计数的句柄。
- 实现通常在 `__cxa_exception` 头部维护引用计数，`exception_ptr` 的复制增加计数。
- 异常对象在最后一个 `exception_ptr` 释放且 `catch` 结束时销毁。
- `std::rethrow_exception` 在另一个线程或稍后重新抛出，保留原始类型。
- 跨线程传递 `exception_ptr` 需要同步，句柄本身不是原子的。
- `std::make_exception_ptr` 直接构造，不经过 `throw`，适合在无异常路径上创建错误对象。

```cpp
#include <exception>

void run() {
    try {
        work();
    } catch (...) {
        auto ep = std::current_exception();
        report(ep);
    }
}
```

### 9.20（场景）二进制体积异常增大，如何定位异常相关部分？

- 用 `size -A` 对比各节，`.eh_frame` 与 `.gcc_except_table` 异常增大说明模板实例或 try 块过多。
- `readelf --debug-dump=frames` 统计 FDE 数量，与函数数量对比。
- `nm -C --size-sort` 找出体积最大的函数，检查是否包含大量 try 块或模板展开。
- 关闭异常支持可以显著减小体积，但需要评估标准库与第三方库的行为。
- `-fno-asynchronous-unwind-tables` 移除不必要的中断展开表，影响调试与性能分析。
- 用 `bloaty` 按编译单元与节归因，确认增长来自业务代码还是模板实例。

## 10. 调试信息 DWARF 与栈展开

### 10.1 DWARF 的主要节各保存什么？

- `.debug_info` 保存 DIE 树，描述编译单元、类型、函数、变量与作用域。
- `.debug_abbrev` 定义 DIE 的属性组合缩写，`.debug_str` 保存字符串，`.debug_str_offsets` 为 DWARF 5 的字符串索引表。
- `.debug_line` 保存行号程序，把机器指令地址映射到源文件与行号；DWARF 5 增加 `.debug_line_str`。
- `.debug_ranges` 与 `.debug_loc` 在 DWARF 5 中被 `.debug_rnglists` 与 `.debug_loclists` 取代，保存非连续地址范围。
- `.debug_frame` 保存调试用的调用帧信息，`.eh_frame` 保存运行时展开信息，`.debug_addr` 集中存放地址。
- `.debug_aranges` 提供地址到编译单元的快速索引，`.debug_names` 是 DWARF 5 的名称索引。

### 10.2 DIE 与 abbrev 如何编码？

- 每个 DIE 以 abbrev 编号开头，编号对应 `.debug_abbrev` 中的一项，决定标签、是否有子节点与属性列表。
- 属性由属性名与形式（form）组成，形式决定值的编码长度与解释方式，如 `DW_FORM_strp`、`DW_FORM_data4`。
- DIE 树按深度优先排列，有子节点的 DIE 后跟子节点，以终止符 0 结束。
- 相同结构的 DIE 共享 abbrev，减少重复的属性描述，是 DWARF 体积优化的基础。
- `readelf --debug-dump=info` 解码 DIE 树，`llvm-dwarfdump` 提供更紧凑的输出。
- DWARF 5 引入 `DW_FORM_strx` 等索引形式，把字符串与地址移出主节。

### 10.3 行号表如何把地址映射到源码行？

- `.debug_line` 包含行号程序，由状态机指令序列构成，状态含地址、文件、行号、列号与 `is_stmt` 标志。
- `DW_LNS_copy` 输出当前状态为一行记录，`DW_LNS_advance_pc` 与 `DW_LNS_advance_line` 推进状态。
- 特殊操作码把地址推进与行号推进合并编码，减少体积。
- 每个序列以 `DW_LNE_set_address` 设置起始地址，以 `DW_LNE_end_sequence` 结束。
- 调试器用行号表把断点地址映射回源码，`addr2line` 与 `llvm-symbolizer` 使用同一份数据。
- 优化会重排指令，行号表可能出现同一行对应多个地址，或地址对应到不直观的源码行。

### 10.4 变量位置如何描述？

- 局部变量用 `DW_AT_location` 描述，值可以是寄存器、栈偏移或位置表达式。
- `DW_OP_fbreg` 表示相对于帧基址的偏移，`DW_OP_reg5` 表示变量位于某个寄存器。
- 变量在生命周期内可能移动，位置列表按 PC 范围给出不同的位置描述。
- 优化后变量可能只存在于寄存器，或被拆分为多个片段，用 `DW_OP_piece` 组合。
- 变量被优化掉时没有位置信息，调试器显示 `<optimized out>`。
- `DW_AT_frame_base` 定义帧基址，通常指向 CFA 或帧指针。

### 10.5 `-g` 的级别与 DWARF 版本如何选择？

- `-g0` 不生成调试信息，`-g1` 只生成最小信息（行号与函数名），`-g2` 为默认，`-g3` 增加宏定义。
- `-gdwarf-4` 与 `-gdwarf-5` 选择版本，DWARF 5 需要较新的 GDB、objdump 与 IDE 支持。
- GCC 11 起默认生成 DWARF 5，旧工具链可能无法解析新增的节。
- `-g` 与优化级别独立，`-O2 -g` 可以共存，但变量可见性与行号精度下降。
- `-g3` 会显著增大调试信息体积，宏信息通常只在需要时开启。
- `-gsplit-dwarf` 把调试信息移出目标文件，配合 `dwp` 打包。

### 10.6（场景）优化构建中变量为何显示为 `<optimized out>`？

- 变量被寄存器分配后不再有稳定的内存位置，调试信息只能记录寄存器或片段。
- 变量在断点处尚未初始化或已超出生命周期，位置列表中没有覆盖当前 PC 的项。
- inline 展开把变量分散到多个实例，调试器需要选择正确的 `DW_TAG_inlined_subroutine`。
- 编译器删除了未使用的变量，或把常量传播后不再保留存储。
- 降低优化级别到 `-O0` 或 `-Og` 可以保留更多变量，代价是性能。
- 用 `info locals`、`info args` 与反汇编对照，确认值是否仍在寄存器中。

### 10.7 行号表在优化后为何跳转异常？

- 指令调度与 inline 展开把不同源码行的指令混排，行号表只能近似描述。
- 尾调用优化会移除当前帧，回溯显示的调用者可能与源码结构不一致。
- inline 函数的行号记录在调用点的编译单元中，需要 `DW_AT_call_file` 与 `DW_AT_call_line` 还原调用链。
- 相同源码行可能生成多个地址区间，单步执行会在行间反复跳转。
- GCC 的 `-gstatement-frontiers` 影响语句边界记录，进而影响单步行为。
- 调试时结合 `disassemble /m` 与行号表，可以判断指令对应的真实源码位置。

### 10.8 `.eh_frame` 与 `.debug_frame` 的区别？

- `.eh_frame` 参与运行时展开，带 `SHF_ALLOC`，加载到内存，格式与 `.debug_frame` 相近但不完全相同。
- `.debug_frame` 只供调试器使用，不加载，可被 `strip --strip-debug` 删除。
- `.eh_frame` 的 CIE 使用 augmentation 字符串描述 personality 与 LSDA 编码，`.debug_frame` 不需要。
- `.eh_frame` 的地址编码常使用 PC 相对与 `DW_EH_PE_*` 编码，节省重定位。
- 许多工具链默认只生成 `.eh_frame`，是否生成 `.debug_frame` 由编译器与选项决定，由实现定义。
- 用 `readelf --debug-dump=frames` 查看两种节，`--debug-dump=frames-interp` 输出解释后的规则。

### 10.9 CFI 指令如何描述一帧？

- `DW_CFA_def_cfa` 定义 CFA 的计算方式，x86-64 进入函数后常见为 `rsp + 8`。
- `DW_CFA_offset` 说明某个寄存器保存在 CFA 的哪个偏移，返回地址通常在 CFA 减 8 的位置。
- `DW_CFA_advance_loc` 推进到新的 PC 区间，后续规则只在该区间生效。
- `DW_CFA_remember_state` 与 `DW_CFA_restore_state` 保存与恢复规则栈，处理分支与清理路径。
- `DW_CFA_def_cfa_register` 在帧指针建立后把 CFA 基准切换到 `rbp`。
- 规则序列化在 CIE 与 FDE 中，CIE 保存初始规则，FDE 保存函数特有的增量。

### 10.10 展开器如何用 CFI 恢复上一帧？

- 从当前 PC 定位 FDE，合并 CIE 初始规则与 FDE 指令得到当前规则集。
- 按 CFA 规则计算规范帧地址，再按偏移规则读取返回地址与 callee-saved 寄存器。
- 返回地址写入 PC，CFA 成为上一帧的栈指针，循环进入上一层。
- 若规则缺失或地址超出 FDE 范围，展开失败，`backtrace` 提前结束。
- `_Unwind_Backtrace` 依赖 CFI，`backtrace()` 在多数实现上也使用展开表，区别在于接口与展开器的来源。
- 无帧指针的代码完全依赖 CFI，剥离 `.eh_frame` 会导致回溯中断。

### 10.11 `-fomit-frame-pointer` 与展开的关系？

- x86-64 在 `-O1` 及以上默认省略帧指针，把 `rbp` 释放为通用寄存器。
- 展开依赖 `.eh_frame` 中的 CFA 规则，而不是帧指针链，因此省略帧指针不影响基于 CFI 的回溯。
- 手写汇编或缺少 CFI 的代码在省略帧指针后无法回溯，性能分析工具只能给出部分调用栈。
- `-fno-omit-frame-pointer` 保留帧指针链，便于采样分析器快速遍历，代价是一个寄存器与少量指令。
- `perf` 的 `--call-graph fp` 依赖帧指针，`--call-graph dwarf` 依赖调试信息。
- 发布构建常在性能与可观测性之间选择，服务端通常保留帧指针。

### 10.12（场景）线上 core 文件只能看到地址，如何恢复符号？

- 从 core 或二进制读取 build-id，`readelf -n` 显示 `NT_GNU_BUILD_ID`。
- 按 build-id 在 `/usr/lib/debug/.build-id/` 下查找对应调试文件，或配置 `debuginfod`。
- `gdb` 加载二进制与 core 后，用 `info sharedlibrary` 与 `bt` 查看缺少符号的帧。
- 若调试文件与二进制不匹配，GDB 会给出 warning，栈回溯可能错位。
- `addr2line -e binary -f -C 0x...` 可以在无调试器时把地址转换为函数与行号。
- 确认编译时的 `-g` 与优化级别，缺少调试信息的二进制只能依赖动态符号表。

### 10.13 build-id 与 `.gnu_debuglink` 的作用？

- build-id 是链接器生成的唯一标识，通常为 160 位 SHA-1，写入 `.note.gnu.build-id`。
- 调试文件按 build-id 存放在 `/usr/lib/debug/.build-id/ab/cdef....debug`，GDB 与 debuginfod 按此查找。
- `.gnu_debuglink` 记录调试文件名与 CRC，GDB 在二进制同目录、`.debug` 子目录与全局调试目录中查找。
- `objcopy --only-keep-debug` 生成调试文件，`--add-gnu-debuglink` 写入链接信息。
- build-id 在 strip 后保留，是定位调试文件最可靠的键。
- `.gnu_debuglink` 依赖文件名，重命名调试文件会导致查找失败。

### 10.14 debuginfod 如何工作？

- debuginfod 是 HTTP 服务，按 build-id 提供调试信息、源码与可执行文件。
- 客户端设置 `DEBUGINFOD_URLS` 环境变量，GDB、elfutils 与 systemd-coredump 会按需查询。
- `debuginfod-find debuginfo <build-id>` 直接下载对应文件，`debuginfod-find source` 获取源码。
- 服务端索引构建产物，支持按 build-id、文件名与源码路径查询。
- 使用前需要确认网络策略与隐私要求，调试信息可能包含源码路径与构建环境信息。
- 缓存目录由 `DEBUGINFOD_CACHE_PATH` 指定，默认位于用户主目录下。

### 10.15 分离调试信息的标准流程？

- 构建时用 `-g` 生成完整调试信息，链接后用 `objcopy --only-keep-debug app app.debug` 提取。
- 用 `strip --strip-debug app` 或 `strip --strip-unneeded` 移除调试节，保留动态符号与 `.eh_frame`。
- 用 `objcopy --add-gnu-debuglink=app.debug app` 写入链接信息，部署时只分发精简后的二进制。
- 调试文件按 build-id 放入调试目录，或与二进制同目录并保持文件名一致。
- 验证用 `readelf -S app` 确认 `.debug_*` 已移除，`gdb app` 能自动加载调试文件。
- 发布流程需要保存调试文件与源码版本的对应关系，否则后续无法还原。

### 10.16 `-gsplit-dwarf` 的使用与限制？

- 该选项把调试信息写入 `.dwo` 文件，目标文件中只保留骨架 DIE 与 `DW_AT_dwo_name`。
- 链接阶段生成与主二进制分离的布局，调试器按路径或 build-id 查找 `.dwo`。
- `dwp` 把多个 `.dwo` 打包为 `.dwp`，便于分发与调试。
- 并行编译时减少目标文件体积与链接输入，适合大型工程。
- `.dwo` 文件丢失后调试信息不完整，部署时需要与二进制一起保存。
- 不同编译器生成的 `.dwo` 在扩展与索引上可能不同，跨工具链调试由实现定义。

### 10.17 调试信息的压缩与裁剪？

- `-gz=zlib` 压缩 `.debug_*` 节，磁盘体积下降，调试器透明解压。
- `-Wl,--compress-debug-sections=zlib` 在链接阶段压缩，效果与编译期选项相同。
- `-feliminate-unused-debug-types` 移除未使用的类型 DIE，减少调试信息体积。
- `-g1` 只保留行号与函数信息，适合发布版本的符号化需求。
- `strip --strip-debug` 删除调试节但保留 `.symtab`，`strip` 默认删除更多符号。
- 压缩后的节可能名为 `.zdebug_*`，也可能保留原名并设置 `SHF_COMPRESSED`，取决于工具链。

### 10.18（场景）inline 函数的断点与回溯为何异常？

- inline 函数没有独立栈帧，断点落在调用者的地址范围，GDB 用 inline 实例信息显示逻辑帧。
- `DW_TAG_inlined_subroutine` 记录 inline 的地址范围与调用点，`bt` 可以显示 inline 帧。
- 同一函数多处 inline 时，断点会落在多个地址上，GDB 在设置时列出多个 location。
- `-O0` 禁止 inline 优化，调试行为接近源码结构，但性能与发布版本不同。
- `__attribute__((noinline))` 可用于保留特定函数的帧，便于定位。
- 调试信息缺失时，inline 帧完全不可见，回溯只显示物理帧。

### 10.19 `addr2line` 与 `llvm-symbolizer` 的差异？

- `addr2line -e app -f -C 0x401136` 输出函数名与文件行号，`-i` 展开 inline 帧。
- `llvm-symbolizer --obj=app 0x401136` 输出类似信息，支持 inline 展开与更丰富的格式。
- 两者都依赖 `.debug_line` 与 `.debug_info`，缺少调试信息时只给出 `??`。
- `addr2line` 对 PIE 与共享库需要传入对象内的虚拟地址，而不是运行时加载地址。
- `llvm-symbolizer` 被 sanitizer 与 `perf` 用作符号化后端，通过 `LLVM_SYMBOLIZER_PATH` 指定。
- 批量符号化时把地址列表传给工具，比逐个调用效率高。

### 10.20（场景）发布二进制体积因调试信息膨胀，如何处理？

- 先用 `size -A app` 与 `bloaty app` 分解各节，确认 `.debug_*` 的占比。
- 发布构建分离调试信息，只分发 strip 后的二进制，调试文件归档保存。
- 用 `-g1` 或 `-gz` 降低调试信息体积，保留行号用于符号化。
- 检查是否误把 `-g3` 与未裁剪的模板调试信息带入发布产物。
- `.eh_frame` 与 `.symtab` 不属于调试信息，`strip --strip-debug` 不会删除它们。
- 用 `readelf -S` 对比构建选项变化前后的节大小，定位增长来源。

## 11. LTO、PGO 与优化选项

### 11.1 LTO 与传统分离编译的差别是什么？

- 传统流程中每个翻译单元独立生成机器码，跨单元只能靠链接器做重定位与符号解析，inline、常量传播与死代码消除都局限在单个翻译单元内。
- LTO 让编译器前端输出中间表示，把跨单元优化推迟到链接阶段；GCC 使用 GIMPLE 字节码，存放在 ELF 的 `.gnu.lto_*` 段，Clang 使用 LLVM bitcode，ELF 下位于 `.llvmbc` 段。
- 链接时由 LTO 插件重新调用编译器后端，GCC 对应 `lto1` 与 `lto-wrapper`，Clang 对应链接器插件与 `libLTO`。
- fat LTO object 同时保留机器码与中间表示，插件不可用时退回普通链接；GCC 用 `-ffat-lto-objects` 控制，Clang 没有等价物。
- 跨单元优化能看到完整调用图，因而可以删除未被引用的外部函数、传播常量、对单态虚调用去虚拟化。
- 代价是链接阶段的内存与时间上升，目标文件变大，增量构建粒度从单个文件退化为整个 LTO 单元。
- 编译与链接必须使用同一套 LTO 插件与兼容的编译器版本，否则会报插件错误或静默退回非 LTO 路径。

### 11.2（辨析）`-flto` 与 `-flto=thin` 的取舍是什么？

- GCC 与 Clang 的 `-flto` 默认都使用 full LTO，把所有中间表示合并为一个优化单元，优化视野最完整。
- full LTO 的链接内存近似随程序规模线性增长，大型项目常在链接阶段出现内存峰值或超时。
- ThinLTO 在编译期为每个模块生成摘要，链接时先建立全局索引，再按需把函数体导入调用方模块。
- ThinLTO 的后端优化按模块并行，内存占用与单模块规模相关，适合多核机器与增量链接。
- 跨模块优化是机会性的，导入受指令数阈值限制，效果通常接近 full LTO，但不保证等价。
- GCC 与 Clang 都提供 `-flto=thin`，成熟度与可用参数随版本变化，由实现定义。
- 选择时应以链接内存、构建时长与运行时基准共同判断，不能只看优化级别。

### 11.3（实现）ThinLTO 的索引、摘要与导入如何工作？

- 编译阶段每个模块输出 bitcode，并记录函数摘要：指令数、调用边、可见性与是否可导入。
- 链接阶段先合并摘要生成全局索引，完成符号解析、可见性判定与跨模块 inline 决策。
- 后端阶段按模块并行执行，将收益足够的函数体从其他模块导入当前模块，阈值由 `-import-instr-limit` 一类参数控制。
- 导入会复制函数体，可能增大代码体积；链接器依靠 `linkonce_odr` 与相同代码折叠去重。
- Clang 的 `-fwhole-program-vtables` 配合 LTO 做全程序虚表分析，为去虚拟化提供类型信息。
- 每个模块的后端产物可按输入哈希缓存，分布式链接可以只重算受影响的模块。
- 排查导入决策时，Clang 可用 `-Wl,-plugin-opt=save-temps` 保留中间产物，再检查导入后的 bitcode。

### 11.4 LTO 下静态库为什么需要专用归档工具？

- `ar` 不加载 LTO 插件，无法从中间表示读取符号，归档索引可能缺少 LTO 符号。
- 索引缺失时链接器看不到归档成员提供的符号，表现为 `undefined reference`，即使成员确实存在。
- GCC 提供 `gcc-ar`、`gcc-ranlib` 与 `gcc-nm`，运行时加载 `liblto_plugin`，从中间表示提取符号。
- 用 `-flto` 编译的静态库应当用对应包装工具创建与更新索引，不能混用系统 `ar`。
- 也可以使用 `-ffat-lto-objects`，让归档保留普通符号表，代价是目标文件体积翻倍。
- 检查归档内容用 `ar t`，检查索引用 `nm -s`；直接对 bitcode 运行 `nm` 可能显示无符号。
- 链接时加 `-Wl,--verbose` 可以确认插件是否加载，以及归档是否按预期被扫描。

### 11.5 混用 LTO 与非 LTO 目标文件会发生什么？

- 链接器把非 LTO 目标按普通机器码处理，LTO 插件只优化中间表示部分，跨边界的 inline 与常量传播失效。
- GCC 在 full LTO 下遇到非 LTO 输入会退化为部分 LTO，仍能完成链接，但优化范围缩小。
- 只有中间表示、没有机器码的目标文件在插件缺失时无法处理，链接器会报无法识别的文件格式。
- 编译与链接的 LTO 模式不一致，例如一端 `-flto=thin`、另一端 `-flto`，可能报插件错误或产生非预期结果。
- 不同编译器版本生成的 bitcode 不保证兼容，LLVM 的 bitcode 带版本号，升级工具链后旧对象可能无法读取。
- 第三方预编译库通常不含中间表示，LTO 对其无效，应显式用 `-fno-lto` 隔离或接受优化边界。
- 检查目标文件：`readelf -S` 查看 `.gnu.lto_*` 或 `.llvmbc` 段，`file` 查看是否标记为 LLVM IR。

### 11.6 LTO 与符号可见性、`-fno-semantic-interposition` 有什么关系？

- 默认可见性下，编译器必须假设共享库内的符号可能被同名符号插入，因此不能随意 inline 或折叠常量。
- `-fno-semantic-interposition` 取消这一假设，允许对库内符号做 inline 与去虚拟化，主要用于 `-fPIC` 共享库。
- `-fvisibility=hidden` 把符号默认设为隐藏，只对显式标注 `visibility("default")` 的接口导出，能缩小动态符号表。
- LTO 在链接时能看到最终绑定，可能把隐藏符号或本地符号 internalize，再删除未引用代码。
- `-Wl,-Bsymbolic` 在链接时绑定库内引用，改变插入语义，使用前需要确认没有依赖符号插入的扩展机制。
- 这些选项改变语义假设，ABI 兼容性需要单独评估，不能当作单纯的优化开关。
- 检查导出符号用 `nm -D --defined-only`，检查 `SYMBOLIC` 标志用 `readelf -d`。

### 11.7 `-ffunction-sections` 与 `--gc-sections` 如何减小体积？

- `-ffunction-sections` 把每个函数放入独立段，段名形如 `.text.foo`；`-fdata-sections` 对数据做同样处理。
- 链接时 `--gc-sections` 从入口、导出符号与 `KEEP` 标记出发做可达性分析，丢弃不可达段。
- 没有分节时，同一段内的函数只能整体保留，垃圾回收的粒度不足。
- 对静态库效果明显：未被引用的初始化函数、模板实例与异常清理代码可以被删除。
- 代价是段数量与重定位项增加，目标文件变大，链接时间上升。
- 与 LTO 叠加时，LTO 先做跨模块死代码消除，`--gc-sections` 再清理剩余段，两者互补。
- 构造函数指针表、链接脚本的 `KEEP` 与 `__attribute__((used))` 会让段被视为可达，需要逐项确认。

### 11.8 `-O0`、`-O1`、`-O2`、`-O3` 的边界在哪里？

- `-O0` 关闭优化，变量可独立观察，调试体验最好，运行时间与代码体积最差。
- `-O1` 打开常量传播、死代码消除、尾调用与基础寄存器分配，编译快，体积适中。
- `-O2` 增加指令调度、公共子表达式消除、循环优化与小函数 inline，是发布构建的常用起点。
- `-O3` 增加循环向量化、循环展开、更激进的 inline 与过程间优化，可能显著增大体积并降低指令缓存命中。
- `-Ofast` 在 `-O3` 之上启用 `-ffast-math`，放弃 IEEE 浮点的严格语义，NaN、Inf 与结合律行为都会改变。
- 每个级别对应一组具体开关，内容由编译器与版本决定，GCC 与 Clang 的同名级别并不等价。
- 选择应以基准测试为准，按文件混合 `-O2` 与 `-O3` 比全局调高更可控。

### 11.9 `-Os` 与 `-Oz` 如何选择？

- `-Os` 在 `-O2` 基础上关闭会增大体积的优化，例如部分循环展开与激进对齐，性能通常接近 `-O2`。
- `-Oz` 进一步牺牲性能换取体积，关闭更多对齐、展开与 inline，较新的 GCC 也提供该选项。
- 闪存、移动端分发与 WebAssembly 场景通常优先 `-Os`，对安装包大小极敏感时才用 `-Oz`。
- 两者的性能下降幅度取决于代码特征，热路径密集的程序在 `-Oz` 下可能明显变慢。
- 与 LTO 组合时，inline 决策会参考体积模型，`-Oz` 会抑制跨模块 inline。
- 配合 `--gc-sections`、`-fno-asynchronous-unwind-tables` 可进一步压缩，但会影响异常处理与栈回溯。
- `-fno-exceptions` 与 `-fno-rtti` 能显著减小体积，但改变语言语义与 ABI，不能对已编译的库单方面启用。

### 11.10 `-Og` 适合什么场景，代价是什么？

- `-Og` 的目标是保留调试体验的优化级别，GCC 文档建议用它替代 `-O0` 作为默认调试构建。
- 它打开不影响单步与变量观察的优化，生成的代码比 `-O0` 更接近发布版本。
- 优化程度低于 `-O1`，运行性能不能代表发布构建，不能据此得出性能结论。
- 被 inline 的函数与提升到寄存器的变量仍可能无法观察，需要 `-fno-inline` 或 `-O0` 辅助。
- Clang 对 `-Og` 的实现与 GCC 不同，启用的优化集合由实现定义。
- 适合日常开发与单元测试，发布构建仍应使用 `-O2` 或 `-O3` 单独验证。
- 与 sanitizer 组合时，`-Og` 比 `-O0` 更接近真实执行路径，但栈帧仍可能被优化。

### 11.11（陷阱）`-march=native` 的部署风险如何评估？

- `-march=native` 让编译器探测构建机的指令集扩展，生成依赖 AVX、AVX-512、BMI2 等特性的代码。
- 构建机与部署机代际不同时，可能执行到非法指令并收到 `SIGILL`，容器与虚拟机环境更容易出现。
- 虚拟化层可能屏蔽或伪造 CPUID，探测结果与真实运行环境不一致；探测方式与结果由实现定义。
- 发布产物应使用明确的基线，例如 `-march=x86-64-v2`、`-march=x86-64-v3`，或按目标 CPU 指定 `-mavx2`。
- `-mtune` 只影响指令选择与调度，不提高指令集要求，可以按目标微架构安全设置。
- 需要利用新指令时，采用运行时派发：多版本函数、`ifunc` 或显式的函数指针选择。
- 验证方式是在最低配置机器上运行冒烟测试，并用 `objdump -d` 搜索不应出现的指令。

### 11.12 PGO 的插桩流程有哪几步？

- 第一阶段用 `-fprofile-generate` 编译与链接，插入计数器，生成带插桩的可执行文件。
- 用代表性负载运行，计数器写入剖面文件：GCC 为 `.gcda`，Clang 为 `.profraw`。
- 剖面路径由 `-fprofile-dir` 或 `LLVM_PROFILE_FILE` 控制，多进程运行会产生多份文件。
- 第二阶段用 `-fprofile-use` 重新编译，读取剖面做分支布局、inline 与去虚拟化。
- 训练负载的分支分布必须接近真实负载，偏差会把冷路径误判为热路径，性能可能下降。
- GCC 用 `-fprofile-correction` 容忍计数不一致，Clang 用 `llvm-profdata merge` 合并剖面。
- 剖面与源码版本绑定，源文件行号变化会导致剖面错配，需要重新训练并重新生成。

### 11.13（辨析）插桩 PGO 与采样 PGO 的差别是什么？

- 插桩 PGO 精确记录每个分支与调用边的执行次数，运行时开销从百分之十到数倍不等。
- 采样 PGO 用 `perf` 一类工具采集调用栈，离线转换为剖面，运行时开销低，适合生产环境。
- 采样对短函数与低频分支覆盖不足，精度低于插桩，且依赖准确的符号与调试信息。
- Clang 用 `-fprofile-sample-use` 读取转换后的采样剖面，GCC 提供 `-fauto-profile`。
- 插桩 PGO 需要专门的训练环境与可重复负载，采样 PGO 可以在真实流量上持续采集。
- 两者都要求源码与构建配置稳定，采样 PGO 还需要把地址准确映射回函数。
- 选择取决于精度与可复现性要求，编译器发行版自身常使用采样 PGO。

### 11.14 PGO 剖面过期或路径变化时如何诊断？

- GCC 找不到 `.gcda` 时给出 `-Wmissing-profile`，计数不一致时给出 `-Wcoverage-mismatch`。
- Clang 用 `-Wprofile-instr-missing`、`-Wprofile-instr-out-of-date` 与 `-Wprofile-instr-unprofiled` 区分缺失、过期与未覆盖。
- 常见原因是构建目录被清理、`-fprofile-dir` 与运行目录不一致、多个配置共用同一剖面目录。
- 源文件增删行后，基于行号的剖面会错位，正确做法是重新训练；关闭告警会掩盖问题。
- `-fprofile-correction` 只处理计数不一致，不修复过期的映射关系。
- 用 `gcov` 或 `llvm-cov` 查看剖面覆盖率，确认训练是否覆盖关键路径。
- 构建系统应把剖面文件作为显式输入并纳入缓存键，避免静默复用旧数据。

### 11.15 间接调用与虚函数在 PGO 下如何被优化？

- 剖面记录每个间接调用点实际到达的目标，编译器可把间接调用改写为「守卫 + 直接调用」，即推测性去虚拟化。
- 单态调用点收益最大，一个目标占绝大多数时，守卫失败的概率低。
- GCC 用 `-fdevirtualize-speculatively` 与 `-fdevirtualize-at-ltrans` 控制该类优化，Clang 在 `-fprofile-use` 下启用推测。
- 去虚拟化只有在后续 inline 与常量传播能利用具体类型时才有明显收益，否则只是省一次间接跳转。
- 训练数据只覆盖一种派生类时，推测会在其他类型上失败并增加分支开销。
- 与 `final` 以及全程序虚表分析配合，可以扩大可去虚拟化的范围。
- 检查优化结果可用 `objdump -d` 查看守卫分支，或 `-fdump-tree-optimized` 一类中间表示转储。

### 11.16 `__builtin_expect` 与 PGO 会冲突吗？

- `__builtin_expect` 提供静态分支概率，PGO 提供实测概率，两者同时存在时通常以剖面为准。
- GCC 文档说明剖面反馈会覆盖内置提示，Clang 的行为类似，具体优先级由实现定义。
- 没有剖面时，内置提示影响基本块布局与分支预测提示，对现代 CPU 的直接收益有限。
- C++20 的 `[[likely]]` 与 `[[unlikely]]` 是标准属性，表达同样的意图，同样会被剖面覆盖。
- 手工提示应只用于稳定知识，例如错误路径与冷分支，不能替代训练数据。
- 混用不会导致错误，但会让性能归因变复杂，基准报告应记录两者的使用情况。
- 检查布局可用 `objdump -d` 观察热路径是否连续，用 `perf` 观察分支缺失。

```cpp
#include <cstdlib>

int parse(const char* s) {
    if (s == nullptr) [[unlikely]] {
        return -1;
    }
    return std::atoi(s);
}
```

### 11.17 BOLT 与 PGO 的分工是什么？

- BOLT 是链接后优化器，输入是已链接的 ELF，按剖面重排函数与基本块，减少指令缓存与 iTLB 缺失。
- PGO 在编译期改变 inline 与代码生成，BOLT 在二进制层改变布局，两者可以叠加。
- 典型流程是用 `perf record` 采集剖面，再用 `llvm-bolt` 重写 ELF，最后修正调试信息。
- BOLT 需要未剥离的二进制与准确的剖面，剥离调试信息后效果受限。
- 它还支持函数拆分与热冷分离，适合大型服务与指令缓存敏感的程序。
- 与编译期的 `-freorder-blocks-and-partition` 互补，后者依赖剖面质量。
- 重排会改变地址，符号化与缓存需要保留原始二进制与构建 ID。

### 11.18 如何定位二进制体积的增长来源？

- 先看总体分布：`size` 与 `llvm-size` 给出各段大小，`bloaty` 可以下钻到编译单元与符号。
- `nm --size-sort -C` 列出符号大小，`readelf -S` 查看段布局，`objdump -h` 查看对齐填充。
- 对比两个版本时用 `bloaty -d compileunits,symbols` 做差分，比单看总量更有效。
- 常见来源包括模板实例化、异常表与 RTTI、调试信息、静态初始化与 inline 函数的重复副本。
- 编译选项层面检查 `-O3` 的过度 inline、`--gc-sections` 是否开启、异常与 RTTI 是否必需。
- 链接层面检查是否误带静态库、是否导出过多符号、是否保留未使用的段。
- 发布包可用 `-gsplit-dwarf` 或 `objcopy --only-keep-debug` 分离调试信息，调试时再按构建 ID 取回。

### 11.19 热冷分离与代码布局如何影响指令缓存？

- 热冷分离把很少执行的路径移到 `.text.unlikely`，减少热路径占用的指令缓存行。
- GCC 的 `-freorder-blocks-and-partition` 需要剖面数据，缺少剖面时依赖静态启发式。
- 函数重排把经常连续调用的函数放近，减少 iTLB 缺失与页切换，BOLT 与链接脚本都能实现。
- 对齐填充会增大体积，`-falign-functions` 一类参数需要按微架构与体积目标调整。
- 过度 inline 会让热函数膨胀，反而挤出指令缓存，`-O2` 通常比 `-O3` 更稳。
- 度量用 `perf stat` 观察指令缓存缺失，用 `perf record` 结合符号定位热点。
- 布局策略与硬件强相关，跨平台比较时需要固定编译器版本与参数。

### 11.20（场景）开启 LTO 后二进制变大且调试困难，如何排查？

- 先用 `bloaty` 对比开启前后的段与符号，区分代码增长、调试信息增长与对齐填充。
- LTO 会扩大 inline 与函数克隆，检查是否产生大量副本，必要时用 `--param inline-unit-growth` 限制。
- 确认 `-g` 同时出现在编译与链接阶段，GCC 的 LTO 链接行缺少 `-g` 会丢失调试信息。
- 变量消失与行号偏移是优化的正常结果，可用 `-fno-inline`、`-Og` 或 `-g3` 辅助定位。
- 检查 `--gc-sections` 是否仍生效，LTO 合并段后可达性分析的粒度可能变化。
- 链接内存不足时改用 ThinLTO 或调整 `-flto` 的并行度，不要直接放弃 LTO。
- 建立体积基线并纳入 CI，用 `size` 或 `bloaty` 的差值判断回归。

## 12. sanitizer 与静态分析

### 12.1（实现）ASan 如何用影子内存检测越界？

- 编译期在每次内存访问前插入检查，读取地址对应的影子字节；影子内存约为地址空间的八分之一。
- 每 8 字节应用内存对应 1 字节影子：0 表示全部可访问，1 到 7 表示前 N 字节可访问，负值表示红区。
- 堆分配在对象两侧放置红区，栈对象周围插入红区，全局对象周围放置全局红区，越界会命中红区。
- 释放的堆块进入隔离区延迟复用，use-after-free 在块被复用前仍能被识别。
- 影子地址由固定偏移映射得到，x86-64 上常用偏移为 `0x7fff8000`，运行时在启动时保留该区域。
- 命中错误时输出访问类型、地址、影子值、分配栈与释放栈，随后终止进程。
- 只检测被插桩的代码，未插桩的第三方库内部越界可能漏报。

```cpp
int read_after_free() {
    int* p = new int(42);
    delete p;
    return *p;  // use-after-free，ASan 可在此报告
}
```

### 12.2 ASan 报告的典型结构如何阅读？

- 首行给出类别：`heap-buffer-overflow`、`stack-buffer-overflow`、`use-after-free`、`double-free`、`global-buffer-overflow`。
- `READ of size 4 at 0x...` 给出访问宽度与地址，随后一行说明该地址位于哪个对象边界之外。
- 分配栈与释放栈描述对象生命周期，访问栈指向出错语句，三者需要分开阅读。
- `#0` 是出错函数，`#1` 起是调用链；inline 可能折叠帧，需要调试信息与帧指针。
- `Shadow bytes around the buggy address` 显示影子字节，`=>` 标记命中的影子，可判断越界距离。
- `Thread T0` 与末尾的 `SUMMARY` 行便于日志聚合与去重。
- 栈帧显示 `??` 时先检查符号化工具与二进制是否匹配，符号缺失比报告错误更常见。

### 12.3（辨析）ASan 与 LeakSanitizer 的关系是什么？

- LeakSanitizer 是独立检测器，可单独用 `-fsanitize=leak`，也是 ASan 的默认组成部分。
- 进程退出时暂停所有线程，从栈、寄存器、全局与 TLS 出发做可达性分析，不可达堆块视为泄漏。
- 输出泄漏块大小与分配栈；仍被全局缓存引用的块不会被报告。
- Linux 上停止线程与扫描内存依赖 `ptrace`，容器权限不足时会报运行时错误，可用 `detect_leaks=0` 绕过。
- ASan 的隔离区延迟复用，会让泄漏与 use-after-free 更容易暴露，但两者检测目标不同。
- 自定义分配器、被截断的指针与未登记的根会造成误报，可用 `__lsan_ignore_object` 或抑制文件处理。
- 泄漏检测适合在独立 CI 任务中运行，避免与性能测试或内存受限任务混在一起。

### 12.4 UBSan 能检查哪些未定义行为？

- `-fsanitize=undefined` 覆盖有符号整数溢出、移位越界、除零、空指针解引用、对齐错误与无效枚举值。
- 有符号溢出属于未定义行为（`[expr.pre]/4`），检查依赖该前提，`-fwrapv` 会把语义改为回绕，溢出不再属于未定义行为。
- 触发时打印 `runtime error` 与源码位置，默认继续执行，适合一次运行收集多个问题。
- Clang 另有 `-fsanitize=integer`，检查无符号溢出与隐式截断，这些不属于未定义行为。
- `-fsanitize=null`、`-fsanitize=alignment` 可单独启用，部分检查在低优化级别下更可靠。
- 与 ASan 组合为 `-fsanitize=address,undefined`，运行时开销叠加，报告顺序可能交错。
- 数据竞争、未初始化读与严格别名违规不在覆盖范围内，需要 TSan、MSan 或其他手段。

```cpp
int add(int a, int b) {
    return a + b;  // 超出 int 范围时是未定义行为
}
```

### 12.5 UBSan 触发后如何让程序停下并进入调试器？

- 默认只打印并继续；`-fno-sanitize-recover=all` 让首次错误直接终止。
- `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1` 可在运行时控制，后者需要符号化支持。
- 组合 sanitizer 时，`-fno-sanitize-recover=undefined` 只影响 UBSan，ASan 默认终止。
- `-fsanitize-trap=undefined` 把检查替换为陷阱指令，便于调试器捕获，但不再输出诊断文本。
- CI 中建议终止，避免错误被后续日志掩盖；模糊测试中可保留继续以收集更多样本。
- 终止后仍要保存完整日志，源码行与调用栈是定位依据。
- 运行时的 recover 与 abort 处理函数不同，裁剪运行库会改变行为。

### 12.6（实现）TSan 如何检测数据竞争？

- 为每个内存字维护影子单元，记录最近访问的线程、访问类型与逻辑时钟。
- 每次访问插桩检查 happens-before：不同线程、至少一次写、且无同步边时报告竞争。
- 互斥量、原子操作、条件变量与线程创建/join 被拦截，用于更新向量时钟。
- 采用当前时钟与快照时钟两套结构，降低存储开销；整体开销通常在 5 到 10 倍。
- 报告包含两侧访问栈、涉及的锁与线程创建栈，用于判断哪一侧缺少同步。
- 只认识被拦截的同步原语，自定义自旋锁与直接 futex 调用需要注解。
- 原子操作默认按顺序一致建模，宽松序可能产生误报或漏报。

```cpp
int counter = 0;

void worker() {
    for (int i = 0; i < 1000; ++i) {
        ++counter;  // 两个线程同时执行时构成数据竞争
    }
}
```

### 12.7 TSan 的误报如何抑制与注解？

- 常见误报来源是自定义同步、信号处理、`volatile` 轮询与未被拦截的汇编。
- `__tsan_acquire(addr)` 与 `__tsan_release(addr)` 建立 happens-before 边，把地址声明为同步点。
- `__tsan_ignore_thread_begin()` 与 `__tsan_ignore_thread_end()` 用于忽略不参与同步模型的线程。
- `__tsan_atomic*` 系列为自定义原子操作提供建模，避免运行时不认识。
- 抑制文件通过 `TSAN_OPTIONS=suppressions=...` 加载，条目形如 `race:foo`。
- 抑制只应用于第三方库或已确认无害的竞争，并记录原因与复核时间。
- 注解在非 TSan 构建中应提供空实现，避免污染正常编译。

### 12.8（实现）MSan 如何跟踪未初始化内存？

- 为每个字节维护影子值，标记是否已初始化，并在算术、比较与内存操作中传播。
- 读取未初始化值时报告，并给出该值的来源：栈分配、堆分配或系统调用返回。
- 要求整个程序都插桩，包括 C 与 C++ 标准库，否则未插桩代码会破坏影子状态。
- `-fsanitize-memory-track-origins` 追溯来源，开销高于基础模式。
- 与 ASan、TSan 互斥，不能链接到同一个二进制。
- 常见误报来自 `read` 填充的缓冲区、inline 汇编与未插桩的第三方库。
- `__msan_unpoison` 可手动标记已初始化，使用前要确认数据确实被写入。

### 12.9 sanitizer 组合的兼容性边界是什么？

- ASan 与 UBSan 可以组合，ASan 与 LSan 默认一体，TSan 与 ASan、MSan 互斥。
- MSan 与 ASan 互斥，两者的影子内存布局与运行时不兼容。
- HWASan 使用 AArch64 的地址标记，依赖特定内核与分配器，不能与 ASan 同时启用。
- 开销叠加：ASan 约 2 倍，MSan 约 3 倍，TSan 约 5 到 10 倍，具体因程序而异。
- 不同 sanitizer 使用不同运行库，静态链接时容易出现重复定义或初始化顺序问题。
- CI 通常拆成多个任务并行运行，避免把所有检查放进一个二进制。
- 可用组合由编译器与运行时版本决定，升级后需要重新验证。

### 12.10（陷阱）sanitizer 运行时链接失败如何排查？

- 典型错误包括 `undefined reference to __asan_init`、找不到 `-lasan`、`DSO missing from command line`。
- 编译与链接必须使用同一个编译器驱动，直接用 `ld` 链接会丢失 sanitizer 运行库。
- Clang 在 Linux 上默认静态链接 ASan 运行时，GCC 默认动态链接 `libasan.so`，行为不同。
- 共享库被插桩时，最终可执行文件也必须链接运行时，否则符号未定义。
- `-static-libasan` 可静态链入，但多个共享库各自静态链接会导致状态不一致。
- 运行时版本必须与编译器匹配，混用 GCC 与 Clang 的运行库会崩溃或误报。
- 检查 `ldd`、`nm -D` 中的 `__asan_*` 符号，并在链接行加 `-v` 查看实际参数。

### 12.11 `ASAN_OPTIONS` 的常用项如何影响行为？

- `detect_leaks=0/1` 控制泄漏检测，`halt_on_error=1` 让首次错误终止。
- `abort_on_error=1` 产生 core 便于调试，`print_summary=1` 输出汇总。
- `symbolize=1` 与 `external_symbolizer_path` 控制符号化，路径错误会导致栈帧显示地址。
- `quarantine_size_mb` 调整隔离区，过小会漏报 use-after-free，过大会推高内存。
- `allocator_may_return_null=1` 让分配失败返回空指针，用于测试 OOM 路径。
- `detect_stack_use_after_return=1` 检测返回后的栈使用，`strict_string_checks=1` 加强字符串检查。
- 选项通过环境变量传递，CI 中应固定取值并写入日志，便于复现。

### 12.12 符号化失败时如何定位地址？

- 确认二进制带调试信息：`file` 显示 `with debug_info`，`readelf -S` 存在 `.debug_info`。
- ASan 优先调用 `llvm-symbolizer`，确保在 `PATH` 中或设置 `external_symbolizer_path`。
- GCC 生成的二进制可用 `addr2line -e binary -f -C 0x...`，PIE 下需要把运行时地址换算为文件偏移。
- `-g` 与优化级别独立，`-O2 -g` 仍有行号，但变量可能被优化掉。
- 分离调试信息时，`.debug` 文件必须与二进制构建 ID 匹配，`objcopy --add-gnu-debuglink` 建立关联。
- inline 函数需要 `llvm-symbolizer --inlines` 或 `addr2line -i` 展开。
- 完全 strip 的二进制无法还原源码行，只能依赖符号服务器或未剥离的副本。

### 12.13（场景）CI 中 ASan 任务内存占用过高如何处置？

- ASan 的影子内存主要是虚拟地址预留，常驻内存来自隔离区、红区与分配元数据，先看峰值 RSS。
- 并行运行多个测试进程会成倍放大占用，限制并发或按测试分片。
- 泄漏检测在退出时扫描堆，可能抬高峰值，可与主测试分开运行。
- 32 位进程地址空间不足会直接失败，应改用 64 位或减小隔离区。
- 容器内存上限过低会触发 OOM killer，日志中表现为没有 ASan 报告的突然退出。
- 可用 `quarantine_size_mb` 与 `malloc_context_size` 降低开销，再逐步调回。
- 仍不足时改用 HWASan，或只在关键测试集上启用 ASan。

### 12.14 sanitizer 与优化级别、帧指针的关系是什么？

- sanitizer 可在 `-O1` 与 `-O2` 下工作，优化会改变栈布局，但报告中的行号通常仍可信。
- `-fno-omit-frame-pointer` 改善栈回溯，ASan 在 x86-64 上依赖帧指针遍历调用栈。
- `-O0` 下部分 UBSan 检查更精确，但代码膨胀更大，覆盖的执行路径不同。
- 高优化级别可能删除或合并访问，导致漏报，也可能让未定义行为表现为难以解释的结果。
- TSan 建议使用 `-O1` 到 `-O2`，过低会放大插桩开销，过高会改变竞争窗口。
- `-g` 不影响检测能力，只影响符号化质量；发布前可用 `-g1` 减小体积。
- 具体行为由编译器版本与目标架构决定，不能假设不同优化级别报告一致。

### 12.15 Clang Static Analyzer 如何做路径敏感分析？

- 在 Clang AST 上做符号执行，沿控制流探索路径，维护路径条件与符号值。
- 检查器以插件形式注册，常用集合包括 `core`、`unix`、`deadcode` 与 `security`。
- 遇到分支时分叉状态，路径过多时按节点上限与循环展开上限剪枝。
- 能发现空指针解引用、资源泄漏、越界与未初始化读，受路径爆炸限制。
- `scan-build` 包装构建命令并生成 HTML 报告，`clang --analyze` 可对单个文件运行。
- 跨函数分析依赖 inline 与函数摘要，虚调用与函数指针通常保守处理。
- 结果需要人工判定，误报率高于编译器告警。

### 12.16 `clang-tidy` 如何接入构建系统？

- 依赖编译数据库 `compile_commands.json`，CMake 用 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` 生成。
- 运行 `clang-tidy -p build <file>`，`-p` 指向编译数据库所在目录。
- 检查项用 `--checks=-*,bugprone-*,performance-*` 选择，`.clang-tidy` 文件可按目录配置。
- `--fix` 应用替换，`--fix-errors` 在存在编译错误时也尝试修复，结果需要人工审查。
- `run-clang-tidy` 并行处理整个项目，`-header-filter` 控制头文件告警范围。
- 检查项与 LLVM 版本绑定，升级后告警集合变化，CI 应固定版本。
- 全量运行成本高，通常只对改动文件运行，再定期做全量扫描。

### 12.17（辨析）编译器告警、静态分析与 sanitizer 的分工是什么？

- 编译器告警基于单个翻译单元的语法与语义，成本低，覆盖确定性问题。
- 静态分析做跨路径、跨函数的推理，能发现运行时才暴露的问题，误报与成本更高。
- sanitizer 在运行时插桩，只报告实际执行到的路径，精度高但依赖测试覆盖。
- 三者互补：告警挡住低级错误，静态分析覆盖难以触发的路径，sanitizer 验证真实执行。
- 告警与静态分析在编译期运行，sanitizer 需要代表性负载。
- 误报治理方式不同：告警用抑制与基线，静态分析用检查器配置，sanitizer 用抑制文件与注解。
- 任何一类都不能证明缺陷不存在，覆盖范围需要明确记录。

### 12.18 告警基线如何建立与维护？

- 先固定工具链版本与告警集合，建立基线，只对新增代码要求零告警。
- 基线文件记录每条存量告警的位置与规则，代码移动后需要重新生成。
- `-Werror` 配合按目录的 `-Wno-*`，避免全局关闭某类告警。
- 存量告警按类别统计，优先修复与未定义行为、资源生命周期相关的项。
- 抑制条目要写明原因与负责人，并设置复核周期。
- 把告警数量纳入 CI 指标，设置只降不升的阈值。
- 新编译器版本先在旁路任务运行，评估增量后再切换默认工具链。

### 12.19 GCC `-fanalyzer` 的能力与代价是什么？

- `-fanalyzer` 在 GCC 中间表示上做过程间路径敏感分析，能发现泄漏、双重释放、空指针与越界。
- 复用编译器前端，不需要额外构建系统，但编译时间可能成倍增加。
- 检查器用 `-fanalyzer-checker=...` 选择，告警由 `-Wanalyzer-*` 控制。
- 跨函数分析受 inline 与摘要限制，递归与函数指针会降低精度。
- 误报可借助 `__attribute__((malloc))` 一类属性与抑制选项减少。
- 适合在独立 CI 任务中分析核心文件，不宜对全部代码常开。
- 检查集与 Clang Static Analyzer 不同，结果不能直接互换。

### 12.20（场景）第三方头文件引发大量告警，如何处理？

- 第三方头文件的告警通常来自系统宏、旧式转换与未使用参数，先确认是否可升级依赖。
- CMake 中用 `SYSTEM` 关键字包含目录，GCC 与 Clang 会把这些路径当作系统头文件并降低告警级别。
- 手工编译时用 `-isystem` 代替 `-I`，效果相同。
- 必须保留告警时，用 `#pragma GCC diagnostic push/pop` 包住包含点，范围要尽量小。
- 不要用 `-w` 全局关闭告警，它会把项目自身的缺陷一起隐藏。
- 对固定在项目内的第三方源码，可单独设为不启用 `-Werror` 的目标。
- 记录每项抑制对应的库与版本，升级后重新评估。

## 13. 构建系统与 CMake

### 13.1 CMake 的目标模型与变量模型有何区别？

- 现代 CMake 以目标为中心：`add_library`、`add_executable` 定义目标，属性描述源文件、包含目录、编译选项与依赖。
- 变量（`set`、`CMAKE_*`）具有目录作用域与缓存作用域，容易泄漏到无关目录；目标属性随目标传播，边界清晰。
- `target_link_libraries` 不仅建立链接关系，还传递使用要求，例如头文件路径与编译定义。
- 目标类型包括 `STATIC`、`SHARED`、`MODULE`、`OBJECT`、`INTERFACE` 与 `IMPORTED`，不同类型有不同的传播规则。
- 生成器负责把目标图翻译为具体构建文件，目标模型与生成器无关。
- 安装与导出基于目标，`install(TARGETS ... EXPORT ...)` 生成的配置文件可被下游 `find_package` 使用。
- 全局 `include_directories`、`link_directories` 与 `add_definitions` 缺少传播语义，属于应当避免的旧式写法。

### 13.2 `PUBLIC`、`PRIVATE`、`INTERFACE` 的传播规则是什么？

- `PRIVATE` 只用于当前目标的构建，不传递给消费者。
- `PUBLIC` 同时用于当前目标与消费者，等价于 `PRIVATE` 加 `INTERFACE`。
- `INTERFACE` 只传递给消费者，当前目标自身不使用，头文件库常用这种形式。
- 传播沿 `target_link_libraries` 的依赖图进行，静态库的 `PRIVATE` 依赖在最终链接时仍可能出现。
- CMake 用 `$<LINK_ONLY:...>` 表达只参与链接、不传播使用要求的依赖。
- 编译定义与包含目录遵循同一套关键字，误用会导致消费者缺少宏或头文件路径。
- 生成器表达式可区分构建树与安装树，例如 `$<BUILD_INTERFACE:...>` 与 `$<INSTALL_INTERFACE:...>`。

### 13.3 生成器的选择依据是什么？

- `Unix Makefiles` 兼容性最好，并行能力弱于 Ninja，适合老旧环境或需要 Makefile 的场合。
- `Ninja` 生成 `build.ninja`，启动与增量构建快，依赖图精确，是多数项目的默认推荐。
- `Visual Studio` 与 `Xcode` 是多配置生成器，配置类型在构建时选择，不使用 `CMAKE_BUILD_TYPE`。
- `Ninja Multi-Config` 支持多配置并共享一份依赖图，适合 CI 同时产出 Debug 与 Release。
- 生成器一旦选定会被 `CMakeCache.txt` 锁定，切换时需要清理缓存或新建构建目录。
- 生成器影响可用特性：Ninja 对 `DEPFILE`、restat 与多输出命令的支持更完整。
- 跨平台项目应在 CI 覆盖主要生成器，避免只在一种生成器下验证。

### 13.4 `CMAKE_BUILD_TYPE` 与多配置生成器如何配合？

- 单配置生成器用 `CMAKE_BUILD_TYPE` 选择 `Debug`、`Release`、`RelWithDebInfo` 与 `MinSizeRel`。
- 多配置生成器用 `--config` 选择配置，`CMAKE_BUILD_TYPE` 为空，读取它会得到空字符串。
- `CMAKE_CONFIGURATION_TYPES` 定义可用配置列表，可在多配置生成器下裁剪。
- 各配置的默认选项由 `CMAKE_CXX_FLAGS_<CONFIG>` 提供，`RelWithDebInfo` 通常为 `-O2 -g -DNDEBUG`。
- 自定义配置需要同时设置编译与链接的 `CMAKE_*_FLAGS_<CONFIG>` 变量。
- 生成器表达式 `$<CONFIG:Debug>` 可在目标属性中按配置分支。
- 不应在 `CMakeLists.txt` 中硬编码 `-O2`，它会覆盖配置默认值并破坏多配置构建。

### 13.5 交叉编译的工具链文件如何编写？

- 用 `-DCMAKE_TOOLCHAIN_FILE=...` 指定工具链文件，该文件在启用语言之前被读取。
- 必须设置 `CMAKE_SYSTEM_NAME` 与 `CMAKE_SYSTEM_PROCESSOR`，否则 CMake 按本机编译处理。
- 设置 `CMAKE_C_COMPILER` 与 `CMAKE_CXX_COMPILER` 为目标工具链的绝对路径，避免 `PATH` 中同名驱动造成歧义。
- `CMAKE_SYSROOT` 或 `CMAKE_FIND_ROOT_PATH` 限定头文件与库的搜索范围。
- `CMAKE_FIND_ROOT_PATH_MODE_PROGRAM` 设为 `NEVER`，让构建期工具仍从本机查找；库与头文件模式设为 `ONLY`。
- `CMAKE_CROSSCOMPILING` 为真时 `try_run` 无法执行目标程序，需要改用 `try_compile` 或提供缓存变量。
- 工具链文件只描述编译器与目标系统，项目逻辑应留在 `CMakeLists.txt`。

### 13.6（辨析）`find_package` 的两种模式有何差别？

- Module 模式查找 `Find<Package>.cmake`，由 CMake 或项目提供，内部用 `find_path` 与 `find_library` 探测。
- Config 模式查找 `<Package>Config.cmake` 或 `<lowercase>-config.cmake`，由包自身安装，通常携带导入目标。
- 默认先尝试 Module 模式，再尝试 Config 模式，`CMAKE_FIND_PACKAGE_PREFER_CONFIG` 可以改变优先级。
- Config 模式能提供版本文件与组件，`find_package(Qt6 COMPONENTS Widgets)` 依赖包的组件声明。
- 导入目标形如 `Foo::Foo`，携带包含目录、编译定义与链接依赖，优于直接给出库路径。
- 排查时用 `cmake --debug-find` 输出搜索路径，`Foo_DIR` 可显式指定配置目录。
- 找不到包时要区分未安装、版本不符与组件缺失，三种情况的错误信息不同。

### 13.7 导入目标与别名目标有什么用？

- `add_library(Foo::Foo ALIAS foo)` 让消费者用带命名空间的名字引用目标，避免与系统库重名。
- `IMPORTED` 目标由 `find_package` 或 `add_library(... IMPORTED)` 创建，属性只读，用于描述外部依赖。
- 别名目标不能安装或导出，只用于统一构建树内部的引用名称。
- `INTERFACE` 库适合头文件库，`target_include_directories(... INTERFACE ...)` 把路径传播给消费者。
- 导入目标可设置 `IMPORTED_LOCATION`、`IMPORTED_IMPLIB` 与 `INTERFACE_INCLUDE_DIRECTORIES`。
- 导出时生成的目标文件会引用依赖的导入目标，消费方必须能通过 `find_dependency` 找到它们。
- 用 `$<BUILD_INTERFACE:...>` 与 `$<INSTALL_INTERFACE:...>` 区分构建树与安装树路径。

### 13.8 `target_link_libraries` 的顺序与传递依赖如何处理？

- CMake 会按依赖图重排链接行，但循环依赖仍需 `--start-group` 与 `--end-group` 手工处理。
- 传统 `ld` 对静态库顺序敏感，`LINK_INTERFACE_MULTIPLICITY` 可强制重复某个库以满足符号解析。
- 共享库在启用 `--as-needed` 时，未被引用的库会从 `DT_NEEDED` 中消失。
- 静态库的 `PRIVATE` 依赖仍会出现在最终链接行，因为静态库没有运行时依赖表达。
- `LINK_LIBRARIES` 保存当前目标的直接依赖，`INTERFACE_LINK_LIBRARIES` 保存传播给消费者的依赖。
- `$<LINK_ONLY:foo>` 用于表达只链接、不传播使用要求的依赖。
- 排查时用 `cmake --build --verbose` 查看完整链接行，用 `readelf -d` 查看 `NEEDED`。

### 13.9 构建缓存 `CMakeCache.txt` 为何会导致配置异常？

- 缓存保存变量与探测结果，路径、编译器与选项变化后旧值不会自动失效。
- 移动源码目录或构建目录后，`CMAKE_HOME_DIRECTORY` 与绝对路径失效，需要重新配置。
- 切换编译器必须新建构建目录，CMake 不允许在已配置目录中更换编译器。
- `cmake --fresh` 删除缓存与 `CMakeFiles` 后重新配置，适合排查顽固问题。
- `cmake -U <var>` 可清除匹配的缓存项，`-D<var>=` 可把变量置空。
- `CMakeCache.txt` 中的 `INTERNAL` 项由 CMake 维护，不应手工编辑。
- CI 中应把构建目录视为一次性产物，避免缓存跨工具链版本复用。

### 13.10 `add_custom_command` 的依赖为何经常失效？

- 自定义命令需要显式声明 `DEPENDS`，否则源文件变化不会触发重新生成。
- `OUTPUT` 与 `BYPRODUCTS` 区分主产物与副产物，Ninja 需要后者才能正确清理与调度。
- `DEPFILE` 让编译器输出头文件依赖，例如 `-MD -MF` 生成的 `.d` 文件，供构建系统追踪。
- 多输出命令在 Makefiles 下可能重复执行，Ninja 对多输出的支持更完整。
- `add_custom_target` 总是被视为过期，适合作伪目标，不适合生成需要增量更新的文件。
- 生成的头文件被多个目标使用时，应通过 `add_custom_command` 的 `OUTPUT` 建立依赖。
- 排查时用 `ninja -d explain` 查看重新构建的判定依据。

### 13.11 Ninja 的构建图如何阅读与诊断？

- `build.ninja` 由 CMake 生成，主要包含 `rule`、`build` 与 `default` 三类语句。
- `ninja -t targets` 列出目标，`ninja -t query <target>` 查看输入输出，`ninja -t graph` 输出 DOT 图。
- `ninja -d explain` 解释重建原因，`-d keepdepfile` 保留依赖文件。
- `ninja -t compdb` 生成编译数据库，内容与 `compile_commands.json` 等价。
- `ninja -t clean` 清理产物，`ninja -t cleandead` 删除不再被图引用的文件。
- `ninja -j` 控制并行度，内存不足时降低并行度比更换生成器更有效。
- 生成器表达式展开错误会直接出现在 `build.ninja` 的编译行中，适合从生成结果反查配置。

### 13.12 C++20 模块在 CMake 中如何支持？

- CMake 3.28 起提供 `CXX_MODULES` 文件集，用 `target_sources(foo PUBLIC FILE_SET CXX_MODULES FILES foo.cppm)` 声明模块接口单元。
- 对标准库模块 `import std` 的支持出现在后续版本，使用前需要确认 CMake 与编译器版本。
- `CMAKE_CXX_SCAN_FOR_MODULES` 控制是否扫描模块依赖，扫描器路径由 `CMAKE_CXX_COMPILER_CLANG_SCAN_DEPS` 一类变量指定。
- BMI 是编译器私有格式，不同编译器与版本不兼容，不能跨工具链复用。
- 需要支持动态依赖的生成器，Ninja 是常用选择，Makefiles 对模块扫描的支持有限。
- 模块与头文件混用时，全局模块片段与 `import` 的顺序需要按标准规则处理。
- 支持程度由实现定义，生产项目应固定编译器版本并验证增量构建。

### 13.13 预编译头如何正确使用？

- `target_precompile_headers(foo PRIVATE pch.h)` 生成并复用预编译头，`PRIVATE` 表示只用于当前目标。
- `PUBLIC` 会把预编译头传播给消费者，通常不合适，因为消费者的编译选项可能不同。
- 预编译头对稳定、体积大的系统头效果最好，频繁变动的项目头会导致反复重建。
- GCC 与 Clang 的预编译头格式不同，CMake 负责生成对应参数，Clang 使用 `-include-pch` 一类机制。
- 编译选项与宏必须一致，`-D` 变化会使预编译头失效。
- 预编译头会掩盖头文件的自包含性问题，不能替代包含关系整理。
- 应比较开启前后的编译时间与内存，避免为小项目引入额外复杂度。

### 13.14 安装与导出如何让下游 `find_package` 成功？

- `install(TARGETS foo EXPORT FooTargets ...)` 安装目标，`install(EXPORT FooTargets NAMESPACE Foo:: ...)` 导出目标集合。
- 需要生成 `FooConfig.cmake` 与 `FooConfigVersion.cmake`，可用 `configure_package_config_file` 与 `write_basic_package_version_file`。
- 导出目标的 `INTERFACE_INCLUDE_DIRECTORIES` 应使用 `$<INSTALL_INTERFACE:include>`，不能保留构建树的绝对路径。
- 依赖包要在配置文件中用 `find_dependency` 声明，否则下游会缺少传递依赖。
- `GNUInstallDirs` 提供 `CMAKE_INSTALL_LIBDIR` 等变量，避免硬编码 `lib` 或 `lib64`。
- 用 `cmake --install` 安装到临时前缀，再用独立消费项目验证，不能只在构建树内测试。
- 导出文件中的绝对路径是常见错误，应检查 `FooTargets.cmake` 的内容。

### 13.15 `FetchContent` 与 `ExternalProject` 的差别是什么？

- `FetchContent` 在配置阶段下载并 `add_subdirectory`，与被依赖项目共享同一个构建图。
- `ExternalProject` 在构建阶段下载并独立构建，通过 `ExternalProject_Add` 管理各步骤。
- `FetchContent` 适合头文件库与需要统一编译选项的依赖，代价是配置时间变长。
- `ExternalProject` 适合工具链、不可共存的依赖或需要独立安装的组件。
- 在 `FetchContent_Declare` 中使用 `FIND_PACKAGE_ARGS`，可优先复用已安装的包。
- 两者都受网络影响，应把 `GIT_TAG` 固定到提交哈希并配置离线镜像。
- 重复引入同一依赖时，可用 `OVERRIDE_FIND_PACKAGE` 或统一的版本管理避免冲突。

### 13.16 构建缓存工具如何接入 CMake？

- `CMAKE_CXX_COMPILER_LAUNCHER` 设为 `ccache` 或 `sccache`，CMake 会为每个编译命令加前缀。
- ccache 按预处理输出、编译选项与编译器版本计算哈希，直接模式会跳过预处理以提速。
- 缓存命中率受宏定义、头文件路径与绝对路径影响，`CCACHE_BASEDIR` 可提高跨目录命中。
- 调试信息中的绝对路径会破坏跨机器复用，需要 `-fdebug-prefix-map` 归一化。
- sccache 支持远端共享缓存，适合 CI；ccache 以本地缓存为主。
- 预编译头与模块可能绕过缓存，需要确认工具版本支持。
- 工具链升级后应清空缓存或切换命名空间，避免旧对象被错误复用。

### 13.17（场景）配置阶段找到错误版本的库如何排查？

- 查看 `CMakeCache.txt` 中的 `<Package>_DIR`、包含目录与库路径缓存项。
- 用 `cmake --debug-find` 或 `--trace-expand` 观察搜索顺序与变量展开。
- 检查 `CMAKE_PREFIX_PATH`、`CMAKE_FIND_ROOT_PATH` 与环境变量 `<Package>_ROOT` 是否指向旧安装。
- 系统包管理器与自建安装并存时，搜索优先级由 `CMAKE_FIND_USE_*` 系列变量控制。
- 版本文件可能声明了兼容范围，导致高于预期的版本被接受。
- 导入目标的属性可能指向错误路径，用 `get_target_property` 打印确认。
- 清理缓存后仍失败时，直接检查包自身的 `FooConfig.cmake` 内容。

### 13.18（场景）修改头文件后增量构建没有重新编译，原因是什么？

- 依赖文件缺失：编译器未生成 `.d` 文件，或生成器没有读取 `DEPFILE`。
- 头文件通过绝对路径或符号链接引入，依赖记录与实际路径不一致。
- 预编译头没有跟踪其包含的头文件变化，需要重新生成。
- 时间戳异常会让构建系统认为文件未更新，常见于克隆、解压与跨时区复制。
- 缓存工具错误命中：哈希没有覆盖某个宏、头文件或编译器参数。
- 生成的头文件未声明为 `DEPENDS`，或 `add_custom_target` 被当作总是最新。
- 用 `ninja -d explain` 或 `make --debug=b` 确认判定依据。

### 13.19 `CMakePresets.json` 解决什么问题？

- 预设把生成器、构建类型、工具链文件与缓存变量固化为 JSON，减少命令行参数。
- `configurePresets`、`buildPresets`、`testPresets` 与 `packagePresets` 分别对应各阶段。
- `inherits` 支持分层复用，`hidden` 预设只作为基类，不会直接出现在用户选择中。
- 环境变量可在预设中设置，`$env{...}` 与 `$penv{...}` 区分继承环境与父环境。
- 预设文件可提交到仓库，保证团队与 CI 使用同一配置。
- 版本字段决定可用特性，CMake 版本过低会拒绝读取。
- 预设不能替代工具链文件，交叉编译参数仍应放在工具链文件中。

### 13.20（场景）大型项目配置阶段过慢如何优化？

- 用 `--profiling-format=google-trace` 与 `--profiling-output` 生成 trace，按命令累计时间排序。
- 常见瓶颈是 `find_package`、`execute_process` 与 `FetchContent` 在配置阶段下载依赖。
- 减少配置阶段的子项目配置，改用预构建依赖或包管理器提供二进制。
- 避免在循环中反复调用 `find_library`，把探测结果缓存到 `CMakeCache.txt`。
- 优先使用 Config 模式的导入目标，减少 Module 模式的文件系统扫描。
- 用 `add_subdirectory` 的 `EXCLUDE_FROM_ALL` 控制不参与默认构建的子目录。
- 配置阶段不应执行耗时脚本，生成代码应放到构建阶段。

## 14. 包管理与依赖

### 14.1 Conan 2 的配方与二进制模型是什么？

- 配方 `conanfile.py` 描述源码、依赖、选项与构建方法，`requirements()` 声明直接依赖。
- 包引用形如 `zlib/1.3.1`，`package_id` 进一步区分平台、编译器、选项与依赖版本。
- `conan create` 构建包并放入本地缓存，`conan upload` 推送到远端，消费者按 `package_id` 匹配二进制。
- profile 描述编译器、架构、构建类型与选项，`-pr:b` 与 `-pr:h` 分别指定构建环境与宿主环境。
- `requires` 表达常规依赖，`tool_requires` 表达构建期工具，两者解析到不同的依赖图。
- `conan.lock` 固定解析结果，保证不同机器与不同时间得到同一组包。
- 与 CMake 集成通过 `CMakeToolchain` 与 `CMakeDeps` 生成工具链文件与包配置文件。

### 14.2 vcpkg 的 triplet 与 manifest 模式如何工作？

- triplet 描述目标平台与链接方式，例如 `x64-windows`、`x64-linux`、`arm64-osx`，定义文件位于 `triplets/` 目录。
- manifest 模式用 `vcpkg.json` 声明依赖与版本约束，`builtin-baseline` 固定基线提交。
- 经典模式把包安装到全局 `installed/` 目录，manifest 模式按项目隔离依赖。
- `vcpkg install` 读取 manifest，配合 `CMAKE_TOOLCHAIN_FILE` 指向 `vcpkg.cmake` 注入导入路径。
- `VCPKG_TARGET_TRIPLET` 选择三元组，自定义 triplet 可覆盖编译选项与链接方式。
- 二进制缓存通过 `VCPKG_BINARY_SOURCES` 配置，支持文件系统、NuGet 与 HTTP 后端。
- 端口（port）以 CMake 脚本描述构建过程，修改端口后需要重新生成包。

### 14.3（辨析）Conan 与 vcpkg 的取舍是什么？

- Conan 是独立包管理器，支持任意构建系统，配方可定制，适合多平台与私有包分发。
- vcpkg 与 CMake 集成紧密，端口以 CMake 脚本描述，Windows 与微软生态的支持较完整。
- Conan 的 `package_id` 按编译器、选项与依赖精细区分二进制，适合多配置与二进制分发。
- vcpkg 的 triplet 模型较简单，自定义构建逻辑需要编写 portfile。
- 两者都提供版本约束与锁文件，Conan 的版本范围表达更完整。
- 选择应考虑既有构建系统、私有 registry、CI 缓存设施与团队维护成本。
- 混合使用会引入两套依赖图，通常不推荐。

### 14.4（陷阱）`_GLIBCXX_USE_CXX11_ABI` 不一致会发生什么？

- 该宏控制 libstdc++ 的 `std::string` 与 `std::list` 实现，0 为旧 ABI，1 为 C++11 引入的新 ABI。
- 新 ABI 的符号带 `__cxx11` 标记，两边不一致时链接报未定义符号，例如 `std::__cxx11::basic_string` 相关引用。
- 该宏由编译器默认值决定，GCC 5 起默认为 1；混用不同 GCC 版本或预编译第三方库时容易触发。
- 运行期混用可能出现字符串布局错乱，即使链接通过也不代表安全。
- 修复方式是统一宏并重新编译全部依赖，不能只改一个翻译单元。
- 边界处传递字符串对象时，两侧必须使用同一 ABI；跨边界转换需要显式复制或改用 C 接口。
- 用 `nm -C` 检查符号是否带 `__cxx11`，用 `readelf -p .comment` 查看编译器版本。

### 14.5 语义化版本与版本约束如何表达？

- 语义化版本为 `MAJOR.MINOR.PATCH`，主版本变化表示不兼容，次版本新增功能，补丁修复缺陷。
- Conan 用 `[>=1.2 <2]`、`~1.2`、`^1.2` 表达范围，`~` 允许补丁更新，`^` 允许次版本更新。
- vcpkg 用 `version>=`、`version-semver`、`version-string` 与 `builtin-baseline` 组合约束。
- 版本约束只在解析阶段生效，最终仍需锁文件固定具体版本与修订号。
- 预发布版本的排序与匹配规则由工具定义，不能假设与语义化版本完全一致。
- 传递依赖的约束会合并，冲突时用覆盖或统一升级解决。
- 不应把 Git 分支当作版本，分支内容可变，无法复现。

### 14.6 依赖冲突如何解析与覆盖？

- Conan 2 从根需求出发合并版本范围，冲突时报告 `version conflict` 并给出依赖链。
- 覆盖可在配方中用 `self.requires(..., override=True)` 声明，也可在 profile 的 `[replace_requires]` 中集中配置。
- vcpkg 用 `overrides` 字段强制版本，`builtin-baseline` 提供默认版本。
- 覆盖会改变整个依赖图，可能引入 ABI 不兼容，需要重新构建下游。
- 优先升级直接依赖或放宽范围，覆盖应作为最后手段。
- 锁文件记录解析结果，覆盖后必须重新生成并提交。
- 用 `conan graph info` 或 `vcpkg depend-info` 查看完整依赖链。

### 14.7 二进制缓存如何工作，缺失时如何回退？

- Conan 缓存分为本地缓存与远端，`conan upload` 上传包，`conan install --build=missing` 在缺失时本地构建。
- `package_id` 是缓存键，编译器、选项、依赖版本任一变化都会产生新键。
- vcpkg 按包的 ABI 哈希索引二进制，`VCPKG_BINARY_SOURCES` 配置存储后端与读写权限。
- 缓存命中要求工具链、编译选项与依赖完全一致，绝对路径差异也可能导致未命中。
- 远端缓存应设置保留策略与完整性校验，避免被错误产物污染。
- 回退到源码构建时，构建环境必须可复现，否则缓存结果与本地结果不一致。
- 命中率是核心指标，低命中率通常意味着 `package_id` 维度过细或工具链不稳定。

### 14.8（辨析）供应链安全在包管理中如何实施？

- 固定版本与修订号：Conan 的 `revision`、vcpkg 的基线提交与端口哈希。
- 锁文件进入版本控制，CI 使用锁文件安装，避免每次重新解析。
- 下载内容校验哈希或签名，`GIT_TAG` 不应指向可变分支或可移动标签。
- 构建脚本本身是攻击面：recipe 与 portfile 能以构建用户权限执行任意命令。
- 私有 registry 应启用认证与审计，限制上传权限，二进制与源码分开授权。
- 生成依赖清单与 SBOM，配合漏洞数据库扫描，记录每个包的来源。
- 减少依赖数量，定期清理未使用项，缩小需要审计的范围。

### 14.9 私有 registry 与离线构建如何配置？

- Conan 2 用 `conan remote add` 注册远端，`conan remote login` 认证，可对接 Artifactory 一类实现。
- `conan download` 可把包预取到本地缓存，离线时用 `--no-remote` 禁止访问远端。
- vcpkg 可用文件系统或 NuGet 源作为二进制缓存，离线前预置 `downloads/` 与已安装目录。
- 离线构建要求所有源码包已缓存，`--build=missing` 在无网络时会失败。
- 私有包应带命名空间，避免与公共包同名冲突。
- 镜像同步要保证修订号一致，只同步版本号可能得到不同内容。
- CI 缓存目录需要跨任务共享，并按工具链版本分区，避免互相污染。

### 14.10 系统包管理器与 C++ 包管理器的边界在哪里？

- 系统包管理器管理 ABI 稳定的系统库，版本更新影响全局环境。
- C++ 包管理器管理项目级依赖，可并行存在多个版本，适合频繁升级的库。
- 同一库不应同时从两处引入，否则会出现头文件与库版本错配。
- Conan 可通过 `SystemPackageTool` 调用系统包管理器，也可在配方中声明依赖由系统提供。
- 容器镜像应固定系统库版本，项目依赖由包管理器锁定。
- 边界不清时，优先让包管理器拥有依赖，系统只提供工具链与基础运行库。
- 系统库升级后要重新验证 ABI 兼容性，不能假设次版本更新一定安全。

### 14.11 头文件库的依赖如何传播？

- 头文件库通常建模为 `INTERFACE` 目标，`target_include_directories(... INTERFACE ...)` 传播路径。
- Conan 的 `package_type = "header-library"` 让包不产生二进制，安装时只消费头文件。
- vcpkg 的 port 可声明依赖与支持平台，安装时只复制头文件。
- 头文件库的依赖必须作为 `INTERFACE` 链接，否则消费者缺少传递依赖。
- 宏定义与标准版本要求也应放入使用要求，不能只传播包含路径。
- 版本升级可能只改头文件，仍需重新编译消费者，缓存键要包含头文件哈希。
- 头文件库的 ABI 风险较低，但 ODR 违规风险较高，需要保证全程序使用同一版本。

### 14.12 共享库的 ABI 稳定性如何维护？

- 只导出稳定接口，默认隐藏符号，用显式导出宏标注公共 API。
- 避免在接口中暴露标准库容器与 inline 函数，不同标准库实现不保证兼容。
- 用 pImpl 隐藏实现细节，减少对象布局变化对消费者的影响。
- 新增虚函数会改变虚表布局，结构体字段变化会改变大小与偏移，两者都破坏二进制兼容。
- 用版本脚本控制导出符号集合，配合 SONAME 管理兼容版本。
- ABI 变化时提升 SONAME 主版本，让动态链接器拒绝加载旧二进制。
- 用 `abi-compliance-checker` 与 `abi-dumper` 对比版本间的接口与布局差异。

### 14.13 SONAME 与包版本如何对应？

- `SONAME` 写入 `DT_SONAME`，链接时记录到可执行文件的 `DT_NEEDED`。
- 惯例是 `libfoo.so.MAJOR`，主版本变化表示不兼容，`libfoo.so` 符号链接供开发期链接。
- `-Wl,-soname,libfoo.so.1` 在链接时设置，CMake 的 `SOVERSION` 与 `VERSION` 属性生成对应文件。
- 包管理器升级共享库时，`SONAME` 不变则无需重新链接，变化则需要重新构建消费者。
- 运行时查找由 `RPATH`、`RUNPATH`、`LD_LIBRARY_PATH` 与 `ldconfig` 缓存共同决定。
- 未版本化的 `.so` 不应安装到系统目录，容易出现版本错配。
- 用 `readelf -d libfoo.so` 查看 `SONAME`，用 `objdump -p` 查看 `NEEDED`。

### 14.14（场景）升级依赖后出现未定义符号或重复定义，如何排查？

- 未定义符号先确认是否真的缺失：`nm -D --defined-only libfoo.so` 查看导出，注意 C++ 名称修饰。
- 头文件与库版本不匹配会让代码调用不存在的符号，检查安装前缀与包含路径是否指向同一版本。
- 检查 `_GLIBCXX_USE_CXX11_ABI`、标准库版本与编译器的 `-std` 选项是否一致。
- 检查可见性：符号可能被 `-fvisibility=hidden` 隐藏，或未列入版本脚本。
- 检查链接顺序与 `--as-needed`，静态库可能因顺序被丢弃。
- 重复定义通常来自同一静态库被两条路径各链接一次，或 inline 函数与模板实例在多个目标中重复；用 `nm -A -C` 找出定义所在的目标文件。
- `--allow-multiple-definition` 只能用于诊断，不能作为修复手段；应消除重复来源或调整链接边界。

### 14.15 `pkg-config` 与 CMake 包配置的差别是什么？

- `pkg-config` 读取 `.pc` 文件，输出 `-I`、`-L`、`-l` 与版本信息，基于文本约定。
- CMake 的 Config 模式提供导入目标，能表达编译定义、依赖关系与配置相关属性。
- `.pc` 文件通常不区分构建配置，Debug 与 Release 共用一份，容易错配。
- `pkg-config` 的 `Requires` 与 `Libs.private` 表达能力弱于 CMake 的 `INTERFACE_*` 属性。
- 交叉编译时 `PKG_CONFIG_SYSROOT_DIR` 与 `PKG_CONFIG_PATH` 必须正确设置。
- CMake 可用 `FindPkgConfig` 消费 `.pc`，但结果仍是文本拼接，缺少目标级传播。
- 新项目应优先提供 CMake Config，兼容旧生态时再附带 `.pc` 文件。

### 14.16 依赖数量如何影响构建时间与二进制体积？

- 每个依赖增加配置、编译与链接时间，头文件依赖还会放大重编译范围。
- 静态链接会把未使用的代码带入，`--gc-sections` 与 LTO 可回收一部分。
- 模板库的实例化成本随使用方式增长，包含大量头文件的依赖会显著增加编译时间。
- 动态链接减少复制，但增加运行时加载与符号解析开销。
- 传递闭包可能远大于直接依赖数，构建图规模需要按闭包评估。
- 用 `ninja -t query` 查看依赖边，用 Clang 的 `-ftime-trace` 分析编译热点。
- 定期审计未使用依赖，避免为一个小功能引入整套框架。

### 14.17 依赖下载与构建脚本的攻击面有哪些？

- `GIT_TAG` 指向分支或标签时可被移动，应固定到提交哈希。
- 下载的压缩包需要校验哈希，HTTPS 只保证传输完整，不保证内容可信。
- 包的构建脚本以构建用户权限执行，可读写工作区并访问网络。
- 传递依赖的脚本同样会执行，审计范围应覆盖整个依赖图。
- 镜像与私有 registry 需要认证与完整性保护，防止内容被替换。
- 构建沙箱限制网络与文件系统访问，可降低脚本失控的影响。
- SBOM 与来源证明用于事后追溯，不能替代构建期的隔离。

### 14.18 可复现构建与包管理器的关系是什么？

- 可复现要求相同输入产生逐字节相同的输出，包管理器负责固定依赖版本与来源。
- 时间戳、绝对路径、文件顺序与随机种子都会破坏可复现性，需要编译器与归档工具配合。
- 锁文件固定解析结果，但下载源的可用性仍影响构建能否完成。
- 二进制缓存应记录构建环境，避免把不可复现的产物当作可信输入。
- `SOURCE_DATE_EPOCH` 统一时间戳，`-fdebug-prefix-map` 消除路径差异。
- 包管理器的修订号与哈希是复现的起点，充分条件还包括构建环境的确定性。
- 验证方式是在干净环境重建并比较产物哈希。

### 14.19（场景）同一项目在不同机器解析出不同依赖版本，如何定位？

- 比较两台机器的锁文件与 `conan graph info` 或 `vcpkg depend-info` 的输出。
- 检查是否有人使用更新选项（例如 Conan 的 `--update`）或未提交锁文件，导致重新解析。
- 检查 profile、triplet、环境变量与 `CMAKE_PREFIX_PATH` 是否不同。
- 私有 registry 与镜像的包集合可能不同步，导致可选版本不一致。
- 传递依赖的范围约束可能因新版本发布而变化，锁文件应阻止这种漂移。
- CI 与开发机的包管理器版本不同，解析算法可能有差异。
- 统一工具版本、提交锁文件，并在 CI 中校验锁文件未被改动。

### 14.20 vendoring 与子模块的取舍是什么？

- vendoring 把依赖源码复制进仓库，构建完全可控，但升级与安全修补需要手工同步。
- Git 子模块指向固定提交，仓库体积小，但克隆与离线构建需要额外步骤。
- 包管理器提供版本解析与二进制缓存，但引入外部基础设施依赖。
- vendoring 适合小型、稳定或需要深度修改的依赖。
- 子模块适合需要源码但不需要修改的依赖，需固定提交并记录来源。
- 三种方式都应与许可证审计配合，避免版权问题。
- 混合使用时明确边界，避免同一库出现多份副本导致 ODR 违规。

## 15. 工具链设计题

### 15.1 设计跨平台构建系统时，核心抽象如何划分？

- 第一层是目标图，描述库、可执行文件与测试，以及目标之间的使用要求。
- 第二层是工具链描述，记录编译器、链接器、目标三元组、sysroot 与默认参数。
- 第三层是动作图，把目标展开为具体命令、输入文件、输出文件与环境变量。
- 第四层是执行器，负责调度、并行、沙箱、缓存与远程执行。
- 配置阶段只构造图与做探测，构建阶段只执行动作，两者分离才能保证增量正确。
- 所有输入必须可枚举，隐式读取环境或网络会破坏缓存与可复现性。
- 每层都要暴露可观测数据：图规模、动作耗时、缓存命中与失败原因。

### 15.2 符号服务器如何设计？

- 构建时生成 PDB、DWARF 或 Breakpad 符号，按构建 ID 索引：ELF 用 `NT_GNU_BUILD_ID`，PE 用 PDB GUID，Mach-O 用 UUID。
- 符号文件存入对象存储，元数据记录构建 ID、产品版本、平台、架构与保留期。
- 调试器按构建 ID 查询，服务返回匹配文件；`debuginfod` 是公开协议，客户端通过 `DEBUGINFOD_URLS` 指定服务。
- CI 在发布阶段上传符号，上传失败不阻塞发布，但必须产生告警并支持补传。
- 符号文件包含源码路径与函数名，需要访问控制与必要的脱敏。
- 保留策略与制品版本对齐，删除旧版本前确认没有线上回溯需求。
- 下载端校验哈希，避免符号与二进制不匹配导致错误归因。

### 15.3（实现）插件系统的 ABI 边界如何设计？

- 边界使用 C ABI，导出 `extern "C"` 的入口函数与版本化结构体，不跨边界传递 C++ 对象。
- 句柄加函数表模式隐藏实现：宿主只持有不透明指针，通过回调完成创建、使用与销毁。
- 插件入口返回带 `version` 字段的结构体，宿主拒绝不兼容的主版本，次版本可做能力协商。
- 明确内存所有权：跨边界分配的内存必须由同一侧释放，销毁函数随创建函数成对提供。
- 不让 C++ 异常跨越边界，改用错误码或回调传递失败信息。
- 加载失败时输出库路径与 `dlerror` 或 `GetLastError` 的内容。
- 插件崩溃会影响宿主，关键插件可放入独立进程，通过 IPC 隔离。

```cpp
extern "C" {
struct plugin_api {
    int version;
    void* (*create)(const char* name);
    void (*destroy)(void* handle);
};
using plugin_entry = const plugin_api* (*)();
}
```

### 15.4 增量编译的依赖图如何维护？

- 依赖来源包括编译器生成的 `.d` 文件（`-MD -MF`）、模块扫描结果与显式声明的 `DEPENDS`。
- 图节点是文件与动作，边表示输入输出关系；内容哈希比时间戳可靠，能抵抗时间戳异常。
- 头文件删除、宏变化、编译选项变化都要使节点失效，选项本身应进入缓存键。
- 模块与生成的头文件会产生动态依赖，构建过程需要支持在图中追加边。
- 缓存键包含编译器版本、参数、输入内容与环境变量白名单。
- 定期清理孤立产物，避免缓存无限增长与旧文件误命中。
- 验证方式是随机修改头文件，确认所有受影响的翻译单元都重新编译。

### 15.5 分布式构建的正确性边界是什么？

- 远程执行要求动作封闭：只读取声明的输入，不依赖网络、时间、随机数或未声明的环境变量。
- 工具链必须可分发且版本一致，编译器、链接器、sysroot 与运行库要一起打包。
- 输出必须确定性，并行度与执行顺序不应改变结果。
- 动作在沙箱中执行，限制文件系统与网络访问。
- 失败重试要区分基础设施错误与确定性失败，避免重试掩盖代码问题。
- 输入使用内容寻址存储，相同文件只上传一次。
- 度量远程命中率、排队时间与执行时间，区分网络瓶颈与算力瓶颈。

### 15.6 诊断工具如何聚合编译器输出？

- 统一输入格式：GCC 支持 `-fdiagnostics-format=json`，较新的 Clang 提供 SARIF 输出。
- 归一化字段：文件路径、行列号、严重级别、诊断 ID 与修复建议映射到同一 schema。
- 去重：同一诊断经头文件展开后可能重复出现，按位置与 ID 合并。
- 把诊断关联到目标与动作，便于定位是哪个编译单元或生成步骤产生。
- 增量展示只呈现本次变更引入的诊断，历史告警进入基线。
- SARIF 可上传到代码扫描平台，保留趋势数据；原始文本仍需保存以便人工阅读。
- 解析失败时要保留原始输出，不能让聚合层丢弃编译器信息。

### 15.7 构建缓存键如何设计？

- 键由动作类型、输入内容哈希、工具链标识、参数与环境变量白名单共同组成。
- 工具链标识应包含编译器二进制的哈希，而不只是版本字符串。
- 环境变量只纳入会影响输出的项，纳入过多会降低命中率。
- 路径需要归一化，`-fdebug-prefix-map` 与 `CCACHE_BASEDIR` 可消除绝对路径差异。
- 输出不参与键计算，但命中后可比对输出哈希做完整性校验。
- 缓存分层为本地、团队远端与 CI 共享，按信任级别隔离。
- 工具链升级、依赖更新与编译参数变化都应使旧键不可达。

### 15.8 二进制体积守门如何接入 CI？

- 建立基线：按目标、配置与平台记录 `size` 或 `bloaty` 的结果。
- 设置双阈值：总量增量与单目标增量，超过阈值时失败或要求审批。
- 生成差分报告，列出增长最多的编译单元、符号与段。
- 调试信息与符号表单独统计，避免 `-g` 或 strip 策略变化造成误报。
- 构建条件必须一致，编译器、选项与依赖版本变化时重新建立基线。
- 历史数据入库并绘制趋势，识别持续增长，避免只看单次波动。
- 保留豁免流程，避免团队为通过门禁而关闭有用功能。

### 15.9 崩溃栈的符号化流水线如何设计？

- 采集端记录构建 ID、模块列表与模块内偏移，不能只记录函数名或绝对地址。
- 崩溃报告进入存储后，按构建 ID 关联符号文件与未剥离二进制。
- 服务端用 `llvm-symbolizer`、`addr2line` 或 Breakpad 工具还原文件与行号。
- 保留 inline 展开的栈帧，区分真实调用与 inline 位置。
- 构建 ID 不匹配时拒绝符号化并告警，避免把栈归因到错误版本。
- 按栈指纹聚合，忽略地址、临时路径与线程编号。
- 符号与二进制按发布周期保留，支持回溯历史版本。

### 15.10 编译器包装器与 ccache 如何协作？

- 包装器记录真实编译器路径与参数，ccache 依据编译器标识与参数区分不同版本。
- `CCACHE_COMPILERCHECK=content` 比 `mtime` 可靠，但哈希大型二进制有成本。
- 包装器注入的宏、包含路径与时间戳会改变哈希，需要保证输入可复现。
- 分布式缓存要求包装器不依赖本地绝对路径，否则其他机器无法命中。
- 调试信息路径用 `-fdebug-prefix-map` 归一化，避免同一源码产生不同哈希。
- 包装器必须原样传递退出码与 `stderr`，不能丢弃编译器诊断。
- 工具链升级后切换缓存命名空间，避免旧对象被错误复用。

### 15.11 多配置构建产物如何管理？

- 目录布局按平台、配置与架构分层，避免 Debug 与 Release 产物混用。
- 调试信息与二进制分离：DWARF、PDB、dSYM 与构建 ID 一起归档。
- 配置相关宏（例如 `NDEBUG`）必须进入缓存键，否则会错误复用。
- 安装树使用 `GNUInstallDirs` 的目录变量，运行时依赖用 `RPATH` 或打包工具处理。
- 符号服务器按构建 ID 存储，不按文件路径存储。
- 清理策略按配置与时间执行，保留最近若干个可回溯版本。
- 验证时从安装树运行，构建树中的路径会掩盖安装问题。

### 15.12 依赖更新与安全公告如何自动化？

- 依赖清单与锁文件进入仓库，机器人定期检查新版本与已知漏洞。
- 更新 PR 触发完整构建与测试，ABI 变化时额外运行兼容性检查。
- 漏洞数据库匹配需要准确的包名与版本，SBOM 提供输入。
- 自动合并只适用于补丁级更新，主版本升级需要人工评审。
- 保留回滚路径：旧锁文件与旧二进制缓存不能立即删除。
- 通知按团队与严重级别路由，避免告警疲劳。
- 度量平均修复时间与未修复高危数量，更新次数不能反映风险。

### 15.13 大型 monorepo 的构建图如何切分？

- 按目标切分，目录边界与依赖边界通常不一致，目标之间只通过声明的依赖交互。
- 用 `BUILD` 文件或 `CMakeLists.txt` 显式声明依赖，禁止隐式全局包含。
- 切分粒度影响并行度与缓存命中，过细会增加调度开销。
- 受影响目标分析从变更文件反向遍历依赖图，只构建受影响子集。
- 跨语言目标统一到同一动作图，避免多套构建系统拼接。
- 远程缓存按目标与配置分区，避免不同分支互相污染。
- 度量关键路径长度、并行效率与缓存命中率，总时长无法定位瓶颈。

### 15.14 工具链版本如何固定与升级？

- 固定编译器、链接器、标准库与构建工具的完整版本，记录在工具链描述文件中。
- 用容器镜像或 SDK 包封装工具链，保证开发机与 CI 一致。
- 升级在独立分支进行：先执行全量测试与性能基准，再切换默认版本。
- 保留旧工具链一段时间，支持回滚与旧版本分支构建。
- 编译器升级会改变告警、优化行为与 ABI，需要分别评估。
- 工具链哈希进入缓存键，升级后旧缓存自动失效。
- 文档记录每个产品版本使用的工具链，便于问题追溯。

### 15.15 构建可观测性应采集哪些指标？

- 阶段耗时：配置、编译、链接与打包，按目标与文件聚合。
- 关键路径：并行构建中最长的依赖链，决定总时长下限。
- 缓存命中率：本地与远端分开统计，区分命中质量。
- 资源使用：CPU、内存、I/O 与网络，用于定位瓶颈。
- 失败率与重试次数，区分基础设施故障与代码错误。
- 诊断数量与新增告警趋势，反映代码健康度。
- 全量采集成本高，按构建采样并保留聚合数据。

### 15.16 构建沙箱如何设计？

- 文件系统隔离：只挂载声明的输入与输出目录，其余路径只读或不可见。
- 网络默认禁止，需要下载的动作显式声明并通过代理访问。
- 进程隔离：限制子进程、信号与 `/proc` 访问。
- 资源限制：CPU、内存、文件描述符与执行时间。
- 可复现要求固定或屏蔽环境变量、主机名与时间。
- 逃逸面包括用户命名空间、`ptrace` 与设备访问，需要额外限制。
- 兼容性方面要为编译器保留 `/tmp` 与共享内存，白名单应尽量小。

### 15.17 跨平台工具链如何分发？

- 以压缩包或容器镜像分发，包含编译器、链接器、sysroot、标准库与调试工具。
- 使用版本化路径，避免多个版本互相覆盖。
- 发布时提供哈希与签名，使用前校验完整性。
- 环境脚本设置 `PATH`、`CC`、`CXX` 与 `SYSROOT`，不修改系统全局配置。
- Windows 需要处理路径长度、CRT 与 PDB 工具；macOS 需要 SDK 与代码签名。
- 工具链组件的许可证要随分发附带，并做许可审计。
- 升级与回滚通过切换版本目录完成，不覆盖正在使用的工具链。

### 15.18 静态分析如何增量接入 CI？

- 先对新增与修改文件运行，再逐步扩展到核心目录。
- 固定检查项集合与工具版本，避免结果随升级漂移。
- 基线文件记录存量问题，CI 只比较新增诊断。
- 与代码评审集成，先以评论形式呈现，稳定后再升级为阻塞门禁。
- 分析任务与构建任务分离，使用缓存与并行控制成本。
- 误报处理流程包括确认、抑制并注明原因、反馈规则改进。
- 度量新增缺陷数、修复率与误报率，告警总数不能反映质量。

### 15.19（场景）线上崩溃只有地址，如何还原源码行？

- 先确认崩溃对应的二进制与构建 ID，找到同版本的符号文件或未剥离二进制。
- 计算模块加载基址，把运行时地址转换为模块内偏移或文件偏移。
- 用 `addr2line -e binary -f -C -i 0x...` 或 `llvm-symbolizer` 还原文件与行号。
- PIE 与 ASLR 下地址每次不同，必须记录加载基址或直接上报相对偏移。
- inline 函数需要 `-i` 展开，模板与名称修饰需要 `-C` 还原。
- 优化会造成行号偏移与变量消失，必要时结合反汇编与源码核对。
- 建立按构建 ID 索引的符号服务器，避免每次手工查找二进制。

### 15.20 为大型团队统一工具链，如何分阶段实施？

- 第一阶段统一编译器与构建入口，固定版本并采集构建时长、失败率等基线数据。
- 第二阶段统一依赖管理与缓存，引入锁文件、二进制缓存与私有 registry。
- 第三阶段接入 sanitizer、静态分析与体积门禁，先在小范围目标试点。
- 第四阶段推进远程执行与可复现构建，要求动作封闭、输出确定。
- 每阶段定义验收指标：构建时长、缓存命中率、失败率与缺陷发现数。
- 治理上采用 RFC、灰度与回滚机制，工具链变更不直接全量推送。
- 集中化会增加特殊平台的支持成本，需要保留扩展点与例外流程。
