## 1. 可靠、可扩展与可维护

### 1.1 可靠性、可扩展性与可维护性分别关注什么问题？

- 可靠性指系统在出现故障时仍能提供正确服务，关注故障发生后的行为。
- 可扩展性指负载增长时，系统维持性能与成本目标的能力，关注增长路径。
- 可维护性指工程团队修改、部署、排障与演进的成本，关注长期效率。
- 三者会互相制约，强一致复制提升可靠性，却增加写延迟与运维复杂度。
- 可靠性不能由单一副本数推出，需说明故障模型与恢复目标。
- 可扩展性也不能由单次压力测试推出，需说明负载参数与增长假设。
- 评估时应分别给出故障模型、扩展假设与维护成本指标，避免用单一结论覆盖三者。

### 1.2（辨析）故障与失效的边界在哪里？

- 故障是组件偏离规格的状态，失效是系统对外停止提供约定服务。
- 冗余可避免单副本故障升级为系统失效。
- 失效可以是崩溃、超时、返回错误结果或性能不达标。
- 崩溃停止与崩溃恢复的故障模型不同，恢复后可能丢失未持久化状态。
- 拜占庭故障指节点返回错误结果，普通冗余无法处理。
- 设计时需说明假设哪类故障、检测时间与恢复动作。

### 1.3 硬件故障、软件故障与人为错误各有什么特点？

- 硬件故障通常被视为独立随机事件，磁盘、网卡与电源的故障率可用冗余降低。
- 软件故障具有相关性，同一缺陷会在所有副本上同时触发。
- 人为错误是常见故障源之一，配置变更与误操作常通过自动化放大。
- 同一机架、同一电源或同一固件的故障可能相关，冗余设计需考虑故障域。
- 软件缺陷需靠测试、灰度、回滚与输入校验降低影响。
- 人为错误需靠权限、审批、可回滚发布与演练降低概率和损失。

### 1.4 冗余为什么不能单独构成可靠性方案？

- 冗余通过增加副本把单点故障转为可切换状态。
- 副本若共享电源、网络或软件版本，独立性不成立，故障仍会相关。
- 故障切换本身可能失败，未演练的切换流程会延长失效时间。
- 双主可能产生脑裂，需要仲裁或租约限定写权限。
- 冗余增加复制流量、存储成本与一致性协调。
- 可靠性方案需同时覆盖检测、切换、恢复与回切。

### 1.5（陷阱）故障注入测试通过是否说明系统可靠？

- 故障注入能验证特定假设，不能覆盖未注入的故障组合。
- 测试环境与生产在规模、配置、流量模式上不同，结果不能直接外推。
- 注入工具的观测点可能遗漏静默错误，例如返回旧数据。
- 单次通过只说明该场景下系统未失效，不说明恢复时间达标。
- 有效做法包括生产灰度、受控实验、故障演练与长期指标。
- 结论应写成「在给定故障模型与负载下通过」，并保留失败样本。

### 1.6 SLO 与 SLA 的差别是什么？

- SLA 是服务等级协议，规定服务提供方与客户之间的指标、窗口与违约后果。
- SLO 是服务等级目标，可作为内部目标，用可测量的 SLI 定义，例如成功请求比例与延迟分位。
- SLO 通常严于 SLA，为告警与恢复留出余量。
- SLI 是服务等级指标，需明确成功判定、统计窗口、请求范围与数据来源。
- 错误预算等于窗口内允许的失败量，可用于平衡发布与稳定性。
- 只有 SLA 没有内部 SLO 时，团队会在违约边缘才采取行动。

### 1.7 如何从用户体验推导 SLO 指标？

- 从用户路径选取指标，例如登录、下单与支付，而非只看单机 CPU。
- 延迟目标应写成分位与阈值，例如 P99 小于 300 ms。
- 成功率需定义可重试错误与客户端错误的归类。
- 统计窗口可为滚动 28 天或自然月，两者对告警影响不同。
- 多地域与多租户需分别设定目标，避免全局平均稀释局部问题。
- 指标应可追溯到日志、追踪与监控，否则无法仲裁。

### 1.8（估算）错误预算如何约束发布节奏？

- 以 30 天、99.9% 的 SLO 为例，允许不可用时间约 43 分 12 秒。
- 错误预算消耗速率可用于区分偶发故障与持续劣化。
- 发布门禁可按预算余额分级，余额充足时加快，余额不足时收紧。
- 预算不应覆盖计划内维护，维护需单独计入或暂停统计。
- 预算耗尽后应优先修复可靠性，而非继续叠加新功能。
- 预算模型需防止团队通过放宽成功判定来制造余额。

```cpp
double error_budget_minutes(double slo, int days) {
    return days * 24.0 * 60.0 * (1.0 - slo);
}
```

### 1.9 可用性几个 9 与 30 天停机时间如何换算？

- 99% 可用性在 30 天内允许约 7 小时 12 分停机。
- 99.9% 在 30 天内允许约 43 分 12 秒停机。
- 99.99% 在 30 天内允许约 4 分 19 秒停机。
- 99.999% 在 30 天内允许约 26 秒停机。
- 可用性按请求成功率与按时间统计会得到不同结果，需说明口径。
- 计划内维护、降级服务与部分功能不可用是否计入，需在 SLO 中约定。
- 多副本切换的检测与恢复时间会直接消耗停机预算。

### 1.10（辨析）吞吐量与响应时间是什么关系？

- 吞吐量是单位时间完成的请求或数据量，响应时间是个体请求的耗时。
- 吞吐量必须在延迟约束下比较，脱离延迟的峰值没有意义。
- 负载接近饱和时，排队使延迟非线性上升，吞吐量趋于稳定。
- 批处理与流水线可提高吞吐，但可能增加单请求等待。
- 读多写少与写多读少的吞吐瓶颈不同，需分别测量。
- 报告吞吐量时应同时给出负载组合、并发度与延迟分位。

### 1.11 平均延迟为什么不足以反映慢请求？

- 平均值会被大量快请求降低，无法反映少量慢请求的影响。
- 用户遇到的慢请求比例由分位描述，P99 表示最慢 1% 的阈值。
- 平均值相同的一组系统，尾部分布可能差异很大。
- 压力测试工具若采用闭合模型，慢请求会减少发送速率，导致尾延迟被低估。
- 应按接口、实例、地域与错误类型拆分统计。
- 分位数不可直接平均，聚合时需合并直方图或保留原始样本。

### 1.12 尾延迟由哪些因素放大？

- 扇出调用会放大尾延迟，单次调用超过 P99 阈值的概率为 1% 时，在独立假设下，100 次调用至少一次超阈值的概率约 63%。
- 并行扇出的响应时间由最慢分支决定，尾延迟更易出现。
- 队列、垃圾回收、合并与磁盘抖动会把短时抖动传递给上游。
- 重试会增加负载，并在故障时进一步增加延迟。
- 多租户的邻近租户争用会让尾延迟随负载分布变化。
- 降低尾延迟的手段包括超时、隔离、去重、预计算与容量余量。

### 1.13（场景）P99 升高但平均值正常，如何排查？

- 先确认指标口径是否变化，例如成功请求集合或统计窗口调整。
- 按接口、实例、版本与客户端拆分，定位是否集中在少数分组。
- 对比同时间段的依赖延迟、错误率与重试次数。
- 检查资源指标中的队列长度、垃圾回收暂停、合并任务与磁盘等待。
- 抽取慢请求追踪，比较各阶段耗时，避免只看总耗时。
- 若平均值正常而 P99 升高，优先怀疑流量结构变化与局部故障。

### 1.14 负载参数应如何选取？

- 负载参数包括请求速率、读写比例、数据规模、访问分布与并发连接数。
- 平均请求速率不足以描述峰值，需给出突发倍数与持续时间。
- 键分布影响缓存命中与分片倾斜，均匀假设常不成立。
- 负载还需描述事务大小、扇出与依赖调用次数。
- 同一系统在不同负载组合下瓶颈不同，参数应成组记录。
- 可扩展性结论必须绑定负载参数，否则无法复现。

### 1.15（陷阱）压力测试流量翻倍就能验证可扩展性吗？

- 流量翻倍只覆盖一个增长点，不能说明系统在十倍负载下仍线性。
- 压力测试数据量不足时，缓存命中率与索引深度与生产不同。
- 瓶颈会随负载转移，从 CPU 转向 IO、锁或网络。
- 短时压力测试无法暴露内存泄漏、合并积压与元数据增长。
- 应在多个负载级别测量延迟与吞吐，并找到性能转折点。
- 可扩展性验证还需包含故障注入与长时间稳定性测试。

### 1.16 垂直扩展与水平扩展的取舍是什么？

- 垂直扩展提升单机资源，改动小，但受硬件上限与成本曲线约束。
- 垂直扩展的故障域仍集中在单机，恢复依赖重启或切换。
- 水平扩展通过分片与副本增加容量，但引入路由、重平衡与一致性。
- 无状态服务水平扩展较直接，有状态服务需先解决数据分布。
- 小规模系统优先垂直扩展可降低复杂度，接近上限时再拆分。
- 选择应基于增长预测、成本、故障域与团队运维能力。

### 1.17（设计）无状态服务与有状态服务如何分别扩展？

- 无状态服务把会话与缓存外置，可在负载均衡后任意增加实例。
- 无状态并不等于无共享，数据库与缓存仍是共享依赖。
- 有状态服务需按分片键拆分，并为副本选择一致性与故障转移策略。
- 扩容时重平衡会迁移数据，需限制速率并保证读写不中断。
- 热点分片无法靠增加普通实例解决，需拆分热点键或做缓存。
- 两类服务应分别设定容量指标与故障恢复目标。

### 1.18 可维护性包含哪些工程属性？

- 可操作性包括部署、监控、告警、排障、备份与容量管理。
- 简单性要求减少不必要的组件、状态与隐式依赖。
- 可演化性要求接口、数据格式与部署方式支持渐进变更。
- 文档与运行手册属于可维护性的一部分，不能只靠口口相传。
- 认知负担与交接成本会随组件数量与特殊配置上升。
- 可维护性可通过变更前置时间、恢复时间与缺陷复发率观察。

### 1.19 可演化性如何在数据格式与接口层面体现？

- 数据格式演进需同时考虑旧版本读新数据与新版本读旧数据的兼容性。
- 向后兼容指新代码读旧数据，向前兼容指旧代码读新数据，方向需说清。
- 接口新增字段通常安全，删除字段与改变语义通常不安全。
- 滚动升级期间新旧版本并存，双读或双写可缩短不兼容窗口。
- 事件日志需保留模式版本与默认值，消费者按版本解析。
- 演化方案应包含回滚路径与旧客户端淘汰计划。

### 1.20（场景）需求变化导致模式演进，如何降低耦合？

- 优先采用可加字段与可选字段，避免原地改变字段含义。
- 为旧数据补默认值，并在读取层兼容缺失字段。
- 大表变更采用影子表、双写与回填，校验后再切换读路径。
- 迁移期间需有对账任务，比较新旧模型的记录数与关键字段。
- 版本字段可让应用按记录粒度选择解析逻辑。
- 回滚方案需覆盖已写入的新格式数据，否则切换会失败。

## 2. 关系与文档数据模型

### 2.1 关系模型与文档模型的核心差异是什么？

- 关系模型把数据表示为带模式的元组集合，通过键与连接组合。
- 文档模型把相关数据组织为嵌套文档，通常以聚合为单位读写。
- 关系模型强调独立写入与多对多关系，文档模型强调局部性与整文档读取。
- 两者都能表达一对多与多对多，差异在默认建模方式与查询路径。
- 关系数据库通常提供强事务与连接，文档数据库通常提供灵活模式与水平扩展。
- 选型应依据访问模式、一致性要求与数据关系密度，而非模型名称。
- 选型验证应比较核心查询的连接次数、延迟与写入一致性，不能只比较功能。

### 2.2（辨析）规范化与反规范化分别解决什么问题？

- 规范化把每个事实保存一次，减少冗余与更新异常。
- 反规范化复制派生数据，以减少连接或跨节点读取。
- 规范化提高写一致性与存储效率，代价是查询连接与规划成本。
- 反规范化提高读性能，代价是复制延迟、写放大与修复逻辑。
- 反规范化适用于读多写少、聚合结果稳定且可校验的场景。
- 决策应以访问模式与一致性预算为依据，并保留重建派生数据的能力。

### 2.3 第一范式到第三范式在工程中如何理解？

- 第一范式要求字段值不可再分，避免把多个值放入一个字段。
- 第二范式要求非主属性完全依赖于候选键，消除部分依赖。
- 第三范式要求非主属性不传递依赖于候选键，消除间接依赖。
- 工程上可理解为每张表只负责一类事实，修改时只有一个权威位置。
- 范式分解会增加连接，需用索引、视图或适度反规范化补偿。
- 现代类型系统允许数组与 JSON 字段，但语义上的原子性仍需设计。

### 2.4（陷阱）范式越高，查询性能越好吗？

- 更高范式减少冗余，却不保证查询更快，连接与随机读可能增加。
- 低范式表若宽而稀疏，扫描成本与缓存占用可能更高。
- 读多写少的报表场景可通过物化视图或宽表降低连接成本。
- 写多且一致性要求高的场景，规范化更利于维护单一事实。
- 性能取决于访问路径、索引与数据分布，不能由范式级别直接推断。
- 变更前应测量查询计划与写放大，表数量不能作为判断依据。

### 2.5 多对多关系为什么在关系模型中更自然？

- 多对多关系需要独立的连接实体，记录两侧标识与关系属性。
- 关系模型用连接表与联合主键表达，连接查询由优化器选择算法。
- 连接表可为关系附加时间、角色与状态等属性。
- 两侧外键与索引决定连接方向与查找成本。
- 文档模型若把关系嵌入数组，容易在两侧产生重复副本。
- 关系数据库的引用完整性可阻止悬空引用，跨服务时需由应用保证。

### 2.6 文档模型如何处理多对多关系？

- 文档模型可在文档内保存对方标识数组，读取后由应用发起二次查询。
- 也可嵌入对方的关键字段，形成反规范化副本，减少一次读取。
- 标识数组适合关系数量有界且更新不频繁的场景。
- 嵌入副本适合读多写少且能接受短暂不一致的场景。
- 关系数量无界时，文档会持续增长并逼近大小限制。
- 需要双向查询时，应在两侧维护索引或改用关系表。

### 2.7（场景）订单与商品适合嵌入还是引用？

- 订单中的商品行适合嵌入订单文档，因为读取时通常一起返回。
- 商品名称与下单时价格应作为快照嵌入，避免商品后续修改影响历史订单。
- 商品目录的当前价格与库存应保存在商品侧，订单只引用商品标识。
- 商品行数量很大时应拆为独立集合，避免单文档过大。
- 嵌入快照会带来冗余，但换取历史可追溯与读取局部性。
- 退款与履约状态若独立并发更新，拆分为独立实体更合适。

```cpp
struct OrderItem {
    std::string product_id;
    int quantity;
    Money unit_price;
};

struct Order {
    std::string id;
    std::vector<OrderItem> items;
};
```

### 2.8 对象与关系之间的阻抗失配指什么？

- 阻抗失配指应用中的对象、引用与继承结构，与关系表的行、列与外键之间不能直接对应。
- 集合属性需要独立表或序列化字段，继承可映射为单表、连接表或具体表。
- 对象身份与数据库主键的语义不同，前者可随会话变化，后者需稳定。
- 延迟加载会在事务边界之外触发查询，导致 `N+1` 与延迟加载异常。
- ORM 可降低映射代码量，却不能消除模式设计与查询计划问题。
- 处理方式包括显式映射、按用例建模与在边界处使用数据传输对象。

### 2.9 ORM 会带来哪些阻抗失配问题？

- ORM 可能把一次关联读取拆成多次查询，形成 `N+1`。
- 延迟加载把查询时机推迟到访问属性时，事务可能已经结束。
- 身份映射与一级缓存会让读取结果与数据库当前状态不同。
- 类型映射可能丢失精度，例如十进制金额映射为浮点。
- 批量更新与级联删除可能生成未预期的 SQL 与锁范围。
- 应开启 SQL 日志与慢查询分析，验证 ORM 的实际访问路径。

### 2.10（陷阱）文档数据库是否不需要模式？

- 文档数据库通常不强制固定表结构，但应用代码仍依赖隐含模式。
- 缺少写时校验会把错误数据留到读取阶段，增加修复成本。
- 可选校验规则能约束关键字段，但跨文档一致性仍需应用保证。
- 异构文档适合事件、日志与快速演进的场景，代价是查询复杂。
- 模式自由不等于无需迁移，字段改名与类型变化仍需回填。
- 应为文档定义版本与必填字段，并对旧版本提供读取兼容。

### 2.11 读时模式与写时模式的取舍是什么？

- 写时模式在写入时校验并转换，读取路径简单且查询优化信息明确。
- 读时模式在读取时解释异构数据，写入灵活但每次读取都要处理分支。
- 写时模式适合结构稳定、质量要求高的核心交易数据。
- 读时模式适合多来源、结构频繁变化的数据湖与事件流。
- 读时模式会把校验成本与错误暴露推迟到消费端。
- 混合方案可在写入时做基本校验，在读取时兼容历史版本。

### 2.12（设计）模式演进时如何兼容旧数据？

- 新增字段应可选，并为缺失字段定义默认语义。
- 字段改名可先双写新旧字段，回填后再切换读取。
- 类型变化需确认精度、范围与序列化格式，避免静默截断。
- 迁移脚本应可重复执行，并按主键分批处理。
- 读取层应同时兼容多个模式版本，直到旧数据回填完成。
- 回滚时需确保旧代码能忽略新字段，且新字段不参与关键判定。

### 2.13 数据局部性对文档模型意味着什么？

- 数据局部性指一次读取所需的数据在存储上相邻或同节点。
- 文档模型把聚合放在一起，读取整个聚合时只需一次查找。
- 局部性只在访问模式与聚合边界一致时有效。
- 跨文档连接会增加网络往返与随机读。
- 更新整个文档可能重写未修改部分，带来写放大。
- 聚合边界应依据常用读取路径划分，而非仅依据实体关系。

### 2.14（场景）文档过大为什么会放大读写成本？

- 文档越大，单次读取传输与反序列化成本越高。
- 更新一个字段也可能重写整个文档，写放大随文档大小增长。
- 大文档会延长锁持有时间与复制日志大小。
- 文档接近大小上限时，追加数组可能失败，需要应用拆分。
- 热字段与冷字段混在一起会降低缓存命中率。
- 可将大数组拆为子文档，或将频繁更新的字段放到独立集合。

### 2.15 关系模型的数据局部性如何获得？

- 关系模型可通过聚簇索引按主键顺序把相邻行连续存放。
- 覆盖索引可让查询只读索引，避免回表。
- 物化视图可预计算连接结果，提供受控的冗余。
- 相邻行在页内连续，但跨表连接仍需额外查找。
- 数据局部性依赖查询模式，通用表结构难以对所有路径最优。
- 可通过分区与排序键让常用查询命中相邻页。

### 2.16（辨析）外键与应用程序级引用如何取舍？

- 外键由数据库强制执行，能阻止悬空引用并支持级联动作。
- 外键检查可能引入锁与插入顺序约束，影响高并发写入。
- 应用级引用把完整性检查移到服务层，适合跨库或跨服务。
- 应用级引用需要补偿、对账与定期清理悬空记录。
- 外键在分库分表后通常无法跨节点生效。
- 选择应基于一致性要求、故障恢复与写入延迟。

### 2.17（陷阱）SQL 的 `JOIN` 一定比多次查询慢吗？

- 有索引的连接通常只需按连接键查找，未必比多次查询慢。
- 多次查询的主要成本是网络往返与重复解析，数据量大时更明显。
- 连接可让优化器选择哈希、归并或嵌套循环，减少中间传输。
- 应用层拼接会把过滤与排序移到内存，可能放大数据传输。
- `N+1` 查询是多次查询的极端形式，应通过批量加载消除。
- 应比较实际执行计划、往返次数与传输字节，而非按语句数量判断。

### 2.18 多对多关系中的连接表如何设计？

- 连接表通常使用两侧标识的联合主键，保证关系唯一。
- 需为两个方向分别建立索引，支持双向查询。
- 关系属性应放在连接表，而不是复制到任一侧。
- 联合主键可阻止重复关系，代理键则便于外部引用。
- 删除一侧实体时需决定级联删除还是保留历史关系。
- 关系数量很大时，连接表本身需要分区与归档策略。

### 2.19（设计）内容管理系统的模型如何选型？

- 文章正文与版本适合文档或宽表，读取时一次取回。
- 用户、权限、标签与审核流程关系复杂，适合关系表。
- 标签与文章的多对多关系可用连接表，也可用搜索引擎索引。
- 混合模型需定义权威数据源与同步方向。
- 内容发布需要机制保证文章状态与索引更新一致。
- 选型应依据编辑、发布、检索与归档四条路径分别评估。

### 2.20（场景）从文档模型迁移到关系模型要注意什么？

- 先梳理实体、关系与访问路径，确认哪些聚合需要原子更新。
- 建立双写或变更捕获，让新旧模型在一段时间内并存。
- 回填时按主键分批，记录进度并支持断点续跑。
- 对账需比较记录数、关键字段与关系完整性。
- 切换读路径前用影子读验证结果一致。
- 回滚方案要覆盖切换后写入的新数据，避免只回滚代码。

## 3. 图数据模型与查询

### 3.1 图模型适合哪些数据与查询？

- 图模型适合实体间关系密集、查询深度不固定的场景。
- 典型查询包括最短路径、邻居聚合、环路检测与影响扩散。
- 社交网络、欺诈检测、知识图谱与依赖分析常使用图模型。
- 以单表扫描或固定连接为主的报表，关系模型更合适。
- 图模型的优势来自局部遍历与关系导航，不来自存储介质。
- 选型需评估关系密度、遍历深度与更新模式。
- 验证应使用真实度数分布与多跳查询，比较图遍历与关系连接的延迟。

### 3.2（辨析）属性图与三元组模型有什么区别？

- 属性图由顶点、边、标签与属性组成，边有方向且可带属性。
- 三元组模型把事实表示为「主语、谓语、宾语」，以资源描述框架（RDF）为代表。
- 属性图把边当作一等实体，适合表达带权重、时间与来源的关系。
- 三元组便于全局标识与数据融合，边属性需通过具体化或命名图表达。
- 属性图查询常以模式匹配表达，三元组查询以图模式与可选连接表达。
- 两者都能表达多跳关系，差异在数据模型与查询语言生态。

### 3.3 顶点与边分别携带哪些信息？

- 顶点通常保存类型标签、业务属性与全局标识。
- 边保存类型、方向、权重、时间戳与来源等属性。
- 边属性适合表达关系强度、交易金额与生效区间。
- 同一对顶点之间可以有多条不同类型的边。
- 边的时间维度决定查询是当前视图还是历史视图。
- 顶点与边的标识应稳定，避免迁移后关系断裂。

### 3.4（陷阱）图数据库一定比关系数据库快吗？

- 图数据库的优势依赖局部遍历与索引邻接，不保证所有查询更快。
- 浅层查询在关系数据库中用索引连接也可能很快。
- 深度遍历时，关系数据库的多次连接会产生大量中间结果。
- 图数据库的写入与分区可能更复杂，批量分析未必占优。
- 数据规模、度数分布与查询模式决定实际差异。
- 应使用代表性查询与真实数据比较延迟，而非按模型判断。

### 3.5 图遍历的复杂度由什么决定？

- 遍历复杂度受分支因子、深度、过滤选择性与重复访问影响。
- 最坏情况下路径数量随深度指数增长，需限制深度与结果集。
- 高度数顶点会显著增加每层扩展的边数。
- 过滤条件若不能下推到遍历，会先生成大量中间路径。
- 去重策略影响内存与正确性，重复访问会放大计算。
- 可用双向搜索、索引查找与预聚合降低扩展量。

### 3.6（辨析）广度优先与深度优先遍历如何取舍？

- 广度优先按层扩展，适合最短路径与近邻查询，但待扩展集合占用内存。
- 深度优先沿单条路径前进，适合路径存在性与回溯，但可能长时间不返回。
- 广度优先在高度数图上会产生较大待扩展集合，需限制并发与批大小。
- 深度优先需显式栈或递归深度限制，避免栈溢出。
- 双向广度优先从两端扩展，可降低搜索层数。
- 选择取决于目标、结果规模与内存预算。

### 3.7（场景）多跳查询的候选路径为什么会迅速增长？

- 多跳查询的候选路径数随平均度数上升迅速增长。
- 无界可变长度路径会把大量无关路径带入中间结果。
- 超级顶点会让单层扩展的边数远超平均值。
- 过滤条件若放在遍历之后，系统会先扩展路径，再执行过滤。
- 应尽早应用标签、属性与时间过滤，并限制跳数。
- 对高频查询可预计算邻居或路径摘要，但需处理更新。

### 3.8 超级顶点对遍历有什么影响？

- 超级顶点是度数远高于平均值的顶点，例如热门商品或公共账号。
- 遍历经过超级顶点时，单步扩展会产生大量候选。
- 超级顶点还会造成分片倾斜与热点写入。
- 可为超级顶点建立专用索引，按边属性过滤后再扩展。
- 可将超级顶点拆分或复制到多个分区，读取时合并结果。
- 查询应限制经过超级顶点的边类型与时间范围。

### 3.9 双向遍历如何降低搜索空间？

- 双向遍历从起点与终点同时扩展，直到搜索前沿相交并确认最短路径。
- 在分支因子为 b、深度为 d 的图上，单向搜索的节点量级约为 b 的 d 次方，双向遍历约为 b 的 d/2 次方。
- 双向遍历要求能沿反向边扩展，或有反向索引。
- 两端扩展速度不均衡时，需按待扩展集合大小调度。
- 终止条件需确保已找到最短路径，不能仅因首次相遇就停止。
- 对高度数图，双向仍可能产生较大待扩展集合，需配合过滤。

### 3.10 Cypher 的匹配思路是什么？

- Cypher 用模式描述顶点与边，模式中的方向与标签决定连接形状。
- 可变长度关系可限定跳数，避免无界遍历。
- 过滤条件用于约束顶点与边的属性，投影决定返回的字段。
- 查询是声明式的，执行计划由优化器选择扩展顺序与索引。
- 模式中的方向与标签会影响可使用的索引与连接顺序。
- 复杂查询可拆分为多个匹配阶段，但需注意笛卡尔积。

```text
match (a:Account)-[:TRANSFER*1..3]->(b:Account)
where a.id = A100
return b.id and count of paths
```

### 3.11（辨析）Cypher 与 SPARQL 的查询范式差异在哪里？

- Cypher 面向属性图，以顶点与边的模式匹配为核心。
- SPARQL 面向 RDF 三元组，以三元组模式与变量绑定为核心。
- SPARQL 的可选匹配表达可选连接，过滤条件表达值约束。
- Cypher 的路径与可变长度关系更直接，SPARQL 可用属性路径表达传递闭包。
- SPARQL 支持命名图与联邦查询，适合跨数据源整合。
- 两者都可表达多跳查询，优化器能力与数据分布决定实际性能。

### 3.12 三元组存储如何表示边属性？

- RDF 三元组只能表示主语、谓语、宾语，边本身不能直接携带属性。
- 具体化把一条边拆为多个三元组，并引入一个表示关系的节点。
- 命名图可把一组三元组放入上下文，适合来源与版本标记。
- 单例属性可为关系创建唯一实例，减少具体化的连接层级。
- 具体化会增加连接与存储开销，查询也更冗长。
- 选择取决于是否需要边属性、来源追踪与标准兼容。

### 3.13（设计）属性图模式如何建模？

- 先确定顶点类型与关系类型，避免使用单一通用关系标签。
- 为高频查询的顶点属性建立索引，例如账号、设备与身份标识。
- 关系方向应按语义固定，双向查询通过反向边或索引支持。
- 边属性应服务于过滤与排序，避免把大对象放入边。
- 时间维度可用边属性或独立时间片表达，取决于查询模式。
- 模式应随查询演进，定期检查未使用的标签与索引。

### 3.14 图存储的邻接表如何组织？

- 邻接表为每个顶点保存出边或入边列表，遍历时直接读取。
- 无索引邻接把边指针与顶点一起存放，减少全局索引查找。
- 静态图可用压缩稀疏行布局，提升顺序扫描效率。
- 动态图需要插入与删除，链表或分段数组更易更新。
- 邻接表顺序会影响局部性与结果稳定性，可按时间或权重排序。
- 超大顶点需单独的边表与分页读取，避免单条记录过大。

### 3.15（陷阱）邻接表与倒排索引能否互相替代？

- 邻接表支持按关系扩展，回答从该顶点出发能到达谁。
- 倒排索引支持按属性查找，回答哪些顶点满足条件。
- 图查询通常先用倒排索引定位起点，再用邻接表扩展。
- 只用倒排索引做多跳查询会产生大量连接与中间结果。
- 只用邻接表做属性过滤会退化为全图扫描。
- 两类索引互补，图数据库通常同时维护。

### 3.16 图分区为什么困难？

- 图分区需把顶点与边分配到节点，目标是减少跨分区边。
- 按顶点哈希分区简单，但会产生大量跨分区边。
- 按社区或标签分区可提高局部性，但需要离线分析与更新。
- 超级顶点会让分区负载倾斜，单一分区可能承载过多边。
- 复制边界顶点可减少跨分区查询，但增加存储与一致性成本。
- 分区策略应结合查询起点分布与遍历深度评估。

### 3.17（场景）跨分区遍历如何减少网络往返？

- 跨分区遍历会产生网络往返，延迟随跳数增加。
- 可按层批量发送待扩展集合，减少单条消息开销。
- 将常一起访问的顶点放在同一分区，可减少跨区边。
- 缓存远端邻居与路径摘要能降低重复查询成本。
- 限制跳数与结果集，避免一次请求拉取过多分支。
- 对离线分析可采用消息传递模型，对在线查询则需控制批大小。

### 3.18 图查询如何做分页与去重？

- 遍历可能通过不同路径到达同一顶点，需去重以保证结果稳定。
- 去重集合可按顶点标识、边标识或完整路径建立，成本不同。
- 分页应使用稳定排序与游标，避免偏移量在数据变化后重复或遗漏。
- 深度优先的结果顺序依赖邻接表顺序，需显式排序。
- 限制每页结果数并记录已访问集合，可避免重复计算。
- 若查询要求所有路径，去重粒度需保留路径差异。

### 3.19（设计）欺诈检测中的图查询如何设计？

- 欺诈检测把账户、设备、电话与交易建模为顶点，把转账与登录建模为边。
- 查询可寻找共用设备的多账户、环形转账或短时间内的异常路径。
- 时间窗口与边属性是过滤关键，缺少时间条件会产生大量误报。
- 图查询适合发现关系，评分与分类仍需统计模型配合。
- 结果需可解释，保留路径与边证据，便于人工审核。
- 隐私与合规要求限制数据保留与跨主体关联。

### 3.20 图模型与关系模型、文档模型如何选型？

- 关系模型适合事务写入、固定报表与强约束场景。
- 文档模型适合以聚合为单位读取、结构多变的场景。
- 图模型适合关系密集、深度不固定、以路径为中心的查询。
- 多模型系统可为不同路径选择不同存储，但需处理同步与一致性。
- 选型应先列出核心查询，再比较连接次数、延迟与运维成本。
- 数据关系会演化，方案应保留迁移与混合查询的能力。

## 4. B 树与 LSM 存储引擎

### 4.1 B 树与 LSM 树的基本写路径差异是什么？

- B 树原地更新页，写入需定位叶子页并修改，随后写预写日志（WAL）。
- 日志结构合并树（LSM）先写内存表与日志，再批量刷成不可变的排序字符串表（SSTable）。
- B 树读路径短，通常一次根到叶的查找。
- LSM 读路径需查内存表与多层 SSTable，并合并结果。
- B 树写放大来自页重写与日志，LSM 写放大来自反复合并。
- 选择取决于读写比例、延迟目标与空间预算。
- 验证应分别测量点查、范围扫描与写入放大，不能只看单一基准。

### 4.2（辨析）B 树为什么适合读多写少？

- B 树在页内原地更新，点查沿索引一次下降。
- 页缓存可让热点索引常驻内存，读放大较低。
- 随机写会触发整页写回，写放大与页大小相关。
- 范围扫描在叶层按序读取，B+ 树变体可用叶子链表减少回溯。
- 读多写少且事务要求强的负载更适合 B 树。
- 页分裂与合并会增加写延迟，需用填充因子留余量。

### 4.3 LSM 树为什么适合写密集负载？

- LSM 把随机写转为顺序追加，先写日志与内存表。
- 内存表满后冻结并刷成 SSTable，写入持续进入新内存表。
- 顺序写提高磁盘带宽利用率，适合写密集负载。
- 合并会重写数据，写放大随层数与合并策略变化。
- 读操作需检查多个组件，读放大高于 B 树。
- 写密集且可接受后台合并的负载更适合 LSM。

### 4.4 写放大由哪些部分构成？

- 写放大等于实际写入字节数除以逻辑写入字节数。
- 组成包括 WAL、内存表刷盘、合并重写与索引更新。
- 副本复制与快照也会增加物理写入，但通常单独统计。
- 合并策略决定重写次数，分级合并的写放大通常较高。
- 小记录会放大元数据与块对齐开销。
- 报告写放大时应说明统计边界与时间窗口。

### 4.5（估算）分级合并的写放大如何粗略估算？

- 设每层容量是下一层的 T 倍，数据从上层合并到下层时，每字节在每个层边界至少重写一次。
- 若共有 L 层，写放大的粗略下界约为 L，实际量级还受容量比例 T 与合并粒度影响，通常明显高于 L。
- 增大 T 可减少层数，但单次合并涉及的数据量更大。
- 层数与容量比例共同决定读放大与空间放大，取舍不能只看写放大。
- 删除标记与更新会保留旧版本，使实际重写字节高于下界。
- 估算结果应由实现参数与负载分布校准，不能直接套用。

### 4.6 读放大由哪些查找组成？

- 读放大等于一次逻辑读取产生的物理读取量，可按字节数或 IO 次数统计。
- 读放大包括内存表查找、多层 SSTable 查找与块内扫描。
- 每层可能命中多个文件，需按时间序合并版本。
- 布隆过滤器可跳过不含目标键的文件。
- 块索引与分区索引减少块内扫描范围。
- 最坏情况下需检查所有层，读延迟随层数增长。
- 读放大还受缓存命中率与合并进度影响。

### 4.7（陷阱）布隆过滤器能消除读放大吗？

- 布隆过滤器用位数组判断键是否可能存在，假阳性会导致多余读取。
- 它不能排除范围查询中的不存在区间，也不支持前缀扫描。
- 假阴性在正确实现中不应出现，但哈希或并发缺陷可能破坏。
- 位数组占用内存，误判率随容量与哈希函数数量变化。
- 分区级过滤器可减少无效文件查找，但增加元数据。
- 布隆过滤器降低读放大，不能替代合并与索引设计。

### 4.8 空间放大如何产生？

- 空间放大等于实际占用空间除以有效数据大小。
- 空间放大来自旧版本、删除标记与尚未合并的数据。
- 更新会保留旧值直到合并完成，快照读也会阻止立即回收。
- 删除标记需保留一段时间，以覆盖更早的快照与副本。
- 合并不及时会让空间持续增长，甚至触发写停顿。
- 副本与备份会按各自生命周期放大总存储。
- 应监控有效数据比例与待合并字节，而非只看磁盘使用率。

### 4.9 合并的触发条件如何设计？

- 触发条件可包括层容量、文件数、读放大与待合并字节。
- 删除标记比例高时应优先合并，以回收空间。
- 读延迟升高时可提高合并优先级，但需限制对前台写入的影响。
- 合并任务应分优先级与配额，避免一次性占满 IO。
- 写停顿通常来自内存表耗尽、L0 文件积压或合并落后，需提前限流。
- 阈值应结合设备带宽、写入速率与恢复时间设定。

### 4.10（场景）合并与前台写入竞争 IO 如何处置？

- 合并与前台写入共享磁盘带宽，需做速率限制与优先级调度。
- 可将合并限制在低峰期，但突发写入仍可能积压。
- 分离 WAL、SSTable 与合并输出到不同设备可降低干扰。
- 写入限流可保护读延迟，但会增加客户端排队。
- 监控合并待办字节、写停顿次数与 P99 延迟，判断是否失衡。
- 扩容或调整层数只能缓解，根因通常是写入速率超过合并能力。

### 4.11（辨析）分级合并与分层合并的取舍是什么？

- 分级合并（leveled compaction）通常读放大与空间放大较低，写放大较高。
- 分层合并（tiered compaction）通常写放大较低，但读放大与空间放大较高。
- 分级合并每层维护键范围不重叠的文件，合并时需重写重叠范围。
- 分层合并每层保留多个可能重叠的有序段，查询需检查更多段。
- 选择取决于写吞吐、读延迟与存储成本的优先级。
- 混合策略可对热数据用分级合并，对冷数据用分层合并。

### 4.12 B 树的填充因子如何影响空间放大与写放大？

- 填充因子决定页内预留空闲空间的比例。
- 预留越多，插入时越不容易分裂，写放大与写延迟越低。
- 空闲空间本身构成空间放大，降低缓存与扫描效率。
- 顺序插入时若分裂策略不均，页利用率可能长期偏低。
- 批量加载可按页填满，减少空闲但增加后续插入的分裂。
- 取值需结合更新频率、扫描模式与存储成本，由实现定义默认值。

### 4.13（陷阱）B 树崩溃后一定需要完整恢复所有页吗？

- B 树崩溃恢复依赖 WAL 重放已提交事务与未完成页修改。
- 部分页写入可能产生撕裂页，需双写缓冲或校验和检测。
- 并非所有页都需要从备份恢复，WAL 可重放到一致状态。
- 检查点缩短恢复时间，但不能替代日志的持久化。
- 恢复目标取决于提交点与刷盘策略，可能丢失未提交事务。
- 恢复后需校验索引与数据页的一致性，并清理未完成操作。

### 4.14 WAL 在 B 树与 LSM 中分别承担什么角色？

- B 树 WAL 记录页修改，通常支持重做与撤销，直到检查点后可截断。
- LSM 的 WAL 保护内存表，刷盘成功后可删除对应日志。
- 两类 WAL 都承担崩溃恢复，但 B 树更依赖页级重放。
- LSM 还需清单文件记录 SSTable 集合与层级。
- 组提交可降低同步次数，但增加单次提交延迟。
- WAL 写入顺序与刷盘语义决定持久性边界。

### 4.15（设计）LSM 的崩溃恢复需要哪些元数据？

- 恢复需知道当前内存表、已刷盘 SSTable 与各层文件清单。
- 清单文件应原子更新，避免崩溃后出现半套文件集合。
- WAL 重放重建未刷盘的内存表，并恢复序列号。
- 临时文件与未引用 SSTable 需在启动时清理。
- 序列号决定快照可见性，恢复时必须保持单调。
- 恢复完成后应校验文件校验和与层级约束。

### 4.16 事务与索引在两种引擎上如何配合？

- B 树可在同一事务中更新数据页与二级索引页，依赖 WAL 与锁。
- LSM 可把主数据与索引更新写入同一批次，按序列号原子可见。
- 跨多个 LSM 树的索引更新需保证批次原子性。
- 长事务会阻止旧版本回收，增加空间放大。
- 快照读需按序列号过滤，避免看到未提交的索引项。
- 事务隔离与索引维护策略需一起设计，不能只考虑主表。

### 4.17（场景）二级索引与主表不一致如何避免？

- 二级索引与主表非原子更新会在崩溃或并发时产生不一致。
- 同一事务写入两者可保证原子性，但会增加锁范围与写放大。
- 异步索引管道需支持幂等重放与失败重试。
- 对账任务可比对索引项与主表记录，修复缺失或过期项。
- 读路径可校验版本或回表确认，但会增加延迟。
- 索引重建应支持在线进行，并保留旧索引作为回滚路径。

### 4.18（设计）如何选择块大小与页大小？

- 页或块越大，顺序扫描与压缩效率越高，点查读放大越大。
- 页越小，缓存粒度越细，元数据与 IO 次数越多。
- 块大小应与设备最小 IO 单位、压缩算法与访问模式匹配。
- 大块适合分析扫描，小块适合随机点查。
- 压缩块需整块解压，块内偏移查询可能得不偿失。
- 参数应由工作负载测试确定，并由实现定义具体上限。

```text
append WAL
insert memtable
if memtable is full:
    freeze memtable
    flush to SSTable
    schedule compaction
```

### 4.19 如何验证存储引擎的写放大与读放大？

- 写放大用物理写入字节除以逻辑写入字节，按设备与时间段统计。
- 读放大用物理读取字节或读 IO 次数除以逻辑查询数。
- 合并统计需记录每层读写字节、文件数与耗时。
- 压力测试应覆盖点查、范围扫描、更新与删除，不能只测插入。
- 生产观测需关联缓存命中、合并积压与设备利用率。
- 微基准可定位单点，端到端负载才能反映真实放大。

### 4.20（场景）读延迟突然升高，如何区分缓存、合并与磁盘故障？

- 先区分缓存未命中、合并积压、写停顿与设备故障。
- 检查块缓存命中率与每层读放大是否同步上升。
- 观察合并待办字节、后台线程利用率与磁盘队列深度。
- 若只有部分实例升高，排查热点分片与设备差异。
- 若延迟伴随错误率上升，优先检查磁盘与文件系统。
- 用追踪定位慢查询在索引查找、块读取还是合并等待。

## 5. 列存与数据分析

### 5.1 分析型查询为什么偏爱列存？

- 分析查询通常只扫描少数列，列存按列读取，避免把整行无关字段搬进内存。
- 同一列的数据类型一致、取值接近，压缩率远高于行存，I/O 量随之下降。
- 列存便于向量化执行，按批处理数组，分支预测与缓存利用率更好。
- 延迟物化可以先做过滤与聚合，再按需读取其他列，减少中间数据。
- 点查与整行更新在列存上代价高，需要按位置拼接多列或维护额外索引。
- 混合负载可以让行存承担事务、列存承担分析，代价是同步与一致性。

### 5.2（辨析）列存一定比行存快吗？

- 列存优势依赖扫描列少、行数多与压缩收益。
- 点查若需读取多列，列存要访问多个列块，可能慢于行存。
- 小结果集查询的调度与元数据开销占比更高。
- 高频更新会触发行块重写或增量存储，列存优势下降。
- 宽表但每次只读少数列时，列存仍可能占优。
- 应按查询模板与数据分布测量，不能按存储格式推断。

### 5.3 列存为什么适合分析查询？

- 分析查询通常扫描大量行但只访问少数列，列存减少 IO。
- 同列数据类型一致，字典、游程与差分编码更有效。
- 列内连续存储便于向量化与 SIMD 处理。
- 列存可跳过不满足谓词的块，减少读取。
- 聚合可先在各块内计算，再合并部分结果。
- 列存对随机点更新不友好，需增量层或合并。

### 5.4（辨析）OLAP 与 OLTP 的负载差异如何影响存储布局？

- 联机事务处理（OLTP）以短事务、点查与高并发写入为主，行存减少整行读写。
- 联机分析处理（OLAP）以长扫描、聚合与少量列为主，列存减少 IO 与解压成本。
- OLTP 通常要求低延迟与强一致，OLAP 通常可接受较高延迟与快照读。
- OLTP 的索引多为 B 树，OLAP 常用分区、列块与区域映射。
- 混合负载需隔离资源，避免分析扫描影响事务延迟。
- 同一份数据可采用行列混合或定期导出列式副本。

### 5.5（陷阱）在行存表上增加列索引就能替代列存吗？

- 行存加列索引仍以行为单位存储，读取多列时需回表。
- 覆盖索引可减少回表，但索引本身通常按行组织，压缩率有限。
- 列索引无法像列存那样对整列做编码与向量化聚合。
- 索引维护会增加写入成本，列存则批量写入更高效。
- 分析查询的列裁剪与块跳过能力，行存索引难以完全替代。
- 小规模或点查为主的场景，行存加索引更简单。

### 5.6 列存的压缩为什么依赖排序与局部性？

- 列存常用行程编码、字典编码与位打包，这些编码依赖相邻值相似或重复。
- 按基数低的列排序后，相同值聚集，行程长度变长，压缩率显著提高。
- 排序键的选择要匹配查询过滤条件，否则过滤仍需扫描大量数据块。
- 块内排序与全局排序的代价不同，全局排序写入成本高，块内排序更常见。
- 压缩率与随机读取存在权衡：压缩越紧，定位单条记录需要的解压工作越多。
- 列存的写入顺序与排序键不一致时，需要后台合并或重写，类似 LSM 的 compaction。

### 5.7 字典编码适合什么数据，何时失效？

- 字典编码把不同值映射为整数标识，值数组只存标识。
- 适合基数低、重复多的列，例如状态、地区与类别。
- 字典可按排序存放，支持等值与范围比较。
- 基数接近行数时，字典与标识的开销可能超过原值。
- 字典需随新值增长，频繁写入会增加维护成本。
- 高基数列可改用差分、前缀或通用压缩。

### 5.8 游程编码与位图编码如何选择？

- 游程编码适合连续重复值多的列，例如排序后的状态列。
- 位图编码适合基数低且查询按位运算的列。
- 游程编码对随机分布的长文本效果有限。
- 位图在基数升高时占用空间迅速增长。
- 排序与聚簇可增加连续重复，提升游程编码效果。
- 编码选择应基于基数、排序性与查询谓词，而非只看压缩率。

### 5.9（估算）给定基数与行数，字典编码的收益如何估算？

- 设行数为 n、不同值为 d、原值宽度为 w 字节、标识宽度为 ceil(log2 d) 位。
- 原始大小约为 n 乘以 w 字节，字典部分约为 d 乘以 w 字节，值数组约为 n 乘以标识宽度位。
- 以 n 为 10 亿、d 为 1000、w 为 16 字节为例，原始约 16 GB。
- 标识宽度约 10 位，值数组约 1.25 GB，字典可忽略。
- 两部分需换算到同一单位后相加，再计入块头、偏移与对齐开销。
- 基数上升或值宽下降会改变收益，估算需用真实分布。

```text
raw_bytes = n * w
encoded_bytes = d * w + n * ceil(log2(d)) / 8
```

### 5.10 排序与局部性对压缩率有什么影响？

- 按常用过滤列排序，可让相同值聚集，提高游程与差分编码效果。
- 排序本身消耗 CPU 与 IO，且会改变行顺序。
- 聚簇可减少扫描块数，但更新时需维护顺序。
- 多列排序只在前缀列上保持局部性。
- 排序列与查询模式不匹配时，压缩收益下降。
- 可在写入时按分区排序，而非全局排序，降低维护成本。

### 5.11（场景）高基数时间序列列如何编码？

- 时间戳列适合差分编码，按时间排序后差值较小。
- 规则采样的时间戳可用差分再差分，进一步降低熵。
- 浮点测量值可用 XOR 编码，保留前值与有效位。
- 标签列基数低时用字典编码，高基数时避免全量字典。
- 精度与单位需在编码前统一，避免同一列混合量纲。
- 乱序写入会破坏差分效果，需按时间分区或缓冲排序。

### 5.12 向量化执行解决了什么问题？

- 向量化把一批值作为数组处理，减少逐行函数调用与分支。
- 批量处理提高 CPU 流水线利用率与缓存命中率。
- 算子接口以列块为单位，便于延迟物化与选择向量。
- 向量化要求处理空值、变长字符串与选择位图。
- 批大小影响缓存与并行度，过大或过小都会降低收益。
- 向量化不改变算法复杂度，只降低常数开销。

### 5.13（辨析）向量化与编译执行如何取舍？

- 向量化实现简单、可移植，适合多算子组合。
- 编译执行把查询编译为专用代码，减少中间物化与虚函数调用。
- 编译执行有编译延迟与代码体积增大，短查询可能不划算。
- 向量化更容易做批处理与 SIMD，编译执行更易做算子融合。
- 混合方案可对热点算子编译，对冷门算子解释执行。
- 选择取决于查询长度、并发度与部署环境。

### 5.14 SIMD 在向量化中的边界是什么？

- 单指令多数据（SIMD）适合无分支、数据并行的定长计算。
- 选择向量与过滤会产生分支，需用掩码或压缩选择向量。
- 字符串比较与变长解码难以直接向量化。
- 数据需按块对齐，尾部需标量处理。
- 不同指令集的可移植性与运行时检测增加复杂度。
- 内存带宽可能先于 SIMD 成为瓶颈。

### 5.15（陷阱）向量化一定提高所有查询的性能吗？

- 小批量查询的调度开销可能超过向量化收益。
- 过滤后剩余数据很少时，向量化利用率下降。
- 随机访问与指针追逐会破坏缓存局部性。
- 复杂表达式中的分支与短字符串比较难以并行。
- 内存带宽或 IO 受限时，CPU 优化收益有限。
- 应比较端到端延迟与吞吐，而非只看单算子基准。

### 5.16 列存的读放大与写放大有什么特点？

- 列存读取只访问所需列，读放大通常低于行存的全行读取。
- 更新一列仍需重写列块或写入增量层，写放大取决于块大小。
- 删除常用墓碑标记，查询时过滤，合并时回收。
- 大块压缩提高压缩率，但小更新会重写整块。
- 批量导入可顺序写列块，随机更新成本更高。
- 副本与合并会进一步增加物理写入。

### 5.17（设计）列存的更新与删除如何实现？

- 列存更新可写入增量行存或增量列存，查询时合并。
- 删除可写墓碑位图，后台合并时物理清除。
- 频繁更新会导致增量层持续增长，需定期合并。
- 更新需维护版本与可见性，支持快照读。
- 主键索引用于定位待更新行，列块按位置或主键关联。
- 更新策略需在写延迟、读放大与空间放大之间取舍。

### 5.18 列存如何做谓词下推与延迟物化？

- 谓词下推把过滤条件下推到扫描层，减少读取与解压。
- 区域映射用块级最小值与最大值跳过不相关块。
- 字典编码可在编码值上比较，避免解码整列。
- 延迟物化先读过滤列与行号，再按需读取其他列。
- 过滤后剩余行较少时，延迟物化可显著减少 IO。
- 过滤后剩余行较多或需整行输出时，提前物化可能更简单。

### 5.19（场景）小文件过多为什么会增加分析查询延迟？

- 小文件增加元数据、打开关闭与任务调度开销。
- 每个文件难以形成有效的块级压缩与索引。
- 查询规划需处理大量文件，增加延迟。
- 小文件过多会降低顺序扫描带宽利用率。
- 应定期合并文件，并按分区与时间控制文件大小。
- 流式写入可使用缓冲与批量提交，减少碎片。

### 5.20（设计）HTAP 系统如何兼顾事务与分析？

- 混合事务与分析处理（HTAP）需同时支持事务写入与分析扫描，资源需求冲突。
- 常见方案是行存主副本加列存只读副本，通过日志同步。
- 同步延迟决定分析结果的新鲜度，需明确一致性语义。
- 列存副本可独立扩展，但会增加存储与网络成本。
- 资源隔离可避免分析查询影响事务延迟。
- 也可采用行列混合存储，但更新与压缩的取舍更复杂。

## 6. 编码格式与模式演化

### 6.1 为什么需要区分内存表示与持久化表示？

- 内存表示服务于访问效率：指针、对象头、虚表与容器的容量字段都随进程布局变化。
- 持久化表示服务于跨进程、跨语言、跨版本交换：字节序列必须自描述或依赖外部模式。
- 把对象按内存布局直接写出，会把编译器、ABI、字节序与填充规则固化成格式，跨版本读取随即失效。
- 编码格式的核心任务是把结构化数据映射为字节序列，并在读端还原为语言内类型。
- 编解码开销包括 CPU、内存分配与复制次数，数据密集型系统中常出现在序列化热点上。
- 判断边界：只在同一进程、同一构建内传递的临时结构可以不定义稳定格式；跨边界的数据必须定义。
- 验证方式：用不同编译器版本、不同优化级别与不同字节序构造读写用例，检查格式是否仍可解析。

### 6.2（辨析）文本格式与二进制格式的边界在哪里？

- 文本格式（JSON、XML、CSV）以可读字符表达结构，便于抓包、日志与人工排查。
- 二进制格式（Protobuf、Thrift、Avro）以紧凑字节表达结构，解析依赖模式或字段标签。
- 文本格式的体积通常更大，数字与字符串需要词法分析，CPU 开销高于紧凑二进制。
- 二进制格式的可读性差，排障需要专用工具与模式文件，缺失模式时字段含义无法还原。
- 文本格式对未知字段更宽容，多出的字段通常可以忽略，缺少的字段可以用默认值补齐。
- 二进制格式的演化依赖字段编号、标签或读写模式匹配，错误的编号改动会静默错位。
- 选择依据是链路位置：对外接口与调试接口偏文本，内部高频 RPC 与存储偏二进制。
- 混合方案常见：传输用二进制，审计与日志用文本。

### 6.3 JSON 在类型系统上有哪些隐含约定？

- JSON 只定义对象、数组、字符串、数字、布尔与 `null` 六种值，没有整数与浮点之分。
- 数字按双精度浮点解析是常见实现选择，超过 2^53 的整数无法精确表示。
- 对象键必须是字符串，键顺序在语义上不保证，不能依赖顺序做比较或签名。
- JSON 没有日期、二进制与枚举类型，通常用字符串或整数约定表达，约定本身不在格式内。
- 重复键的处理由实现定义，多数解析器保留最后一个，签名与校验场景需要显式拒绝。
- `null` 与字段缺失在不同库中可能映射为不同状态，C++ 侧要区分 `std::optional` 与默认值。
- 验证方式：构造大整数、重复键、深嵌套与非法 UTF-8 输入，检查解析器行为是否与约定一致。

### 6.4 XML 与 JSON 相比在模式描述上有什么差异？

- XML 有 XSD、命名空间、属性与元素之分，可以在格式层描述类型、基数与约束。
- JSON 本身没有模式，JSON Schema 是外挂约定，解析器通常不强制校验。
- XML 的命名空间解决同名元素冲突，代价是前缀管理与文档体积。
- XML 支持注释、处理指令与 CDATA，解析模型比 JSON 复杂，安全面更大。
- 两者都可表达树形结构，XML 更适合文档型数据，JSON 更适合记录型数据。
- 解析 XML 需要防范外部实体注入，禁用 DTD 与外部实体是常见配置。
- 模式校验发生在解析之后还是之中，会影响错误定位与内存占用。
- 选型时看生态：企业集成与配置文件常见 XML，Web 接口与日志常见 JSON。

### 6.5（陷阱）JSON 的数字精度为什么会丢失？

- 规范未规定数字的精度与范围，只要求是十进制字面量，具体由解析器决定。
- 常见实现把数字读成 IEEE 754 双精度，53 位有效位之外的整数被舍入。
- 订单号、用户 ID 与纳秒时间戳常超过该范围，读写一轮后值发生变化。
- 序列化端与反序列化端可能使用不同语言与不同库，两侧舍入行为不一定一致。
- 规避方式是把大整数编码为字符串，并在模式中固定该约定。
- 另一种方式是使用支持任意精度的解析器，但下游语言未必能承接。
- 验证方式：对边界值 2^53-1、2^53 与 2^63-1 做往返测试，比较字节级结果。
- 该问题不会抛出错误，属于静默数据损坏，监控应覆盖关键 ID 的校验位。

### 6.6 Thrift 的二进制协议与紧凑协议有什么区别？

- `TBinaryProtocol` 以固定宽度写出整数与长度，解析简单，字节数较大。
- `TCompactProtocol` 使用 varint 与 zigzag 编码，小整数占更少字节。
- 两者共享同一份 IDL 与字段编号，切换协议不改变接口语义。
- 协议选择影响网络带宽与 CPU，紧凑协议在字段值偏小时收益明显。
- 协议不匹配会导致解析失败或读到错误字段，握手阶段应固定协议版本。
- Thrift 还定义传输层（socket、framed、buffered）与服务器模型，二者与协议正交。
- 跨语言实现的质量差异体现在边界检查与未知字段处理上。
- 验证方式：用同一 IDL 生成两种协议的读写端，做交叉解析与截断输入测试。

### 6.7 Thrift 的字段标识与可选性如何影响兼容性？

- Thrift 用数字字段 ID 标识字段，ID 是兼容性的锚点，名称可以改而 ID 不能改。
- `required` 字段缺失时读取失败，`optional` 字段缺失时取默认值或保持未设置。
- 把 `required` 改为 `optional` 对旧数据通常安全，反向修改会让旧数据无法读取。
- 新增字段应给默认值并设为 `optional`，否则旧写入端产生的数据在新读取端会缺字段。
- 字段类型变更（例如 `i32` 改 `i64`）在多数实现中不被接受，需要新增字段并迁移。
- Thrift 的默认值在读取缺失字段时生效，写入端不会把默认值写进字节流。
- 未知字段在部分实现中被跳过，跳过的前提是能按类型长度正确前进。
- 验证方式：保存旧版本写出的字节样本，用新版本 IDL 读取，再反向读取。

### 6.8 Protobuf 的字段编号为什么不能随意修改？

- 线上格式用字段编号与线型定位字段，字段名不进入字节流。
- 编号一旦发布就等同于格式的一部分，修改编号会让新端把旧字段解析成另一个字段。
- 编号 1 至 15 的标签占一个字节，16 至 2047 占两个字节，高频字段应放在小号段。
- 19000 至 19999 为保留段，使用会触发编译错误。
- 删除字段时应保留编号与名称，使用 `reserved` 防止后续复用。
- 复用已删除的编号会导致旧数据被错误解释，属于难以发现的兼容性故障。
- 编号变更不会在编译期报错，只有跨版本读取时才暴露。
- 验证方式：维护编号分配表，并在持续集成中比对历史 `.proto` 的编号集合。

```text
message User {
  reserved 5, 6;
  reserved "legacy_name";
  string name = 1;
  int64 id = 2;
}
```

### 6.9 Protobuf 移除 `required` 说明了什么？

- proto2 的 `required` 要求字段必须出现，缺失即解析失败。
- 该约束无法安全撤销：新写入端可以省略字段，而旧读取端仍要求其存在。
- 反之把可选字段改为必填，会让历史数据与新旧混合流量立刻失败。
- proto3 取消 `required`，标量字段默认没有存在性语义，读取到的是类型零值。
- 需要区分「未设置」与「设置为零」时，应使用 `optional`（proto3 的显式存在性）或包装类型。
- 必填约束更适合放在应用层校验，因为编码层无法随业务演化。
- 该决策体现模式演化的原则：格式只承诺可解析，业务约束由使用方定义。
- 验证方式：构造缺少字段的消息，检查新旧读取端的行为差异是否符合预期。

### 6.10（辨析）Protobuf 的默认值语义有哪些边界？

- proto3 标量字段默认没有 presence，未设置与设置为零在序列化后无法区分。
- 字段值为零时通常不写入字节流，接收端读到类型零值。
- 字符串为空、枚举为 0、布尔为 `false` 都遵循同一规则。
- 消息类型字段有 presence，未设置与设置为空消息可以区分。
- `optional` 标量字段自 proto3 后期版本起提供 presence，需要检查生成代码与运行时版本。
- 依赖默认值做业务判断会把「未设置」误判为「显式设置为零」。
- 规避方式包括使用包装类型、增加位图字段或把零值定义为非法值。
- 验证方式：对每个字段分别测试未设置、零值与非零值三种输入，比较字节与读取结果。

```cpp
User u;
u.set_name("");
// 只有 optional 标量字段生成 has_name()，普通标量无法区分未设置与空串
const bool present = u.has_name();
```

### 6.11（陷阱）Protobuf 的 `int32` 与 `sint32` 编码差异会带来什么问题？

- `int32` 使用 varint 编码，负数的最高位为 1，编码后固定占 10 字节。
- `sint32` 使用 zigzag 映射，把有符号数映射为无符号数后再 varint，负数只占少量字节。
- 字段类型决定线型，`int32` 与 `sint32` 的线型相同，误用不会在解析层报错。
- 把 `int32` 改为 `sint32` 会让同一字节序列被解释为不同数值，属于静默错误。
- 温度、偏移量等可能为负且绝对值小的字段适合 `sint32`。
- 计数器与 ID 等非负字段适合 `int32` 或 `uint32`。
- 类型变更应新增字段编号，旧字段保留为 `reserved`，通过双写完成迁移。
- 验证方式：对负边界值比较两种类型的编码长度与解码结果。

### 6.12 Avro 为什么把写模式与数据分开存放？

- Avro 的数据块不带字段标签，字段按写模式的顺序依次排列。
- 读端必须拿到写模式，才能知道每个位置对应哪个字段及其类型。
- 写模式通常放在文件头或由注册表按版本提供，数据块本身只保留紧凑字节。
- 省去标签带来更小的体积与更快的顺序解析，代价是强依赖模式分发。
- 缺少写模式时数据无法自解释，这是与 Protobuf、Thrift 的关键差异。
- 模式分发依赖文件头、消息头或注册表，三者对应不同的部署复杂度。
- 该设计适合大批量顺序写读的场景，例如日志与数据仓库文件。
- 验证方式：用写模式与读模式不同的组合解析同一份数据，检查字段映射是否符合预期。

### 6.13 Avro 的读写模式解析规则是什么？

- 解析以写模式为准遍历数据，再按读模式组装结果。
- 写模式有而读模式没有的字段被跳过，跳过的依据是写模式中的类型。
- 读模式有而写模式没有的字段使用读模式中的默认值。
- 类型提升有明确清单：`int` 可提升为 `long`、`float`、`double`，`long` 可提升为 `float`、`double`，`float` 可提升为 `double`。
- 反向收窄不被允许，例如 `long` 到 `int` 会导致解析失败。
- 字段重命名需要使用别名，别名写在读模式一侧。
- 写模式含读模式没有的枚举符号时，读模式的默认符号决定映射结果。
- 验证方式：为每类变更构造写读模式对，覆盖允许与禁止的提升组合。

```text
写模式：{id: long, name: string}
读模式：{id: long, name: string, email: string = ""}
结果：  email 取默认值，其余字段按位置映射
```

### 6.14（辨析）Avro 的默认值在解析中起什么作用？

- 默认值只在读模式一侧生效，用于写模式缺失的字段。
- 默认值不会写入数据，也不影响写模式的解析顺序。
- 新增字段必须给默认值，否则旧数据无法被新读模式解析。
- 删除字段不需要默认值，写模式中的该字段会被跳过。
- 默认值的类型必须与字段类型匹配，联合类型需要与第一个分支匹配。
- 默认值不能表达「字段缺失」与「值为默认」的区别，二者在读端合并。
- 依赖默认值做业务语义判断会掩盖数据缺失。
- 验证方式：用缺少新字段的旧数据触发默认值路径，检查结果与写入端约定是否一致。

### 6.15 向后兼容与向前兼容如何判定？

- 向后兼容指新代码能读旧代码写出的数据，升级读端不影响存量数据。
- 向前兼容指旧代码能读新代码写出的数据，升级写端不影响未升级的读端。
- 判定方法是固定一侧版本，替换另一侧，对同一批数据做读写。
- 新增可选字段通常同时满足两种兼容，删除字段通常只满足一种。
- 修改字段类型、编号或语义通常破坏兼容，需要新增字段与迁移。
- 两种兼容的方向常被相反使用，讨论时应先写明「谁读谁写」。
- 全兼容要求任意新旧组合都能工作，成本高于单向兼容。
- 验证方式：建立版本矩阵，覆盖 N 与 N-1 的双向组合，并纳入持续集成。

### 6.16（设计）新增字段时如何保证新旧版本都能读？

- 新字段应可选，并带有明确的默认语义，旧数据缺少该字段时走默认路径。
- 从从未使用过的号段分配字段编号或 ID，避免与保留字段冲突。
- 写入端在字段有值时写出，无值时省略，读端不依赖字段一定存在。
- 业务逻辑需要区分「未设置」时，增加显式的存在性字段或版本号。
- 新旧版本共存期间，读端应能忽略未知字段，写端不应删除未知字段后回写。
- 数据迁移采用双写或回填，回填完成前保留旧字段的读取路径。
- 文档中记录字段的引入版本与语义，避免后续复用编号。
- 验证方式：用旧版本写出的样本驱动新版本读取，再让旧版本读取新样本。

### 6.17 删除与重命名字段分别有什么风险？

- 删除字段后，旧数据中的该字段仍会在读端被跳过，前提是写模式可获取。
- 在 Protobuf 中删除字段若未保留编号，后续复用会导致旧数据被错误解释。
- 在 Thrift 中删除 `required` 字段会使旧读取端无法读取新数据，应先改为 `optional` 并等待旧端下线。
- 重命名字段在 Protobuf 与 Thrift 中通常安全，因为标识是编号而非名称。
- 在 Avro 中重命名必须配置别名，否则读模式找不到对应字段。
- 删除字段前应确认没有读端依赖该字段，包括报表、导出与审计任务。
- 语义变更比重命名更危险：同名字段改变含义不会被任何格式检查捕获。
- 验证方式：扫描代码与查询日志中的字段引用，并用历史数据做回放。

### 6.18（场景）滚动升级期间如何验证编码兼容性？

- 升级顺序决定共存窗口：先升级读端可以提前承接新字段，先升级写端会考验旧读端。
- 在预发环境构造新旧版本混合的集群，按真实流量比例回放。
- 对比新旧版本的解析结果，重点检查默认值、未知字段与枚举新增值。
- 记录解析失败率与字段缺失率，设置阈值阻断发布。
- 对写入路径做双读校验：新旧解析器读同一份字节，比较结构化结果。
- 关注 C++ 侧生成代码的版本，`protoc` 与运行时库不匹配会产生链接或行为差异。
- 回滚方案要包含数据侧：新版本写入的字段在回滚后是否仍可被旧版本忽略。
- 验证方式：把兼容性用例纳入持续集成，并在每次模式变更时运行。

### 6.19 模式注册表解决什么问题？

- 注册表集中存放模式版本，并给每个版本分配唯一 ID。
- 生产者在消息中携带模式 ID，消费者按 ID 拉取对应模式。
- 注册表在注册阶段做兼容性检查，阻止破坏性变更上线。
- 兼容性策略分为向后、向前、全兼容与传递性兼容，作用范围不同。
- 传递性兼容要求新版本与所有历史版本兼容，而不仅是上一版本。
- 注册表本身成为关键依赖，不可用时消费者无法解析新消息。
- 缓存与本地副本可以降低注册表故障的影响，但会引入版本陈旧窗口。
- 验证方式：在测试环境演练注册表不可用与模式删除，检查消费端降级行为。

### 6.20（设计）如何为跨语言服务选择编码格式？

- 先列出约束：是否需要模式、是否跨语言、是否要求可读、是否受带宽限制。
- 内部高频 RPC 优先考虑 Protobuf 或 Thrift，二者都有成熟的 C++ 代码生成。
- 数据文件与批处理管道优先考虑 Avro，写模式随文件存放，解析成本低。
- 对外接口与调试接口可保留 JSON，配合 JSON Schema 做校验。
- 需要零复制或列式访问时，考虑 FlatBuffers、Cap'n Proto 或 Parquet 等专用格式。
- 评估生成代码体积、运行时依赖与构建集成成本，C++ 侧尤其关注 ABI 与异常策略。
- 兼容性策略必须与格式一起确定，否则格式选型无法独立成立。
- 验证方式：用真实消息样本做跨语言往返，比较字节数、解析耗时与内存占用。

## 7. 复制：单主

### 7.1 复制解决哪些问题，又不解决哪些问题？

- 复制把同一份数据保存在多个节点，目标是提高可用性、降低访问延迟、提升读吞吐与支持故障切换。
- 复制不自动带来正确性：多副本之间存在滞后，读到旧值仍可能发生。
- 复制不替代备份：误删除会同步到所有副本，备份需要独立的时间点。
- 复制不解决写扩展：单主复制下写仍然集中在一个节点。
- 复制增加一致性成本：同步复制提高写延迟，异步复制引入数据丢失窗口。
- 复制改变故障模型：节点故障之外还要处理网络分区、主库假死与旧主回归。
- 设计前应明确目标优先级：可用性、延迟与一致性不能同时最优。
- 验证方式：注入节点宕机、网络分区与延迟抖动，观察读写行为与数据差异。

### 7.2 基于语句的复制为什么容易出问题？

- 语句复制把 SQL 文本发给从库重放，日志体积小，便于审计。
- 非确定性函数（例如 `NOW()`、`RAND()`、`UUID()`）在主从两端产生不同结果。
- 自增列、未指定排序的 `LIMIT` 与命中顺序不确定的 `UPDATE`，重放结果依赖执行计划。
- 触发器与存储过程可能产生额外写入，重放时再次触发，导致数据翻倍。
- 时钟与随机数在语句执行时取值，从库重放时刻不同，结果不同。
- 语句复制要求主从的表结构、索引与优化器行为尽量一致。
- 规避方式包括把语句改写为确定性形式，或改用行复制。
- 验证方式：在从库上比对重放后的行校验和，覆盖含随机与时间函数的语句。

### 7.3 预写日志复制与逻辑日志复制有什么区别？

- 物理日志记录页级修改，内容与存储引擎的页布局绑定，重放速度快。
- 逻辑日志记录行级插入、更新、删除等逻辑操作，与存储格式解耦，可被外部消费者解析。
- 物理日志要求主从的存储引擎版本与页格式一致，跨版本升级受限。
- 逻辑日志体积通常更大，但支持跨版本复制与异构下游。
- 逻辑日志需要处理事务边界与提交顺序，否则下游看到部分事务。
- 物理日志适合同构副本，逻辑日志适合变更捕获与多目的地分发。
- 两者的滞后表现不同：物理日志受页写入影响，逻辑日志受解析与下游消费影响。
- 验证方式：比较两种日志在相同写入负载下的字节量、重放耗时与下游可见顺序。

### 7.4 基于行的复制在什么场景下优于语句复制？

- 行复制记录每行修改前后的值，重放结果与主库执行计划无关。
- 含非确定性函数、触发器与自增列的写入在行复制下结果稳定。
- 批量更新大量行时，行日志可能远大于一条语句，网络与存储开销上升。
- 行复制要求表有主键或唯一键，否则定位目标行的代价高。
- 行复制便于下游做变更数据捕获，但需要额外处理事务提交边界。
- 大字段更新会整行记录，未修改的列也可能进入日志，需关注日志膨胀。
- 行复制对表结构变更更敏感，列顺序与类型必须与日志匹配。
- 验证方式：构造批量更新、触发器与非确定性函数三类写入，比较主从校验和与日志体积。

### 7.5 触发器复制与逻辑复制槽分别解决什么问题？

- 触发器复制在写入时触发自定义逻辑，把变更投递到外部系统。
- 触发器运行在与业务事务相同的上下文，失败会影响主库写入。
- 触发器难以保证投递顺序与幂等，重复投递需要下游去重。
- 逻辑复制槽由数据库维护消费位点，支持断点续传与顺序投递。
- 复制槽会保留未被消费的日志，消费者停滞会导致磁盘增长。
- 复制槽不解决下游处理失败，投递语义通常为至少一次。
- 触发器适合轻量通知，复制槽适合稳定的变更流。
- 验证方式：模拟消费者长时间离线，观察磁盘占用与恢复后的追平行为。

### 7.6（辨析）同步复制与异步复制的边界在哪里？

- 同步复制要求主库在提交前等待至少一个从库确认收到或应用日志。
- 异步复制在主库提交后立即返回，从库稍后追平日志。
- 「同步」的确认点不同：收到日志、写入磁盘、应用完成是三件不同的事。
- 同步复制缩小数据丢失窗口，代价是写延迟受最慢副本影响。
- 异步复制延迟低，主库故障时可能丢失尚未传输的日志。
- 半同步复制只等待一个副本确认，其余副本异步，兼顾延迟与冗余。
- 同步复制无法保证从库可读最新数据，除非确认点包含应用完成。
- 验证方式：在主库提交后立即查询从库，比较确认点与可见性之间的差距。

### 7.7 半同步复制如何折中？

- 半同步复制要求至少一个副本确认，超时后退化为异步。
- 退化机制保证主库不会因副本故障而不可写，但会重新打开丢失窗口。
- 确认副本的选择影响故障切换后的数据完整性，应优先选择低延迟且稳定的副本。
- 确认点若只是写入操作系统缓存，掉电仍可能丢失。
- 超时阈值需要与业务延迟预算匹配，过短会频繁退化。
- 半同步不改变读路径，读从库仍可能读到旧值。
- 监控应覆盖退化次数与确认延迟，退化长期存在意味着副本冗余未真正生效。
- 验证方式：制造副本延迟与副本宕机，观察退化触发与恢复后的追平。

### 7.8 同步复制下的「已提交」到底意味着什么？

- 已提交表示事务在主库已持久化，且满足配置的副本确认条件。
- 若确认条件只要求一个副本收到日志，主库与该副本同时故障时仍可能丢失数据。
- 已提交不等于所有副本可见，读从库仍可能读到旧值。
- 已提交不等于已应用，日志传输与应用之间存在窗口。
- 主库故障切换时，只有包含已提交事务的副本才应被提升。
- 若提升的副本缺少已提交事务，客户端会观察到已提交数据消失。
- 选择提升策略时，需要在可用性与已提交数据不丢失之间取舍。
- 验证方式：在提交返回后立即切断主库，检查提升副本是否包含该事务。

### 7.9（陷阱）异步复制下主库返回成功意味着什么？

- 成功通常只表示主库本地完成了写入与日志持久化，不表示副本已收到。
- 主库崩溃后，未传输的日志随主库一起丢失，客户端看到已确认的写入消失。
- 丢失窗口与复制滞后正相关，滞后越大，潜在丢失越多。
- 读从库可能读到比主库更旧的状态，甚至回退到更早的版本。
- 故障切换工具若只比较日志位点，可能选到滞后较小的副本，仍会丢失部分事务。
- 业务上可用补偿、对账与幂等重放降低影响，但无法恢复未落盘的数据。
- 对账需要业务主键与版本号，不能只依赖自增 ID。
- 验证方式：在压测中注入主库宕机，统计确认后丢失的写入比例。

### 7.10 故障切换需要哪些判定条件？

- 判定主库失联需要综合心跳、租约、客户端错误率与旁路探测，单一信号易误判。
- 必须区分进程崩溃、机器宕机、网络分区与主库假死。
- 网络分区下主库可能仍在处理写入，贸然提升副本会产生双主。
- 切换决策应有超时与确认轮次，避免抖动导致反复切换。
- 提升副本前要确认其日志位点，选择最接近主库的副本。
- 切换后要更新路由、连接池与客户端缓存，旧连接需要被拒绝。
- 需要有回滚与人工介入通道，自动切换失败时不能继续放大故障。
- 验证方式：在测试环境分别注入四类故障，检查切换耗时与是否出现双主。

### 7.11（场景）主库失联后如何避免误切？

- 使用租约机制：主库持有带期限的租约，续租失败后自动停止服务。
- 租约依赖时钟，需要区分单调时钟与墙上时钟，墙上时钟回拨会破坏判断。
- 引入仲裁节点或多数派确认，避免两侧同时认为自身是主库。
- 切换前等待一个大于最大网络抖动的时间窗口，降低分区误判。
- 对旧主库启用隔离机制，例如关闭其写入端口或撤销其存储访问。
- 记录切换决策的依据与时间线，便于事后复盘误切原因。
- 客户端应具备重试与幂等能力，切换期间的失败请求不能产生重复副作用。
- 验证方式：用网络分区工具切断主库与多数节点，观察是否只产生一个可用主库。

```cpp
bool can_serve(const Lease& lease, SteadyClock::time_point now) {
  return now < lease.expires && lease.epoch == current_epoch();
}
```

### 7.12 脑裂是怎么产生的？

- 脑裂指两个节点同时认为自己是主库并接受写入，随后产生分叉日志。
- 常见成因是网络分区与超时判定，双方都认为对方已失效。
- 旧主库在分区恢复后仍可能继续服务，若未被隔离，会与新主库同时写入。
- 双主写入同一行会产生冲突，冲突解决策略可能丢失其中一方。
- 自增 ID、唯一约束与计数器在双主下容易产生重复或跳号。
- 脑裂的检测依赖外部观察者，单机视角无法区分分区与对端故障。
- 防御手段包括多数派选举、租约、隔离与 fencing token。
- 验证方式：构造对称分区，检查是否出现两个可写主库及日志分叉。

### 7.13 STONITH 与 fencing token 分别防住什么？

- STONITH 通过带外手段强制关闭旧主库，确保其不再写入。
- fencing token 是单调递增的令牌，存储层拒绝比已见令牌更旧的写入。
- STONITH 依赖电源、管理网与带外接口，管理网故障时可能失效。
- fencing token 依赖存储层配合检查，应用绕过存储直写时失效。
- 两者解决的是「旧主库仍可写」的问题，不解决已分叉数据的合并。
- 令牌需要持久化并跨切换单调递增，重启后不能回退。
- 仅有租约不足以防止暂停的进程恢复后继续写入，需要令牌在写入路径上校验。
- 验证方式：暂停旧主库进程后恢复，检查其写入是否被存储层拒绝。

### 7.14 旧主库恢复后应如何处理？

- 恢复前先隔离，禁止其直接接受写入与读取流量。
- 比较旧主库与新主库的日志位点，找出分叉点。
- 分叉点之后的事务需要人工或工具判定保留、回滚或合并。
- 常见做法是把旧主库作为新主库的从库，回退分叉段后重新追平。
- 回退会丢失已对客户端确认的数据，必须评估业务影响并记录。
- 若业务要求不丢已确认写入，需要更强的提交协议与仲裁，成本更高。
- 恢复过程应可重复执行，避免二次故障时状态不一致。
- 验证方式：在测试环境制造分叉，执行回退并校验数据与业务对账结果。

### 7.15（估算）复制滞后如何度量？

- 时间滞后等于主库写入时刻与从库应用时刻之差，依赖两侧时钟同步。
- 位点滞后等于主库当前日志位点与从库已应用位点之差，单位是字节或事务数。
- 位点差可以换算为时间，但换算系数随写入速率变化。
- 秒级滞后在低流量时可能对应很少事务，在高流量时对应大量数据。
- 监控应同时采集位点差与时间差，单一指标容易误判。
- 滞后分布比均值更重要，尾部的长滞后决定读异常的影响面。
- 从库上的长事务与大批量写入会放大滞后，需要单独观测。
- 估算方式：按峰值写入速率乘以目标滞后上限，得到可容忍的位点差。

```text
lag_bytes = master_lsn - replica_applied_lsn
lag_seconds ≈ lag_bytes / write_bytes_per_second
```

### 7.16 复制滞后会引发哪些读异常？

- 读己之写被破坏：写入后立即读从库，读不到自己的修改。
- 单调读被破坏：连续读两个从库，后一次读到更旧的状态。
- 一致前缀读被破坏：观察到的因果顺序颠倒，回复先于提问出现。
- 跨分区查询可能混合新旧数据，产生不存在的中间状态。
- 异常的影响取决于业务语义，计数器回退比日志延迟更严重。
- 这些异常在异步复制下常态存在，不是故障时才出现。
- 缓解手段包括粘性路由、版本号校验与读写分离策略调整。
- 验证方式：在压测中记录每次读的副本与位点，统计异常出现频率。

### 7.17 复制位点（LSN、GTID）能解决什么问题？

- 位点标识日志中的位置，用于断点续传、滞后度量与一致性判断。
- GTID 为每个事务分配全局唯一标识，便于切换后定位与去重。
- 客户端可以携带读到的位点，服务端据此选择不落后于该位点的副本。
- 位点比较只在同一复制拓扑内有效，跨拓扑需要额外的映射。
- 位点不能替代业务版本号，业务合并仍需要数据自身的版本信息。
- 位点回传会增加请求体积与路由复杂度，需要权衡。
- 位点过旧时可能没有副本满足条件，需要回退到主库或等待。
- 验证方式：让客户端携带位点读取，检查返回副本的位点是否满足单调性。

### 7.18 复制日志的持久化与崩溃恢复有什么关系？

- 在要求持久化的配置下，主库应在返回成功前把日志写入持久存储，否则崩溃会丢失已确认写入。
- 从库需要记录已应用的位点，重启后从该位点继续，避免重复或跳过。
- 位点写入与数据应用通常不在同一原子操作中，需要幂等重放或事务包裹。
- 日志截断策略影响恢复时间与存储占用，过长的日志会拖慢启动。
- 崩溃后可能出现「数据已写、位点未更新」，重放必须能识别重复事务。
- 文件系统缓存与磁盘缓存的差异决定了持久化语义，写入路径上的 `fsync` 与刷盘策略需要显式配置。
- 备份与日志配合可以做时间点恢复，前提是日志完整且可重放。
- 验证方式：在应用日志与更新位点之间注入崩溃，检查恢复后数据是否一致。

### 7.19 级联复制与多级复制有什么取舍？

- 级联复制让从库再向下游复制，减轻主库的上行带宽压力。
- 多级复制增加端到端延迟，层级越深，尾部滞后越大。
- 中间节点故障会切断其下游，影响面大于单层结构。
- 故障切换时，中间节点的位点与角色需要重新计算。
- 跨机房场景常用级联减少跨地域流量，代价是故障域耦合。
- 级联层级应有上限，并监控每一级的滞后。
- 读流量可以按层级就近分配，但一致性保证更难维持。
- 验证方式：逐级注入延迟与故障，测量末端节点的滞后与恢复时间。

### 7.20（设计）单主复制如何做容量与故障域规划？

- 按写入峰值与日志放大系数估算主库磁盘与网络，日志通常大于数据本身。
- 从库数量由读吞吐与故障冗余共同决定，增加从库会同步放大日志传输带宽。
- 故障域应覆盖机架、可用区与地域，避免同一故障同时影响主从。
- 同步副本应跨故障域部署，否则同步确认无法提升可用性。
- 切换时间目标决定是否需要预热副本与常驻候选。
- 容量规划要预留追平窗口，长时间滞后的副本恢复时会集中消耗带宽。
- 监控覆盖复制延迟、日志增长、磁盘余量与切换演练结果。
- 验证方式：按区域失效演练，检查剩余容量是否能承接全部流量。

## 8. 复制：多主与无主

### 8.1 多主复制适用于哪些部署形态？

- 多主复制允许多个节点同时接受写入，每个节点把变更同步给其他主库。
- 典型场景是多数据中心：每个地域就近写入，降低跨地域写延迟。
- 离线客户端与移动端同步也常采用多主模型，设备本地先写，后台合并。
- 协作编辑把多主推到操作级，冲突解决成为核心问题。
- 多主提升写可用性，代价是冲突检测与解决逻辑必须进入应用。
- 多主不适合强约束场景，例如唯一索引与库存扣减，除非引入额外协调。
- 多主的运维复杂度高于单主，拓扑变更与故障恢复都更复杂。
- 验证方式：断开一个主库的复制链路，继续写入后恢复，检查冲突与合并结果。

### 8.2 多主复制中的写冲突从何而来？

- 两个主库并发修改同一行，且互不可见，恢复复制后产生分叉。
- 冲突的前提是并发，若一方先看到另一方的写入，则不构成冲突。
- 冲突粒度可以是行、字段、文档或操作，粒度越细，合并越复杂。
- 自增 ID 分配、唯一约束与计数器在多主下天然冲突。
- 冲突检测依赖版本信息，缺少版本时只能按时间或节点优先级猜测。
- 冲突不一定表现为错误，可能静默覆盖，排查难度更高。
- 冲突解决策略需要在写入路径或读取路径执行，二者代价不同。
- 验证方式：在两个主库同时更新同一主键，恢复复制后检查最终值与预期是否一致。

### 8.3 冲突检测发生在什么时机？

- 写入时检测需要跨节点协调或预分配，延迟高但能尽早失败。
- 复制时检测在日志合并阶段发现冲突，需要保留足够的历史版本。
- 读取时检测把多个版本返回给应用，由应用决定合并结果。
- 后台检测与修复适合最终一致场景，冲突可能长时间存在。
- 检测时机决定存储开销：保留版本越多，合并能力越强，空间成本越高。
- 检测需要因果信息，仅靠墙上时间戳无法判断并发。
- 冲突解决与冲突检测应分开设计，检测遗漏会让解决策略无从执行。
- 验证方式：人为制造并发写并延迟复制，观察冲突在各时机是否被捕获。

### 8.4（辨析）LWW 的「最后」指什么？

- LWW 指 last write wins，按某个时间戳或版本号选择保留哪一个写入。
- 「最后」通常指时间戳最大，时间戳来自客户端、协调者或数据库。
- 客户端时钟不同步时，时间戳顺序与真实发生顺序不一致。
- 同一毫秒内的多个写入需要额外的决胜规则，例如节点 ID。
- LWW 的写入是幂等的，重复应用同一写入不会改变结果。
- LWW 丢弃的写入不会留下痕迹，除非额外记录审计日志。
- 该策略适合每个键只关心最终值的场景，例如用户偏好与缓存。
- 验证方式：构造时钟偏移与同毫秒并发写入，检查保留结果是否符合预期。

### 8.5 LWW 会丢失哪些更新？

- 并发地对同一字段做增量更新时，只有一个增量被保留。
- 对同一文档的不同字段并发修改时，若按整条记录比较，未冲突的字段也会被覆盖。
- 删除与更新并发时，删除可能被时间戳更晚的更新覆盖，产生「复活」。
- 时间戳精度不足时，本应串行的写入被判为并发，丢失概率上升。
- 基于客户端时钟的 LWW 在时钟回拨后可能长期保留旧值。
- 丢失是静默的，业务侧只能通过对账或审计发现。
- 缓解方式包括按字段合并、使用 CRDT 或改为显式版本比较。
- 验证方式：对同一键并发执行自增与赋值，统计最终值是否等于全部增量之和。

### 8.6 版本向量如何判定并发写？

- 版本向量为每个副本维护一个计数器，记录该副本已见的写入数量。
- 比较两个向量：若一方所有分量都不大于另一方且至少一个更小，则前者是后者的祖先。
- 若两个向量互有大小，则两个写入并发，需要合并。
- 若两个向量相等，则是同一版本或重复投递。
- 版本向量能检测冲突，但不能自动决定保留哪个值。
- 向量大小随副本数增长，副本频繁变更时需要压缩或替换机制。
- 客户端也可能携带版本向量，形成客户端与服务端共同维护的因果链。
- 验证方式：构造祖先、并发与相等三类向量对，检查比较函数的输出。

```cpp
enum class Order { Before, After, Concurrent, Equal };

Order compare(const VersionVector& a, const VersionVector& b) {
  auto get = [](const VersionVector& v, NodeId n) {
    auto it = v.find(n);
    return it == v.end() ? 0u : it->second;
  };
  bool a_le_b = true, b_le_a = true;
  for (const auto& [n, c] : a) a_le_b = a_le_b && c <= get(b, n);
  for (const auto& [n, c] : b) b_le_a = b_le_a && c <= get(a, n);
  if (a_le_b && b_le_a) return Order::Equal;
  if (a_le_b) return Order::Before;
  if (b_le_a) return Order::After;
  return Order::Concurrent;
}
```

### 8.7（陷阱）版本向量能自动解决冲突吗？

- 版本向量只提供因果关系，冲突解决仍需要业务规则。
- 检测到并发后，系统需要选择合并、保留多版本或交给应用。
- 若实现按时间戳或节点优先级挑一个，等于隐式采用任意策略，可能丢数据。
- 合并结果本身需要新的版本向量，否则下游无法判断合并的因果位置。
- 多版本存储会增加读路径复杂度，读端必须处理多个候选值。
- 版本向量不包含操作语义，无法判断两个写入是否可交换。
- 冲突解决逻辑应可测试，并覆盖重复投递与乱序到达。
- 验证方式：对并发写入执行合并，再用合并结果与原始版本比较因果关系。

### 8.8 应用层合并有哪些策略？

- 保留多版本并把选择权交给读端，适合需要人工确认的场景。
- 按字段合并，只对冲突字段做决策，减少无谓覆盖。
- 使用业务规则合并，例如取最大值、取并集或按状态机优先级。
- 把冲突写入转为待办任务，由人工在后台处理。
- 合并函数必须满足交换律与幂等性，否则不同到达顺序会产生不同结果。
- 合并后的结果需要持久化并参与后续复制，避免重复合并。
- 合并策略应与业务语义绑定，通用框架只能提供机制。
- 验证方式：对同一组并发写入按不同顺序合并，比较最终结果是否一致。

### 8.9 CRDT 适合什么类型的冲突？

- CRDT 指无冲突复制数据类型，其合并操作满足交换律、结合律与幂等性。
- 计数器、集合、映射与序列都有对应的 CRDT 结构。
- 基于状态的 CRDT 传输完整状态，基于操作的 CRDT 传输增量操作。
- CRDT 保证最终一致，但不保证中间状态符合业务约束。
- 删除需要墓碑，墓碑的清理依赖因果稳定性判断。
- 序列类 CRDT 在并发插入位置相近时可能产生交错，需要额外约束。
- CRDT 的元数据开销随副本与操作数量增长，需要压缩与快照。
- 验证方式：对同一操作集合按任意顺序合并，检查收敛结果与元数据大小。

### 8.10 无主复制的读写 quorum 如何定义？

- 无主复制没有主库，客户端把写发送到多个副本，把读发送到多个副本。
- 写 quorum 为 `W`，表示写入需要收到确认的副本数。
- 读 quorum 为 `R`，表示读取需要收到响应的副本数。
- 副本总数为 `N`，三者共同决定一致性与可用性。
- 当 `W + R > N` 时，读写集合必然相交，读端至少能看到一个最新写入。
- quorum 只保证读到最新值的存在，不保证读端一定选择它，需要版本比较。
- 协调者可以代客户端转发，也可以由客户端直接读写，二者故障模型不同。
- 验证方式：在部分副本不可用时执行读写，检查返回数量与版本选择。

```text
N = 3, W = 2, R = 2  =>  W + R = 4 > 3
N = 3, W = 1, R = 1  =>  W + R = 2 <= 3
```

### 8.11（估算）如何选择 quorum 参数？

- 常见配置是 `N = 3`、`W = 2`、`R = 2`，可容忍一个副本故障。
- 读多写少可以取 `W = N`、`R = 1`，写延迟高但读延迟低。
- 写多读少可以取 `W = 1`、`R = N`，读需要访问全部副本。
- 可用性按副本独立故障率估算，`W = 2` 时单副本故障仍可写。
- 跨地域部署时，quorum 的延迟由最慢的必需副本决定。
- 参数不是固定的，可以按请求级别设置，读写重要性不同。
- 增大 `W` 或 `R` 提升一致性，降低可用性与延迟余量。
- 估算时应把重试与超时计入，失败的副本仍会消耗请求预算。

### 8.12（辨析）读写 quorum 相交保证了什么，又不保证什么？

- 保证读写集合相交，读端有机会看到最近一次成功写入。
- 不保证读端一定返回最新版本，需要版本号或时间戳比较。
- 不保证写入顺序，多个并发写的最终值仍可能不确定。
- 不保证跨键的一致性，不同键的 quorum 可能由不同副本集合完成。
- 不保证失败写入的可见性，未达到 `W` 的写入可能部分生效。
- 不保证会话一致性，客户端换一个协调者后可能读到旧值。
- 在 sloppy quorum 下，`N` 的定义被放宽，相交性不再严格成立。
- 验证方式：并发写入不同版本，读取时统计返回旧版本的比例。

### 8.13 读修复与反熵有什么区别？

- 读修复在读取时比较多个副本的版本，把新版本写回旧副本。
- 反熵在后台持续比较副本数据，修复不一致的键。
- 读修复只覆盖被读取的键，未被访问的数据不会被修复。
- 反熵覆盖全量数据，成本高，通常按范围和速率限制执行。
- 读修复实现简单，但依赖读流量，冷数据可能长期不一致。
- 反熵需要 Merkle 树或类似结构做差异检测，构建与维护有开销。
- 两者可以组合：读修复处理热数据，反熵处理冷数据与故障恢复。
- 验证方式：让副本离线一段时间后恢复，分别观察读修复与反熵的收敛时间。

### 8.14（陷阱）读修复为什么可能读到旧值？

- 读修复发生在读取响应之后，当前这次读仍可能返回旧值。
- 协调者需要比较版本，若版本信息缺失或不完整，无法判断新旧。
- 部分副本返回超时，协调者可能只拿到旧副本的响应。
- 读修复写回是异步的，写回失败不会立即反馈给客户端。
- 并发写入期间，读修复可能把中间版本写回，需要版本比较保护。
- 删除依赖墓碑，墓碑被提前清理会让旧值重新出现。
- 读修复不修复跨键的不一致，只针对被读的键。
- 验证方式：人为让一个副本落后，连续读取并记录返回版本的变化。

### 8.15 hinted handoff 解决什么问题？

- 当目标副本暂时不可用时，协调者把写入暂存在其他节点，并记录提示。
- 目标副本恢复后，持有提示的节点把写入转发过去。
- 该机制提升写可用性，使写入不必等待所有副本在线。
- 提示记录包含目标节点、键与写入内容，需要持久化以防协调者崩溃。
- 提示的保留时间有限，超时后写入可能丢失，需要与反熵配合。
- 提示增加了存储与转发开销，热点键的提示可能集中到一个节点。
- 提示不改变一致性模型，读端仍需要 quorum 与版本比较。
- 验证方式：让一个副本离线并持续写入，恢复后检查提示是否被完整转发。

### 8.16 hinted handoff 的失效场景有哪些？

- 目标副本长时间离线，提示超过保留期被丢弃。
- 持有提示的节点也发生故障，提示副本随之丢失。
- 提示转发失败且没有重试记录，写入静默丢失。
- 网络分区期间提示堆积，恢复后集中转发造成拥塞。
- 提示不保证最终送达，期间读端可能读不到该写入。
- 节点永久下线时，提示无处可送，需要重新分配副本并迁移数据。
- 提示机制与删除墓碑的清理需要协调，否则旧值可能复活。
- 验证方式：模拟长时间离线与持有节点故障，检查数据补齐结果。

### 8.17（场景）节点永久下线后如何补齐数据？

- 先确认节点不再返回，避免恢复后与新副本同时服务。
- 从其余副本读取该节点负责的键范围，按版本选择最新值。
- 重新计算副本分配，把缺失的副本补到新节点。
- 补齐期间读请求仍按 quorum 路由，缺失副本会降低可用余量。
- 补齐需要限速，避免占用过多带宽影响在线请求。
- 补齐完成后用校验和或 Merkle 树比对，确认没有遗漏。
- 若数据量很大，可以分批迁移并按范围切换路由。
- 验证方式：在补齐过程中随机读键，检查是否出现读失败或版本回退。

### 8.18 无主复制中的删除为什么需要墓碑？

- 删除不能简单移除数据，否则旧副本上的值会在后续修复中复活。
- 墓碑是一个带版本的标记，表示该键在某个版本被删除。
- 读修复与反熵比较版本时，墓碑参与比较，旧值被丢弃。
- 墓碑需要保留足够长时间，覆盖所有副本的修复周期。
- 墓碑清理依赖因果稳定性，确认没有更旧的副本会再加入。
- 墓碑数量过多会影响读性能与存储，需要定期压缩。
- 墓碑丢失会导致删除失效，表现为数据「复活」。
- 验证方式：删除一个键后让副本离线再恢复，检查旧值是否重新出现。

### 8.19（设计）多主复制的冲突解决策略如何选择？

- 先按数据语义分类：可交换的操作、需要人工判断的操作、必须强约束的操作。
- 可交换操作用 CRDT 或字段级合并，减少人工介入。
- 需要业务判断的冲突保留多版本，提供后台处理界面。
- 必须强约束的数据不应放在多主模型，改用单主或共识协调。
- 冲突解决结果要可审计，记录输入版本、规则与输出。
- 规则变更需要考虑历史数据，旧冲突可能在新规则下有不同结果。
- 冲突率应作为运行指标监控，持续升高说明分区或路由策略有问题。
- 验证方式：回放历史冲突样本，比较不同策略的结果与人工判断的一致率。

### 8.20（设计）quorum 系统如何应对网络分区？

- 分区把副本分成多数派与少数派，多数派仍可完成 quorum 读写。
- 少数派无法达到 `W` 或 `R`，应快速失败而不是长时间等待。
- 客户端需要知道当前可用的副本集合，避免把请求发往不可达节点。
- sloppy quorum 允许借用其他节点，提升可用性但削弱相交性。
- 分区恢复后需要读修复与反熵补齐，期间读端可能看到旧值。
- 跨分区写入的冲突需要版本比较与合并策略。
- 分区检测依赖超时，超时阈值影响误判率与恢复速度。
- 验证方式：用对称与非对称分区测试读写成功率与恢复后的收敛时间。

## 9. 复制滞后与一致性保证

### 9.1 复制滞后下会出现哪几类读异常？

- 读己之写：写入后立即读，读不到自己的修改。
- 单调读：连续读多个副本，时间上后发生的读反而看到更旧的状态。
- 一致前缀读：观察到的写入顺序违反因果顺序。
- 三类异常对应不同的保证，强度与实现成本依次变化。
- 异常只在存在滞后与多副本时出现，单副本读取不会出现。
- 异常的影响取决于业务：登录态、订单状态与消息顺序的敏感度不同。
- 处理方式包括路由约束、版本校验与客户端修复。
- 验证方式：在压测中记录读请求的副本与版本，统计异常类型与频率。

### 9.2 读己之写保证的是什么？

- 保证同一用户在同一会话中，写入完成后能看到自己的写入。
- 保证范围限于该用户自己的修改，不保证看到其他用户的修改。
- 实现依赖会话粘性或版本追踪，二者都需要在请求间传递状态。
- 该保证不要求全局顺序，也不要求跨设备一致。
- 写入可能尚未复制到所有副本，读请求需要被路由到足够新的副本。
- 若用户切换设备或会话，保证可能失效，需要额外的同步点。
- 该保证属于会话级约束，数据库不会把它当作全局属性。
- 验证方式：写入后立即用同一会话读多个副本，检查是否总能读到新值。

### 9.3 一致前缀读解决什么问题？

- 解决观察到的写入顺序与因果顺序不一致的问题。
- 典型场景是分区数据：不同分区独立复制，观察者可能先看到结果后看到原因。
- 保证读端看到的写入序列是完整前缀，不会跳过中间的写入。
- 该保证约束跨分区的可见顺序，不要求写入实时同步。
- 实现方式包括把相关写入放在同一分区，或显式跟踪因果依赖。
- 该保证弱于线性一致，允许滞后，但不允许顺序倒置。
- 跨分区事务会放大实现难度，需要额外协调。
- 验证方式：构造有因果关系的两次写入，从多个副本读取并检查顺序。

### 9.4 单调读解决什么问题？

- 保证同一客户端后续的读不会看到比之前更旧的状态。
- 典型场景是客户端连接不同副本，后一次读落到滞后更大的副本。
- 实现方式包括把用户固定到同一副本，或记录已读版本并要求副本不落后。
- 单调读不保证读到最新值，只保证不倒退。
- 副本故障切换时，需要选择不落后于客户端已读版本的副本。
- 该保证对用户体验重要，例如消息列表刷新后不能回到更早的状态。
- 单调读与读己之写可以组合，形成会话级的一致性。
- 验证方式：让客户端在多个副本间切换读取，记录版本是否单调不减。

### 9.5（辨析）单调读与读己之写的区别？

- 读己之写关注「自己的写入是否可见」，单调读关注「读到的版本是否倒退」。
- 读己之写需要知道写入的位置或版本，单调读只需要记住已读版本。
- 一个满足单调读的系统不一定满足读己之写：读到的版本可能一直很旧但单调。
- 一个满足读己之写的系统不一定满足单调读：换副本后可能读到更旧的状态。
- 两者都属于会话保证，作用域是单个客户端会话。
- 组合实现通常共享同一份会话状态，例如最后写入位点与最后读取位点。
- 选择取决于业务：个人资料页偏读己之写，信息流偏单调读。
- 验证方式：分别构造「写后读」与「连续读」用例，检查两项保证是否独立成立。

### 9.6（辨析）一致前缀读与线性一致的区别？

- 线性一致要求所有操作看起来在某个全局时间点上原子生效，且与实际时间顺序一致。
- 一致前缀读只要求观察到的写入序列是某个合法全序的前缀，允许滞后。
- 线性一致强于一致前缀读，满足线性一致即满足一致前缀读，反之不成立。
- 一致前缀读不要求读到自己最近的写入，线性一致要求。
- 线性一致通常需要共识或单点协调，成本高。
- 一致前缀读可以通过分区内顺序与因果跟踪实现，成本较低。
- 选择取决于是否需要「读到最新」，很多业务只需要顺序不乱。
- 验证方式：构造延迟写入，检查系统是否允许读到旧值但禁止顺序倒置。

### 9.7 因果顺序包含哪些关系？

- 程序顺序：同一进程内的操作按发出顺序排列。
- 读后写：读到某值后产生的写入，因果依赖于该读。
- 传递性：若 A 先于 B、B 先于 C，则 A 先于 C。
- 并发：两个操作互不依赖，没有先后关系。
- 因果顺序不等同于墙上时间顺序，时钟只能作为近似。
- 因果一致性要求所有节点以相同顺序看到有因果关系的写入。
- 无因果关系的写入可以有不同的可见顺序。
- 验证方式：构造链式依赖与并发分支，检查各副本的可见顺序。

### 9.8（陷阱）时间戳能否替代因果顺序？

- 墙上时钟可能回拨、跳变与不同步，无法稳定表达先后。
- 即使时钟同步，两个事件的时间戳相同也无法判断因果。
- 混合逻辑时钟把物理时间与逻辑计数结合，缩小但不能消除不确定性。
- Lamport 时钟能给出全序，但与真实时间顺序不一定一致。
- 版本向量能表达因果关系，但大小随节点数增长。
- 时间戳适合做近似排序与冲突决胜，不适合作为唯一因果依据。
- 依赖时间戳做「后写覆盖」会丢失并发写入。
- 验证方式：注入时钟偏移与回拨，检查因果判断是否仍然正确。

### 9.9 如何实现读己之写？

- 写入后把版本号或位点返回给客户端，后续读请求携带该信息。
- 服务端只把读路由到已应用该位点的副本。
- 或者把同一用户的读写固定到同一副本，避免跨副本滞后。
- 也可以在客户端本地缓存刚写入的值，读时优先返回。
- 版本号需要与副本的复制位点可比较，跨拓扑时需要映射。
- 位点过旧或没有副本满足条件时，回退到主库读取。
- 本地缓存需要考虑多设备与缓存失效，避免长期返回陈旧值。
- 验证方式：写入后立即读取多个副本，检查是否总能读到不低于写入版本的副本。

```cpp
struct ReadToken {
  uint64_t lsn;
  std::string session_id;
};

bool replica_satisfies(const Replica& r, const ReadToken& t) {
  return r.applied_lsn >= t.lsn;
}
```

### 9.10 读己之写的失效场景有哪些？

- 会话状态丢失，例如进程重启或负载均衡未保持粘性。
- 客户端未持久化位点，重新打开应用后无法携带。
- 写入与读取使用不同的认证主体，服务端无法关联。
- 副本故障切换后，新副本落后于客户端携带的位点。
- 写入本身尚未完成，客户端读取的是写入前的状态。
- 跨数据中心复制延迟超过客户端重试窗口。
- 位点比较使用了不同拓扑的编号，导致误判。
- 验证方式：模拟会话丢失、副本切换与写入超时，检查保证是否仍成立。

### 9.11 如何实现单调读？

- 客户端记录已读的最大版本号或位点，读请求携带该值。
- 服务端选择不落后于该位点的副本，否则拒绝或等待。
- 或者把用户固定到同一副本，直到该副本不可用。
- 固定副本在故障切换时需要重新选择，并校验新副本的位点。
- 版本号可以是逻辑时钟、事务 ID 或复制位点。
- 服务端需要维护副本位点索引，路由层要能实时查询。
- 无法满足时返回错误比返回旧值更安全，但会增加失败率。
- 验证方式：连续读取并切换副本，检查返回版本是否单调不减。

### 9.12 单调读的实现代价是什么？

- 需要维护客户端会话状态，服务端或客户端要持久化已读位点。
- 路由层需要副本位点的实时视图，位点更新本身有延迟。
- 固定副本降低负载均衡的灵活性，热点用户可能集中。
- 位点过旧时可选副本减少，尾部延迟上升。
- 跨地域场景下，满足位点的副本可能距离较远。
- 会话状态过期策略影响内存占用与保证强度。
- 拒绝读请求会提高错误率，需要与业务的重试策略配合。
- 验证方式：在副本滞后与故障场景下测量满足率与额外延迟。

### 9.13 如何实现一致前缀读？

- 把有因果关系的写入路由到同一分区，分区内按日志顺序复制。
- 读取时按分区位点排序，保证先看到原因再看到结果。
- 跨分区写入需要显式记录因果依赖，读端等待依赖满足。
- 可以在写入中携带依赖的版本向量，读端据此判断可见性。
- 客户端观察多个分区时，需要合并各分区的位点并保持顺序。
- 该实现不要求全局时钟，只要求分区内顺序与依赖跟踪。
- 依赖过多会增加写路径的元数据与读路径的等待。
- 验证方式：构造跨分区的因果写入，从不同副本读取并检查顺序。

```text
写入 A：分区 1，序号 7
写入 B：分区 2，序号 3，依赖 A
读端看到 B 时，必须先确认分区 1 的序号 7 已可见
```

### 9.14 分区内因果序如何维护？

- 每个分区维护单调递增的日志序号，写入按序号追加。
- 副本按序号应用，读端按序号判断可见性。
- 跨分区依赖以「分区 ID 加序号」的形式记录。
- 读端看到某条写入时，需要确认其依赖的分区序号已可见。
- 依赖检查可以在服务端完成，也可以在客户端合并结果时完成。
- 分区迁移会改变序号空间，需要版本化或映射表。
- 依赖集合过大会拖慢读路径，需要裁剪与压缩。
- 验证方式：在分区迁移与副本滞后时检查依赖判断是否仍然正确。

### 9.15（场景）跨设备场景下读己之写如何保证？

- 设备切换后没有本地会话状态，需要服务端持久化用户级位点。
- 用户级位点记录该用户最后一次写入的版本，读请求按用户查询。
- 写入路径需要把用户 ID 与版本关联，并保证版本可比较。
- 多设备并发写入时，用户级位点取最大值，读端要求不低于该值。
- 服务端位点存储本身需要高可用，否则读路径会退化。
- 隐私与合规要求可能限制跨设备关联，需要权衡。
- 无法满足时可提示「同步中」，而不是返回旧值。
- 验证方式：在两台设备上交替写入与读取，检查是否总能读到最新写入。

### 9.16 客户端记住版本号的方式有哪些边界？

- 版本号可以存在内存、Cookie、本地存储或请求头中。
- 内存存储在页面刷新或进程重启后丢失。
- 客户端可篡改版本号，服务端必须校验其合法性。
- 版本号需要与副本位点可比较，跨系统时可能需要转换。
- 版本号过大或过旧都会影响路由，需要设置有效期。
- 多标签页与多进程可能各自维护版本，需要合并策略。
- 版本号泄露可能暴露写入时序，敏感场景需要脱敏。
- 验证方式：构造伪造、过期与跨拓扑的版本号，检查服务端拒绝行为。

### 9.17（设计）会话一致性如何落到接口上？

- 在响应中返回一致性令牌，例如位点或版本号。
- 客户端在后续请求中回传令牌，服务端据此路由或等待。
- 接口需要定义令牌缺失、过期与非法时的行为。
- 读接口可以声明一致性级别，例如「尽量新」与「至少包含本次写入」。
- 写接口需要返回令牌，且令牌要在写入成功后生成。
- 错误码要区分「暂不满足」与「永久失败」，便于客户端重试。
- 令牌不应暴露内部拓扑细节，使用不透明字符串更合适。
- 验证方式：用契约测试覆盖令牌的生成、传递与失效路径。

### 9.18（估算）一致性保证对延迟的影响如何估算？

- 强一致读需要等待多数派或主库，延迟下界是往返时延。
- 会话一致读只需等待满足位点的副本，延迟取决于副本分布。
- 固定副本策略把延迟稳定在单副本水平，但故障时切换成本高。
- 等待依赖满足的读可能长时间阻塞，需要超时与降级。
- 位点差距对应的时间可以用写入速率换算，换算结果随负载变化。
- 一致性级别越高，可选副本越少，尾部延迟越差。
- 估算时应把重试与超时计入，失败请求也会占用预算。
- 验证方式：在受控滞后下测量不同一致性级别的 P50 与 P99 延迟。

### 9.19（陷阱）从库读到旧数据是否等于数据丢失？

- 不等于，旧数据可能只是尚未复制，最终会追平。
- 数据丢失指写入未持久化或已被覆盖，旧读只是可见性问题。
- 若主库已崩溃且日志未传输，旧读背后可能是真正的丢失。
- 区分方法是比较主库与从库的位点，确认写入是否存在于日志中。
- 监控应区分「滞后」与「缺失」，二者的处置方式不同。
- 长期滞后可能演变为丢失，例如日志被截断或副本被重建。
- 业务对账可以发现缺失，但无法区分原因，需要日志辅助。
- 验证方式：注入滞后与丢失两类故障，检查监控指标是否能区分。

### 9.20（设计）如何为业务选择合适的一致性级别？

- 先按读操作分类：必须读到自身写入、必须不倒退、只需最终一致。
- 登录态与支付结果通常要求读己之写，信息流可以接受单调读。
- 全局唯一约束与库存扣减需要更强保证，通常超出会话一致性范围。
- 一致性级别越高，延迟与可用性成本越大，应按接口分别设置。
- 降级策略要明确：无法满足时返回错误、返回旧值还是等待。
- 监控覆盖满足率、额外延迟与降级次数。
- 文档中写明每个接口的保证，避免调用方假设过强。
- 验证方式：用故障注入与滞后注入验证各接口在降级路径上的行为。

## 10. 分区策略

### 10.1 分区要解决什么问题？

- 单机的磁盘、内存、CPU 与网络带宽存在上限，分区把数据与负载分散到多个节点。
- 分区提高并行度，不同分区可独立读写，吞吐随节点数近似线性增长。
- 分区提供故障隔离，单个分区不可用时其余分区仍可服务，但这依赖副本配置。
- 分区本身不带来高可用，副本与故障转移属于复制层职责，两者正交。
- 分区的代价是跨分区操作，事务、连接、聚合与排序都需要额外协调。
- 分区粒度决定再平衡成本，过细会增加元数据与路由开销。

### 10.2 键范围分区如何工作？

- 按键的排序顺序切分连续区间，每个分区负责一段键空间，分区内仍然有序。
- 范围扫描与前缀查询可定位到少量分区，适合时间序列与有序主键。
- 边界由系统维护或人工预分，边界信息随数据增长调整。
- 写入集中在相邻键时会形成尾部热点，单调递增键尤其明显。
- 分区过大时单分区成为瓶颈，需要拆分，拆分点影响后续均衡。
- 范围分区对键的分布敏感，键设计需要避免集中。

### 10.3 哈希分区与键范围分区如何取舍？

- 哈希分区对键取哈希后按区间或取模分配，键空间被打散。
- 点查询只需一次路由，范围查询需要广播到所有分区。
- 哈希破坏键的局部性，相邻键落在不同分区，范围扫描代价高。
- 键范围分区保留顺序，范围扫描可裁剪到少量分区，但写入容易集中。
- 组合方案先按哈希打散，再在分区内按排序键组织。
- 选择依据主要是查询模式与写入分布，数据量大小是次要因素。
- `std::hash` 只保证同一次程序运行期间稳定，跨进程路由需要固定算法的哈希。

```cpp
int partition_of(const std::string& key, int partitions) {
    const std::size_t h = std::hash<std::string>{}(key);
    return static_cast<int>(h % partitions);
}
```

### 10.4 取模分区扩容时有什么问题？

- 分区数等于节点数时，增加节点会改变取模基数，多数键需要迁移。
- 扩容一倍时约一半键需要移动，迁移期间双写与校验成本高。
- 节点故障后若重新取模，剩余节点承担全部重分布。
- 解决方式是让分区数远多于节点数，或在键与节点之间加一层映射。
- 一致性哈希只减少迁移范围，虚拟节点与负载均衡仍需处理。
- 取模实现简单，适合节点数稳定且可停机迁移的场景。

### 10.5 为什么分区数应远多于节点数？

- 固定分区数使数据在节点间以分区为单位移动，迁移粒度可控。
- 扩容时只需把部分分区整体搬到新节点，路由表按分区更新。
- 分区数不随节点数变化，取模基数保持稳定。
- 分区过多会增加元数据、快照、日志与调度开销。
- 分区过少则再平衡粒度粗，单分区容量压力大。
- 分区数应预留扩容空间，避免频繁重新分片。

### 10.6 动态分区如何避免预分区错误？

- 动态分区在分区大小超过阈值时拆分，低于阈值时合并。
- 初始只有一个分区，写入增长后逐步分裂，避免数量估计错误。
- 拆分阈值需要结合单分区目标大小与迁移成本设定。
- 空库启动时写入集中在单分区，需要预分区或引导写入。
- 合并减少小分区数量，但涉及数据移动，需要限速。
- 动态分区适合增长不可预测的场景，键范围分区常用。

### 10.7 按节点比例分配分区如何工作？

- 分区总数固定，每个节点分到数量大致相等的分区。
- 新节点加入时从现有节点各抽取若干分区，维持数量均衡。
- 分区大小不一致时，按数量均衡不等于按容量均衡。
- 调度应按字节数而非分区数，并避免反复搬迁。
- 节点故障后其分区由副本接管，恢复后是否迁回取决于策略。
- 该方式常见于依赖外部协调服务的分布式存储。

### 10.8 再平衡在什么情况下必须触发？

- 节点加入或退出导致分区与节点比例失衡。
- 单分区或单节点容量超过阈值，热点持续存在。
- 副本数变化或机架、可用区分布不满足容错要求。
- 集群负载长期倾斜，CPU、磁盘或网络成为瓶颈。
- 再平衡应在低峰执行，并与写入速率联动限速。
- 频繁触发会放大迁移开销，需要设置最小间隔。

### 10.9（陷阱）自动再平衡会带来什么问题？

- 自动触发可能在流量高峰搬运大量数据，挤占磁盘与网络带宽。
- 迁移期间源节点与目标节点同时承担读写，尾延迟上升。
- 多节点同时判定失衡时可能产生搬迁震荡，分区来回移动。
- 自动决策依赖心跳与统计，短时抖动会误判节点失效。
- 常见做法是自动检测、按窗口执行，并限制并发迁移数。
- 迁移需要可暂停、可回滚，并记录进度以便断点续传。

### 10.10 请求路由有哪几种方式？

- 客户端直接连接目标分区所在节点，需要客户端持有分区映射。
- 路由层作为代理，客户端只连代理，由代理转发并处理重试。
- 节点间转发：任意节点接收请求后转发给负责节点。
- 映射信息存放在协调服务或配置中心，客户端订阅变更。
- 客户端缓存映射减少一跳，但缓存过期会短时错路由。
- 路由层便于统一鉴权、限流与观测，但增加延迟与单点风险。

| 方式 | 客户端依赖 | 延迟 |
| --- | --- | --- |
| 客户端直连 | 持有并刷新映射 | 一跳 |
| 路由层代理 | 只连代理 | 两跳 |
| 节点转发 | 只连任意节点 | 两跳以上 |

### 10.11 分区映射信息如何保持一致？

- 映射变更需要版本号或纪元号，请求携带版本以便节点拒绝过期路由。
- 协调服务提供监听机制，客户端在变更时收到通知并刷新缓存。
- 映射更新与数据迁移分两步：先复制数据，再切换映射。
- 切换期间新旧映射并存，读请求可能命中旧节点，需要按版本重定向。
- 映射信息应持久化并带校验，避免协调服务故障后无法恢复。
- 路由错误需要可观测，记录请求键、期望分区与实际节点。

### 10.12 热点键如何产生？

- 单一键的访问量远超其他键，例如明星账号或爆款商品。
- 单调递增键使写入集中到最后一个分区，形成写热点。
- 数据分布本身倾斜，例如按地区分区但某地区用户占多数。
- 查询模式集中，例如全表统计频繁命中同一分区。
- 分区数少或粒度过粗，热点无法拆分到多个节点。
- 缓存与批量任务会在特定时间放大热点。

### 10.13 热点键有哪些缓解手段？

- 键加盐，在键前拼接随机前缀，把一个逻辑键拆成多个物理键。
- 前缀数量按读写需要选择，读取时需要合并多个前缀的结果。
- 为热点键单独建分区或独立表，避免影响同一分区的其他键。
- 应用层缓存热点数据，减少对存储层的重复读。
- 写热点可用批量缓冲与异步合并，把随机写转为顺序写。
- 加盐增加读放大与聚合成本，应按热点程度选择性使用。

### 10.14（场景）单调递增键为什么不适合直接做分区键？

- 按范围分区时新写入总是落在最后一个分区，其他分区空闲。
- 按哈希分区时分布可能均匀，但范围查询失效。
- 时间戳、自增 ID 与雪花 ID 都有类似问题，取决于分区方式。
- 常见做法是时间前缀加哈希后缀，或按时间分表后再哈希。
- 写入热点使单节点磁盘与日志压力集中，尾延迟上升。
- 若查询以时间范围为主，可保留时间维度并配合预分区与限速。

### 10.15 分区键应如何选择？

- 高基数、分布均匀、写入分散是基本要求。
- 应与高频查询条件一致，使多数查询能定位到单个分区。
- 需要稳定，业务变化不应导致大量数据重分布。
- 避免包含可变字段，例如状态、余额与更新时间。
- 复合键可把租户 ID 与业务 ID 组合，兼顾隔离与路由。
- 选择前统计真实数据分布与查询比例，不能只按表结构推断。

### 10.16（估算）跨分区查询的代价如何估算？

- 广播查询的延迟由最慢分区决定，分区数增加会放大尾延迟。
- 网络往返次数与分区数成正比，聚合需要在协调节点合并。
- 跨分区事务需要两阶段提交或类似协议，持有锁的时间更长。
- 结果集需要在内存中归并，分页与排序的代价随分区数上升。
- 跨分区写入失败时需要补偿或重试，幂等设计必不可少。
- 估算应以 P99 而非均值衡量，热点分区会主导尾延迟。

### 10.17 分区数量与并行度是什么关系？

- 分区是并行与迁移的单位，并行度受分区数与节点数共同限制。
- 分区数少于节点数时部分节点空闲，资源利用不足。
- 分区数远多于节点数时单分区数据量小，扫描与聚合的固定开销占比上升。
- 每个分区对应独立的日志、快照与文件句柄，数量过多会消耗内存。
- 查询并行度可按分区切分，协调节点的合并能力会成为瓶颈。
- 分区数应在容量、并行度与元数据开销之间取平衡。

### 10.18 迁移期间如何保证读写正确？

- 迁移按分区整体进行，先全量复制，再追增量，最后原子切换。
- 切换前源节点仍接受写入，目标节点回放增量日志直至追平。
- 切换瞬间需要短暂停写或按版本判定，避免双写冲突。
- 读请求在切换窗口内可能命中旧副本，需要按映射版本重定向。
- 迁移完成后保留源数据一段时间作为回滚窗口。
- 校验包括行数、校验和与抽样比对，差异需要可重放修复。

### 10.19 如何度量分区是否均衡？

- 统计每个分区的字节数、行数、读写 QPS 与 P99 延迟。
- 用最大值与中位数之比衡量倾斜，比值持续偏高说明需要调整。
- 关注热点键的请求占比，单一键超过阈值时应单独处理。
- 监控迁移队列长度与再平衡耗时，避免迁移成为常态。
- 按时间窗口观察分布变化，区分短期突发与长期倾斜。
- 指标需要下钻到键级别，聚合值会掩盖单键热点。

### 10.20（设计）如何验证分区方案？

- 用真实数据分布回放写入，观察各分区增长速率是否一致。
- 构造热点键与单调键，验证加盐与预分区策略是否生效。
- 注入节点故障与网络分区，检查路由切换与重试是否正确。
- 模拟扩容，测量迁移数据量、迁移时长与业务延迟影响。
- 校验跨分区查询的 P99，确认广播与归并成本可接受。
- 记录路由错误率与重试次数，作为方案上线的判据。

## 11. 分区与二级索引

### 11.1 本地索引与全局索引有什么区别？

- 本地索引与数据在同一分区，索引项只覆盖本分区记录，写入只影响单个分区。
- 全局索引按索引项自身分区，一条索引项可指向任意分区中的记录。
- 本地索引又称文档分区索引，全局索引又称词条分区索引。
- 本地索引写入简单，读取需要合并多个分区。
- 全局索引读取只需访问一个索引分区，写入需要更新多个分区。
- 选择取决于读写比例、查询是否需要跨分区扫描以及一致性要求。

### 11.2 本地索引的写入路径是什么？

- 写入先落主分区，再在同一分区内更新索引项。
- 主数据与索引通常在同一批操作中提交，可用本地事务保证一致。
- 分区再平衡时索引随主数据一起迁移，迁移是自包含的。
- 删除与更新只涉及本分区，不需要跨节点协调。
- 写入吞吐随分区数扩展，不存在全局索引的写放大。
- 代价是查询必须访问所有分区，即使只命中少量结果。

### 11.3 本地索引的查询为什么需要 scatter/gather？

- 查询条件不含分区键时，无法判断哪些分区包含匹配项。
- 协调节点向所有分区下发查询，各分区本地检索并返回候选。
- 协调节点归并、排序并截断结果，再返回客户端。
- 查询延迟取决于分区数、并行度与最慢分区的响应时间。
- 可通过并行下发、超时兜底与结果上限控制成本。
- 若查询条件包含分区键，可退化为单分区查询。

```cpp
std::vector<Row> search_all(const Query& q) {
    std::vector<std::future<std::vector<Row>>> fs;
    for (auto& part : partitions) {
        fs.push_back(pool.submit([&part, &q] { return part.search(q); }));
    }
    std::vector<Row> out;
    for (auto& f : fs) {
        append(out, f.get());
    }
    return top_k(std::move(out), q.limit);
}
```

### 11.4 全局索引的写入代价是什么？

- 一次主数据写入需要更新一个或多个索引分区，形成跨分区写。
- 索引更新与主数据更新难以放在同一本地事务中。
- 异步更新存在窗口期，索引可能落后于主数据。
- 索引分区与被索引记录所在分区不同，失败时需要重试与补偿。
- 写放大与跨分区网络往返使写入延迟上升。
- 索引更新放大还会挤占主数据写入的带宽与连接池。

### 11.5 全局索引如何与主数据保持一致？

- 同步方案使用跨分区事务或两阶段提交，一致性强但延迟与阻塞成本高。
- 异步方案通过日志订阅或消息队列投递索引更新，达到最终一致。
- 异步方案需要按主键保序，否则旧版本可能覆盖新版本。
- 重试需要幂等，索引写入以主键加版本号做条件更新。
- 对账任务定期比对索引与主数据，修复缺失与陈旧项。
- 业务需要明确可接受的一致性窗口，并据此选择方案。

### 11.6 全局索引的查询如何路由？

- 按索引列的值计算目标索引分区，只需访问该分区。
- 索引分区返回主键或记录位置，再按主键回表。
- 回表可能跨分区，需要按主键批量读取并缓存。
- 若索引项包含查询所需列，可避免回表。
- 索引分区映射同样需要版本化，客户端缓存过期会错路由。
- 查询涉及多个索引列时，可能需要多次路由并对结果求交。

### 11.7 索引分区按散列还是按值划分？

- 按值分区使等值查询定位到单个分区，但热点值会集中。
- 按散列分区使索引项分布均匀，范围查询需要广播。
- 按文档主键分区会退化为本地索引，查询需要扫描全部分区。
- 复合索引可把高频前缀作为分区键，其余列作为分区内排序键。
- 分区键基数过低会导致倾斜，例如按状态或地区划分。
- 选择需要同时考虑查询模式、写入放大与倾斜风险。

### 11.8（场景）热词为什么会让全局索引倾斜？

- 全局索引按词条分区，热门词条的全部索引项集中到一个分区。
- 该分区的读写量、存储量与连接数远超其他分区。
- 热词查询的并发会打满单分区 CPU 与网络。
- 缓解方式是把热词索引项再散列到多个子分区，查询时合并。
- 也可为热词单独缓存，或使用独立的检索集群。
- 子分区数量需要按访问量调整，固定值难以适应突发。

### 11.9 二级索引的唯一约束如何跨分区保证？

- 唯一约束要求全局唯一，单个本地索引无法判定。
- 常见做法是把唯一键本身作为分区键，使同一键落到同一分区。
- 或者由独立服务、分布式锁或协调者串行化冲突写入。
- 以唯一键分区会让索引按值分布，范围查询与热词问题加剧。
- 冲突写入需要明确失败语义，返回唯一键冲突而不是静默覆盖。
- 跨分区事务不可用时，通常退化为唯一键分区并对账补救。

### 11.10 索引更新失败如何恢复？

- 记录索引更新的位点或版本，失败后从位点重放。
- 索引写入幂等，重复应用同一版本不产生额外影响。
- 使用死信队列隔离持续失败的记录，避免阻塞整体进度。
- 对账任务按时间窗口比对主数据与索引，生成修复任务。
- 修复任务需要限速，避免再次压垮索引分区。
- 监控索引落后时间与失败率，作为一致性达标的指标。

### 11.11 覆盖索引在分区下有什么问题？

- 覆盖索引把查询所需列都放进索引，避免回表。
- 本地索引的覆盖查询仍需访问所有分区并归并。
- 全局索引的覆盖查询可单分区完成，但索引体积增大。
- 索引列越多，写入放大与存储成本越高。
- 跨分区回表带来额外网络往返，覆盖索引可减少这类开销。
- 需要权衡索引宽度与查询覆盖率，避免为少数查询建宽索引。

### 11.12 分区索引如何支持排序与分页？

- 本地索引下，各分区返回排序后的前 N 项，协调节点做堆归并。
- 每个分区需要返回偏移加页大小的行，深分页成本随页码上升。
- 全局索引可按排序键分区，使排序在单分区内完成，但范围查询受限。
- 游标分页以排序键为游标，各分区返回大于游标的前 N 项再归并。
- 排序键需要全局可比，避免时区与精度差异导致顺序不一致。
- 数据变动时分页结果可能重复或遗漏，需要快照或稳定排序键。

### 11.13 全文检索的倒排索引如何分区？

- 按词条分区使单个词的倒排列表集中，查询只需访问相关分区。
- 按文档分区使写入本地化，查询需要访问所有分区并合并评分。
- 按词条分区适合查询为主、写入较少的场景，热词问题突出。
- 按文档分区适合写入吞吐高、查询可并行的场景。
- 混合方案按文档分区并在分区内建本地倒排，查询时归并。
- 评分与截断需要全局统一，否则各分区结果不可比。

### 11.14（估算）本地索引的读放大如何估算？

- 读放大近似等于分区数乘以单分区查询成本，再叠加归并成本。
- 分区数从 10 增到 100 时，单次查询的网络往返与 CPU 消耗近似增加十倍。
- 命中率低时多数分区返回空结果，仍消耗连接与调度资源。
- 并行下发受连接池与线程数限制，实际并行度低于分区数。
- 少数慢分区会主导尾延迟，均值无法反映用户感知。
- 可通过分区裁剪、二级路由与缓存降低有效分区数。

### 11.15 索引与主数据不一致的业务影响如何评估？

- 区分读路径是否依赖索引，列表页、搜索页与报表的影响不同。
- 评估不一致窗口的长度与业务可接受的陈旧程度。
- 对账发现差异后能否自动修复，修复是否会二次伤害。
- 唯一约束类索引不一致会导致重复注册等业务错误。
- 需要定义降级策略，例如索引不可用时回退全表扫描或返回缓存。
- 记录不一致样本，作为调整同步机制的输入。

### 11.16 二级索引能否避免跨分区查询？

- 只有查询条件包含索引分区键时才能定位单分区。
- 全局索引把查询路由到索引分区，但仍需回表取主数据。
- 回表可能跨分区，需要额外的批量读取与缓存。
- 本地索引无法避免跨分区，除非查询带上主数据分区键。
- 物化视图可预先聚合常用查询结果，减少跨分区访问。
- 是否值得取决于查询频率与数据变更频率的比值。

### 11.17 索引再平衡与主数据再平衡有何不同？

- 主数据再平衡迁移整段数据，本地索引随主数据一起移动。
- 全局索引再平衡只迁移索引项，主数据位置不变。
- 索引项通常小于主数据，迁移量小但条目多，元数据压力大。
- 迁移期间索引更新需要双写或按版本路由，避免丢失更新。
- 索引分区过小会导致频繁合并，过大则迁移时间长。
- 两者需要独立调度，避免同时搬运造成带宽争抢。

### 11.18 如何检测索引倾斜？

- 统计各索引分区的项数、字节数与查询 QPS。
- 观察热词占比，单一词条的查询比例超过阈值即需处理。
- 监控索引分区的 P99 延迟与错误率，识别单点瓶颈。
- 对比索引项数与主数据行数，比例异常说明缺失或冗余。
- 按时间窗口观察倾斜是否随事件突增，区分常态与峰值。
- 指标需要支持按词条下钻，聚合值会掩盖单点。

### 11.19 索引维护如何控制写放大？

- 只索引实际查询用到的列，避免为潜在需求建索引。
- 合并批量更新，减少同一索引项的重复写入。
- 异步构建索引，把写放大从请求路径移到后台。
- 对低基数列使用位图或分区裁剪，而不是逐行索引。
- 定期清理无用索引，索引数量与写入成本近似线性相关。
- 用写放大系数与索引命中率评估每个索引的收益。

### 11.20（设计）如何验证分区索引方案？

- 用真实查询日志统计带分区键与不带分区键的比例。
- 压测广播查询，观察分区数增加时的 P99 变化。
- 注入索引更新失败，验证重试、死信与对账是否闭环。
- 模拟热词突发，检查索引分区是否成为瓶颈。
- 扩容测试索引迁移，测量迁移期间的查询错误率。
- 对比索引与主数据的抽样校验结果，确认一致性窗口符合预期。

## 12. 事务与隔离级别

### 12.1 隔离性究竟承诺什么？

- 隔离性描述并发事务之间的可见性，不规定事务的物理执行顺序。
- 不同隔离级别对应不同的异常集合，承诺越强并发代价越高。
- 标准中的级别是下限，具体行为由实现定义。
- 隔离性只约束数据库内的读写可见性，不覆盖外部副作用。
- 应用若同时操作系统之外的组件，隔离性无法保证跨系统一致。
- 选择级别需要结合业务对异常的容忍度与冲突率。

| 级别 | 避免的异常 | 仍可能出现的异常 |
| --- | --- | --- |
| 读已提交 | 脏读、脏写 | 不可重复读、幻读、丢失更新、写偏斜 |
| 快照隔离 | 不可重复读、读侧幻读 | 写偏斜 |
| 可串行化 | 上述全部 | 无，代价是中止与重试 |

### 12.2 读已提交如何实现？

- 写操作加行锁并持有到事务提交，防止脏写。
- 读操作读取语句开始时已提交的最新版本，不等待写锁，通常由多版本并发控制实现。
- 每条语句看到语句开始时刻已提交的数据，语句之间可能变化。
- 同一事务内两次读取可能得到不同结果，即不可重复读。
- 读已提交不防止丢失更新与写偏斜。
- 实现需要维护版本链与可见性判断，旧版本由清理机制回收。

### 12.3 读已提交下为什么允许不可重复读？

- 该级别只承诺不读到未提交数据，不承诺事务内读取稳定。
- 每次查询取当前已提交快照，其他事务提交后立即可见。
- 允许不可重复读降低了版本保留与冲突检测的成本。
- 对报表与对账逻辑，前后统计口径可能不一致。
- 需要稳定读取时应使用快照隔离或显式加锁。
- 不可重复读是同一行的值变化，幻读是结果集行数变化。

### 12.4 快照隔离如何实现？

- 事务开始时获取快照，通常是递增的事务 ID 或时间戳。
- 读取按可见性规则选择版本，只看到快照之前提交的版本。
- 写入创建新版本，旧版本保留供并发读使用。
- 提交时只检查写写冲突，不检查读写冲突。
- 清理机制删除不再可见的旧版本，长事务会阻止清理。
- 快照隔离避免不可重复读，但不保证可串行化。

```cpp
bool visible(std::uint64_t snapshot, const Version& v) {
    return v.commit_ts < snapshot;
}
```

### 12.5 快照隔离与可重复读是什么关系？

- 快照隔离提供事务级一致的读取视图，同一事务内多次读取结果稳定。
- 可重复读在不同实现中语义不同，部分实现等同快照隔离。
- 部分实现的可重复读只锁住已读行，不提供事务级快照。
- SQL 标准未精确定义可重复读的异常集合，行为由实现定义。
- 需要严格串行化语义时应显式选择可串行化，不能依赖级别名称。
- 迁移数据库时需要核对具体实现的可见性规则。

### 12.6 丢失更新在哪些场景下仍会发生？

- 读已提交下，两个事务读取同一行后各自写回，后提交者覆盖前者。
- 基于多版本读的可重复读若不在写入时检查版本，也会出现同样的覆盖。
- 严格快照隔离通常在写写冲突时中止后提交的事务，单库内不会静默丢失，但应用必须处理中止。
- 读-改-写跨越服务或数据库时，任何单库的冲突检测都无法覆盖。
- 写入整行而不是只写变化列，会扩大覆盖范围，未修改字段上的并发修改也会丢失。
- 原子写、条件更新与行锁可以在写入路径消除这类问题。

### 12.7（场景）什么是写偏斜？

- 两个事务读取不同的行，写入时依赖彼此读取的结果。
- 各自检查通过，提交后合并结果违反业务约束。
- 经典例子是值班医生：两人同时查询在岗人数，各自认为还有替补，于是同时请假。
- 写偏斜不是丢失更新，两个事务写的是不同行。
- 快照隔离无法检测这类读写冲突，需要可串行化。
- 物化冲突或显式锁可以缓解，前提是业务约束可以物化。

### 12.8 写偏斜与幻读有什么区别？

- 幻读是同一查询在事务内返回不同的行集合，由其他事务插入或删除引起。
- 写偏斜是并发事务基于各自读取结果做出写入决策，破坏联合约束。
- 幻读可通过范围锁或谓词锁避免。
- 两个事务写入不同的行，行级写锁不会冲突，范围锁也未必覆盖。
- 两者都涉及读取集合的变化，但写偏斜的根源是决策依赖。
- 可串行化能同时排除两类异常，快照隔离对两者都不完全保证。

### 12.9 幻读在快照隔离下还会出现吗？

- 快照隔离的读取视图固定，事务内重复查询不会看到新插入的行。
- 因此读侧幻读被消除。
- 但写入时若基于快照判断不存在则插入，并发插入仍可能产生重复。
- 唯一约束可以在数据库层拦截重复，业务约束未必有唯一索引。
- 谓词锁与可串行化可在写入路径检测这类冲突。
- 是否出现取决于实现是否在提交时检查读写冲突，由实现定义。

### 12.10 可串行化有哪些实现方式？

- 两阶段锁，读加共享锁，写加排他锁，锁持有到提交，冲突时阻塞。
- 串行化快照隔离，在快照隔离基础上检测读写冲突，冲突时中止。
- 串行执行，单线程依次执行事务，适合内存数据库与短事务。
- 乐观并发控制，提交时校验读集是否被修改，冲突则重试。
- 各方式在阻塞、中止率与吞吐上取舍不同。
- 实现可以组合多种机制，具体语义由实现定义。

### 12.11 两阶段锁的死锁如何检测？

- 事务等待锁时形成等待图，图中出现环即死锁。
- 检测器周期性遍历等待图，选择牺牲者回滚以打破环。
- 也可用超时机制粗粒度处理，但会误杀长事务。
- 锁顺序约定可减少死锁，例如按主键顺序更新。
- 死锁回滚后应用需要重试整个事务，而不是单条语句。
- 监控死锁频率与牺牲者分布，定位不合理的访问顺序。

### 12.12 串行化快照隔离的中止率由什么决定？

- 并发事务读写集合的重叠程度越高，危险结构越容易出现。
- 事务越长、读取范围越广，与其他事务交错的机会越多。
- 全表扫描会被记录为大范围谓词，显著提高冲突概率。
- 检测粒度过粗会产生误判，把本来可串行化的执行也中止。
- 应用重试会放大负载，形成中止与重试的循环。
- 降低中止率的手段包括缩短事务、分批提交与为查询建立合适索引。

### 12.13 串行化失败后应如何重试？

- 重试必须覆盖整个事务，包括读取与业务计算。
- 事务需要幂等，避免重试导致重复副作用。
- 设置最大重试次数与退避，避免大量冲突同时重试。
- 区分可重试错误与永久错误，约束冲突不应无限重试。
- 长事务与大批量写入会提高冲突概率，应缩短事务。
- 记录重试率，作为隔离级别与访问模式是否合理的指标。

### 12.14 隔离级别如何与复制交互？

- 从副本读取可能读到旧数据，破坏读己之写与单调读。
- 快照隔离的快照若来自主库，从库回放延迟会导致跨副本不一致。
- 读写分离下需要按会话固定读主库，或等待复制位点。
- 跨分区事务在副本上无法获得全局快照。
- 复制延迟与隔离级别叠加，可能出现事务内读到不同版本。
- 需要明确一致性保证是单副本内还是跨副本。

### 12.15 只读事务能否避免一致性异常？

- 只读事务不写数据，不会产生写偏斜与丢失更新。
- 但它仍可能读到不一致的快照，例如跨分区读取不同时间点。
- 长时间持有可能阻止旧版本清理。
- 在串行化快照隔离下只读事务也可能被中止。
- 需要一致快照时应显式声明只读并获取快照。
- 只读不等于无副作用，外部调用与缓存写入仍需考虑。

### 12.16 数据库约束能否替代可串行化？

- 唯一约束、外键与检查约束能在行级或约束覆盖的范围内拦截部分冲突。
- 约束由数据库在写入时检查，通常借助索引或锁实现。
- 跨行的聚合约束无法用普通约束表达。
- 触发器可实现部分检查，但并发下仍可能读到过期状态。
- 物化冲突把聚合约束转成唯一约束，是有条件的替代方案。
- 约束是最后防线，业务逻辑仍需处理约束冲突的错误。

### 12.17 长事务有什么代价？

- 持有锁或旧版本，阻塞其他事务并推迟清理。
- 多版本机制下旧版本无法回收，存储膨胀，扫描版本链变慢。
- 日志与复制流膨胀，从库回放压力增加。
- 事务超时与重试会放大冲突，形成循环。
- 事务内的外部调用会延长持锁时间，应移出事务。
- 批量任务应拆分为小事务，并控制每批行数。

### 12.18（陷阱）隔离级别名称相同是否语义相同？

- SQL 标准只规定最低要求，各实现可提供更强保证。
- 部分数据库的可重复读实际是快照隔离，部分实现则加锁读。
- 默认级别不同，迁移前需要核对文档与实测行为。
- 同一数据库的不同版本也可能调整实现。
- 应用不应依赖级别名称推断异常集合，应写明依赖的具体行为。
- 需要可移植性时显式使用锁或可串行化，并准备重试逻辑。

### 12.19（设计）如何测试隔离级别的实际行为？

- 构造两个并发会话，按固定顺序执行读写并观察可见性。
- 覆盖脏读、不可重复读、幻读、丢失更新与写偏斜五类异常。
- 使用屏障控制提交顺序，避免结果依赖调度。
- 记录数据库版本与配置，隔离行为由实现定义。
- 对写偏斜需要构造读取不同行、写入不同行的场景。
- 测试应纳入回归，升级数据库后重新执行。

### 12.20 隔离级别与业务补偿如何配合？

- 强隔离降低异常概率，但增加冲突与重试成本。
- 弱隔离需要业务层补偿，例如对账、冲正与幂等重放。
- 补偿逻辑本身需要幂等，且能识别重复补偿。
- 跨系统操作无法纳入数据库事务，只能依赖最终一致。
- 取舍在于异常的业务代价与补偿的实现成本。
- 应记录不一致事件并度量其频率，避免默认其不会发生。

## 13. 并发写冲突

### 13.1 丢失更新有哪两种形态？

- 读-改-写：先读取值，在应用层计算，再写回，覆盖并发更新。
- 盲写：不读取旧值，直接写入完整行，覆盖其他事务的修改。
- 读-改-写在计数器、余额与库存场景常见。
- 盲写在按整行更新时常见，未修改的列也可能被覆盖。
- 两种形态都源于写入未检测版本或未加锁。
- 原子写与条件更新可分别处理两类问题。

### 13.2 比较并交换（CAS）如何避免丢失更新？

- 读取时同时取版本号，写入时以版本号作为条件。
- 数据库执行条件更新，版本不匹配或业务前提不满足时影响行数为零。
- 应用检查影响行数，为零时重新读取并决定是否重试。
- 比较并交换是无锁的乐观方案，冲突少时吞吐高。
- 高冲突下重试次数上升，需要退避与重试上限。
- 版本号需要单调递增，且所有写入路径都必须携带。

```cpp
// 返回受影响行数，0 表示版本冲突或余额不足
int deduct(Db& db, int id, long amount, int version) {
    return db.exec(
        "UPDATE account SET balance = balance - ?, version = version + 1 "
        "WHERE id = ? AND version = ? AND balance >= ?",
        amount, id, version, amount);
}
```

### 13.3 乐观锁的失败路径如何设计？

- 冲突时返回明确错误，由上层决定重试、合并或提示。
- 重试需要重新读取最新状态并重新计算，不能直接重放旧值。
- 对用户交互场景，冲突应提示而不是静默覆盖。
- 对后台任务，可自动重试有限次数并记录冲突率。
- 版本号与业务字段在同一行，条件更新可以在一条语句内完成校验与写入。
- 高冲突业务可改为悲观锁或可串行化，避免无效重试累积。

### 13.4 悲观锁的边界在哪里？

- `SELECT ... FOR UPDATE` 在事务内锁定目标行，阻塞其他写。
- 锁只在事务内有效，事务结束即释放。
- 锁顺序不一致会导致死锁，需要约定访问顺序。
- 锁粒度过大会降低并发，过小则可能漏锁。
- 长事务持锁会放大阻塞，外部调用应移出临界区。
- 悲观锁适合冲突率高且重试代价大的场景。

### 13.5（辨析）写偏斜与丢失更新有什么区别？

- 丢失更新是两个事务写同一行，后写覆盖先写。
- 写偏斜是两个事务写不同行，但决策依赖彼此读取的集合。
- 丢失更新可用行锁或比较并交换解决。
- 写偏斜需要可串行化、谓词锁或物化冲突。
- 写偏斜的写入互不冲突，数据库的写写冲突检测不会触发。
- 业务约束越复杂，写偏斜越难用单行机制防御。

### 13.6 什么是物化冲突？

- 把无法直接用行锁表达的约束，物化为一行或一张表的记录。
- 对该物化记录加锁或写唯一键，使并发事务被迫串行。
- 例如会议室预订：为每个时间段建一行，预订时插入或加锁。
- 物化冲突把谓词冲突转成写写冲突，便于数据库检测。
- 需要预先建好物化结构，并覆盖所有可能的维度组合。
- 物化结构本身成为热点，写入吞吐受限。

### 13.7 物化冲突如何实现？

- 建立冲突槽位表，主键由约束维度组合而成。
- 事务在写入业务数据前，先对槽位行加锁或插入。
- 唯一约束冲突即表示并发冲突，捕获后重试或拒绝。
- 槽位需要与业务数据同事务提交，避免锁提前释放。
- 槽位数量决定可表达的约束粒度，过粗会误伤。
- 清理机制需要处理历史槽位，避免无限增长。

### 13.8 物化冲突的代价是什么？

- 槽位行成为热点，所有相关写入串行化。
- 槽位表的写入与锁竞争会限制吞吐。
- 约束维度组合爆炸时，槽位数量难以控制。
- 跨分区部署时槽位与业务数据可能不在同一分区。
- 物化结构需要与业务规则同步演进。
- 适用于冲突概率低但后果严重的约束，不适合高频写入。

### 13.9 写偏斜能否用唯一约束解决？

- 唯一约束只能表达值不重复，不能表达聚合数量。
- 若约束可转化为唯一键，例如同一时段只能有一条预订，可以。
- 若约束是至少两人在岗，需要先物化为计数行或槽位。
- 直接对业务表加唯一索引通常无法覆盖跨行条件。
- 触发器在并发下仍可能读到过期状态。
- 可串行化是通用方案，物化冲突是针对性方案。

### 13.10 可串行化冲突与死锁有什么区别？

- 死锁是事务互相等待锁，形成环，必须回滚其中一个。
- 可串行化冲突是执行顺序无法对应任何串行顺序，需要中止。
- 串行化快照隔离下冲突通常不阻塞，直接中止后重试。
- 两阶段锁下冲突表现为阻塞，可能进一步演化为死锁。
- 死锁可通过锁顺序避免，串行化冲突不能靠顺序消除。
- 监控指标不同，死锁率与串行化失败率应分别统计。

### 13.11 串行化快照隔离的读写冲突如何判定？

- 记录事务读取的键集合与写入的键集合。
- 若事务 A 读取的键被并发事务 B 写入，且 B 先提交，则 A 可能读到旧值。
- 若 A 的写入影响 B 的读取结果，也构成危险结构。
- 检测到危险结构时中止其中一个事务。
- 判定依赖索引与谓词范围，范围扫描会被记录为谓词锁。
- 误判会增加中止率，需要调优检测粒度。

### 13.12（场景）冲突重试如何保证幂等？

- 事务内的副作用，例如发消息与调用外部接口，不能随重试重复执行。
- 使用幂等键或去重表，确保同一业务操作只生效一次。
- 消息发送放在事务提交后，或使用事务消息与发件箱模式。
- 重试前重新读取状态，避免基于旧值再次计算。
- 记录重试次数与最终结果，便于排查。
- 幂等键需要与业务唯一标识绑定，不能使用随机值。

### 13.13 冲突检测的粒度如何选择？

- 行级检测精确但元数据多，页级与表级检测粗但开销小。
- 粒度越粗，误判越多，重试率越高。
- 索引范围检测需要记录谓词，范围越大越容易冲突。
- 热点行集中时行级锁也会形成排队。
- 检测粒度通常由实现决定，应用只能通过访问模式影响。
- 缩小事务范围与访问集合可降低冲突概率。

### 13.14 分布式环境下比较并交换如何实现？

- 以外部协调服务中的版本号或租约作为比较条件。
- 比较并交换在单个键上原子执行，成功即获得写权限。
- 跨多个键的原子更新需要事务接口或两阶段协议。
- 网络分区下操作可能超时，结果不确定，需要按业务键查询确认。
- 租约过期会导致锁失效，业务需要隔离令牌（fencing token）防止旧持有者写入。
- 分布式比较并交换的延迟高于本地数据库，适合低频关键路径。

### 13.15 队列能否消除并发冲突？

- 单分区队列保证同一键的消息按顺序处理，天然串行化。
- 消费者单线程处理同一键，避免并发写同一行。
- 分区数决定并行度，键分布不均会导致消费倾斜。
- 处理失败与重试会破坏顺序，需要按键的失败队列。
- 队列只能串行化同一键，跨键约束仍需数据库保证。
- 端到端延迟增加，适合异步业务而非同步接口。

### 13.16 业务层如何解决冲突？

- 合并策略，对可交换的操作直接合并，例如计数与集合添加。
- 优先级策略，按时间戳、角色或版本决定胜者。
- 人工介入，冲突无法自动解决时进入待处理队列。
- 冲突解决需要可追溯，记录双方版本与决策依据。
- 合并结果需要满足业务不变量，否则仍需回滚。
- 解决策略应尽量前移到写入路径，减少事后修复。

### 13.17（估算）如何度量并发冲突？

- 统计条件更新影响行数为零的比例。
- 统计事务中止率与重试次数，按业务接口区分。
- 监控锁等待时间与死锁次数。
- 统计同一行的并发写入峰值，识别热点。
- 冲突率与吞吐、延迟一起观察，避免只看单一指标。
- 指标需要按时间窗口与业务键下钻。

### 13.18 冲突与复制延迟如何相互影响？

- 多副本写入时，不同副本可能基于不同版本做决策。
- 主库串行化不代表从库读取时仍一致。
- 读写分离下，读到的旧值会引发错误决策与冲突。
- 需要读己之写时，应读主库或等待复制位点。
- 多主复制下冲突检测需要版本向量或类似机制。
- 冲突解决结果需要收敛，否则副本永久不一致。

### 13.19 如何复现并发写冲突？

- 使用两个以上会话，按脚本控制读取与提交顺序。
- 在读取与写入之间插入屏障，稳定复现交错。
- 对比较并交换场景，并发提交同一版本，断言只有一个成功。
- 对写偏斜，构造读取不同行、写入不同行的用例。
- 反复运行并统计失败次数，确认修复有效。
- 测试环境需要与生产一致的隔离级别与索引。

### 13.20（设计）高频计数器如何选择并发控制方案？

- 单行原子递增适合低冲突场景，数据库以行锁串行化同一行的更新。
- 条件更新可附带阈值判断，例如余额充足才扣减。
- 高并发热点可拆分为多个计数桶，读取时求和。
- 分桶写入分散竞争，但读取需要聚合多个行。
- 允许近似值时可用异步批量合并，把多次更新压缩为一次。
- 需要精确值且冲突极高时，串行化或单分区队列更可控。

## 14. 分布式系统的麻烦

### 14.1（辨析）分布式系统与单机程序的根本差别是什么？

- 单机程序面对的是整体失效：进程崩溃、内存耗尽、磁盘写满，失效时进程消失，调用方立刻得到错误。
- 分布式系统的单个节点可以在继续运行的同时丢消息、延迟、乱序，这种部分失效（partial failure）对调用方不可见，只能靠超时推断。
- 部分失效使「成功」与「失败」之间出现第三种状态：结果未知。系统必须在结果未知时仍然维持不变量。
- 节点规模上升后，任意时刻至少有一个节点处于异常状态成为常态，设计目标从避免失效转为在失效中保持正确。
- 单机上「先写 A 再写 B」的先后关系在分布式系统中不自动成立，需要显式的因果关系或协调。
- 不可靠组件叠加后，端到端可靠性由最弱环节与重试策略共同决定，而不是由单个组件的标称可靠性决定。

### 14.2 网络请求超时后为什么无法判断请求是否成功？

- 超时只说明在给定时间内未收到响应；响应可能仍在网络中、服务端可能仍在处理、也可能已经完成但响应丢失。
- 三种情况对调用方不可区分：请求未到达、请求到达但处理失败、请求成功但响应丢失。
- 因此超时后的重试必须是幂等的，否则会重复执行副作用。
- 增大超时只降低误判概率，不能消除；概率随网络延迟的长尾分布变化。
- 判断真实结果需要额外机制：按请求 ID 查询状态、使用幂等键、或由服务端提供可对账的操作记录。
- 工程上超时值按延迟分位数选取，并接受一定比例的误判，而不是追求零误判。

### 14.3（陷阱）TCP 提供的可靠性为什么不足以支撑分布式语义？

- TCP 保证字节流的有序与去重，作用范围仅限一条连接的两个端点之间。
- 连接断开后，已写入内核缓冲区但未送达的数据会丢失，应用层无法知道哪些字节被对端处理。
- TCP 的重传与确认发生在传输层，应用层处理失败（例如写数据库失败）不会被 TCP 感知。
- 负载均衡器、代理与 NAT 会引入额外缓冲与超时，连接存活不代表对端进程存活。
- 因此「TCP 可靠」只消除了网络层的丢包与乱序，没有消除部分失效。
- 应用层仍需请求 ID、幂等处理与明确的提交语义。

### 14.4（场景）同步网络与异步网络的假设分别导致什么设计差异？

- 同步网络模型假设消息延迟有固定上界，超时即可判定节点失效，协调问题退化为可判定问题。
- 异步网络模型不假设任何时间上界，超时无法区分「节点慢」与「节点失效」，这是 FLP 结论的前提。
- 真实数据中心接近同步但存在长尾：交换机排队、GC、虚拟化调度都会造成毫秒到秒级的抖动。
- 工程折中是把时间假设写进协议：租约、心跳超时、选举超时都依赖「时钟误差有界」。
- 假设被打破时协议不会报错，而是可能同时出现两个自认为有效的领导者，因此假设需要显式记录并监控。
- 部分同步模型是多数共识算法实际采用的假设：系统大部分时间同步，但上界未知。

### 14.5 时钟漂移与时钟偏移分别指什么？

- 时钟漂移（clock drift）指单个时钟相对理想时间的速率误差，石英晶振的典型量级是 10 到 100 ppm。
- 时钟偏移（clock skew）指两个时钟在同一时刻的读数之差，是漂移随时间累积的结果。
- 漂移不可消除，只能借助外部时间源校正；校正会引入跳变，可能使读数倒退。
- 偏移在跨节点比较时间戳时直接影响判断：两个节点的时间戳先后不表示事件先后。
- 温度、电压与器件老化都会改变漂移率，固定补偿值无法长期有效。
- 100 ppm 的漂移在一天内可累积约 8.6 秒，足以让基于时间戳的冲突判定失效。

### 14.6（陷阱）为什么不能用墙上时钟测量时间间隔？

- 墙上时钟（wall-clock time）返回日历时间，会被 NTP 向前或向后调整，测量间隔时可能得到负值。
- 闰秒、时区变更与手动校时都会造成跳变，进程无法感知跳变发生。
- 比较两个节点的时间戳会受到偏移影响，先后关系不可靠。
- 测量耗时、超时、租约续期应使用单调时钟（monotonic clock），它只保证单调不减。
- 单调时钟的起点由实现定义，跨进程、跨机器不可比较，不能写入日志用于跨机排序。
- 需要跨机排序时使用逻辑时钟或版本号，而不是把单调时钟读数发给对端。

```cpp
#include <chrono>

auto t0 = std::chrono::steady_clock::now();
do_request();
auto dt = std::chrono::steady_clock::now() - t0;  // 单调，不受校时影响

auto wall = std::chrono::system_clock::now();     // 仅用于记录时间点
```

### 14.7 单调时钟适合哪些用途，边界在哪里？

- 适合测量时间间隔：请求耗时、超时判定、重试退避、租约剩余时间。
- 适合在同一进程内比较事件先后，不依赖系统时间是否正确。
- 不适合作为时间戳写入持久化数据，重启后起点可能变化，由实现定义。
- 不适合跨进程或跨机器比较，不同机器的单调时钟互相独立。
- 部分系统在挂起（suspend）期间停止单调时钟，导致间隔被低估。
- 单调时钟的精度受计时器分辨率限制，纳秒级读数不表示纳秒级精度。

### 14.8 NTP 校时为什么会引入跳变？

- NTP 客户端会逐步调整频率（slewing）或直接设置时间（stepping），后者造成读数跳变。
- 跳变可能使时间倒退，基于「时间戳递增」的假设失效，例如按时间排序的日志出现乱序。
- 校时源本身可能错误，错误的权威时间源会把偏差传播到整个集群。
- 网络路径不对称会引入偏差，往返延迟的一半不等于单向延迟。
- 虚拟机与容器的时钟受宿主机调度影响，校时精度低于物理机。
- 规避方式是业务逻辑不依赖绝对时间，或在检测到跳变时拒绝写入并告警。

### 14.9（辨析）逻辑时钟与墙上时钟解决什么问题？

- 墙上时钟回答事件发生在什么时刻，逻辑时钟回答事件之间的因果先后。
- Lamport 时钟为每个事件分配一个整数，保证若 A 因果先于 B，则 A 的计数小于 B 的计数。
- 反向不成立：计数小的事件不一定因果先于计数大的事件，因此 Lamport 时钟只给出偏序的保守近似。
- 向量时钟记录每个节点的计数，可以判定因果先后与并发，代价是元数据随节点数增长。
- 混合逻辑时钟把物理时间与逻辑计数结合，兼顾可比较性与接近真实时间。
- 选择依据是需求：判定并发冲突用向量时钟，只需要全序用 Lamport 时钟，按时间查询用墙上时钟加误差界定。

### 14.10 Lamport 时间戳能推出什么因果结论？

- 若事件 a 因果先于事件 b，则 `C(a)` 小于 `C(b)`，这是唯一能推出的方向。
- `C(a)` 小于 `C(b)` 时，a 与 b 可能并发，无法据此判定先后。
- 因果关系包括同进程内的先后、消息发送先于接收，以及上述关系的传递闭包。
- 用 Lamport 时间戳给事件排序得到与因果一致的全序，但不能识别并发。
- 多副本场景中若只按 Lamport 时间戳做「后写覆盖」，并发写会被任意一方覆盖，可能丢失更新。
- 需要检测冲突时改用向量时钟或版本向量，由应用层合并而不是覆盖。

### 14.11（场景）进程暂停会造成哪些误判？

- 暂停期间进程不响应心跳，其他节点判定其失效并触发选举或故障转移。
- 暂停结束后进程继续执行，它持有的状态可能已经过期，例如仍认为自己是领导者。
- 暂停可能发生在任意指令之间，包括写入共享存储之后、返回响应之前。
- 虚拟机挂起、容器 CPU 限额、GC 的 stop-the-world 阶段都会造成秒级暂停。
- 依据「响应快」推断「进程健康」的假设在暂停场景下不成立。
- 防御手段是让写操作携带有效性凭证，由下游校验，而不是依赖进程自身的判断。

### 14.12（陷阱）GC 暂停与虚拟机迁移为什么破坏租约假设？

- 租约依赖「在到期前原持有者不会行动」，其成立需要时钟误差有界且进程按真实时间推进。
- 长时间暂停可能跨越租约到期点，持有者醒来后仍按本地记录认为租约有效。
- 虚拟机迁移会暂停实例并可能重置时钟，迁移期间的时间流逝不被进程感知。
- 客户端与服务器对同一租约剩余时间的判断可能不同，双方的时钟偏移直接转化为安全边界。
- 缩短租约可以缩小窗口，但会增加续期开销，并提高因网络抖动误判失效的概率。
- 正确做法是租约只用于性能优化，安全性仍由令牌或共识校验保证。

### 14.13 领导者租约失效时可能发生什么？

- 旧领导者仍可接受写请求，新领导者已开始服务，两个节点同时认为自己是唯一写入者。
- 若下游只按请求到达顺序执行，旧领导者的迟到写会覆盖新领导者的新值。
- 客户端从旧领导者读到过期数据，违反线性一致性。
- 若系统依赖「同一时刻只有一个领导者」，该不变量被破坏，可能出现重复分配、重复扣款。
- 检测依赖外部观察者比对令牌或版本号，节点自身无法发现。
- 缓解方式包括写路径强制走共识、下游校验令牌、新领导者上任后拒绝旧纪元的请求。

### 14.14 fencing 令牌如何阻止过期写入？

- 每次授予领导者身份时发放一个单调递增的令牌，令牌随每个写请求下发给存储层。
- 存储层记录已见的最大令牌，拒绝令牌小于或等于该值的请求。
- 旧领导者的请求即使迟到，携带的令牌必然较小，因此被拒绝，而不是覆盖新数据。
- 令牌的正确性依赖发放方单调递增，与租约是否过期无关，因此不受时钟误差影响。
- 存储层必须原子地完成「比较令牌并写入」，否则并发请求仍可能交错。
- 令牌只能防止写覆盖，读路径需要额外机制才能避免读到旧值。

```cpp
bool apply_write(uint64_t token, const Write& w) {
    std::lock_guard<std::mutex> lock(mu_);
    if (token <= last_token_) {
        return false;              // 过期领导者的请求
    }
    last_token_ = token;
    wal_.append(w);                // 令牌与数据同批落盘
    return true;
}
```

### 14.15 fencing 为什么必须由下游资源检查？

- 令牌由客户端携带，被保护的资源是存储、锁服务或外部接口，只有资源方能看到全部请求。
- 若由旧领导者自行检查，它已失去判断依据：它认为自己的令牌仍然有效。
- 由中间层检查只能覆盖经过该中间层的请求，绕过中间层的路径不受保护。
- 资源方检查的代价是每次写比较一次令牌，通常可以合入已有的写路径，开销很小。
- 对不支持令牌的外部系统，可用「先写令牌再写数据」的约定由读取方过滤，但无法阻止覆盖。
- 令牌检查必须与写入在同一原子步骤中完成，拆成「读令牌、比较、写入」会重新打开竞态窗口。

### 14.16（设计）如何构造一个单调递增的 fencing 令牌？

- 用共识服务分配，例如 ZooKeeper 的 `zxid` 或 etcd 的 `revision`，天然全局单调。
- 用「纪元号加序号」的两段式结构：纪元号在每次选举时递增，序号在同一任期内递增。
- 令牌必须持久化，重启后从持久值继续，不能依赖内存计数器。
- 发放令牌与授予身份必须是同一次原子操作，否则可能出现两个节点拿到相同令牌。
- 令牌宽度要留出溢出余量，64 位在可预见的使用期内不会耗尽。
- 单调性只对同一资源有意义，跨资源不要求可比。

```text
令牌 = 纪元号 << 32 | 纪元内序号
纪元号：每次任期变更加一，持久化
序号：同一任期内每次授予加一
校验：token 必须严格大于已记录的最大令牌
```

### 14.17（辨析）拜占庭故障与崩溃故障的边界在哪里？

- 崩溃故障（crash fault）假设节点要么按协议执行，要么停止；拜占庭故障允许节点发送任意消息。
- 拜占庭故障包括伪造消息、选择性不响应、向不同节点发送矛盾信息、与其他节点串通。
- 崩溃故障可以用超时与校验和检测；拜占庭故障需要签名与多重确认才能定位。
- 硬件位翻转与消息损坏属于拜占庭故障的特例，通常由校验和在下层消除。
- 软件缺陷导致的错误行为在形式上属于拜占庭故障，但多数系统选择用测试与灰度应对，而不是改造协议。
- 边界不是二元的：故障模型的选择直接决定协议复杂度与节点数量要求。

### 14.18 拜占庭容错为什么需要更多节点？

- 只有崩溃故障时，2f+1 个节点可以容忍 f 个失效，因为任意多数派中至少有一个节点保存了正确状态。
- 拜占庭节点可以撒谎，接收方无法区分「发送方错误」与「发送方看到的是另一个值」，需要更多副本交叉验证。
- PBFT 类协议的法定人数为 2f+1，总节点数为 3f+1，任意两个法定人数的交集至少包含 f+1 个诚实节点。
- 节点数不足时，f 个恶意节点可以与一部分诚实节点构成看似合法的多数派。
- 消息复杂度随节点数平方增长，3f+1 的下界使拜占庭共识的吞吐显著低于崩溃容错共识。
- 联盟链场景节点数较小，这一开销可以接受；公链用工作量证明或权益证明替换了法定人数假设。

### 14.19（场景）哪些系统需要拜占庭容错？

- 参与方互不信任且无法通过法律或运维手段追责的场景，例如跨组织联盟链、多方对账。
- 存在被入侵风险的边缘设备上报数据，且数据直接驱动资金或权限决策。
- 航空航天与安全关键系统，单粒子翻转会导致计算结果错误而不是进程退出。
- 单个组织内部的数据中心通常信任硬件与运维，崩溃故障模型足够，拜占庭协议会带来不必要的延迟。
- 若错误主要表现为崩溃，引入拜占庭协议不会提升可用性，只增加成本。
- 判断依据是「错误是否可能以合法消息的形式出现」，而不是「系统是否重要」。

### 14.20（设计）如何把不可靠网络与不可靠时钟写进设计与测试？

- 明确列出系统依赖的时间假设：心跳周期、选举超时、租约长度、时钟误差上界，写入配置与文档。
- 让每个假设对应一个可观测指标，例如时钟偏移、心跳丢失率、请求超时率，超出阈值时告警。
- 测试中注入延迟、丢包、乱序、时钟跳变与进程暂停，观察不变量是否被破坏。
- 用确定性模拟复现问题，避免只在生产环境暴露。
- 对无法消除的窗口，用令牌、版本号或共识把安全性从时间假设转移到逻辑条件上。
- 假设发生变化（跨地域部署、虚拟机迁移、容器化）时重新评估，而不是沿用原有超时值。

## 15. 一致性与线性化

### 15.1（辨析）一致性一词在分布式语境中有哪些不同含义？

- 副本一致性：多个副本对同一份数据是否返回相同结果，关注收敛。
- 一致性模型：对并发操作的可见顺序做出约束，例如线性一致性、因果一致性。
- 事务隔离级别中的一致性：并发事务之间不产生异常，例如可串行化。
- 共识协议中的一致性：多个节点对同一决定达成一致，与读写可见性无关。
- CAP 中的 C 特指线性一致性，不是泛指「数据正确」。
- 讨论前先限定层次，否则「强一致」这类说法没有可验证的内容。

### 15.2 线性一致性的定义包含哪两个要求？

- 存在一个全序，所有操作按该全序执行，且该全序与操作在真实时间上的先后一致。
- 每个读返回该全序中它之前最近一次写的结果。
- 操作在执行期间生效，因此尚未返回的写可以被并发读看到，也可以不被看到。
- 全序必须扩展真实时间顺序：若操作 A 在操作 B 开始前完成，则 A 排在 B 之前。
- 线性一致性是局部性质（local property），可以逐个对象检查，不需要跨对象协调。
- 它不要求操作瞬时完成，只要求存在一个满足上述条件的生效点。

### 15.3（陷阱）线性一致性为什么不等于所有副本相同？

- 副本最终相同是收敛性要求，通过异步复制即可达到，期间允许读到旧值。
- 线性一致性约束单个操作的可见性；即使所有副本最终一致，读取仍可能违反线性一致。
- 异步复制下，客户端写入后立刻从另一副本读取，读到旧值即违反线性一致，但副本最终会相同。
- 反之，单副本系统天然线性一致，不存在副本是否相同的问题。
- 因此「所有副本数据一致」是必要但不充分条件，判断标准是操作历史是否可线性化。
- 混淆两者会导致用「最终一致」描述一个实际违反读己之写的系统。

### 15.4 线性一致性与可串行化有什么区别？

- 线性一致性针对单个对象上的读写，回答「读到哪个值」。
- 可串行化针对多个对象上的事务，回答「并发执行的效果是否等价于某个串行顺序」。
- 可串行化不要求串行顺序与真实时间一致，事务可以在其时间窗口内任意重排。
- 线性一致性不涉及多对象原子性，两个对象可以分别线性一致，整体却不可串行化。
- 两者结合成为严格可串行化，是强隔离级别中的最强组合。
- 快照隔离提供一致性快照但不保证可串行化，写偏斜是其典型异常。

### 15.5（辨析）严格可串行化指什么？

- 在可串行化基础上增加约束：串行顺序必须与真实时间一致，先完成的事务排在先。
- 它同时满足线性一致性与可串行化，因此单对象读也满足线性一致。
- 实现需要跨对象协调，通常依赖单领导者或共识，跨地域部署时延迟显著上升。
- 数据库宣传的「强一致」多数指严格可串行化，但实际实现可能只覆盖单分区。
- 分片系统中，跨分片事务的严格可串行化通常要两阶段提交加共识，成本约为单分片写的数倍。
- 需要区分「声明支持」与「默认启用」，很多系统要求显式配置隔离级别。

### 15.6 顺序一致性与线性一致性差在哪里？

- 顺序一致性要求存在全序，且每个进程的操作按其程序顺序出现在全序中，但不要求全序与真实时间一致。
- 线性一致性额外要求全序扩展真实时间顺序，因此更强。
- 顺序一致性允许读看到一个较早完成但被排在后面的写，只要不违反进程内顺序。
- 多核处理器的内存模型讨论顺序一致性，与分布式副本的一致性模型有交集但语境不同。
- 顺序一致性在分布式系统中很少单独使用：它既无法保证读到最新写，又比因果一致性强。
- 判断区别的简单方式：顺序一致性允许时间上后发生的操作先生效，线性一致性不允许。

### 15.7（场景）因果一致性如何弱于顺序一致性？

- 因果一致性只要求尊重有因果关系的操作顺序，并发操作可以任意排序。
- 顺序一致性要求所有进程看到同一个全序，因果一致性允许不同进程看到不同的并发顺序。
- 因果一致性在分区期间仍可保持可用，因为它不需要全局协调；顺序一致性需要。
- 它保证读己之写与单调读这类会话保证，因为同一客户端的操作天然有因果关系。
- 违反因果的典型表现是一致前缀读问题：观察者先看到回答、后看到提问。
- 实现方式包括向量时钟、因果依赖跟踪，或把相关写路由到同一分区。

### 15.8 为什么跨分区的因果顺序难以保证？

- 各分区独立复制，副本进度不同，观察者可能先看到结果分区的新数据。
- 因果关系不会自动跨分区传播，需要显式跟踪依赖，例如版本向量或逻辑时钟。
- 读取时要等待所有依赖的位点追平，等待时间取决于最慢的分区。
- 把有因果关系的写路由到同一分区可以避免等待，但会限制分区键的选择。
- 跨分区事务把依赖与提交绑定在一起，代价是协调开销与可用性下降。
- 工程上常选择弱化保证，只对关键链路保证因果，其余接受前缀乱序。

### 15.9 读己之写如何实现？

- 目标是保证同一客户端在写入成功后，后续读能读到该写。
- 方式一：读请求固定路由到负责该数据的副本或领导者。
- 方式二：客户端记录最后写入的版本号或位点，读时要求副本至少追平该位点，否则等待或转发。
- 方式三：写后一段时间内强制读主，时间窗口由复制延迟上界决定，依赖时钟假设。
- 跨设备场景不成立：同一用户在手机写入、在桌面读取，两者不是同一会话，需要显式携带版本。
- 它不保证读到其他客户端的最新写，因此弱于线性一致性。

### 15.10 单调读防止什么异常？

- 防止同一客户端的时间倒退：先读到新值，之后又读到旧值。
- 成因是多次读被路由到延迟不同的副本。
- 解决方式是把会话固定到同一副本，或记录已读位点并要求后续副本追平。
- 单调读不保证读到最新值，只保证读到的值不会变旧。
- 与读己之写组合后，形成常见的会话保证集合。
- 故障转移时会话固定被打破，需要客户端携带位点重新选择副本。

### 15.11（陷阱）为什么读到旧值不一定是缺陷？

- 若系统声明最终一致，读到旧值是允许的，判断标准是收敛时间上界是否被满足。
- 线性一致读需要协调，代价是延迟与可用性；多数读场景可以接受陈旧数据。
- 真正的缺陷是违反所声明的一致性模型，例如承诺读己之写却读到旧值。
- 监控应度量陈旧度（stale read lag），而不是统计「是否读到旧值」。
- 业务上区分可容忍陈旧的读与不可容忍的读：列表与推荐可以，余额与库存确认不可以。
- 把陈旧度写入服务等级目标，比笼统声明「强一致」更有可验证性。

### 15.12 CAP 中的 C 与 A 分别指什么？

- C 指线性一致性，即整个系统对外表现为单副本，读写满足线性一致。
- A 指每个非故障节点收到的请求都能在有限时间内返回非错误响应。
- 分区指节点之间的网络消息丢失或延迟，系统被切成无法互通的部分。
- CAP 讨论的是分区发生期间的取舍，不是平时状态的三选二。
- 选择 CP 意味着分区期间少数派拒绝服务；选择 AP 意味着可能返回陈旧或冲突的数据。
- 三个属性中分区不是可选项，网络分区在真实系统中必然发生。

### 15.13（辨析）CAP 的分区限定为什么是关键？

- 无分区时系统可以同时满足 C 与 A，取舍只在网络断开时出现。
- 分区期间的 CP 系统让少数派不可用，可用性下降是设计选择而不是缺陷。
- AP 系统在分区期间继续服务，但必须接受读到旧值或写入冲突。
- 分区结束后需要恢复机制：反熵、冲突解决，或按版本合并。
- 把 CAP 理解为「永远只能选两个」会导出错误结论，例如认为 CP 系统不可用。
- 实际系统按操作区分：元数据走 CP，数据读走 AP。

### 15.14（陷阱）CAP 为什么常被误读成三选二？

- 简化表述把系统分成 CA、CP、AP 三类，省略了「分区发生时」这一前提。
- 忽略了分区在网络系统中不可放弃，CA 只在单机或理想网络中存在。
- 把可用性理解为「系统是否在线」，而 CAP 的 A 要求每个非故障节点都能响应。
- 把一致性理解为「数据是否正确」，而 CAP 的 C 特指线性一致性。
- 忽略了延迟：分区判定依赖超时，超时值的选择实际决定了系统在延迟抖动下的行为。
- 更贴近工程的框架是 PACELC：分区时在可用性与一致性之间取舍，否则在延迟与一致性之间取舍。

### 15.15（设计）延迟与一致性之间的取舍如何量化？

- 量化指标是陈旧度上界：读到的数据最多落后写入多少时间或多少个版本。
- 异步复制的陈旧度由复制延迟分布决定，通常取 P99 而不是均值。
- 同步复制把陈旧度降为零，代价是写延迟等于最慢副本的往返时间。
- 法定人数读写把延迟与一致性强度绑定：读集与写集相交保证读到最新写，代价是等待多个副本。
- 跨地域部署时，强一致的延迟下界是到多数派所在区域的往返时间。
- 取舍应写成每个读路径的陈旧度预算，而不是全局开关。

### 15.16 线性一致性的实现代价来自哪里？

- 需要为每个操作确定全局生效顺序，这要求协调，协调需要至少一次网络往返。
- 单领导者方案把所有读写集中到一处，吞吐受单节点上限约束，跨地域延迟高。
- 法定人数方案要求读写集合相交，写等待多数派确认，读等待足够新的副本。
- 需要处理领导者失效，失效检测依赖超时，切换期间服务不可用或降级。
- 每次读都走共识的开销远高于本地读，因此出现租约读、读索引等优化，代价是额外的正确性假设。
- 代价的本质是把并发操作串行化所需的信息交换，无法通过增加副本消除。

```cpp
// 线性一致读：先取读索引，再等本地状态机追平该索引
int64_t read_index = leader.commit_index();
if (!replica.wait_applied(read_index, timeout)) {
    return Status::Unavailable;   // 追平失败，不能返回本地旧值
}
return replica.get(key);
```

### 15.17（场景）哪些场景必须线性一致，哪些可以放宽？

- 必须：唯一性约束（用户名注册）、分布式锁、选主、余额校验、幂等键的首次登记。
- 可以放宽：社交动态、商品列表、推荐、日志检索、统计报表。
- 读己之写足以覆盖多数用户可见的交互，例如提交表单后看到自己的修改。
- 单调读可以避免刷新后内容倒退的观感问题。
- 因果一致性适合协作编辑与评论树，能保证回复不早于被回复内容。
- 判断依据是「错误的读是否造成不可逆的副作用」，而不是「用户是否可能察觉」。

### 15.18 快照隔离与因果一致性是什么关系？

- 快照隔离让每个事务读取同一时间点的已提交数据，因此不会看到果先于因。
- 若事务 T2 读到 T1 的写，T2 的快照必然晚于 T1 的提交，因果顺序被保持。
- 因此快照隔离提供因果一致性，但不提供可串行化，写偏斜仍可能发生。
- 跨分片的快照隔离需要全局时间戳或时钟同步，否则不同分片的快照无法对齐。
- 因果一致性的实现可以更轻量，只需跟踪因果依赖，不需要全局快照。
- 区分点在于：快照隔离约束读哪些版本，因果一致性约束可见顺序。

### 15.19（设计）如何验证一个存储系统是否线性一致？

- 记录完整操作历史：调用时间、返回时间、操作类型、参数与返回值。
- 用模型检查器判断是否存在满足线性一致约束的全序，常用实现有 Knossos 与 Elle。
- 检查复杂度随并发度增长，实际通过限制并发数与缩短历史来控制规模。
- 故障注入必须覆盖分区、节点崩溃、时钟跳变与进程暂停，否则只验证了无故障路径。
- 结论要区分「未发现反例」与「证明正确」，测试只能提供前者。
- 对关键系统同时验证声明的弱模型，例如读己之写，因为强模型失败时弱模型可能仍成立。

### 15.20（估算）线性一致读的延迟下界如何估计？

- 单领导者、单区域：下界约为客户端到领导者的往返时间加上领导者处理时间。
- 跨区域：下界约为客户端到领导者所在区域的往返时间，与副本数量无关。
- 法定人数读：下界为客户端到最近法定人数集合中最慢节点的往返时间。
- 若读需要等待日志应用，还要加上从提交到应用到状态机的延迟。
- 用 P99 往返时间估算比均值更接近实际，尾延迟由最慢节点决定。
- 任何低于一次网络往返的线性一致读，必然依赖租约或本地缓存，其正确性需要额外假设支撑。

## 16. 共识与两阶段提交

### 16.1（辨析）共识问题与原子广播是什么关系？

- 共识：多个节点对同一个值达成一致，且该值必须是某个节点提议过的值。
- 原子广播（atomic broadcast）：所有节点按相同顺序交付相同的消息集合。
- 两者等价，可以互相归约：用共识为每条消息确定序号即得到原子广播，用原子广播对提议排序即得到共识。
- 等价性意味着实现其中一个即可得到另一个，工程上通常实现带日志的原子广播。
- 复制状态机建立在原子广播之上：相同顺序的确定性命令产生相同状态。
- 因此共识库的接口常表现为追加日志，而不是决定单个值。

### 16.2 共识算法需要满足哪三条性质？

- 一致同意：所有正确节点决定相同的值。
- 完整性：每个节点最多决定一次，且决定的值必须被某个节点提议过。
- 终止性：所有正确节点最终都会做出决定。
- 异步网络中同时满足三者不可能，这是 FLP 结论；实用算法通过随机化或部分同步假设绕过。
- 工程上还要求效率：决定所需的往返次数与消息量有界。
- 失效恢复后新加入的节点必须能追上已决定的历史，因此日志需要持久化。

### 16.3（陷阱）为什么多数派能避免脑裂？

- 任意两个多数派必然相交，交集节点不会对两个不同的值都投赞成票。
- 少数派无法单独做出决定，因此分区期间只有包含多数派的一侧可以推进。
- 前提是投票权按节点数计算，且节点不会重复投票；成员配置不一致时该前提被破坏。
- 多数派的定义依赖成员集合，成员变更期间需要同时满足旧配置与新配置的多数派。
- 多数派只保证安全性，不保证可用性：失去多数派的一侧必须停止服务。
- 若允许读在少数派进行而不做校验，脑裂仍会以读到旧值的形式出现。

### 16.4 两阶段提交的 prepare 与 commit 分别做什么？

- 协调者向所有参与者发送 prepare，参与者执行事务但不确定提交，返回「可以提交」或「中止」。
- 参与者把 prepare 结果与事务修改持久化，并持有锁，直到收到最终决定。
- 若全部参与者同意，协调者把提交决定写入自己的日志，然后发送 commit。
- 任一参与者拒绝或超时，协调者发送 abort，参与者回滚并释放锁。
- 提交决定一旦写入协调者日志就不可撤销，参与者必须最终执行。
- 提交决定的落盘点称为提交点（commit point），跨过该点后结果不可改变。

```text
协调者                     参与者 A            参与者 B
  |-- prepare ------------->|                   |
  |-- prepare --------------------------------> |
  |<-- yes -----------------|                   |
  |<-- yes ------------------------------------ |
  |  (写 commit 决定到日志)                     |
  |-- commit -------------->|                   |
  |-- commit ---------------------------------> |
```

### 16.5（陷阱）2PC 的协调者崩溃为什么会导致阻塞？

- 参与者已 prepare 并持有锁，但不知道最终决定，只能等待协调者恢复。
- 参与者不能自行提交，因为其他参与者可能已中止；也不能自行中止，因为协调者可能已决定提交。
- 阻塞期间锁不释放，相关数据行无法被其他事务访问，形成级联等待。
- 协调者日志若丢失，决定永久不可知，需要人工介入。
- 因此 2PC 是阻塞协议，其可用性依赖协调者的可靠性与恢复速度。
- 协调者单点是根因，解决方向是让协调者本身成为共识组，复制协调者日志。

### 16.6 2PC 与共识算法解决的是同一个问题吗？

- 2PC 解决原子提交：让多个独立资源管理器对「提交或中止」达成一致。
- 共识解决复制：让多个副本对同一序列的决定达成一致。
- 2PC 不满足终止性：协调者失效时参与者可能永远等待，因此不是共识算法。
- 共识算法在多数派存活时可继续推进，具备容错终止性。
- 工程组合是共识加 2PC：用共识复制协调者状态，用 2PC 协调跨分片事务。
- 组合后仍保留 2PC 的锁持有时间，跨分片事务的延迟与阻塞特性不变。

### 16.7（辨析）2PC 中「不确定」状态为什么难以消除？

- 不确定源于参与者已承诺但未收到决定，承诺不可撤回，因此必须等待。
- 要消除等待，参与者必须能自行推断决定，这要求它掌握全部参与者的投票，等价于拥有全局信息。
- 让参与者互相通信推断会退化为另一个共识过程，消息复杂度上升。
- 减少不确定窗口的办法是缩短 prepare 到 commit 的时间，例如提高协调者可靠性。
- 三阶段提交增加 pre-commit 阶段让参与者可以安全推断，但依赖同步网络假设。
- 实用做法是接受窗口存在，用超时告警与人工恢复兜底。

### 16.8（设计）如何降低 2PC 的阻塞窗口？

- 把协调者做成共识组，决定一旦被多数派持久化即可恢复，缩短不可用时间。
- 参与者侧设置事务超时，但对已 prepare 的事务不能单方面中止，只能告警。
- 减少跨分片事务比例：按业务键分区，让多数事务落在单分片。
- 提前预留资源（例如预扣库存）替代长时间持锁，把锁持有时间从秒级降到毫秒级。
- 用幂等的补偿操作替代分布式事务，把强一致降为最终一致。
- 监控「已 prepare 未决定」的事务数量与最老事务年龄，作为核心指标。

### 16.9 三阶段提交为什么在实践中很少使用？

- 3PC 增加 pre-commit 阶段，使参与者在超时后可以安全地提交或中止，从而非阻塞。
- 其正确性依赖网络延迟有界与时钟同步，真实网络的长尾延迟会破坏该假设。
- 分区与节点失效同时发生时，3PC 仍可能产生不一致。
- 多一轮往返使延迟上升，而收益只在协调者失效的少数场景体现。
- 主流系统选择 2PC 加共识复制协调者，或用基于日志的补偿方案。
- 3PC 更多出现在教材与协议分析中，生产系统少有采用。

### 16.10 Paxos 与 Raft 在工程上的主要差异是什么？

- Paxos 描述单次决定的协议，实际系统使用 Multi-Paxos，其领导者维持机制与日志连续性需要额外设计。
- Raft 把领导者选举、日志复制、成员变更与快照整合为完整协议，约束更强但更易实现。
- Raft 要求日志连续且领导者只追加，简化恢复逻辑；Paxos 允许日志空洞，恢复时需要填充。
- Raft 的选举由随机超时驱动，Paxos 的领导者维持方案由实现决定。
- 两者在同样的多数派假设下提供相同级别的安全性，差异在工程复杂度与可验证性。
- 选择依据通常是生态与运维工具，而不是协议的理论强度。

### 16.11（陷阱）Multi-Paxos 的领导者为什么仍需持久化状态？

- 领导者需要记录自己承诺过的最大提案号，否则重启后可能接受更小的提案号，破坏安全性。
- 接受者需要持久化已承诺的提案号与已接受的值，否则崩溃恢复后可能推翻已接受的值。
- 只持久化部分状态（例如只存值不存提案号）会在恢复后产生两个不同的决定。
- 持久化需要 fsync，这是共识写延迟的主要来源之一。
- 批量提交可以摊薄 fsync 成本，但会增加单次决定的延迟。
- 任何声称无需持久化的优化都必须证明重启后不会违反投票约束。

### 16.12 共识系统的成员变更为什么不能一步完成？

- 多数派按当前成员集合计算，切换集合的瞬间可能出现两个不相交的多数派。
- 例如从 3 节点扩到 5 节点，若新旧配置各自计算多数派，两侧可能同时选出领导者。
- 因此变更必须经过新旧配置并存的中间状态，或限制每次只增删一个节点。
- 单节点变更的安全性来自新旧多数派必然相交这一算术性质。
- 变更期间必须拒绝并发的第二次变更，否则交集性质不再成立。
- 变更记录本身也要走共识，保证所有节点对成员集合的认知一致。

### 16.13 单节点变更与联合共识各有什么代价？

- 单节点变更实现简单，安全性由多数派交集保证，但扩容 N 个节点需要 N 轮。
- 联合共识（joint consensus）在中间状态要求同时获得旧配置多数派与新配置多数派的同意。
- 联合共识可以在一次变更中替换任意数量的节点，但实现复杂，需要两套配置并行计算法定人数。
- 联合共识期间可用性下降：需要两侧多数派都存活，容错能力暂时降低。
- 单节点变更在偶数规模下会短暂降低容错，通常避免偶数节点配置。
- 生产系统多采用单节点变更加自动化多轮执行，兼顾简单与可运维。

### 16.14（场景）成员变更期间的多数派如何计算？

- 联合共识阶段，写需要同时得到旧配置多数派与新配置多数的确认。
- 若新旧集合重叠较大，实际所需节点数接近较大集合的多数。
- 单节点变更阶段，法定人数按变更前配置计算，变更提交后按新配置计算。
- 实现必须把配置本身作为日志条目复制，节点按日志中的配置版本判断当前法定人数。
- 计算错误会导致两个分区各自认为自己有多数派，是成员变更最典型的安全缺陷。
- 验证方式是构造新旧配置交叠的边界场景，检查任一时点的法定人数集合是否必然相交。

```cpp
// 联合共识阶段：两侧多数派都必须满足
bool quorum_ok(uint64_t old_votes, uint64_t old_size,
               uint64_t new_votes, uint64_t new_size) {
    return old_votes * 2 > old_size && new_votes * 2 > new_size;
}
```

### 16.15 领导者租约如何避免读请求落到旧领导者？

- 领导者向追随者授予租约：在租约到期前，追随者不参与选举、不投票给其他候选人。
- 领导者因此可以确认租约期内没有新领导者产生，本地读即可满足线性一致。
- 租约的授予与续期走共识日志，追随者按自己的单调时钟计时。
- 租约长度必须小于选举超时，并扣除时钟漂移与网络延迟的余量。
- 租约把每次读都走共识降为本地读加周期性续期，显著提升读吞吐。
- 安全性依赖时钟假设，跨地域部署时租约长度受往返时间限制，收益下降。

### 16.16（陷阱）租约依赖时钟，为什么仍然被广泛使用？

- 时钟不同步只影响假设的成立范围，只要误差有界，租约就是安全的。
- 数据中心的 NTP 同步通常能把偏移控制在毫秒级，租约取秒级时余量充足。
- 不用租约的替代方案是每次读走共识，延迟高一个数量级，吞吐受共识往返限制。
- 租约失效的后果通常是被检测到的可用性问题，而不是静默的数据损坏，前提是有令牌或版本校验。
- 虚拟机迁移与长时间 GC 会打破假设，因此实现通常监控时钟偏移并主动放弃租约。
- 结论是租约属于有条件的优化，条件必须写入文档并被监控覆盖。

```cpp
bool leader_can_serve_read() const {
    // 本地租约未到期才允许读，到期判断使用单调时钟
    return std::chrono::steady_clock::now() < lease_deadline_;
}

void on_lease_granted(Duration ttl) {
    // 到期时间从本地收到消息时开始计算，并扣除安全余量
    lease_deadline_ = std::chrono::steady_clock::now() + ttl - safety_margin_;
}
```

### 16.17（设计）租约续期失败后的安全边界如何确定？

- 领导者在本地租约到期时必须立即停止服务读请求，不能等待确认。
- 到期判断使用单调时钟，避免时钟回拨延长有效时间。
- 追随者在租约到期后才允许发起选举，到期时间从收到租约消息时开始计算，而不是从发送时。
- 两侧的到期时间需要留有安全余量，余量覆盖网络延迟上界与时钟漂移。
- 续期失败时应主动降级为需要走共识的读，而不是直接返回错误。
- 监控应记录租约剩余时间的最小值，作为容量与时钟健康的预警指标。

### 16.18 共识的写放大与延迟下界来自哪里？

- 一次写需要领导者追加日志、并行发送给追随者、等待多数派 fsync 后提交。
- 延迟下界约为一次到多数派的往返加一次 fsync，跨地域时往返占主导。
- 写放大的来源是每条日志被复制到全部节点，并可能多次落盘（日志与状态机快照）。
- 批处理与流水线可以提升吞吐，但不降低单次写的延迟下界。
- 读也有成本：线性一致读需要确认领导者身份，或走读索引等待状态机追平。
- 因此共识适合元数据与配置，不适合高吞吐的数据面写入。

### 16.19（场景）跨数据中心部署共识为什么会显著抬高写延迟？

- 多数派必须包含跨地域的节点，写需要等待最远的多数派成员确认。
- 三地域部署时任意两地域构成多数派，写延迟约为到第二近地域的往返时间。
- 五地域部署容错更高，但多数派需要三个地域，延迟进一步上升。
- 跨地域链路的抖动与丢包率高于机房内网络，尾延迟放大明显。
- 缓解方式是把共识限定在元数据，数据面用异步复制加本地读。
- 另一种方式是把多数派固定在同一地域，接受该地域故障时整体不可用。

### 16.20（设计）如何验证共识实现的正确性？

- 用确定性模型检查（例如 TLA+）验证选举、日志匹配、成员变更等不变量。
- 用故障注入测试分区、消息重排、节点重启与时钟跳变，检查已提交日志不被覆盖。
- 用线性一致性检查器对客户端历史做验证，覆盖读、写、比较并交换等操作。
- 检查成员变更期间的法定人数计算，构造新旧配置交叠的边界场景。
- 验证恢复路径：落后节点追赶、快照传输、日志截断，这些路径最容易出错。
- 测试只能提高置信度，关键系统还应保留形式化规约与代码的对应关系审查。

## 17. 批处理与 MapReduce

### 17.1（辨析）批处理与流处理的分界在哪里？

- 批处理以有界输入为前提，作业开始时输入集合已确定，可以在全量数据上做全局排序与聚合。
- 流处理以无界输入为前提，数据持续到达，没有输入结束这一时刻。
- 分界不在延迟：微批可以做到秒级延迟，但仍以有界分片为单位。
- 分界在是否依赖输入结束：批处理可以在结束前不产出任何结果，流处理必须持续产出。
- 同一套算子可以同时支持两种模式，差别在于触发器与状态管理。
- 选择依据是结果时效性与重算成本，而不是数据量。

### 17.2 MapReduce 的 shuffle 阶段为什么是性能关键？

- shuffle 需要把 map 输出按 key 分区、排序，并跨网络传输到对应 reducer。
- 数据量与实际网络带宽决定作业下界，shuffle 通常占总耗时的多数。
- shuffle 通常先物化：map 输出写入本地磁盘，再由 reducer 拉取，磁盘与网络双重压力。
- 中间数据的序列化格式与压缩率直接影响传输量。
- 分区函数不均衡会导致部分 reducer 成为长尾。
- 优化方向是减少 shuffle 数据量（提前聚合、列裁剪）与提高并行度。

### 17.3（场景）map 端 join 与 reduce 端 join 如何选择？

- map 端 join 要求一侧数据足够小，可以完整装入内存并广播到每个 map 任务。
- reduce 端 join 对两侧规模没有限制，但需要按 join key 重分区，产生完整 shuffle。
- map 端 join 的代价是广播开销随 map 任务数增长，小表被重复传输。
- reduce 端 join 的代价是 shuffle 全量数据，且对倾斜敏感。
- 若两侧都很大且已按同一 key 分区，可以直接做分桶 join，避免 shuffle。
- 选择依据是两侧规模比、分区是否已对齐，以及是否允许中间结果落盘。

```cpp
// map 端 join：小表构建哈希表，只构建一次并随任务分发
void map_join(const Row& big, const HashMap& small_index) {
    auto it = small_index.find(big.join_key);
    if (it != small_index.end()) {
        emit(merge(big, it->second));
    }
}
```

### 17.4（陷阱）reduce 端 join 为什么依赖分区正确？

- reduce 端 join 的正确性前提是同一 key 的所有记录被送到同一个 reducer。
- 若两侧使用不同的分区函数，例如一侧按哈希、另一侧按范围，同一 key 会落到不同 reducer，join 结果丢失。
- 分区数不同也会破坏前提，即使函数相同。
- 自定义分区器在数据分布变化后可能不再匹配，需要在作业中显式校验。
- 校验方式是抽样比对两侧 key 的分区归属，或对 join 结果做计数核对。
- 该缺陷不报错，只表现为结果偏少，属于静默错误。

### 17.5 广播哈希 join 与分桶 join 的适用条件？

- 广播哈希 join：小表构建哈希表并随任务分发，大表流式探测，适合大小表差异悬殊。
- 分桶 join：两侧按同一 key 与同一分桶数预先分区，桶内直接 join，适合周期性重复 join 的两张大表。
- 广播的瓶颈是分发带宽与每个任务的内存占用，小表上限受执行器内存约束。
- 分桶的瓶颈是预处理成本与分桶数固定，数据增长后需要重新分桶。
- 分桶 join 要求两侧写入时使用完全一致的分区策略，包括空值与类型转换规则。
- 两者都不产生完整 shuffle，因此在大规模场景下明显优于 reduce 端 join。

### 17.6（设计）如何用排序合并实现 join？

- 两侧数据按 join key 排序，然后双指针推进，key 相等时输出组合。
- 排序可以由上游的 shuffle 阶段顺带完成，避免额外排序。
- 合并阶段只需常驻内存保存当前 key 的组，内存占用与组大小相关，而不是全表。
- 若某一 key 的组极大，内存仍可能溢出，需要退化为分块处理。
- 输出顺序由 key 决定，天然有序，便于后续按 key 聚合。
- 排序合并对倾斜的容忍度好于哈希 join，但排序本身有成本。

### 17.7 数据倾斜有哪些成因？

- key 分布本身不均，例如少数商品占据大部分订单。
- 分区函数与数据分布不匹配，例如按哈希分区但某个 key 出现频率极高。
- 空值或默认值集中到同一分区。
- 数据量与分区数不匹配，分区数过少导致单个分区过大。
- 上游过滤导致某些分区数据骤减，而另一些分区不变。
- 倾斜的判定要看单任务处理量与耗时的分布，而不只看输入大小。

### 17.8（场景）热键导致的倾斜如何缓解？

- 对热键做拆分：给 key 加随机后缀，把一条逻辑 key 变成多条物理 key，聚合后再合并。
- 对热键单独处理：把热键数据路由到专门的 reduce 任务，其余走常规路径。
- 在 map 端做预聚合，把同一 key 的多条记录先合并，减少传输量。
- 提高分区数可以让更多小分区分担，但对单一超大 key 无效。
- 广播小表侧可以消除 join 的 shuffle，从根本上绕开倾斜。
- 缓解手段要与语义兼容：加盐会改变输出顺序与去重语义，需要在合并阶段恢复。

### 17.9（陷阱）加盐为什么会让结果膨胀？

- 加盐把一个 key 拆成 N 个，聚合结果变成 N 条部分结果，需要二次聚合。
- 若下游直接消费未合并的结果，会出现重复计数。
- 二次聚合本身可能再次倾斜，因为部分结果的 key 相同。
- 对 join 加盐需要两侧同时加盐，否则匹配不上，实现复杂度上升。
- 加盐会破坏按 key 的有序性，影响依赖顺序的下游。
- 因此加盐必须与合并阶段成对出现，并验证总计数与未加盐时一致。

```text
原始 key：user_42   -> 一条逻辑 key
加盐后：  user_42#0、user_42#1、...、user_42#7   -> 8 条物理 key
合并：    按 user_42 汇总 8 条部分结果
校验：    sum(部分结果) == 未加盐时的总数
```

### 17.10 倾斜检测应在哪个阶段做？

- 在 shuffle 写入阶段统计每个分区的记录数与字节数，成本低且覆盖全量。
- 在任务运行时采样各任务的输入速率，用于动态调整，但会引入额外开销。
- 作业开始前对 key 分布做抽样统计，适合周期性作业，能提前选择策略。
- 检测指标应包括最大分区与中位分区的比值，而不只是绝对大小。
- 检测结果应写入作业元数据，供后续作业复用。
- 只在失败后看日志属于事后检测，会浪费一整轮计算。

### 17.11 批处理的输出为什么强调不可变与幂等？

- 批处理作业可能因失败重跑，输出必须能被重复写入而不产生重复结果。
- 常见做法是写入新分区或新目录，完成后原子地切换视图。
- 覆盖写依赖分区隔离，若直接修改目标表，重跑期间会读到中间状态。
- 幂等要求输出与输入一一对应，或写入时按主键去重。
- 不可变输出便于回滚：保留旧版本，切换指针即可恢复。
- 增量作业需要按分区幂等，而不是按整表幂等。

### 17.12（陷阱）输出部分失败后重跑为什么可能重复？

- 作业在写入部分输出后失败，重跑会再次写入同一批记录。
- 若输出端不支持按主键覆盖或按分区替换，重复记录会累积。
- 提交协议缺失时，读取方可能在重跑期间看到部分新旧混合的数据。
- 多任务并行写同一分区时，失败任务的重试与成功任务的结果交错。
- 解决方式是两阶段提交输出：先写临时位置，全部成功后原子重命名，或使用幂等写入。
- 需要验证的性质是「重跑两次的结果与重跑一次相同」。

### 17.13 工作流调度器与 MapReduce 框架的职责边界？

- MapReduce 框架负责任务内的数据流：切分、map、shuffle、reduce、失败重试。
- 调度器负责作业之间的依赖：触发时间、上游完成检测、参数传递、失败重跑策略。
- 把多阶段逻辑塞进单个作业会失去按阶段重跑的粒度，失败时需全量重算。
- 调度器的代价是引入外部状态：依赖关系、运行历史、并发控制都需要持久化。
- 调度器需要处理上游成功但数据未就绪的情况，通常用哨兵文件或分区存在性检查。
- 边界清晰时，单个作业可独立测试，工作流可独立回填。

### 17.14（设计）如何保证多阶段工作流的原子发布？

- 所有阶段写入带版本号的临时目录，最后一步用原子重命名或指针切换发布。
- 发布前校验分区完整性：行数、分区覆盖范围、schema 版本。
- 读取方只读已发布版本，不读临时目录。
- 失败时保留临时目录用于排查，发布指针不变，读取方不受影响。
- 回滚即把指针切回上一版本，前提是旧版本未被覆盖。
- 该模式要求存储支持原子重命名或等价的元数据切换。

```text
s3://warehouse/orders/_staging/run=2026-11-15/   <- 各阶段写入
s3://warehouse/orders/dt=2026-11-15/             <- 原子重命名后发布
发布检查：分区数、总行数、schema 版本、校验和
读取方：  只读 dt= 路径，不读 _staging
```

### 17.15 增量重算相比全量重算解决了什么？

- 全量重算的代价随历史数据增长，日增数据占比很小时浪费明显。
- 增量重算只处理变化的分区，成本与增量规模成正比。
- 增量需要处理迟到数据：旧分区可能被新数据修正，需要回填机制。
- 增量结果的正确性依赖分区边界与业务时间对齐，否则跨分区聚合会错。
- 增量与全量的结果必须可对账，定期跑全量校准是必要的。
- 选择依据是数据增长率、可接受延迟与回填成本。

### 17.16（估算）shuffle 数据量如何估算？

- shuffle 数据量约等于 map 输出中被选中的列与行数的乘积，再乘以序列化开销。
- 压缩后传输量取决于压缩率，文本与 JSON 通常可压缩数倍，已编码的二进制压缩率低。
- 分区数决定并行度，也决定每个分区文件的元数据开销。
- 网络传输时间约为数据量除以可用带宽，需扣除其他作业的占用。
- 中间数据落盘量通常是传输量的两倍（写一次、读一次），磁盘容量需要预留。
- 估算应给出区间而不是单点，输入分布与过滤率的不确定性会影响结果。

### 17.17（辨析）map 端聚合与 reduce 的区别？

- map 端聚合在 map 输出上做局部归并，减少传输量，要求操作满足结合律与交换律。
- map 端聚合可能执行零次、一次或多次，实现不保证调用次数，因此不能有副作用。
- reduce 接收全部同 key 记录，结果确定；map 端聚合的结果只是中间态。
- 平均值不能用 map 端聚合直接计算，需要传 `(sum, count)` 而不是单一值。
- 两者使用同一函数时，必须保证该函数幂等且可重入。
- 收益取决于 key 重复率：重复率低时 map 端聚合几乎没有作用。

### 17.18（场景）批处理作业的尾延迟由什么决定？

- 单个慢任务决定作业完成时间，可能由磁盘坏道、负载不均、GC 造成。
- 倾斜使某个分区远大于其他分区，该任务成为长尾。
- 推测执行可以缓解，但会重复计算并争抢资源。
- 分区数过少时单任务数据量大，长尾更明显。
- 资源调度延迟（等待容器分配）也会贡献尾延迟，尤其在集群繁忙时。
- 优化应针对 P99 任务耗时，而不是平均耗时。

### 17.19 批处理与流处理的统一解决了什么问题？

- 统一引擎让同一份逻辑同时支持有界与无界输入，避免两套代码的语义漂移。
- 统一的关键是把批视为流的特例：有界流在结束时触发最终结果。
- 统一要求状态后端、检查点、事件时间语义在两种模式下一致。
- 收益是减少重复实现与结果不一致，代价是批处理可能失去针对性优化。
- 迁移时需验证批模式与流模式在相同输入上产生相同结果。
- 统一的边界在交互式查询：即席分析仍需要专门的查询引擎。

### 17.20（设计）如何验证批处理结果的正确性？

- 与独立实现（SQL 查询、单机脚本）在小规模数据上对账。
- 校验不变量：行数守恒、金额求和、唯一键无重复、分区覆盖完整。
- 构造含空值、重复键与极端值的测试数据集，覆盖 join 与聚合的边界。
- 对比重跑结果，验证幂等性与确定性。
- 对增量结果与全量结果做定期比对，发现回填遗漏。
- 记录输入版本与作业版本，使任何结果都可追溯到确定的输入。

## 18. 流处理与数据集成

### 18.1（辨析）消息队列与日志在语义上的差别？

- 消息队列在消费后删除消息，同一消息通常只被一个消费者处理，语义偏向任务分发。
- 日志是持久化的追加序列，保留策略与消费位点解耦，多个消费者可以独立读取同一份数据。
- 日志支持重放：消费者可以回退位点重新处理历史，队列删除后无法重放。
- 日志的顺序按分区保证，队列通常不保证跨消息顺序。
- 日志的保留策略是时间或大小，队列的保留策略是确认消费。
- 选择依据是是否需要多订阅者、重放与顺序保证。

### 18.2 日志的偏移量与消费位点分别表示什么？

- 偏移量（offset）是消息在分区内的位置，由 broker 分配，单调递增。
- 消费位点是消费者已处理到的位置，由消费者提交。
- 位点提交的时机决定语义：先处理后提交为至少一次，先提交后处理为至多一次。
- 位点按消费者组保存，不同消费者组互不影响。
- 位点提交必须是单条记录的原子写入，避免部分更新。
- 位点回退会触发重放，要求下游幂等。

```cpp
// 先处理，再提交位点：至少一次语义
for (;;) {
    auto batch = consumer.poll(100ms);
    if (batch.empty()) continue;
    process(batch);                       // 可能失败并重试
    consumer.commit(batch.last_offset + 1);  // 失败后重放整批
}
```

### 18.3（场景）日志压缩适合哪类主题？

- 日志压缩（log compaction）按 key 保留每个 key 的最新值，删除更早的版本。
- 适合当前状态类主题：配置、用户资料、库存快照，消费者只需要最新值。
- 不适合事件流：需要完整历史的场景压缩后会丢失中间事件。
- 压缩后偏移量不连续，消费者不能假设位点连续。
- 压缩需要墓碑标记删除，并配置删除保留期。
- 压缩是后台过程，不保证及时性，读取方仍需处理同一 key 的多条记录。

### 18.4 CDC 与双写相比解决了什么问题？

- 双写在应用层同时写数据库与下游，两次写不在同一事务中，可能部分成功。
- 双写还会遗漏绕过应用的写入，例如批量导入、运维脚本、其他服务。
- CDC 从数据库日志读取变更，覆盖所有写入路径，且顺序与事务提交顺序一致。
- CDC 的延迟取决于日志读取与投递，通常为秒级。
- CDC 需要处理 schema 变更与初始快照，快照与增量之间要保证不重不漏。
- 双写的优点是实现简单、延迟低，适合对一致性要求不高的场景。

### 18.5（陷阱）CDC 为什么仍可能丢事件？

- 数据库日志的保留期有限，采集端停止时间过长会导致位点之后的日志被清理。
- 采集端崩溃后从检查点恢复，若检查点落后于已投递消息会重复，超前则会丢失。
- 大事务或 DDL 可能被采集工具过滤或截断。
- 主从切换后日志文件名变化，位点映射错误会导致跳过。
- 下游消费失败而采集端继续推进位点，等于丢弃。
- 因此 CDC 的端到端保证取决于采集、传输、消费三段的位点语义是否对齐。

### 18.6 事件时间与处理时间为什么要分开？

- 事件时间由数据本身携带，表示事件实际发生时刻；处理时间由处理节点的时钟决定。
- 事件可能迟到，按处理时间开窗会把同一业务窗口的数据分到不同窗口。
- 重放历史数据时处理时间是当前时刻，只有事件时间能得到可重现的结果。
- 事件时间窗口的结果取决于水位线推进，处理时间窗口的结果取决于到达顺序。
- 事件时间需要处理乱序与迟到，处理时间不需要，但结果不可重现。
- 多数业务指标应按事件时间计算，运维指标（吞吐、延迟）按处理时间计算。

### 18.7（陷阱）水位线为什么不能保证不丢迟到数据？

- 水位线是「事件时间小于该值的数据大概率已到达」的估计，不是保证。
- 基于事件时间最大值减固定延迟的水位线，在乱序超过延迟时仍会漏。
- 数据源空闲时水位线不推进，窗口迟迟不触发；数据源突然涌入旧数据会破坏估计。
- 多分区流的水位线取各分区最小值，任一分区滞后会拖住整体。
- 因此需要定义水位线之后迟到数据的处理方式：丢弃、发到旁路，或触发窗口重算。
- 允许迟到（allowed lateness）是对水位线的补充，不是替代。

### 18.8 窗口类型如何选择？

- 滚动窗口固定长度不重叠，适合按小时、按天统计。
- 滑动窗口固定长度且可重叠，适合移动平均，计算量随重叠度上升。
- 会话窗口按活动间隔切分，长度不定，适合用户行为分析。
- 全局窗口需要自定义触发器，否则不会触发。
- 窗口的对齐基准要明确：按事件时间对齐到自然边界，还是按首条事件对齐。
- 窗口状态大小直接影响内存，滑动窗口的重叠度会成倍放大状态。

### 18.9（设计）迟到事件的处理策略有哪些？

- 丢弃：实现简单，但会低估指标，需要监控丢弃量。
- 旁路输出：把迟到数据写入单独的主题，供离线修正。
- 重算：保留窗口状态直到允许迟到期限，期限内到达的数据触发结果更新。
- 结果撤回：下游支持按主键覆盖或撤回，才能把修正传播出去。
- 阈值告警：迟到比例超过阈值时通知上游修正时间戳或调整发送时机。
- 策略必须与下游语义匹配，否则修正无法生效。

```text
窗口 [10:00, 10:05)，水位线推进到 10:05
  - 10:04 的事件在 10:06 到达：落在允许迟到期限内，触发窗口重算
  - 10:04 的事件在 10:20 到达：超过允许迟到，写入旁路主题
旁路主题由离线作业合并，并在指标中标记迟到比例
```

### 18.10（辨析）恰好一次与至少一次、至多一次的边界？

- 至少一次：不丢，可能重复；实现方式是先处理再提交位点。
- 至多一次：不重，可能丢；实现方式是先提交位点再处理。
- 恰好一次：每条输入对输出的影响恰好一次，投递次数可能大于一，需要位点与输出落在同一原子边界内。
- 在无状态且可幂等的外部系统上，恰好一次可以由去重实现，不需要事务。
- 三种语义的成本差异在于是否允许重试与是否要求原子提交，而不是投递次数。
- 选择取决于副作用成本：重复扣款不可接受，重复写日志通常可接受。

### 18.11（陷阱）恰好一次为什么依赖幂等或事务？

- 处理失败后必须重试，重试意味着至少一次的投递。
- 要消除重复效果，要么输出端能按唯一键去重，要么位点与输出原子提交。
- 去重需要稳定的唯一键（例如事件 ID），且去重表不能无限增长。
- 事务需要输出端支持事务，且事务边界与位点提交一致。
- 跨系统的恰好一次需要分布式事务或两阶段提交，代价高。
- 因此恰好一次总是相对于某个边界成立，跨边界时会退化为至少一次。

### 18.12 端到端一致性需要哪些环节配合？

- 源端：位点或快照的获取必须与数据一致，避免读到半个事务。
- 传输端：消息不丢、顺序按分区保持、位点可提交。
- 处理端：状态与位点在同一检查点中持久化，失败后从一致点恢复。
- 输出端：支持幂等写或事务提交，且与位点提交原子绑定。
- 任一端缺失，整体保证降级，且降级点通常难以观测。
- 端到端验证需要注入故障并核对输出与输入的对应关系。

### 18.13（设计）如何用位点提交与输出事务实现端到端恰好一次？

- 将输出写入与位点提交放在同一个事务中，两者要么都成功要么都失败。
- 若输出端与位点存储不是同一系统，使用两阶段提交，或把位点写入输出端的同一事务。
- 另一种做法是把位点写入输出记录本身，由下游按位点去重。
- 检查点必须包含算子状态与输入位点，恢复时同时回滚。
- 事务超时会触发中止，需要保证中止后不留部分输出。
- 验证方式是统计输出条数与输入条数，并在故障注入后比对。

```cpp
txn.begin();
txn.put(out_key, record);             // 业务输出
txn.put(offset_key, next_offset);     // 输入位点，同一事务
txn.commit();                         // 两者同时可见
```

### 18.14 流处理中的状态为什么需要持久化？

- 窗口聚合、join 缓冲、去重表都依赖跨事件的状态。
- 进程崩溃后状态丢失会导致结果错误或重复计算。
- 状态需要定期做检查点，检查点包含状态快照与输入位点。
- 状态大小可能超过内存，需要分层存储：内存、本地磁盘、远程存储。
- 恢复时间与状态大小成正比，影响故障恢复时间。
- 状态后端的选择影响吞吐与恢复时间，需要按业务权衡。

### 18.15（场景）状态恢复为什么要靠变更日志？

- 变更日志（changelog）把每次状态更新作为追加记录写入日志主题。
- 恢复时重放变更日志重建状态，不需要传输完整快照。
- 变更日志可以压缩，只保留每个 key 的最新值，降低恢复数据量。
- 与快照结合：快照提供基线，变更日志提供增量，缩短恢复时间。
- 变更日志本身走复制，具备与输入流相同的持久性保证。
- 若变更日志落后于检查点，恢复会不一致，因此两者需要对齐位点。

### 18.16 流表对偶指什么？

- 流可以看作表的变化日志，表可以看作流在某一时刻的物化结果。
- 对流的聚合产生表，对表的变更捕获产生流。
- 对偶关系使同一份数据可以在两种视图间转换，选择取决于查询方式。
- 物化视图是这一对偶的工程实现：持续消费变更流并更新本地表。
- 对偶不保证可逆：从表无法恢复历史流，除非保留变更日志。
- 设计时需要决定哪一侧是事实来源，避免双向同步产生循环。

### 18.17（设计）如何用日志构建可重建的派生视图？

- 把所有写入建模为不可变的追加日志，派生视图只读日志。
- 派生逻辑必须是确定性的，相同输入产生相同输出，便于重放验证。
- 视图重建通过重置位点并重放实现，重建期间旧视图继续服务。
- 重建完成后原子切换，避免读到部分重建的状态。
- 日志保留期必须覆盖最慢消费者的重建需求。
- 版本化派生逻辑，使结果可追溯到具体的代码版本。

```text
orders 日志（事实来源，保留 7 天）
  -> 消费者 A -> 搜索索引
  -> 消费者 B -> 分析宽表
  -> 消费者 C -> 缓存
重建：新建索引写入别名 v2，追平后切换别名，旧索引延迟下线
```

### 18.18（陷阱）多消费者写入同一外部系统时如何避免乱序？

- 同一 key 的事件必须由同一消费者按顺序处理，否则后写覆盖先写。
- 按 key 分区并保证分区内单线程消费，是最直接的方案。
- 消费者扩缩容会触发分区再平衡，再平衡期间需要停止处理或等待移交完成。
- 多个消费者组写同一目标时，需要按 key 路由到固定目标分片，或由目标端按版本号拒绝旧写。
- 重试会加剧乱序：失败消息重试时，后续消息可能已成功。
- 版本号或事件时间戳的单调校验是最后一道防线。

### 18.19（场景）数据集成为什么难以避免多个存储并存？

- 不同访问模式对应的存储引擎差异巨大：点查、全文检索、聚合分析、图遍历各有专用系统。
- 单一存储无法同时满足低延迟点查与大规模扫描，专用系统在各自场景占优。
- 因此数据被派生到多个系统，集成的目标是让派生保持一致且可重建。
- 集成的难点是顺序与重复：不同派生路径延迟不同，观察者可能看到不一致的视图。
- 解决方向是统一日志作为事实来源，派生系统只读日志，避免互相写入。
- 需要接受派生系统之间的短暂不一致，并用陈旧度指标描述。

### 18.20（设计）如何验证端到端不丢不重？

- 给每条输入打唯一标识，输出侧统计标识的覆盖与重复。
- 注入故障：消费者崩溃、位点提交失败、输出超时、再平衡，观察最终结果。
- 对比输入与输出的计数与校验和，按分区与时间窗口分别核对。
- 验证重放：回退位点重放一段历史，输出应保持不变或可被识别为重复。
- 监控位点滞后与检查点年龄，滞后突增通常先于数据问题出现。
- 结论是概率性的：测试覆盖的故障组合有限，需保留长期运行的对账作业。
