## 导读：为什么值得把包管理器当一门学问

一台新机器上最先被安装的东西往往是包管理器，而它也是整台机器上最少被人真正读懂的部件。

大多数人跟它的关系停留在几组条件反射：

- 缺个工具，`apt install` 或 `dnf install` 一下
- 项目跑不起来，`rm -rf node_modules && npm install` 一下
- 版本不对，`nvm use` 或 `pyenv global` 一下

这些反射大部分时候有效，直到某天失效：包装不上、装上了跑不起来、昨天还是绿的 CI 今天红了、某条构建日志里冒出一个你没听说过的包名。失效的原因几乎从不在命令本身，而在于我们没搞清命令背后那台机器：谁在决定版本、谁在执行代码、谁在缓存什么、失败时到底是哪一层在报错。

## 术语与约定

中文技术写作里最容易含糊的几组词，这里先定死：

- **包（package）**：可被安装的最小分发单位。它可能是二进制（`.deb`、`.rpm`、wheel），也可能是构建脚本或源码（crate、sdist、PKGBUILD、ebuild）。
- **制品（artifact）**：构建设计产出并被分发的东西，范围比“包”更宽，容器镜像也属于制品。
- **仓库（registry / repository）**：发布与索引服务，如 npm registry、PyPI、crates.io、Maven Central。本文一律叫“仓库”。
- **源（source / mirror）**：镜像、代理或本地私有服务，如 `sources.list` 里的条目、国内镜像站、企业 Nexus。本文一律叫“源”。
- **清单（manifest）**：声明**约束**的文件，如 `package.json`、`Cargo.toml`、`pyproject.toml`、`requirements.in`。
- **锁文件（lockfile）**：记录**求解结果**的文件，如 `package-lock.json`、`Cargo.lock`、`poetry.lock`。清单与锁文件的区别是理解全文的一把钥匙。
- **求解（resolution）**：从约束集合中选出一组具体版本的过程。
- **隔离（isolation）**：让不同项目或不同版本的依赖互不干扰的机制，形式从目录嵌套到内核命名空间都有。
- **系统级 / 语言级 / 应用级**：分别指发行版包管理器、语言生态包管理器、以及 Flatpak／容器这类以整个应用或镜像为单位的分发机制。

命令示例以 Debian/Ubuntu、macOS 和 Windows 为主，涉及其他发行版时单独标注。示例中的包名、路径与版本以写作时（2026 年）的现状为准；包管理器是变化最快的软件之一，遇到不一致时以官方文档为准。

## 第一部分 · 原理

### 1 包管理器替代了哪些手工劳动

在没有包管理器的年代，装一个库有一套固定的手工流程：去项目主页找下载页，挑一个 tarball，解压到 `/usr/local/src`，读 `README` 和 `INSTALL`，跑 `./configure`。`configure` 常常在第一步就失败，因为缺头文件——你得先知道这个库依赖谁，而这件事通常只写在 `README` 的一行小字里。补完依赖再 `make`，编译报错指向某个 API 变了，于是回头换一个更旧的版本重来。最后 `make install`，文件散进 `/usr/local/lib`、`/usr/local/include`、`/usr/local/bin`。半年后要卸载，你只能凭记忆删文件，或者干脆留着。

这段流程的每个环节都不是技术难点，而是**账本问题**：谁依赖谁、装了什么版本、文件放在哪、怎么回退。人脑不擅长记账，所以问题会以最别扭的形式爆出来——编译到一半缺头文件，或者升级一个库之后另一个程序启动就段错误。

包管理器的价值可以拆成九件事，前六件让它能替代手工流程，后三件让它比手工流程更可靠：

| 承诺 | 具体含义 | 机制所在 |
|---|---|---|
| 发现 | 按名字找到包，不用记住下载地址 | 仓库与索引（见第 7 章） |
| 版本选择 | 从多个版本里挑一个满足约束的 | 依赖求解（见第 3 章） |
| 传递依赖 | 自动把依赖的依赖也装上 | 同上 |
| 构建 | 需要编译时由工具代跑构建 | 源码分发（见第 2 章）、安装脚本（见第 8 章） |
| 安装到正确位置 | 文件落点由工具决定并登记 | 数据库 |
| 冲突检测 | 两个包要同一个文件时能发现 | 求解器与数据库 |
| 升级 | 知道当前版本，能算出可升级的版本 | 数据库 + 求解器 |
| 卸载 | 精确删除自己装的文件，不动别人的 | 文件清单 |
| 来源校验 | 校验哈希与签名 | 见第 35、36 章 |

把这张表压成一句话：包管理器本质上是**数据库 + 求解器 + 分发网络**。数据库记录“本机装了什么、每个包装了哪些文件”；求解器决定“应该装哪些版本”；分发网络负责“把内容取下来，且取到的东西可以验证”。下载只是分发网络里最不重要的那一环——`curl` 也能下载。

这个视角能解释很多看似奇怪的现象。为什么 `apt` 需要先 `update`？因为“哪个包有哪些版本”存在本地索引里，索引过期，求解器就是在解一道错误的题。为什么在 PEP 668 之前 `pip install` 会建议 `--user`？因为写入系统目录需要权限，而在数据库层面，用户级安装与系统级安装是两套账本。为什么两个包管理器装同一个软件会打架？因为两套数据库互不知情，各自的文件清单都认为自己拥有那些文件。

边界也要划清。包管理器不负责“怎么把代码变成产物”——那是构建系统的事（见第 31 章）；不负责“装哪个语言运行时版本”——那是版本管理器的事（见第 32 章）；也不负责“把整个应用连同运行时一起发出去”——那是容器与 Flatpak 这类机制的事（见第 29、30 章）。它们经常被混为一谈，因为它们都要读写磁盘、都要改 `PATH`，但账本是分开的。

> 一句话总结：包管理器的核心是账本与求解器，下载只是它最容易被替代的一部分。

### 2 包的形态：源码分发与二进制分发

同一个包名，可能是两种完全不同的东西：一份可以直接铺到磁盘上的预编译产物，或者一份必须先在你这台机器上编译的源码加构建脚本。

二进制分发是发行版的主流形态。Debian 的 `.deb`、Fedora 的 `.rpm`、Alpine 的 `.apk`、Windows 的 MSI、Python 的 wheel，里面都是已经编译好的文件加元数据。Python 的 wheel 文件名把兼容性写进了名字里：`numpy-2.0.0-cp312-cp312-manylinux_2_17_x86_64.whl` 依次声明 CPython 3.12、CPython ABI、Linux 的 glibc 下限 2.17、x86-64 架构。装不上的时候，pip 报的错通常是“找不到匹配的发行版”——它其实在说：索引里没有一份能在你这台机器上运行的二进制，而源码构建又失败了。

源码分发则是另一套账。Rust 的 crate 发布到 crates.io 的是源码，用户本地用 `cargo build` 编译；Go module 也是源码；Debian 的 source package、Arch 的 `PKGBUILD`、Gentoo 的 ebuild、Nix 的 derivation，都是“构建配方”而非产物。配方的价值在于用户能改：Gentoo 的 `USE` 标记、Nix 的 derivation 参数、`PKGBUILD` 里的编译选项，都允许在构建时做选择。代价同样明确：用户机器上得有完整工具链，构建时间从几十秒到几小时不等，构建过程中还得联网取更多依赖，而且**同源码不同机器不一定编译出同样的东西**（见第 8 章）。

二进制分发的代价集中在构建矩阵。一个包要覆盖 glibc 与 musl 两套 C 库、x86-64 与 aarch64 两种架构、若干 Python 版本，产物数量很快变成两位数。这就是为什么 manylinux 这类规范存在：它把“最低 glibc 版本”变成一个可以写进文件名的标签，让一份产物能覆盖一片系统。这也解释了 Alpine 上装 Python 包的经典困境——musl 与 glibc 不兼容，linux 版 wheel 直接不可用。CPU 指令集同理：为 `x86-64-v3` 编译的二进制在老机器上会直接非法指令退出，而包管理器在解析阶段无从得知。

元数据是两种形态共有的部分，也是包管理器的真正抓手：包名与版本、依赖声明、冲突声明、文件清单、安装与卸载脚本、以及哈希或签名。差别在于谁来生成。二进制包的元数据由打包者写好后封进包里，安装时直接读；源码包的元数据部分来自包自己的清单（`Cargo.toml`、`pyproject.toml`），部分要跑一遍构建才能得到——Python 的 `setup.py` 时代尤其如此，依赖声明甚至可能在安装时动态计算出来，这使得“先求解、后安装”的顺序在 Python 里长期无法彻底成立（见第 20 章）。

各生态的选择很能说明问题。Rust 与 Go 习惯源码分发，因为语言自带构建系统、生态包普遍很小、跨平台编译足够简单；Debian 与 Arch 严格二进制，因为“用户机器上什么都装得出来”是发行版不能接受的假设；Nix 两头都做，但无论源码还是二进制都先落进 store，用输入哈希决定路径，把两种形态统一到同一个寻址模型里（见第 17 章）。没有哪种更先进，只是对“谁来承担构建成本”这一问题给出了不同答案。

> 一句话总结：源码分发把成本推给用户换灵活性，二进制分发把成本压给打包者换速度。

### 3 依赖求解：从贪心到 SAT

依赖求解（dependency resolution）可以形式化得很干净：给定一组包、每个包的若干版本、每个版本的依赖约束，求一组版本赋值，使所有被选中版本的依赖都成立，且“同一个包最多选一个版本”这条隐含约束也成立。后者是关键，它把“顺着图走一遍”变成了搜索。

把每个包版本看作布尔变量，“选 A 就必须选 B 的某个版本”写成逻辑蕴含，问题就等价于布尔可满足性问题（SAT），而 SAT 是 NP 完全的。但**最坏情况不等于常见情况**：真实图里相邻版本的需求高度相似、可选解极多，多数求解根本不必回溯。uv 的官方文档说得很直接——理论上要穷举所有组合，实践中“对大多数解析，求解器不需要回溯，迭代地挑版本就够了”。所以衡量求解器的标准有两个：需要回溯时是否高效，失败时能否解释原因。

现实策略大致分四类。

**优先取最新的深度优先回溯（没有冲突学习）**：按顺序把依赖排成队列，每个依赖优先挑最新的可行版本，走不通就回溯到上一个决策点换一个候选，直到找到一组解或穷尽所有候选。Cargo 官方文档的伪代码正是这个形状（`pick_next_dep` 选依赖、`pick_next_version` 优先取最新、失败则回溯）；`pip` 自 20.3 起默认的解析器（resolvelib）也属于这一类，它偶尔长时间卡在“正在解析依赖”正是回溯在起作用。代价是最坏情况要遍历大量组合，而且**失败时说不出为什么**：没有冲突学习的实现给不出跨多层传递依赖的解释。

**回溯加冲突学习**在采用回溯的解析器里已是主流做法之一（PubGrub 系：uv、Poetry、Dart 的 pub），源自 SAT 里的 CDCL（冲突驱动子句学习）：冲突时把根因记成一条“不可兼得”的事实，以后遇到同样组合直接跳过。PubGrub 的实现文档说明它据此生成人类可读的解释，形如“因为 `foo <1.1.0` 依赖 `a ^1.0.0`，而 `a` 依赖 `b ^2.0.0`，所以 `foo <1.1.0` 需要 `b ^2.0.0`；又因为 `foo <1.1.0` 依赖 `b ^1.0.0`，`foo <1.1.0` 被禁止”。uv 用 Rust 的 pubgrub-rs，Dart 的 pub 属同一谱系。

**完整的 SAT 求解**把问题编码成布尔公式交给通用求解器，libsolv 是这条路线最知名的实现，被 openSUSE 的 zypper 使用。它能力上限高，能顺带表达“两个包不能共存”“尽量保留已安装版本”这类非依赖约束；代价是编码开销，以及错误信息是求解器视角的（“不可满足的子句集”），离用户的语言较远。

**放弃全局求解**换了一条路：让同一包的多个版本共存于不同子树，冲突自然消失。npm 早期的嵌套 `node_modules` 就是这个模型，代价是目录爆炸、同一份代码被装多次、幻影依赖（见第 6 章）。Maven 的依赖调解（dependency mediation）按“最近优先”挑版本，同深度时先声明者胜出；它不搜索，所以不会解析失败，而是可能悄悄选错版本，症状变成运行时的 `NoClassDefFoundError`（见第 23 章）。Go 的 MVS 更彻底，把“选最新可行版本”换成“取所有约束里最高的最小版本”，问题退化成图遍历，代价是升级不积极（见第 22 章）。

最后是判断标准。**“找不到解”和“解不是你想要的”是两回事**：前者是求解空间为空，需要解释谁和谁冲突、卡在哪条路径；后者是合法解很多而求解器选得意外——Cargo 文档承认，`>=0.6` 这类开放约束会让解析器不做去重，产出两份本可合并的依赖，要用 `cargo update --precise` 收拾。两类问题的修复手段完全不同。

> 一句话总结：求解器之间的差距不在能不能解，而在回溯效率与失败时能否讲清原因。

### 4 版本约束的方言

语义化版本（SemVer）只承诺一件事：`MAJOR.MINOR.PATCH` 中只有 major 递增才允许破坏兼容。它管不到的比管得到的更多——行为兼容、性能、传递依赖变化都不在承诺内（见第 9 章）。而各生态“如何把约束写下来”的方言差异，比语义本身大得多。

同一个意图——“至少 1.2.3，但不跨到 2.0.0”——写法如下：

| 生态 | 写法 | 展开后的实际范围 |
|---|---|---|
| npm / Cargo | `^1.2.3` | `>=1.2.3 <2.0.0` |
| Cargo 默认 | `1.2.3` | 同 `^1.2.3`，Cargo 的裸版本号就是 caret |
| npm 默认 | `1.2.3` | 恰好 `1.2.3`，npm 的裸版本号是精确匹配 |
| Python（PEP 440） | `>=1.2.3,<2.0.0` | 需要显式写出上下限 |
| Maven | `[1.2.3,2.0.0)` | 方括号含、圆括号不含 |

上表里最值得记住的是第三、四行：**裸版本号在 npm 与 Cargo 里含义相反**。`npm install lodash@1.2.3` 与 `Cargo.toml` 里写 `lodash = "1.2.3"` 看似一样，前者钉死一个版本，后者是一个区间。这是两套默认值哲学：npm 把“我测过这个版本”当默认，Cargo 把“我要兼容的语义范围”当默认。

其他方言的细节同样不能凭直觉。npm 的 `~1.2` 和 `1.2.x` 都等价于 `>=1.2.0 <1.3.0`；npm 的 caret 在 0.x 上会收紧，`^0.2.3` 是 `>=0.2.3 <0.3.0`，`^0.0.3` 是 `>=0.0.3 <0.0.4`，因为 0.x 没有兼容性承诺。Cargo 的兼容性定义是“最左侧非零位相同”，`"0.2.3"` 同样等于 `>=0.2.3, <0.3.0`；Cargo 的 `~1` 是 `>=1.0.0 <2.0.0`，npm 的 `~1` 同样等价于 `1.x`。Python 的 `~=` 是“兼容发布”子句，语义反直觉：`~=2.2` 等价于 `>=2.2, ==2.*`（不允许写成 `~=2`），`~=1.4.5` 等价于 `>=1.4.5, ==1.4.*`，想收紧范围就多补一个零，`~=2.2.0` 变成 `>=2.2.0, ==2.2.*`。Maven 的区间支持并集与排除：`(,1.0],[1.2,)` 表示“≤1.0 或 ≥1.2”。

`*` 与 `latest` 是另一个坑：Cargo 官方建议避免 `*`，crates.io 不允许发布带裸 `*` 的依赖，因为它会在一次普通的 `cargo update` 里把不兼容的 major 拉进来。Go 把所有约束写成“最小版本”：`require example.com/mod v1.2.3` 意思是“至少 1.2.3”，最终取图中所有约束里最高的最小版本，所以 Go 的约束不含上限。日期版本（CalVer）也常见：Ubuntu 用 `24.04` 表示 2024 年 4 月，排序天然正确、人能读懂时间，代价是它不携带兼容性语义。

预发布、构建元数据、本地版本号这三类差异最集中。预发布（`1.0.0-beta.1`）几乎在所有生态里都默认被排除，除非显式写出：Cargo 的 `foo = "1.0"` 不匹配 `1.0.0-alpha`，要写 `foo = "1.0.0-alpha"`；PEP 440 规定已安装的预发布可被接受，别处的预发布只在没有正式版本能满足时才考虑；uv 把这条做成开关，默认 `if-necessary`，另有 `allow`、`disallow`。构建元数据（`+` 之后的部分）几乎一律被忽略：Cargo 明确说版本元数据不应用于约束，Go 会把带构建元数据的版本转成伪版本（pseudo-version）以维持全序。本地版本号（`1.0.0+local`）是 Python 特有机制，PEP 440 允许下游用它标记“与上游 API 兼容但打了补丁的重建版本”，同时明确要求 PyPI 不接受它——它是给发行版与私有源用的。

最后是**上限（upper bound）之争**：库该不该在依赖里写 `<2.0`？

主张设上限的理由是：库可能在小版本里悄悄破坏构建，上限能保证发布时验证过的组合在未来也成立。反对的理由是上限会传染：若 A 依赖 `B >=1.2,<2`，而 `B 2.0` 早已发布且被 C 需要，整张图可能因 A 的上限而无解。更糟的是上游被卡住时的常见应对是“发布一个去掉上限的旧版本补丁”，求解器于是回溯到更老、更少人用的版本，问题被掩盖而非解决——uv 的文档把这个现象写进了它忽略 `requires-python` 上限的理由里。

现实分布：npm 与 Cargo 默认不设上限（Cargo 建议不要写比下一个不兼容版本更窄的上限，如 `~2.0`、`>=2.0,<2.4`）；Python 社区偏向设上限，尤其是带 C 扩展或与运行时强耦合的包。判断条件可以写出来：**叶子依赖（你独占它）的上限成本与收益都归你；公共库的上限成本会转嫁给整张依赖图。** 区间越宽越好装、越窄越可复现，这是同一枚硬币的两面；真正的解法通常不是调区间，而是把可复现性交给锁文件（见第 5 章）。

> 一句话总结：约束方言的差异是默认值哲学之争，上限问题该按“谁承担成本”判断。

### 5 锁文件：可复现性的最小代价

#### 锁文件记录的是求解结果

清单（`package.json`、`Cargo.toml`、`pyproject.toml`）写的是约束，锁文件写的是这台机器在某个时刻对约束求解出来的答案。约束是“我可以接受哪些版本”，答案是“这次我拿了哪个版本、从哪个地址拿的、它的哈希是多少”。这个区别决定了很多事：改清单不一定让锁文件失效（放宽区间、加一个可选依赖都可能不需要重解），改锁文件却几乎一定要求清单能解释它——`npm ci` 和 `--frozen-lockfile` 检查的正是这条一致性；同一条清单在不同时间、不同平台、不同镜像上可以解出不同的答案。

求解器默认偏向“最新可行版本”，所以不提交锁文件的项目，今天的构建和六个月后的构建不是同一个东西。

一个具体的例子：同一个 `package-lock.json` 里，`node_modules/lodash` 对应的条目会写明 `4.17.21`、`resolved` 里的下载地址，以及 `integrity` 里的内容哈希。三样东西分别回答了“哪个版本”“从哪拿”“拿到的是不是同一份字节”。清单里对应的只是 `"lodash": "^4.17.0"` 这一行约束。

#### 各生态的形态对照

| 生态 | 文件 | 粒度与校验 |
|---|---|---|
| npm | `package-lock.json` | 完整依赖图 + `integrity` 哈希 |
| pnpm | `pnpm-lock.yaml` | 完整图 + 完整性哈希，导入方与快照分离 |
| Yarn | `yarn.lock` | 完整图 + 校验和 |
| Python（uv） | `uv.lock` | 全域锁，覆盖所有平台与 Python 版本标记 |
| Rust | `Cargo.lock` | 完整图 + 校验和 |
| Go | `go.mod` + `go.sum` | 没有锁文件；`go.sum` 只做校验 |
| .NET | `packages.lock.json` | 需显式开启锁定恢复 |
| Ruby | `Gemfile.lock` | 完整图，含平台标记 |

Go 是个例外中的例外：最小版本选择是确定性的，构建列表每次重新计算都一样，所以不需要像 npm 那样保存一份答案，`go.sum` 只负责防止内容被篡改。这也说明“锁文件”不是包管理的必备件，而是“求解结果不稳定”这个前提的补丁。

#### 库与应用：惯例不同

应用提交锁文件，库通常不提交。理由是库的消费者会自己求解，库锁死自己的依赖只会把过时的版本钉在别人身上。Rust 官方在 2023 年调整过这条指引：不再区分库与二进制，建议以提交 `Cargo.lock` 为默认，`cargo new` 也不再把库的锁文件写进忽略规则；理由是便于二分定位问题、验证 MSRV，以及给 CI 一个稳定的起点。

升级靠改锁文件而不是改清单：`npm update`、`cargo update`、`uv lock --upgrade` 都在不动约束的前提下重解。CI 则相反，要拒绝重解：`npm ci`、`pnpm install --frozen-lockfile`、`uv sync --locked`、`cargo build --locked`，锁文件与清单不一致时直接失败。

#### 锁文件锁不住的东西

常见事故有三类。Git 合并锁文件时冲突，人肉手改的版本组合多半没被求解器验证过，正确做法是接受任一版本后重新生成。跨平台可选依赖会漏：`esbuild`、`sharp` 这类包把平台二进制放在 `optionalDependencies` 里，锁文件只记下了解析时所在平台的条目，换平台需要重解。镜像与锁文件的哈希对不上时，安装器会拒绝而不是降级使用，这是设计如此。

更根本的一点：锁文件只固定了包，不固定工具链。Node 版本、Python 解释器、C 编译器、构建时的环境变量都不在锁文件里，而它们同样影响结果。真正的可复现要一路钉到工具链和构建环境（见第 30、31 章）。

> 一句话总结：锁文件把“这次解出了什么”变成可提交的产物，但它只锁住依赖，锁不住工具链和构建环境。

### 6 隔离：从全局到项目级

#### 三种隔离目标

隔离要解决三个层次的问题：依赖版本互不干扰、可执行文件指向正确的那个版本、构建环境互不污染。多数工具只做前两件。前两件是显而易见的失败——同一个库的两个版本装在同一处必然互相覆盖；第三件要隐蔽得多，它在你写了原生扩展、需要头文件和编译器时才会暴露，而且暴露的方式是“在你机器上能编过”。

| 机制 | 做法 | 代价 |
|---|---|---|
| 嵌套 `node_modules` | 每个包带自己的依赖目录 | 目录极深、重复安装 |
| 提升（hoisting） | 能合的依赖提到顶层共享 | 产生幻影依赖 |
| pnpm store + 符号链接 | 内容寻址存储 + 硬链接 + 严格符号链接 | 布局非常规，工具兼容问题 |
| venv | 改 `sys.prefix`，隔离 `site-packages` | 只隔离 Python 包，不隔离解释器与系统库 |
| conda 前缀 | 每个环境一个前缀目录 | 需要单独分发二进制，体积大 |
| Nix store | 输入哈希决定路径 | 路径不像 FHS，编译适配麻烦 |
| 容器 | 文件系统与进程命名空间 | 最彻底，也最重 |

这张表里没有“免费”的选项：隔离越强，构建与调试的隐式假设就越多地被打破，团队要么接受这份成本，要么在某个环节重新放开。

#### hoisting 与幻影依赖

历史上 npm 早期用的是纯嵌套布局，目录能深到突破 Windows 的路径长度限制，磁盘占用也成倍增加。扁平化是对这个问题的直接回应。

npm 从嵌套改成扁平化，是为了让共用依赖只装一份。规则是：同名同版本尽量提到顶层 `node_modules`，版本冲突的留在需要它的包的 `node_modules` 里。结果是顶层目录里堆了一大批你没有声明过的包。

Node 的解析算法会沿父目录逐级向上找 `node_modules`，于是 `require('semver')` 这种代码即使你从未声明 `semver`，只要它恰好被别的依赖提升上来，本地就能跑。这就是幻影依赖（phantom dependency，也叫幽灵依赖）。CI 挂掉的原因是安装顺序、包管理器版本或锁文件状态的细微差别让那次提升没有发生。

pnpm 用符号链接把“谁能看到谁”写死在目录结构里，只暴露声明过的依赖，因此天然拒绝幻影依赖；代价是它默认仍会为兼容破损包做一层提升，要完全严格需要显式关闭提升。Yarn PnP 更进一步，直接不生成 `node_modules`，改用 `.pnp.cjs` 这个解析器接管 `require`，把未声明的访问变成带包名的报错。代价是生态里那些依赖幻影依赖的包会当场报错，编辑器与工具链也要额外适配。

诊断手段：`npm ls <pkg>` 会打印这个包在树里的位置以及是谁依赖了它；`npm dedupe --dry-run` 能看出还有哪些重复版本可以被合并；pnpm 的 `why <pkg>` 直接给出解析路径。

#### PATH 与 shim

可执行文件是第二层隔离。`node_modules/.bin` 下的脚本是 npm 生成的 shim，Windows 上会额外生成 `.cmd` 与 `.ps1`，共三个文件；`bundle exec`、`uv run`、`poetry run`、`npx` 走的都是“先切环境再执行命令”这条路。它们的差别在隐式程度：`bundle exec` 要求你显式调用，`direnv` 和 Nix devShell 直接改你的 shell 环境，方便但让“当前用的是哪个版本”变得不可见。隐式的代价是排查变难，显式的代价是每条命令都要多打几个字。

全局安装没有被淘汰，是因为它服务的是另一类需求：CLI 工具需要在任何目录下可用，系统集成需要固定路径。当同一个包既有 CLI 又是库，全局安装与项目依赖就会打架——全局的 `eslint` 和项目里的 `eslint` 版本不同，报错行为也不同。这类工具更适合用“独立环境安装”的办法（见第 20、38 章）。

> 一句话总结：隔离的难点不在版本，而在可执行文件与构建环境；hoisting 用便利换来了幻影依赖。

### 7 仓库、镜像与私有源

#### 中央仓库的构成

一个仓库由四件事组成：包文件的存储、可查询的元数据索引、搜索与发布 API、命名空间与所有权规则。前两个决定安装能不能成功，后两个决定生态能长成什么样。

命名空间是最容易被忽略的一条。npm 的全局命名空间先到先得，scope 只是可选的一层，因此名字冲突只能靠争议处理流程解决；crates.io 干脆不提供命名空间，包名先到先得；Maven Central 用 `groupId` 做组织边界；PyPI 也没有命名空间，只能靠项目名唯一性。名字的所有权规则直接决定了仿冒包（typosquatting）的空间有多大，这个代价在安全章节会再次出现（见第 34 章）。

#### 索引形态决定能力边界

索引怎么组织，决定了搜索、镜像与离线能做到什么程度。

npm 的索引是“每个包一个元数据文档”，客户端拿到包名就能取版本列表与下载地址。PyPI 的 Simple API 是“每个项目一个页面，列出全部文件链接”，简单到可以用静态文件实现。Cargo 从 Git 索引换成了稀疏 HTTP 索引：客户端不必克隆整个索引仓库，只请求自己需要的那几个前缀路径。Debian 走的是另一条路：`apt update` 把仓库的 `Packages` 索引与签名一起下载到本地，此后查询、依赖计算全部离线完成。Go 的模块代理是一套定义明确的 HTTP 协议，`GOPROXY` 可以列多个地址，前一个返回 404 就试下一个。

理解这个差异，就能解释很多现象：为什么 `apt` 需要 `update`，而 `npm install` 不需要；为什么在 Debian 上离线仍然能 `apt-cache policy`，而在 Node 里离线连版本列表都拿不到。

#### 镜像、代理与离线

镜像（mirror）是完整复制，代理（proxy）是按需缓存。两者的失败模式不同：镜像会滞后，滞后期间你看到的版本列表是旧的，锁文件里写着一个镜像上还不存在的版本时，安装直接失败；代理则可能在首次请求时变慢或失败，但它缓存过的制品是确定的。

企业里常见的是 Nexus、Artifactory 这类工具，它们同时扮演三种角色：远程代理、内部包宿主仓库、聚合多个源的虚拟仓库。虚拟仓库的源顺序是有语义的——顺序错了，内部包名可能被公网同名包抢先（见第 33、34 章）。

离线安装的手段按生态各不相同：`apt-get download` 拿的是已编译的二进制包，可以直接进离线仓库；`pip download` 与 `npm pack` 拿的是注册表里的分发产物（可能是预编译 wheel，也可能是 sdist 或源码 tarball），离线环境里仍然可能要编译；`cargo vendor`、`go mod vendor` 复制的是源码，离线环境里仍然要能编译。后者看起来更“干净”，但它把编译器和构建依赖也变成了你必须在离线环境里解决的问题。

#### 可用性是被低估的风险

中央仓库挂掉，全球 CI 一起红。这不是假设，而是大多做过大规模 CI 的团队都遇到过的事。缓解办法有几层：在企业代理里缓存已有制品，让已发布版本的安装不依赖上游；给 `npm install` 这类命令设好重试与超时；把“必须联网”这一步压到最小——有了锁文件和本地代理，只有首次拉取新版本才需要真正的网络。

> 一句话总结：仓库的索引形态决定了查询与离线的能力上限，而命名空间规则决定了生态要付多少仿冒成本。

### 8 安装时执行代码：一切矛盾的根源

#### 谁在安装时执行代码

“安装”这个动作在很多生态里并不只是把文件复制到某个目录。

npm 里，依赖包可以声明 `preinstall`、`install`、`postinstall`，以及发布前的 `prepare`；原生模块还会隐式触发 `node-gyp` 编译。Python 装 sdist 时要走构建后端（PEP 517）：pip 先临时装好 `[build-system] requires` 里的依赖，再调用后端把源码变成 wheel，这一步执行的是上游仓库里的构建代码。Cargo 把 `build.rs` 编译成可执行文件，在构建包之前运行它；它能读环境变量、跑任意命令、把产物写进 `OUT_DIR`。Debian 的 `preinst`、`postinst`、`prerm`、`postrm` 由 dpkg 以 root 执行。Nix 则把构建放进沙箱，限制网络与可写路径，让“构建时执行代码”这件事变成可控输入。

#### 为什么它无法回避

因为它承担了三件正事：编译原生扩展、在安装时下载平台相关的二进制、生成代码（解析器、协议定义、绑定）。这些工作都发生在制品被消费的那一刻，而不是打包的那一刻。

代价也很直白：安装脚本的权限等同于运行安装的那个用户。一个依赖链深达几十层的包，它的 `postinstall` 和你自己写的脚本权限完全一样：能读你的凭据文件、能改你的 shell 配置、能向外发请求。这就是第 34 章那一整套威胁模型的物理基础：投毒不需要攻击你的构建系统，只要让你的包管理器去装它。

#### 三种应对及其代价

| 应对 | 做法 | 代价 |
|---|---|---|
| 禁止 | `npm ci --ignore-scripts`、只允许 wheel | 需要编译的包直接装不上 |
| 隔离 | 容器内安装、非 root 用户、Nix/Bazel 沙箱 | 搭建与维护成本，构建产物要重建 |
| 审计 | provenance、attestation、只允许 allowlist | 生态覆盖不全；只证明构建来源（谁、从哪个 commit、什么流程），不代表内容安全 |

三种应对都不是免费午餐。禁止最省事，但把“需要编译”的包全判了死刑，实践中往往只在 CI 或不可信依赖上使用，本地开发又放开，于是策略在最需要它的地方被绕过。隔离最彻底，但要求你把构建环境也声明化，否则沙箱只是换了个地方执行同样的命令。审计依赖 registry 与构建服务的配合，它回答的是“这个制品从哪个 commit、由谁构建”，而不是“这段构建脚本干了什么”（见第 36 章）。

近两年最大的变化是默认值在移动。npm v12 起，依赖的生命周期脚本与隐式 `node-gyp` 构建默认不再执行，Git 依赖与远程 URL 依赖默认也不解析，需要显式允许并提交一份 allowlist。这说明“默认拒绝执行”在主流生态里已经可行，剩下的问题是如何处理那批确实需要构建的包。

#### 与可复现构建的冲突

安装脚本与可复现构建天然冲突：脚本可以读网络、读时间、读编译器版本、读环境变量，同样的输入不保证同样的输出。哈希锁定只能保证“同一个文件”，保证不了“同一次构建”。

Bazel 和 Nix 走的路线是把构建动作本身建模成有输入输出的动作，谁执行了、读了什么、产出了什么都要能被记录和缓存，这样才谈得上可复现。代价是你必须为构建产物建立缓存和描述，而不是简单地运行一个脚本。

> 一句话总结：安装脚本的安全等级，等于你愿意给 registry 和整条上游依赖链的信任等级。

### 9 兼容性、语义化版本与现实

#### SemVer 承诺了什么，又管不到什么

语义化版本（Semantic Versioning）的承诺只有一句：主版本号增加才允许破坏向后兼容。它管不到的东西比管得到的多：类型定义可以变严（同样调用在新版本里编译不过）、运行时行为可以变（边界条件、错误类型、默认值）、性能特征可以变、传递依赖可以变。最后一条最容易被忽略——一个 patch 版本可以只是升级了自己的依赖，然后经由那条路径传进来一个不兼容变更。

多数生态还给 `0.x` 开了后门：Cargo 把 `0.x` 的次版本升级视为可能破坏兼容的变更，Go 明确写着主版本为 0 的模块不受兼容性要求约束。这不是漏洞，是承认“还没定型的东西不能假装有承诺”。

#### 依赖数量是乘法

假设单个依赖在一个月内发生破坏性变更的概率是 p，你有 n 个传递依赖，那么“至少有一个出问题”的概率是 1−(1−p)^n。p 很小时这个数看似可以忽略，但现代应用的 n 常常是几百到上千，于是它迅速逼近某个不能忽略的值。这就是定期升级比一次性大升级更安全的原因：不是升级本身变安全了，而是每次升级引入的未知量变小了。

left-pad 事件是另一种失败：不是兼容性破坏，而是上游撤包。2016 年，一个作者撤下了自己的 273 个包，其中一个被 `babel`、`webpack`、React Native 等通过 `line-numbers` 间接依赖且明确要求了 `0.0.3` 这个版本，全球构建在几十分钟内成批失败。这次事故之后 npm 收紧了撤回策略。它说明可复现性不仅依赖版本号存在，还依赖那个版本的制品仍然存在。

#### 两种策略

宽区间 + 锁文件 + 定期小步升级：日常开发不用频繁重解，CI 用冻结模式保证一致，每周或每两周由升级机器人提 PR，冲突小、可回滚。它的代价是锁文件里的版本会逐渐落后于上游，安全修复需要有人推动。

严格 pin + 定期大升级：版本确定，纪律性强，适合发布节奏固定的产品。代价是升级变成一件大事，攒得越久越难做，最终常常演变为“不升级”。

判断条件很实际：如果项目依赖多、人力少、发布频繁，选前者；如果合规要求版本可追溯、或者依赖很少，后者也成立。

#### monorepo 与上游弃维护

monorepo 里的内部包通常走本地链接而不是发布，好处是改动即刻反映，坏处是“本地能跑”不再需要发布验证，容易掩盖版本声明错误。一旦要对外发布，就出现了一致性问题：多个包如何同版本发布、依赖内部包时写范围还是写精确版本、发布顺序怎么保证。

上游不再维护时只有四条路，每条都有代价：fork 并自行维护，你得接住后续的安全修复与兼容适配；vendor 进仓库，一劳永逸地冻结，但从此收不到任何上游更新；换成替代实现，迁移成本集中在 API 差异与测试覆盖；接受风险，但要写下来并规定复查时间，否则“暂时先用着”会变成默认状态。

> 一句话总结：SemVer 只承诺 API 兼容，不承诺行为与依赖树兼容；依赖越多，唯一安全的升级方式是步子迈小。

## 第二部分 · 系统级包管理器

### 10 dpkg 与 apt：Debian 系的基石

#### 两层分工：装单个包，和管整个依赖图

Debian 系把一件事拆给了两个程序。dpkg 做最底层的工作：解开一个 `.deb`、把文件写到文件系统、在 `/var/lib/dpkg/` 里登记状态。它不联网、不认识仓库、不解决依赖。apt 建在 dpkg 之上，负责索引、求解与下载，最后把一串操作交给 dpkg 依次执行。

这个分工解释了最常见的翻车方式：`dpkg -i foo.deb` 缺依赖时不会回滚，而是把包解包完成、状态标成未配置，于是系统进入“半装”状态，后续所有 apt 操作都被这一个坏包卡住。正确做法是把本地文件也交给 apt：

```bash
sudo apt install ./foo.deb
```

前导的 `./` 不是风格问题，没有它 apt 会把参数当包名去仓库里找。真被 `dpkg -i` 弄坏了，用 `sudo apt --fix-broken install` 让求解器补齐缺失依赖，这比逐个手工 `dpkg -i` 依赖干净。

#### sources：旧格式与 deb822

索引来自 `/etc/apt/sources.list` 与 `/etc/apt/sources.list.d/`。传统格式一行一个源：

```text
deb https://deb.debian.org/debian trixie main contrib non-free
```

新的 deb822 格式把每个源写成一个小节，字段化、天然支持多行与逐源签名密钥，文件名以 `.sources` 结尾：

```text
Types: deb
URIs: https://deb.debian.org/debian
Suites: trixie
Components: main contrib non-free
Signed-By: /usr/share/keyrings/debian-archive-keyring.gpg
```

两者可以共存，apt 都读，所以迁移不必一次性完成；Debian 13 与 Ubuntu 24.04 起，安装器默认生成 deb822 的 `.sources` 文件，旧的一行式 `sources.list` 仍被支持但已进入弃用过程（Debian 13 为此提供了 `apt modernize-sources`）。`apt update` 只刷新索引，不安装任何东西；只跑 `upgrade` 而不先 `update`，等于用过期库存做决策，是“明明有新版本却装不上”的常见原因。

#### upgrade 与 full-upgrade：差别不在激进度

- `apt upgrade` 只会升级已经装好的包，不安装新包，也不删除任何包。当新版本需要新的依赖或与旧包冲突时，apt 把它列进“kept back”直接跳过，系统可以停在混合状态。
- `apt full-upgrade` 允许为完成升级而安装新包、删除挡路的旧包。它不会主动卸载无关软件，但在发行版内滚动（Debian testing/sid）或大版本升级时，它删除的包可能正是你以为还在的东西。

因此判断条件很简单：升级前先跑 `apt -s full-upgrade`（`-s` 是模拟），看清“将被删除”那一段，再决定是否执行。`apt-get` 是这套逻辑的脚本友好界面，输出稳定、默认行为常年不变，适合写进自动化；`apt-cache` 负责查询元数据。较新的 `apt` 命令把两者合并并加上进度条和更短的输出，为人类交互设计，官方明确不保证其输出格式稳定——脚本里解析 `apt` 的文本属于自找麻烦。

#### 版本优先级：一个容易失控的旋钮

同一个包在多个源里出现时，apt 按优先级选版本，规则比大多数人想的更硬：

| 优先级 P | 含义 |
|---|---|
| ≥ 1000 | 允许降级安装 |
| 990–999 | 即使不属于目标发行版也安装（除非已装版本更新） |
| 500–989 | 目标发行版没有版本时才用 |
| 100–499 | 已装版本或其它发行版优先 |
| 0 < P < 100 | 仅在完全未安装时安装（P = 0 属未定义行为，不要使用） |
| < 0 | 永不安装 |

默认情况下已装版本是 100、其它可用版本是 500；Debian backports 因 `NotAutomatic: yes` 加 `ButAutomaticUpgrades: yes` 而落在 100。规则写在 `/etc/apt/preferences` 或 `/etc/apt/preferences.d/`（文件名必须以 `.pref` 结尾或不带扩展名，且按字典序解析）。pin 是强力的东西：写错一个负优先级就能让包永远装不上，而 apt 不会质疑你的偏好，它只会照做。

hold 是另一个粒度更粗的锁：`apt-mark hold <pkg>` 阻止该包被自动升级（`apt-mark unhold` 解除，`apt-mark showhold` 查看）。它和“kept back”不是一回事：前者是你的决定，后者是求解器拒绝了这次变更。第三方源（PPA、厂商仓库）的风险也要在这里理解——它们的包和系统包装在同一套路径下、以 root 权限运行维护者脚本，信任等级等同于发行版本身；deb822 的 `Signed-By` 让密钥按源隔离，比传统的全局 `trusted.gpg` 好，但 `trusted=yes` 一写，签名校验就没了。

#### 查询与清理

| 目的 | 命令 |
|---|---|
| 列出所有可升级包 | `apt list --upgradable` |
| 看某包为何是这个版本 | `apt-cache policy <pkg>` |
| 查某包装了哪些文件 | `dpkg -L <pkg>` |
| 查某文件属于哪个包 | `dpkg -S /path/to/file` |
| 查某包的状态与版本 | `dpkg -l <pkg>` |
| 删除不再需要的自动依赖 | `sudo apt autoremove` |
| 清空下载的包缓存 | `sudo apt-get clean` |
| 只清过期缓存 | `sudo apt-get autoclean` |

`autoremove` 的依据是安装时标记的“自动安装”位。早期用 `dpkg -i` 安装的包可能被标成手动，导致该删的留下；`apt-mark auto <pkg>` 可以纠正这个标记。安全更新方面，`unattended-upgrades` 默认只装安全源里的更新；内核或 glibc 升级后，运行中的进程不会自动换成新文件，`needrestart` 就是用来提示哪些服务需要重启、哪些情况必须重启机器——Ubuntu 24.04 起 server 镜像自带它并在 APT 事务末尾运行，Debian 上则需要自行安装该包才会有这个钩子。见第 30 章关于容器里 `apt-get update` 与 `install` 必须写在同一层 `RUN` 的讨论。

> 一句话总结：apt 的价值在求解器和优先级表，dpkg 只是执行器；搞混两者就是“半装”状态的来源。

### 11 rpm 与 dnf：Fedora 与 RHEL 系

#### rpm 是格式加本地库，不是包管理器

`.rpm` 既是包格式也是那个查询工具的名字。`rpm` 命令直接读 `/var/lib/rpm` 里的数据库，回答“装了什么、文件属于谁、包的元数据长什么样”，但它不联网、不解决依赖。Red Hat 系的历史就是在这之上叠求解器的历史：yum（Python）→ dnf4（Python + libdnf/hawkey，用 libsolv 做 SAT 求解）→ dnf5。装配依赖、下载、事务这一层才算包管理器。

dnf5 是一次架构重写：C++ 实现，库是 libdnf5，不再是 Python 包加插件的组合。它在 Fedora 41 起成为默认的 `/usr/bin/dnf`；Fedora 46 的变更提案（截至 2026 年秋仍在提案阶段）计划整体移除 dnf4 套件（`dnf`、`microdnf`、`libdnf` v1、`python3-dnf`、`dnf-plugins-core`）。dnf4 与 dnf5 混用被官方明确劝阻：两者的历史数据库与安装原因记录不兼容。

#### dnf5 与 dnf4 的 CLI 差异

大部分交互命令长相不变，但脚本会踩到下面这些：

- 子命令不再可省略：`dnf history <id>` 必须写成 `dnf history info <id>`；`dnf updateinfo` 变成 `dnf advisory summary`。
- 旧别名被移除：`groupinstall`/`grouplist`/`groupinfo` 一律改成 `dnf group install` 等形式。
- `dnf -v` 目前未实现；`--downloaddir` 改为 `--destdir`；`--sec-severity` 改名 `--advisory-severities`。
- 新增按源过滤的选项：`--from-repo=<id>`（只在指定源里找命令行给出的包）与 `--installed-from-repo=<id>`，取代了被删掉的 `repository-packages` 命令族。
- `config-manager` 从选项变成子命令（`dnf config-manager addrepo`、`setopt`），并且不再改原文件，而是写 drop-in 覆盖文件。
- 缓存目录变了：root 侧是 `/var/cache/libdnf5`，用户侧是 `~/.cache/libdnf5`，dnf4 的 `dnf clean all` 清不到 libdnf5 的新缓存目录。
- `best` 的默认值从 false 改成 true：求解器更倾向于“报错”而不是“跳过装不上的包”，这会让你看到以前被静默略过的依赖问题。

#### 模块流的现状

modularity（模块流）曾是 Fedora 解决“同一个包要提供多个版本”的方案：一个模块给多条流（stream），如 `nodejs:18` 与 `nodejs:20`。

结论要说得克制：Fedora 官方已在 Fedora 39 退役模块化构建，此后系统包不再以模块流分发；Fedora 46 的提案进一步把遗留的 `libmodulemd` 一并移除。但第三方仓库仍可能携带模块元数据，dnf5 也仍保留 `module` 子命令。新项目不应再依赖模块流;需要多版本共存时，容器或语言级版本管理器是更稳的路径（见第 32 章）。

#### 事务、回滚与 zypper

dnf 会记录每一次事务，这是它相对 apt 的一个明显优势：

```bash
sudo dnf history list          # 看事务编号
sudo dnf history info 42       # 看某次事务装删了什么
sudo dnf history undo 42       # 反向执行
```

`undo` 的可靠边界要说清楚：它反的是包集合与版本，不反服务重启、不反配置文件改动、也不保证当时仓库里还有那个旧版本可用（包已被淘汰时 undo 会失败）。跨大版本升级走 `dnf system-upgrade download --releasever=<N>` 加 `dnf system-upgrade reboot`，这是离线事务：下载完、重启、在 systemd 的离线环境里完成升级，避免升级到一半的中间态。它不做回滚，回滚要么靠 `history undo`，要么靠文件系统快照——Fedora 上的 Btrfs + snapper 与 openSUSE 的同类方案，属于文件系统能力而不是包管理器能力。

openSUSE 的 zypper 共享 rpm 与 libsolv，但更新语义不同：Leap 用 `zypper up`（升级已装包，不删除），Tumbleweed 用 `zypper dup`（把系统对齐到当前快照，可以删除包，也能处理厂商变更）。在 Tumbleweed 上只跑 `up` 会留下跨快照的混合状态，和 Arch 的部分升级是同一类错误。SUSE 的补丁模型也值得知道：zypper 以 patch 为单位组织更新，`zypper patch` 装的是标记为安全或推荐的补丁，与按包升级不是一回事。

#### 速查

| 目的 | 命令 |
|---|---|
| 列出已装包 | `rpm -qa` |
| 列出包内文件 | `rpm -ql <pkg>` |
| 查文件属于哪个包 | `rpm -qf /path/to/file` |
| 查未安装的 rpm 文件 | `rpm -qpi foo.rpm` |
| 查某个能力由谁提供 | `dnf provides '*/bin/nc'` 或 `dnf repoquery --whatprovides` |
| 查谁依赖某包 | `dnf repoquery --whatrequires <pkg>` |
| 装一组包 | `dnf group install '<组名>'` |
| 查可用更新 | `dnf check-upgrade` |

`dnf repoquery` 是 dnf 系最有价值的一条命令：它查的是仓库元数据而非本地状态，可以问“哪些包提供这个文件”“哪些包依赖这个库”，配合 `--queryformat` 能输出机器可读的清单。`rpm -qf` 与 `dnf provides` 的分工正是本地库与仓库索引的分工，与 dpkg/apt 那对关系同构，见第 10 章。

> 一句话总结：dnf 的差异化优势是事务历史与离线升级，但 dnf4/dnf5 混用会污染这份历史。

### 12 pacman 与 AUR：Arch 的滚动哲学

#### 部分升级为什么危险

Arch 不区分“发行版版本”，仓库里的包始终是当前的一套。这意味着一个硬约束：本地已安装的包必须互相匹配（coherent），因为共享库的主版本会在任意一次更新中一起前移。

`pacman -Sy` 只刷新仓库索引，不升级任何已安装的包。之后单独执行 `pacman -S foo`，你会得到最新版的 foo，但它链接的库版本可能是系统上还不存在的新版本——于是 foo 拒绝启动，报的是某个 `.so` 找不到或符号未定义。这就是部分升级（partial upgrade），Arch 官方明确不支持这种状态，也不为它排错。

```bash
# 错的：只刷索引，再单装一个包
sudo pacman -Sy
sudo pacman -S foo

# 对的：刷索引与全量升级在同一个操作里完成
sudo pacman -Syu

# 镜像元数据不同步时，强制重取后整体升级
sudo pacman -Syyu
```

规则可以总结成一句：`-Sy` 之后除了 `-u` 不要再接任何安装动作。`-Syu` 是原子的升级；`-Sy` 单独使用只在一种场景下合理——你确定索引损坏需要重取，随后立即跑 `-Su`。同样的约束也解释了为什么 Arch 要你“升级前读新闻”：当变更需要人工介入（比如某个包被合并、需要先重建 AUR 包、或者手动的迁移步骤），pacman 自己无法知道，新闻页是这套契约的一部分。跨月不升级的系统，一次 `-Syu` 可能带来几十个需要人读的变更，此时更稳妥的是分批升并处理每批的提示。

#### 本地数据库与查询

pacman 的本地库是 `/var/lib/pacman/local/`，每个包一个目录，里面有 `desc`（元数据）与 `files`（文件清单）。`-Q` 系列就是查这个目录：

| 目的 | 命令 |
|---|---|
| 列出已装包 | `pacman -Q` |
| 只看显式安装的 | `pacman -Qe` |
| 只看外部包（AUR 或已从仓库移除） | `pacman -Qm` |
| 列出某包的文件 | `pacman -Ql <pkg>` |
| 查文件属于哪个包 | `pacman -Qo /path/to/file` |
| 列出孤儿依赖（安静输出） | `pacman -Qtdq` |

`pacman -Qm` 是滚动发行版里最有用的一条查询：它把系统分成“仓库管的”和“你自己负责的”两半。而 `pacman -Qtdq | sudo pacman -Rns -` 是标准清理套路——`-Qtdq` 找出没有任何包依赖、自己也不是显式安装的包，`-Rns` 表示连同依赖（`-s`）与配置文件（`-n`）一起删。`-n`（`--nosave`）会**直接删除**配置文件；不加 `-n` 时 pacman 才把被修改过的配置保留成 `.pacsave`，这才是 `-Rns` 与 `-Rn` 的关键差别。缓存清理则是 `pacman -Sc`（删除已卸载包的缓存）与 `pacman -Scc`（清空整个 `/var/cache/pacman/pkg`），后者意味着之后任何回滚降级都得重新下载——在滚动发行版里，本地缓存是最省事的降级来源（Arch Linux Archive 也能取到历史包），别随手清空。

#### AUR 的本质

AUR 不是仓库。它是一堆 PKGBUILD 构建脚本加元数据，没有二进制、没有签名、没有任何人替你审核内容。`makepkg -si` 的 `-s` 会装构建依赖、`-i` 会在构建成功后调用 pacman 安装；也可以在 PKGBUILD 所在目录直接 `makepkg -si`。你的机器负责编译，构建脚本也就在你的机器上以你的权限运行。

yay、paru 这类 AUR helper 只是自动化：解析 AUR 元数据、递归装依赖、下载快照。它们不改变信任链——helper 的便利恰恰在于让“读一遍 PKGBUILD”这一步变得更容易被跳过。Arch 与“不打包主义”的关系也在这里：官方仓库只收录主流软件，长尾软件和冷门变体全靠 AUR 与用户自己。这换来的是仓库规模可控、维护负担低；代价是用户实际上承担了打包者的角色，安全边界也随之从发行版维护者位移到每个用户。

> 一句话总结：滚动发行版的代价不是更新频繁，而是任何一次更新都必须整体完成。

### 13 apk 与 Alpine：容器时代的极小系统

#### 设计取向：小、快、少依赖

Alpine 的基础镜像能压到几 MB，靠的是三件事：BusyBox 提供精简的 coreutils、shell 与 init；包被拆成细粒度子包，只装用得上的部分；apk 本身是 C 写的，索引是单个签名过的 `APKINDEX.tar.gz`，解析快、内存占用低。这在容器里是实打实的优势：拉取快、攻击面小、层数少。

但极小系统建立在一个硬选择上：Alpine 用 musl libc，不是 glibc。这不是口味问题，而是兼容边界。任何在别处编译、动态链接 glibc 的二进制拿到 Alpine 上都跑不起来，报错通常是 `not found`（看起来像文件不存在，实际是解释器 `/lib64/ld-linux-x86-64.so.2` 不存在）。Python 生态里这一点最明显：PyPI 上的 manylinux wheel 链的是 glibc，Alpine 需要 musllinux wheel，而发布 musllinux wheel 的项目远少于 manylinux——于是同一个 `pip install` 在 Debian 镜像里是下载，在 Alpine 里是源码编译，需要 gcc、Python 头文件和几十秒到几分钟。

#### --virtual：容器构建的标准套路

容器里装构建依赖再清理，最干净的做法是用虚拟包把临时依赖打成一捆：

```dockerfile
RUN apk add --no-cache --virtual .build-deps gcc musl-dev python3-dev \
 && pip install --no-cache-dir -r requirements.txt \
 && apk del .build-deps
```

`--virtual .build-deps` 让这一串依赖注册成一个名为 `.build-deps` 的虚拟包，`apk del .build-deps` 一次清掉全部，不用手写长列表、也不怕漏。`--no-cache` 让 apk 不把索引写进 `/var/cache/apk`，省掉后续 `rm -rf` 那一步。这两点合起来才能让构建依赖不留在最终层里——注意最后一条 `apk del` 与 `apk add` 必须在同一个 `RUN` 里，否则中间层已经把依赖固化进镜像了，与第 30 章讲的分层语义是同一个问题。

#### world、repositories 与查询

`/etc/apk/world` 记录的是“你要求系统满足的约束”，每行 `名称{@标签}{版本条件}`，而不是已安装包的完整列表——依赖是求解出来的副作用。手工改过这个文件后要跑 `apk fix` 让它与实际安装状态重新对齐。仓库列表在 `/etc/apk/repositories`；官方镜像与常规安装通常已启用 `community`，但如果你用的是只开 `main` 的精简或自建 rootfs，就得手动追加，否则 `apk add` 会报 `unable to select packages`（包在别的仓库里）。要固定版本，可以直接往 world 里写条件：`apk add 'asterisk<1.6.1'` 之后，`apk upgrade` 会升级其余一切而放过它。

| 目的 | 命令 |
|---|---|
| 刷新索引 | `apk update` |
| 升级全部已装包 | `apk upgrade` |
| 列出已装包 | `apk info` |
| 列出包内文件 | `apk info -L <pkg>` |
| 查文件属于哪个包 | `apk info --who-owns /path` |
| 查依赖 / 反向依赖 | `apk info -R <pkg>` / `apk info -r <pkg>` |
| 看版本来自哪个仓库 | `apk policy <pkg>` |
| 清理本地缓存 | `apk cache clean` |

#### 什么时候不该用 Alpine

以下情况选 Debian slim 或 Ubuntu 基础镜像会更省事，理由都是同一个：你正在为 musl 支付重编译成本，而省下的体积在应用层面前微不足道。

- 依赖大量预编译二进制或闭源产物（数据库客户端、厂商 SDK、部分 JVM 原生库）。
- Python 或 Node 技术栈里有需要编译的原生扩展，构建时间会显著拉长。
- 需要 glibc 专属行为，例如某些 NSS 模块、`nsswitch.conf` 驱动的目录服务集成；musl 的解析器实现与 glibc 不同，混合环境和内网域名解析出过不少难查的问题。
- 团队成员不熟悉 musl，出问题时排查成本会超过镜像体积带来的收益。

再往极简走就是 distroless 与 scratch：不装包管理器，只放运行时和你的产物，结合多阶段构建（见第 30 章）。那是另一个取舍点——镜像更小更安全，但你失去了在容器里临时排查的工具，只能在构建阶段或独立调试镜像里做。

> 一句话总结：Alpine 省下的是镜像体积，付出的是 musl 带来的重编译与生态兼容成本。

### 14 Portage 与 USE 标记：可配置性的极限

#### USE 标记把功能开关变成依赖维度

多数发行版把“要不要 X11 支持”“要不要 IPv6”这类编译期开关定死在包里，用户只能接受。Gentoo 的 USE 标记（USE flag）把这个决定权交出来：每个包声明一组可选的编译特性，用户通过设置这些标记影响配置与编译参数。配置文件分两层——`/etc/portage/make.conf` 里的 `USE=` 是全局默认，`/etc/portage/package.use/` 下按包覆盖，`-flag` 表示关闭。

这个设计的代价是组合爆炸。一个包的输出取决于它自身的 USE 集、依赖的 USE 集、以及 profile 里定义的基础集；依赖图上的每一层都参与，可能的构建配置数量随包数指数增长。这也是为什么 Gentoo 不能简单地共享二进制包：同一个包在不同 USE 集下是不同的构建产物，ABI 与文件清单都可能不一致。binhost 提供的二进制包必须与你的 USE 配置匹配，否则只能退回源码编译。反过来说，二进制发行版之所以能存在，前提正是它把这份组合空间收窄成了一个固定点——这是两者最根本的交换。

#### ebuild、overlay 与日常操作

每个包由一个 ebuild（`*.ebuild`，本质是 bash 脚本）描述：从哪下源码、用什么参数配置、装什么文件、依赖是什么。overlay 是额外的 ebuild 集合，官方仓库之外的东西（第三方软件、你的本地修改）放进去，用 `eselect repository` 之类的工具管理，或直接写进 `/etc/portage/repos.conf`。

```bash
emerge --ask --verbose firefox          # 交互确认，并打印将执行的编译选项
emerge --ask --verbose --update --deep --newuse @world
emerge --ask --depclean                 # 删除不再需要的包
emerge --ask @preserved-rebuild         # 重建链接到被保留旧库的包
```

`--newuse`（`-N`）让 Portage 在 USE 集变化时重建受影响的包；`--deep`（`-D`）让更新递归到依赖；`@world` 是系统集与你显式安装的集合的并集，记录在 `/var/lib/portage/world`。`--depclean` 是危险但必要的一步：它按依赖图删除无人需要的包，误删的典型来源是手工编译安装、没进 world 的东西。`@preserved-rebuild` 解决的是库升级的特有麻烦——升级一个共享库时，旧版本会被临时保留（preserve-libs 特性），因为还有包链接在它上面；Portage 把这些包放进 `@preserved-rebuild` 集合，你重跑一次这个集合就能清掉旧库。这是源码编译发行版才有的问题：没有稳定的 ABI 边界，就得靠“重建所有依赖者”来保证一致性。

#### 真实的代价

- **时间**：每个包在本机编译。日常更新是分钟级到小时级，浏览器、LibreOffice、LLVM 这类大包是小时级；换一次 CFLAGS 或补一次 `--newuse` 意味着一轮大规模重建。
- **磁盘**：编译工作目录默认在 `/var/tmp/portage`，大包需要数 GB 临时空间；再加上包数据库、distfiles 缓存与 binhost 包，根分区规划要留余量。
- **可复现性**：你的系统是“你的 USE 组合 + 你的编译器版本 + 你的 profile”的产物。这既是它最大的价值（同一个包能编译出真正贴合用途的形态），也意味着出现问题时几乎没有第二个人能复现同样的构建，社区支持很难给你现成答案。

Portage 值得读的原因不在于要不要用 Gentoo，而在于它把“包管理器能承担多少策略”推到了边界：它把依赖求解、编译配置、构建调度、二进制缓存、集合管理等全部收进一个工具。多数发行版选择放弃这套能力，不是因为想不明白，而是因为它的代价必须以用户时间为单位支付——这笔账在服务器和桌面上都算不过来，只在少数需要极致裁剪的场景（嵌入式、特定硬件、极端体积约束）才划算。理解了这一点，也就理解了第 18 章里各家取舍的分界线在哪。

> 一句话总结：USE 标记把编译期决策交给用户，代价是构建组合爆炸与无法共享的二进制。

### 15 Homebrew：macOS 的社区事实标准

macOS 随系统附带的命令行工具很少，真正的用户态软件长期没有官方分发渠道：要么去官网下载 `.dmg`，要么自己编译。Homebrew 填补的就是这个空白，而它的设计几乎全部围绕一个约束展开——**不碰系统目录，因此不需要 sudo**。

#### formula、cask 与 prefix

formula 是从源码或官方构建好的 bottle（预编译二进制包）安装的命令行软件，装进 `$(brew --prefix)/Cellar`；cask 分发的是 macOS 上的图形应用和 `.pkg` 安装包，通常落到 `/Applications`。两者共用同一套命令，但信任模型不同：formula 的安装过程受 Homebrew 控制，cask 走的是上游的签名与公证体系，所以 cask 会因为 Gatekeeper 检查失败而被停用甚至移除，这并不等于它被判定为恶意软件。

prefix 由架构决定，不是可随意选择的品味问题：

| 平台 | 默认 prefix |
|---|---|
| macOS Apple Silicon | `/opt/homebrew` |
| macOS Intel | `/usr/local` |
| Linux / WSL2 | `/home/linuxbrew/.linuxbrew` |

Apple Silicon 用 `/opt/homebrew` 是为了和 Rosetta 2 下的 `/usr/local` 并存，且两者都能用 bottle。自定义 prefix 也能用 bottle，但要求更严；默认位置才是被测试最多的那条路。

PATH 必须显式接入，装完不做这一步 `brew` 就不可用：

```bash
eval "$(/opt/homebrew/bin/brew shellenv)"
```

`shellenv` 会把 `$(brew --prefix)/bin`、`sbin` 加进 PATH。这里有个常被忽略的后果：**GUI 应用默认拿不到 Homebrew 的 PATH**，从 Dock 启动的编辑器因此找不到 `node`、`python3`。另外 `brew install python@3.13` 这类包是 keg-only——只进 Cellar，不链接到 prefix，因为链接会遮蔽系统同名工具；`brew info` 会告诉你该怎么把它加进 PATH。

#### 命令与机器复现

日常只用得起少数几个：`brew install`/`uninstall`/`upgrade`、`brew list`、`brew info`、`brew deps <formula>` 与反查方向的 `brew uses --installed <formula>`、`brew doctor`、`brew cleanup`。`brew outdated` 先告诉你哪些能升，`brew pin <formula>` 可以按住某个包不升级。

机器复现靠 `brew bundle`：`brew bundle dump --global --force` 把当前状态写成 `~/.Brewfile`，`brew bundle` 负责把机器拉回该状态，`brew bundle cleanup --force` 删掉清单之外的包。Brewfile 不只是 Homebrew 的清单，还能写 `mas`、`vscode`、`cargo`、`uv`、`flatpak`，WSL 里甚至能写 `winget`。但要说清它的边界：**Brewfile 没有锁**。官方文档明确表示不会提供类似 `Gemfile.lock` 的机制，因为 Homebrew 是滚动发布的，不保证任意旧版本可安装。Brewfile 记录的是“装了哪些包”，不是“钉在哪些版本”。要真正冻结版本，只能把一部分软件交给别的工具（见第 17、38 章）。

#### 代价与边界

Homebrew 不支持任意版本混搭，升级时会连带升级依赖它的包和它依赖的包，`brew upgrade` 一次性动几十个 formula 是常态。旧版本在升级后会被自动清理，想保留得关掉自动 cleanup。

它不接管系统依赖，这是刻意的：系统组件（libxml2、Python、OpenSSL 等）必须用系统自带的，覆盖它们会破坏签名校验和系统更新。Linux 上的 Homebrew 定位是“发行版没打包或太旧的软件”，它不依赖宿主库（只需要够新的 glibc 和 gcc），因此同一个可执行文件可能链接到 `/home/linuxbrew` 下的另一份 libc 依赖树，与发行版包管理器并存时容易出现“同名命令指向不同实现”。第三方 tap 过去是纯信任关系，Homebrew 6.0.0 起引入 tap trust，非官方 tap 需要 `brew trust` 显式授权才会被加载——它的理由是 formula 和 cask 是可执行的 Ruby 包定义，而不是纯元数据。

> 一句话总结：Homebrew 的价值在于不碰系统、免 sudo，代价是没有版本锁定与系统集成。

### 16 Windows 的三条路线：winget、Scoop、Chocolatey

Windows 上“装软件”有三层并存的状态：MSIX/Store 应用、传统安装器（`.exe`/`.msi`，状态写在注册表里）、绿色软件目录（状态只在文件系统里）。三个包管理器都在这块地基上工作。

#### winget：官方出品的安装器编排器

winget 是微软官方的命令行包管理器，也是系统组件，随 Windows 交付并在商店里更新。它最容易误解的地方是：**winget 不分发软件**。仓库 `winget-pkgs` 存的是 manifest——包标识、版本、安装器 URL、哈希与静默安装参数。所谓安装，是下载上游安装器再按其静默参数调用。

后果有两个。第一，升级能力受上游限制：上游没提供静默参数，或安装器升级时会弹交互界面，`winget upgrade` 就可能失败、挂起或什么都没做。第二，它判断“已安装”“可升级”时的信息源不止一个（自有数据库与系统已安装程序记录），不一致就会误报。这是“编排安装器”这条路线固有的弱点。

```powershell
winget search 7zip
winget list <name>
winget upgrade --all
winget install --id <Publisher.Package> --source winget
```

本文写作所用的这台机器上，`winget --version` 与 `winget search` 均执行失败（进程以非零状态退出，无输出），因此本章不引用任何 winget 版本号；manifest 的字段与可用子命令请以 `winget --help` 和官方文档为准。

#### Chocolatey：NuGet 生态 + PowerShell 脚本

Chocolatey 是三者中历史最久的，包格式建立在 NuGet 之上（`.nupkg` 加 `chocolateyInstall.ps1` 等脚本）。安装脚本以管理员权限执行 PowerShell，能力最大，风险也最大：装一个社区包等于执行一段第三方代码，脚本行为决定了软件最终装在哪、注册了什么。

本机核实：`choco --version` 输出 `2.5.0`，`ChocolateyInstall=C:\ProgramData\chocolatey`，shim 在 `C:\ProgramData\chocolatey\bin`，包体与解包内容分别在 `lib` 和 `tools` 下。`choco list` 列出本机已安装，`choco upgrade all -y` 是全量升级的常见写法。

因为要写 `C:\ProgramData` 和注册表，它基本需要管理员权限，所谓绿色版安装只是“脚本没写注册表”的特例。企业场景关心的是许可版本提供的内部源、自建包与包审核流程。社区仓库的包经过审核，但审核不等于审计。

#### Scoop：不写注册表的用户级目录

Scoop 反其道而行：默认装到用户目录，不写注册表，不需要管理员权限。本机实测根路径 `C:\Users\<user>\scoop`，含 `apps`、`buckets`、`shims`、`persist`、`cache` 等子目录。`buckets` 就是 Git 仓库，`git pull` 即更新软件清单，可读性与可审计性远高于二进制脚本。`shims` 为每个可执行文件生成 `.cmd`/`.ps1` 转发脚本，靠 PATH 生效——本机 shims 目录里有 88 个文件，大致对应 88 个可用命令（其中也可能含非命令转发）。`persist` 存放跨版本保留的配置，是另外两者没有的设计。

本机核实：`scoop --version` 输出 `Current Scoop version: ... Bump to version 0.5.3`；`scoop config` 显示 `root_path` 为 `C:\Users\lzh\scoop`、`scoop_repo` 指向 GitHub 上的 Scoop 仓库。`scoop update *` 更新全部应用，`scoop cleanup *` 清理旧版本。

代价很直接：需要注册表的软件装不了或装了不工作——服务、Shell 扩展、要写 HKLM 的驱动类工具都属此类；GUI 覆盖也不如另外两者。

#### 共存与冲突

三者都只持有“引用”而非所有权，所以同一个软件被两个管理器装了，双方都不会知道，也没有机制阻止。“不要用多个管理器管同一个软件”只是一条靠人遵守的约定；真重叠了，先让一个卸载干净再由另一个接管，日常调用哪个由 PATH 顺序决定。

三者的差异可以压成一张表：

<div style="overflow-x:auto">

| 维度 | winget | Chocolatey | Scoop |
|---|---|---|---|
| 分发内容 | manifest，指向上游安装器 | `.nupkg` + PowerShell 脚本 | bucket 里的清单 + 归档 |
| 权限 | 视安装器而定，常需提权 | 基本需要管理员 | 默认不需要 |
| 安装位置 | 由上游安装器决定 | `C:\ProgramData\chocolatey` | 用户目录 `~\scoop` |
| 注册表 | 由安装器写入 | 由脚本写入 | 不写 |
| 生态规模 | 官方仓库 + 商店 | NuGet/社区仓库，历史最长 | 官方 bucket + 社区 bucket |

</div>

判断顺序是：需要系统集成（服务、驱动、Shell 扩展）走 winget 或 Chocolatey；开发工具、CLI、绿色软件走 Scoop；条件允许时优先用软件自带的更新机制，因为包管理器只是在猜上游的静默参数。Windows 上手工安装的比例至今很高，原因是大量商业软件既不提供稳定的静默参数，也不提供可脚本化的下载地址。

> 一句话总结：Windows 三条路线的分野在权限与状态存放位置，而不在命令风格。

### 17 Nix 与 Guix：把包管理器当成构建系统

多数包管理器的核心数据是“已安装了什么”，Nix 的核心数据是“如何构建出这个产物”。这个差别派生出了它全部的性质，也派生出它全部的代价。

#### derivation：构建计划本身是数据

一个 derivation（派生）是一段描述构建过程的 Nix 表达式：builder（通常是 bash）、参数、输入路径、环境变量、输出名。它不执行任何操作，只是数据。

真正的关键在下一步。Nix 把这个 derivation 的序列化内容（ATerm 形式）连同全部输入的路径一起哈希，取 SHA-256 的前 160 位做 base-32 编码，得到 store 路径：

```text
/nix/store/<digest>-<name>
```

也就是说，**路径本身就是输入的函数**（Guix 同构，只是 store 目录换成 `/gnu/store`）。这带来一个反直觉但极其有力的结果：不存在“升级”这个动作，只有“另一个路径出现了”。

- 依赖 A 从 1.0 换成 1.1 → 所有下游的哈希全部改变 → 得到一批全新路径。旧路径不动，随时可以指回去。
- 两个项目分别需要同一个库的不同版本 → 两个路径同时存在于 store，互不覆盖。
- 安装是原子的：新路径构建成功后切换符号链接指向，中途失败就什么也没变。

所有构建在沙箱里进行，默认无网络（声明了输出哈希的 fixed-output derivation 例外）。“可复现构建”在这里第一次成为默认而非附加选项。

#### profile 与 generations：回滚为什么几乎免费

用户可见的一层是 profile：一个装着大量符号链接的目录，链接指向 store 里的包。每次改动都会生成新的一代——`~/.local/state/nix/profiles/profile` 指向 `profile-N-link`，而后者又指向 store。回滚就是改一个符号链接，没有文件复制，没有重新构建。

```bash
nix-env -iA nixpkgs.ripgrep        # 传统的命令式安装
nix profile install nixpkgs#ripgrep
nix profile list
nix profile rollback
nix-env --list-generations
nix develop                        # 进入由 flake 定义的开发环境
nix build .#hello
nix store gc
```

需要留意两点。其一，`nix profile` 属于实验性的 `nix-command` 特性，接口仍可能变；而且一旦用过 `nix profile`，`nix-env` 会直接拒绝操作同一个 profile，报 profile 与 `nix-env` 不兼容。其二，旧的 generation 是垃圾回收的根，只要它们还留着，对应的 store 路径就不能被删——**“随时能回滚”的代价就是磁盘不会自己变小**。`nix store gc` 与 `nix profile wipe-history` 才是真正释放空间的动作。

#### flakes：把“环境”变成可锁定对象

flakes 之前，Nix 表达式依赖 channel：一个指向 nixpkgs 某次提交的全局状态，和项目没有绑定。`flake.nix` + `flake.lock` 把依赖的提交哈希写进仓库，“环境”因此可被 git 追踪，`nix build .#x` 在不同机器上取到同一份 nixpkgs。

争议也在这里。flakes 长期停留在实验性特性上：需要显式打开，接口不保证稳定，社区对它的设计（锁文件语义、registry、与旧命令的割裂）持续争论，一部分用户坚持用 channel 或 pin 版本的旧写法。它同时是“事实上的标准”和“官方尚未定型的实验特性”，这个状态本身就是决策风险。

#### 代价

- **非 FHS 路径的适配**：包不在 `/usr` 下，而是 `/nix/store/<hash>-foo/bin`。Nix 靠包装脚本、修补 ELF 的 rpath/interpreter 让它们工作。这对生态里其他工具是破坏性的：预编译二进制、硬编码 `/usr/lib` 的构建脚本、依赖 `#!/usr/bin/env python` 找到解释器的脚本，都可能失效，需要 patch 或加包装层。这不是读几页文档就能绕开的边角问题，而是长期要付的适配成本。
- **磁盘**：不同 closure 各带一份依赖，同一个库在 store 里可能有多份；`nix store optimise` 能去重，但要主动执行。
- **学习曲线**：Nix 是一门惰性求值的函数式语言，官方文档、社区 wiki 与那个著名的“非官方教程”长期并存，新手看到的多套写法经常互不兼容。

#### Guix 的差异

Guix 与 Nix 同源（构建守护进程、store 哈希机制、沙箱思路都来自 Nix），差别在语言与立场：配置与包定义全用 Scheme（Guile），没有 Nix 那样混杂的 DSL；更严格地只收录自由软件，非自由固件与驱动需要另开渠道；store 目录是 `/gnu/store`；Guix System 用一份 Scheme 配置声明整个操作系统，对位 NixOS。它的生态规模明显小于 nixpkgs，包数量与二进制缓存覆盖率都差一个量级，这是选型时的硬约束。

#### 什么时候值得用

三件事同时成立时它才划算：要的是**很强的可复现性**（不只是“有锁文件”，而是构建过程本身可复现）、机器上确实需要**多版本长期并存**、并且愿意把开发环境写成代码（`flake.nix`、devShell、NixOS 模块）而不是维护一长串安装脚本。反过来，如果只是想在 macOS 上快速装几个 CLI 工具，Homebrew 的边际成本低得多（见第 15 章）。

> 一句话总结：Nix 把“安装”变成“计算路径”，换来原子回滚与多版本共存，代价是适配与学习成本。

### 18 系统级横向对比与共存策略

第 10–17 章的工具各自解决同一类问题的不同侧面，放进同一张表取舍关系会清楚很多。

<div style="overflow-x:auto">

| 管理器 | 包格式 / 仓库 | 求解方式 | 发布模型与回滚 | 沙箱 / 安装脚本 | 系统状态所在 |
|---|---|---|---|---|---|
| apt（dpkg） | `.deb` / 发行版镜像 | 贪心 + 局部回溯 | 固定发行版，无内建回滚 | 有 maintainer script，无强沙箱 | `/var/lib/dpkg` |
| dnf（rpm） | `.rpm` / 仓库 + 模块 | libsolv 的 SAT 求解 | 固定发行版，`dnf history undo` | 有 scriptlet | `/var/lib/rpm` |
| pacman（Arch） | `.pkg.tar.zst` / 滚动仓库 | 依赖图整体求解 | 滚动，靠降级缓存 | 有 install script，无沙箱 | `/var/lib/pacman/local` |
| apk（Alpine） | `.apk` / 仓库 | 依赖图求解 | 固定发行版 + edge | 有脚本，极小依赖 | `/lib/apk/db` |
| Portage（Gentoo） | ebuild 源码 + binhost | 依赖图 + USE 标记 | 滚动，配置即状态 | 本地编译，几乎无隔离 | `/var/db/pkg`、`world` |
| Homebrew | formula / cask + tap | 版本唯一，尽量不混搭 | 滚动，旧版本被清理 | 用户权限构建，无沙箱 | prefix 下的 Cellar |
| winget | manifest → 上游安装器 | 无跨包求解 | 跟随上游安装器 | 由安装器决定 | 注册表 + winget DB |
| Chocolatey | NuGet 包 + 脚本 | 无跨包求解 | 脚本驱动升级 | PowerShell 以管理员执行 | `C:\ProgramData\chocolatey` |
| Scoop | bucket 清单 + 归档 | 无跨包求解 | 目录切换，可保留旧版 | 用户权限，不写注册表 | 用户目录 `~\scoop` |
| Nix | derivation / nixpkgs | 求解 + 哈希寻址 | 任意回滚（generations） | 沙箱构建，默认无网 | `/nix/store` + profile |
| Guix | Scheme 包定义 | 求解 + 哈希寻址 | 任意回滚 | 沙箱构建 | `/gnu/store` + profile |

</div>

表里最值得记住的一列是“系统状态所在”。状态在数据库里的（dpkg、rpm、pacman、apk）能回答“这个文件属于哪个包”“谁依赖它”，因此有能力做一致性诊断；状态在目录里的（Scoop、Nix profile）回滚便宜但反查能力弱；状态散在注册表与上游安装器里的（winget、Chocolatey），包管理器自己也说不清当前到底是什么。

另一条轴是**求解粒度**。apt/dnf/pacman/apk 和 Nix 做整机或整 profile 范围的依赖求解；三个 Windows 管理器不做跨包求解，每个包各管各的，因此“装 A 破坏了 B”在 Windows 上没有求解器能提前发现。

#### 混装顺序

一台机器上同时存在多个管理器是常态。可行的分层顺序是：

1. **系统关键库与系统服务**：只交给发行版包管理器（Linux）或系统自带机制（macOS 的 `/usr`、Windows 的 MSVC 运行时与系统 DLL）。任何跨平台工具都不该覆盖这一层。
2. **语言运行时**：交给版本管理器（见第 32 章），不要用系统包管理器装的解释器去做项目构建，也不要用语言级包管理器去升级系统解释器。
3. **项目依赖**：语言级包管理器 + 虚拟环境，装到项目目录或用户目录，永不写系统路径（见第 19–28 章）。
4. **用户级 CLI 工具**：Homebrew、Scoop、Nix profile、pipx 这一层，属于“用户自己用得爽”的区域，坏了不影响系统。

判断谁在生效永远看 PATH 顺序，不要凭记忆。第一步 `which -a <命令>`（Windows 上是 `Get-Command <命令> -All`），第二步看该路径属于哪个 prefix。这能解决大部分“我明明升级了但版本没变”。

风险集中在两处。一是**跨平台工具覆盖系统关键组件**：Linux 上装 Homebrew 或 Nix 后，若让它们的 `bin` 排在 PATH 前面，`python3`、`openssl`、`curl` 可能整批换成另一套，而系统工具仍按老路径调用，于是出现“同一个名字、两个 ABI”的错乱；NixOS 这类由 Nix 接管全系统的发行版要求“全有或全无”，原因就在这里。二是**反向覆盖**：用系统包管理器装某工具的“系统版”，再用 Homebrew/Nix 装同一个工具，两者争抢同一个命令名。

#### 经典事故：系统 Python 被污染

最出名的一类事故是往系统 Python 里 `pip install`。发行版自带的 Python 是系统工具（`dnf`、部分 apt 组件、桌面环境脚本）的运行环境，直接装包会替换它们依赖的库版本，症状是命令突然报 `ImportError`，而报错里的名字和用户最近装的东西毫无关系。

这个问题的现代答案是 PEP 668：发行版可以在 Python 环境里放一个 `EXTERNALLY-MANAGED` 标记文件，pip 检测到后拒绝安装，报 `externally-managed-environment`。它把“不要这样做”从文档建议变成工具层面的拒绝，代价是用户必须改用 venv、pipx 或发行版包。细节与正确做法见第 20 章；系统级视角只要记住一条：**任何直接写进系统解释器 site-packages 的操作，都应当被当成对系统的修改来对待。**

#### 容器与虚拟机

把系统包管理的问题外包给镜像是另一条路：镜像天然一次性、可重建，回滚靠换 tag 或 digest，隔离靠命名空间——比任何“共存策略”都彻底。代价是镜像内的包级状态不可回滚（换层就是换整个环境）、锁粒度从 lockfile 变成 digest、基础镜像本身成了需要长期维护的依赖。对“多个管理器打架”这类问题，容器是回避而不是解决；什么时候该回避、什么时候该正面解决，见第 30 章与第 38 章。

> 一句话总结：分层放置、看 PATH 定胜负、绝不覆盖系统运行时，是共存的全部规则。

## 第三部分 · 语言级包管理器

### 19 JavaScript：npm 与它的对手们

JavaScript 生态是包管理的实验场：包的数量最多、工具更替最快、几乎所有设计争论都先在这里发生。理解 npm 的历史，等于看一遍“取舍如何层层累积”。

#### npm 的演化：每个决定都在还上一个决定的债

npm 最初的设计很直接：包声明依赖范围，安装时求解，**每个包在自己的目录下带一份自己的依赖**。这保证了近乎完美的隔离——`node_modules/a/node_modules/b` 与 `node_modules/c/node_modules/b` 可以是两个版本。

代价很快就来了：路径极深（Windows 的路径长度限制一度是真问题）、同一个版本被复制几十份、安装耗时随依赖树增长。

npm 3（2015）改为**扁平化安装**：尽量把共用依赖提升（hoist）到顶层的 `node_modules`。磁盘和速度问题缓解了，但引入了两个长期后果：一是**幻影依赖**（代码能 `require` 到没声明过的包），二是**安装结果受顺序影响**（谁先被处理，谁占据顶层位置）。

锁文件随后补齐确定性：npm 5（2017）引入 `package-lock.json`（lockfileVersion 1，本质是一份“当时的依赖树快照”）；npm 7 升级为 v2，同时记录 `packages` 树与旧格式快照以保证向后兼容；npm 9 起常见 v3，只保留 `packages`。v1 描述的是“那一刻的样子”，v2/v3 描述的是“确定的树加完整性哈希”。

同一时期还有 `peerDependencies` 的语义变化：npm 7 之前只在冲突时警告，npm 7 起会**自动安装** peer 依赖。好处是消灭了一类“插件找不到宿主框架”的运行时错误，代价是求解器要同时满足更多约束，意外引入的包也更多。

#### Yarn：两个世代，一套问题

Yarn 1（classic，2016）针对当时 npm 的确定性与速度短板，`yarn.lock` 很快成为行业标配，离线缓存也先于 npm 提供。但它的安装模型仍是 `node_modules` 加提升，所以幻影依赖依旧存在。

Yarn 2 及之后的 Berry 走了另一条路：**PnP（Plug'n'Play）**。它不生成 `node_modules`，而是生成一份解析映射（`.pnp.cjs`），由运行时插件按映射加载包。收益很实在：依赖必须显式声明（幻影依赖在机制上不可能）、安装更快、磁盘占用更小。

代价同样实在：任何依赖 `node_modules` 物理布局的工具都可能出错——部分编辑器、打包器、原生模块、以及一些历史版本的测试框架。迁移需要引入 SDK 适配，这也是 Berry 的接受度始终不如 classic 的原因。

Berry 还提出过 zero-installs（把 `.yarn/cache` 提交进仓库），启动快，但仓库体积激增，社区争议很大。

#### pnpm：内容寻址 + 严格布局

pnpm 用两个机制同时解决“省空间”和“边界清晰”：

- **全局内容寻址 store**：包按内容哈希存放，项目里的文件通过硬链接指向 store，于是同一版本在全机器只存一份，跨项目也共享。
- **严格的 `node_modules` 布局**：顶层只放**直接依赖**的符号链接，每个包的依赖放在 `.pnpm/` 下的独立目录里。因此代码无法解析到未声明的包——幻影依赖会立刻以“找不到模块”暴露，而不是在换机器时才发作。

它的锁文件（`pnpm-lock.yaml`）记录了导入者与依赖的关系，支持 workspace，冻结安装用 `--frozen-lockfile`。需要兼容旧工具时，可以用 `public-hoist-pattern` 或 `shamefully-hoist` 显式打开提升——注意是“显式”，代价写在配置里，而不是藏在默认行为中。

#### bun 与 deno：两个方向的激进

**bun** 是一体化工具链（运行时 + 包管理 + 打包 + 测试），用 Zig 实现，目标是与 npm 生态兼容且显著更快。它早期使用二进制锁文件 `bun.lockb`，后来引入文本格式以改善 diff 与冲突处理。它的激进之处在于愿意跳过部分兼容性检查来换速度，这让它在个别依赖上出现与 npm 不同的行为。

**deno** 的方向不同：默认不依赖中心化 registry，用 URL 导入模块，权限模型显式（网络、文件、环境变量都要授权），后续加入的 npm 兼容层让它能消费 npm 包。它和 JSR 一起，是对“npm 无命名空间、包名先到先得”这一现实的回应——包名抢注与 typosquatting 在无命名空间的仓库里几乎是必然产物。

#### workspace、npx 与 corepack

- **workspaces**：npm、yarn、pnpm 都支持，本地包通过符号链接互相引用，一次提交可以同时改多个包，避免“发布—安装—再改”的循环。
- **npx**：临时获取并执行一次性 CLI，不污染项目依赖。
- **corepack**：按 `package.json` 里的 `packageManager` 字段激活指定版本的包管理器，解决“团队里每个人 yarn/pnpm 版本不同、锁文件格式不同”的问题。注意它自 Node.js 25 起不再随 Node 分发，需要单独安装。

#### 命令速查与常见坑

| 任务 | npm | pnpm |
|---|---|---|
| 冻结安装 | `npm ci` | `pnpm i --frozen-lockfile` |
| 加依赖 | `npm i x` | `pnpm add x` |
| 开发依赖 | `npm i -D x` | `pnpm add -D x` |
| 查依赖来源 | `npm ls x` | `pnpm why x` |
| 更新 | `npm update` | `pnpm update` |
| 跑脚本 | `npm run x` | `pnpm run x` |

常见坑，几乎全部与“隔离和确定性”有关：

- **原生模块重编译**：node-gyp 需要 Python 与 C++ 编译工具链，Windows 上还依赖 VS Build Tools；而 npm 12 起安装脚本默认不放行（见第 8 章），所以先确认这个包在 allowlist 里——否则失败原因不是缺编译器，而是脚本没被允许。优先选提供预编译二进制的版本，或把安装放进容器。
- **可选依赖的平台差异**：esbuild、rollup、sharp 这类包按平台声明可选依赖，跨平台锁文件因此容易“只在 CI 上失败”（见第 5 章）。
- **锁文件合并冲突**：不要手工合并，取一方的 `package.json` 重新生成并核对差异。
- **`npm install` 与 `npm ci` 混用**：前者会改锁文件，后者会拒绝不一致。CI 必须用后者。
- **全局安装的 CLI 与项目依赖打架**：把工具声明为开发依赖，通过项目脚本或 `npx` 调用。
- **`rm -rf node_modules && npm install`**：它是排查手段而不是解决方案。如果它能修好问题，说明之前的状态不可复现——那才是要修的地方。

> 一句话总结：JS 生态的每个工具都在回答同一个问题——当“允许共存”成为默认，谁来保证依赖边界不被污染。

### 20 Python：从 requirements.txt 到 uv

Python 的包管理是全文里“历史层积”最厚的一章：语言本身没有内置依赖管理（第 21 章的 Cargo、第 22 章的 Go 都是语言自带），于是标准、仓库与外部工具各自演化了二十年，留下的是一堆能互相兼容但不完全等价的东西。

#### 分发形态：sdist、wheel 与平台标签

PyPI 上同一个版本通常有两种文件：源码分发（sdist，一般是 `.tar.gz`）与二进制分发（wheel）。sdist 安装时要执行构建后端（见第 8 章）；wheel 是已构建好的 zip，安装基本等于解压加写元数据。

wheel 文件名在 `包名-版本-` 之后编码了 `python 标签-ABI 标签-平台标签`：

```text
cryptography-46.0.5-cp311-abi3-manylinux_2_34_x86_64.whl
```

- `cp311`：CPython 3.11 及以上（`abi3` 表示用稳定 ABI 编译，一份二进制可供多个版本共用）
- `manylinux_2_34`：Linux + glibc ≥ 2.34；老机器上是 `manylinux2014`（等价于 `manylinux_2_17`）
- `musllinux_1_2`：Alpine 那类 musl libc 系统（第 13 章），与 manylinux 不是一类标签
- `win_amd64` / `macosx_11_0_arm64`：Windows 与 macOS

于是“装不上”绝大多数不是包不存在，而是**没有匹配当前平台的 wheel**。pip 会退回去下载 sdist 并现场编译，失败信息通常是 `error: Microsoft Visual C++ 14.0 or greater is required`、`gcc: command not found`、`fatal error: Python.h: No such file or directory`。结论是：**这类故障是环境问题，不是版本问题**，换版本号、加 `--force-reinstall` 都不会有用。

诊断顺序：

```bash
python -c "import sysconfig; print(sysconfig.get_platform())"
pip index versions cryptography   # 看某包在该源上有哪些版本（实验性命令）
pip download cryptography --only-binary=:all: -d /tmp/wheels
```

最后一条最有用：`--only-binary=:all:` 明确禁止编译，报“找不到匹配的发行版”就把“缺 wheel”与“编译不过”分开了。`--no-binary=:all:` 则强制源码构建，只在需要按本机 CPU 指令集优化时才用，代价是时间长、失败率高。

还有一个容易忽略的变量：MSYS2、Windows Store 版、conda 环境里的解释器传给 PyPI 的标签组合各不相同，同一个包在其中一个上装得了、换一个就装不了，是正常的。

标签差异解释了几种常见困惑。Windows 用 `win_amd64`、`win_arm64` 而非“位数”，解释器位数直接决定能装哪个。Alpine 镜像里的 Python 只认 `musllinux_*`，所以同一个包在 `python:3.13-slim`（Debian）能直接装、在 `python:3.13-alpine` 里却要编译，这是很多团队在数据科学镜像上放弃 Alpine 的实际原因（第 30 章）。`pip install` 输出里 “Using cached …” 后面跟着 `.tar.gz` 而不是 `.whl`，就是“接下来要编译”的预告。

#### 虚拟环境：venv 做了什么

`venv` 是标准库自带的隔离机制（第 6 章）。它不复制解释器，而是建出 `pyvenv.cfg` 加一套目录，用路径改写让解释器优先看 `.venv/Lib/site-packages`（Windows）或 `.venv/lib/python3.13/site-packages`（Linux/macOS）：

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # bash/zsh
python -m pip install -r requirements.txt
```

它隔离的是**依赖与可执行文件**，不隔离解释器版本，也不隔离构建环境（编译 sdist 用的 C 编译器仍来自系统）。`--system-site-packages` 会把全局 site-packages 挂进来，代价是“这个包到底从哪来”重新变得不可预测。

#### 标准的演进：从 setup.py 到 pyproject.toml

早期唯一可执行的是 `setup.py`，于是“包的元数据”实质上是“一段必须被执行的 Python 代码”，这正是第 8 章那类问题的源头。四份 PEP 把它拆成声明式的两层：

- **PEP 518**：引入 `pyproject.toml` 与 `[build-system]`，声明构建需要哪些工具；
- **PEP 517**：定义构建后端接口（`build_wheel`、`build_sdist` 等钩子），前端（pip/uv）与后端（setuptools、hatchling、flit、poetry-core、maturin）解耦；
- **PEP 621**：把项目元数据（名字、版本、依赖、入口点）标准化进 `[project]` 表；
- **PEP 735**：把“开发依赖分组”标准化为 `[dependency-groups]`。

于是今天一个普通项目的清单可以相当统一：

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27,<1",
  "pydantic~=2.7",
]

[project.optional-dependencies]      # 面向使用者：pip install "myapp[postgres]"
postgres = ["psycopg[binary]>=3.1"]

[dependency-groups]                  # 面向开发者：uv sync --group dev
dev = ["pytest>=8", "ruff>=0.6"]

[project.scripts]
myapp = "myapp.cli:main"
```

`[build-system]` 与 `[project]` 分开不是冗余：前者只在“构建这个包”时需要，后者是“这个包是谁”的元数据。对应用（不发布）来说，用 uv 这类把项目当 non-package 处理的工具时，`[build-system]` 甚至可以省略，直接只用 `[dependency-groups]` 加 `dependencies`；但一旦要 `pip install -e .`，构建后端仍然必需（缺省回退到 setuptools）。

#### requirements.txt 与 requirements.in 的定位差异

这两个文件常被混用，但角色完全不同：

| 文件 | 内容 | 角色 |
|---|---|---|
| `requirements.in` | 手写的直接依赖，可以带范围 | 约束（manifest） |
| `requirements.txt` | `pip-compile` 生成的完整闭合集合，全部 `==` 并带来源注释 | 求解结果（lock） |

也就是说，`requirements.in` 对应第 5 章说的“清单”，`requirements.txt` 对应“锁文件”；前者人写，后者机器生成。把两者都提交，并在 CI 里校验“重新编译结果是否与本文件一致”，才拿到可复现性。

而 `pip freeze > requirements.txt` 是另一回事：它导出**当前环境里所有已安装的包**，包括你从没声明过的传递依赖、以及可能来自本地路径安装的东西（在 Windows 上会写出 `-e file:///C:/...` 这类绝对路径）。临时冻结一台机器时它有用，在正经项目里会把环境里的脏东西一并固化。

#### 工具谱系：从 pip 到 uv

`pip` 只做一件事：把给定的要求装进当前环境。它不生成锁文件、不管项目结构、也不管你在哪个环境里。

**pip-tools** 用两个命令补上锁定这一环：`pip-compile` 把 `.in` 编译成完全固定的 `.txt`，`pip-sync` 让环境精确等于 `.txt`（会卸载多余的包）。一个关键限制是它按**当前环境**求解：Python 版本、操作系统、甚至已装包都会影响输出，所以不同平台需要各自编译一份 `.txt`，并明确按平台与 Python 版本命名区分。

**Poetry** 走一体化路线：`pyproject.toml` + `poetry.lock`，配 `poetry add`/`install`/`run`。它在 2.0 之后把元数据写进标准的 `[project]` 表，只在 `[tool.poetry]` 里保留标准没有的部分，这是一次重要的收敛。代价是它自带一套环境与安装逻辑，和 `pip` 的行为不总是逐条一致。

**PDM** 与 **Hatch** 是同一层里的另两个选择。PDM 强调同时兼容 PEP 621 与 `[dependency-groups]`，并能导出 `requirements.txt` 给不认 `pyproject.toml` 的部署环境；Hatch 的核心是构建后端 `hatchling` 加可声明的环境矩阵，更偏项目任务编排而非依赖求解。

**uv** 是 Rust 实现的一体化工具，把这些前端、锁文件、venv、Python 版本安装、`pipx` 式工具运行收进了一个二进制。两个关键设计：解析器基于 **PubGrub**（第 3 章讨论的冲突学习型算法），并且生成**跨平台通用锁文件** `uv.lock`——不像 `pip-compile` 那样每个平台各锁一份。

迁移路径是 `uv pip` 这层兼容接口：`uv pip install`、`uv pip compile`、`uv pip sync` 的参数尽量贴近 `pip`/`pip-tools`，不用重写脚本。取舍是：`uv pip` 默认仍按当前环境求解、不产生 `uv.lock`（那要 `uv lock` + `uv sync`），所以它解决的是“快”，不自动解决“可复现”；要可复现就得接受 uv 的项目模型，而不是只换命令前缀。

截至 2026 年中，uv 的版本仍在 0.x 阶段（PyPI 上为 0.12.x 系列），但已被声明为生产就绪，并把 0.x 的次版本号当作可能的破坏性变更边界——升级前值得读 changelog。Poetry 则在 2.x 系列。这两个事实都易变，使用前以官方文档为准。

#### 为什么 pip 的解析曾经那么慢

“pip 装得慢”经常被归因于 Python 慢，这不准确。真实原因有三层，按影响排序：

**一，回溯求解需要元数据，而元数据曾经必须下载整包才能拿到。** pip 在 20.3 之前用的是“只取最新版”的贪心解析，20.3 起默认换成带回溯的解析器，遇到冲突会退回尝试别的版本。正确性大幅提升，代价是它要读取大量候选版本的依赖声明。在 PEP 658 之前，PyPI 的 Simple API 只提供文件链接，要读 `.dist-info/METADATA` 就得把整个 wheel 下下来——解析一个包等于下载几十个 wheel。PEP 658 增加了紧随其后的 `.metadata` 文件，pip 也支持用 HTTP range 请求只取 zip 中央目录里的那一段；但**只发 sdist 的包没有这个便利**，仍要下载甚至构建，这就是某些包解析特别慢的原因。

**二，回溯本身在冲突严重时是指数级的**（第 3 章）。约束互相矛盾的依赖图会让解析器反复试错，典型表现是输出不断刷新的 “Downloading …” 与最终一句 `ResolutionImpossible`。

**三，大包的体积与网络。** torch 这类包的 wheel 动辄几百 MB 到数 GB，这一步耗时与求解器无关。

uv 之所以快，是同时在这三层上做了事：Rust 实现与并行下载只是表象，更关键的是它优先读 PEP 658 元数据、激进缓存、用 PubGrub 减少无效回溯、并且用硬链接/写时复制从全局缓存“安装”（第 6 章里 pnpm 的同类思路）。所以在依赖图复杂、需要多次解析的项目上，两者的差距比在简单项目上大得多。

#### conda / mamba / pixi：另一条路线

conda 不是 Python 包管理器，而是**跨语言的二进制分发与环境管理器**。它的包可以装 Python 解释器、编译器、MPI、CUDA runtime、`ffmpeg`、R 语言。对“numpy + 一块匹配驱动的 CUDA + cudnn”这种需求，conda 是少数能一次说清的方案；pip 只能管 Python 那一半。

机制上它以**环境为中心**：一个环境就是一个前缀目录，里面有自己的解释器、库和 `bin/`；求解由 conda 自己做，历史上默认求解器性能一般，后来换成基于 libsolv 的 libmamba（`conda-libmamba-solver`，从 conda 23.10 起成为默认）。`mamba` 是最早用上 libmamba 的独立客户端。`pixi` 是较新的一代：同样基于 conda 生态的包，但把项目清单、锁文件（`pixi.toml` + `pixi.lock`）与任务运行做成了 Cargo 式的体验。

conda 与 pip 混用的现实问题值得单独说：**conda 不知道 pip 装了什么**。你在环境里 `pip install` 一个包，之后 `conda install` 另一个需要同类依赖的包，conda 会按自己的视图重新安排文件，pip 装的那份可能被覆盖或变得不一致。可见的做法是先用 conda 装尽可能多的东西、最后用 pip 补；或干脆用 pixi/uv 把两类依赖声明在同一份清单里，让工具去协调。

#### PEP 668 与 externally-managed-environment

这是近年最常见的报错之一：

```text
error: externally-managed-environment
× This environment is externally managed
```

原因不是 pip 坏了，而是发行版在 Python 的 `stdlib` 目录里放了标记文件 `EXTERNALLY-MANAGED`（PEP 668 规定的位置），它标记的是**整个解释器安装**。触发它的历史事故是真实存在的：用 pip 升级系统 Python 的某个库，把 `dnf`、`apt` 的 Python 依赖搞坏，甚至 `pip uninstall` 删掉发行版拥有的文件（第 18 章）。

这个标记在虚拟环境里不会触发，因为规则本来就是“虚拟环境内任意安装”。所以在 Debian 12、Ubuntu 23.04+、Fedora、Homebrew 的 Python 上，三种正确做法是：

1. **项目依赖 → venv。** `python -m venv .venv` 后在里面装。这是默认答案，覆盖 90% 的场景。
2. **命令行工具 → pipx。** `pipx install ruff` 会给每个工具建一个独立 venv 并把可执行文件暴露到 `~/.local/bin`，工具之间互不干扰，也不碰系统 Python。`uv tool install` 是同类能力。
3. **系统集成 → 发行版包。** 如果某个东西要被系统服务、系统脚本导入，就用 `apt install python3-xxx`，让它受发行版的生命周期管理。

命令行的逃生门是 `--break-system-packages`（环境变量 `PIP_BREAK_SYSTEM_PACKAGES=1`），把它当成“我知道我在改系统 Python”的显式声明，不要写进任何文档或脚本模板——一写进去就会被复制到别人机器上。

#### 命令速查

| 目的 | pip / venv | uv（项目模式） |
|---|---|---|
| 建环境 | `python -m venv .venv` | `uv venv`（默认 `.venv`） |
| 加依赖 | 编辑文件后 `pip install -r requirements.txt` | `uv add httpx` |
| 装全部 | `pip install -r requirements.txt` | `uv sync` |
| 加开发依赖 | `pip install -r dev-requirements.txt` | `uv add --group dev pytest` |
| 升级单个 | `pip install -U httpx` | `uv lock --upgrade-package httpx && uv sync` |
| CI 冻结安装 | `pip install --require-hashes -r req.txt` | `uv sync --locked` |
| 导出兼容锁 | `pip-compile --generate-hashes` | `uv export --format requirements-txt` |

`--locked` 的含义是“锁文件与清单不一致就直接失败”，这正是 CI 想要的语义；`uv sync --frozen` 则是“不重新解析，直接用现有锁文件装”，两者别混。

#### 常见坑

**`==` 与 `~=` 的语义差别。** `~=2.2` 表示 `>=2.2, ==2.*`；`~=1.4.5` 表示 `>=1.4.5, ==1.4.*`。也就是说尾部组件数决定了“锁到哪一位”，`~=1.4.5` 允许升到 1.4.9 但不允许 1.5.0。写 `~=` 之前先确认自己想要的边界，它的行为跟 npm 的 `~` 不是一回事。

**dev 依赖分组要选一种并写清。** 三种写法并存是常见的混乱源：`[project.optional-dependencies]`（使用者可见，`pip install "pkg[dev]"`）、`[dependency-groups]`（PEP 735，开发专用）、以及 Poetry/uv 的私有分组表。前两者是标准，第三方工具也能读；后者只有对应工具认。给库用前者，给应用用后者，别两边都写一遍。

**锁文件与 CI 必须配套。** 提交了锁文件但 CI 里仍跑 `pip install -r requirements.txt`（没有哈希校验、且会按需升版本），等于没有锁。生产镜像里推荐 `--require-hashes` 或工具自带的冻结模式（第 35 章会展开）。

**`--index-url` 与 `--extra-index-url` 的优先级陷阱。** `--index-url` 是替换默认索引（也就是不指定时用的 PyPI），`--extra-index-url` 是**追加**。关键点在于 pip 会把所有源合并成一个候选池，然后选**版本号最高**的那个：它没有“私有源优先”的概念。于是当一个内部包名恰好也存在于公网 PyPI 上，攻击者只要发一个版本号更高的同名包，pip 就会从公网装它——这就是依赖混淆（dependency confusion，详见第 34 章）。稳妥做法是：`--index-url` 指向唯一可用的源；需要多源时按包名配置而不是全局混合；用哈希校验（`--require-hashes`）让“内容不对”直接失败，而不是靠源顺序赌运气。

**`pip freeze` 当作锁文件。** 它导出的是环境快照而不是求解结果（前面讲 `requirements.txt` 时已经解释过），后果很具体：环境里的脏东西会被一并固化。

**`python -m pip` 而不是 `pip`。** PATH 里存在多个 Python（系统、pyenv、conda、uv 装的）时，裸 `pip` 可能指向另一个解释器；`python -m pip` 才保证装进当前解释器，这是排查“装上了但 import 不到”的第一条命令。

> 一句话总结：Python 打包的标准已经收敛，剩下的分歧在于你选谁来做求解、锁与隔离这三件事。

### 21 Rust：Cargo 的一体化设计

#### 它替代了哪些工具

在 Cargo 出现之前，Rust 项目靠 Makefile 加 rustc 自己拼装；C 语言生态到今天仍在为“构建脚本该用哪一套”争论（见第 25 章）。Cargo 把依赖声明、构建、测试、文档、发布压进一个命令，配置全部落在 `Cargo.toml`：一个 `[dependencies]` 表既是清单（约束），也是构建输入的来源。`cargo test`、`cargo doc`、`cargo publish`、`cargo bench` 不需要额外的插件或脚本。

这种一体化买来的是一致性：任何 Rust 项目用同一条命令还原、构建、测试，CI 配置几乎可以照抄。代价是 Cargo 成了一个很难替换的单点，任何它不支持的构建需求（自研工具链、非常规产物布局）都只能靠 `build.rs` 绕过。

#### SemVer 假设与 resolver 版本

Cargo 假定 crate 遵守 SemVer。`bitflags = "1.0"` 的含义是 `>=1.0.0,<2.0.0`；只要能统一，Cargo 会尽量复用同一个版本，以减少编译时间和让类型在 API 之间可以互换。`0.x` 是特例：`^0.1.2` 的实际范围是 `>=0.1.2,<0.2.0`，前导非零段才定义兼容性。这是承认 0.x 天然不稳定，也意味着升级到下一个次版本就可能是破坏性变更。

解析器版本按 edition 演进（截至 2026 年）：`edition = "2021"` 默认 resolver v2，它改变了 feature 与 target 的合并方式；`edition = "2024"` 默认 resolver v3（resolver v3 需要 Rust 1.84+，而 edition 2024 本身需要 Rust 1.85+），它把 `resolver.incompatible-rust-versions` 的默认值从 `allow` 改成 `fallback`。也就是说 v3 的主要变化不是 feature，而是让解析器倾向选择不超出 `rust-version` 声明的依赖版本。

#### features 合并是抱怨的源头

一个包依赖 `im` 并开 `serde`，另一个依赖 `im` 并开 `rayon`，Cargo 会同时打开两个，因为它们是一份编译产物。这样设计是为了减少重复编译、让类型可以跨 API 传递；代价是 feature 集合会渗透到所有使用方，一个下游启用重型 feature，整个依赖图就跟着变重。社区讨论最多的例子就是 `serde`、`schemars` 这类会被下游顺手打开的 feature，根源在于这个机制没有反向的隔离手段。

resolver v2 的修正是把合并拆细：目标平台不匹配的 target-specific feature 不再启用；`build-dependencies`、proc-macro 的 feature 不再和普通依赖合并；dev-dependencies 只在真正构建测试时才合并。workspace 一起构建时（`--workspace` 或多次 `-p`）feature 仍然统一，想避开只能分成多次 cargo 调用。

排查靠命令：

```bash
cargo tree -d                      # 列出重复出现的依赖版本
cargo tree --invert serde          # 谁引入了 serde
cargo tree --edges features        # 哪个包打开了这个 feature
```

`-d` 特别有用：同一 crate 出现两个不兼容版本时，类型会被编译器视为不同类型，`downcast_ref` 之类通常会在编译期就报错，偶尔才表现为运行期行为异常——这与第 23 章 JVM 的“运行时缺类”是同一类问题的不同表现。

#### 安全卫生与生态现实

`cargo audit` 和 `cargo deny` 不是 Cargo 自带的子命令，而是两个独立工具（`cargo install cargo-audit`、`cargo install cargo-deny` 装上后以子命令形式调用）。前者查 RustSec advisory 数据库里的漏洞；后者读一份 `deny.toml`，把许可证白名单、重复依赖、禁用来源、advisory 检查放进同一个策略文件，更适合当 CI 门禁。`rust-version` 字段声明 MSRV，工具链过旧时 Cargo 会直接报错；resolver v3 的 `fallback` 是在此之外再让解析器避开超出 MSRV 的依赖版本。

生态层面的现实是 crates.io 没有命名空间：包名全局独一无二，`serde` 只能有一个所有者，抢注之后基本没有回收机制。加上“依赖大量小 crate”的惯例，一个中等项目的依赖图动辄几十上百个包，编译时间成为主要成本，`cargo vendor` 和离线构建则把网络风险换成了仓库体积。

> 一句话总结：Cargo 用一体化换来了确定性，代价是 feature 合并无法真正隔离，只能靠拆包规避。

### 22 Go：GOPATH 的教训与最小版本选择

#### 从 GOPATH 到 modules

GOPATH 时代只有一个目录树，所有项目的依赖按 import 路径平铺在 `$GOPATH/src` 下，谁也无法声明“我要哪个版本”。两个项目需要同一个库的不同版本时，没有解。社区先是用 `vendor/` 目录做项目内快照，再出现 dep 这类工具，最后由 modules 接管。

modules 给出的答案不是更聪明的求解器，而是把问题从根上削掉一半：版本以模块为单位，约束是“最低要求”而不是“精确要求”，并且用主版本后缀（`example.com/mod/v2`）让不兼容版本成为**不同的模块路径**。两个主版本可以合法共存，diamond dependency 不再是矛盾，而是两个不同名字的依赖。

#### MVS 到底选了什么

最小版本选择（Minimal Version Selection）的规则一句话：从主模块出发遍历依赖图，每个模块记录所有约束里最高的那个最低要求，遍历结束时这组版本就是构建列表。官方文档的例子很直白——主模块要求 A 1.2 和 B 1.2，A 1.2 要 C 1.3、B 1.2 要 C 1.4，而 C 1.3 与 C 1.4 都要 D 1.2，结果是 A 1.2、B 1.2、C 1.4、D 1.2；即使 B 和 D 有更新版本，没有东西要求它们，就不会被选中。

这不是“取最新兼容版”，而是“取所有约束里最高的最小版本”，它是可判定的、不需要回溯求解的。

好处是可预测和不漂移：MVS 是确定性的，新的依赖版本发布不会改变构建列表，所以 Go 不需要锁文件，`go list -m all` 每次都能重算。坏处同样明显——它“升级不积极”。`go get -u` 是显式的，没有它，间接依赖就一直停在首次引入的最低版本上，一个已知漏洞可能在你完全不碰 go.mod 的情况下继续存在。

还有一处容易被误解的细节：MVS 的计算要读取被选中版本的 `go.mod`，所以当你（或某个升级工具）把某个依赖升到新的 patch 版本时，如果它在新版本里提高了自己某个依赖的最低要求，构建列表会被一起推高。写下 `require C v1.3.0`，得到的可能是 C 1.5.0。

#### go.sum、校验数据库与私有模块

`go.sum` 不是锁文件，它记录的是模块内容的校验和（包括 go.mod 文件本身的哈希），作用是校验完整性；构建列表由 MVS 每次算出来。`go mod tidy` 默认会按 `go` 指令的版本往前一个版本记录校验和，`-compat` 可以改这个默认。校验和不匹配时构建直接失败——这是第 35 章“哈希只能证明内容一致，不能证明首次没被投毒”的具体形态。

`GOPROXY` 是一个逗号分隔的列表，元素可以是代理 URL，也可以是关键字 `direct`（直接走 VCS）或 `off`。go 命令按顺序尝试：某个源返回 404 或 410 才继续下一个，其他错误则停下。因此“公司代理在前、proxy.golang.org 在后”的顺序会同时得到内网优先和公网兜底。

`GOPRIVATE` 声明不走代理、也不查校验数据库的模块路径（例如 `*.corp.example.com`），是私有模块最常用的一个开关；`GONOPROXY` 和 `GONOSUMDB` 可以分别覆盖这两个维度。校验数据库由 `GOSUMDB` 控制，默认是 `sum.golang.org`，设为 `off` 就整体关闭。

#### 工具链也归包管理器管

Go 1.21 起，`go` 命令和工具链分离，`go.mod` 里的 `go` 行声明最低要求的 Go 版本，`toolchain` 行声明偏好的版本（缺省时视作与 `go` 行一致）。当默认工具链比它旧时，go 命令先找 PATH 里名为 `go1.21.9` 的可执行文件，找不到就下载并校验后再运行。

`GOTOOLCHAIN` 默认是 `auto`；设为 `local` 强制只用内置工具链（此时遇到要求更新的模块会直接报错），设为 `GOTOOLCHAIN=go1.21rc3` 这类具体值则强制使用指定版本。有一个值得知道的不对称：工具链是以 `golang.org/toolchain` 模块的形式下载的，但因为具体版本取决于系统默认工具链和 GOOS/GOARCH，它的校验和不写进 `go.sum`，而是靠校验数据库验证——所以 `GOSUMDB=off` 会让工具链下载因缺少校验而失败，且 `GOPRIVATE`、`GONOSUMDB` 对工具链不生效。

排查和离线：

```bash
go mod graph        # 模块依赖图
go mod why -m pkg   # 为什么这个模块在构建列表里
go mod vendor       # 生成 vendor/，离线构建用
```

两个常见坑。一是 `replace` 滥用：指向本地路径的 replace 在 CI 里通常解析不到，或者让本地通过、CI 失败。二是 `go.work` 是否提交——官方建议一般不要提交，因为它会让 CI 选中与“本模块被别人依赖时”不同的版本组合。

> 一句话总结：MVS 用“最低要求取最高”换掉了求解器和锁文件，代价是依赖不会自己变新。

### 23 JVM：Maven 的约定与 Gradle 的灵活

#### Maven 的模型

Maven 用坐标（groupId/artifactId/version）标识依赖，用固定的构建生命周期组织编译、测试、打包、发布，中央仓库提供默认源。依赖声明直接写在 `pom.xml` 的 `<dependencies>` 里，传递依赖自动引入且没有层数限制。所有依赖最终挂到一个扁平 classpath 上，一个类加载器，没有版本隔离——这一点决定了后面所有问题。

#### nearest-wins 与“运行时缺类”

依赖版本的仲裁规则叫最近优先（nearest definition wins）：选依赖树里离项目最近的那个版本；两个版本深度相同时，先声明的那一条胜出。官方文档的例子是 A → B → C → D 2.0 与 A → E → D 1.0，因为经过 E 的路径更短，D 1.0 会被选中。

这为什么会导致运行时错误而不是解析失败？因为仲裁一定会选出**一个**版本，从不因为冲突而中止构建。被淘汰的版本里存在的类就成了“编译期能引用、运行时不存在”：编译时 classpath 上恰好有那个类，运行时挂载的 jar 里没有，于是抛 `NoClassDefFoundError` 或 `ClassNotFoundException`。更麻烦的是方法签名变化——两个版本都有这个类，但方法不同，报错位置和真实原因相隔很远。

根本原因是 JVM 类路径没有原生隔离机制（模块系统和自定义类加载器是绕行方案，但代价大），所以“选一个版本”是框架层面的必然，而不是 Maven 的懒惰。

#### dependencyManagement 与作用域

`<dependencyManagement>` 是官方给的补救：它只声明版本、作用域和排除规则，不引入依赖；但它的优先级高于传递依赖的仲裁。父 POM 里集中写一遍，子模块引用时连版本都不必写。三条来自文档的注意点：dependencyManagement 不影响插件的传递依赖，只影响项目依赖；导入 BOM 用 `<type>pom</type>` 加 `<scope>import</scope>`，多个 BOM 里都有某个 artifact 时，先导入的赢；导入方仍然要自己为传递依赖指定版本，否则会因为缺版本而构建失败。

作用域共六种，常用的四组差别值得记牢：`compile` 是默认，参与所有 classpath 且向下传递；`provided` 参与编译和测试但不进运行 classpath（典型是 Servlet API，由容器提供），且不传递；`runtime` 不进编译 classpath、进运行 classpath；`test` 只用于测试编译与执行，不传递。传递依赖的作用域会按文档里的合并表裁剪，例如 `compile` 依赖带来的 `provided` 传递依赖会被直接丢弃。排除用 `<exclusions>`，按坐标匹配。

排查靠 `mvn dependency:tree`，先看是哪条路径把错误版本拉进来的，再决定用 exclusion 还是用 dependencyManagement 钉版本。

#### Gradle 的不同答案

Gradle 的等价机制是配置约束而不是先来后到：`implementation(platform("..."))` 导入 BOM 作为约束，`enforcedPlatform` 则强制其版本覆盖其他来源；`dependencies { constraints { ... } }` 声明约束而不引入依赖；`resolutionStrategy.force` 和 `resolutionStrategy.failOnVersionConflict()` 提供更硬的开关。Gradle 默认的冲突解法是选**最高**版本而不是最近版本，这一点与 Maven 相反，两边行为不一致是混用两个构建工具时最容易踩的坑。

版本目录（version catalog）是另一件事：`gradle/libs.versions.toml` 用 `[versions]`、`[libraries]`、`[bundles]`、`[plugins]` 四张表集中声明版本，build 脚本里以类型安全的 `libs.xxx` 访问。它解决的是多模块仓库里版本散落各处的可维护性问题，本身不是求解策略——同一个版本仍是全仓库一个值，改一处即全改。

JVM 生态有一个别处少见的强约束：Maven Central 不允许对同一坐标重新发布，这让版本号大致可信，也让“重新发布修正版”这种诱人做法行不通——代价是得发新版本号。sbt 和 Mill 在 Scala 与混合语言构建里各有一批用户，但整个生态的冲突模型是同一套。

> 一句话总结：JVM 的扁平类路径决定了它只能选一个版本，运行时缺类是这个选择的必然产物。

### 24 .NET：NuGet 与 PackageReference

#### 从 packages.config 到 PackageReference

旧式 `packages.config` 是一个独立的 XML 文件，列出项目直接依赖的包及其版本，还原时把包解到解决方案旁边的 `packages/` 目录，项目文件里逐条写入 `HintPath` 引用。它的结构性缺陷是：每个包都算顶层依赖，传递依赖不会自动出现，必须手动装一遍；升级一个库往往要连带调整一串引用。

PackageReference 把依赖声明直接写进 MSBuild 项目文件：

```xml
<ItemGroup>
  <PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
</ItemGroup>
```

这一步换来的是传递依赖、项目级统一的版本选择、`PrivateAssets`/`IncludeAssets` 对资产流的控制，以及不再污染解决方案目录。代价是引入了版本选择问题：`Version="4.0.0"` 的含义是“>=4.0.0，且偏好最低的那个”，官方文档把这个取向叫“最近的最低版本”（nearest minimum version）。它带来一个反直觉的后果：即使仓库里已经有 4.1.0、4.2.0、4.3.0，只要 4.0.0 尚未发布，它就会解析到 4.1.0；等 4.0.0 真正发布，它反而会换成 4.0.0。想看清实际选了哪个版本，需要锁文件和 `dotnet list package --include-transitive`，这也是下面这套可复现性机制存在的原因。

#### packages.lock.json 与集中版本管理

锁文件默认不生成。在项目文件里设 `<RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>` 之后，第一次 restore 会生成 `packages.lock.json`，把直接与传递依赖的完整闭包连同版本一起记下来（官方文档给出的一个理由很具体：`Version="4.0.0"` 在某天可能因为 4.0.0 还没发布而被解析成 4.1.0，等 4.0.0 真的发布，还原结果又会变）。此后在清单未变时，restore 会先按锁文件跑、不再重新求值依赖图；一旦项目文件有变化，它仍会重新解析并在需要时更新锁文件。

CI 应该用 `dotnet restore --locked-mode`。锁文件与项目不一致时不会静默升级，而是直接报错 NU1004，错误信息会明确写出差异，例如目标框架从 `net5.0,net6.0` 变成 `net6.0`，或者某个 `PackageReference` 的版本范围从 `[2.0.0, )` 改成了 `[1.2.3, )`。这条报错在 CI 里出现，基本都意味着有人改了依赖但忘了更新锁文件。

锁文件该不该提交，官方建议和第 5 章讲的一般惯例一致：应用（处在依赖链起始位置、要交付可执行文件的项目）提交；被别的项目引用的库不提交，因为库自己的锁文件管不到上层项目的还原结果。

版本浮动（floating version）会削弱锁文件的价值：`Version="3.6.*"` 表示取区间内最新，没有锁文件时，新版本一发布就会改变下次还原的结果；有锁文件时它停在锁定的那一个，除非显式加 `--force-evaluate` 重新求值。浮动版本是“永远自动升级”和“永远不动”之间的第三个选项，代价是本地与 CI 有可能在同一份代码上得到不同版本。

集中包管理（Central Package Management，CPM）解决的是另一个维度：多项目仓库里同一个包的版本号散落在几十个项目文件里。在仓库根放 `Directory.Packages.props`：

```xml
<PropertyGroup>
  <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
</PropertyGroup>
<ItemGroup>
  <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
</ItemGroup>
```

各项目文件里只写 `<PackageReference Include="Newtonsoft.Json" />`，不写 `Version`，值统一由 props 文件提供；个别项目需要偏离时用 `VersionOverride`。它是逐级向上查找的，所以可以在子目录再放一份覆盖。注意 CPM 和锁文件是两件独立的事，同时启用时两边都要维护。

#### 源、缓存与多目标框架

`NuGet.config` 沿目录层级向上合并，`<packageSources>` 里的顺序就是优先级；在某一层的配置里用 `<clear />` 可以清空继承来的源列表——这是企业内网最常见的写法，目的是防止内部包名意外从公网同名包还原下来。`<packageSourceMapping>` 做得更细：为包名模式绑定允许的源。

全局包缓存默认在用户配置文件下的 `.nuget\packages`（Windows）或 `~/.nuget/packages`，`dotnet nuget locals all --list` 能打印各个缓存的实际路径，`dotnet nuget locals all --clear` 清空。缓存内容错乱和源顺序错乱的症状很像：还原出来的版本或内容不对，先清缓存再复现，能区分是源的问题还是本地状态的问题。

多目标框架（TFM）是 .NET 特有的一层复杂度，`<TargetFrameworks>net8.0;net48</TargetFrameworks>` 会让依赖出现条件分支：用 `Condition="'$(TargetFramework)' == 'net48'"` 给不同框架配不同包。它直接反映在锁文件里——锁文件按框架分别记录，所以加一个目标框架就会让 NU1004 触发。

> 一句话总结：PackageReference 换来了传递依赖，也换来了必须自己维护的锁文件与集中版本表。

### 25 C/C++：没有标准答案的领域

#### 为什么这里没有中心化包管理器

JS、Python、Rust、Go 的包管理器都有中心仓库，C/C++ 没有，原因不在社区懒，而在三个技术前提都不成立。

第一，C++ 没有稳定的 ABI。Linux 上 GCC 与 Clang 默认都用 libstdc++、同属 Itanium ABI，通常可以互链；真正的分界线是标准库实现（libstdc++ 与 libc++）、`_GLIBCXX_USE_CXX11_ABI`（改一次，`std::string` 的内存布局就变了）、MSVC 与 MinGW、以及 glibc 与 musl。第二，没有统一构建系统：Autotools、CMake、Meson、手写 Makefile 长期并存，且每个项目的安装布局各不相同。第三，库的来源本身是分裂的：zlib、OpenSSL 通常由系统包管理器提供，而 header-only 的 fmt、Catch2 往往直接塞进源码树。

于是“装一个包”在这里必须回答两个别处不用问的问题：用哪个编译器编？链接动态库还是静态库？这两个问题不解决，二进制就无法复用。这就是 C/C++ 的“包管理”实质是**可复现的构建配置管理**。

#### 四条路线与各自代价

| 路线 | 拿到什么 | 代价 |
|---|---|---|
| Conan | 配方 + 二进制缓存，跨平台构建矩阵 | 要自建或租用制品库，profile 概念陡峭 |
| vcpkg | 清单模式 + triplet，与 CMake 工具链自动集成 | 大型三元组（triplet）组合下构建量大，需自建二进制缓存 |
| CMake 自带机制 | 零外部依赖，依赖随项目源码一起编 | 无缓存、无版本求解，同步发生在 configure 期 |
| Spack | 源码构建 + 编译器/MPI 变体，环境可整体重现 | 一个变体组合就是一次构建，时间成本高 |

四者不互斥：HPC 之外的项目常见组合是系统包管理器提供基础库、vcpkg 或 Conan 提供其余依赖。

#### Conan：把二进制缓存当第一批公民

Conan 2 的核心概念是配方（recipe，`conanfile.py`）、profile（编译器、架构、构建类型）和二进制包 ID。包 ID 由 settings、options 与依赖共同哈希得出，因此“换编译器”不是覆盖安装，而是多出一个可并存的二进制。

```python
from conan import ConanFile
from conan.tools.cmake import CMakeDeps, CMakeToolchain

class AppConan(ConanFile):
    settings = "os", "arch", "compiler", "build_type"
    requires = "zlib/1.3.1", "fmt/11.0.2"
    generators = "CMakeDeps", "CMakeToolchain"
```

```bash
conan install . --build=missing -s build_type=Release
```

`--build=missing` 的语义值得记住：缺少匹配二进制时回落到源码构建，而不是自动降级到旧版本。如果想装旧版本，必须在配方里写死；默认行为是缺二进制就报错。Conan 也有锁文件：`--lockfile-out=conan.lock` 生成，下次 `conan install` 会优先读取同目录的 `conan.lock`（Conan 2.32 文档口径，2026 年）。

#### vcpkg：用工具链文件接管 `find_package`

vcpkg 的巧妙之处是不发明新构建流程，而是把自己伪装成一个 CMake 工具链文件。在 `CMakePresets.json` 里声明：

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "release",
      "binaryDir": "${sourceDir}/build",
      "cacheVariables": {
        "CMAKE_TOOLCHAIN_FILE": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake",
        "VCPKG_TARGET_TRIPLET": "x64-windows"
      }
    }
  ]
}
```

`vcpkg.json` 里声明依赖，configure 阶段会自动执行安装。两个容易踩的点：所有影响 vcpkg 的变量必须写在第一个 `project()` 之前；清单模式下依赖装到 `${CMAKE_BINARY_DIR}/vcpkg_installed`（经典模式才是 `$VCPKG_ROOT/installed`），因此构建目录一换就等于重装，二进制缓存（`VCPKG_BINARY_SOURCES`）在生产里几乎是必需的。

#### CMake 自带机制：把依赖当源码

`FetchContent` 是最朴素的一条路：在 configure 期把依赖源码拉下来，用 `add_subdirectory` 编进同一个构建树。

```cmake
include(FetchContent)
FetchContent_Declare(fmt
  GIT_REPOSITORY https://github.com/fmtlib/fmt.git
  GIT_TAG 11.0.2)
FetchContent_MakeAvailable(fmt)
target_link_libraries(app PRIVATE fmt::fmt)
```

它省掉了所有外部基础设施，代价也来自同一处：没有版本求解——两个依赖分别要 fmt 10 和 11，冲突只会在编译或链接时暴露；没有二进制缓存，每次干净构建都要重编整棵依赖树；版本可变性靠 `GIT_TAG` 人工保证，没有锁文件。CPM.cmake 是它的一层薄封装，补上版本声明与包缓存，但求解能力依然为零。适合依赖少、构建时间可接受的库和示例项目。

#### Spack：HPC 场景的另一种答案

Spack 面向的是“同一台机器上要并存二十种编译配置”，把它当包管理器用会很别扭。它的模型与第 17 章的 Nix 接近：manifest（`spack.yaml`）加锁文件（`spack.lock`），`spack concretize` 求解，“安装”是前缀目录加一个 view（符号链接聚合的目录树）。

```bash
spack env create sim
spack -e sim add "hdf5+mpi+fortran %gcc@13 ^openmpi"
spack -e sim concretize
spack -e sim install
```

同一个 `hdf5`，`+mpi` 与 `~mpi` 是两个不同的 concretized spec，可以同时在环境里存在——这正是系统包管理器做不到、科学计算又必须要的能力。代价是变体组合爆炸，以及大量包本来就不支持源码外构建（out-of-source build）。

#### 结论

判断标准可以简化成一句话：**你需要二进制缓存吗？**

需要，并且在企业内网分发、要管理自己的构建矩阵，选 Conan 或 vcpkg；依赖少且都是源码友好型，用 `FetchContent` 加 CPM 就够，引入 Conan 只会多一层要维护的制品库；吃编译期变体（MPI、CUDA、不同编译器），只有 Spack 这类模型撑得住。

真正的成本不在选哪个工具，而在构建矩阵有多大：编译器版本 × C 库（glibc 与 musl 不可互换）× 构建类型 × 特性开关，每多一维，需要构建和验证的二进制就翻倍。工具只能帮你管理这些组合，不能帮你减少它们。

外链参考：[Conan 2 `conan install`](https://docs.conan.io/2/reference/commands/install.html)、[vcpkg in CMake projects](https://learn.microsoft.com/en-us/vcpkg/users/buildsystems/cmake-integration)。

> 一句话总结：C/C++ 的包管理是构建配置管理，选型取决于你需不需要二进制缓存。

### 26 Ruby 与 PHP：Bundler 与 Composer

#### 先有语言级分发，后有项目级锁定

Ruby 与 PHP 的演化路径几乎一样，值得单独讲，因为它是理解第 19 至 24 章的一条暗线。RubyGems 与 Packagist 先解决了“把包发出去、让别人装得上”这一层；若干年后，Bundler（2010 年前后）与 Composer 才补上“这个项目到底用了哪几个具体版本”。

这个先后顺序决定了工具的默认行为。`gem install` 是包级的：装进一组共享的 gem 集合，激活哪个版本由运行时决定，两个依赖要同一个 gem 的不同版本时，冲突往往不在安装期暴露，而拖到运行期才炸。`composer install` 恰好相反：只有在没有 `composer.lock` 时它才等同于重新求解，环境换了，装出来的东西也就换了。

Bundler 与 Composer 都是项目级的：清单声明约束，锁文件保存求解结果，求解结果才是“这个项目用哪些版本”的答案。前者的清单是 `Gemfile`、锁文件是 `Gemfile.lock`，另外还有 `gemspec` 描述“我这个 gem 对别人的要求”；后者是 `composer.json` 与 `composer.lock`。一个容易混淆的点：`gemspec` 面向的是你的用户，`Gemfile` 面向的是你自己这个开发仓库——前者不该锁死版本，后者必须锁。

#### `bundle exec` 为什么存在

这是这一章最该讲清楚的机制。`bundle exec rspec` 做的事是：按 `Gemfile.lock` 设置 `BUNDLE_GEMFILE`、`BUNDLE_BIN_PATH`、`RUBYOPT`（`-rbundler/setup`）与 `PATH`，让子进程只看见这份锁文件里的 gem，再执行目标命令。

不写 `bundle exec` 也能跑通，是因为系统里恰好有一个同名的可执行文件；官方文档把这种情形称为“不可靠且痛苦的一大来源”。rails、rspec 这类命令在机器上可能来自另一个版本，你测的东西就不是锁文件里的东西。binstubs 是它的替代品：`bundle binstubs rspec-core` 在 `bin/rspec` 生成一个绑定到本 bundle 的启动脚本，提交进仓库后团队成员直接跑 `bin/rspec` 即可。

部署侧的配置语义也值得记牢（Bundler 4 文档）：deployment 模式要求存在 `Gemfile.lock`、要求它与 `Gemfile` 同步，并把 gem 装到项目的 `vendor/bundle` 而不是系统目录。其中一条设计细节解释了 Bundler 为什么可靠：`without` 只跳过安装被排除的分组，**仍然会下载这些 gem 并参与求解**，这样生产和开发解出的是同一个依赖图，不会因为分组不同而换掉 Rack 的大版本。

版本约束的方言是 `~>`（pessimistic operator）：`~> 2.2` 等价于 `>= 2.2` 且 `< 3.0`，`~> 2` 则是 `>= 2` 且 `< 3.0`，位数决定上限抬到哪一位。RubyGems 官方指南给的判断很克制——在 `gemspec` 里优先只写下限，因为悲观约束会连锁锁死使用者的整个依赖图。另外两条硬事实：RubyGems 不强制 SemVer，但一个版本号一旦发布永不复用，yank 也不会释放这个号码。

#### Composer：把 PHP 的短板变成了自己的职责

PHP 没有内置模块系统，所以 Composer 多了一项别家没有的工作：生成自动加载器。实现方式是 PSR-4 把命名空间前缀映射到目录，开发期按需查找，`composer install --optimize-autoloader` 转成 classmap 以提升性能；`--classmap-authoritative` 更进一步，只认 classmap，不再回退到文件系统查找——快，而且能把类名拼写错误提前暴露成失败。生产部署的惯用组合因此是：

```bash
composer install --no-dev --optimize-autoloader --classmap-authoritative
```

另一处独特设计是把 PHP 本身和扩展当成虚拟包：`php`、`ext-mbstring`、`lib-curl` 都可以写进 `require`。这解决了 PHP 生态的老问题——构建机的 PHP 版本不代表部署机。`config.platform` 可以声明目标环境版本，让求解按目标而不是按当前解释器进行；无法满足的依赖在解析期就报错，而不是留到生产。`--ignore-platform-reqs` 是逃生门，用它的代价是把失败从今天推迟到部署之后。

Composer 的退出码值得记：0 表示成功，2 表示依赖求解失败，`--strict-psr-autoloader` 这类严格模式还会用 6 表示 PSR-4 映射错误。CI 里把 2 和通用失败 1 分开处理，可以直接区分“代码提交错了”和“依赖解不开了”。

#### 共同的坑

两个生态的坑几乎可以互相翻译。第一是锁文件与清单不同步：`Gemfile` 改了没跑 `bundle install`，或 `composer.json` 改了没跑 `composer update`，Composer 会给出锁文件过期的警告，此时 `composer install` 装的是过期版本。第二是平台要求泄漏：在 PHP 8.3 上求解、部署到 8.1，或在 macOS 上求解、部署到 Linux（原生扩展的预编译 gem 与平台相关，`Gemfile.lock` 里的 `PLATFORMS` 段会因此变化）。第三是 dev 依赖混入生产，用 `--no-dev` 或 deployment 模式隔离即可。

> 一句话总结：Bundler 与 Composer 的价值不在装包，而在把“项目用哪几个版本”变成可提交的文件。

### 27 其余生态速览：从 Cabal 到 tlmgr

这一节按“最独特的一点 + 一个代表性命令”处理，不追求覆盖全部功能。

**Haskell（Cabal/Stack）。** 独特之处是两条路线并存：`cabal` 走普通约束求解，用 `cabal freeze` 把解出的版本与 flag 固化到 `cabal.project.freeze`；`stack` 走快照路线，`stack.yaml` 里的 `snapshot` 键（旧名 resolver）指向一个 Stackage LTS 快照，一次性钉住 GHC 版本与整批包版本，再把补丁信息写进 `stack.yaml.lock`。Cabal 官方建议 freeze 文件随可执行程序分发，库则不要提交——因为库的用户需要自行决定版本组合。

```bash
cabal freeze
```

**OCaml（opam）。** 独特之处是 switch 即前缀：每个 switch 是一套独立的编译器加包集合，目录形式的 switch 会在你进入该目录时自动生效，项目因此能各自钉住 OCaml 版本而不需要虚拟环境。

```bash
opam switch create . 5.2.0
```

**Elixir/Erlang（Hex/Mix）。** `mix deps.get` 把 Hex 上的依赖拉到 `deps/` 并写入 `mix.lock`，锁文件记录每个依赖的精确版本与内容哈希，`mix deps.get --check-locked` 可以在 CI 里禁止它顺手升级。

```bash
mix deps.get --check-locked
```

**Dart（pub）。** 首次 `dart pub get` 会解出完整依赖图并生成 `pubspec.lock`，应用提交它、纯库按惯例不提交；`dart pub outdated` 用 Current / Upgradable / Resolvable / Latest 四列，把“当前装的”“能升到的”“约束允许的”“最新的”分开。

```bash
dart pub outdated
```

**Swift（SwiftPM 与 CocoaPods）。** 同一个工程里两套依赖机制同时存在是常态，冲突通常发生在原生依赖的版本约束和构建方式上；SwiftPM 用 `Package.resolved` 记录解析结果，用 `swift package resolve` 复现。

```bash
swift package resolve
```

**R（CRAN 与 renv）。** 独特之处是“库”本身就是隔离单位：renv 为每个项目建一个独立的包库，把整库状态写进 `renv.lock`，再用 `renv::restore()` 在另一台机器上重建，不需要虚拟环境这个概念。

```r
renv::restore()
```

**Julia（Pkg）。** 环境由 `Project.toml`（直接依赖）加 `Manifest.toml`（完整解析结果，含版本与哈希）两文件描述，项目目录就是环境，`Pkg.instantiate()` 按 manifest 精确还原。

```julia
using Pkg; Pkg.instantiate()
```

**Perl（CPAN）。** 历史最久，也最缺项目级锁定：`cpanfile` 声明依赖、`cpanm` 安装是后来的补救，`cpanm --installdeps .` 只保证“装得上”，不保证“装得一样”。

```bash
cpanm --installdeps .
```

**Lua（LuaRocks）。** 与系统库关系最紧：rockspec 里可以直接依赖 C 库，装不上通常不是 Lua 包的问题，而是缺开发头文件。`luarocks --tree ./lua_modules install ...` 给了一个轻量的项目级目录，但没有锁文件。

```bash
luarocks --tree ./lua_modules install luafilesystem
```

**TeX（tlmgr）。** 最反常的一点是常受发行版约束：Debian 打包的 tlmgr 只以用户模式运行，而 Debian 仓库里的 TeX Live 通常落后于 CTAN，因此别在系统安装上直接跑在线自更新。稳妥做法是用官方安装器装到独立目录，让发行版包和 TeX Live 互不干涉。

```bash
tlmgr update --list
```

**PowerShell（PSGallery）。** PSResourceGet（PowerShellGet 3.x）默认把 PSGallery 注册为优先级 50 且标记为**不受信任**，需要显式信任；安装是可写全局模块目录的，因此这不只是提示，而是一次信任决策。

```powershell
Set-PSResourceRepository -Name PSGallery -Trusted
```

**Nim、Zig、V 等新兴语言。** 共同取向是不自建中央仓库，改用 URL 加哈希。Zig 的 `build.zig.zon` 里每个依赖声明 `url` 与 `hash`，官方文档的表述很直白：包来自 `hash` 而非 `url`，URL 只是众多镜像之一；改了 URL 必须删掉旧 hash，否则等于声明你还期望在那个新地址拿到旧内容。

#### 三条规律

第一，越年轻的语言越倾向内置一体化工具。Go 把模块、构建、工具链版本写进 `go.mod`，Zig 把依赖表放进 `build.zig.zon`，它们没有“先有一个社区工具、再被官方收编”的阶段，也就没有工具间互相摩擦的成本。

第二，依赖锁定几乎是共识。差异只在形式与惯例：从 `cabal.project.freeze`、`stack.yaml.lock`、`mix.lock`、`renv.lock`、`Manifest.toml` 到 `Package.resolved`，都在记录“上次解出的是什么”。没有锁文件的 CPAN 和 LuaRocks 不是想反潮流，而是成型太早。

第三，生态规模决定“别人替你踩坑”的速度。包多、用户多，失败模式会被反复记录成文档和默认值；包少的小生态里，失败往往只能靠读构建日志自己定位——这比任何设计差异都更影响日常体验。

> 一句话总结：小生态的工具差异不大，没有锁文件的那些才是真正的风险点。

#### 四条设计轴

**一体化程度。** Go、Rust、Dart 是一条龙：包管理、构建、测试、发布在同一份配置里，好处是依赖与构建配置天然一致，代价是“换掉工具”的成本极高。Python 与 JS 是松耦合：pip、venv、构建后端、lock 工具各管一段，好处是每层可独立演进，坏处是组合方式多到需要专门写文档，而且边界处最容易出问题——“我装了但 import 不到”几乎都发生在这里。C/C++ 属于第三种情况：不是选择分离，而是从来没有过合一的可能。

**求解策略。** 回溯（PubGrub、Bundler、Composer、Conan）能证明无解并给出原因，代价是冲突多时耗时不可预测；贪心或最近优先（Maven、NuGet）几乎不会失败，但失败被转移成运行期的 `NoClassDefFoundError`；激进策略（npm 默认取最新兼容版本）让新项目省事，却把“某次干净安装突然换了一批版本”变成常态；MVS（Go）取所有约束中最低版本里的最高者，结果可预测但社区升级意愿低。这里没有优劣，只有你把成本放在解析期还是运行期。

**隔离模型。** 嵌套结构兼容性最好，幻影依赖与磁盘放大是它的代价；内容寻址加符号链接（pnpm）几乎消除重复与幻影依赖，代价是依赖布局不合常规，某些工具会假设依赖在 `node_modules` 顶层；环境级隔离（venv、conda、opam switch、renv 库）隔离的是环境本身而不仅是版本，代价是必须显式激活。C/C++ 的隔离落在构建前缀上，因为“同一个库的两个版本”在链接层面的处理方式，与脚本语言完全不同。

**发布治理。** crates.io 与 npm 没有强制命名空间（npm 的 scope 可选），PyPI 长期是先到先得，Go 干脆用模块路径即 URL 来绕开所有权问题，Maven 的 groupId 靠域名反写来约定，RubyGems 的规则是版本号永不复用。这些差异直接决定了第 34 章那些攻击的形态：没有命名空间的地方，抢注与依赖混淆（dependency confusion）成本最低。

#### 给读者的判断框架

拿到一个新生态，按这个顺序问四个问题就够：

第一，锁文件是什么、提交了吗、CI 用的是冻结模式还是重新求解？这一步决定构建可不可复现。

第二，依赖如何求解、冲突时是报错还是静默挑一个？静默挑一个的工具，需要额外手段才能查出实际生效的版本。

第三，隔离边界在哪里、安装或构建时会不会执行代码（见第 8 章）？会执行的话，信任范围就是这个生态的全部上游维护者。

第四，社区治理：命名空间、撤销政策、签名与证明机制成熟到什么程度（第 34 至 37 章展开）。

最后回到一个反直觉的判断：为什么“最好的包管理器”不可比。MVS 之所以在 Go 里成立，是因为 Go 编译快、无原生依赖、依赖图相对窄；同一套策略搬到需要编译 C 扩展的生态会立刻失效。工具的设计空间由语言的构建特性、生态的年龄和包的数量级共同决定，而这些条件不可迁移。有用的比较不是“谁更好”，而是“它在哪个约束下做了取舍，那个约束在你的项目里是否成立”。

> 一句话总结：先看锁文件与求解器，再看隔离与脚本执行，最后才轮到工具口碑。

## 第四部分 · 应用层与工具链

### 29 Flatpak、Snap 与 AppImage：应用分发的新一层

桌面应用有一个发行版包管理器解决不了的问题：**应用与系统库的版本节奏不一致**。发行版大约每半年（Fedora）到两年（Debian、Ubuntu LTS）才发布一次，而浏览器、IDE、设计工具可能每两周更新一次。让上游为每个发行版各打一份包，成本落在应用作者身上；让用户等发行版升级，体验落在用户身上。

Flatpak、Snap、AppImage 是对这个问题的三种不同回答，共同点是**把运行时也一起打包**，不再依赖系统提供依赖。

#### Flatpak：运行时 + 沙箱 + portal

Flatpak 把应用与它依赖的运行时（runtime）分开打包，多个应用共享同一个 runtime，因此不会每个应用各带一份 GTK 或 Qt。应用运行在沙箱里（基于 bubblewrap），要访问文件、网络、设备，需要权限声明，用户可以通过 `flatpak override --user` 调整。

```bash
flatpak install flathub org.gnome.Builder
flatpak run org.gnome.Builder
flatpak update
flatpak override --user --filesystem=~/projects org.example.App
```

它的优点是技术中立、Flathub 集中分发、运行时共享减少了重复。代价是磁盘（可能同时存在多个 runtime 版本）、沙箱带来的文件访问摩擦，以及主题与字体集成需要额外工作。

#### Snap：守护进程与自动更新

Snap 由 `snapd` 守护进程管理，自动更新是默认行为，隔离分严格（strict）与经典（classic）两种模式。它由 Canonical 运营商店，后端高度中心化。

它的优点是跨发行版一致、更新自动化、服务器端也有使用场景。争议同样明确：自动更新的时间窗口不可控（生产环境尤其敏感）、首次启动速度受 squashfs 挂载影响、商店中心化意味着分发权集中在一家公司。企业内网部署通常需要自建 Snap Store 代理。

#### AppImage：单文件，无依赖解析

AppImage 是“把应用和它的库打进一个可执行文件”。它不需要安装、不需要 root、在很老的系统上也能跑，这是它最大的价值。

代价是没有基础设施：默认没有更新机制（除非应用内置了更新组件）、没有系统集成（菜单、文件关联要自己处理）、体积大，而且**安全修复只能靠用户手动换文件**。它适合“一次性工具”和“对老旧环境兼容”的场景，不适合当作长期维护的分发方式。

#### 它们与系统包管理器的关系

这层机制不替代系统包管理器，而是改变了分工：系统包管理器仍然管内核、驱动、系统库和基础工具；应用层分发机制管那些更新节奏快、依赖复杂的用户态应用。

理解了这一层，也就理解了后面第 30 章的容器：**容器是把“自带依赖”推到极致的做法**，代价同样是体积和重复。

> 一句话总结：应用层分发用“自带运行时”换更新自由，代价是磁盘、重复与集中化的分发权。

### 30 容器与 OCI 镜像：分发单元的迁移

容器镜像把分发的单位从“包”变成了“镜像”。这个变化带来一个直接后果：**锁定的单位也跟着变了**——从锁文件里的版本号，变成镜像的 digest。

```bash
docker pull debian:12.5@sha256:...
```

tag（包括 `latest`）是可变的指针，digest 指向不可变的内容。生产环境如果只写 tag，就等于接受“某天拉到的内容和我上次验证的不一样”。这是容器场景里最容易被忽略、后果又最直接的一条规则。

#### Dockerfile 里调用包管理器的规范做法

```dockerfile
FROM debian:12-slim@sha256:<digest>

# update 与 install 必须在同一个 RUN 里：分开写会命中缓存，
# 导致使用过期的索引安装
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates curl \
 && rm -rf /var/lib/apt/lists/*

# 先复制锁文件再安装依赖，最后复制源码：
# 源码改动不会导致依赖层失效
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY . .
```

四个要点：`update` 与 `install` 合并；装完清理包管理器缓存；先锁文件后源码以利用层缓存；基础镜像按 digest 固定。能固定包版本（如 `curl=7.88.1-10`）时更好，代价是升级要显式改 Dockerfile，而这正是可复现性的本来含义。

#### 多阶段构建与 distroless

多阶段构建把“构建环境”和“运行环境”分开：builder 阶段装编译器、SDK、包管理器，runtime 阶段只复制产物。

```dockerfile
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12
COPY --from=builder /out/app /app
ENTRYPOINT ["/app"]
```

这不仅缩小体积，更是安全上的改进：**安装脚本、构建工具、包管理器缓存都留在 builder 阶段**，运行镜像里没有它们（呼应第 8 章）。distroless 与 scratch 把这条路走到极致——没有 shell、没有包管理器，攻击者拿到 RCE 也没有现成的工具可用（但仍能发起网络请求或自带载荷）。代价是调试困难：没有 shell 就得靠临时调试容器或静态编译的调试工具。

#### 镜像里的“包管理”问题

- **无法单包回滚**：镜像是一个整体，回滚意味着换 digest。这既是缺点（粒度粗）也是优点（状态明确）。
- **层内的一致性依赖基础镜像**：`apt-get install` 在层里装到的版本取决于基础镜像的索引，所以同一个 Dockerfile 在不同时间构建会得到不同结果——除非固定包版本或固定基础镜像 digest。
- **跨架构**：多架构构建（amd64/arm64）意味着构建矩阵回来了，而且 Python 的 wheel、npm 的可选依赖在不同架构上差异更大（见第 2、5 章）。
- **层缓存与锁文件**：`COPY` 顺序错了，锁文件变化就不会触发依赖重装，于是出现“锁文件改了但镜像里还是旧依赖”。

容器是最彻底的隔离方案，也是最重的：每次构建都要重新获取、每一次运行都有额外的启动与存储开销。它值得，通常是因为部署与一致性收益大于这些成本。

> 一句话总结：容器的锁定单位是 digest，不是版本号——凡是可变的指针，都不能作为可复现的依据。

### 31 Bazel、Nx、Turborepo：从依赖管理到构建图

先划边界：**包管理器回答“拿哪些代码”，构建工具回答“怎么把这些代码变成产物”**。前者管理输入，后者管理过程。混淆两者，就会出现“我换了包管理器为什么构建没变快”这类问题。

#### Bazel：目标图 + 沙箱动作 + 远程缓存

Bazel 把每个构建步骤建模成**动作（action）**，输入与输出都显式声明。因为输入完全声明，动作可以在沙箱里执行、可以被哈希、结果可以被缓存——输入没变就不重跑，本地或远程缓存命中就直接取产物。

规则（rule）定义“如何构建某类目标”，目标（target）通过依赖关系组成图。外部依赖由 bzlmod（`MODULE.bazel`）管理，并有锁文件保证解析结果稳定。

它的收益在大规模 monorepo 上非常明显：增量构建的正确性由机制保证（不是靠时间戳猜测）、多语言可以共用一套构建与缓存、CI 上能只重跑受影响的目标。代价也很明确：学习曲线陡、要为每种语言适配规则、构建描述文件的维护量不小，而且它的收益随仓库规模增长——小仓库用 Bazel 是纯负债。

#### Nx 与 Turborepo：JS/TS monorepo 的任务编排

这两个工具不做依赖获取——依赖仍然由 npm/pnpm/yarn 安装。它们补的是“任务图与缓存”：

- 识别项目之间的依赖关系，从而算出**受影响的包**
- 把 `build`/`test`/`lint` 组织成带依赖的任务图并并行执行
- 本地与远程缓存产物，命中即跳过

在 Node 生态里，这往往就是把 CI 从二十分钟压到两分钟的关键。它们的前提是仓库结构清晰（工作区、包边界明确），否则会陷入“缓存命中率低、配置难维护”的状态。

Pants、Buck2 属于同一位置的其他选择，取舍类似：能力更强、门槛更高。

#### 什么时候值得上

判断标准不是“工具有多先进”，而是三个具体问题：仓库规模是否让全量构建变得不可接受；是否真的存在多语言构建需求；构建结果是否需要强可复现（审计、发布、合规）。三个都不成立时，包管理器加一个简单的任务脚本就够了。

> 一句话总结：包管理器管代码从哪来，构建工具管产物怎么算——把这两件事分开，选型就不再纠结。

### 32 版本管理器不是包管理器：nvm、pyenv、rustup、asdf、mise

这两类工具经常被混为一谈，而混淆它们的代价是具体的：装完 nvm 之后发现依赖装不上，于是去查包管理器的文档，方向从一开始就错了。

- **版本管理器（version manager）**换的是**运行时/工具链版本**：Node 18 还是 20，Python 3.11 还是 3.12，rustc 1.7x 还是 1.8x。
- **包管理器（package manager）**装的是**依赖包**：库、框架、工具。

两者是正交的两个维度。

#### 常见工具

| 语言 | 工具 |
|---|---|
| Node | nvm、fnm、volta |
| Python | pyenv |
| Rust | rustup |
| Ruby | rbenv |
| 多语言 | asdf、mise、proto |

#### 机制：shim 与 PATH

主流实现有两类。pyenv、rbenv、asdf、volta 走 **shim**：把一个代理可执行文件放在 PATH 的最前面，运行 `node` 或 `python` 时，shim 根据当前目录的版本声明（`.nvmrc`、`.python-version`、`.tool-versions`）决定真正执行哪个版本。nvm 不用 shim——它是 shell 函数，`nvm use` 直接把所选版本的 bin 目录前置到 PATH（nvm-windows 则用符号链接指向对应版本目录）。

好处是切换成本极低、可以按目录按 shell 切换。代价是**真实路径被隐藏**：当你执行 `pip install` 时，包会装进 shim 背后的那个解释器，而不是你以为的那个。

排查方法永远是一样的——先问“真正在跑的是谁”：

```bash
which -a python        # 所有候选
python -c "import sys; print(sys.executable)"
node -v && command -v node
```

Windows 上对应 `Get-Command python -All` 与 `(Get-Command python).Source`。

#### 项目级声明要提交

`.nvmrc`、`.python-version`、`.tool-versions`、`rust-toolchain.toml`、`.mise.toml`，以及 `package.json` 的 `engines` 字段——这些文件的作用和锁文件类似：**把“我机器上恰好是这样”变成“仓库要求这样”**。

版本管理器与包管理器配合时，顺序也很重要：先切运行时，再装依赖。反过来的话，依赖会落到上一个运行时上。

#### rustup 的特殊之处

rustup 同时管工具链、组件（clippy、rustfmt）和目标平台（`x86_64-unknown-linux-musl` 之类），还能根据 `rust-toolchain.toml` 自动下载指定版本。Go 也有类似能力：`go.mod` 里的 `toolchain` 行会在构建时获取指定的 Go 版本（见第 22 章）。这类“包管理器顺带管工具链”的设计，正在把两个维度合到一起。

#### 与容器、Nix 的关系

把工具链版本也纳入声明式管理，是团队一致性最好的做法：devcontainer 镜像、`nix develop`、`mise.toml` 都能让“新同事的第一条命令”变成一条，而不是七条。

> 一句话总结：先确认真正在运行的解释器是谁，再决定用哪个命令装包——大多数“环境问题”都错在这一步。

### 33 私有仓库与依赖代理：企业环境的必修课

很多团队第一次认真对待依赖基础设施，都是在一次事故之后：上游删了包、公网仓库挂了、合规要求出具组件清单、或者发现生产镜像里装着来源不明的包。

#### 为什么需要

- **气隙与网络限制**：构建机不能直连公网
- **合规与许可证审查**：需要知道实际用了哪些组件与许可证
- **可用性**：上游删包或服务故障时，构建不能跟着停
- **内部包分发**：私有库不能发到公网仓库
- **审计**：谁在什么时候拉取了哪个版本，是事件响应的证据

#### 三种部署形态

| 形态 | 作用 | 典型用途 |
|---|---|---|
| 代理缓存（proxy） | 转发公网仓库并缓存 | 加速、断网可用 |
| 宿主仓库（hosted） | 存放内部发布的包 | 私有库分发 |
| 聚合仓库（group/virtual） | 把多个源聚合成一个 URL | 客户端只配一个源 |

常见实现：Nexus、Artifactory、Cloudsmith、GitHub Packages、GitLab Package Registry；语言专属的还有 devpi（PyPI）、Verdaccio（npm）、Harbor（容器镜像）。

#### 配置要点

- **客户端只配一个聚合源**。这样优先级由服务端定义，而不是由客户端的多源合并逻辑决定——后者的典型反例是 pip 的 `--extra-index-url`，它会把多个源合并，同名包可能来自公网（见第 35 章）。
- **凭据不要写进仓库**。用环境变量或 CI 密钥注入；锁文件、Dockerfile、仓库内配置文件都不应该出现 token。
- **自签证书要装进信任链**。否则每个工具都要加例外参数（`--trusted-host` 之类），例外一多就没人记得为什么有。
- **定期验证离线可用性**：把外网断开跑一次完整构建。这是最直接能证明代理真的缓存住了的方法。

#### 治理

- **内部包使用命名空间或 scope**，并确保公网源不能顶替内部命名空间——这是依赖混淆最直接的防线。
- **保留审计日志**：包名、版本、请求者、时间。事件发生时，“我们到底装了没有”这个问题必须有答案。
- **缓存策略要允许回源**：把缓存永久冻结，等于把安全修复也一起冻结了；需要明确什么时候允许拉取新版本。

> 一句话总结：私有仓库的价值不在于“快”，而在于把依赖的可用性与审计权收回到自己手里。

## 第五部分 · 供应链安全

### 34 威胁模型：依赖链为什么脆弱

装一个依赖，你信任的不是一个包，而是：**它的全部传递依赖 + 全部维护者 + 整条发布链路**（包括仓库账号的安全策略、CI 的 token 权限、以及签名机制覆盖到哪一步）。

#### 攻击面清单

**typosquatting（包名抢注与拼写诱导）**：注册与流行包相近的名字（如 `reqeusts`），等待手快或拼错的人安装。更精细的做法是同时伪造空壳仓库与虚假文档，让搜索结果看起来可信。

**dependency confusion（依赖混淆）**：在公网仓库发布与内部包同名的包，并给一个更高的版本号。如果客户端把公网源与内部源**合并**（比如 pip 的 `--extra-index-url`），求解器可能选中公网那个更高版本——于是内部代码意外地执行了外部代码。

**维护者账号接管**：钓鱼、凭据泄露、CI token 泄露。攻击者以维护者身份发布一次“正常更新”，所有下游都会在例行升级中拿到它。这类攻击最难防，因为它**能通过签名验证**——签名只证明“是维护者发布的”，不证明“发布的东西是安全的”。

**安装脚本 RCE**：npm 12 之前，一步 `postinstall` 就能执行任意代码；npm 12 起生命周期脚本默认不执行、需要显式 allowlist（见第 8 章），但 Python 的 PEP 517 构建后端与 Rust 的 `build.rs` 仍然会在安装或构建时执行。攻击者不必等你运行程序，安装就够了。

**上游投毒与长期渗透**：三个常被引用的案例代表了三种不同的路径。

- **event-stream（2018）**：原作者交出维护权后，新维护者通过新增依赖注入针对特定钱包应用的恶意代码。路径是“所有权转移 + 恶意子依赖”。
- **ua-parser-js（2021）**：维护者账号被劫持，发布带挖矿与窃密代码的版本。路径是“账号接管”。
- **xz-utils（2024，CVE-2024-3094）**：攻击者用长期社交换取提交权限，逐步植入后门，几乎进入主流发行版。路径是“长周期信任渗透”。

**protestware 与自毁代码**：作者在包内加入针对特定地区或用户的破坏逻辑，或以删库作为施压手段。它提醒一个事实：**作者随时有权改变包的行为**，而你依赖的是他此刻的选择。

#### 为什么难防

JS 与 Python 项目的传递依赖动辄几百上千个（Go、Rust 通常少一个量级，但没有本质区别），每个都有自己的维护者、发布流程与安全水平；逐个审计在多数团队里不现实；而“不升级”又意味着放弃安全修复。这是结构性困境，不是态度问题。

从攻击者视角看，经济性也很清楚：一个包名或一次钓鱼的成本极低，影响面却可以覆盖成千上万的下游，归因还困难。

#### 应对的姿态

结论不是“关掉网络、从此不用依赖”，而是**把依赖当代码来审计，并承认防护是分层的**：

1. 能用机制自动挡住的，不要靠人（第 35 章）
2. 能证明来源与构建过程的，比“看起来没问题”更可靠（第 36 章）
3. 残余风险要显式记录，而不是默认忽略

> 一句话总结：你在信任的不是一个包，而是它背后所有维护者与整条发布链路。

### 35 防御（一）：锁定、校验与最小权限

#### 先锁死可复现性

这一步几乎没有争议，而且收益最大：

- 提交锁文件，CI 用冻结模式安装（`npm ci`、`--frozen-lockfile`、`--locked`）
- 容器镜像按 digest 固定，不用可变的 tag
- 保持完整性校验开启：`go.sum`、lockfile 的 integrity 哈希、`cargo` 的校验和，都不要用 `--no-package-lock`、`--no-deps`、`strict-ssl false` 之类的捷径绕过

**但必须理解它的边界**：哈希与锁文件只能防“在你验证过之后被篡改”，防不住“第一次就装到被投毒的新版本”——因为那个哈希本来就来自被投毒的包。第一次信任必须靠别的机制：人工过目、发布时间门槛、来源限制。

#### 减少执行面

安装期执行代码是最大的风险来源（第 8 章），所以优先级是：**能不执行就不执行，必须执行就隔离执行**。

```bash
npm ci --ignore-scripts        # 显式禁用依赖的安装脚本（npm 12 起默认已禁用）
pip install --only-binary :all: -r requirements.txt   # 只装 wheel
```

- 需要跑脚本的包（通常是原生模块）走白名单：npm 12 起用 `package.json` 的 `allowScripts` 配合 `npm approve-scripts` 授权，并逐个说明原因。
- 构建与安装放进容器或沙箱：非 root 用户、只读文件系统、**构建期无网络**。无网络是性价比最高的一招，它同时挡住了“构建时偷偷下载东西”这一类问题。
- 把“下载”和“执行”分开：先取包并记录哈希，再在受控环境里安装。

#### 依赖最小化

每删掉一个直接依赖，你同时删掉了它带来的整棵子树。这一点在审计上极其划算。

新增依赖时的过目清单：

- 维护者是谁，有几个人，最近的发布频率如何
- 是否包含安装脚本、`build.rs`、原生构建步骤
- 包的下载量与依赖它的人有多少（不是安全证据，但影响暴露面）
- 是否可以用几十行代码自己实现，从而免掉一个依赖

#### 组织层面的策略

- **私有源优先**：内部命名空间不允许被公网源顶替（第 33 章），并**避免使用把多个源合并的配置**（如 pip 的 `--extra-index-url`）。
- **版本年龄门**：新发布的版本先等 N 天再允许进入生产。这不能挡住长期渗透（xz 那种），但能挡住大量“投毒后一小时内被抓”的机会型攻击。
- **生产依赖变更走审批**：不是为了卡人，而是为了让“这个依赖是谁批准的、为什么”有记录。

#### 现实提醒

安全措施只有在“能自动执行、不阻断开发”时才活得久。人肉全量审查撑不过三个月，之后会退化成“全都点通过”。所以策略应该是：机制负责大部分，人力集中在新增直接依赖和特权变更上。

> 一句话总结：哈希防篡改、锁文件防漂移，但第一次信任只能靠来源限制与人工判断。

### 36 防御（二）：签名、证明与 SBOM

#### 两个不同的问题

这是最容易混淆的一点：

- **签名**回答“谁发布的”——身份问题
- **证明（provenance / attestation）**回答“它是怎么构建出来的”——过程问题：哪个仓库、哪个 commit、哪个 CI 工作流、什么构建参数

两者都重要，但替代不了彼此。签名挡不住“维护者账号被接管后正常发布”，证明则能显著提高这类攻击的成本——因为攻击者还必须伪造出与源码一致的构建过程记录，而这个记录会进透明日志。前提是构建平台本身可信：如果攻击者能改 CI 工作流或仓库配置，provenance 依然会显示为“真实”，所以还需要 SLSA L3 与工作流保护。

#### Sigstore 生态

Sigstore 把“密钥管理”这个最大的落地障碍变成了“身份管理”：

- **cosign**：签名与验证工具
- **Fulcio**：签发与 OIDC 身份绑定的短期证书，不再需要长期私钥
- **Rekor**：透明日志，提供“某个签名在某个时间点确实存在”的公开可验证记录

#### 各生态的现状

| 生态 | 机制 | 主要缺口 |
|---|---|---|
| npm | provenance 证明（受支持的 CI 发布时生成），`npm audit signatures` 可校验 | 覆盖面取决于发布者是否启用 |
| PyPI | Trusted Publishing（OIDC，免长期 token）与证明 | 老项目迁移缓慢 |
| crates.io | Trusted Publishing（OIDC，2025-07 起）+ 发布者 token | 仍无强制的构建证明 |
| Go | `go.sum` + 校验和数据库 | 只保证完整性，不证明构建过程 |
| 容器 | cosign 签名、SLSA provenance、in-toto | 采用率不均衡 |

**SLSA** 是一套描述“构建防篡改性”的分级框架：等级越高，越要求构建平台可信、输入显式声明、过程可审计。它是目标框架而不是一键工具，落地通常从“在 CI 里生成 provenance”开始。

#### SBOM：审计的起点

SBOM（软件物料清单）的主流格式是 **SPDX** 与 **CycloneDX**。两个要点：

1. **在构建产物上生成**，而不是在源码目录生成。源码目录里的清单会漏掉实际链接进去的组件。
2. 它是**审计起点，不是安全保证**。SBOM 只回答“我包含了什么”，不回答“其中哪个有已知漏洞、是否可达、是否真的能被利用”。

#### 工具链与排序方法

- **升级**：Dependabot、Renovate——配合锁文件与测试，让小步升级成为常规动作
- **漏洞扫描**：Trivy、Grype、OSV-Scanner，以及各语言自带的 `cargo audit`、`npm audit`、`pip-audit`
- **生成 SBOM**：Syft 之类的工具

扫描结果的排序比数量重要：优先看**可达性**（这段代码真的会被调用吗）、**暴露面**（是否在公网服务里）、**利用条件**（是否需要特定配置或权限）。按 CVSS 分数从高到低处理，通常会让人淹死在告警里，然后开始无视所有告警——那才是真正的安全风险。

> 一句话总结：签名证明身份、证明描述过程、SBOM 记录组成——三者互补，都不能替代“别装你不理解的东西”。

### 37 平台机制一览与个人清单

#### 一览表

| 生态 | 现有机制 | 成熟度 |
|---|---|---|
| npm | provenance 证明、`npm audit`、签名校验命令 | 中高，取决于发布者 |
| PyPI | Trusted Publishing（OIDC）、2FA 推广、证明 | 中高，老包迁移慢 |
| crates.io | Trusted Publishing（OIDC）、token 安全、yank 政策、`cargo audit`/`cargo deny` | 中 |
| Go | `go.sum`、校验和数据库、模块代理 | 高（完整性），低（构建证明） |
| Maven Central | 签名与校验和、不可变发布 | 高（不可变），中（身份验证） |
| NuGet | 包签名、可信发布流程 | 中 |
| 容器/OCI | cosign 签名、SLSA provenance、in-toto | 中，采用不均衡 |

#### 治理：平台侧在做什么

- **账号安全**：2FA 与硬件密钥要求、token 权限最小化、CI 的短期凭据（OIDC 而非长期 token）
- **撤销与 yank 政策**：允许撤回但通常不允许覆盖已发布版本；撤回后下游如何应对是各生态的长期痛点
- **命名空间所有权**：争议处理机制、商标与企业命名空间、弃用与交接流程
- **不可变性**：Maven Central 长期不允许覆盖版本，这类约束看似不灵活，却是可复现性的地基

#### 个人与小团队的可执行清单

1. 提交锁文件；CI 一律用冻结安装
2. 生产镜像按 digest 固定基础镜像
3. 默认禁用安装脚本，例外走白名单
4. 新增直接依赖做一次人工过目：维护者、安装脚本、最近发布
5. 开启自动升级 PR，小步合并，并保证测试覆盖
6. 漏洞扫描按“每个 PR 跑增量 + 每周跑全量”的节奏执行，并按其可达性而不是分数排序处理
7. 对关键产物生成 SBOM 并存档
8. 私有源优先，内部包使用命名空间，避免多源合并配置
9. 凭据只通过环境变量或 CI 密钥注入，绝不进仓库
10. 每季度做一次“从零重建”演练：清空缓存重新安装，验证真的能复现

#### 一句话原则

安全预算要花在**能自动执行、且不阻断开发**的机制上。做不到这两点中的任何一条，措施通常在几周到三个月内退化。

> 一句话总结：先让机制自动兜住大部分风险，人力只留给新增依赖与特权变更。

## 第六部分 · 实践

### 38 决策指南：什么场景用什么

先说清一件事：不存在“推荐一个包管理器”这回事。真正要回答的是——在这台机器的这个场景里，谁负责系统、谁负责项目、谁负责用户级 CLI。三条边界划清了，选型基本自动确定。

#### Linux 服务器

**首选**：发行版自带的那套（Debian/Ubuntu 用 apt，RHEL 系用 dnf）。**备选**：需要更新的语言运行时或工具时，用容器，或走语言级工具的用户级安装（`uv`、`rustup` 这类不碰系统目录的方式）。

**不要做**：在服务器上 `pip install` 到系统 Python；把第三方 PPA/Copr 与官方源混着开却不做优先级控制；用 Nix/Homebrew 覆盖系统库。

理由很朴素：服务器上“可预测”比“新”值钱得多。发行版的安全更新通道，是你唯一能自动化处理漏洞公告的路径；一旦关键库被跨平台包管理器替换，安全更新就没人替你兜底了。

#### 桌面工作站

**Linux 滚动发行版**（Arch、openSUSE Tumbleweed）：就用 pacman/zypper，代价是必须接受完整升级的纪律，并养成看发布公告的习惯。**Debian 系桌面**：apt 管系统，Flatpak 管桌面应用，两者分工明确。**macOS**：Homebrew 管 CLI 与 GUI（cask）。**Windows**：winget 管常规软件，Scoop 管免管理员的 CLI 工具集，Chocolatey 留给企业内部的既有脚本。

**不要做**：在滚动发行版上做部分升级（见第 12 章）；用 Homebrew 覆盖 macOS 系统自带的组件（见第 15 章）。

#### 容器基础镜像

**首选**：镜像自带的最小包管理器（Alpine 的 apk、`debian:12-slim` 的 apt），构建期安装、运行期不带构建工具，基础镜像按 digest 固定（见第 30 章）。**备选**：distroless 或 scratch + 静态二进制。

**不要做**：在容器里执行 `apt upgrade`；把编译器、头文件、包管理器缓存留在运行镜像里。

#### 数据科学环境

**首选**：conda/mamba 或 pixi 管非 Python 依赖（CUDA、数学库、编译器），pip/uv 管纯 Python 包；重环境用容器固化。**不要做**：在同一个环境里让 pip 与 conda 都去管同一个包——这是最难排查的一类损坏（见第 20 章）。

#### 多语言 monorepo

**首选**：每个子项目用自己的语言级工具，外加统一的任务编排与缓存层（Turborepo/Nx/Bazel，见第 31 章），CI 里对每种语言都用冻结安装。

**不要做**：试图用一个包管理器管所有语言。以环境为单位的方案（Nix、conda）能做到，但那是另一套成本模型。

#### 离线与气隙环境

**首选**：企业代理仓库（Nexus、Artifactory 之类）加定期镜像同步；语言级依赖用 vendor 目录或离线包目录随代码一起进版本库。**不要做**：让构建依赖公网 registry 的实时可用性——它总会在最不方便的时候出问题。

#### 一台机器上的共存规则

1. **系统关键组件**（libc、openssl、系统 python3、系统 curl）只由系统包管理器管，任何其他工具都不许覆盖。
2. **项目依赖**只进项目目录：venv、node_modules、目标构建目录，而不是全局。
3. **用户级 CLI** 交给专用工具（pipx、uvx、Scoop、Homebrew），并且把 PATH 顺序显式写进 shell 配置——不要靠“装的时候顺序刚好对”。
4. 需要**两个版本并存**时，用版本管理器或容器，而不是覆盖安装（见第 32 章）。

#### 反模式清单

- 用系统包管理器装语言库，事后再用语言级工具装同一个包
- 用语言级包管理器装系统库（尤其是编译器和 OpenSSL）
- 把“全局安装”当作部署方案：全局状态无法回滚，也无法在 CI 复现
- CI 用 `npm install`、本地用 `npm ci`（或反之）：两者对锁文件的处理不同，差异会在最坏的时刻暴露
- 依赖“最新版”而不锁定，同时又在生产环境要求稳定

#### 团队层面

只有三条硬要求：**锁文件必须提交**；**本地与 CI 使用同一条冻结安装命令**；**依赖升级走独立的 PR**，而不是顺手 `update` 一把混在功能提交里。前两条保证“本地能跑”等于“CI 能跑”，第三条保证升级可回滚、可二分定位。

> 一句话总结：选型不是挑最好的工具，而是把系统、项目、用户级三条边界钉死并写进文档。

### 39 十二个常见陷阱

下面十二条几乎涵盖了日常遇到的绝大部分依赖问题。格式统一为：现象、原因、怎么办。

#### 1. 锁文件没提交，或与清单不同步

**现象**：本地能跑，CI 或同事机器上装出来的版本不一样。**原因**：清单里的范围约束在不同时间会解析出不同结果；锁文件要么没进版本库，要么改了清单却没重新生成。**怎么办**：把锁文件当源码提交，改完清单立刻重新解析并在同一个 PR 里提交锁文件变化；CI 用冻结模式安装。

#### 2. CI 用 install，本地用 ci（或反过来）

**现象**：CI 上多装/少装包，偶发失败。**原因**：`npm install` 会更新锁文件，`npm ci` 只按锁文件装并拒绝不一致；其他生态的 `install`/`--frozen-lockfile`/`--locked` 也是同一组语义差异。**怎么办**：团队统一一条命令，写进文档和 CI 配置；把不一致交给报错而不是交给运气。

#### 3. 部分升级

**现象**：滚动发行版上装完一个包，桌面或某个程序崩了。**原因**：先刷新索引再单独安装，等于把新旧版本的库混在一个系统里（Arch 的 `pacman -Sy` 后接单包装就是典型）。**怎么办**：永远用一次完整的系统升级（`pacman -Syu`、`zypper dup`），或者用容器隔离新软件。

#### 4. 幻影依赖

**现象**：代码里 `import` 了一个从没在清单里声明过的包，本地正常，换台机器就报找不到。**原因**：扁平化安装或提升把传递依赖摆在了可被解析到的位置。**怎么办**：把它提为直接依赖；用不提升布局的工具（pnpm 的严格结构、Yarn PnP）能从机制上暴露这类问题（见第 6、19 章）。

#### 5. 跨平台锁文件差异

**现象**：只能在某个平台复现的安装失败或依赖缺失。**原因**：可选依赖按平台解析（原生模块、平台专用二进制），不同平台生成或验证锁文件的结果不同；此外换行符与镜像差异也会造成哈希不匹配。**怎么办**：锁文件在 CI 覆盖的全部平台上生成或至少验证；不要把平台专用依赖手工删掉。

#### 6. 用范围版本，却从不升级

**现象**：安全补丁发了半年，项目还在旧版本；某天被迫一次性大升级。**原因**：范围约束只是“允许升级”，不是“会升级”；锁文件把版本钉住后，没人主动更新。**怎么办**：让自动升级工具（Dependabot、Renovate 之类）定期开 PR，小步合并；把升级当常规工作而不是紧急事件。

#### 7. 全局 CLI 与项目依赖版本打架

**现象**：命令行跑的工具行为与项目里配置的不一致，或者两个项目要求不同的工具版本。**原因**：全局安装只有一个版本，且优先于项目内的版本。**怎么办**：项目内工具作为开发依赖声明，通过项目脚本或 `npx`/`uvx` 调用；真正的全局工具只留少数与项目无关的（机制见第 6 章，版本切换见第 32 章）。

#### 8. 混淆版本管理器与包管理器

**现象**：装了新版本的运行时，但包还是装进了旧环境；或者 `python`/`node` 指向的工具与预期不同。**原因**：版本管理器改的是 PATH 与 shim，包管理器装的是包；两者的作用域不一致时，包会落到“另一个”解释器上。**怎么办**：先确认当前解释器路径（`which python`、`node -v` 与 `Get-Command`），再决定用哪个包安装命令；把版本声明文件（`.nvmrc`、`.python-version`）提交到仓库。

#### 9. 镜像与源滞后

**现象**：某个新版本在本地装得到、在另一台机器上“找不到”。**原因**：镜像同步有延迟，企业代理还有缓存过期策略；不同机器配置了不同的源。**怎么办**：统一团队与 CI 的源配置并纳入版本库；发布流程里避免依赖“刚发布几分钟”的版本。

#### 10. 私有源顺序错误

**现象**：内部包名被公网同名包顶替，或装到了非预期的版本。**原因**：源优先级决定了同名包的胜出者，而多数工具默认“先到先得”或合并多个源。**怎么办**：私有源优先并对内部包使用命名空间/作用域；必要时对公网源启用白名单（这是依赖混淆的防线，见第 33、35 章）。

#### 11. 开发依赖混进生产

**现象**：生产镜像或部署包里带着测试框架、构建工具，体积和攻击面同时变大；或者反过来，生产缺了运行必需的包。**原因**：安装时没有区分依赖分组，或在生产环境用了“装全部”的命令。**怎么办**：明确区分运行时依赖与开发依赖，生产安装显式排除开发组（`--no-dev`、`--omit=dev`、`--production`），并在 CI 里验证生产安装能跑起来。

#### 12. 无节制全量升级

**现象**：一次升级几十个主版本，出了问题无法定位是哪一个导致的。**原因**：把升级当成一次性任务批量处理，且缺少测试覆盖作为安全网。**怎么办**：分批升级，优先补丁与小版本；把大版本升级拆成独立 PR；用锁文件回滚作为最后手段。

这十二条的共同点只有一个：**把“可复现”当成了可选项**。可复现不是洁癖，它是你出事之后唯一能用的定位手段。

> 一句话总结：依赖事故几乎都能归到两类——状态没钉死，或者边界没划清。

### 40 结语：包管理器是社会产物

把全文的三十九章压成一句话：包管理器是**在几对无法同时满足的目标之间选位置**的工具。

三对矛盾反复出现：

- **可复现与便利**：锁文件让构建确定，代价是升级必须显式进行；自动升级省心，代价是某天早上依赖变了。
- **集中与分散**：中央仓库降低发现成本、放大单点风险；vendoring 与私有源提升可控性、增加维护面积。
- **信任与效率**：安装脚本让原生扩展开箱即用，同时把宿主权限交给了上游；沙箱与审计把风险压下去，也把成本抬起来。

每个具体工具——apt、pacman、Nix、npm、Cargo、uv、Conan——都只是在这三点之间占了不同的位置。理解了位置，就不需要记住所有命令，也不容易被“某某工具更好”的说法带走。

但包管理器不完全由技术决定。它是**社区治理结构的固化**：

- **谁有权发布**：npm 的命名先到先得、crates.io 的平铺命名、Maven Central 对 groupId 所有权的验证、PyPI 对 2FA 与 Trusted Publishing 的要求，都是治理政策，不是技术必然。
- **谁能撤销**：yank 的权限、撤销后下游如何应对、仓库是否允许覆盖已发布版本——这些规则直接决定了“依赖一个包”这件事的长期风险。
- **谁在维护**：2024 年的 xz 后门事件提醒所有人，被无数系统依赖的项目可能只由一两个人在业余时间维护。维护者倦怠、账号接管、企业消费开源却难以回馈，都是同一结构性问题的一部分。
- **公共资源的拥挤**：包名抢注、占位包、垃圾包、以及为了抢名字而发布的空包，是没有明确产权制度的公共空间的典型症状。

所以，当你在清单文件里写下一行依赖，你做的不只是技术选择。你在给一个具体的维护者、一套治理规则、一条分发链路投票——而这一票的后果，往往在几年之后才显现。

如果这篇文章只留下三句话，我希望是：

1. **把依赖当作负债来管理**，而不是当作资产来收集。每增加一个直接依赖，都增加一份长期的升级、审计与替换成本。
2. **先把可复现性修好**：锁文件提交、CI 冻结安装、镜像按 digest 固定。这三件事能消掉大部分“本地能跑、线上不行”的玄学问题。
3. **理解机制，而不是背命令**。命令会变，机制几乎不变：谁在求解、谁在执行代码、谁在缓存、失败时哪一层在报错。

回到最开始那句话：一台新机器上最先被安装的部件，往往是包管理器。它决定了这台机器几年之后是否还能被干净地重建。选哪一个从来不是最重要的问题，知不知道自己选了什么，才是。

> 一句话总结：工具会换，取舍不换——把依赖当负债管、先把可复现性修好，比记住命令更重要。
